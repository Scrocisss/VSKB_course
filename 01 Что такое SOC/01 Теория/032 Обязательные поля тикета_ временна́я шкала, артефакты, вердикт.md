# Обязательные поля тикета: временна́я шкала, артефакты, вердикт

## Временна́я шкала как основа хронологии инцидента

Временна́я шкала (timeline) — это структурированная хронологическая последовательность событий, составляющих инцидент информационной безопасности. В контексте работы аналитика SOC L1 шкала фиксирует наблюдаемые действия, состояния системы и предпринятые ответные меры с точностью до секунды. Её основная функция — обеспечить однозначную восстановимость картины инцидента для последующего анализа (L2/L3), аудита и отчётности.

С точки зрения аудита SOC 2, временна́я шкала служит доказательством того, что организация среагировала на событие в соответствии с документированным планом реагирования. Критерий CC7.2 (Security Incident Response) требует демонстрации способности обнаруживать и анализировать инциденты, а именно временна́я шкала показывает, **когда** было зафиксировано событие, **как быстро** начато расследование и **в какой момент** выполнены ключевые действия по сдерживанию и устранению. Аудитор, проводящий выборочную проверку тикетов, обращает внимание не только на факт заполнения, но и на логическую связность шкалы: каждое действие должно вытекать из предыдущего, а метки времени — строго следовать друг за другом без разрывов.

### Структура записи временной шкалы

Каждая запись шкалы, как правило, содержит минимальный набор полей:

- **Timestamp** — временна́я метка в UTC (ISO 8601). Единый часовой пояс обязателен, чтобы избежать путаницы при корреляции логов из разных источников.
- **Event** — краткое наименование события, например «Alert triggered», «User login observed», «Malicious process started», «Containment action: network isolation».
- **Source** — источник информации: SIEM (указание правила), EDR, файрвол, почтовый шлюз, ручное действие аналитика.
- **Detail** — дополнительный контекст: учётная запись, IP-адрес, хост, хеш файла, название правила, идентификатор связанного алерта.
- **Action** — если событие представляет собой реактивное действие (containment, escalation), фиксируется кто и что именно сделал. Для простоты именно это поле часто заполняется на уровне L1.

Ниже приведена иллюстративная структура записи шкалы в формате, удобном для помещения в тикет:

```json
{
  "timestamp": "2026-03-12T09:14:32Z",
  "event": "Suspicious email delivered",
  "source": "Email Gateway Log",
  "detail": {
    "sender": "phish@malicious.example",
    "recipient": "user@company.com",
    "subject": "Urgent Invoice",
    "attachment_sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
  },
  "action": "Alert generated by rule EML-001"
}
```

На практике временна́я шкала может быть представлена в виде упорядоченной таблицы непосредственно в теле тикета. Многие тикет-системы (Jira, ServiceNow, TheHive) позволяют встраивать комментарии с автоматической меткой времени, формируя шкалу по мере работы аналитика. Важно, чтобы аналитик не нарушал хронологию: если шкала заполняется после завершения расследования, последовательность должна быть восстановлена по артефактам.

### Методология наполнения шкалы на уровне L1

Аналитик первой линии не обязан проводить глубинный анализ, но должен собрать в шкалу все наблюдаемые события, относящиеся к инциденту. В минимальный набор обычно входят:

1. **Момент срабатывания алерта** — время генерации SIEM-правила или поступления сообщения от EDR.
2. **Первичный осмотр аналитика** — время открытия тикета, проверки источника.
3. **Ключевые наблюдаемые артефакты** — времена запуска процессов (по данным EDR), сетевых соединений, изменения реестра, создания файлов.
4. **Действия по верификации** — запрос репутации IP/домена, проверка VirusTotal, WhoIs (с указанием времени запроса).
5. **Выполненные ответные действия (L1)** — если предусмотрено процедурой: изоляция хоста, сброс пароля (с отметкой времени и исполнителем).

Шкала не должна содержать субъективных оценок вроде «очень подозрительно» — только констатацию зафиксированных фактов с точными временами.

### Инструменты автоматизации

Современные платформы управления инцидентами, такие как [incident.io](https://incident.io/blog/best-incident-management-tools-for-compliance-auditing), автоматически захватывают временные метки действий аналитиков и стыкуют их с логами из интегрированных систем. Тем не менее, в условиях SOC L1 часто используется полуавтоматический подход: алерт из SIEM создаёт тикет с начальной временной точкой, а аналитик дополняет шкалу вручную по мере опроса источников. Важно, чтобы все времена были синхронизированы по NTP; расхождение более чем на 1-2 секунды между логами с разных систем может привести к неверной реконструкции цепочки событий.

### Пример фрагмента временной шкалы в тикете

Ниже показан фрагмент шкалы, который может быть непосредственно вставлен в поле комментария тикета:

```text
[2026-03-12 09:14:32 UTC] Email delivered from phish@malicious.example to user@company.com (src IP 198.51.100.12, SPF fail).
[2026-03-12 09:14:35 UTC] SIEM rule "Phishing_Attachment_Detected" fired (alert ID: AL-45678).
[2026-03-12 09:16:10 UTC] Analyst John.Doe opened ticket #INC-2345, acknowledged alert.
[2026-03-12 09:17:05 UTC] EDR query on host WKST-USER-01: process "invoice_scr.pdf.exe" started at 09:15:22 UTC, PID 3452.
[2026-03-12 09:18:00 UTC] URL query for embedded link hxxp://mal.example/drop: VirusTotal 8/70 detections.
[2026-03-12 09:20:45 UTC] Analyst requested host isolation via EDR console; isolation confirmed at 09:21:12.
```

Такой линейный формат прост для восприятия и удовлетворяет требованиям аудита, демонстрируя прогресс реагирования и обоснованность каждого шага.

### Типичные ошибки при документировании шкалы

- **Отсутствие меток времени для действий аналитика** — создаёт иллюзию, что расследование не проводилось.
- **Использование локального времени без указания зоны** — делает невозможным корреляцию с логами из облачных сервисов.
- **Нарушение порядка записей** — например, событие из лога поставлено после описания ответного действия, которое было предпринято на его основе.
- **Смешение фактов и предположений** — «вероятно, пользователь открыл вложение» вместо «в EDR зафиксирован запуск процесса из временной папки, ассоциированного с почтовым клиентом».

Таким образом, временна́я шкала — не просто формальность, а рабочий инструмент, который в первую очередь дисциплинирует самого аналитика, вынуждая его последовательно фиксировать наблюдаемую картину. При последующей эскалации она становится фундаментом, на котором старшие специалисты строят гипотезы атаки и принимают решение о характере угрозы.

## Артефакты инцидента: сбор и документирование

Артефактами в контексте SOC-тикета называются любые данные и их производные, которые были собраны в ходе расследования и служат доказательной базой для определения характера инцидента. Артефакты включают сырые логи, результаты запросов к SIEM/EDR, хеши файлов, сетевые индикаторы компрометации (IoC), скриншоты, дампы памяти и выдержки из отчётов внешних сервисов (VirusTotal, AbuseIPDB). Требование к обязательному включению артефактов в тикет продиктовано необходимостью воспроизводимости анализа и последующей аудиторской проверки.

Согласно рекомендациям [Black Hills Information Security](https://www.blackhillsinfosec.com/the-formula-for-great-soc-tickets), слабая доказательная база — одна из главных причин возврата тикета на доработку. Внешний аудитор или внутренний контролёр качества должен иметь возможность «перепройти» расследование по оставленным артефактам и прийти к тому же выводу. Именно поэтому артефакты не могут ограничиваться пересказом алерта: требуется первичная информация, с которой работал аналитик.

### Классификация артефактов для SOC L1

В зависимости от типа инцидента аналитик оперирует различным набором артефактов. Укрупнённо их можно разделить на несколько категорий, представленных в таблице:

| Категория артефактов | Типичные примеры | Тип инцидента, где обязательны |
|----------------------|------------------|--------------------------------|
| Сетевые индикаторы | IP-адреса источника/назначения, доменные имена, URL, номера портов | C2-коммуникации, фишинг, вредоносное ПО |
| Файловые индикаторы | Хеши (SHA256, MD5), имена файлов, пути в файловой системе, размер | Вредоносное ПО, подозрительные скрипты |
| Поведенческие артефакты | Командные строки процессов, ключи реестра, запланированные задания, сервисы | Аномальная активность на хосте, privilege escalation |
| Аутентификационные события | Имя пользователя, источник входа (IP, хост), тип аутентификации, результат (успех/неудача) | Компрометация учётной записи, подбор пароля |
| Почтовые метаданные | Email-заголовки, From, Return-Path, SPF/DKIM/DMARC результаты, тема | Фишинг, BEC |
| Результаты внешних проверок | JSON/текстовые отчёты VirusTotal, данные WHOIS, репутация IP из Threat Intelligence Platform | Любой инцидент с внешними IoC |

Источником артефактов служат платформы, интегрированные с SOC: SIEM, EDR, NGFW, почтовые шлюзы, IDS/IPS. Прямой доступ к ним является обязательным условием работы L1.

### Правила документирования артефактов в тикете

При вставке артефакта в тикет необходимо придерживаться нескольких принципов, обеспечивающих целостность и полезность данных:

1. **Цитируемость.** Не пересказывайте содержимое лога своими словами — вставьте его фрагмент как есть (plain text). Используйте fenced code block с указанием источника и времени.
2. **Минимально необходимый контекст.** Если вставлен фрагмент лога, укажите, из какой системы он извлечён, по какому фильтру и в какое время. Это поможет при повторном запросе.
3. **Неизменяемость.** Если тикет-система поддерживает контроль версий, артефакты следует добавлять как вложения или в виде постоянных комментариев. Изменение артефактов задним числом недопустимо.
4. **Хеширование файловых артефактов.** Если в ходе расследования обнаружен подозрительный файл, его хеш (SHA256) должен быть зафиксирован в тикете, даже если сам файл не загружается (например, ссылка на хранилище образцов с контролем доступа). В будущем это позволяет сравнить с новыми образцами.

Следующий пример показывает, как может выглядеть блок артефактов в тикете для инцидента, связанного с вредоносным макросом:

```text
=== Artifacts collected ===

[EDR Process Creation Event]
Timestamp: 2026-03-12T09:15:22Z
Host: WKST-USER-01
Parent Process: winword.exe (PID 2345)
Command Line: "C:\Users\user\AppData\Local\Temp\maldoc.exe"
SHA256: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2
Network connections initiated: 198.51.100.45:443

[Firewall Log]
Timestamp: 2026-03-12T09:15:24Z
Source IP: 10.0.1.15 (WKST-USER-01)
Destination IP: 198.51.100.45
Action: allowed (outbound HTTPS)

[VirusTotal Report]
Query: SHA256 a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2
Detection Ratio: 42/70
Malicious label: Trojan.Downloader.Generic
```

Наличие такой совокупности артефактов позволяет любому, кто просматривает тикет, немедленно оценить обоснованность вердикта, не обращаясь к исходным системам.

### Артефакты как средство от ложных срабатываний

Частая проблема SOC L1 — закрытие тикета как False Positive без достаточных доказательств. Например, аналитик видит алерт на подозрительный сетевой трафик и, обнаружив, что IP-адрес принадлежит известному облачному провайдеру, закрывает инцидент как «трафик к доверенному вендору». Однако, как отмечено в практике [Black Hills Information Security](https://www.blackhillsinfosec.com/the-formula-for-great-soc-tickets), если этот провайдер предоставляет услуги хранения, куда любой может загрузить данные, такой вывод несостоятелен. Чтобы избежать таких ошибок, аналитик обязан зафиксировать артефакты проверки: WHOIS-запись, репутационные данные, ответ от TI-платформы, и только затем аргументировать вердикт.

Фрагмент артефакта WHOIS, вставляемый для подтверждения легитимности адреса, может выглядеть так:

```text
$ whois 203.0.113.10
...
NetName:        CLOUD-PROVIDER-NET
OrgName:        Example Cloud, Inc.
...
```

Но этого недостаточно — дополнительно требуется проверить, не используется ли данный IP в отчётах о фишинге, и вставить ответ AbuseIPDB или аналогичного сервиса.

### Связь артефактов с другими полями тикета

Артефакты не существуют изолированно: они обязательно упоминаются во временной шкале (каждое событие маркируется источником-артефактом) и являются фундаментом для вердикта. Таким образом, в идеальном тикете выстраивается трёхкомпонентная система:

- временна́я шкала (когда и что произошло);
- артефакты (первичное доказательство каждого пункта шкалы);
- вердикт (аналитическое заключение на основе артефактов и шкалы).

Аналитик L1 должен мыслить в этой парадигме при работе с любым алертом: без чётко зафиксированных артефактов временна́я шкала превращается в бездоказательный пересказ, а вердикт — в субъективное мнение.

## Вердикт: классификация и обоснование результата расследования

Вердикт — это формализованное заключение аналитика SOC L1 по результатам первичного расследования инцидента. В отличие от временной шкалы и артефактов, которые фиксируют объективные данные, вердикт представляет собой экспертную оценку на основе этих данных. Он определяет, является ли наблюдаемая активность злонамеренной, ошибочной или допустимой, и задаёт дальнейший сценарий обработки тикета (закрытие или эскалация). Корректно сформулированный вердикт служит связующим звеном между фактами и организационными решениями и является объектом пристального внимания при аудите инцидентов.

Согласно требованиям SOC 2 и общим принципам управления инцидентами, вердикт должен быть:

- **Конкретным** — категория инцидента (True Positive, False Positive, Benign, Escalated) без двусмысленности;
- **Обоснованным** — опираться на артефакты и временную шкалу, а не на предположения;
- **Воспроизводимым** — другой аналитик, имея тот же набор артефактов, должен прийти к аналогичному выводу.

Тикет с вердиктом вроде «похоже на ложняк» является прямым кандидатом на доработку и может привести к неудовлетворительным результатам аудита.

### Типология вердиктов SOC L1

В большинстве зрелых SOC принята следующая классификация результатов первичного анализа:

- **True Positive (TP)** — инцидент подтверждён, активность является вредоносной или несанкционированной, существует реальный ущерб или потенциальная угроза. Обычно требует немедленной эскалации на L2/L3.
- **False Positive (FP)** — алерт сработал на легитимную активность, которая не несёт угрозы. После документирования причин тикет закрывается.
- **Benign True Positive (BTP)** или **Informational** — активность действительно подпадает под сигнатуру правила, но является разрешённой или ожидаемой в контексте организации (например, тестирование безопасности, автоматизированные скрипты легитимного ПО). В отличие от FP, здесь событие соответствует критериям алерта, но контекст делает его безопасным. Требуется настройка исключений или пересмотр правила, но инцидента как такового нет.
- **Undetermined / Insufficient Data** — у аналитика недостаточно данных для принятия решения; требуется дополнительное расследование (эскалация с пометкой о необходимости сбора дополнительных артефактов).
- **Escalated** — не столько тип вердикта, сколько статус: аналитик L1 подтверждает подозрительный характер и передаёт тикет на дальнейший анализ.

Каждая из этих категорий предписывает определённый набор действий: закрытие, эскалацию, запрос уточнений или передачу в смежные отделы (например, администраторам для отключения учётной записи).

### Структура поля вердикта в тикете

Вердикт не должен ограничиваться одним словом. Обычно он включает:

1. **Категорию** (True Positive, False Positive и т.д.).
2. **Уровень уверенности** (Confidence): High, Medium, Low — оценка степени убеждённости аналитика в правильности вывода. Полезна для приоритизации эскалированных тикетов.
3. **Краткое обоснование** (Rationale) — 2–5 предложений, связывающих артефакты с выводом. Здесь допустимо ссылаться на пункты временной шкалы или конкретные IoC.
4. **Рекомендуемые действия** (Recommended Actions) — что должно произойти дальше: эскалация на L2, изоляция хоста, уведомление владельца актива, закрытие тикета с настройкой suppression rules.

Пример оформления вердикта в виде структурированного JSON-фрагмента, вставляемого в комментарий тикета:

```json
{
  "verdict": "True Positive",
  "confidence": "High",
  "rationale": "Observed outbound connection from user workstation to a known C2 IP (198.51.100.45) that is listed in multiple threat intel feeds. Process maldoc.exe was spawned by winword.exe, indicating a successful malicious macro execution. File hash flagged by 42/70 vendors on VirusTotal.",
  "recommended_actions": [
    "Escalate to L2 for full containment and forensic analysis.",
    "Isolate affected host WKST-USER-01 (if not already done).",
    "Block destination IP at firewall level.",
    "Initiate credential reset for user account 'user'."
  ]
}
```

В средах, где тикет-система не поддерживает JSON, используется текстовый блок с аналогичным содержанием.

### Обоснование False Positive и Benign

Наибольшее количество ошибок SOC L1 связано с неправильной классификацией ложных срабатываний. Аналитик должен явно указать, почему событие признано безопасным. Простое указание «FP, потому что пользователь так обычно делает» неприемлемо. Вместо этого необходимо привести контекст: например, связь с легитимным бизнес-приложением, подтверждённая администратором, или точное совпадение с ранее описанным разрешённым поведением, зафиксированным в базе знаний SOC.

Пример обоснованного вердикта False Positive:

```text
Verdict: False Positive
Confidence: High
Rationale: The alert was triggered due to a DNS query to domain 'update.legitsoftware.com'. Review of internal asset management shows the domain belongs to an approved patch management tool used by IT. Historical logs indicate the same activity from this host at the same time daily for the past 30 days, correlating with the update schedule. No other malicious indicators present.
Recommended action: Close ticket. Recommend adding domain to SIEM whitelist for rule DNS-SUSP-001.
```

Здесь видно, как артефакты (логи DNS, asset management) и временна́я составляющая (история за 30 дней) формируют объективную базу для вердикта.

### Связь вердикта с SLA и аудитом

Для SOC, работающих по соглашениям об уровне обслуживания (SLA), вердикт напрямую влияет на метрики: время до вердикта (Time to Verdict) является частью MTTD (Mean Time to Detect) или TTD (Time to Detect). Аудиторы, проверяющие тикеты в рамках SOC 2 Type II, ожидают, что каждый закрытый или эскалированный тикет содержит вердикт с обоснованием; отсутствие обоснования расценивается как неспособность организации последовательно применять процедуры реагирования. Поэтому вердикт — не просто техническая оценка, а элемент доказательной базы зрелости процессов.

В рабочем процессе L1 вердикт, как правило, является финальной точкой работы над тикетом перед передачей на следующий уровень или закрытием. Ответственность за его полноту несёт непосредственно аналитик, и автоматизированный контроль качества часто проверяет наличие и непустоту поля заключения в тикете.

## Сквозной практический пример: расследование фишингового инцидента и заполнение тикета SOC L1

### Исходные условия

Среда: корпоративная сеть с SIEM Microsoft Sentinel, EDR Microsoft Defender for Endpoint, почтовый шлюз Proofpoint. Аналитик первой линии получает алерт о срабатывании правила «Potential Phishing Email with Malicious Attachment». Алерт содержит ID инцидента, временную метку, идентификаторы получателя и отправителя. Роль аналитика — провести первичное расследование, собрать временную шкалу, артефакты, вынести вердикт и при необходимости эскалировать. Тикет ведётся в ServiceNow.

**Цель: продемонстрировать, как на каждом шаге формируются обязательные поля тикета.**

### Шаг 1. Открытие тикета и фиксация начальной временной метки

Аналитик открывает тикет #INC-56789 из панели SIEM. Первое действие — зафиксировать в шкале момент создания и параметры алерта.

```text
[2026-03-12 09:14:35 UTC] SIEM Alert "Potential Phishing Email with Malicious Attachment" triggered (Rule: EML-Phish-02).
[2026-03-12 09:16:20 UTC] Analyst Jane.Smith acknowledged alert and created ticket INC-56789.
```

Эти строки становятся первыми записями в поле «Timeline» тикета.

### Шаг 2. Сбор артефактов из почтового шлюза и анализ вложения

Аналитик запрашивает детали сообщения из Proofpoint и получает заголовки письма. Из них извлекаются ключевые артефакты: отправитель, получатель, SPF/DKIM статус, тема, хеш вложения. Также через консоль EDR запрашиваются события доставки email и запуска процессов на хосте получателя. Команда в KQL (Microsoft Sentinel) и её вывод:

```kql
EmailEvents
| where RecipientEmailAddress == "user@company.com"
| where Timestamp >= datetime(2026-03-12T09:10:00Z)
| project Timestamp, SenderFromAddress, Subject, AttachmentCount, ThreatTypes, NetworkMessageId
```

Вывод (иллюстративная схема):

```text
Timestamp: 2026-03-12T09:14:32Z
Sender: phish@malicious.example
Subject: "Urgent Invoice"
AttachmentCount: 1
ThreatTypes: ["Malware"]
NetworkMessageId: <d686f4-34aa-...>
```

Эти данные помещаются в раздел «Artifacts» тикета с комментарием об источнике.

Отдельно аналитик извлекает SHA256 вложения из EDR-записи создания файла на хосте:

```kql
DeviceFileEvents
| where DeviceName == "WKST-USER-01"
| where InitiatingProcessAccountName == "user"
| where Timestamp between (datetime(2026-03-12T09:14:00) .. datetime(2026-03-12T09:20:00))
| where FileName endswith ".pdf.exe"
| project Timestamp, FolderPath, SHA256
```

Вывод:

```text
Timestamp: 2026-03-12T09:15:15Z
FolderPath: C:\Users\user\AppData\Local\Temp\invoice_scr.pdf.exe
SHA256: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2
```

Результат запроса VirusTotal по этому хешу также помещается в артефакты (можно вставить JSON-ответ платформы или сводку детектов).

### Шаг 3. Формирование временной шкалы на основе собранных данных

Объединив данные из SIEM, EDR и почтового шлюза, аналитик строит целостную временную шкалу и вносит её в тикет:

```text
[2026-03-12 09:14:32 UTC] Proofpoint: email from phish@malicious.example delivered to user@company.com with attachment invoice_scr.pdf.exe.
[2026-03-12 09:14:35 UTC] SIEM: alert generated (Rule: EML-Phish-02).
[2026-03-12 09:14:50 UTC] EDR: email client outlook.exe downloads attachment to temp folder (C:\Users\user\AppData\Local\Temp\invoice_scr.pdf.exe).
[2026-03-12 09:15:12 UTC] EDR: user double-clicks attachment; process invoice_scr.pdf.exe spawned by explorer.exe.
[2026-03-12 09:15:22 UTC] EDR: new process maldoc.exe launched from dropped file, PID 3452.
[2026-03-12 09:15:24 UTC] Network: outbound HTTPS connection from host WKST-USER-01 to 198.51.100.45:443 (C2 communication).
[2026-03-12 09:16:20 UTC] Analyst Jane.Smith started investigation.
[2026-03-12 09:18:30 UTC] Analyst collected artifacts: email headers, file hash, network connection log.
[2026-03-12 09:20:00 UTC] Analyst verified file hash on VirusTotal: 42/70 detections, labeled Trojan.Downloader.
[2026-03-12 09:22:10 UTC] Analyst initiated host isolation via Defender for Endpoint; confirmation received.
```

### Шаг 4. Вынесение вердикта и эскалация

Основываясь на шкале и артефактах, аналитик классифицирует инцидент как True Positive с высокой степенью уверенности и формирует вердикт, вставляя его в соответствующее поле тикета:

```json
{
  "verdict": "True Positive",
  "confidence": "High",
  "rationale": "Phishing email with malicious attachment successfully delivered and executed on host. Observed process chain (PDF icon exe -> maldoc.exe) and immediate C2 connection to a known malicious IP. File hash detected by numerous engines. No legitimate business context for this activity.",
  "recommended_actions": [
    "Escalate to L2 for full forensic investigation and threat hunting.",
    "Block destination IP 198.51.100.45 at perimeter firewall.",
    "Reset credentials for user account 'user'.",
    "Consider reimaging affected workstation."
  ]
}
```

Вердикт вместе с временной шкалой и артефактами образуют целостный пакет, готовый для передачи на L2.

### Ожидаемый вывод примера

Данный сквозной кейс демонстрирует, как последовательная работа с тремя обязательными полями тикета (временна́я шкала, артефакты, вердикт) превращает формальный алерт в структурированный и аудируемый документ. Аналитик L1 не просто фиксирует факт срабатывания, а воссоздаёт хронологию атаки, подкрепляет её объективными доказательствами и даёт обоснованную экспертную оценку. Именно такой подход позволяет SOC удовлетворять требованиям стандартов (SOC 2 CC7.2, CC7.3) и обеспечивать качество реагирования на инциденты. Тикет, сформированный по этим правилам, может быть передан как для оперативного реагирования, так и для последующей аудиторской проверки без дополнительной доработки.
