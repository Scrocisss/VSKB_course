# Формат записи audit.log и интерпретация полей

## 1. Роль и место audit.log в инфраструктуре аудита Linux

Linux Audit Framework — это встроенная подсистема ядра, регистрирующая события на уровне системных вызовов, обращений к файлам, действий пользователей и изменений конфигурации. Центральным компонентом выступает демон `auditd`, который получает записи от ядерного аудита и фиксирует их в файл `/var/log/audit/audit.log`. В отличие от традиционных логов приложений, audit.log отражает события, невидимые для стандартного syslog, и служит основой для расследований инцидентов, контроля целостности и соблюдения регуляторных требований (PCI-DSS, HIPAA).

Три ключевых компонента образуют экосистему журналирования:
*   **Kernel audit subsystem** перехватывает системные вызовы и другие типы событий, помеченные правилами аудита.
*   **Auditd daemon** управляет журналированием: принимает события из ядра через netlink-сокет, записывает их в audit.log, выполняет ротацию и опционально отправляет агрегированные данные во внешние системы.
*   **Audit rules** определяют, что именно регистрируется: конкретные файлы (`-w`), системные вызовы (`-a`), пользователи или типы событий. Правила загружаются утилитой `auditctl` или описываются в `/etc/audit/rules.d/`.

Записи audit.log отличаются от сообщений, попадающих в `/var/log/messages`, `/var/log/auth.log` или `wtmp`, как по источнику, так и по внутренней организации. Приведённая ниже таблица систематизирует эти различия.

| Характеристика | audit.log | syslog / auth.log |
|----------------|-----------|-------------------|
| **Источник данных** | Системные вызовы и хуки ядра, аудит-события пространства пользователя (например, LOGIN). | Приложения, демоны (sshd, cron, sudo) через syslog(3) или journald. |
| **Инициируется** | Правилами аудита, заданными администратором (auditctl, rules.d). | Вызовами функций логирования внутри программного кода. |
| **Защита от подмены** | Журнал защищён самой подсистемой аудита (активность auditd логируется отдельно, удаление записей требует привилегий и генерирует события). | Легче подделать; при компрометации процесса можно фальсифицировать сообщения. |
| **Формат** | Жёстко заданная последовательность пар `key=value`; каждая строка — самостоятельная запись с префиксом `type=`. | Произвольный текст с временной меткой, именем хоста и процессом; структура не унифицирована. |
| **Детализация** | Точные значения аргументов системных вызовов, идентификаторы пользователей (реальный, эффективный, аудиторский), метаданные файлов, SELinux-контекст. | Как правило, только факт события и идентификатор пользователя. |
| **Пример записи** | `type=SYSCALL msg=audit(1364481363.243:24287): arch=c000003e syscall=2 success=no ...` | `Jul 10 10:15:30 host sshd[1234]: Accepted password for root from ...` |

Базовой единицей audit.log является **запись (record)** — одна строка, начинающаяся с `type=...` и описывающая определённый аспект события. Несколько записей, имеющих одинаковую временную метку и идентификатор события в поле `msg`, образуют одно **событие аудита (audit event)**. Например, попытка открытия файла порождает записи типов `SYSCALL`, `PATH`, `CWD` и, возможно, `PROCTITLE` — все с совпадающим `msg=audit(epoch:\ID)`. Понимание этой мультистрочной природы критически важно для анализа, поскольку одиночная строка даёт лишь часть контекста.

Для SOC-аналитика audit.log выступает первичным источником информации о низкоуровневых действиях: кто, с какими привилегиями, каким процессом и к какому файлу обращался, исполнял ли программу, менял ли права доступа. Умение читать и интерпретировать поля записи позволяет быстро выявлять аномалии — от попыток эскалации привилегий до скрытого выполнения вредоносного кода.

## 2. Анатомия записи: синтаксис, структура и ключевые компоненты

Запись audit.log подчиняется общей схеме:
```
type=<ТИП_СОБЫТИЯ> msg=audit(<epoch>.<миллисекунды>:<ID>): <поле1>=<знач> <поле2>=<знач> … [полеN=<знач>]
```
Необязательный префикс `node=<имя_хоста>` может предшествовать `type=`. Значения разделяются пробелом или запятой, хотя в некоторых устаревших типах записей (например, `DAEMON_START`) встречаются отступления — текстовая строка без формата `key=value`, а между токенами могут присутствовать запятая плюс пробел. Спецификация из документации Red Hat (см. [Red Hat Security Guide](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/7/html/security_guide/sec-understanding_audit_log_files)) подчёркивает, что основной синтаксис — пары `имя=значение`, но на практике парсер должен быть готов к обработке исключений.

Рассмотрим подробно типичную запись, взяв за основу событие неудачного доступа к файлу из руководства Red Hat:
```
type=SYSCALL msg=audit(1364481363.243:24287): arch=c000003e syscall=2 success=no exit=-13 a0=7fffd19c5592 a1=0 a2=7fffd19c4b50 a3=a items=1 ppid=2686 pid=3538 auid=1000 uid=1000 gid=1000 euid=1000 suid=1000 fsuid=1000 egid=1000 sgid=1000 fsgid=1000 tty=pts0 ses=1 comm="cat" exe="/bin/cat" key="sshd_config"
```
Компоненты — **type**, **msg**, **атрибуты события** — раскрываются далее с помощью сводной таблицы полей.

### Обязательное поле `msg`
Формат: `audit(<timestamp>:<event_id>)`.  
- `timestamp` — время возникновения события в секундах от начала эпохи Unix (можно преобразовать через `date -d @<значение>`). Дробная часть указывает миллисекунды.  
- `event_id` — серийный номер, уникальный в рамках одного события: все записи, порождённые одним системным вызовом (или иным действием), разделяют этот номер. Абсолютная уникальность на длительных промежутках не гарантируется; при длительной работе аудита возможны повторения, поэтому для надёжной идентификации рекомендуется сочетать ID с ключом правила (`key`) или временной меткой.

### Систематический обзор ключевых полей записи

Ниже представлены поля, встречающиеся в большинстве событий (в первую очередь типа `SYSCALL`). Таблица служит структурной основой для интерпретации.

| Поле | Описание | Пример значения | Интерпретация |
|------|----------|-----------------|---------------|
| `type` | Тип записи. Всегда первый элемент. | `SYSCALL`, `PATH`, `CWD`, `PROCTITLE`, `DAEMON_START` и др. | Определяет, какие поля следуют дальше и смысл записи. |
| `msg` | Временная метка и идентификатор события. | `audit(1364481363.243:24287)` | 1364481363.243 секунд от Unix epoch; ID события 24287. |
| `arch` | Архитектура CPU (hex). | `c000003e` | После интерпретации: `x86_64` (`ausearch -i` или таблица). |
| `syscall` | Номер системного вызова. | `2` | `open` (см. `/usr/include/asm/unistd_64.h` или `ausyscall`). |
| `success` | Успех или провал системного вызова. | `no` / `yes` | `no` — вызов вернул ошибку. |
| `exit` | Код возврата вызова (dec). | `-13` | `-EACCES` (Permission denied). |
| `a0` … `a3` | Первые 4 аргумента системного вызова (hex). | `a0=7fffd19c5592` (указатель на строку пути) | Интерпретация строго зависит от syscall; `ausearch -i` отображает их в читаемом виде. |
| `items` | Количество `PATH`-записей, ассоциированных с данным `SYSCALL`. | `1` | Запись типа `PATH` с `item=0` идёт следующей. |
| `ppid` | PID родительского процесса. | `2686` | Позволяет восстановить дерево процессов. |
| `pid` | PID текущего процесса. | `3538` | Идентификатор процесса, совершившего вызов. |
| `uid`, `euid`, `suid`, `fsuid` | Пользовательские идентификаторы (реальный, эффективный, сохранённый, файловой системы). | `uid=1000 euid=1000` | Если `euid≠uid`, процесс работает с повышенными привилегиями (suid-программа). |
| `gid`, `egid`, `sgid`, `fsgid` | Аналогичные групповые идентификаторы. | `gid=1000 egid=1000` | Анализ смены группы. |
| `auid` | Аудиторский идентификатор — пользователь, вошедший в систему (login UID). | `1000` | Не меняется после `su`/`sudo`; ключевое поле для расследования. |
| `ses` | Идентификатор сессии. | `1` | Позволяет объединить события в рамках одного входа. |
| `tty` | Терминал, с которого производился вызов. | `pts0` | Может быть пустым для демонов. |
| `comm` | Имя команды (из `/proc/pid/comm`). | `"cat"` | Не обязательно совпадает с именем исполняемого файла. |
| `exe` | Полный путь к исполняемому файлу. | `"/bin/cat"` | Важнейший индикатор запущенной программы. |
| `key` | Метка, заданная в правиле аудита (`-k`). | `"sshd_config"` | Упрощает поиск связанных событий. |

### Дополнительные типы записей в составе события

*   **PATH** сопровождает системные вызовы, взаимодействующие с файловой системой. Содержит поля:  
    *   `item` — номер элемента (начинается с 0), соответствует числу `items` в SYSCALL.  
    *   `name` — абсолютный путь к файлу.  
    *   `inode`, `dev` — идентификаторы файловой системы.  
    *   `mode` — права доступа в восьмеричном формате (например, `0100600`).  
    *   `ouid`, `ogid` — владельцы файла.  
    *   `obj` — SELinux-контекст объекта.  
    *   `objtype` — `NORMAL` для целевого файла, `PARENT` для родительского каталога.  
*   **CWD** фиксирует текущий рабочий каталог процесса: `cwd="/home/shadowman"`.  
*   **PROCTITLE** хранит аргументы командной строки в шестнадцатеричном представлении (поле `proctitle`). Декодируется утилитой `xxd`.

Запись **DAEMON_START** демонстрирует нестандартный синтаксис: после `msg=audit(...)` вместо пар `key=value` следует текст `auditd start, ver=2.4 format=raw kernel=3.16.0-4-586 ...`. Эта особенность объясняется историческим форматом сообщений демона и должна учитываться при написании парсеров — после префикса `msg` может идти свободный текст, который интерпретируется только знанием конкретного типа записи.

Также в начале строки может присутствовать `node=hostname1`. Это опциональный элемент, добавляемый при агрегации логов с нескольких узлов; локальные записи обычно его не содержат.

Таким образом, каждая запись представляет собой жёстко типизированный контейнер с самодостаточным описанием одного аспекта события, а совокупность записей, объединённых общей меткой времени и ID, формирует полную картину действия.

## 3. Интерпретация полей: от машинных идентификаторов к человеческому анализу

Сырые значения, записанные в audit.log, редко пригодны для немедленного восприятия. Задача аналитика — преобразовать числовые коды, временные метки и битовые маски в осмысленные индикаторы. Все необходимые механизмы предоставляются штатными утилитами пакета `audit` и стандартными средствами Linux.

### Преобразование временной метки

Поле `msg` несёт метку в формате epoch-секунд с миллисекундами. Быстрая конвертация в читаемый вид:
```bash
date -d @1364481363 '+%Y-%m-%d %H:%M:%S'
```
Пример вывода: `2013-03-28 14:16:03`.

Для повседневной работы удобнее применять `ausearch` с опцией `-i` (или `--interpret`), которая автоматически преобразует временные метки во всех полях:
```bash
ausearch -k sshd_config -i
```
Вывод будет содержать строку вида `msg=audit(01/23/2013 14:16:03.243:24287)`.

### Интерпретация системного вызова и аргументов

Номер системного вызова (`syscall=2`) можно сопоставить с именем при помощи утилиты `ausyscall`:
```bash
ausyscall 2
```
Ожидаемый вывод: `open`.  
Полный список доступен по `ausyscall --dump`.

Архитектура процессора (`arch=c000003e`) при использовании `ausearch -i` отображается как `x86_64`. Без ключа интерпретации можно свериться с заголовочными файлами ядра, но на практике встроенный механизм надёжен.

Аргументы системного вызова (`a0`…`a3`) специфичны для каждого вызова. В примере с `open`: `a0` — указатель на строку пути, `a1` — флаги доступа (`0` в случае `open` с флагами `O_RDONLY`), `a2` — права при создании файла. `ausearch -i` пытается их декодировать; ручной разбор требует знания сигнатур системных вызовов.

Код возврата `exit` интерпретируется опцией `--interpret --exit`:
```bash
ausearch --interpret --exit -13
```
Если в логе присутствует событие с таким кодом, `ausearch` добавит символьное обозначение: `exit=-13(EACCES)`.

### Идентификация пользователя: цепочка учётных идентификаторов

Особое внимание при анализе следует уделять паре `auid` и `uid` (а также `euid`).
- **`auid`** (audit user ID) устанавливается при входе пользователя в систему и не изменяется при вызовах `su`, `sudo`, `pkexec`. Значение `4294967295` (или `-1`) соответствует «неустановленному» аудиторскому ID, что характерно для системных процессов, стартующих до инициализации аудита.
- **`uid`** — реальный идентификатор владельца процесса.
- **`euid`** — эффективный идентификатор, определяющий права доступа в момент вызова.

Расхождение между `uid` и `euid` указывает на выполнение SUID-программы. Если `auid` отличается от `uid` при интерактивной сессии, это свидетельствует о смене пользователя (`su`). Таким образом, аудиторский ID позволяет точно связать действие с исходным пользователем даже после горизонтального перемещения.

### Декодирование строки PROCTITLE

Поле `proctitle` в записи типа `PROCTITLE` содержит полную командную строку, закодированную в hex (аргументы разделены нулевыми байтами). Декодирование выполняется через `xxd`:
```bash
echo "636174002F6574632F7373682F737368645F636F6E666967" | xxd -r -p | tr '\0' ' '
```
Результат: `cat /etc/ssh/sshd_config`. В реальных логах шестнадцатеричная строка длиннее, но принцип тот же. Утилита `ausearch -i` также раскодирует это поле.

### Анализ PATH-записей

Запись `PATH` предоставляет детализированную информацию о файле, с которым взаимодействовал процесс.
- `name` — путь.
- `mode=0100600` интерпретируется как права доступа: владелец может читать и писать (`0600`), бит `0100000` — обычный файл.
- `ouid=0` — владелец root.
- `obj=system_u:object_r:etc_t:s0` — SELinux-контекст.

Сопоставляя `uid` процесса с `ouid` файла, можно сразу сделать вывод о причине отказа в доступе: у пользователя shadowman (uid=1000) нет прав на чтение файла, принадлежащего root (ouid=0). Это видно и по `exit=-13(EACCES)`.

### Обработка исключений

При разборе записей, подобных `DAEMON_START`, парсеру необходимо реализовать условную логику: после извлечения `type` и `msg` анализируется тип, и для известных неструктурированных типов остаток строки обрабатывается как произвольное сообщение. В SIEM-системах для таких записей создают отдельные правила экстракции, извлекая версию демона и другие параметры с помощью регулярных выражений.

### Инструментарий для планового анализа

Помимо `ausearch` для ad-hoc поиска и `aureport` для построения сводок (например, `aureport --failed` — все неудачные события), аналитики нередко пишут скрипты на Python, использующие библиотеку `auparse` из пакета `audit-libs-python`. При интеграции с SIEM (Splunk, ELK, Sumo Logic) данные audit.log парсятся на лету с применением регулярок, которые должны учитывать описанные выше вариации формата.

## 4. Группировка записей: восстановление полного события

Одиночная строка `audit.log` редко представляет собой законченный инцидент. Событие аудита, инициированное системным вызовом или внутренним действием демона, обычно состоит из нескольких записей, объединённых общим идентификатором в поле `msg` — `<epoch>:<ID>`. Умение корректно собирать эти фрагменты является обязательным навыком для любого специалиста, работающего с журналом аудита.

### Принцип мультистрочной группировки

Все записи, относящиеся к одному событию, разделяют одинаковый кортеж (временная метка, event ID). Рассмотренный ранее пример включает три записи (SYSCALL, PATH, PROCTITLE) и, возможно, CWD. В документации Red Hat прямо указано, что SYSCALL является заглавным типом для большинства системно-вызванных событий, а поле `items` задаёт количество последующих PATH-записей. Это позволяет построить детерминированную процедуру сборки:
1. Найти запись типа `SYSCALL` с интересующим ID.
2. Прочитать значение `items` (например, `items=1`).
3. Извлечь ровно N записей `PATH`, следующих за данной SYSCALL (обычно они идут в порядке возрастания поля `item`).
4. Дополнительно могут присутствовать записи `CWD` и `PROCTITLE` (последняя часто завершает группу).

Другие типы событий могут порождать иные комбинации. Ниже представлены характерные шаблоны, встречающиеся в повседневной практике.

### Типовые комбинации записей для различных сценариев

| Действие | Типовая последовательность записей | Примечание |
|----------|-----------------------------------|------------|
| Открытие файла (open) | SYSCALL (syscall=open), PATH (item=0, objtype=NORMAL), CWD | Если флаги включают O_CREAT, добавляется PATH с objtype=PARENT для родительского каталога; items становится равным 2. |
| Создание нового файла (creat) | SYSCALL (syscall=creat), PATH (создаваемый файл), PATH (родительский каталог, objtype=PARENT), CWD | items=2. |
| Запуск программы (execve) | SYSCALL (syscall=59 или execve), PATH (исполняемый файл), CWD, PROCTITLE | items=1. Важно декодировать PROCTITLE для получения аргументов. |
| Сетевой вызов (connect, bind) | SYSCALL (syscall=connect без PATH, поля a содержат struct sockaddr) | items=0, отдельные PATH отсутствуют. Адресная информация восстанавливается из аргументов вызова. |
| Аутентификация (USER_AUTH, USER_LOGIN) | USER_AUTH или USER_LOGIN (одиночная запись) | Не группируются с SYSCALL. Содержат поля `acct`, `hostname`, `terminal`. |
| Мониторинг демона (DAEMON_START, DAEMON_END) | DAEMON_START (или END) — одиночная запись | Как обсуждалось, формат отличается. |
| Конфигурационные изменения (CONFIG_CHANGE) | CONFIG_CHANGE (обычно одна запись) | Фиксирует добавление/удаление правил аудита. |

### Схема группировки на примере

```text
Событие ID=24287 (execve /bin/cat /etc/ssh/sshd_config):
┌─────────────┐   ┌─────────────────────┐   ┌──────────────┐   ┌──────────────────────────────────┐
│ type=SYSCALL │──▶│ type=PATH            │──▶│ type=CWD     │──▶│ type=PROCTITLE                   │
│ syscall=59   │   │ name="/bin/cat"      │   │ cwd="/root"  │   │ proctitle=636174002F657463...     │
│ items=1      │   │ objtype=NORMAL       │   │              │   │ (декодируется как "cat /etc/...")│
└─────────────┘   └─────────────────────┘   └──────────────┘   └──────────────────────────────────┘
       ▲
       │
  Заглавная запись; items=1 указывает, что далее идёт ровно одна PATH.
```

Когда логи агрегируются с нескольких машин, поле `node=` помогает разделить идентичные ID, возникшие на разных хостах.

### Практические рекомендации для использования в SOC

В SIEM-решениях (Splunk, Elastic) и облачных сервисах (Sumo Logic) группировку реализуют через регулярные выражения. Опорой служит выражение, захватывающее `msg=audit(` и извлекающее временную метку с идентификатором. Многострочное объединение обычно настраивают по совпадению этого шаблона. В Splunk, например, параметр `SHOULD_LINEMERGE = False` с явно заданным regex `audit\(\d+\.\d+:\d+\)` обеспечивает корректное разбиение на события. После группировки аналитик может строить корреляции: последовательность из нескольких SYSCALL-событий от одного пользователя с неудачными попытками доступа к критическим файлам с последующим `CONFIG_CHANGE` может свидетельствовать об атаке.

Корректная интерпретация группировки позволяет избежать классической ошибки — реагирования на одиночную PATH-запись без контекста, который даёт SYSCALL-запись (кто, с каким результатом и зачем).

## Сквозной практический пример: расследование неудачного доступа к /etc/ssh/sshd_config

**Исходные условия.** Сервер RHEL 7 с запущенным auditd; в правилах присутствует мониторинг файла `/etc/ssh/sshd_config` с меткой `sshd_config`:
```
-w /etc/ssh/sshd_config -p warx -k sshd_config
```
SOC-аналитик получает оповещение от SIEM о всплеске событий с `key=sshd_config` и `success=no` от непривилегированного пользователя. Задача: идентифицировать пользователя, процесс и обстоятельства попытки доступа.

**Шаг 1. Извлечение всех событий с заданным ключом за последние 10 минут.**
```bash
ausearch -k sshd_config --start recent -i
```
Вывод представляет собой набор сгруппированных событий. Аналитик выбирает подозрительный ID `24287`.

**Шаг 2. Получение полного события по ID.**
```bash
ausearch -k sshd_config -i -e 24287
```
Примерный вывод (адаптирован из документации Red Hat):
```
----
type=SYSCALL msg=audit(01/23/2013 14:16:03.243:24287) : arch=x86_64 syscall=open success=no exit=-13(EACCES) a0=0x7fffd19c5592 a1=0 a2=0x7fffd19c4b50 a3=0xa items=1 ppid=2686 pid=3538 auid=shadowman uid=shadowman gid=shadowman euid=shadowman suid=shadowman fsuid=shadowman egid=shadowman sgid=shadowman fsgid=shadowman tty=pts0 ses=1 comm=cat exe=/bin/cat key=sshd_config
type=CWD msg=audit(01/23/2013 14:16:03.243:24287) : cwd="/home/shadowman"
type=PATH msg=audit(01/23/2013 14:16:03.243:24287) : item=0 name="/etc/ssh/sshd_config" inode=409248 dev=fd:00 mode=0100600 ouid=0 ogid=0 rdev=00:00 obj=system_u:object_r:etc_t:s0 objtype=NORMAL cap_fp=none cap_fi=none cap_fe=0 cap_fver=0
type=PROCTITLE msg=audit(01/23/2013 14:16:03.243:24287) : proctitle=636174002F6574632F7373682F737368645F636F6E666967
```

**Шаг 3. Интерпретация и ручное декодирование аргументов.**
Из поля `proctitle` получаем шестнадцатеричную строку:
```bash
echo "636174002F6574632F7373682F737368645F636F6E666967" | xxd -r -p | tr '\0' ' '
```
Результат:
```
cat /etc/ssh/sshd_config
```
Проверяем код возврата и системный вызов:
```bash
ausyscall 2
```
Вывод: `open` — действительно, событие вызвано системным вызовом открытия файла.

**Шаг 4. Анализ контекста и формирование вывода.**
Сводка ключевых полей:
- **Пользователь:** auid=shadowman (аудиторский ID), uid=shadowman. Пользователь не менял учётную запись.
- **Процесс:** `comm=cat`, `exe=/bin/cat`, родительский процесс ppid=2686 (можно дополнительно проверить по журналу).
- **Объект:** `/etc/ssh/sshd_config`, владелец root (ouid=0), права `0600` (чтение/запись только владельцу).
- **Результат:** `success=no`, `exit=-13 (EACCES)`. Ядро запретило открытие из-за недостаточности прав.
- **Текущий каталог:** `/home/shadowman`.

Вывод: пользователь `shadowman`, находясь в своей домашней директории, выполнил команду `cat /etc/ssh/sshd_config` из оболочки `pts0` в сеансе `ses=1`. Попытка чтения конфигурационного файла SSH, принадлежащего root, была блокирована на уровне системного вызова. Инцидент может указывать на действия любопытствующего пользователя либо на начальную стадию разведки перед атакой. Рекомендуется провести беседу с пользователем, проверить соседние события в рамках той же сессии (по аудит ID 24287 и соседним ID) на предмет других подозрительных действий.

Сквозной пример демонстрирует полный цикл работы с audit.log: от поиска и группировки до детальной интерпретации всех значимых полей, что является ключевой компетенцией специалиста уровня SOC L1.
