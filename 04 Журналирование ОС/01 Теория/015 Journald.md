# Journald

## 1. Journald в экосистеме Linux: назначение и отличие от syslog

Демон `systemd-journald` — это централизованная служба сбора, хранения и индексации системных журналов, входящая в состав менеджера инициализации systemd. На любом современном дистрибутиве Linux, использующем systemd, journald является единой точкой входа для сообщений ядра, системных служб, приложений, записей аудита и пользовательских процессов. Он заменил собой разрозненную модель традиционного syslog, при которой каждый источник записывал текстовые строки в отдельные файлы `/var/log/` без встроенной структуры.

Ключевое разграничение, которое необходимо усвоить с самого начала: **journald** — это сервис-сборщик (демон `systemd-journald`), а **journalctl** — инструмент командной строки для чтения и фильтрации накопленных журналов. Сам демон не предназначен для интерактивного просмотра; вся работа аналитика ведётся через journalctl. Это разделение ролей схоже с архитектурой СУБД, где демон хранит данные в собственном формате, а клиентское приложение выполняет запросы.

Исторически стандартом протоколирования в Unix-подобных ОС был протокол syslog, реализованный демонами вроде `rsyslog` или `syslog-ng`. Они принимают сообщения по сокету `/dev/log`, классифицируют их по facility и priority, и записывают в текстовые файлы согласно набору правил. Journald же разрушает эту парадигму по нескольким осям, что отражено в сравнительной таблице:

| Характеристика | syslog (традиционный) | journald |
|----------------|-----------------------|----------|
| **Формат хранения** | Простой текст, обычно одна строка на событие | Бинарный структурированный формат с индексами |
| **Метаданные** | Только те, что включены в текстовое сообщение (вручную) | Автоматически добавляемые поля: PID, UID, GID, unit, SELinux-контекст, cgroup и др. |
| **Структурированность** | Нативная поддержка отсутствует; требуется парсинг строк | Все поля типизированы и доступны для запросов без разбора |
| **Производительность** | При высоких нагрузках возможна задержка записи на диск, блокировки | Оптимизирован для высоких объёмов: асинхронная запись, индексация, быстрый поиск |
| **Ротация** | Требует ручной настройки logrotate или встроенных механизмов демона | Автоматическая по размеру и времени, настраивается через `journald.conf` |
| **Удалённое протоколирование** | Встроенная поддержка отправки по сети (TCP/UDP/TLS) | Не имеет собственного сетевого транспорта; требует настройки пересылки в syslog или прямой интеграции через API |
| **Целостность** | Легко подделать или удалить записи в текстовых файлах | Возможность подписи журналов (Forward Secure Sealing, FSS), бинарный формат усложняет несанкционированное редактирование |

Journald не отменяет syslog полностью: во многих конфигурациях он сосуществует с rsyslog, принимая сообщения от приложений, которые всё ещё пишут через вызов `syslog()`. Демон journald прослушивает сокет `/run/systemd/journal/syslog` и направляет полученные данные в общий журнал, одновременно имея возможность переслать их дальше в традиционный syslog-демон, если включена опция `ForwardToSyslog=yes`. Таким образом, в типичной современной системе Linux журнал journald является центральным концентратором, а rsyslog — вторичным получателем для совместимости и сетевой ретрансляции.

Для SOC-аналитика первого уровня понимание этой архитектуры означает, что журнал journald становится приоритетным источником информации при расследовании инцидентов на хосте. В отличие от разрозненных текстовых логов, здесь все события привязаны к контексту исполнения (unit, PID, пользователь), что позволяет быстро фильтровать данные без написания сложных регулярных выражений. Например, для поиска всех действий SSH-сервера за последний час достаточно одной команды journalctl, а не ручного разбора `/var/log/auth.log`. Более того, бинарный формат гарантирует, что даже после перезагрузки службы или сбоя индексы остаются целостными, а временные метки — монотонными и точными.

Таким образом, journald выступает как фундамент локального логирования в Linux-системах, обеспечивая единый интерфейс для сбора, хранения и быстрого поиска событий. Следующий раздел детально рассматривает внутреннее устройство демона и его источники данных.

## 2. Архитектура и внутреннее устройство journald

Демон `systemd-journald` построен как событийно-ориентированный сервис, работающий в пользовательском пространстве и взаимодействующий с ядром через специальные файловые дескрипторы. Его архитектура может быть описана в терминах: **источники сообщений**, **внутренняя структура записей**, **хранилище** и **механизмы доставки**. Рассмотрим каждый слой.

### 2.1. Источники сообщений

Journald принимает данные из пяти основных источников, каждому из которых соответствует уникальное значение поля `_TRANSPORT` в итоговой записи.

```text
                    ┌────────────────────────────────────────────────┐
                    │            systemd-journald                    │
                    │   (приём, индексация, запись, пересылка)       │
                    └───┬──────────┬──────────┬──────────┬──────────┘
            ┌──────────┘          │          │          └──────────┐
            ▼                     ▼          ▼                     ▼
    ┌──────────────┐   ┌─────────────────┐   │   ┌─────────────────┐
    │  /dev/kmsg   │   │ stdout/stderr   │   │   │ /run/systemd/   │
    │   (kernel)   │   │  сервисных      │   │   │ journal/syslog  │
    └──────┬───────┘   │  units          │   │   └────────┬────────┘
           │           └────────┬────────┘   │            │
           │TRANSPORT=kernel    │TRANSPORT=stdout          │TRANSPORT=syslog
           ▼                    ▼             ▼            ▼
        ┌──────┐           ┌──────┐      ┌──────┐      ┌──────┐
        │Ядро  │           │Службы│      │ API  │      │legacy│
        └──────┘           └──────┘      └──────┘      └──────┘
```

- **Kernel messages (`_TRANSPORT=kernel`)**. Демон читает устройство `/dev/kmsg`, получая все сообщения, генерируемые ядром: информация о загрузке, ошибки оборудования, действия netfilter, oops. Эти сообщения традиционно доступны через `dmesg`, но journald сохраняет их наравне с остальными, обогащая метаданными.
- **Стандартные потоки служб (`_TRANSPORT=stdout`)**. При запуске любого сервиса под управлением systemd его стандартные потоки вывода (`stdout`) и ошибок (`stderr`) автоматически перехватываются и перенаправляются в журнал. Это означает, что разработчику не нужно добавлять поддержку syslog: достаточно писать в консоль. В записи фиксируется имя unit-файла (`_SYSTEMD_UNIT`), PID, cgroup.
- **Syslog-совместимый сокет (`_TRANSPORT=syslog`)**. Для обратной совместимости journald прослушивает сокет `/run/systemd/journal/syslog`. Приложения, использующие библиотечную функцию `syslog()` или утилиту `logger`, попадают в этот поток. Сообщение также получает метаданные syslog-сообщения: facility, severity.
- **Native Journal API (`_TRANSPORT=journal`)**. Приложения могут записывать структурированные события напрямую через библиотеку `libsystemd` (функции `sd_journal_send()` и др.). Этот метод позволяет передавать произвольные поля в формате ключ-значение, которые сохраняются как есть и могут быть позднее отфильтрованы. API также используется компонентами самого systemd.
- **Аудит (`_TRANSPORT=audit`)**. Если в системе активна подсистема аудита ядра (`auditd`), journald может принимать записи аудита и включать их в общий журнал, обогащая правилами подсистемы.

Помимо этого, при правильной интеграции контейнерные среды (Docker, Podman) способны направлять логи контейнеров прямо в journald через драйвер логирования, добавляя такие поля, как `CONTAINER_ID`, `CONTAINER_NAME`, `IMAGE_NAME`. Это превращает journald в универсальный коллектор для всех процессов на хосте.

### 2.2. Структура записи и автоматические метаданные

Каждое событие, поступающее в journald, преобразуется в объект, состоящий из набора типизированных полей. Ядро события — поле `MESSAGE`, содержащее текст сообщения, как он был сгенерирован источником. Однако основная ценность для аналитика — неявные (implicit) метаданные, добавляемые демоном автоматически и гарантирующие достоверность контекста. Полный перечень полей описан в `systemd.journal-fields(7)`. Наиболее значимые для SOC-специалиста:

| Поле | Описание | Пример использования в SOC |
|------|----------|----------------------------|
| `_PID`, `_UID`, `_GID` | Идентификаторы процесса, пользователя и группы, породивших запись | Поиск действий конкретного пользователя: `_UID=1000` |
| `_COMM` | Имя исполняемого файла (без пути) | Идентификация процесса, даже если имя в MESSAGE отличается |
| `_SYSTEMD_UNIT` | Имя юнита systemd, к которому относится процесс | Фильтрация логов только SSH-сервера: `-u sshd.service` |
| `_TRANSPORT` | Канал поступления (kernel, syslog, stdout, journal, audit) | Отделение сообщений аудита от ошибок приложений |
| `PRIORITY` | Числовой уровень важности (0-7, от emerg до debug) | Выборка только событий уровня error и выше: `-p err` |
| `_BOOT_ID` | Уникальный идентификатор загрузки системы | Привязка к конкретной сессии (полезно после перезагрузки) |
| `_HOSTNAME` | Имя хоста | Корреляция в распределённой среде (при централизованном сборе) |
| `_SOURCE_REALTIME_TIMESTAMP` | Монотонная временная метка в микросекундах с момента загрузки | Точное упорядочивание событий в пределах одной загрузки |
| `__REALTIME_TIMESTAMP` | Абсолютная временная метка (Unix epoch в микросекундах) | Построение временной шкалы инцидента |

Эти поля индексируются, что позволяет выполнять выборку по ним без линейного сканирования всего журнала. Бинарный формат хранит записи в виде сегментов-файлов с индексами, содержащими ссылки на блоки данных. Благодаря этому даже при объёмах журнала в несколько гигабайт поиск по точному значению поля выполняется практически мгновенно.

### 2.3. Хранение и управление жизненным циклом

По умолчанию journald хранит журналы в памяти (путь `/run/log/journal/`), и они теряются при перезагрузке. Такое поведение соответствует опции `Storage=auto` в конфигурационном файле `journald.conf`: если директория `/var/log/journal/` не существует, используется энергозависимое хранение. Для персистентного журнала достаточно создать эту директорию с корректными правами:

```bash
mkdir -p /var/log/journal
systemd-tmpfiles --create --prefix /var/log/journal
```

После этого все новые записи будут сбрасываться на диск, а предыдущие (из энергозависимого журнала) перенесены туда при следующем срабатывании `systemd-journal-flush.service`.

Ключевые параметры управления дисковым пространством задаются в `/etc/systemd/journald.conf`:

- `SystemMaxUse=` — максимальный суммарный объём постоянного журнала (например, `500M`).
- `RuntimeMaxUse=` — лимит для энергозависимого журнала в `/run`.
- `SystemKeepFree=` — минимальное свободное место на файловой системе, которое journald обязан оставить.
- `MaxRetentionSec=` — максимальное время хранения записи (например, `1month`).
- `MaxFileSec=` — максимальный возраст одного файла-сегмента до ротации.
- `Compress=yes` (по умолчанию) — включает сжатие сегментов, уменьшая занимаемое место.

Механизм автоматической ротации и удаления старых записей (vacuuming) может быть запущен и вручную с помощью команд `journalctl --vacuum-size=200M` или `journalctl --vacuum-time=2weeks`, что позволяет администратору очистить место без изменения глобальной конфигурации.

Важной особенностью является защита целостности: при включённой опции `Seal=yes` journald использует Forward Secure Sealing (FSS) — криптографическую подпись сегментов журнала, которая позволяет в будущем проверить, не были ли записи подделаны или удалены. Для SOC это даёт дополнительную гарантию достоверности улик.

Таким образом, внутреннее устройство journald демонстрирует продуманный баланс между производительностью, надёжностью и гибкостью. Оно обеспечивает полноту сбора данных и их пригодность для последующего анализа, что становится базой для практической работы, описываемой в следующем разделе.

## 3. Практическое применение journalctl и конфигурация journald

Если journald — это механизм накопления, то journalctl — универсальный инструмент извлечения и анализа. В повседневной работе SOC-аналитика именно journalctl становится основным интерфейсом для оперативного поиска по локальным логам, эскалации инцидентов и подготовки данных для SIEM.

### 3.1. Основные операции с journalctl

Начнём с базовых команд, которые решают 80% типовых задач.

**Просмотр всех логов с навигацией:**
```bash
journalctl
```
Открывает пейджер (обычно `less`) со всеми доступными записями, начиная с самых старых. Для быстрой оценки последних событий удобнее использовать `-r` (обратный порядок) и `-n` (количество строк):
```bash
journalctl -r -n 50
```

**Отслеживание в реальном времени** аналогично `tail -f`:
```bash
journalctl -f
```
Всякая новая запись немедленно выводится на экран, что полезно при воспроизведении проблемы.

**Фильтрация по идентификатору загрузки.** Каждая загрузка системы получает уникальный `_BOOT_ID`. Просмотр логов только с текущей загрузки:
```bash
journalctl -b
```
Предыдущая загрузка: `journalctl -b -1`. Список всех загрузок с временными метками:
```bash
journalctl --list-boots
```
Эта возможность критична, когда инцидент мог произойти до перезагрузки и требуется проверить, не потеряны ли логи.

**Временные диапазоны.** Параметры `--since` и `--until` принимают как абсолютное время (`"2025-06-01 12:00:00"`), так и относительное (`"1 hour ago"`, `"yesterday"`):
```bash
journalctl --since "2025-06-07 08:00:00" --until "2025-06-07 09:00:00"
```
Для быстрого ответа на алерт SOC часто применяется `--since "30 min ago"`.

**Фильтрация по службе (unit):**
```bash
journalctl -u sshd.service --since "1 hour ago"
```
Возвращает только логи конкретного юнита. Допустимо использовать shell-маски: `-u 'systemd-*.service'`.

**Фильтрация по приоритету.** Уровни задаются числами 0-7 или именами: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`. Например, все критические ошибки:
```bash
journalctl -p crit
```
Можно комбинировать: `journalctl -u nginx.service -p err`.

**Фильтрация по произвольным полям.** Каждое поле из каталога `systemd.journal-fields` может быть использовано в фильтре:
```bash
journalctl _UID=1000
journalctl _PID=8453
journalctl _TRANSPORT=kernel
```
Поля регистрозависимы и требуют наличия ведущего подчёркивания для неявных метаданных. Фильтры объединяются логическим «И».

**Расширенный поиск по тексту.** journalctl не имеет встроенного полнотекстового поиска по телу сообщения, но это легко компенсируется pipe в `grep`:
```bash
journalctl -u sshd --since "1 hour ago" | grep "Failed password"
```
При больших объёмах эффективнее сначала сузить набор записей с помощью метаданных, а затем фильтровать строки.

### 3.2. Форматы вывода для автоматизации

Для интеграции с SIEM, скриптовыми анализаторами или быстрой визуализации данным полезно сразу получать структурированный вывод. journalctl поддерживает десятки форматов, наиболее востребованные:

- `-o short-iso` — классический вид с датой в ISO 8601 и полным именем хоста.
- `-o json` — полный вывод в JSON (компактный, без переносов).
- `-o json-pretty` — многострочный, удобный для чтения человеком.
- `-o export` — бинарный, предназначен для передачи между экземплярами journald (используется при репликации).

Пример получения JSON-записей для последующей обработки `jq`:
```bash
journalctl -u sshd -o json --since "1 hour ago" | jq '.__REALTIME_TIMESTAMP'
```
Таким образом можно быстро извлечь конкретные поля для статистики или построения таймлайна.

### 3.3. Конфигурация демона journald

Файл `/etc/systemd/journald.conf` управляет поведением демона. После изменений требуется перезагрузка:
```bash
sudo systemctl daemon-reload
sudo systemctl restart systemd-journald
```

Рассмотрим конфигурацию, типичную для сервера, обрабатывающего умеренный поток событий и требующую сохранения логов в течение двух недель:

```ini
[Journal]
Storage=persistent
Compress=yes
SystemMaxUse=500M
SystemKeepFree=100M
MaxRetentionSec=2week
SyncIntervalSec=5m
RateLimitIntervalSec=30s
RateLimitBurst=10000
ForwardToSyslog=yes
```

Пояснения:
- `Storage=persistent` — безусловное сохранение на диск.
- `SystemMaxUse=500M` ограничивает журнал полугигабайтом; по достижении порога старые записи автоматически удаляются.
- `SystemKeepFree=100M` гарантирует, что на файловой системе всегда останется не менее 100 МБ свободного места.
- `MaxRetentionSec=2week` удаляет всё старше двух недель, даже если лимит размера не исчерпан.
- `RateLimitIntervalSec` и `RateLimitBurst` предотвращают переполнение логами от одного чрезмерно активного источника: если в течение 30 секунд поступит больше 10000 сообщений, последующие будут отброшены.
- `ForwardToSyslog=yes` перенаправляет все сообщения в традиционный syslog-демон, что может потребоваться для уже существующих централизованных систем сбора на базе rsyslog.

### 3.4. Управление занятым пространством

Для оперативного контроля и обслуживания журнала без редактирования конфигурации применяются встроенные утилиты:

```bash
journalctl --disk-usage
```
Показывает суммарный размер архивов на диске и в памяти.

Очистка до указанного размера:
```bash
journalctl --vacuum-size=200M
```
Удалить записи старше заданного промежутка:
```bash
journalctl --vacuum-time=1week
```

Эти команды безопасны и могут быть добавлены в cron, чтобы гарантировать освобождение места.

### 3.5. Роль journalctl в рабочем процессе SOC L1

В контексте центра мониторинга безопасности журнал journald выступает в двух качествах: как первый источник при реагировании на алерт с конкретного хоста и как источник данных для централизованной системы логирования (SIEM). В первом случае аналитик через SSH подключается к скомпрометированному (или подозреваемому) хосту и с помощью описанных приёмов быстро извлекает относящиеся к инциденту записи. Второй случай предполагает настройку пересылки логов с хоста на коллектор. Поскольку journald не поддерживает собственную передачу по сети, стандартным решением является либо сохранение в файл через `systemd-journal-remote`, либо использование ForwardToSyslog и последующей ретрансляции rsyslog на центральный сервер. В обоих вариантах богатые метаданные journald (поля `_SYSTEMD_UNIT`, `_UID`, `_PID`) упаковываются в структурированные сообщения и становятся доступными для корреляции в SIEM.

Более современные подходы включают прямую отправку отформатированных JSON-логов через агенты (Fluentd, Vector) с использованием вывода `journalctl -o json`. Это позволяет сохранить все поля без потери информации и использовать их как индексы в платформе.

Таким образом, journalctl — это не просто утилита просмотра, а многофункциональный аналитический инструмент, незаменимый при локальных расследованиях и подготовке данных для эскалации.

## 4. Сквозной практический пример: расследование попытки подбора пароля через SSH

**Исходные условия.** Сервер Ubuntu 24.04 под управлением systemd, journald настроен на персистентное хранение (`Storage=persistent`). SOC-аналитик первого уровня получает алерт от SIEM: «Множественные неуспешные аутентификации SSH с одного IP-адреса за короткий промежуток времени». Необходимо локально подтвердить факт атаки, собрать детали (IP, время, учётные записи) и предоставить выжимку для эскалации. Инструменты: journalctl, jq (опционально), grep.

**Шаг 1: Получение общего контекста по службе SSH за последний час.**
```bash
journalctl -u sshd.service --since "1 hour ago" -n 30
```
Ожидаемый вывод (иллюстративная схема):
```
-- Logs begin at Wed 2025-06-10 08:00:00 UTC, end at Wed 2025-06-10 09:15:00 UTC. --
Jun 10 09:10:12 ubuntu-server sshd[1250]: Failed password for root from 203.0.113.45 port 51234 ssh2
Jun 10 09:10:13 ubuntu-server sshd[1250]: Failed password for invalid user admin from 203.0.113.45 port 51234 ssh2
Jun 10 09:10:15 ubuntu-server sshd[1250]: Failed password for root from 203.0.113.45 port 51235 ssh2
...
```
Вывод демонстрирует многократные неудачные попытки с адреса 203.0.113.45 под разными учётными записями. Поля `_SYSTEMD_UNIT=sshd.service`, `PRIORITY=5` (notice) присутствуют неявно.

**Шаг 2: Фильтрация только по ошибкам аутентификации для этого unit.**
```bash
journalctl -u sshd.service -p err --since "1 hour ago" --no-pager
```
Вывод сокращается до критических и error-событий, среди которых могут быть не только неудачные логины, но и, например, сообщения о неверном ключе хоста. Однако в данном случае преобладают `Failed password`. Опция `--no-pager` удобна для скриптов, но при интерактивном анализе её часто опускают.

**Шаг 3: Поиск всех событий, связанных с подозрительным IP.**
journalctl не умеет фильтровать по содержимому MESSAGE, поэтому используем комбинацию:
```bash
journalctl -u sshd.service --since "1 hour ago" | grep "203.0.113.45"
```
Результат содержит все строки с этим адресом, включая успешные аутентификации после подбора (если таковой был). Аналитик быстро визуально вычленяет, был ли успешный вход (`Accepted password`).

**Шаг 4: Экспорт детализированных записей в JSON для формализованного отчёта.**
```bash
journalctl -u sshd.service -o json --since "1 hour ago" \
  | jq 'select(.__REALTIME_TIMESTAMP != null) | {ts: (.__REALTIME_TIMESTAMP | tonumber / 1000000 | strftime("%Y-%m-%d %H:%M:%S")), ip: (.MESSAGE // "" | scan("\\d+\\.\\d+\\.\\d+\\.\\d+") | first), msg: .MESSAGE}'
```
Пояснение: мы преобразуем микросекундную метку в читаемый формат, регулярным выражением извлекаем первый IP из сообщения и выводим компактный объект. Результат выглядит так (иллюстративная схема):
```json
{"ts":"2025-06-10 09:10:12","ip":"203.0.113.45","msg":"Failed password for root from 203.0.113.45 port 51234 ssh2"}
{"ts":"2025-06-10 09:10:13","ip":"203.0.113.45","msg":"Failed password for invalid user admin from 203.0.113.45 port 51234 ssh2"}
```
Этот структурированный массив легко вставить в заявку на эскалацию или встроить в SOAR-сценарий.

**Шаг 5: Проверка, охватывает ли текущая загрузка весь инцидент.**
Алгоритм атаки может растянуться на часы, и возможны перезагрузки. Смотрим список загрузок:
```bash
journalctl --list-boots
```
Вывод:
```
-2 d70f7... Wed 2025-06-10 07:00:00 UTC—Wed 2025-06-10 08:00:00 UTC
-1 e8b2a... Wed 2025-06-10 08:05:00 UTC—Wed 2025-06-10 08:30:00 UTC
 0 9f14c... Wed 2025-06-10 08:31:00 UTC—Wed 2025-06-10 09:15:00 UTC
```
Если подозрительная активность началась в 08:10, то она попадает на загрузку -1. Чтобы извлечь логи из предыдущей загрузки, выполняем:
```bash
journalctl -b -1 -u sshd.service --since "2025-06-10 08:10:00"
```
Таким образом гарантируется, что никакие события не пропущены.

**Ожидаемый вывод примера.** Аналитик подтверждает факт брутфорс-атаки с IP 203.0.113.45, отмечает отсутствие успешного входа, фиксирует временной интервал атак и прикладывает JSON-выборку к инцидент-тикету. Весь процесс занял не более пяти минут, благодаря возможностям journalctl по фильтрации и экспорту данных.

Приведённый сценарий иллюстрирует ключевое преимущество journald в SOC: журнал выступает не пассивным хранилищем, а активным инструментом, позволяющим быстро и точно ответить на вопросы «кто, когда и откуда». Для аналитика первого уровня овладение этим инструментом равносильно умению быстро ориентироваться в среде, где каждая секунда на счету.
