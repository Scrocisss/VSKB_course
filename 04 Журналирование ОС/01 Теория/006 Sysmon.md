# Sysmon: расширенное журналирование Windows для SOC L1

## Место Sysmon в мониторинге Windows и разграничение понятий

Системный монитор (System Monitor, Sysmon) — это системная служба и драйвер Windows, разработанные Microsoft (Sysinternals) и предназначенные для регистрации детальной телеметрии безопасности. Утилита не входит в стандартную поставку ОС; её требуется отдельно загрузить и установить. Sysmon регистрирует события в специально выделенном канале журнала Windows — **Microsoft-Windows-Sysmon/Operational** — и остаётся активным после перезагрузок, начиная работу на ранних этапах загрузки системы. Важно подчеркнуть: Sysmon только **фиксирует** системную активность; он не выполняет анализ событий, не генерирует предупреждения самостоятельно и не блокирует вредоносные действия. Анализ, корреляция и оповещение реализуются внешними средствами — SIEM-системами, EDR-платформами или скриптами, потребляющими журнал Sysmon.

Во избежание типичной путаницы необходимо чётко разграничить Sysmon, стандартные журналы безопасности Windows и коммерческие EDR-решения. Различия сведены в таблицу ниже.

| Характеристика | Windows Security Event Log | Sysmon | EDR (Endpoint Detection and Response) |
|----------------|----------------------------|--------|---------------------------------------|
| **Назначение** | Базовая регистрация событий безопасности (вход в систему, доступ к объектам, аудит политик) | Глубокая телеметрия процессов, сети, файловой системы и реестра, недоступная в стандартных журналах | Непрерывный анализ, обнаружение угроз, блокировка, расследование инцидентов |
| **Источник** | Встроен в Windows, управляется политиками аудита | Устанавливается отдельно (Sysinternals), управляется XML-конфигурацией | Внешний агент (вендорский) с собственной политикой и облачной аналитикой |
| **Способ доставки** | Каналы Windows Event Log (Security, System, Application) | Канал Microsoft-Windows-Sysmon/Operational | Собственное хранилище (часто облачное) или отдельные журналы, API |
| **Анализ и реакция** | Отсутствуют; только запись событий, настроенных администратором | Отсутствуют; только детальная запись согласно конфигурации | Полный цикл: обнаружение, оповещение, автоматическое реагирование (изоляция, завершение процессов) |
| **Типичный охват событий** | Ограниченный набор Event ID (4624, 4688, 5156 и др.), не включает хэши процессов, полные командные строки, контекст родительского процесса | Расширенный набор (Event ID 1–29): создание процессов с хэшами, сетевые соединения, загрузка драйверов, доступ к процессам, DNS-запросы и т.п. | Все события Sysmon + дополнительные поведенческие индикаторы, телеметрия памяти, анализ угроз в реальном времени |
| **Управление** | Групповые политики, локальные политики аудита | Командная строка, XML-файл конфигурации (include/exclude, RuleGroup) | Централизованная консоль управления агентом |
| **Стоимость** | Бесплатно (в составе ОС) | Бесплатно | Коммерческая лицензия |

Таким образом, Sysmon представляет собой промежуточный уровень: он существенно расширяет видимость по сравнению со штатными журналами, но не заменяет полноценную систему обнаружения и реагирования. В SOC уровня 1 Sysmon используется как источник высококачественных данных для поиска угроз (threat hunting) и первичного анализа, а также как база для правил детекции на стороне SIEM. Его ценность заключается в способности регистрировать артефакты сложных атак — например, внедрение кода в процесс, манипуляции с временем создания файла, скрытые WMI-подписки или аномальные сетевые подключения, — которые отсутствуют в дефолтном аудите Windows.

## Внутреннее устройство: события, конфигурация и архитектура

Sysmon функционирует как связка драйвера режима ядра и пользовательской службы. Драйвер перехватывает системные вызовы и передаёт информацию службе, которая формирует события и записывает их в журнал. Управление осуществляется исключительно через конфигурационный файл в формате XML, который определяет, какие типы событий записываются, и позволяет задавать фильтры включения (include) и исключения (exclude) на основе значений полей (путь, хэш, командная строка, IP-адрес и т.д.). Событие попадает в журнал, только если оно соответствует хотя бы одному фильтру включения и ни одному фильтру исключения для данного типа события.

Конфигурация состоит из корневого элемента `<Sysmon>`, содержащего один или несколько элементов `<EventFiltering>`, внутри которых для каждого типа события могут быть объявлены блоки `<RuleGroup>`. Каждая группа правил может включать условие `groupRelation` (значения `and` или `or`). Итоговая логика: событие обрабатывается, если оно удовлетворяет хотя бы одной активной группе правил с учётом её внутренней связи и не отфильтровано глобальными исключениями. Иллюстративная упрощённая структура конфигурации:

```xml
<Sysmon schemaversion="4.80">
  <EventFiltering>
    <RuleGroup name="Detect suspicious processes" groupRelation="or">
      <ProcessCreate onmatch="include">
        <CommandLine condition="contains">powershell -enc </CommandLine>
      </ProcessCreate>
      <ProcessCreate onmatch="include">
        <Image condition="end with">\wscript.exe</Image>
      </ProcessCreate>
    </RuleGroup>
    <!-- Исключение легитимного администраторского инструмента -->
    <ProcessCreate onmatch="exclude">
      <Image condition="is">C:\Windows\System32\mmc.exe</Image>
    </ProcessCreate>
  </EventFiltering>
</Sysmon>
```

Все значимые параметры события, включая хэши файлов (SHA1, MD5, SHA256), цифровые подписи, полные командные строки, идентификаторы родительского процесса и GUID процесса, обогащают запись. Благодаря этому SOC-аналитик может, например, отследить цепочку `winword.exe → cmd.exe → powershell.exe` вплоть до параметров кодированной команды.

Sysmon поддерживает до 29 типов событий (Event ID), охватывающих ключевые аспекты активности конечной точки. Ниже представлена сводная таблица основных категорий с соответствующими идентификаторами и кратким описанием, основанная на документации Microsoft и отраслевых источниках.

| Категория | Event ID | Описание (контролируемые артефакты) |
|-----------|----------|-------------------------------------|
| Создание процесса | 1 | Полная информация о запущенном процессе: образ, командная строка, хэши, родительский процесс, пользователь, идентификатор цепочки |
| Изменение времени создания файла | 2 | Фиксация попытки изменить временные метки файла (техника, используемая злоумышленниками для заметания следов) |
| Сетевое соединение | 3 | Протокол, локальный и удалённый IP, порты, инициатор процесса (образ, PID) |
| Состояние службы Sysmon | 4 | Запуск, остановка службы, состояние обработки конфигурации |
| Завершение процесса | 5 | Время завершения, идентификатор процесса; позволяет вычислять длительность жизни процесса |
| Загрузка драйвера | 6 | Подпись, хэши загружаемого драйвера; критично для обнаружения руткитов |
| Загрузка образа (DLL) | 7 | Путь загруженной библиотеки, цифровая подпись; выявляет инъекцию DLL |
| Создание удалённого потока | 8 | Информация о создании потока в адресном пространстве другого процесса — классический индикатор инъекции кода |
| Чтение «сырого» доступа (RawAccessRead) | 9 | Прямой доступ к диску в обход файловой системы; часто используется для дампа учётных данных |
| Доступ к процессу | 10 | Запросы на открытие процесса с определёнными правами (например, для внедрения или дампа памяти) |
| Создание/изменение файла | 11 | Создание, удаление, перезапись файлов с хэшами; мониторинг дропперов и изменений в автозагрузке |
| События реестра | 12, 13, 14 | Создание/удаление ключей и значений (12), изменение значений (13), переименование ключей (14) |
| Создание альтернативного потока файла | 15 | Запись ADS-потока; техника сокрытия данных в NTFS |
| Изменение конфигурации Sysmon | 16 | Логирование перезагрузки конфигурации службы |
| Именованные каналы (Pipes) | 17, 18 | Создание (17) и подключение (18) к именованным каналам; актуально для C2-коммуникаций |
| WMI-активность | 19, 20 | Фильтр событий WMI (19) и потребитель (20); обнаружение персистентности и выполнения через WMI |
| DNS-запросы | 22 | Домен, IP процесса-инициатора; базовый инструмент для выявления DGA и туннелирования |
| Другие события | 21, 23–29 | Клипборд (24), удаление файла (23) и пр. (используются реже) |

События Sysmon записываются в единый операционный журнал `Microsoft-Windows-Sysmon/Operational`; физический файл размещается по пути `C:\Windows\System32\winevt\Logs\Microsoft-Windows-Sysmon%4Operational.evtx`. Каждая запись содержит богатую XML-структуру, доступную для разбора как вручную через Event Viewer, так и автоматическими средствами сбора логов (Windows Event Forwarding, агенты SIEM). Подобный унифицированный формат упрощает нормализацию и корреляцию в аналитических платформах.

## Применение и типовые операции

Работа с Sysmon в среде SOC предполагает три основных направления: развёртывание и конфигурирование, сбор и маршрутизация логов, анализ с использованием правил детекции.

**Установка и управление.** Утилита поставляется в архиве `Sysmon.zip`, доступном на официальном сайте Microsoft (Sysinternals). Архив содержит исполняемые файлы `Sysmon.exe` и `Sysmon64.exe`. Установка выполняется от имени администратора. Базовая команда для установки службы с принятием лицензионного соглашения и без файла конфигурации (будут записываться все типы событий, что избыточно):

```powershell
.\Sysmon64.exe -i -accepteula
```

Практически всегда требуется передать XML-конфигурацию:

```powershell
.\Sysmon64.exe -i -accepteula .\sysmonconfig.xml
```

Обновление конфигурации (без переустановки службы) производится флагом `-c`:

```powershell
.\Sysmon64.exe -c .\sysmonconfig.xml
```

Просмотр текущей конфигурации осуществляется через `-c --`, удаление службы — `-u`. Следует отметить, что Sysmon не является стандартной программой: он устанавливается как защищённая служба Windows, и её остановка или удаление требуют административных прав и регистрируются событием 16 (Sysmon Configuration Change), что само по себе может служить индикатором подозрительной активности.

**Логирование и управление журналом.** После установки события немедленно начинают поступать в указанный канал. Для просмотра в Event Viewer достаточно открыть Applications and Services Logs → Microsoft → Windows → Sysmon и выбрать Operational. Для быстрой выгрузки событий из командной строки удобно использовать утилиту `wevtutil`. Например, экспорт всех событий Sysmon за последний час в XML-файл:

```bash
wevtutil qe Microsoft-Windows-Sysmon/Operational /f:XML /e:root > sysmon_events.xml
```

В крупных развёртываниях применяется Windows Event Forwarding (WEF) для направления событий на коллектор, откуда SIEM-агент или сама SIEM забирает данные.

**Конфигурирование.** Ключевой навык аналитика SOC L1 — понимать логику фильтрации и уметь читать конфигурационные файлы. Хорошо зарекомендовала себя практика использования общедоступных конфигураций, например, предложенная SwiftOnSecurity, которая содержит сбалансированный набор правил для продуктивной среды с исключением типичного легитимного шума. Однако любая готовая конфигурация требует адаптации под конкретную инфраструктуру, чтобы избежать ложных срабатываний и переполнения журнала.

Пример фрагмента конфигурации, нацеленного на логирование подозрительных вызовов PowerShell с закодированными командами и исключением доверенных путей:

```xml
<RuleGroup name="Suspicious PowerShell" groupRelation="or">
  <ProcessCreate onmatch="include">
    <Image condition="end with">\powershell.exe</Image>
    <CommandLine condition="contains">-enc</CommandLine>
  </ProcessCreate>
</RuleGroup>
<ProcessCreate onmatch="exclude">
  <Image condition="begin with">C:\Program Files\</Image>
</ProcessCreate>
```

Такая конфигурация гарантирует, что в журнал попадут только события запуска PowerShell с аргументом `-enc` (сокращение для `-EncodedCommand`), что является распространённым вектором атак, но при этом отсекаются легитимные экземпляры из доверенных каталогов.

**Анализ и детекция.** На практике события Sysmon редко анализируются изолированно. В SOC L1 типичен следующий рабочий процесс: SIEM-платформа (Splunk, Elastic, Microsoft Sentinel) получает поток событий, нормализует их и применяет корреляционные правила, написанные, например, в формате Sigma. Проект Sigma приобрёл особое значение после 2020 года, когда комьюнити приняло бэкенд, генерирующий непосредственно правила include/exclude для конфигурации Sysmon. Таким образом, одни и те же детектирующие правила могут использоваться и для SIEM, и для тонкой настройки самого Sysmon. Типичные сценарии обнаружения включают:

- **Подозрительные командные строки** (Event ID 1): запуск `mshta.exe`, `regsvr32.exe` с удалёнными URL, PowerShell с `-enc` или `-w hidden`.
- **Нестандартные отношения «родитель-потомок»**: офисное приложение (Excel) порождает командный интерпретатор.
- **Сетевые соединения (ID 3)** к редко используемым портам или IP без предшествующего DNS-запроса (отсутствие записи ID 22).
- **Доступ к процессам (ID 10)** с флагами, которые позволяют внедрение кода, например `0x1F0FFF` (PROCESS_ALL_ACCESS) к критичным процессам типа `lsass.exe`.

Важнейшая ловушка — избыточное логирование. Без тщательного тюнинга конфигурации громкость событий способна за считанные минуты заполнить дисковое пространство или перегрузить коллектор. Поэтому базовая рекомендация для SOC L1: никогда не разворачивать Sysmon с пустой конфигурацией в продуктивной сети; всегда начинать с консервативных правил, постепенно добавляя более детализированные логи по мере оценки влияния на производительность.

## Сквозной практический пример: обнаружение подозрительного запуска PowerShell

**Исходные условия:** Изолированная лабораторная среда Windows 10, права локального администратора, Sysmon и файл конфигурации `sysmonconfig.xml` размещены в `C:\Tools`. Цель — продемонстрировать, как Sysmon регистрирует детали процесса с закодированной командой PowerShell, и как выглядят эти данные для анализа.

**Шаг 1. Установка Sysmon с конфигурацией, включающей логирование всех запусков PowerShell.**
Создадим минимальный конфигурационный файл, который фиксирует любое создание процесса с образом `powershell.exe`.

```xml
<!-- C:\Tools\sysmonconfig.xml -->
<Sysmon schemaversion="4.80">
  <EventFiltering>
    <ProcessCreate onmatch="include">
      <Image condition="end with">\powershell.exe</Image>
    </ProcessCreate>
  </EventFiltering>
</Sysmon>
```

Установим службу:

```bash
cd C:\Tools
.\Sysmon64.exe -i -accepteula .\sysmonconfig.xml
```

**Ожидаемый вывод:** Сообщения об установке драйвера и службы, итоговый статус `Sysmon installed. SysmonDrv installed.`. В Event Viewer появляется канал Operational.

**Шаг 2. Генерация тестового события.**
Запустим PowerShell со скрытым окном и закодированной командой, выводящей строку в файл (имитация безвредной активности).

```powershell
powershell.exe -w hidden -enc JABhACAAPQAgACIAVABoAGkAcwAgAGkAcwAgAGEAIAB0AGUAcwB0ACIALAAgACgARwBlAHQALQBEAGEAdABlACkAIAA+ACAAQwA6AFwAVABlAG0AcABcAHQAZQBzAHQALgB0AHgAdAA=
```

**Пояснение:** Base64-строка декодируется в `$a = "This is a test"; (Get-Date) > C:\Temp\test.txt`. Условие `-enc` в командной строке — характерный маркер.

**Шаг 3. Просмотр события в Event Viewer.**
Откроем Event Viewer, перейдём по цепочке `Applications and Services Logs → Microsoft → Windows → Sysmon → Operational`. Найдём событие с Event ID 1, соответствующим нашему процессу. Альтернативно используем PowerShell для фильтрации:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" | Where-Object { $_.Id -eq 1 -and $_.Properties[4].Value -like "*powershell*" } | Format-List
```

**Ожидаемый вывод (иллюстративная схема):** Объект события содержит поля:

- `Image`: `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`
- `CommandLine`: `"C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -w hidden -enc JABhACA...`
- `Hashes`: `SHA256=...`
- `ParentImage`: `C:\Windows\System32\cmd.exe` или `explorer.exe`
- `ParentCommandLine`: путь к родительскому процессу.

**Шаг 4. Выгрузка события в XML для ручного анализа.**
Используя `wevtutil`, экспортируем одно последнее событие и изучим его структуру:

```bash
wevtutil qe "Microsoft-Windows-Sysmon/Operational" /c:1 /rd:true /f:xml
```

**Ожидаемый фрагмент (иллюстративная схема):**
```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <EventID>1</EventID>
    <Channel>Microsoft-Windows-Sysmon/Operational</Channel>
    ...
  </System>
  <EventData>
    <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
    <Data Name="CommandLine">"C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -w hidden -enc ...</Data>
    <Data Name="Hashes">SHA256=83E9...</Data>
    <Data Name="ParentImage">C:\Windows\System32\cmd.exe</Data>
  </EventData>
</Event>
```

**Ожидаемый вывод:** Данный пример наглядно показывает, что Sysmon предоставляет контекст, отсутствующий в стандартном событии 4688 журнала безопасности: полные хэши исполняемого файла, неотфильтрованную командную строку (даже при включенном аудите процессов стандартный лог может обрезать или маскировать часть параметров), а также полную цепочку родительских процессов. Наличие флага `-enc` в сочетании с нетипичным родителем `cmd.exe` (вместо `explorer.exe`) является сильным индикатором подозрительной активности, доступным для правила корреляции в SIEM, что демонстрирует практическую пользу Sysmon для SOC L1.
