# Auditd: подсистема аудита Linux для SOC L1

## Контекст, назначение и ключевые разграничения

Auditd — демон пользовательского пространства, реализующий центральный компонент Linux Auditing System. Его основная функция — сбор, фильтрация и запись событий безопасности, перехваченных на уровне ядра ОС. В отличие от систем логирования общего назначения, auditd ориентирован на детальный мониторинг системных вызовов, доступа к файлам и изменения критических объектов, что делает его незаменимым источником телеметрии для центров мониторинга безопасности (SOC) уровня L1.

Согласно документации SUSE, Linux audit framework обеспечивает сбор информации о любых событиях, релевантных безопасности, и является требованием для сертификации по Common Criteria CAPP/EAL. Auditd не реализует активную защиту, но предоставляет аудиторский след, позволяющий отследить действия пользователей и процессов, вплоть до параметров каждого системного вызова, и тем самым выступает основой для обнаружения вторжений, расследования инцидентов и контроля соответствия нормативным требованиям.

### Компоненты экосистемы аудита

В состав Linux Auditing System входят несколько взаимодействующих элементов:

- **Ядерный модуль** — перехватывает системные вызовы и события согласно загруженным правилам, помещает записи в очередь.
- **auditd** — демон, читающий очередь ядра и записывающий события в файл журнала `/var/log/audit/audit.log`.
- **auditctl** — утилита управления правилами аудита во время работы системы (временные правила).
- **ausearch** — инструмент поиска и фильтрации записей в журнале аудита.
- **aureport** — генератор сводных отчётов на основе журнала.
- **autrace** — утилита трассировки отдельного процесса с записью выполняемых системных вызовов.

В контексте SOC L1 auditd часто интегрируется с SIEM-системами через агенты (например, Wazuh, Elastic Auditd Manager) или путём прямой пересылки логов по протоколу syslog с сохранением структурированного формата.

### Разграничение со смежными подсистемами логирования

На одном хосте могут параллельно работать несколько механизмов сбора событий. Ключевое отличие auditd от syslog (rsyslog/syslog-ng) и systemd-journald — в источнике данных и уровне детализации.

| Характеристика               | auditd                                     | rsyslog (syslog)                           | systemd-journald                          |
|------------------------------|--------------------------------------------|--------------------------------------------|-------------------------------------------|
| **Источник событий**         | Ядро (перехват системных вызовов, доступ к объектам) | Сообщения приложений и служб через `/dev/log` | Все сообщения systemd-юнитов, stdout/stderr служб, ядра |
| **Уровень детализации**      | Полный контекст: PID, UID, EUID, AUID, путь, атрибуты, аргументы системных вызовов | Строка сообщения с приоритетом и источником | Структурированные поля, но без гарантированной целостности аудита |
| **Целостность логов**        | Встроенные механизмы защиты (неизменяемость, подпись) | Зависит от конфигурации (обычно нет)       | Подписывание возможно, не всегда включено  |
| **Производительность**       | Высокая нагрузка при мониторинге высокочастотных системных вызовов, требует тщательной настройки правил | Низкая нагрузка, масштабируется асинхронно | Легковесный, но при большом объёме может потреблять ресурсы |
| **Типичная роль в SOC**      | Детектирование аномального поведения процессов, изменений в конфигурациях, попыток эксплуатации уязвимостей | Приём логов приложений (веб-серверы, БД) для общего мониторинга | Первичный сбор для форвардинга в SIEM через агентов |

С точки зрения SOC L1, auditd — это источник низкоуровневых событий, которые после нормализации и корреляции позволяют выявлять сложные техники MITRE (например, T1003 — Credential Dumping через отслеживание доступа к `/etc/shadow`).

## Внутреннее устройство: архитектура и правила

Подсистема аудита построена вокруг взаимодействия ядерного модуля и демона auditd. Ядро перехватывает системные вызовы в точках входа/выхода и применяет цепочку правил, загруженных через `auditctl`. При совпадении условий событие помещается в netlink-сокет, откуда его забирает демон auditd и сохраняет в файл. В современных дистрибутивах постоянные правила хранятся в файлах `/etc/audit/rules.d/audit.rules` или `/etc/audit/audit.rules` (зависит от версии).

### Архитектурная схема

```text
[Пользовательский процесс]
        │
        ▼
[Системный вызов: open, execve, …]
        │
        ▼
[Ядерный модуль аудита] ◄── [Цепочка правил (загружена auditctl)]
        │
        │  (событие совпало?)
        │         │
        ▼         ▼
[Netlink-сокет]   [Игнорировать]
        │
        ▼
[auditd] ──► /var/log/audit/audit.log
        │
        ▼ (дополнительно)
[плагины audisp] ──► syslog, SIEM
```

### Типы правил и их синтаксис

Все правила, определяющие что именно аудировать, делятся на три категории: управляющие (`control`), файловые (`file`) и правила системных вызовов (`syscall`). Управляющие правила задают параметры работы самой подсистемы, файловые правила (watch) привязываются к объектам файловой системы, а системные правила — наиболее гибкий механизм, отслеживающий определённые системные вызовы.

Стандартный синтаксис правила системного вызова:

```bash
auditctl -a <action>,<filter> -S <syscall> -F <field=value> -k <key>
```

- **action** – `always` (всегда регистрировать) или `never` (никогда, для исключений).
- **filter** – определяет точку перехвата: `task` (создание процесса), `exit` (при выходе из системного вызова), `user` (определённые действия пользователя), `exclude` (исключение из аудита).
- **-S** – название системного вызова (можно перечислять несколько, например `-S open -S truncate`).
- **-F** – дополнительный фильтр: по UID (`-F uid=1000`), AUID (`-F auid>=1000`), пути (`-F path=/etc/shadow`), коду возврата (`-F exit=-EPERM`) и т.д.
- **-k** – произвольная метка (ключ) для облегчения поиска по логам.

Файловое правило (watch) имеет упрощённый формат:

```bash
auditctl -w <path> -p <permissions> -k <key>
```

где `-p` комбинирует: `r` (чтение), `w` (запись), `x` (выполнение), `a` (изменение атрибутов).

Важно: правила обрабатываются системой аудита по принципу **первого совпадения** (first-match-win). Если первое правило предписывает игнорировать все вызовы `open`, а второе — логировать `open` для пути `/etc/shadow`, второе никогда не сработает. Порядок следования правил критичен.

Следующая таблица систематизирует типы правил с примерами и типичными сценариями использования.

| Тип правила       | Синтаксическая основа                                           | Пример (иллюстративный)                                                                                  | Сценарий в SOC L1                                                                                             |
|-------------------|-----------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------|
| **Control**       | Флаги управления: `-b`, `-f`, `-e`, `-D`, `--backlog_wait_time` | `-b 8192` (установка размера очереди), `-e 2` (блокировка загрузки при невозможности аудита)               | Настройка производительности и отказоустойчивости подсистемы.                                                  |
| **File (watch)**  | `-w <путь> -p <маска> -k <ключ>`                                 | `-w /etc/passwd -p wa -k user-modify` (отслеживание записи и атрибутов /etc/passwd)                      | Контроль изменений критических файлов конфигурации, паролей, теневых файлов, бинарников SUID, каталогов cron. |
| **System call**   | `-a always,exit -S <вызов> -F <фильтры> -k <ключ>`              | `-a always,exit -F arch=b64 -S execve -F euid=0 -k root_exec` (регистрация запуска программ от root)      | Мониторинг исполнения команд, обращения к сокетам (`connect`), работы с памятью (`ptrace`), модификации файлов.|

### Журнал аудита: структура записи

Каждое событие в `/var/log/audit/audit.log` состоит из одной или нескольких текстовых строк, начинающихся с маркера `type=...`. Например, типичная запись о выполнении команды от root содержит блоки `SYSCALL`, `EXECVE`, `CWD`, `PATH`. Ключевые поля: `msg=audit(время.секунды:порядковый номер)`, `uid=`, `auid=` (логин UID), `ses=` (сессия), `comm=` (имя процесса), `exe=` (полный путь), `key=` (метка, если задана в правиле). Именно поле `key` используется при поиске через `ausearch -k`.

```json
// Иллюстративная схема полей записи события типа SYSCALL
{
  "type": "SYSCALL",
  "msg": "audit(1711666401.123:456)",
  "arch": "x86_64",
  "syscall": 2,          // номер вызова open
  "success": "yes",
  "exit": 3,             // файловый дескриптор
  "a0": 0x7ffd...,       // аргументы системного вызова
  "items": 1,
  "ppid": 1234,
  "pid": 5678,
  "auid": 1000,          // первоначальный логин UID
  "uid": 0,             // реальный UID процесса
  "gid": 0,
  "euid": 0,
  "suid": 0,
  "fsuid": 0,
  "egid": 0,
  "sgid": 0,
  "fsgid": 0,
  "tty": "pts0",
  "ses": 1,
  "comm": "useradd",
  "exe": "/usr/sbin/useradd",
  "key": "user-modify"
}
```

Такая структура позволяет SOC-аналитику точно идентифицировать, кто (auid) и с какими привилегиями (euid) выполнил операцию, даже если злоумышленник повысил права через sudo или su.

## Применение и работа с auditd в SOC-контексте

Практическая эксплуатация auditd на конечных узлах подразумевает три ключевых этапа: настройка правил аудита, управление службой и анализ накопленных данных. Ниже приведён минимальный набор операций, которым должен владеть специалист уровня L1.

### Установка и активация

В большинстве корпоративных дистрибутивов (RHEL, CentOS, Oracle Linux) пакет `audit` установлен по умолчанию. На Debian/Ubuntu его добавляют командой:

```bash
sudo apt install auditd
```

Запуск демона и включение автозагрузки:

```bash
sudo service auditd start    # использование service гарантирует корректный UID
sudo systemctl enable auditd
```

Конфигурация самого демона находится в `/etc/audit/auditd.conf`. Стандартные параметры (формат лога `RAW`, ротация по размеру, частота обновления) обычно достаточны для первых шагов. Для высоконагруженных сред увеличивают `backlog_limit` (в правилах через `-b`).

### Создание правил: временные и постоянные

Для оперативного тестирования используют `auditctl`, правила добавляются в текущее ядро и теряются после перезагрузки:

```bash
sudo auditctl -w /etc/shadow -p r -k shadow_read
sudo auditctl -l   # проверка загруженных правил
```

Чтобы правила пережили перезагрузку, их помещают в файл `/etc/audit/rules.d/audit.rules`. Например, набор правил для отслеживания модификации ключевых файлов и действий root может выглядеть так:

```bash
# Мониторинг файлов паролей и групп
-w /etc/passwd -p wa -k user-modify
-w /etc/shadow -p wa -k shadow-modify
-w /etc/group -p wa -k group-modify

# Действия root: запуск любых бинарников
-a always,exit -F arch=b64 -S execve -F euid=0 -k root_exec
-a always,exit -F arch=b32 -S execve -F euid=0 -k root_exec

# Контроль прав доступа
-a always,exit -F arch=b64 -S chmod -S fchmod -S chown -S fchown -F auid>=1000 -F auid!=4294967295 -k perm_mod
```

После редактирования файла правила загружаются перезапуском демона или командой:

```bash
sudo service auditd reload
```

либо ручной перезагрузкой в ядро:

```bash
sudo auditctl -R /etc/audit/rules.d/audit.rules
```

При использовании централизованного управления (например, Elastic Auditd Manager) правила могут поставляться через конфигурацию агента, а локальный файл очищаться — в этом случае важно учитывать, что флаг `-D` не требуется, так как агент сам удаляет старые правила перед вливанием новых.

### Анализ логов: ausearch и aureport

Файл журнала по умолчанию расположен в `/var/log/audit/audit.log`. Поиск событий по ключевому слову:

```bash
sudo ausearch -k user-modify
```

Типичный вывод содержит секции с `SYSCALL` и `PATH`, показывая какой процесс и с какими аргументами трогал отслеживаемый файл. Для получения сводной информации используют `aureport`:

```bash
sudo aureport -k   # сводка по ключам
sudo aureport -u   # отчёт о действиях пользователей
sudo aureport -f   # отчёт о файловых событиях
```

В SOC L1 эти инструменты применяются при ретроспективном анализе, но в промышленной эксплуатации логи auditd, как правило, отправляются в SIEM (Wazuh, Elastic) через настроенный плагин audisp или считываются агентом напрямую из файла. Аналитик видит уже нормализованные события, например, алерт Wazuh уровня 12 о модификации `/etc/passwd` с деталями в поле `audit.key`.

### Типичные ошибки и влияние на производительность

Неумеренный аудит системных вызовов может перегрузить ядро и демон auditd, особенно если не указаны фильтры. Например, правило `-a always,exit -S open` без дальнейших ограничений сгенерирует лавину событий. Рекомендуется:

- всегда использовать комбинацию `-F` для сужения области (по UID, пути, коду возврата);
- при аудите частых вызовов (open, read, write) ограничиваться конкретными файлами (`-F path=...`);
- избегать дублирования правил — порядок следования должен исключать лишние срабатывания;
- мониторить размер очереди: при переполнении события теряются, о чём auditd сигнализирует в своём логе.

Также важно не забывать об архитектуре: 64-битные системы требуют отдельных правил для arch=b64 и arch=b32, так как 32-разрядные приложения используют иные таблицы системных вызовов.

## Сквозной практический пример: выявление создания пользователя

В качестве демонстрации возможностей auditd рассмотрим кейс, типичный для SOC L1: обнаружение несанкционированного добавления учётной записи. Будем считать, что на хосте установлен auditd, текущий пользователь имеет права sudo, а логи аудита записываются в стандартный файл.

### Исходные условия
- ОС: Red Hat Enterprise Linux 8 (или совместимый)
- auditd установлен и запущен
- Файл конфигурации правил: `/etc/audit/rules.d/audit.rules`
- Цель: отследить изменение `/etc/passwd` и идентифицировать пользователя, инициировавшего операцию.

### Шаги

1. **Добавление правила в конфигурацию**

   Открываем файл правил и добавляем отслеживание записи и атрибутов для `/etc/passwd`:

   ```bash
   sudo tee -a /etc/audit/rules.d/audit.rules <<EOF
   -w /etc/passwd -p wa -k user-modify
   EOF
   ```

2. **Загрузка правила в подсистему аудита**

   Перезагружаем демон, чтобы правило вступило в силу:

   ```bash
   sudo service auditd reload
   ```

   Альтернативно, можно вручную загрузить правила:

   ```bash
   sudo auditctl -R /etc/audit/rules.d/audit.rules
   ```

3. **Верификация загруженного правила**

   Проверяем, что правило активно:

   ```bash
   sudo auditctl -l
   ```

   **Ожидаемый вывод** (будет присутствовать строка):

   ```
   -w /etc/passwd -p wa -k user-modify
   ```

4. **Генерация события аудита**

   Создаём тестового пользователя, что приведёт к изменению `/etc/passwd`:

   ```bash
   sudo useradd testuser
   ```

5. **Поиск и анализ события в журнале аудита**

   Используем `ausearch` с ключом, заданным в правиле:

   ```bash
   sudo ausearch -k user-modify
   ```

   **Иллюстративный фрагмент вывода** (значения времени и PID будут отличаться):

   ```
   ----
   time->Mon Mar 28 15:37:02 2024
   type=PROCTITLE msg=audit(1711640222.123:789): proctitle=7573657261646400746573747573657200
   type=PATH msg=audit(1711640222.123:789): item=0 name="/etc/passwd" inode=28931 dev=fc:01 mode=0100644 ouid=0 ogid=0 rdev=00:00 nametype=NORMAL cap_fp=0 cap_fi=0 cap_fe=0 cap_fver=0 cap_frootid=0
   type=CWD msg=audit(1711640222.123:789): cwd="/root"
   type=SYSCALL msg=audit(1711640222.123:789): arch=c000003e syscall=82 success=yes exit=0 a0=7fff1234 a1=1a4 a2=100 a3=0 items=1 ppid=2345 pid=2346 auid=1000 uid=0 gid=0 euid=0 suid=0 fsuid=0 egid=0 sgid=0 fsgid=0 tty=pts0 ses=1 comm="useradd" exe="/usr/sbin/useradd" key="user-modify"
   ```

   В записи `SYSCALL` видно: `comm="useradd"` (имя команды), `auid=1000` (исходный аутентифицированный пользователь), `uid=0` (реальный UID процесса, так как использован sudo), `key="user-modify"`. Это позволяет однозначно установить, что пользователь с логин UID 1000 выполнил useradd с повышенными привилегиями, изменив файл паролей.

   Дополнительно можно получить сводный отчёт:

   ```bash
   sudo aureport -k
   ```

   В выводе будет зафиксировано количество срабатываний ключа `user-modify`.

### Ожидаемый результат примера

Настроенный аудит позволил зарегистрировать факт изменения `/etc/passwd` с привязкой к конкретному пользователю (auid) и процессу (useradd). В SOC-системе такое событие было бы классифицировано как создание пользователя и, возможно, привело бы к созданию инцидента, если бы операция выполнялась без согласования.
