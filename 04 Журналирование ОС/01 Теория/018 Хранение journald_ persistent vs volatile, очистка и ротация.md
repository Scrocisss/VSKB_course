# Хранение journald: persistent и volatile, очистка и ротация

## Режимы хранения journald: persistent, volatile, auto и none
`systemd-journald` — централизованный демон сбора и хранения журнальных сообщений в Linux, заменивший классические syslog-демоны для систем на базе systemd. В отличие от текстовых файлов `/var/log/messages` и подобных, журнал хранится в структурированном бинарном формате, индексируется и запрашивается утилитой `journalctl`. Один из первых вопросов при построении инфраструктуры логирования, особенно для специалиста SOC L1, — **переживут ли журналы перезагрузку** и **сколько места они займут**. Ответ определяется параметром `Storage` в конфигурации `journald.conf`.

`Storage` может принимать четыре значения, каждое из которых задаёт целевую файловую систему и политику создания каталогов. Ниже приведена сравнительная таблица, описывающая эти режимы.

| Режим       | Целевой каталог                           | Сохранение после перезагрузки | Создание каталога при старте    | Поведение при невозможности записи на диск           |
|-------------|-------------------------------------------|-------------------------------|----------------------------------|------------------------------------------------------|
| `volatile`  | `/run/log/journal/` (tmpfs, в памяти)     | Нет, данные теряются          | Да, если отсутствует            | Не применимо, всегда в памяти                        |
| `persistent`| `/var/log/journal/` (на диске)            | Да, данные сохраняются        | Да, если отсутствует            | Fallback на `/run/log/journal/` (память)             |
| `auto`      | `/var/log/journal/` если каталог существует, иначе `/run/log/journal/` | Да, если каталог есть; иначе нет | Каталог `/var/log/journal` **не создаётся** автоматически | Аналогично persistent, но без принудительного создания |
| `none`      | —                                         | Нет, все данные отбрасываются | —                                | Не применимо; пересылка в syslog/kmsg/console может работать |

**Пояснения к поведению**:
- **`volatile`**: Журнал существует исключительно в оперативной памяти (tmpfs по пути `/run/log/journal`). При перезагрузке все записи безвозвратно удаляются. Это стратегия по умолчанию во встраиваемых системах или при желании минимизировать износ флеш-памяти (например, на Toradex-модулях, где производитель прямо рекомендует `volatile` для сохранения ресурса eMMC/Toradex Developer Center).
- **`persistent`**: Данные пишутся предпочтительно на диск в `/var/log/journal`. Если на раннем этапе загрузки диск ещё не смонтирован или недоступен для записи, journald временно сохраняет сообщения в `/run/log/journal` (в памяти), а затем при вызове `journalctl --flush` (или автоматически через `systemd-journal-flush.service`) переносит их на диск. Таким образом, даже в этом режиме непродолжительные сбои диска не приводят к потере логов — они будут сохранены в fallback-области и перемещены позже.
- **`auto`**: Режим по умолчанию в большинстве дистрибутивов. Если администратор вручную создал каталог `/var/log/journal`, поведение идентично `persistent`; иначе — `volatile`. Это позволяет простым созданием/удалением каталога управлять сохраняемостью журнала, не редактируя конфигурационные файлы. Например, в стандартной установке RHEL каталог отсутствует, и журнал теряется при перезагрузке.
- **`none`**: Все записи отбрасываются. Это не означает отсутствие сбора — демон продолжает принимать сообщения, но никуда не сохраняет. Полезно, если журнал пересылается в другую систему (syslog, сокет) и локальное хранение не нужно, но для SOC такой режим практически исключает локальное расследование инцидентов.

**Важный нюанс**: при изменении режима с `persistent` на `volatile` существующие данные на диске (`/var/log/journal`) автоматически не удаляются. Для их очистки требуется ручное вмешательство (см. раздел "Очистка"). При обратном переключении с `volatile` на `persistent` накопленные в памяти журналы можно принудительно сбросить на диск командой `journalctl --flush`, иначе они будут потеряны при следующей перезаписи или остановке демона.

Для SOC-аналитика критически важно понимать, что `volatile`-режим означает отсутствие исторических данных после перезагрузки, что может скрыть следы атаки, произошедшей до перезагрузки. Поэтому на продуктивных серверах настоятельно рекомендуется включать persistent-хранилище с одновременной настройкой лимитов (см. разделы "Очистка" и "Ротация").

## Внутреннее устройство хранилища journald
Файловая структура журнала организована по принципу «один каталог с бинарными файлами, принадлежащими конкретной системе». Это обеспечивает атомарность операций и целостность индексов. Основные компоненты и их взаимодействие представлены на схеме:

```text
[Ядро] ──► /dev/kmsg ──┐
[Службы systemd] ──► stdout/stderr ──┤
[Приложения через syslog()] ──► /run/systemd/journal/syslog ──┼──► [systemd-journald]
[SD-Journal API] ──► sd_journal_send() ──┘                     │
                                                               ├──► /run/log/journal/<machine-id>/*.journal  (Runtime, tmpfs)
                                                               │    (всегда активен, принимает все сообщения)
                                                               │
                                                               └──► вызов journalctl --flush или systemd-journal-flush.service
                                                                    переносит накопленные файлы в
                                                                    /var/log/journal/<machine-id>/*.journal (Persistent, диск)
```

**Ключевые точки**:
1. **Единая точка приёма** — journald слушает несколько источников: ядерный буфер `/dev/kmsg`, стандартные потоки служб (systemd перенаправляет stdout/stderr), сокет syslog, прямой API. Все сообщения структурируются и снабжаются полями (например, `_TRANSPORT=kernel`, `_SYSTEMD_UNIT=sshd.service`).
2. **Runtime-хранилище** — `/run/log/journal/<machine-id>/`. Machine-id — это уникальный идентификатор системы, гарантирующий изоляцию журналов разных хостов при централизованном сборе. Даже если настроен persistent-режим, journald начинает запись в runtime-каталог (tmpfs), чтобы не зависеть от готовности дисковой подсистемы. Позже специальный сервис `systemd-journal-flush.service` или ручной вызов `journalctl --flush` перемещают файлы из `/run` в `/var`.
3. **Persistent-хранилище** — `/var/log/journal/<machine-id>/`. Содержит как активный (текущий) файл журнала с расширением `.journal`, так и ротированные (архивные) файлы с расширением `.journal~`. Все файлы, не соответствующие этим суффиксам, демоном игнорируются. Это гарантирует, что временные, повреждённые или посторонние объекты не нарушат работу.
4. **Бинарный формат** — файлы представляют собой бинарные индексированные структуры, содержащие не только сообщения, но и их метаданные (временные метки, PID, UID, SELinux-контекст и др.). Такой формат позволяет быстро выполнять фильтрацию и поиск без разбора текста, но делает невозможным просмотр простыми утилитами вроде `cat` или `less` — требуется `journalctl`.
5. **Сжатие и запечатывание** — опционально. Параметр `Compress=yes` включает сжатие ротированных файлов (`*.journal~`) с помощью LZ4, уменьшая занимаемое место. `Seal=yes` активирует Forward Secure Sealing (FSS), добавляя криптографические метки, позволяющие впоследствии проверить целостность журнала. Эти механизмы влияют на производительность и могут быть отключены в высоконагруженных средах.

**Управление пространством** — базовая ротация встроена в логику самого journald. Демон отслеживает общий размер файлов в persistent-каталоге и при превышении порога удаляет самые старые архивные сегменты (с тильдой). Пороги задаются опциями `SystemMaxUse` (максимальный общий объём persistent-журнала) и `SystemKeepFree` (минимальный свободный объём на файловой системе). Аналогичные `Runtime*` опции действуют для runtime-хранилища. Более детально механизмы очистки и ротации описаны в соответствующих разделах.

Важно: если `/var/log/journal` не существует, а параметр `Storage=persistent`, journald автоматически создаст этот каталог. Однако в режиме `auto` создание не происходит — это ключевое различие. Настройки `SystemMaxUse` и другие применяются только к активному хранилищу, определяемому по тому, смонтирован ли `/var` и есть ли в нём каталог `/var/log/journal`.

## Очистка журналов journald: ручное и автоматическое освобождение места
Под очисткой (cleanup) подразумевается удаление накопленных журнальных данных для освобождения дискового пространства или принудительного сокращения глубины хранимой истории. Journald предоставляет два основных механизма: автоматическую очистку при превышении лимитов и ручные операции с помощью `journalctl --vacuum-*`.

**Автоматическая очистка по лимитам** срабатывает непрерывно. Как только общий размер файлов в активном хранилище (например, `/var/log/journal`) превышает значение `SystemMaxUse`, демон находит самые старые ротированные файлы (с суффиксом `.journal~`) и удаляет их до тех пор, пока общий размер не станет ниже порога с учётом требования `SystemKeepFree`. Эта операция прозрачна и не требует вмешательства администратора. По умолчанию `SystemMaxUse` установлен в 10% от размера файловой системы, но не более 4 ГБ, а `SystemKeepFree` — 15% или 4 ГБ (берётся меньшее). В результате на диске всегда остаётся достаточно места для других нужд.

**Ручная очистка** выполняется утилитой `journalctl` с подкомандами `--vacuum-size`, `--vacuum-time`, `--vacuum-files`. В отличие от простого удаления файлов в `/var/log/journal/`, эти команды корректно обновляют внутренние индексы и не нарушают целостность базы журнала.

Примеры из реальной практики (на основе выдержки [nbailey.ca](https://nbailey.ca/post/clean-the-systemd-journal)):

```bash
# Освободить место, чтобы общий размер журнала не превышал 500 МБ
sudo journalctl --vacuum-size=500M
```

Вывод команды будет содержать список удалённых архивных файлов и итоговый объём освобождённого места:
```
Deleted archived journal /var/log/journal/f8dfbb5a095c4855a5f326d99bb598a6/system@a1b2...journal~ (24.5M).
Deleted archived journal /var/log/journal/f8dfbb5a095c4855a5f326d99bb598a6/system@c3d4...journal~ (18.2M).
...
Vacuuming done, freed 488.1M of archived journals from /var/log/journal/f8dfbb5a095c4855a5f326d99bb598a6.
```

```bash
# Удалить все записи старше 2 дней
sudo journalctl --vacuum-time=2d
```

```bash
# Оставить только последние 20 файлов журнала (активный + архивные)
sudo journalctl --vacuum-files=20
```

Эти команды работают исключительно с архивными файлами (`.journal~`). Текущий активный файл (`.journal`) не затрагивается, если только не используется специальный сигнал ротации (см. раздел "Ротация"). Удаление происходит по одному файлу за раз, что безопасно даже при нехватке inode.

**Неправильные, но иногда встречающиеся подходы**:
- Ручное удаление файлов из `/var/log/journal/` — journald может не распознать исчезновение данных и оставить мусорные индексы, что приведёт к ошибкам при последующих запросах. Производители (и сообщество) прямо предостерегают от такого способа.
- Использование `rm -rf /run/log/journal` для очистки runtime-хранилища — хотя технически это возможно, лучше применять `journalctl --flush` для переноса в persistent и затем вакуумирование.

**Особый случай**: после изменения `Storage` с `persistent` на `volatile` старые данные на диске останутся нетронутыми. Для их полной зачистки необходимо сначала переключить режим на `volatile`, перезапустить journald, а затем вручную удалить каталог `/var/log/journal` (после остановки демона) или, если требуется сохранить часть, выполнить `journalctl --vacuum-time=1s` (удалить всё).

Для специалиста SOC важно помнить, что очистка может уничтожить криминалистически значимые артефакты. Поэтому перед радикальной очисткой на боевых системах следует снимать криминалистический образ журнала с помощью `journalctl -o export > /evidence/journal-export.txt` или копирования бинарных файлов на внешний носитель.

## Ротация журналов: управление размером, временем и количеством файлов
Ротация журналов в journald принципиально отличается от классического `logrotate`. Вместо работы с текстовыми файлами, journald ротирует бинарные сегменты по достижению определённых лимитов, создавая архивированные копии с суффиксом `~`. Параметры ротации настраиваются в секции `[Journal]` файла `journald.conf`. Понимание этих параметров критически важно для баланса между глубиной хранимой истории и производительностью (как подчёркнуто в обсуждениях Arch Linux, большие журналы замедляют `journalctl` и могут влиять на время загрузки).

Все параметры ротации можно разделить на три группы: лимиты размера одного файла, лимиты количества файлов и временные ограничения. Их взаимодействие определяет, когда текущий файл закрывается, архивируется и когда старые архивы удаляются.

**Параметры, определяющие ротацию и хранение**:

| Параметр | Область действия | Описание | Значение по умолчанию |
|----------|-----------------|----------|------------------------|
| `SystemMaxFileSize` | Persistent (/var) | Максимальный размер одного файла журнала. При достижении — текущий файл закрывается и архивируется (получает `~`), создаётся новый. | 1/8 от `SystemMaxUse`, но не более 128 МБ |
| `RuntimeMaxFileSize` | Runtime (/run) | Аналог для runtime-хранилища. | 1/8 от `RuntimeMaxUse`, макс 128 МБ |
| `SystemMaxFiles` | Persistent | Максимальное количество файлов (активный + архивные) в `/var/log/journal`. При превышении самые старые архивы удаляются. | 100 |
| `RuntimeMaxFiles` | Runtime | Аналог для runtime. | 100 |
| `MaxFileSec` | Любое | Максимальное время до ротации текущего файла. Полезно для создания равномерных по времени сегментов. | не задано (ротация только по размеру) |
| `MaxRetentionSec` | Persistent / Runtime | Максимальное время хранения записей. Записи старше этого срока автоматически удаляются при любой возможности (не только при ротации). Может использоваться совместно с другими ограничениями. | не задано (ограничений по возрасту нет) |
| `SystemMaxUse` | Persistent | Общий максимальный объём persistent-журнала. При превышении запускается удаление старейших архивов. | 10% файловой системы, но ≤4 ГБ |
| `RuntimeMaxUse` | Runtime | Общий максимальный объём runtime-журнала. | 10% tmpfs, ≤4 ГБ |
| `SystemKeepFree` | Persistent | Минимальное свободное место на файловой системе, которое journald должен оставить. | 15% или 4 ГБ |
| `RuntimeKeepFree` | Runtime | Аналог для tmpfs. | 15% или 4 ГБ |

**Механизм ротации** работает следующим образом:
1. Текущий активный файл (например, `system.journal`) наполняется записями.
2. Если его размер достигает `SystemMaxFileSize` или истекает период `MaxFileSec`, journald закрывает файл, переименовывает его, добавляя суффикс `~` (например, `[email protected]~`), и создаёт новый активный файл `system.journal`.
3. Если количество файлов в каталоге превышает `SystemMaxFiles`, удаляется самый старый архивный файл.
4. Фоновый процесс постоянно следит за общим размером: когда он превосходит `SystemMaxUse`, удаляются самые старые архивные файлы (без учёта временных меток внутри — удаление идёт по имени файла, которое отражает примерное время). То же происходит при снижении свободного места ниже `SystemKeepFree`.
5. При наличии `MaxRetentionSec` дополнительно удаляются все записи старше указанного срока; для этого journald может удалить весь файл, если все его записи старше лимита.

**Практический пример настройки для SOC-среды** (иллюстративный конфигурационный сниппет в стиле `/etc/systemd/journald.conf.d/00-soc-retention.conf`):

```ini
[Journal]
Storage=persistent
SystemMaxUse=2G
SystemKeepFree=1G
SystemMaxFileSize=128M
SystemMaxFiles=50
MaxRetentionSec=6month
MaxFileSec=1week
Compress=yes
```

Такая конфигурация гарантирует хранение журналов за последние 6 месяцев, сегментирование по неделям, ограничение общего объёма 2 ГБ с резервированием 1 ГБ свободного места и максимальным размером одного файла 128 МБ, что даёт приемлемую скорость запросов `journalctl`.

**Когда ротации недостаточно**: если необходима история глубже, чем позволяет `SystemMaxUse`, либо требуется хранить логи годами, можно параллельно настроить пересылку в классический syslog (через `ForwardToSyslog=yes`) и использовать `logrotate` для текстовых файлов `/var/log/messages`. В этом случае journald работает как высокоскоростной краткосрочный буфер, а syslog обеспечивает долгосрочное текстовое архивирование. Такой гибридный подход описан в сообществе Arch Linux, где пользователи сталкиваются с проблемой медленного `journalctl` при огромных журналах.

**Важно для SOC**:
- Ротация не делает журнал недоступным — архивные файлы с `~` по-прежнему читаются `journalctl` без дополнительных действий.
- При атаке типа «забивание диска логами» (log flooding) правильно настроенные лимиты `SystemMaxUse` и `MaxRetentionSec` защитят файловую систему от переполнения, но могут ускорить потерю старых записей. Поэтому критически важно настроить мониторинг заполнения журнала и своевременное реагирование на аномальный рост (например, отправка алерта при превышении порога `SystemMaxUse` на 80%).

## Сквозной практический пример: настройка persistent-журнала, лимитов и очистки на RHEL 9
**Исходные условия**: свежеустановленная система RHEL 9 с настройками по умолчанию (`Storage=auto`, каталог `/var/log/journal` отсутствует). Цель — включить постоянное хранение, задать лимиты, продемонстрировать ротацию и ручную очистку. Все действия выполняются от root.

**Шаг 1. Проверка текущего состояния и включение persistent**
```bash
# Проверим, куда пишется журнал (должен быть /run/log/journal)
ls -l /var/log/journal 2>&1
# Ожидаемый вывод: "ls: cannot access '/var/log/journal': No such file or directory"

# Создаём каталог для постоянного хранения
mkdir -p /var/log/journal
systemd-tmpfiles --create --prefix /var/log/journal   # корректные права
# После этого, так как режим auto, логи начнут сохраняться постоянно.
# Чтобы быть уверенным, явно зададим persistent в конфигурации:
echo -e "[Journal]\nStorage=persistent" > /etc/systemd/journald.conf.d/00-persistent.conf
systemctl restart systemd-journald
```

**Шаг 2. Настройка лимитов размера и ротации**
```bash
cat > /etc/systemd/journald.conf.d/10-limits.conf <<EOF
[Journal]
SystemMaxUse=300M
SystemKeepFree=100M
SystemMaxFileSize=50M
SystemMaxFiles=20
MaxRetentionSec=30day
Compress=yes
EOF
systemctl restart systemd-journald
# Проверим применение параметров
journalctl --disk-usage
# Пример вывода: "Archived and active journals take up 15.3M on disk."
```

**Шаг 3. Принудительная ротация и наблюдение**
```bash
# Вызовем немедленную ротацию текущего файла
journalctl --rotate
# Теперь в /var/log/journal/<machine-id>/ появится архивный файл *.journal~
ls -lh /var/log/journal/*/
# Вывод покажет несколько файлов, среди них system.journal и [email protected]~
journalctl --list-boots  # список загрузок, убедимся, что записи доступны
```

**Шаг 4. Симуляция наполнения и очистка через vacuum**
```bash
# Сгенерируем нагрузку (пример) — множество сообщений от тестового процесса
for i in {1..20000}; do logger "Test message $i for journal filling"; done
# Через некоторое время размер журнала вырастет.
journalctl --disk-usage
# Допустим, вывод: "Archived and active journals take up 280.0M on disk."
# Применим ручное освобождение, чтобы уложиться в 200M
journalctl --vacuum-size=200M
# Пример вывода:
# Deleted archived journal .../system@xxx.journal~ (35.2M).
# Vacuuming done, freed 80.0M of archived journals.
# Проверим итоговый размер
journalctl --disk-usage
# Теперь около 200M.
```

**Ожидаемый вывод**: демонстрация того, как настройка `Storage=persistent` и лимиты влияют на поведение журнала, как ротация создаёт архивированные сегменты, и как `--vacuum-size` безопасно освобождает место, удаляя исключительно старые ротированные файлы.
