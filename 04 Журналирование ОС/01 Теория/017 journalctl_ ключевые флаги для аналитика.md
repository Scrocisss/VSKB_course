# journalctl: ключевые флаги для SOC-аналитика

## 1. journalctl в инфраструктуре логирования Linux: архитектура и назначение

`journalctl` — штатная утилита системного менеджера `systemd`, предоставляющая унифицированный доступ к журналу событий, который ведёт демон `systemd-journald`. В отличие от классических текстовых логов, рассредоточенных по `/var/log/messages`, `/var/log/syslog` и десяткам других файлов, journald собирает сообщения ядра, системных служб и пользовательских процессов в централизованное хранилище с бинарной индексацией. Для SOC-аналитика это означает, что один инструмент способен быстро ответить на вопросы «что происходило с процессом sshd последние 15 минут?» или «были ли ошибки аутентификации после 02:00?» без конкатенации и построчной фильтрации нескольких текстовых файлов.

Исторически сбор логов в Linux опирался на демоны семейства syslog (rsyslog, syslog-ng), которые записывали сообщения в plaintext-файлы каталога `/var/log`. Каждая подсистема (аутентификация, ядро, почта) имела собственный файл, а администратор использовал цепочки `grep`, `tail`, `awk` для извлечения нужной информации. С внедрением systemd, чья главная цель — унификация управления службами, журнал также был переосмыслен: вместо разрозненных текстовых артефактов появилось структурированное бинарное хранилище с возможностью высокопроизводительной фильтрации и обогащения метаданными. `rsyslog` и journald могут сосуществовать: большинство дистрибутивов по умолчанию перенаправляют сообщения из journald в традиционные файлы, но для оперативного расследования journalctl — первичный инструмент, потому что он обращается напрямую к «первоисточнику» ещё до того, как данные будут преобразованы в текстовый формат.

Центральное место journalctl в современной экосистеме иллюстрирует следующая схема, показывающая поток данных от источников к аналитику.

```text
         ┌─────────┐    ┌───────────┐    ┌────────────┐    ┌──────────┐
Ядро ───▶│         │    │           │    │            │    │          │
Службы ─▶│ journald│───▶│  бинарный  │◀───│ journalctl │───▶│ Аналитик │
Прилож.─▶│ (сбор)  │    │   журнал   │    │ (запросы)  │    │          │
         └─────────┘    └───────────┘    └────────────┘    └──────────┘
              │                                      ▲
              │    ┌───────────┐                    │
              └───▶│  rsyslog  │───▶ текстовые файлы│
                   └───────────┘    /var/log/*.log  │
                                                   │
              Альтернативный доступ: less, grep ───┘
```

Источники (ядро, службы) отправляют сообщения через сокеты `/dev/log`, `/run/systemd/journal/socket` и другие механизмы непосредственно в демон journald. Тот записывает их в бинарное хранилище, обычно расположенное в `/var/log/journal/` (при включённом постоянном хранении) или `/run/log/journal/` (временное, в памяти). Параллельно `rsyslog` может получать эти же сообщения и дублировать их в привычные текстовые файлы. Однако `journalctl` взаимодействует напрямую с бинарным хранилищем, минуя прослойку текстовых логов, что и даёт выигрыш в скорости и выразительности запросов.

Значение этой архитектуры для специалиста уровня SOC L1 трудно переоценить. Во-первых, journald автоматически добавляет к каждому событию метаполя: идентификатор процесса (`_PID`), пользователя (`_UID`), имя юнита systemd (`_SYSTEMD_UNIT`), уникальный номер загрузки (`_BOOT_ID`) и монотонные/реальные временные метки. Все эти поля доступны как критерии фильтрации, что избавляет от необходимости вручную разбирать временные штампы и строки идентификации службы. Во-вторых, структурированность записей позволяет легко экспортировать события в JSON-формат для передачи в SIEM-систему (MaxPatrol SIEM, Splunk, Elastic) либо для дальнейшего программного анализа. В-третьих, поддержка запросов по диапазону времени, приоритету, конкретному юниту или даже бинарному исполняемому файлу даёт возможность локализовать инцидент за считанные секунды, что критически важно при первичной сортировке алертов.

Для полноты понимания важно развести `journalctl` и текстовые инструменты, которые всё ещё применяются при работе с унаследованными или резервными копиями. Следующая таблица фиксирует ключевые различия.

| Характеристика          | journalctl                                              | grep / less по текстовым логам                    |
|-------------------------|---------------------------------------------------------|----------------------------------------------------|
| Формат хранилища        | Бинарный, индексированный                               | Текстовый (plaintext)                              |
| Структура записей       | Строго типизированные поля (`_PID`, `_UID`, `PRIORITY`) | Неструктурированный текст, разбирается вручную     |
| Скорость поиска         | На основе индексов, быстрый доступ к диапазонам времени | Линейное сканирование файла, медленно на больших объёмах |
| Фильтрация              | По полям, времени, юнитам, приоритету                   | По регулярным выражениям, контекстным строкам      |
| Передача в SIEM         | Прямой экспорт в JSON (`-o json`)                      | Требует парсинга, нормализации                     |
| Зависимость от служб    | Требует работающего `systemd-journald`                  | Только чтение файлов, не зависит от journald       |
| Сохранность после перезагрузки | При постоянном хранилище доступен предыдущий журнал (`-b -1`) | Определяется политикой ротации логов       |

Таким образом, `journalctl` не является заменой текстовой утилите `grep`, но представляет собой специальный инструмент для работы с живым журналом systemd, заточенный под разбор инцидентов в реальном времени и предоставляющий гораздо более мощную семантику запросов. В SOC-практике предпочтение всегда отдаётся journalctl для получения первичной картины события, тогда как текстовые архивы задействуются для исторического анализа или в ситуациях, когда journal-хранилище недоступно.

## 2. Внутреннее устройство systemd-journald: структура записей и поля

Демон `systemd-journald` собирает события из нескольких источников: буфера сообщений ядра (`/dev/kmsg`), системного сокета `/dev/log`, перенаправленных потоков stdout/stderr служб, запущенных через systemd, а также через собственное API, доступное по сокету `/run/systemd/journal/socket`. Каждое поступившее сообщение преобразуется в запись — структурированную единицу, состоящую из набора полей «ключ-значение». Именно эти поля лежат в основе всех механизмов фильтрации, доступных через `journalctl`, и понимание их семантики обязательно для эффективного поиска.

Хранение записей реализовано в виде бинарного журнала с последовательной записью и множественными индексами. Файлы журнала (с расширением `.journal`) размещаются в каталоге `/var/log/journal/` при условиях, что том смонтирован с опцией `acl`, а права доступа позволяют journald создавать свой каталог. Каждый файл содержит набор объектов‑записей, упакованных в контейнеры; индексы расположены в том же файле и связывают идентификаторы полей с их значениями, а также поддерживают быстрый поиск по времени и идентификатору загрузки. Благодаря хранению полей в нормализованной форме (имя поля хранится один раз, а значения ссылаются на него) достигается высокая степень сжатия — журнал объёмом несколько сотен мегабайт способен вместить миллионы событий без существенного роста.

Центральным понятием является поле записи. Оно обладает именем в верхнем регистре (иногда с префиксом `_` для обозначения предопределённых метаполей), типом (строка, целое, 64-битное беззнаковое и т.п.) и значением. Следующая JSON-подобная структура иллюстрирует типичный набор полей, который можно наблюдать при экспорте записи journald (конкретные значения зависят от среды и служат лишь демонстрацией схемы).

```json
{
  "__CURSOR": "s=6a1f4b7d...",
  "__REALTIME_TIMESTAMP": "1696760400123456",
  "__MONOTONIC_TIMESTAMP": "1234567890123",
  "_BOOT_ID": "b9c6a8d4e2f14a7eb1c0d3e5f6a7b8c9",
  "_UID": "0",
  "_GID": "0",
  "_PID": "10342",
  "_COMM": "sshd",
  "_EXE": "/usr/sbin/sshd",
  "_SYSTEMD_UNIT": "sshd.service",
  "_SYSTEMD_CGROUP": "/system.slice/sshd.service",
  "_HOSTNAME": "srv-lnx-01",
  "_MACHINE_ID": "d8e7f6a5b4c3d2e1f0a9b8c7d6e5f4a3",
  "PRIORITY": "6",
  "SYSLOG_FACILITY": "10",
  "SYSLOG_IDENTIFIER": "sshd",
  "MESSAGE": "Failed password for root from 192.168.1.100 port 22 ssh2",
  "_TRANSPORT": "syslog",
  "_SOURCE_REALTIME_TIMESTAMP": "1696760400123400"
}
```

Прокомментируем основные группы полей, опираясь на их фактическое назначение.

**Идентификаторы источника.** `_SYSTEMD_UNIT` — имя юнита systemd, породившего событие (чаще всего `.service`). Именно это поле используется при фильтрации по флагу `-u`. `_COMM` — имя исполняемого файла (без пути), `_EXE` — полный путь к бинарному файлу. `_PID` и `_UID`/`_GID` позволяют привязать запись к конкретному процессу и его владельцу, что крайне полезно при анализе подозрительной активности: например, поиск событий от процессов, запущенных от пользователя `www-data`, но имеющих доступ к нехарактерным для него ресурсам.

**Временные метки.** `__REALTIME_TIMESTAMP` — монотонно возрастающее 64-битное число микросекунд с начала эпохи Unix, используемое для фильтрации по реальному времени (`--since`, `--until`). `__MONOTONIC_TIMESTAMP` — время в микросекундах с момента загрузки системы, не подверженное скачкам при ручной установке часов; применяется для точной корреляции событий внутри одной загрузки. Поле `_BOOT_ID` уникально для каждой загрузки, что позволяет отфильтровать события конкретного сеанса работы ОС (`-b`).

**Приоритет и служба syslog.** `PRIORITY` — целое число от 0 (emergency) до 7 (debug), соответствующее уровням syslog (RFC 5424). Запись `"6"` в примере означает информационное сообщение (info). Фильтрация по приоритету (`-p`) аналитиком чаще всего применяется с порогом `warning` (4) или `err` (3), чтобы отсечь отладочную информацию и сосредоточиться на аномалиях. Поле `SYSLOG_FACILITY` указывает на категорию источника (ядерные сообщения, аутентификация, демоны и т.п.), однако в практике SOC-аналитика чаще используется привязка к юниту или конкретному бинарному файлу.

**Сообщение и транспорт.** `MESSAGE` — собственно текст события в кодировке UTF-8. Поле `_TRANSPORT` указывает, каким способом запись попала в journal: `syslog` — через стандартный syslog-сокет, `stdout` — из стандартного вывода службы, `journal` — через собственный API, `kernel` — от ядра. Эти сведения незаменимы при траблшутинге: если сообщения от сервиса не появляются, проверка транспорта помогает понять, корректно ли служба интегрирована с journald.

**Курсор и идентификатор записи.** `__CURSOR` — уникальная строка, однозначно идентифицирующая запись в журнале. Применяется для продолжения чтения с определённой точки без повторной фильтрации по времени, что особенно удобно при скриптовом обходе больших массивов.

Благодаря тому, что journald индексирует именно поля, фильтры `journalctl` работают не как текстовый поиск, а как сравнение значений в индексе. Например, запрос `_PID=10342` немедленно найдёт все записи от процесса с этим идентификатором, не сканируя весь журнал. Аналогично, `_UID=0` отберёт события, инициированные суперпользователем. Этот механизм позволяет на лету строить сложные выборки, комбинируя несколько критериев, что для txt-файлов потребовало бы написания многоступенчатого конвейера grep'ов.

Необходимо учитывать ограничения: journald по умолчанию хранит данные в разреженном кольцевом буфере в `/run/log/journal`, который очищается при перезагрузке; для постоянного хранения администратор должен создать каталог `/var/log/journal` и настроить ограничения дискового пространства в `/etc/systemd/journald.conf`. В распределённой инфраструктуре без централизованного SIEM аналитик обязан проверять наличие постоянного журнала, иначе инцидент, произошедший до перезагрузки, может остаться без следов. Также журнал может быть настроен на ограничение максимального размера (по умолчанию — 10% от файловой системы), что при интенсивном логировании приводит к вытеснению старых событий; при расследовании давних инцидентов приходится обращаться к текстовым архивам rsyslog.

## 3. Применение journalctl: ключевые флаги и аналитические приемы

Практическая работа аналитика SOC L1 с `journalctl` строится вокруг нескольких повторяющихся сценариев: первичный осмотр событий конкретного сервиса, изоляция временного окна инцидента, отслеживание подозрительной активности в реальном времени и подготовка данных для эскалации в SIEM. Ниже перечислены ключевые флаги утилиты, сгруппированные по этим задачам, с пояснением логики их применения и примерами команд.

**Просмотр событий определённого юнита.** Флаг `-u` (или `--unit=`) принимает имя systemd-юнита и ограничивает вывод записями, у которых поле `_SYSTEMD_UNIT` совпадает с указанным. Это основной способ привязаться к сервису, например, SSH, веб-серверу или базе данных.  
```bash
journalctl -u sshd.service
```  
Вывод покажет все события, относящиеся к службе SSH, включая старт, остановку, ошибки аутентификации, смену конфигурации. Если точное имя юнита неизвестно, можно использовать автодополнение командной оболочки или просмотреть список активных юнитов через `systemctl list-units --type=service`.

**Фильтрация по времени.** Инцидент всегда имеет временные границы. Флаги `--since` и `--until` позволяют задать начало и конец временного окна в абсолютном (`"YYYY-MM-DD HH:MM:SS"`) или относительном (`"5 min ago"`, `"yesterday"`) формате. Комбинирование обоих флагов даёт точный срез периода предполагаемой активности.  
```bash
journalctl -u sshd.service --since "2025-06-15 09:30:00" --until "2025-06-15 10:00:00"
```  
В SOC-работе часто используется относительный синтаксис: при поступлении алерта о подозрительном входе аналитик немедленно выполняет `--since "15 min ago"`, чтобы охватить последние минуты до и после инцидента.

**Работа с уровнями критичности.** Флаг `-p` (или `--priority=`) фильтрует записи по максимальному значению приоритета syslog, в порядке возрастания серьёзности: 7 — debug, 6 — info, 5 — notice, 4 — warning, 3 — err, 2 — crit, 1 — alert, 0 — emerg. Передавая одно число, мы получаем все сообщения с таким приоритетом и выше. Для быстрого отсева штатного шума хорошей практикой является старт с `warning`.  
```bash
journalctl -u sshd.service -p warning --since "1 hour ago"
```  
Эта команда покажет только предупреждения, ошибки и критические события службы ssh за последний час, что мгновенно выделит подозрительные или сбойные ситуации.

**Слежение в реальном времени.** Флаг `-f` (или `--follow`) включает режим, аналогичный `tail -f`: после вывода последних записей утилита продолжает ожидать новые и отображает их по мере поступления. Этот приём критичен во время активной атаки — например, при брутфорсе SSH — так как позволяет наблюдать попытки подбора паролей в прямом эфире и оперативно реагировать.  
```bash
journalctl -u sshd.service -f
```

**Фильтрация по отдельным полям.** Помимо высокоуровневых флагов, `journalctl` поддерживает прямое указание пар «поле=значение». Наиболее ходовые в SOC-контексте: `_PID=<pid>` (события конкретного процесса), `_UID=<uid>` (действия определённого пользователя), `_COMM=<имя>` (процессы по имени исполняемого файла), `_TRANSPORT=stdout` (только то, что попало из stdout служб).  
```bash
journalctl _UID=0 _COMM=sshd --since "10 min ago"
```  
Эта выборка возвращает действия, выполненные процессом sshd от имени root за последние 10 минут — мощный фильтр для выявления попыток эксплуатации уязвимостей с эскалацией привилегий.

**Ограничение количества вывода.** В первичной фазе анализа, особенно при больших журналах, полезно сначала взять несколько последних записей (`-n 100`) или обратиться к конкретной загрузке системы (`-b` для текущей, `-b -1` для предыдущей).  
```bash
journalctl -u sshd -b -n 20
```  
Показывает 20 последних событий SSH, зарегистрированных с момента текущей загрузки. Это быстрая проверка, не было ли явных проблем при старте системы.

**Выбор формата вывода.** По умолчанию `journalctl` отображает записи в пейджере, похожем на `less`, с цветовым выделением. Для последующей программной обработки или отправки в SIEM наиболее востребован JSON - его обеспечивает опция `-o json` (одна строка на запись) или `-o json-pretty` (удобочитаемый многострочный вывод). Кроме того, доступны `export` (бинарный формат, пригодный для переноса между системами) и `short-iso` (классический syslog-стиль с ISO-метками времени).  
```bash
journalctl -u sshd -p err --since "today" -o json-pretty
```

**Комбинирование фильтров.** Все перечисленные флаги могут объединяться. Например, чтобы извлечь ошибки аутентификации, случившиеся сегодня, от службы `sshd`, порождённые процессами с именем `sshd`, с приоритетом не ниже warning и вывести в JSON для SIEM, используется:  
```bash
journalctl -u sshd _COMM=sshd -p warning --since "today" -o json
```

**Типичные ошибки и подводные камни.** Новички часто забывают, что при работе в обычной учётной записи вывод может быть ограничен правами доступа: journalctl по умолчанию показывает только те сообщения, на которые у текущего пользователя есть права. Если аналитик входит в группу `adm` или `systemd-journal`, доступ расширяется до всех системных логов. При отсутствии привилегий результаты фильтрации могут оказаться пустыми даже при наличии событий. Другая распространённая ошибка — отсутствие постоянного хранилища (`/var/log/journal`), из-за чего после перезагрузки недоступны старые записи. Наконец, применение слишком широкого временного окна без `-n` может привести к загрузке сотен тысяч строк и задержке пары десятков секунд, поэтому всегда рекомендуется ограничивать период или количество.

## 4. Сквозной практический пример: расследование bruteforce-атаки на SSH

**Исходные условия.** Сервер на базе Ubuntu 24.04 LTS, постоянное хранилище journald настроено (каталог `/var/log/journal` существует). SOC-аналитику L1 поступает алерт от IDS о множественных ошибках входа на SSH за последние 10 минут. Необходимо подтвердить или опровергнуть атаку, идентифицировать источник и подготовить артефакты для эскалации. Аналитик имеет учётную запись в группе `adm` и доступ по SSH к серверу.

**Шаг 1. Первичный осмотр логов службы sshd за аномальный период.**  
Запрос: вывести все события юнита `sshd.service` с момента, на 15 минут предшествующего текущему моменту (чуть больше, чем временное окно алерта, чтобы захватить возможную подготовку).

```bash
journalctl -u sshd.service --since "15 min ago"
```

Ожидаемый вывод (иллюстративная схема):

```
Jun 15 09:45:22 srv-lnx-01 sshd[10342]: Failed password for root from 203.0.113.45 port 55122 ssh2
Jun 15 09:45:23 srv-lnx-01 sshd[10342]: Connection closed by authenticating user root 203.0.113.45 port 55122 [preauth]
Jun 15 09:45:25 srv-lnx-01 sshd[10343]: Failed password for root from 203.0.113.45 port 55123 ssh2
...
Jun 15 09:54:50 srv-lnx-01 sshd[10450]: Failed password for admin from 203.0.113.45 port 55310 ssh2
Jun 15 09:54:51 srv-lnx-01 sshd[10450]: Connection closed by authenticating user admin 203.0.113.45 port 55310 [preauth]
```

Аналитик видит монотонные записи вида «Failed password» и «Connection closed», все с одного IP-адреса, что уже является сильным индикатором bruteforce-атаки. За короткий промежуток зафиксированы десятки попыток.

**Шаг 2. Фильтрация по приоритету для оценки критичности.**  
Чтобы отделить ошибки аутентификации от информационных сообщений (старт сервиса, перезагрузка конфигурации), сузим выборку до уровня `err` и выше.

```bash
journalctl -u sshd.service -p err --since "15 min ago"
```

Вывод будет содержать только строки, начинающиеся с `sshd[...]: Failed password ...`, что подтверждает концентрацию неуспешных попыток без вспомогательного шума. Это ускоряет подсчёт количества атакованных учётных записей: в примере фигурируют `root` и `admin`.

**Шаг 3. Быстрый поиск по ключевому слову и уточнение источника.**  
Хотя поле `MESSAGE` содержит нужную информацию, для быстрой выдержки можно применить стандартный grep, но лучше воспользоваться дополненным конвейером с извлечением уникальных IP.

```bash
journalctl -u sshd.service --since "15 min ago" -o cat | grep "Failed password" | awk '{print $(NF-3)}' | sort | uniq -c
```

Здесь `-o cat` убирает лишние метаполя и отдаёт только сообщение. Ожидаемый результат:

```
     48 203.0.113.45
```

Он показывает, что атакующий использует один и тот же IP, а количество попыток велико. Это облегчает принятие решения о блокировке.

**Шаг 4. Наблюдение в реальном времени для проверки продолжающейся активности.**  
Прежде чем блокировать адрес, полезно удостовериться, что атака всё ещё идёт, и принять меры динамически.

```bash
journalctl -u sshd.service -f
```

Экран начнёт заполняться новыми записями «Failed password» с периодичностью 1–2 в секунду, что визуально подтверждает активную атаку. Аналитик может немедленно передать информацию сменному администратору для блокировки IP на межсетевом экране (например, через iptables/fail2ban).

**Шаг 5. Подготовка артефактов для эскалации в SIEM.**  
Для документирования инцидента и загрузки в SIEM-систему требуется структурированный экспорт.

```bash
journalctl -u sshd.service -p err --since "15 min ago" -o json > /tmp/bruteforce_sshd.json
```

Результирующий файл содержит массив JSON-объектов, каждый с полями, описанными в разделе 2, включая временные метки, IP-адрес, имя пользователя и PID процесса. Эти данные могут быть напрямую импортированы в MaxPatrol SIEM, Splunk или Elastic для дальнейшей корреляции с другими событиями (например, с последующим успешным входом).

**Ожидаемый вывод примера.** Сквозной сценарий демонстрирует, что, используя всего несколько флагов `journalctl`, аналитик за 2–3 минуты способен подтвердить bruteforce-атаку на SSH, определить источник, оценить масштаб и подготовить материал для эскалации и блокировки. Кейс подчёркивает эффективность `-u` для привязки к сервису, `--since` для изоляции временного окна, `-p` для фильтрации серьёзных ошибок и `-o json` для интеграции с SIEM. Именно эти приёмы входят в обязательный арсенал SOC L1 при работе с журналами Linux.
