# Конфигурация Sysmon для аналитика L1

## 1. Системный монитор Sysmon в цепочке поставки данных SOC: роль и ключевые понятия

Sysmon (System Monitor) — системная служба и драйвер уровня ядра Windows, входящая в состав набора Sysinternals. Она фиксирует в операционном журнале событий («Applications and Services Logs/Microsoft/Windows/Sysmon/Operational») детализированную телеметрию процессов, сетевых соединений, операций с файлами, реестром, загрузкой образов и рядом других действий. Для аналитика уровня L1 Sysmon выступает одним из основных источников данных о состоянии конечной точки: его события агрегируются SIEM-системой и служат базой для правил корреляции, детектирования и первичного триажа инцидентов.

Стандартные журналы безопасности Windows (Security Log) регистрируют преимущественно события аудита учётных записей, входов и привилегий, тогда как Sysmon существенно расширяет область видимости. Различия сведены в таблице ниже.

| Характеристика | Windows Security Log (стандартный аудит) | Sysmon |
|----------------|-------------------------------------------|--------|
| **Субъект телеметрии** | События безопасности ОС: входы (4624/4625), доступ к объектам, изменение политик | Активность процессов, сетевые соединения, загрузка DLL/драйверов, создание/удаление файлов, прямой доступ к диску, перехват буфера обмена и др. |
| **Командная строка и хеши процессов** | Не регистрируются централизованно (только если отдельно включён аудит создания процессов, event 4688 с ограниченной полнотой) | Регистрируются полная командная строка, хеши образа (MD5, SHA1, SHA256, IMPHASH), идентификатор родительского процесса, GUID процесса — Event ID 1 |
| **Сетевые соединения** | Не регистрируются в Security Log (только через аудит Filtering Platform, что требует сложной настройки) | Event ID 3: источник/назначение IP и порт, протокол, образ процесса, GUID процесса |
| **Гранулярность фильтрации** | Включение/выключение категорий аудита через политику (`auditpol`), без возможности тонких исключений на уровне отдельных исполняемых файлов или сетевых IP | Конфигурационный XML-файл позволяет задавать include/exclude-правила по полному пути образа, хешу, командной строке, IP-адресам и другим атрибутам — фильтрация на стороне драйвера |
| **Устойчивость к отключению** | Аудит может быть остановлен злоумышленником с правами администратора без дополнительных средств защиты | Sysmon регистрирует собственное изменение состояния (Event ID 4), а остановка службы также видна, что усложняет скрытное подавление логов |
| **Роль в SOC** | Используется для базового мониторинга учётных записей и аутентификации, соответствия нормативным требованиям (например, PCI DSS) | Основной источник для обнаружения аномалий процессов, C2-коммуникаций, закрепления в системе (persistence), инжекций кода и других техник MITRE ATT&CK |

Ключевые идентификаторы событий Sysmon, которые должны быть знакомы аналитику L1, перечислены в документации Microsoft и руководствах сообщества:  
- **Event ID 1: Process Creation** — запуск процесса; содержит поля `Image`, `CommandLine`, `ParentProcessId`, `Hashes`.  
- **Event ID 3: Network Connection** — исходящее/входящее TCP/UDP-соединение; `SourceIp`, `DestinationIp`, `DestinationPort`, `Image`.  
- **Event ID 7: Image Loaded** — загрузка DLL или EXE-модуля в память процесса; критично для обнаружения DLL Hijacking и инжекций.  
- **Event ID 11: FileCreate** — создание файла; применяется для отслеживания дропперов вредоносного ПО и staging-активности.  
- **Event ID 22: DNS Query** — DNS-запрос, отправленный процессом; `QueryName`, `Image`. Позволяет выявлять DGA-домены и маяки C2.  
- **Event ID 10: ProcessAccess** — доступ одного процесса к другому (например, открытие дескриптора LSASS с флагами `0x1FFFFF`); индикатор дампа учётных данных.  
- **Event ID 8: CreateRemoteThread** — создание удалённого потока; классический признак инжекции кода (Mimikatz, Cobalt Strike).  
- **Event ID 23: FileDelete** — удаление файла; может указывать на зачистку следов атаки.

Все эти события попадают в журнал только при условии, что они **включены** в конфигурационном файле. Таким образом, для аналитика L1 понимание того, какая именно конфигурация развёрнута на конечной точке, прямо определяет доступную доказательную базу. Если правило для Event ID 3 отсутствует или исключает легитимный `svchost.exe`, аналитик не увидит сетевого соединения, инициированного вредоносной программой, маскирующейся под этот системный процесс. Поэтому конфигурация Sysmon — не только забота инженера, но и элемент грамотности аналитика, интерпретирующего телеметрию.

## 2. Конфигурационный файл Sysmon: структурные компоненты и модели фильтрации

Конфигурация Sysmon представляет собой XML-документ, загружаемый службой при запуске или при применении командой `sysmon -c <config.xml>`. В файле описывается, события каких типов регистрируются, какие хеш-алгоритмы вычисляются (MD5, SHA1, SHA256, IMPHASH) и, главное, набор правил на включение (`include`) и исключение (`exclude`) для каждого типа событий. Структуру можно упрощённо представить как:

```text
[Sysmon драйвер] ──(событие ядра)──▶ [Фильтр конфигурации]
                                      │
                       ┌──────────────┴──────────────┐
                       ▼                              ▼
                [Нет совпадений]              [Совпадение с include / exclude]
                (событие отброшено)          │
                                       ┌─────┴─────┐
                                       ▼           ▼
                                 [include]   [exclude]
                                 (событие    (событие отброшено)
                                  записано)
```

Каждое правило в XML содержит условия, опирающиеся на атрибуты события: путь к образу (`Image`), командную строку (`CommandLine`), хеш, IP-адреса, подпись и т.д. Сопоставление происходит на этапе генерации события драйвером, поэтому события, отфильтрованные на этом уровне, вообще не попадают в журнал. Это принципиально отличает Sysmon от механизмов пост-обработки в SIEM: аналитик не может восстановить то, что было исключено конфигурацией на хосте.

В сообществе сложились три основные модели построения конфигураций, сравнительные характеристики которых приведены в таблице.

| Модель конфигурации | Принцип | Примеры | Преимущества для SOC | Недостатки и требования к L1 |
|---------------------|---------|---------|-----------------------|--------------------------------|
| **Exclusion-based (исключение известного хорошего)** | События регистрируются для всех процессов и соединений, кроме явно исключённых «нормальных» | [SwiftOnSecurity/Sysmon-config](https://github.com/SwiftOnSecurity/sysmon-config) (упоминается в выдержке) — сотни исключений для типичного ПО (Microsoft Office, браузеры, системные службы) | Максимальный охват, малый риск пропустить неизвестную угрозу. L1 видит широкий спектр аномалий. | Высокий первоначальный шум; требуется регулярный тюнинг при обновлениях приложений. Аналитик должен уметь отличать легитимное событие, не попавшее в исключения, от подозрительного. |
| **Inclusion-based (включение известного подозрительного)** | Регистрируются только события, соответствующие заранее определённым паттернам атак | ION-Storm/sysmon-config (упоминается в выдержке) — правила, нацеленные на техники MITRE ATT&CK | Низкий уровень шума; каждое событие с высокой вероятностью является релевантным. Меньше необходимость фильтрации на SIEM. | Пропуск новых, неизвестных техник или вариаций, не описанных в правилах. Аналитик L1 может столкнуться с ситуацией, когда индикаторы компрометации просто отсутствуют в логах. Требует более частого обновления конфигурации. |
| **Модульная (гибридная на основе модулей)** | Конфигурация собирается из независимых файлов-модулей, каждый покрывает определённую категорию техник или активов | [Olaf Hartong/sysmon-modular](https://github.com/olafhartong/sysmon-modular) (упоминается в выдержке) — модули по идентификаторам MITRE ATT&CK | Гибкость адаптации под инфраструктуру; можно включить только нужные модули, снижая шум без потери охвата на критических направлениях. | Сложность первоначальной настройки; аналитик должен понимать, какие модули активны, чтобы корректно интерпретировать отсутствие событий. |

Независимо от модели, конфигурация включает опции вычисления хешей. Часто выбирают SHA256 как компромисс между уникальностью и производительностью. Наличие хешей в Event ID 1 позволяет аналитику немедленно проверить образ через VirusTotal, не получая доступ к самому файлу. Кроме того, указывается сохранение полной командной строки (`CommandLine`) и GUID процесса (`ProcessGuid`), что обеспечивает точную корреляцию событий (например, связывание Event ID 1 и Event ID 3 через `ProcessGuid` или `ProcessId`).

Пример минимального конфигурационного XML, который включает базовый набор событий (ID 1, 3, 7, 11, 22) с вычислением SHA256, может выглядеть (схематично):

```xml
<Sysmon schemaversion="4.82">
  <HashAlgorithms>SHA256</HashAlgorithms>
  <EventFiltering>
    <ProcessCreate onmatch="exclude">
      <!-- Правила исключения/включения для Event ID 1 -->
    </ProcessCreate>
    <NetworkConnect onmatch="include">
      <!-- Правила для Event ID 3 -->
    </NetworkConnect>
    <FileCreate onmatch="exclude">
      <!-- Правила для Event ID 11 -->
    </FileCreate>
    <!-- другие элементы... -->
  </EventFiltering>
</Sysmon>
```

Важно свойство `onmatch`: `include` означает «записывать событие только при совпадении с правилом», `exclude` — «записывать всё, кроме совпадений». От этого напрямую зависит логика видимости. Для L1 это означает, что при `onmatch="include"` без явных правил события вообще не будут регистрироваться, а при `onmatch="exclude"` они пойдут потоком, пока не будут заданы исключения.

Таким образом, конфигурация Sysmon — это не просто технический XML, а определяющий фактор того, **какие артефакты доступны аналитику при расследовании**. Знание принятой в организации модели фильтрации — обязательный компонент компетенции L1.

## 3. Применение конфигурационных настроек в повседневной работе аналитика L1

Аналитик первого уровня взаимодействует с событиями Sysmon через интерфейс SIEM, но также может напрямую обращаться к журналу на отдельной машине при расследовании или для проверки гипотез. Базовый инструментарий: оснастка Event Viewer (`eventvwr.msc`) и PowerShell с командлетом `Get-WinEvent`. Приведённые ниже команды иллюстрируют типовые операции, которые помогают понять полноту и корректность конфигурации.

Для проверки, какие события Sysmon вообще поступают (например, чтобы убедиться, что Event ID 3 включён на хосте), можно выполнить запрос, возвращающий количество событий каждого типа за последний час:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    StartTime = (Get-Date).AddHours(-1)
} | Group-Object -Property Id | Select-Object Name, Count
```

Если в выводе отсутствует строка с ID 3, а в сети ожидается мониторинг сетевых соединений, это прямо указывает на то, что конфигурация не включает данный тип событий или они исключены фильтром. Быстрое получение последних 10 событий ID 1 (Process Creation) с выводом ключевых полей может выглядеть так:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    ID = 1
} -MaxEvents 10 | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    [PSCustomObject]@{
        TimeCreated = $_.TimeCreated
        Image = ($data | Where-Object { $_.Name -eq 'Image' }).'#text'
        CommandLine = ($data | Where-Object { $_.Name -eq 'CommandLine' }).'#text'
        ParentImage = ($data | Where-Object { $_.Name -eq 'ParentImage' }).'#text'
        Hashes = ($data | Where-Object { $_.Name -eq 'Hashes' }).'#text'
    }
} | Format-Table -AutoSize
```

Этот скрипт даёт быстрый обзор запускаемых процессов и их атрибутов. Если какие-то поля (например, `Hashes`) не заполнены, вероятно, в конфигурации отсутствуют соответствующие алгоритмы хеширования или событие генерировалось версией Sysmon, не включающей хеши.

**Как аналитик L1 использует знание конфигурации для снижения шума.** Типичная проблема начального уровня — огромное количество событий от легитимной активности. Если аналитик видит поток Event ID 11 (FileCreate) от браузера, записывающего временные файлы, это говорит о том, что в конфигурации, вероятно, используется exclusion-based модель с недостаточными исключениями для конкретного приложения. Запрос в службу эксплуатации о донастройке исключений для пути `*\Google\Chrome\*` позволит сократить шум и сконцентрироваться на действительно аномальных событиях.

С другой стороны, отсутствие событий от подозрительной активности (например, нет Event ID 8 при инжекции, которую детектирует другое средство) сигнализирует о возможной inclusion-based модели или исключениях, которые нужно пересмотреть. Навык определения «слепых зон» по результатам триажа — непосредственная зона роста аналитика L1.

**Интерпретация атрибутов.** Полнота командной строки (Event ID 1) прямо зависит от опции `CommandLine` в конфигурации. Если она включена, то закодированные команды (например, `powershell -enc SQBFAFgAIAAoAE4AZQB3AC...`) становятся видимыми в исходном виде и могут быть декодированы. Родительский процесс (ParentImage) и GUID процесса позволяют восстанавливать цепочку выполнения: например, Microsoft Word (winword.exe) → cmd.exe → powershell.exe — характерный паттерн документного вектора атаки.

Аналогично, в Event ID 3 поля `SourceIp`, `DestinationIp`, `DestinationPort` и `Image` позволяют мгновенно определить, какой именно процесс инициировал сетевое соединение. Это контрастирует с традиционными сетевыми логами, где виден только IP/порт хоста, но не конкретный исполняемый файл.

Таким образом, каждое поле, включённое конфигурацией, является потенциальным индикатором компрометации. Аналитик L1 должен знать, какие поля доступны в используемой конфигурации, чтобы не тратить время на поиск несуществующих данных и корректно оценивать надёжность своих выводов.

## 4. Сквозной практический пример: анализ подозрительного сетевого соединения

**Исходные условия.**  
Конечная точка — Windows 10, развёрнута конфигурация Sysmon на базе подхода SwiftOnSecurity (exclusion-based) с включёнными ID 1, 3, 7, 11, 22, хешированием SHA256 и полной командной строкой. В SIEM поступил алерт: процесс `powershell.exe` инициировал TCP-соединение на нестандартный порт к внешнему IP. Аналитик L1 должен провести первичный триаж, используя локальные журналы машины для детализации.

**Шаг 1. Извлечение детального события Network Connection (ID 3).**  
Выполняется поиск события по времени и процессу PowerShell:

```powershell
$events = Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    ID = 3
    StartTime = [datetime]"2025-06-15T10:00:00"
    EndTime   = [datetime]"2025-06-15T10:05:00"
}
$ps_event = $events | Where-Object {
    $xml = [xml]$_.ToXml()
    ($xml.Event.EventData.Data | Where-Object { $_.Name -eq 'Image' }).'#text' -like '*powershell.exe'
}
$ps_event | Select-Object TimeCreated, Message
```

Вывод (иллюстративная схема): событие с `UtcTime: 2025-06-15 10:02:33.456`, `ProcessId: 4684`, `ProcessGuid: {1A2B3C4D-...}`, `Image: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`, `SourceIp: 192.168.1.10`, `DestinationIp: ` (заменяем на `A.B.C.D`), `DestinationPort: 8080`.  

**Шаг 2. Корреляция с событием создания процесса (ID 1) для получения командной строки и родительского процесса.**  
Используем `ProcessGuid` из события сети:

```powershell
$guid = ($xml.Event.EventData.Data | Where-Object { $_.Name -eq 'ProcessGuid' }).'#text'
$parent_event = Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    ID = 1
    StartTime = [datetime]"2025-06-15T10:00:00"
    EndTime   = [datetime]"2025-06-15T10:05:00"
} | Where-Object {
    $xml2 = [xml]$_.ToXml()
    ($xml2.Event.EventData.Data | Where-Object { $_.Name -eq 'ProcessGuid' }).'#text' -eq $guid
}
$xml1 = [xml]$parent_event.ToXml()
$data1 = $xml1.Event.EventData.Data
[PSCustomObject]@{
    ParentImage = ($data1 | Where-Object { $_.Name -eq 'ParentImage' }).'#text'
    CommandLine = ($data1 | Where-Object { $_.Name -eq 'CommandLine' }).'#text'
    Hashes = ($data1 | Where-Object { $_.Name -eq 'Hashes' }).'#text'
}
```

Результат (иллюстративно): `ParentImage: C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE`, `CommandLine: "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -WindowStyle Hidden -ExecutionPolicy Bypass -EncodedCommand SQBuAH...`.  
Хеши (`Hashes`) содержат `SHA256=ABCDEF...`, `IMPHASH=123456...`.

**Шаг 3. Индикаторы атаки.**  
Родительский процесс — Microsoft Word — в сочетании с PowerShell, выполняющим скрытый закодированный скрипт, чётко указывает на фишинговый документ с вредоносным макросом. Закодированная команда после декодирования (например, `[System.Text.Encoding]::Unicode.GetString([System.Convert]::FromBase64String(...))` в локальном сеансе) раскрывает попытку загрузки следующей стадии с внешнего ресурса.

**Шаг 4. Проверка сетевой цели.**  
Событие ID 22 (DNS Query) в тот же временной промежуток подтвердит разрешение доменного имени (если было). При необходимости можно выполнить:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    ID = 22
    StartTime = [datetime]"2025-06-15T10:02:00"
    EndTime   = [datetime]"2025-06-15T10:03:00"
} | Where-Object { $_.Message -match 'powershell' }
```

Если DNS-событие присутствует, оно покажет `QueryName`, связанное с целевым IP. В противном случае подключение могло идти напрямую по IP, что дополнительно подозрительно.

**Ожидаемый вывод.**  
Благодаря наличию полной конфигурации (включены ID 1, 3, 22 с командной строкой и хешами) аналитик L1 за считанные минуты восстанавливает цепочку атаки: Word → PowerShell с обфусцированной полезной нагрузкой → исходящее соединение на удалённый хост. На основе этих данных он эскалирует инцидент с высокой достоверностью. Если бы конфигурация не включала командную строку или хеш-алгоритмы, остались бы лишь косвенные улики, что затянуло бы принятие решения.
