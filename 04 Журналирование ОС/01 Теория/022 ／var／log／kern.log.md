# /var/log/kern.log: анализ журнала ядра Linux для задач SOC L1

## Контекст и базовые понятия журнала ядра

**kern.log** — это текстовый файл, в который демон системного логирования (rsyslog, syslog-ng) записывает сообщения, поступающие от ядра Linux через интерфейс `/dev/kmsg` или системный вызов `syslog(2)`. Файл является основным хранилищем записей о низкоуровневых событиях операционной системы: загрузке и выгрузке модулей ядра, ошибках оборудования, срабатывании OOM‑killer, нарушениях мандатного контроля доступа (SELinux/AppArmor), паниках и “oops” ядра. Для специалиста SOC L1 этот журнал — один из первоочередных источников при расследовании инцидентов, затрагивающих стабильность и безопасность хоста.

В современной экосистеме Linux сообщения ядра могут одновременно существовать в нескольких представлениях, что создаёт путаницу на начальном этапе обучения. Разберём четыре ключевые сущности, с которыми сталкивается аналитик.

1. **Кольцевой буфер ядра** — область в оперативной памяти фиксированного размера, куда ядро помещает свои сообщения через функцию `printk()`. Доступен для чтения командой `dmesg`. Буфер не сохраняется после перезагрузки, а наиболее старые записи вытесняются новыми при переполнении.
2. **/var/log/kern.log** — постоянный файл на диске, в который демон syslog (rsyslog или syslog-ng) сохраняет сообщения, получаемые из `/dev/kmsg`. Файл ротируется утилитой logrotate, поэтому доступен для долгосрочного расследования.
3. **Журнал systemd-journald** — бинарное хранилище, куда journald может писать сообщения ядра (при использовании `systemd`). Просмотр выполняется командой `journalctl -k`. Журнал может быть как временным (в `/run/log/journal`), так и постоянным (в `/var/log/journal`).
4. **/var/log/syslog** — общий текстовый файл, куда syslog-демон направляет сообщения от различных источников (включая ядро, если это настроено в правилах роутинга). Присутствие ядерных записей в syslog зависит от конфигурации.

Сравнительная таблица ниже фиксирует принципиальные различия, существенные для оперативной работы SOC.

| Сущность | Источник данных | Хранение | Типовые команды доступа | Роль в работе SOC L1 |
|----------|-----------------|----------|--------------------------|-----------------------|
| Кольцевой буфер (dmesg) | Внутренний буфер ядра, ограничен размером (обычно 64–256 КБ) | В ОЗУ, очищается при перезагрузке | `dmesg`, `dmesg -T` | Быстрая проверка актуального состояния после подозрительного события, если хост ещё доступен |
| /var/log/kern.log | Демон syslog (rsyslog/syslog-ng) получает сообщения через `/dev/kmsg` | Текстовый файл на диске, ротируется | `less`, `grep`, `awk` | Ретроспективный поиск IoC, корреляция по времени, долгосрочное хранение |
| Журнал systemd (journald) | systemd-journald через `/dev/kmsg`, структурированные бинарные записи | Бинарный журнал в `/var/log/journal/` или `/run/log/journal` | `journalctl -k`, `journalctl -k -p err` | Фильтрация по приоритетам, идентификаторам загрузки, юнитам; экспорт в машиночитаемые форматы |
| /var/log/syslog | Тот же демон syslog с правилами для `kern.*` или `*.*` | Текстовый файл, часто агрегирующий все источники | `grep`, `tail` | Быстрая общая картина инцидента, если kern.log не архивирован или пересылается в SIEM вместе с другими событиями |

Для SOC L1 критически важно понимать, что `kern.log` содержит ту же информацию, что и кольцевой буфер, но с постоянным хранением. Однако именно конфигурация syslog-демона определяет, какие уровни сообщений попадают в файл. По умолчанию большинство дистрибутивов записывают все сообщения ядра (`kern.*`) в `/var/log/kern.log`, но это может быть изменено администратором. В централизованной архитектуре SOC события из kern.log передаются в SIEM агентом (например, rsyslog с форвардингом по TCP/TLS) и обогащаются временными метками коллектора, что решает проблему отсутствующего года и часовых поясов.

Архитектурная схема движения сообщения ядра к аналитику:
```text
[Ядро] --printk()--> [Кольцевой буфер] --> [/dev/kmsg] --> [Демон syslog]
                                                               |
                                                               +--> /var/log/kern.log (локальный файл)
                                                               +--> удалённый syslog-сервер / SIEM (по сети)
                                                               +--> journald (если настроен ForwardToSyslog=yes)
```

Таким образом, kern.log выступает связующим звеном между низкоуровневыми событиями ядра и процессами мониторинга безопасности.

## Классификация сообщений ядра и их значение для безопасности

Сообщения ядра, попадающие в kern.log, генерируются различными подсистемами с помощью функции `printk()` и несут уровень критичности от 0 (KERN_EMERG) до 7 (KERN_DEBUG). Уровни определяют не только серьёзность, но и часто влияют на правила записи в файлы: администратор может настроить запись в kern.log только уровней `warn` и выше, хотя общепринято сохранять все (`kern.*`).

Стандартные уровни сообщений ядра и примеры их проявления в kern.log сведены в таблицу.

| Уровень | Имя (KERN_*) | Значение | Типичные записи в kern.log (иллюстративная схема) |
|---------|--------------|----------|---------------------------------------------------|
| 0 | EMERG | Система неработоспособна | `kernel: Kernel panic - not syncing: Fatal exception` |
| 1 | ALERT | Требуется немедленное вмешательство | `kernel: Temperature above threshold, cpu clock throttled` |
| 2 | CRIT | Критическое состояние | `kernel: EXT4-fs error (device sda1): ext4_lookup: deleted inode referenced` |
| 3 | ERR | Ошибка | `kernel: ata1.00: failed command: READ FPDMA QUEUED` |
| 4 | WARNING | Предупреждение | `kernel: nf_conntrack: table full, dropping packet` |
| 5 | NOTICE | Нормальные, но значимые события | `kernel: usb 1-2: new low-speed USB device number 3 using ehci-pci` |
| 6 | INFO | Информационное сообщение | `kernel: Bluetooth: Core ver 2.22` |
| 7 | DEBUG | Отладочное сообщение | `kernel: input: Logitech USB Optical Mouse as /devices/pci0000:00/0000:00:1a.0/usb1/1-1/1-1:1.0/input/input17` |

Для задач SOC L1 уровни ERR, WARNING и NOTICE представляют наибольший интерес, так как именно в них фиксируются ошибки безопасности, предупреждения мандатного контроля и события загрузки модулей. Уровень EMERG и CRIT всегда требует немедленной реакции, поскольку может свидетельствовать об эксплуатации уязвимости ядра или отказе критического оборудования.

Сообщения в kern.log имеют стандартный формат, определяемый шаблоном rsyslog (обычно `RSYSLOG_TraditionalFileFormat`). Каждая строка содержит:

```
месяц день время (с точностью до секунды) хост ядро: [секунды_от_загрузки] текст_подсистемы
```

Пример записи (иллюстративная схема):
```
Oct 14 10:15:02 web-prod-01 kernel: [4321.001234] usb 3-2: device descriptor read/64, error -110
```

Число в квадратных скобках (uptime) позволяет определить, как давно после загрузки произошло событие, что может быть полезно при анализе атак на этапе инициализации ядра.

С точки зрения SOC, сообщения ядра удобно классифицировать по подсистемам-отправителям. Это помогает быстро определить природу угрозы и выбрать направление дальнейшего расследования. Систематизируем основные категории.

| Категория | Характерные префиксы / подсистемы в логе | Пример сообщения (иллюстративная схема) | Значение для мониторинга безопасности |
|-----------|------------------------------------------|---------------------------------------|----------------------------------------|
| Управление памятью и OOM | `kernel: Out of memory`, `kernel: oom_reaper` | `kernel: Out of memory: Kill process 3128 (java) score 912 or sacrifice child` | Признак исчерпания ресурсов; возможна DoS-атака типа «fork bomb» или эксплуатация уязвимости, приводящая к утечке памяти. Частые OOM на одном хосте — индикатор атаки на доступность. |
| Ошибки и паники ядра | `kernel: BUG:`, `kernel: PANIC:`, `kernel: Oops:` | `kernel: BUG: unable to handle kernel NULL pointer dereference at 00000000` | Потенциальная эксплуатация уязвимости ядра (use-after-free, переполнение буфера). «Oops» может быть следствием целенаправленной атаки с последующей попыткой повышения привилегий. |
| Загрузка и выгрузка модулей ядра | `kernel: [имя_модуля] loading`, `kernel: taints kernel` | `kernel: stealth_mod: loading out-of-tree module taints kernel.` | Основной индикатор установки руткита на уровне ядра (LKM rootkit). Неподписанный модуль или модуль с «taint» без цифровой подписи — немедленная эскалация. |
| Сетевые подсистемы и фильтрация пакетов | `kernel: nf_conntrack`, `kernel: iptables`, `kernel: netfilter` | `kernel: nf_conntrack: table full, dropping packet` | Указывает на DoS-атаку с исчерпанием таблицы соединений (например, SYN‑флуд). Записи iptables позволяют отслеживать конкретные пакеты, отброшенные правилами. |
| Мандатный контроль доступа (SELinux / AppArmor) | `kernel: type=1400 audit`, `kernel: apparmor=“DENIED”` | `kernel: apparmor=“DENIED” operation=“open” profile=“/usr/sbin/nginx” name=“/etc/shadow”` | Фиксация попыток нарушения политик безопасности. Множественные AVC-отказы SELinux могут означать как некорректную настройку, так и целенаправленное действие злоумышленника. |
| Аппаратные ошибки (диски, память, PCI) | `kernel: mce: [Hardware Error]`, `kernel: ata`, `kernel: EDAC` | `kernel: mce: [Hardware Error]: CPU 0: Machine Check: 0 Bank 4: …` | Критические аппаратные сбои могут влиять на доступность или быть следствием физического воздействия. В контексте SOC важна корреляция с несанкционированным доступом в дата-центр. |
| Ошибки процессов (segfault, сигналы) | `kernel: [процесс][PID]: segfault`, `kernel: traps:` | `kernel: nginx[12345]: segfault at ffff ip 00007f… error 4 in libc‑2.31.so` | Неоднократные segfault в одном процессе могут сигнализировать об атаке на переполнение буфера или о вредоносной активности, нарушающей нормальную работу приложения. |

Такая категоризация не является исчерпывающей, но покрывает 90% инцидентов, с которыми сталкивается первая линия SOC. Каждое сообщение следует оценивать в контексте: единичный аппаратный сбой может быть случайностью, а вот появление неподписанного модуля ядра в продуктивной среде без зарегистрированного изменения — почти гарантированный признак компрометации.

## Применение /var/log/kern.log в практике SOC L1

На уровне L1 аналитик чаще всего работает с уже агрегированным в SIEM логом, однако умение непосредственно взаимодействовать с файлом на хосте необходимо при первичном триаже, когда SIEM-алерт требует быстрой проверки контекста, либо в случае недоступности централизованного логирования. Рассмотрим ключевые операции и команды, которые решают типовые задачи.

### 1. Просмотр и фильтрация по времени и ключевым словам

Формат временной метки в kern.log стандартизирован, но не содержит года и часового пояса. При анализе «живого» файла полезно использовать текущую системную дату и утилиту `date` для генерации шаблона поиска. Например, чтобы найти все записи за последние 15 минут, можно выполнить:

```bash
grep "$(date +'%b %e %H:' -d '15 min ago')" /var/log/kern.log | head -20
```

*Иллюстративный вывод (схема):*
```
Oct 14 15:45:01 web-prod-01 kernel: [345678.123456] stealth_mod: loading out-of-tree module taints kernel.
Oct 14 15:45:01 web-prod-01 kernel: [345678.123457] stealth_mod: module verification failed: signature and/or required key missing
Oct 14 15:45:30 web-prod-01 kernel: [345708.654321] nf_conntrack: table full, dropping packet
```

Однако временной фильтр на основе `grep` может давать ложные срабатывания из-за ротации файлов (по умолчанию kern.log ротируется с суффиксом `.1`, `.2.gz` и т.п.). Более надёжный способ — использовать `journalctl -k` с временными рамками, если journald собирает сообщения ядра и настроено постоянное хранилище:

```bash
journalctl -k --since "2024-10-14 15:45:00" --until "2024-10-14 15:46:00"
```

*Вывод (схема):*
```
Oct 14 15:45:01 web-prod-01 kernel: stealth_mod: loading out-of-tree module taints kernel.
Oct 14 15:45:01 web-prod-01 kernel: stealth_mod: module verification failed
Oct 14 15:45:30 web-prod-01 kernel: nf_conntrack: table full, dropping packet
```

Для быстрого поиска ошибок и критических событий по текстовому файлу используют комбинацию `grep` с регулярным выражением, охватывающим основные паттерны:

```bash
grep -E "Kernel panic|Oops|Out of memory|segfault|BUG|error|fail" /var/log/kern.log | tail -20
```

Регулярное выражение можно дополнить специфичными для инфраструктуры ключевыми словами, например, названиями критически важных модулей.

### 2. Выявление загрузки подозрительных модулей ядра

Загрузка модуля ядра через `insmod` или `modprobe` генерирует записи, содержащие слово “loading” и, в случае неподписанных модулей, “taints kernel”. Это немедленный сигнал для проверки. Команда для поиска таких событий:

```bash
grep -iE "loading|taints|init_module" /var/log/kern.log
```

*Иллюстративный вывод:*
```
Oct 14 15:45:01 web-prod-01 kernel: [345678.123456] stealth_mod: loading out-of-tree module taints kernel.
Oct 14 15:45:01 web-prod-01 kernel: [345678.123457] stealth_mod: module verification failed: signature and/or required key missing - tainting kernel
Oct 13 08:22:10 db-server kernel: [12345.678901] e1000e: Intel(R) PRO/1000 Network Driver - 3.2.6-k
```

Здесь видно, что модуль `e1000e` — легитимный подписанный драйвер, тогда как `stealth_mod` не содержит подписи и имеет подозрительное имя. После обнаружения такого события L1 должен немедленно проверить список загруженных модулей `lsmod` и сверить имя с перечнем разрешённых в конфигурациях, а также эскалировать инцидент.

### 3. Обнаружение аномалий, связанных с памятью (OOM-killer)

Ядро логирует каждый вызов OOM-killer с указанием жертвы и её оценки (oom_score). Частые срабатывания за короткий промежуток времени могут свидетельствовать о DoS-атаке. Простейший способ проверки — подсчёт количества событий OOM за сутки:

```bash
grep -c "Out of memory" /var/log/kern.log
```

Для более детального анализа извлекают PID убитых процессов:

```bash
grep "Out of memory" /var/log/kern.log | grep -oP 'process \K\d+' | sort | uniq -c
```

*Схема вывода:*
```
3 3128
1 407
2 1602
```

Повторяющееся завершение одного и того же процесса (например, Java‑приложения) в сочетании с аномальной загрузкой CPU может указывать на атаку, провоцирующую неконтролируемое потребление памяти.

### 4. Анализ сетевых событий ядра (netfilter)

Если на хосте включено логирование пакетных фильтров (iptables c правилом `LOG`), сообщения попадают в kern.log и содержат детали: интерфейсы, MAC, IP, протокол, порты. SOC-аналитик может вычленить подозрительную активность, например, сканирование портов. Пример парсинга для выделения IP-адресов источника и назначения (формат зависит от распределения полей в правиле iptables):

```bash
grep "IN=.*DST=" /var/log/kern.log | awk '{for(i=1;i<=NF;i++){if($i ~ /^SRC=/){print $i}}}'
```

*Иллюстративный вывод (схема):*
```
SRC=192.168.1.100
SRC=10.20.30.40
SRC=192.168.1.100
SRC=192.168.1.100
```

Такой список может быть передан на проверку в threat intelligence. Однако в большинстве сред правила iptables LOG настраиваются редко, предпочитая использовать специализированные IDS/NIDS.

### 5. Мониторинг нарушений мандатного доступа (AppArmor/SELinux)

AppArmor и SELinux логируют отказы в kern.log (иногда также в audit.log), что прямо относится к попыткам несанкционированного доступа. Например, при попытке веб‑сервером открыть `/etc/shadow`:

```bash
grep -i "apparmor.*DENIED\|type=1400.*denied" /var/log/kern.log
```

Такие события требуют проверки: если была попытка эксплуатации уязвимости в веб‑приложении, которая привела к обращению к неразрешённому файлу, это подтверждает активную атаку.

### Типичные ошибки и подводные камни

Начинающие аналитики часто допускают следующие просчёты при работе с kern.log:

* **Игнорирование временной метки uptime.** При корреляции с другими логами необходимо учитывать, что время в квадратных скобках — это не абсолютное время, а смещение от загрузки, поэтому его нельзя напрямую сравнивать с syslog-сообщениями от сервисов.
* **Пренебрежение ротацией логов.** Если файл `/var/log/kern.log` не найден, возможно, он был перемещён в `kern.log.1` или сжат. Неудачный grep по текущему файлу может дать ложное отсутствие событий.
* **Неверная интерпретация «обычных» ошибок.** Сообщения вроде `ata1.00: failed command` могут годами появляться из-за проблем с кабелем и не иметь отношения к безопасности. Без корреляции с другими событиями легко поднять ложную тревогу.
* **Слепое доверие формату.** В некоторых конфигурациях syslog-демона ядерные сообщения могут записываться без разделения по приоритетам или с дополнительными полями (например, structured data по RFC 5424). Парсер должен быть адаптирован под конкретные системы.

## Сквозной практический пример: обнаружение LKM-руткита через /var/log/kern.log

**Исходные условия:** Сервер `web-prod-01` под управлением Ubuntu 22.04 LTS, на котором rsyslog записывает все сообщения ядра (`kern.*`) в `/var/log/kern.log`. SOC L1 получает из SIEM алерт: «Хост web-prod-01: загрузка модуля ядра с пометкой taint (неподписанный out‑of‑tree модуль)». Аналитик имеет SSH-доступ к системе и должен оперативно подтвердить или опровергнуть инцидент, используя kern.log.

**Шаг 1. Получить последние события загрузки модулей из kern.log.**  
```bash
grep -iE "loading|taints|init_module" /var/log/kern.log | tail -10
```
*Иллюстративный вывод:*
```
Oct 14 15:45:01 web-prod-01 kernel: [345678.123456] stealth_mod: loading out-of-tree module taints kernel.
Oct 14 15:45:01 web-prod-01 kernel: [345678.123457] stealth_mod: module verification failed: signature and/or required key missing - tainting kernel
Oct 14 15:45:02 web-prod-01 kernel: [345678.200000] stealth_mod: initialized
Oct 13 08:22:10 web-prod-01 kernel: [12345.678901] nvme: loading out-of-tree module taints kernel.
Oct 13 08:22:10 web-prod-01 kernel: [12345.678901] nvme: module verification failed: signature and/or required key missing - tainting kernel
```
Наблюдаем две подозрительные записи от модуля `stealth_mod`; модуль `nvme` мог быть частью драйверов хранилища и требует дополнительной проверки, но сейчас фокус на новом модуле.

**Шаг 2. Уточнить весь контекст вокруг загрузки модуля stealth_mod.**  
```bash
grep "stealth_mod" /var/log/kern.log
```
*Вывод:*
```
Oct 14 15:45:01 web-prod-01 kernel: [345678.123456] stealth_mod: loading out-of-tree module taints kernel.
Oct 14 15:45:01 web-prod-01 kernel: [345678.123457] stealth_mod: module verification failed: signature and/or required key missing - tainting kernel
Oct 14 15:45:02 web-prod-01 kernel: [345678.200000] stealth_mod: initialized
Oct 14 15:45:02 web-prod-01 kernel: [345678.200100] stealth_mod: hiding process PID 12345
```
Дополнительное сообщение `hiding process PID 12345` — классическое поведение руткита, предназначенного для сокрытия вредоносного процесса. Факт скрытия процесса записан самим модулем (в зависимости от реализации руткита такие сообщения могут и отсутствовать, но здесь они присутствуют из-за отладочной печати).

**Шаг 3. Проверить, загружен ли модуль в память в настоящее время.**  
```bash
lsmod | grep stealth_mod
```
*Иллюстративный вывод:*
```
stealth_mod            16384  0
```
Модуль активен. Это подтверждает, что компрометация всё ещё присутствует в системе.

**Шаг 4. Связать время загрузки модуля с событиями аутентификации (auth.log) для выявления учётной записи злоумышленника.**  
```bash
grep "$(date -d '15:45' +'%b %e %H:%M')" /var/log/auth.log
```
*Возможный вывод:*
```
Oct 14 15:44:59 web-prod-01 sshd[1337]: Accepted publickey for admin from 10.0.0.100 port 50123 ssh2: RSA SHA256:...
Oct 14 15:45:01 web-prod-01 sudo: admin : TTY=pts/0 ; PWD=/tmp ; USER=root ; COMMAND=/sbin/insmod stealth_mod.ko
```
Вторая запись однозначно указывает на пользователя `admin`, который использовал `sudo` для загрузки модуля. Это действие не было санкционировано, из чего следует компрометация учётной записи.

**Шаг 5. Зафиксировать инцидент, собрать артефакты и эскалировать.**  
С точки зрения L1, выявлено:
- Факт загрузки неподписанного вредоносного модуля ядра.
- Признаки руткит-активности (сокрытие процесса).
- Учётная запись, использованная для установки.

На основе этих фактов инцидент эскалируется на L2 с рекомендацией немедленно изолировать хост, снять дамп модуля и памяти, инициировать процедуру реагирования. В качестве приложения к тикету прикладываются извлечённые строки из kern.log и auth.log.

Таким образом, на примере kern.log продемонстрировано, как SOC L1 может за несколько минут подтвердить серьёзную компрометацию и предоставить необходимые данные для дальнейшего расследования.
