# rsyslog и syslog-ng: назначение и роль агрегации

## 1. Эволюция систем протоколирования: от syslogd к современным агрегаторам

Протокол syslog, описанный первоначально в RFC 3164 и обновлённый в RFC 5424, служит стандартным механизмом доставки структурированных сообщений о событиях от хостов и приложений к коллекторам. На прикладном уровне его реализуют демоны, собирающие локальные логи ядра, системных служб и пользовательских программ, чтобы либо записать их в файлы, либо передать по сети на центральный узел. Исходный демон `syslogd` (пакет `sysklogd`), появившийся в ранних версиях UNIX, выполнял минимальную задачу: принимал сообщения через Unix-сокет `/dev/log` и распределял их согласно правилам в `/etc/syslog.conf`, как правило по фиксированным файлам. Однако с ростом инфраструктур и требований к безопасности выявились фундаментальные ограничения: транспорт только по UDP (ненадёжная доставка), отсутствие аутентификации и шифрования, примитивная фильтрация по фиксированным шаблонам facility.severity, невозможность динамического преобразования сообщений и сохранения в базы данных.

Для преодоления этих ограничений были созданы два доминирующих проекта: **rsyslog** (Rocket-fast SYStem for LOG processing) и **syslog-ng** (syslog next generation). Оба являются надстройками над протоколом syslog и решают задачу **агрегации** — централизованного сбора, нормализации, фильтрации и маршрутизации событий от множества источников к одному или нескольким хранилищам. В контексте SOC L1 агрегация даёт единую точку наблюдения, позволяя аналитикам мониторить всю ИТ-инфраструктуру через один интерфейс, строить корреляции между событиями разных систем и автоматизировать обнаружение инцидентов с помощью SIEM-правил.

Принципиальное различие между rsyslog и syslog-ng кроется в их происхождении и философии конфигурирования. Rsyslog был ответвлён от традиционного `sysklogd` с сохранением обратной совместимости: файл `rsyslog.conf` принимает классический синтаксис `facility.level <файл>`. Syslog-ng написан с нуля и вводит объектно-ориентированный конфигурационный язык, где source, destination, filter и log являются самостоятельными сущностями, которые можно переиспользовать. Несмотря на синтаксические различия, функциональные возможности обоих продуктов во многом пересекаются благодаря модульной архитектуре и поддержке расширений. Таблица 1 фиксирует ключевые параметры, помогающие разграничить три поколения syslog-демонов.

| Критерий | syslogd (традиционный) | rsyslog | syslog-ng |
|----------|------------------------|---------|-----------|
| **Транспорт** | UDP (ненадёжный) | UDP, TCP, TCP+TLS, RELP | UDP, TCP, TCP+TLS |
| **Безопасность** | Нет шифрования/аутентификации | TLS с взаимной аутентификацией, ACL по IP | TLS, проверка сертификатов, контроль доступа |
| **Фильтрация** | Только facility.level | Выражения на RainerScript и фильтры на основе свойств (property-based), регулярные выражения | SQL-подобный синтаксис filter { … }, регулярные выражения, сопоставление по параметрам |
| **Парсинг и нормализация** | Отсутствует | Модули mmjsonparse, mmnormalize (liblognorm), пользовательские парсеры | Встроенные парсеры: csv, json, db-parser, patterndb |
| **Очереди и надёжность** | Нет | Дисковые очереди (Disk-Assisted Queues), контроль обратного давления | Надёжная буферизация (log-fifo-size), дисковые буферы в последних версиях, но исторически менее развиты |
| **Выводы** | Локальные файлы | Файлы, БД (MySQL, PostgreSQL), Elasticsearch, Kafka, HTTP, Splunk HEC и др. | Файлы, БД (SQL, MongoDB), AMQP, Kafka, HTTP |
| **Совместимость с systemd-journald** | Не применимо | Модули imjournal (структурированные данные) и imuxsock (через ForwardToSyslog) | Получение данных из journald через systemd-journal source |
| **Конфигурационный синтаксис** | Традиционный syslog.conf | Традиционный + RainerScript (новый формат) | Собственный объектный синтаксис |
| **Производительность** | Однопоточный | Многопоточный, до сотен тысяч сообщений/с | Высокая, хорошо масштабируется на сложных правилах |

*Таблица 1: Сравнение трёх поколений syslog-демонов (данные агрегированы из [Server Fault](https://serverfault.com/questions/692309/what-is-the-difference-between-syslog-rsyslog-and-syslog-ng), [CrowdStrike](https://www.crowdstrike.com/en-us/guides/syslog-logging/working-with-syslog-ng), [rsyslog.com](https://www.rsyslog.com)).*

Роль агрегации становится ясна при рассмотрении типичной SOC-архитектуры: десятки и сотни источников — веб-серверы, межсетевые экраны, рабочие станции — генерируют события, каждое из которых в отдельности малозначимо. Без централизованного сбора аналитику пришлось бы вручную заходить на каждый узел, просматривать локальный `/var/log/`, сопоставлять временные метки и искать аномалии. Агрегатор, будь то rsyslog или syslog-ng, объединяет потоки в единую шину, позволяя применять к ним единые политики хранения, маршрутизации и эскалации. Именно поэтому оба инструмента занимают критическое место в цепочке «журналирование ОС → система пересылки логов» и являются обязательным знанием для специалиста SOC L1.

## 2. Архитектура и внутреннее устройство rsyslog и syslog-ng

Оба продукта реализуют конвейерную обработку сообщений, где данные проходят последовательность этапов: приём — разбор — фильтрация — преобразование — доставка. Однако внутренняя реализация и способы описания этой цепочки существенно различаются.

### Модульная архитектура rsyslog

Rsyslog построен на динамически загружаемых модулях, разделённых по функциональному признаку:
- **im (input module)** — источники: `imuxsock` (локальный Unix-сокет `/dev/log`), `imklog` (буфер ядра), `imudp`, `imtcp`, `imfile` (чтение произвольных текстовых файлов), `imjournal` (импорт из systemd-journal) и другие;
- **pm (parser module)** — парсеры сообщений различных форматов: `pmrfc3164`, `pmrfc5424`;
- **mm (message modification module)** — трансформация на лету: `mmjsonparse` для разбора JSON, `mmnormalize` для применения liblognorm-правил;
- **om (output module)** — целевые системы: `omfile`, `omfwd` (пересылка по сети), `omkafka`, `omhttp`, `omelasticsearch`, `omprog` (передача внешней программе) и т.д.

Центральную роль играет **очередь сообщений** (queue). Rsyslog позволяет вставлять асинхронные очереди между любыми стадиями обработки и настраивать их тип (Direct, Disk, LinkedList, FixedArray), размер, поведение при заполнении. Дисковые очереди (Disk-Assisted) гарантируют сохранность сообщений при переполнении памяти и перезапуске службы, что критично для агрегации в production-средах. Так, типичный сценарий `input -> parser -> queue -> filter -> output-queue -> action` обеспечивает баланс между пропускной способностью и надёжностью.

Управление конвейером описывается в конфигурационном файле `/etc/rsyslog.conf` (и файлах в `/etc/rsyslog.d/`) с помощью двух допустимых синтаксисов. Традиционный legacy-синтаксис унаследован от syslogd:
```
mail.*   /var/log/mail.log
*.emerg  :omusrmsg:*
```
Современный **RainerScript** предлагает полноценный скриптовый язык с переменными, функциями, условными операторами и шаблонами. Пример загрузки модуля входных данных и отправки в JSON-файл:
```
module(load="imuxsock")
module(load="imklog")

template(name="jsonl" type="list") {
    constant(value="{\"ts\":\"")
    property(name="timereported" dateFormat="rfc3339")
    constant(value="\",\"host\":\"")
    property(name="hostname")
    constant(value="\",\"msg\":\"")
    property(name="msg" format="json")
    constant(value="\"}\n")
}
*. action(type="omfile" file="/var/log/events.jsonl" template="jsonl")
```
*Фрагмент взят из [официального сайта rsyslog](https://www.rsyslog.com).*

Мощь rsyslog раскрывается через гибкие правила маршрутизации. Например, события от SSH-сервера можно выделить в отдельный топик Kafka:
```
if ($programname == "sshd") then {
    action(type="omkafka" broker=["kafka:9092"] topic="security-auth"
           template="RSYSLOG_TraditionalFileFormat")
}
```

### Объектная архитектура syslog-ng

Syslog-ng организует логическую схему сбора и передачи через четыре базовые сущности:
- **source** — источник сообщений: драйверы `system()`, `internal()`, `udp()`, `tcp()`, `file()`, `network()`, `syslog()`, `systemd-journal()` и другие;
- **destination** — цель: `file()`, `udp()`, `tcp()`, `program()`, `mongodb()`, `elasticsearch()`, `kafka()` и т.д.;
- **filter** — условие отбора: facility, level, host, match регулярного выражения, in-list и др.;
- **log** — связка source-filter-destination с дополнительными опциями (парсер, перезапись, флаги).

Все компоненты именуются и могут многократно использоваться в разных правилах. Конфигурация размещается в `/etc/syslog-ng/syslog-ng.conf`. Минимальный пример приёма по UDP и записи в файл:
```
source s_network {
    udp(ip(0.0.0.0) port(514));
};
destination d_file {
    file("/var/log/remote.log");
};
log {
    source(s_network);
    destination(d_file);
};
```
Такой модульный подход упрощает поддержку в крупных инсталляциях, где сотни устройств отправляют логи на несколько целевых хранилищ.

Встроенный парсер patterndb даёт syslog-ng уникальную возможность распознавать сообщения по сигнатурам, извлекать пары «ключ-значение» и классифицировать события в реальном времени. Это особенно ценно в SOC: стандартизированные события легко подаются на вход SIEM, избавляя аналитиков от ручного разбора неструктурированного текста. Кроме того, syslog-ng поддерживает конвейеризацию через блоки `parser`, `rewrite` и `junction` (условное ветвление без filter), что позволяет строить сложные сценарии обработки без дублирования правил.

### Сравнительный анализ возможностей

Несмотря на разный синтаксис, оба инструмента покрывают широкий спектр потребностей агрегации. Таблица 2 сопоставляет их по ключевым функциональным областям.

| Функция | rsyslog | syslog-ng |
|--------|---------|-----------|
| Надёжная пересылка | RELP (Reliable Event Logging Protocol) в дополнение к TCP; дисковые очереди с контролем обратного давления | TCP с буферизацией; опция `keep-alive()` и `log-fifo-size()`. |
| Безопасная передача | TLS через модуль `gtls`, поддержка взаимной аутентификации, шифрование отдельных направлений | TLS через `tcp()` с параметрами `tls(…)`, проверка отпечатков сертификатов |
| Высокопроизводительная маршрутизация | Многопоточность на уровне правил; очереди с настраиваемым параллелизмом | Многопоточность на уровне источников и назначений; эффективная работа с регулярными выражениями |
| Гибкость парсинга | Внешние парсеры через liblognorm; mmjsonparse; возможность вызова внешних программ | Встроенные парсеры csv, json, db-parser, patterndb; корреляция событий |
| Интеграция с современными платформами | Kafka, Elasticsearch, Splunk HEC, Loki, HTTP-эндпоинты | Kafka, Elasticsearch, MongoDB, AMQP, HTTP |
| Совместимость с systemd | imjournal (структурированный импорт), imuxsock (через ForwardToSyslog) | драйвер `systemd-journal()` |
| Условная логика | if-else, switch, вложенные вызовы функций в RainerScript | filter {}, блоки `junction` и `channel` |
| Обратное сжатие логов | Не предусмотрено | Поддержка сжатия на уровне файлового вывода и передачи по сети (опционально) |

*Таблица 2: Функциональное сопоставление rsyslog и syslog-ng (данные из [Uptrace](https://uptrace.dev/blog/syslog-guide), [ManageEngine](https://www.manageengine.com/products/eventlog/logging-guide/syslog/syslog-ng.html), [New Relic](https://newrelic.com/blog/log/agentless-syslog-onboarding-new-relic-log-management)).*

Таким образом, выбор между rsyslog и syslog-ng чаще продиктован не техническими ограничениями, а административными предпочтениями, существующей экспертизой команды и сложностью правил маршрутизации. В дистрибутивах на базе Debian/Ubuntu и Red Hat/CentOS rsyslog является стандартным демоном, поэтому инженер SOC L1 сталкивается с ним в первую очередь. Syslog-ng чаще внедряется в средах с высокими требованиями к унификации конфигураций и глубокому парсингу на стороне агрегатора.

## 3. Типовые сценарии агрегации и операционная практика

Фундаментальный сценарий — централизованный сбор логов с множества Unix-подобных клиентов на выделенный log-сервер. В SOC L1 такой сервер выполняет роль «логовой шины»: принимает потоки от всех управляемых систем, сохраняет их на диск и/или направляет в SIEM (например, Wazuh, Splunk). Ниже рассматриваются основные операции настройки обеих систем.

### Развёртывание принимающего сервера rsyslog

Rsyslog по умолчанию слушает только локальный сокет `/dev/log`. Для приёма удалённых сообщений необходимо активировать входные модули. В файл `/etc/rsyslog.conf` (или отдельный файл в `/etc/rsyslog.d/`) добавляются строки:
```
module(load="imudp")
input(type="imudp" port="514")

module(load="imtcp")
input(type="imtcp" port="514")
```
После перезапуска демон будет принимать данные по UDP и TCP на порту 514. Чтобы обеспечить сохранность, используется дисковый буфер:
```
$workDirectory /var/spool/rsyslog  # рабочая директория для очередей
*.* action(type="omfile" file="/var/log/remote.log"
           queue.filename="remote_queue" queue.type="LinkedList"
           queue.maxdiskspace="1g" queue.saveonshutdown="on")
```
Данный пример создаёт асинхронную очередь с хранением на диске объёмом до 1 ГБ, предотвращая потери при пиковых нагрузках.

### Конфигурация клиента rsyslog

На каждом узле, который должен отправлять логи, достаточно одной строки в `/etc/rsyslog.conf`:
```
*.* @@logserver:514
```
Одиночный символ `@` означает UDP, `@@` — TCP. Для продакшн-сред рекомендуется TCP с TLS:
```
*.* action(type="omfwd" target="logserver" port="6514" protocol="tcp"
           action.resumeRetryCount="-1"
           StreamDriver="gtls" StreamDriverMode="1"
           StreamDriverAuthMode="x509/name"
           StreamDriverPermittedPeer="logserver.example.com")
```

### Настройка syslog-ng в роли агрегатора

Система конфигурации syslog-ng поощряет разделение определений. Пример `/etc/syslog-ng/syslog-ng.conf` для приёма и файлового сохранения:
```
source s_remote {
    tcp(ip(0.0.0.0) port(514) max-connections(100));
    udp(ip(0.0.0.0) port(514));
};

destination d_local {
    file("/var/log/remote_${HOST}.log" create-dirs(yes));
};

log {
    source(s_remote);
    destination(d_local);
};
```
Переменная `${HOST}` позволяет автоматически раскладывать логи по файлам с именем клиентского хоста, что удобно для SOC-аналитика при ручном разборе.

Фильтрация критичных событий в отдельный файл реализуется через блок filter:
```
filter f_errors {
    level(err..emerg);
};

destination d_errors {
    file("/var/log/remote_errors.log");
};

log {
    source(s_remote);
    filter(f_errors);
    destination(d_errors);
};
```

### Интеграция с systemd-journal

В современных Linux-системах journald является первичным сборщиком логов. Чтобы журналы попали в агрегатор, применяются два подхода:

1. **Пересылка через ForwardToSyslog**. В `/etc/systemd/journald.conf` выставляется:
```
[Journal]
ForwardToSyslog=yes
MaxLevelSyslog=debug
```
Journald будет дублировать сообщения в сокет `/run/systemd/journal/syslog`, который читает rsyslog (модуль `imuxsock`).

2. **Импорт напрямую**. Rsyslog использует модуль `imjournal`, который получает структурированные данные из journal:
```
module(load="imjournal")
module(load="mmjsonparse")
*.* action(type="omfile" file="/var/log/journal.log")
```
Syslog-ng работает через драйвер `systemd-journal()`:
```
source s_journal {
    systemd-journal();
};
```

Оба способа позволяют агрегировать не только классические syslog-сообщения, но и события, записанные напрямую в journald сервисами, не обращающимися к syslog API.

### Типичные ошибки и подводные камни

- **Блокировка порта 514**. Если на сервере уже запущен другой syslog-демон, rsyslog не сможет открыть порт. Диагностика: `ss -tuln | grep 514`. Решение — отключить конфликтующий сервис.
- **Синтаксические конфликты в rsyslog**. Смешение legacy- и RainerScript-синтаксиса в одном файле может приводить к неожиданному поведению; рекомендуется либо придерживаться одного стиля, либо строго изолировать блоки.
- **Потеря сообщений при TCP-разрыве**. По умолчанию клиент rsyslog использует кратковременный буфер; чтобы гарантировать доставку, необходимо настроить `action.resumeRetryCount="-1"` и, при необходимости, дисковую очередь.
- **Разрастание дискового пространства**. Без ротации логов агрегатор быстро заполнит хранилище. Следует настроить logrotate для файлов в `/var/log/` или использовать встроенные средства (например, в syslog-ng опция `log-fifo-size()` не управляет файловым ротированием, и здесь нужен внешний механизм).
- **Проблемы с DNS**. При использовании символических имён хостов в конфигурациях rsyslog может блокироваться на разрешении имён при старте. Рекомендуется либо указывать IP-адреса, либо разрешить DNS-кеширование локально.

SOC-аналитик L1 должен уметь проверить поток логов простыми утилитами. Команда `logger "Test message with SOC"` на клиенте генерирует сообщение уровня notice. На сервере успешный приём подтверждается просмотром целевого файла:
```
tail /var/log/remote.log
```
Ожидаемый результат — строка с временной меткой, именем хоста-отправителя и текстом «Test message with SOC». При использовании TCP можно дополнительно убедиться в активном соединении командой `ss -tnp | grep rsyslog`.

Роль агрегации на этом уровне выражается в том, что аналитик имеет в одной консоли полный срез событий: от попыток SSH-аутентификации до ошибок веб-приложений, что критически важно для первичного триажа инцидентов.

## 4. Сквозной практический пример: построение агрегирующего сервера на основе rsyslog и syslog-ng

**Исходные условия**: две виртуальные машины под управлением Ubuntu Server 22.04 LTS, находящиеся в одной сети (IP-адреса 192.168.10.10 — будущий сервер логов, 192.168.10.20 — клиент). На обеих машинах установлены базовые системные компоненты, права sudo. Задача: развернуть централизованный сбор логов по TCP, чтобы все системные сообщения с клиента дублировались на сервер. Пример демонстрирует оба решения — эталонный rsyslog (как штатный демон) и альтернативный syslog-ng, позволяя будущему специалисту SOC L1 увидеть разницу в синтаксисе и проверить работоспособность схемы.

**Шаг 1. Установка пакетов (одинаково для обоих инструментов)**

На серверной и клиентской машинах выполняем обновление индекса пакетов и установку нужного демона. Для rsyslog:
```bash
sudo apt update
sudo apt install rsyslog -y
sudo systemctl enable --now rsyslog
```
Для syslog-ng (при необходимости предварительно остановить rsyslog):
```bash
sudo apt install syslog-ng -y
sudo systemctl enable --now syslog-ng
```
*Примечание: в Ubuntu rsyslog установлен по умолчанию, но команда приведена для явной гарантии.*

**Шаг 2. Конфигурация сервера (rsyslog)**

Открываем файл `/etc/rsyslog.conf` (или создаём новый в `/etc/rsyslog.d/00-receiver.conf`) и добавляем блок приёма по TCP:
```
module(load="imtcp")
input(type="imtcp" port="514")

# Шаблон для удобочитаемого сохранения
template(name="RemoteFormat" type="string" string="%TIMESTAMP% %HOSTNAME% %syslogtag%%msg%\n")
*.* action(type="omfile" file="/var/log/remote.log" template="RemoteFormat")
```
Перезапускаем демон:
```bash
sudo systemctl restart rsyslog
```
Ожидаемый вывод: статус active (running) при проверке `systemctl status rsyslog`, порт 514 прослушивается (`ss -tlnp | grep 514` показывает строку с процессом rsyslog).

**Шаг 3. Конфигурация клиента (rsyslog)**

На клиентской машине в `/etc/rsyslog.conf` добавляем правило пересылки по TCP на сервер:
```
*.* @@192.168.10.10:514
```
Перезапускаем службу:
```bash
sudo systemctl restart rsyslog
```
С этого момента все локальные сообщения дублируются на агрегатор.

**Шаг 4. Верификация потока**

На клиенте генерируем тестовое сообщение:
```bash
logger "SOC test event from client"
```
На сервере проверяем появление записи в `/var/log/remote.log`:
```bash
tail /var/log/remote.log
```
Типичный вывод (иллюстративная схема):
```
2025-06-15T14:23:01+00:00 client-hostname logger: SOC test event from client
```
Видна метка времени, имя хоста клиента (client-hostname), тэг процесса (logger) и текст. Факт появления строки подтверждает успешную агрегацию. Дополнительно можно убедиться в установленном TCP-соединении командой `ss -tnp | grep 514`, которая покажет активный сеанс между клиентом и сервером.

**Альтернативный вариант с syslog-ng**

На сервере конфигурация `/etc/syslog-ng/syslog-ng.conf`:
```
@version: 3.35
source s_net {
    tcp(ip(192.168.10.10) port(514));
};
destination d_file {
    file("/var/log/remote_syslogng.log" template("${ISODATE} ${HOST} ${PROGRAM}: ${MESSAGE}\n"));
};
log {
    source(s_net);
    destination(d_file);
};
```
Перезапуск: `sudo systemctl restart syslog-ng`. На клиенте (опционально замена rsyslog на syslog-ng) создаём клиентскую конфигурацию:
```
@version: 3.35
destination d_remote {
    tcp("192.168.10.10" port(514));
};
log {
    source(s_sys);
    destination(d_remote);
};
```
После генерации `logger "syslog-ng test"` на сервере в `/var/log/remote_syslogng.log` появляется аналогичная строка. Таким образом, инженер SOC L1 на практике видит, что оба инструмента обеспечивают идентичный результат с точки зрения агрегации, но требуют разного подхода к конфигурированию.

**Ожидаемый вывод примера** — демонстрация работающей цепочки «клиент → агрегатор», подтверждённая реальными логами. Специалист понимает, как именно развернуть сервер сбора, проверить его работоспособность и использовать в дальнейшем для анализа в SIEM или ручного расследования.
