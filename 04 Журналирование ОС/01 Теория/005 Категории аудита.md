# Категории аудита в Windows: от базовых политик до гранулярного мониторинга

## 1. Два мира аудита: базовые и расширенные политики

Категории аудита — это управляющие элементы, которые определяют, какие события безопасности операционная система будет регистрировать в журнале «Security». Именно они формируют «скелет» видимости действий пользователей, процессов и системы в среде Windows. В SOC L1 понимание этих категорий напрямую связано с тем, какие события попадают в SIEM‑систему и на какие из них настроены правила корреляции.

Основная путаница связана с существованием двух параллельных механизмов конфигурирования аудита:
- **Basic (Local) Security Audit Policy** — классические политики, доступные в оснастке `secpol.msc` или через групповые политики (GPO) по пути `Computer Configuration → Windows Settings → Security Settings → Local Policies → Audit Policy`. Каждая политика соответствует укрупнённой категории событий (например, «Audit logon events») и оперирует лишь успехом/отказом без возможности детального выбора.
- **Advanced Security Audit Policy** — появились в Windows 7 / Server 2008 R2, расположены в `Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration → System Audit Policies`. Здесь крупные категории разбиты на десятки подкатегорий, позволяя включать аудит гранулярно: например, отдельно успешные входы Kerberos‑служб или только управление учётными записями компьютеров.

Обе парадигмы оперируют общим набором из девяти родительских категорий, но на уровне реализации это два разных подхода. С точки зрения администратора и SOC‑аналитика важно не смешивать их: если для одного компьютера одновременно настроены базовая и расширенная политики одной категории, действует **механизм приоритета Advanced‑политики** — она переопределяет базовую. Официальная рекомендация Microsoft [Advanced Security Auditing FAQ](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-R2-and-2008/ff182311(v=ws.10)): не применять оба набора одновременно во избежание «неожиданных результатов в отчётности», если только не установлен параметр `Audit: Force audit policy subcategory settings to override audit policy category settings` в значение `Disabled`.

Сравнительная характеристика подходов обобщена в таблице.

| Параметр | Basic Audit Policy | Advanced Audit Policy |
|----------|-------------------|------------------------|
| **Степень детализации** | Категория целиком: включена либо полностью, либо нет | До 60+ подкатегорий, независимое управление успехом/отказом для каждой |
| **Гибкость настройки** | Минимальная: можно только выбрать «Success», «Failure» или оба | Выборочное включение только нужных операций (например, только создание процессов без отслеживания завершения) |
| **Метод применения** | Через `secpol.msc`, GPO (Local Policies) или `auditpol` в режиме совместимости | Через GPO (Advanced Audit Policy), `auditpol` напрямую или скрипты PowerShell |
| **Итоговое поведение** | Если нет Advanced‑политики для категории, действует Basic; если есть — Advanced переопределяет Basic | Всегда имеет приоритет над Basic при совпадении категории |
| **Рекомендуемый сценарий** | Простейшие стенды, устаревшие системы до Win7/2008 R2 | Все современные внедрения, SOC‑мониторинг, соответствие стандартам |

Таким образом, в любой современной инфраструктуре мониторинга следует использовать **Advanced Audit Policy**, а базовые политики оставлять только там, где не требуется тонкая настройка.

## 2. Анатомия категорий: Event ID, подкатегории и смысл каждой группы

Advanced Audit Policy структурирована в девять родительских категорий, каждая из которых содержит от одной до десяти подкатегорий. В совокупности они генерируют **свыше 400 Event ID**, значительная часть которых используется в правилах детектирования. Понимание внутренней организации помогает SOC‑аналитику быстро соотнести конкретный Event ID с категорией аудита, оценить источник события и корректно интерпретировать алерт.

Ниже представлена сводная таблица категорий, их ключевых подкатегорий и примеров наиболее значимых для мониторинга событий. Данные основаны на картах сопоставления Event ID, опубликованных Microsoft [Advanced Audit Policy Configuration settings](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/advanced-audit-policy-configuration), Splunk Threat Research Team [Splunk blog](https://www.splunk.com/en_us/blog/security/windows-audit-policy-guide.html).

| Категория Advanced Audit | Назначение | Характерные подкатегории | Примеры значимых Event ID (описание) |
|--------------------------|------------|--------------------------|--------------------------------------|
| **Account Logon** | Проверка учётных данных на контроллере домена или локальном SAM | Credential Validation, Kerberos Service Ticket Operations, Kerberos Authentication Service | 4768 (TGT запрошен), 4771 (сбой предварительной аутентификации Kerberos), 4776 (сбой проверки NTLM) |
| **Account Management** | Изменения учётных записей и групп безопасности | User Account Management, Security Group Management, Computer Account Management | 4720 (создание пользователя), 4724 (попытка сброса пароля), 4756 (добавление в глобальную группу) |
| **Detailed Tracking** | Активность отдельных процессов и приложений | Process Creation, Process Termination, DPAPI Activity, RPC Events | 4688 (создание процесса) — фундаментальное событие для цепочек атак, 4698 (запланированное задание) |
| **DS Access** | Доступ и изменения объектов Active Directory (только на контроллерах домена) | Directory Service Access, Directory Service Changes, Directory Service Replication | 4662 (операция над объектом AD), 5136 (изменение атрибута объекта) |
| **Logon/Logoff** | Локальные и сетевые входы пользователей на конкретную машину | Logon, Logoff, Special Logon, Account Lockout | 4624 (успешный вход — типы 2,3,10), 4625 (неудачный вход), 4648 (использование явных учётных данных) |
| **Object Access** | Попытки обращения к файловым объектам, реестру, ядру | File System, Registry, Kernel Object, SAM, Certification Services | 4663 (попытка доступа к объекту с указанием AccessMask), 5145 (сетевой доступ к файлу/папке) |
| **Policy Change** | Модификации политик безопасности, прав пользователей и аудита | Audit Policy Change, Authentication Policy Change, Authorization Policy Change | 4719 (изменение политики аудита), 4704 (изменение прав пользователя) |
| **Privilege Use** | Исполнение привилегированных операций | Sensitive Privilege Use, Non‑Sensitive Privilege Use | 4673 (вызвана привилегированная служба), 4674 (операция над привилегированным объектом) |
| **System** | События целостности и изменения состояния самой системы | Security State Change, Security System Extension, System Integrity | 4608 (запуск Windows), 4616 (изменение системного времени), 5024 (запуск фаервола) |

Важная оговорка: категории **Object Access** и **DS Access** требуют не только включения подкатегорий в политике аудита, но и **настройки SACL** на целевых объектах (например, файлах, папках, разделах реестра, объектах AD). Без SACL события доступа генерироваться не будут. Это часто упускают начинающие администраторы, что приводит в SOC к отсутствию ожидаемых событий.

Иерархия структуры аудита схематично выглядит следующим образом:

```text
Advanced Audit Policy (корень)
├── Account Logon
│   ├── Credential Validation
│   ├── Kerberos Service Ticket Operations
│   ├── Other Account Logon Events
│   └── Kerberos Authentication Service
├── Account Management
│   ├── User Account Management
│   ├── Security Group Management
│   ├── Computer Account Management
│   └── ...
├── ...
└── System
    ├── Security State Change
    ├── Security System Extension
    └── System Integrity

Каждая подкатегория → набор Event ID (успех/отказ)
```

С точки зрения SOC‑аналитика, категории не равноценны по объёму и ценности. Например, «Object Access» c включённым аудитом файловой системы на файловых серверах может генерировать десятки тысяч событий в минуту, тогда как «Policy Change» — единицы в день. Рекомендации по приоритету мониторинга основаны на критичности: события Logon (4624/4625) и Account Management (4720,4724) должны отслеживаться всегда, тогда как «Detailed Tracking» (4688) включается на рабочих станциях и критичных серверах с учётом нагрузки [System Audit Policy recommendations](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/audit-policy-recommendations).

## 3. Настройка и эксплуатация: команды, подводные камни и практические приёмы

Работа с категориями аудита в реальной среде SOC L1/L2 делится на два этапа: **развёртывание политик** и **интерпретация событий**. Ниже рассмотрены типовые операции, инструменты и ошибки, которые часто встречаются на практике.

**Просмотр текущей конфигурации.** Основной интерфейс — утилита командной строки `auditpol`. Вывод информации о всех категориях и подкатегориях:

```bash
auditpol /get /category:*
```

Типичный вывод (сокращён) иллюстрирует настройки успеха/отказа для каждой подкатегории:

```text
System audit policy
Category/Subcategory                      Setting
Account Logon
  Credential Validation                   Success and Failure
  Kerberos Service Ticket Operations      Success
  ...
Logon/Logoff
  Logon                                   Success and Failure
  ...
Object Access
  File System                             No Auditing
  Registry                                No Auditing
...
```

Здесь видно, что аудит файлового доступа неактивен — распространённая ситуация по умолчанию.

**Активация подкатегории через `auditpol`.** Например, включение аудита файловой системы для успешных и неудачных попыток:

```bash
auditpol /set /subcategory:"File System" /success:enable /failure:enable
```

После выполнения можно повторно проверить подкатегорию. **Важный нюанс:** если одновременно задана базовая политика категории «Audit object access», её влияние будет переопределено расширенной настройкой; если расширенная политика вообще не задана, будет действовать базовая (включено/выключено для всей категории). Именно поэтому в доменных средах рекомендуется централизованно задать Advanced Audit Policy через GPO, а локальные базовые политики оставить не заданными, чтобы избежать путаницы.

**Использование GPO.** Для доменных машин применяется путь `Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration → Audit Policies`. Например, для аудита создания процессов выбирают подкатегорию `Process Creation` (включить успех). После применения GPO выполняется `gpupdate /force` и события сразу начинают поступать в Security log.

**Подводные камни, важные для SOC:**

1. **Игнорирование объёма журнала.** Подкатегория `Process Creation` на высоконагруженных серверах может генерировать тысячи событий 4688 в минуту. Без настроенной ротации и пересылки логов в SIEM система может быстро остаться без места, а старые события будут затираться. Netwrix [Windows audit policy best practices](https://netwrix.com/en/resources/guides/windows-audit-policy-best-practices) подчёркивает необходимость заранее рассчитать максимальный размер журнала и стратегию хранения.
2. **Не включён SACL для Object Access.** Включение подкатегории «File System» или «Registry» не приводит к появлению событий, пока на целевых объектах не установлены записи аудита. Аналитик SOC, видя отсутствие событий 4663, может ошибочно предположить, что доступ не производился, хотя аудит фактически не был настроен полностью.
3. **Смешение Basic и Advanced политик.** Если в домене развернута GPO с базовыми политиками аудита, а локально или через другую GPO задана Advanced‑политика для той же категории, результирующая конфигурация может быть непредсказуемой. SOC‑команда должна проверять согласованность политик с помощью `auditpol /get /category:*` на проблемных хостах.
4. **Неправильная интерпретация Event ID.** Событие 5156 (The Windows Filtering Platform has allowed a connection) само по себе не является инцидентом, но при резком всплеске с нестандартного процесса может служить индикатором закрепления (persistence). SOC L1 должен знать контекст: 5156/5157 относятся к категории **Object Access** (подкатегория Filtering Platform Connection) или **System**, в зависимости от версии ОС, и требуют корреляции с 4688.

**Инструменты для анализа.** Помимо стандартной оснастки Event Viewer, в SOC широко применяется PowerShell для фильтрации логов:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4663} -MaxEvents 5 | Format-List
```

Эта команда извлекает последние пять событий доступа к объектам. В комбинации с `Where-Object` можно фильтровать по имени процесса или AccessMask.

Типичная ошибка новичков — ожидать, что все события появляются мгновенно. После настройки аудита и SACL может потребоваться до нескольких минут (или перезапуск процесса) из-за кэширования дескрипторов безопасности. Это важно для проверки срабатывания.

## 4. Сквозной практический пример: аудит доступа к критичной папке с разбором Event ID 4663

**Исходные условия.**  
Лабораторная среда: Windows Server 2019 (член домена). Цель — настроить аудит всех успешных и неудачных попыток чтения/записи в папку `C:\Finance`, чтобы потом в SOC отслеживать несанкционированный доступ. Используется Advanced Audit Policy; текущая конфигурация не включает аудит объектов файловой системы. Инструменты: `auditpol`, `icacls`, Event Viewer, PowerShell.

**Шаг 1. Активация подкатегории «File System».**  
Открываем командную строку с привилегиями администратора и выполняем:

```bash
auditpol /set /subcategory:"File System" /success:enable /failure:enable
```

Проверяем результат:

```bash
auditpol /get /category:"Object Access"
```

Ожидаемый вывод (сокращён):

```text
Category/Subcategory                      Setting
Object Access
  File System                             Success and Failure
```

**Шаг 2. Настройка SACL на целевой папке.**  
Создаём папку `C:\Finance`, затем устанавливаем запись аудита для встроенной группы «Everyone» (для демонстрации) на операции чтения данных и создания файлов:

```bash
icacls "C:\Finance" /grant "Everyone:(OI)(CI)F" /T
icacls "C:\Finance" /audit "Everyone:(OI)(CI)(X,WD,AD)" /T
```

Вторая команда добавляет SACL: аудит для `Everyone` на выполнение (X), запись данных (WD), добавление подкаталогов (AD) для этой папки, её подпапок и файлов. (В реальной среде ограничиваются только нужными учётными записями, например, «Domain Users».)

**Шаг 3. Генерация события доступа.**  
Создаём в папке текстовый файл из‑под учётной записи обычного пользователя (не администратора), затем открываем его в блокноте:

```powershell
New-Item -Path "C:\Finance\report.txt" -ItemType File -Value "Confidential"
notepad "C:\Finance\report.txt"
```

**Шаг 4. Просмотр события в журнале Security.**  
Через несколько секунд открываем Event Viewer, переходим в `Windows Logs\Security` и фильтруем по Event ID 4663. Альтернативно используем PowerShell:

```powershell
$event = Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4663} -MaxEvents 1
$event | Format-List
```

Ожидаемый фрагмент вывода (ключевые поля):

```text
TimeCreated  : 03.05.2025 14:22:15
Id           : 4663
Message      : An attempt was made to access an object.
 
Subject :
	Security ID:		S-1-5-21-... (иллюстративная схема)
	Account Name:		User1
	Account Domain:		DOMAIN
	Logon ID:		0x3E7
Object :
	Object Server:		Security
	Object Type:		File
	Object Name:		C:\Finance\report.txt
	Handle ID:		0x1234
Process Information :
	Process ID:		0xabc
	Process Name:		C:\Windows\System32\notepad.exe
Access Request Information :
	Accesses:		ReadData (or ListDirectory)
	Access Mask:		0x1
```

**Ожидаемый вывод примера.**  
Событие 4663 задокументировало факт чтения файла `report.txt` процессом `notepad.exe` от имени `User1`. SOC‑аналитик, получив это событие, может связать имя учётной записи, тип доступа (`ReadData`) и объект (конфиденциальный файл) для выявления подозрительной активности. Пример демонстрирует полный цикл настройки категорий аудита: от включения подкатегории до появления осмысленного события в журнале, готового к использованию в SIEM‑правилах.
