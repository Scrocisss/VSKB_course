# Использование Beats-утилит

## Beats в конвейере доставки логов: место, роль и разграничение понятий

Beats — семейство легковесных агентов-сборщиков данных, распространяемых компанией Elastic как часть Elastic Stack. Их основная задача — получать операционные данные (логи, метрики, сетевые пакеты, события аудита) непосредственно на узлах-источниках и **надёжно доставлять** их в централизованную систему обработки и хранения. В контексте SOC L1 Beats решают две критически важные проблемы: **универсальность захвата** разнородных источников без написания агентов вручную и **устойчивость к сбоям** канала связи, гарантируя, что ни одно событие не будет потеряно при временной недоступности приёмника.

Beats часто ошибочно отождествляют с Logstash — ещё одним компонентом Elastic Stack, отвечающим за пересылку логов. Принципиальное различие состоит в их архитектурной роли: Beats — децентрализованные оконечные агенты, работающие на периферии инфраструктуры; Logstash — централизованный обработчик, выступающий концентратором, фильтром и буфером. В таблице ниже зафиксированы ключевые различия, важные для понимания границ ответственности при построении SOC-конвейера.

| Компонент | Топология | Функция | Ресурсы | Типичное место в SOC-архитектуре |
|-----------|-----------|---------|---------|----------------------------------|
| Beats (Filebeat, Winlogbeat и др.) | Оконечный агент на каждом источнике | Чтение данных из локального источника, структурирование, буферизация, отправка | Минимальное потребление CPU/памяти, строго ограниченный footprint | Серверы, рабочие станции, сетевые зонды, контейнеры |
| Logstash | Централизованный узел или кластер, может разворачиваться за балансировщиком | Приём из многих источников, сложная фильтрация, преобразование, маршрутизация в несколько хранилищ | Значительное потребление ресурсов, JVM-основа, требует настройки heap | Периметр SOC: коллекторный слой между агентами и Elasticsearch/Kafka |
| Альтернативные агенты (Fluentd, nxlog, Syslog-ng) | Оконечный или шлюзовый | Аналог Beats с другими протоколами вывода, экосистемой плагинов и моделями конфигурации | Разнится, часто сравним с Beats | Возможно применение в гетерогенных средах, где нет поддержки официальных Beats |

Beats не являются получателем syslog-сообщений в классическом понимании: они не открывают слушающие порты UDP/TCP. Вместо этого они активно читают файлы, подписываются на системные API (ETW в Windows, libaudit в Linux) или опрашивают метрики. Именно такая модель работы обеспечивает безопасное разграничение зон: скомпрометированный агент не может принимать произвольный трафик извне.

В SOC L1 первостепенное значение имеют Beats, ориентированные на журналы операционных систем: **Winlogbeat** (журналы событий Windows), **Auditbeat** (системный аудит Linux, метаданные процессов, сокетов, пользователей), **Filebeat** (текстовые журналы приложений в произвольном формате). Дополнительные Beats — **Metricbeat** (метрики CPU, памяти, дисков), **Heartbeat** (проверки доступности), **Packetbeat** (сетевой трафик) — расширяют видимость для детектирования аномалий, но их настройка чаще входит в зону ответственности L2/L3 или инженеров платформы. Ниже перечислены ключевые члены семейства с их целевым назначением.

```text
Filebeat ── чтение логов: /var/log/*.log, Docker-контейнеры, JSON-файлы
Winlogbeat ── подписка на Windows Event Log: Security, System, Application
Auditbeat ── аудит системы: execve, tcp_connect, user_login
Metricbeat ── опрос метрик: CPU, память, сетевые интерфейсы, процессы
Heartbeat ── ICMP/TCP/HTTP-проверки: доступность сервисов
Packetbeat ── cниффинг трафика: DNS, HTTP, TLS-рукопожатия
```

Каждый Beat распространяется как отдельный бинарный файл, конфигурируется через YAML-файл и поддерживает единую модель вывода: Elasticsearch, Logstash, Kafka, Redis, а также стандартные потоки вывода (stdout) для отладки. Подобный подход унифицирует доставку независимо от типа данных и упрощает архитектуру «систем пересылки логов», где Beats играют роль первичного сборщика.

## Класс утилит Beats: архитектурная модель и внутренние компоненты

Семейство Beats образует класс однотипных агентов, объединённых общей архитектурой, моделью конфигурации и логикой работы с выводами. Внутренне Beat устроен как конвейер из трёх основных стадий: **Input** (источник), **Processor** (обработка) и **Output** (вывод), с необязательной очередью перед отправкой.

### Общая архитектурная модель

```text
[Источник данных] ──► [Input] ──► [Processor Pipeline] ──► [Spool/Queue] ──► [Output]
                                                                                   │
                                                                                   ├── Elasticsearch
                                                                                   ├── Logstash
                                                                                   ├── Kafka
                                                                                   └── Redis
```

**Input** определяет, откуда и как читаются данные. Для Filebeat это модуль `log`, реализующий чтение файлов с отслеживанием позиции (registry) и поддержкой ротации логов. Winlogbeat использует подписку на журналы событий через Windows Event Log API (EvtSubscribe), передавая события по мере их появления. Auditbeat взаимодействует с Auditd через netlink-сокет или читает файловые дескрипторы. Каждый Input формирует событие в сыром виде.

**Processors** выполняют фильтрацию и обогащение событий непосредственно на агенте до отправки. К типичным операциям относятся: отбрасывание событий (`drop_event`), удаление полей (`drop_fields`), добавление метаданных (`add_host_metadata`, `add_cloud_metadata`), разбор структурированных сообщений (`decode_json_fields`, `dissect`, `grok`). Локальная предобработка снижает нагрузку на центральный обработчик и сокращает объём трафика. Каждое событие проходит через цепочку процессоров последовательно; порядок задаётся в конфигурации.

**Spool (очередь)** — буфер в памяти и/или на диске, реализующий модель **at-least-once** доставки. Пока выходное подключение недоступно, события накапливаются; при переполнении памяти включается сброс на диск (spool-to-disk). Таким образом обеспечивается устойчивость к кратковременным перебоям сети, что критично для SOC, поскольку потеря даже нескольких секунд Windows Security Event 4688 может лишить аналитика контекста атаки.

**Output** отвечает за отправку событий в централизованные приёмники. Все Beats используют общий транспортный слой (libbeat), обеспечивающий единые параметры повторных попыток, тайм-аутов, балансировки нагрузки между несколькими узлами Elasticsearch или Logstash. При использовании Elasticsearch Beats автоматически управляют шаблонами индексов и ILM-политиками (Index Lifecycle Management), если это разрешено, упрощая администрирование.

### Конфигурационная структура на примере Winlogbeat

Для иллюстрации внутреннего устройства приведём формат конфигурационного YAML-файла (значения полей условны, схема соответствует актуальной версии Winlogbeat 7.x/8.x):

```yaml
winlogbeat.event_logs:
  - name: Security
    processors:
      - drop_fields:
          fields: ["event.original"]
output.elasticsearch:
  hosts: ["https://elasticsearch:9200"]
  username: "winlogbeat_writer"
  password: "${ES_PWD}"
  ssl.verification_mode: certificate
  ssl.certificate_authorities: ["/etc/winlogbeat/ca.crt"]
setup.kibana:
  host: "https://kibana:5601"
logging.level: info
```

В этом фрагменте заданы секции: объявление источника событий (`event_logs`), цепочка процессоров (удаляется поле `event.original` для экономии места), выходные настройки с аутентификацией и TLS. Секция `setup.kibana` позволяет автоматически загружать дашборды при инициализации. Такая структура типична для всех Beats: каждому модулю или источнику соответствует свой блок ввода, а блоки вывода и процессинга — общие или детализируемые.

### Сравнительная характеристика основных утилит

Для SOC L1 полезно понимать различия Beats применительно к источникам данных. Таблица ниже фокусирует отличительные признаки и типовые индикаторы, используемые при мониторинге, расследованиях и поиске угроз.

| Beat | Назначение сбора | Ключевые источники / модули | Типичные индикаторы для правил детекции (SOC) |
|------|------------------|-------------------------------|----------------------------------------------|
| Filebeat | Текстовые журналы приложений, системного демона | `syslog`, `apache`, `nginx`, `mysql`, `auditd` (через файл) | Сообщения об ошибках аутентификации, SQL-инъекциях, подозрительных HTTP-кодах; срабатывания файловых правил |
| Winlogbeat | События Windows | `Security` (Event ID 4624, 4625, 4688), `System`, `Application` | Обнаружение атак Kerberoasting (4769), запуск процессов из подозрительных путей, аномальные входы |
| Auditbeat | Системный аудит Linux | Auditd, метаданные файловой системы (`audit/file_integrity`) | Мониторинг исполнения команд (`execve`), изменения критических конфигов, установления сетевых соединений нестандартными процессами |
| Metricbeat | Метрики ОС и сервисов | `system`, `windows`, `docker`, `kubernetes` | Скачки загрузки CPU при криптомайнинге, резкое увеличение сетевого трафика на нехарактерных портах |
| Heartbeat | Проверки доступности (ICMP/TCP/HTTP) | `icmp`, `tcp`, `http` | Длительные недоступности агентов или критичных сервисов; TLS-сертификаты с истекающим сроком |
| Packetbeat | Анализ сетевого трафика (L7) | `dns`, `http`, `tls`, `flow` | DGA-подобные DNS-запросы, аномальные TLS-сертификаты, HTTP-запросы к подозрительным User-Agent |

Каждый Beat эволюционирует независимо, но все используют общую базу libbeat, что гарантирует единообразное поведение: одна и та же логика повторных попыток, идентичный формат метаданных событий (`@timestamp`, `host.*`, `agent.*`), совместимость с Elastic Common Schema (ECS). Это упрощает корреляцию: Winlogbeat и Filebeat, собирающие данные с одного и того же узла, выдадут события с идентичными `host.name` и `agent.id`, позволяя объединять их в SIEM-запросах.

## Применение Beats в ежедневных операциях SOC: настройка, типовые операции, ошибки

### Установка и конфигурирование агентов

Для SOC-инженера L1 типовой стартовой процедурой является развёртывание Winlogbeat на серверах Windows с контроллером домена. Шаги включают загрузку архива (или MSI-пакета), извлечение в `C:\Program Files\Winlogbeat`, правку конфигурационного файла и регистрацию службы. Ниже приведены команды PowerShell для типовой установки (схематично, значения параметров зависят от среды):

```powershell
# Распаковка и перемещение в стандартную директорию
Expand-Archive -Path ".\winlogbeat-8.15.0-windows-x86_64.zip" -DestinationPath "C:\Program Files"
# Редактирование winlogbeat.yml в любом редакторе
notepad "C:\Program Files\Winlogbeat\winlogbeat.yml"
# Установка службы (PowerShell с правами администратора)
cd "C:\Program Files\Winlogbeat"
.\install-service-winlogbeat.ps1
# Проверка конфигурации
.\winlogbeat.exe test config -c .\winlogbeat.yml
# Запуск службы
Start-Service winlogbeat
```

Аналогичная процедура в Linux для Filebeat включает добавление репозитория Elastic, установку через менеджер пакетов и правку `/etc/filebeat/filebeat.yml`. Пример проверки конфигурации в Linux:

```bash
sudo filebeat test config -c /etc/filebeat/filebeat.yml
sudo systemctl enable filebeat --now
```

### Настройка вывода: работа с Logstash или Elasticsearch

Выбор вывода определяется архитектурой SOC. Если присутствует слой Logstash для обогащения (GeoIP, разбор сложных форматов, маршрутизация в холодное/горячее хранилища), Beats направляют события в Logstash по протоколу lumberjack (Beats input). Минимальная конфигурация со стороны Beat:

```yaml
output.logstash:
  hosts: ["10.0.10.50:5044"]
  loadbalance: true
  compression_level: 3
```

При прямой записи в Elasticsearch (характерно для небольших внедрений) конфигурация требует аутентификации и может выглядеть так:

```yaml
output.elasticsearch:
  hosts: ["https://elastic1:9200", "https://elastic2:9200"]
  protocol: "https"
  username: "beat_prod"
  password: "securepassword"
  ssl.verification_mode: full
```

Важно отметить, что при использовании Logstash между Beat и Elasticsearch сам Beat не выполняет управление индексами; за это отвечает Logstash (через `elasticsearch` plugin). Неверное распределение обязанностей часто становится причиной путаницы у начинающих аналитиков.

### Типичные ошибки и методы их предотвращения

В SOC-практике наиболее частые проблемы связаны с тремя аспектами: аутентификация, буферизация и мониторинг состояния агентов.

**Аутентификация и TLS.** При развёртывании в корпоративной среде часто забывают правильно настроить сертификаты или смешивают опции `ssl.verification_mode: none`. Это может приводить к успешной отправке логов, но создаёт риск MITM-атаки при компрометации сети. Рекомендуемый подход — развернуть доверенное CA и выдавать каждому Beat клиентский сертификат для взаимной аутентификации. Конфигурация для взаимного TLS (mutual TLS) включает поля `ssl.certificate` и `ssl.key`.

**Переполнение очереди и потеря данных.** По умолчанию Beat хранит очередь в памяти, и её размер ограничен. При длительном отключении Logstash или перегрузке Elasticsearch память очереди заполняется, и в зависимости от настройки (`queue.mem.flush.min_events` и disk queue) события могут быть отброшены. Для критичных источников рекомендуется включать дисковую очередь:

```yaml
queue.spool:
  file:
    path: "/var/lib/filebeat/spool.dat"
    size: 512MiB
    page_size: 32KiB
  write:
    codec: cbor
    flush_timeout: 1s
```

**Отсутствие мониторинга самих Beats.** SOC-аналитик должен видеть не только данные, но и факт доставки. Beats способны сообщать собственные метрики (количество отправленных/отброшенных событий, размер очереди) через HTTP-эндпоинт (по умолчанию отключен) или через `monitoring.elasticsearch`. Рекомендуется включить мониторинг в том же кластере Elasticsearch, создав отдельные индексы. Это позволяет строить дашборды состояния агентов и реагировать на снижение поступления событий от конкретного узла до того, как оно приведёт к пропуску инцидента.

**Несовместимость версий.** Версии Beats, Elasticsearch и Logstash должны совпадать по мажорной цифре (например, 8.х с 8.х); использование Beats 7.х с Elasticsearch 8.х может привести к ошибкам индексов и нарушению ECS-полей. Для SOC-аналитика важно при разборе отсутствия данных проверять соответствие версий через логи агента (`logs/winlogbeat` или `systemctl status`).

### Типовые паттерны использования для SOC L1

На уровне L1 аналитику не требуется настраивать Beats с нуля, но необходимо понимать, как интерпретировать поступающие данные и взаимодействовать с инженерами для решения проблем сбора. Основные паттерны:

- **Сбор логов Windows для детектирования атак:** Winlogbeat передаёт весь журнал Security, что позволяет правилам SIEM срабатывать на Event ID 4625 (неудачный вход), 4688 (создание процесса), 5156 (сетевое подключение) и т.д. При отсутствии событий аналитик проверяет статус службы winlogbeat и наличие ошибок в `C:\ProgramData\Winlogbeat\logs\winlogbeat.log`.
- **Сбор syslog с Linux-серверов через Filebeat:** Filebeat с модулем `system` читает `/var/log/syslog` и `/var/log/auth.log`, парсит сообщения о sudo-сессиях, входах SSH. При жалобе на пропуск событий L1 может выполнить `filebeat test output` для проверки связности с центральным приёмником.
- **Мониторинг целостности файлов через Auditbeat:** Auditbeat может отслеживать изменения системных файлов, что используется для обнаружения модификации бинарников или конфигураций. Аналитик может проверить журнал `auditbeat` при обнаружении несанкционированной активности.

## Сквозной практический пример: настройка Winlogbeat для отправки событий безопасности Windows в Elasticsearch

### Исходные условия

Имеется тестовая среда: контроллер домена на Windows Server 2022, развёрнут Elasticsearch (8.15) и Kibana на Linux-узле с адресом 192.168.10.50. Сетевое взаимодействие разрешено по порту 9200 (Elasticsearch) и 5601 (Kibana). Задача — настроить Winlogbeat, чтобы события журнала Security поступали в Elasticsearch, и убедиться в их доступности в Kibana для последующего построения правил детекции.

### Шаги выполнения

**Шаг 1: Установка и базовая конфигурация Winlogbeat**

Скачиваем актуальный дистрибутив Winlogbeat с зеркала Elastic (артефакт — запуск установщика). После извлечения правим `winlogbeat.yml`, указывая источник событий и вывод в Elasticsearch:

```yaml
winlogbeat.event_logs:
  - name: Security
    processors:
      - add_host_metadata:
          when.not.contains.tags: forwarded

output.elasticsearch:
  hosts: ["https://192.168.10.50:9200"]
  username: "elastic"
  password: "changeme"
  ssl.verification_mode: certificate
  ssl.certificate_authorities: ["C:/ProgramData/Elastic/Beats/certs/ca.crt"]

logging.to_files: true
logging.level: debug
```

*Комментарий:* `ssl.verification_mode: certificate` требует наличия корневого сертификата CA, которым подписан сертификат Elasticsearch. Файл `ca.crt` предварительно скопирован.

**Шаг 2: Установка службы и проверка конфигурации**

Выполняем командлет установки службы и тестируем конфигурацию:

```powershell
cd "C:\Program Files\Winlogbeat"
.\install-service-winlogbeat.ps1
.\winlogbeat.exe test config -c .\winlogbeat.yml
```

Ожидаемый вывод:

```text
Config OK
```

Далее тестируем подключение к Elasticsearch:

```powershell
.\winlogbeat.exe test output -c .\winlogbeat.yml
```

Вывод (иллюстративный, фактические значения зависят от версии):

```text
elasticsearch: https://192.168.10.50:9200...
  parse url... OK
  connection...
    parse host... OK
    dns lookup... OK
    addresses: 192.168.10.50
    dial up... OK
  TLS... OK
  talk to server... OK
  version: 8.15.0
```

**Шаг 3: Запуск Winlogbeat и контроль первых событий**

Запускаем службу и инициируем несколько событий входа в систему, чтобы появился поток данных:

```powershell
Start-Service winlogbeat
# Моделирование неудачного входа (выполняется из другого сеанса или консоли)
net use \\localhost /user:wronguser wrongpassword
```

Спустя несколько секунд проверяем состояние очереди Winlogbeat:

```powershell
.\winlogbeat.exe export queue -c .\winlogbeat.yml
```

Вывод может показывать пустую очередь, если события успешно отправлены. При наличии проблем отобразятся накопленные события. Далее просматриваем логи самого Beat:

```powershell
Get-Content C:\ProgramData\Winlogbeat\logs\winlogbeat.log -Tail 20
```

В логах должны присутствовать записи об успешной публикации:

```log
2025-06-18T09:15:23.134+0300 INFO [publisher_pipeline_output] pipeline/output.go:151 Attempting to reconnect to backoff(elasticsearch(https://192.168.10.50:9200)) with 1 reconnect attempt(s)
2025-06-18T09:15:23.140+0300 INFO [publisher_pipeline_output] pipeline/output.go:167 Connection to backoff(elasticsearch(https://192.168.10.50:9200)) established
```

**Шаг 4: Верификация в Kibana**

Переходим в Kibana `https://192.168.10.50:5601`. Открываем Index Management и видим новый индекс `winlogbeat-8.15.0-2025.06.18-000001`. Создаём Data View с паттерном `winlogbeat-*`. В разделе Discover выполняем запрос KQL:

```kql
event.code : 4625 and winlog.event_data.TargetUserName : "wronguser"
```

Результат запроса должен показать событие с Event ID 4625, содержащее поля `host.name`, `event.provider`, `winlog.event_data.TargetUserName`. Скриншот не прилагается, но аналитик видит структурированную запись с временной меткой, соответствующую моменту, когда была выполнена команда `net use`.

### Ожидаемый вывод примера

Демонстрируется, что Winlogbeat успешно собирает события Windows Security, надёжно доставляет их в Elasticsearch в соответствии с заданным выводом, и аналитик SOC может немедленно использовать эти данные для обнаружения попыток неудачного входа через SIEM-запросы. Настройка проста, но критична для обеспечения видимости на конечных точках.
