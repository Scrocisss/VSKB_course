# Windows Event Log: архитектура, анализ и оперативное применение в SOC

## 1. Журналы событий Windows: роль и место в экосистеме безопасности

Windows Event Log — встроенная подсистема операционной системы, обеспечивающая структурированное протоколирование событий, генерируемых ядром, системными службами, приложениями и подсистемой аудита безопасности. Каждая запись содержит временную метку, идентификатор события, источник (провайдер), уровень критичности и контекстные данные, что превращает журналы в непрерывную хронологическую летопись активности на конечной точке. В контексте SOC журналы событий Windows выполняют четыре ключевые функции [CyberDefenders](https://cyberdefenders.org/blog/event-log-analysis-for-soc-analysts):

- **Обнаружение угроз в реальном времени** – корреляция событий аутентификации, доступа к объектам и изменений конфигурации позволяет выявлять индикаторы компрометации (IoC) непосредственно в момент их появления.
- **Расследование инцидентов** – детальные записи дают возможность реконструировать временную шкалу атаки, трассировать боковое перемещение и определить первопричину.
- **Соблюдение нормативных требований** – регламенты вроде PCI DSS, HIPAA, GDPR предписывают обязательное протоколирование и хранение записей; журналы Windows служат основным источником доказательной базы при аудите.
- **Проактивная охота за угрозами (Threat Hunting)** – ретроспективный анализ накопленных данных позволяет обнаружить скрытые атаки, не замеченные сигнатурными средствами.

В отличие от файловой системы или реестра, предоставляющих статический слепок состояния, событийные журналы фиксируют временной поток изменений с точной привязкой ко времени. При этом они не всеобъемлющи: журналы могут затираться при переполнении, а злоумышленник с правами администратора способен очистить их. Поэтому в современной защитной практике журналы Windows всегда комбинируют с дополнительными источниками телеметрии — Sysmon, записями реестра, файлами Prefetch, журналами PowerShell и централизованным сбором в SIEM [Elcomsoft](https://blog.elcomsoft.ru/2026/02/kriminalisticheskij-analiz-zhurnala-sobytij-windows-event-log).

Ключевое разграничение, которое необходимо усвоить с первых шагов, — классификация самих журналов. По умолчанию оснастка Event Viewer группирует их на две крупные категории: «Windows Logs» и «Applications and Services Logs». Первые включают пять традиционных контейнеров, создаваемых самой ОС; вторые — каналы отдельных приложений, служб и компонентов, структурированные по поставщикам (provider).

Таблица ниже систематизирует базовые категории журналов Windows и их назначение.

| Название журнала | Источник событий | Характерные Event ID и примеры | Применение в SOC |
|------------------|------------------|-------------------------------|------------------|
| **Application** | Приложения и службы пользовательского режима | Ошибки установки, вылеты процессов (например, 1000 — Application Error), предупреждения о нехватке ресурсов | Выявление сбоев легитимных защитных средств, индикация атак на приложения |
| **Security** | Подсистема аудита безопасности (LSASS) | **4624** (успешный вход), **4625** (неудачный вход), **4672** (назначение привилегий), **4688** (создание процесса), **4720** (создание учётной записи) | Ключевой источник для обнаружения брутфорса, бокового перемещения, повышения привилегий и создания аккаунтов персистентности |
| **System** | Ядро ОС и системные драйверы | События загрузки/выключения (6005, 6006), остановки служб (7036), сбои драйверов | Отслеживание перезагрузок (возможное сокрытие следов), падение критичных служб безопасности |
| **Setup** | Установщик Windows и ролей сервера | События добавления/удаления компонентов ОС | Обнаружение неавторизованной установки средств мониторинга или отключения защитных ролей |
| **Forwarded Events** | Сборщик Windows Event Forwarding | Копии событий с других машин домена | Централизованный мониторинг, если нет выделенного SIEM |
| **Applications and Services Logs** | Провайдеры конкретных компонентов (PowerShell, WMI, OpenSSH, PrintService и др.) | *Microsoft-Windows-PowerShell/Operational*: 4104 (выполнение сценариев), *Microsoft-Windows-Sysmon/Operational*: 1 (создание процесса) [HackMD](https://hackmd.io/@hackermans/BkFx7kx8T) | Расширенный анализ скриптовых атак (LOTL), WMI-злоупотреблений, сетевых взаимодействий через Sysmon |

Таблица демонстрирует, что журнал **Security** является краеугольным аналитическим источником для SOC, тогда как каналы приложений и служб критичны для раскрытия техник Living-off-the-Land, маскирующихся под легитимную активность. Разграничение журналов по провайдерам позволяет выстраивать многоуровневый сбор: штатные политики аудита фиксируют базовые события безопасности, а такие компоненты как Sysmon добавляют низкоуровневую телеметрию (хэши процессов, сетевые соединения, изменения файлов), невидимую для стандартного Security-лога [Australian Cyber Security Centre (ACSC)](https://www.cyber.gov.au/sites/default/files/2024-08/best-practices-for-event-logging-and-threat-detection.pdf).

На уровне предприятия потоки событий консолидируются через Windows Event Forwarding либо агенты (Winlogbeat, Fluent Bit) и попадают в SIEM‑платформу, где применяется корреляционный анализ. Локальные файлы `.evtx` могут быть очищены или перезаписаны, тогда как централизованное хранилище сохраняет полную картину — этот принцип закладывается в проект системы логирования с самого начала.

Таким образом, Windows Event Log — это не изолированный артефакт, а центральный узел сбора телеметрии, требующий понимания иерархии журналов, формата записей и методов извлечения данных.

## 2. Внутреннее устройство журналов: от события до файла .evtx

Внутреннее устройство Windows Event Log определяется двумя уровнями: логической моделью «провайдер–канал–событие» и физическим форматом хранения данных в файлах `.evtx`.

### 2.1 Логическая модель

Событие генерируется **провайдером** (provider) — компонентом, зарегистрированным в системе как источник событий. Провайдеры реализуются через инфраструктуру Event Tracing for Windows (ETW). Каждый провайдер привязан к одному или нескольким **каналам** (channel), которые и определяют, в какой журнал попадёт запись. Каналы бывают четырёх типов [CrowdStrike](https://www.crowdstrike.com/en-us/guides/windows-logging):

- **Административные** (Administrative) — наиболее распространённые, в них попадают события, интересные администраторам и аналитикам; журналы Security, System, Application относятся к этому типу.
- **Операционные** (Operational) — фиксируют штатные операции компонента, полезны для диагностики и расширенного мониторинга (например, Microsoft-Windows-PowerShell/Operational).
- **Аналитические** (Analytic) — содержат высокодетализированные события, описывающие внутреннюю работу компонента; по умолчанию отключены из-за большого объёма.
- **Отладочные** (Debug) — низкоуровневые события, используемые разработчиками; практически не применяются в SOC.

Журнал представляет собой хранилище событий одного канала. Внутри журнала записи упорядочены по локальному идентификатору **EventRecordID**; глобального сквозного ID, охватывающего все журналы, не существует.

### 2.2 Формат файла .evtx и структура записи

Начиная с Windows Vista и Server 2008 журналы хранятся в формате **.evtx**, пришедшем на смену устаревшему `.evt`. Файл `.evtx` — это бинарный контейнер с внутренней фрагментацией, внутри которого находятся сериализованные XML-записи. Такая архитектура сочетает компактность бинарного хранения с гибкостью и расширяемостью XML [Elcomsoft](https://blog.elcomsoft.ru/2026/02/kriminalisticheskij-analiz-zhurnala-sobytij-windows-event-log). Каждая запись инкапсулирует два обязательных элемента: **System** (метаданные) и **EventData** (полезная нагрузка). Некоторые события могут дополнительно содержать элементы **UserData** или **RenderingInfo**. Ниже представлена структурная схема ключевых полей элемента `System`, формирующих поисковый каркас для аналитика.

| Поле | Описание | Пример (иллюстративная схема) |
|------|----------|-------------------------------|
| **Provider Name** | Идентификатор провайдера, сгенерировавшего событие; соответствует зарегистрированному ETW-провайдеру | `Microsoft-Windows-Security-Auditing` |
| **Provider Guid** | Уникальный GUID провайдера, неизменяемый идентификатор | `{54849625-5478-4994-a5ba-3e3b0328c30d}` (фиксирован для Security) |
| **EventID** | Числовой идентификатор класса события; совместно с Provider определяет схему | `4624` (успешный вход) |
| **Version** | Версия схемы события; изменения в данных события могут увеличивать версию | `0` |
| **Level** | Уровень важности: 1 — Critical, 2 — Error, 3 — Warning, 4 — Informational (по умолчанию), 5 — Verbose [Jalblas](https://www.jalblas.com/blog/tryhackme-windows-event-logs-walkthrough) | `0` (LogAlways) для аудита успеха |
| **Task** | Категория задачи, уточняющая контекст (например, Logon, Logoff, Special Logon) | `12544` (Logon) |
| **Opcode** | Код операции в рамках задачи; часто показывает начало или завершение действия | `0` (Info) |
| **Keywords** | Битовая маска, помечающая принадлежность события к классификационным группам (например, Audit Success, Audit Failure) | `0x8020000000000000` (Audit Success) |
| **TimeCreated SystemTime** | Временная метка создания события в формате UTC (ISO 8601) | `2025-04-01T09:15:32.4876543Z` |
| **EventRecordID** | Локальный порядковый номер записи внутри конкретного журнала; монотонно возрастает | `123456` |
| **Execution ProcessID** | PID процесса-провайдера, записавшего событие; для Security-аудита обычно PID процесса LSASS | `728` |
| **Execution ThreadID** | Идентификатор потока внутри процесса провайдера | `812` |
| **Channel** | Имя канала (журнала), в который помещена запись | `Security` |
| **Computer** | Имя компьютера, на котором возникло событие | `DESKTOP-ABC123` |
| **Security UserID** | SID пользователя, от имени которого выполнялась операция (если применимо) | `S-1-5-18` (SYSTEM) |

Элемент **EventData** содержит динамический набор пар имя-значение, специфичный для каждой комбинации Provider + EventID. Например, для события 4624 это `SubjectUserSid`, `TargetUserName`, `LogonType`, `IpAddress` и др. Именно эти поля аналитик извлекает для фильтрации и корреляции.

Упрощённое представление XML-записи события 4624:

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="{...}"/>
    <EventID>4624</EventID>
    <Version>0</Version>
    <Level>0</Level>
    <Task>12544</Task>
    <Opcode>0</Opcode>
    <Keywords>0x8020000000000000</Keywords>
    <TimeCreated SystemTime="2025-04-01T09:15:32.4876543Z"/>
    <EventRecordID>123456</EventRecordID>
    <Execution ProcessID="728" ThreadID="812"/>
    <Channel>Security</Channel>
    <Computer>DESKTOP-ABC123</Computer>
    <Security UserID="S-1-5-18"/>
  </System>
  <EventData>
    <Data Name="SubjectUserSid">S-1-5-18</Data>
    <Data Name="TargetUserName">User1</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="IpAddress">192.168.1.100</Data>
    <!-- ... другие поля -->
  </EventData>
</Event>
```

Приведённая XML-структура — иллюстративная схема, реальные имена полей зависят от версии ОС и схемы события. Важно понимать, что физически этот XML упаковывается в бинарный поток внутри `.evtx`-файла; прямой разбор файлов без специализированных API затруднителен. Утилиты вроде `wevtutil`, `Get-WinEvent` и коммерческие инструменты берут на себя десериализацию и предоставляют события в объектном или текстовом виде.

### 2.3 Модель ротации и хранения

Каждый журнал имеет максимальный размер (по умолчанию 20 МБ для Security, 1 МБ для Application и System). При достижении лимита поведение управляется политикой: события могут перезаписываться по принципу «старые затираются новыми», архивный файл создаётся автоматически или запись прекращается. В расследованиях часто приходится восстанавливать затертые записи из теневых копий тома или обращаться к централизованным архивам. Кроме того, временные метки хранятся в UTC, но Event Viewer отображает их в локальном часовом поясе; ошибки привязки ко времени — частая причина неверной корреляции событий между системами. Проверку коррекции времени выполняют через параметр `ActiveTimeBias` ветви реестра `HKLM\SYSTEM\CurrentControlSet\Control\TimeZoneInformation` [Elcomsoft](https://blog.elcomsoft.ru/2026/02/kriminalisticheskij-analiz-zhurnala-sobytij-windows-event-log).

## 3. Инструменты и техники анализа журналов Windows

Анализ журналов Windows на практике выполняется тремя основными инструментами, предоставляемыми самой ОС: оснасткой Event Viewer, утилитой командной строки `wevtutil.exe` и командлетами PowerShell `Get-WinEvent`. Каждый из них решает определённый класс задач, и выбор инструмента определяется контекстом: интерактивное расследование на локальной машине, удалённый сбор или автоматизация в скриптах и пайплайнах.

### 3.1 Event Viewer (eventvwr.msc)

Графическая консоль Event Viewer группирует журналы в дерево, позволяет открыть любой журнал, применить фильтр по уровню, времени, Event ID и ключевым словам, а также создавать пользовательские представления (Custom Views) на основе XPath-запросов [CrowdStrike](https://www.crowdstrike.com/en-us/guides/windows-logging). Основное применение — быстрое ознакомление с состоянием системы, проверка свежих критических ошибок, просмотр детальной информации о конкретном событии с отформатированным текстовым описанием (если провайдер поставляет локализованные строки). Однако в SOC-контексте Event Viewer имеет серьёзные ограничения:

- отсутствие автоматической корреляции между разными журналами или хостами;
- максимальный размер загружаемого журнала и низкая скорость фильтрации при больших объёмах;
- невозможность строить сложные многокомпонентные запросы, выходящие за рамки элементарного XPath 1.0.

Поэтому оперативное реагирование и проактивный поиск практически всегда ведутся через PowerShell или централизованные SIEM-консоли.

### 3.2 wevtutil.exe

Консольная утилита `wevtutil` позволяет выполнять весь спектр административных и аналитических операций с журналами: перечисление журналов (`el`), запрос событий (`qe`), экспорт в `.evtx` или текстовые форматы, очистка (`cl`), настройка параметров (`sl`). Для аналитика ключевой является команда `qe`, поддерживающая XPath-запросы. Ниже приведён типичный пример извлечения последних пяти событий успешного входа из журнала Security с отображением в текстовом виде.

```powershell
wevtutil qe Security /q:"*[System[(EventID=4624)]]" /c:5 /rd:true /f:text
```

Разбор параметров:
- `/q:` — XPath-выражение, фильтрующее события по `EventID=4624`.
- `/c:5` — ограничение числа возвращаемых записей.
- `/rd:true` — сортировка от новых к старым (reverse direction).
- `/f:text` — вывод в текстовом формате; доступен также `RenderedXml`, `XML`.

Частый кейс — подсчёт количества неудачных входов за последние сутки группировкой по IP-адресу; для этого результат `wevtutil` обычно перенаправляют в PowerShell или используют напрямую командлет `Get-WinEvent`.

### 3.3 Get-WinEvent (PowerShell)

Командлет `Get-WinEvent` предоставляет наиболее гибкий механизм выборки: фильтрацию по хэш-таблице (FilterHashtable), по XPath (FilterXPath) или по заранее подготовленному XML-фильтру (FilterXml). Хэш-таблица — самый простой и производительный способ, так как фильтрация происходит на стороне провайдера, и по сети (при удалённом сборе) передаются только подходящие события. Пример извлечения десяти последних событий с идентификатором 4625:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security';ID=4625} -MaxEvents 10 |
    Format-List TimeCreated, ProviderName, Id, Message
```

Для более сложных условий, например, поиска входов типа RDP (LogonType 10) в определённом временном окне, используют XPath-запрос. Следующий запрос возвращает события 4624 с LogonType = 10 и IP-адресом из указанного диапазона:

```powershell
$xmlFilter = @"
<QueryList>
  <Query Id="0" Path="Security">
    <Select Path="Security">
      *[System[(EventID=4624)]]
      and
      *[EventData[Data[@Name='LogonType']='10']]
      and
      *[EventData[Data[@Name='IpAddress'] and (Data >= '192.168.1.0' and Data <= '192.168.1.255')]]
    </Select>
  </Query>
</QueryList>
"@
Get-WinEvent -FilterXml $xmlFilter -MaxEvents 20 | Select-Object -First 1
```

Эта конструкция — мощный инструмент для точечного извлечения событий без необходимости «пролистывать» весь журнал.

### 3.4 Расширение телеметрии: Sysmon и интеграция с SIEM

Штатные возможности аудита Windows не покрывают низкоуровневые артефакты, критически важные для обнаружения продвинутых угроз: детали сетевых соединений, хэши исполняемых файлов, полные командные строки процессов, изменения файловой системы по определённым маскам. Для этого Microsoft предлагает Sysmon (System Monitor) — драйвер и службу, записывающие события в канал `Microsoft-Windows-Sysmon/Operational` [HackMD](https://hackmd.io/@hackermans/BkFx7kx8T). Ключевой идентификатор Sysmon — **EventID 1** (ProcessCreate) — содержит поля `CommandLine`, `Hashes`, `ParentProcessId`, позволяющие восстанавливать деревья процессов и детектировать аномалии вроде запуска PowerShell из электронной таблицы Excel или вызова `rundll32` с подозрительными аргументами [TryHackMe](https://medium.com/@RosanaFS/windows-logging-for-soc-tryhackme-walkthrough-e4aa10339261).

В корпоративных SOC-средах журналы со всех конечных точек пересылаются в SIEM (Splunk, Elastic Security, Microsoft Sentinel) с помощью Windows Event Forwarding или легковесных агентов (Winlogbeat). На стороне SIEM аналитик оперирует не сырыми ID, а корреляционными правилами и панелями визуализации: например, правило «множественные 4625 → 4624 в течение 60 секунд» автоматически создаёт инцидент с оценкой серьёзности.

### 3.5 Типичные ошибки анализа

- **Интерпретация Logon Type без контекста.** Тип 3 (Network) не всегда указывает на удалённую атаку — он также используется при подключении к сетевым папкам. Для верификации необходимо учитывать `WorkstationName`, `IpAddress` и сопутствующие события (например, 4648 — явное указание учётных данных для входа).
- **Игнорирование события 4648.** При использовании `runas` или подобных механизмов сначала генерируется 4648 (Logon with explicit credentials), а затем 4624. Пропуск 4648 может скрыть факт применения украденных учётных данных.
- **Полагаться только на журнал Security.** PowerShell-атаки без включения логирования скриптов (EventID 4104) не оставляют следов в Security; аналогично, WMI-подписки (EventID 5861) требуют активированных аналитических каналов.
- **Неучёт расхождения часовых поясов.** Если SIEM преобразует время, а локальный Event Viewer показывает UTC+смещение, временная разница способна исказить последовательность событий на десятки минут.

## 4. Сквозной практический пример: расследование атаки с подбором пароля и повышением привилегий

**Исходные условия.** Рабочая станция Windows 10 под управлением доменной политики аудита. Включены подкатегории «Logon/Logoff» и «Account Management», Sysmon не развёрнут. Аналитик L1 получает из SIEM алерт: с одного IP-адреса зафиксирована серия неудачных попыток входа с последующей успешной аутентификацией. Цель — подтвердить или опровергнуть компрометацию, используя только локальные журналы Security и PowerShell.

### Шаг 1: Профилирование неудачных входов

Необходимо извлечь все события 4625 за последний час и определить IP-адрес наиболее активного источника неудачных попыток. Команда группирует события по значению поля `IpAddress` и сортирует по убыванию частоты.

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security';ID=4625;StartTime=(Get-Date).AddHours(-1)} |
    ForEach-Object {
        $xml = [xml]$_.ToXml()
        $ipNode = $xml.Event.EventData.Data | Where-Object { $_.Name -eq 'IpAddress' }
        [PSCustomObject]@{ IP = $ipNode.'#text' }
    } |
    Group-Object -Property IP |
    Sort-Object Count -Descending
```

Ожидаемый вывод (иллюстративная схема):

```
Count Name          Group
----- ----          -----
  147 203.0.113.45  {@{IP=203.0.113.45}, @{IP=203.0.113.45}, ...}
    3  10.0.0.1     {@{IP=10.0.0.1}, ...}
```

Вывод демонстрирует 147 неудачных попыток с внешнего адреса `203.0.113.45` за час, что является сильным индикатором атаки методом перебора или распыления пароля.

### Шаг 2: Поиск успешного входа с того же IP

Следующий логический шаг — проверить, завершилась ли атака успешной аутентификацией. Ищем события 4624, где поле `IpAddress` соответствует выявленному адресу, и ограничиваемся одной записью для подтверждения факта.

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security';ID=4624;StartTime=(Get-Date).AddHours(-1)} |
    Where-Object {
        $xml = [xml]$_.ToXml()
        $data = $xml.Event.EventData.Data
        ($data | Where-Object { $_.Name -eq 'IpAddress' }).'#text' -eq '203.0.113.45'
    } |
    Select-Object -First 1 |
    ForEach-Object {
        $xml = [xml]$_.ToXml()
        $data = $xml.Event.EventData.Data
        $props = @{
            TimeCreated = $_.TimeCreated
            TargetUser  = ($data | Where-Object Name -eq 'TargetUserName').'#text'
            LogonType   = ($data | Where-Object Name -eq 'LogonType').'#text'
            LogonID     = ($data | Where-Object Name -eq 'TargetLogonId').'#text'
            IpAddress   = ($data | Where-Object Name -eq 'IpAddress').'#text'
        }
        [PSCustomObject]$props
    }
```

Иллюстративный вывод:

```
TimeCreated      : 2025-04-01T09:15:32.4876543Z
TargetUser       : svc_backup
LogonType        : 10
LogonID          : 0x3E7A1B2C
IpAddress        : 203.0.113.45
```

Обнаружен успешный вход под учётной записью `svc_backup` по протоколу RDP (LogonType 10). LogonID `0x3E7A1B2C` служит якорем для дальнейшего отслеживания всей сессии.

### Шаг 3: Проверка повышения привилегий

Компрометация сервисной учётной записи часто ведёт к попытке повысить привилегии. Событие 4672 (Special Privileges assigned to new logon) регистрирует назначение административных привилегий во время входа. Найдём его для того же LogonID.

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security';ID=4672;StartTime=(Get-Date).AddHours(-1)} |
    Where-Object {
        $xml = [xml]$_.ToXml()
        ($xml.Event.EventData.Data | Where-Object Name -eq 'TargetLogonId').'#text' -eq '0x3E7A1B2C'
    } |
    Format-List TimeCreated, @{
        n='Privileges'; e={
            ($xml.Event.EventData.Data | Where-Object Name -eq 'PrivilegeList').'#text'
        }
    }
```

Ожидаемый вывод:

```
TimeCreated : 2025-04-01T09:15:32.5012345Z
Privileges  : SeSecurityPrivilege
              SeTakeOwnershipPrivilege
              SeLoadDriverPrivilege
              ...
```

Присутствие события 4672 с обширным списком привилегий прямо после успешного входа подтверждает, что злоумышленник получил уровень администратора на системе.

### Шаг 4: Анализ пост-аутентификационной активности через отслеживание процессов

Даже без Sysmon можно частично восстановить действия злоумышленника, если включена подкатегория аудита «Process Creation» (событие 4688). Фильтруем все такие события, связанные с LogonID `0x3E7A1B2C`.

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security';ID=4688;StartTime="2025-04-01T09:15:00Z"} |
    Where-Object {
        $xml = [xml]$_.ToXml()
        ($xml.Event.EventData.Data | Where-Object Name -eq 'SubjectLogonId').'#text' -eq '0x3E7A1B2C'
    } |
    Select-Object TimeCreated,
        @{n='ProcessName';e={($xml.Event.EventData.Data | Where-Object Name -eq 'NewProcessName').'#text'}},
        @{n='CommandLine';e={($xml.Event.EventData.Data | Where-Object Name -eq 'CommandLine').'#text'}}
```

Иллюстративная схема вывода:

```
TimeCreated             ProcessName          CommandLine
-----------             -----------          -----------
2025-04-01T09:16:01Z   C:\Windows\...\cmd   cmd.exe /c whoami /priv
2025-04-01T09:16:15Z   C:\Windows\...\pwsh  powershell -enc QwBmAH...
```

Запуск закодированного PowerShell-скрипта (флаг `-enc`) немедленно после повышения привилегий — классический паттерн действий злоумышленника по закреплению или эксфильтрации данных.

**Ожидаемый вывод.** Сквозной анализ демонстрирует полную цепочку компрометации: брутфорс RDP → успешный вход под учётной записью `svc_backup` → немедленное получение административных привилегий → запуск подозрительных процессов. Полученных улик достаточно для эскалации инцидента на уровень L2/L3, изоляции рабочей станции и инициирования процедуры реагирования. Пример подчёркивает, как последовательное извлечение и корреляция всего нескольких типов событий (4625 → 4624 → 4672 → 4688) способны раскрыть сложную атаку даже при отсутствии специализированного инструментария вроде Sysmon.
