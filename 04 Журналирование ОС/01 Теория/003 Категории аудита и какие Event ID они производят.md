# Категории аудита и генерируемые ими события Windows

## 1. Категории аудита Windows: место в архитектуре безопасности и базовые понятия

События безопасности Windows (Windows Event Log) — фундаментальный источник для мониторинга, расследования инцидентов и соблюдения стандартов управления доступом. Система аудита состоит из трёх ключевых элементов: **политик аудита** (определяющих, *что* регистрировать), **журнала безопасности** (Security log — канал записи) и **провайдеров событий** (компоненты ОС и приложений, генерирующих события). Термин «категория аудита» в контексте Windows имеет двойное значение, поэтому необходимо чётко разграничить **наследуемые категории верхнего уровня** (Legacy Audit Policy) и **расширенные подкатегории** (Advanced Audit Policy), которые являются основой для тонкой настройки.

Начиная с Windows Vista и Server 2008, Microsoft внедрила Advanced Audit Policy, которая заменила грубые девять категорий Legacy (например, «Аудит входа в систему», «Аудит доступа к объектам») на иерархию из **59 подкатегорий**, сгруппированных по тем же девяти родительским категориям. Включение хотя бы одной подкатегории в рамках Advanced автоматически переопределяет глобальные настройки Legacy. Это критически важно для SOC-аналитика: традиционная настройка через `secpol.msc` (Legacy) может не дать ожидаемого результата, если в домене применяется более детальная Advanced-политика.

Центральная единица политики аудита — **подкатегория** (subcategory). Она соответствует определённому классу операций системы безопасности (например, «Вход в систему», «Изменение членства в группе»). Каждая подкатегория может находиться в одном из трёх состояний: **без аудита**, **аудит успехов**, **аудит отказов** или **аудит успехов и отказов** (комбинация). Реальная полезность Advanced-политик раскрывается именно на уровне подкатегорий: специалист может регистрировать только успешные обращения к объектам файловой системы, игнорируя остальные типы объектов, или отслеживать только отказы привилегированных операций.

Связь между включённой подкатегорией и появлением записей в журнале безопасности осуществляется через **MS-Windows-Security-Auditing** — главного провайдера событий безопасности. Если подкатегория активна (например, «Вход в систему» с аудитом успехов), провайдер при возникновении события успешного интерактивного входа генерирует запись с Event ID 4624 и помещает её в Security log. Важно, что не все события безопасности привязаны к политикам аудита; ряд системных событий (запуск служб, остановка ОС) генерируются автоматически без настроек аудита (например, Event ID 6005). Однако для SOC-мониторинга нас интересуют события, управляемые аудитом.

Ниже представлена сравнительная характеристика двух подходов к управлению аудитом.

| Параметр                         | Legacy Audit Policy (9 базовых категорий)            | Advanced Audit Policy (59 подкатегорий)                |
|----------------------------------|------------------------------------------------------|--------------------------------------------------------|
| Охват событий                    | Каждая категория включает широкий набор событий      | Тонкая настройка: можно изолировать конкретные операции|
| Настройка                        | Включается/выключается глобально                     | Включается для успеха / отказа / обоих                 |
| Инструменты управления           | `secpol.msc` (локальная политика), `gpedit.msc`      | `auditpol.exe`, `Set-GPRegistryValue`, групповая политика с расширенными шаблонами |
| Приоритет                        | Уступает Advanced; если Advanced настроена, Legacy игнорируется | Переопределяет Legacy при любых заданных подкатегориях |
| Пример детализации               | «Аудит доступа к объектам» фиксирует все типы объектов (файлы, реестр, ядро) | Подкатегория «File System» изолирует только доступ к файлам |
| Типичные Event ID (пример)       | 4663 (доступ к объекту) без различия типа объекта    | 4663 с детальным полем *ObjectType* = File, Key и т.д. |

Таким образом, для построения эффективного мониторинга SOC L1 критически использовать Advanced Audit Policy, ориентируясь на конкретные подкатегории и чётко документируя включённые комбинации успеха/отказа. Именно через подкатегории и определяются, **какие Event ID** появятся в журнале при наступлении отслеживаемого действия.

## 2. Структура категорий аудита и механизм генерации событий

Advanced Audit Policy группирует 59 подкатегорий в девять родительских категорий, унаследованных от Legacy, но с радикальным расширением охвата. Родительская категория задаёт тематическую область (например, «Управление учётными записями»), а подкатегория — конкретную операцию («Аудит создания учётной записи пользователя»). При включённом аудите подкатегории система активирует регистрацию строго определённого набора Event ID. Однако следует понимать, что одна подкатегория может порождать **несколько** событий для разных исходов (успех, отказ) или для разных вариантов операции (локальный вход, сетевой вход, вход через службу). SOC-специалист должен знать эти связки, чтобы сопоставить поступающий Event ID с конкретной подкатегорией и, при необходимости, скорректировать политику детектирования.

Иерархию политик, подкатегорий, провайдера и журнала удобно представить в виде схемы:

```text
[Политика аудита заданного уровня (групповая/локальная)]
            │
            ▼
[Родительская категория (напр., Logon/Logoff)]
            │
            ▼
[Подкатегория (напр., Logon)]  – состояние {+успех, +отказ}
            │
            ▼
[MS-Windows-Security-Auditing провайдер]
            │
            └──(при действии)→ [Генерация события с конкретным Event ID]
                                  │
                                  ▼
                         [Журнал безопасности Security.evtx]
```

Каждое событие в журнале содержит системные поля: **Event ID** (числовой идентификатор), **Task Category** (текстовое имя подкатегории, например, «Вход в систему»), **Keywords** (битовая маска: Audit Success, Audit Failure), **Уровень** (Information, Warning, Error), **Идентификатор записи**, **компьютер**, **пользователь**, а также расширенный набор полей (EventData), специфичный для каждого Event ID. Именно поле Task Category однозначно указывает, какая подкатегория породила событие. Например, Event ID 4720 (создание пользователя) в журнале всегда сопровождается Task Category «Управление учётными записями пользователей», если подкатегория «Аудит управления учётными записями пользователей» включена.

Ниже приведена фундаментальная таблица соответствия **подкатегорий** ключевым **Event ID**, которые чаще всего востребованы в задачах SOC L1 (обнаружение аномалий, атак, требование ISO/SOC2). Список не претендует на охват абсолютно всех возможных Event ID для каждой подкатегории (полный перечень насчитывает сотни параметров), но даёт исчерпывающее покрытие *наиболее значимых* для мониторинга идентификаторов.

Представленная таблица отражает **причинно-следственную связь**: включение подкатегории (второй столбец) делает возможной генерацию перечисленных Event ID при наступлении соответствующих попыток (успешных или неудачных в зависимости от настроек). Аналитик, видя в ленте событий Event ID 4625 с кодом ошибки 0xC000006D (учётная запись отключена), мгновенно определяет, что источником является подкатегория Logon из блока Logon/Logoff. Это знание необходимо для написания точных правил корреляции и поиска угроз (threat hunting). Более того, многие подкатегории взаимоусиливаются: например, «отслеживание процессов» в комбинации с «аудитом объекта» позволяет построить цепочку «создание процесса – доступ к файлу».

Таким образом, архитектура аудита построена так, что Event ID является продуктом включённой подкатегории, и специалист должен уметь обратным ходом от Event ID переходить к стоящей за ней задаче безопасности. Это закладывает основу для практической работы с журналом.

## 3. Настройка, сбор и анализ событий: практический инструментарий

На уровне SOC L1 повседневная работа с событиями аудита включает три взаимосвязанные задачи: **(1) настройка политик аудита для обеспечения видимости**, **(2) централизованный сбор или локальный доступ к журналу**, **(3) поиск и интерпретация событий по известным индикаторам**. Рассмотрим каждую из них с конкретными приёмами, которые должен освоить специалист.

**Настройка аудита с помощью `auditpol.exe`**
Утилита командной строки `auditpol` — основной инструмент для просмотра и изменения Advanced Audit Policy в современных ОС Windows, включая серверные редакции. Она работает напрямую с базой политик аудита, не требуя перезагрузки, хотя для немедленного применения некоторых изменений нужен `gpupdate /force`. Рассмотрим типовые операции.

Просмотр текущих политик для всех подкатегорий:
```cmd
auditpol /get /category:*
```
Вывод показывает каждую подкатегорию с состоянием: No Auditing, Success, Failure, Success and Failure. Пример фрагмента:
```
System audit policy
Category/Subcategory                      Setting
  Security System Extension              No Auditing
  System Integrity                       Success and Failure
...
```

Включение аудита успешных и неудачных попыток входа в систему (подкатегория Logon из категории Logon/Logoff):
```cmd
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
```
Команда выполняется без сообщений в случае успеха. Убедиться можно повторным `auditpol /get /subcategory:"Logon"`. Этой же командой можно оставить только мониторинг отказов: `/failure:enable /success:disable`. Для отключения аудита по подкатегории целиком используется `/success:disable /failure:disable`.

Настройка аудита через групповые политики (GPO) является предпочтительным методом в доменной среде. Путь в редакторе: `Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration → Audit Policies`. После задания политик обновление на машинах выполняется стандартным циклом GPO (90+30 минут) или принудительно `gpupdate /force`.

**Сбор событий**
Для локального анализа чаще всего используют Windows Event Viewer (`eventvwr.msc`) или PowerShell. Удалённый сбор в SOC обычно реализуется через Windows Event Forwarding (WEF) или агенты (например, Winlogbeat) с передачей в SIEM. Ниже сконцентрируемся на командах PowerShell как наиболее гибких и воспроизводимых.

Извлечение событий из журнала безопасности с помощью `Get-WinEvent`. Например, поиск всех событий входа за последние 24 часа:
```powershell
Get-WinEvent -LogName Security -FilterXPath "*[System[EventID=4624]]" -MaxEvents 100 |
    Format-Table TimeCreated, Id, Message -AutoSize
```
Более сложная фильтрация: только неудачные входы с кодом ошибки 0xC000006A (неверное имя пользователя или пароль):
```powershell
$xml = '*[System[EventID=4625]] and *[EventData[Data[@Name="Status"]="0xC000006A"]]'
Get-WinEvent -LogName Security -FilterXPath $xml -MaxEvents 50 |
    ForEach-Object { $_.Message }
```
Здесь `$_.Message` выводит текстовое представление, но в реальной работе удобнее разбирать поля EventData программно через `$_.Properties`.

**Интерпретация событий**
Получив запись, аналитик должен извлечь ключевые значения. Рассмотрим структуру Event ID 4688 (создание процесса). При включённой подкатегории «Process Creation» в журнал записывается имя исполняемого файла и, при соответствующей настройке, командная строка. Пример фильтрации процессов, запущенных из временной папки:
```powershell
Get-WinEvent -LogName Security -FilterXPath "*[System[EventID=4688]]" | 
    Where-Object { $_.Properties[5].Value -like '*\Temp\*' } |
    Select-Object TimeCreated, 
        @{n='Process';e={$_.Properties[5].Value}},
        @{n='CommandLine';e={$_.Properties[8].Value}}
```
- `Properties[5].Value` — NewProcessName
- `Properties[8].Value` — CommandLine (требуется включённый аудит создания процессов с командной строкой, GPO «Include command line in process creation events»)

**Типичные ошибки и подводные камни**
- **Конфликт Legacy и Advanced**: если в Advanced задана политика хотя бы для одной подкатегории, все остальные подкатегории, не упомянутые явно, наследуют состояние от Advanced (обычно «No Auditing»), игнорируя Legacy-настройки. Поэтому часто администраторы не видят ожидаемых событий, забыв отключить все Advanced-политики.
- **Недостаточное дисковое пространство**: Аудит множества подкатегорий (особенно Object Access) генерирует огромный объём данных, журнал безопасности может переполняться. Необходимо настраивать размер журнала и перезапись старых событий.
- **Не все действия фиксируются при аудите только успеха**: например, для детектирования брутфорса критичен аудит отказов подкатегории Logon. Если он не включен, Event ID 4625 не появится.
- **Зависимость от SACL**: для Object Access (File System) одного включения подкатегории недостаточно — необходимо также задать System Access Control List (SACL) на конкретном объекте (файле, папке), указывающий, какие попытки доступа аудируются. Без SACL подкатегория бесполезна.

Эти практические навыки позволяют аналитику SOC L1 оперативно проверить охват аудита и корректно интерпретировать поступающие алерты.

## Сквозной практический пример: расследование несанкционированного доступа к файлу с аудитом

**Исходные условия**  
ОС Windows Server 2019, развёрнута в тестовой среде. Администратор настроил аудит согласно рекомендациям:  
- Подкатегория «File System» (Object Access) включена для успехов и отказов через `auditpol`.
- На конфиденциальной папке `C:\Finance\Reports` установлен SACL, аудирующий доступ группы «Everyone» на чтение/запись.
- SOC-аналитик получает из SIEM оповещение: обнаружена единичная попытка чтения файла `Salary_2024.xlsx` нестандартным процессом.

Задача: проверить факт несанкционированного доступа, идентифицировать пользователя и процесс, восстановить временную шкалу.

**Шаг 1: Верификация настроек аудита**
Прежде чем искать события в журнале, убедимся, что требуемая подкатегория активна и на папке применён SACL.

```cmd
auditpol /get /subcategory:"File System"
```
**Ожидаемый вывод**: `Success and Failure`.

Проверим SACL папки (права аудита) через PowerShell. Хотя это вспомогательная команда, она подтверждает корректность аудита.
```powershell
(Get-Acl -Path "C:\Finance\Reports").Audit | Format-Table IdentityReference, FileSystemRights, AuditFlags
```
**Ожидаемый вывод**: строка типа `Everyone   Read,Write   Success,Failure`.

**Шаг 2: Поиск релевантных событий в журнале безопасности**
Основной идентификатор доступа к объекту файловой системы — **Event ID 4663**. Нам нужно найти события, связанные с целевым файлом, за последние 12 часов (предполагаемое время инцидента). Используем PowerShell с XPath-фильтром. Поскольку полное имя файла хранится в EventData/Data[@Name="ObjectName"], построим фильтр:

```powershell
$filter = @"
<QueryList>
  <Query Id="0" Path="Security">
    <Select Path="Security">
      *[System[EventID=4663]] and
      *[EventData[Data[@Name="ObjectName"] and (Data='C:\Finance\Reports\Salary_2024.xlsx' or contains(Data,'Salary_2024.xlsx'))]]
    </Select>
  </Query>
</QueryList>
"@
Get-WinEvent -LogName Security -FilterXml $filter -MaxEvents 5 | 
    Select-Object TimeCreated, 
        @{n='User';e={$_.Properties[1].Value}}, 
        @{n='Process';e={$_.Properties[13].Value}},
        @{n='AccessMask';e={$_.Properties[8].Value}}
```
**Ожидаемый вывод (иллюстративный)**:
```
TimeCreated          User         Process           AccessMask
2024-06-15 18:23:01  CORP\jdoe   C:\tools\nc.exe   0x120089 (ReadAttributes, ReadData...)
```
Мы видим, что процесс `nc.exe` от пользователя `jdoe` получил доступ на чтение. Значение AccessMask показывает запрошенные права; интерпретировать их можно через справочник MSDN.

**Шаг 3: Детальный анализ события для верификации**
Чтобы получить полный набор данных, извлекаем событие с указанным временем и разбираем все свойства.

```powershell
$event = Get-WinEvent -LogName Security -FilterXPath "*[System[EventID=4663]]" -MaxEvents 1 |
         Where-Object { $_.TimeCreated -eq '2024-06-15T18:23:01' }
$event.Properties
```
**Ожидаемый вывод**: список из 16 свойств, включая SubjectUserSid, ProcessId, ObjectType (File), HandleId. Особое внимание на ProcessId и его соотнесение с событиями создания процесса.

**Шаг 4: Корреляция с созданием процесса и входом**
По ProcessId (допустим, 5328) находим событие создания процесса (4688):

```powershell
Get-WinEvent -LogName Security -FilterXPath "*[System[EventID=4688]]" |
    Where-Object { $_.Properties[4].Value -eq 5328 } |
    Select-Object TimeCreated, 
        @{n='CommandLine';e={$_.Properties[8].Value}},
        @{n='ParentProcess';e={$_.Properties[13].Value}}
```
**Ожидаемый вывод**: показывает, что `nc.exe` был запущен с командной строкой, содержащей IP-адрес, а родительским процессом был `cmd.exe`. Затем для проверки сессии находим событие входа (4624) того же пользователя `jdoe` с Logon ID, который ассоциирован с указанным процессом (связь через поле `SubjectLogonId` в 4663). Эта цепочка подтверждает, что учётная запись была скомпрометирована и использовалась для эксфильтрации файла.

Таким образом, сквозной пример демонстрирует, как комбинация правильно настроенных подкатегорий аудита (File System, Process Creation, Logon) позволяет аналитику SOC L1 восстановить полную картину инцидента, опираясь на конкретные Event ID, порождённые этими подкатегориями.
