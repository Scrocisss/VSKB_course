# Системы пересылки логов: протоколы, агенты и архитектура централизованного сбора

## Фундамент централизованного логирования: протоколы, демоны и ключевые различия

Централизованный сбор логов — базовая практика в SOC и инфраструктуре информационной безопасности, позволяющая агрегировать события с множества узлов в единое хранилище для корреляции, поиска и расследования. Техническим фундаментом этого процесса выступают системы пересылки логов — программные или аппаратные агенты, передающие сгенерированные записи от источника (ОС, приложение, сетевое устройство) на выделенный log-сервер. Ключевым протоколом взаимодействия остаётся **syslog**, определённый первоначально в RFC 3164 и обновлённый до стандарта RFC 5424 [Syslog Protocol: A Reference Guide - Graylog](https://graylog.org/post/syslog-protocol-a-reference-guide). Однако на практике под «syslog» часто ошибочно понимают конкретную реализацию демона, в то время как необходимо различать сам протокол, формат сообщения и программный агент.

**Протокол syslog** описывает способ передачи структурированных текстовых сообщений по UDP (порт 514) или TCP, включая поля приоритета (Facility и Severity), временную метку и имя хоста. Современная версия RFC 5424 добавляет поддержку структурированных данных в формате ключ-значение, временные метки с микросекундной точностью и кодировку UTF-8. Протокол не гарантирует доставку при использовании UDP и не предусматривает шифрования «из коробки» — эти аспекты закрываются транспортным уровнем (TLS, TCP) и расширениями конкретных реализаций.

**Демоны syslog** — это сервисы операционной системы или отдельных приложений, реализующие приём, фильтрацию, модификацию и пересылку сообщений. Самыми распространёнными в Linux-средах являются `rsyslog`, `syslog-ng` и классический `syslogd` (часто из пакета `sysklogd`). Каждый из них поддерживает базовый протокол, но кардинально различается по производительности, гибкости маршрутизации и возможностям интеграции.

**Система пересылки логов** в широком смысле включает:

- Клиентский агент (локальный демон), собирающий сообщения от ядра (через `/dev/kmsg`), системных служб (через сокет `/dev/log` или journald) и пользовательских приложений;
- Правила маршрутизации, определяющие, какие сообщения и куда отправлять (локальные файлы, удалённый сервер, база данных);
- Транспортный канал с выбранным протоколом и параметрами надёжности;
- Серверный агент, принимающий входящие потоки, выполняющий дополнительный парсинг и сохраняющий логи в хранилище.

Разграничение понятий важно для корректного проектирования конвейера логов в SOC. Смешение «syslog» как протокола и «rsyslog» как реализации приводит к ошибкам конфигурации, особенно при переходе на шифрованные транспорты или при интеграции с SIEM, ожидающим строго определённый формат сообщения (RFC 5424, JSON).

## Внутреннее устройство: формат сообщения, модель доставки и компоненты конвейера

Система пересылки логов объединяет несколько логических компонентов, образующих сквозной конвейер: генерация → локальный сбор → трансформация → передача по сети → приём → сохранение. Рассмотрим каждый уровень подробнее.

### Формат syslog-сообщения

Каждая запись, передаваемая по протоколу syslog, состоит из трёх основных частей:

1. **PRI (Priority)** — вычисляемое значение `Facility × 8 + Severity`. Facility определяет категорию источника (например, `0` — kernel, `3` — system daemons, `4` — security/authorization, `16–23` — local use). Severity задаёт критичность от `0` (Emergency) до `7` (Debug). PRI обычно отображается в угловых скобках: `<34>` для facility=4, severity=2.
2. **HEADER** — временна́я метка и имя хоста. В RFC 3164 метка имеет формат `Mmm dd hh:mm:ss`, без указания года и часового пояса. RFC 5424 использует стандарт ISO 8601 с микросекундами, например `2025-01-03T14:07:15.003Z`.
3. **MSG** — поле сообщения, содержащее тег процесса (имя программы и PID) и произвольный текст. В RFC 5424 дополнительно включаются структурированные данные в формате `[ID параметр="значение"]`, что делает сообщение машиночитаемым без парсинга свободного текста.

Пример целого сообщения RFC 5424 (иллюстративная схема полей):

```
<34>1 2025-03-17T09:42:15.000Z web-server-prod su 12345 ID47 - 'su root' failed for user admin on /dev/pts/0
```

Разбор: `<34>` → facility=4 (auth), severity=2 (Critical); `1` — версия RFC 5424; далее временна́я метка, хост `web-server-prod`, имя приложения `su`, PID `12345`, ID сообщения `ID47`, пустые структурированные данные (`-`), и само сообщение.

### Архитектура конвейера на базе rsyslog

Демон `rsyslog` реализует модульную модель, состоящую из трёх этапов: `input → processing → output`. Применительно к пересылке логов эта архитектура выглядит как распределённый пайплайн:

```text
[Приложения/ядро]──►[/dev/log, /dev/kmsg]──►[Input-модули: imuxsock, imjournal, imudp]──►[Ruleset: фильтры, шаблоны, модификация]──►[Action: omfile, omfwd, omelasticsearch]
                                       │
                                       └──►[Очередь (LinkedList/Disk)]──►[Output-модуль: omfwd]──►(сеть: TCP/TLS/UDP)──►[Удалённый rsyslog: imtcp/imudp]──►[Локальное хранилище]
```

Сердцевина конвейера — **ruleset**, где принимаются решения о маршрутизации. В `rsyslog` правила записываются в `RainerScript`. Базовая директива для отправки всех сообщений на удалённый сервер по TCP выглядит так (иллюстрация, реальный target должен быть заменён):
```bash
action(type="omfwd" Target="logcollector.example.com" Port="514" Protocol="tcp"
       queue.type="LinkedList" queue.filename="fwd_to_central")
```
Здесь `queue.type="LinkedList"` создаёт связанный список сообщений в памяти, с возможностью сброса на диск при переполнении. Это предотвращает блокировку локального логирования при недоступности центрального сервера, что является best practice для TCP-пересылки [Forwarding Logs - rsyslog 8 daily stable documentation](https://docs.rsyslog.com/doc/getting_started/forwarding_logs.html).

При использовании UDP очереди не требуются ввиду отсутствия подтверждений доставки, но это сопряжено с риском потери сообщений.

### Транспортные протоколы и гарантии доставки

Выбор транспорта критически влияет на надёжность всей системы. Основные варианты, поддерживаемые `rsyslog` и `syslog-ng`:

- **UDP (514)** — без установления соединения, минимальные накладные расходы, но нет гарантии доставки и порядка. Сообщение может быть потеряно при перегрузке сети или приёмника. Подходит для некритичных потоков высокой frequency, где допустима потеря отдельных записей.
- **TCP (514)** — гарантирует доставку и порядок, но при обрыве соединения отправляющий демон может блокироваться (head-of-line blocking), если не настроена очередь. Рекомендован для большинства production-сценариев.
- **TLS over TCP (6514)** — шифрует и аутентифицирует канал, предотвращая перехват и подмену логов. Обязателен при передаче чувствительных данных через недоверенные сети.
- **RELP (Reliable Event Logging Protocol, порт 20514)** — расширяет TCP механизмами квитирования на уровне приложения, что исключает потерю сообщений при разрыве сессии. Рекомендован для high-value событий аудита.

В индустрии SOC принято использовать TCP с TLS для всех межсегментных соединений, а внутри доверенного VLAN иногда допускается plain TCP для снижения нагрузки на CPU.

### Приёмная сторона и интеграция с SIEM

Центральный log-сервер, как правило, представляет собой инстанс `rsyslog` или специализированное ПО (Graylog, Splunk, ELK), настроенное на приём входящих потоков. Минимальная конфигурация `rsyslog`-сервера включает загрузку модулей `imudp` и/или `imtcp` и определение шаблона имени выходного файла:

```bash
module(load="imtcp")
input(type="imtcp" port="514")
template(name="RemoteLogs" type="string" string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log")
*.* ?RemoteLogs
```
Подобный подход с динамическим созданием каталогов по имени хоста позволяет сразу сегрегировать данные до передачи в SIEM. Для прямой отправки в Elasticsearch может использоваться модуль `omelasticsearch` [Efficient Log Management with rsyslog: From Concepts to Implementation](https://medium.com/@habibullah.127.0.0.1/efficient-log-management-with-rsyslog-from-concepts-to-implementation-5743fbf73675).

С точки зрения SOC L1, понимание формата и пути сообщения необходимо для диагностики проблем сбора. Если логи не поступают в SIEM, аналитик должен проверить: доступность порта на коллекторе, корректность facility/severity в правилах фильтрации, наличие очередей и ошибок в логах самого rsyslog (обычно `/var/log/syslog` или journalctl).

## Практическая работа с пересылкой: конфигурирование клиента и сервера rsyslog, типовые ошибки и отладка

### Базовая настройка клиента пересылки

На большинстве Linux-дистрибутивов `rsyslog` уже установлен. Для включения пересылки необходимо создать файл в директории `/etc/rsyslog.d/` (например, `50-forward.conf`) с правилами перенаправления. Рассмотрим несколько типовых сценариев.

**Отправка всех сообщений по UDP** (менее надёжный, но простой способ):
```bash
*.* @192.168.1.100:514
```
Синтаксис: один символ `@` означает UDP, два `@@` — TCP [Syslog Implementation: Servers, Integration and Best Practices](https://uptrace.dev/blog/syslog-guide).

**Отправка по TCP с очередью (рекомендуемый промышленный вариант)**:
```bash
action(
    type="omfwd"
    target="logserver.example.com"
    port="514"
    protocol="tcp"
    queue.type="LinkedList"
    queue.filename="q_central"
    queue.maxdiskspace="1g"
    queue.saveonshutdown="on"
    queue.highwatermark="8000"
    queue.lowwatermark="4000"
    action.resumeRetryCount="-1"
)
```
Параметры:
- `queue.filename` — имя файла дисковой очереди при переполнении памяти;
- `action.resumeRetryCount="-1"` — бесконечные попытки восстановления соединения;
- `highwatermark/lowwatermark` — пороги активации/деактивации режима буферизации.

**Точечная пересылка только событий безопасности (facility auth, authpriv)**:
```bash
auth,authpriv.* @@logserver.example.com:514
```
Или с использованием conditional RainerScript:
```bash
if $syslogfacility-text == ["auth", "authpriv"] then {
    action(type="omfwd" target="siem.internal" port="6514" protocol="tcp"
           streamdriver="gtls" streamdriver.mode="1"
           streamdriver.authmode="x509/name" streamdriver.permittedpeer="*.internal")
}
```
Этот пример также показывает включение TLS с проверкой сертификата — критически важное требование для передачи аутентификационных логов.

**Пересылка в формате JSON**:
Для упрощения парсинга в SIEM-системах можно задать шаблон, формирующий сообщение в JSON:
```bash
template(name="json_forward" type="list") {
    constant(value="{")
    property(name="timegenerated" outname="timestamp" format="jsonf")
    constant(value=",")
    property(name="hostname" outname="host" format="jsonf")
    constant(value=",")
    property(name="syslogseverity" outname="severity" format="jsonf")
    constant(value=",")
    property(name="msg" outname="message" format="jsonf")
    constant(value="}\n")
}
action(type="omfwd" target="central" port="515" protocol="tcp" template="json_forward")
```

### Настройка серверной стороны

Сервер должен принимать логи по заданным транспортам. Конфигурация `/etc/rsyslog.conf` или `/etc/rsyslog.d/00-server.conf`:

```bash
# Загрузка модулей
module(load="imudp")
module(load="imtcp")

# UDP
input(type="imudp" port="514")

# TCP
input(type="imtcp" port="514")

# TLS
module(load="imtcp" streamdriver.name="gtls" streamdriver.mode="1"
       streamdriver.authmode="x509/name")
input(type="imtcp" port="6514")

# Шаблон хранения в зависимости от хоста
template(name="PerHost" type="string"
         string="/data/logs/%HOSTNAME%/%$year%-%$month%-%$day%.log")
if $fromhost-ip != "127.0.0.1" then {
    action(type="omfile" dynafile="PerHost")
    stop
}
```
Директива `stop` предотвращает запись в локальные системные файлы, если сообщение пришло извне (чтобы избежать дублирования).

### Типичные подводные камни при пересылке

1. **UDP-потери при высокой нагрузке**: без контроля перегрузки кернел-буфер UDP быстро переполняется. Симптом — пропуски в логах на приёмнике. Решение: переход на TCP или RELP.
2. **Блокировка клиента при падении TCP-сервера**: без очереди процесс rsyslog приостанавливается до восстановления соединения, задерживая локальное логирование. Обязательное применение `queue.type="LinkedList"`.
3. **Расхождение форматов времени**: если клиент и сервер не синхронизированы по NTP, временные метки становятся бесполезными для корреляции. Рекомендуется на приёмной стороне добавлять собственную метку получения (`$timegenerated` vs `$receivedfrom`).
4. **Некорректный DNS-резолвинг**: при указании имени сервера важно, чтобы DNS работал на момент загрузки `rsyslog`. Лучше использовать IP-адреса или настраивать `action.resumeRetryCount="-1"`.
5. **Ошибки прав доступа**: выходная директория сервера должна быть доступна для записи пользователю `syslog` (или тому, от которого запущен демон). Нередко логи теряются из-за `permission denied`.

### Отладка и мониторинг

Для диагностики проблем пересылки SOC-аналитик может использовать:

- Просмотр логов самого `rsyslog`: `journalctl -u rsyslog --since "10 minutes ago"` или `cat /var/log/syslog | grep rsyslog`.
- Включение отладочного вывода на клиенте путём запуска `rsyslogd -dn` (в foreground), что покажет весь поток обрабатываемых сообщений и ошибки сетевого взаимодействия.
- Проверку сетевой связности: `netcat -z -v -u logserver 514` для UDP, `telnet logserver 514` для TCP.
- Утилиту `logger` для инъекции тестовых сообщений: `logger -p local0.info "Test from host01"`.
- На серверной стороне – мониторинг количества входящих сообщений: `watch -n 1 "ls -lh /data/logs/"` или использование `rsyslog impstats` для сбора метрик.

## Сквозной практический пример: настройка отказоустойчивой пересылки логов SSH на центральный сервер

**Исходные условия**: Учебный стенд: две виртуальных машины Ubuntu 22.04. Клиент (`client01`) собирает логи аутентификации SSH, сервер (`logserver`) выполняет роль централизованного коллектора. Задача: настроить пересылку всех сообщений категории `authpriv.*` по TCP с TLS на порт 6514, с буферизацией на случай недоступности сервера. Сертификаты (самоподписанные) заранее сгенерированы и распространены.

### Шаг 1. Проверка исходного состояния клиента

Убеждаемся, что `rsyslog` запущен и логи аутентификации пишутся локально в `/var/log/auth.log`:
```bash
systemctl status rsyslog
tail -5 /var/log/auth.log
```
Пример вывода `tail`:
```log
Mar 17 10:00:01 client01 CRON[1123]: pam_unix(cron:session): session opened for user root
Mar 17 10:05:00 client01 sshd[1234]: Failed password for admin from 192.168.1.101 port 22
Mar 17 10:05:03 client01 sshd[1234]: Connection closed by authenticating user admin 192.168.1.101 port 22 [preauth]
```
Логи фиксируются локально, пересылка пока не активна.

### Шаг 2. Конфигурация клиента

Создаём файл `/etc/rsyslog.d/30-ssh-forward.conf` со следующим содержимым (использованы упрощённые TLS-настройки для учебного примера, без проверки имени peer):
```bash
# Загружаем модуль TLS
module(load="omfwd")
module(load="builtin:omfwd" stremdriver="gtls" streamdriver.mode="1"
       streamdriver.authmode="x509/name"
       streamdriver.permittedpeer="logserver.example.com")

# Шаблон для передачи
template(name="AuthFormat" type="string" string="%TIMESTAMP% %HOSTNAME% %syslogtag% %msg%\n")

# Правило пересылки authpriv с очередью
if $syslogfacility-text == "authpriv" then {
    action(
        type="omfwd"
        target="logserver.example.com"
        port="6514"
        protocol="tcp"
        streamdriver="gtls"
        streamdriver.mode="1"
        streamdriver.authmode="x509/name"
        streamdriver.permittedpeer="logserver.example.com"
        template="AuthFormat"
        queue.type="LinkedList"
        queue.filename="authq"
        queue.maxdiskspace="500m"
        queue.saveonshutdown="on"
        action.resumeRetryCount="-1"
    )
    stop
}
```
После сохранения файла применяем конфигурацию:
```bash
sudo systemctl restart rsyslog
```

### Шаг 3. Конфигурация сервера

На `logserver` настраиваем приёмник. В файле `/etc/rsyslog.d/10-tls-server.conf`:
```bash
module(load="imtcp" streamdriver.name="gtls" streamdriver.mode="1"
       streamdriver.authmode="x509/name"
       streamdriver.permittedpeer="client01.example.com")

input(
    type="imtcp"
    port="6514"
)

template(name="AuthDest" type="string"
         string="/var/log/remote/auth/%HOSTNAME%/%$year%-%$month%-%$day%.log")

if $syslogfacility-text == "authpriv" then {
    action(type="omfile" dynaFile="AuthDest")
    stop
}
```
Перезапуск:
```bash
sudo systemctl restart rsyslog
```

### Шаг 4. Генерация тестового события

На клиенте имитируем неудачную аутентификацию:
```bash
ssh admin@localhost
# Вводим намеренно неверный пароль
```
Также можно воспользоваться `logger`:
```bash
logger -p authpriv.crit "manual test message for forwarding verification"
```

Проверяем, что локально событие записалось:
```bash
tail -1 /var/log/auth.log
```
Вывод:
```log
Mar 17 11:20:15 client01 sshd[1345]: Failed password for admin from 127.0.0.1 port 22
```

### Шаг 5. Проверка доставки на сервере

На `logserver` проверяем, что файл для хоста `client01` создан и содержит сообщение:
```bash
ls /var/log/remote/auth/client01/
cat /var/log/remote/auth/client01/2025-03-17.log
```
Ожидаемый вывод:
```log
Mar 17 11:20:15 client01 sshd[1345]: Failed password for admin from 127.0.0.1 port 22
Mar 17 11:21:00 client01 admin: manual test message for forwarding verification
```
Наличие обеих записей подтверждает, что пересылка authpriv-сообщений по защищённому каналу выполняется успешно, а очередь гарантирует сохранность данных при временных обрывах связи.

### Ожидаемый вывод

Пример демонстрирует полный цикл настройки защищённой пересылки логов с буферизацией. Для SOC-аналитика первого уровня такой стенд служит наглядной моделью того, как события аутентификации попадают из ОС в центральное хранилище, и даёт опорные точки для диагностики при расследовании инцидентов — проверка локального лога, конфигурации rsyslog, связности до коллектора и целостности данных на приёмной стороне.
