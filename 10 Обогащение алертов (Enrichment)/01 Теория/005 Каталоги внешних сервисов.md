# Каталоги внешних сервисов для обогащения алертов в SOC

## Роль внешних сервисов в процессе обогащения алертов

Обогащение алертов (alert enrichment) — это автоматизированное или ручное дополнение сырого события безопасности контекстной информацией, позволяющей аналитику точнее оценить его критичность и вектор атаки. В SOC внешние сервисы выступают основным источником таких данных, предоставляя сведения об IP-адресах, доменах, URL‑адресах и хэшах файлов, которых нет во внутренних логах организации. Без них аналитик уровня L1 вынужден принимать решение об эскалации практически вслепую, опираясь лишь на сигнатуру SIEM.

Значительная часть индикаторов компрометации (IoC) уже была замечена глобальным сообществом: вредоносный IP мог участвовать в ботнет-кампании, домен — быть зарегистрированным за сутки до атаки, а хэш файла — детектироваться десятками антивирусов как троян. Внешние каталоги агрегируют такие сведения от множества сенсоров, песочниц, поставщиков Threat Intelligence и делают их доступными через единый интерфейс. Для L1 это повторяемый, быстрый и документированный способ добавить к алерту репутационную оценку, географическую привязку, информацию о владельце и историю активности, после чего можно уверенно эскалировать инцидент или закрыть его как ложное срабатывание.

В отличие от внутренних источников (CMDB, Active Directory, EDR-логи), каталоги внешних сервисов целиком размещены за пределами периметра организации. Их использование сопряжено с рядом особенностей:

* **Доступность.** Внешние API могут быть недоступны из-за сетевых ограничений, поэтому в SOC часто развёртывают кэширующий прокси или используют автономные загрузки списков индикаторов.
* **Доверие.** Оценки разных сервисов могут противоречить друг другу; аналитик должен уметь взвешивать источники.
* **Платный или бесплатный доступ.** Многие сервисы имеют бесплатные тарифы с ограничением по числу запросов в день или минуту.
* **Задержка.** Информация о новом индикаторе появляется не мгновенно: время распространения Threat Intelligence от сенсоров до API может составлять от нескольких минут до суток.

Ключевые термины, необходимые для работы с внешними каталогами:
* **Индикатор компрометации (IoC)** — артефакт, наблюдаемый в сети или на хосте и с высокой вероятностью связанный с вредоносной активностью.
* **Репутация** — численная или категориальная оценка вредоносности индикатора, вычисленная сервисом на основе его глобальной истории.
* **Контекст** — любые дополнительные данные: порты, сертификаты, связанные домены, сектор экономики владельца IP, время первой активности.
* **API-ключ** — секретный токен, идентифицирующий потребителя API и ограничивающий квоты.

В таблице ниже систематизированы основные типы внешних сервисов, применяемых в SOC для обогащения, с их целевым назначением и типичными примерами (конкретные реализации названы исключительно как иллюстрация распространённых инструментов).

| Тип сервиса | Назначение | Примеры сервисов (иллюстративно) | Типичный артефакт обогащения |
|-------------|------------|----------------------------------|-------------------------------|
| Репутационные IP-базы | Оценка вредоносности IP-адреса, количество жалоб, история атак | AbuseIPDB, AlienVault OTX, IBM X-Force Exchange | Доверительный рейтинг (confidence score), категория угрозы (например, C2, сканирование) |
| Индексаторы интернет-хостов | Информация о сервисах, открытых портах, баннерах и уязвимостях хоста | Shodan, Censys | Список портов с сервисами, версии ПО, CVE, географическое положение |
| Anti-вирусные агрегаторы | Сводка детектов файла (хэш, URL) многими антивирусами и поведенческих отчетов | VirusTotal, MetaDefender, Hybrid Analysis | Количество позитивных детектов, название вредоносного семейства, песочный отчет |
| Базы вредоносных URL и фишинга | Проверка URL-адресов на наличие в чёрных списках, фишинговых базах | URLhaus, PhishTank, Google Safe Browsing | Статус URL (online/offline), дата добавления, связанные вредоносные файлы |
| WHOIS- и DNS-историки | Данные о регистрации домена, возраст, владельце, исторические NS-записи | WhoisXML API, DomainTools, SecurityTrails | Дата создания, регистратор, смена владельца за последние дни |
| Геолокационные сервисы | Сопоставление IP с географическими координатами, страной, провайдером | MaxMind GeoIP, ipinfo.io | Страна, город, провайдер, координаты |
| Пассивный DNS | Исторические соответствия домен–IP и наоборот, выявление DGA-доменов | VirusTotal PDNS, Farsight DNSDB, RiskIQ | Список IP-адресов, с которыми разрешался домен, временные метки |
| Платформы Threat Intelligence | Консолидированные данные из множества источников с аналитикой и графами связей | Anomali, ThreatConnect, MISP-сообщества | Связки индикаторов, таксономия угроз, MITRE ATT&CK |

Зная функциональные группы, аналитик L1 быстро определяет, к какому сервису обращаться за недостающей информацией. Например, для подозрительного исходящего TCP-соединения к неизвестному IP в первую очередь проверяют репутационный сервис и Shodan, тогда как для фишингового URL — VirusTotal и URLhaus.

## Архитектура и разновидности каталогов внешних данных

Внешние сервисы Threat Intelligence устроены по общей модульной схеме, несмотря на различия в специализации. Их можно рассматривать как распределённую систему, где сбор данных отделён от аналитики и предоставления результатов. Понимание этой архитектуры помогает аналитику интерпретировать ответы API и оценивать актуальность сведений.

Типичный сервис состоит из четырёх логических блоков:

1. **Сенсорная сеть и коллекторы.** Исходные данные получаются от распределённых агентов, honeypots, спам-ловушек, пользовательских отправок (submissions), сетевых телескопов, а также из открытых источников (OSINT) и коммерческих партнёрств.
2. **Хранилище и индексация.** Собранные IoC и метаданные сохраняются в высокопроизводительной базе данных (часто колоночной или документной — Elasticsearch, Bigtable), оптимизированной для поиска по индикаторам и связям.
3. **Аналитический движок.** Здесь выполняется корреляция, кластеризация, машинное обучение для автоматического выставления репутационной оценки, выявления кампаний и связывания индикаторов в группы.
4. **API-интерфейс и кэширование.** RESTful HTTP API принимает запросы от клиентов, авторизует их, проверяет лимиты и возвращает структурированный ответ (JSON, реже STIX, CSV). Для снижения нагрузки популярные запросы кэшируются.

```text
[Сенсоры (honeypots, user submissions, OSINT)] ──► [Коллектор]
                                                         │
                                                         ▼
                                              [Хранилище необработанных данных]
                                                         │
                                                         ▼
                                              [Аналитический движок (корреляция, ML)]
                                                         │
                                                         ▼
                                              [База индикаторов с оценками]
                                                         │
                                                         ▼
                                              [API-шлюз (REST, rate limiter)] ──► [SOC-аналитик / SIEM]
```

Вариации этой архитектуры зависят от класса сервиса:

* **Репутационные базы** (AbuseIPDB, OTX) ориентированы на быстрый поиск по IP/домену и возвращают оценку по простой шкале; их внутренняя логика может быть реализована как агрегация сообществом, где ключевой фактор — количество и свежесть жалоб.
* **Индексаторы интернет-хостов** (Shodan) регулярно сканируют всё адресное пространство IPv4 и выборочные порты IPv6, собирая баннеры сервисов, а затем предоставляют полнотекстовый поиск. Запрос к Shodan через API вернёт детальную карточку хоста.
* **Антивирусные агрегаторы** (VirusTotal) для каждого файла или URL выполняют множество параллельных проверок десятками антивирусных движков, сохраняя сырые и агрегированные результаты. API VirusTotal v3 отдаёт сложный объект с атрибутами `last_analysis_results` и `last_analysis_stats`.
* **Пассивный DNS** (Farsight DNSDB) хранит исторические записи разрешения доменов с временными метками, что позволяет отследить смену IP даже после вывода домена из эксплуатации. Ответ API — временной ряд записей.

В таблице ниже обобщены ключевые отличия в API-моделях нескольких популярных сервисов, что важно учитывать при интеграции.

| Сервис (иллюстративно) | URL API-эндпоинта (типовая схема) | Аутентификация | Формат ответа | Типичные ограничения бесплатного плана |
|------------------------|-----------------------------------|----------------|---------------|----------------------------------------|
| AbuseIPDB v2 | `https://api.abuseipdb.com/api/v2/check` | API-ключ в заголовке `Key` | JSON (flat) | 1000 запросов/день |
| VirusTotal v3 | `https://www.virustotal.com/api/v3/ip_addresses/{ip}` | API-ключ в заголовке `x-apikey` | JSON (вложенный) | 4 запроса/мин, 500 запросов/день |
| Shodan REST API | `https://api.shodan.io/shodan/host/{ip}` | API-ключ в параметре `key` | JSON | Без платного ключа доступны только ограниченные методы |
| OTX AlienVault | `https://otx.alienvault.com/api/v1/indicators/IPv4/{ip}/general` | Не требует ключа (публичный) | JSON | Без ограничений на чтение |
| URLhaus | `https://urlhaus-api.abuse.ch/v1/host/` | Не требует ключа (публичный) | JSON | Без ограничений |

Для аналитика L1 нет нужды углубляться во внутреннюю механику каждого сервиса, однако знание этих особенностей ускоряет выбор инструмента и написание скриптов автоматизации.

## Интеграция внешних сервисов в работу аналитика L1

Непосредственная работа аналитика с каталогами внешних сервисов сводится к трём сценариям:

* **Ручной разовый запрос через браузер.** Наиболее оперативный метод для единичного алерта. Аналитик открывает веб-интерфейс VirusTotal или AbuseIPDB, вставляет индикатор и анализирует сводную информацию. Недостатки — медленный при массовом поступлении алертов и отсутствие документирования шагов.
* **Автоматизация через SOAR или SIEM.** Настроенные playbook (например, в Cortex XSOAR, Splunk SOAR) при появлении алерта автоматически выполняют HTTP-запросы к выбранным сервисам и помещают ответ в поля инцидента. L1 получает уже обогащённый алерт и может сосредоточиться на вердикте.
* **Полуавтоматические скрипты обогащения.** Аналитик запускает заранее подготовленный скрипт (на curl, PowerShell, Python) с индикатором в качестве параметра и читает структурированный вывод. Именно этот сценарий чаще всего отрабатывается на начальных этапах обучения, так как он не требует готовых интеграций и позволяет освоить API сервисов.

Ниже приведён практический пример использования утилиты curl для обогащения IP-адреса через AbuseIPDB. Предполагается, что аналитик уже зарегистрировался и получил API-ключ. Команда отправляет GET-запрос к v2 эндпоинту, аутентификация выполняется через заголовок `Key`. Вывод отформатирован для иллюстрации — реальные значения полей зависят от проверяемого адреса.

```bash
curl -sS "https://api.abuseipdb.com/api/v2/check" \
  --data-urlencode "ipAddress=198.51.100.10" \
  -H "Key: <ваш_api_ключ>" | jq '.'
```

*Схематичный фрагмент ответа (реальные данные отличаются):*

```json
{
  "data": {
    "ipAddress": "198.51.100.10",
    "isPublic": true,
    "ipVersion": 4,
    "abuseConfidenceScore": 95,
    "countryCode": "US",
    "usageType": "Data Center/Web Hosting/Transit",
    "isp": "Example ISP",
    "domain": "example.com",
    "hostnames": ["host.example.com"],
    "totalReports": 1200,
    "lastReportedAt": "2025-03-14T08:15:22+00:00"
  }
}
```

Ключевое поле здесь — `abuseConfidenceScore`, принимающее значения от 0 до 100. Чем выше число, тем вероятнее зловредная активность. Дополнительно аналитик смотрит на `totalReports` (как давно и часто адрес попадал в чёрные списки) и `usageType` (серверный хостинг неизвестен организации — косвенный признак подозрительности). Эти данные сразу дают взвешенное основание эскалировать инцидент на L2 при высоком score.

Для проверки хэша файла эффективен VirusTotal API v3:

```bash
curl -sS "https://www.virustotal.com/api/v3/files/<SHA256>" \
  -H "x-apikey: <ваш_api_ключ>" | jq '.data.attributes.last_analysis_stats'
```

*Схематичный вывод:*

```json
{
  "malicious": 42,
  "suspicious": 3,
  "undetected": 28,
  "harmless": 5,
  "timeout": 2
}
```

Аналитик видит, что 42 из 80 движков определили файл как вредоносный. Этот показатель вместе с названиями детектов (можно извлечь из `last_analysis_results`) позволяет быстро классифицировать объект. При отсутствии функциональности прямого вызова curl из интерфейса SIEM подобные проверки могут быть оформлены в виде однострочников, сохраняемых в заметках к алерту.

Типичные ошибки на этапе ручного обогащения:
* **Игнорирование временного контекста.** IoC мог быть замечен в атаках три года назад, но сейчас IP принадлежит легитимному облачному провайдеру. Важно проверять дату последней жалобы.
* **Слепое доверие одному источнику.** Публичный сервис может содержать ложные срабатывания (например, из-за включения диапазона адресов VPN в чёрный список). Поэтому желательна кросс-проверка двух-трёх сервисов разного типа.
* **Превышение лимитов во время инцидента.** Если аналитик массово обогащает сотни индикаторов, бесплатный ключ быстро уходит в бан. В учебной среде стоит изучить ограничения и возможности автоматической задержки между запросами.
* **Использование неподходящего сервиса.** Репутационный сервис не заменит Shodan для понимания, что за служба работает на порту, а VirusTotal не покажет текущие открытые порты.

Грамотное применение каталогов внешних сервисов в рутинной работе SOC L1 — не просто механическая проверка, а аналитическая привычка: перед принятием решения просмотреть несколько разнородных источников и сопоставить их выводы, документируя свои шаги.

## Сквозной практический пример: обогащение индикаторов из сетевого алерта

### Исходные условия
Аналитик L1 получает из SIEM (например, Splunk) алерт: с внутреннего хоста `192.168.1.25` зафиксировано несколько исходящих TCP-сессий на IP-адрес `198.51.100.10` по нестандартному порту `8443`. В том же временном окне на хост был загружен файл `suspicious.exe` (SHA-256: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` — в реальности хэш пустого файла, здесь используется как нейтральная заглушка для демонстрации процесса). В распоряжении аналитика рабочая станция с установленными curl и jq, API-ключи от AbuseIPDB (бесплатный) и VirusTotal (бесплатный), а также доступ к веб-интерфейсу Shodan без ключа. Задача — за 5 минут обогатить оба индикатора и принять решение об эскалации.

### Шаг 1. Проверка репутации IP-адреса через AbuseIPDB

Запрос аналогичен показанному ранее. Адрес `198.51.100.10` (диапазон TEST-NET-2, используется для демонстрации) будет заменён на реальный при повторении.

```bash
curl -s "https://api.abuseipdb.com/api/v2/check" \
  --data-urlencode "ipAddress=198.51.100.10" \
  -H "Key: YOUR_API_KEY" | jq '.data | {abuseConfidenceScore, totalReports, lastReportedAt, usageType}'
```

*Иллюстративный вывод:*

```json
{
  "abuseConfidenceScore": 95,
  "totalReports": 1200,
  "lastReportedAt": "2025-03-14T08:15:22+00:00",
  "usageType": "Data Center/Web Hosting/Transit"
}
```

### Шаг 2. Исследование открытых портов и сервисов через Shodan (веб-запрос или API)

Для получения детальной картины аналитик проверяет этот же IP в Shodan. Через curl (при наличии платного ключа) это выглядело бы так:

```bash
curl -s "https://api.shodan.io/shodan/host/198.51.100.10?key=YOUR_SHODAN_KEY" | jq '.ports, .data[] | {port, transport, product, version}'
```

В условиях бесплатного доступа аналитик открывает `https://www.shodan.io/host/198.51.100.10` в браузере и видит карточку хоста (иллюстративно):

```text
Port 8443/tcp
Service: HTTPS
Product: Apache Tomcat/Coyote JSP engine 1.1
Version: 1.2.3
```

Наличие открытого порта с известной серверной технологией на облачном IP нехарактерно для простого пользовательского соединения, что усиливает подозрение.

### Шаг 3. Проверка хэша файла через VirusTotal API v3

```bash
curl -s "https://www.virustotal.com/api/v3/files/e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" \
  -H "x-apikey: YOUR_VT_KEY" | jq '.data.attributes | {last_analysis_stats, popular_threat_classification}'
```

*Иллюстративный вывод:*

```json
{
  "last_analysis_stats": {
    "malicious": 55,
    "suspicious": 2,
    "undetected": 15,
    "harmless": 0
  },
  "popular_threat_classification": {
    "suggested_threat_label": "trojan.raccoonstealer"
  }
}
```

### Шаг 4. Интерпретация и принятие решения

Совокупность трёх обогащённых источников:
* AbuseIPDB оценивает IP как высоко-вредоносный с недавней активностью.
* Shodan показывает, что на нестандартном порту работает веб-сервер на хостинговом IP — вероятный командный центр.
* VirusTotal детектирует хэш как троян семейства RaccoonStealer.

На основании этих данных аналитик делает вывод, что внутренний хост вероятно заражён стилером, связывающимся с C2-сервером. Инцидент эскалируется на L2 для реагирования. Все шаги документируются: в карточке инцидента добавляются скриншоты или копипасты JSON-ответов и краткий вердикт.

Этот пример демонстрирует стандартную цепочку применения каталогов внешних сервисов: точечные API-запросы по каждому типу индикатора, извлечение значимых полей, кросс-валидация и формирование обоснованного решения.
