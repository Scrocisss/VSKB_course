# WHOIS и Passive DNS: история домена и резолвинга

## 1. Контекст: WHOIS и Passive DNS в задачах обогащения алертов SOC L1

Обогащение алертов (enrichment) — ключевая операция первой линии мониторинга (SOC L1), позволяющая превратить сырой индикатор (домен, IP-адрес, URL) в контекст, достаточный для принятия решения об эскалации. Два фундаментальных источника контекстной информации о доменной инфраструктуре — **WHOIS** и **Passive DNS (pDNS)**. Оба предоставляют исторические данные, но принципиально разного происхождения, охвата и применимости.

WHOIS — это протокол и система баз данных, хранящих регистрационные сведения о доменных именах, IP-адресах и автономных системах. Он отвечает на вопрос «кто владеет ресурсом и когда он был зарегистрирован». Passive DNS, в свою очередь, фиксирует фактические разрешения доменных имён в IP-адреса, реконструируя историю резолвинга — «на какой IP-адрес указывал домен в прошлом и какие ещё домены указывали на тот же IP».

В SOC L1 аналитик сталкивается с необходимостью быстро ответить на следующие типовые вопросы:

*   Является ли домен, фигурирующий в алерте, легитимным или вновь созданным (potentially malicious)?
*   Связан ли он с известной вредоносной инфраструктурой (общие регистранты, NS-серверы, IP-подсети)?
*   Менялась ли инфраструктура домена непосредственно перед или во время атаки?
*   Какие ещё артефакты можно извлечь для корреляции и поиска дополнительных индикаторов компрометации (IoC)?

WHOIS и Passive DNS дополняют друг друга, закрывая разные стадии анализа. WHOIS-данные сообщают о регистранте, дате создания, регистраторе, что критически важно для выявления «однодневок». Passive DNS фиксирует динамику IP-адресов, почтовых серверов и name-серверов, выявляя инфраструктурные связи, недоступные через WHOIS из-за широкого распространения сервисов защиты приватности (WHOIS privacy).

**Разграничение понятий: WHOIS, Passive DNS и другие смежные термины**

| Термин | Сущность | Период охвата | Ключевой источник |
|---|---|---|---|
| **WHOIS** | Регистрационные данные домена / IP | Текущее состояние + исторический WHOIS (срезы БД регистраторов на определённые даты) | Реестры (Verisign, Afilias), регистраторы (GoDaddy, Namecheap), RIR (ARIN, RIPE) |
| **Passive DNS (pDNS)** | Лог фактических DNS-ответов, собранных на рекурсивных резолверах | Непрерывный поток или периодические снимки с датировкой каждой записи | Сенсоры на рекурсивных DNS-серверах, магистральный пассивный сбор |
| **Active DNS** | Прямой запрос к текущему состоянию зоны через резолвер (dig, nslookup) | Только настоящее время, без истории | Любой доступный DNS-сервер (8.8.8.8, авторитативные NS) |
| **Reverse WHOIS** | Поиск доменов по атрибутам регистранта (email, организация, телефон) | На основе исторических срезов WHOIS | Специализированные сервисы (DomainTools, WhoisFreaks) |
| **RDAP (RFC 7482)** | Современная замена протокола WHOIS для gTLD; возвращает структурированный JSON по HTTPS | Аналогично WHOIS, но машиночитаемый формат | ICANN-аккредитованные RDAP-серверы регистров |

Исторические данные WHOIS (historical WHOIS) часто представлены в виде снапшотов, сохраняемых сторонними агрегаторами, тогда как Passive DNS является нативной хронологической записью. Для SOC L1 важно понимание, что WHOIS даёт ответ «кто и когда», а pDNS — «как и с кем». Корреляция этих двух слоёв позволяет, например, заметить, что домен с только что изменённым регистрантом (WHOIS) внезапно начал резолвиться на IP-адрес, ранее ассоциированный с фишинговым кит-хостингом (pDNS).

Описанный ниже подход к обогащению соответствует рекомендациям по применению Passive DNS и WHOIS в рамках техник MITRE ATT&CK, в частности, для обнаружения приобретённой или скомпрометированной инфраструктуры (T1583, T1584) [MITRE ATT&CK, Data Component DC0096](https://attack.mitre.org/datacomponents/DC0096). Аналитик L1, вооружённый этими источниками, сокращает время триажа с десятков минут до секунд и получает объективную основу для решения о ложноположительном срабатывании или эскалации на L2.

## 2. WHOIS: структура данных и методы доступа

Протокол WHOIS (RFC 3912) обеспечивает текстовый запрос-ответ через порт 43, однако индустрия активно переходит на Registration Data Access Protocol (RDAP, RFC 7482), предоставляющий ответы в формате JSON через HTTPS. Для SOC-аналитика знание структуры WHOIS-записи важно независимо от протокола: поля несут предсказуемую следственную нагрузку.

Ядро WHOIS-записи домена включает следующие поля (на примере типичного ответа регистратора для gTLD):

| Поле WHOIS | Пример иллюстративного значения | Значение для расследования SOC |
|---|---|---|
| **Domain Name** | EXAMPLE.COM | Объект расследования |
| **Registrar** | Example Registrar, Inc. | Некоторые регистраторы (например, «Alpnames Limited», «Todaynic») исторически ассоциированы со спамом и вредоносной активностью; статистические перекосы позволяют повысить приоритет алерта |
| **Creation Date** | 2025-07-10T12:00:00Z | Домены моложе 30 дней на момент инцидента — высокий риск; при обогащении фишинговых алертов дата создания часто совпадает с датой атаки |
| **Updated Date** | 2025-07-15T09:30:00Z | Резкое изменение записи (смена NS, регистранта) незадолго до алерта может указывать на перехват домена или целенаправленную настройку инфраструктуры |
| **Expiration Date** | 2026-07-10T12:00:00Z | Короткий цикл регистрации (1 год) характерен для «одноразовой» инфраструктуры |
| **Registrant Name / Organization** | REDACTED FOR PRIVACY (GDPR) | До 2018 года это поле было основным для атрибуции; теперь часто скрыто, но при наличии (например, в ccTLD без GDPR) позволяет делать Reverse WHOIS |
| **Registrant Email** | ple.com@whoisproxy.org | Даже скрытый email прокси-сервисом является уникальным идентификатором, по которому возможен поиск связанных доменов |
| **Name Servers** | ns1.examplens.com | Общие NS-серверы — мощный связующий признак инфраструктуры; если 10 фишинговых доменов используют ns1.badns.ru, это кластеризует угрозу |
| **Status Codes** | clientTransferProhibited | Коды EPP (Extensible Provisioning Protocol) характеризуют состояние домена: ok (активен), redemptionPeriod (удалён, но восстанавливаем), pendingDelete и пр. Домен в статусе pendingDelete может указывать на то, что он освободился и перехвачен злоумышленником |

Исторический WHOIS (Historical WHOIS) фиксирует все записи на даты изменений. Сервисы вроде DomainTools Iris [DomainTools Iris Investigate User Guide](https://docs.domaintools.com/iris/investigate/userguide) и WhoisFreaks предоставляют доступ к архивам WHOIS за многие годы, позволяя отследить не только цепочку владельцев, но и выявить периоды, когда домен мог быть не продлён и доступен для перехвата.

Для получения данных в реальном времени через командную строку или API SOC-аналитик использует утилиты `whois` (Linux/BSD) или RDAP-клиенты. В качестве иллюстрации структуры RDAP-ответа можно рассматривать следующий сокращённый JSON (поля и структура соответствуют стандарту [RFC 7483](https://datatracker.ietf.org/doc/html/rfc7483)):

```json
{
  "objectClassName": "domain",
  "handle": "2336792_DOMAIN_COM-VRSN",
  "ldhName": "example.com",
  "events": [
    {
      "eventAction": "registration",
      "eventDate": "2025-01-15T00:00:00Z"
    },
    {
      "eventAction": "expiration",
      "eventDate": "2026-01-15T00:00:00Z"
    }
  ],
  "entities": [
    {
      "roles": ["registrar"],
      "vcardArray": ["vcard", [ ... ]]
    }
  ],
  "nameservers": [
    {
      "objectClassName": "nameserver",
      "ldhName": "ns1.example.com"
    }
  ]
}
```

Этот структурированный формат облегчает программный разбор дат, регистратора и списка name-серверов без рискованных регулярных выражений, характерных для текстового WHOIS.

Reverse WHOIS, как отдельная техника, позволяет по частичному совпадению в поле регистранта (email, имя организации) найти все домены, когда-либо регистрировавшиеся с этим атрибутом. В SOC L1 этот метод обычно не применяется вручную из-за ресурсоёмкости, но результаты Reverse WHOIS, полученные через API TI-платформы, могут автоматически обогащать алерт списком связанных доменов, расширяя поверхность инцидента.

## 3. Passive DNS: история резолвинга и внутреннее устройство

Passive DNS (пассивный DNS, pDNS) — это технология долговременного сохранения ответов DNS-серверов, позволяющая реконструировать, какой IP-адрес сопоставлялся домену в любой момент прошлого. В отличие от активного опроса текущего состояния зоны, pDNS не инициирует запросов, а записывает ответы, проходящие через рекурсивные резолверы, оснащённые сенсорами.

Принцип сбора данных: когда клиент делает запрос, например, A-запись для `login.example.com`, рекурсивный резолвер может иметь актуальную запись в кэше (cache hit) или обратиться к авторитативному серверу (cache miss). Сенсор pDNS активируется при cache miss и сохраняет пакет ответа, содержащий само доменное имя, тип записи, значение (IP, имя хоста), TTL и точную временную метку [Spamhaus, What is Passive DNS?](https://www.spamhaus.com/resource-center/what-is-passive-dns-a-beginners-guide). Так накапливается массив исторических наблюдений, в отраслевых базах насчитывающий миллиарды записей (например, Farsight DNSDB, WhoisFreaks с индексом >16 млрд записей [WhoisFreaks DNS History tool](https://whoisfreaks.com/tools/dns/history/lookup)).

Основные типы DNS-записей, фиксируемые pDNS, и их интерпретация в SOC:

| Тип записи | Фиксируемое значение | Аналитическая ценность |
|---|---|---|
| **A** | IPv4-адрес, на который ресолвился домен | Позволяет отследить смену хостинга, миграцию на bulletproof-хостинг, выявить периоды, когда домен указывал на известный вредоносный IP |
| **AAAA** | IPv6-адрес | Аналогично A, используется реже, но может указывать на специфическую инфраструктуру (например, C2 поддерживает только IPv6) |
| **CNAME** | Каноническое имя, на которое ссылается домен | Выявляет использование CDN (Cloudflare, Akamai) и сокрытие реального IP, также позволяет находить связанные поддомены |
| **MX** | Почтовый сервер | Исторический MX может показать, использовался ли домен для спам-рассылок; изменение MX на легитимный сервис после компрометации — признак восстановления |
| **NS** | Авторитативные DNS-серверы домена | Смена NS — сильный сигнал; если домен сменил NS с легитимного регистратора на бесплатный хостинг, это часто предшествует фишингу |
| **TXT** | Произвольный текст (SPF, DKIM, верификация) | TXT-запись SPF показывает разрешённые отправляющие серверы; злоумышленники часто настраивают «+all» или убирают SPF |
| **SOA** | Start of Authority — административная информация | Содержит contact email администратора зоны; историческая SOA может показать, кто администрировал домен до передачи |
| **PTR** | Обратная запись (IP → имя) | Позволяет получить имя хоста по IP, используется для проверки соответствия прямого и обратного резолвинга и обнаружения хостинга |

Пассивный DNS позволяет решать обратную задачу: по заданному IP-адресу найти все домены, когда-либо на него указывавшие (даже если в данный момент они не резолвятся). Эта операция называется **Reverse Passive DNS** или поиск по «rdata» (resource record data) [Farsight DNSDB API: Rdata Lookups](https://docs.domaintools.com/iris/investigate/userguide). Именно она даёт SOC-аналитику возможность связать атакуемый IP с десятками доменов, образующих инфраструктуру злоумышленника, и пополнить IoC-список.

Внутреннее устройство системы pDNS можно представить схемой:

```text
[Клиент] --(DNS-запрос)--> [Рекурсивный резолвер с сенсором]
                               |
                        (если cache miss)
                               |
                               v
                [Авторитативный сервер домена]
                               |
         (DNS-ответ: A 192.0.2.1, TTL 300)
                               |
                               v
[Рекурсивный резолвер] --(копия пакета)--> [Коллектор pDNS]
                               |
                               v
[Центральная база pDNS]   (timestamp, домен, тип, значение)
                               |
                               v
[API / SIEM / Scout-интерфейс] --> аналитик SOC
```

Каждая запись в БД pDNS (формат иллюстративный) содержит как минимум: `rrname` (домен), `rrtype` (тип записи), `rdata` (значение), `time_first` (первое появление), `time_last` (последнее наблюдение), `bailiwick` (зона, в которой была возвращена запись). Благодаря временным меткам аналитик может наложить окно инцидента на историю резолвинга и точно определить, участвовал ли конкретный IP в атаке.

Важное ограничение pDNS — пассивный сбор не гарантирует полноту; запись может отсутствовать, если запросы шли через резолверы, не имеющие сенсоров, или если использовались нетрадиционные DNS-транспорты (DNS over HTTPS без возможности перехвата). Однако крупнейшие сенсорные сети (Farsight, WhoisFreaks, VirusTotal) обеспечивают достаточное покрытие для практически значимого расследования.

## 4. Применение WHOIS и Passive DNS в SOC L1: практика обогащения

Ежедневный workflow аналитика SOC L1 при получении алерта, содержащего подозрительный домен или IP, включает быстрое обогащение с использованием описанных выше источников. Рассмотрим инструментальные средства и команды, доступные в Linux-окружении типовой рабочей станции аналитика; аналогичные действия выполняются программно через API при интеграции с SIEM/SOAR.

**a) Первичный WHOIS-запрос**

Утилита `whois` (или `jwhois`) делает запрос к соответствующему whois-серверу регистра (IANA определяет сервер по TLD). Для gTLD рекомендуется использовать RDAP там, где он доступен, поскольку вывод JSON легко парсится. Пример команды для домена (название домена условное, иллюстрация):

```bash
$ whois example.com | grep -E "Creation Date|Registrar|Name Server"
Creation Date: 2025-07-10T12:00:00Z
Registrar: Example Registrar, Inc.
Name Server: ns1.examplehosting.com
```

Сразу фиксируются факты: домен создан менее суток назад (если текущая дата 2025-07-11), регистратор принадлежит бюджетному хостингу, часто используемому для фишинга.

Там, где RDAP доступен, запрос может выглядеть так:

```bash
$ curl -s https://rdap.verisign.com/com/v1/domain/example.com | jq '.events[] | select(.eventAction == "registration")'
{
  "eventAction": "registration",
  "eventDate": "2025-07-10T12:00:00Z"
}
```

**b) Запрос исторического Passive DNS**

Для получения истории A-записей домена используется API одного из pDNS-провайдеров. Обращение через `curl` к WhoisFreaks Historical DNS API (иллюстративная схема, токен подставлен условно) может возвращать структуру:

```bash
$ curl -H "Authorization: Bearer $API_TOKEN" \
  "https://api.whoisfreaks.com/v1/dns/history?domain=example.com&type=A" | jq '.records[0]'
```
Пример ответа (схема):
```json
{
  "query": "example.com",
  "type": "A",
  "first_seen": "2025-06-01 00:00:00",
  "last_seen": "2025-07-11 12:00:00",
  "ip": "192.0.2.45",
  "count": 150
}
```
Аналитик видит, что домен впервые указал на IP 192.0.2.45 месяц назад, однако из других источников (TI-фиды) этот IP известен как часть подсети, используемой фишинговыми комплектами. Такой контекст резко повышает приоритет алерта.

**c) Поиск связанных доменов через Reverse Passive DNS (по IP)**

Зная IP 192.0.2.45, аналитик выполняет обратный запрос, чтобы найти все домены, когда-либо ресолвившиеся на этот адрес. Через Farsight DNSDB API (аналогично) или WhoisFreaks Reverse DNS API:

```bash
$ curl -H "Authorization: Bearer $API_TOKEN" \
  "https://api.whoisfreaks.com/v1/dns/reverse?ip=192.0.2.45&limit=10"
```
Ответ (иллюстративный):
```json
{
  "query": "192.0.2.45",
  "results": [
    {"domain": "phish-login123.com", "last_seen": "2025-07-11 13:00:00"},
    {"domain": "secure-update.net",   "last_seen": "2025-07-10 08:00:00"},
    {"domain": "example.com",         "last_seen": "2025-07-11 12:00:00"}
  ]
}
```

Теперь ясно, что `example.com` соседствует с двумя явно фишинговыми доменами, что является сильным индикатором вредоносности.

**d) Корреляция с историческим WHOIS**

Далее сопоставляется дата создания WHOIS с первой активностью в pDNS: если домен зарегистрирован 2025-07-10, а первое появление A-записи — 2025-07-10 12:01, то инфраструктура была развёрнута сразу после регистрации, типично для drive-by фишинга. При этом обращение к историческому WHOIS может показать, что до 2025-07-10 домен принадлежал другой организации и был «дропнут» (просрочен) — тогда злоумышленник перехватил освободившийся домен с сохранившейся репутацией.

**Инструментальные замечания для SOC L1**

*   Для оперативного использования в CLI помимо `whois` удобны `dig`, `nslookup` для активного DNS (быстрая проверка текущего состояния), однако для истории они не подходят.
*   Бесплатные инструменты: whois-серверы регистров, VirusTotal (исторический WHOIS и pDNS доступны через веб-интерфейс и API), SecurityTrails.
*   Платные сервисы (DomainTools Iris, WhoisFreaks, Farsight DNSDB) предоставляют полный исторический срез и Reverse WHOIS, часто интегрируются в SOAR как автоматические действия по обогащению.
*   Типичная ошибка начинающего аналитика — полагаться исключительно на активный DNS и игнорировать историю pDNS, из-за чего упускаются связи с вредоносной инфраструктурой, активной ранее.
*   В условиях GDPR/WHOIS privacy ключевые поля регистранта скрыты; в таких случаях pDNS становится единственным источником инфраструктурных связей.

## 5. Сквозной практический пример: расследование фишингового домена

**Исходные условия**

Рабочая станция аналитика SOC L1 (Linux, доступны утилиты `whois`, `dig`, `curl`, `jq`). Получен алерт от SIEM: правило «Possible Phishing Domain — Newly Registered» задетектило домен `secure-verify-example.com`. Действие: посетитель корпоративной сети перешёл по URL, который ведёт на этот домен. Требуется в течение 5 минут принять решение (эскалация или закрытие).

**Шаг 1: WHOIS-дамп для оценки «возраста» домена**

```bash
$ whois secure-verify-example.com | grep -E 'Creation Date|Registrar|Name Server'
Creation Date: 2025-07-11T08:15:00Z
Registrar: BudgetRegistrar Inc.
Name Server: ns1.fastfluxdns.ru
Name Server: ns2.fastfluxdns.ru
```
*Результат:* Домен зарегистрирован сегодня (алерт получен в 14:00 того же дня). Регистратор BudgetRegistrar Inc. неоднократно фигурировал в отчётах о фишинге. NS-серверы с доменом `.ru` и названием «fastflux» вызывают немедленное подозрение.

**Шаг 2: Запрос исторической A-записи через pDNS API (WhoisFreaks — иллюстрация)**

```bash
$ curl -s -H "Authorization: Bearer $WF_API_TOKEN" \
  "https://api.whoisfreaks.com/v1/dns/history?domain=secure-verify-example.com&type=A" | jq '.records[] | select(.ip != null)'
```
Пример ответа (схема):
```json
{
  "first_seen": "2025-07-11 08:20:01",
  "last_seen": "2025-07-11 14:05:00",
  "ip": "203.0.113.88",
  "count": 120
}
```
*Результат:* Домен начал ресолвиться на IP 203.0.113.88 всего через 5 минут после регистрации. Это классический паттерн «быстрого развёртывания».

**Шаг 3: Проверка обратного Passive DNS для IP**

```bash
$ curl -s -H "Authorization: Bearer $WF_API_TOKEN" \
  "https://api.whoisfreaks.com/v1/dns/reverse?ip=203.0.113.88&limit=5" | jq '.results[] | .domain'
```
Вывод:
```
"secure-verify-example.com"
"fake-banklogin.com"
"update-payment.cc"
```
*Результат:* На том же IP в последние дни были активны ещё два домена с явно фишинговыми названиями. Это связывает текущий алерт с известной инфраструктурой.

**Шаг 4: Корреляция с историческим WHOIS (если доступен) на предмет смены владельца**

Предположим, через платную подписку DomainTools Iris аналитик проверяет исторический WHOIS: домен `secure-verify-example.com` ранее, до 2025-07-10, принадлежал легитимной компании и был в статусе `pendingDelete`. Это означает, что злоумышленник перехватил освободившийся домен с остаточной репутацией. Запрос API (условный):

```bash
$ curl -H "Authorization: Bearer $DT_API_TOKEN" \
  "https://api.domaintools.com/v1/domains/secure-verify-example.com/whois/history/" | jq '.history[] | select(.date | contains("2025-07-08"))'
```
Ответ (упр.):
```json
{
  "date": "2025-07-08",
  "registrant": "Legitimate Company LLC",
  "status": "pendingDelete"
}
```
*Результат:* Факт дроп-перехвата подтверждает злонамеренность: атакующий использовал ранее доверенный домен для обхода репутационных фильтров.

**Шаг 5: Финальная проверка текущего резолвинга и закрытие/эскалация**

Быстрый активный запрос подтверждает, что домен до сих пор активен:

```bash
$ dig +short A secure-verify-example.com
203.0.113.88
```

Аналитик добавляет в инцидент собранные IoC: домен, IP, связанные домены, дата регистрации, статус перехвата. Порог эскалации достигнут: инцидент передаётся на L2 для дальнейшего анализа и блокировки.

**Ожидаемый вывод**

Сквозной пример демонстрирует, как за 5 минут благодаря каскаду обогащений (WHOIS → pDNS исторический → pDNS обратный → исторический WHOIS) неопытный аналитик L1 получает полную картину: домен-однодневка, созданный после перехвата, разделяет IP с известными фишинговыми доменами и зарегистрирован у регистратора из группы риска. Все шаги подкреплены командами и структурированными ответами API, что обеспечивает воспроизводимость процесса.
