# VirusTotal как инструмент первичного обогащения алертов: проверка файлов, IP-адресов, доменов и URL

## 1. Контекст и место VirusTotal в рабочем процессе SOC L1

VirusTotal — облачный сервис-агрегатор, предоставляющий бесплатный и коммерческий доступ к результатам проверки подозрительных объектов десятками антивирусных движков, системами поведенческого анализа и базами репутации. Для аналитика уровня L1 в центре мониторинга безопасности (SOC) этот инструмент выполняет роль первичного фильтра при обогащении (enrichment) алертов: он позволяет за секунды получить контекст по индикатору компрометации (IoC) — хешу файла, IP-адресу, доменному имени или URL — и на основе этого принять решение об эскалации инцидента на более глубокий анализ.

В отличие от глубокого реверс-инжиниринга или ручного исследования сетевых артефактов, VirusTotal предоставляет готовый консенсус десятков движков в одном интерфейсе. Это делает его идеальным начальным узлом в процессе обогащения: даже если сервис не даёт исчерпывающего ответа, он быстро показывает «красные флаги» — наличие детектов, связи с вредоносной инфраструктурой, аномалии в пассивном DNS. В SOC L1 ожидается, что аналитик, получив алерт от SIEM или EDR, извлечёт из него наблюдаемые сущности и в первую очередь «прогонит» их через VirusTotal, чтобы ответить на вопрос: «Это реальная угроза или ложное срабатывание?»

Сервис работает со структурно разными типами объектов, каждый из которых требует собственной методики проверки и возвращает специфичный для своего типа контекст. Путаница между ними — распространённая ошибка начинающих аналитиков, поэтому целесообразно сразу разграничить ключевые понятия.

| Тип объекта | Что проверяется | Основной способ идентификации | Типичные артефакты в отчёте | Ограничения |
|------------|-----------------|------------------------------|-----------------------------|-------------|
| **Файл** | Сам файл или его криптографический хеш (MD5, SHA‑1, SHA‑256) | Хеш-сумма (предпочтительно SHA‑256) | Результаты антивирусных движков (`scans`), метки (`tags`), имена, под которыми файл загружался (`submission_names`), связи с доменами и IP (`contacted_domains`, `contacted_ips`) | Размер загружаемого файла ограничен (обычно 650 МБ для бесплатного публичного API); конфиденциальные файлы не должны отправляться в публичный сервис |
| **IP-адрес** | Репутация конкретного IPv4/IPv6-адреса | IP-адрес в десятичном или URL-encoded формате | Статистика детектирования вредоносных файлов, коммуницировавших с этим IP; данные пассивного DNS (`resolutions`); WHOIS-информация; категории (например, `web`, `proxy`, `tor`) | Данные пассивного DNS могут быть неполными; один IP может использоваться несколькими независимыми абонентами, что ведёт к шуму |
| **Домен** | Репутация доменного имени второго или более высокого уровня | Полное доменное имя (FQDN) | Аналогичная IP-статистика по связанным файлам и URL; DNS-записи (A, MX, NS, SOA); списки поддоменов (`subdomains`); WHOIS-история | Информация о недавно зарегистрированных доменах может отсутствовать; динамический DNS и сервисы сокращения ссылок создают дополнительный уровень индирекции |
| **URL** | Контент, доступный по конкретному URL (включая файлы, загружаемые при переходе) | Полный URL в кодировке | Результаты сканеров URL (анализ содержимого страницы); редиректы (`redirecting_urls`); загруженные файлы; финальный URL после всех редиректов (`last_final_url`) | Сканирование не выполняется для страниц, требующих аутентификации; некоторые URL могут быть ошибочно отнесены к категории `unrated` |

Для аналитика L1 критически важно, что VirusTotal **не подтверждает и не отрицает вредоносность** сам по себе — он агрегирует мнения. Флаг «5/70» означает, что 5 антивирусных движков из 70 сочли файл подозрительным; это может быть как началом серьёзной атаки, так и ложным срабатыванием на неопасный инструмент. Поэтому VirusTotal — это лишь первый этап обогащения, требующий дальнейшей верификации.

Принципиальная схема взаимодействия аналитика с VirusTotal в цепочке обогащения выглядит так:

```text
[SIEM/EDR-алерт] → [извлечение IoC (хэш, IP, домен, URL)]
                         │
                         ▼
               [Запрос к VirusTotal API / GUI]
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼               ▼
      [Файловый       [IP/доменная    [URL-сканер]
       анализ]        репутация]
          │              │               │
          └──────────────┼──────────────┘
                         ▼
               [Сводный контекст → решение об эскалации]
```

Понимание того, где именно в этом потоке возникают ограничения и как интерпретировать выходные данные для каждого типа объекта, является обязательной компетенцией SOC-аналитика начального уровня.

## 2. Внутреннее устройство VirusTotal и модель данных для разных типов объектов

VirusTotal предоставляет унифицированный REST API (как правило, версии 3), через который и веб-интерфейс, и автоматизированные инструменты взаимодействуют с его бэкендом. Бэкенд сервиса агрегирует информацию от более чем 70 антивирусных движков, песочниц, сервисов пассивного DNS, списков сетевой репутации и собственных алгоритмов VT. Отчёт, возвращаемый по любому из четырёх типов объектов, представляет собой JSON-документ с единообразной структурой верхнего уровня, но отличающимся содержимым секций `data.attributes` в зависимости от типа.

Для структурного понимания того, как данные организованы и что из них извлекает аналитик, удобно представить модель в виде таблицы, фиксирующей ключевые поля для каждого класса объектов. Это позволит студентам быстро ориентироваться в ответах API и сопоставлять наблюдаемые значения с их смыслом.

| Поле / группа полей | Тип объекта «файл» (file) | Тип объекта «IP-адрес» (ip_address) | Тип объекта «домен» (domain) | Тип объекта «URL» (url) |
|---------------------|--------------------------|-----------------------------------|-------------------------------|----------------------------|
| **Идентификатор** | `id` = SHA‑256 хеш (реже MD5/SHA‑1); обязателен для запроса | `id` = IP-адрес в строковом виде | `id` = доменное имя (FQDN) | `id` = URL в кодировке base64url без завершающих `=` |
| **Основные атрибуты** | `type_description`, `size`, `magic`, `first_submission_date`, `last_analysis_date`, `tags`, `meaningful_name` | `country`, `as_owner`, `last_https_certificate` (связанный TLS-сертификат), `jarm` | `whois` (дата создания, expiry, регистратор), `last_dns_records` (массив записей), `subdomains` | `last_final_url`, `title`, `threat_names`, `categories` (набор категорий, напр. `malware`, `phishing`) |
| **Статистика детектирования** | `last_analysis_stats`: `{harmless, malicious, suspicious, undetected, timeout}` + `positives` / `total` (устар.) | `last_analysis_stats` — агрегация по категориям детектов связанных файлов: `harmless`, `malicious`, `suspicious` и т.д. | `last_analysis_stats` — аналогично IP, но фокус на URL/файлах, связанных с доменом | `last_analysis_stats` — аналогично, но движки анализируют сам URL (содержимое, редиректы) |
| **Результаты движков** | `last_analysis_results` — объект, ключ = имя движка, значение = объект с полями `category` (malicious/harmless/…) и `result` (метка) | `last_analysis_results` — объект, ключ = имя движка, значение = результат категоризации IP | `last_analysis_results` — аналогично IP | `last_analysis_results` — аналогично, результат классификации URL |
| **Связи (relationships)** | `contacted_domains`, `contacted_ips`, `embedded_domains` | `communicating_files`, `referrer_files`, `resolutions` (пассивный DNS) | `communicating_files`, `referrer_files`, `resolutions` | `downloaded_files`, `referrer_files`, `redirections` |
| **Специфичные данные** | `sigma_analysis_results`, `pe_info` (структура PE-файла), `crowdsourced_ids_results` | `whois` — данные о владельце сети | `whois` — полная история регистрационных данных, `categories` (веб-категоризация) | `outlinks`, `tls_certificate`, `html_meta` |

Все запросы к API аутентифицируются через HTTP-заголовок `x-apikey`. Бесплатный публичный ключ имеет жёсткие ограничения: 4 запроса в минуту для обычных пользователей, 500 запросов в день (зависит от типа ключа). Это делает массовое автоматическое обогащение в реальном времени без квотирования затруднительным, но для единичных проверок индикаторов из алертов достаточно. В коммерческих SOC часто используются корпоративные лицензии VirusTotal (VT Enterprise) с повышенными лимитами и приватным режимом поиска, при котором загруженные файлы не попадают в публичный датасет.

Важно отметить, что логика работы с файлами отличается от логики работы с URL. При проверке файла по хешу запрос `GET /api/v3/files/{sha256}` немедленно возвращает сохранённый отчёт, если такой хеш ранее уже был загружен и проанализирован другими пользователями. Если хеш неизвестен, можно инициировать загрузку файла через `POST /api/v3/files` с бинарными данными. В SOC L1 это происходит редко, чаще аналитик сталкивается с уже известными хешами. Проверка IP и домена также работает только по ранее собранным данным: `GET /api/v3/ip_addresses/{ip}` и `GET /api/v3/domains/{domain}` возвращают агрегированную информацию без активного сканирования. URL же обычно требуется отправлять на активный анализ: `POST /api/v3/urls` с телом `{"url": "http://..."}`, после чего сервис возвращает идентификатор сканирования, а затем результат можно получить через `GET /api/v3/urls/{id}`. Эта асимметрия объясняется тем, что содержимое URL может быстро меняться, и VirusTotal должен выполнить свежий проход сканерами.

Ещё одна структурная особенность — поле `last_analysis_stats`. Оно содержит агрегированные количества детектов движков по категориям, а не простую пару `positives/total`. Например, для IP-адреса может быть указано: `"malicious": 15, "suspicious": 3, "harmless": 50, "undetected": 2`. Это даёт гораздо более нюансированную картину, чем просто «15/70». Аналитик должен искать аномалии: если для внутреннего корпоративного ресурса вдруг появляются `malicious` > 0, это повод для расследования, даже если абсолютное большинство движков считают объект безвредным.

## 3. Применение VirusTotal в SOC L1: типовые операции, интерпретация и подводные камни

На практике аналитик L1 взаимодействует с VirusTotal двумя способами: через графический веб-интерфейс (для единичных проверок) и через REST API (для автоматизации в скриптах или интеграции с SOAR). Рассмотрим оба подхода с акцентом на типичные ошибки и принципы интерпретации результатов по каждому типу индикаторов.

### 3.1. Проверка файлов по хешу

Наиболее частый сценарий: из EDR-алерта получен SHA‑256 хеш исполняемого файла. Аналитик выполняет запрос к API (или вводит хеш в веб-интерфейс). Ниже приведён пример запроса с помощью `curl` и типового ответа (иллюстративная схема, значения зависят от среды):

```bash
curl --request GET \
  --url 'https://www.virustotal.com/api/v3/files/275a021bbfb6489e54d471899f7db9d1663fc695ec2fe2a2c4538aabf651fd0f' \
  --header 'x-apikey: <ваш_ключ>'
```

Фрагмент ответа, на который в первую очередь обращает внимание аналитик:

```json
{
  "data": {
    "id": "275a021bbfb6489e54d471899f7db9d1663fc695ec2fe2a2c4538aabf651fd0f",
    "type": "file",
    "attributes": {
      "last_analysis_stats": {
        "harmless": 58,
        "malicious": 8,
        "suspicious": 2,
        "undetected": 2,
        "timeout": 0
      },
      "last_analysis_results": {
        "Fortinet": { "category": "malicious", "result": "W32/Agent.D!tr" },
        "Kaspersky": { "category": "malicious", "result": "Trojan.Win32.Agent" },
        "McAfee": { "category": "malicious", "result": "RDN/Generic Trojan" },
        "Microsoft": { "category": "malicious", "result": "Trojan:Win32/Agent" }
      },
      "tags": ["peexe", "trojan"],
      "first_submission_date": 1620000000,
      "meaningful_name": "invoice_042025.exe"
    }
  }
}
```

Интерпретация: 8 движков из 70 определили файл как вредоносный, причём авторитетные вендоры (Kaspersky, Microsoft, Fortinet) дают конкретные детекты класса `trojan`. Имя файла `invoice_042025.exe` — типичный приём социальной инженерии. Этого достаточно, чтобы классифицировать файл как подозрительный и эскалировать инцидент. **Критическая ошибка**: неопытный аналитик может решить, что «8/70 = низкая детектируемость, возможно, ложняк», игнорируя метки известных движков. Правило: смотреть не только на количество, но и на качество детектов (вендоров) и наличие меток троянов/бэкдоров.

Также стоит обращать внимание на `last_analysis_stats.harmless` > 0 и `undetected`: нулевые детекты не гарантируют безопасность — возможно, файл просто новый и ещё не проанализирован большинством движков.

### 3.2. Проверка IP-адреса

Для IP запрос предельно прост. Команда:

```bash
curl --request GET \
  --url 'https://www.virustotal.com/api/v3/ip_addresses/203.0.113.42' \
  --header 'x-apikey: <ваш_ключ>'
```

Пример структуры значимых полей ответа:

```json
{
  "data": {
    "id": "203.0.113.42",
    "type": "ip_address",
    "attributes": {
      "last_analysis_stats": { "malicious": 12, "suspicious": 2, "harmless": 56 },
      "last_analysis_results": {
        "AlienVault": { "category": "malicious", "result": "compromised" },
        "BitDefender": { "category": "malicious", "result": "malware_activity" }
      },
      "whois": "netname: EXAMPLE-NET\ncountry: US",
      "last_https_certificate": { "issuer": { "CN": "Fake CA" } },
      "jarm": "2ad2ad0002ad2ad22c2ad2ad2ad2ad7e7c8d7e7c8d7e7c8d7e7c8d"
    }
  }
}
```

Аналитик должен обратить внимание на `malicious` > 0 — это прямой сигнал, что IP был замечен в раздаче вредоносного ПО или управлении C2. Поле `last_https_certificate` с подозрительным издателем и нестандартный JARM-хэш дополнительно указывают на нелегитимный TLS-сервер. При этом IP может иметь и легитимную часть (`harmless`), если на нём размещены разные сервисы. Ошибка: считать IP безопасным только на том основании, что `harmless` >> `malicious`. В SOC действует правило «если есть хотя бы один авторитетный источник, классифицирующий IP как вредоносный, необходимо углублённое исследование».

Информация пассивного DNS (`relationships.resolutions`) помогает понять, какие домены ранее резолвились на этот IP. Если среди них есть известные фишинговые страницы, угроза подтверждается.

### 3.3. Проверка домена

Запрос к API:

```bash
curl --request GET \
  --url 'https://www.virustotal.com/api/v3/domains/evil.example.com' \
  --header 'x-apikey: <ваш_ключ>'
```

Ключевые данные ответа:

```json
{
  "data": {
    "id": "evil.example.com",
    "type": "domain",
    "attributes": {
      "whois": "Creation Date: 2025-04-01\nRegistrar: NameCheap, Inc.",
      "last_dns_records": [
        { "type": "A", "value": "203.0.113.42", "ttl": 300 }
      ],
      "last_analysis_stats": { "malicious": 9, "suspicious": 3, "harmless": 58 },
      "subdomains": ["login.evil.example.com", "docs.evil.example.com"],
      "categories": { "Forcepoint": "phishing" }
    }
  }
}
```

Выводы: домен зарегистрирован недавно (возраст несколько дней) — индикатор свежей фишинговой кампании. Короткий TTL (300 сек) часто используется для быстрой смены IP-инфраструктуры. Категория `phishing` подтверждает целевую угрозу. Наличие поддоменов с характерными именами (`login`, `docs`) расширяет поверхность атаки.

Ошибка: игнорировать «некритичный» детект только одного вендора, например, Forcepoint, и считать домен безопасным. Как и с IP, важно не количество, а контекст: если детект относится к авторитетному для организации источнику (например, используется внутренний TI-фид), даже единичный флаг требует проверки.

### 3.4. Проверка URL

Проверка URL требует двух шагов: сначала отправка на анализ, затем получение результата.

**Шаг 1 — отправка**:

```bash
curl --request POST \
  --url 'https://www.virustotal.com/api/v3/urls' \
  --header 'x-apikey: <ваш_ключ>' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'url=https://evil.example.com/payload.exe'
```

Ответ содержит `id` — идентификатор сканирования (например, `u-23f8b6a2...`).

**Шаг 2 — получение результата** (через некоторое время, обычно несколько минут):

```bash
curl --request GET \
  --url 'https://www.virustotal.com/api/v3/urls/u-23f8b6a2...' \
  --header 'x-apikey: <ваш_ключ>'
```

Ответ:

```json
{
  "data": {
    "id": "u-23f8b6a2...",
    "type": "url",
    "attributes": {
      "last_final_url": "http://203.0.113.42/payload.exe",
      "redirecting_urls": [
        "https://evil.example.com/payload.exe",
        "http://cdn.evil.example.com/payload.exe"
      ],
      "last_analysis_stats": { "malicious": 15, "suspicious": 2, "harmless": 53 },
      "last_analysis_results": {
        "Avira": { "category": "malicious", "result": "phishing" },
        "ESET": { "category": "malicious", "result": "Win32/TrojanDownloader" }
      },
      "outlinks": ["http://203.0.113.42/update.exe"],
      "title": "Invoice Download Portal"
    }
  }
}
```

Аналитик видит, что URL прошёл через несколько редиректов, финальный адрес указывает на тот же IP, который ранее был проверен и признан вредоносным. Детекты классифицируют URL как фишинговый и загрузчик трояна. Заголовок «Invoice Download Portal» соответствует социальной инженерии, использованной в фишинговом письме. Наличие `outlinks` на дополнительные файлы указывает на многоступенчатую атаку.

Типичная ошибка: полагать, что анализ URL немедленно доступен. Необходимо предусмотреть задержку и повторные запросы. Кроме того, не все URL могут быть просканированы: если страница требует авторизации, VirusTotal не сможет получить содержимое, и результат будет `unrated`. В таких случаях обогащение через VT бесполезно, и требуются другие методы, например, ручное открытие в изолированной среде.

Во всех случаях аналитик должен фиксировать в тикете прямой URL отчёта VirusTotal (поле `permalink` в устаревшем API, в v3 — поле `self` в `links`), чтобы старший аналитик мог быстро перейти к деталям.

## 4. Сквозной практический пример: оценка многосоставного инцидента с помощью VirusTotal

**Исходные условия:** SOC L1 аналитик получил оповещение от EDR: на конечной точке пользователя `DESKTOP‑A1B2C3` зафиксирован запуск процесса `invoice_042025.exe` с дочерним процессом `powershell.exe`, скачивающим файл с IP-адреса `203.0.113.42`. EDR передал хеш SHA‑256 родительского файла, IP-адрес источника и URL, по которому был скачан файл (https://evil.example.com/payload.exe). Все три индикатора необходимо проверить через VirusTotal, чтобы принять решение об эскалации.

Ниже приведены шаги с реально воспроизводимыми командами и фрагментами ответов (конкретные хеши и IP иллюстративны, однако структура данных соответствует v3 API).

**Шаг 1: Проверка хеша файла**

Действие: запросить у VirusTotal отчёт по хешу файла.

```bash
curl -s --request GET \
  --url 'https://www.virustotal.com/api/v3/files/275a021bbfb6489e54d471899f7db9d1663fc695ec2fe2a2c4538aabf651fd0f' \
  --header 'x-apikey: $VT_API_KEY' | jq '.data.attributes.last_analysis_stats, .data.attributes.last_analysis_results["Kaspersky"], .data.attributes.tags'
```

Вывод (ключевые части):
```json
{
  "harmless": 52,
  "malicious": 15,
  "suspicious": 3,
  "undetected": 0,
  "timeout": 0
}
{
  "category": "malicious",
  "result": "Trojan.Win32.Agent.tkgej"
}
[
  "peexe",
  "trojan",
  "downloader"
]
```

Результат: 15 движков детектируют вредоносность, метки прямо указывают на трояна-загрузчика. Это критический уровень, требующий немедленной эскалации.

**Шаг 2: Проверка IP-адреса, с которого загружался файл**

Действие: запросить репутацию IP-адреса `203.0.113.42`.

```bash
curl -s --request GET \
  --url 'https://www.virustotal.com/api/v3/ip_addresses/203.0.113.42' \
  --header 'x-apikey: $VT_API_KEY' | jq '.data.attributes.last_analysis_stats, .data.attributes.last_analysis_results.AlienVault, .data.attributes.whois'
```

Вывод:
```json
{
  "harmless": 45,
  "malicious": 18,
  "suspicious": 5,
  "undetected": 2,
  "timeout": 0
}
{
  "category": "malicious",
  "result": "compromised"
}
"netname:         CUSTOMER-NET
country:         US
descr:           Hosting Provider
"
```

Результат: 18 движков помечают IP как вредоносный, категория `compromised` подтверждает, что этот IP участвует во вредоносной активности. WHOIS указывает на хостинг-провайдера, что типично для временных C2-серверов. Это усиливает подозрения.

**Шаг 3: Проверка URL, с которого скачивался файл**

Действие: отправить URL на анализ и получить результат.

```bash
# Отправка
curl -s --request POST \
  --url 'https://www.virustotal.com/api/v3/urls' \
  --header 'x-apikey: $VT_API_KEY' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'url=https://evil.example.com/payload.exe' | jq '.data.id'

# Пусть выдан id = "u-1a2b3c4d..."
# После задержки (30-60 секунд) получаем результат
curl -s --request GET \
  --url 'https://www.virustotal.com/api/v3/urls/u-1a2b3c4d...' \
  --header 'x-apikey: $VT_API_KEY' | jq '.data.attributes.last_analysis_stats, .data.attributes.last_final_url, .data.attributes.redirecting_urls'
```

Вывод:
```json
{
  "harmless": 40,
  "malicious": 22,
  "suspicious": 5,
  "undetected": 3,
  "timeout": 0
}
"http://203.0.113.42/payload.exe"
[
  "https://evil.example.com/payload.exe",
  "http://203.0.113.42/payload.exe"
]
```

Результат: 22 детекта, финальный URL совпадает с IP, уже признанным вредоносным. Редиректы показывают, что изначальный домен ведёт на тот же IP. URL надёжно классифицирован как вредоносный.

**Шаг 4: Агрегирование и принятие решения**

На основе трёх проверок L1 аналитик формирует следующий вывод:
- Хеш файла `invoice_042025.exe` детектируется авторитетными антивирусами как троян-загрузчик.
- IP-адрес `203.0.113.42` имеет плохую репутацию (связан с вредоносной активностью, хостинг-провайдер, используемый для C2).
- URL https://evil.example.com/payload.exe ведёт после редиректов на тот же IP и распознаётся сканерами как вредоносный.
- Все три индикатора взаимно подтверждают друг друга, образуя связную картину атаки с использованием социальной инженерии (фишинг с темой счёта-фактуры), доставкой вредоносного файла и связью с внешней инфраструктурой.

Ожидаемый вывод примера: данный набор проверок демонстрирует, как VirusTotal позволяет за считанные минуты подтвердить угрозу, выявить взаимосвязи между индикаторами и принять обоснованное решение об эскалации инцидента на уровень L2 для глубокого анализа и реагирования.
