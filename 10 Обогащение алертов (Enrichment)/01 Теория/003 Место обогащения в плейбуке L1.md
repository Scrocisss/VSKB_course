# Место обогащения в плейбуке аналитика первой линии SOC

## Контекст и базовые понятия

Обогащение алертов (alert enrichment) — это процесс дополнения сырого события безопасности контекстной информацией, позволяющей аналитику первой линии (L1) быстрее и точнее оценить его критичность, определить природу угрозы и принять решение о дальнейших шагах. Цель обогащения — минимизировать ручной сбор данных, снизить количество ложноположительных эскалаций и обеспечить единообразие первичного анализа.

В рабочем процессе SOC уровень L1 выполняет триаж (сортировку) входящих алертов, руководствуясь плейбуком — документированной последовательностью операций для конкретного типа инцидента. Обогащение обычно встраивается в начальную фазу плейбука, сразу после получения алерта и его первичной валидации (проверки, не является ли событие тестовым, дублирующимся или очевидно ложным). Таким образом, место обогащения — между регистрацией алерта и фазой углублённого анализа (который может выполняться тем же аналитиком или передаваться на L2). В некоторых реализациях автоматическое обогащение запускается ещё до того, как алерт попадает в очередь L1, но аналитик обязан интерпретировать его результаты и при необходимости выполнить ручные запросы, специфичные для контекста организации.

Важно разграничить обогащение со смежными процессами:

| Процесс | Определение | Ключевые признаки | Типичные параметры / пример |
|---------|-------------|-------------------|------------------------------|
| Обогащение (enrichment) | Дополнение алерта внешними и внутренними данными без изменения его структуры | Добавляет поля: репутация IP, владелец, геолокация, принадлежность хоста к критичным активам | Запрос к VirusTotal для проверки хеша, поиск IP в CMDB |
| Корреляция (correlation) | Объединение нескольких событий в один инцидент на основе правил | Применяется на уровне SIEM, порождает новый алерт, сокращая количество первичных событий | Правило: 5 неудачных входов за 1 минуту → инцидент |
| Расследование (investigation) | Построение гипотез, поиск дополнительных индикаторов, восстановление цепочки атаки | Итеративный процесс, часто требует доступа к сырым логам, форензике, интервью с пользователем | Анализ временной линии, выгрузка дампа памяти |
| Валидация (validation) | Проверка алерта на ложность: тестовые системы, исключения, дубликаты | Чисто бинарное решение («да/нет»), не добавляет новых данных, только фильтрует | Проверка: алерт с хоста, выведенного из эксплуатации, закрывается |

Различие между обогащением и корреляцией особенно значимо для L1: корреляция снижает поток на входе, а обогащение добавляет информацию к отдельному алерту, уже прошедшему корреляцию. Обогащение не предназначено для построения полной картины атаки — эту задачу решает расследование на L2/L3.

Ключевое понятие — контекст. Различают внутренний контекст (данные организации: инвентаризация активов, учётные записи, уязвимости, сетевые сегменты) и внешний контекст (threat intelligence: репутационные списки, пассивный DNS, whois, данные о тактиках и техниках). Эффективный плейбук L1 предписывает комбинировать оба типа, причём внутренний контекст часто имеет решающее значение: вредоносный IP, обращение к которому зафиксировано с сервера разработки, менее опасен, чем такое же соединение с контроллера домена.

## Внутреннее устройство обогащения в плейбуке L1

Поскольку тема является процессом, встроенным в методологию реагирования, рассмотрим его жизненный цикл в виде последовательных фаз, ролей и артефактов. Типовая схема обогащения в плейбуке L1 может быть представлена как линейный поток с возможностью прерывания.

```text
[Алерт получен] 
    ↓
[Фаза 1: Первичная валидация] → (не валиден) → [Закрыть алерт]
    ↓ (валиден)
[Фаза 2: Определение требуемого контекста] 
    ↓
[Фаза 3: Сбор данных обогащения]
    │
    ├── Автоматические запросы (SIEM/SOAR)      
    └── Ручные запросы аналитика L1
    ↓
[Фаза 4: Интерпретация результатов и оценка критичности]
    ↓
[Фаза 5: Принятие решения: закрыть / эскалировать]
```

Рассмотрим каждую фазу подробно с точки зрения ролей и артефактов.

### Фаза 1: Первичная валидация (фильтрация)
Роль: автоматика (SIEM) или аналитик L1. На этом этапе алерт проверяется по «белым спискам» (исключениям) и критериям тестовой инфраструктуры. Если система определяет, что событие заведомо ложно, оно закрывается без дальнейшего обогащения. В противном случае формируется карточка алерта, содержащая базовые поля: временная метка, источник, тип события, урезанные данные (например, IP-адрес, имя процесса). Этот набор — входные данные для обогащения.

### Фаза 2: Определение требуемого контекста
Роль: аналитик L1 (иногда с подсказками плейбука). В зависимости от типа алерта (например, подозрительное сетевое соединение vs срабатывание антивируса) формируется минимально необходимый набор контекстных атрибутов. Плейбук типизирует запросы:
- Для сетевых индикаторов (IP, домен) — whois, реверсивный DNS, геолокация, пассивный DNS, репутационные сервисы.
- Для файловых индикаторов (хеши) — запросы к VirusTotal, внутренней песочнице.
- Для хостовых индикаторов (имя хоста, пользователь) — поиск в CMDB, Active Directory, системе управления конфигурациями.
- Для индикаторов уязвимостей (CVE) — данные патч-менеджмента, сканеров уязвимостей.

На этом же этапе учитываются ограничения: доступность источников, временные квоты API, допустимая задержка.

### Фаза 3: Сбор данных обогащения
Роль: автоматизированные инструменты (скрипты, SOAR-плэйбуки) и аналитик L1, выполняющий ручные запросы в консоли. 
- Автоматические источники интегрируются через API или локальные базы. Например, SIEM при поступлении алерта может самостоятельно дополнить его полями GeoIP, а SOAR — инициировать проверку IP во внешних Threat Intelligence Platform (TIP).
- Ручные запросы производятся, когда автоматика не дала результата, либо для валидации трудных случаев. Аналитик выполняет команды в терминале или использует веб-консоли.

Артефакт этой фазы — обогащённые поля алерта, документированные в тикет-системе. Пример структуры обогащённых данных (JSON-подобное представление):

```json
{
  "alert_id": "AL-20250401-0012",
  "raw": {
    "src_ip": "<IP-адрес источника>",
    "dst_ip": "<IP-адрес назначения>",
    "dst_port": 443
  },
  "enrichment": {
    "src_internal": {
      "hostname": "PC-JDOE",
      "user": "jdoe",
      "department": "Marketing",
      "criticality": "low"
    },
    "dst_external": {
      "reverse_dns": "suspicious.example.com",
      "whois_org": "Some Hosting Ltd.",
      "geo_country": "RU",
      "reputation": {
        "vt_score": "18/90",
        "abuseipdb_confidence": "95%"
      }
    }
  }
}
```

### Фаза 4: Интерпретация результатов и оценка критичности
Роль: аналитик L1. Комбинируя внутренний и внешний контекст, аналитик оценивает серьёзность ситуации. Плейбук содержит матрицу эскалации: например, если dst_ip имеет высокий reputation score, а src_host входит в критичную подсеть, алерт немедленно эскалируется. Если внешний индикатор неоднозначен, а внутренний контекст низкорисковый, алерт может быть закрыт с пометкой «безопасный».

### Фаза 5: Принятие решения
Результат: либо закрытие алерта с документированием проведённого обогащения, либо эскалация на L2 с приложением собранных данных.

Важная характеристика процесса — глубина обогащения. Она определяется временем, отпущенным на триаж (обычно 5–15 минут). Поэтому плейбук явно ограничивает количество источников и задаёт приоритеты: сначала быстрые внутренние источники, затем внешние, но только для подозрительных индикаторов.

Ошибкой является попытка полного расследования на уровне L1: обогащение не должно заменять углублённый анализ. Ограничение глубины достигается условиями в плейбуке: «Если по итогам трёх источников репутация неоднозначна — эскалировать».

## Применение и работа с обогащением

На практике аналитик L1 взаимодействует с обогащением через несколько каналов: интерфейс SIEM, терминал, SOAR-платформу, веб-интерфейсы внешних сервисов. Рассмотрим типовые инструменты и приёмы, избегая голого перечисления продуктов.

Работа начинается с идентификации индикаторов для обогащения. Вычленение IP-адресов, доменов, URL, хешей файлов, имён пользователей из сырого события обычно автоматизировано, но аналитик должен уметь делать это вручную для неструктурированных логов.

### Источники и соответствующие команды

**Сетевые индикаторы (IP, домен)**

- WHOIS: для определения владельца IP-блока или домена.
```bash
whois <IP-адрес> | grep -E "OrgName|netname|descr|country"
```
Вывод показывает организацию-владельца и страну регистрации.

- Обратный DNS: проверка PTR-записи.
```bash
dig -x <IP-адрес> +short
```
Отсутствие или подозрительное имя усиливает подозрения.

- Пассивный DNS: запрос к внутреннему серверу или сервису (например, PassiveTotal / RiskIQ). Типовой API-вызов (иллюстрация):
```bash
curl -s "https://api.passivetotal.org/v2/dns/passive/<IP-адрес>" -H "Authorization: Bearer <токен>"
```
Ожидаемый ответ содержит массив разрешений, указывающий, какие домены ранее связывались с IP.

- Репутационные API: VirusTotal, AbuseIPDB.
```bash
curl -s "https://www.virustotal.com/api/v3/ip_addresses/<IP-адрес>" \
  -H "x-apikey: <ваш_ключ>" | jq '.data.attributes.last_analysis_stats'
```
Вывод вроде `{"harmless": 60, "malicious": 18, ...}` позволяет быстро оценить степень угрозы.

- Геолокация: запрос к локальной базе GeoIP или сервисам.
```bash
geoiplookup <IP-адрес>
```

**Хостовые индикаторы**

- CMDB / инвентаризационная система: проверка принадлежности хоста, критичности, ответственного лица. Пример запроса к REST API внутренней CMDB:
```bash
curl -s "http://cmdb.internal/api/v1/hosts?ip=<IP-адрес>" | jq '.hostname, .criticality'
```
- Active Directory / LDAP: получение атрибутов пользователя.
```powershell
Get-ADUser -Identity "jdoe" -Properties Department, Title | Select Department, Title
```
Такой запрос покажет, что учётная запись принадлежит отделу маркетинга, что снижает критичность подозрительной активности, если нет дополнительных факторов.

**Файловые индикаторы (хеши)**

- VirusTotal: аналогичный запрос для хеша.
```bash
curl -s "https://www.virustotal.com/api/v3/files/<SHA-256>" \
  -H "x-apikey: <ключ>" | jq '.data.attributes.last_analysis_stats'
```

- Локальная песочница: ручная отправка файла через веб-интерфейс или API. В плейбуке обычно предписано отправить файл, если он был помещён в карантин антивирусом.

**Индикаторы уязвимостей**

- Запрос к внутренней системе управления уязвимостями (Vulnerability Management) на наличие CVE на затронутом хосте.
```bash
curl -s "http://vulnmgmt/api/assets?hostname=PC-JDOE" | jq '.cves[]?'
```
Вывод списка CVE, сроков исправления помогает решить, связан ли алерт с известной уязвимостью.

### Типичные ошибки и подводные камни

- Избыточные запросы: отправка тысяч API-вызовов в короткий срок вызывает блокировку. Плейбук должен регламентировать кэширование и использование агрегированных источников.
- Игнорирование таймаутов: зависший запрос не должен блокировать триаж. Важно задать таймаут команд (например, `--connect-timeout 5` для curl).
- Неверная интерпретация результатов: высокий репутационный счёт не всегда означает вредоносность — легитимные сервисы могут попадать в чёрные списки ошибочно. Обогащение всегда требует сопоставления с внутренним контекстом.
- Пропуск внутренних источников: анализ только внешней репутации без учёта функции хоста — частая причина ложных эскалаций. В плейбуке должно быть явное указание: «Сначала CMDB/AD, потом внешние сервисы».
- Слепое следование автоматике: при автоматическом обогащении необходимо проверять релевантность полученных полей. Например, геолокация может быть неточной для Anycast-сетей.

### Интеграция в пайплайн триажа

Обогащение эффективно, когда его результаты визуализированы в интерфейсе SIEM. Современные системы отображают карточку алерта с вкладками: «Контекст хоста», «Внешний контекст», «История». Аналитик L1 работает в режиме «одного окна», по клику видя всю собранную информацию. Ручные запросы выполняются только для нестандартных ситуаций, оговорённых плейбуком.

## Сквозной практический пример: алерт на сетевое соединение с подозрительным IP

Исходные условия: SIEM сгенерировал алерт типа «Outbound connection to known malicious IP» на основе логов межсетевого экрана. Сырые данные: хост 192.168.50.45 (внутренняя подсеть) установил исходящее TCP-соединение с IP 203.0.113.77 на порт 443. Плейбук L1 для сетевых алертов предписывает трёхэтапное обогащение. Роль — аналитик L1, доступны терминал, консоль SIEM, API-ключи внешних сервисов.

**Шаг 1: Первичная валидация и извлечение индикаторов**
Аналитик открывает карточку алерта в SIEM, убеждается, что событие не относится к исключениям (источник не является сервером обновлений). Индикаторами для обогащения являются IP-адрес источника и назначения.
Карточка алерта (фрагмент):
```text
Alert ID: AL-20250401-0012
Time: 2025-04-01 09:15:43 UTC
Source IP: 192.168.50.45 (internal)
Destination IP: 203.0.113.77
Destination Port: 443 (TCP)
Action: Allowed
Rule: "Suspicious External Connection"
```

**Шаг 2: Обогащение внутреннего контекста источника**
Выполняется запрос к CMDB для идентификации хоста-источника. Команда:
```bash
curl -s "http://cmdb.internal/api/v1/assets?ip=192.168.50.45" | jq '.hostname, .criticality, .owner'
```
Ожидаемый вывод:
```json
"SRV-FINANCE-02"
"high"
"user: jdoe"
```
Выясняется, что это сервер финансового отдела с высокой критичностью, что повышает приоритет алерта.

**Шаг 3: Обогащение внешнего контекста по IP назначения**
Последовательно выполняются команды:

```bash
# whois
whois 203.0.113.77 | grep -i "orgname\|netname\|country"
```
Вывод: `netname: BADHOSTING`, `country: XX`, что не указывает на легитимный бизнес.

```bash
# Обратный DNS
dig -x 203.0.113.77 +short
```
Вывод: `c2-malware.example.com` — явно подозрительное имя.

```bash
# VirusTotal репутация
curl -s "https://www.virustotal.com/api/v3/ip_addresses/203.0.113.77" \
  -H "x-apikey: <ключ>" | jq '.data.attributes.last_analysis_stats'
```
Вывод:
```json
{ "malicious": 72, "suspicious": 8, "harmless": 2, "undetected": 13 }
```
72 антивируса определили IP как вредоносный.

```bash
# AbuseIPDB (через API)
curl -s -G "https://api.abuseipdb.com/api/v2/check" \
  --data-urlencode "ipAddress=203.0.113.77" \
  -H "Key: <ключ>" | jq '.data.abuseConfidenceScore'
```
Вывод: `98` — высокая степень уверенности в зловредности.

**Шаг 4: Интерпретация и принятие решения**
Собранные данные сопоставляются: критичный внутренний сервер обратился на IP, классифицированный 72 антивирусами как вредоносный, с подозрительным PTR-именем «c2-malware». Плейбук в такой ситуации однозначно предписывает немедленную эскалацию на L2 для изоляции хоста и начала расследования.

Аналитик документирует итог в тикет-системе:
```text
Enrichment Summary:
- Source: SRV-FINANCE-02 (critical)
- Destination: 203.0.113.77 (c2-malware.example.com, VT 72/90 malicious)
- Decision: Escalate to L2 per playbook rule PN-03.
```

**Ожидаемый вывод примера:** Демонстрируется, как целенаправленное обогащение на начальном этапе плейбука L1 превращает сырое событие в инцидент с чёткими признаками компрометации и позволяет быстро активировать процедуру реагирования, избегая задержек на рутинный поиск информации в разных системах.
