# Объекты ядра: процессы, потоки, дескрипторы — что видит аналитик

## Процессы: контейнер ресурсов и точка входа в анализ

Процесс в Windows — это изолированная среда выполнения, предоставляющая потокам код, приватное виртуальное адресное пространство и таблицу открытых дескрипторов. С точки зрения SOC-аналитика именно процесс является первой сущностью, на которую обращают внимание при беглом осмотре системы, поскольку вредоносная активность почти всегда привязана к конкретному адресному пространству и образу исполняемого файла. В официальной документации Microsoft объект «процесс» относится к категории объектов ядра (kernel objects), управляемых менеджером объектов и диспетчером процессов/потоков [Managing Kernel Objects](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/managing-kernel-objects).

Ключевое разграничение, необходимое аналитику: программа — это статичный файл на диске, тогда как процесс — динамическая сущность, созданная ядром на основе этого файла (или даже без файла, как в случае Pico-процессов и минимальных процессов) [A deep dive into Processes, Threads, Fibers and Jobs on Windows](https://de-engineer.github.io/Processes-threads-jobs-fibers). Процесс характеризуется уникальным идентификатором (PID), маркером доступа (access token), списком потоков, контекстом безопасности, переменными окружения и загруженными модулями. В отличие от потока, процесс не исполняется сам по себе — он лишь предоставляет ресурсы потокам, которые и выполняют код.

Ниже приведена сравнительная таблица, фиксирующая различия между процессом и часто смешиваемыми с ним сущностями.

| Сущность          | Определение                                                                 | Видимость для аналитика (артефакты)                                         | Характерный идентификатор          |
|-------------------|----------------------------------------------------------------------------|------------------------------------------------------------------------------|------------------------------------|
| Программа         | Файл (PE/EXE, DLL) на носителе                                           | Цифровая подпись, хэш, путь, метаданные                                     | Имя файла, SHA256                  |
| Процесс           | Контейнер потоков и ресурсов, созданный на основе программы или пустой    | PID, командная строка, родительский PID, время запуска, дерево процессов    | PID (Process ID)                   |
| Поток (thread)    | Исполняемая единица внутри процесса, планируемая ядром                    | TID, стартовый адрес, приоритет, состояние, время ЦП                        | TID (Thread ID)                    |
| Задание (job)     | Группа процессов, управляемая как единое целое (лимиты, изоляция)         | Имя задания, ограничения памяти/ЦП, список входящих процессов               | Дескриптор или имя объекта Job     |

Процесс в Windows представлен структурой EPROCESS в пространстве ядра и PEB (Process Environment Block) в пользовательском пространстве. Для аналитика прямой доступ к EPROCESS возможен только через отладчик ядра или дамп памяти, но важнейшие производные атрибуты доступны через стандартные инструменты:

- **PID и родительский PID** — основа построения дерева процессов.
- **Путь к образу (Image Path)** — позволяет проверить расположение исполняемого файла (например, `C:\Windows\System32\` против `C:\Users\*\AppData\Local\Temp\`).
- **Командная строка** — раскрывает параметры запуска, внедрённые скрипты, иногда пароли в открытом виде.
- **Маркер доступа** — определяет, от имени какого пользователя выполняется процесс, его привилегии (SeDebugPrivilege, SeImpersonatePrivilege и т.д.) и членство в группах.
- **Время запуска** — помогает коррелировать активность с логами.
- **Счётчики дескрипторов, потоков, операций ввода-вывода** — косвенные индикаторы поведения.

Знание этих полей помогает быстро оценить легитимность процесса. Например, `svchost.exe`, запущенный не из System32, не от имени SYSTEM, без параметра `-k`, с родителем, отличным от `services.exe`, – типичный признак маскировки.

Для получения перечисленных атрибутов аналитик обычно прибегает к комбинации встроенных средств Windows и специализированных утилит. Команда ниже демонстрирует получение расширенной информации о процессе, включая интересующие SOC-аналитика поля:

```powershell
Get-Process -Id 1234 |
    Select-Object Id, ProcessName, Path, StartTime,
                  @{N='ParentPID';E={(Get-CimInstance Win32_Process -Filter "ProcessId=$($_.Id)").ParentProcessId}},
                  @{N='Owner';E={ (Get-CimInstance Win32_Process -Filter "ProcessId=$($_.Id)").GetOwner().User } },
                  HandleCount, ThreadCount, WorkingSet64 |
    Format-List
```

Пример ожидаемого вывода (иллюстративная схема):

```
Id            : 1234
ProcessName   : suspicious
Path          : C:\Users\jdoe\AppData\Local\Temp\payload.exe
StartTime     : 25.05.2025 8:43:12
ParentPID     : 5678
Owner         : CORP\jdoe
HandleCount   : 148
ThreadCount   : 5
WorkingSet64  : 28311552
```

Дерево процессов, выводимое утилитой Process Explorer или командой `Get-CimInstance Win32_Process | Select-Object ProcessId, ParentProcessId, Name`, даёт контекст цепочки запуска. Вредоносные программы часто порождают дочерние процессы для инжектирования или обхода контроля учётных записей (UAC). Аналитик должен сопоставлять родительский процесс с ожидаемым поведением: например, `winword.exe` не должен запускать `cmd.exe /c powershell ...` в нормальных условиях.

Таким образом, процесс как объект ядра не только инкапсулирует исполняемый код и ресурсы, но и предоставляет поверхность наблюдения, которая в руках аналитика становится первичным индикатором компрометации.

## Потоки: двигатели выполнения и тени вредоносного кода

Если процесс – это «дом», то потоки – «жильцы», выполняющие инструкции. Поток в Windows является планируемой ядром единицей выполнения, обладающей собственным набором регистров, стека (пользовательского и ядерного) и контекста безопасности. Все потоки одного процесса разделяют его виртуальное адресное пространство, таблицу дескрипторов и другие ресурсы [Windows Kernel-Mode Process and Thread Manager](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/windows-kernel-mode-process-and-thread-manager).

С точки зрения ядра любой поток представлен структурой ETHREAD, содержащей в том числе ссылку на родительский процесс (EPROCESS), идентификатор потока (TID), текущий приоритет, состояние (Ready, Running, Waiting), контекст выполнения (регистры процессора) и счётчики времени. Именно на TID аналитики ориентируются при изучении вкладки «Threads» в Process Explorer или при разборе дампов памяти.

Критически важно различать три уровня абстракций, фигурирующих в литературе: потоки ядра (kernel threads), пользовательские потоки (реализованные библиотекой) и файберы (fibers). В контексте Windows все потоки, видимые планировщику, являются ядерными; даже потоки, созданные через Win32 API `CreateThread`, реализуются как kernel threads. Понятие «пользовательские потоки» (как, например, в старых реализациях POSIX) в Windows не применимо на уровне ОС. Однако существуют файберы – легковесные блоки исполнения, планируемые вручную внутри одного потока, без участия ядра. Для аналитика файберы прозрачны: они не видны в стандартных средствах мониторинга потоков, пока не используется специальная отладка. Вредоносное ПО редко использует файберы для скрытия активности, но отдельные APT-группы применяли их для обхода хуков антивирусов.

Сравнительная таблица ниже сопоставляет основные характеристики потока и процесса, а также добавляет файберы для полноты.

| Характеристика               | Процесс                                           | Поток (kernel thread)                            | Файбер (fiber)                                  |
|------------------------------|---------------------------------------------------|--------------------------------------------------|-------------------------------------------------|
| Изоляция адресного пространства | Собственное виртуальное адресное пространство    | Разделяет адресное пространство процесса         | Разделяет адресное пространство потока          |
| Участие планировщика ядра    | Нет (планируются потоки)                          | Да, ядро переключает потоки                      | Нет, планируется вручную в коде потока          |
| Ресурсы операционной системы | Выделяются процессу (квоты памяти, таблицы)       | Использует ресурсы процесса, собственный стек    | Собственный стек, минимальные структуры         |
| Видимость в Process Explorer | Отдельная строка                                  | Вкладка «Threads» с TID и стартовым адресом       | Не видны (видны только как часть содержащего потока) |
| Идентификатор                | PID                                               | TID (Thread ID)                                   | Отсутствует общесистемный ID                    |

Для SOC-аналитика наибольшее значение имеют TID, стартовый адрес потока и его состояние. Стартовый адрес – это виртуальный адрес в памяти процесса, с которого поток начинает выполнение после создания. Этот адрес, отображаемый в Process Explorer, обычно указывает на легитимную функцию модуля (например, `ntdll.dll!RtlUserThreadStart`). Если стартовый адрес указывает на область памяти, не принадлежащую загруженному модулю (регион типа Private, размеченный через `VirtualAlloc`), или на динамически выделенный участок, это веский признак внедрения кода (code injection). Вредоносное ПО, инжектирующее шелл-код в удалённый процесс, создаёт удалённый поток со стартовым адресом, указывающим на выделенную память, часто с правами исполнения.

Следующая команда PowerShell перечисляет потоки конкретного процесса и отображает их идентификаторы и стартовые адреса (при наличии прав на чтение памяти процесса):

```powershell
$proc = [System.Diagnostics.Process]::GetProcessById(1234)
$proc.Threads | Select-Object Id,
    @{N='StartAddress';E={$_.StartAddress.ToString('X')}},
    @{N='ThreadState';E={$_.ThreadState}},
    TotalProcessorTime
```

Пример вывода (иллюстративная схема):

```
 Id StartAddress       ThreadState TotalProcessorTime
 -- ------------       ----------- ------------------
124 00007FF8A3C5D120   Wait        00:00:02.5000000
456 000001F0008A1000   Running     00:00:10.1250000
789 00007FF8A3C5D120   Wait        00:00:01.0000000
```

Если бы адрес `000001F0008A1000` не соответствовал базе ни одного загруженного модуля (проверяется через список DLL в Process Explorer вкладкой «Image» или командой `Get-Process -Id 1234 | Select-Object -ExpandProperty Modules`), это немедленно вызвало бы подозрение. Дополнительные индикаторы: поток находится в состоянии «Wait:UserRequest» с высоким временем процессора при отсутствии оконного интерфейса; большое количество потоков в процессе, который обычно однопоточный.

Планировщик потоков Windows использует приоритетную вытесняющую многозадачность с квантованием времени. Приоритеты потоков варьируются от 0 до 31; динамические приоритеты (класс 1–15) могут временно повышаться для решения проблем инверсии приоритетов. Подозрительные процессы могут поднимать приоритет своих потоков до высоких значений (например, `Realtime`), чтобы перехватывать больше процессорного времени. При анализе в Process Explorer колонка «Base Priority» и «Dynamic Priority» дают эту информацию.

Таким образом, изучение потоков позволяет аналитику выявить аномальные паттерны исполнения, даже если родительский процесс на первый взгляд кажется легитимным. Потоки — это динамическая «пульсирующая» часть системы, и аномалии в их атрибутах зачастую являются ранними признаками компрометации.

## Дескрипторы: ключи к объектам ядра и карта скрытых взаимодействий

Дескриптор (handle) в Windows – это непрозрачная ссылка, используемая пользовательским режимом для доступа к объектам ядра. Создание или открытие объекта (файла, процесса, ключа реестра, семафора) возвращает приложению целочисленный индекс, который действителен только в контексте процесса, создавшего дескриптор. Этот индекс ссылается на запись в таблице дескрипторов процесса (handle table), которая в свою очередь содержит указатель на тело объекта ядра в системной памяти и битовую маску предоставленных прав доступа [Give Me a Handle, and I'll Show You an Object](https://www.labri.fr/perso/betrema/winnt/handles1.html). Для аналитика таблица дескрипторов – это карта всех ресурсов, к которым процесс получил доступ: от открытых файлов до других процессов.

Таблица дескрипторов управляется менеджером объектов (Object Manager) и представляет собой иерархическую структуру с уровнями для масштабирования (одно-, двух-, трёхуровневая). Каждая запись содержит, помимо указателя на объект, набор флагов (наследование, и т.п.) и маску прав доступа, которая была запрошена при открытии объекта. Это означает, что один и тот же объект может быть открыт разными процессами через разные дескрипторы с разными правами. При попытке использовать дескриптор с операцией, не разрешённой сохранённой маской, система возвращает ошибку «access denied», даже если субъект имел бы достаточно прав при новом открытии.

Основные категории объектов ядра, доступных через дескрипторы, и их значение для расследования приведены в таблице.

| Тип объекта       | Пример имени (при наличии)       | Типичные права доступа                              | Значение для аналитика                                          |
|-------------------|----------------------------------|-----------------------------------------------------|-----------------------------------------------------------------|
| Process           | \System\Process\1234           | PROCESS_VM_READ, PROCESS_QUERY_INFORMATION, PROCESS_TERMINATE | Обнаружение межпроцессного взаимодействия, инжектирования       |
| Thread            | (обычно без имени)              | THREAD_SET_CONTEXT, THREAD_SUSPEND_RESUME           | Индикатор управления чужими потоками (например, удалённый shellcode) |
| File              | \Device\HarddiskVolume3\...\mal.exe | FILE_READ_DATA, FILE_WRITE_DATA, DELETE           | Доступ к файлам на диске, особенно скрытым или в нестандартных расположениях |
| Key (Registry)    | \Registry\Machine\Software\...  | KEY_READ, KEY_WRITE, KEY_SET_VALUE                  | Отслеживание изменений реестра (persistence)                    |
| Token             | \Security\Token\...             | TOKEN_DUPLICATE, TOKEN_IMPERSONATE                  | Эскалация привилегий через манипуляции токенами                 |
| Section           | \BaseNamedObjects\...           | SECTION_MAP_READ, SECTION_MAP_WRITE                 | Разделяемая память между процессами (обмен данными)             |
| Mutant (Mutex)    | \BaseNamedObjects\MyMutex       | MUTANT_QUERY_STATE                                  | Синхронизация; вредоносы используют для предотвращения повторного запуска |
| Event             | \BaseNamedObjects\MyEvent       | EVENT_MODIFY_STATE, SYNCHRONIZE                     | Сигнализация событий, может использоваться в многокомпонентных угрозах |

Инструмент `handle.exe` из набора Sysinternals (или вкладка «Handles» в Process Explorer) позволяет перечислить все открытые дескрипторы процесса. Аналитик должен искать необычные сочетания: например, офисное приложение, удерживающее дескриптор процесса `lsass.exe` с правами `PROCESS_VM_READ`, что характерно для атак дампа учётных данных. Или процесс, открывший дескриптор к файлу в каталоге другого пользователя, когда такому приложению нет причин для межпрофильного доступа.

Пример команды для перехвата всех дескрипторов процесса с PID 1234 (иллюстративная схема; точный вывод зависит от среды):

```bash
C:\Tools\SysinternalsSuite> handle.exe -p 1234 -a
```

Пример вывода (сокращён):

```
Handle v5.0
Copyright (C) 1997-2025 Mark Russinovich
Sysinternals - www.sysinternals.com

------------------------------------------------------------------------------
suspicious.exe pid: 1234 CORP\jdoe
  48: File          C:\Users\jdoe\AppData\Local\Temp\config.ini
  4C: Key           HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
  54: Process        lsass.exe (PID: 660)
  78: Token         CORP\jdoe:impersonation (Level: Anonymous)
```

Здесь мы немедленно видим: процесс «suspicious» открывает ключ реестра `Run` (вероятно, для закрепления), удерживает дескриптор процесса `lsass.exe` и содержит impersonation-токен. Такая комбинация очень подозрительна.

Важно понимать, что закрытие дескриптора не уничтожает объект ядра; объект существует до тех пор, пока на него ссылается хотя бы один дескриптор или пока ядро явно не освободит его. Менеджер объектов ведёт счётчик ссылок. Аналитику это объясняет, почему вредоносный процесс может открыть дескриптор на файл и удалить сам файл с диска, но продолжать работать с ним, пока дескриптор открыт.

Для SOC L1 дескрипторы – это не просто счётчик, а мощное средство обнаружения скрытых взаимодействий. Совместное использование дескрипторов несколькими процессами (например, через наследование при создании или через `DuplicateHandle`) может создавать сложные графы доверия, которые трудно отследить без автоматизированных средств вроде EDR. Тем не менее базовое ручное исследование таблицы дескрипторов часто даёт достаточно улик для эскалации инцидента.

## Аналитическое видение: от процессов к инциденту

Разрозненные знания об объектах ядра складываются в целостную картину, когда аналитик SOC накладывает их на модель угроз. Процессы, потоки и дескрипторы — не изолированные сущности, а взаимосвязанные элементы, изменения в которых служат индикаторами компрометации (Indicators of Compromise, IoC). Этот раздел обобщает, как выглядят подозрительные артефакты в трёх рассмотренных слоях, и предлагает типовые запросы, которые аналитик уровня L1 может выполнить для быстрой триажи.

Сначала систематизируем типовые индикаторы, сгруппированные по слоям.

| Слой                      | Индикатор                                                                                   | Объяснение                                                                                               |
|---------------------------|---------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| **Процесс**               | Процесс с именем системного (`svchost.exe`, `lsass.exe`), расположенный не в `System32`     | Маскировка под легитимный процесс, часто используется для обхода поверхностного мониторинга              |
|                           | Процесс, запущенный из временной папки (`%TEMP%`, `%PUBLIC%`)                               | Большинство легитимных приложений не устанавливаются во временные каталоги                               |
|                           | Процесс без цифровой подписи или с недействительной подписью                                | Признак непроверенного ПО; особенно подозрительно у образов в системных каталогах                        |
|                           | Родительский процесс не соответствует ожидаемому (например, `winword.exe` → `cmd.exe`)     | Возможна эксплуатация офисного документа или запуск скрипта через COM                                   |
|                           | Аномально высокий Private Working Set при отсутствии GUI                                   | Признак memory-only вредоносного ПО или майнера                                                          |
| **Поток**                 | Стартовый адрес потока вне загруженных модулей                                              | Классический признак внедрения кода (shellcode injection)                                                |
|                           | Поток с приоритетом Realtime (31) у процесса без UI                                        | Попытка захватить процессорное время; может свидетельствовать о майнинге или DoS-условиях                |
|                           | Большое количество потоков (>100) у простого приложения                                    | Нетипичное поведение, возможна попытка порождения множества рабочих потоков для обхода ограничений       |
| **Дескриптор**            | Дескриптор процесса `lsass.exe`, `csrss.exe` с правами VM_READ или VM_WRITE              | Подготовка к дампу учётных данных (Mimikatz-подобное поведение)                                           |
|                           | Открытые дескрипторы ключей реестра Run/RunOnce в несистемном процессе                    | Закрепление в автозагрузке                                                                                |
|                           | Дескриптор файла, недавно удалённого с диска (при проверке с `-a`)                         | Возможное уклонение от файловых сканеров                                                                 |
|                           | Дескриптор токена с уровнем Impersonation или Anonymous в процессе, не являющемся сервисом  | Эскалация или перехват контекста безопасности                                                             |

При первичном осмотре рабочей станции аналитик часто начинает с простых командлетов PowerShell, позволяющих отфильтровать подозрительные процессы по комбинации признаков. Пример ниже выводит процессы, запущенные не из системных каталогов и не имеющие цифровой подписи, с указанием родительского процесса:

```powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.ExecutablePath -and
                   $_.ExecutablePath -notmatch 'C:\\Windows\\System32|C:\\Program Files' } |
    Select-Object ProcessId, Name, ExecutablePath, ParentProcessId,
                  @{N='Owner';E={(Invoke-CimMethod -InputObject $_ -MethodName GetOwner).User}} |
    Format-Table -AutoSize
```

Вывод покажет все процессы за пределами доверенных каталогов. Для уточнения аналитик вручную проверяет подпись каждого образа через свойства файла или командлет `Get-AuthenticodeSignature`.

Что касается потоков, ручная проверка каждого процесса неэффективна, но сигнатурный модуль EDR может отслеживать создание удалённых потоков (событие Sysmon Event ID 8) и записывать стартовый адрес. Не имея EDR, аналитик загружает дамп памяти подозрительного процесса и анализирует его в Volatility или MemProcFS. На уровне L1 обычно достаточно зафиксировать факт подозрительных потоков в Process Explorer и эскалировать инцидент.

Для дескрипторов командная оболочка `handle.exe` с ключом `-a` по всем процессам может выявить опасные комбинации. Массовую проверку можно автоматизировать скриптом, который запускает `handle.exe -a -u` (показать дескрипторы объектов с именами) и парсит вывод в поисках `lsass.exe` или `csrss.exe` с правами `0x...` (побитовая маска). Пример фрагмента вывода такого массового поиска:

```bash
C:\Tools> handle.exe -a -u | findstr /i "lsass.exe"
  54: Process        lsass.exe (PID: 660)   pid: 1234  suspicious.exe
  A0: Process        lsass.exe (PID: 660)   pid: 5678  unknown.exe
```

В совокупности артефакты процессов, потоков и дескрипторов образуют улики для построения timeline атаки. Например, процесс `invoice.doc.exe` запускается из временного каталога, порождает `cmd.exe`, после чего в `cmd.exe` появляется дескриптор `lsass.exe` — это классическая картина фишинговой атаки с дампом паролей. Понимание внутренних механизмов объектов ядра позволяет аналитику не просто фиксировать аномалии, но и объяснять их природу, что критично для составления отчёта и рекомендаций.

## Сквозной практический пример: анализ заражённой рабочей станции

**Исходные условия.** SOC получил алерт от системы мониторинга о подозрительном поведении на узле `WKSTN-CORP-25`. Пользователь `corp\jdoe` сообщил о медленной работе системы. Аналитик имеет доступ к станции через консоль с правами локального администратора и набор Sysinternals Suite. Задача: определить, присутствует ли вредоносная активность, и собрать улики.

**Шаг 1. Выявление подозрительного процесса по PID и образу.** Открываем Process Explorer или выполняем команду PowerShell для поиска процессов с высоким потреблением ЦП, не из системных папок.

```powershell
Get-Process | Where-Object {$_.CPU -gt 30} |
    Select-Object Id, Name, Path, CPU, StartTime
```

Вывод (пример):

```
 Id Name          Path                                        CPU      StartTime
 -- ----          ----                                        ---      ---------
 8452 update      C:\Users\Public\update\update.exe           95.4     25.05.2025 9:15:00
```

Обнаружен `update.exe` в публичной папке с аномально высокой нагрузкой ЦП. PID 8452. Проверяем родительский процесс:

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId=8452" | Select-Object ParentProcessId
```

Вывод:

```
ParentProcessId
---------------
           1234
```

Родительский PID 1234 – это, допустим, `cmd.exe`, запущенный из временной папки. Признак компрометации.

**Шаг 2. Проверка цифровой подписи.** Через свойства файла или PowerShell:

```powershell
Get-AuthenticodeSignature -FilePath "C:\Users\Public\update\update.exe"
```

Вывод:

```
SignerCertificate    Status      StatusMessage
-----------------    ------      -------------
                     NotSigned   The file is not digitally signed.
```

Файл не подписан, что нетипично для легитимного обновления.

**Шаг 3. Анализ потоков процесса.** Открываем Process Explorer, дважды кликаем на `update.exe`, переходим на вкладку «Threads». Видим несколько потоков:

```text
TID   CPU Cycles     Start Address
452   125,000,000    update.exe+0x12a4
1240  98,000,000    0x001F0000 (Private memory, no module)
1896  5,000,000     ntdll.dll!RtlUserThreadStart+0x21
```

Второй поток со стартовым адресом `0x001F0000`, который не принадлежит загруженным модулям (проверяем в «Image» – там только update.exe и системные DLL), явный признак внедрения шелл-кода в собственный процесс. Примечание: в выводе Process Explorer адрес может отображаться как «<no module>».

**Шаг 4. Анализ дескрипторов процесса.** Используем `handle.exe` для PID 8452:

```bash
C:\Tools\SysinternalsSuite> handle.exe -p 8452 -a
```

Пример фрагмента вывода:

```
update.exe pid: 8452 CORP\jdoe
  10: File          C:\Users\Public\update\update.exe
  14: Key           HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
  18: Process        lsass.exe (PID: 660)
  1C: Token         NT AUTHORITY\SYSTEM (Impersonation)
  20: Section       \BaseNamedObjects\_PEB_8452_shared
```

Обнаружены:
- Дескриптор ключа `Run` – попытка закрепиться в автозагрузке.
- Дескриптор `lsass.exe` – вероятно, для дампа учётных данных (хотя права не показаны в выводе, стандартно `PROCESS_VM_READ` требует подозрительного дескриптора).
- Имперсонирующийся токен SYSTEM – признак повышения привилегий.

**Шаг 5. Проверка сетевых соединений.** Выполняем `netstat -ano -p TCP` и фильтруем по PID 8452:

```bash
netstat -ano -p TCP | findstr "8452"
```

Вывод:

```
TCP    192.168.1.25:49876    10.2.3.4:443        ESTABLISHED     8452
TCP    192.168.1.25:49877    5.5.5.5:8080         ESTABLISHED     8452
```

Установлено соединение на `5.5.5.5:8080` – известный вредоносный C2-сервер по данным Threat Intelligence. Подтверждение зловредной активности.

**Ожидаемый вывод примера.** Комбинация артефактов – неподписанный процесс из публичной папки, шелл-код в потоке, дескриптор `lsass.exe` и автозагрузочный ключ реестра, сетевое подключение к C2 – позволяет классифицировать `update.exe` как троян-стилер. Аналитик фиксирует IoC (PID 8452, файл, IP-адрес C2, пути реестра) и эскалирует инцидент по процедуре IR.
