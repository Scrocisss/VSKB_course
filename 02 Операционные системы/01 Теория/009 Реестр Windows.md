# Реестр Windows

## 1. Реестр как центральная конфигурационная база Windows: роль, понятия и границы

Реестр Windows — это иерархическая база данных, в которой хранятся настройки операционной системы, приложений, аппаратных компонентов и пользовательских профилей. Он заменил разрозненные текстовые .ini‑файлы эпохи Windows 3.x и MS-DOS (autoexec.bat, config.sys) и превратился в единый источник конфигурационной истины для всей платформы. Определение из Microsoft Computer Dictionary пятого издания характеризует его как центральную иерархическую базу данных, используемую в Windows 98, Windows CE, Windows NT и Windows 2000 для хранения информации, необходимой для настройки системы в отношении одного или нескольких пользователей, приложений и аппаратных устройств. В современных версиях Windows 10 и 11 реестр остаётся критически важным компонентом, управляющим загрузкой, поведением драйверов, политиками безопасности, ассоциациями файлов и многим другим.

Понятийный аппарат реестра включает несколько уровней абстракции, и путаница между ними способна привести к неверной интерпретации артефактов при расследовании. Базовыми логическими единицами выступают корневые **ветви** (root keys), фактически являющиеся предопределёнными дескрипторами Win32 API. Они имеют постоянные числовые значения и общепринятые сокращённые обозначения. Эти ветви не являются хранилищами данных непосредственно, а служат точками монтирования для **кустов** (hives) — бинарных файлов, лежащих на диске. Куст реестра — это логическая группа ключей, подразделов и параметров вместе с набором вспомогательных файлов, обеспечивающих целостность и возможность восстановления. Таким образом, когда мы говорим о HKEY_LOCAL_MACHINE\SYSTEM, мы обращаемся к кусту SYSTEM, хранящемуся в `%SystemRoot%\System32\Config\SYSTEM` (в Windows NT и выше).

Внутри куста данные организованы в виде дерева: каждый узел называется **ключом** (key). Ключ может содержать вложенные ключи — подразделы (subkeys), а также **параметры** (values). Параметр состоит из имени, типа данных и самого значения. Реестр не накладывает ограничений на глубину вложенности, однако практический максимум составляет 512 уровней. Имена ключей регистронезависимы и не могут содержать символ обратной косой черты, а имена параметров и их данные — могут. Наличие ключа без параметров уже может нести информацию для приложения или службы.

Особое место в SOC-аналитике занимает разделение на общесистемные и пользовательские настройки. HKEY_LOCAL_MACHINE (HKLM) содержит конфигурацию, единую для всех пользователей компьютера: установленное ПО, драйверы, параметры загрузки, политики безопасности. Ветви HKEY_USERS (HKU) хранят профили всех зарегистрированных пользователей, идентифицируя их по SID. HKEY_CURRENT_USER (HKCU) — это просто символическая ссылка на подраздел HKU с SID текущего вошедшего пользователя, что позволяет приложениям всегда обращаться к настройкам интерактивного пользователя. Ветвь HKEY_CLASSES_ROOT (HKCR) объединяет глобальные ассоциации файловых типов и COM-объектов из HKLM\Software\Classes и пользовательские переопределения из HKCU\Software\Classes, предоставляя единое представление. HKEY_CURRENT_CONFIG (HKCC) отражает текущий аппаратный профиль, являясь подмножеством куста SYSTEM, а HKEY_DYN_DATA, присутствовавшая в Windows 9x, ныне не используется.

Для аналитика SOC критически важно различать, на каком уровне (машинном или пользовательском) проводилось изменение, поскольку это напрямую влияет на масштаб скомпрометированности и требуемые привилегии атакующего. Следующая таблица фиксирует ключевые разграничения и привязку логических ветвей к физическим файлам.

| Корневой ключ (сокр.) | Основные файловые кусты | Хранит / Роль |
|---|---|---|
| HKEY_LOCAL_MACHINE\SAM | C:\Windows\System32\Config\SAM, SAM.log*, SAM.sav | База данных SAM, хэши паролей локальных учётных записей |
| HKEY_LOCAL_MACHINE\Security | C:\Windows\System32\Config\SECURITY, SECURITY.log*, SECURITY.sav | Политики безопасности, права, аудит |
| HKEY_LOCAL_MACHINE\Software | C:\Windows\System32\Config\SOFTWARE, SOFTWARE.log*, SOFTWARE.sav | Глобальные параметры приложений, лицензирование, COM‑регистрация |
| HKEY_LOCAL_MACHINE\System | C:\Windows\System32\Config\SYSTEM, SYSTEM.alt, SYSTEM.log*, SYSTEM.sav | Конфигурация оборудования, критические драйверы, параметры загрузки, перечень служб |
| HKEY_USERS\.DEFAULT | C:\Windows\System32\Config\DEFAULT, DEFAULT.log*, DEFAULT.sav | Шаблон профиля для всех новых пользователей |
| HKEY_CURRENT_USER | C:\Users\<username>\NTUSER.DAT, NTUSER.DAT.LOG*; C:\Users\<username>\AppData\Local\Microsoft\Windows\UsrClass.dat | Настройки интерактивного пользователя: персонализация, ассоциации, автозагрузка |
| HKEY_CURRENT_CONFIG | Часть куста SYSTEM | Аппаратный профиль, используемый при текущей сессии |
| HKEY_CLASSES_ROOT | Логическое объединение HKLM\Software\Classes и HKCU\Software\Classes | Ассоциации расширений, COM-серверы, контекстное меню |

* Примечание: транзакционные журналы (.LOG1, .LOG2 в Windows 10/11) могут иметь иное расширение в зависимости от версии и состояния флаша.

Эта таблица даёт базовую карту для навигации по реестру и понимания, где искать следы воздействия. Далее мы рассмотрим внутреннее устройство кустов более детально — ведь именно оно объясняет, почему одни ключи могут «исчезнуть» из живого реестра, но оставить следы в журналах.

## 2. Архитектура реестра: кусты, журналы, типы данных и защита

Куст реестра — это не просто файл, а структурированное бинарное хранилище. На диске оно представлено файлом с базовой сигнатурой `regf` (первые 4 байта заголовка) и набором блоков (bins) фиксированного размера (обычно 4096 байт), внутри которых размещаются ячейки (cells), содержащие ключи, параметры, дескрипторы безопасности и списки подразделов. Для линейного аналитика SOC знание точной бинарной структуры избыточно, однако понимание того, что куст — это транзакционная база данных, принципиально для корректной интерпретации удалённых артефактов.

Операционная система не пишет изменения напрямую в основной файл куста. Вместо этого используется механизм транзакционных журналов. В классической модели (Windows NT — Windows 7) применялся один основной файл и один или два журнальных файла (часто .LOG и .LOG1). В современных Windows 10/11, где внедрена многоуровневая архитектура реестра (layered keys), каждый куст может сопровождаться файлами .LOG1 и .LOG2, а также файлами резервных копий .sav. Когда процесс вызывает RegSetValueEx, ядро записывает модификацию в журнальный файл, после чего периодически (например, при выгрузке куста или по таймеру) выполняется сброс (flush) изменений в основной файл. Журналы не являются историческим логом всех операций, они служат лишь гарантией согласованности данных на случай сбоя питания или краха системы.

Для форензической экспертизы это имеет прямое следствие: ключ, который был создан и затем удалён злоумышленником непосредственно перед выключением или дампом памяти, может полностью отсутствовать в активном представлении реестра (если удаление успело попасть в основной файл), но всё ещё находится в журнальных файлах. Анализ с помощью утилит, умеющих парсить .LOG1/.LOG2 параллельно с основным кустом (например, реконструкция состояния с учётом всех несохранённых транзакций), иногда позволяет восстановить удалённые данные. Однако это вероятностный процесс, и успех зависит от версии ОС, интенсивности операций с кустом и времени, прошедшего с момента удаления.

Ниже представлена упрощённая ASCII-схема взаимодействия компонентов:

```text
[Пользовательский процесс] ──(RegSetValueEx)──▶ [Диспетчер конфигурации (CM)]
                                              │
                                              ▼
                                    [Журнал транзакций (.LOG1/.LOG2)]
                                              │
                                    (периодический flush)
                                              │
                                              ▼
                                    [Основной файл куста (NTUSER.DAT, SYSTEM, ...)]
                                              │
                                              ▼
                                    [Загруженный куст в дереве реестра]
```

Помимо транзакционных журналов, существенной информационной частью являются **резервные копии**, автоматически создаваемые в `C:\Windows\System32\Config\RegBack` (до Windows 10 версии 1803 этот механизм был активен по умолчанию; начиная с Windows 10 1803 плановое резервирование отключено, но может быть включено вручную). Даже при отсутствии RegBack-копий на исследуемом образе аналитик может попытаться извлечь старые версии кустов из теневых копий (VSS).

Теперь рассмотрим, что именно хранится внутри ключей в виде параметров. Каждый параметр имеет три атрибута: имя, тип данных и само значение. Тип данных задаёт интерпретацию бинарных данных. Основные типы, которые встретятся аналитику SOC:

```text
| Тип              | Код | Формат                                                     | Пример использования                   |
| ---------------- | --- | ---------------------------------------------------------- | -------------------------------------- |
| REG_NONE         | 0   | Нет значения или неопределённый тип                        | Редко, обёртка                         |
| REG_SZ           | 1   | Строка фиксированной длины в UTF-16LE с завершающим нулём  | Пути, имена, описания                  |
| REG_EXPAND_SZ    | 2   | Строка с подстановкой переменных окружения (%SystemRoot%)  | Пути, зависящие от системы             |
| REG_BINARY       | 3   | Произвольные бинарные данные                               | Закодированные настройки, ключи шифрования |
| REG_DWORD        | 4   | 32-битное целое (little-endian)                            | Флаги, тайм-ауты, счетчики             |
| REG_MULTI_SZ     | 7   | Массив строк, каждая оканчивается нулём, двойной нуль в конце | Списки зависимостей, мультизначения   |
| REG_QWORD        | 11  | 64-битное целое (little-endian)                            | Большие целые, тайм-ауты в 64-битных системах |
```

Эта классификация не исчерпывающая (существуют ещё REG_LINK, REG_RESOURCE_LIST и др.), но охватывает 99 % параметров, используемых приложениями и ОС. Знание типов помогает корректно интерпретировать значения: например, REG_DWORD в little-endian формате при ручном просмотре в hex редакторе будет выглядеть «перевёрнутым» (младший байт первым).

Для обеспечения безопасности каждая ветвь и каждый ключ могут иметь дескриптор безопасности (Security Descriptor) с собственным списком управления доступом (DACL). Разрешения реестра наследуются от родительских ключей по стандартным правилам Windows. Стандартный пользователь имеет право на запись в ветвь HKEY_CURRENT_USER, но не может по умолчанию модифицировать ветви HKLM, что порождает два класса техник злоумышленников: персистентность на уровне пользователя (доступна без прав администратора) и на уровне системы (требует повышения привилегий). При расследовании полезно проверять права на ключ, чтобы понять, насколько просто атакующий мог осуществить изменение.

Дополнительный аспект, важный для SOC L1: начиная с Windows Vista, были введены так называемые **Application Hives** (App Hives), которые позволили непривилегированным процессам загружать собственные кусты в реестр через вызов kernel‑функций, ранее доступных только системным службам. Это расширило поверхность атаки: как отмечается в исследовании Project Zero, около 30 % серьёзных уязвимостей требовали или значительно упрощались именно загрузкой контролируемого куста как App Hive. Аналитик должен помнить, что аномальная загрузка куста из нетипичного пути (например, `C:\Users\<user>\AppData\Local\Temp\malicious.dat`) может быть индикатором попытки эксплуатации.

Таким образом, внутреннее устройство реестра определяет как его надёжность, так и возможности для форензического восстановления. Перейдём к тому, как эти знания применяются в повседневной практике специалиста SOC.

## 3. Реестр в работе аналитика SOC: мониторинг, сбор артефактов и детектирование угроз

Для специалиста службы SOC L1 реестр — это, прежде всего, источник высококачественных индикаторов компрометации и артефактов персистентности. Работа с ним делится на два основных режима: исследование **живой системы** (как правило, удалённо) и **оффлайн‑анализ** образов дисков или памяти. В первом случае используются штатные утилиты `reg.exe`, PowerShell и оснастки `regedit.exe`; во втором — специализированные форензические инструменты, способные разбирать бинарные кусты без загрузки в работающую ОС.

Перед началом анализа кусты необходимо изъять. На работающей системе копирование файлов `%SystemRoot%\System32\Config\*` и `NTUSER.DAT` стандартными средствами проводника невозможно из‑за блокировки ядром. Для преодоления этого применяются три группы инструментов:

- **Агенты реагирования**: KAPE (Kroll Artifact Parser and Extractor) позволяет рекурсивно скопировать кусты с теневых копий или обойти блокировку, попутно запуская парсеры (например, RegRipper) для немедленного извлечения артефактов.
- **Программы для создания образов дисков**: FTK Imager и Autopsy способны извлекать кусты из live-системы или готового образа в формате E01/dd.
- **Ручное извлечение**: если доступ возможен только через CLI, можно выполнить `reg save HKLM\System system.hiv` — эта команда создаёт копию куста, доступную для оффлайн-анализа.

После получения файлов их содержимое просматривают с помощью Registry Explorer Эрика Циммермана, REGA, Registry Viewer или бесплатной утилиты `offreg.dll` в пакете Windows Assessment and Deployment Kit. Для автоматизированного разбора большого числа кустов применяют RegRipper с набором плагинов.

В контексте SOC L1 наиболее критичными являются ключи, связанные с автозапуском и устойчивостью вредоносного ПО. Перечислим основные локации:

- `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` и симметричный `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`
- `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce` и `RunServices`
- `HKLM\SYSTEM\CurrentControlSet\Services` (особенно параметр Start = 0x02 и ImagePath, указывающий на подозрительный исполняемый файл)
- `HKLM\Software\Microsoft\Windows NT\CurrentVersion\Winlogon` (параметры `Shell`, `Userinit`, `Notify`)
- `HKLM\Software\Microsoft\Windows NT\CurrentVersion\Image File Execution Options`
- `HKLM\Software\Microsoft\Windows\CurrentVersion\Explorer\ShellServiceObjects`, `Browser Helper Objects`
- `HKLM\System\CurrentControlSet\Control\Session Manager` (параметр `PendingFileRenameOperations` для выживания после перезагрузки)
- Ключи расширений оболочки (`ShellEx`) и контекстных меню.

Для быстрого триажа на живой системе аналитик может использовать PowerShell-команду, которая опрашивает наиболее популярные точки автозапуска, включая куст текущего пользователя и всех пользователей, чьи профили загружены в HKU.

```powershell
# Получаем Run-ключи для всех пользователей, чьи SID не заканчиваются на _Classes
Get-ChildItem Registry::HKEY_USERS | Where-Object { $_.PSChildName -match '^S-1-5-21-[\d-]+$' } | ForEach-Object {
    $sid = $_.PSChildName
    $runPath = "Registry::HKEY_USERS\$sid\Software\Microsoft\Windows\CurrentVersion\Run"
    if (Test-Path $runPath) {
        Write-Host "=== Run для пользователя с SID $sid ==="
        Get-ItemProperty -Path $runPath | Format-List
    }
}
# А также машинный Run
Get-ItemProperty -Path "Registry::HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Run"
```

Вывод этой команды (иллюстративная схема) покажет все значения и соответствующие исполняемые файлы. Сопоставление с известными легитимными записями (базовые строки можно получить из чистой контрольной системы) позволяет быстро выявить незнакомые или подозрительные строки.

Для мониторинга изменений реестра в реальном времени SOC опирается на журналы Windows и Sysmon. Windows Security Log регистрирует событие с кодом 4657 (Audit Registry Value Change), если включена аудит-политика. Sysmon предоставляет более детальную информацию:
- Event ID 12 (RegistryEvent – Object create and delete)
- Event ID 13 (RegistryEvent – Value Set)
- Event ID 14 (RegistryEvent – Key and Value Rename)

Пример (иллюстративный) JSON-фрагмента алерта SIEM, основанного на событии Sysmon 13:

```json
{
  "EventId": 13,
  "UtcTime": "2026-02-20T14:35:02.123Z",
  "Computer": "WS001.corp.local",
  "User": "CORP\\jdoe",
  "EventType": "SetValue",
  "Image": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\dropper.exe",
  "TargetObject": "HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run\\MalwareService",
  "Details": "C:\\Users\\jdoe\\AppData\\Roaming\\Payload\\malware.exe"
}
```

Аналитик L1, увидев такое событие, должен выполнить следующие шаги:
1. Определить, является ли процесс-образ (`Image`) известным и легитимным. В данном случае временная папка и подозрительное имя — тревожный признак.
2. Проверить текущее состояние ключа (с помощью приведённой выше PowerShell-команды или `reg query`), чтобы убедиться, что запись не была удалена.
3. Скоррелировать с другими логами (Sysmon Event ID 1 — создание процесса `dropper.exe`, сетевые коннекты).
4. Классифицировать инцидент и, при подтверждении вредоносности, инициировать эскалацию на L2/IR с предоставлением полного контекста: хэш файла, путь, целевой ключ.

Важно помнить об ограничениях живого просмотра: корневой ключ HKEY_CLASSES_ROOT является виртуальным объединением, и запись, добавленная атакующим в пользовательский подраздел `HKCU\Software\Classes`, может не отображаться в HKLM-ветви. Поэтому рекомендуется явно опрашивать и пользовательский хайв. Для оффлайн‑анализа образов необходимо загрузить NTUSER.DAT и обрабатывать его отдельно, используя инструменты вроде Registry Explorer, где можно нативно просмотреть все вложенные ключи.

## 4. Сквозной практический пример: расследование подозрительной модификации реестра

**Исходные условия:** аналитик SOC L1 получает уведомление от EDR о том, что на рабочей станции `DESKTOP-9XE` (Windows 11 23H2) сработало правило на подозрительную запись в реестр. Пользователь `shopov` недавно открыл вложение электронной почты. В SIEM доступны логи Sysmon. Цель — подтвердить или опровергнуть инцидент персистенции.

**Инструменты:** удалённый доступ PowerShell, SIEM с интеграцией Sysmon, локальный `reg.exe` (при необходимости).

### Шаг 1: Анализ первичного алерта в SIEM

Аналитик открывает инцидент и видит событие Sysmon Event ID 13, зафиксированное в 10:30 UTC. Детали события (поля типичные для Sysmon, представлены в JSON-подобной форме для читаемости):

```json
{
  "EventID": 13,
  "Computer": "DESKTOP-9XE.acme.local",
  "User": "ACME\\shopov",
  "Image": "C:\\Users\\shopov\\Downloads\\invoice_03256.pdf.exe",
  "TargetObject": "HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run\\WindowsUpdateSvc",
  "Details": "C:\\Users\\shopov\\AppData\\Roaming\\Microsoft\\svchost.exe"
}
```

Процесс `invoice_03256.pdf.exe` запущен из папки Downloads, что является типичным вектором вредоносных вложений. Запись добавлена в автозагрузку текущего пользователя.

### Шаг 2: Проверка текущего состояния реестра

Чтобы исключить возможность, что запись была удалена позже, аналитик выполняет удалённый опрос через PowerShell:

```powershell
Invoke-Command -ComputerName DESKTOP-9XE -ScriptBlock {
    Get-ItemProperty -Path "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run" -Name "WindowsUpdateSvc" -ErrorAction SilentlyContinue
}
```

Ожидаемый вывод (иллюстративная схема):

```text
WindowsUpdateSvc : C:\Users\shopov\AppData\Roaming\Microsoft\svchost.exe
PSPath            : Microsoft.PowerShell.Core\Registry::HKEY_USERS\S-1-5-21-...\Software\Microsoft\Windows\CurrentVersion\Run
PSParentPath      : ...
```

Вывод подтверждает, что подозрительное значение всё ещё активно, и система продолжит его исполнение при следующем входе пользователя.

### Шаг 3: Корреляция с событием создания процесса

В SIEM ищется Sysmon Event ID 1 для того же компьютера в интервале около 10:30. Найденная запись:

```json
{
  "EventID": 1,
  "Computer": "DESKTOP-9XE.acme.local",
  "ProcessId": 4860,
  "Image": "C:\\Users\\shopov\\Downloads\\invoice_03256.pdf.exe",
  "CommandLine": "\"C:\\Users\\shopov\\Downloads\\invoice_03256.pdf.exe\"",
  "ParentImage": "C:\\Program Files\\Mozilla Firefox\\firefox.exe",
  "ParentCommandLine": "\"C:\\Program Files\\Mozilla Firefox\\firefox.exe\" -osint -url \"...\"",
  "Hashes": "SHA1=6e90f8a1c9b207a...",
  "IntegrityLevel": "Medium"
}
```

Процесс запущен из браузера Firefox (скорее всего, после клика по вредоносному вложению), имеет низкую редкость хэша и отсутствует в базе разрешённых. Эти данные подтверждают скачивание и исполнение неизвестного файла.

### Шаг 4: Принятие решения и эскалация

Совокупность артефактов позволяет заключить:
- Временной отрезок 10:29–10:30, пользовательский контекст, процесс‑родитель указывают на загрузку вредоносного файла из интернета;
- Создание персистентного ключа автозапуска с ложным именем `WindowsUpdateSvc` и путём к исполняемому файлу, маскирующемуся под `svchost.exe`, является классическим механизмом закрепления.
- Хэш процесса не совпадает ни с одним легитимным файлом.

На основе этих заключений инцидент классифицируется как вероятная компрометация (True Positive) и эскалируется команде реагирования (L2/IR). В эскалационном отчёте указываются: ID компьютера, имя пользователя, точный ключ реестра, путь к вредоносному файлу, хэш и временные метки.

Данный пример демонстрирует, как реестр служит не просто конфигурационным хранилищем, но и надёжным хранилищем индикаторов атаки, позволяющих аналитику SOC L1 быстро выявить угрозу.
