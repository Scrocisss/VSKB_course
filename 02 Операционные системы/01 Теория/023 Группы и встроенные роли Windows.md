# Группы и встроенные роли Windows

## Идентификация и классификация групп в модели безопасности Windows

Модель безопасности Windows опирается на механизм контроля доступа к объектам, основанный на списках управления доступом (Access Control Lists, ACL). Каждый защищаемый объект — файл, процесс, раздел реестра, служба — содержит ACL, в виде набора записей (Access Control Entries, ACE), каждая из которых связывает идентификатор безопасности (Security Identifier, SID) с разрешённым или запрещённым набором операций. Непосредственное присвоение прав каждой отдельной учётной записи быстро приводит к неконтролируемой фрагментации разрешений, поэтому в системе предусмотрены **группы безопасности** — контейнеры, объединяющие пользователей, компьютеры и другие группы, чтобы назначать доступ агрегированно.

Группа в Windows — это объект-принципал безопасности, обладающий уникальным SID. Свойства и область действия группы определяются её типом, который разграничивает сценарии применения: одни существуют только в контексте локального компьютера, другие реплицируются между контроллерами домена Active Directory, третьи предназначены исключительно для рассылки электронной почты (группы распространения — вне периметра контроля доступа). В SOC‑аналитике принципиальное значение имеют группы, способные фигурировать в ACL и влиять на уровень привилегий учётной записи, поэтому ниже рассматриваются только группы безопасности.

Понятие **«роль»** в экосистеме Windows не формализовано в виде отдельного объекта, а реализуется через наборы встроенных локальных групп, каждая из которых наделена фиксированной комбинацией пользовательских прав (User Rights Assignments) и разрешений на критичные системные ресурсы. Например, роль «администратор» материализуется членством в группе `Administrators` (S‑1‑5‑32‑544), а роль «оператор резервного копирования» — в группе `Backup Operators` (S‑1‑5‑32‑551). Аналитику SOC L1 необходимо понимать не только имена групп, но и их статичные SID‑идентификаторы, потому что именно они фигурируют в журналах аудита, а в некоторых сценариях атак злоумышленник намеренно добавляет SID непосредственно в токен доступа, минуя привычные интерфейсы.

Ключевое различие между группами разных типов проистекает из их **области видимости** и места хранения. Следующая таблица систематизирует категории, встречающиеся в современных версиях Windows (Windows 10/11, Server 2016 и новее). Специальные идентификаторы (Well‑known SID), такие как `Everyone` или `Authenticated Users`, формально не являются группами в смысле контейнеров членов — это динамически вычисляемые SID, добавляемые в токен доступа ядром системы при входе, и они также приведены, поскольку часто фигурируют в аудитных записях.

```text
| Категория (тип)        | Область действия                           | Где определена / хранится          | Пример SID / группы              | Примечание для SOC                                                                 |
|------------------------|--------------------------------------------|------------------------------------|----------------------------------|------------------------------------------------------------------------------------|
| Built‑in Local (встроенная локальная) | Локальный компьютер; на DC распространяется на весь домен | SAM локального компьютера         | Administrators (S‑1‑5‑32‑544)     | Фиксированный RID, членство критично для эскалации.                                |
| Local (пользовательская локальная) | Только конкретный компьютер               | SAM локального компьютера         | МояЛокальнаяГруппа (S‑1‑5‑21‑...) | Создаётся администратором компьютера; в доменной среде не реплицируется.            |
| Domain Local (доменная локальная) | Все машины домена                         | Active Directory                   | IT‑Support (S‑1‑5‑21‑...)         | Может содержать доменных пользователей, глобальные и универсальные группы.         |
| Global (глобальная)     | Все машины домена и доверенных доменов     | Active Directory                   | Domain Users (S‑1‑5‑21‑...‑513)    | Обычно объединяет сущности одного домена; сама может быть членом локальных групп.  |
| Universal (универсальная) | Все домены в лесу Active Directory          | Active Directory (GC)              | Enterprise Admins (S‑1‑5‑21‑...‑519) | Использует глобальный каталог, повышает нагрузку на репликацию.                     |
| Специальный идентификатор (Well‑known SID) | Вычисляется динамически при создании токена | Не хранится как группа             | Everyone (S‑1‑1‑0), Authenticated Users (S‑1‑5‑11) | Нельзя модифицировать вручную, применяется в ACL для охвата категорий пользователей.  |
```

Правильное соотнесение типа группы с её SID позволяет аналитику на стадии триажа определить, о каком масштабе инцидента идёт речь. Например, добавление постороннего участника в группу `Server Operators` (S‑1‑5‑32‑549, Built‑in Local на контроллере домена) означает, что компрометация затронула DC и злоумышленник стремится к закреплению и манипуляции службами. Если же регистрируется событие в глобальной группе `Domain Admins` (S‑1‑5‑21‑*‑512), то под угрозой весь домен. Специальные идентификаторы, в свою очередь, часто используются администраторами для упрощения ACL, но в логах аудита они будут фигурировать как SID в составе токена проверяемого субъекта, что требует от аналитика узнавания этих значений.

Концепция ролей через встроенные группы решает задачу предоставления минимально необходимых прав для выполнения определённых административных функций. Например, членство в `Event Log Readers` (S‑1‑5‑32‑573) даёт возможность читать журналы безопасности без предоставления полного административного доступа — это типичная роль для SIEM‑агента. С точки зрения SOC всякое отклонение от ожидаемого членства в таких ролях служит индикатором компрометации, поэтому критически важно знать, какая группа какой привилегированный функционал открывает.

## Внутреннее устройство групп и систематизация встроенных ролей

Каждый объект-группа в Windows обладает SID, сформированным по иерархической схеме. Рассмотрим строение на примере встроенной группы `Administrators`, чей стандартизированный идентификатор — `S-1-5-32-544`.  

- **S** — заголовок, указывающий, что строка является идентификатором безопасности.  
- **1** — редакция спецификации SID; в современных ОС всегда равна 1.  
- **5** — идентификатор центра выдачи (Identifier Authority), значение `NT Authority`; означает, что SID управляется подсистемой безопасности Windows NT.  
- **32** — первый суб-авторитет, обозначающий домен `Builtin`. Именно этот компонент фиксирован для всех встроенных локальных групп и отделяет их от доменных SID, у которых на этом месте находится идентификатор домена (три 32‑битных числа после числа `21`).  
- **544** — относительный идентификатор (RID), уникальный в пределах домена `Builtin`. RID определяет конкретную роль: 544 — Administrators, 545 — Users, 546 — Guests и т.д.

Система генерирует SID для группы однократно при её создании; для встроенных групп RID предопределён и неизменен на любом компьютере под управлением Windows. Это свойство даёт аналитику SOC возможность декодировать групповую принадлежность субъекта, не обращаясь к списку имён, что полезно при разборе дампов токенов или неструктурированных логов, где могут отсутствовать дружественные названия.

С точки зрения ядра ОС группа материализуется в **токене доступа** (access token), который конструируется для каждого процесса при интерактивном или неинтерактивном входе. Токен содержит массив SID, включающий SID пользователя и SID всех групп, в которые этот пользователь входит прямо или транзитивно. Дополнительно включаются специальные SID, отражающие тип учётной записи (например, `Authenticated Users`), способ входа (`Console Logon`, `Remote Interactive Logon`), уровень целостности и другие атрибуты. Когда поток запрашивает доступ к объекту, диспетчер безопасности сравнивает массив SID из токена с записями ACL и применяет соответствующие маски доступа.

Ниже приведена структурная схема, отображающая, как группы связаны с токеном и ACL:

```text
[Пользователь] ──(вход в систему)──▶ [LSA / SAM] ──(сбор SID)──▶ [Access Token:
                                                                   User SID
                                                                   Group SIDs (Built-in, Local, Domain)
                                                                   Well‑known SIDs (Interactive, Authenticated Users, ...)]
 
[Процесс] ──(запрос доступа к объекту)──▶ [SRM (Security Reference Monitor)] ──(сравнение SID из токена с ACL)──▶ [Разрешено / Запрещено]
```

Анализируя такой процесс, аналитик понимает: если злоумышленник добавил вредоносный SID в токен процесса с помощью инструментов вроде Mimikatz (`token::elevate`), то проверки ACL будут пройдены, даже если в стандартных групповых членствах изменений не зафиксировано. Поэтому аудит операций с группами — необходимый, но не единственный слой защиты.

Приведённые SID демонстрируют, что RID однозначно идентифицирует роль, а подстановка домена `32` подчёркивает локальную, но в случае DC — доменную область действия. Аналитику следует выучить наизусть «опасные» RID: 544, 551, 549, 550, 555, 573, чтобы при беглом просмотре логов мгновенно распознавать рискованные модификации.

Отдельного внимания заслуживает специальная группа **Protected Users** (S‑1‑5‑21‑*‑525 только для доменной версии), которая вводилась для защиты привилегированных учётных записей от кэширования учётных данных и уязвимых протоколов NTLM. Хотя она не встроена в локальный SAM каждого компьютера, о ней полезно знать, поскольку SOC‑команды часто мониторят добавление в неё неожиданных аккаунтов.

## Практическое применение и мониторинг группового членства в SOC

В операционной деятельности SOC L1 основная задача, связанная с группами, заключается в контроле их состава. Аналитик должен уметь:

- быстро получать текущий список членов локальной или доменной группы;
- искать и интерпретировать события аудита изменений группового членства;
- сопоставлять обнаруженные изменения с политикой безопасности и известными тактиками злоумышленников (MITRE ATT&CK: T1098 — Account Manipulation, T1078 — Valid Accounts).

### Командные инструменты для проверки членства

Для локальных компьютеров базовым средством остаётся утилита `net localgroup`. Она не требует повышенных привилегий для чтения и выдаёт дружественный вывод:

```powershell
net localgroup "Administrators"
```
Ожидаемый вывод (иллюстративная схема):
```
Alias name     Administrators
Comment        Administrators have complete and unrestricted access to the computer

Members

-------------------------------------------------------------------------------
Administrator
Domain Admins
CONTOSO\IT_Admins
The command completed successfully.
```

В PowerShell версии 5.1 и выше доступны командлеты `Get-LocalGroupMember`, `Get-LocalGroup`:

```powershell
Get-LocalGroupMember -Group "Backup Operators"
```
Вывод:
```
ObjectClass Name                 PrincipalSource
----------- ----                 ---------------
User        CONTOSO\svc_backup    ActiveDirectory
```

Для доменных групп используется модуль Active Directory, предустановленный на серверах с ролью AD DS или RSAT:

```powershell
Get-ADGroupMember -Identity "Domain Admins"
```

При расследовании предпочтительнее использовать PowerShell, так как он возвращает объекты с полями SID и источником (PrincipalSource), что облегчает расширенный анализ.

### События аудита и их интерпретация

Для обнаружения изменений в группах безопасности необходимо включить аудит подкатегории **Security Group Management** (в локальной политике или через групповые политики). Тогда ОС регистрирует следующие ключевые события (Event ID) в журнале `Security`:

- **4732** — участник добавлен в локальную группу безопасности, имеющую S‑1‑5‑32‑*;  
- **4733** — участник удалён из такой группы;  
- **4728**, **4729** — добавление/удаление из глобальной группы;  
- **4756**, **4757** — добавление/удаление из универсальной группы;  
- **4731**, **4735** — создание/удаление локальной группы безопасности.

Каждое событие содержит в теле XML структурированные поля. Для аналитика критичны:

- `SubjectUserSid` / `SubjectUserName` — кто выполнил действие;  
- `MemberSid` / `MemberName` — какого участника добавили/удалили;  
- `GroupSid` / `GroupName` — целевая группа;  
- `TargetUserName` / `TargetDomainName` — в ряде событий дублирует информацию о группе.

Пример фрагмента события 4732 (представлен в упрощённой форме):

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="..."/>
    <EventID>4732</EventID>
    <TimeCreated SystemTime="2025-03-21T18:45:12.000Z"/>
  </System>
  <EventData>
    <Data Name="SubjectUserSid">S-1-5-21-3623811015-3361044348-30300820-1001</Data>
    <Data Name="SubjectUserName">JohnDoe</Data>
    <Data Name="SubjectDomainName">CONTOSO</Data>
    <Data Name="MemberSid">S-1-5-21-3623811015-3361044348-30300820-1103</Data>
    <Data Name="MemberName">svc_web</Data>
    <Data Name="MemberDomain">CONTOSO</Data>
    <Data Name="TargetSid">S-1-5-32-551</Data>
    <Data Name="TargetUserName">Backup Operators</Data>
    <Data Name="TargetDomainName">Builtin</Data>
  </EventData>
</Event>
```

Здесь `SubjectUserSid` показывает, что рядовой пользователь `JohnDoe` (RID > 1000) добавил служебную учётную запись `svc_web` в группу `Backup Operators`. Уже по этому фрагменту аналитик может подозревать несанкционированное действие: почему пользователь с обычными правами смог модифицировать привилегированную группу? Такое возможно, например, если субъекту ранее были делегированы соответствующие права, что тоже требует проверки.

### Практический сбор данных

Для поиска всех фактов добавления в критическую группу за последние сутки можно применить фильтр по журналу:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    ID = 4732
    StartTime = (Get-Date).AddDays(-1)
} | Where-Object {
    $_.Properties[2].Value -in @('Administrators','Backup Operators','Remote Desktop Users','Server Operators')
} | ForEach-Object {
    [PSCustomObject]@{
        TimeCreated = $_.TimeCreated
        Subject     = $_.Properties[1].Value + '\' + $_.Properties[0].Value
        Member      = $_.Properties[5].Value + '\' + $_.Properties[4].Value
        Group       = $_.Properties[2].Value
    }
}
```

Индексы `Properties` соответствуют порядку полей в шаблоне события. Такой скрипт можно вызывать при расследовании алерта или использовать как часть автоматизированного мониторинга. В средах, где внедрён Microsoft Defender XDR или Sentinel, применяются KQL-запросы, опирающиеся на таблицу `IdentityDirectoryEvents` и событие `Account added to security group`, как показано в публикации [verboon](https://www.verboon.info/2024/02/monitoring-windows-built-in-local-security-groups-with-microsoft-defender-xdr-or-sentinel).

Важно помнить, что события аудита могут отсутствовать, если аудит не был включён предварительно. Поэтому в SOC часто настраивают базовые политики аудита через GPO для всех рабочих станций и серверов.

## Сквозной практический пример: расследование несанкционированного добавления в Backup Operators

### Исходные условия

Рабочая станция `WS‑CONTOSO‑001` под управлением Windows 11 Enterprise, состоящая в домене `contoso.com`, включена в политику аудита Security Group Management. Инцидентом является алерт SIEM‑системы: «Пользователь `JohnDoe` выполнил добавление учётной записи `svc_backup` в группу `Backup Operators`». Аналитик SOC L1 должен проверить легитимность действия и подготовить предварительные выводы.

**Инструменты:** локально выполняемые команды `net localgroup`, `Get-WinEvent`, `whoami`.

### Шаг 1: Проверка текущего состава группы

Выполняется команда для получения текущего списка членов группы «Backup Operators»:

```cmd
net localgroup "Backup Operators"
```

Ожидаемый вывод (иллюстративная схема):

```
Alias name     Backup Operators
Comment        Backup Operators can override security restrictions for the sole purpose of backing up or restoring files

Members

-------------------------------------------------------------------------------
svc_backup
JohnDoe
The command completed successfully.
```

Присутствие `svc_backup` и самого `JohnDoe` (возможно, он добавил себя в группу ранее) подтверждает, что группа уже содержит подозрительных членов. В нормальном состоянии группа должна быть пустой или содержать только разрешённые сервисные учётные записи, список которых задокументирован в корпоративном стандарте.

### Шаг 2: Поиск события добавления

Аналитик запрашивает журнал Security за последние 4 часа для события 4732 с целевой группой `Backup Operators`:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    ID = 4732
    StartTime = (Get-Date).AddHours(-4)
} | Where-Object { $_.Properties[2].Value -eq 'Backup Operators' }
```

Возможный результат (упрощён):

```
TimeCreated               : 21.03.2025 18:45:12
SubjectUserName           : JohnDoe
SubjectUserSid            : S-1-5-21-3623811015-3361044348-30300820-1001
MemberName                : svc_backup
MemberSid                 : S-1-5-21-3623811015-3361044348-30300820-1103
TargetUserName            : Backup Operators
TargetSid                 : S-1-5-32-551
```

Субъектом является доменный пользователь `JohnDoe` (RID 1001), у которого по должностной инструкции нет прав на управление административными группами. Целевой SID группы совпадает с известным идентификатором `Backup Operators`.

### Шаг 3: Идентификация контекста субъекта

Аналитик проверяет собственный SID для наглядного сопоставления:

```powershell
whoami /user
```

Вывод:

```
User Name SID
========= ==============================================
contoso\analyst_mike S-1-5-21-3623811015-3361044348-30300820-1105
```

RID аналитика >1000 подтверждает, что и `JohnDoe`, и `svc_backup` — обычные доменные учётные записи, не относящиеся к встроенным сущностям. Домен `CONTOSO` совпадает с доменом субъекта.

### Шаг 4: Оценка легитимности и документирование

Совокупность фактов:

- встроенная группа с критическими привилегиями получила нового члена;
- субъект действия (`JohnDoe`) не относится к привилегированным администраторам;
- добавленная учётная запись (`svc_backup`) является сервисной, и её появление в группе не регламентировано;
- действие зафиксировано вне планового окна изменений.

На основе этой информации аналитик делает вывод о вероятной эскалации привилегий (MITRE ATT&CK T1098). Артефакты инцидента:

- SID субъекта: `S-1-5-21-...‑1001`
- Добавляемый SID: `S-1-5-21-...‑1103`
- Целевая группа: `S-1-5-32-551`
- Время: 2025-03-21T18:45:12Z
- Хост: `WS‑CONTOSO‑001`

Результат эскалируется на L2 для блокировки учётной записи, принудительного сброса паролей и форензического анализа.

### Вывод по примеру

Пример демонстрирует, что даже без сложных инструментов, используя встроенные утилиты и знание SID критических групп, аналитик SOC L1 способен за минуты обнаружить и описать попытку закрепления злоумышленника.
