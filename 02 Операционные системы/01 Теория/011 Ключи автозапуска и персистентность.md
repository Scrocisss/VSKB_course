# Реестр Windows: ключи автозапуска и механизмы персистентности

## 1. Персистентность и роль реестра в её реализации

Персистентность (persistence) в MITRE ATT&CK определена как тактика TA0003 — «закрепление» злоумышленника в скомпрометированной системе с расчётом на выживание после перезагрузок, смены учётных данных, очистки временных файлов или других дестабилизирующих событий. С точки зрения защитника, персистентность превращает однократную инфекцию в долговременную угрозу, способную к повторному запуску без внешнего вмешательства атакующего. Именно поэтому обнаружение следов закрепления является одной из приоритетных задач аналитика SOC L1 при первичной сортировке инцидентов.

Среди двух десятков техник, описанных в тактике TA0003, доминирует T1547.001 — **Registry Run Keys / Startup Folder**, на которую, по данным телеметрии сообщества, приходится непропорционально большая доля реальных атак [Nextron Systems, 2025](https://www.nextron-systems.com/2025/07/29/detecting-the-most-popular-mitre-persistence-method-registry-run-keys-startup-folder/). Высокая популярность объясняется простотой реализации, штатным поведением Windows и отсутствием необходимости во вредоносном коде, постоянно висящем в памяти: достаточно однократно записать путь к полезной нагрузке в одну из точек автозапуска реестра, и ОС сама запустит её при следующем входе пользователя.

**Реестр** — централизованная иерархическая база данных Windows, хранящая конфигурацию системы, пользовательские настройки, параметры драйверов, приложений и служб [Blue Team Cookbook](https://vasilisa-l.gitbook.io/blue-team-cookbook/windows/registry). Для SOC-аналитика реестр интересен как богатейший источник артефактов: практически любое изменение, влияющее на поведение ОС, отражается в записях реестра. Злоумышленники, модифицируя определённые ключи, способны добиться автоматического запуска своего кода без использования нестандартных механизмов, маскируясь под легитимные приложения или сервисы.

Путаница может возникнуть между **точкой автозапуска** и **способом её использования**. Сам по себе ключ `Run` не является вредоносным — это штатная функция Windows, применяемая для запуска агентов обновления, утилит безопасности, индикаторов раскладки клавиатуры и т.п. Угрозу представляет непредусмотренное администратором значение, указывающее на вредоносный исполняемый файл, скрипт или DLL. Аналитик должен чётко разграничивать легитимные записи и подозрительные, опираясь на контекст: путь к файлу, цифровую подпись, родительский процесс, частоту появления в среде.

**Сравнение ключевых механизмов автозапуска** (таблица фиксирует разграничения, важные для первичной сортировки):

| Механизм / ключ | Ключевые признаки (условие запуска) | Контекст выполнения | Пример легитимного или вредоносного поведения |
|------------------|--------------------------------------|----------------------|------------------------------------------------|
| `Run` (HKCU/HKLM) | При каждом входе пользователя в сеанс | Контекст учётной записи пользователя (для HKCU) или любого пользователя (для HKLM, если программа умеет работать с системными привилегиями) | Легитимно: `OneDrive` с параметром `"C:\Program Files\Microsoft OneDrive\OneDrive.exe" /background`. Вредоносно: `RAT`-троян, прописавшийся как `"C:\Users\Public\svchost.exe"` без цифровой подписи. |
| `RunOnce` (HKCU/HKLM) | Однократно при ближайшем входе, после чего значение (не ключ!) удаляется системой | Аналогично `Run`, но выполняется только один раз | Используется установщиками для завершения настройки после перезагрузки. Атакующие применяют для одноразового срабатывания дроппера, который затем удаляет сам ключ, заметая следы. |
| `RunOnceEx` (только HKLM) | Однократно, с возможностью задания зависимостей (Depend) и расширенным контролем порядка запуска | Системный контекст (LocalSystem) | Штатно применяется в корпоративных средах для развёртывания ПО. Вредоносно: создание ключа `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnceEx\0001\Depend` для загрузки DLL-библиотеки [MITRE ATT&CK](https://attack.mitre.org/techniques/T1547/001). |
| `RunServices` / `RunServicesOnce` | При загрузке системы, до входа пользователя (устаревшие, но всё ещё работают в отдельных версиях) | Высокие привилегии, системный контекст | Редко встречается в современных атаках, но может быть использован для закрепления kernel-level вредоносов или legacy-троянов. |
| `Userinit` / `Winlogon` | Во время интерактивного входа, выполняется процессом Winlogon | Система, до создания оболочки пользователя | Легитимное значение `Userinit` = `C:\Windows\system32\userinit.exe,`. Злоумышленник может дописать вторую команду через запятую, что приведёт к выполнению вредоносного кода с привилегиями системы. |
| `AppInit_DLLs` | При загрузке любого приложения, использующего user32.dll (при включённой опции `LoadAppInit_DLLs`) | Контекст загружаемого приложения | Устаревший механизм, используемый для инжектирования DLL во все GUI-процессы. Требует включения через реестр, нередко отключается современными защитными решениями. |
| Папки автозагрузки (`Startup`) | При входе пользователя — ярлыки или файлы в папке автозагрузки | Контекст пользователя | Пути: `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup` (текущий пользователь) и `%ProgramData%\Microsoft\Windows\Start Menu\Programs\Startup` (все пользователи). Вредонос может разместить туда скрипт или LNK-файл. |

Приведённая таблица разграничивает сценарии, с которыми аналитик столкнётся при просмотре алертов. Глубинная детализация каждого ключа последует во втором разделе, однако уже на этапе сортировки важно уметь отличать `Run` (постоянное срабатывание) от `RunOnce` (самоочищающийся), а также оценивать уровень привилегий, которые получит вредоносный процесс.

Пример команды, с которой аналитик может начать первичную проверку подозрительного хоста, — вывод текущих значений ключа `Run` для локальной машины:

```powershell
reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
```

Вывод (иллюстративная схема) содержит список записей типа `REG_SZ` с именем программы и путём к исполняемому файлу. Аномалия здесь — наличие пути во временной папке пользователя или в `AppData\Roaming` без валидной цифровой подписи; именно такие отклонения служат индикатором компрометации.

## 2. Структура и классификация регистрационных ключей автозапуска

Раздел рассматривает внутреннее устройство ключей реестра, обеспечивающих персистентность на этапе входа в систему. Поскольку тема относится к классу «обзор класса» (разновидности ключей, их свойства и индикаторы), обязательной является сравнительная таблица, фиксирующая все значимые элементы. Помимо неё, демонстрируется JSON-подобная структура значения и команда прямого добавления ключа для понимания формата данных.

Реестр организован в виде кустов (hives). Для механизма автозапуска при входе наиболее важны кусты `HKEY_CURRENT_USER` (HKCU) и `HKEY_LOCAL_MACHINE` (HKLM), а также их подразделы `Software\Microsoft\Windows\CurrentVersion`. Внутри этих веток существует целое семейство ключей, исторически расширявшееся от версии к версии Windows. Основные типы ключей и их характеристики сведены в таблицу ниже; каждый из них способен выступать точкой закрепления.

**Сравнительная таблица ключей автозапуска (расширенная)**

| Элемент (путь к ключу) | Куст | Область видимости | Условие запуска | Очищается ли системой? | Типичные значения (легитимные примеры) |
|------------------------|------|-------------------|-----------------|------------------------|----------------------------------------|
| `…\Run` | HKCU, HKLM | Текущий пользователь (HKCU) или все пользователи (HKLM) | Каждый интерактивный вход | Нет (постоянно) | `SecurityHealth` — `%ProgramFiles%\Windows Defender\MSASCuiL.exe` |
| `…\RunOnce` | HKCU, HKLM | Соответственно пользователь/машина | Однократно при следующем входе | Да, значение удаляется после выполнения | Обычно пуст после срабатывания; установщики временно помещают скрипты |
| `…\RunOnceEx` | HKLM (только) | Все пользователи, системный контекст | Однократно, с обработкой вложенной структуры (зависимости, флаги) | Да, удаляется после выполнения | Сложные инсталляционные пакеты; структура: `0001`, `0002` с параметрами `Depend`, `Flags` |
| `…\RunServices` | HKCU, HKLM | Все пользователи или текущий | При старте системы, до входа | Нет (аналог Run, но для служб) | Legacy-драйверы и утилиты сопровождения |
| `…\RunServicesOnce` | HKCU, HKLM | Аналогично RunServices | Однократно при следующей загрузке | Да | Почти не встречается в современных ОС |
| `…\Policies\Explorer\Run` | HKCU, HKLM | Соответственно | При входе; управляется групповыми политиками | Нет | Используется доменными политиками для обязательных программ; злоумышленники могут модифицировать с высокими привилегиями |
| `…\Windows\Load` | HKCU | Текущий пользователь | При входе (параметр `Load` в ключе `…\Windows`) | Нет | Редко используется; вредоносные программы могут дописывать свою DLL в этот строковый параметр |
| `…\Winlogon\Userinit` | HKLM | Системный, перед загрузкой оболочки | Во время интерактивного входа (выполняется процессом Winlogon) | Нет | Легитимно: `C:\Windows\system32\userinit.exe,`; атака: `C:\Windows\system32\userinit.exe, C:\malware\payload.exe` |
| `…\Winlogon\Shell` | HKLM | Системный | При входе, определяет оболочку вместо Explorer | Нет | Легитимно: `explorer.exe`; подмена на вредоносный файл даёт полный контроль над сеансом |
| `AppInit_DLLs` (ключ `…\Windows`) | HKLM | Все процессы, загружающие user32.dll | При загрузке процесса | Нет (отключён по умолчанию, требует `LoadAppInit_DLLs=1`) | Использовался для инжекта; вредонос: `C:\malware.dll` |

Эти ключи срабатывают на разных этапах процесса входа и обслуживают разные сценарии. Аналитику SOC L1 необходимо знать как минимум основные четыре (`Run`, `RunOnce`, `RunOnceEx`, `Userinit`) и уметь находить их в реестре с помощью стандартных утилит.

**Структура значения реестра (пример для Run)**
Запись в ключе `Run` представляет собой тип `REG_SZ` (строковый) или `REG_EXPAND_SZ` (расширяемый строковый с поддержкой переменных среды). Имя значения обычно является произвольной строкой (например, `OneDrive`), а данные — командной строкой для исполнения. В формализованном виде структура выглядит так:

```json
{
  "hive": "HKEY_LOCAL_MACHINE",
  "key_path": "SOFTWARE\\Microsoft\\Windows\\CurrentVersion\\Run",
  "value_name": "<отображаемое имя записи>",
  "value_type": "REG_SZ",
  "value_data": "\"<путь к исполняемому файлу>\" <параметры>"
}
```

Значение может содержать дополнительные аргументы; оболочка Explorer интерпретирует его как команду для `CreateProcess`. Именно поэтому злоумышленники могут указывать скриптовые движки (`wscript.exe`, `powershell.exe`) с URL-адресами или закодированными командами. Пример подозрительного значения, записанного трояном, иллюстрирует эту возможность:

```bash
reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v "SecurityUpdate" /t REG_SZ /d "powershell.exe -WindowStyle Hidden -ExecutionPolicy Bypass -File C:\Users\Public\update.ps1" /f
```

Эта команда добавляет в реестр ключ с именем, маскирующимся под легитимное обновление безопасности. Аналитик, обнаружив такую строку, должен проверить файл `update.ps1`, его содержимое и цепочку загрузки.

Для полноты картины следует помнить, что записи могут быть размещены не только в стандартных путях. На 64-разрядных системах существует разделение на 32- и 64-битные представления реестра: 32-битные приложения видят ветку `HKLM\Software\Wow6432Node\...`. Вредонос, запущенный в 32-битном процессе, может прописаться в `Run` внутри `Wow6432Node`, что иногда ускользает от инструментов, не проверяющих оба представления. Поэтому при поиске артефактов необходимо анализировать как `Software\Microsoft\Windows\CurrentVersion\Run`, так и `Software\Wow6432Node\Microsoft\Windows\CurrentVersion\Run`.

**Автоматизированный сбор ключей автозапуска**
Документирование всех потенциальных точек вручную трудоёмко. В реальной работе SOC используются утилиты вроде Sysinternals Autoruns (командная строка `autorunsc.exe`), которые агрегируют все известные местоположения. Пример вывода команды, запущенной на заражённом хосте, может помочь наглядно показать размах проблемы:

```bash
autorunsc.exe -a -c -m
```

Опция `-a` — все локации, `-c` — CSV-вывод, `-m` — скрывать подписанные Microsoft записи. В результате SOC-аналитик получает таблицу всех подозрительных элементов автозапуска, включая `Run`, `RunOnce`, планировщик задач, загружаемые модули и т.п., что значительно ускоряет сортировку.

Таким образом, внутреннее устройство ключей автозапуска представляет собой иерархический набор предопределённых путей реестра, каждый из которых имеет фиксированное поведение при входе в систему. Понимание различий между ними необходимо для корректной интерпретации алертов и эффективного реагирования.

## 3. Применение и работа с ключами автозапуска

Данный раздел посвящён практическим аспектам: как злоумышленники используют рассмотренные ключи для закрепления, какие инструменты применяются, и, главное, как аналитик SOC может выявить такие модификации в корпоративной среде. Акцент сделан на детектирование и анализ, а не на пошаговые инструкции по эксплуатации.

### 3.1 Инструментарий атакующих и типичные сценарии

Наступательные фреймворки и вредоносное ПО имеют встроенные модули персистентности через Run-ключи. Например, **Metasploit** предоставляет модуль `post/windows/manage/persistence`, который по умолчанию создаёт запись в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. **Empire** и **PoshC2** также содержат специализированные команды: `persistence/elevated/registry` или `install-persistence`, автоматически записывающие агента в `Run`-ключ с маскировочным именем вроде «IEUpdate» или «Wallpaper» [PentestLab, 2019](https://pentestlab.blog/2019/10/01/persistence-registry-run-keys). **SharPersist** (автор Brett Hawkins) — это C#-инструмент, объединяющий множество техник, включая `-t reg` для Run-ключей [v4resk/red-book](https://github.com/v4resk/red-book/blob/main/redteam/persistence/windows/run-keys.md). Синтаксис SharPersist для установки персистентности в HKCU:

```powershell
SharPersist.exe -t reg -c "C:\Windows\Tasks\payload.exe" -a "/k" -k "hkcu_run" -v "WindowsUpdate" -m add
```

Эта команда добавляет значение `WindowsUpdate` в куст HKCU\...\Run, указывающее на вредоносный файл, маскируя его под легитимное обновление. Анализ телевых атак показывает, что группировки часто применяют именно `HKCU\Run`, поскольку для записи в эту ветку не требуются привилегии администратора.

При наличии прав SYSTEM злоумышленник может модифицировать `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`, делая программу запускаемой для всех пользователей, либо более скрытно прописаться в `RunOnceEx` с зависимостями, обеспечивая однократное выполнение загрузчика DLL [MITRE ATT&CK T1547.001](https://mitre.ptsecurity.com/ru-RU/T1547.001). Пример команды с использованием `reg` для создания записи с зависимостью:

```bash
reg add HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\RunOnceEx\0001\Depend /v 1 /d "C:\temp\evil.dll"
```

Следует отметить, что `RunOnceEx` очищается после выполнения, поэтому такой метод хорош для «одноразовой» полезной нагрузки — например, для запуска дроппера, который сам удалит и ключ, и исходный файл, оставив в системе только загруженный вредонос, чья персистентность обеспечена иным способом.

### 3.2 Типичные ошибки злоумышленников и признаки компрометации

Несмотря на кажущуюся простоту, атакующие часто допускают ошибки, создающие надёжные индикаторы:

- **Путь к исполняемому файлу в подозрительных каталогах:** `C:\Users\<user>\AppData\Roaming\...`, `C:\ProgramData\Temp`, `C:\Users\Public\...`, редко используемая папка в `%TEMP%`. Легитимные программы редко запускаются оттуда, и многие EDR регистрируют такие пути.
- **Использование скриптовых хостов:** `powershell.exe -Window Hidden -File ...`, `wscript.exe //B C:\users\public\script.vbs`, `mshta.exe http://...`. Сам факт вызова PowerShell в Run-ключе — сильный сигнал.
- **Неконсистентная цифровая подпись:** значение указывает на неподписанный бинарный файл, в то время как соседние легитимные записи подписаны. Детектор Sysmon (Event ID 13) фиксирует изменение значения, и в логе видно имя процесса, вносившего запись — часто это `reg.exe` или PowerShell.
- **Аномалии в именах значений:** злоумышленники часто пытаются имитировать системные утилиты, допуская опечатки: `WindwosDefender`, `GoogleUpdater` (вместо `GoogleUpdate`), `AdobeReader` и т.п. Гигиена имён — эффективный low-hanging fruit для охотника.

### 3.3 Методы обнаружения: логи, правила и инструменты

Основные источники событий для выявления модификаций Run-ключей:

- **Sysmon Event ID 13** — «Registry value set»: содержит полный путь к ключу, имя значения, данные и образ процесса, выполнившего запись. Пример записи в формате JSON (иллюстративная схема, структура совпадает с реальным выводом):

```json
{
  "EventID": 13,
  "UtcTime": "2025-09-15T10:23:15.421Z",
  "ProcessGuid": "{c1f2a3b4-5678-90ab-cdef-1234567890ab}",
  "Image": "C:\\Windows\\System32\\reg.exe",
  "TargetObject": "HKU\\S-1-5-21-...\\Software\\Microsoft\\Windows\\CurrentVersion\\Run\\MalwareUpdater",
  "Details": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\payload.exe"
}
```

По этому событию строится правило: если `Image` не является доверенным установщиком (например, не подписан Microsoft, не msiexec) и `TargetObject` оканчивается на `\Run\*` или `\RunOnce\*`, генерируется алерт.

- **Windows Event Log** (Security, Event ID 4657) — «A registry value was modified» — может быть включён аудитом, но менее детален, чем Sysmon.
- **Sigma-правило** для обнаружения подозрительных записей Run:

```yaml
title: Suspicious Registry Run Key Addition
id: 810f5c91-7863-40b9-a3a1-642885cfc7d2
status: experimental
description: Detects suspicious additions to Run or RunOnce registry keys
logsource:
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 13
    TargetObject|contains|all:
      - '\Software\Microsoft\Windows\CurrentVersion\Run'
      - '\Software\Microsoft\Windows\CurrentVersion\RunOnce'
  filter:
    Image|contains: '\Windows\System32\'
  condition: selection and not filter
level: high
```

Это иллюстративное правило выделяет изменения в Run-ключах, выполненные не из системной папки System32 (что часто указывает на вредоносный процесс). В реальных SOC правила дорабатываются с учётом исключений для легитимных установщиков.

- **Hunting с помощью Autoruns и PowerShell.** Массовая проверка хостов может быть автоматизирована скриптом, собирающим все записи Run-ключей удалённо:

```powershell
Invoke-Command -ComputerName target01 -ScriptBlock {
    Get-ItemProperty "HKLM:\Software\Microsoft\Windows\CurrentVersion\Run" | Select-Object -Property *
}
```

Подобный сбор помогает найти аномалии в большом парке машин.

- **EDR и платформы мониторинга** реализуют корреляцию: появление подозрительного значения в Run вкупе с созданием файла на диске за несколько секунд до этого — сильная цепочка, указывающая на активность дроппера.

Таким образом, работа с ключами автозапуска со стороны защиты строится на многоуровневом сборе артефактов, начиная от логирования изменений реестра и заканчивая поведенческим анализом запущенных программ.

## Сквозной практический пример: детектирование и анализ вредоносного Run-ключа

**Исходные условия:** Аналитик SOC L1 получает срабатывание SIEM на основе Sigma-правила (Event ID 13 Sysmon). Хост `WS-ADMIN01` (Windows 10, 22H2). Пользователь — `domain\svc_backup`. Подозрение: запись в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, созданная процессом `cmd.exe`.

**Шаг 1. Просмотр алерта и сбор контекстной информации**
Первым делом аналитик открывает алерт: видит полный путь ключа и имя значения `WindowsService`, данные — `C:\Users\svc_backup\AppData\Local\svchost.exe`. Процесс-источник `cmd.exe` с командной строкой, содержащей `reg add "HKCU\...\Run" /v "WindowsService" ...`. Очевидно, используется утилита `reg.exe`.

```powershell
# Симулированный вывод алерта
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -FilterXPath "*[System[EventID=13]]" -MaxEvents 1 | Select-Object -Property *
```

Пример вывода:

```
EventID         : 13
UtcTime         : 2025-09-15T08:15:10.123Z
ProcessGuid     : {abcdef01-2345-6789-abcd-ef0123456789}
Image           : C:\Windows\System32\cmd.exe
TargetObject    : HKCU\Software\Microsoft\Windows\CurrentVersion\Run\WindowsService
Details         : C:\Users\svc_backup\AppData\Local\svchost.exe
```

**Шаг 2. Верификация значения реестра на хосте**
Аналитик подключается к рабочей станции и проверяет текущее состояние ключа:

```bash
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v "WindowsService"
```

Ожидаемый вывод (иллюстративная схема):

```
HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
    WindowsService    REG_SZ    C:\Users\svc_backup\AppData\Local\svchost.exe
```

Запись присутствует, тип `REG_SZ`, данные указывают на исполняемый файл в нетипичной локации.

**Шаг 3. Анализ файла, на который ссылается ключ**
Следующий этап — получить криптографический хеш, проверить цифровую подпись, размер, а также заглянуть в статические артефакты (строки). Используем PowerShell на удалённой машине:

```powershell
Get-FileHash -Path "C:\Users\svc_backup\AppData\Local\svchost.exe" -Algorithm SHA256
Get-AuthenticodeSignature -FilePath "C:\Users\svc_backup\AppData\Local\svchost.exe"
```

Вывод `Get-AuthenticodeSignature`:

```
SignerCertificate                         Status       Path
-----------------                         ------       ----
                                          NotSigned    C:\Users\svc_backup\AppData\Local\svchost.exe
```

Файл не имеет цифровой подписи, что является красным флагом. Размер и дата создания не совпадают с легитимным `svchost.exe`, находящимся в `C:\Windows\System32`.

**Шаг 4. Поиск дополнительных индикаторов закрепления**
Для полноты картины аналитик проверяет все автозагрузочные локации на хосте с помощью Autoruns, фильтруя только подозрительные неподписанные записи:

```bash
autorunsc.exe -a -c -m | findstr /i "svc_backup"
```

Пример фрагмента вывода:

```
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
  WindowsService  REG_SZ  C:\Users\svc_backup\AppData\Local\svchost.exe
```

Других записей не обнаружено. При инциденте с точкой входа `svc_backup` следует также проверить `RunOnce` и `Winlogon`, но в данном кейсе фокус на `Run`.

**Шаг 5. Реагирование и восстановление**
Аналитик классифицирует инцидент как вредоносное закрепление, изолирует хост и удаляет запись реестра:

```bash
reg delete "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v "WindowsService" /f
```

Затем следует удалить сам файл `svchost.exe`, провести анализ на наличие других закреплений и инициировать смену пароля учётной записи `svc_backup`, так как её контекст был скомпрометирован.

**Ожидаемый вывод примера:** Кейс демонстрирует полный цикл работы аналитика SOC L1 с типовой персистентностью через Run-ключ: от получения алерта Sysmon до верификации, анализа артефактов и восстановления. На каждом шаге используются реальные (или приближенные к реальным) команды и структуры данных, формирующие у студента практическое понимание процедуры.
