# Признаки злоупотребления: нетипичные задачи, пути и триггеры в планировщике задач Windows

## Анатомия злоупотреблений: планировщик задач как мишень для персистентности и скрытности

Планировщик задач Windows (Task Scheduler) — встроенный компонент операционной системы, обеспечивающий выполнение произвольных действий по наступлению заданных условий. Его ключевая функция — автоматизация обслуживания системы и прикладного программного обеспечения. Однако именно гибкость настроек и интеграция в доверенную среду делают планировщик привлекательным инструментом для злоумышленников: от закрепления после эксплуатации уязвимости до латерального перемещения и эскалации привилегий. Для аналитика SOC L1 критически важно разграничивать нормальную активность и признаки компрометации, сосредотачивая внимание на аномалиях в конфигурациях задач, путях к исполняемым файлам и задействованных триггерах.

**Базовые понятия.** Задача (task) представляет собой совокупность конфигураций, определяющих, *что* (действия), *когда* (триггеры) и *при каких условиях* (дополнительные параметры) должно быть выполнено. Действие (action) — запуск программы, отправка электронной почты или отображение сообщения; практически во всех вредоносных сценариях используется запуск программы. Триггер (trigger) задаёт расписание или событие, инициирующее выполнение. Условия (conditions) определяют дополнительные ограничения, например, запуск только при питании от сети или бездействии. Контекст выполнения задачи определяется учётной записью (principle), под которой она выполняется, и флагом «Выполнять с наивысшими правами» (run with highest privileges). Злоупотребление планировщиком фиксируется в тактике MITRE ATT&CK **T1053.005 – Scheduled Task** именно как техника персистентности, но также применима для исполнения (Execution) и повышения привилегий (Privilege Escalation).

**Признаки злоупотребления: нетипичные задачи.** Легитимные задачи хорошо структурированы, создаются преимущественно доверенными установщиками или системными службами, используют цифровые подписи Microsoft или известных вендоров, размещаются в иерархических папках (`\Microsoft\Windows\...`) и редко модифицируются вне циклов обновлений. Вредоносная задача, напротив, проявляет один или несколько из следующих признаков:
- Находится в корне библиотеки планировщика (`\`) или в нестандартной папке, имитирующей легитимное имя (например, `\Microsoft\Windows\UpdateTask` — с намеренным искажением названия).
- Содержит действие запуска исполняемого файла из подозрительного расположения: временные папки пользователя (`%TEMP%`, `%APPDATA%`), скрытые директории (`AppData\Roaming\...`), сетевые ресурсы (пути UNC).
- Использует триггер, несвойственный окружению — например, «При запуске компьютера» для задачи, которая не требует прав администратора и не относится к драйверам или службам.
- Выполняется с правами Local System или высокопривилегированной учетной записи без видимой необходимости.
- Обладает нехарактерной частотой срабатывания (повтор каждые 5 минут на протяжении нескольких дней) или скрытыми триггерами, такими как «По простою» или «При подключении сеанса».
- Не имеет описания или его текст составлен из бессмысленного набора символов/Base64, что может указывать на автоматизированное развертывание вредоносным фреймворком.

При расследовании подозрительной задачи аналитик должен оперировать не изолированными признаками, а их корреляцией. Отдельно взятый путь `%ProgramData%\Microsoft\Windows\Start Menu\Programs\Startup` вполне легитимен для некоторых задач, но в сочетании с триггером «At logon» и исполняемым файлом, чья цифровая подпись не соответствует Microsoft, становится индикатором компрометации.

Следующая таблица иллюстрирует ключевые различия между ожидаемыми, допустимыми пользовательскими и вероятными вредоносными задачами.

| Характеристика               | Легитимные системные задачи                 | Пользовательские/административные задачи   | Подозрительные / вредоносные задачи       |
|------------------------------|---------------------------------------------|--------------------------------------------|--------------------------------------------|
| **Расположение в иерархии**  | `\Microsoft\Windows\...`, `\Microsoft\Office\...` | `\TaskScheduler\`, собственные папки администратора | `\`, поддельные каталоги с орфографическими ошибками |
| **Исполняемый файл (путь)**  | `C:\Windows\System32\...`, `%ProgramFiles%\...` | `C:\Tools\`, программные каталоги          | `%TEMP%\`, `%APPDATA%\Roaming\`, UNC-пути (`\\192.168...`), скрытые папки |
| **Цифровая подпись**         | Microsoft Corporation, доверенные издатели   | Ожидаемый вендор (например, Adobe, Oracle) | Отсутствует, самозаверяющая, несовпадающая   |
| **Триггеры**                 | При запуске, ежедневные, по событиям служб   | По расписанию, вход пользователя           | Нетипичные (on idle, on event log), частый повтор (< 5 мин), несколько триггеров разных типов |
| **Контекст учётной записи**  | SYSTEM, NETWORK SERVICE, LOCAL SERVICE       | Собственная учётная запись пользователя    | SYSTEM, администратор, пользователь с флагом «Выполнять с наивысшими правами» без необходимости |
| **Описание/метаданные**      | Чёткое описание функции                      | Содержит пояснение (часто заполненное)     | Пустое, garbled, Base64-строка, поддельное имя «Flash Update» |
| **Частота создания/модификации** | Редкая, в рамках обновлений ОС            | По мере необходимости                      | Внезапное создание в момент инцидента, изменение существующей задачи |

Такая дифференциация позволяет на первом этапе триажа быстро отсеивать очевидно подозрительные объекты из потока событий, фокусируя усилия на детальном анализе.

Злоупотребление планировщиком редко бывает изолированным: вредоносная задача, как правило, является следствием выполнения скрипта, дроппера или post-exploitation фреймворка (Cobalt Strike, Empire, Metasploit). Поэтому SOC-аналитик, заметивший аномальную задачу, должен немедленно инициировать проверку родительских процессов создания задачи (обычно `svchost.exe` с параметром `-k netsvcs` для штатных механизмов, либо `schtasks.exe`, `powershell.exe` при ручном создании), а также проверить сопутствующие артефакты: записи реестра, службы, запуск WMI. Это позволяет восстановить полную картину атаки, не ограничиваясь точечным удалением задачи.

## Структура задачи как вектор атаки: пути, триггеры и аномальные конфигурации

Планировщик задач хранит конфигурации в реестре (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tasks` для 64-разрядных систем), а также в XML-файлах `%SystemRoot%\System32\Tasks`. Каждая задача определена набором XML-элементов, регламентированных схемой Microsoft. Аналитику важно понимать внутреннее устройство, так как злоумышленники манипулируют именно полями `Actions`, `Triggers` и `Principals`, чтобы замаскировать вредоносную нагрузку.

**Компоненты задачи.**  
Схематически задачу можно представить следующим образом:

```text
[Task]
 ├─ RegistrationInfo (описание, автор, дата)
 ├─ Triggers (набор событий запуска)
 │   ├─ Trigger (тип, параметры, задержка, повтор)
 │   └─ ...
 ├─ Settings (множественные параметры)
 ├─ Principals (контекст безопасности)
 │   └─ Principal (UserId, LogonType, RunLevel)
 ├─ Actions (список действий)
 │   └─ Action (Exec/ComHandler/Email/Message)
 │       ├─ Command
 │       ├─ Arguments
 │       └─ WorkingDirectory
 └─ ...
```

Из этой структуры для выявления аномалий наиболее критичны три элемента: `Actions` (определяют **пути** к исполняемым файлам и аргументы), `Triggers` (тип и временные характеристики **триггеров**) и `Principals` (учётная запись и уровень привилегий). Именно через манипуляцию ими злоумышленник достигает скрытности и персистентности.

### Пути в действиях (Actions)

Элемент `Action` типа `Exec` (наиболее частый) содержит:
- `Command` – полный путь к исполняемому файлу или команде.
- `Arguments` – передаваемые параметры.
- `WorkingDirectory` – рабочая папка (часто равна каталогу исполняемого файла, но может быть изменена).

Вредоносные задачи эксплуатируют доверие к стандартным системным директориям, размещая вредоносный бинарник вне них. Классификация нетипичных путей:

| Тип пути                   | Примеры каталогов                                         | Характер угрозы                                      | Контрмеры / наблюдения                             |
|----------------------------|-----------------------------------------------------------|------------------------------------------------------|----------------------------------------------------|
| Временные и пользовательские папки | `%TEMP%`, `%APPDATA%\Local\Temp`, `%LOCALAPPDATA%`      | Типичное место дропа загрузчиков, bat-скриптов; отсутствие легитимных задач | Мониторинг создания задач, указывающих на эти каталоги; правило Sigma на `Command` с регулярным выражением `(?i)(\\AppData\\Local\\Temp\\|%TEMP%)` |
| Сетевые ресурсы (UNC)      | `\\10.0.0.5\share\payload.exe`, `\\fileserver\hidden\evil.dll` | Загрузка кода по SMB/WebDAV; выполнение без копирования на диск | Контроль создания задач с UNC-путями; анализ SMB-трафика |
| Скрытые или нестандартные системные папки | `C:\ProgramData\Microsoft\Windows\Start Menu\Programs\Startup\evil.lnk`, `C:\Windows\System32\Tasks\` (не XML, а исполняемый) | Мимикрия под легитимную структуру, но неверное местоположение | Сверка путей с эталонной конфигурацией ОС |
| Сочетание легитимного процесса с вредоносными аргументами | `Command: "C:\Windows\System32\cmd.exe"`, `Arguments: "/c powershell -enc <Base64>"` | Обход белых списков путей; запуск интерпретатора с закодированной нагрузкой | Разбор аргументов в команде, поиск patten `-enc`, `IEX`, `Start-Process` |
| Короткие имена (8.3 формат) или симлинки | `C:\PROGRA~1\EVILAP~1\run.exe`                           | Затруднение визуального анализа, обход простых текстовых правил | Раскрытие коротких имён при анализе, учёт символических ссылок |

Аналитик должен уметь отличать легитимные задачи, использующие переменные окружения (`%WINDIR%`) или пути установки приложений, от вредоносных. На практике, если задача с именем, напоминающим системное обновление, запускает `%APPDATA%\ms\update.exe`, то высока вероятность компрометации.

### Триггеры (Triggers)

Планировщик поддерживает более десятка типов триггеров. Каждый имеет свой идентификатор (Type) и параметры. Злоумышленники выбирают те, которые минимизируют частоту обнаружения и максимизируют надёжность персистентности. Ниже представлены основные типы и их потенциал для злоупотреблений.

| Идентификатор типа (TASK_TRIGGER_TYPE) | Описание                                | Легитимное использование                      | Вредоносный сценарий                                    | Индикаторы злоупотребления                              |
|--------------------------------------|-----------------------------------------|----------------------------------------------|--------------------------------------------------------|---------------------------------------------------------|
| 1 (EVENT_TRIGGER_EVENT)              | На основе события в журнале Windows    | Реакция на критический сбой службы            | Запуск кода при регистрации определённого события (Event ID 4688 и др.), скрытое сохранение | Задачи с триггером на события безопасности (несистемные источники), либо на редко используемые каналы |
| 2 (TIME_TRIGGER_DAILY)               | Ежедневно в указанное время            | Резервное копирование, отчёты                | Замаскированное выполнение бэкдора каждые 24 часа        | Внезапное появление новой задачи с ежедневным триггером вскоре после подозрительного входа |
| 3 (TIME_TRIGGER_WEEKLY)              | Еженедельно                            | Обслуживание, обновления сигнатур антивируса  | Аналогично ежедневному, но реже                         | Недельная задача, указывающая на пользовательский каталог |
| 4 (TIME_TRIGGER_MONTHLY)             | Ежемесячно                             | Финансовые отчёты                            | Редко используется, т.к. долгий интервал                 | Присутствие месячного триггера у задачи с недавней датой создания — аномалия |
| 5 (TIME_TRIGGER_MONTHLYDOW)          | Раз в месяц по дням недели             | Специфичные корпоративные скрипты            | Аналогично                                              |                                                         |
| 6 (TIME_TRIGGER_IDLE)                | При бездействии компьютера             | Дефрагментация диска, индексация поиска       | Активация только тогда, когда пользователь отсутствует, но система включена; сложно отследить запуск | Задача без видимой связи с техническим обслуживанием, выполняющаяся при простое; обычно должна быть подписана Microsoft |
| 7 (REGISTRATION_TRIGGER)             | При создании/изменении задачи          | Не используется для выполнения действий       | Теоретически возможен, но крайне редок                   | Нестандартный; любое появление подозрительно              |
| 8 (TIME_TRIGGER_ONCE)                | Однократно в указанное время           | Установочные скрипты, финальная очистка        | Запуск вредоносной нагрузки ровно один раз (логическая бомба) | «Одноразовая» задача, оставшаяся активной после завершения инцидента |
| 9 (EVENT_TRIGGER_SESSION_STATE_CHANGE) | При подключении/отключении сеанса пользователя | Синхронизация параметров пользователя         | Запуск keylogger'а сразу после входа пользователя в систему | Задача с триггером «At logon» без привязки к легитимному профилю, особенно при выполнении из подозрительного пути |
| 10 (EVENT_TRIGGER_AT_TASK_CREATION)  | При создании задачи                    | Практически не используется                   | Возможно, для самоуничтожения или репликации             | Крайне аномально, признак вредоносного framework        |
| 11 (MACHINE_TRIGGER_ON_IDLE)         | При простое машины (ранее отдельный тип) | Очистка кэша                                  | Аналогичен IDLE_TRIGGER                                 |                                                         |
| 12 (EVENT_TRIGGER_ON_LOCK)           | При блокировке рабочей станции         | Шифрование временных файлов                   | Запуск кода при блокировке экрана (негативный сценарий — скрытая активность, пока пользователь отошел) | Должен соответствовать политикам безопасности; задачи от неподписанных издателей подозрительны |

Наиболее часто вредоносные задачи используют комбинацию: триггер **«При запуске системы»** (Boot trigger, не указан в таблице, это тип 8? Уточним: в структуре триггеров тип BOOT_TRIGGER = 8, но он подразумевает выполнение при загрузке ОС, независимо от входа пользователя). Этот триггер аналогичен TIME_TRIGGER_ONCE со специальным флагом, и часто фигурирует в вредоносных схемах для получения максимально ранней персистентности.

Не менее важен параметр повторения (`Repetition`), который позволяет настроить периодический запуск задачи с интервалом вплоть до одной минуты. Злоумышленники, использующие трояны удалённого доступа (RAT), часто создают задачу, которая каждые 5–15 минут обращается к командному центру, при этом сам триггер — «At logon» с бесконечным повторением. Такой паттерн легко детектировать, так как административные задачи обычно не требуют столь частого выполнения при входе пользователя.

Другой метод — использование триггера «При событии» (event-based) для срабатывания на специфические события, например, открытие определённого приложения или подключение USB-устройства. Он сложнее в выявлении, так как требует анализа подписок на события, и может быть упущен при беглом просмотре списка задач. Аналитик должен обращать внимание на наличие задач, привязанных к нетипичным каналам журналов (не System или Application).

**Условия и контекст безопасности.**  
Кроме раздела `Triggers`, на скрытность влияют условия (IdleSettings, NetworkSettings), но их редко используют вредоносные программы напрямую. Важнее поле `Principal`: атакующие стремятся выполнять код либо с правами `SYSTEM`, чтобы иметь доступ ко всем ресурсам, либо с правами текущего пользователя, но с флагом «Выполнять с наивысшими правами». При этом LogonType часто устанавливается в `S4U` (Service-for-User) — это легитимный механизм, но применяемый задачами, которые должны запускаться независимо от входа пользователя. Вредоносная задача с контекстом `InteractiveToken` и запросом административных прав при каждом входе любого пользователя — типичная попытка повышения привилегий.

Итогом анализа структуры должно стать понимание, что аномальная задача объединяет несколько неправомерных характеристик: подозрительный путь `Command`, нетипичный триггер с частым повторением и повышенные привилегии. Идентификация любого из этих компонентов на начальном этапе SOC L1 служит триггером для эскалации инцидента и углублённого расследования.

## Практическое обнаружение: команды, логи и инструментарий аналитика SOC L1

Обнаружение нетипичных задач, путей и триггеров в пределах мониторинга уровня 1 базируется на трёх столпах: утилиты командной строки для ручного аудита, централизованный сбор событий Windows и простые автоматизированные правила анализа. Аналитик должен уметь быстро идентифицировать подозрительные артефакты по чётким критериям, не углубляясь в объёмный форензический разбор.

### Ручное перечисление задач с фильтрацией

Основная утилита — `schtasks.exe`, входящая в состав ОС. Она позволяет извлекать информацию о задачах как локально, так и с удалённых машин. Для выявления аномалий эффективен вывод в формате списка с подробными свойствами (`/fo LIST /v`), после чего применяется текстовый поиск и фильтрация.

**Пример 1: получение списка задач и поиск подозрительных путей.**  
Команда выгружает все задачи в текстовый файл:
```bash
schtasks /query /fo LIST /v > C:\temp\tasks_dump.txt
```
Затем аналитик может вручную или с помощью скрипта искать строки, содержащие индикаторы:
- `%TEMP%`, `%APPDATA%`, `%LOCALAPPDATA%`
- Пути UNC (`\\`)
- Исполняемые файлы в `C:\Users\Public`
- Строки с `-enc`, `-EncodedCommand`, `IEX` в аргументах

Более продвинутый способ — фильтрация с помощью PowerShell, где команда `Get-ScheduledTask` возвращает объект с детальными свойствами, что позволяет программно отсеивать легитимные задачи.

**Пример 2: поиск задач, запускающих исполняемые файлы из пользовательских временных каталогов, с помощью PowerShell:**
```powershell
Get-ScheduledTask | Where-Object {
    $_.Actions.Execute -like '*AppData\Local\Temp*' -or
    $_.Actions.Arguments -like '*-enc*'
} | Format-Table TaskName, TaskPath, @{n='Command';e={$_.Actions.Execute}}, @{n='Arguments';e={$_.Actions.Arguments}}
```
Ожидаемый вывод будет включать только подозрительные объекты, например:
```
TaskName       TaskPath         Command                                     Arguments
--------       --------         -------                                     ---------
UpdaterService \Microsoft\...   C:\Users\jdoe\AppData\Local\Temp\upd.exe   -server 10.0.0.5
RefreshCache   \                powershell.exe                              -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiA...
```

Затем для каждой выявленной задачи проводится ручной осмотр с `schtasks /query /tn "<taskname>" /fo LIST /v`, чтобы проанализировать триггеры и контекст выполнения.

### Анализ триггеров

При получении детального вывода задачи необходимо обратить внимание на блок `Triggers`. Например:
```
TaskName:                         \MaliciousUpdater
...
Triggers:
    Trigger 0:
        Type:                     At logon
        User:                     DOMAIN\jdoe
        Enabled:                  Yes
        Repetition:
            Interval:             00:15:00
            Duration:             1 day
            StopAtDurationEnd:    Yes
...
```
Триггер «At logon» (SessionStateChange) с повторением каждые 15 минут для пользовательской задачи из каталога `%APPDATA%` является классическим признаком заражения. Аналитику следует проверить, когда задача была создана: обычно на это указывает событие Event ID 4698 (Security) или Event ID 106 (Microsoft-Windows-TaskScheduler/Operational). Создание задачи немедленно после времени компрометации подтверждает подозрения.

Специфичный индикатор — триггер типа «On event» с фильтром на нестандартный канал. Например, задача может ожидать событие от `Microsoft-Windows-WMI-Activity/Operational` или от `Windows PowerShell`. Для выявления таких триггеров требуется запросить XML-представление задачи:
```powershell
$task = Get-ScheduledTask -TaskName "SuspiciousTask"
$triggers = $task.Triggers
$triggers | ForEach-Object { $_.CimInstanceProperties | ForEach-Object { "$($_.Name): $($_.Value)" } }
```
Если в выводе присутствует `Subscription` с нетривиальным XPath-запросом, задача подозрительна.

### Мониторинг журналов событий

SOC L1 в значительной мере опирается на SIEM-правила, агрегирующие события создания и изменения задач. Ключевые события:

- **Security Event ID 4698** — «A scheduled task was created». Содержит XML-представление задачи в поле `TaskContent`. Позволяет получить все параметры: путь `Command`, триггеры, контекст. Пример критического фильтра: `TaskContent contains "%APPDATA%"` или `TaskContent contains "<Repetition><Interval>PT5M"`.
- **Security Event ID 4702** — «A scheduled task was updated». Аналогично, фиксирует модификацию.
- **Microsoft-Windows-TaskScheduler/Operational Event ID 106** — задача зарегистрирована. Более детализирован, но требует включения этого журнала (включён по умолчанию на Windows 10/11). Включает User Context и путь задачи.
- **Event ID 140** — задача обновлена, Event ID 141 — задача удалена.

Для автоматизированного детектирования на уровне SOC L1 разрабатываются корреляционные правила, например:
```text
If Event ID 4698 occurs AND (TaskContent contains ('TEMP' or 'APPDATA')) AND (TaskContent not contains ('Microsoft Corporation as author'))
THEN generate alert with severity High.
```
Такой подход минимизирует ложные срабатывания и фокусирует внимание на аномалии. Однако аналитик должен верифицировать алерт дополнительным контекстом, так как могут существовать легитимные приложения, устанавливающие задачи в пользовательские каталоги (например, модули обновления браузеров). Здесь помогает проверка цифровой подписи исполняемого файла и анализ его репутации.

### Инструментарий и методика первичного реагирования

Помимо командной строки, аналитик может использовать Sysinternals Autoruns — графическую утилиту, которая в закладке «Scheduled Tasks» отображает все задачи и сразу подсвечивает неподписанные исполняемые файлы. Но в массовом SOC более применим сбор информации через PowerShell Remoting или агенты EDR. Штатный модуль PS `ScheduledTasks` даёт исчерпывающий доступ к задачам.

Типичный алгоритм действий аналитика L1 при получении уведомления о подозрительной задаче:
1. Изолировать хост от сети (если политика разрешает самоизоляцию уровня L1).
2. Снять дамп задач: `schtasks /query /fo LIST /v > \\collection_server\forensic\<hostname>_tasks.txt`.
3. Локально проверить параметры задачи по её имени, извлечённой из алерта: `schtasks /query /tn "\MaliciousUpdater" /fo LIST /v`.
4. Проверить цифровую подпись целевого исполняемого файла: `Get-AuthenticodeSignature -FilePath "<путь>"`.
5. Если подпись отсутствует или недоверенная — выгрузить образец в песочницу (при наличии процедур), запросить углублённый анализ второго уровня.
6. Задокументировать артефакты: триггеры, пути, аргументы, время создания, родительский процесс (из EDR-телеметрии).
7. При необходимости и разрешении старшего аналитика — временно отключить задачу через `schtasks /change /tn "\MaliciousUpdater" /disable` (НЕ удалять, чтобы сохранить для исследования).

Важно помнить: злоумышленники могут создать задачу от имени SYSTEM с настройкой «Скрытая задача» (флаг `Hidden` в реестре), что делает её невидимой для стандартного `schtasks /query`. Для полного охвата требуется анализ реестра `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tasks\{GUID}` напрямую, что уже выходит за рамки L1, но L1 должен знать о такой возможности и при подозрении инициировать эскалацию.

### Типичные ошибки анализа и ложные срабатывания

Аналитик L1 должен чётко разграничивать нестандартные, но легитимные конфигурации. Примеры:
- Некоторые процессы обновления ПО (например, Google Chrome, Mozilla) создают задачи, указывающие на `%LOCALAPPDATA%\...\update.exe`. Эти задачи подписаны доверенным сертификатом и имеют разумное описание.
- Корпоративные скрипты аудита часто помещают задачи в корень `\`, но с чётким документированием.
- Задачи с повторением в несколько минут могут быть частью мониторинга инфраструктуры (SCOM, SCCM). Ключ — их принадлежность системному контексту и подписи.

Поэтому приоритет при триаже отдаётся комбинации признаков: подозрительный путь + неподписанный файл + нетипичный триггер + создание в период инцидента.

## Сквозной практический пример: выявление вредоносной персистентности через задачу-имитацию обновления Windows

### Исходные условия

Рабочая станция под управлением Windows 10, 21H2. Пользователь сообщил о подозрительной активности (медленная работа, всплывающие окна). Первичный анализ SIEM показал ряд алертов на необычные сетевые соединения с хоста. Аналитик SOC L1 получил задание проверить персистентность на локальной машине, начав с планировщика задач. Инструментарий: `schtasks`, `PowerShell`, доступ к журналу Security локально и через EDR-агент.

### Шаг 1: Получение списка всех задач и выделение подозрительного элемента

Выполняется команда дампа всех задач в структурированный файл с последующим поиском по ключевым словам:
```bash
schtasks /query /fo LIST /v > tasks_full.txt
findstr /i /c:"%APPDATA%" /c:"%TEMP%" /c:"-enc" /c:"IEX" tasks_full.txt > suspicious_lines.txt
type suspicious_lines.txt
```
 Вывод:
```
HostName:                             DESKTOP-X
TaskName:                             \Microsoft\Windows\WindowsUpdateTask
...
Task To Run:                          C:\Users\jdoe\AppData\Local\Temp\winupd.exe -auto
...
```
Обнаружена задача с именем `WindowsUpdateTask`, но путь её размещения — `\Microsoft\Windows\`, что типично для системных задач. Однако исполняемый файл расположен во временной папке пользователя, что является аномалией.

### Шаг 2: Детальный анализ конфигурации подозрительной задачи

Выгрузка полной информации по задаче:
```bash
schtasks /query /tn "\Microsoft\Windows\WindowsUpdateTask" /fo LIST /v
```
Результат (иллюстративная схема значимых полей):
```
TaskName:                             \Microsoft\Windows\WindowsUpdateTask
Author:                               DESKTOP-X\jdoe
Description:                          Windows Update Service
Run As User:                          DESKTOP-X\jdoe
Run with highest privileges:          Yes
Schedule Type:                        At logon
Repeat: Every:                        00:05:00 for 1 day
Start Time:                           09:15:00
Start Date:                           2025-03-27
Actions:
    Type:                             Execute
    Command:                          C:\Users\jdoe\AppData\Local\Temp\winupd.exe
    Arguments:                        -auto
```
Атрибуты явно вредоносны:
- Автор — обычный пользователь, а не SYSTEM.
- Флаг «Выполнять с наивысшими правами» — попытка эскалации.
- Триггер «At logon» с повторением каждые 5 минут — явный признак RAT-инфраструктуры.
- Команда из временной папки с аргументом `-auto`.

### Шаг 3: Проверка цифровой подписи исполняемого файла

Проверка подлинности файла:
```powershell
Get-AuthenticodeSignature -FilePath "C:\Users\jdoe\AppData\Local\Temp\winupd.exe" | Format-List
```
Вывод:
```
SignerCertificate      : 
Status                 : NotSigned
Path                   : C:\Users\jdoe\AppData\Local\Temp\winupd.exe
```
Файл не имеет цифровой подписи. В то время как легитимные модули обновления Windows всегда подписаны сертификатом Microsoft Corporation. Это подтверждает подозрения.

### Шаг 4: Анализ журнала событий создания задачи и родительского процесса

Из EDR-консоли аналитик извлёк запись Event ID 4698 (создание задачи) для временной метки, близкой к началу инцидента. В XML-содержимом поля `TaskContent` чётко видны все параметры задачи. Также был отслежен процесс создания задачи:
```text
Process Create (Sysmon Event 1):
ParentProcess: C:\Windows\System32\cmd.exe
ParentCommandLine: "C:\Windows\system32\cmd.exe" /c powershell -exec bypass -enc SQBFAFAA...
Process: C:\Windows\System32\schtasks.exe
CommandLine: schtasks /create /tn "\Microsoft\Windows\WindowsUpdateTask" /tr "C:\Users\jdoe\AppData\Local\Temp\winupd.exe -auto" /sc ONLOGON /rl HIGHEST /f ...
```
Цепочка показывает, что задачу создал `cmd.exe`, запущенный с закодированной командой PowerShell. Это типичная техника post-exploitation фреймворков (Empire/Cobalt Strike). Наличие `-enc` и `bypass` дополнительно указывает на злонамеренную активность.

### Шаг 5: Изоляция и документирование

Аналитик L1, следуя регламенту:
1. Отключил задачу: `schtasks /change /tn "\Microsoft\Windows\WindowsUpdateTask" /disable`.
2. Собрал образец `winupd.exe` в защищённое хранилище.
3. Зафиксировал IOC: путь `C:\Users\jdoe\AppData\Local\Temp\winupd.exe`, имя задачи, триггеры, время создания.
4. Эскалировал инцидент второму уровню с приложением артефактов.

**Ожидаемый вывод:** пример демонстрирует, как использование нетипичного пути (временная папка), триггера с коротким повторением и контекста с наивысшими правами позволяет аналитику оперативно идентифицировать вредоносную задачу. Комбинация простых команд и анализа событий даёт достаточную уверенность для принятия мер и передачи на углублённое расследование.
