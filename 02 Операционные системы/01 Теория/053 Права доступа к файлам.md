# Права доступа к файлам в Linux

## Контекст, базовая модель и ключевые разграничения

Linux — многопользовательская операционная система, наследующая модель безопасности Unix. Контроль доступа к файлам и каталогам реализован на уровне файловой системы и базируется на трёх сущностях: владелец (user, u), группа (group, g) и все остальные (others, o). Каждому объекту файловой системы назначается идентификатор пользователя-владельца и идентификатор группы, а права доступа хранятся в метаданных (inode) и проверяются ядром при любой попытке операции.

Для SOC-аналитика понимание этой модели — фундамент при расследовании инцидентов: неправильно выставленные права часто становятся причиной компрометации, а в логах аудита (например, `ausearch`) фиксируются события изменения владения или прав. В рамках L1-разбора критически важно уметь быстро идентифицировать аномальные разрешения и соотносить их с потенциальным вектором атаки.

Базовый набор прав состоит из трёх операций: чтение (read, r), запись (write, w) и выполнение (execute, x). Они интерпретируются по‑разному в зависимости от типа объекта — обычного файла или каталога. Путаница между этими интерпретациями — частая ошибка начинающих; таблица ниже фиксирует различия.

| Право | Для обычного файла | Для каталога |
|-------|-------------------|--------------|
| r (чтение) | Открытие и чтение содержимого файла. Программы могут загружать динамические библиотеки, считывать конфигурации. | Просмотр имён файлов внутри каталога (команда `ls` без `-l`). Без права `x` на каталог `r` бесполезно. |
| w (запись) | Изменение содержимого файла, дозапись, усечение. Удаление файла **не** требует `w` на сам файл — нужно `w` на родительский каталог. | Создание и удаление файлов/подкаталогов внутри каталога. Для удаления файла не нужно прав на него, достаточно `w` на каталог и `x` на весь путь. |
| x (выполнение) | Запуск файла как программы (если он является исполняемым бинарным файлом или скриптом с корректным shebang). Для библиотек и модулей ядра обычно `x` не требуется. | Вход в каталог (сделать его текущим, использовать в путях). Без `x` невозможно получить доступ ни к одному объекту внутри, даже если известны имена. |

Помимо базовых прав, в расширенной модели присутствуют специальные биты (SUID, SGID, sticky bit), которые модифицируют поведение при выполнении или наследовании группы. Они будут рассмотрены во втором разделе как часть внутреннего устройства прав.

Каждый пользователь обладает уникальным числовым идентификатором UID, а каждая группа — GID. При создании файла ядро записывает в inode UID текущего процесса и GID родительского каталога (если не установлен SGID-бит, тогда наследуется группа каталога). Именно эти идентификаторы используются при проверке доступа, а не символьные имена. Отображение имён на числа происходит через `/etc/passwd` и `/etc/group`, однако система оперирует именно числами, что важно при анализе файловых систем или контейнеров, где пространство имён может отличаться.

Порядок проверки прав жёстко детерминирован и выполняется ядром за одну атомарную операцию:

```text
Process UID == file owner UID ?
├── Да → применяются права владельца (user), проверка закончена.
└── Нет
    └── Process GID (или любая дополнительная группа) == file group GID ?
        ├── Да → применяются права группы (group), проверка закончена.
        └── Нет → применяются права остальных (others).
```

Важно: права владельца имеют приоритет над правами группы и остальных. Если владелец состоит в группе-владельце файла, но у него установлены права, скажем, `---` на уровне user, то он не получит доступ, даже если для группы разрешено `rwx`. Эта логика критична при разборе ситуаций, когда пользователь root-ом добавил себя в группу, но не может прочитать файл — владелец перекрывает группу.

Дополнительный уровень контроля предоставляет ACL (Access Control Lists), позволяющий назначать права конкретным пользователям и группам вне основной триады. В базовом курсе SOC L1 работа с ACL обычно не является обязательной, однако важно знать о существовании `getfacl` и `setfacl`, потому что в выводах `ls -l` расширенные права отображаются символом `+` в конце строки режима.

Таким образом, базовая концепция прав доступа в Linux строится вокруг триады «владелец-группа-остальные», трёх типов операций и жёсткого порядка проверки. Чёткое разграничение поведения прав для файлов и каталогов избавляет от многих ошибок конфигурации и помогает быстрее идентифицировать первопричину отказа в доступе, регистрируемого в логах ядра (обычно `Permission denied`).

## Внутреннее устройство: от битов до umask

Права доступа хранятся в поле `mode` inode, которое включает тип файла и 12 бит разрешений. При отображении командой `ls -l` первые 10 символов строки режима выглядят, например, как `-rwxr-xr--`. Структура этой записи стандартизирована и может быть визуализирована следующим образом:

```text
Символ 1      : тип файла (- обычный, d каталог, l символическая ссылка и т.д.)
Символы 2-4   : права владельца (r, w, x, -)
Символы 5-7   : права группы
Символы 8-10  : права остальных

Пример: -rwxr-xr--
Тип: обычный файл
Владелец: rwx (чтение, запись, выполнение)
Группа:   r-x (чтение, выполнение)
Остальные: r-- (только чтение)
```

На уровне битов права кодируются тремя восьмеричными цифрами (или четырьмя, если учитывать специальные биты). Каждая цифра — сумма значений: 4 (r), 2 (w), 1 (x). Соответствие между символами и восьмеричными значениями представлено в таблице ниже.

| Восьмеричное значение | Символы  | Смысл |
|------------------------|----------|-------|
| 0 | `---` | Нет прав |
| 1 | `--x` | Только выполнение |
| 2 | `-w-` | Только запись |
| 3 | `-wx` | Запись и выполнение |
| 4 | `r--` | Только чтение |
| 5 | `r-x` | Чтение и выполнение |
| 6 | `rw-` | Чтение и запись |
| 7 | `rwx` | Полный доступ |

Таким образом, режим `rwxr-xr--` эквивалентен числу 754. Эта нотация используется в командах `chmod`, `umask` и многих системных вызовах.

Специальные биты расширяют базовую модель и индицируются в строке режима за счёт переиспользования позиций execute-битов:

- **SUID (4xxx)** — на месте пользовательского `x` отображается `s` (или `S`, если execute не установлен). Применяется к исполняемым файлам: процесс получает эффективный UID владельца файла, а не запустившего пользователя. Классический пример — `/usr/bin/passwd`, позволяющий обычному пользователю менять пароль, записывая в `/etc/shadow`.
- **SGID (2xxx)** — аналогично, но для группы (символ `s` в позиции группы). Влияет на наследование группы для новых объектов внутри каталога: файлы, создаваемые в каталоге с SGID, наследуют группу каталога, а не первичную группу создателя. Это широко используется для совместной работы над проектами.
- **Sticky bit (1xxx)** — отображается как `t` в позиции остальных (если execute есть) или `T` (без execute). Для каталогов запрещает удаление файлов не-владельцами, даже если у них есть запись в каталог. Классический пример — `/tmp` с режимом `1777`.

Четырёхзначная восьмеричная нотация специальных битов: SUID=4, SGID=2, sticky=1, записываются перед основной триадой, например, `4755` включает SUID и права `755`.

Теперь рассмотрим, как формируются права у вновь создаваемых объектов. За это отвечает **umask** — битовая маска, которая «вычитается» из максимально возможных прав. Максимальные права для файлов — 666 (rw-rw-rw-), для каталогов — 777 (rwxrwxrwx). При создании объекта ядро выполняет побитовую операцию `(max_permissions & ~umask)`. Обратите внимание: umask не добавляет прав, а только ограничивает. Стандартное значение umask во многих дистрибутивах — 022, что даёт для каталогов 755, для файлов 644.

Иллюстрация вычисления:
- umask = 022 (восьмерично) → битовая маска `000 010 010`
- Каталог: 777 & ~(022) = 777 & 755 = 755
- Файл: 666 & ~(022) = 666 & 644 = 644

Из-за того, что для файлов максимальные права уже лишены бита execute, никакое значение umask не может заставить новые файлы создаваться исполняемыми. Требуется явный `chmod +x`. Это фундаментальное правило безопасности Unix: созданный файл никогда не будет выполняться автоматически.

Просмотреть текущий umask можно командой `umask` (в восьмеричном виде) или `umask -S` (в символьном). Установка umask действует на текущий сеанс оболочки и наследуется дочерними процессами. Постоянные значения обычно задаются в `/etc/profile` или `/etc/bash.bashrc`.

С точки зрения SOC L1, umask важен при анализе конфигураций и инцидентов: ослабленная umask (например, `umask 000`) приводит к тому, что новые файлы создаются со слишком открытыми правами, открывая возможности для локальной атаки. В логах аудита это не фиксируется, поэтому аудит umask входит в регулярные проверки безопасности.

## Применение и практическая работа с разрешениями

Основные утилиты для управления правами: `chmod`, `chown` и `chgrp`. Просмотр текущих прав выполняется командой `ls -l`, а для ACL — `getfacl`. В SOC L1 важно не только уметь изменять права, но и правильно интерпретировать их вывод в ходе расследования или при проверке конфигурации.

**Команда chmod** поддерживает два режима: символьный и числовой. Символьный режим оперирует мнемониками:

- `who`: `u` (user), `g` (group), `o` (others), `a` (all, эквивалент `ugo`).
- `operator`: `+` (добавить), `-` (убрать), `=` (установить точно).
- `permissions`: `r`, `w`, `x`, `X` (специальный: добавляет выполнение только если для какой-то категории уже есть execute, полезен для каталогов), `s` (SUID/SGID), `t` (sticky).

Примеры символьного режима:

```bash
# Добавить владельцу право выполнения на скрипт
chmod u+x script.sh

# Убрать у группы права записи
chmod g-w file.txt

# Установить остальным только чтение
chmod o=r document.pdf

# Комбинированная операция: добавить выполнение владельцу и группе, убрать запись у остальных
chmod ug+x,o-w script.sh
```

Числовой режим более лаконичен и часто используется в скриптах и инструкциях. Каждая цифра задаёт комбинацию прав для владельца, группы и остальных.

```bash
# Владелец rwx, группа r-x, остальные r-x — типично для исполняемых файлов и каталогов
chmod 755 /usr/local/bin/tool

# Только владелец rw, остальные без прав — для приватных ключей
chmod 600 ~/.ssh/id_rsa

# Владелец rw, группа r, остальные r — для конфигураций
chmod 644 /etc/myapp/config.yaml
```

В SOC-контексте быстрое восстановление прав числовым методом предпочтительнее: оно исключает ошибки интерпретации текущих прав, сразу задавая целевую маску.

Флаг `-R` (рекурсивное применение) изменяет права каталога и всего его содержимого. Это мощный, но опасный инструмент: применение `chmod -R 777` к системным каталогам делает систему легкодоступной для атакующего. Рекомендуется всегда разделять установку прав на каталоги и файлы:

```bash
# Для каталогов — добавить execute, но убрать запись для группы и остальных (типично 755)
find /path -type d -exec chmod 755 {} \;

# Для файлов — убрать execute, оставить только чтение (644)
find /path -type f -exec chmod 644 {} \;
```

**Команды chown и chgrp** изменяют владельца и группу файла. Синтаксис:

```bash
# Смена владельца
chown user1 file.txt

# Смена владельца и группы одновременно
chown user1:group1 file.txt

# Рекурсивная смена владельца и группы на каталог
chown -R www-data:www-data /var/www/html
```

При работе с SOC-инцидентами важно помнить: обычный пользователь не может передать владение файлом другому пользователю, только root может выполнить `chown`. Это предотвращает попытки скрытия следов, но также означает, что если злоумышленник получил root, он может изменить владельца критических файлов. Контроль целостности (например, AIDE) фиксирует такие изменения.

**Утилита id** позволяет быстро проверить текущий UID, GID и дополнительные группы. Это необходимо при диагностике отказа в доступе:

```bash
id
# uid=1000(student) gid=1000(student) groups=1000(student),4(adm),27(sudo)
```

Если пользователь не может получить доступ к файлу, хотя состоит в группе, стоит проверить вывод `id`, т.к. изменения групп вступают в силу только при новом входе в систему.

**Эскалация привилегий** через `su` и `sudo` напрямую связана с правами доступа. `su` полностью переключает сессию на другого пользователя (требует пароль целевого пользователя, если не root). `sudo` выполняет одну команду с правами root (или другого пользователя согласно конфигурации `/etc/sudoers`). В SOC-расследованиях анализ прав `sudo` — отдельная задача: пользователь с `sudo ALL` может делать что угодно. Но в контексте файловых прав `sudo` позволяет временно обходить ограничения, например, читать чужие файлы с правами 600.

Типичные контрольные цифры прав, применяемые в индустрии и запрашиваемые на собеседованиях SOC:

- **Приватные SSH-ключи** — 600, иначе SSH-клиент откажется их использовать.
- **Конфигурационные файлы с чувствительными данными** (пароли, токены) — 600 или 400, владелец root.
- **Веб-директории**: каталоги — 755, файлы — 644, чтобы веб-сервер (часто www-data) мог читать, но не записывать. Записываемые каталоги для загрузок — 755 с владельцем веб-сервера, возможно 775.
- **Исполняемые скрипты** — 755, реже 750, если должны запускаться только членами определённой группы.
- **/tmp** — 1777 (sticky bit обязателен для предотвращения удаления чужих временных файлов).

При аудите или пентесте слишком открытые права — сигнал к дальнейшему исследованию. Например, `find / -perm -o+w -type f` перечислит все файлы, доступные для записи всем, что может указывать на ошибку конфигурации или закладку. SOC L1 может использовать эту команду в рамках проверки по инциденту.

**Подводные камни:**

1. Права на символические ссылки не имеют значения; система всегда проверяет права целевого файла. Поэтому `chmod` на симлинк изменит права оригинала.
2. Скрипты с shebang требуют права на чтение и выполнение (r+x), иначе ядро не сможет загрузить интерпретатор. Даже `chmod 700` не позволит выполнить скрипт от имени другого пользователя, если тот не может прочитать сам файл — интерпретатор открывает файл для чтения.
3. `chmod 777` — всегда ошибка. Если владелец — root, а права 777, злоумышленник может записать в файл вредоносный код и дождаться выполнения.
4. Изменение прав через `chmod` требует либо владения файлом, либо привилегий root. При расследовании инцидента полезно искать события `chmod` в логах аудита (syscall `chmod` с необычными масками).

Таким образом, практическое владение командами `chmod`, `chown`, `umask` и вспомогательными утилитами составляет основу ежедневной работы администратора и является обязательным навыком SOC-аналитика при валидации инцидентов и первичном реагировании.

## Сквозной практический пример: защита приватного SSH-ключа

Сценарий имитирует ситуацию, типичную для разбора инцидента или начальной настройки сервера. Пользователь `analyst` создал пару SSH-ключей, но не установил корректные права. При попытке подключения клиент выдаёт ошибку. Необходимо диагностировать проблему, исправить права и подтвердить доступ. Пример выполняется на стандартном дистрибутиве Linux (Ubuntu 22.04 LTS) с учётной записью `analyst`.

**Исходные условия:**
- Пользователь: `analyst` (UID 1000).
- Имеется закрытый ключ `~/.ssh/id_rsa`, созданный командой `ssh-keygen`.
- На целевом сервере `lab-server` настроен доступ по ключу.
- Задача: обеспечить корректные разрешения, при которых ключ принимается клиентом OpenSSH.

### Шаг 1: Просмотр текущих прав и диагностика ошибки

Выполняем `ls -l`, чтобы увидеть исходные права ключа. Затем пробуем подключение и фиксируем ошибку.

```bash
ls -l ~/.ssh/id_rsa
# -rw-r--r-- 1 analyst analyst 2602 Jan 16 10:23 /home/analyst/.ssh/id_rsa

ssh -i ~/.ssh/id_rsa analyst@lab-server
# Выходные данные (stderr):
# @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
# @         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
# @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
# Permissions 0644 for '/home/analyst/.ssh/id_rsa' are too open.
# It is required that your private key files are NOT accessible by others.
# This private key will be ignored.
# Load key "/home/analyst/.ssh/id_rsa": bad permissions
# analyst@lab-server: Permission denied (publickey).
```

Артефакт ясно указывает причину: права 0644 означают, что группа и остальные имеют право чтения (`r--`), что неприемлемо для приватного ключа. Клиент SSH требует, чтобы ключ был доступен только владельцу.

### Шаг 2: Исправление прав командой chmod

Устанавливаем значение 600 — только владелец читает и записывает, все остальные не имеют никаких прав.

```bash
chmod 600 ~/.ssh/id_rsa
```

Проверяем результат:

```bash
ls -l ~/.ssh/id_rsa
# -rw------- 1 analyst analyst 2602 Jan 16 10:23 /home/analyst/.ssh/id_rsa
```

### Шаг 3: Повторная попытка подключения и подтверждение успеха

Теперь права скорректированы согласно политике OpenSSH. Подключение должно пройти успешно (предполагается, что публичный ключ уже добавлен в `authorized_keys` на целевом сервере).

```bash
ssh -i ~/.ssh/id_rsa analyst@lab-server
# Welcome to Ubuntu 22.04 LTS ...
# analyst@lab-server:~$
```

Подключение установлено без ошибок, что подтверждает корректное применение прав.

### Шаг 4: Проверка попытки чтения ключа другим пользователем (демонстрация эффекта)

Чтобы продемонстрировать разницу, временно переключимся на учётную запись `observer` (UID 1001) и попробуем прочитать ключ.

```bash
su - observer -c "cat /home/analyst/.ssh/id_rsa"
# cat: /home/analyst/.ssh/id_rsa: Permission denied
```

Отказ в доступе ожидаем: права 600 запрещают чтение для всех, кроме владельца `analyst`. Если бы права были 644, `observer` смог бы скопировать ключ, что привело бы к компрометации.

**Ожидаемый вывод по итогам примера:** Продемонстрировано, как неверные права (0644) приводят к отказу клиента OpenSSH, а изменение на 600 решает проблему и восстанавливает безопасность. На практике SOC-аналитик может обнаружить подобный инцидент в отчёте сканера уязвимостей или при расследовании сообщения о подозрительном доступе: наличие приватных ключей с правами, отличными от 600, — немедленный индикатор потенциальной утечки.
