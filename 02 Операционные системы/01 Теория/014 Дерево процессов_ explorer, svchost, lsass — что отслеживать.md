# Дерево процессов: explorer, svchost, lsass — что отслеживать

## 1. Explorer.exe: норма и аномалии в дереве процессов

Explorer.exe является основным процессом графической оболочки Windows, предоставляя пользователю рабочий стол, панель задач, проводник файлов и меню «Пуск». Это первый процесс, запускаемый в интерактивной сессии пользователя после успешной аутентификации, и ключевая точка взаимодействия между пользователем и операционной системой. Знание нормальных характеристик explorer.exe и его роли в иерархии процессов позволяет аналитику SOC эффективно выявлять вредоносную активность — от банальной маскировки под легитимный процесс до сложных техник инъекции кода.

С точки зрения дерева процессов Windows, explorer.exe занимает позицию корневого процесса для всех пользовательских приложений, запущенных в конкретной сессии. Когда пользователь входит в систему, процессы winlogon.exe и userinit.exe инициируют запуск explorer.exe, после чего userinit.exe завершается, и explorer.exe остаётся без живого родительского процесса (в утилитах вроде Process Explorer родитель может отображаться как `<Non-existent Process>`). Сиротство explorer.exe — штатное поведение, которое важно отличать от подозрительного отсутствия родителя у других системных процессов. Каждый последующий экземпляр explorer.exe (например, открытый по комбинации Win+E) порождается уже существующим экземпляром.

Ниже приведена сводка нормальных и аномальных характеристик, которая служит базовой линией для мониторинга.

| Параметр | Норма | Аномалия (индикатор компрометации) |
|----------|-------|-----------------------------------|
| **Путь к образу** | `%SystemRoot%\explorer.exe` (обычно `C:\Windows\explorer.exe`) | Запуск из временных каталогов (`%TEMP%`, `%APPDATA%`), общедоступных папок (`C:\Users\Public`), смонтированных сетевых дисков. Любое отличие от `C:\Windows\explorer.exe` нетипичного пути. |
| **Родительский процесс** | `userinit.exe` (при входе) или `explorer.exe` (дочерние окна). После завершения `userinit.exe` родитель может отсутствовать. | `cmd.exe`, `powershell.exe`, офисные приложения, неизвестные процессы. Появление живого родителя, отличного от `explorer.exe`, после начального запуска сессии. |
| **Учётная запись** | Вошедший пользователь (доменный или локальный). Процесс работает в контексте интерактивной сессии. | Запуск от имени `SYSTEM`, `LOCAL SERVICE` или другого пользователя, не имеющего активного сеанса на рабочем столе. |
| **Количество экземпляров** | По одному экземпляру на каждый активный пользовательский сеанс, плюс дополнительные при открытии новых окон проводника (разделяют общий процесс по умолчанию, но возможны отдельные процессы при включённом параметре «Запускать окна с папками в отдельном процессе»). | Множественные экземпляры с разными пользователями в рамках одной сессии; необъяснимый рост числа процессов explorer.exe без действий пользователя. |
| **Цифровая подпись** | Подписано Microsoft Corporation. | Отсутствие подписи, подпись неизвестного издателя или несовпадение отпечатка. |
| **Дочерние процессы** | Пользовательские приложения (браузеры, офисные пакеты, интерпретаторы командной строки, запущенные осознанно пользователем). | Необычные дочерние процессы: `powershell.exe -enc ...`, `rundll32.exe` с подозрительными DLL, `wscript.exe`, `mshta.exe`; сетевые утилиты (`net.exe`, `nslookup.exe`), запущенные не пользователем. |
| **Сетевые соединения** | Подключения к внутренним сетевым ресурсам (сетевые диски, общие папки) инициируются процессом explorer.exe легитимно. | Исходящие соединения на внешние IP-адреса, особенно на нестандартные порты или к известным вредоносным C2. |

Злоумышленники используют explorer.exe несколькими способами. Самый очевидный — маскировка: вредоносный исполняемый файл получает имя `expl0rer.exe`, `explorer .exe` (с пробелом) или `explorer.exe` размещается в несистемном каталоге и добавляется в автозапуск. Более продвинутая техника — внедрение кода (Process Injection, T1055): легитимный процесс explorer.exe жертвует своей памятью для выполнения вредоносной нагрузки, что позволяет обходить контроль запуска приложений и скрывать сетевое взаимодействие за доверенным процессом. Ещё один вектор — использование explorer.exe как родителя: атакующий запускает shellcode через explorer.exe с помощью техники Parent PID Spoofing, чтобы дочерний вредоносный процесс выглядел порождённым легитимным родителем.

При расследовании инцидента особое внимание следует уделять событиям создания процессов (Sysmon Event ID 1) и загрузки DLL (Event ID 7) для образа explorer.exe. Мониторинг командной строки, пути образа и родительского процесса позволяет автоматизировать выявление аномалий. Дополнительно ценную информацию даёт анализ загруженных библиотек через Process Explorer: присутствие неизвестных DLL в адресном пространстве explorer.exe является сильным признаком инъекции.

ASCII-схема типичной иерархии для сессии пользователя:

```text
winlogon.exe ──▶ userinit.exe ──▶ explorer.exe (PID X) ──▶ приложения (chrome.exe, cmd.exe ...)
                 (завершается)       │ 
                                     ├──▶ explorer.exe (PID Y, новое окно) 
                                     │
                                     └──▶ ... (другие дочерние процессы)
```

В нормальном состоянии цепочка завершается быстро, и explorer.exe остаётся «сиротой», поэтому детектирование аномалий на основе родительского процесса должно учитывать этот нюанс.

Таким образом, мониторинг explorer.exe требует чёткого знания базовой линии и постоянного сопоставления с ней. Любое отклонение — подозрительный путь, необычный родитель, неожиданные сетевые соединения — должно инициировать глубокий анализ контекста события, чтобы вовремя выявить компрометацию пользовательской сессии.

## 2. Svchost.exe: архитектура и индикаторы компрометации

Процесс Service Host (svchost.exe) — это универсальный контейнер для запуска служб Windows, реализованных в виде динамических библиотек (DLL). Его главная задача — обеспечить изоляцию, группировку и управление жизненным циклом многочисленных системных и сторонних служб. В чистом виде svchost.exe не выполняет никакой полезной работы: он лишь загружает с помощью функции `svchost.exe -k <имя_группы>` одну или несколько служебных DLL, которые и являются реальными сервисами. Понимание внутренней архитектуры svchost.exe и его нормального поведения критически важно, поскольку этот процесс часто становится мишенью для инъекций и применяется злоумышленниками для маскировки вредоносной активности.

С точки зрения дерева процессов, все экземпляры svchost.exe порождаются процессом `services.exe` (менеджером служб), который, в свою очередь, запускается `wininit.exe`. Таким образом, полная родительская цепочка выглядит как `wininit.exe → services.exe → svchost.exe`. В некоторых конфигурациях возможен запуск svchost.exe непосредственно от `services.exe`, но никогда от пользовательского процесса или напрямую от `wininit.exe`. Количество экземпляров svchost.exe варьируется от десятка до нескольких сотен в зависимости от числа установленных служб и политики группировки, которая в современных системах (особенно при объёме ОЗУ >3.5 ГБ) склоняется к модели «одна служба — один процесс» для повышения надёжности.

Каждый экземпляр svchost.exe обязательно имеет параметр `-k` в командной строке, задающий имя группы служб. Группа объединяет службы со схожими требованиями безопасности или производительности. Примеры стандартных групп:

- `-k LocalSystemNetworkRestricted` — службы, работающие с ограниченным сетевым доступом;
- `-k LocalService` — службы с правами локальной учётной записи Local Service;
- `-k LocalServiceNetworkRestricted` — их ограниченная версия;
- `-k NetworkService` — службы от имени Network Service;
- `-k netsvcs` — многочисленные службы с правами SYSTEM;
- `-k DcomLaunch`, `-k RPCSS`, `-k UnistackSvcGroup` — группы для COM‑ и RPC‑ориентированных сервисов.

Путь к образу во всех случаях — `%SystemRoot%\System32\svchost.exe`. Любое отклонение по пути (например, `C:\Windows\Temp\svchost.exe`) или отсутствие параметра `-k` является высококритичным индикатором вредоносной активности.

Учётная запись, от которой запущен конкретный экземпляр, зависит от конфигурации служб, размещённых в группе. Типичные учётные записи: `NT AUTHORITY\SYSTEM`, `NT AUTHORITY\LOCAL SERVICE`, `NT AUTHORITY\NETWORK SERVICE`. Запуск svchost.exe от имени интерактивного пользователя возможен, но требует специальной настройки (например, для служб, взаимодействующих с рабочим столом). Аномальным будет появление svchost.exe от имени доменного пользователя без явной необходимости.

Время запуска первых экземпляров — в течение нескольких секунд после старта `services.exe`, то есть на раннем этапе загрузки ОС. Дополнительные экземпляры могут запускаться по мере активации служб. Важно понимать, что на одном компьютере сосуществуют несколько процессов svchost.exe с разными комбинациями `-k`, и это норма.

Злоумышленники активно эксплуатируют особенности svchost.exe. Известны следующие основные методы злоупотребления:

1. **Маскировка** — размещение вредоносного файла с именем `svchost.exe` во временных папках, добавление в реестр фиктивных служб, указывающих на этот файл. Обнаруживается по отсутствию параметра `-k`, пути образа и родителю.
2. **Подмена службы** — изменение параметра `ServiceDll` в реестре для существующей легитимной группы, чтобы svchost.exe загрузил вредоносную DLL вместо системной. Индикаторы: появление несвойственных DLL в списке загруженных модулей svchost.exe (можно увидеть в Process Explorer).
3. **Инъекция кода в запущенный svchost.exe** — внедрение вредоносного кода в легитимный процесс через техники типа Process Hollowing или классическую DLL‑инъекцию с последующим выполнением вредоносной нагрузки под видом системного процесса. Обнаруживается по аномальным правам доступа к памяти, загруженным библиотекам нестандартного происхождения или подозрительным сетевым соединениям от процесса.
4. **Запуск вредоносного процесса с подделкой родителя** — атакующий может создать svchost.exe с искусственно подставленным родителем `services.exe`, чтобы обойти эвристики. В этом случае необходимо дополнительно проверять путь образа и цифровую подпись.

Сравнительная таблица нормальных и аномальных свойств svchost:

| Параметр | Норма | Аномалия |
|----------|-------|----------|
| **Образ** | `C:\Windows\System32\svchost.exe` | Любой другой путь; имена, отличные от `svchost.exe` (например, `scvhost.exe`, `svhost.exe`). |
| **Родительский процесс** | `services.exe` | `explorer.exe`, `cmd.exe`, `powershell.exe`, любой пользовательский процесс; отсутствие родителя (сирота). |
| **Командная строка** | Начинается с `C:\Windows\system32\svchost.exe -k ...` | Отсутствие параметра `-k`; наличие непонятных ключей (`-e`, `-p`) или Base64-кодированных строк. |
| **Учётная запись** | `SYSTEM`, `LOCAL SERVICE`, `NETWORK SERVICE` | Интерактивный пользователь (без явной причины), низкопривилегированные пользователи, доменные учётные записи. |
| **Количество экземпляров** | Зависит от установленных служб; может быть несколько десятков. | Резкое увеличение количества после инцидента; единичный экземпляр при явно недостающем количестве для нормальной работы ОС (признак блокировки легитимных служб). |
| **Загруженные DLL** | Системные DLL из `System32`, подписанные Microsoft; специфичные службы (например, `dhcpcore.dll`, `dnsrslvr.dll`). | Библиотеки из временных каталогов, не подписанные или с подписью неизвестного издателя; DLL, характерные для вредоносного ПО. |
| **Сетевые соединения** | Соединения, инициируемые службами (DHCP, DNS, обновления Windows) к легитимным серверам. | Соединения с внешними IP, не связанными с рабочими функциями, особенно на нестандартные порты или с периодическими «маяками». |

Дерево процессов для svchost можно представить так:

```text
System (PID 4) ──▶ smss.exe ── ...
                └──▶ wininit.exe (PID 456)
                        └──▶ services.exe (PID 632)
                                ├──▶ svchost.exe -k DcomLaunch
                                ├──▶ svchost.exe -k RPCSS
                                ├──▶ svchost.exe -k netsvcs
                                └──▶ ... другие экземпляры
```

Мониторинг svchost.exe в SOC‑контексте должен основываться на журнале создания процессов (Event ID 1) и, при возможности, на событиях загрузки DLL (Event ID 7) при включённом Sysmon. Правила детектирования автоматически выделяют процессы с подозрительными путями, отсутствием ключа `-k` в команде или нетипичным родителем. В дополнение полезен анализ сетевых соединений на предмет сессий, инициированных процессами svchost.exe, которые не соответствуют профилю запущенных служб.

Таким образом, знание архитектуры Service Host и индикаторов компрометации позволяет отличить штатное поведение от действий злоумышленника, маскирующегося под легитимную службу.

## 3. Lsass.exe: критический процесс и векторы атак

Процесс Local Security Authority Subsystem Service (lsass.exe) выполняет центральную роль в системе безопасности Windows. Он отвечает за проверку учётных данных пользователей при входе, управление билетами Kerberos, обработку токенов доступа, аудит событий безопасности и хранение в памяти чувствительной информации: хешей паролей, ключей, билетов TGT и NTLM-сессий. Именно концентрация аутентификационных данных делает lsass.exe приоритетной целью для злоумышленников на этапе постэксплуатации и бокового перемещения в сети.

С точки зрения дерева процессов lsass.exe всегда один на всю систему. Он запускается процессом `wininit.exe` на ранней стадии загрузки, до того, как создаются пользовательские сессии. Родительская цепочка: `System → smss.exe → wininit.exe → lsass.exe`. После старта `wininit.exe` продолжает работать в фоне, и завершение любого из этих процессов влечёт крах системы. Путь к образу lsass.exe жёстко фиксирован: `%SystemRoot%\System32\lsass.exe`. Процесс работает под учётной записью `NT AUTHORITY\SYSTEM`, имеет высокие привилегии и защищён механизмом Protected Process Light (PPL) в современных версиях Windows, что ограничивает возможность даже администраторам открывать его память или внедрять код.

Тем не менее, атакующие постоянно совершенствуют техники обхода PPL и извлечения учётных данных из lsass.exe. Наиболее распространённые атаки классифицируются по MITRE ATT&CK как T1003.001 (OS Credential Dumping: LSASS Memory). Их вариации и необходимые условия приведены в таблице ниже.

| Техника атаки | Необходимые условия | Индикаторы (на уровне Sysmon / Windows) | Контрмера |
|---------------|---------------------|----------------------------------------|-----------|
| **Прямой дамп памяти с помощью MiniDump (procdump, comsvcs.dll)** | Административные привилегии; возможность вызвать `MiniDumpWriteDump` из `comsvcs.dll` или запустить `procdump.exe` с PID lsass. | Sysmon Event ID 10 — доступ к процессу lsass от procdump.exe, rundll32.exe с `comsvcs.dll`; Event ID 1 — запуск procdump с аргументом `-accepteula -ma <PID>`. | Credential Guard изолирует секреты в виртуализированной среде; ASR-правило «Block credential stealing from the Windows local security authority subsystem»; мониторинг вызова `MiniDumpWriteDump`. |
| **Mimikatz и его варианты (sekurlsa::logonpasswords)** | Возможность загрузить DLL в память (через `rundll32`, PowerShell) или выполнить от имени администратора, обходя PPL с драйвером. | Sysmon Event ID 7 — загрузка `mimikatz.dll` (или подозрительных DLL) в системный процесс; Event ID 10 — подозрительный доступ с правами `PROCESS_VM_READ`, `PROCESS_QUERY_INFORMATION`; Event ID 1 — запуск `mimikatz.exe`, `powershell -c "IEX (New-Object Net.WebClient).DownloadString(...)"` со скриптами Mimikatz. | Отключение отладочных привилегий для не-администраторов; контроль загрузки DLL с помощью AppLocker / WDAC; детектирование сигнатур Mimikatz в памяти. |
| **Использование легитимных средств (Task Manager, Process Explorer) для выгрузки дампа** | Интерактивный доступ с правами администратора, возможность открыть свойства lsass и выбрать «Создать дамп памяти». | Sysmon Event ID 10 — доступ от taskmgr.exe, procexp.exe к lsass; затем создание файла дампа в `%TEMP%`. | Ограничение интерактивного входа администраторов; аудит использования инструментов Sysinternals. |
| **Уязвимости ядра (например, CVE-2021-36934 «HiveNightmare»)** | Наличие незащищённых SAM, SYSTEM файлов, позволяющих извлечь хеши без прямого доступа к lsass. | Не связан напрямую с доступом к lsass — скорее с доступом к теневым копиям. | Установка обновлений безопасности, ограничение прав на каталог `%SystemRoot%\System32\config`. |

Помимо кражи учётных данных, злоумышленники могут подделывать сам процесс lsass для сокрытия активности. Распространённые тактики включают:

- **Маскировка имени:** `lsass.exe` (с двумя s), `lsasss.exe`, `ISASS.EXE` (заглавная I вместо l), размещённые вне System32.
- **Подмена образа:** копирование вредоносного файла в System32 под именем lsass.exe с предварительным переименованием легитимного (требует обхода TrustedInstaller).
- **Загрузка вредоносной DLL в lsass.exe:** инъекция через технику отражённой загрузки DLL или через легитимные механизмы (например, пакет аутентификации).

Нормальные характеристики lsass.exe, используемые как базовая линия:

- Путь к образу: `C:\Windows\System32\lsass.exe`
- Родительский процесс: `wininit.exe`
- Количество экземпляров: **ровно один**
- Учётная запись: `NT AUTHORITY\SYSTEM`
- Время запуска: в пределах первых секунд загрузки системы

Любое отклонение от этих параметров (несколько экземпляров, иной родитель, другой путь, работа от имени другого пользователя) — признак вмешательства. Даже если вредоносный процесс имеет допустимый путь, но запущен не от `wininit.exe`, это должно рассматриваться как инцидент высокой степени критичности.

Мониторинг lsass.exe строится вокруг событий доступа к процессу (Sysmon Event ID 10). Поскольку нормальные процессы, такие как антивирусы и средства мониторинга, регулярно открывают lsass, используется таргетированный подход: в конфигурации Sysmon в разделе `<ProcessAccess>` фиксируются только те доступы, где целевой процесс — `lsass.exe`, и исключаются заведомо легитимные программы (список формируется в соответствии с политикой организации). Дополнительную ценность даёт анализ загруженных в lsass.exe DLL (Event ID 7) — появление неподписанных или неизвестных библиотек является прямым доказательством инъекции.

```text
wininit.exe ──▶ services.exe ──▶ svchost.exe ...
            └──▶ lsass.exe (PID 456) — единственный экземпляр, SYSTEM
```

Таким образом, понимание роли lsass.exe как хранилища секретов и знание векторов атак на него позволяют выстроить эффективную систему детектирования инцидентов, сфокусированную на аномальном доступе, попытках дампа и аномалиях в поведении самого процесса.

## 4. Что отслеживать: методология мониторинга и детектирования

Объединение знаний о трёх критических процессах — explorer.exe, svchost.exe, lsass.exe — в единую практическую дисциплину мониторинга требует системного подхода. Аналитик SOC должен не просто запомнить нормальные параметры, но и освоить инструменты и правила, позволяющие автоматизировать выявление отклонений, а также уметь проводить ручной анализ инцидента. В данном разделе рассматриваются ключевые журналы событий, источники телеметрии, типовые правила детектирования и практические приёмы работы с утилитами для мониторинга дерева процессов.

### Источники телеметрии

Основу наблюдения за процессами в инфраструктуре Windows составляют журналы событий, обогащаемые средствами вроде Sysinternals Sysmon. Минимально необходимый набор источников для полноценного анализа дерева процессов и подозрительного доступа включает:

- **Журнал безопасности Windows (Security.evtx)**, события с кодами:
  - **4688** — создание процесса (командная строка, пользователь, родительский PID);
  - **4689** — завершение процесса;
  - **5156/5158** — сетевые соединения уровня ядра с привязкой к PID процесса.
- **Sysmon**, каналы `Microsoft-Windows-Sysmon/Operational`:
  - **Event ID 1** — создание процесса (включает хеш файла, полный путь, родителя, пользователя);
  - **Event ID 7** — загрузка DLL (путь, подпись, хеш);
  - **Event ID 10** — доступ к процессу (целевой процесс, исходный процесс, запрошенные права доступа);
  - **Event ID 22** — событие DNS-запроса (если процесс делает DNS-запросы), полезно при анализе сетевой активности explorer.exe и svchost.exe.
- **PowerShell журналы** (если включено Script Block Logging) — событие 4104, может содержать расшифрованные скрипты, используемые для кражи учётных данных.

### Конфигурация Sysmon для целевого мониторинга

Поскольку логирование всех межпроцессных взаимодействий порождает колоссальный объём данных, в сообществе принят подход **targeted include** — регистрировать доступ только к определённым, наиболее чувствительным процессам. Фрагмент соответствующей конфигурации Sysmon (иллюстративная схема):

```xml
<Sysmon>
   <EventFiltering>
      <ProcessAccess onmatch="include">
         <!-- Отслеживаем доступ к lsass.exe -->
         <TargetImage condition="end with">lsass.exe</TargetImage>
         <!-- Исключаем легитимные системные процессы -->
         <SourceImage condition="excludes">C:\Program Files\Antivirus\agent.exe</SourceImage>
         <SourceImage condition="excludes">C:\Windows\System32\taskmgr.exe</SourceImage>
      </ProcessAccess>
      <ProcessCreate onmatch="exclude">
         <!-- Базовая очистка шумных событий -->
         <CommandLine condition="contains">C:\Windows\system32\svchost.exe -k netsvcs</CommandLine>
      </ProcessCreate>
   </EventFiltering>
</Sysmon>
```

Приведённая схема гарантирует, что любое обращение к памяти lsass (не от доверенных утилит) будет записано в журнал как потенциальная попытка дампа учётных данных.

### Правила детектирования и практические примеры

На основе поступающих событий строятся правила корреляции. Рассмотрим несколько практических запросов и команд, используемых аналитиком.

1. **Поиск подозрительных процессов svchost без параметра -k** с помощью PowerShell:

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'svchost.exe'" | Where-Object {
    $_.CommandLine -notmatch '-k'
} | Select-Object ProcessId, CommandLine, ExecutablePath, ParentProcessId
```

Вывод покажет все экземпляры Service Host, у которых командная строка не содержит ключ `-k`, что почти всегда свидетельствует о вредоносном процессе.

2. **Проверка экземпляров lsass, запущенных не из System32:**

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'lsass.exe'" | 
    Where-Object { $_.ExecutablePath -ne 'C:\Windows\System32\lsass.exe' } |
    Select-Object ProcessId, ExecutablePath, ParentProcessId
```

При нормальной работе вывод должен быть пустым. Любая запись — сигнал тревоги.

3. **Выявление explorer.exe с подозрительными дочерними процессами** (на основе логов Sysmon Event ID 1) с помощью EQL-подобного запроса (используется в SIEM-решениях, например Elastic Security):

```eql
process where event.code == "1" and 
  process.parent.name == "explorer.exe" and
  process.name in ("powershell.exe", "wscript.exe", "mshta.exe", "regsvr32.exe", "rundll32.exe")
```

Данный запрос отбирает случаи, когда explorer.exe порождает системные интерпретаторы, что может быть индикатором активности dropper’а или скриптовой атаки.

4. **Детектирование доступа к lsass через Sysmon Event ID 10 с подозрительным уровнем прав:**

В среде Elastic Security правило может выглядеть так:

```eql
sequence by process.entity_id with maxspan=5m
  [process_access where event.code == "10" and 
      winlog.event_data.TargetImage : "*\\lsass.exe" and
      winlog.event_data.GrantedAccess : "*0x1010*" /* PROCESS_VM_READ + PROCESS_QUERY_INFORMATION */]
```

На практике точный список исключаемых легитимных процессов настраивается под конкретную инфраструктуру.

### Ручной анализ с помощью Process Explorer

Когда автоматизированные правила генерируют алерт, аналитик переходит к ручному исследованию. Утилита Process Explorer (procexp.exe) позволяет визуально оценить дерево процессов, а также изучить детали каждого экземпляра.

**Типовая последовательность действий при подозрении на инцидент:**

- Открыть Process Explorer и включить нижнюю панель в режиме «DLLs» или «Handles».
- Найти в дереве подозрительный процесс, проверить его родителя и дочерние процессы.
- Проверить цифровую подпись образа (колонка «Verified Signer»).
- Для svchost — удостовериться, что в командной строке присутствует `-k` и путь соответствует `System32`.
- Для процессов, подозреваемых в инъекции в lsass или explorer, посмотреть список загруженных DLL: отсутствие подписи или путь вне системных каталогов — красный флаг.
- Использовать встроенный поиск (Ctrl+L), чтобы найти процессы, работающие с подозрительным файлом или DLL.

Командная утилита `handle.exe` (из набора Sysinternals) также может быть полезна для выяснения, какой процесс держит открытым дескриптор к lsass. Например, команда:

```bash
handle64.exe -a lsass
```

покажет все открытые дескрипторы к объектам, в имени которых содержится «lsass». Если среди них окажется неизвестный исполняемый файл с правами чтения памяти — это веский аргумент для дальнейшего углублённого анализа.

### Построение базового уровня и реагирование

Эффективный мониторинг невозможен без создания baseline — нормального профиля каждого из трёх процессов в конкретной среде. В рамках SOC‑операций рекомендуется еженедельно собирать статистику по количеству экземпляров svchost, типичным дочерним процессам explorer, легитимным программам, обращающимся к lsass. Это позволит выявлять даже небольшие изменения, характерные для скрытых атак.

При обнаружении аномалий процедура эскалации может включать:
- Немедленную изоляцию хоста при подтверждённом дампе lsass;
- Детальный анализ памяти и диска (снятие дампа с подозрительного процесса для реверс-инжиниринга);
- Корреляцию с журналами сетевых подключений для выявления C2-коммуникаций, инициированных скомпрометированными процессами.

Таким образом, ответ на вопрос «что отслеживать» заключается не в запоминании отдельных признаков, а в построении многоуровневой системы сбора телеметрии, автоматизированного анализа и навыков ручного расследования, позволяющей с высокой вероятностью выявлять злоупотребления легитимными процессами Windows.

## Сквозной практический пример: расследование подозрительного доступа к lsass.exe

### Исходные условия

В SIEM поступил алерт из правила, детектирующего подозрительный доступ к процессу lsass. Источник — рабочая станция сотрудника (Windows 11, сборка 22621), на которой установлен Sysmon с политикой targeted include для `TargetImage` lsass.exe. Аналитику SOC L1 необходимо провести первичное расследование, используя доступные журналы и инструменты командной строки.

### Шаг 1. Анализ события Sysmon Event ID 10

Извлекаем детали события, используя PowerShell:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = "Microsoft-Windows-Sysmon/Operational"
    ID = 10
    StartTime = (Get-Date).AddHours(-2)
} | Where-Object {
    $_.Properties[9].Value -like "*lsass.exe"  # TargetImage
} | Select-Object -First 1 | Format-List *
```

Вывод (иллюстративная схема):

```
TimeCreated  : 2025-02-15 14:32:10
Id           : 10
Properties   : { ......
               TargetImage: C:\Windows\System32\lsass.exe
               SourceImage: C:\Users\Public\Downloads\updater.exe
               GrantedAccess: 0x1FFFFF  (PROCESS_ALL_ACCESS)
               SourceProcessId: 8140
               TargetProcessId: 696
               ... }
```

Ключевые поля: `SourceImage` — подозрительный исполняемый файл из общедоступной папки пользователя, запрошенные права `0x1FFFFF` (полный доступ) явно избыточны для легитимной активности.

### Шаг 2. Проверка процесса-источника (updater.exe)

Ищем событие создания процесса `updater.exe` (Sysmon Event ID 1):

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = "Microsoft-Windows-Sysmon/Operational"
    ID = 1
} | Where-Object {
    $_.Properties[4].Value -eq "updater.exe"
} | Format-List TimeCreated, @{n='CommandLine';e={$_.Properties[8].Value}}, 
                   @{n='ParentImage';e={$_.Properties[20].Value}}, 
                   @{n='ParentPID';e={$_.Properties[19].Value}}
```

Результат:

```
TimeCreated  : 2025-02-15 14:31:50
CommandLine  : "C:\Users\Public\Downloads\updater.exe"
ParentImage  : C:\Windows\explorer.exe
ParentPID    : 4520
```

Очевидно, что `updater.exe` был запущен пользователем через проводник (explorer.exe) из подозрительной папки загрузок. Командная строка не содержит параметров, что также нетипично для легитимных установщиков.

### Шаг 3. Анализ родительского процесса explorer.exe

Проверяем, не подвергся ли explorer.exe инъекции. Смотрим список загруженных DLL (Sysmon Event ID 7) для PID 4520 за последний час:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = "Microsoft-Windows-Sysmon/Operational"
    ID = 7
    StartTime = (Get-Date).AddHours(-3)
} | Where-Object {
    $_.Properties[3].Value -eq 4520 -and 
    $_.Properties[4].Value -like "*.dll" -and
    ($_.Properties[6].Value -notmatch "Microsoft Corporation|Microsoft Windows")
} | Format-List TimeCreated, @{n='ImageLoaded';e={$_.Properties[4].Value}}, 
                   @{n='Signature';e={$_.Properties[6].Value}}
```

Предположим, вывод обнаруживает загрузку `C:\Users\Public\payload.dll` без валидной подписи около времени запуска `updater.exe`. Это подтверждает инъекцию кода в explorer.exe.

### Шаг 4. Корреляция с сетевыми соединениями

Анализируем сетевую активность подозрительного процесса (PID 8140) через встроенный журнал Windows или Sysmon Event ID 22:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = "Microsoft-Windows-Sysmon/Operational"
    ID = 22
    StartTime = (Get-Date).AddHours(-2)
} | Where-Object {
    $_.Properties[4].Value -eq 8140   # ProcessId
} | Select-Object TimeCreated, @{n='QueryName';e={$_.Properties[12].Value}}
```

Если обнаруживается DNS-запрос к домену вида `bad.example.com`, это подтверждает C2-коммуникации и необходимость немедленной изоляции хоста.

### Ожидаемый вывод

Сквозной пример демонстрирует, как методология последовательного анализа, базирующаяся на знании нормальных параметров процессов explorer, svchost и lsass, позволяет за несколько минут подтвердить инцидент кражи учётных данных через инъекцию в explorer.exe и последующий доступ к памяти lsass. Такой подход минимизирует время реакции и даёт чёткую картину для эскалации на следующий уровень.
