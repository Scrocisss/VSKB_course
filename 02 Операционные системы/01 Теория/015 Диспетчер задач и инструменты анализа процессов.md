# Диспетчер задач и инструменты анализа процессов

## 1. Контекст и ключевые различия: встроенный монитор и специализированные анализаторы

Диспетчер задач (Task Manager, `taskmgr.exe`) — штатный компонент Windows, предоставляющий базовый мониторинг запущенных приложений, процессов, служб, использования ресурсов и сетевой активности. Инструмент известен как средство первого реагирования при зависаниях и аномальной нагрузке, однако его информационная глубина ограничена: он не показывает загруженные библиотеки, не раскрывает связи между процессами, не даёт деталей о дескрипторах и не позволяет отслеживать вызовы API в реальном времени. В повседневной практике специалиста SOC уровня 1 диспетчер задач служит стартовой точкой, тогда как углублённый анализ выполняется отдельным классом инструментов — специализированными анализаторами процессов, к которым относятся Process Explorer, Process Monitor, System Informer (ранее Process Hacker) и ряд других утилит. Смешение этих инструментов в одну категорию «мониторы процессов» приводит к неверным ожиданиям от их возможностей и неправильному использованию в ходе расследования инцидентов.

Диспетчер задач оперирует поверхностными метриками и предназначен прежде всего для быстрой оценки ситуации конечным пользователем или администратором, тогда как анализаторы процессов ориентированы на детальное исследование внутреннего состояния процессов, потоков, дескрипторов, загруженных модулей, привилегий и сетевых соединений. Их применяют для поиска признаков внедрения вредоносного кода, анализа аномалий, reverse engineering’а поведения программ и аудита безопасности.

Существует распространённая путаница между диспетчером задач и Process Explorer как якобы взаимозаменяемыми утилитами. На самом деле Process Explorer не заменяет Task Manager, а дополняет его. В официальной документации Microsoft по устранению неполадок процессорной активности [подчёркивается](https://learn.microsoft.com/ru-ru/troubleshoot/windows-server/support-tools/support-tools-task-manager), что диспетчер задач — встроенное решение для мониторинга производительности, тогда как Process Explorer — часть набора Sysinternals, предоставляющая «обширную информацию о каждом процессе, включая используемые ресурсы, открытые дескрипторы и загруженные библиотеки» [источник](https://ya.ru/neurum/c/tehnologii/q/kakie_instrumenty_krome_dispetchera_zadach_4e4991e4). Различия фундаментальны и должны осознаваться уже на начальном уровне SOC.

Для чёткого разграничения предметной области ниже приведена сравнительная таблица.

| Инструмент | Тип / происхождение | Основные возможности | Ограничения | Роль в SOC L1 |
|------------|---------------------|----------------------|-------------|---------------|
| **Task Manager (`taskmgr`)** | Встроенный компонент Windows (начиная с NT 4.0) | Вкладки: Процессы, Производительность, Запуск, Пользователи, Сведения, Службы. Завершение процессов, анализ базового потребления ЦП/ОЗУ/диска/сети | Не показывает дерево процессов, скрытые процессы (маскирующиеся), дескрипторы, DLL, цифровые подписи, контекст безопасности; не записывает историю. Непригоден для расследования инцидентов | Первичная сортировка: «какой процесс ест ЦП», «сколько памяти занято», выявление явных аномалий |
| **Process Explorer (`procexp`)** | Sysinternals (Microsoft) | Иерархическое дерево процессов; нижняя панель с дескрипторами или DLL; цветовая маркировка типов процессов; проверка VirusTotal; свойства процесса (подпись, командная строка, путь, threads, TCP/IP, окружение); поиск дескрипторов/ DLL; дампы памяти | Не записывает поток событий в реальном времени; для любительской проверки подписи требуется ручной запуск. Не мониторит реестр и файловую систему | Детективное исследование подозрительного процесса: проверка родительского процесса, цепочки загрузки, поиск скрытых и руткит-процессов, анализ DLL-инъекций |
| **Process Monitor (`procmon`)** | Sysinternals (Microsoft) | Регистрация операций файловой системы, реестра и процессов/потоков в реальном времени; гибкая фильтрация; стек вызовов; сохранение журналов | Не даёт статической картины иерархии процессов; требует настройки фильтров из-за высокой частоты событий. Не рассчитан на быстрое «кто ест память» | Выявление вредоносного поведения: отслеживание изменения реестра, создание/удаление файлов, загрузка DLL, сетевое взаимодействие на уровне операций |
| **System Informer (Process Hacker)** | Открытое ПО | Расширенное управление процессами: древовидное представление, свойства, модули, потоки, дескрипторы, сетевые соединения, дисковая активность, службы, драйверы; терминал утилиты; поиск строк в памяти | Не имеет встроенной записи событий как у Procmon; требует знаний об устройстве Windows для интерпретации некоторых данных | Быстрое углублённое управление процессами и поиск аномалий (скрытые сетевые соединения, внедрённые потоки), детальный анализ загруженных модулей |

Путаница также возникает между понятиями «анализатор процессов» и «менеджер задач». Менеджер задач (как класс) ориентирован на завершение и управление, анализатор — на сбор улик. В SOC L1 оба типа инструментов используются комплементарно: Task Manager даёт моментальный снимок, специализированные анализаторы — доказательную базу.

## 2. Внутреннее устройство и функциональные возможности диспетчера задач и инструментов анализа

Диспетчер задач Windows построен как клиент, собирающий данные через ряд системных API и источников. Его архитектура включает:

- **`taskmgr.exe`** — исполняемый файл, который отображает интерфейс, в Windows 10/11 — приложение Universal Windows Platform (UWP), но серверные версии сохраняют классический Win32-вид.
- **Поставщики данных**:
  - **Performance Counters (PDH)** — для вкладок производительности (ЦП, память, диск, сеть).
  - **Toolhelp API (`CreateToolhelp32Snapshot`)** — для перечисления процессов и потоков; используется на вкладках «Процессы» и «Подробности» (ранее «Процессы» в Win7).
  - **Service Control Manager (SCM)** — для вкладки «Службы».
  - **Network Statistics API (`GetTcpTable`, `GetUdpTable`)** — для отображения активных сетевых соединений (вкладка «Производительность» с графами, не путать с подробной таблицей соединений, отсутствующей в стандартном Task Manager).
- Вкладка «Автозагрузка» (Startup) получает данные из реестровых Run-ключей и планировщика заданий.
- Вкладка «Пользователи» (Users) отображает активные сессии, используя `WTSEnumerateSessions`.

Диспетчер задач не использует механизмы трассировки событий (ETW) и не регистрирует исторические данные, что принципиально ограничивает его ценность в расследованиях. Интерфейс предоставляет шесть основных вкладок (в Windows 10/11): Процессы, Производительность, Журнал приложений (история приложений), Автозагрузка, Пользователи, Подробности, Службы. В более старых версиях структура отличалась: вкладки «Приложения», «Процессы», «Производительность», «Сеть», «Пользователи». Для аналитика SOC L1 важны вкладки «Подробности» (Details) — аналог классического списка процессов со всеми системными процессами, PID, именем пользователя, сеансом, потреблением ресурсов — и «Процессы» (в новом дизайне группировка по приложениям, что скрывает множество служебных процессов). Показательно: вкладка «Процессы» в Windows 10/11 **не отображает фоновые процессы**, которые присутствуют на вкладке «Подробности», поэтому при расследовании всегда предпочтительнее последняя.

Специализированные анализаторы процессов имеют иную архитектуру, основанную на прямых запросах к ядру Windows через Native API и использованием драйвера для доступа к расширенной информации.

**Process Explorer (`procexp64.exe`/ `procexp.exe`)** организует отображение в двух основных панелях:
- Верхняя панель — иерархическое дерево процессов, где родительские и дочерние связи устанавливаются на основе структуры `EPROCESS` и `InheritedFromUniqueProcessId`. Цветовая схема: синий — процессы, работающие в контексте текущего пользователя, розовый — сервисы, фиолетовый — упакованные образы, и т.п.
- Нижняя панель переключается между режимом дескрипторов (Handle View) и режимом DLL (DLL View) для выделенного процесса. В режиме Handle отображается список открытых дескрипторов (файлы, ключи реестра, события, мьютексы) с указанием типа и имени объекта, что критически важно для поиска вредоносных файловых блокировок или индикаторов компрометации. В режиме DLL показываются все загруженные модули, включая их путь, версию, подпись и таймштамп. Это позволяет немедленно обнаружить подозрительную DLL без цифровой подписи, расположенную во временном каталоге.
- Свойства процесса (двойной щелчок или Enter) содержат больше 10 вкладок, в том числе: Image (путь, командная строка, Auto Start, проверка VirusTotal), Performance (графы использования ресурсов, потоки), Threads (стек, стартовый адрес), TCP/IP (список сетевых подключений процесса), Security (токен, привилегии), Environment, Strings. Встроенная функция Verify Signer не только проверяет криптографическую подпись, но и позволяет одним кликом отправить хеш образа на VirusTotal (при настроенной интернет-политике).

**Process Monitor (`procmon64.exe`)** работает как фильтрующая платформа событий, перехватывающая вызовы от трёх провайдеров:
- File System (дисковое в/в, файловые операции, включая создание, чтение, запись, удаление, с атрибутами);
- Registry (операции с кустами реестра, ключами и значениями);
- Network (сетевые события Winsock/TCP/IP, но не пакетный уровень).
Столбец `Operation` содержит конкретное действие (CreateFile, RegSetValue, TCP Connect), колонки `Result` и `Detail` уточняют успешность и параметры. Process Monitor сохраняет миллионы событий в журнал и позволяет задавать сложные фильтры по процессу, пути, операции и т.д. Ключевой элемент — **стек вызовов** для каждого события, отображающий цепочку функций в пространстве ядра и пользовательском режиме, что прямо ведёт к источнику подозрительного поведения (например, внедрённому коду). Без возможности записи истории он был бы бесполезен.

**System Informer (ранее Process Hacker)** — открытый проект, объединяющий многие функции. Его архитектура модульная: графический интерфейс (`SystemInformer.exe`), драйвер ядра `KProcessHacker.sys` (для доступа к объектам ядра, закрытия защищённых процессов), консольная утилита `SystemInformerClient.exe`. Помимо дерева процессов, вкладки: Services, Network (с фильтрацией по процессам), Disk, Firewall (отображение правил Windows Filtering Platform), Devices (драйверы). Есть встроенный терминал с командами для управления процессами. Для SOC L1 важны возможности по проверке цифровой подписи, поиску скрытых процессов (например, через DKOM-техники, которые детектятся по несоответствию PspCidTable и списков системных процессов), а также отображение загруженных модулей с отметкой о доверии подписи (зелёный/красный знак).

Следующая таблица сопоставляет возможности, релевантные для анализа в SOC, помогая быстро выбрать нужный инструмент.

| Функция / Задача | Task Manager | Process Explorer | Process Monitor | System Informer |
|------------------|--------------|------------------|-----------------|-----------------|
| Просмотр потребления ЦП, ОЗУ, диска, сети в реальном времени | Да, графики на вкладке «Производительность» | Нет общей панели, только performance-графы в свойствах процесса | Нет | Есть графики по процессам, но общая панель не так наглядна |
| Иерархическое дерево процессов (родитель–потомок) | Нет | Да, верхняя панель | Нет, только список с PID и Parent PID | Да |
| Загруженные DLL для процесса | Нет | Да, нижняя панель DLL | Нет, но можно отследить Load Image события | Да, вкладка Modules со свойствами каждой DLL |
| Открытые дескрипторы (файлы, ключи реестра, мьютексы) | Нет | Да, нижняя панель Handle | Да, косвенно через операции | Да, вкладка Handles |
| Сетевые соединения процесса (TCP/IP) | Только график и список на вкладке «Производительность» без привязки к процессам | В свойствах процесса вкладка TCP/IP | Да, Network Summary и события | Да, вкладка Network с фильтрацией по процессам |
| Проверка цифровой подписи образа | Нет (только в столбце «Издатель» для некоторых) | Да, Verify Signer, VT-интеграция | Нет (можно увидеть путь к файлу) | Да, с цветовой индикацией |
| Отслеживание операций файлового/реестрового/сетевого ввода-вывода с записью | Нет | Нет | Да, основное назначение | Нет, только мониторинг текущего состояния |
| Завершение процессов / деревьев / создание дампа | Завершение процесса/дерева (мин. дамп через свойства в Win11) | Kill Process / Kill Process Tree, дамп (полный/мини/строк) | Нет (не предназначен для управления) | Terminate / Suspend / Resume, дамп и пр. |
| Поиск процесса по загруженной DLL или открытому дескриптору | Нет | Да, Find Handle или DLL | Нет (но можно фильтровать по событию) | Да, Find Handles/DLLs |
| Обнаружение упакованных образов (Entropy) | Нет | Да, по цвету | Нет | Нет |

Таким образом, каждый инструмент закрывает свою нишу: Task Manager — быстрый обзор, Process Explorer — глубокий статико-динамический анализ процессов, Process Monitor — трассировка событий, System Informer — универсальное управление и анализ с открытым кодом.

## 3. Типовые сценарии работы с процессами в SOC L1: команды и процедуры

На первой линии центра мониторинга безопасности (SOC L1) знания об операционной системе и её процессах позволяют быстро отсеивать ложные срабатывания и эскалировать подозрительные события. Инструментарий не ограничивается графическими утилитами: во многих скриптовых и удалённых сценариях используются встроенные команды Windows и PowerShell, а также консольная версия Sysinternals.

### Базовый аудит процессов через командную строку и PowerShell

Первое действие аналитика при подозрении на компрометацию — получить список процессов с максимумом деталей. Штатный `tasklist` способен выдать список загруженных модулей и служб, в которых участвует процесс. Например, для поиска всех процессов, использующих определённую DLL (потенциальный индикатор DLL side-loading), можно выполнить:

```cmd
tasklist /m /fi "modules eq malicious.dll"
```

Однако точность фильтрации ограничена, и данные необходимо перепроверять. В PowerShell для быстрой фильтрации подозрительных процессов без цифровой подписи полезен скрипт с использованием `Get-AuthenticodeSignature`:

```powershell
Get-Process | ForEach-Object {
    $sig = Get-AuthenticodeSignature -FilePath $_.Path -ErrorAction SilentlyContinue
    if ($sig.Status -ne 'Valid') {
        [PSCustomObject]@{
            ProcessName = $_.Name
            Id          = $_.Id
            Path        = $_.Path
            Signature   = $sig.Status
        }
    }
} | Format-Table -AutoSize
```

Вывод отобразит процессы с неподписанными или недоверенными образами — распространённый приём маскировки вредоносного ПО. В реальной среде команда потребует доработки для обработки процессов без файла образа (System, Idle), поэтому на практике часто добавляют проверку существования `$_.Path`.

### Углублённый анализ подозрительного процесса с помощью Process Explorer

При получении алерта от EDR на необычную активность процесса `svchost.exe` (например, дочерний процесс `cmd.exe` от нестандартного экземпляра `svchost.exe`) аналитик SOC L1 использует Process Explorer для верификации. Порядок действий:

1. Запустить Process Explorer от имени администратора (требуется для отображения всех процессов и дескрипторов).
2. Найти подозрительный `svchost.exe` в дереве процессов, обратить внимание на родительский процесс. Обычно легитимный `svchost.exe` запущен от `services.exe` с параметром `-k <группа служб>`; появление родителя `explorer.exe` или напрямую `wininit.exe` подозрительно.
3. Открыть свойства процесса, на вкладке «Image» проверить полную командную строку (`Command line`) и путь к исполняемому файлу. Легитимный `svchost.exe` всегда находится в `%SystemRoot%\System32\svchost.exe`; любые отклонения (например, `C:\Users\Public\svchost.exe`) — явный индикатор.
4. На вкладке «Strings» можно выполнить поиск строк «http», «cmd», «powershell» — это даст первичное представление о вредоносной нагрузке.
5. Отправить хеш образа на VirusTotal через вкладку «Image» > «Verify Signer» > «Submit to VirusTotal», при наличии корпоративного соглашения.

### Фиксация улик и взаимодействие с командой L2

Перед эскалацией аналитик должен зафиксировать минимальный набор артефактов, не нарушая целостность машины (насколько позволяет настройка):

- Создание дампа подозрительного процесса в Process Explorer: **Process > Create Dump > Create Full Dump**. Это допустимо на изолированном хосте и при согласовании с IR-процедурами.
- Сохранение списка дескрипторов: **File > Save As** > выбрать формат `txt`. В полученном файле будет перечень всех открытых дескрипторов с путями к файлам, что помогает выявить скрытые файлы.
- Экспорт логов Process Monitor за короткий период активности подозрительного процесса: запустить мониторинг с фильтром `Process Name is svchost.exe`, собирать события 1–2 минуты, затем сохранить в `.PML`-файл. Пример фильтра в Process Monitor задаётся через **Filter > Process Name > is > `svchost.exe`** > **Include**.

Типичная ошибка начинающего специалиста — полагаться исключительно на Task Manager при оценке вредоносности. Вредонос способен скрывать себя от стандартного списка процессов (например, путём манипуляции со структурой `EPROCESS`), но будет виден в Process Explorer через проверку целостности системных списков (System Informer позволяет выявить DKOM-руткиты через сравнение активных процессов и PspCidTable). Второй частый промах — игнорирование столбца «CPU Time» в Process Explorer. Даже если процесс сейчас не потребляет CPU, многоминутное процессорное время с момента старта может указывать на фоновую активность (майнинг, брутфорс).

### Удалённый анализ и скриптовая автоматизация

При расследовании на удалённой машине без GUI аналитик применяет `psexec` или WinRM для запуска команд Process Monitor с консольной обвязкой (утилита `Procmon.exe` поддерживает параметры `/BackingFile` и `/Quiet` для автоматического сбора). Пример запуска тихого сбора с фильтром по имени процесса:

```cmd
procmon.exe /AcceptEula /Quiet /BackingFile C:\temp\capture.pml
```

После непродолжительного сбора (например, 30 сек) процесс завершается, и файл передаётся для анализа. PowerShell также предоставляет встроенные командлеты для анализа TCP-соединений процессов:

```powershell
Get-NetTCPConnection | Where-Object State -eq Established | Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, OwningProcess | ForEach-Object { $_ | Add-Member -MemberType NoteProperty -Name ProcessName -Value (Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).Name -PassThru } | Format-Table
```

Этот однострочник выдаёт таблицу установленных соединений с именами процессов — аналог `netstat -ano` с разрешением имён.

Таким образом, аналитик L1 должен владеть как графическими анализаторами, так и минимальным набором консольных команд для быстрого триажа и фиксации улик до передачи более опытным коллегам.

## 4. Сквозной практический пример: выявление и анализ подозрительного процесса PowerShell

### Исходные условия
Среда: Windows 10 Enterprise, инструменты — Task Manager, Process Explorer, PowerShell. Сценарий: оператор SOC получает уведомление от системы мониторинга о повышенной загрузке ЦП пользовательским хостом `powershell.exe`, запущенным от процесса `explorer.exe`, с командной строкой, содержащей обфусцированный фрагмент. Задача: быстро оценить легитимность процесса и, при необходимости, зафиксировать первичные артефакты до полного снятия образа памяти.

### Шаг 1. Первичная оценка через Task Manager
Аналитик открывает диспетчер задач (Ctrl+Shift+Esc) и переходит на вкладку «Процессы» с сортировкой по ЦП. Обнаружен процесс `powershell.exe` с высоким CPU, пользователь — `user1`, запущен недавно. Переключившись на вкладку «Подробности» и добавив столбец «Командная строка», он видит:

```text
powershell.exe -NoP -NonI -W Hidden -Enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABO... (base64)
```

Командная строка явно обфусцирована. Первичный подозрительный признак: скрытое окно (`-W Hidden`) и кодированная команда (`-Enc`) без легитимного повода. Task Manager дал достаточно для эскалации, но необходимо детальное исследование.

### Шаг 2. Проверка дерева процессов и образа в Process Explorer
Запущен Process Explorer от администратора. На дереве процессов видно, что `powershell.exe` порождён процессом `explorer.exe` (PID 4321) вместо стандартного `svchost.exe` или `taskeng.exe` для запланированных заданий. Свойства процесса `powershell.exe` раскрывают дополнительные детали на вкладке «Image»:

```
Path: C:\Users\user1\AppData\Local\Temp\powershell.exe
Command line: "C:\Users\user1\AppData\Local\Temp\powershell.exe" -NoP -NonI -W Hidden -Enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoA...
Parent: explorer.exe(4321)
Start time: 2025-04-10 09:17:33
Auto Start: (none)
```

Путь размещения `powershell.exe` в пользовательском временном каталоге — явный признак подмены или вредоносной копии легитимной утилиты. Легитимный `powershell.exe` обязан находиться в `C:\Windows\System32\WindowsPowerShell\v1.0\`. Проверка цифровой подписи через кнопку «Verify Signer» показывает, что подпись отсутствует (unsiged). На вкладке «TCP/IP» обнаружено исходящее соединение на внешний IP-адрес по порту 443. Вкладка «Strings» содержит строки, характерные для загрузчика: `DownloadString`, `Net.WebClient`, `IEX`.

### Шаг 3. Сбор артефактов до прерывания
Аналитик создаёт минидамп процесса: Right-click по процессу > **Create Dump > Create Full Dump**. Файл сохраняется в `C:\Users\admin\Desktop\powershell_1234.dmp`. Затем экспортируется список дескрипторов для последующего анализа блокировок: выделив процесс, File > Save as > `powershell_handles.txt`. В полученном файле видны открытые handle к сокетам и случайным файлам в Temp.

### Шаг 4. Проверка сетевой активности и эскалация
Перед завершением процесса (если это разрешено playbook), аналитик выполняет в PowerShell консоли (уже от администратора) команду для документирования сетевого соединения:

```powershell
Get-NetTCPConnection -OwningProcess 1234 | Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, State, CreationTime | Format-Table -AutoSize
```

Вывод:

```text
LocalAddress LocalPort RemoteAddress RemotePort State     CreationTime
----------- --------- ------------- ---------- -----     ------------
192.168.1.15 54321     93.184.216.34 443        Established 09:17:35
```

Удалённый адрес не соответствует легитимным корпоративным серверам. Аналитик фиксирует IP и порт для Threat Intelligence, завершает процесс через Process Explorer (Kill Process Tree) и формирует записку эскалации на L2, прикладывая дамп, сохранённые дескрипторы и скриншоты.

### Ожидаемый вывод примера
Сквозной кейс демонстрирует, что Task Manager используется только для быстрой идентификации аномалии, тогда как Process Explorer и PowerShell предоставляют доказательства компрометации: нестандартный путь, отсутствие подписи, подозрительные сетевые соединения. SOC L1 без специализированных анализаторов не смог бы подтвердить вредоносность и корректно зафиксировать улики.
