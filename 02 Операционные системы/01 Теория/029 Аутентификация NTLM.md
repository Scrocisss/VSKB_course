# Аутентификация NTLM

## 1. NTLM в экосистеме аутентификации Windows

NTLM (NT LAN Manager) — это набор протоколов безопасности Microsoft, обеспечивающий аутентификацию, целостность и конфиденциальность в сетях на базе Windows [1], [2]. Первоначально разработанный для замены более слабого протокола LAN Manager (LM), NTLM в различных версиях (NTLMv1, NTLMv2, NTLM2 Session) долгое время оставался основным механизмом проверки подлинности в доменах Windows до появления Kerberos.

С выходом Windows 2000 протокол Kerberos стал стандартным методом аутентификации в Active Directory, однако NTLM не был выведен из эксплуатации [3]. Он продолжает использоваться в ситуациях, где применение Kerberos невозможно или нецелесообразно:

- аутентификация локальных учётных записей на компьютерах, не входящих в домен (рабочие группы);
- локальный вход на контроллерах домена и других серверах в изолированных средах;
- доступ к ресурсам, когда имя целевого сервера неизвестно или не может быть разрешено (например, IP-адрес вместо имени);
- обратная совместимость с устаревшими версиями Windows (Windows 95/98/NT 4.0) и старыми приложениями, жёстко привязанными к NTLM [4], [5].

Современная реализация NTLM в Windows использует Security Support Provider Interface (SSPI) — архитектурный слой, абстрагирующий работу с протоколами аутентификации. Конкретным провайдером для NTLM является `NTLMSSP` (NT LM Security Support Provider), загружаемый как динамическая библиотека и предоставляющий три основные функции: `AcquireCredentialsHandle`, `InitializeSecurityContext` и `AcceptSecurityContext` [6], [7].

Ключевое отличие NTLM от Kerberos, определяющее его уязвимость и сценарии применения, заключается в том, что NTLM является протоколом с прямым взаимодействием «клиент-сервер» (а при делегировании проверки — с участием контроллера домена), тогда как Kerberos опирается на доверенную третью сторону (KDC) и билеты. Это различие сведено в таблице ниже.

| Характеристика | NTLM | Kerberos |
|----------------|------|----------|
| **Тип протокола** | Challenge–response (запрос–ответ) | Билетная система с центром распределения ключей (KDC) |
| **Доверенная сторона** | Сервер может проверить ответ напрямую или через запрос к контроллеру домена | KDC выдаёт билеты после проверки подлинности |
| **Взаимная аутентификация** | Только NTLMv2 (опционально); NTLMv1 — односторонняя | Да, за счёт билета службы (service ticket) |
| **Криптостойкость** | Устаревшие хэш-функции (MD4, LM-хэш DES), HMAC-MD5 в NTLMv2; отсутствие поддержки AES/SHA-256 [8] | Современные шифры, AES, RC4-HMAC (в старых режимах) |
| **Устойчивость к Relay-атакам** | Низкая; NTLMv2 с проверкой подлинности канала (Channel Binding) или подписью улучшает ситуацию | Высокая (привязан к имени службы в билете) |
| **Использование в современных средах** | Для совместимости, локальные учётные записи, отказоустойчивость при недоступности KDC | По умолчанию в AD-доменах с Windows 2000 и выше |

В рамках SOC L1 важно понимать, что NTLM до сих пор встречается в корпоративных сетях, а его устаревшая криптография и отсутствие по умолчанию строгих политик подписи делает протокол привлекательной мишенью для атак типа Pass-the-Hash, Relay и брутфорс. Поэтому NTLM остаётся серьёзным вектором угроз, требующим как технического контроля, так и осознанного вытеснения из инфраструктуры.

Терминологический нюанс: в обиходе часто смешивают понятия «NTLM-хэш» и «NetNTLM». **NT-хэш** (или NTLM-хэш) — это результат применения MD4 к паролю пользователя в кодировке UTF-16-LE [1]. **NetNTLM** (NetNTLMv1, NetNTLMv2) — это результат вычисления ответа на challenge с использованием этого хэша; именно эти значения передаются по сети и могут быть перехвачены для офлайн-подбора пароля или relay-атаки. Хранение NT-хэша в базе SAM или NTDS.dit делает его «эквивалентом пароля»: злоумышленник, завладевший хэшем, может аутентифицироваться без знания пароля (Pass-the-Hash) [9].


## 2. Архитектура и криптографические механизмы NTLM

Протокол NTLM работает по схеме «запрос-ответ» и в базовом варианте обменивается тремя сообщениями (четвёртое используется опционально для обеспечения целостности). Рассмотрим детально каждую фазу и параллельно разберём внутренние структуры и варианты реализации криптографических вычислений.

### 2.1 Фазы аутентификационного обмена

Аутентификация NTLM происходит в рамках установленного транспортного соединения (например, SMB, HTTP, RPC) и представлена тремя ключевыми сообщениями [1], [10]:

1. **NEGOTIATE_MESSAGE** — клиент направляет серверу перечень поддерживаемых возможностей (версия протокола, требования к сессионной подписи, поддержка NTLMv2 и т.п.).
2. **CHALLENGE_MESSAGE** — сервер генерирует случайную 8-байтовую (для NTLMv1) или 8-байтовую структуру (для NTLMv2 добавляется временная метка и другие поля) и отправляет её клиенту вместе со своими флагами возможностей.
3. **AUTHENTICATE_MESSAGE** — клиент на основе своего парольного хэша и полученного вызова вычисляет ответ (response), упаковывает его вместе с именем пользователя и доменом и отправляет серверу. Сервер либо самостоятельно верифицирует ответ (если локальная учётная запись), либо пересылает данные на контроллер домена, который выполняет проверку.

ASCII-схема базового обмена:

```text
Клиент                                     Сервер
  |                                           |
  |---(1) NEGOTIATE_MESSAGE (флаги)---------->|
  |                                           |
  |<--(2) CHALLENGE_MESSAGE (вызов, флаги)---|
  |                                           |
  |---(3) AUTHENTICATE_MESSAGE (ответ)------->|
  |                                           |
  |         (при необходимости)               |
  |<--(4) Завершающее сообщение проверки ----|
```

### 2.2 Структура ключевых сообщений

Сообщения протокола имеют фиксированный набор полей, часть из которых буферизируется отдельно. Ниже представлена упрощённая структура полей, актуальная для анализа сетевого трафика и логов:

| Поле | NEGOTIATE_MESSAGE | CHALLENGE_MESSAGE | AUTHENTICATE_MESSAGE |
|------|-------------------|-------------------|----------------------|
| **Signature** | "NTLMSSP\0" | "NTLMSSP\0" | "NTLMSSP\0" |
| **MessageType** | 1 | 2 | 3 |
| **NegotiateFlags** | Флаги клиента | Флаги сервера | Флаги клиента (финальные) |
| **DomainName** | Опционально | Server domain (буфер) | Client domain (буфер) |
| **UserName** | – | – | Client username (буфер) |
| **WorkstationName** | – | – | Workstation (буфер) |
| **Challenge** | – | 8-байтовый случайный вызов | – |
| **ServerContext/Reserved** | – | Зарезервировано | – |
| **NtChallengeResponse** | – | – | Ответ на основе NT-хэша |
| **LmChallengeResponse** | – | – | Ответ на основе LM-хэша |
| **SessionKey** | – | – | Буфер сессионного ключа (опционально) |

Данная таблица даёт представление о составе сообщений и позволяет аналитику SOC соотносить события в логах с передаваемыми данными. Значения флагов определяют, например, будет ли использоваться подпись трафика, согласуется ли NTLMv2 или более старые версии.

### 2.3 Хэши паролей и вычисление ответа

Центральный элемент безопасности (и слабость) NTLM — парольные хэши. Хранятся два типа хэшей длиной 16 байт каждый [2]:

- **LM-хэш** — вычисляется от первых 14 символов пароля, приведённых к OEM-кодировке; основан на DES. Сегодня почти повсеместно отключён или не хранится.
- **NT-хэш (NTLM-хэш)** — результат `MD4(UTF-16-LE(пароль))`. Именно он используется в NTLMv2 и часто в NTLMv1; является эквивалентом пароля.

**NTLMv1.** Способ вычисления ответа основан на DES:
```
C = 8-байтовый серверный challenge (случайное число)
H = NTLM-хэш (16 байт)          // (или LM-хэш для LM ответа)
H_expanded = H + 0x00*5          // дополнение нулями до 21 байта
K1|K2|K3 = H_expanded            // разбиение на 3 части по 7 байт

response = DES(K1, C) | DES(K2, C) | DES(K3, C)   (24 байта)
```
В стандартной конфигурации отправляются оба ответа: и на основе NT-хэша, и на основе LM-хэша [2].

**NTLMv2.** Использует HMAC-MD5 и клиентский nonce, существенно усиливая стойкость [2], [6]:
- Клиент генерирует временную метку и случайную последовательность (blob), включая поля `Timestamp`, `ClientChallenge` и, опционально, имя целевого сервера (для защиты от relay).
- Вычисляется `NTLMv2-Session-Key = HMAC-MD5(NTLM-Hash, HMAC-MD5(NTLM-Hash, ServerChallenge + Blob))`
- Ответ серверу: `Blob + HMAC-MD5(NTLM-Hash, ServerChallenge + Blob)`.

Кроме того, NTLMv2 поддерживает **взаимную аутентификацию**, когда сервер предоставляет доказательство знания пароля клиенту.

Реализация через SSPI инкапсулирует эти вычисления внутри вызовов `InitializeSecurityContext` (клиент) и `AcceptSecurityContext` (сервер). Для SOC‑аналитика важно, что в логах аутентификации фигурирует имя пакета (`NTLM` или `Kerberos`), а детали ответов доступны только при сетевом анализе или глубоком аудите.

### 2.4 Версионность и уровни совместимости LM

Поведение NTLM на конкретной машине определяется параметром реестра `LmCompatibilityLevel`, расположенным по пути:
`HKLM\SYSTEM\CurrentControlSet\Control\Lsa\`

Этот параметр задаёт допустимые и отправляемые версии ответов [9]:

| Уровень | Описание (упрощённо) | Примечание |
|---------|----------------------|------------|
| 0 | Отправлять LM- и NTLM-ответы, использовать NTLMv2 сессию, если согласовано | Максимальная совместимость, минимальная безопасность |
| 1 | Использовать NTLMv2 сессию, если согласовано | – |
| 2 | Отправлять только NTLM-ответы (без LM) | – |
| 3 | Отправлять только NTLMv2-ответ | Рекомендация Microsoft; широко распространён |
| 4 | Отправлять только NTLMv2-ответ, отказывать LM | Как уровень 3, но с отказом от LM на стороне сервера |
| 5 | Отправлять только NTLMv2-ответ, отказывать LM и NTLM | Наиболее строгий; предписан NIST и современными рекомендациями |

Большинство организаций находятся на уровне 3, что всё ещё допускает определённые сценарии relay-атак, особенно при отсутствии обязательной подписи SMB или LDAP. Полный отказ от NTLM возможен только при переходе исключительно на Kerberos или современные альтернативы, что, согласно планам Microsoft, будет реализовано по умолчанию в жизненном цикле Windows 11 [4].


## 3. Эксплуатация, мониторинг и защита NTLM

Знание внутреннего устройства протокола позволяет как использовать NTLM в легитимных сценариях, так и выявлять злоупотребления. В SOC L1 работа с NTLM сводится к трём направлениям: аудит событий входа, контроль конфигураций и распознавание типичных атак.

### 3.1 Журналирование и базовые проверки

Windows регистрирует события аутентификации NTLM в журнале безопасности (Security log). Основной идентификатор — **4624** (An account was successfully logged on), где в поле `Authentication Package` отображается `NTLM`. Для сеансов с отказами — 4625. Аналитик должен сопоставлять такие события с типом входа (logon type), чтобы определить, происходит ли, например, интерактивный вход на сервер с использованием устаревшего протокола.

Пример поиска успешных NTLM-входов на рабочей станции с помощью PowerShell (иллюстративная схема полей):

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4624} -MaxEvents 100 |
    Where-Object { $_.Properties[8].Value -eq 'NTLM' } |
    Select-Object TimeCreated, 
        @{N='User';E={$_.Properties[5].Value}},
        @{N='Domain';E={$_.Properties[6].Value}},
        @{N='LogonType';E={$_.Properties[10].Value}},
        @{N='Workstation';E={$_.Properties[11].Value}} |
    Format-Table -AutoSize
```
Вывод покажет события, где поле Authentication Package равно NTLM, и позволит быстро оценить, какие учётные записи используют этот протокол.

Другой важный источник — **операционный журнал NTLM** (Operational log, доступен при включении аудита). Он содержит подробные события о попытках аутентификации, используемой версии и причине отказа.

### 3.2 Контроль уровня совместимости

Аналитику SOC часто требуется проверить текущий уровень LM-совместимости на узле. Следующая команда возвращает значение параметра реестра:

```powershell
Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" `
    -Name LmCompatibilityLevel | Select-Object -ExpandProperty LmCompatibilityLevel
```
Вывод, например, `3` означает уровень «Send NTLMv2 response only». Если ожидается более строгий уровень, расхождение фиксируется как несоответствие политике безопасности.

Для массовой инвентаризации в домене можно использовать Invoke-Command или групповые политики. Рекомендуемое значение для большинства организаций, исключивших старые клиенты, — **5** (Refuse LM and NTLM). Однако изменение на уровень 5 требует тестирования, так как может нарушить работу приложений, жёстко привязанных к NTLM.

### 3.3 Распространённые атаки и их индикаторы

С точки зрения SOC L1 важно знать основные векторы атак на NTLM и сопутствующие индикаторы:

- **Pass-the-Hash (PtH)** — злоумышленник, завладевший NT-хэшем (из дампа SAM, NTDS.dit или памяти), использует его для аутентификации на удалённых ресурсах без знания пароля. Индикаторы: события входа 4624 с типом 3 (сетевой вход), где учётная запись используется с необычных хостов или в нерабочее время, при этом пароль не менялся. Атака возможна, потому что NTLM не требует доказательства владения паролем, а только хэшем.
- **NTLM Relay** — перехваченный ответ NetNTLM (например, через LLMNR/NBNS spoofing, rogue SMB сервер) перенаправляется на целевую службу для аутентификации от имени жертвы. Индикаторы: сетевые алерты на подозрительные SMB-запросы из неожиданных подсетей, использование некорректных имён пакетов, а также события 4624, где источник (workstation) не совпадает с ожидаемым.
- **Brute-force / Password spraying** — подбор паролей с попытками NTLM-аутентификации. Проявляется множеством событий 4625, часто с одинаковым доменом и пользовательскими именами. В логах может указываться `NTLM` в пакете аутентификации.

Для предотвращения relay-атак на уровне протокола в NTLMv2 добавлен механизм **Service Binding** (Channel Binding): клиент включает в blob информацию об SPN или сеансовый идентификатор TLS, чем доказывает, что общается именно с целевым сервером. Проверка этого поля сервером (EPA – Extended Protection for Authentication) отсекает relay, но требует настройки на стороне сервера.

### 3.4 Практические шаги по снижению рисков

1. **Повысить уровень LmCompatibilityLevel до 5** с помощью GPO:  
   `Computer Configuration\Windows Settings\Security Settings\Local Policies\Security Options\Network security: LAN Manager authentication level`.
2. **Включить обязательную подпись SMB** (SMB signing) и LDAP signing, чтобы предотвратить подмену вызовов.
3. **Включить аудит NTLM** для детального отслеживания попыток использования устаревших версий (события в операционном журнале NTLM).
4. **Ограничить исходящий NTLM-трафик** через брандмауэр Windows или групповые политики «Network security: Restrict NTLM: Outgoing NTLM traffic to remote servers».
5. **Мигрировать серверы и приложения на Kerberos** и отключить NTLM, где это возможно. Инструменты вроде Silverfort [11] предоставляют анализ зависимостей и помогают поэтапно вывести NTLM из эксплуатации.

Для SOC L1 центральной задачей остаётся корректная идентификация событий NTLM и своевременное эскалирование отклонений, особенно при обнаружении использования NTLMv1, отсутствия подписи или аномального поведения учётных записей.


## 4. Сквозной практический пример: выявление небезопасной аутентификации NTLMv1

**Исходные условия.** Аналитик SOC L1 получил уведомление от SIEM о том, что на одном из серверов домена (`SRV-FINANCE`) зафиксирована успешная аутентификация с использованием NTLMv1. Доменная политика предписывает уровень совместимости не ниже 3 (только NTLMv2). Сервер работает под управлением Windows Server 2022, оповещение пришло через настроенный сбор событий аудита NTLM. Задача — проверить факт, определить источник и устранить нарушение.

**Шаг 1.** Проверить журнал безопасности на источнике (`SRV-FINANCE`) на наличие событий с NTLMv1. Используем PowerShell для поиска связанных событий аудита NTLM (Event ID 8001 в Operational log, иллюстративно):

```powershell
$events = Get-WinEvent -LogName "Microsoft-Windows-NTLM/Operational" -MaxEvents 50 |
    Where-Object { $_.Id -eq 8001 -and $_.Message -match "NTLMv1" }
$events | Select-Object TimeCreated, Id,
    @{N='Target';E={($_.Properties | ? {$_.Value -match 'SRV'}).Value}},
    @{N='User';E={($_.Properties | ? {$_.Value -match 'DOMAIN'}).Value}} |
    Format-Table -AutoSize
```

Ожидаемый вывод (схематично):
```
TimeCreated           Id   Target       User
-----------           --   ------       ----
02.03.2025 14:15:10  8001 SRV-FINANCE  DOMAIN\finance_user
```

Событие показывает, что учётная запись `finance_user` из домена успешно аутентифицирована с использованием NTLMv1. Это прямое нарушение политики.

**Шаг 2.** Проверить текущий уровень LmCompatibilityLevel на сервере, где произошла аутентификация. На `SRV-FINANCE` выполняем:

```powershell
Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" -Name LmCompatibilityLevel
```

Фактический вывод:
```
LmCompatibilityLevel : 0
PSPath               : Microsoft.PowerShell.Core\Registry::HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Lsa
...
```

Значение `0` («Send LM & NTLM responses») объясняет, почему был разрешён NTLMv1. Сервер не применяет даже базового повышения безопасности.

**Шаг 3.** Выяснить, с какого хоста происходила аутентификация. Дополнительный анализ события 4624 за тот же промежуток времени:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4624; StartTime=(Get-Date).AddHours(-1)} |
    Where-Object { $_.Properties[8].Value -eq 'NTLM' } |
    Select-Object TimeCreated,
        @{N='User';E={$_.Properties[5].Value}},
        @{N='Domain';E={$_.Properties[6].Value}},
        @{N='Workstation';E={$_.Properties[11].Value}} |
    Format-Table -AutoSize
```

Вывод (иллюстративно):
```
TimeCreated           User                 Domain       Workstation
-----------           ----                 ------       -----------
02.03.2025 14:15:10   finance_user         DOMAIN       DESKTOP-OLD
```

Источником запроса оказалась старая рабочая станция `DESKTOP-OLD`, которая, вероятно, использует устаревший клиент или не получает обновлённую политику.

**Шаг 4.** Применить корректирующие действия: установить уровень совместимости 5 на `SRV-FINANCE` через локальную политику или GPO. С помощью команды (требует прав администратора и перезагрузки для полного применения):

```powershell
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa" `
    -Name LmCompatibilityLevel -Value 5 -Type DWord
```

Для проверки результата повторно читаем параметр и видим значение `5`. После перезагрузки сервера все последующие аутентификации от `DESKTOP-OLD` будут завершаться ошибкой, если рабочая станция не способна на NTLMv2. В журнале безопасности появятся события 4625 с пакетом `NTLM` и кодом ошибки, что станет индикатором необходимости обновления клиента или перехода на Kerberos.

**Ожидаемый вывод примера.** Аналитик не только подтвердил факт использования устаревшего варианта протокола, но и выявил первопричину — недостаточный уровень совместимости на сервере, вероятно, оставленный по умолчанию при развёртывании. Изменение настройки до уровня 5 устранило возможность аутентификации с помощью NTLMv1 и улучшило безопасность ресурса, параллельно подсветив необходимость модернизации парка рабочих станций. Пример демонстрирует, как средствами Windows и штатных логов можно на практике контролировать состояние аутентификации NTLM в среде, что является рутинной задачей SOC L1.
