# Пользовательский режим и режим ядра в архитектуре Windows

## Разграничение привилегий: зачем и как Windows изолирует код

В основе устройства любой современной операционной системы лежит архитектурное разделение кода на два принципиально разных уровня выполнения — пользовательский режим (User Mode) и режим ядра (Kernel Mode). Это разделение реализовано на аппаратном уровне: процессоры архитектуры x86 и x64 предоставляют четыре кольца защиты (Ring 0 – Ring 3), где Ring 0 обладает наивысшими привилегиями, а Ring 3 — наименьшими. Windows, как и большинство универсальных ОС, использует только два кольца: Ring 0 для режима ядра и Ring 3 для пользовательского режима [Windows Architecture basics](https://vimalshekar.github.io/reverse-engg/Windows-Architecture-Basics). Такая модель служит двум фундаментальным целям — безопасности и стабильности системы.

Код, выполняющийся в режиме ядра, имеет неограниченный доступ ко всей физической памяти, оборудованию и критическим структурам данных операционной системы. Это позволяет ему максимально эффективно управлять ресурсами, но любая ошибка или вредоносное действие в этом режиме способны привести к краху всей системы (например, к синему экрану смерти — bug check). Напротив, приложения и большинство служб выполняются в изолированных адресных пространствах пользовательского режима с жёсткими ограничениями: они не могут напрямую обращаться к памяти ядра, выполнять привилегированные инструкции процессора или взаимодействовать с оборудованием. В случае сбоя приложения страдает только сам процесс — операционная система продолжает работать [What is the difference between user and kernel modes in operating systems?](https://stackoverflow.com/questions/1311402/what-is-the-difference-between-user-and-kernel-modes-in-operating-systems).

Для специалиста SOC L1 эта дихотомия критически важна при первичной сортировке инцидентов. Сообщение о внезапной перезагрузке сервера с кодом остановки, указывающим на ошибку в драйвере (например, `DRIVER_IRQL_NOT_LESS_OR_EQUAL`), сразу говорит о проблеме на уровне ядра, требующей повышенного внимания. В то же время аварийное завершение пользовательского приложения, зафиксированное в журнале `Application`, обычно не угрожает стабильности всей системы и классифицируется как инцидент с меньшим приоритетом. Понимание границы между режимами также помогает выявлять аномалии: легитимный код крайне редко пересекает эту границу неестественным образом, тогда как многие вредоносные программы стремятся попасть в ring0 для сокрытия своего присутствия (руткиты) или обхода средств защиты.

**Ключевые различия между пользовательским режимом и режимом ядра** удобно свести в сравнительную таблицу, которая наглядно демонстрирует последствия архитектурного разделения:

| Характеристика | Пользовательский режим (Ring 3) | Режим ядра (Ring 0) |
|----------------|----------------------------------|----------------------|
| **Привилегии процессора** | Ограниченный набор инструкций; привилегированные инструкции (например, `HLT`, `RDMSR`) запрещены | Полный набор инструкций, включая управление процессором, таблицами страниц, портами ввода-вывода |
| **Доступ к памяти** | Только собственное виртуальное адресное пространство процесса; попытка чтения/записи памяти ядра или другого процесса без санкционированного разделения приводит к исключению | Полный доступ ко всей физической памяти, включая память всех процессов и системные структуры |
| **Взаимодействие с оборудованием** | Только через документированные API (файловые операции, сетевые сокеты и т.д.) с посредничеством драйверов | Прямой доступ к регистрам устройств, DMA, обработка аппаратных прерываний |
| **Последствия ошибки** | Аварийное завершение процесса (exception); система продолжает работу, другие процессы не затрагиваются | Крах системы (BSOD, зависание); нарушается целостность критических структур |
| **Типичный код** | Пользовательские приложения (notepad.exe, chrome.exe), системные службы (spoolsv.exe), подсистемы окружения, DLL (kernel32.dll, user32.dll) | Исполнительная система (ntoskrnl.exe), драйверы устройств (.sys), HAL (hal.dll), графическая подсистема (win32k.sys) |
| **Механизм перехода** | Вызывает функции WinAPI, которые через библиотеку ntdll.dll и инструкцию `syscall` (x64) или `int 2Eh` (x86) передают управление в ядро | Возвращает управление через `sysret` после обработки запроса; может инициировать APC или DPC для вызова callback-функций в контексте пользовательского потока |

Эта таблица даёт базовый каркас для последующего детального рассмотрения архитектурных компонентов каждого режима и механизмов их взаимодействия.

## Архитектурная начинка режимов: компоненты и иерархия

Внутреннее устройство Windows отражает модульный подход, при котором компоненты строго распределены между двумя режимами. Ниже представлена упрощённая схема, основанная на классической диаграмме архитектуры Windows NT [Архитектура Windows NT](https://ru.wikipedia.org/wiki/%D0%90%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0_Windows_NT) и более поздних публикациях [Deep Dive into Windows Architecture](https://medium.com/@Usta0x001/deep-dive-into-windows-architecture-88f429e8843e):

```text
[Пользовательский режим (Ring 3)]
  ┌────────────────────────────────────────────────────────────────┐
  │      Пользовательские приложения (notepad.exe, cmd.exe)        │
  │                          Системные процессы                    │
  │          (smss.exe, csrss.exe, winlogon.exe, services.exe)      │
  │              Подсистемы окружения (Win32, POSIX, OS/2)         │
  │                 DLL подсистем (kernel32.dll, user32.dll)        │
  └──────────────────────────────┬─────────────────────────────────┘
                                 │  (системный вызов через ntdll.dll)
  ┌──────────────────────────────┴─────────────────────────────────┐
  [Режим ядра (Ring 0)]                                             │
  │                                                                 │
  │  ┌────────────────────────────────────────────────────────────┐│
  │  │        Исполнительная система (Executive)                  ││
  │  │  Диспетчеры: объектов, памяти, процессов, ввода-вывода,    ││
  │  │  безопасности, конфигурации, кэша, электропитания, PnP     ││
  │  └──────────────────────────────┬─────────────────────────────┘│
  │                                 │                               │
  │  ┌──────────────────────────────┴─────────────────────────────┐│
  │  │    Ядро ОС (ntoskrnl.exe, «микроядро»)                      ││
  │  │    Планирование потоков, синхронизация, обработка          ││
  │  │    прерываний и исключений, базовые механизмы IPC          ││
  │  └──────────────────────────────┬─────────────────────────────┘│
  │                                 │                               │
  │      ┌───────────────┬──────────+──────────┬────────────────┐  │
  │   Драйверы       Драйверы     HAL      Графическая     Win32k.sys│
  │   устройств   файловых систем (hal.dll) подсистема    (GDI/USER) │

  └──────────────────────────────────────────────────────────────┘
```

Рассмотрим обе половины подробнее.

### Пользовательский режим

В пользовательском режиме работают все процессы, прямо видимые в Диспетчере задач. Их можно разделить на несколько функциональных групп:

- **Пользовательские приложения** — программы, запущенные интерактивными пользователями или службами. Каждое приложение выполняется в собственном изолированном виртуальном адресном пространстве и взаимодействует с системой исключительно через документированные API-функции, предоставляемые библиотеками DLL. Например, текстовый редактор для открытия файла вызывает функцию `CreateFileW` из `kernel32.dll`.

- **Системные процессы** — специальные процессы, выполняющие критически важные задачи и запускаемые автоматически на ранних этапах загрузки. К ним относятся: `smss.exe` (Session Manager — инициализация сессий), `csrss.exe` (Client/Server Runtime Subsystem — оконная функциональность), `winlogon.exe` (аутентификация пользователей), `services.exe` (хост для фоновых служб). Хотя они относятся к пользовательскому режиму, многие из них работают с повышенными привилегиями (системный контекст) и имеют доступ к критическим объектам ядра через дескрипторы.

- **Подсистемы окружения** — модули, обеспечивающие совместимость приложений, написанных для различных программных интерфейсов. Основной является подсистема Win32, реализуемая через процесс `csrss.exe` и набор DLL (kernel32.dll, user32.dll, gdi32.dll). Исторически существовали также подсистемы POSIX (psxdll.dll) и OS/2, но поддержка POSIX прекращена начиная с Windows 7 [АРХИТЕКТУРА WINDOWS NT](https://cyberleninka.ru/article/n/arhitektura-windows-nt). Каждая подсистема транслирует вызовы своего API в вызовы *native* API, предоставляемого ntdll.dll.

- **Динамические библиотеки (DLL)** — исполняемый код, загружаемый в адресное пространство процесса во время выполнения. Ключевой библиотекой, присутствующей в каждом процессе Windows, является `ntdll.dll`. Она выполняет роль шлюза между пользовательским режимом и режимом ядра: экспортирует сотни функций-заглушек (например, NtCreateFile, NtQuerySystemInformation), каждая из которых содержит инструкцию перехода в Ring 0 (на x64 — `syscall`). Другие важные DLL, такие как kernel32.dll или kernelbase.dll, являются надстройками над ntdll, предоставляя более удобные и документированные API для прикладных программистов [НОУ ИНТУИТ | Введение во внутреннее устройство Windows](https://intuit.ru/studies/courses/10471/1078/lecture/16569).

Изоляция процессов в пользовательском режиме является первым эшелоном защиты: даже если одно приложение скомпрометировано, злоумышленник не может напрямую вмешаться в память ядра или другого процесса без дополнительной техники повышения привилегий.

### Режим ядра

Компоненты, выполняющиеся в Ring 0, образуют так называемое «гибридное ядро» — комбинацию монолитного ядра и микроядра. Вся совокупность кода режима ядра собрана, в основном, в файле `ntoskrnl.exe`, а также в отдельных модулях драйверов и HAL. Ключевые блоки:

- **Исполнительная система (Executive)** — верхний уровень ядра, реализующий наиболее сложную логику управления ресурсами. Она состоит из набора независимых диспетчеров (менеджеров):
  - *Диспетчер объектов (Object Manager)* — унифицирует создание, удаление и контроль доступа ко всем объектам ядра (процессы, потоки, файлы, семафоры, секции и т.д.). Каждый объект ядра в пользовательском режиме представлен непрозрачным дескриптором (handle).
  - *Диспетчер памяти (Memory Manager)* — управляет виртуальной памятью процессов, реализует подкачку страниц, разделение памяти между процессами и проецирование файлов.
  - *Диспетчер процессов (Process Manager)* — отвечает за создание и завершение процессов и потоков, управление их состоянием.
  - *Диспетчер ввода-вывода (I/O Manager)* — маршрутизирует запросы ввода-вывода от пользовательских приложений к соответствующим драйверам с помощью пакетов IRP (I/O Request Packet). Именно здесь реализована асинхронная модель ввода-вывода, характерная для Windows NT.
  - *Диспетчер безопасности (Security Reference Monitor)* — централизованно проверяет права доступа к объектам на основе дескрипторов безопасности (ACL). Каждый раз, когда процесс запрашивает доступ к объекту, диспетчер сверяет маркер доступа процесса с ACL объекта.
  - *Диспетчер конфигурации (Configuration Manager)* — управляет системным реестром, предоставляя к нему интерфейс как к иерархической базе данных.
  - *Диспетчер кэша (Cache Manager)* и *Диспетчер PnP/электропитания* — обеспечивают кэширование файловых данных и управление питанием/подключением устройств соответственно.

- **Ядро (микроядро)** — низкоуровневый слой, реализующий самые фундаментальные функции: планирование и диспетчеризацию потоков, обработку прерываний и ловушек (trap handling), низкоуровневую синхронизацию (спин-блокировки), а также механизмы IPC, такие как APC (Asynchronous Procedure Call) и DPC (Deferred Procedure Call). Этот компонент наиболее сильно зависит от архитектуры процессора.

- **Драйверы устройств** — модули, загружаемые по мере необходимости, для взаимодействия с конкретным «железом» (дисками, сетью, графикой) или для расширения функциональности ядра (например, драйверы файловых систем ntfs.sys, сетевые фильтры). Драйверы выполняются в контексте вызвавшего их потока или в контексте системных рабочих потоков. С точки зрения безопасности драйверы — критическая поверхность атаки, поскольку они разделяют адресное пространство ядра и в случае ошибки могут нарушить его целостность [АРХИТЕКТУРА WINDOWS NT](https://cyberleninka.ru/article/n/arhitektura-windows-nt).

- **HAL (Hardware Abstraction Layer)** — библиотека hal.dll, скрывающая от остального ядра аппаратные различия платформ. Она предоставляет абстрактные интерфейсы для работы с прерываниями (IDT), таймерами APIC, DMA и шинами PCI/PCIe. Благодаря HAL один и тот же образ ntoskrnl.exe может работать на разнородном оборудовании без модификации.

- **Графическая подсистема** — компоненты, обеспечивающие оконную графику: `win32k.sys` содержит реализацию GDI (Graphics Device Interface) и менеджмент окон (USER). Исторически этот код был вынесен в ядро ради производительности, но это решение породило значительную долю уязвимостей, эксплуатируемых для локального повышения привилегий [НОУ ИНТУИТ | Введение во внутреннее устройство Windows](https://intuit.ru/studies/courses/10471/1078/lecture/16569).

Отношения между перечисленными компонентами образуют строгую иерархию: пользовательский запрос (например, на открытие файла) проходит цепочку от приложения через DLL подсистем, ntdll, границу режимов, диспетчер ввода-вывода, драйвер файловой системы и драйвер диска до самого оборудования с ответом по обратному пути. Такое устройство гарантирует, что прикладной код ни на одном шаге не получает бесконтрольного доступа к ресурсам.

## Переход между мирами: системные вызовы, IRP и практические инструменты

Разрыв между пользовательским режимом и режимом ядра преодолевается через чётко определённые интерфейсы. Основным каналом служат **системные вызовы** (system calls). В Windows на платформе x64 механизм выглядит так:

1. Код приложения вызывает документированную функцию WinAPI, например, `CreateFileW` из `kernel32.dll`. Эта функция после выполнения некоторых служебных действий вызывает недокументированный аналог `NtCreateFile` из `ntdll.dll`.
2. В теле `NtCreateFile` в `ntdll.dll` находится инструкция `syscall` (на x86 — `int 2Eh` или более поздний `sysenter`). Эта инструкция переключает процессор в Ring 0 и передаёт управление точке входа, указанной в модельно-специфическом регистре MSR `LSTAR` (обычно это функция `KiSystemCall64` в `ntoskrnl.exe`).
3. Диспетчер системных сервисов в ядре по номеру вызова (переданному в регистре eax) находит соответствующую функцию Executive (например, `NtCreateFile` в том же ntoskrnl.exe) и вызывает её. После выполнения управление через `sysret` возвращается обратно в ntdll, а затем и в приложение.

Для подсистемы ввода-вывода архитектура дополнительно включает **пакеты запросов ввода-вывода (IRP)**. Когда диспетчер ввода-вывода получает системный вызов на операцию с файлом, он создаёт IRP — структуру данных, описывающую запрос (код операции, буфер, смещение, целевой объект-устройство), и посылает его по стеку драйверов, соответствующих файловой системе и дисковому устройству. Драйверы обрабатывают IRP по цепочке, возможно, модифицируя его, и завершают запрос, после чего результат возвращается вызывающему потоку [Архитектура Windows NT](https://ru.wikipedia.org/wiki/%D0%90%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0_Windows_NT).

С практической точки зрения, специалист SOC может использовать несколько встроенных и бесплатных инструментов для наблюдения за пересечением границы режимов.

**Просмотр экспортов ntdll** — простейший способ убедиться, что шлюзовые функции действительно существуют. Команда `dumpbin /exports` (доступна в составе Visual Studio или Windows SDK) отображает точки входа DLL. Ниже показан иллюстративный вывод для `ntdll.dll`, демонстрирующий наличие экспорта `NtCreateFile`:

```powershell
dumpbin /exports C:\Windows\System32\ntdll.dll | findstr NtCreateFile
# Примерный фрагмент вывода (иллюстративная схема)
#          Ordinal   Hint RVA      Name
#          0x0158      1  000A3B20 NtCreateFile
```

Это подтверждает, что любое приложение, загрузившее ntdll (а это делают все процессы Windows), имеет на руках «телефонный номер» функции, переводящей вызов в ядро.

**Проверка загрузки DLL в процессы** — утилита `tasklist` с ключом `/m` показывает, какие модули использует каждый процесс:

```cmd
tasklist /m ntdll.dll
# (вывод сокращён)
# Имя образа                     PID Модули
# ========================== ======== ===========
# System Idle Process              0 Н/Д
# System                           4 Н/Д
# smss.exe                       324 ntdll.dll
# csrss.exe                      508 ntdll.dll
# wininit.exe                    544 ntdll.dll
# services.exe                   596 ntdll.dll
# lsass.exe                      604 ntdll.dll
# notepad.exe                   4732 ntdll.dll
```

Отсутствие `ntdll.dll` в адресном пространстве запущенного процесса — серьёзная аномалия, которая может указывать на подмену образа процесса или использование недокументированных методов сокрытия (например, процесс с полностью выгруженным ntdll встречается у некоторых вредоносных программ, стремящихся избежать хуков).

**Мониторинг системных вызовов в реальном времени** — для глубокого обучения полезен Process Monitor из набора Sysinternals. При фильтрации по конкретному процессу можно видеть не только события файловой системы и реестра, но и соответствующие им операции в ядре. Каждое событие содержит стек вызовов, который наглядно показывает переход от приложения до драйвера. Пример детального анализа будет приведён в следующем разделе.

**Ключевое ограничение для SOC L1** — даже имея стек, необходимо помнить, что детальная внутренняя реализация API-функций может меняться в разных версиях и сборках Windows. Поэтому при анализе инцидентов важнее понимать общую схему, а не запоминать конкретные смещения. Кроме того, инструменты вроде Procmon перехватывают события на уровне драйвера фильтрации, а не самого приложения, что иногда приводит к разнице в порядке или количестве событий; это нормально.

## Сквозной практический пример: трассировка открытия файла от Блокнота до NTFS

### Исходные условия

Система: Windows 10 x64 (сборка 21H2). Установлен утилитарный пакет Sysinternals (Process Monitor). Задача: на примере простейшей операции открытия файла в Блокноте проследить полный путь от пользовательского клика до обработки в драйвере файловой системы NTFS, демонстрируя архитектурное разделение режимов и ключевые промежуточные компоненты.

### Шаг 1. Захват событий с фильтрацией

Запускаем Process Monitor с правами администратора. Включаем захват, устанавливаем фильтр: `Process Name` is `notepad.exe`. Запускаем Блокнот, в меню `Файл` → `Открыть` выбираем тестовый файл `C:\temp\example.txt` и нажимаем «Открыть». Сразу после этого останавливаем захват событий (Ctrl+E).  
В окне Procmon появляется несколько тысяч событий; нас интересуют операции типа `CreateFile`.

### Шаг 2. Идентификация целевого события

Ищем строку, где `Operation` = `CreateFile`, `Path` содержит `C:\temp\example.txt`, а результат `SUCCESS`. Типичный вид строки (иллюстративная схема, основанная на реальном выводе Procmon):

```text
Sequence: 1432
Time: 10:34:21.0451237
Process Name: notepad.exe
PID: 4732
Operation: CreateFile
Path: C:\temp\example.txt
Result: SUCCESS
Detail: Desired Access: Generic Read, Disposition: Open, Options: Synchronous IO Non-Alert, Attributes: N, ShareMode: Read, AllocationSize: 0
```

Это событие доказывает, что операция успешно завершилась. Но главное — Procmon позволяет увидеть, какой путь прошёл запрос внутри системы.

### Шаг 3. Изучение стека вызовов

При двойном клике на событие открывается окно свойств, вкладка **Stack**. На ней отображается цепочка вызовов, сохранённая драйвером фильтрации Procmon (Procmon.sys) в момент операции. Ниже приведён иллюстративный фрагмент, воссозданный по типичному стеку для простого открытия файла:

```text
Фрагмент стека (иллюстративная схема, WinDbg-подобный вывод)
Драйверная часть (Ring 0):
 ntoskrnl.exe!NtCreateFile
 ntoskrnl.exe!IoCreateFileEx
 ntoskrnl.exe!IopCreateFile
 FLTMGR.SYS!FltpCreateFileEx2+0x...
 ntfs.sys!NtfsFsdCreate+0x...
 ntoskrnl.exe!IofCallDriver+0x...
 ntoskrnl.exe!KiSystemServiceCopyEnd+0x...
-----------------------------------------------
Пользовательская часть (Ring 3):
 ntdll.dll!NtCreateFile
 kernelbase.dll!CreateFileW
 notepad.exe!main+0x...
```

Здесь отчётливо видны:
- Исходная точка в notepad.exe, вероятно, вызвавшая высокоуровневую функцию.
- kernelbase.dll, реализующая документированное API `CreateFileW`.
- ntdll.dll с `NtCreateFile` — точка входа в ядро.
- Обработка в ntoskrnl.exe: диспетчеризация системного сервиса (`KiSystemServiceCopyEnd`) и затем исполнительная функция `NtCreateFile`, которая через менеджер ввода-вывода (`IoCreateFileEx`) передала запрос драйверу фильтрации (`FLTMGR.SYS`) и, наконец, драйверу файловой системы NTFS (`ntfs.sys`).

### Шаг 4. Анализ IRP (дополнительно, для понимания)

Хотя стек из Procmon не показывает структуру IRP, можно мысленно восстановить её содержимое. На базе параметров из колонки `Detail`:

- `Desired Access: Generic Read` → в IRP поле `Parameters.Create.SecurityContext` с запрошенными правами.
- `Disposition: Open` → указывает, что файл должен быть открыт, а не создан.
- `Options: Synchronous IO Non-Alert` → IRP с флагом `IRP_SYNCHRONOUS_API`.

IRP был создан диспетчером ввода-вывода и направлен в стек драйверов: `\FileSystem\ntfs` → `\Driver\Disk`. На каждом уровне драйвер мог модифицировать или просто пробросить IRP дальше. Такой подход позволяет, например, антивирусному фильтру (зарегистрированному в цепочке через FLTMGR) перехватить запрос и проверить файл перед тем, как он будет прочитан.

### Ожидаемый вывод

Данный пример на практике подтверждает теоретическую модель: взаимодействие приложения с файловой системой реализовано не напрямую, а через длинную цепочку посредников в пользовательском режиме и режиме ядра. Для аналитика SOC Level 1 этот эксперимент даёт следующие важные навыки:

- Умение связать высокоуровневое действие пользователя (открытие файла) с низкоуровневыми событиями, видимыми в мониторинге.
- Понимание, что сбой на любом из этапов (ntdll, ntoskrnl, драйвер) может привести к совершенно разным внешним симптомам: ошибка в приложении, «зависание» операции, BSOD.
- Способность при разборе инцидентов с подозрительной активностью (например, процесс пытается открыть системный файл в обход стандартных API) интерпретировать стек вызовов из Procmon или Sysmon Event ID 1 (Process Create), видя в нём аномалии вроде отсутствия ntdll или нестандартных путей DLL.

Таким образом, архитектурное разделение на пользовательский режим и режим ядра — не просто теоретическая конструкция, а ежедневно работающий механизм, с которым специалист SOC сталкивается в журналах событий, дампах памяти и логах средств защиты.
