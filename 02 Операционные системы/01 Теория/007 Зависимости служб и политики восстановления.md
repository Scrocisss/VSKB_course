# Зависимости служб и политики восстановления в Windows

## 1. Службы как управляемые объекты: контекст надёжности

Службы Windows — фоновые процессы, управляемые диспетчером управления службами (Service Control Manager, SCM). От их бесперебойной работы зависит функционирование всей ОС: от сетевого стека до доменных служб Active Directory. Администратор и специалист SOC должны чётко понимать два базовых механизма, обеспечивающих предсказуемость и отказоустойчивость служб:

- **Зависимости служб** (service dependencies) — формальные связи, гарантирующие, что служба запускается только при наличии необходимых компонентов, и определяющие порядок старта.
- **Политики восстановления** (recovery policies) — набор правил, задающих автоматические действия SCM при аварийном завершении или остановке службы с ошибкой.

Хотя оба механизма конфигурируются независимо и решают разные задачи, на практике они часто применяются совместно для построения самовосстанавливающейся серверной инфраструктуры. В таблице ниже сопоставлены их ключевые характеристики.

| Характеристика | Зависимости служб | Политики восстановления |
|----------------|-------------------|--------------------------|
| **Цель** | Гарантировать, что все требуемые компоненты запущены до старта; задать жёсткий порядок инициализации | Автоматически реагировать на сбои, чтобы минимизировать время простоя |
| **Хранение конфигурации** | Значение `DependOnService` (REG_MULTI_SZ) в разделе реестра `HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>` | Значение `FailureActions` (REG_BINARY) и флаг `FailureActionsOnNonCrashFailures` (REG_DWORD) в том же разделе |
| **Способ настройки** | `services.msc` → вкладка Dependencies; `sc config <svc> depend= ...` | `services.msc` → вкладка Recovery; `sc failure <svc> reset= ... actions= ...` |
| **Момент срабатывания** | При старте службы (до вызова точки входа `ServiceMain`) | При падении процесса службы либо, при установленном флаге, при остановке с ненулевым кодом |
| **Характер воздействия** | Блокирующий: если хотя бы одна зависимость не запущена, целевая служба не стартует | Реактивный: счётчик отказов увеличивается, SCM выполняет действие, соответствующее текущей попытке |
| **Пример** | Служба `W3SVC` зависит от `HTTP`, поэтому пока `HTTP` остановлен, IIS не запустится | При первом падении `SQLANYs_servicename` перезапуск через 60 с, при втором — снова через 60 с, затем бездействие |

Важно разграничить зависимости служб и механизм **групп загрузки** (`LoadOrderGroup`). Группы определяют лишь относительный порядок попыток запуска внутри фазы загрузки ОС, но не гарантируют, что служба-предшественник уже находится в состоянии `SERVICE_RUNNING`. Зависимости же являются жёстким контрактом: SCM рекурсивно стартует всё дерево зависимых служб (если для них задан автоматический тип запуска) и дожидается, пока каждая из них просигнализирует о готовности. Поэтому для критически важных цепочек следует полагаться именно на зависимости, а не на группы загрузки.

Другой смежный механизм — **отложенный запуск** (Automatic Delayed Start). Он не влияет на порядок относительно других служб, а лишь добавляет паузу после загрузки всех автоматических служб перед попыткой старта. Это полезно для снижения конкуренции за ресурсы при старте ОС, но не заменяет зависимостей.

Таким образом, зависимости и политики восстановления — два столпа надёжности служб Windows. Понимание их различий и внутреннего устройства позволит проводить грамотную диагностику инцидентов и проактивно настраивать отказоустойчивость.

## 2. Внутреннее устройство: реестр, цепочки и структуры действий

Оба механизма реализованы через параметры реестра под ключом `HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>`. SCM считывает их при старте службы (зависимости) или при каждом переходе в состояние ошибки (политики восстановления).

### 2.1. Хранение зависимостей

Зависимости перечислены в значении `DependOnService` типа `REG_MULTI_SZ`. Каждая строка — это короткое имя службы (не отображаемое имя). Например, для контроллера домена значение `DependOnService` у службы `Netlogon` может содержать:

```
LanmanWorkstation
LanmanServer
```

При запуске службы SCM проверяет все указанные зависимости и, если какая-либо из них не запущена, пытается запустить её (при условии, что для неё задан автоматический тип запуска). Транзитивность работает рекурсивно: зависимости проверяются по цепочке. На практике это означает, что для успешного старта `Netlogon` должны быть полностью работоспособны и `LanmanWorkstation`, и `LanmanServer`, а также их собственные зависимости.

На основе документации Microsoft и [статьи Troubleshoot Netlogon Service Startup Failures](https://learn.microsoft.com/en-us/troubleshoot/windows-server/windows-security/troubleshoot-netlogon-service-startup-failures) можно изобразить типичную цепочку:

```text
[Netlogon] ──требует──▶ [LanmanWorkstation] ──требует──▶ [Browser]
           │                                         │
           │                                         └──требует──▶ [MrxSMB20] ...
           │
           └──требует──▶ [LanmanServer] ──требует──▶ [SAMSS]
                                         │
                                         └──требует──▶ [SRV2] ──требует──▶ [SRVNET] ...
```

Если в процессе диагностики служба не запускается, необходимо пройти по цепочке зависимостей в обратном порядке, запуская службы вручную от наиболее глубоких уровней, как рекомендовано в [How To Troubleshoot System Services](https://redmondmag.com/articles/2014/06/11/troubleshoot-system-services.aspx). Это позволяет выявить тот единственный отказавший узел, который блокирует всю иерархию.

Добавление пользовательских зависимостей через реестр (`reg add`) или `sc config` допустимо, но требует точного знания коротких имён. В [PDF-документе Viewing, Creating and Modifying Service Dependencies](https://cdn.logic-control.com/doc_downloader.php?f=ftp%2FAVEVA%2FTech+Notes%2FTech+Note+716+View+and+Create+Service+Dependencies.pdf) описан пример, когда добавление зависимости службы Wonderware AlarmDBLogger от SuiteLink обеспечило корректный порядок старта промышленного ПО.

### 2.2. Структура политик восстановления

Политики восстановления хранятся в бинарном значении `FailureActions`, формат которого соответствует структуре `SERVICE_FAILURE_ACTIONS`, документированной в MSDN. Основные поля:

- `dwResetPeriod` (DWORD, секунды) — период сброса счётчика отказов. Если за это время не произошло новых сбоев, счётчик обнуляется.
- `lpRebootMsg` (указатель на широкую строку) — сообщение, которое будет записано в системный журнал перед перезагрузкой (если выбрано действие `Reboot`).
- `lpCommand` (указатель на строку) — командная строка для действия `Run a Program`.
- `cActions` (DWORD) — количество записей в массиве действий.
- `lpsaActions` — массив структур `SC_ACTION`, каждая из которых содержит:
  - `Type` (DWORD): `0` = None, `1` = Reboot, `2` = Restart, `3` = RunCommand.
  - `Delay` (DWORD, миллисекунды) — задержка перед выполнением действия.

Кроме того, в ключе может присутствовать значение `FailureActionsOnNonCrashFailures` (REG_DWORD). Если оно установлено в `1`, SCM применяет сконфигурированные действия не только при аварийном завершении процесса (когда служба не успела перейти в состояние `SERVICE_STOPPED`), но и при явной остановке службы с ненулевым кодом ошибки. Эта функция появилась в Windows Vista/Server 2008 и управляется также командой `sc failureflag` [ServerFault](https://serverfault.com/questions/72318/set-up-recovery-actions-to-take-place-when-a-service-fails). По умолчанию флаг равен `0`, и действия при остановке с ошибкой не срабатывают.

Логика SCM при возникновении сбоя:

1. Счётчик отказов инкрементируется.
2. Среди массива `SC_ACTION` выбирается элемент с индексом `min(счётчик, cActions) - 1`.
3. Выполняется соответствующее действие с указанной задержкой.
4. Таймер сброса `dwResetPeriod` запускается заново; если он истекает без новых сбоев, счётчик сбрасывается в 0.

Типы действий и их семантика обобщены в таблице:

| Константа | Числовой код | GUI-аналог | Поведение |
|-----------|--------------|------------|-----------|
| SC_ACTION_NONE | 0 | Take No Action | Ничего не предпринимается, счётчик не сбрасывается |
| SC_ACTION_REBOOT | 1 | Restart the Computer | Перезагрузка компьютера (с сообщением `lpRebootMsg`) |
| SC_ACTION_RESTART | 2 | Restart the Service | Перезапуск упавшей службы |
| SC_ACTION_RUN_COMMAND | 3 | Run a Program | Запуск указанной в `lpCommand` программы |

Графический интерфейс `services.msc` позволяет задать действия для первого, второго и последующих сбоев, что соответствует трём элементам массива `SC_ACTION`. Командная утилита `sc.exe` даёт полный контроль над количеством действий и их параметрами.

## 3. Инструменты и практические приёмы работы

Работа с зависимостями и политиками восстановления на уровне SOC L1 предполагает уверенное владение стандартными утилитами командной строки и понимание реестра.

### 3.1. Просмотр и изменение зависимостей

Основной инструмент — `sc.exe`. Команда `qc` выводит конфигурацию службы, включая строку `DEPENDENCIES`. Например, для `Netlogon` на DC (см. [MS Learn](https://learn.microsoft.com/en-us/troubleshoot/windows-server/windows-security/troubleshoot-netlogon-service-startup-failures)):

```cmd
sc qc netlogon
```

Ожидаемый вывод (фрагмент):

```
SERVICE_NAME: netlogon
        TYPE               : 20  WIN32_SHARE_PROCESS
        START_TYPE         : 2   AUTO_START
        ...
        DEPENDENCIES       : LanmanWorkstation
                           : LanmanServer
        SERVICE_START_NAME : LocalSystem
```

Чтобы добавить зависимость, используется команда:

```cmd
sc config <сервис> depend= <список_через_слеш>
```

Пример из [Windows Forum](https://windowsforum.com/threads/manage-windows-services-create-configure-set-recovery-options-win10-11.380710) не приводит прямой команды на добавление зависимостей, но в [PDF-документе](https://cdn.logic-control.com/doc_downloader.php?f=ftp%2FAVEVA%2FTech+Notes%2FTech+Note+716+View+and+Create+Service+Dependencies.pdf) описан подход через реестр. В реальной практике команда может выглядеть так:

```cmd
sc config AlarmDBLogger depend= SuiteLink
```

**Важно:** после знака равенства в параметрах `sc config` и `sc failure` должен стоять пробел.

Для просмотра зависимостей в PowerShell удобно использовать встроенные методы объектов `ServiceController`:

```powershell
Get-Service -Name w3svc -RequiredServices
Get-Service -Name w3svc -DependentServices
```

Первая команда выводит список служб, от которых зависит `w3svc`; вторая — служб, которые зависят от `w3svc`. Эти командлеты полезны для быстрой оценки «снизу вверх» и «сверху вниз» в дереве зависимостей.

Для низкоуровневой работы с реестром можно применить `reg query`:

```cmd
reg query HKLM\SYSTEM\CurrentControlSet\Services\Netlogon /v DependOnService
```

Вывод отобразит значение типа `REG_MULTI_SZ`, где каждая строка — одна зависимость. Прямое редактирование возможно через `reg add` с ключом `/t REG_MULTI_SZ`, но должно выполняться с осторожностью, так как ошибка в синтаксисе способна сделать службу незапускаемой.

### 3.2. Настройка политик восстановления

Основной инструмент — `sc failure`. Полный синтаксис:

```cmd
sc failure <ServiceName> [reset= <сек>] [actions= <тип1>/<задержка1>[/<тип2>/<задержка2>...]] [reboot= <сообщение>] [command= <путь>]
```

Ключевые моменты:
- `reset=` задаёт `dwResetPeriod` в секундах.
- `actions=` принимает последовательность пар «тип/задержка», где тип — `run`, `reboot`, `restart`, `none`, задержка в миллисекундах.
- Если указано действие `reboot`, можно через `reboot=` указать широковещательное сообщение (необязательно).
- Если указано действие `run`, `command=` определяет исполняемый файл.

Пример из сообщества SAP [SAP Community](https://community.sap.com/t5/technology-q-a/setting-windows-service-recovery-actions-via-commandline-dbsvc/qaq-p/13836669):

```cmd
sc failure SQLANYs_servicename reset= 240 actions= restart/60000/restart/60000/none/0
```

Эта команда задаёт: при первом сбое перезапуск через 60 000 мс (1 мин), при втором — снова через 60 000 мс, при третьем — бездействие (`none/0`). Счётчик отказов сбрасывается, если за 240 секунд (4 мин) не было новых сбоев.

Проверить текущие настройки можно командой:

```cmd
sc qfailure SQLANYs_servicename
```

Вывод покажет значения `RESET_PERIOD`, `REBOOT_MESSAGE`, `COMMAND_LINE` и массив `FAILURE_ACTIONS`.

Флаг `failureflag` управляет учётом ошибок остановки. Установка:

```cmd
sc failureflag <ServiceName> 1
```

В [ServerFault](https://serverfault.com/questions/72318/set-up-recovery-actions-to-take-place-when-a-service-fails) поясняется, что это эквивалентно установке `FailureActionsOnNonCrashFailures = 1`. Это важно, если служба может корректно завершить работу, но сделать это с ненулевым кодом (`exit code != 0`), сигнализирующим о логической ошибке. Без этого флага SCM не запустит цепочку восстановления.

В PowerShell, в отличие от зависимостей, штатных команлетов для настройки восстановления нет, однако можно изменить параметры через WMI:

```powershell
$svc = Get-WmiObject -Class Win32_Service -Filter "Name='w3svc'"
$svc.sc-Change( ... )  # требует специфического вызова с параметрами восстановления
```

Но проще и надёжнее использовать `sc.exe` — он непосредственно взаимодействует с API SCM.

### 3.3. Диагностика и типовые ошибки

При диагностике отказов службы часто возникает две типовых ситуации.

**Сбой из-за зависимостей.** Симптомы: служба не стартует, в системном журнале событий может появиться запись о том, что зависимая служба или группа не запустилась. Последовательность действий:
1. `sc qc <проблемная_служба>` — выявить прямые зависимости.
2. Проверить состояние каждой зависимости: `sc query <dep1>` и т.д.
3. Если какая-то зависимость остановлена — попытаться запустить вручную: `sc start <dep>`. Ошибка запуска указывает на корневую причину.
4. Рекурсивно пройти по дереву зависимостей, пока не найдётся служба, которая не стартует из-за собственной ошибки (некорректный `ImagePath`, проблемы с правами, отсутствующий файл и т.п.). В [Redmondmag](https://redmondmag.com/articles/2014/06/11/troubleshoot-system-services.aspx) подчёркивается, что ручной запуск с самого глубокого уровня цепочки — самый надёжный способ локализации.

**Политики восстановления не срабатывают, когда ожидалось.** Возможные причины:
- Не установлен флаг `failureflag 1`, а служба завершилась вызовом `SERVICE_STOPPED` с ненулевым кодом (типично для серверных процессов, управляемых внутренней логикой).
- Неверный синтаксис `sc failure`: пропущен пробел после `=`, неверный порядок типов (например, указан `run` без предварительного `command=`).
- Неправильно рассчитан период сброса: если сбой происходит реже, чем `dwResetPeriod`, счётчик может быть уже сброшен, и первое действие (например, перезапуск) применяется снова вместо второго.
- Ограничения безопасности: если в качестве учётной записи службы задана учётка без права входа в систему (`Log on as a service`) или без прав на запуск указанной программы, действия `Run a Program` не выполнятся.

Также стоит помнить, что для служб с защищёнными процессами (`Protected Service`) часть параметров восстановления может быть ограничена (зависит от версии ОС и конфигурации антивирусной защиты).

## 4. Сквозной практический пример: восстановление IIS с настройкой автоматического перезапуска

**Исходные условия:** сервер Windows Server 2019, роль IIS с сайтом, который должен быть постоянно доступен. В ходе мониторинга SOC обнаруживает, что сайт не отвечает, а служба `W3SVC` (World Wide Web Publishing Service) находится в состоянии `STOPPED`. Администратор должен оперативно восстановить работоспособность и настроить автоматический перезапуск при сбоях.

**Шаг 1.** Проверить состояние проблемной службы и её прямых зависимостей.

```cmd
sc query w3svc
```

Вывод (иллюстративная схема):

```
SERVICE_NAME: w3svc
        TYPE               : 20  WIN32_SHARE_PROCESS
        STATE              : 1  STOPPED
        WIN32_EXIT_CODE    : 0  (0x0)
        SERVICE_EXIT_CODE  : 0  (0x0)
        ...
```

Служба остановлена. Выясняем, какие зависимости у неё указаны:

```cmd
sc qc w3svc
```

Фрагмент вывода:

```
        DEPENDENCIES       : HTTP
                           : WAP (Windows Process Activation Service)
```

**Шаг 2.** Проверить состояние зависимости. Служба `HTTP` (Windows HTTP Service) критически важна.

```cmd
sc query http
```

Вывод:

```
SERVICE_NAME: http
        STATE              : 4  RUNNING
        ...
```

Служба работает, но следующая в цепочке — `WAP` (Windows Process Activation Service) — может быть остановлена. Проверим:

```cmd
sc query wap
```

Ожидаемый результат: `STATE : 1 STOPPED`. Именно она блокирует старт `w3svc`. Исследуем зависимости `WAP`:

```cmd
sc qc wap
```

Вывод показывает, что `WAP` зависит от `RPCSS` (Remote Procedure Call). Проверим `RPCSS`:

```cmd
sc query rpcss
```

Если `RPCSS` работает, значит проблема не в зависимостях верхнего уровня, а в самой службе `WAP`. Попытка ручного запуска:

```cmd
sc start wap
```

Возвращает ошибку (например, `FAILED 1068: The dependency service or group failed to start`). Дальнейшая диагностика может показать сбой конфигурации `WAS` (Windows Process Activation Service) или повреждённый файл конфигурации. Для целей примера предположим, что проблема устранена корректировкой типа запуска с ручного на автоматический:

```cmd
sc config wap start= auto
sc start wap
```

После успешного старта `WAP` запускаем целевую службу:

```cmd
sc start w3svc
```

Теперь `sc query w3svc` показывает `STATE : 4 RUNNING`. Доступность сайта восстановлена.

**Шаг 3.** Настроить политику восстановления для `w3svc`, чтобы в будущем не требовалось ручное вмешательство.

Зададим следующую логику: при первом сбое — перезапуск через 1 минуту, при втором — перезапуск через 2 минуты, при третьем — перезагрузка сервера с задержкой 5 минут (чтобы дать время на корректное завершение других процессов). Сброс счётчика отказов — через 24 часа (86400 с). Команда:

```cmd
sc failure w3svc reset= 86400 actions= restart/60000/restart/120000/reboot/300000
```

Проверяем применённые настройки:

```cmd
sc qfailure w3svc
```

Ожидаемый вывод (ключевые поля):

```
        RESET_PERIOD      : 86400 seconds
        FAILURE_ACTIONS   : RESTART -- Delay = 60000 milliseconds.
                           : RESTART -- Delay = 120000 milliseconds.
                           : REBOOT  -- Delay = 300000 milliseconds.
```

Убедимся также, что действия будут срабатывать при остановке с ошибкой, а не только при аварийном завершении:

```cmd
sc failureflag w3svc 1
```

**Шаг 4.** Имитация сбоя для проверки.

Найдём PID процесса, на котором работает служба (обычно это один из дочерних процессов в `svchost.exe -k iissvcs`). Можно воспользоваться командой:

```cmd
tasklist /svc | findstr w3svc
```

Завершим процесс (только в учебной/тестовой среде!):

```cmd
taskkill /pid <PID> /f
```

После этого служба `W3SVC` перейдёт в состояние `STOPPED`. В течение минуты (задержка первого действия) SCM перезапустит её автоматически. Наблюдать можно повторной командой:

```cmd
sc query w3svc
```

Через некоторое время состояние сменится обратно на `RUNNING`.

**Ожидаемый вывод:** пример демонстрирует, как анализ цепочки зависимостей позволил быстро найти корневую причину недоступности сайта (остановленная `WAP`), а затем настроенная политика восстановления обеспечила автоматическое устранение будущих сбоев. Сочетание этих двух механизмов — ключевая компетенция специалиста SOC L1 при работе со службами Windows.
