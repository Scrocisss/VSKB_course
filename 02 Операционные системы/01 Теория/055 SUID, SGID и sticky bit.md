# SUID, SGID и Sticky Bit в Linux

## Контекст и базовые понятия

В Linux каждый файл и каталог обладает базовым набором прав доступа, определяющим возможность чтения (`r`), записи (`w`) и выполнения (`x`) для трёх категорий: владельца-пользователя (`user`), владельца-группы (`group`) и всех остальных (`other`). Эта модель покрывает большинство повседневных задач, однако в многопользовательской среде возникают требования, которые не решить только комбинациями `rwx`:

* разрешить обычному пользователю выполнить операцию, требующую привилегий другого пользователя (например, смена собственного пароля);
* обеспечить совместную работу над файлами в каталогах таким образом, чтобы все участники автоматически получали корректную групповую принадлежность;
* защитить общедоступные каталоги от удаления чужих временных файлов.

Для этих целей служат три специальных бита прав, расширяющие стандартную схему: **SUID (Set User ID)**, **SGID (Set Group ID)** и **sticky bit**. Они не заменяют обычные права, а модифицируют поведение процессов при выполнении файлов или правила владения для каталогов. В отличие от первичных битов `rwx`, каждый из них имеет строго определённую узкую функцию, и их настройка напрямую влияет на безопасность всей системы.

Исторически sticky bit (от «sticky» — прилипать) впервые появился в Unix для маркировки исполняемых файлов, которые должны были оставаться в своп-пространстве после завершения, чтобы ускорить повторный запуск. В современных Linux-системах эта функция полностью утратила смысл, и sticky bit сохранился исключительно как атрибут каталогов с совершенно другой семантикой. SUID и SGID пришли из необходимости временного повышения привилегий без обращения к `su` или `sudo` — идея, восходящая к тому, что определённые системные утилиты должны выполняться с правами их владельца, а не того, кто их запустил.

Ниже представлена сравнительная характеристика трёх специальных битов. Она фиксирует разницу в поведении на файлах и каталогах, а также индикаторы, видимые в выводе стандартных утилит.

| Специальный бит        | Восьмеричный префикс | Действие на исполняемый файл                                                                    | Действие на каталог                                                                                                                                              | Отображение в `ls -l` (при наличии права `x`) | Пример из системы (иллюстративно)                         |
|------------------------|----------------------|-------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------|------------------------------------------------------------|
| SUID (Set User ID)     | 4                    | Процесс получает эффективный UID владельца файла (effective uid) вместо реального UID вызвавшего | Не оказывает типового эффекта; в большинстве ОС Linux игнорируется на каталогах (не повышает привилегии для создаваемых в нём файлов)                             | `s` в триаде пользователя: `rws` вместо `rwx` | `/usr/bin/passwd` (владелец root)                          |
| SGID (Set Group ID)    | 2                    | Процесс получает эффективный GID (групповой идентификатор) группы-владельца файла                | Все новые файлы и подкаталоги, создаваемые внутри, наследуют группу родительского каталога (а не первичную группу владельца процесса)                        | `s` в триаде группы: `rws` или `r-s`          | `/usr/bin/wall` (группа root, исполняется с GID root)      |
| Sticky bit             | 1                    | Игнорируется в современных ядрах (ранее — удержание в памяти, «sticky»)                         | Удалить или переименовать файл в каталоге может только владелец файла, владелец каталога или root (даже если права записи на каталог есть у других пользователей) | `t` в триаде остальных: `rwt` вместо `rwx`    | `/tmp` (доступен на запись всем, но чужие файлы не удалить) |

Символ `s` или `t` отображается в поле, где обычно стоит `x`. Если право выполнения для соответствующей категории не установлено, используется заглавная буква `S` или `T`, что одновременно сигнализирует об отсутствии `x` и о том, что специальный бит не сможет проявить ожидаемый эффект. Например, `rw-rwsr--` — некорректная запись; правильная будет `rwSrw-r--`, где `S` указывает на SUID без execute-бита.

Принципиальное разграничение между этими битами и обычным правом выполнения кроется в *контексте* исполнения. Обычный `x` говорит: «пользователь может запустить программу от своего имени», тогда как SUID добавляет: «но программа временно получает права владельца файла». Аналогично, SGID на каталоге не регулирует доступ к самому каталогу, а управляет атрибутами создаваемых внутри объектов. Sticky bit и вовсе не касается выполнения — он модифицирует только операции удаления/переименования в рамках конкретной директории.

Для аналитика SOC L1 важно понимать не только назначение каждого бита, но и то, как их неправильная конфигурация создаёт векторы повышения привилегий или нарушения целостности данных, которые рассматриваются во втором и третьем разделах.

## Внутреннее устройство: биты, системные вызовы и логика ядра

Специальные разрешения хранятся в том же поле `mode` индексного дескриптора (inode), что и базовые права. Полное 12-битное представление режима доступа выглядит как конкатенация трёх групп по четыре бита, где старшие три бита как раз кодируют SUID, SGID и sticky, а младшие девять — традиционные `rwx` для user, group и other. Восьмеричная запись использует отдельную позицию перед классической тройкой: `0«спец»«user»«group»«other»`, например, `4755` раскладывается на `4` (SUID) и `755` (`rwxr-xr-x`).

На уровне исходного кода ядра (Linux VFS) эти биты представлены константами в заголовочном файле `<linux/stat.h>`: `S_ISUID` (0004000), `S_ISGID` (0002000), `S_ISVTX` (0001000). При вызове системной функции `chmod()` или её обёрток ядро атомарно модифицирует поле `mode` inode, затем обновляет кэш атрибутов. Файловые системы, такие как ext4 или xfs, транслируют эти изменения в свои структуры на диске без дополнительных проверок — ограничения накладывает только политика `chmod`, например, игнорирование SUID/SGID для скриптов.

Работа каждого бита во время доступа к файлу/каталогу описана в обработчиках системных вызовов `execve()`, `open()`/`creat()`, `unlink()`, `rename()`. Рассмотрим детали.

**SUID на исполняемых файлах.** Когда процесс вызывает `execve()` для загрузки ELF-образа, ядро (функция `prepare_binprm()`) проверяет наличие бита `S_ISUID`. Если он установлен и файл не трассируется (проверка `ptrace`), ядро изменяет эффективный UID процесса на значение `uid` владельца файла, сохраняя реальный UID неизменным. Это краткосрочное повышение привилегий: процесс работает с правами владельца файла, но для сигналов и учёта остаётся связан с реальным UID. Сохранённый set-user-ID (saved set-user-ID) также обновляется, чтобы процесс мог временно понижать и восстанавливать привилегии через `setuid()`.

Аналогично обрабатывается **SGID на исполняемых файлах**: эффективный GID процесса становится равным GID группы-владельца файла, если установлен `S_ISGID`. Если же файл исполняется с SUID, ядро дополнительно сбрасывает effective GID в реальный GID, чтобы предотвратить наследование группового доступа через SUID-программу.

**SGID на каталогах.** Здесь поведение реализуется в момент создания файла через `open()` с флагом `O_CREAT` или `mkdir()`. Файловая система вызывает `inode_init_owner()`. Если каталог, в котором создаётся объект, имеет установленный `S_ISGID`, то новый объект получает ту же группу, что и родительский каталог, при условии, что создатель является членом этой группы (или имеет привилегии). В противном случае группа наследуется от эффективного GID процесса. Это правило не влияет на пользователя-владельца нового файла — им всегда становится эффективный UID процесса-создателя.

**Sticky bit на каталогах.** Ограничение удаления проверяется в `vfs_unlink()` и `vfs_rename()`. Если удаляемый объект находится в каталоге с битом `S_ISVTX`, операция разрешена только при выполнении одного из условий: вызывающий процесс обладает мандатом `CAP_FOWNER` (обычно root), его эффективный UID совпадает с UID владельца файла, или его эффективный UID совпадает с UID владельца каталога. Простого наличия права записи `w` на каталог недостаточно — это ключевое отличие от обычной логики удаления. Именно поэтому каталог `/tmp` с правами `1777` позволяет создать файл любому, но удалить — только создателю.

**Особый случай: интерпретируемые скрипты.** Если исполняемый файл начинается с `#!` (shebang), ядро загружает интерпретатор, указанный в строке. По соображениям безопасности SUID и SGID биты на таких файлах игнорируются во всех актуальных версиях Linux (существует устаревший механизм `uselib`, но он отключен). Причина в том, что интерпретатор запускается с повышенными привилегиями и может стать жертвой манипуляций с переменными окружения, такими как `LD_PRELOAD`. Поэтому сценарии оболочки с SUID не повысят привилегии, даже если бит установлен; администратору необходимо либо переписывать скрипт в компилируемый код, либо использовать `sudo` с правилами.

**Отображение символов `s`, `S`, `t`, `T`.** Утилита `ls` формирует строку прав по `mode`. Если специальный бит установлен и соответствующая категория имеет право `x`, подставляется строчная буква (`s` или `t`). Если `x` отсутствует — заглавная. Например:
* `rwSr--r--` — SUID установлен, но право выполнения у владельца отсутствует (файл не исполняемый).
* `rwxr-Sr--` — SGID установлен, но группа (вторая триада) не имеет `x`, поэтому отображается `S`.
* `rwxrwxrwT` — sticky bit на каталоге без права выполнения для other (невозможно войти в директорию; на практике `/tmp` всегда имеет `x`).

Эти нюансы важны при аудите: файл с `S` может ошибочно считаться защищённым, тогда как на деле SUID не сработает из-за отсутствия execute.

В качестве структурной иллюстрации ниже показана восьмеричная маска битов:

```text
    (старшие биты)               (младшие биты)
    [SUID] [SGID] [sticky] [U r w x] [G r w x] [O r w x]
      4      2       1       4 2 1     4 2 1     4 2 1
   ----------------------- -------------------------------
   Пример: 4755 = (4) SUID + (7) rwx + (5) r-x + (5) r-x
            2755 = (2) SGID +   755
            1777 = (1) sticky + 777
```

Таким образом, специальные биты — не изолированные флаги, а составная часть модели прав, которая интерпретируется кодом ядра на каждом системном вызове. Целостное понимание этого механизма необходимо для безопасного администрирования и корректной интерпретации событий журналирования, рассматриваемых далее.

## Применение и работа с SUID, SGID и sticky bit

Управление специальными разрешениями на практике сводится к трём основным операциям: установка/снятие битов через `chmod`, просмотр текущих атрибутов штатными утилитами и систематический аудит файлов с такими флагами. В роли SOC L1 аудитор сталкивается с задачами инвентаризации SUID/SGID-файлов, выявления аномалий и устранения избыточных прав.

**Установка и снятие.** Утилита `chmod` поддерживает как символьный, так и числовой синтаксис. Числовой префикс добавляется перед обычными тремя цифрами прав: `4` – SUID, `2` – SGID, `1` – sticky. Символьный формат использует букву `s` для user (`u+s`) или group (`g+s`) и `t` для sticky (`+t`). Снятие – замена `+` на `-` или явная установка восьмеричного префикса `0`. Существует особенность: числовой метод `chmod 4xxx файл` всегда устанавливает SUID, но если опустить префикс (например, `chmod 0755 файл`), биты SUID/SGID **сбрасываются** для обычных файлов и **сохраняются** для каталогов (согласно POSIX), если не указано иное. Это может приводить к неожиданной потере SUID при исправлении прав.

Примеры:
```bash
# Установить SUID и execute для владельца
chmod u+s /usr/local/bin/agent
# Установить SGID на каталог и полные права для группы
chmod g+sw /srv/collab
# Восьмеричный способ: sticky + полные права для всех
chmod 1777 /scratch
# Удалить SUID символьным методом
chmod u-s /usr/local/bin/agent
```

**Просмотр специальных прав.** Помимо `ls -l`, команда `stat` показывает восьмеричное представление вместе с разбором по категориям:
```bash
stat -c '%a %A %n' /usr/bin/passwd
# вывод (пример): 4755 -rwsr-xr-x /usr/bin/passwd
```
Эта форма удобна для скриптов и сбора данных при расследовании.

**Аудит опасных SUID/SGID файлов.** Основной инструмент — `find` с проверкой битов через `-perm`. Ключевые комбинации:

- `/4000` — любой файл с SUID (бит 4000); `/2000` — SGID; `/1000` — sticky-бит.
- `-4000` — файл, у которого биты SUID **строго** установлены (совпадают с маской), но для инвентаризации чаще применяют поиск по `/`, чтобы не упустить экземпляры с дополнительными разрешениями.
- Для ограничения поиска только обычными файлами добавляют `-type f`, для директорий – `-type d`.

Ниже пример типового аудита SUID в системных директориях:
```bash
find /usr/bin /usr/sbin /bin /sbin -type f -perm /4000 -exec ls -l {} \; 2>/dev/null
```
Аналогично для поиска каталогов с SGID:
```bash
find /var /opt -type d -perm /2000 -ls 2>/dev/null
```
Система также позволяет проверять целостность предустановленных SUID/SGID файлов с помощью пакетного менеджера. Например, в RHEL/CentOS:
```bash
rpm -Va | grep '^......S'   # файлы с некорректным размером или SUID, изменённые после установки
```
В Debian/Ubuntu аналогичный подход через `dpkg --verify`. Отклонения от пакетной базы сигнализируют о потенциальной компрометации или ошибке администрирования.

**Типовые сценарии использования и лучшие практики.** 
*SUID.* Применяется к ключевым системным утилитам вроде `passwd`, `ping`, `mount`, `su`. Добавление SUID-флага на пользовательские скомпилированные программы должно быть исключительной мерой и всегда сопровождаться аудитом кода на уязвимости (переполнение буфера, небезопасные вызовы `system()`). Администраторам рекомендуется периодически запускать поиск «лишних» SUID-файлов, появившихся после обновлений или в результате действий пользователей, и сравнивать с эталонным списком.

*SGID на директориях.* Широко востребован в веб-фермах, где каталог `/var/www` принадлежит группе `www-data`. При установке SGID любой контент, создаваемый разработчиками, становится доступен веб-серверу. В средах совместной работы аналитиков SOC каталог `/opt/soc/artifacts` с SGID гарантирует, что все доказательства, загруженные членами группы `soc-analysts`, будут доступны каждому аналитику без ручной смены группового владельца.

*Sticky bit.* Необходим для `/tmp`, `/var/tmp` и любых других «мировых» каталогов с правами 777. Без sticky-бита злоумышленник может удалить файл сокета или временный файл другого пользователя, что часто используется в атаках типа race condition (например, подмена временного файла привилегированной программы). Наложение sticky-бита предотвращает этот вектор.

**Типичные ошибки и заблуждения.**
- Установка SUID на shell-скрипт. Как говорилось, она не даст желаемого повышения привилегий, но может ввести администратора в заблуждение, будто скрипт защищён.
- Путаница между строчными и заглавными `S`/`T`. Например, после `chmod 4700 program` (SUID, но без `x` для владельца) команда `ls -l` покажет `-rwS------`. Владелец не сможет выполнить файл, следовательно, SUID-поведение не сработает. Администратор ожидает обратное — риск.
- При копировании файла с SUID утилита `cp` по умолчанию сбрасывает SUID/SGID биты, если копирование выполняет непривилегированный пользователь. Это защитная мера, но иногда приводит к «пропаже» функционала после восстановления из резервной копии. Для сохранения специальных битов следует использовать `cp -p` или `cp --preserve=mode`.
- При изменении владельца (`chown`) SUID/SGID также сбрасываются из соображений безопасности (только root может повторно установить биты).

**Мониторинг и реагирование.** В SOC важно настроить отправку событий при изменении атрибутов SUID/SGID файлов. Аудит-подсистема Linux (auditd) позволяет отслеживать вызовы `chmod` с флагами S_ISUID или S_ISGID. Правила могут выглядеть так:
```bash
# /etc/audit/rules.d/10-suid.rules
-a always,exit -F arch=b64 -S chmod -F a1&04000 -k suid_change
-a always,exit -F arch=b64 -S chmod -F a1&02000 -k sgid_change
```
Эти события вместе с `PATH` записями дают полную картину для анализа.

Таким образом, работа со специальными правами — непрерывный цикл «установка только там, где обоснованно → периодический аудит → мониторинг изменений». Такой подход минимизирует поверхность атаки и соответствует принципам защиты в глубину.

## Сквозной практический пример: общая рабочая среда команды SOC с SUID-инструментом

Пример демонстрирует настройку каталога с SGID и sticky bit для групповой работы аналитиков, а также создание минимальной SUID-программы для обслуживания этого каталога от имени привилегированного пользователя. Все действия выполняются на типовой системе Linux с ядром 5.x и coreutils 8.32.

**Исходные условия.** На хосте присутствуют пользователи `analyst_1` и `analyst_2`, оба должны состоять в общей группе `soc-staff`. Целевой каталог `/soc/cases` должен обеспечивать:  
- создаваемые аналитиками файлы автоматически получают группу `soc-staff`;  
- участники не могут удалить файлы друг друга (защита от случайного или злонамеренного удаления);  
- существует утилита `/soc/bin/collector`, которая может читать/удалять все файлы в каталоге независимо от владельца, запускаясь любым аналитиком.

**Шаг 1. Подготовка инфраструктуры.**
Создаём группу и пользователей, затем каталоги и базовые права.
```bash
# от root
groupadd soc-staff
useradd -m -G soc-staff analyst_1
useradd -m -G soc-staff analyst_2
mkdir -p /soc/cases /soc/bin
chown root:soc-staff /soc/cases
chown root:soc-staff /soc/bin
# каталог cases: SGID + sticky + rwx для group, владелец root
chmod 3775 /soc/cases
ls -ld /soc/cases
```
Вывод `ls -ld` (иллюстративный):
```
drwxrwsr-t 2 root soc-staff 4096 Jan 15 10:00 /soc/cases
```
Расшифровка: `d` – директория; `rwx` – root полный доступ; `rws` – группа, где `s` указывает SGID (и execute есть); `r-t` – остальные, где `t` обозначает sticky bit при наличии execute.

**Шаг 2. Создание файла одним аналитиком.**
Выполняем вход под `analyst_1` и создаём доказательство.
```bash
# под analyst_1
cd /soc/cases
echo "Evidence from A1" > case_001.evidence
ls -l case_001.evidence
```
Ожидаемый вывод:
```
-rw-rw-r-- 1 analyst_1 soc-staff 18 Jan 15 10:05 case_001.evidence
```
Видно, что групповая принадлежность унаследована от родительского каталога (`soc-staff`), а не равна первичной группе `analyst_1`. Аналитик `analyst_2` теперь может читать этот файл (если права `0644`), но не может его удалить, что проверяется на следующем шаге.

**Шаг 3. Попытка удаления чужим пользователем.**
Переключаемся на `analyst_2` и пробуем удалить файл.
```bash
# под analyst_2
rm /soc/cases/case_001.evidence
```
Результат:
```
rm: cannot remove '/soc/cases/case_001.evidence': Operation not permitted
```
Sticky bit запрещает удаление, даже несмотря на то, что `analyst_2` имеет право записи в каталог (благодаря группе `soc-staff`). Это защита от несанкционированного удаления улик.

**Шаг 4. Создание SUID-утилиты для обслуживания.**
Для операций очистки устаревших файлов нужна программа, запускаемая аналитиком с правами root (или выделенного пользователя). Создадим и скомпилируем простейший инструмент на C.
```c
// collector.c
#include <stdio.h>
#include <unistd.h>
#include <sys/types.h>
#include <stdlib.h>

int main(void) {
    // Вывод текущих UID для демонстрации
    printf("Real UID: %d\n", getuid());
    printf("Effective UID: %d\n", geteuid());
    // В реальной утилите здесь был бы код безопасного удаления
    return 0;
}
```
Компиляция и установка SUID от root:
```bash
gcc -o collector collector.c
cp collector /soc/bin/
chown root:soc-staff /soc/bin/collector
chmod 4755 /soc/bin/collector
ls -l /soc/bin/collector
```
Вывод `ls -l`:
```
-rwsr-xr-x 1 root soc-staff 16032 Jan 15 10:10 /soc/bin/collector
```
Здесь `s` в триаде пользователя подтверждает, что файл исполняется с эффективным UID владельца (root).

Запуск от любого аналитика:
```bash
# под analyst_1
/soc/bin/collector
```
Вывод:
```
Real UID: 1001
Effective UID: 0
```
Это иллюстрирует ключевую механику: программа выполняется с реальным UID пользователя, но эффективным — root, что даёт ей привилегии для удаления любых файлов в `/soc/cases`. В боевой версии такая программа должна тщательно проверять аргументы и окружение, чтобы избежать повышения привилегий через уязвимости.

**Ожидаемый вывод примера.** В одном сценарии продемонстрированы все три специальных бита: SGID гарантирует единое групповое владение вновь создаваемыми файлами, sticky bit защищает файлы от удаления не-владельцами, SUID позволяет безопасной служебной программе обходить ограничения sticky bit точечно и под контролем администратора. Подобная конфигурация типична для защищённой совместной работы в SOC и иллюстрирует корректное применение специальных прав в соответствии с требованиями информационной безопасности.
