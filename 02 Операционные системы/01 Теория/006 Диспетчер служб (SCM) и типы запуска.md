# Диспетчер служб (SCM) и типы запуска

## Роль и место Диспетчера управления службами в архитектуре Windows

Служба Windows (Windows Service) — это приложение, исполняемое операционной системой в фоновом режиме независимо от статуса пользователя. Концептуально она аналогична демонам в Unix-подобных системах, но обладает жёсткой привязкой к API и подсистемам Windows. Службы выполняют критически важные функции: от сетевого взаимодействия и обработки событий аудита до поддержки оборудования и обновлений безопасности [Служба Windows — Википедия](https://ru.wikipedia.org/wiki/%D0%A1%D0%BB%D1%83%D0%B6%D0%B1%D0%B0_Windows). В контексте SOC понимание служб является одним из базовых навыков, поскольку злоумышленники часто используют их для закрепления в системе и маскировки вредоносной активности.

Центральным элементом управления жизненным циклом служб выступает **Диспетчер управления службами** (Service Control Manager, SCM). Это системный процесс `services.exe`, который стартует на раннем этапе загрузки Windows (до входа интерактивного пользователя) и выполняет следующие ключевые функции [Диспетчер управления службами — Википедия](https://ru.wikipedia.org/wiki/%D0%94%D0%B8%D1%81%D0%BF%D0%B5%D1%82%D1%87%D0%B5%D1%80_%D1%83%D0%BF%D1%80%D0%B0%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D1%8F_%D1%81%D0%BB%D1%83%D0%B6%D0%B1%D0%B0%D0%BC%D0%B8):

- поддержка базы данных установленных служб и драйверов;
- автоматический запуск служб при старте системы в соответствии с их типом запуска и зависимостями;
- обработка запросов на запуск, остановку, приостановку или изменение конфигурации служб;
- отслеживание состояния запущенных служб;
- предоставление RPC-интерфейса для локального и удалённого управления.

SCM опирается на иерархию типов запуска, которая определяет, когда и при каких условиях служба будет активирована. Рассмотрение этой иерархии невозможно без чёткого разграничения между собственно службами пользовательского режима и драйверами устройств, поскольку некоторые типы запуска (Boot, System) предназначены исключительно для драйверов. В повседневной работе через оснастку `services.msc` администратор видит лишь автоматический, ручной и отключённый запуск (плюс вариант отложенного автоматического), однако на уровне реестра доступны ещё два типа, имеющих критическое значение для безопасности: Boot и System.

Следующая таблица разграничивает ключевые сущности, с которыми имеет дело SOC-аналитик при исследовании автозагрузки и фоновых процессов.

| Сущность | Процесс-хост | Управление | Ключ автозагрузки | Типичные примеры |
|----------|--------------|------------|-------------------|------------------|
| Служба Windows (user-mode) | `svchost.exe`, собственный `.exe` | SCM через API | `HKLM\SYSTEM\CurrentControlSet\Services\<имя>` | Spooler, WinRM, Windows Update |
| Драйвер устройства (kernel-mode) | Ядро (System) | SCM (для загрузки), менеджер PnP | Тот же раздел реестра | `disk.sys`, `tcpip.sys` |
| Планировщик задач | `taskeng.exe` | Task Scheduler | `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache` | Запланированные скрипты обслуживания |
| Запуск через Run-ключи | Процесс пользователя | Никакой центральный менеджер | `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` | Автозапуск приложений |

С точки зрения SOC важно, что вредоносное ПО может маскироваться под службу, драйвер или задачу планировщика. Для служб характерно наличие ключа в разделе `Services` с заполненными полями `ImagePath`, `Start` и `Type`. Легитимные драйверы с типом запуска Boot или System всегда подписаны Microsoft или публикуются доверенными поставщиками. Обнаружение пользовательской службы с типом Boot (Start=0) — сильный индикатор компрометации.

Таким образом, SCM выступает единым реестром и диспетчером для всех фоновых компонентов, использующих парадигму служб, а типы запуска являются первичным атрибутом, который определяет порядок активации и возможности вмешательства администратора.

## Архитектура SCM и детализация типов запуска служб

### Внутреннее устройство SCM

SCM реализован в образе `services.exe` и запускается процессом `wininit.exe` на этапе загрузки сессии 0. Он функционирует как RPC-сервер, прослушивая именованные каналы (`\pipe\ntsvcs`) для обслуживания запросов от клиентов: оснастки `services.msc`, утилиты `sc.exe`, PowerShell, а также удалённых систем. Любое приложение, желающее управлять службами, должно открыть дескриптор SCM через функцию `OpenSCManager`, после чего может вызывать `CreateService`, `StartService`, `ControlService` и другие API [LDAPWiki: Service Control Manager](https://ldapwiki.com/wiki/Wiki.jsp?page=Service+Control+Manager).

База данных служб хранится в реестре по пути:
```
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services
```
Для каждой установленной службы (или драйвера) создаётся подключ, имя которого обычно совпадает с кратким именем службы. Структура этого подключа содержит критически важные для функционирования SCM значения, среди которых:

- `Start` (REG_DWORD) — тип запуска (0–4);
- `Type` (REG_DWORD) — тип службы (драйвер, процесс, разделяемый процесс и др.);
- `ErrorControl` — поведение при сбое;
- `ImagePath` — путь к исполняемому файлу;
- `DependOnService` / `DependOnGroup` — зависимости;
- `Group` — группа загрузки (определяет порядок);
- `DelayedAutostart` (REG_DWORD) — флаг отложенного запуска (1) для служб с Start=2.

SCM загружает эту базу на раннем этапе и, руководствуясь порядком групп из ключа `ServiceGroupOrder`, запускает службы в определённой последовательности. Алгоритм старта учитывает зависимости: если служба типа Manual нужна для работы Auto-службы, она также будет запущена автоматически [LDAPWiki: Service Control Manager](https://ldapwiki.com/wiki/Wiki.jsp?page=Service+Control+Manager).

### Детализация типов запуска

Ключ `Start` задаёт поведение при загрузке системы. Возможные значения и их семантика сведены в таблицу ниже. Дополнительные модификаторы (отложенный запуск, запрет остановки) реализуются отдельными флагами.

| Значение `Start` | Название | Описание | Применение | Управление через UI |
|------------------|----------|----------|------------|---------------------|
| 0 | Boot | Загружается загрузчиком ОС (`ntldr`/`bootmgr`) до инициализации ядра | Драйверы загрузочных устройств (диски, ФС) | Не отображается |
| 1 | System | Загружается ядром в фазе инициализации | Драйверы низкого уровня (ACPI, PCI) | Не отображается |
| 2 | Automatic | Запускается SCM при старте системы | Службы и драйверы, критичные для ОС | Automatic |
| 2 + `DelayedAutostart=1` | Automatic (Delayed Start) | Запускается SCM с задержкой ~2 мин. после загрузки всех Auto-служб | Службы, не критичные для немедленной работы | Automatic (Delayed Start) |
| 3 | Manual | Запускается вручную или по запросу другого компонента | Вспомогательные службы, запускаемые по требованию | Manual |
| 4 | Disabled | Запрещён к запуску; попытка запуска вернёт ошибку | Отключённые или неиспользуемые компоненты | Disabled |

Особого внимания заслуживает тип «обязательная служба», упомянутый в [Служба Windows — Википедия](https://ru.wikipedia.org/wiki/%D0%A1%D0%BB%D1%83%D0%B6%D0%B1%D0%B0_Windows). Он не задаётся значением `Start`, а определяется комбинацией флагов в `Type` (установлен бит `SERVICE_TYPE_WIN32_OWN_PROCESS` и одновременно внутренний флаг `SERVICE_ACCEPT_STOP` снят). Такая служба запускается автоматически, и SCM не позволяет её остановить штатными средствами. Вредоносное ПО может модифицировать существующую службу, убрав возможность остановки, что затрудняет удаление.

Иерархия загрузки всех компонентов выглядит следующим образом (иллюстративная ASCII-схема):

```text
Загрузчик ОС
  │
  └─ Драйверы Boot (Start=0)
       │
       └─ Ядро (ntoskrnl.exe)
            │
            └─ Драйверы System (Start=1)
                 │
                 └─ services.exe (SCM)
                      │
                      ├─ Службы Automatic (Start=2) в порядке групп
                      │    ├─ Группа "Event Log"
                      │    ├─ Группа "PlugPlay"
                      │    └─ ...
                      │
                      └─ Службы Automatic (Delayed Start) с задержкой
```

Важно, что SCM не управляет непосредственно драйверами Boot и System на этапе их загрузки — они инициализируются загрузчиком и ядром. Однако SCM регистрирует их в своей базе, позволяя впоследствии запрашивать их состояние или изменять параметры (перезапуск после обновления конфигурации). Для SOC-специалиста эта деталь означает, что попытка злоумышленника загрузить вредоносный драйвер с типом Boot даст ему максимальные привилегии и защищённость, но требует обхода механизма подписи драйверов (Driver Signature Enforcement) и привлечёт внимание средств защиты.

### Взаимодействие SCM с процессами служб

Служба пользовательского режима должна реализовывать функцию `ServiceMain`, регистрируемую через `StartServiceCtrlDispatcher`. После запуска процесса-хоста (например, `svchost.exe`) SCM передаёт ему управление. Далее служба обязана вызвать `RegisterServiceCtrlHandler` для приёма управляющих команд: остановка, пауза, продолжение, shutdown. Если служба не отвечает в течение определённого времени (обычно 30 секунд), SCM принудительно завершает процесс. Это объясняет, почему вредоносная служба иногда может блокировать остановку, «зависая» или игнорируя команды.

## Управление службами и типами запуска в практике SOC

Работа аналитика SOC L1 с Windows-службами сводится к трём основным сценариям:

- проверка состояния и конфигурации служб в ответ на инцидент (например, неожиданное отключение брандмауэра);
- изменение типа запуска в целях временного устранения угрозы (изоляция подозрительной службы переводом в Manual/Disabled);
- поиск аномалий, указывающих на присутствие вредоносного ПО (нестандартные типы `Start`, нелегитимные пути исполняемых файлов).

### Инструментарий

Основные средства управления — утилита командной строки `sc.exe`, PowerShell и оснастка `services.msc`. Для удалённого взаимодействия используются PowerShell Remoting или, в крайнем случае, `sc \\<host>`. В SOC-контексте предпочтительны `sc` и PowerShell, поскольку они позволяют автоматизировать сбор артефактов и встраивать команды в сценарии реагирования.

#### Сбор информации о службах

Для получения полного списка служб с их состояниями и типами запуска удобна следующая конструкция:

```powershell
Get-Service | Select-Object Name, DisplayName, Status, StartType | Format-Table -AutoSize
```

Вывод содержит четыре основных типа запуска (Automatic, Manual, Disabled, а также AutomaticDelayedStart). Однако PowerShell не показывает разницу между Automatic и Automatic (Delayed) в отдельном поле — `StartType` у них обоих выводится как "Automatic". Более точную информацию даёт утилита `sc`:

```cmd
sc qc <ServiceName>
```

Пример вывода для службы Windows Update:

```text
SERVICE_NAME: wuauserv
        TYPE               : 20  WIN32_SHARE_PROCESS
        START_TYPE         : 2   AUTO_START  (DELAYED)
        ERROR_CONTROL      : 1   NORMAL
        BINARY_PATH_NAME   : C:\Windows\system32\svchost.exe -k netsvcs -p
        LOAD_ORDER_GROUP   : NetworkProvider
        TAG                : 0
        DISPLAY_NAME       : Windows Update
        DEPENDENCIES       : rpcss
        SERVICE_START_NAME : LocalSystem
```

Здесь `START_TYPE : 2 AUTO_START (DELAYED)` говорит о том, что служба имеет тип Automatic с флагом отложенного запуска. Именно `sc qc` позволяет увидеть нестандартные числовые значения `Start`, если злоумышленник вручную выставил 0 или 1.

#### Изменение типа запуска

Для перевода подозрительной службы в отключённое состояние достаточно:

```cmd
sc config <имя_службы> start= disabled
```

Обратите внимание на обязательный пробел после знака равенства. Для перевода в Automatic (Delayed):

```cmd
sc config <имя_службы> start= delayed-auto
```

Через PowerShell аналогичная операция выполняется так:

```powershell
Set-Service -Name <имя_службы> -StartupType Disabled
```

При необходимости изменять службы на удалённых хостах можно использовать `Invoke-Command` с соответствующим сессионным блоком, при условии наличия прав администратора и работающего WinRM.

### Приёмы детектирования аномалий

Аналитику L1 часто приходят алерты о создании новой службы или изменении типа запуска существующей. Ручная проверка начинается с поиска служб, имеющих следующие признаки:

- параметр `Start` равен 0 (Boot) или 1 (System), но `ImagePath` указывает на исполняемый файл в нестандартном каталоге (всё, что не является легитимным драйвером);
- значение `Start` равно 2, но отсутствует цифровая подпись исполняемого файла или путь расположен в пользовательских директориях (`C:\Users\`, `C:\ProgramData\`);
- наличие служб с именами, маскирующимися под системные (например, `Sppsvc` vs `Sppsvc1`, `WinDefend` vs `WinDefender`).

Ниже представлен PowerShell-фрагмент, выявляющий службы с типом запуска Boot (0), которые, скорее всего, не являются драйверами. Скрипт перебирает ветку `CurrentControlSet\Services`, исключает известные легитимные ключи:

```powershell
$services = Get-ChildItem HKLM:\SYSTEM\CurrentControlSet\Services
foreach ($svc in $services) {
    $start = (Get-ItemProperty -Path $svc.PSPath -Name Start -ErrorAction SilentlyContinue).Start
    $type = (Get-ItemProperty -Path $svc.PSPath -Name Type -ErrorAction SilentlyContinue).Type
    # Type=1 (Kernel driver) для Boot допустим; Type=16,32 (Win32 service) — подозрительно
    if ($start -eq 0 -and $type -band 0x10) {
        Write-Output "Suspicious Boot-start service: $($svc.PSChildName)"
    }
}
```

Аналогичный подход применим для поиска служб с `Start=1` и флагом пользовательской службы. Результаты таких сканирований должны проверяться по базе IOC и загружаться в EDR для дальнейшего анализа.

### Подводные камни

- Для изменения типа запуска требуются привилегии администратора; без них команды `sc` и `Set-Service` завершатся ошибкой «Access denied».
- Остановка некоторых системных служб может привести к немедленному краху системы или блокировке удалённого доступа. В условиях SOC это допустимо только при явном разрешении старшего аналитика и при наличии физического или out-of-band доступа к хосту.
- Не все вредоносные службы видны через стандартные средства: rootkit-уровневое сокрытие может перехватывать вызовы API и скрывать ключи реестра. В таких случаях диагностика проводится с использованием memory-forensics или загрузки с чистой среды.

## Сквозной практический пример: расследование подозрительной службы с нестандартным типом запуска

### Исходные условия

Аналитик SOC L1 получает эскалированный алерт от SIEM: на рабочей станции Windows 10 (среда корпоративного домена) обнаружена новая служба с именем "WdDefenderService". Алерт сработал по правилу, отслеживающему создание служб с параметром `Start=0` и путём к файлу вне защищённых системных каталогов. Цель аналитика — проверить легитимность службы, собрать первичные артефакты и принять решение об эскалации на L2.

### Шаг 1. Определение конфигурации службы

Подключаемся к удалённой системе через WinRM (если настроено) либо с помощью `Enter-PSSession` и выполняем:

```cmd
sc qc WdDefenderService
```

Полученный вывод:

```text
SERVICE_NAME: WdDefenderService
        TYPE               : 10  WIN32_OWN_PROCESS
        START_TYPE         : 0   BOOT_START
        ERROR_CONTROL      : 0   IGNORE
        BINARY_PATH_NAME   : C:\Users\Public\Downloads\wddefender.exe
        LOAD_ORDER_GROUP   :
        TAG                : 0
        DISPLAY_NAME       : Windows Defender Core Service
        DEPENDENCIES       :
        SERVICE_START_NAME : LocalSystem
```

Аналитик фиксирует два ключевых индикатора: `START_TYPE` равен 0 (Boot), что абсолютно нехарактерно для пользовательской службы (тип 10 — `WIN32_OWN_PROCESS`). Легитимные драйверы с Boot-стартом всегда имеют `TYPE` со значением, соответствующим драйверу ядра. Кроме того, `BINARY_PATH_NAME` указывает на пользовательскую папку `Downloads`, что недопустимо для системных компонентов.

### Шаг 2. Проверка подлинности исполняемого файла

Выполняем стандартную проверку цифровой подписи с помощью утилиты `sigcheck` (Sysinternals) или встроенного `Get-AuthenticodeSignature`:

```powershell
Get-AuthenticodeSignature C:\Users\Public\Downloads\wddefender.exe
```

Результат (иллюстративный):

```text
SignerCertificate          : 
Status                     : NotSigned
StatusMessage              : The file is not digitally signed.
```

Отсутствие подписи для файла, претендующего на роль системного компонента, подтверждает подозрения.

### Шаг 3. Анализ реестрового ключа

Дополнительно изучаем полный ключ реестра службы, чтобы выявить флаги, применяемые злоумышленником для усложнения ручного удаления:

```powershell
Get-ItemProperty HKLM:\SYSTEM\CurrentControlSet\Services\WdDefenderService
```

Иллюстративный вывод:

```text
Type            : 16 (WIN32_OWN_PROCESS, SERVICE_ACCEPT_STOP отсутствует)
Start           : 0
ErrorControl    : 0
ImagePath       : C:\Users\Public\Downloads\wddefender.exe
DisplayName     : Windows Defender Core Service
ObjectName      : LocalSystem
Description     : Provides core threat protection services
...
```

Поле `Type` содержит значение 16, что означает `SERVICE_WIN32_OWN_PROCESS`, но без флага `SERVICE_ACCEPT_STOP`. Следовательно, остановить службу штатными средствами невозможно — SCM не будет посылать ей команду остановки. Это поведение характерно для вредоносных программ, стремящихся помешать защитным мерам реагирования.

### Шаг 4. Оценка IOC и эскалация

Собранные артефакты:

- Имя службы: WdDefenderService
- Стартовый тип: Boot (0) — аномалия
- Исполняемый файл: `C:\Users\Public\Downloads\wddefender.exe`, отсутствие цифровой подписи
- Служба не принимает команду остановки (`Type` = 16)

Аналитик фиксирует IOC: SHA256 хэш файла, путь, значения реестра. С учётом высокого риска (служба работает с правами `LocalSystem` и стартует на самом раннем этапе) немедленно передаёт кейс на уровень L2 для углублённого анализа и, возможно, изоляции хоста.

### Ожидаемый вывод

Данный пример демонстрирует, как знание архитектуры SCM и семантики типов запуска позволяет быстро идентифицировать вредоносную активность. Аналитик L1 без инструментов реверс-инжиниринга способен выявить ключевые аномалии: недопустимый `START_TYPE`, подозрительный путь, отсутствие подписи и блокировку остановки. Эти признаки служат надёжным основанием для эскалации и запуска более глубокого расследования.
