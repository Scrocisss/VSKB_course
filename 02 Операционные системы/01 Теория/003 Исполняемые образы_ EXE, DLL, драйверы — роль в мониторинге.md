# Исполняемые образы: EXE, DLL, драйверы — роль в мониторинге

## 1. Исполняемый образ EXE — самостоятельный процесс: структура и роль в системе

Исполняемый образ Windows — это файл в формате PE (Portable Executable), способный загружаться и выполняться в пользовательском или привилегированном режиме. Наиболее узнаваемый представитель этой категории — файл с расширением **EXE**, запускающий независимый процесс. В контексте SOC-мониторинга EXE является первичной единицей наблюдения: каждое появление нового процесса порождает событие, которое аналитик L1 оценивает по множеству параметров — пути запуска, командной строке, цифровой подписи, родительскому процессу и дочерним активностям.

### 1.1 Базовые понятия и отличия от родственных образов
EXE, DLL и драйверы (.sys) объединяет общий формат PE, однако их поведение после загрузки кардинально различается. **EXE** содержит точку входа (Entry Point), которая при создании процесса вызывает функцию `main` / `WinMain` пользовательского кода. Он выполняется в собственном адресном пространстве пользовательского режима, и его запуск приводит к генерации событий создания процесса (Security 4688, Sysmon Event ID 1). **DLL** не может выполняться самостоятельно — она отображается в память вызывающего процесса и разделяет его привилегии. **Драйвер** работает в режиме ядра (Ring 0), загружается менеджером служб диспетчера ввода-вывода и имеет уникальные требования к цифровой подписи и целостности.

Ниже приведена сравнительная таблица, фиксирующая ключевые разграничения между тремя типами исполняемых образов:

| Характеристика | EXE (исполняемый файл) | DLL (динамическая библиотека) | Драйвер (.sys) |
|---|---|---|---|
| Расширение | .exe (реже .com, .scr) | .dll, .ocx, .cpl | .sys |
| Запуск | Создаёт независимый процесс | Загружается в существующий процесс | Загружается в ядро, становится частью системы |
| Режим выполнения | Пользовательский (User mode) | Пользовательский (в контексте процесса) | Режим ядра (Kernel mode) |
| Точка входа | main / WinMain / wWinMain | DllMain (опциональная) | DriverEntry |
| Адресное пространство | Собственное виртуальное пространство процесса | Общее с хост-процессом | Системное адресное пространство ядра |
| Экспорт функций | Обычно отсутствует (но технически возможен) | Основная задача — экспорт функций | Экспорт callback-функций для диспетчера ввода-вывода, Plug and Play и др. |
| Регистрация в системе | Не требуется | Может регистрироваться (COM, regsvr32) | Обязательно регистрируется как служба в `HKLM\System\CurrentControlSet\Services` |
| События Sysmon для мониторинга | Event ID 1 (ProcessCreate) | Event ID 7 (Image loaded) | Event ID 6 (Driver loaded) |
| Типичный пример | `cmd.exe`, `notepad.exe` | `kernel32.dll`, `ntdll.dll` | `ntfs.sys`, `tcpip.sys` |

Для аналитика SOC L1 уже на этапе первичного триажа важно знать эту классификацию: EXE-образы поддаются прямому мониторингу через отслеживание процессов, тогда как DLL и драйверы требуют специализированных событий загрузки образов (Event ID 7 и 6 соответственно).

### 1.2 PE-формат как общая основа
Любой исполняемый образ Windows построен по единой спецификации PE/COFF. Файл начинается с MS-DOS заглушки и сигнатуры `PE\0\0`, за которой следует COFF-заголовок, опциональный заголовок и таблицы секций (`.text`, `.data`, `.rsrc`, `.reloc` и др.). В поле `Characteristics` заголовка бит 0x2000 указывает, что образ является DLL; бит 0x0002 — EXE. Драйверы обычно используют значение `IMAGE_FILE_EXECUTABLE_IMAGE` (0x0002) и `IMAGE_FILE_LARGE_ADDRESS_AWARE`, но ключевой идентификатор — подсистема: для драйверов она устанавливается в `IMAGE_SUBSYSTEM_NATIVE`. Эта информация доступна при статическом анализе или через инструменты вроде `dumpbin /headers`. Для мониторинга это означает, что классифицировать образ до его загрузки трудно — аналитик полагается на поведение и события, генерируемые уже после отображения образа в память.

### 1.3 Жизненный цикл EXE в контексте наблюдения
Запуск EXE-файла инициируется вызовом `CreateProcess`. Ядро создаёт структуру EPROCESS, загружает образ в память, настраивает адресное пространство, создаёт главный поток. В этот момент генерируется событие безопасности: Windows Security Event 4688 или Sysmon Event ID 1 (при настроенном драйвере). Событие содержит полную командную строку, путь к образу, идентификатор родительского процесса, хеш-сумму образа, информацию о пользователе и цифровой подписи. Именно эти поля аналитик L1 использует для первичной оценки: легитимный системный процесс ожидается запущенным из `C:\Windows\System32`, иметь доверенную подпись Microsoft, а командная строка не должна содержать признаков обфускации или нестандартных параметров.

После старта процесс может загружать дополнительные модули (DLL), создавать дочерние процессы, получать доступ к памяти других процессов — всё это становится отдельными точками мониторинга. Таким образом, EXE — не только объект детектирования, но и узел, связывающий события загрузки DLL, создания потоков и сетевых подключений в единую картину атаки.

## 2. DLL — динамическая библиотека: загрузка, связывание и угрозы

Динамически подключаемая библиотека (DLL) — это PE-образ, спроектированный для многократного переиспользования кода и данных между процессами. В отличие от EXE, DLL не создаёт собственного процесса, а загружается в адресное пространство вызывающего кода. Именно DLL реализуют подавляющее большинство Windows API: `kernel32.dll`, `ntdll.dll`, `advapi32.dll` и сотни других системных библиотек. С точки зрения мониторинга DLL являются одновременно источником высокого фонового шума и критически важным индикатором компрометации, поскольку атакующие активно внедряют вредоносный код через легитимные механизмы загрузки библиотек.

### 2.1 Структура DLL и экспорт функций
Внутренняя структура DLL сохраняет все компоненты PE: заголовки, секции, таблицу импорта (IAT) и таблицу экспорта (EAT). Ключевое отличие — наличие **экспортируемых функций**, объявленных разработчиком. Именно они становятся точками входа для вызовов из других модулей. Необязательная функция `DllMain` вызывается при загрузке/выгрузке DLL или создании/завершении потока и может выполнять инициализацию. Аналитик SOC должен помнить, что вредоносная активность часто размещается именно в `DllMain`, поскольку она выполняется автоматически при загрузке без явного вызова клиентом.

### 2.2 Процесс загрузки DLL
Загрузка DLL происходит по запросу процесса через вызов `LoadLibrary` (или `LoadLibraryEx`), либо неявно при разрешении импортов загрузчиком во время старта процесса. Алгоритм поиска библиотеки строго определён порядком, который может быть атакован:

```text
    Процесс вызывает LoadLibrary("example.dll")
    │
    ├─ Известный список загрузки (KnownDLLs) — только для системных библиотек
    ├─ Директория приложения
    ├─ Системная директория (C:\Windows\System32)
    ├─ 16-битная системная директория (C:\Windows\System)
    ├─ Директория Windows (C:\Windows)
    ├─ Текущая рабочая директория
    ├─ Директории из переменной окружения PATH
    └─ (дополнительно) Пути, зарегистрированные через SetDllDirectory или манифесты
```

Если злоумышленник разместит вредоносную DLL с именем легитимной в одном из приоритетных путей (например, в рабочей директории перед System32), то произойдёт **подмена DLL (DLL hijacking)**. Загрузчик создаст объект-секцию, отобразит файл в память процесса, обработает импорты и вызовет `DllMain`. На этом этапе операционная система может вызвать зарегистрированные уведомления (notify routines) для антивирусов и EDR-систем, но само событие мониторинга генерируется только сторонними драйверами вроде Sysmon.

### 2.3 Событие Sysmon Event ID 7 и проблемы высокого объёма
Отслеживание загрузки DLL реализуется Sysmon через тип события **Event ID 7 (Image loaded)**. В журнале фиксируются: путь к загруженному образу, его хеш, идентификатор процесса, подпись и имя правила. Проблема в том, что даже штатная работа Windows генерирует сотни тысяч таких событий в час — браузер при открытии одной страницы может загрузить более 50 DLL, офисный пакет — сотни модулей. Согласно руководству TrustedSec, конфигурация Sysmon для Image Load не может строиться на исключении (exclusion‑based approach): логировать всё и отсеивать шум нереально из-за падения производительности и объёма логов [SysmonCommunityGuide](https://github.com/trustedsec/SysmonCommunityGuide/blob/master/chapters/image-loading.md). Вместо этого применяется строго целевой включающий подход: мониторятся только конкретные подозрительные DLL или комбинации «процесс — DLL», характерные для известных техник атак.

### 2.4 Паттерны злоупотребления DLL
Атакующие используют DLL в нескольких типовых сценариях, обнаруживаемых при корректной настройке мониторинга:

- **DLL Injection (T1055.001)** — внедрение DLL в чужой процесс. Индикаторы: подпись DLL отсутствует или не соответствует контексту, DLL загружена из временной папки (`%TEMP%`, `%PUBLIC%`), хеш известен как вредоносный.
- **Reflective DLL Loading** — загрузка DLL напрямую в память без участия файловой системы. Труднее детектировать на этапе загрузки, но можно выявить по загрузке редких системных DLL (например, `ntdll.dll`) процессом, который обычно этого не делает.
- **Living Off the Land** — легитимный процесс (например, `rundll32.exe`, `regsvr32.exe`, `mshta.exe`) загружает DLL, предоставляющие функциональность для выполнения скриптов или обращения к сетям. Яркий пример — загрузка `scrobj.dll` процессом `regsvr32.exe` соответствует технике Squiblydoo (T1218.010), а загрузка `System.Management.Automation.dll` процессом Word указывает на выполнение PowerShell‑кода из макросов.
- **Rundll32 abuse** — штатная утилита `rundll32.exe` предназначена для вызова экспортируемых функций DLL. Вредоносное использование часто сопровождается нетипичными параметрами: обфусцированным именем точки входа (например, `JskFxphZumezrjnI`), вызовом экспорта `DllRegisterServer`, который обычно используется `regsvr32.exe`, или путём к DLL, содержащим альтернативные потоки данных (ADS). Согласно отчёту Red Canary, подобные командные строки являются одними из надёжных индикаторов злонамеренной активности [Rundll32 - Red Canary](https://redcanary.com/threat-detection-report/techniques/rundll32).

Пример командной строки, типичный для атакующих (иллюстративная схема):

```cmd
rundll32.exe C:\ProgramData\45f51194.dat,DllRegisterServer
```

Здесь нестандартное расширение `.dat`, вызов `DllRegisterServer` вместо ожидаемого запуска функции из DLL, и расположение в скрытой папке `ProgramData` — все эти признаки аналитик L1 должен сопоставлять с контекстом.

### 2.5 Резюме по DLL в мониторинге
Для аналитика SOC L1 DLL — двуликий Янус: необходимый фоновый шум и потенциальный сигнал атаки. Эффективный мониторинг достигается не попыткой охватить все загрузки, а фокусировкой на известных техниках MITRE ATT&CK, аномальных путях, нетипичных комбинациях процессов и библиотек. Конфигурация Sysmon с целевыми правилами для Event ID 7 позволяет снизить объём данных до приемлемого уровня и сохранить видимость в критические операции.

## 3. Драйверы Windows — код уровня ядра: архитектура и контроль целостности

Драйверы (.sys) — исполняемые образы, работающие в привилегированном режиме ядра (Ring 0). Они обеспечивают взаимодействие операционной системы с оборудованием, реализует сетевые стеки, фильтры файловой системы и множество критических функций. В силу своего высокого уровня привилегий драйвер представляет особую ценность для атакующих: компрометация или загрузка вредоносного драйвера даёт полный контроль над ОС, включая возможность отключения защитных механизмов, сокрытия процессов и перехвата системных вызовов. Именно поэтому мониторинг загрузки драйверов — обязательный компонент программы SOC.

### 3.1 Классификация драйверов Windows
Windows поддерживает несколько архитектурных типов драйверов, которые по-разному загружаются, управляются и взаимодействуют с системой. Их различия важны для аналитика: события загрузки могут поступать из разных источников в зависимости от типа драйвера.

| Тип драйвера | Режим загрузки | Примеры | Особенности мониторинга |
|---|---|---|---|
| Драйвер устройства (WDM) | On‑demand (вручную или при обнаружении устройства) | `pci.sys`, `usbhub.sys` | Загружается по мере подключения устройств; события создания службы могут отсутствовать |
| Драйверы файловых систем | Boot / System | `ntfs.sys`, `fastfat.sys` | Загружаются на ранних этапах загрузки ОС, до запуска большинства средств мониторинга |
| Mini‑filter драйверы | System / Auto | `fileinfo.sys`, антивирусные фильтры | Регистрируются в менеджере фильтров; их открепление (detach) — подозрительный признак |
| Сетевые драйверы (NDIS) | System / Manual | `ndis.sys`, драйвер протокола TCP/IP | Участвуют в цепочке сетевого стека; компрометация позволяет перехватывать трафик |
| Программные драйверы | Auto / Manual | Legitimate: `vmsrvc.sys` (VMware), Malicious: руткиты | Часто не связаны с оборудованием; создаются для расширения функциональности или скрытых целей |

Наиболее опасны для SOC драйверы, стартующие на этапе загрузки (Boot/System) — их загрузка происходит до инициализации подсистемы аудита, и они могут обойти ранние антивирусные callback-и. Однако каждая успешная загрузка драйвера вызывает **PsSetLoadImageNotifyRoutine** — механизм, позволяющий зарегистрированным антивирусным и EDR-модулям получать уведомление о загрузке любого исполняемого образа, включая драйверы [Way to detect driver unload - NTDEV](https://community.osr.com/t/way-to-detect-driver-unload/55212). Таким образом, даже очень ранние драйверы могут быть обнаружены, если защитное решение успело установить callback до их загрузки.

### 3.2 Цифровая подпись и контроль целостности
Начиная с 64-битных версий Windows Vista/7 действует требование обязательной цифровой подписи для драйверов уровня ядра. Code Integrity (CI) проверяет подпись при загрузке; неподписанный или подписанный недоверенным сертификатом драйвер будет отвергнут. Это создаёт препятствие для атакующих, но не абсолютное: известны случаи использования украденных сертификатов или эксплуатации уязвимых легитимных драйверов (BYOVD — Bring Your Own Vulnerable Driver). SOC-аналитик должен проверять не только наличие подписи, но и её статус (действительный, отозванный), а также принадлежность сертификата к ожидаемому издателю. Sysmon Event ID 6 фиксирует сертификат, и аналитик может сопоставить его с известными скомпрометированными или подозрительными сертификатами.

### 3.3 Загрузка и выгрузка драйверов: события и сложности
Загрузка драйвера управляется Service Control Manager (SCM). Драйвер регистрируется как служба типа `SERVICE_KERNEL_DRIVER`, и при старте ОС или вручную (через `sc start` или API `NtLoadDriver`) он загружается в ядро. В этот момент:
- Генерируется событие безопасности Event ID 7045 (новый сервис), если драйвер устанавливается впервые.
- Sysmon записывает **Event ID 6 (Driver loaded)** с информацией: путь к файлу, хеш, подпись, имя правила.
- EDR-платформы получают уведомление через callback `PsSetLoadImageNotifyRoutine`.

Выгрузка драйвера значительно сложнее для мониторинга. Согласно обсуждению на OSR, не существует документированного стабильного callback для отслеживания выгрузки [Way to detect driver unload](https://community.osr.com/t/way-to-detect-driver-unload/55212). Единственный надёжный метод — периодический опрос списка загруженных модулей ядра и сравнение с предыдущим состоянием, что создаёт задержку и накладные расходы. Поэтому в SOC-мониторинге фокус смещён на обнаружение загрузки неожиданных драйверов, а не на их выгрузку. Аналитик может выявить снятие драйвера косвенно — по исчезновению связанного с ним объекта устройства или изменению поведения системы.

### 3.4 Влияние драйверов на SOC L1
Для специалиста первого уровня драйверы — сравнительно редкие, но крайне значимые объекты. Любое событие загрузки нового драйвера должно проверяться по чек-листу:
- **Путь**: ожидается `C:\Windows\System32\drivers\` или подкаталог работающей легитимной службы. Драйвер из временной папки, `AppData` или сетевого ресурса — немедленный повод для эскалации.
- **Имя файла**: известные вредоносные драйверы (по IoC) либо необычные имена (случайные символы, двойные расширения).
- **Цифровая подпись**: валидность, доверенность издателя, отсутствие подписи на 64-битной системе.
- **Контекст времени**: появление драйвера вне периода обновлений, планового обслуживания или подключения нового устройства.

Особое внимание следует уделять технике BYOVD, когда легитимный, но уязвимый драйвер загружается атакующим и эксплуатируется для получения привилегий ядра. Списки таких драйверов публикуются сообществами, и многие EDR-решения сигнатурят их.

## 4. Мониторинг исполняемых образов в SOC L1: события, техники и инструменты

Роль аналитика SOC первой линии в отношении исполняемых образов сводится к оперативному распознаванию аномалий в потоке событий загрузки и созданию надёжных детектирующих правил. Эффективный мониторинг опирается на корреляцию трёх типов событий: создание процесса (EXE), загрузка DLL и загрузка драйвера. Ниже рассматриваются практические аспекты реализации такого мониторинга с использованием Sysmon и подходов к конфигурированию.

### 4.1 Ключевые события Sysmon для мониторинга образов

- **Event ID 1 (ProcessCreation)** — идеально подходит для отслеживания запуска EXE-файлов. Включает командную строку, текущую директорию, хеш-сумму образа, ID родительского процесса, информацию о пользователе. Объём события, как правило, управляемый, что позволяет использовать исключающие правила для известных легитимных процессов.
- **Event ID 7 (Image loaded)** — фиксирует загрузку DLL (и других модулей) в память процесса. Как обсуждалось, из-за экстремально высокого объёма требует строго включающей конфигурации: логируются только конкретные DLL или пары «процесс-библиотека», соответствующие известным техникам атак.
- **Event ID 6 (Driver loaded)** — регистрирует загрузку драйвера. Объём невелик, поэтому можно логировать все события или применять минимальную фильтрацию по доверенным подписантам.

Дополнительно ценность представляют Event ID 8 (CreateRemoteThread) и Event ID 10 (ProcessAccess) для выявления инъекций, при которых DLL загружается в чужой процесс без легитимного контекста.

### 4.2 Построение конфигурации Sysmon для DLL (Event ID 7)
Согласно руководству TrustedSec, конфигурирование Image Load должно следовать принципу **include-based**: в секции `<ImageLoad>` описываются только те DLL, которые необходимо отслеживать [SysmonCommunityGuide](https://github.com/trustedsec/SysmonCommunityGuide/blob/master/chapters/image-loading.md). Попытка логировать все загрузки с последующим исключением шума неприемлема — система будет перегружена. Пример минимальной конфигурации (иллюстративная схема):

```xml
<Sysmon schemaversion="4.50">
   <EventFiltering>
      <ImageLoad onmatch="include">
         <!-- Загрузка PowerShell DLL процессом, отличным от powershell.exe -->
         <Image condition="end with">System.Management.Automation.dll</Image>
         <Image condition="end with">System.Management.Automation.ni.dll</Image>

         <!-- Загрузка скриптовых движков Office-приложениями -->
         <Image condition="end with">vbscript.dll</Image>
         <Image condition="end with">jscript9.dll</Image>

         <!-- Подозрительные DLL, загружаемые из временных каталогов -->
         <Image condition="begin with">C:\Users\Public\</Image>
         <Image condition="begin with">C:\Windows\Temp\</Image>
      </ImageLoad>
   </EventFiltering>
</Sysmon>
```

Такой подход гарантирует, что в журнал попадут только высокоинформативные события. Аналитик L1, просматривая событие ID 7, видит чётко отобранные индикаторы, а не многотысячный поток системных библиотек.

### 4.3 Техники детектирования для SOC L1
Первичный анализ события исполняемого образа включает быструю проверку базовых атрибутов. Для EXE:
- Проверка пути: не должно быть запусков из `%TEMP%`, `%PUBLIC%`, `Downloads`, сетевых папок.
- Командная строка: наличие обфускации (кавычки, экранирование, `^`, base64-строки), вызов нетипичных утилит (`rundll32.exe` с `DllRegisterServer`).
- Родительский процесс: Office-приложение не должно порождать `cmd.exe` или `powershell.exe`.
- Хеш: сравнение с известным списком вредоносных (IoC).

Для DLL (Event ID 7):
- Проверка подписи: неподписанная DLL в чувствительном процессе (LSASS, winlogon) — критичный признак.
- Путь загрузки: DLL из папки пользователя или временного каталога.
- Комбинация процесс→библиотека: например, загрузка `System.Management.Automation.dll` процессом `winword.exe` однозначно указывает на активацию PowerShell через макросы.
- Редкие системные DLL: загрузка `ntdsapi.dll` процессом, не связанным с Active Directory.

Для драйверов (Event ID 6):
- Проверка сертификата: допустимы только подписи Microsoft или известных вендоров (при наличии обновлённого списка разрешённых).
- Анализ даты сборки: драйвер с датой в будущем или очень старой, не соответствующий установленным обновлениям, подозрителен.

### 4.4 Инструментарий аналитика
На позиции L1 аналитик редко проводит глубокий реверс-инжиниринг; его инструменты — это EDR-консоль, SIEM-интерфейс и вспомогательные утилиты:
- **Kibana / Splunk**: фильтрация событий Sysmon, построение дашбордов аномалий загрузки DLL.
- **Sysmon View / Chainsaw**: открытие локальных evtx-файлов.
- **PowerShell**: команда `Get-AuthenticodeSignature` для проверки подписи файла, `Get-FileHash` для вычисления хеша и сверки с индикаторами.
- **VirusTotal**: проверка хеша или подозрительного имени (с соблюдением политик конфиденциальности организации).

Пайплайн обработки события выглядит так: получение алерта из SIEM (например, повышение частоты загрузки DLL из `%TEMP%`) → выгрузка артефактов: пути, хеша, командной строки → первичная проверка подписи → поиск в базе IoC → эскалация на L2, если аномалия подтверждена.

### 4.5 Типичные ошибки и ловушки
- **Настройка Sysmon Image Load на исключение шума** — приводит к throughput-проблемам и пропуску важных событий из-за переполнения логов.
- **Игнорирование легитимных утилит** — восприятие `rundll32.exe` или `regsvr32.exe` как всегда безвредных; наоборот, за ними должен быть усиленный контроль.
- **Ограничение мониторинга только Event ID 1** — без ID 7 невозможно заметить Reflectively Loaded DLL или PowerShell-активность в Office-приложениях.
- **Невнимание к контексту загрузки драйверов** — пропуск BYOVD-атак, когда подпись валидна, но драйвер уязвим.

## Сквозной практический пример: обнаружение загрузки вредоносной DLL через Rundll32

**Исходные условия**  
Инфраструктура: Windows 10 21H2 с установленным Sysmon 14.11 (конфигурация включает правила для Event ID 1 и целевые правила ID 7, отслеживающие вызовы `DllRegisterServer` и загрузку из `C:\Users\Public`). Аналитик SOC L1 получает алерт от SIEM, сработавший по корреляции событий Sysmon. Сценарий: злоумышленник через фишинговый документ получит доступ к командной строке и попытается загрузить DLL `C:\Users\Public\payload.dll`, экспортирующую вредоносную функцию `DllRegisterServer`, с помощью `rundll32.exe`.

**Шаги расследования**

### Шаг 1: Получение и разбор первичных событий
Аналитик открывает SIEM и видит два связанных события. Первое — Sysmon Event ID 1 с запуском `rundll32.exe`:

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="{5770385F-C22A-43E0-BF4C-06F5698FFBD9}" />
    <EventID>1</EventID>
    <Version>5</Version>
    <Level>4</Level>
    <Task>1</Task>
    <Opcode>0</Opcode>
    <Keywords>0x8000000000000000</Keywords>
    <TimeCreated SystemTime="2025-03-16T08:22:17.123456700Z" />
    <EventRecordID>1152921504606846976</EventRecordID>
    <Correlation />
    <Execution ProcessID="4" ThreadID="8" />
    <Channel>Microsoft-Windows-Sysmon/Operational</Channel>
    <Computer>WS-SOC-01.corp.local</Computer>
    <Security UserID="S-1-5-18" />
  </System>
  <EventData>
    <Data Name="RuleName">technique_id=T1218.011,technique_name=Rundll32</Data>
    <Data Name="UtcTime">2025-03-16 08:22:17.123</Data>
    <Data Name="ProcessGuid">{e3a22b5e-1a2c-640a-5678-9a00bc0d0e0f}</Data>
    <Data Name="ProcessId">4280</Data>
    <Data Name="Image">C:\Windows\System32\rundll32.exe</Data>
    <Data Name="FileVersion">10.0.19041.546 (WinBuild.160101.0800)</Data>
    <Data Name="Description">Windows host process (Rundll32)</Data>
    <Data Name="Product">Microsoft® Windows® Operating System</Data>
    <Data Name="Company">Microsoft Corporation</Data>
    <Data Name="OriginalFileName">RUNDLL32.EXE</Data>
    <Data Name="CommandLine">"C:\Windows\System32\rundll32.exe" C:\Users\Public\payload.dll,DllRegisterServer</Data>
    <Data Name="CurrentDirectory">C:\Users\Public\</Data>
    <Data Name="User">CORP\jdoe</Data>
    <Data Name="LogonGuid">{e3a22b5e-1234-5678-9abc-def012345678}</Data>
    <Data Name="LogonId">0x3e7</Data>
    <Data Name="TerminalSessionId">1</Data>
    <Data Name="IntegrityLevel">Medium</Data>
    <Data Name="Hashes">SHA1=ABCDEF1234567890ABCDEF1234567890ABCDEF12,MD5=ABCDEF1234567890ABCDEF1234567890, ...</Data>
    <Data Name="ParentProcessGuid">{e3a22b5e-5678-1234-9abc-def012345678}</Data>
    <Data Name="ParentProcessId">2840</Data>
    <Data Name="ParentImage">C:\Windows\System32\cmd.exe</Data>
    <Data Name="ParentCommandLine">"C:\Windows\System32\cmd.exe"</Data>
  </EventData>
</Event>
```

Ключевые поля:
- `CommandLine`: отчётливо виден вызов `DllRegisterServer`, что не является штатным для `rundll32.exe`.
- `ParentImage`: `cmd.exe`. Ожидаемый родитель для интерактивного запуска `rundll32` — `explorer.exe`, а `cmd.exe` часто указывает на скриптовую активность.
- `Image` DLL расположен в `C:\Users\Public`, что является изменяемой пользователями папкой и нехарактерно для легитимных библиотек.

### Шаг 2: Проверка загрузки DLL (Sysmon Event ID 7)
Аналитик ищет событие ID 7 в том же временном окне для процесса PID 4280:

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Sysmon" Guid="{...}" />
    <EventID>7</EventID>
    ...
  </System>
  <EventData>
    <Data Name="RuleName">-</Data>
    <Data Name="UtcTime">2025-03-16 08:22:17.125</Data>
    <Data Name="ProcessGuid">{e3a22b5e-1a2c-640a-5678-9a00bc0d0e0f}</Data>
    <Data Name="ProcessId">4280</Data>
    <Data Name="Image">C:\Windows\System32\rundll32.exe</Data>
    <Data Name="ImageLoaded">C:\Users\Public\payload.dll</Data>
    <Data Name="FileVersion">-</Data>
    <Data Name="Description">-</Data>
    <Data Name="Product">-</Data>
    <Data Name="Company">-</Data>
    <Data Name="OriginalFileName">-</Data>
    <Data Name="Hashes">MD5=0123456789ABCDEF0123456789ABCDEF,SHA256=... </Data>
    <Data Name="Signed">false</Data>
    <Data Name="Signature">-</Data>
    <Data Name="SignatureStatus">NotSigned</Data>
  </EventData>
</Event>
```

Основные индикаторы:
- `ImageLoaded`: совпадает с путём из командной строки.
- `Signed`: false, вместе с `SignatureStatus=NotSigned` — критично для модуля, загружаемого в системный процесс (пусть и легитимный `rundll32.exe`).
- Отсутствие информации о версии (`FileVersion`, `Description`, `Company`) косвенно указывает на то, что DLL собрана наспех или специально лишена метаданных.

### Шаг 3: Контекстная проверка с помощью PowerShell
Для документирования инцидента аналитик запускает на подозрительном хосте (через удалённую сессию) команду проверки цифровой подписи и хеша:

```powershell
Get-AuthenticodeSignature -FilePath "C:\Users\Public\payload.dll" | Format-List

SignerCertificate      : 
Status                 : NotSigned
StatusMessage          : Формат сообщения, возвращаемого в случае отсутствия подписи
Path                   : C:\Users\Public\payload.dll
SignatureType          : None
IsOSBinary             : False
```

Отсутствие подписи подтверждено. Затем вычисляется SHA256 для сверки с известными вредоносными образцами (IoC):

```powershell
Get-FileHash -Path "C:\Users\Public\payload.dll" -Algorithm SHA256

Algorithm       Hash                                                                   Path
---------       ----                                                                   ----
SHA256          E3B0C44298FC1C149AFBF4C8996FB92427AE41E4649B934CA495991B7852B855       C:\Users\Public\payload.dll
```

(хеш приведён иллюстративный; в реальности он будет уникальным)

### Шаг 4: Корреляция и эскалация
Аналитик связывает событие создания процесса (Event ID 1) с событием загрузки образа (ID 7). Формируется заключение: пользователь `CORP\jdoe` запустил `rundll32.exe` из скрипта (родитель `cmd.exe`), загрузив неподписанную DLL из публичной папки и вызвав нестандартную функцию `DllRegisterServer`. Данные признаки соответствуют технике MITRE T1218.011 (Rundll32) и могут свидетельствовать о компрометации учётной записи. Инцидент эскалируется на L2 для изоляции хоста и анализа образа DLL.

### Ожидаемый вывод примера
Пример демонстрирует, как анализ событий Sysmon, охватывающих загрузку исполняемых образов разных типов, позволяет аналитику первого уровня идентифицировать вредоносную активность на ранней стадии. Корреляция Event ID 1 и ID 7 даёт полное представление о способе запуска и загружаемом коде, а проверка подписи и пути загрузки подтверждает аномалию без необходимости в глубоком реверс-инжиниринге.
