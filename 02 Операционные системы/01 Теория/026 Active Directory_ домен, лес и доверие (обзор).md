# Active Directory: домен, лес и доверие (обзор)

## 1. Контекст и базовые понятия: логическая архитектура Active Directory и роль доверия

Доменные службы Active Directory (Active Directory Domain Services, AD DS) реализуют централизованную модель управления идентификацией и доступом в средах Windows Server. Тремя фундаментальными логическими конструкциями этой модели являются **домен**, **лес** и **доверие (trust)**. Несмотря на частое совместное употребление, эти три сущности выполняют различные функции: домен задаёт границы администрирования и репликации, лес объединяет домены общей схемой и глобальным каталогом, а доверие определяет, могут ли, и при каких условиях, учётные записи одного домена аутентифицироваться в другом. Для специалиста SOC L1 критически важно уметь различать их, поскольку от типа доверительных отношений напрямую зависят возможные пути распространения атакующего в многоуровневой Active Directory.

**Домен** — это логический контейнер, объединяющий компьютеры, пользователей и группы под единой политикой безопасности и с общей базой учётных записей, хранящейся на контроллерах домена. Внутри домена действуют единые правила парольной политики, аудита и делегирования. Границы домена одновременно являются границами репликации: изменения объектов одного домена тиражируются только на контроллеры этого же домена (за исключением фрагментов глобального каталога). Таким образом, домен представляет собой самостоятельную единицу администрирования, хотя технически полностью изолированная работа домена без привязки к лесу невозможна: каждый домен является частью ровно одного леса.

**Лес (forest)** — наивысший логический контейнер в AD DS. Лес состоит из одного или нескольких доменов, которые разделяют общую схему (определение всех классов и атрибутов объектов) и контейнер конфигурации (топология репликации, информация о сайтах, сервисах). Все домены одного леса связаны автоматически создаваемыми двухсторонними транзитивными доверительными отношениями, что обеспечивает сквозную аутентификацию между любыми доменами леса. Лес определяет границу безопасности на уровне административного контроля схемы и конфигурации: злоумышленник, захвативший привилегии уровня Enterprise Admin в лесу, получает контроль над всеми доменами леса. Поэтому с точки зрения моделирования угроз лес часто рассматривается как единая зона доверия, а домен — как логический сегмент внутри неё.

**Доверие (trust)** — это логическая связь между двумя доменами, позволяющая контроллеру одного домена (доверяющего, trusting) принимать аутентификационные данные, выданные контроллером другого домена (доверенного, trusted). Доверие не копирует учётные записи и не объединяет каталоги; оно лишь создаёт канал для проверки подлинности и авторизации. Итоговое решение о доступе к ресурсу принимает контроллер домена, которому принадлежит ресурс, на основе предъявленного пакета привилегий (PAC) из билета Kerberos или данных NTLM.

Важно разделять несколько сходных по названию, но функционально различных сущностей, в которых встречается слово «лес» или «доверие»:

```text
| Сущность                          | Ключевые признаки                                                                           | Типичная область применения / пояснение                              |
|-----------------------------------|---------------------------------------------------------------------------------------------|----------------------------------------------------------------------|
| Домен AD                          | Единая база учётных записей, граница репликации и политик; часть леса                       | Элементарная единица управления идентификацией в AD DS               |
| Дерево доменов (tree)             | Набор доменов с непрерывным пространством имён DNS, объединённых транзитивными трастами     | Иерархическая группировка доменов внутри леса (например, corp.com и sub.corp.com) |
| Лес (forest)                      | Наивысший контейнер; общая схема и конфигурация, автоматические двунаправленные трасты между всеми доменами | Граница безопасности, в рамках которой действуют Enterprise Admins   |
| Доверие внутри леса (intra-forest trust)  | Автоматически создаётся между доменами одного леса; транзитивное, двунаправленное | Обеспечивает сквозную аутентификацию между любыми доменами леса      |
| Лесное доверие (forest trust)     | Создаётся вручную между корневыми доменами двух лесов; транзитивное в пределах этих лесов, но не распространяется на третий лес | Интеграция ресурсов двух организаций или слияние AD после поглощения |
| Внешнее доверие (external trust)  | Нетранзитивное доверие между доменами разных лесов (или с доменом NT4); применяется для доступа к конкретному домену-партнёру | Точечная интеграция без расширения доверия на другие домены леса     |
| Доверие области (realm trust)     | Связь домена AD с областью Kerberos v5 (например, MIT Kerberos)                             | Интеграция Unix/Linux-систем, использующих чистый Kerberos            |
```

Дополнительно выделяют ярлыки (shortcut trusts) — транзитивные доверия между двумя доменами одного леса, создаваемые для оптимизации пути аутентификации при сложной иерархии. Они не меняют логику безопасности, но сокращают длину доверительного пути.

В выдержке [Netwrix](https://netwrix.com/en/resources/blog/trusts-in-active-directory) подчёркивается, что внутри леса все домены доверяют друг другу благодаря автоматически создаваемым двусторонним транзитивным трастам. При переходе к Windows 2000 эта модель заменила ручное создание многочисленных односторонних трастов на NetBIOS, характерное для архитектуры Windows NT 4.0.

Таким образом, домен – фундаментальная единица, лес – контейнер, а доверие – механизм взаимодействия. Дальнейшее изложение детально рассматривает устройство каждого из этих элементов.

## 2. Внутреннее устройство домена, леса и доверительных связей

Понимание того, как устроены домен и лес на уровне служебных данных и сетевых взаимодействий, необходимо для анализа журналов безопасности и расследования инцидентов, связанных с аутентификацией. В этом разделе последовательно разбираются структура леса, компоненты домена и архитектура доверия.

### 2.1 Лес как совокупность служебных разделов

Лес AD DS физически представлен контроллерами доменов, каждый из которых хранит несколько разделов каталога (directory partitions), также называемых контекстами именования. Выделяют три основных раздела:

- **Domain Naming Context** – раздел, содержащий объекты конкретного домена (пользователи, компьютеры, группы, организационные подразделения). Каждый домен имеет собственный контекст, реплицируемый исключительно между контроллерами этого домена.
- **Configuration Naming Context** – раздел с данными о топологии леса: сайты, сервисы, настройки репликации. Он реплицируется на все контроллеры всех доменов леса, обеспечивая единство конфигурации.
- **Schema Naming Context** – раздел, определяющий схему: множество классов объектов и их атрибутов. Схема едина для всего леса и реплицируется на все контроллеры.

Глобальный каталог (Global Catalog, GC) – это частичная реплика раздела каждого домена, которая хранит подмножество атрибутов объектов, наиболее часто используемых для поиска (например, `userPrincipalName`, `memberOf`). GC размещается на выделенных контроллерах (GC-серверах) и позволяет быстро находить объекты в любом домене леса без обращения к специализированному контроллеру целевого домена.

На уровне DNS лес представлен иерархией зон, соответствующих доменным именам. Корневой домен леса – первый созданный домен; его удаление невозможно до тех пор, пока существуют дочерние домены. Схема леса управляется группой Schema Admins, а конфигурация – группой Enterprise Admins (только в корневом домене).

Приведённая ниже ASCII-схема иллюстрирует пример леса с двумя деревьями и несколькими доменами, а также автоматические транзитивные трасты внутри леса:

```text
         Forest: example.com (корневой домен)
        [DC: dc01.example.com]
              |
    ┌─────────┴──────────────┐
    |                        |
   [Tree1]                  [Tree2]
 example.com              another.org
  ├─ east.example.com       ├─ dept.another.org
  └─ west.example.com       └─ sales.another.org

Автоматические двусторонние транзитивные трасты:
  example.com <-> east.example.com
  example.com <-> west.example.com
  example.com <-> another.org
  another.org <-> dept.another.org
  another.org <-> sales.another.org
 (и аналогично между любыми комбинациями)
```

Все контроллеры леса хранят идентичные копии разделов конфигурации и схемы; разделы доменов хранятся только на соответствующих контроллерах. Благодаря транзитивности трастов аутентификация проходит по кратчайшему пути, автоматически вычисляемому службой Net Logon.

### 2.2 Домен: контроллеры, роли и репликация

Контроллер домена (Domain Controller, DC) – сервер Windows Server, хранящий полную копию раздела своего домена и выступающий точкой аутентификации для участников домена. В каждом домене должно быть не менее одного контроллера; для отказоустойчивости и распределения нагрузки используется несколько DC. Данные между DC одного домена реплицируются с помощью механизмов AD Replication (по протоколам RPC или SMTP), управляемых службой Knowledge Consistency Checker (KCC).

Логическая целостность домена поддерживается пятью ролями Flexible Single Master Operations (FSMO), распределёнными по контроллерам:

- **Schema Master** (лес) – единственный DC, на котором разрешено изменение схемы.
- **Domain Naming Master** (лес) – управляет добавлением и удалением доменов в лесу.
- **RID Master** (домен) – выделяет пулы относительных идентификаторов (RID) для создания новых объектов безопасности.
- **PDC Emulator** (домен) – эмулятор основного контроллера NT4; синхронизация времени, обработка блокировок паролей, приоритетная репликация изменений паролей.
- **Infrastructure Master** (домен) – обновляет ссылки на объекты других доменов в локальных группах.

С точки зрения SOC, компрометация ролей PDC Emulator или RID Master даёт злоумышленнику дополнительные возможности, такие как перехват изменений паролей (DCSync) или создание дублирующихся SID.

### 2.3 Механизм доверия: объект TDO и аутентификация

Каждое доверительное отношение представлено в Active Directory объектом класса `trustedDomain` (TDO), расположенным в контейнере System домена-доверяющего. Как отмечено в [Netwrix](https://netwrix.com/en/resources/blog/trusts-in-active-directory), TDO содержит критически важные атрибуты, характеризующие тип и поведение траста. Основные атрибуты:

- `trustType`: 1 – доверие с доменом Windows NT (down-level), 2 – доверие с доменом Active Directory, 3 – доверие с областью Kerberos (MIT).
- `trustDirection`: 0 – отключено, 1 – входящее (локальный домен доверяет удалённому), 2 – исходящее (локальный домен является доверенным для удалённого), 3 – двунаправленное.
- `trustAttributes`: битовая маска, в которой биты определяют свойства: транзитивность (`0x0001`), фильтрацию SID (`0x0004`), выборочную аутентификацию (`0x0008`), тип лесного доверия (`0x0020`) и др.
- `trustPartner`: Distinguished Name или NetBIOS-имя домена-партнёра.

Аутентификация по трасту использует два основных протокола: Kerberos и NTLM. Для Kerberos механизм основан на рефералах (referrals). Когда пользователь домена A запрашивает доступ к ресурсу в домене B, контроллер домена A выдаёт билет TGT, который содержит информацию о домене учётной записи, но не даёт прямого доступа. При обращении к домену B клиент запрашивает у своего DC межобластной билет (inter-realm TGT), ссылающийся на домен B через цепочку доверий. Контроллер домена B проверяет цепочку и, при успехе, выдаёт служебный билет для целевого ресурса. Эта процедура детально описана в [AWS Security Blog](https://aws.amazon.com/blogs/security/everything-you-wanted-to-know-about-trusts-with-aws-managed-microsoft-ad), где подчёркивается, что проверка пути доверия выполняется вычислительно, и именно от корректности трастов зависит успех аутентификации.

Служба Net Logon устанавливает защищённый канал RPC между контроллерами доменов-партнёров, используя общий секрет — пароль доверия (trust password), который периодически меняется согласно политикам безопасности. Эта связь обеспечивает обмен SID и проверку членства в группах.

Транзитивность трастов — ключевое свойство, отличающее внутрилесные и лесные доверия от внешних. Внутри одного леса все трасты транзитивны: если домен A доверяет B, а B доверяет C, то A автоматически доверяет C. Для лесных доверий Microsoft уточняет, что транзитивность действует только в пределах двух участвующих лесов и не распространяется на третий лес, даже если между вторым и третьим существует лесное доверие; документ [How trusts work for Microsoft Entra Domain Services](https://learn.microsoft.com/en-us/entra/identity/domain-services/concepts-forest-trust) прямо утверждает: «лесное доверие создаётся только между корневыми доменами двух лесов и не может быть неявно расширено на третий лес». Это важное ограничение, которое следует учитывать при анализе возможных путей перемещения злоумышленника: даже при наличии цепочки лесных доверий A↔B и B↔C, домен A не будет доверять C, если не создано прямое доверие.

Объект TDO и связанные атрибуты являются первоочередными артефактами для аудита и инвентаризации доверий, что будет продемонстрировано в практическом разделе.

## 3. Применение и работа с довериями в контексте SOC L1

Для специалиста первой линии мониторинга безопасности знание инструментария и практических команд для работы с довериями необходимо при анализе алертов о подозрительной аутентификации, а также при базовом расследовании инцидентов, связанных с перемещением между доменами (lateral movement). В этом разделе описаны типовые операции, ключевые команды PowerShell и важные аспекты, касающиеся уязвимостей трастов.

### 3.1 Инвентаризация и аудит существующих доверий

Перед реагированием на инцидент необходимо уметь быстро оценить текущую топологию доверий в домене. Сделать это можно с помощью модуля Active Directory для PowerShell.

**Просмотр всех доверий домена** (команда возвращает исчерпывающую информацию о каждом объекте доверия):

```powershell
Get-ADTrust -Filter *
```

Пример иллюстративного вывода (значения зависят от среды):

```
Direction         : Bidirectional
DisallowTransivity: False
DistinguishedName : CN=otherdomain.com,CN=System,DC=example,DC=com
ForestTransitive  : True
IntraForest       : False
IsTreeParent      : False
IsTreeRoot        : False
Name              : otherdomain.com
ObjectClass       : trustedDomain
Target            : otherdomain.com
TrustAttributes   : 8
TrustedPolicy     :
TrustingPolicy    :
TrustType         : Uplevel
UplevelOnly       : False
UsesAESKeys       : False
UsesRC4Encryption : False
```

Для выборочного отображения ключевых свойств, полезных при триаже:

```powershell
Get-ADTrust -Filter * | Format-Table Name, Direction, TrustType, ForestTransitive, IntraForest
```

**Поиск объекта TDO напрямую через AD**, как рекомендуется в [Netwrix](https://netwrix.com/en/resources/blog/trusts-in-active-directory), позволяет получить все атрибуты:

```powershell
Get-ADObject -SearchBase "cn=system,dc=example,dc=com" -Filter * -Properties * | Where-Object {$_.objectClass -eq "trustedDomain"} | Format-List
```

Данный способ полезен при отсутствии загруженного модуля AD Trust cmdlets или в средах с ограниченными правами.

При SOC-мониторинге следует обращать внимание на неожиданные изменения атрибутов трастов: появление нового TDO, изменение направления на Inbound/Outbound, добавление атрибута `TRUST_ATTRIBUTE_QUARANTINED_DOMAIN` (0x0004), который включает фильтрацию SID — механизм, предотвращающий подделку идентификаторов безопасности из доверенного домена.

### 3.2 Создание и настройка доверия (лесного) — практическая процедура

Хотя инженерная настройка обычно выполняется администраторами, понимание процесса создания траста помогает анализировать легитимность изменений и интерпретировать события аудита. Ниже приведена обобщённая последовательность создания двустороннего лесного доверия между лесами `A.corp` и `B.corp` с использованием PowerShell (из контекста домена-инициатора `A.corp`). Процесс опирается на предварительно настроенные DNS-зоны, как указано в документации [Digicert](https://docs.digicert.com/en/trust-lifecycle-manager/enroll-and-manage-certificates/autoenrollment-server/cross-forest-trust-to-allow-autoenrollment-server-enrollments-across-a-multi-domain-forest-network-structure/trust-between-two-forests--using-dns-stub-zone-.html).

**Шаги создания:**
1. Убедиться во взаимной доступности контроллеров по DNS (например, через `nslookup b.corp`).
2. Выполнить на DC леса A:

```powershell
$cred = Get-Credential  # учетные данные администратора леса B
New-ADTrust -Name "B.corp" -ForestTrust -Direction Bidirectional -OtherForestCredential $cred
```
Опция `-ForestTrust` задаёт тип «лесной», `-Direction Bidirectional` создаёт двусторонний траст; пароль генерируется автоматически.

3. На контроллере леса B администратор либо выполняет аналогичную команду, либо может принять готовое исходящее доверие, созданное на стороне A, если используется централизованный сценарий (члены Enterprise Admins обоих лесов). По окончании работы команды `New-ADTrust` возвращает объект TDO.

**Проверка состояния траста и его свойств:**

```powershell
Get-ADTrust -Identity "B.corp"
```

Ожидаемые ключевые параметры: `Direction: Bidirectional`, `ForestTransitive: True`, `TrustType: Uplevel`, `IntraForest: False`. При наличии двустороннего лесного доверия аутентификация будет проходить между всеми доменами обоих лесов благодаря транзитивности.

### 3.3 Анализ событий, связанных с трастами

Для выявления подозрительной аутентификации через доверительные отношения на контроллерах доменов регистрируются события безопасности:

- **4768** — запрос билета TGT (Kerberos). В поле `Account Domain` отображается домен запрашивающего, а в `Service Name` — krbtgt/DOMAIN. При аутентификации через траст может появляться билет с именем krbtgt удалённого домена.
- **4769** — запрос служебного билета. Комбинация `Account Domain`, отличного от локального домена, и `Service Name`, связанного с ресурсом, указывает на крос-доменную активность.
- **4771** — сбой предварительной аутентификации Kerberos; часто используется для обнаружения атак Kerberoasting, в том числе направленных на учётные записи доверенных доменов.

Пример фрагмента журнала безопасности (иллюстративная схема событий):

```text
Event ID: 4769
Account Name: jdoe
Account Domain: A.corp
Service Name: cifs/fileserver.B.corp
Service ID: %{S-1-5-21-<domain-sid>...}
Client Address: ::ffff:10.0.0.100
Status: 0x0
```

Интерпретация: пользователь `jdoe` домена A.corp успешно получил служебный билет для доступа к файловому серверу в домене B.corp, что свидетельствует о рабочем трасте. SOC-аналитик должен соотнести такую активность с рабочим временем и легитимными обязанностями пользователя.

### 3.4 Уязвимости и атаки, эксплуатирующие доверия

Доверительные отношения могут быть использованы злоумышленниками для расширения присутствия. Наиболее известные техники:

- **Trust hopping** – перемещение между доменами через цепочку трастов. Как показано в [dirkjanm.io](https://dirkjanm.io/active-directory-forest-trusts-part-two-trust-transitivity), внутри леса компрометация одного домена потенциально ведёт к контролю над всем лесом из-за транзитивности и наличия административных групп уровня Enterprise. В случае лесных доверий атакующий может переходить только между непосредственно доверяющими лесами; третий лес остаётся недоступным без явного траста.
- **SID History подделка** – если фильтрация SID отключена на входящей стороне траста, пользователь доверенного домена может внедрить подложный SID (например, SID группы Enterprise Admins) в свой PAC и получить несанкционированный доступ к ресурсам доверяющего домена. Защитной мерой является включение SID filtering (trustAttributes = 0x0004), реализуемое через политику «Quarantine Trust».
- **Выборочная аутентификация** – когда на трасте активирована selective authentication (trustAttributes = 0x0008), доступ разрешён только к тем ресурсам, на которых явно указана группа «Разрешённая аутентификация». Неправильная настройка может оставить «дыры», поэтому SOC должен обращать внимание на события отказа с кодом 0x22 (STATUS_ACCOUNT_DISABLED) при кросс-лесных запросах.
- **Межлесное Kerberoasting** – атака, при которой злоумышленник, обладая учётной записью в одном лесу, запрашивает TGS для учётных записей служб в доверенном лесу и перебирает хэши офлайн.

Обнаружение этих атак требует корреляции событий аутентификации с топологией трастов и контроля целостности атрибутов TDO. В следующем разделе представлен сквозной пример, демонстрирующий реалистичный сценарий аудита и защиты.

## 4. Сквозной практический пример: аудит и обеспечение безопасности одностороннего доверия между лесами

**Исходные условия.** Организация провела слияние, и в результате появилось два леса: `acme.corp` (существующая инфраструктура) и `subsidiary.corp` (присоединённая компания). Для предоставления пользователям `subsidiary.corp` доступа к файловым ресурсам `acme.corp` администраторы создали одностороннее входящее доверие: лес `acme.corp` доверяет лесу `subsidiary.corp`. SOC-аналитик должен убедиться, что доверие настроено корректно, SID-фильтрация включена, а попытки несанкционированного доступа из недоверенных доменов отсутствуют. Лабораторная среда: Windows Server 2019, PowerShell 5.1, права Domain Admin.

**Шаг 1. Проверка текущей конфигурации траста со стороны `acme.corp`**

Выполняется команда для извлечения атрибутов траста:

```powershell
Get-ADTrust -Identity "subsidiary.corp"
```

Вывод (иллюстративная схема, значения зависят от среды):

```
Direction                : Inbound
DisallowTransivity       : False
DistinguishedName        : CN=subsidiary.corp,CN=System,DC=acme,DC=corp
ForestTransitive         : True
IntraForest              : False
Name                     : subsidiary.corp
Target                   : subsidiary.corp
TrustAttributes          : 4   (TRUST_ATTRIBUTE_QUARANTINED_DOMAIN)
TrustType                : Uplevel
```

Аналитик обращает внимание на `TrustAttributes = 4`, что соответствует включённой фильтрации SID – это базовая гигиена безопасности.

**Шаг 2. Проверка DNS-разрешения и доступности контроллеров**

Для уверенности в физической достижимости партнёра выполняется запрос к контроллеру домена `subsidiary.corp`:

```powershell
nslookup -type=SRV _ldap._tcp.subsidiary.corp
```

Ожидаемый вывод содержит запись SRV с указанием имени DC:

```
_ldap._tcp.subsidiary.corp    SRV service location:
          priority       = 0
          weight         = 100
          port           = 389
          svr hostname   = dc01.subsidiary.corp
dc01.subsidiary.corp    internet address = 192.168.10.5
```

**Шаг 3. Тестовая аутентификация с анализом Kerberos-билета**

На рабочей станции в домене `acme.corp` под учётной записью пользователя из доверенного домена (например, `user1@subsidiary.corp`) выполняется попытка подключения к файловому ресурсу:

```cmd
net use \\fileserver.acme.corp\shared
```

После успешного подключения аналитик проверяет кэширование билетов Kerberos:

```cmd
klist
```

Фрагмент вывода:

```
Cached Tickets: (2)

#0>     Client: user1 @ SUBSIDIARY.CORP
        Server: cifs/fileserver.acme.corp @ ACME.CORP
        KerbTicket Encryption Type: AES-256-CTS-HMAC-SHA1-96
        Ticket Flags 0x40a10000 -> forwardable renewable pre_authent name_canonicalize
        Start Time: 2/10/2025 9:15:00 (local)
        End Time:   2/10/2025 19:15:00 (local)

#1>     Client: user1 @ SUBSIDIARY.CORP
        Server: krbtgt/ACME.CORP @ SUBSIDIARY.CORP
        KerbTicket Encryption Type: AES-256-CTS-HMAC-SHA1-96
...
```

Билеты подтверждают, что клиент получил межобластной TGT (`krbtgt/ACME.CORP`) и служебный билет к файловому серверу. Транзитивность лесного доверия обеспечила аутентификацию без участия дополнительных доменов.

**Шаг 4. Эмуляция попытки несанкционированного доступа с отключённой SID-фильтрацией (обучающий пример)**

В исследовательских целях аналитик временно отключает фильтрацию SID на доверии (операция выполняется администратором):

```powershell
Set-ADTrust -Identity "subsidiary.corp" -SIDFilteringQuarantined $false
```

Затем пользователь `user1` пробует добавить в свой PAC подложный SID (например, SID группы Enterprise Admins леса `acme.corp`). Подобная атака требует специального инструментария, как Mimikatz, и в лаборатории демонстрируется для осознания риска. При отключённом SID filtering злоумышленник мог бы получить несанкционированный доступ. Аналитик регистрирует событие отказа (Event ID 4768) при попытке получить TGT с недоверенным SID после повторного включения фильтрации. Возврат безопасного состояния:

```powershell
Set-ADTrust -Identity "subsidiary.corp" -SIDFilteringQuarantined $true
```

**Ожидаемый вывод.** Пример демонстрирует, как с помощью стандартных команд PowerShell и анализа журналов можно верифицировать конфигурацию доверия в лесу, удостовериться в работоспособности аутентификации и выявить потенциально опасную деактивацию механизмов защиты (SID filtering). Для SOC L1 это означает умение собрать доказательную базу о легитимности или подозрительности крос-доменной активности.
