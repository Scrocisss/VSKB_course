# Файловая система и структура каталогов в Linux

## Файловая система Linux: базовые понятия и классификация

В Linux термин «файловая система» обозначает одновременно два взаимосвязанных понятия: технологию организации хранения данных на физическом носителе (логический том, форматирование) и иерархическое дерево каталогов, видимое пользователю. Путаница между ними осложняет обучение, но для специалиста по безопасности критично понимать разницу. Первое – конкретная реализация: ext4, XFS, Btrfs и другие, определяющая способ размещения файлов, журналирования и восстановления. Второе – стандартизированное пространство имён, определяемое **Filesystem Hierarchy Standard (FHS)** и начинающееся с единого корня `/`. Даже если система использует несколько физических разделов с разными ФС, все они монтируются в единое дерево, образуя виртуальную единую файловую структуру. Эта архитектура – прямое следствие принципа «всё есть файл», фундаментальной парадигмы UNIX/Linux.

**Разграничение фундаментальных понятий**:

| Понятие | Определение | Функция в Linux | Примеры / Отношение к SOC |
|---------|------------|-----------------|---------------------------|
| Файловая система (технология) | Программно-аппаратный комплекс, управляющий размещением данных на блочном устройстве; включает структуры суперблока, инодов, таблиц размещения, журнал | Обеспечивает надёжное хранение, производительность, восстановление после сбоев | ext4, XFS, Btrfs; журналирование важно для целостности логов и цепочки доказательств |
| Иерархия каталогов (FHS) | Логическая структура размещения файлов и каталогов в пространстве имён, независимая от физического носителя | Унифицирует расположение системных утилит, конфигураций, пользовательских данных, упрощая администрирование и реагирование на инциденты | `/etc`, `/var/log`, `/proc`; зная FHS, SOC‑аналитик предсказуемо находит артефакты |
| Тип файла | Классификация объекта файловой системы: обычный файл, каталог, символьная/блочная ссылка, сокет, FIFO | Определяет поведение при обращении: чтение, запись, поиск; влияет на контроль доступа и методы сокрытия | Символьная ссылка на `/etc/shadow`; блочное устройство `/dev/sda` |
| Точка монтирования | Каталог, в который встраивается корень подключаемой файловой системы | Обеспечивает объединение нескольких физических разделов (или виртуальных ФС) в единое дерево | `/mnt/usb`, `/proc` (procfs); скрытое монтирование может маскировать вредоносные структуры |

**Принцип «всё есть файл»** означает, что почти любой объект операционной системы представлен в виде файла или файлоподобного дескриптора. Так, каталоги – это файлы, содержащие список записей; жёсткие диски – блочные файлы устройств в `/dev`; информация о процессах и ядре – виртуальные файлы в `/proc` и `/sys`. Для SOC‑аналитика это оборачивается тем, что любые действия злоумышленника или легитимные процессы оставляют следы в виде файлов: логи, дампы памяти, конфигурационные изменения, временные файлы. Умение оперировать понятием типа файла необходимо для корректной интерпретации находок.

**Типы файлов** распознаются по первому символу вывода `ls -l`; полный список определён в стандарте POSIX:

| Символ | Тип | Описание | Типичные примеры, значимые для SOC |
|--------|-----|----------|------------------------------------|
| `-` | Обычный файл | Последовательность байтов; может быть текстовым, бинарным, исполняемым | `/bin/ls`, `/etc/passwd`, логи (`/var/log/syslog`) |
| `d` | Каталог | Содержит имена и ссылки на другие объекты | `/home`, `/tmp`, `/etc/cron.d` |
| `l` | Символьная ссылка | Указатель на другой файл по имени | `/bin` → `/usr/bin`; ссылка на библиотеку |
| `c` | Символьное устройство | Побайтовый доступ к аппаратному или виртуальному устройству | `/dev/tty`, `/dev/null` |
| `b` | Блочное устройство | Посекторный доступ, обычно к дискам | `/dev/sda`, `/dev/loop0` |
| `s` | Сокет | IPC‑соединение между процессами | `/run/dbus/system_bus_socket` |
| `p` | FIFO (именованный канал) | Однонаправленный поток данных между процессами | Специфичные IPC‑объекты; могут использоваться для скрытой коммуникации |

Для определения типа файла на практике используется команда `file`, анализирующая сигнатуры и структуру:
```bash
$ file /bin/ls
/bin/ls: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 3.2.0, stripped
$ file /dev/sda
/dev/sda: block special (8/0)
```
Подобное разграничение помогает при расследовании: например, символьная ссылка на системный файл может использоваться для обхода проверок целостности.

## Внутреннее устройство файловых систем Linux

Современные дисковые файловые системы Linux (ext4, XFS) построены вокруг трёх логических слоёв: метаданные файловой системы, данные и механизмы обеспечения согласованности. Понимание их внутреннего устройства необходимо для восстановления удалённых данных, выявления скрытых артефактов (например, стеганографии в slack‑пространстве) и анализа аномалий, зафиксированных на уровне блоков.

### Компоненты типичной файловой системы (на примере ext4)

```text
[Суперблок] ──(содержит общую информацию о ФС: размер блока, количество инодов, метку тома)──▶ [Группа блоков 0] ... [Группа блоков N]
           │
           └──(размножен в нескольких группах для отказоустойчивости)

В каждой группе блоков:
[Таблица инодов] ──(массив структур inode)──▶ [Битовые карты блоков/инодов] ──▶ [Блоки данных]
```

Основные структуры:

- **Суперблок (superblock)** содержит глобальные параметры: версию, общий размер, количество зарезервированных блоков, время последнего монтирования и проверки. Повреждение суперблока делает ФС нечитаемой; для восстановления хранятся резервные копии в фиксированных смещениях. В SOC‑контексте суперблок — источник меток времени последней активности, полезных для временной реконструкции.

- **Инод (inode)** — структура, описывающая один файл или каталог. Инод не содержит имени файла, но хранит:
  - Тип объекта и права доступа (режим)
  - Идентификаторы владельца (UID) и группы (GID)
  - Временные метки: последнее чтение (atime), модификация данных (mtime), изменение метаданных (ctime), удаление (dtime)
  - Счётчик жёстких ссылок
  - Размер в байтах
  - Указатели на блоки данных (прямые, косвенные, дважды/трижды косвенные — для больших файлов)
  - В ext4 используется экстентное дерево (extent tree) вместо непрямых блоков, что ускоряет доступ к крупным файлам.

  Иллюстративная схема полей инода (упрощённо):
  ```json
  {
    "inode_number": "целое, уникальное в ФС",
    "mode": "тип + права доступа (например, 100644 для обычного файла)",
    "uid": "числовой идентификатор владельца",
    "gid": "числовой идентификатор группы",
    "size": "размер в байтах",
    "blocks": "количество занятых 512-байтовых блоков",
    "timestamps": {
      "atime": "unix-время последнего доступа",
      "mtime": "изменение данных",
      "ctime": "изменение метаданных"
    },
    "extents": [
      {"start_block": "логический номер первого блока экстента", "length": "число блоков"}
    ]
  }
  ```

- **Каталог** — особый тип файла, содержащий список записей «имя → номер инода». Таким образом, жёсткая ссылка — это просто запись в каталоге с тем же номером инода. Удаление файла (системный вызов `unlink`) уменьшает счётчик ссылок в иноде; когда он достигает нуля, блоки освобождаются. С точки зрения форензики, даже при удалении файла инод может сохраняться в журнале или на диске, пока его место не перезаписано.

- **Блоки данных** хранят непосредственно содержимое файлов. Минимальная единица выделения — логический блок (обычно 4 КиБ). Из-за фрагментации файл может занимать несколько экстентов (указателей на непрерывные диапазоны блоков), что замедляет чтение. Анализ фрагментов неудалённых блоков часто выявляет остаточные данные.

### Журналирование

Журналируемые файловые системы (ext3/4, XFS, Btrfs) протоколируют изменения метаданных (или полные данные) в специальном циклическом буфере — журнале. При сбое питания после монтирования выполняется «восстановление журнала», гарантируя согласованность структуры. Это предотвращает необходимость полной проверки `fsck`, но не защищает содержимое файлов при отложенной записи.

Сравнение режимов журналирования ext4:

| Режим | Журналируемые объекты | Риск потери данных | Производительность |
|-------|----------------------|-------------------|-------------------|
| `data=ordered` (по умолчанию) | только метаданные; данные записываются до метаданных | возможна потеря последних записанных данных при сбое | высокая |
| `data=writeback` | только метаданные; порядок записи не гарантируется | риск разрушения уже существующих данных при сбое | максимальная |
| `data=journal` | и метаданные, и данные (полное журналирование) | минимальный, но наибольшее изнашивание накопителя | низкая |

В SOC‑расследованиях особый интерес представляют журнальные транзакции: они фиксируют в хронологическом порядке записи об изменении метаданных (например, создание файла, модификация прав). При наличии доступа к дисковому образу можно восстановить недавно удалённые файлы или атрибуты, извлекая старые копии инодов из журнала.

### Виртуальные файловые системы

Помимо дисковых, Linux активно использует виртуальные ФС, не имеющие физического носителя. Они предоставляют интерфейс к данным ядра и процессов, что критично для мониторинга и реагирования.

- **procfs** (`/proc`) — иерархия на основе struct proc; каждый процесс представлен каталогом `/proc/<PID>`, внутри которого файлы `cmdline`, `environ`, `fd/`, `exe`, `maps`, `stack`, `status` и т.д. Чтение этих файлов даёт оперативную информацию без модификации памяти процесса. SOC‑аналитик может сравнить `/proc/<PID>/exe` с ожидаемым исполняемым файлом, чтобы выявить подлог.
- **sysfs** (`/sys`) — представление объектов ядра (устройств, модулей), параметров и состояния. Через `/sys/kernel/security/` доступны текущие настройки модуля безопасности SELinux, AppArmor.
- **tmpfs** — временная ФС в ОЗУ, часто используемая для `/tmp`, `/run`. При перезагрузке содержимое теряется, но во время работы системы анализ артефактов в `/run` может выявить временные файлы вредоносного ПО до их очистки.
- **devtmpfs** — управление файлами устройств в `/dev`.

Понимание этих механизмов позволяет аналитику эффективно собирать «живые» данные.

## Структура каталогов: стандарт FHS

Файловая иерархия Linux определяется стандартом **Filesystem Hierarchy Standard (FHS)**, последняя версия 3.0 выпущена Linux Foundation и поддерживается FreeDesktop. Цель FHS — обеспечить совместимость между дистрибутивами и предсказуемость расположения исполняемых файлов, конфигураций и данных, что упрощает автоматизацию, разработку и инцидент-реагирование. Большинство дистрибутивов (Debian, Ubuntu, Fedora, RHEL, SUSE) следуют FHS с незначительными вариациями.

**Обязательные каталоги корневого уровня** (присутствуют во всех FHS‑совместимых системах):

| Каталог | Назначение | Важные для SOC‑аналитика элементы |
|---------|-----------|-----------------------------------|
| `/bin` | Основные исполняемые файлы для всех пользователей (в большинстве современных дистрибутивов — символическая ссылка на `/usr/bin` в рамках usr‑merge) | `/bin/sh`, `/bin/cat`, `/bin/ls`; утилиты восстановления системы |
| `/boot` | Статические файлы загрузчика и ядра (vmlinuz, initrd, grub) | `/boot/grub/grub.cfg` — конфигурация загрузчика, цель для руткитов; `/boot/efi/` — EFI‑раздел с подписанными загрузчиками |
| `/dev` | Файлы устройств (блочные и символьные) | `/dev/sda` — диск, `/dev/mem` — физическая память, `/dev/null`; аномальные устройства могут указывать на скрытые тома |
| `/etc` | Системные конфигурационные файлы (статическая информация) | `/etc/passwd`, `/etc/shadow`, `/etc/group`, `/etc/sudoers`, `/etc/ssh/sshd_config`, `/etc/crontab`, `/etc/systemd/`; несанкционированные изменения здесь — признак компрометации |
| `/lib` | Основные разделяемые библиотеки (в usr‑merge → `/usr/lib`) | `/lib/modules/` — модули ядра; /lib/systemd/ — критично для загрузки |
| `/media` | Точки автоматического монтирования сменных носителей | Мониторинг появления неизвестных устройств / возможный вектор атаки через USB |
| `/mnt` | Точки временного ручного монтирования | Часто используется при подключении образов для форензики; нестандартные точки монтирования могут скрывать вредоносные файловые системы |
| `/opt` | Дополнительное программное обеспечение (пакеты, не входящие в дистрибутив) | Вредоносные программы иногда устанавливаются в `/opt/` с собственными именами; проверка целостности важна |
| `/run` | Данные времени выполнения (PID‑файлы, сокеты, блокировки); tmpfs, очищается при перезагрузке | `/run/utmp` — сеансы пользователей, `/run/systemd/` — состояние systemd; временные артефакты атакующих |
| `/sbin` | Системные утилиты администрирования (usr‑merge → `/usr/sbin`) | `fsck`, `init`, `ifconfig`, `iptables`; часто требуют прав root, цель для замены бэкдорами |
| `/srv` | Данные, предоставляемые системой как сервис (веб‑серверы, FTP) | `srv/http/`, `/srv/ftp/`; размещение веб‑шеллов |
| `/sys` | Виртуальная ФС (sysfs) с параметрами ядра и устройств | `/sys/kernel/security/`, `/sys/devices/` — состояние модулей безопасности; информация о подключённых устройствах |
| `/tmp` | Временные файлы для всех пользователей; sticky bit | `/tmp/sql-*`, `/tmp/.X11-unix/`; злоумышленники часто используют `/tmp` для скриптов и исполняемых файлов; анализ оставленных фрагментов |
| `/usr` | Вторичная иерархия для данных, доступных только для чтения (read-only) | `/usr/bin`, `/usr/sbin`, `/usr/share`, `/usr/local/` — основная масса приложений; `/usr/bin/passwd` SUID‑файл для смены пароля |
| `/var` | Изменяемые данные: логи, очереди, кеши, временные файлы, сохраняемые между перезагрузками | `/var/log/` — все системные журналы (`auth.log`, `syslog`, `kern.log`); `/var/spool/cron/` — задания cron; `/var/tmp/` — временные файлы с длительным сроком жизни |

**Опциональные каталоги** (могут отсутствовать, если компонент не установлен):

- `/root` — домашний каталог суперпользователя root; расположен вне `/home` для обеспечения доступности при монтировании `/home` с сетевого хранилища.
- `/home` — домашние каталоги обычных пользователей; может быть отдельным разделом.
- `/proc` — виртуальная procfs; становится доступной только при смонтированной procfs (монтируется на ранних стадиях загрузки автоматически).

**Важное уточнение**: `/root` и `/` — разные понятия. `/root` — это домашний каталог суперпользователя, а `/` — корень всей файловой системы. Попытка записать в `/` без root‑прав приведет к ошибке доступа, так как владельцем является root и права `755`.

### Влияние usr‑merge

С конца 2010‑х годов большинство дистрибутивов перешли на **usr‑merge**: содержимое `/bin`, `/sbin` и `/lib` перенесено в соответствующие директории внутри `/usr`, а на прежних местах созданы символические ссылки для совместимости. Это упрощает создание read‑only корневого раздела и облегчает атомарные обновления. Для SOC‑аналитика это означает, что анализируя аномальные бинарники в `/bin`, нужно проверять их реальное расположение (например, через `ls -la /bin`), чтобы не пропустить подмену в `/usr/bin`.

### Принципы разграничения уровней

FHS проектирует иерархию так, чтобы отделить:
- **статические** файлы (исполняемые, библиотеки, конфигурации) от **динамических** (логи, очереди, временные данные) — `/usr` и `/var` соответственно;
- **общие для всех систем** (shareable) `/usr/share` от **локальных хостовых** (`/etc`);
- **изолированные** прикладные пакеты (`/opt`).

С точки зрения безопасности это облегчает применение политик неизменности и мониторинг изменения критических областей. Например, `tmp` и `var/tmp` очищаются по расписанию, но `/var/tmp` сохраняет данные дольше, что может быть использовано атакующим для персистентности.

## Применение и работа с файловой системой и каталогами: навигация, монтирование и анализ

Для специалиста SOC L1 практические навыки работы с файловой системой сводятся к трём категориям: навигация и идентификация аномалий, управление монтированием и сбор артефактов. Ниже приводятся ключевые команды и их интерпретация.

### Навигация и исследование каталогов

`ls` — основная утилита вывода содержимого; флаг `-l` выдаёт детальную строку с типом, правами, владельцем, размером и временем. Флаг `-a` показывает скрытые файлы (начинающиеся с точки), флаг `-i` выводит номера инодов. Для анализа директории с большим количеством файлов рекомендуется `ls -la --time-style=long-iso`.

Определение типа файла и его метаданных:
```bash
ls -la /etc/passwd
-rw-r--r-- 1 root root 3120 Feb 27 10:23 /etc/passwd
stat /etc/shadow
  File: /etc/shadow
  Size: 1344      	Blocks: 8          IO Block: 4096   regular file
Device: 8,2	Inode: 130574      Links: 1
Access: (0640/-rw-r-----)  Uid: (0/    root)   Gid: (42/ shadow)
Access: 2025-02-27 10:23:33.887499557 +0300
Modify: 2025-02-27 10:23:33.887499557 +0300
Change: 2025-02-27 10:23:33.887499557 +0300
 Birth: 2025-02-27 10:23:33.887499557 +0300
```
SOC‑аналитик обращает внимание на время изменения (mtime) файлов конфигурации — недавняя модификация может указывать на вторжение. Команда `find` с фильтрами по времени: `find /etc -mtime -1 -type f` выведет файлы, изменённые за последние сутки.

### Поиск по атрибутам и правам

Для обнаружения потенциально опасных SUID/SGID файлов (исполняемых с повышенными привилегиями) используют:
```bash
find / -perm -4000 -type f -exec ls -la {} \; 2>/dev/null
find / -perm -2000 -type f -exec ls -la {} \; 2>/dev/null
```
Типичные легитимные SUID‑файлы: `/usr/bin/passwd`, `/usr/bin/sudo`, `/usr/bin/pkexec`. Появление новых SUID‑бинарников — классический признак локального повышения привилегий или бэкдора.

Поиск файлов, принадлежащих отсутствующим в системе пользователям (числовой UID без записи в `/etc/passwd`), выявляет артефакты после удаления учётной записи злоумышленника или ошибки конфигурации:
```bash
find / -nouser -o -nogroup 2>/dev/null
```

### Монтирование и контроль точек подключения

Команда `mount` без параметров отображает все смонтированные файловые системы. Особое внимание уделяется типам файловых систем: присутствие `tmpfs` в нестандартных местах, подозрительные `overlay`, `fuse` или монтирование с опцией `noexec` на разделах, где этого не должно быть (например, /tmp без noexec — риск исполнения вредоносного кода). Проверка точек монтирования:
```bash
mount | column -t
```
Пример вывода (схематично):
```
sysfs       on  /sys         type  sysfs       (rw,nosuid,nodev,noexec,relatime)
proc        on  /proc        type  proc        (rw,nosuid,nodev,noexec,relatime)
/dev/sda1   on  /            type  ext4        (rw,relatime,errors=remount-ro)
/dev/sda2   on  /boot        type  ext4        (rw,relatime)
/dev/sdb1   on  /mnt/data    type  ntfs-3g     (rw,relatime,uid=1000,gid=1000)
```
Аналитик должен убедиться, что к ключевым разделам не добавлена опция `user` (разрешающая монтирование обычному пользователю), которая может быть использована для атаки.

Для просмотра использования дискового пространства, что может сигнализировать о заполнении логов или скрытых файлах большого объёма, применяется `df -h` и `du -sh` по конкретному каталогу:
```bash
df -h /
du -sh /var/log
```

### Сбор информации о процессах через procfs

В `/proc/<PID>/` содержится срез состояния процесса. Базовый способ выявить аномальные процессы — перебрать все PID и сопоставить команды с исполняемыми файлами:
```bash
for pid in /proc/*/; do
    cmdline=$(cat $pid/cmdline 2>/dev/null | tr '\0' ' ')
    exe=$(readlink -f $pid/exe 2>/dev/null)
    [ -n "$exe" ] && echo "PID ${pid##*/} EXE: $exe CMD: $cmdline"
done
```
Если `exe` помечен как `(deleted)`, это означает, что исполняемый файл был удалён после запуска процесса — классический приём для скрытия вредоносного кода. Также проверяются переменные окружения через `cat /proc/<PID>/environ` для поиска внедрённых библиотек.

### Работа с логами в `/var/log`

Центральное место для сбора улик. Аналитик использует утилиты `grep`, `journalctl` (для систем с systemd) для фильтрации событий, связанных с аутентификацией, ошибками доступа, модификацией учётных записей:
```bash
grep "Failed password" /var/log/auth.log
grep "sudo: pam_unix" /var/log/auth.log
journalctl --since "2025-02-27 10:00:00" --until "2025-02-27 11:00:00" -u sshd
```
Важно отслеживать изменение самих логов: время модификации файла лога, его размер (внезапное уменьшение — признак ротации или очистки атакующим). Рекомендуется проверять права доступа: `/var/log/auth.log` должен быть доступен только для чтения группе adm или root (в зависимости от дистрибутива).

## Сквозной практический пример: SOC‑анализ подозрительной активности на Linux-сервере

**Исходные условия**: SOC‑аналитик уровня L1 получает алерт от системы мониторинга о повышенной нагрузке на CPU и многократных неудачных попытках входа по SSH на веб-сервер под управлением Ubuntu 22.04. Аналитик подключается к хосту через SSH с правами непривилегированного пользователя, которому разрешён `sudo` для чтения критичных файлов.

**Шаг 1: Первичный осмотр недавних изменений в системных конфигурациях.**  
Выполняется поиск файлов, изменённых за последние 24 часа в `/etc`.
```bash
sudo find /etc -mtime -1 -type f -exec ls -la {} \;
```
Ожидаемый вывод: список файлов с временными метками. Аналитик видит недавнюю модификацию `/etc/ssh/sshd_config` и `/etc/sudoers`. Это ненормально, так как изменения в конфигурации SSH без планового обслуживания не производятся.

**Шаг 2: Проверка несанкционированных записей в sudoers и аномальных SUID-файлов.**  
Команда для поиска файлов с установленным SUID-битом, не являющихся стандартными:
```bash
sudo find / -perm -4000 -type f -exec ls -la {} \; 2>/dev/null | grep -v "^.* \/usr\/lib\/openssh\/ssh-keysign$\|^.* \/usr\/bin\/passwd$\|^.* \/usr\/bin\/sudo$\|^.* \/usr\/bin\/pkexec$"
```
(символ `\|` означает экранированный pipe; в реальной команде используется `egrep` с регулярным выражением). В результатах обнаруживается `/tmp/.hidden/bd` (произвольное имя), исполняемый файл с SUID. Это нетипичное расположение SUID‑бинарника явно указывает на бэкдор.

**Шаг 3: Анализ запущенных процессов и поиск процесса, связанного с подозрительным бинарником.**  
Перебор `/proc` для поиска запущенного файла, помеченного `(deleted)`:
```bash
for dir in /proc/*/; do
    exe=$(sudo readlink -f $dir/exe 2>/dev/null)
    if echo "$exe" | grep -q "deleted"; then
        pid=$(basename $dir)
        cmdline=$(sudo cat $dir/cmdline 2>/dev/null | tr '\0' ' ')
        echo "PID $pid: $exe -> $cmdline"
    fi
done
```
Выводится PID процесса, чей исполняемый файл удалён. Далее проверяется его сетевое взаимодействие с помощью `sudo ls -la /proc/$pid/fd` — обнаруживается открытый сокет к внешнему IP.

**Шаг 4: Исследование логов аутентификации на предмет несанкционированного входа.**  
Команда для извлечения всех событий неудачных и успешных попыток входа:
```bash
sudo grep -E "Failed|Accepted" /var/log/auth.log | tail -30
```
Аналитик видит множество попыток с различными именами пользователей, а также успешный вход для пользователя `user` с IP, не принадлежащего корпоративной сети.

**Ожидаемый вывод примера:**  
В результате этих шагов SOC‑аналитик фиксирует:
- несанкционированное изменение `/etc/sudoers`;
- присутствие вредоносного SUID-файла в `/tmp/.hidden/`;
- процесс с удалённым исполняемым файлом, открытым сетевым сокетом;
- подозрительную аутентификацию в `auth.log`.

Эти артефакты позволяют классифицировать инцидент как успешную компрометацию с установкой бэкдора и эскалацией привилегий. Последующая эскалация до L2 инициирует процедуру сбора дампа памяти и дискового образа для полного форензического анализа. Данный пример демонстрирует практическое применение знаний о файловой системе и структуре каталогов в работе специалиста по кибербезопасности.
