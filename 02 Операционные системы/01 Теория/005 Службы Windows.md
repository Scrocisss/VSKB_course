# Службы Windows: обзор для специалиста SOC L1

## 1. Службы Windows в экосистеме операционной системы и безопасности

Служба Windows (Windows service) — это особый тип исполняемого модуля, управляемый диспетчером управления службами (Service Control Manager, SCM). Она стартует до входа пользователя, работает в фоновом режиме и не требует интерактивного сеанса — за исключением короткого переходного периода в сессии 0, изолированной с Windows Vista/Server 2008. Службы реализуют ключевую функциональность ОС: сетевые сервисы (DNS-клиент, DHCP, брандмауэр), планировщики, агенты обновлений, компоненты безопасности (Windows Defender, Credential Guard). Для специалиста SOC первого уровня критично понимать, что любая служба — это потенциальный вектор выполнения кода с высокими привилегиями, и злоумышленники активно эксплуатируют механизм служб для закрепления (persistence), эскалации привилегий (privilege escalation) и обхода средств контроля запуска приложений.

Фундаментальное свойство службы, отличающее её от обычного пользовательского процесса, — регистрация в базе SCM. Процесс становится службой только после того, как его параметры зафиксированы в реестре в ключе `HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>`. До регистрации он — просто исполняемый файл, запущенный любым способом. Это разграничение необходимо удерживать при анализе инцидентов: детектирование вредоносной активности часто опирается на факт создания нового ключа реестра с параметрами запуска службы, а не просто на появление нового процесса.

Второй важный аспект — изоляция сеансов. Все службы, не помеченные как интерактивные, выполняются в сеансе 0, полностью отделённом от консольного сеанса пользователя. Интерактивное взаимодействие (окна, диалоги) из службы в сеансе 0 подавлено. Это значит, что легитимная служба не должна показывать окна или ожидать ввода с клавиатуры пользователя, что можно использовать как дополнительный индикатор аномалии.

### 1.1 Отличие служб от смежных компонентов автозагрузки

Ошибкой начинающего аналитика является отождествление служб с другими механизмами автоматического запуска: запланированными заданиями (Task Scheduler), драйверами, элементами реестра `Run`/`RunOnce`. Хотя все они могут обеспечить персистентность, архитектурные различия существенны для расследования.

| Компонент | Способ запуска и управление | Привилегии и контекст | Типичные артефакты мониторинга |
|-----------|----------------------------|-----------------------|--------------------------------|
| **Служба Windows** | SCM запускает по триггерам (авто, ручной, отложенный); состояние отслеживается SCM, возможен перезапуск при сбое. | Определяются учётной записью, под которой сконфигурирована служба (LocalSystem, NetworkService, конкретный пользователь). | Ключ реестра `HKLM\SYSTEM\CurrentControlSet\Services\...`, Event ID 7045 (System log) или 4697 (Security log). |
| **Драйвер устройства** | Загружается ядром или PnP-менеджером на этапе загрузки системы; не подчиняется SCM. | Исполняется в ядерном режиме (kernel mode), наивысшие привилегии. | Записи в `Services` с типом `SERVICE_KERNEL_DRIVER`, проверка подписи, блокировка уязвимых драйверов (Microsoft vulnerable driver blocklist [Windows security documentation](https://learn.microsoft.com/en-us/windows/security)). |
| **Запланированное задание** | Планировщик задач (`taskschd.msc`, `schtasks.exe`); запускается по расписанию или событию. | Контекст запуска определяется в задании (SYSTEM, пользователь, группа). Не управляется через SCM. | Файлы заданий в `C:\Windows\System32\Tasks` или `C:\Windows\Tasks`; Event ID 106/140/141 (Microsoft-Windows-TaskScheduler). |
| **Элементы Run/RunOnce (Winlogon)** | Запускаются при входе пользователя или загрузке системы через ключи реестра `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`. | Обычно контекст пользователя, выполнившего вход, или SYSTEM для машинных ключей. | Соответствующие ключи реестра; Event ID не генерируется напрямую. |

### 1.2 Почему службы — цель злоумышленников

Службы привлекательны для атакующих по нескольким причинам:

- **Высокий уровень привилегий.** Локальная система (NT AUTHORITY\SYSTEM) — это наивысшая учётная запись локальной машины, превосходящая даже администратора. Запуск вредоносной службы с такими правами даёт практически неограниченный контроль над ОС.
- **Ранний старт.** Службы с типом запуска «Авто» стартуют до входа пользователя и работают постоянно, позволяя вредоносному коду переживать перезагрузки.
- **Скрытность.** Процессы, запущенные как службы, часто не видны пользователю через Диспетчер задач в стандартном представлении (особенно группированные в svchost.exe). Атакующий может маскировать вредоносную нагрузку под легитимную службу.
- **Обход контроля учётных записей (UAC).** Локальные администраторы могут создавать и запускать службы, при этом сама служба, стартуя от имени SYSTEM, не подвержена UAC-проверкам. Техники типа T1543.003 (Windows Service) описаны в MITRE ATT&CK как стандартный способ персистентности.

Согласно лучшим практикам усиления безопасности Windows-серверов, сокращение поверхности атаки требует удаления или отключения неиспользуемых ролей, компонентов и служб, таких как Telnet или устаревший протокол SMBv1 [Windows Server Security Best Practices](https://www.linkedin.com/posts/reshmith-raveendran-5716001a_windows-server-security-best-practices-activity-7373378254407188480-8sNV). Установка Server Core (без графического интерфейса) дополнительно минимизирует количество запущенных служб и потенциальных векторов атаки.

## 2. Внутренняя архитектура и конфигурация служб

### 2.1 Service Control Manager и база данных служб

Диспетчер управления службами — это процесс `services.exe`, стартующий на ранних этапах загрузки. Он читает конфигурацию служб из реестра и управляет их жизненным циклом: запуск, остановка, приостановка, обработка управляющих запросов от клиентов (например, оснастки `services.msc` или утилиты `sc.exe`). Взаимодействие с SCM происходит через RPC, а для локального администрирования — через Win32 API (`OpenSCManager`, `CreateService`, `StartService`, `ControlService`).

База данных служб хранится в ветви реестра `HKLM\SYSTEM\CurrentControlSet\Services`. Каждая служба представлена вложенным ключом, внутри которого обязательными являются значения:

- `ImagePath` — путь к исполняемому файлу или DLL (для svchost-группировки указывает `svchost.exe -k <group>`).
- `Type` — тип службы (например, `0x10` — Win32-процесс в собственном процессе; `0x20` — Win32-процесс, который разделяет процесс с другими службами).
- `Start` — тип запуска (числовое значение).
- `ErrorControl` — действие при сбое запуска (нормальное, серьёзное, критическое).
- `ObjectName` — учётная запись, под которой работает служба (если `LocalSystem`, указывается `LocalSystem`).

Для служб, сгруппированных в общий хост-процесс, дополнительно задаётся значение `ServiceDll` в подключе `Parameters`, указывающее на DLL, реализующую логику службы.

### 2.2 Типы запуска и их числовые значения

Параметр `Start` определяет, когда и как SCM запускает службу. В SOC-анализе знание кодов помогает вручную интерпретировать содержимое реестра или сырые логи конфигурации.

| Тип запуска | Значение `Start` | Описание | Примеры (легитимные) | Примечание для расследования |
|-------------|------------------|----------|----------------------|------------------------------|
| Boot Start | 0 | Загружается загрузчиком ОС до инициализации ядра | Драйверы файловой системы, дисковые фильтры | Присутствует только у драйверов. |
| System Start | 1 | Инициализируется во время загрузки ядра | Драйверы сетевых адаптеров, TPM-драйвер | Аналогично, только драйверы. |
| Automatic | 2 | Запускается SCM автоматически при старте системы | DHCP Client, Windows Event Log, антивирус | Самый вероятный выбор атакующего для персистентности. |
| Manual | 3 | Запускается по требованию (триггер, другое приложение) | Windows Update, Software Protection | Может быть запущена вручную после перезагрузки злоумышленником. |
| Disabled | 4 | Не может быть запущена | Telnet, устаревшие службы | Отключённые службы могут быть включены в ходе атаки, после чего будет создано событие 7045. |
| Automatic (Delayed Start) | 2 + параметр `DelayedAutostart`=1 | Запускается автоматически, но с задержкой после загрузки всех авто-служб | Windows Search, Windows Defender Antivirus Network Inspection Service | Аналитик может заметить по времени запуска относительно загрузки системы. |

Атакующие часто устанавливают службу с `Start=2`, чтобы она перезапускалась после перезагрузки. Вредоносный код также может модифицировать существующую легитимную службу, изменив `ImagePath` на свою полезную нагрузку (техника T1574.011 – Services Registry Permissions Weakness), сохраняя оригинальное имя и Type.

### 2.3 Учётные записи и модель безопасности служб

Значение `ObjectName` определяет контекст безопасности процесса службы. Аналитик должен идентифицировать аномалию, если, например, служба, традиционно работающая от имени Network Service, запущена как LocalSystem.

**Основные встроенные учётные записи:**

- **LocalSystem (NT AUTHORITY\SYSTEM).** Полный доступ к локальной машине, не имеет сетевого доступа за пределами машины (если не делегированы учётные данные машины в домене). Вредоносные службы почти всегда используют эту учётную запись.
- **LocalService (NT AUTHORITY\LocalService).** Минимальные привилегии, локальный доступ, сетевое взаимодействие с аутентификацией как анонимный пользователь.
- **NetworkService (NT AUTHORITY\NetworkService).** Как LocalService, но сетевые запросы выполняются с учётными данными компьютера.

Злоумышленник, получив права локального администратора, может создать службу с произвольной учётной записью, включая SYSTEM, потому что право `SeServiceLogonRight` по умолчанию есть у группы Администраторы и Локальная система. Если в организации настроен аудит прав, событие 4672 (Special Logon) для входа службы может указать, какой именно пользователь создал службу.

### 2.4 Группировка служб в svchost.exe

Для снижения потребления ресурсов множество системных служб работает внутри общих хост-процессов `svchost.exe`. Каждая группа определяется строковым идентификатором (например, `netsvcs`, `LocalServiceAndNoImpersonation`). Запуск происходит через `svchost.exe -k <group>`, а конфигурация службы указывает `ServiceDll` в реестре.

С точки зрения SOC-аналитика, это создаёт сложность: вредоносный код может быть загружен как DLL в легитимный `svchost.exe`, если злоумышленник изменит параметры существующей службы или создаст новую с подходящей группой. Поэтому анализ только имени процесса (просто `svchost.exe`) недостаточен — необходимо проверять фактические загруженные библиотеки и параметры командной строки.

Иллюстративная структура ключа реестра для службы, сгруппированной в svchost:

```text
HKLM\SYSTEM\CurrentControlSet\Services\W32Time
  Type                 = 0x20 (разделяет процесс)
  Start                = 2 (автоматический)
  ErrorControl         = 0x1 (нормальный)
  ImagePath            = "%systemroot%\system32\svchost.exe -k LocalService"
  ObjectName           = "NT AUTHORITY\LocalService"
  DisplayName          = "Windows Time"
  Parameters
    ServiceDll         = "%systemroot%\system32\w32time.dll"
```

Изменения любого из этих полей (особенно `ImagePath` или `ServiceDll`) должны немедленно вызывать инцидент.

## 3. Мониторинг, аудит и работа со службами для аналитика L1

### 3.1 Инструментарий аналитика первого уровня

В распоряжении специалиста SOC L1 обычно находятся консоль SIEM, средство удалённого выполнения команд (через EDR или WinRM) и, возможно, административный доступ к отдельным хостам для сбора данных. Ключевые инструменты для работы со службами:

- **`sc.exe query` / `sc.exe qc`** — командная строка для просмотра конфигурации и состояния конкретной службы.
- **PowerShell cmdlet'ы:** `Get-Service`, `Get-WmiObject -Class Win32_Service` или `Get-CimInstance -ClassName Win32_Service`. Предпочтительны для удалённого сбора, так как позволяют получать подробный список с `Select-Object *`.
- **`services.msc`** — графическая оснастка для быстрого визуального осмотра на месте инцидента.
- **Sysinternals Autoruns** — комплексный анализатор автозагрузки, показывающий все точки входа (включая службы) с проверкой цифровых подписей и вычислением хэшей.

В SIEM-системах, таких как Splunk или Sentinel, данные о службах поступают из стандартных журналов Windows, от EDR-агентов и, возможно, из событий PowerShell.

### 3.2 Ключевые события и их интерпретация

Мониторинг служб базируется на регистрации событий создания и изменения состояния. В SOC наиболее распространены следующие ID событий.

**Создание новой службы (Event ID 7045)** — регистрируется в журнале **System** при успешном добавлении службы через SCM (например, `CreateService` WinAPI). Это основной индикатор, на который строятся правила корреляции. Пример фрагмента лога в формате, близком к тому, что поступает в SIEM (иллюстративная схема):

```json
{
  "EventID": 7045,
  "Provider": {
    "Name": "Service Control Manager"
  },
  "TimeCreated": "2026-01-15T09:23:12.4321123Z",
  "EventData": {
    "ServiceName": "UpdaterHelper",
    "ImagePath": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\update.exe"
  }
}
```

Аналитик, видя `ImagePath` во временной папке пользователя, немедленно эскалирует.

**Установка службы через SCM (Event ID 4697)** — записывается в журнал **Security**, если включён аудит (Audit Policy → Security System Extension). Событие содержит имя субъекта, создавшего службу, что критически важно для определения учётной записи, инициировавшей атаку. Включение этого аудита — одна из рекомендаций раздела о мониторинге в руководстве по безопасности Windows [Falcongaze: Защита Windows](https://falcongaze.com/ru/pressroom/publications/texnologii/operacionnye-sistemy/what-windows-security-includes.html).

**Изменение состояния службы (Event ID 7034, 7036)** — в журнале System. ID 7034 указывает на неожиданное завершение службы, что может свидетельствовать о сбоях, вызванных вредоносной активностью. ID 7036 — на обычную смену состояния (остановлена/запущена). Эти события часто используются для профилирования нормального поведения и выявления отклонений.

#### Запросы для SIEM (концептуальные примеры)

Базовый поиск подозрительных путей в событиях 7045 за последние 24 часа на языке, подобном Kusto (Azure Sentinel) или SPL (Splunk), может выглядеть так:

```kql
Event
| where EventID == 7045
| where TimeGenerated > ago(24h)
| extend ImagePath = tostring(EventData.ImagePath)
| where ImagePath matches regex @"(?i)(C:\\\\Users|\\\\AppData\\\\Local\\\\Temp|\\\\Windows\\\\Temp)"
| project TimeGenerated, Computer, ServiceName, ImagePath
```

Или для Splunk:

```spl
index=windows source="WinEventLog:System" EventCode=7045
| rex field=Message "ImagePath:\s+(?<ImagePath>.+)"
| where ImagePath LIKE "%C:\\Users%" OR ImagePath LIKE "%Temp%"
| table _time, host, ServiceName, ImagePath
```

При проверке конкретного хоста аналитик может выполнить через PowerShell:

```powershell
Get-CimInstance Win32_Service |
    Where-Object { $_.StartName -eq "LocalSystem" -and $_.PathName -match 'C:\\\\Users' } |
    Select-Object Name, DisplayName, PathName, StartName, State
```

Вывод должен быть пустым или указывать на исключения, которые известны админу.

### 3.3 Типовые аномалии и индикаторы компрометации (IoC)

При анализе служб SOC L1 ориентируется на следующие подозрительные признаки:

- **Бинарный путь (ImagePath) в пользовательских директориях:** `C:\Users\*`, `C:\ProgramData\*` (если не установлено ПО, использующее эти пути). Исключения — легитимные приложения типа Google Chrome Elevation Service (проверяются по подписи).
- **Использование интерпретаторов и хост-процессов:** командная строка службы, включающая `powershell.exe`, `cmd.exe`, `wscript.exe`, `mshta.exe`, `rundll32.exe`. Например, `ImagePath: %COMSPEC% /c ...` — крайне нетипично для легитимной службы.
- **Случайные или имитирующие легитимные имена службы:** злоумышленники могут использовать названия с опечатками (`WinDefend` вместо `WinDefend`), двойными пробелами или явно бессмысленные строки. Маскировка под существующую службу Windows — частый приём.
- **Изменение типа запуска легитимной службы с Disabled на Automatic** без планового окна обслуживания. Такое изменение фиксируется аудитом реестра (Event ID 4657 с путём к ключу `Services\<имя>\Start`).
- **Отсутствие цифровой подписи у бинарного файла службы** при том, что большинство служб Microsoft и легитимного стороннего ПО подписаны.

Дополнительным источником информации служит процесс загрузки библиотек. EDR-решения могут показывать, что процесс службы загружает нестандартные DLL, например, из каталогов профиля пользователя.

### 3.4 Базовые практики усиления безопасности служб

Хотя первоочередная задача L1 — обнаружение, полезно знать профилактические меры, чтобы отличить штатную настройку от подозрительной.

Следуя лучшим практикам, администраторы:

- Отключают неиспользуемые службы (Telnet, SMBv1, устаревшие помощники) [Windows Server Security Best Practices](https://www.linkedin.com/posts/reshmith-raveendran-5716001a_windows-server-security-best-practices-activity-7373378254407188480-8sNV).
- Применяют роль «Server Core» там, где это возможно, сокращая поверхность атаки.
- Используют групповые политики для управления разрешениями на службы (с помощью `sc sdset` или GPO Restricted Groups для служб с учётными записями).
- Настроят аудит событий безопасности согласно Microsoft Security Baselines, который включает аудит создания служб (Security System Extension) и изменений в реестре.
- Периодически проводят инвентаризацию служб с использованием инструментов типа `Autoruns` и сравнение с эталонным образом.

В Windows 11 доступны новые механизмы контроля приложений (Smart App Control), однако они не подменяют мониторинг служб, поскольку злоумышленники могут эксплуатировать легитимно подписанные исполняемые файлы с вредоносными аргументами [Windows security documentation](https://learn.microsoft.com/en-us/windows/security).

## 4. Сквозной практический пример: обнаружение вредоносной службы

### Исходные условия

ОС: Windows 10 Enterprise 22H2, управление через Microsoft Defender for Endpoint, SIEM: Azure Sentinel.  
Роль аналитика: специалист SOC L1, первичная сортировка алертов.  
Сценарий: сработало аналитическое правило «New Service Created from User Temporary Folder» на основе события 7045.

### Шаг 1: Анализ алерта SIEM

Аналитик видит инцидент: на хосте `WKSTN-JDOE` создана служба `SystemUpdateService` с путём `C:\Users\jdoe\AppData\Local\Temp\svchost.exe`. Алерт сопровождается выдержкой из события.

```json
{
  "IncidentId": "INC-9218",
  "AlertName": "Suspicious service creation from Temp folder",
  "Computer": "WKSTN-JDOE.fabrikam.local",
  "EventID": 7045,
  "ServiceName": "SystemUpdateService",
  "ImagePath": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\svchost.exe",
  "TimeGenerated": "2026-03-14T11:45:22Z"
}
```

Аналитик подтверждает, что зафиксировано нестандартное расположение исполняемого файла, имя файла совпадает с легитимной системной утилитой, но путь явно не системный. Это первый признак компрометации.

### Шаг 2: Удалённая проверка конфигурации службы

Аналитик запускает PowerShell-команду через MDE live response для получения детальной информации:

```powershell
Get-CimInstance Win32_Service -Filter "Name = 'SystemUpdateService'" |
    Select-Object Name, DisplayName, PathName, StartMode, StartName, ProcessId
```

Ожидаемый вывод (иллюстративная схема):

```text
Name               : SystemUpdateService
DisplayName        : System Update Manager
PathName           : C:\Users\jdoe\AppData\Local\Temp\svchost.exe
StartMode          : Auto
StartName          : LocalSystem
ProcessId          : 0
```

Видно, что служба настроена на автозапуск и работает от имени `LocalSystem` (высшие привилегии). Отсутствие `ProcessId` (0) может означать, что служба ещё не стартовала, либо была остановлена, но конфигурация персистентна.

### Шаг 3: Сопоставление с процессами и автозагрузкой

Для выявления работающих экземпляров аналитик проверяет текущие процессы, используя ту же удалённую сессию:

```powershell
Get-Process | Where-Object { $_.Path -eq 'C:\Users\jdoe\AppData\Local\Temp\svchost.exe' } |
    Select-Object Id, Name, StartTime, Threads
```

Если процесс существует, вывод может быть:

```text
   Id Name       StartTime            Threads
   -- ----       ---------            -------
 4872 svchost    14.03.2026 11:44:15       5
```

Далее аналитик запускает утилиту Sysinternals `autorunsc.exe` (через EDR) с фильтром по имени службы:

```bash
autorunsc.exe -s | findstr /i "SystemUpdateService"
```

Выводится запись, подтверждающая, что этот элемент присутствует в автозагрузке, с тем же путём и без цифровой подписи (отсутствует издатель).

### Шаг 4: Подтверждение угрозы и эскалация

Совокупность признаков (путь в пользовательской временной папке, запуск от имени SYSTEM, отсутствие легитимной подписи, имитация имени системного процесса) позволяет с высокой уверенностью классифицировать инцидент как установку вредоносной службы — вероятно, для закрепления после эксплуатации. Аналитик L1 эскалирует инцидент на уровень L2 с приложением всех собранных артефактов и предлагает немедленную изоляцию хоста от сети.

### Ожидаемый вывод

Пример демонстрирует, как последовательный анализ одного события (7045) с дополнительным контекстом о конфигурации и процессе приводит к быстрой идентификации попытки персистентности. Для L1 важно не только фиксировать аномалию, но и дополнять её данными из других источников (реестр, процессы), чтобы сократить время реакции и обосновать эскалацию.
