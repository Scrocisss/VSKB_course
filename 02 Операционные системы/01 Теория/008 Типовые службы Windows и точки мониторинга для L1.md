# Типовые службы Windows и точки мониторинга для L1

## 1. Службы Windows как объект мониторинга: базовые понятия и роль в SOC

Служба Windows (Windows Service) — это процесс, выполняющийся в фоновом режиме, не требующий интерактивного входа пользователя и управляемый диспетчером управления службами (Service Control Manager, SCM). Службы обеспечивают функционирование ключевых подсистем операционной системы: сетевого стека, журналирования, обновлений, планирования заданий, аутентификации. Именно поэтому злоумышленники регулярно обращаются к данному механизму для закрепления (persistence), повышения привилегий (privilege escalation) или выполнения вредоносного кода (execution). В матрице MITRE ATT&CK этой технике посвящена техника **T1543.003 — Create or Modify System Process: Windows Service**, а выполнение через службы описывается **T1569.002 — System Services: Service Execution**.

Для специалиста первой линии SOC (Tier 1) службы Windows — это одновременно и объект защиты, и источник сигналов тревоги. Именно аналитики L1 первыми видят алерты на подозрительное создание служб, изменение их конфигураций или нетипичные переходы состояний. Их задача — в сжатые сроки (как правило, 15–30 минут для высококритичных оповещений) распознать, является ли событие легитимной операцией администрирования или индикатором компрометации, и, в последнем случае, эскалировать инцидент на второй уровень.

Важно чётко разграничить смежные понятия, с которыми часто путают службы.

| Сущность | Определение | Отношение к службам | Пример |
|----------|------------|---------------------|--------|
| Служба Windows | Процесс, управляемый SCM, с записью в реестре `HKLM\SYSTEM\CurrentControlSet\Services` | Является объектом мониторинга | `wuauserv` — служба Windows Update |
| Драйвер устройства | Особый тип службы, работающий в режиме ядра (kernel mode) | Подмножество служб; запускается SCM, но с типом `SERVICE_KERNEL_DRIVER` | `Beep` — системный драйвер |
| Запланированная задача | Задание, запускаемое планировщиком заданий в определённое время или по триггеру | Иногда используется как альтернатива службам для persistence, но механизм управления разный | `\Microsoft\Windows\UpdateOrchestrator\Reboot` |
| Фоновый процесс | Любой процесс, работающий в фоне, не обязательно управляемый SCM | Служба является частным случаем фонового процесса с особым жизненным циклом | `notepad.exe` не является службой |
| Демон (Linux) | Аналог службы в Linux-системах, управляемый systemd или init | Функционально схож, но технически — иная подсистема | `sshd` |

Различие особенно значимо при анализе логов. Так, создание запланированной задачи регистрируется событием с Event ID 4698 в журнале безопасности, в то время как установка новой службы — событиями 7045 (System) или 4697 (Security), а модификация параметров службы — 7040 (System). Аналитик L1 обязан ориентироваться в этих идентификаторах, чтобы не тратить время на нерелевантные записи.

В контексте SOC мониторинг служб решает три основных задачи:
- **Выявление вредоносных закреплений.** Одна из наиболее распространённых целей злоумышленника — обеспечить автоматический запуск своего кода при каждой загрузке системы. Службы с типом запуска «Автоматически» (`SERVICE_AUTO_START`) предоставляют надёжное и относительно скрытное средство для этого.
- **Обнаружение повышения привилегий.** Атаки могут модифицировать существующие легитимные службы, особенно те, что запускаются с правами `LOCALSYSTEM`, подменяя исполняемый файл (ImagePath) или настройки учётной записи (техника T1574.011 — Services Registry Permissions Weakness). Такой трюк позволяет злоумышленнику выполнить полезную нагрузку с максимальными привилегиями.
- **Выявление аномального поведения.** Законные службы могут неожиданно сменить состояние или тип запуска, перестать запускаться (события 7000, 7009) или, напротив, запускаться в нерабочее время. Всё это может свидетельствовать о попытках вывести защитные механизмы из строя.

Особое внимание уделяется службам, которые поставляются с операционной системой, но при этом обладают известными уязвимостями или избыточными правами. Пример — служба `Spooler` (печать), которая неоднократно становилась вектором атак, включая знаменитую уязвимость PrintNightmare, или `WinRM` (Windows Remote Management), используемый для удалённого управления и движения в lateral movement. Для L1-аналитика такая служба, внезапно запущенная на клиентской рабочей станции, где она не должна использоваться, — немедленный сигнал к проверке контекста: кто инициировал запуск, какие сопутствующие события зафиксированы в журналах.

Таким образом, службы Windows — не просто технический компонент ОС, а одна из ключевых контрольных точек в цепочке мониторинга SOC, требующая как знания внутреннего устройства механизма, так и умения выделять значимые события из общего потока логов.

## 2. Архитектура и классификация типовых служб Windows

Чтобы осмысленно анализировать события, связанные со службами, аналитик должен понимать, как они устроены, как классифицируются и какие из них наиболее часто фигурируют в инцидентах. В данном разделе мы рассмотрим архитектурный остов подсистемы служб, дадим полную классификацию типовых служб с точки зрения SOC-мониторинга и выделим основные структурные компоненты, фигурирующие в журналах событий.

**Архитектурные компоненты и реестр**

Управление службами в Windows осуществляется Service Control Manager (SCM) — системным процессом `services.exe`, запускаемым на раннем этапе загрузки. SCM читает конфигурацию каждой службы из реестра по пути `HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>`. Каждая запись содержит критически важные параметры:

- `ImagePath` — путь к исполняемому файлу, включая аргументы командной строки.
- `Start` — DWORD, определяющий тип запуска: 0 (Boot), 1 (System), 2 (Automatic), 3 (Manual), 4 (Disabled).
- `Type` — тип службы: 0x10 (Win32 Own Process), 0x20 (Win32 Share Process, например, общий процесс `svchost.exe`), 0x01 (Kernel Driver).
- `ObjectName` — учётная запись, от которой запускается служба (чаще всего `LocalSystem`, `NT AUTHORITY\NetworkService` или `NT AUTHORITY\LocalService`).
- `ErrorControl` — поведение при сбое запуска.

При изменении любого из этих полей (особенно `ImagePath`, `Start`, `ObjectName`) возникают события, подлежащие анализу. Злоумышленник, обладающий правами администратора или нашедший слабо защищённые ветки реестра, может подменить значения и добиться запуска своего кода.

Ключевая архитектурная особенность — запуск многих системных служб внутри разделяемых процессов-хостов `svchost.exe`. Каждый такой хост группирует службы по типу учётной записи и флагу изоляции. Изменение списка служб, работающих внутри конкретного экземпляра `svchost.exe`, может быть следствием установки новой службы. Это можно отследить по событиям запуска процессов (4688, Sysmon Event ID 1), где в командной строке `svchost.exe` указывается параметр `-k <group>`, а также по событиям 7036, 7045.

**Классификация служб по назначению и рискам**

Для практической работы в SOC уместно разделить службы на несколько категорий по их функциональному назначению и степени критичности для безопасности. Ниже представлена исчерпывающая классификация с акцентом на типичные признаки мониторинга.

| Категория | Примеры служб | Назначение | Риски для SOC | Типичные события для мониторинга |
|-----------|---------------|------------|---------------|-----------------------------------|
| Базовые системные | `EventLog`, `PlugPlay`, `Power`, `RPCSS` | Основа функционирования ОС; без них система неработоспособна | Обычно не трогаются злоумышленниками, но отказ может быть симптомом деструктивных атак (wiper) | 7036 (остановка), 7000, 7009 (ошибки), 7040 (изменение типа запуска) |
| Сетевые и коммуникационные | `Dhcp`, `Dnscache`, `LanmanWorkstation`, `WinRM`, `W3SVC` (IIS) | Сетевые подключения, разрешение имён, удалённое управление, веб-сервер | Эксплуатация уязвимостей (WinRM для lateral movement), неожиданный запуск на рабочей станции | 7045 (установка), 7036 на клиентах, сетевые соединения с необычными портами |
| Службы безопасности и обновлений | `WinDefend` (Defender), `wuauserv`, `SecurityHealthService` | Антивирусная защита, обновление системы | Принудительная остановка или отключение — явный признак атаки | 7036 (остановка), 7040 (Disabled), 5001 (действия Защитника, если настроен аудит) |
| Аутентификация и авторизация | `SamSs`, `LSM`, `Netlogon` | Локальная и доменная аутентификация, безопасность учётных записей | Аномальное изменение конфигурации, перезапуск во время атаки | 7036, 7040, события 4616 (изменение контекста безопасности) |
| Службы планирования и автоматизации | `Schedule`, `BITS` | Выполнение заданий по расписанию, фоновая передача данных | Использование для загрузки вредоносных модулей, создания заданий | 7045 (неожиданные новые BITS-задачи), 4698 (новое задание) |
| Сторонние и прикладные | `MSSQLSERVER`, `teamviewer_service`, службы легитимных ПО | Поддержка приложений, удалённый доступ | Легитимный софт может быть использован как инструмент (living-off-the-land); подмена ImagePath | 7045, 7036, оригинальное имя файла, проверка цифровой подписи |

Особый подкласс — службы, созданные вредоносным ПО. Такие службы часто имеют случайно выглядящие имена (например, `bvxYgKlmQ`) или маскируются под системные с небольшими искажениями (`wuauserv` vs `wuausrv`). Аналитик L1 должен помнить о подобных приёмах и при анализе события 7045 всегда сверять имя и ImagePath со списком известных легитимных служб, поставляемых Microsoft, а также с белыми списками предприятия.

**Модель подсистемы служб: схема взаимодействия**

Для наглядного представления архитектуры приведём упрощённую ASCII-схему компонентов и потоков информации, значимых для мониторинга.

```text
[SCM (services.exe)] ──чтение конфигурации──▶ [Реестр HKLM\...\Services\<Name>]
     │                                           │
     │ управляет запуском                        │ параметры: ImagePath, Start, Type, ObjectName
     ▼                                           │
[Процесс службы (exe/svchost)] ◀────────────────┘
     │
     │ при запуске/остановке/изменении генерирует события в
     ▼
[Windows Event Log:
  System: 7036, 7040, 7045, 7000, 7009, 7022, 7023...
  Security: 4697 (Security-Auditing), 4624 (Logon), 4672 (Privileges)
  Application: ошибки конкретных служб]
     │
     │ собираются агентами/коллекторами
     ▼
[SIEM / Log Collector] ── алерты ──▶ [SOC Tier 1 Analyst]
```

**Типовые службы, наиболее значимые для мониторинга**

Исходя из практики расследований, выделим несколько десятков системных служб, поведение которых служит надёжным индикатором атак.

Служба **Spooler** (`Spooler`): отвечает за диспетчеризацию печати. Известна множеством уязвимостей повышения привилегий. Остановка или отключение на рядовой клиентской машине — возможно, защитная мера. Установка новой службы с привязкой к spoolsv-подобному имени — потенциальная атака.

Служба **Windows Remote Management (`WinRM`)** обеспечивает удалённое выполнение команд через протокол WS-Management. Внезапный запуск на рабочей станции, где удалённое управление не требуется, должен коррелироваться с событиями входа (4624 с типом входа 3 или 10), а также с событиями PowerShell (4104, 800). Это классический инструмент lateral movement.

Служба **BITS** (`BITS`) используется для фоновой загрузки файлов по HTTP. Злоумышленники эксплуатируют её для загрузки вредоносных компонентов, так как BITS работает в контексте доверенного процесса `svchost.exe`. Создание пользовательских заданий BITS регистрируется в журнале `Microsoft-Windows-Bits-Client/Operational` и может отражаться в событиях с Event ID 3 (новое задание), 59.

Служба **Windows Update** (`wuauserv`) и служба **Defender** (`WinDefend`) — частые мишени для отключения защитных механизмов. События 7040 (изменение типа запуска на Disabled) или 7036 (остановка) этих служб без последующего включения администратором — серьёзный тревожный сигнал.

Служба **Task Scheduler** (`Schedule`) — хотя запуск заданий не является напрямую службой, сам планировщик — служба, и её аномальные остановки могут предшествовать атакам или маскировать вредоносную активность.

Все перечисленные элементы и их системные идентификаторы составляют фундамент, на котором строится повседневная работа Tier 1 по анализу служб Windows.

## 3. Точки мониторинга служб для аналитика L1: события, журналы, инструментарий

Аналитику первого эшелона недостаточно знать классификацию служб — необходимо владеть конкретными инструментами и методиками извлечения и интерпретации сигналов. Данный раздел описывает основные источники событий, ключевые идентификаторы (Event ID) и практические приёмы фильтрации, позволяющие быстро отделить подозрительную активность от фонового шума.

**Основные каналы журналов, содержащие информацию о службах**

В операционных системах Windows Vista / Server 2008 и новее доступна расширенная политика аудита, позволяющая управлять категориями и подкатегориями аудита [URL: https://www.anti-malware.ru/practice/methods/Setting-up-auditing-in-Windows-for-full-SOC-monitoring]. Для мониторинга служб необходимо активировать как минимум следующие подкатегории в разделе `Advanced Audit Policy Configuration` → `System Audit Policies`:

- **Security State Change** — регистрирует изменения в подсистеме безопасности (модификации служб через Security Event 4697).
- **Audit Policy Change** — отслеживает изменения самих политик аудита (Event 4719), что важно для выявления попыток замести следы.
- **Process Creation** — даёт события о запуске процессов (4688), что позволяет связать создание службы с порождающим процессом.
- **Logon/Logoff** — события входа (4624, 4625, 4647) необходимы для определения пользователя, осуществившего операцию.

Кроме журнала безопасности, критически важны:

- **System** — содержит события 7036 (изменение состояния), 7040 (изменение типа запуска), 7045 (новая служба), 7000/7009 (ошибки запуска), 7022 (служба зависла при запуске), 7023 (аварийное завершение) и другие.
- **Application** — фиксирует ошибки и предупреждения конкретных служб, например антивирусных средств; полезен для выявления проблем, возможно, вызванных действиями злоумышленника.
- **Microsoft-Windows-Services/Operational** (и аналогичные) — специализированные каналы с детальной информацией о состоянии служб.

В корпоративной среде эти журналы централизованно собираются в SIEM-систему (Security Information and Event Management), где аналитик L1, используя стандартные дэшборды и поисковые запросы, производит первичную сортировку.

**Ключевые Event ID для мониторинга служб**

Ниже представлен сводный перечень событий, которые формируют точки контроля для L1-аналитика, с указанием журнала, описания и типичного контекста проверки.

| Event ID | Журнал    | Описание                                     | Контекст проверки аналитиком |
|----------|-----------|----------------------------------------------|-------------------------------|
| 7045     | System    | В системе установлена новая служба           | Проверить имя службы, путь к файлу, учётную запись. Сравнить с базой легитимных служб, поискать в VirusTotal по хешу исполняемого файла. |
| 7036     | System    | Служба перешла в состояние «Работает» или «Остановлена» | Внезапная остановка защитных служб (Defender, wuauserv) или неожиданный запуск WinRM на клиентской ОС — повод для эскалации. |
| 7040     | System    | Изменён тип запуска службы (авто/вручную/отключена) | Отключение антивирусных служб или изменение с Manual на Auto у подозрительной службы. |
| 4697     | Security  | Служба была установлена в системе            | Более детальное событие, чем 7045: содержит имя учётной записи, установившей службу, и дополнительную информацию. Требует настроенной подкатегории аудита `Security State Change`. |
| 7000 / 7009 | System | Служба не запустилась (тайм-аут или ошибка)  | Может указывать на то, что вредоносная служба «сломалась» после обновления или что злоумышленник пытался запустить легитимную службу с невалидным бинарем. |
| 7022 / 7023 | System | Служба зависла при запуске / аварийно завершилась | Часто наблюдается у плохо написанного вредоносного ПО; аномальное поведение служб, которые обычно работают стабильно. |
| 1102     | Security  | Журнал безопасности очищен                  | Косвенный индикатор действий злоумышленника, пытающегося замести следы после манипуляций со службами. |
| 4688     | Security  | Создан новый процесс                         | Позволяет отследить, какой именно процесс инициировал установку службы (например, `sc.exe`, `powershell.exe`, `msiexec.exe`). |
| 4624     | Security  | Successful logon                             | Для определения сеанса, в рамках которого было выполнено изменение. |
| 1 (Sysmon)| Microsoft-Windows-Sysmon/Operational | Создание процесса (детальная информация)     | Включает хеш, родительский процесс и командную строку. Чрезвычайно полезен при расследовании служб. |

Событие 7045 — базовый сигнал для L1. Его структура (в иллюстративной форме) включает:

- `Service Name` — имя новой службы.
- `Image Path` — полный путь к исполняемому файлу.
- `Service Type` — тип (обычно `user mode service`).
- `Account Name` — учётная запись, от которой запускается служба.
- `EventID` — 7045.

Пример фильтрации в современном SIEM (KQL-подобный синтаксис):

```kusto
EventLog
| where EventLog == "System" and EventID == 7045
| project TimeGenerated, Computer, ServiceName = tostring(EventData.ServiceName), ImagePath = tostring(EventData.ImagePath)
| where ImagePath !contains "\\System32\\"  // грубый фильтр системных путей
| distinct *
```

Аналитик L1 не обязан писать сложные запросы, но должен понимать, как пользоваться предварительно созданными правилами и панелями мониторинга.

**Практический инструментарий и процедуры**

Основным рабочим местом аналитика является интерфейс SIEM, однако в ряде случаев требуется точечная проверка непосредственно на хосте. Набор утилит и команд ограничивается минимально необходимым для первичного сбора информации.

Проверка запущенных служб и их параметров с помощью PowerShell:

```powershell
Get-Service | Where-Object { $_.Status -eq 'Running' } | Format-Table Name, DisplayName, StartType
```

Эта команда выведет список работающих служб с типами запуска. Аналитик может быстро сопоставить незнакомые имена со своим чек-листом.

Поиск в журнале System событий, связанных с конкретной службой:

```powershell
Get-WinEvent -LogName System | Where-Object { $_.Id -eq 7036 -and $_.Message -match "Spooler" } | Select-Object -First 5
```

Получение детальных свойств конкретной службы:

```powershell
Get-CimInstance Win32_Service -Filter "Name='Spooler'" | Select-Object *
```

Результат включает `PathName`, `StartName`, `StartMode` и другие атрибуты, что позволяет сравнить их с эталонными значениями.

Команда `sc qc <ServiceName>` (из командной строки) покажет конфигурацию службы:

```bash
sc qc wuauserv
```

Вывод (иллюстративная схема) содержит значения `START_TYPE`, `SERVICE_START_NAME`, `BINARY_PATH_NAME`. Изменение `BINARY_PATH_NAME` на нестандартный — явный признак компрометации.

Аналитики L1 часто используют типовые runbooks (заранее утверждённые плейбуки), в которых описаны шаги по обработке алертов о службах. Например, при срабатывании правила на 7045 с образом, расположенным в `C:\Users\*\AppData\*`, runbook предписывает:
1. Проверить временную метку и компьютер.
2. Найти в SIEM события входа 4624 за несколько секунд до 7045, установить владельца сеанса.
3. Поискать событие 4688 (запуск `sc.exe` или `powershell.exe` с командой `New-Service`) в тот же период.
4. Проверить репутацию хеша исполняемого файла в Threat Intelligence Platform.
5. При подтверждении аномальности — зарегистрировать инцидент и эскалировать на Tier 2.

**Типичные ложно-положительные срабатывания и способы фильтрации**

Для снижения нагрузки на L1 важно настроить фильтры, исключающие заведомо легитимные события. Частые ложные срабатывания:

- Установка служб легитимными инсталляторами MSI (например, обновления корпоративного ПО). В таких случаях обычно имеется корреляция с событиями 11707 (установка продукта) в журнале Application.
- Создание служб процессом `trustedinstaller.exe` или `msiexec.exe` в рамках планового обновления системы. Легитимные инсталляторы подписываются Microsoft.
- Запуск WinRM на серверах управления, что является штатной конфигурацией.

Грамотно построенная baseline (базовый профиль) для каждой группы узлов позволяет динамически выявлять отклонения, а не полагаться исключительно на статические списки разрешённых путей.

**Корреляционный анализ: связь служб с другими событиями**

Службы редко бывают единственным подозрительным артефактом. L1 аналитик обучен искать ассоциации. Например, создание новой службы с типом запуска «Automatic» и последующая (или предшествующая) запись в реестр в ветке Run (RunKey) свидетельствует о множественных способах закрепления. Связывание 7045 с событием 11 Sysmon (создание файла) может выявить, откуда был скопирован исполняемый файл службы. Использование таких корреляций — ключевая компетенция, отличающая опытного аналитика от новичка.

## 4. Сквозной практический пример: обнаружение подозрительной службы и первичный анализ

Рассмотрим реалистичный сценарий, с которым может столкнуться стажёр на позиции Tier 1. Все описанные ниже шаги — иллюстративные, конфигурация среды и конкретные значения зависят от инфраструктуры.

**Исходные условия**

Операционная система: Windows 10 Enterprise, находящаяся в домене `corp.local`. Аналитик L1 видит на панели SIEM системы оповещение о правиле «New Service Created with Suspicious Path». Алерт сгенерирован на основе события с Event ID 7045, полученного от коллектора логов с компьютера `DESKTOP-JN92KL`. В среде используется агент мониторинга, пересылающий журналы в централизованный SIEM с задержкой не более 30 секунд.

**Шаг 1: Изучение исходного алерта**

Аналитик открывает детализацию алерта в интерфейсе SIEM и видит следующий фрагмент события (иллюстративная схема):

```json
{
  "EventID": 7045,
  "Computer": "DESKTOP-JN92KL.corp.local",
  "TimeCreated": "2025-06-16T02:14:32.000Z",
  "ServiceName": "SysHelperSvc",
  "ImagePath": "C:\\Users\\jdoe\\AppData\\Local\\temp\\update.exe",
  "ServiceType": "user mode service",
  "AccountName": "LocalSystem"
}
```

Служба `SysHelperSvc` отсутствует в белом списке организации. Путь к исполняемому файлу размещён в пользовательской временной папке, что является типичным индикатором вредоносной активности. Учётная запись запуска — `LocalSystem`, дающая максимальные привилегии.

**Шаг 2: Проверка сопутствующих событий входа**

Аналитик выполняет поиск в SIEM событий с Event ID 4624 (успешный вход) на том же компьютере за несколько минут до создания службы. Фильтр:

```kusto
EventLog
| where Computer == "DESKTOP-JN92KL.corp.local" and EventID == 4624
| where TimeGenerated between (datetime(2025-06-16T02:10:00Z) .. datetime(2025-06-16T02:15:00Z))
| project TimeGenerated, TargetUserName, LogonType, IpAddress
```

Результат (иллюстративная схема):

| TimeGenerated | TargetUserName | LogonType | IpAddress    |
|---------------|----------------|-----------|--------------|
| 02:13:28      | jdoe           | 2         | 127.0.0.1    |
| 02:13:45      | jdoe           | 10        | 192.168.1.25 |

LogonType 2 — интерактивный вход, вероятно, пользователь `jdoe` работал локально. LogonType 10 — удалённый вход через RDP, что может быть как легитимным действием самого пользователя, так и компрометацией его учётной записи из внешней сети. В контексте алерта это требует дальнейшей проверки.

**Шаг 3: Поиск родительского процесса создания службы**

Чтобы понять, кто именно создал службу, аналитик ищет событие 4688 (создание процесса) с процессами, способными устанавливать службы:

```kusto
EventLog
| where Computer == "DESKTOP-JN92KL.corp.local" and EventID == 4688
| where TimeGenerated between (datetime(2025-06-16T02:14:00Z) .. datetime(2025-06-16T02:15:00Z))
| where ProcessName has_any ("sc.exe", "powershell.exe", "cmd.exe")
| project TimeGenerated, ProcessName, CommandLine, ParentProcessName, AccountName
```

Вывод показывает:

```text
TimeGenerated: 02:14:30
ProcessName: sc.exe
CommandLine: sc create SysHelperSvc binPath= "C:\Users\jdoe\AppData\Local\temp\update.exe" start= auto
ParentProcessName: cmd.exe
AccountName: jdoe
```

Командная строка явно указывает на ручное создание службы утилитой `sc.exe` с установкой автоматического запуска. Родительский процесс — `cmd.exe`, что может быть следствием выполнения вредоносного пакетного файла.

**Шаг 4: Поиск артефактов исполняемого файла**

Для получения хеша исполняемого файла аналитик обращается к событиям Sysmon, если они собираются (Event ID 1). Допустим, в SIEM доступна запись:

```json
{
  "EventID": 1,
  "Computer": "DESKTOP-JN92KL.corp.local",
  "TimeCreated": "2025-06-16T02:14:31.520Z",
  "Image": "C:\\Users\\jdoe\\AppData\\Local\\temp\\update.exe",
  "Hashes": "SHA256=7A2C...F1B3",
  "ParentImage": "C:\\Windows\\System32\\services.exe"
}
```

Аналитик отправляет хеш в корпоративный Threat Intelligence или в VirusTotal (если политика позволяет) и выясняет, что файл известен как троян, обеспечивающий удалённый доступ. Также можно проверить цифровую подпись файла через встроенные механизмы Windows:

```powershell
Get-AuthenticodeSignature -FilePath "C:\Users\jdoe\AppData\Local\temp\update.exe"
```

Если подпись отсутствует или недействительна — дополнительное подтверждение аномалии.

**Ожидаемый вывод**

Собирая воедино все улики (создание службы в пользовательском каталоге, удалённый вход пользователя незадолго до инцидента, ручная команда `sc create`, вредоносный хеш), аналитик L1 приходит к выводу, что учётная запись `jdoe`, вероятно, скомпрометирована, а на рабочей станции внедрён механизм постоянного присутствия в виде службы. Согласно плейбуку, он немедленно повышает серьёзность инцидента до высокой, заполняет карточку инцидента с собранными артефактами и эскалирует на Tier 2 для изоляции узла, детального форензического анализа и сброса паролей учётной записи.
