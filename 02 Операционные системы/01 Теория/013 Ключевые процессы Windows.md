# Ключевые процессы Windows

## 1. Системные процессы в Windows: фундамент мониторинга безопасности

При расследовании инцидентов на рабочих станциях и серверах Windows аналитик SOC L1 регулярно сталкивается с десятками работающих процессов. Не все они равнозначны. Ряд процессов являются неотъемлемой частью загрузки ОС, без них система не может функционировать, их поведение строго детерминировано. Именно отклонения от этого «нормального» поведения служат первыми индикаторами компрометации. Понимание архитектуры системных процессов, их ролей и взаимосвязей позволяет отличить штатную активность от действий вредоносного ПО, пытающегося замаскироваться под легитимный компонент.

**Пользовательский режим и режим ядра.** Все процессы Windows работают в одном из двух режимов: пользовательском (User mode) или режиме ядра (Kernel mode). Код пользовательского режима выполняется в изолированном виртуальном адресном пространстве, не имея прямого доступа к аппаратуре или критическим структурам памяти ОС. Сбой такой программы затрагивает только её саму. Код режима ядра (драйверы, ядро `ntoskrnl.exe`) выполняется в едином привилегированном адресном пространстве, где ошибка может привести к краху всей системы. Ключевое разграничение приведено в таблице:

| Характеристика | Пользовательский режим | Режим ядра |
|----------------|------------------------|------------|
| Адресное пространство | Частное, изолированное для каждого процесса | Общее для всех компонентов ядра |
| Привилегии | Ограниченные, доступ к оборудованию через API | Полный доступ ко всем ресурсам |
| Последствия сбоя | Завершение приложения | Синий экран (BSOD) |
| Примеры | `explorer.exe`, `cmd.exe`, все службы-хосты (`svchost.exe`) | Системные потоки (PID 4), драйверы, `ntoskrnl.exe` |

С точки зрения безопасности компрометация процесса ядра даёт атакующему абсолютный контроль, но сегодня мы сосредоточимся на процессах пользовательского режима, так как именно с ними аналитик взаимодействует чаще всего и именно под них чаще всего маскируются вредоносы.

**Понятие сессии и изоляция Session 0.** Современные версии Windows (начиная с Vista/Server 2008) изолируют службы и системные процессы в сессии 0. Пользовательские рабочие столы запускаются в отдельных сессиях (1, 2, …). Это предотвращает атаки типа «Shatter», когда вредоносное ПО из пользовательской сессии пыталось взаимодействовать с привилегированными окнами служб. Для аналитика знание о том, что все критически важные системные процессы (кроме `explorer.exe` и запущенных пользователем) должны находиться в Session 0, является простым и надёжным индикатором: процесс, претендующий на системную роль, но работающий в пользовательской сессии, почти наверняка вредоносен.

**Иерархия запуска – каркас доверия.** Процессы в Windows не появляются стихийно. Существует жёсткая, выверенная цепочка порождения, идущая от загрузчика: ядро → первый процесс user‑mode → ключевые подсистемы. Отклонения в этой цепочке — ещё один мощный индикатор аномалии. На рисунке представлена упрощённая, но достаточная для SOC‑аналитика схема иерархии запуска:

```text
[System Idle Process (PID 0)]
           │
    [System (PID 4)] ── потоки ядра
           │
    ┌───── smss.exe (Master, Session 0) ──────┐
    │ запускает подсистемы, переменные окружения,    │
    │ создает paging-файлы                      │
    └───────────────┬─────────────────────────────┘
                    │  (порождает дочерние копии для каждой новой сессии)
    ┌───────────────┴──────────────────────────────┐
    │                                              │
 smss.exe (child, Session 1)          smss.exe (child, Session 2 и т.д.)
    │  (самоуничтожается после запуска подсистем)    │
    │                                              │
    ├─ csrss.exe (Session 1)                       │
    ├─ winlogon.exe (Session 1)                    │
    │                                              
    │  wininit.exe (Session 0)                     
    │      ├─ services.exe (SCM) - родитель svchost.exe, spoolsv.exe и др.
    │      ├─ lsass.exe
    │      └─ lsaiso.exe (если включён Credential Guard)
    │                                              
    │  После аутентификации пользователя:          
    │  winlogon.exe → userinit.exe → explorer.exe
```

Каждая стрелка в этой схеме отображает родительско-дочернюю связь, которая должна строго соблюдаться. Попытка перехватить звено этой цепи (например, запуск `lsass.exe` напрямую из пользовательского `cmd.exe`) — высокий приоритет для эскалации в SOC.

**«Норма» как отправная точка.** Понятие нормального поведения процесса складывается из нескольких повторяющихся атрибутов: путь к исполняемому файлу, родительский процесс, количество экземпляров, сессия, учётная запись, время старта и наличие цифровой подписи. Именно эти ориентиры подробно рассмотрены в следующем разделе для каждого из ключевых процессов. Отклонение хотя бы одного из этих параметров должно автоматически запускать дальнейший анализ, даже если сразу не видно явной вредоносной активности.

Знание системных процессов — это не мёртвая теория, а оперативная база для первичного тража (triage) алертов в SIEM и при работе с EDR-решениями. Оно позволяет отвечать на вопросы «запускался ли этот процесс в системе легитимно?», «какой процесс должен быть его родителем?» и «может ли данный путь быть подлинным?» за секунды, а не минуты.

## 2. Архитектура ключевых процессов: роли, характеристики и индикаторы аномалий

В этом разделе все процессы, которые аналитик должен распознавать безошибочно, систематизированы в обзорную таблицу, после которой даны пояснения по наиболее тонким моментам. Таблица спроектирована для быстрой ориентации при расследовании; каждая строка — профиль одного процесса, включая индикаторы, вызывающие подозрение.

| Процесс | Роль | Путь к образу (норма) | Родительский процесс | Экземпляров (норма) | Сессия (норма) | Учётная запись | Признаки аномалий |

**Особенности, требующие внимания.**

*Svchost.exe и ключ -k.* Службы в Windows редко реализованы отдельными исполняемыми файлами. Большинство из них — это DLL, загружаемые в общий процесс `svchost.exe`. Группировка DLL осуществляется по параметру командной строки `-k <имя_группы>`, который ссылается на запись в реестре `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost`. Таким образом, легитимный `svchost.exe` всегда содержит ключ `-k`. Отсутствие этого параметра — красный флаг, часто встречающийся в дропперах, которые просто копируют `svchost.exe` в свою папку и запускают без аргументов. Дополнительная проверка: наличие запущенного `svchost.exe` с ключом группы, отсутствующей в реестре, также индикатор компрометации.

*Csrss.exe и завершённый родитель.* При анализе в Process Explorer или Process Hacker процесс `csrss.exe` будет показывать родителя как `<Non-existent Process>`. Это нормально: создавший его экземпляр `smss.exe` самоуничтожился. Попытка же увидеть работающий родительский процесс (особенно с необычным именем) — признак инжекта или подмены.

*Lsass.exe и дампы учётных данных.* `Lsass.exe` – излюбленная цель для инструментов извлечения учётных данных (Mimikatz и аналогов), которые либо инжектят код в процесс, либо создают его дамп. SOC‑аналитик должен отслеживать события Sysmon Event ID 10 (ProcessAccess) с правами доступа `0x1010` к процессу `lsass.exe`, а также создание файлов дампов (`.dmp`) с неожиданных путей.

*Explorer.exe и дочерние процессы.* Нормально, когда `explorer.exe` порождает процессы приложений, запущенных пользователем. Однако запуск неинтерактивных процессов, таких как `powershell.exe`, `cmd.exe`, или тем более `svchost.exe`, напрямую от `explorer.exe` нестандартен и может указывать на закрепление вредоносного ПО через реестр (Run‑ключи), когда зловред стартует вместе с оболочкой.

Приведённая таблица и пояснения формируют профиль нормы, который служит основой для практических проверок, описанных в следующем разделе.

## 3. Практические методы идентификации и верификации процессов в SOC

Понимание нормативных значений полезно только в сочетании с навыком быстрого сбора и фильтрации информации о процессах. В распоряжении аналитика SOC L1 имеется три основных класса инструментов: встроенные утилиты командной строки (`tasklist`, `wmic`, PowerShell), продвинутые GUI-инструменты (Process Explorer, Process Hacker) и агенты EDR/SIEM, поставляющие централизованные данные.

**Базовый сбор информации через командную строку.** Первый и самый доступный подход – использование утилиты `tasklist`. Она позволяет получить список процессов с минимальной фильтрацией и не требует административных привилегий для базового вывода. Пример команды, извлекающей процессы по имени и путь к образу:

```cmd
tasklist /v /fo csv | findstr /i "svchost"
```

Однако `tasklist` не показывает родительский PID. Для этого применяется `wmic`:

```cmd
wmic process where "Name='lsass.exe'" get ProcessId,ParentProcessId,ExecutablePath,CommandLine /format:csv
```

Более гибкий и рекомендуемый способ — использование PowerShell. Командлет `Get-Process` в сочетании с `Get-CimInstance` или `Get-WmiObject` позволяет формировать сложные запросы. Следующий скрипт проверяет наличие критически важных процессов, запущенных не из системного каталога, что является грубой аномалией:

```powershell
$criticalProcesses = @('smss', 'csrss', 'wininit', 'services', 'lsass', 'winlogon')
Get-Process -Name $criticalProcesses -ErrorAction SilentlyContinue |
    Where-Object { $_.Path -notlike "$env:SystemRoot\System32\*" } |
    Select-Object Name, Id, Path, StartTime
```

Если скрипт возвращает хотя бы одну строку, это немедленный кандидат на детальный разбор. Аналогично, для проверки подписей можно использовать встроенный `Get-AuthenticodeSignature`:

```powershell
Get-ChildItem "$env:SystemRoot\System32\*.exe" |
    Where-Object { $_.Name -in @('lsass.exe','csrss.exe','wininit.exe') } |
    Get-AuthenticodeSignature | Where-Object { $_.Status -ne 'Valid' }
```

**Продвинутая визуальная верификация.** Утилита Process Explorer (часть набора Sysinternals) предоставляет графическое представление дерева процессов, подсвечивая цветом тип исполняемого файла (подписанный Microsoft, неподписанный и т.п.), а также прямо показывает командную строку, сессию и загруженные DLL. При анализе подозрительного процесса аналитик должен:
1. Проверить вкладку *Image*: путь, родителя, командную строку, аргументы (особенно для `svchost`).
2. Перейти на вкладку *TCP/IP* (при её наличии) — наличие активных сетевых подключений для процесса, который не должен их инициировать (`csrss.exe`, `wininit.exe`), подозрительно.
3. Открыть вкладку *Strings* и поискать URL, IP-адреса, пути к вредоносным DLL.
4. Убедиться, что вкладка *Verify Signer* подтверждает подпись «Microsoft Windows» или «Microsoft Corporation» и статус «Valid».

Иллюстративный вывод свойств `svchost.exe` в Process Explorer для легитимного процесса будет содержать:
- *Path*: C:\Windows\System32\svchost.exe
- *Command line*: C:\Windows\System32\svchost.exe -k NetworkService -p -s Dnscache
- *Parent*: services.exe (PID X)
- *Verified signer*: Microsoft Windows Publisher
- *Session*: 0

Любое расхождение с этим шаблоном должно фиксироваться.

**Работа с телеметрией EDR/SIEM.** В условиях современного SOC аналитик редко заходит на хост напрямую; основная масса расследований ведётся по событиям. Для мониторинга создания процессов чаще всего используется Sysmon Event ID 1 (Process Creation). Он фиксирует Image, CommandLine, ParentImage, ParentCommandLine, User, IntegrityLevel и хеши. Правило корреляции в SIEM может выглядеть как поиск событий, где Image в точности соответствует `C:\Windows\System32\lsass.exe`, но ParentImage не равен `C:\Windows\System32\wininit.exe`. Альтернативно, можно отслеживать случаи, когда `svchost.exe` запускается без подстроки `-k` в CommandLine.

При использовании Sysmon также крайне важен Event ID 10 (ProcessAccess), который регистрирует доступ одного процесса к другому. Так, запросы к `lsass.exe` с правами `0x143A` или `0x1010` от нетипичного исходного процесса — классический признак попытки кражи учётных данных.

**Автоматизированная проверка целостности.** Полезной оперативной практикой является периодическая проверка хеш-сумм легитимных системных файлов. Утилита `sigcheck` из Sysinternals позволяет проверить подпись и сохранить хеш в CSV-базу, а затем сравнивать с актуальным состоянием. Команда:

```cmd
sigcheck -e -h C:\Windows\System32\svchost.exe
```

выведет как цифровую подпись, так и SHA256, который должен совпадать с эталоном для данной версии ОС.

**Типичные ошибки начинающего аналитика.** Самая частая — игнорирование контекста сессии. Процесс `csrss.exe`, запущенный в Session 1 на сервере терминалов — норма, в то время как на однопользовательской рабочей станции дополнительный экземпляр в нестандартной сессии уже подозрителен. Ещё одна ловушка: считать, что любой процесс в `System32` легален. Вредоносное ПО с правами администратора может разместить файл прямо в `System32`. Поэтому необходимо всегда проверять цифровую подпись, а не полагаться только на путь.

Таким образом, три кита практической верификации — **путь + родитель + подпись** — в комбинации с контекстом сессии и командной строкой покрывают подавляющее большинство аномалий, с которыми столкнётся аналитик L1.

## 4. Сквозной практический пример: расследование подозрительного процесса svchost.exe

**Исходные условия.** Рабочая станция сотрудника под управлением Windows 10 Enterprise. Пользователь сообщает о кратковременных зависаниях. Аналитик SOC L1 получает тикет и приступает к первичному исследованию с использованием удалённого PowerShell и Process Explorer, запущенного в сессии пользователя. Предполагается, что агент EDR также передаёт события в SIEM, но для целей примера мы работаем непосредственно на хосте.

**Шаг 1. Выявление отклонений по пути и командной строке.**  
Аналитик вводит PowerShell-команду для фильтрации всех экземпляров `svchost.exe`, путь к которым не соответствует системному каталогу, либо у которых отсутствует ключ `-k`:

```powershell
Get-CimInstance Win32_Process -Filter "Name='svchost.exe'" |
    Select-Object ProcessId, ExecutablePath, CommandLine |
    Where-Object { ($_.ExecutablePath -ne 'C:\Windows\System32\svchost.exe') -or ($_.CommandLine -notmatch '-k ') }
```

*Ожидаемый вывод (сокращён):*
```
ProcessId ExecutablePath                                CommandLine
--------- ----------------                                -----------
     1234 C:\Users\Public\Downloads\svchost.exe         "C:\Users\Public\Downloads\svchost.exe"
     5678 C:\Windows\System32\svchost.exe               svchost.exe -k UnistackSvcGroup
```
Видно, что экземпляр с PID 1234 запущен из нетипичного местоположения, а командная строка не содержит `-k`, что противоречит норме.

**Шаг 2. Выяснение родительско-дочерней связи.**  
Для подозрительного PID 1234 аналитик определяет родительский процесс и его аргументы с помощью `wmic`:

```cmd
wmic process where "ProcessId=1234" get ParentProcessId, CommandLine /value
```

*Вывод:*
```
ParentProcessId=9012
CommandLine="C:\Users\Public\Downloads\svchost.exe"
```
Теперь выясним, что из себя представляет процесс с PID 9012:

```cmd
wmic process where "ProcessId=9012" get Name, ExecutablePath
```

*Вывод:*
```
Name          ExecutablePath
explorer.exe  C:\Windows\explorer.exe
```
Родителем `svchost.exe` оказался `explorer.exe`. Легитимный `svchost.exe` всегда запускается менеджером служб `services.exe`, поэтому такая родительская цепочка с высокой вероятностью указывает на вредоносный запуск оболочкой при старте пользователя (скорее всего, через Run-ключ реестра).

**Шаг 3. Проверка цифровой подписи.**  
Чтобы исключить ошибку, аналитик проверяет подпись файла напрямую:

```powershell
Get-AuthenticodeSignature -FilePath "C:\Users\Public\Downloads\svchost.exe" | Format-List
```

*Ожидаемый вывод:*
```
SignerCertificate      : 
Status                 : NotSigned
StatusMessage          : The file is not digitally signed.
Path                   : C:\Users\Public\Downloads\svchost.exe
```
Файл не имеет цифровой подписи Microsoft. Легитимный системный `svchost.exe` всегда подписан действующим сертификатом Microsoft Windows Publisher. Налицо факт полной подмены.

**Шаг 4. Обнаружение сетевых подключений.**  
Далее аналитик проверяет, инициирует ли процесс сетевые соединения. Легитимный сервисный хост может иметь подключения (например, к контроллеру домена), но подозрительный процесс нестандартного расположения заслуживает особого внимания:

```cmd
netstat -ano | findstr /i "1234"
```

*Иллюстративный вывод:*
```
TCP    192.168.1.101:49876    203.0.113.55:443    ESTABLISHED     1234
```
Процесс установил исходящее соединение с внешним IP-адресом (203.0.113.55) по порту 443. Этот адрес не ассоциирован с инфраструктурой компании, легитимные обновления также не должны идти из папки Downloads.

**Шаг 5. Фиксация и эскалация.**  
Собранные артефакты — путь к файлу, отсутствие ключа `-k`, родитель `explorer.exe`, недействительная подпись, сетевой трафик к неизвестному IP — с высокой достоверностью классифицируют процесс как вредоносный. Аналитик L1 выполняет следующие действия:
- Заносит в тикет все полученные показатели (PID, путь, хеш файла, IP-адрес).
- Инициирует процедуру изоляции хоста в сети (если предусмотрено) и блокировку IP на межсетевом экране.
- Создаёт алерт в SIEM с приоритетом High и передаёт тикет на уровень L2 для дальнейшего анализа (форензика памяти, снятие дампа процесса, поиск артефактов постоянства в реестре).

**Демонстрация результата.** Данный сквозной пример иллюстрирует, как систематическое знание нормальных характеристик ключевого процесса (`svchost.exe`) и применение минимального набора командных инструментов позволяют в течение нескольких минут различить тщательно замаскированную угрозу и принять первоочередные меры по локализации инцидента.
