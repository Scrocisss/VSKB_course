# Локальные и доменные учётные записи: отличия и видимость в логах

## 1. Контекст и базовые понятия

Учётные записи в Windows делятся на две принципиально разные категории по области действия и месту хранения учётных данных: **локальные** и **доменные**. Локальная учётная запись существует только в контексте одного компьютера — её имя и хэш пароля хранятся в локальной базе SAM (Security Account Manager). Доменная учётная запись определена в Active Directory и доступна на всех машинах, входящих в домен или доверенные домены; проверка её учётных данных всегда выполняется с участием контроллера домена (DC). Для специалиста SOC L1 способность различать эти два типа записей по событиям в журналах безопасности является базовым навыком: от этого зависит корреляция инцидента, определение масштаба компрометации и выбор дальнейшей стратегии реагирования.

Путаницу часто вызывает схожесть терминов «Account Logon» и «Logon/Logoff» в структуре Windows Security Log. Account Logon — событие аутентификации, то есть проверки учётных данных (пароля, сертификата, токена). Logon/Logoff — событие создания и завершения сеанса на конкретном компьютере. Эти две категории регистрируются в разных местах для одного и того же входа: если пользователь входит в домен со своей рабочей станции, на контроллере домена фиксируется Account Logon (проверка пароля), а на рабочей станции — Logon (создание сессии). Для локального входа на той же машине оба события пишутся в её журнал безопасности (4776 — Account Logon, 4624 — Logon). Понимание этого разделения критически важно, поскольку, например, неудачные попытки проверки учётных данных локальной учётной записи на контроллере домена (событие 4776 с кодом 0xC0000064 «пользователь не существует») являются сильным индикатором попытки доступа к сетевым ресурсам с локального аккаунта, чьи учётные данные невалидны для домена.

Нижеследующая таблица фиксирует ключевые различия локальных и доменных учётных записей в Windows, которые затем детально исследуются.

| Признак | Локальная учётная запись | Доменная учётная запись |
|---------|--------------------------|-------------------------|
| Хранилище учётных данных | SAM-куст реестра (файл `%SystemRoot%\System32\config\SAM`) | База данных Active Directory (NTDS.dit) на контроллерах домена |
| Область видимости | Только данный компьютер | В пределах домена и всех доверенных доменов леса |
| Идентификатор безопасности (SID) | Начинается с S-1-5-21-<идентификатор машины>-<RID> (для пользователей) или S-1-5-… (для встроенных учётных записей, например S-1-5-18 — LocalSystem) | Содержит SID домена: S-1-5-21-<домен SID>-<RID>, где домен SID одинаков для всех объектов домена |
| Процесс аутентификации | Локальный процесс LSASS сравнивает хэш введённого пароля с хэшем в SAM | Kerberos (TGT/TGS) или NTLM challenge-response через контроллер домена |
| Источник событий Account Logon | Локальная машина (если вход на неё); для сетевого доступа к чужому ресурсу аутентификации на локальной машине не происходит | Контроллер домена, обслуживающий запрос; на клиенте Account Logon не пишется |
| Типичные значения поля `TargetDomainName` в событиях Logon | Имя компьютера | NetBIOS-имя домена |
| Встроенные администраторы | Локальный Administrator (RID 500), члены группы Administrators | Администратор домена (RID 500), члены Domain Admins |
| Управление паролями | Локальные политики, LAPS (если настроен) | Доменные политики паролей, fine-grained password policies |

Локальные учётные записи широко используются для локального администрирования, встроенных сервисных учётных записей (SYSTEM, LOCAL SERVICE, NETWORK SERVICE), а также для предоставления ограниченного доступа на отдельно стоящих или входящих в рабочую группу машинах. В доменной среде сохраняется необходимость в локальном администраторе для восстановления системы, но повседневная работа ведётся под доменными учётными записями. Распространённая ситуация, важная для SOC: пользователь, работая на домашнем компьютере под локальной учётной записью, подключается по VPN к корпоративной сети, используя доменную учётную запись, а затем пытается открыть сетевую папку. Windows по умолчанию сначала пытается использовать учётные данные текущего интерактивного сеанса (локальные), что приводит к появлению на DC событий неудачной проверки подлинности 4776 для локального имени. Это объяснение из [сообщества Spiceworks](https://community.spiceworks.com/t/why-is-a-local-user-account-authenticating-to-domain-servers/755935) зафиксировано как типовой сценарий ложного срабатывания, но при анализе атак такие события могут указывать на попытку злоумышленника «выйти из песочницы» локального контекста.

Таким образом, отправной точкой для любого анализа событий входа является умение по SID, имени домена и типу события сразу классифицировать учётную запись как локальную или доменную. Без этого навыка невозможно построить цепочку атаки и отличить нормальное поведение от инцидента.

## 2. Внутреннее устройство: хранение, форматы SID и механизмы аутентификации

Различия, отмеченные в первом разделе, проистекают из фундаментальной архитектуры подсистемы безопасности Windows. В этом разделе детально рассматриваются места хранения учётных данных, структура идентификаторов безопасности (SID) и процессы аутентификации, чтобы дать аналитику инструменты для интерпретации низкоуровневых артефактов.

**Хранилища данных.** Локальные учётные записи хранятся в кусте реестра SAM, загружаемом в `HKLM\SAM`. Доступ к этому ключу ограничен даже для администраторов; в работающей системе прочитать содержимое можно только от имени SYSTEM (например, через `psexec -s` или задачу с наивысшими привилегиями). Файл SAM лежит в `%SystemRoot%\System32\config\SAM`, резервные копии — в `%SystemRoot%\System32\config\RegBack\SAM`. Доменные учётные записи хранятся в базе данных NTDS.dit, которая расположена на каждом контроллере домена в `%SystemRoot%\NTDS\ntds.dit` и реплицируется между DC в пределах сайта и за его пределами. Прямой доступ к NTDS.dit для извлечения хэшей — цель множества инструментов злоумышленников (ntdsutil, vssadmin, secretsdump.py), и обнаружение таких действий — классическая задача мониторинга событий Windows (например, событие 4662 — операция с объектом каталога).

**Структура SID.** Идентификатор безопасности SID позволяет однозначно установить, к какому «авторитетному источнику» относится учётная запись. Формат SID имеет вид `S-1-5-...`, где первые два числа фиксированы (ревизия и идентификатор авторитетного органа — NT Authority), а последующие компоненты определяют конкретного эмитента и относительный идентификатор (RID).

Таблица ниже обобщает стандартные формы SID для разных типов учётных записей (иллюстративные значения доменных и машинных идентификаторов).

| Тип учётной записи | Структура SID | Пример (иллюстративный) | Примечания |
|-------------------|---------------|--------------------------|------------|
| Доменный пользователь | S-1-5-21-<домен SID>-<RID> | S-1-5-21-3623811015-3361044348-30300820-1107 | RID >= 1000 для обычных пользователей; RID=500 — встроенный администратор домена |
| Доменная группа | S-1-5-21-<домен SID>-<RID> | S-1-5-21-3623811015-3361044348-30300820-512 (группа Domain Admins) | RID групп определены стандартом (например, 512 — Domain Admins, 513 — Domain Users) |
| Локальный пользователь на машине (член рабочей группы или домена) | S-1-5-21-<машинный SID>-<RID> | S-1-5-21-123456789-234567890-345678901-1001 | Машинный SID генерируется случайно при установке ОС; RID = 1000+ для созданных пользователей, 500 — встроенный администратор |
| Встроенная локальная учётная запись (SYSTEM, LOCAL SERVICE, NETWORK SERVICE) | S-1-5-<фиксированный RID> | S-1-5-18 (LocalSystem), S-1-5-19 (LocalService), S-1-5-20 (NetworkService) | Не зависят от машинного или доменного SID, всегда одинаковы на всех системах |
| Группа локальных администраторов | S-1-5-32-544 | — | Стандартный SID для Builtin\Administrators |

Аналитик, видя в логе SID `S-1-5-21-...-1120`, не может без дополнительных данных сказать, локальный он или доменный. Ключ к определению — сравнение доменной части SID либо с известным SID домена (можно получить из AD или из события 4624 на другом компьютере), либо через контекст события: в структуре события 4624 поле `TargetDomainName` содержит имя источника учётной записи (компьютер или домен), а `TargetUserSid` содержит полный SID. Например, если `TargetDomainName` = `DESKTOP-ABC`, то учётная запись локальная для этого компьютера. Важно помнить, что в доменной среде SID локального администратора на разных машинах будет разным, даже если имя пользователя совпадает (например, везде «admin» с одинаковым паролем). Это позволяет в SOC отличать горизонтальное перемещение с использованием общих локальных учётных записей: если на сервере `SRV-01` зафиксирован вход под именем `Administrator` с `TargetDomainName = SRV-02`, то злоумышленник использовал локального администратора машины `SRV-02` для доступа к `SRV-01`.

**Процесс аутентификации и роли компонентов.** Для локального входа на компьютер (консоль или RDP, LogonType 2 или 10) последовательность такова: Winlogon считывает введённые учётные данные, передаёт их в LSASS, который хэширует пароль и сравнивает с хэшем, извлечённым из SAM. В случае успеха LSASS создаёт маркер доступа (access token) и регистрирует события: Account Logon (4776) и Logon (4624) — оба в журнале безопасности той же машины. SubjectUserSid в таких событиях обычно SYSTEM, поскольку именно система выступает инициатором сеанса для пользователя.

Для доменной аутентификации рабочий процесс усложняется (см. схему ниже). Клиентская машина обращается к контроллеру домена, используя Kerberos (по умолчанию) или NTLM. В Kerberos потоке: AS_REQ → TGT (событие 4768 на DC), затем TGS_REQ → TGS (4769). На рабочей станции после успешной аутентификации создаётся сессия и пишется Logon (4624). NTLM-аутентификация (при подключении к ресурсам по IP-адресу, старые системы) порождает на DC событие 4776 (Credential Validation), а на клиенте — Logon (4624) с LogonType=3 (сетевой вход). Таким образом, при работе в домене аналитик для реконструкции одного входа должен объединять события с различных машин, опираясь на временные метки, имена пользователей и рабочих станций.

```text
[Рабочая станция]                         [Контроллер домена]
      │                                           │
      ├──(AS_REQ, шифрованный timestamp)─────────►│
      │                                           ├── проверка учётных данных в NTDS.dit
      │◄───────────────(TGT, зашифрованный)───────┤
      │                                           │  Событие 4768
      ├──(TGS_REQ, TGT + запрос на сервис)────────►│
      │                                           ├── проверка TGT и выписка TGS
      │◄───────────────(TGS)──────────────────────┤   Событие 4769
      │                                           │
      ├── создание локальной сессии LSASS ────────┤
      Событие 4624 (Logon)
```

Если аутентификация не удалась, на DC фиксируется соответствующее событие с кодом ошибки: для Kerberos — 4771 (Pre-authentication failed), для NTLM — 4776 со статусом не `0x0`. На клиенте — 4625. При попытке доступа к сетевому ресурсу с локальной учётной записью, не существующей в домене, DC зарегистрирует 4776 с кодом `0xC0000064` (The specified user does not exist). Именно такие цепочки позволяют SOC-аналитику идентифицировать описанный ранее сценарий «локальный пользователь ломится в домен».

**Группы и их SID.** Группы также имеют SID, который отражает область действия. Глобальные (глобальные группы домена) и универсальные группы имеют SID, содержащий доменный SID. Локальные группы компьютера имеют SID, содержащий машинный SID. Встроенные группы, такие как локальные Administrators, используют фиксированный SID `S-1-5-32-544`. События добавления членов в группы (4728, 4732, 4756) содержат SID группы, что позволяет быстро определить, куда именно был добавлен пользователь — в доменную или локальную группу, и на каком уровне произошло повышение привилегий.

## 3. Видимость в логах: события, поля и приёмы анализа

Применение полученных знаний в повседневной работе SOC L1 означает умение извлечь из потока событий Windows Security Log индикаторы компрометации и корректно интерпретировать контекст. В этом разделе описываются ключевые идентификаторы событий (Event ID), структура полей, важных для различения локальных и доменных входов, и практические методики фильтрации.

**Категории событий и их различие.** Как подчёркнуто в [статье Netsurion](https://www.netsurion.com/articles/the-key-difference-between-account-logon-and-logon-logoff-events-in-the-windows-security-log), категория «Account Logon» фиксирует факт проверки учётных данных и является точечным событием; категория «Logon/Logoff» — события начала и завершения сеанса. Для SOC критично следующее разделение.

- **События Account Logon** генерируются на машине, которая фактически выполняет аутентификацию: для локальной учётной записи это сама машина, для доменной — контроллер домена. Основные события: 4776 (проверка NTLM), 4768 (TGT запрос), 4771 (Kerberos pre-auth failure), 4769 (TGS запрос).
- **События Logon/Logoff** генерируются на том компьютере, где создаётся пользовательский сеанс: при входе на рабочую станцию, при подключении к сетевой папке, при запуске запланированного задания и т.д. Основные события: 4624 (успешный вход), 4625 (неудачный вход), 4634/4647 (завершение сеанса).

**Ключевые идентификаторы событий и контекст локальности/доменности.** Таблица ниже суммирует наиболее часто используемые события с указанием того, в каких из них можно непосредственно определить тип учётной записи.

| Event ID | Категория | Описание | Типичное место возникновения для доменного входа | Поля, раскрывающие локальность/доменность |
|----------|-----------|----------|-----------------------------------------------|-------------------------------------------|
| 4624 | Logon | Успешный вход (сессия создана) | Рабочая станция, на которую выполнен вход | `TargetUserName`, `TargetDomainName` (имя системы или домена), `TargetUserSid`, `LogonType` |
| 4625 | Logon | Неудачный вход | Рабочая станция | `TargetUserName`, `TargetDomainName`, `FailureReason`, `SubjectUserSid` |
| 4647 | Logoff | Инициация завершения сеанса пользователем | Рабочая станция | `TargetUserSid` |
| 4634 | Logoff | Сеанс завершён системой | Рабочая станция | `TargetUserSid` |
| 4776 | Account Logon | Проверка NTLM-учётных данных | Контроллер домена (или локальная машина) | `TargetUserSid`, `Workstation` (имя клиента), `Status` (0x0 — успех, 0xC0000064 — нет пользователя) |
| 4768 | Account Logon | Запрошен TGT (Kerberos) | Контроллер домена | `TargetUserName`, `TargetDomainName`, `TargetSid` |
| 4771 | Account Logon | Kerberos pre-authentication failed | Контроллер домена | `TargetUserName`, `TargetSid`, `FailureCode` |
| 4672 | Logon | Специальный вход (привилегированная учётная запись) | Та же машина, что и 4624 | `SubjectUserSid` — SID учётной записи с административными привилегиями |
| 4720 | Account Management | Создана учётная запись | Где произошло действие (DC для доменных, локальная машина для локальных) | `SamAccountName`, `Sid` |
| 4726 | Account Management | Удалена учётная запись | Аналогично | `SamAccountName`, `Sid` |

**Поле LogonType в событии 4624** принципиально важно для понимания характера доступа. Значения определены в официальной документации Microsoft и воспроизводятся ниже.

- 2 – Interactive (локальный вход с консоли)
- 3 – Network (доступ к общим ресурсам, сетевое подключение)
- 4 – Batch (задание по расписанию)
- 5 – Service (запуск службы)
- 7 – Unlock (разблокировка экрана)
- 8 – NetworkCleartext (сетевой вход с передачей пароля открытым текстом, например Basic-аутентификация IIS)
- 9 – NewCredentials (вызов RunAs с флагом `/netonly`, клонирование токена)
- 10 – RemoteInteractive (RDP)
- 11 – CachedInteractive (вход с кэшированными доменными учётными данными без доступного DC)

Для SOC L1 особенно интересны типы 3, 10 и 2. Сетевой вход (3) с доменной учётной записью часто указывает на доступ к файловым ресурсам или использование инструментов типа PsExec. Если при этом `TargetDomainName` совпадает с именем исходной рабочей станции, вход произведён локальной учётной записью, что при межмашинном взаимодействии практически всегда означает атаку (горизонтальное перемещение с общим локальным администратором).

**Практические приёмы фильтрации и разбора событий.** Ниже приведён фрагмент PowerShell, иллюстрирующий извлечение событий входа 4624 с машины и разбор ключевых полей с помощью XML (иллюстративная команда, адаптируемая под конкретные условия). Такой подход позволяет быстро определить локальность учётной записи по `TargetDomainName` и `TargetUserSid`.

```powershell
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    ID        = 4624
    StartTime = (Get-Date).AddHours(-4)
} | ForEach-Object {
    $x = [xml]$_.ToXml()
    $data = $x.Event.EventData.Data
    $targetUser = ($data | Where-Object {$_.Name -eq 'TargetUserName'}).'#text'
    $targetDomain = ($data | Where-Object {$_.Name -eq 'TargetDomainName'}).'#text'
    $targetSid = ($data | Where-Object {$_.Name -eq 'TargetUserSid'}).'#text'
    $logonType = ($data | Where-Object {$_.Name -eq 'LogonType'}).'#text'
    [PSCustomObject]@{
        Time       = $_.TimeCreated
        User       = $targetUser
        Domain     = $targetDomain
        SID        = $targetSid
        LogonType  = $logonType
    }
} | Format-Table -AutoSize
```

В выводе аналитик может сразу идентифицировать подозрительные входы: например, если `Domain = DESKTOP-ABC`, а `User = Administrator` и `LogonType = 3` — это сетевой вход с локального администратора машины DESKTOP-ABC на анализируемую систему. Для подтверждения, что это локальная учётная запись, необходимо проверить SID: он должен содержать машинный SID, отличающийся от доменного.

Событие 4776 на контроллере домена даёт похожую информацию. Иллюстративный фрагмент события:

```xml
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
 <System>
  <Provider Name="Microsoft-Windows-Security-Auditing" Guid="{...}"/>
  <EventID>4776</EventID>
 </System>
 <EventData>
  <Data Name="PackageName">MICROSOFT_AUTHENTICATION_PACKAGE_V1_0</Data>
  <Data Name="TargetUserName">jdoe</Data>
  <Data Name="Workstation">DESKTOP-ABC</Data>
  <Data Name="Status">0xc0000064</Data>
 </EventData>
</Event>
```

Здесь `TargetUserName` = `jdoe`, рабочая станция = `DESKTOP-ABC`, код ошибки `0xC0000064` — «пользователь не существует». Такие события не являются ошибкой конфигурации, если `jdoe` — локальный пользователь на рабочей станции. Однако массовое появление подобных записей с одного или нескольких хостов может свидетельствовать о распространении вредоносного ПО, пытающегося получить доступ к сетевым ресурсам под контекстом текущего пользователя.

Ещё один важный для SOC артефакт — событие 4672 (Special Logon), которое регистрируется при каждом входе учётной записи, обладающей привилегиями администратора или аналога (например, SeBackupPrivilege). Оно содержит `SubjectUserSid`, который позволяет отличить, была ли использована локальная административная учётная запись или доменная. При анализе Lateral Movement с Pass-the-Hash аналитик ищет сначала 4624 с LogonType 3 и TargetUserName=Administrator, а затем проверяет, есть ли сопутствующее событие 4672. Если SID в 4672 имеет локальный машинный идентификатор, это подтверждает использование локального администратора.

**Обнаружение типовых угроз.** Для SOC L1 полезно иметь готовые правила корреляции (выраженные, например, в псевдокоде Sigma), нацеленные именно на различие локального и доменного контекста. Иллюстративное правило:

```yaml
title: Обнаружена попытка сетевого входа с локальной учётной записи на множество хостов
description: >
  Выявляет горизонтальное перемещение с использованием общего локального администратора.
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4624
    LogonType: 3
    TargetUserName: 'Administrator'
    TargetDomainName|re: '^(?!CORP\\)'    # не доменное имя, а имя компьютера
  timeframe: 10m
  condition: selection | count(TargetUserName) by WorkstationName > 5
```

В нём ключевым фильтром является `TargetDomainName`, не совпадающее с именем домена (здесь `CORP`). Подобная логика реализуется в SIEM-системах.

**Важные оговорки и шум.** При анализе событий обязательна фильтрация шума: системные учётные записи DWM и UMFD (Desktop Windows Manager, Usermode Font Driver) выполняют входы на рабочие станции с LogonType 2 и 7, генерируя множество событий 4624. Как отмечено в [руководстве Active Countermeasures](https://www.activecountermeasures.com/hunting-windows-event-logs), их необходимо исключать из анализа. Кроме того, кэшированные доменные входы при отсутствии DC (LogonType 11) отображают `TargetDomainName` = имя домена, но при этом фактически используют локальные хэши; важно не спутать их с локальными учётными записями.

## 4. Сквозной практический пример: идентификация горизонтального перемещения с локальным администратором

**Исходные условия.** Сеть организации построена на домене `CORP.local`. Все рабочие станции и серверы имеют локальную учётную запись `svc_backup` с одинаковым паролем (нарушение best practices). Злоумышленник, скомпрометировав рабочую станцию `WS-BACKUP-01`, извлёк учётные данные `svc_backup` и предпринял попытку горизонтального перемещения на сервер `SRV-DB-01` с целью кражи базы данных. SOC L1 получает уведомление от SIEM о множественных неудачных входах на `SRV-DB-01` с учётной записью, не существующей в домене.

**Шаг 1. Сбор первичных событий с сервера-жертвы.** Аналитик удалённо извлекает события безопасности с `SRV-DB-01` за последние 2 часа, фокусируясь на неудачных попытках входа (4625) с сетевым типом (LogonType=3).

```powershell
Get-WinEvent -ComputerName SRV-DB-01 -FilterHashtable @{
    LogName='Security'; ID=4625; StartTime=(Get-Date).AddHours(-2)
} | Where-Object {
    $x = [xml]$_.ToXml()
    $lt = ($x.Event.EventData.Data | ? Name -eq 'LogonType').'#text'
    $lt -eq '3'
} | ForEach-Object {
    $x = [xml]$_.ToXml()
    $data = $x.Event.EventData.Data
    [PSCustomObject]@{
        Time       = $_.TimeCreated
        User       = ($data | ? Name -eq 'TargetUserName').'#text'
        Domain     = ($data | ? Name -eq 'TargetDomainName').'#text'
        Workstation= ($data | ? Name -eq 'WorkstationName').'#text'
        Status     = ($data | ? Name -eq 'Status').'#text'
    }
} | Format-Table -AutoSize
```

*Ожидаемый вывод (иллюстративная схема):*
```
Time            User        Domain              Workstation      Status
----            ----        ------              -----------      ------
12:15:32        svc_backup  WS-BACKUP-01        WS-BACKUP-01     0xC0000064
12:15:35        svc_backup  WS-BACKUP-01        WS-BACKUP-01     0xC0000064
...
```
Вывод демонстрирует, что имя пользователя `svc_backup`, домен совпадает с именем рабочей станции `WS-BACKUP-01`, а код ошибки `0xC0000064` означает, что учётная запись не найдена на целевом сервере. Это типичный признак попытки использования локальной учётной записи с удалённой машины.

**Шаг 2. Проверка существования учётной записи на контроллере домена.** Чтобы окончательно убедиться, что `svc_backup` не является доменным пользователем, аналитик запрашивает DC.

```powershell
Get-ADUser -Filter {SamAccountName -eq 'svc_backup'}
```

Вывод пуст — пользователь отсутствует в AD. Локальный характер `svc_backup` подтверждён.

**Шаг 3. Определение масштаба: поиск успешных входов этой учётной записи на других системах.** Злоумышленник мог добиться успеха на системах, где существует такая же локальная запись с тем же паролем. Аналитик выполняет запрос по всем серверам, ища 4624 с LogonType=3 и TargetUserName=svc_backup.

```powershell
$servers = 'SRV-FS-01','SRV-WEB-01','SRV-DB-01'  # примеры
foreach ($srv in $servers) {
    Get-WinEvent -ComputerName $srv -FilterHashtable @{
        LogName='Security'; ID=4624; StartTime=(Get-Date).AddHours(-4)
    } | ForEach-Object {
        $x = [xml]$_.ToXml()
        $data = $x.Event.EventData.Data
        $user = ($data | ? Name -eq 'TargetUserName').'#text'
        $domain = ($data | ? Name -eq 'TargetDomainName').'#text'
        $logontype = ($data | ? Name -eq 'LogonType').'#text'
        if ($user -eq 'svc_backup' -and $logontype -eq '3') {
            [PSCustomObject]@{Server=$srv; Time=$_.TimeCreated; SourceDomain=$domain; User=$user}
        }
    }
}
```

*Ожидаемый вывод (иллюстративная схема):*
```
Server      Time            SourceDomain        User
------      ----            ------------        ----
SRV-FS-01   12:18:05        WS-BACKUP-01        svc_backup
SRV-WEB-01  12:19:22        WS-BACKUP-01        svc_backup
```
Вывод показывает, что с `WS-BACKUP-01` были успешные сетевые входы на файловый и веб-серверы под именем `svc_backup`. `SourceDomain` = `WS-BACKUP-01` означает, что использовалась локальная учётная запись именно этого компьютера, указывая на горизонтальное перемещение.

**Шаг 4. Проверка сопутствующих событий привилегированного входа.** Аналитик проверяет, получил ли злоумышленник административный доступ. Для этого на `SRV-FS-01` выполняется поиск события 4672, произошедшего в тот же момент времени, что и 4624.

```powershell
Get-WinEvent -ComputerName SRV-FS-01 -FilterHashtable @{
    LogName='Security'; ID=4672; StartTime='12:15'; EndTime='12:25'
} | ForEach-Object {
    $x = [xml]$_.ToXml()
    $sid = ($x.Event.EventData.Data | ? Name -eq 'SubjectUserSid').'#text'
    $sid
}
```

*Ожидаемый вывод:* `S-1-5-21-123456789-234567890-345678901-1001` (машинный SID `WS-BACKUP-01`, RID 1001). Это означает, что во время входа был присвоен административный токен. Следовательно, на `SRV-FS-01` злоумышленник получил права локального администратора через общую локальную учётную запись.

**Вывод.** На основе анализа событий с разных машин аналитик установил, что злоумышленник, контролируя `WS-BACKUP-01`, сумел аутентифицироваться под локальной учётной записью `svc_backup` на двух серверах, получив на одном из них административные привилегии. Источником атаки является `WS-BACKUP-01`. Ключевым идентификатором локального характера учётной записи стало поле `TargetDomainName`, совпадающее с именем исходного компьютера, а не домена, а также SID, содержащий машинный идентификатор.
