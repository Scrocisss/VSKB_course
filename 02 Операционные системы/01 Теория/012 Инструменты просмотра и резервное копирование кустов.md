# Инструменты просмотра и резервное копирование кустов реестра Windows

## Контекст и базовые понятия: кусты реестра как объекты анализа и защиты

**Куст (hive)** — это бинарный файл на диске, содержащий фрагмент иерархической базы данных реестра Windows. Операционная система загружает кусты в память при загрузке и постоянно поддерживает их согласованность с помощью механизма транзакций. Различие между логическим представлением (Редактор реестра показывает единое дерево) и физическим хранением (разрозненные файлы в `%SystemRoot%\System32\Config` и профилях пользователей) принципиально для инструментов просмотра и резервного копирования: одни работают с API реестра, другие — напрямую с двоичными файлами.

Основные кусты и их файлы, с которыми встречается специалист SOC L1, перечислены в таблице. Каждый файл при загрузке системы монтируется в соответствующую ветвь реестра.

| **Файл куста (путь)**                                          | **Точка монтирования**          | **Хранимые данные**                                                        |
|----------------------------------------------------------------|----------------------------------|----------------------------------------------------------------------------|
| `%SystemRoot%\System32\config\SAM`                              | `HKEY_LOCAL_MACHINE\SAM`        | Хеши паролей, членство в группах, данные учётных записей                    |
| `%SystemRoot%\System32\config\SECURITY`                         | `HKEY_LOCAL_MACHINE\SECURITY`   | Политики безопасности, кэш LSA, журнал паролей                              |
| `%SystemRoot%\System32\config\SOFTWARE`                         | `HKEY_LOCAL_MACHINE\SOFTWARE`   | Установленное ПО, конфигурации, автозагрузка, лицензии                      |
| `%SystemRoot%\System32\config\SYSTEM`                           | `HKEY_LOCAL_MACHINE\SYSTEM`     | Контрольные наборы (ControlSet), параметры оборудования, загрузки           |
| `%SystemRoot%\System32\config\DEFAULT`                          | `HKEY_USERS\.DEFAULT`           | Шаблон профиля для вновь создаваемых пользователей                          |
| `%UserProfile%\NTUSER.DAT`                                      | `HKEY_CURRENT_USER`             | Настройки конкретного пользователя (рабочий стол, переменные, ассоциации)   |
| `%UserProfile%\AppData\Local\Microsoft\Windows\UsrClass.dat`    | `HKEY_CURRENT_USER\Software\Classes` | COM-классы и расширения файлов, перенаправляемые из HKCU\Software\Classes |
| `%SystemRoot%\AppCompat\Programs\Amcache.hve`                  | Внутренний (не подключается)    | Артефакты исполнения программ (Amcache)                                     |

Два корневых ключа — `HKEY_LOCAL_MACHINE` (HKLM) и `HKEY_USERS` (HKU) — являются реальными контейнерами кустов; `HKEY_CURRENT_USER` — символическая ссылка на подключ HKU, соответствующий вошедшему пользователю, а `HKEY_CLASSES_ROOT` объединяет `HKLM\SOFTWARE\Classes` и `HKCU\Software\Classes`. Понимание этих связей критически важно, когда аналитик загружает чужой куст: выбранное временное имя становится подразделом HKLM или HKU, и далее можно обращаться по пути.

**Зачем SOC-аналитику просматривать и бэкапить кусты?** В ходе реагирования на инциденты (IR) и мониторинга (SOC L1) кусты реестра — один из основных источников артефактов. Просмотр позволяет:

- выявлять точки закрепления вредоносного ПО (Run, RunOnce, Winlogon, AppInit_DLLs, службы);
- проверять историю подключений USB-устройств (ключи `HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR`);
- искать следы сетевой активности (прокси-серверы, DNS-параметры);
- восстанавливать временные метки установки программ и запуска приложений;
- анализировать изменения политик безопасности.

Резервное копирование необходимо для:

- создания «снимка» состояния системы для последующего офлайн-анализа без риска изменения работающей ОС;
- сохранения состояния «до» и «после» инцидента;
- восстановления повреждённых или атакованных ключей;
- обеспечения целостности доказательств при изъятии данных с хоста.

В отличие от файловой системы, где достаточно скопировать файл из теневой копии, куст, открытый системой в монопольном режиме, требует штатных механизмов: `reg save`, Volume Shadow Copy Service, либо загрузки с внешнего носителя.

## Внутреннее устройство кустов: формат, структура и поведение

Файл куста имеет бинарный формат с сигнатурой «regf» в начале, определённый Microsoft и обратно инженерно документированный сообществом. Понимание его устройства помогает разобраться, почему одни инструменты показывают удалённые ключи, а другие — нет, и почему простое копирование файла без снятия блокировки может привести к повреждению.

Каждый куст состоит из четырёх типов структур:

- **Base block** — заголовок, содержащий сигнатуру («regf»), номер версии (обычно 1.3 или 1.5), имя куста, последовательный номер, временную метку последней модификации и указатели на списки «грязных» страниц.
- **Hive bins** — блоки фиксированного размера (обычно 4096 байт), внутри которых размещаются ячейки; каждый bin имеет заголовок с сигнатурой «hbin».
- **Cells** — ячейки переменной длины, хранящие ключи, значения, списки безопасности, списки подразделов, данные значений. Ячейка ключа содержит временную метку последней записи, имя ключа, флаги, указатели на родительский ключ, список подразделов и список значений.
- **Transaction logs** — файлы с расширениями `.LOG`, `.LOG1`, `.LOG2`, расположенные рядом с основным файлом куста. Они содержат журнал изменений для обеспечения атомарности; в нормальном режиме при загрузке куста незавершённые транзакции «докатываются» (roll-forward), а затем журналы очищаются. Именно поэтому куст, скопированный в момент незавершённой транзакции (например, без использования VSS), может читаться с ошибками.

Схематично связь элементов можно представить так:

```text
[Base block "regf"]
  |
  +-- [HBIN 0]
  |     +-- [CELL_KEY "Control"]
  |     |     +-- [CELL_VALUE "WaitToKillServiceTimeout" (REG_DWORD)]
  |     |     +-- [CELL_SUBKEY_LIST → "Session Manager"]
  |     +-- [CELL_KEY "Session Manager"] ...
  +-- [HBIN 1] ...
```

Для специалиста SOC достаточны практические следствия этой структуры:

- Значения и ключи могут быть помечены как удалённые (флаг «tombstone»), но их ячейки ещё не перезаписаны. Специализированные инструменты (Registry Explorer, chntpw) способны их показать, тогда как regedit — нет.
- Восстановление удалённых данных возможно, если не произведена компактификация куста.
- При копировании для судебного анализа необходимо захватывать и основной файл, и логи, чтобы обеспечить восстановление консистентного состояния. Утилита `reg save` делает это корректно.

Также важно различать два режима доступа к кусту: *online* (через загрузку в живой реестр) и *offline* (прямое чтение файла парсером). В offline-режиме не требуется административных привилегий на анализируемой машине, что удобно для SOC-аналитиков при разборе дампов с удалённых хостов.

## Инструменты просмотра кустов

Инструменты просмотра можно разделить на встроенные средства Windows, которые требуют загрузки куста в живой реестр, и специализированные па́рсеры, работающие напрямую с файлами. Для SOC L1 характерна работа с уже изъятыми кустами, поэтому акцент сделан на офлайн-подход.

### Встроенные инструменты (требуют загрузки в живой реестр)

**Regedit.exe** — графический Редактор реестра. Для просмотра офлайн-куста необходимо:

1. Запустить regedit от имени администратора.
2. Выделить `HKEY_LOCAL_MACHINE` или `HKEY_USERS`.
3. Меню `Файл → Загрузить куст`, указать путь к файлу куста и произвольное имя подключа.

После этого куст появляется как подраздел выбранного корневого ключа, и его можно исследовать в интерфейсе. Недостатки: невозможность поиска по значениям в загруженном кусте (только ручная навигация), отсутствие отображения удалённых элементов.

**Утилита reg.exe** — консольный аналог. Пример загрузки, запроса и выгрузки:

```bash
reg load HKLM\TempHive "E:\evidence\SOFTWARE"
reg query "HKLM\TempHive\Microsoft\Windows\CurrentVersion\Run"
reg unload HKLM\TempHive
```

**PowerShell** с провайдером `Registry::` после загрузки куста (тем же `reg load`) предоставляет более гибкий доступ:

```powershell
$path = "Registry::HKEY_LOCAL_MACHINE\TempHive\Microsoft\Windows\CurrentVersion\Run"
Get-ItemProperty -Path $path | Format-List *
```

Эти встроенные методы хороши для быстрой проверки, но для глубокого анализа образа диска или сохранённого куста они неудобны: требуется ручная загрузка, невозможно сохранить снимок для отчёта без дополнительных действий.

### Специализированные утилиты офлайн-просмотра

**Registry Explorer** (разработка Eric Zimmerman) — графический инструмент, открывающий файлы кустов напрямую, без необходимости загружать их в реестр. Функции: навигация по дереву, поиск, просмотр удалённых ключей (при наличии информации в логах), экспорт ветки в .reg, встроенная поддержка транзакционных логов для восстановления удалённых значений. Типичный рабочий процесс: выбрать File → Open, указать `SOFTWARE`, развернуть `Microsoft\Windows\CurrentVersion\Run`. Поддерживает закладки и создание отчётов.

**RegRipper** (консольный Perl-скрипт) — автоматический парсер, извлекающий сотни предопределённых артефактов. SOC-аналитик запускает его с указанием файла куста и плагина, получая структурированный текстовый вывод. Пример:

```bash
rip -r E:\case\SOFTWARE -p appcompatflags
```

Вывод (иллюстративная схема):

```
AppCompatFlags
  LastWrite time: 2024-03-14 15:02:30Z
  Keys:
    \Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers
      Value: C:\Users\user\Desktop\malware.exe    REG_SZ    WINXPSP2
```

RegRipper особенно ценен на этапе первичного триажа для быстрого получения ключевых IoC.

**Belkasoft X** — коммерческий форензический продукт, который при добавлении образа диска автоматически находит и парсит все кусты, извлекая множество артефактов (USB-устройства, запущенные программы, беспроводные сети, учётные записи) и предоставляя встроенный Registry Viewer для ручного просмотра с поиском. Это значительно ускоряет расследование, позволяя одним кликом получить список подозрительных автозагрузок со всех профилей.

**FTK Imager** — хоть и предназначен для создания образов, он включает предварительный просмотр (preview) и возможность экспорта кустов. Аналитик может открыть образ диска, перейти в `\Windows\System32\Config`, выбрать куст `SAM`, щёлкнуть правой кнопкой и выбрать «Export File Hash List» или просто извлечь. Встроенный просмотр некоторых ключей возможен в панели свойств.

Выбор инструмента определяется задачей: если нужно только проверить конкретный ключ, `reg` или PowerShell с загрузкой подходят; если требуется составить отчёт по десяткам артефактов — RegRipper; для полного расследования — Registry Explorer или Belkasoft.

## Резервное копирование кустов

Корректное резервное копирование кустов — не побочная задача, а стандартная операция SOC при изъятии данных, создании снимка «до» внесения изменений или восстановлении системы. Неправильно снятая копия может оказаться бесполезной, особенно если не учесть транзакционные логи.

### Экспорт отдельных ветвей в .reg-файлы

Самый простой, но наименее надёжный способ. Команда `reg export` записывает содержимое ключа (включая все подразделы) в текстовый REG-файл формата Unicode. Полученный файл можно импортировать обратно, но:

- не сохраняются списки управления доступом (ACL);
- при импорте файл объединяется с существующим реестром (merge), а не заменяет; отсутствующие в файле ключи остаются без изменений, что может привести к неполному восстановлению;
- удалённые между экспортом и импортом ключи не восстанавливаются;
- некоторые двоичные данные кодируются в HEX-строки, увеличивая размер файла.

Тем не менее, для документирования состояния отдельного ключа (например, `Run`) в тикете .reg-экспорт удобен. Пример создания резервной копии всего куста HKLM\SOFTWARE:

```bash
reg export HKLM\SOFTWARE C:\backups\software_backup.reg
```

### Сохранение бинарных кустов через reg save

Команда `reg save` (аналог WinAPI `RegSaveKey`) создаёт точную двоичную копию куста, включая ACL и все текущие журналы транзакций. Это рекомендуемый метод для судебных копий, поскольку файл идентичен тому, что находится на диске, и может быть загружен в любой редактор реестра для анализа. Синтаксис:

```bash
reg save HKLM\SYSTEM C:\forensics\SYSTEM.hiv
```

При сохранении куста, находящегося в пользовательском профиле (например, HKCU), нужно указывать полный путь в реестре, а не файл NTUSER.DAT:

```bash
reg save HKCU C:\backups\NTUSER.hiv
```

Важно: на момент сохранения система захватывает блокировку и сбрасывает все незавершённые транзакции в основной файл, так что полученный `.hiv` содержит консистентное состояние. Именно этот метод используют средства захвата live-систем (KAPE, FastIR Collector, CyLR) для извлечения кустов. В сценариях SOC-аналитик часто выполняет удалённо:

```powershell
Invoke-Command -ComputerName WS01 -ScriptBlock {
    reg save HKLM\SOFTWARE \\storage\evidence\WS01_SOFTWARE.hiv /y
}
```

### Резервное копирование состояния системы (System State)

Служба резервного копирования Windows Server (wbadmin) и клиентских версий (через панель управления) поддерживает создание резервной копии состояния системы, в которую включаются все кусты плюс база регистрации COM+ и файлы загрузки. При восстановлении System State заменяет кусты целиком, что является самым полным способом отката. Команда:

```bash
wbadmin start systemstatebackup -backupTarget:D:
```

Для SOC этот метод малоприменим при быстром сборе данных с хоста, но полезен при подготовке стенда: развернув копию состояния системы в изолированной среде, аналитик получает точную копию реестра без риска повредить оригинал.

### Копирование из папки RegBack

В системах Windows 7 и некоторых сборках Windows 10 ОС автоматически создавала резервную копию кустов в `%SystemRoot%\System32\config\RegBack` каждые 10 дней. Если эта папка не пуста, файлы в ней — это консистентные копии кустов, сделанные через тот же механизм, что и `reg save`. Проверить наличие можно командой:

```bash
dir C:\Windows\System32\config\RegBack
```

Скопировав файлы на аналитическую станцию, их можно исследовать офлайн. Однако Microsoft отключила эту функцию начиная с Windows 10 версии 1809, оставив лишь пустые заглушки, поэтому полагаться на неё нельзя. При расследовании инцидента на более новых ОС актуальнее использовать теневые копии.

### Доступ к кустам через теневые копии (VSS)

Если служба защиты системы создаёт точки восстановления, теневые копии содержат снимки кустов за разные моменты времени. Утилита `vssadmin list shadows` показывает доступные копии. Затем можно смонтировать нужный снимок через создание символьной ссылки (в Windows 10/11 доступно через `mklink /d` на путь тени) и скопировать файлы кустов, либо использовать инструмент `ShadowCopyView` от NirSoft. Пример перечисления теневых копий:

```cmd
vssadmin list shadows
```

Вывод:

```
Shadow Copy ID: {d46b...}
   Volume: (C:)\\
   Originating Machine: WS01
   ...
```

SOC-аналитик может извлечь историческую версию куста для сравнения с текущей, что особенно ценно при поиске следов сокрытия: например, подозрительный ключ автозагрузки мог быть удалён злоумышленником после выполнения.

### Частичное восстановление из резервной копии

Иногда необходимо восстановить не весь куст, а лишь одно поддерево. Замена всего файла системного куста вручную — рискованная операция, требующая загрузки с внешнего носителя. Более безопасный способ — загрузить резервный куст офлайн в live-реестр и скопировать нужную ветку в рабочий куст с сохранением иерархии. PowerShell предоставляет командлет `Copy-Item`, который при копировании между ветвями реестра работает рекурсивно, но не всегда копирует ACL. Пример восстановления утраченного ключа SAM:

```powershell
reg load HKLM\OldSAM D:\backups\SAM
Copy-Item -Path 'Registry::HKLM\OldSAM\SAM\Domains\Account\Users\000001F4' -Destination 'Registry::HKLM\SAM\SAM\Domains\Account\Users\000001F4' -Recurse -Force
reg unload HKLM\OldSAM
```

Внимание: неосторожные манипуляции с SAM могут вывести систему из строя; данная операция — для продвинутых пользователей с документированной причиной. Альтернативно можно экспортировать ветку в .reg и импортировать, но при этом ACL будут потеряны.

## Сквозной практический пример: выявление вредоносной автозагрузки через офлайн-анализ куста

### Исходные условия

На удалённом компьютере под управлением Windows 11 (имя `WS02`) сработало оповещение EDR о подозрительном процессе. SOC-аналитик L1 должен, не прерывая работу пользователя, изъять куст `SOFTWARE`, исследовать точку закрепления и сохранить снимок для архива. Доступ к WS02 осуществляется по сети с правами локального администратора. Инструментарий: командная строка с `reg.exe`, рабочая станция аналитика с Registry Explorer, PowerShell.

### Шаги

**Шаг 1: Сохранение куста SOFTWARE на сетевой ресурс**

Через PowerShell Remoting выполняем на WS02:

```powershell
Invoke-Command -ComputerName WS02 -ScriptBlock {
    reg save HKLM\SOFTWARE \\FileServer\Evidence\WS02_SOFTWARE.hiv /y
}
```

Ожидаемый результат: сообщение «The operation completed successfully». Появление файла `WS02_SOFTWARE.hiv` в сетевой папке.

**Шаг 2: Загрузка куста на аналитической станции офлайн-инструментом**

На рабочей станции аналитика запускаем Registry Explorer, открываем файл `\\FileServer\Evidence\WS02_SOFTWARE.hiv`. Альтернативно, используем PowerShell с `reg load`:

```powershell
reg load HKLM\WS02_SW "\\FileServer\Evidence\WS02_SOFTWARE.hiv"
```

Убеждаемся, что загрузка успешна:

```powershell
Get-ChildItem "Registry::HKEY_LOCAL_MACHINE\WS02_SW\Microsoft\Windows\CurrentVersion\Run" -ErrorAction SilentlyContinue
```

**Шаг 3: Просмотр и извлечение подозрительных значений**

Проверяем содержимое Run-ключей:

```powershell
Get-ItemProperty "Registry::HKEY_LOCAL_MACHINE\WS02_SW\Microsoft\Windows\CurrentVersion\Run"
```

Вывод (иллюстративная схема):

```
SecurityHealth       : C:\Windows\system32\SecurityHealthSystray.exe
WindowsDefender      : "C:\Program Files\Windows Defender\MSASCuiL.exe"
WMI_Provider         : C:\Users\Public\wmi_provider.exe
```

Значение `WMI_Provider`, указывающее на `C:\Users\Public\wmi_provider.exe`, не является легитимным. Экспортируем этот фрагмент в текстовый файл отчёта:

```powershell
Get-ItemProperty "Registry::HKEY_LOCAL_MACHINE\WS02_SW\Microsoft\Windows\CurrentVersion\Run" |
    Out-File C:\Reports\WS02_runkeys.txt
```

**Шаг 4: Создание частичного .reg-бэкапа для приложения к тикету**

Экспортируем только анализируемую ветку в REG-файл:

```bash
reg export "HKLM\WS02_SW\Microsoft\Windows\CurrentVersion\Run" C:\Reports\WS02_run.reg
```

Фрагмент полученного файла:

```
Windows Registry Editor Version 5.00

[HKEY_LOCAL_MACHINE\WS02_SW\Microsoft\Windows\CurrentVersion\Run]
"SecurityHealth"="C:\\Windows\\system32\\SecurityHealthSystray.exe"
"WindowsDefender"="\"C:\\Program Files\\Windows Defender\\MSASCuiL.exe\""
"WMI_Provider"="C:\\Users\\Public\\wmi_provider.exe"
```

Индикатор закрепления документирован. Исходный бинарный куст `WS02_SOFTWARE.hiv` сохраняется как полносвязный образ для возможного дальнейшего анализа.

**Шаг 5: Выгрузка куста и очистка**

```powershell
reg unload HKLM\WS02_SW
Remove-Item C:\Reports\WS02_run.reg -Force   # при необходимости
```

Проверка: `Test-Path "Registry::HKEY_LOCAL_MACHINE\WS02_SW"` возвращает `False`.

### Ожидаемый вывод

Пример демонстрирует типовой workflow SOC L1: безопасное изъятие куста утилитой `reg save`, офлайн-просмотр для поиска аномалий, создание полного бэкапа куста и дополнительного текстового экспорта улик. Методика минимизирует воздействие на рабочую станцию пользователя, обеспечивает сохранность артефактов и формирует отчётную базу для эскалации инцидента.
