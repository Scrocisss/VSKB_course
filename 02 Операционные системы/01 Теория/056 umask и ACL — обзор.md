# Права доступа к файлам в Linux: umask и ACL

## 1. Контекст и базовые понятия: от традиционных прав к расширенному управлению доступом

Каждый объект файловой системы в Linux (файл, каталог, именованный канал) обладает стандартным набором из трёх классов владения: **владелец-пользователь (u)**, **владелец-группа (g)** и **остальные (o)**. Для каждого класса независимо задаются три базовых права: чтение (r), запись (w) и исполнение (x). Эта модель зафиксирована в POSIX-совместимых системах и обеспечивает дискреционное управление доступом, но имеет врождённое ограничение: невозможно предоставить разные разрешения двум разным пользователям, не являющимся владельцем, или нескольким группам одновременно [Red Hat, Configuring basic system settings, Chapter 10 / 10.1. Managing file permissions](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/configuring_basic_system_settings/managing-file-system-permissions_configuring-basic-system-settings).

Для расширения возможностей традиционных битов разрешений Linux предлагает два дополнительных механизма: **umask** (маска создания режима доступа к файлам) и **ACL** (Access Control Lists — списки управления доступом). В совокупности они позволяют администратору гибко задавать права, наследуемые новыми объектами, и назначать доступ индивидуальным пользователям и группам без изменения владельца файла или членства в первичной группе.

**umask** — это значение (маска), вычитаемое из базовых прав, которые процесс пытается установить при создании файла или каталога. Она действует на уровне процесса, не хранится в метаданных объектов и предназначена для ужесточения прав, назначаемых по умолчанию [umask(2) — Arch manual pages](https://man.archlinux.org/man/umask.2.ru). Прикладные программы, создающие файлы через системные вызовы `open(2)` или `mkdir(2)`, обычно запрашивают полные права (например, 0666 для файлов и 0777 для каталогов), а ядро применяет к этим запросам текущую umask, отбрасывая указанные в маске биты. Итоговые права вычисляются как `mode & ~umask` (где `mode` — аргумент системного вызова).  

**ACL** — это список дополнительных записей, ассоциированных с файлом или каталогом и определяющих разрешения для произвольных пользователей и групп. ACL в Linux реализованы на основе черновиков POSIX 1003.1e и 1003.2c (хотя они официально не были приняты как стандарт) и поддерживаются многими файловыми системами, включая ext4, XFS, btrfs, NFSv4 [SLES 12 SP5 Security and Hardening Guide, Chapter 11 — Access Control Lists in Linux](https://documentation.suse.com/sles/12-SP5/html/SLES-all/cha-security-acls.html). В отличие от umask, ACL являются постоянным атрибутом объекта и могут содержать записи для именованных пользователей, именованных групп, а также специальную запись-маску, регулирующую эффективные права.

Ключевые различия между тремя сущностями систематизирует таблица ниже. Она помогает избежать распространённой путаницы: umask иногда ошибочно воспринимают как способ задать права «всем», а ACL — как замену `chmod`.

| Сущность | Область действия | Где хранится и кем применяется | Характер влияния | Типичные команды/API |
|----------|------------------|----------------------------------|-------------------|-----------------------|
| Традиционные биты разрешений (`rwx` для u/g/o) | Один файл или каталог; только три уровня доступа (владелец, группа, остальные) | Метаданные inode; интерпретируются ядром при каждой попытке доступа | Определяют фактический доступ; изменяются явными `chmod` | `chmod`, `ls -l`, системные вызовы `stat()`, `chmod()` |
| umask (маска создания) | Процесс и его потомки (глобальная для сеанса) | Переменная ядра на уровне процесса; не видна в метаданных файлов | Модифицирует права, запрашиваемые при создании объектов (только ужесточает, отбрасывая биты) | команда оболочки `umask`, системный вызов `umask()` |
| ACL (POSIX ACL) | Отдельные именованные пользователи и группы, а также владелец, группа-владелец и остальные | Расширенные атрибуты (xattrs) файла или каталога; часть метаданных | Добавляет детализированные разрешения поверх традиционной модели; может включать наследуемые (**default**) записи для каталогов | `setfacl`, `getfacl`, библиотеки libacl, системный вызов `setxattr()` |

Механизмы umask и ACL не изолированы — они взаимодействуют при создании новых объектов. Если родительский каталог не имеет **ACL по умолчанию** (default ACL), то процесс создания проходит в два этапа: приложение передаёт ядру желаемый `mode` (например, 0666), ядро обрезает его текущей umask вызывающего процесса, и полученные биты сохраняются в inode. Если же на каталоге задан default ACL, то umask **игнорируется** — ядро строит начальные разрешения на основе наследуемого ACL, а биты, отсутствующие в аргументе `mode`, дополнительно сбрасываются [umask(2) — Linux manual page](https://man7.org/linux/man-pages/man2/umask.2.html). Эта логика гарантирует, что наследуемые права не будут случайно ужесточены umask’ом пользователя, создающего файл.

Дополнительное взаимодействие возникает при использовании команд `chmod` в символьной нотации: без указания класса пользователей (т. е. без символов `u`, `g`, `o`) `chmod` применяет текущую umask к запрошенным изменениям, как если бы выполнялась операция `chmod a±perms`, но биты, установленные в umask, не затрагиваются [umask — Wikipedia](https://en.wikipedia.org/wiki/Umask). Это часто приводит к неожиданным результатам для пользователей, привыкших к явному указанию класса.

Таким образом, модель прав доступа в современном Linux представляет собой трёхслойную систему:
1. **базовые биты разрешений** (контролируются через `chmod`);
2. **umask** — фильтр, ограничивающий права при создании объектов (при отсутствии default ACL);
3. **ACL** — расширенное переопределение базовых прав и наследование с возможностью индивидуальной настройки.

Понимание этой иерархии и приоритетов критически важно для специалиста SOC L1, анализирующего инциденты, связанные с несанкционированным доступом, а также для администраторов, внедряющих политики разграничения доступа.

## 2. Внутреннее устройство umask и ACL: форматы, маски и правила вычисления эффективных прав

В данном разделе рассматривается внутренняя логика обоих механизмов. Так как тема охватывает два разнородных компонента — числовую маску процесса и структурированный список записей — изложение разделено на подразделы, каждый из которых углубляется в особенности устройства одной из сущностей, а затем показывает их совместную работу при создании файлов.

### 2.1. umask как битовая маска процесса

umask представляет собой целое число (тип `mode_t`), в котором значащими являются только младшие 9 бит — по три бита для владельца, группы и остальных. Биты, установленные в 1, указывают, какие права должны быть **запрещены** при создании новых объектов. Системный вызов `umask(mask)` устанавливает маску процесса равной `mask & 0777` и возвращает предыдущее значение. Маска наследуется дочерними процессами через `fork(2)` и сохраняется при вызове `execve(2)` [umask(2) — Linux manual page](https://man7.org/linux/man-pages/man2/umask.2.html).

Константы, используемые в заголовочном файле `<sys/stat.h>`, соответствуют восьмеричным значениям:

| Символическая константа | Восьмеричное значение | Бит | Описание |
|-------------------------|-----------------------|-----|----------|
| `S_IRUSR` | 0400 | r владельца | Allow read by owner |
| `S_IWUSR` | 0200 | w владельца | Allow write by owner |
| `S_IXUSR` | 0100 | x владельца | Allow execute/search by owner |
| `S_IRGRP` | 0040 | r группы | Allow read by group |
| `S_IWGRP` | 0020 | w группы | Allow write by group |
| `S_IXGRP` | 0010 | x группы | Allow execute/search by group |
| `S_IROTH` | 0004 | r остальных | Allow read by others |
| `S_IWOTH` | 0002 | w остальных | Allow write by others |
| `S_IXOTH` | 0001 | x остальных | Allow execute/search by others |

Типичная заводская umask для обычных пользователей равна 022 (восьмеричное), что соответствует `S_IWGRP | S_IWOTH` — запрет записи для группы и остальных. В результате при создании файла с запрашиваемыми правами 0666 (`rw-rw-rw-`) итоговые права станут 0644 (`rw-r--r--`). Математически это `0644 = 0666 & ~022`. Для каталогов базовый режим 0777 (`rwxrwxrwx`) преобразуется в 0755 (`rwxr-xr-x`).

Изменения, произведённые утилитой `umask` командной оболочки, действуют только на текущий сеанс и его потомков. Для постоянного применения маску определяют в конфигурационных файлах (`/etc/profile`, `~/.bashrc`), где команда `umask <mask>` устанавливает нужное значение.

Важная тонкость: umask никогда не добавляет права — только убирает. Она не может «разрешить» бит, который отсутствовал в аргументе `mode` при открытии файла. Более того, umask не влияет на права, заданные явно через `chmod`, и не применяется к объектам, чьи права уже унаследованы через default ACL.

### 2.2. Структура записей ACL и понятие эффективных прав

ACL файла или каталога состоит из набора текстовых записей, каждая из которых определяет права для определённого субъекта. Спецификация POSIX определяет шесть возможных типов записей, сведённых в таблицу [SUSE LINUX–Administration Guide, Appendix B.3.1](http://www.novell.com/documentation//suse91/suselinux-adminguide/html/apbs03.html):

| Тип записи | Текстовая форма | Описание |
|------------|-----------------|----------|
| owner | `user::rwx` | Права владельца файла (соответствует битам `u`) |
| named user | `user:имя:rwx` | Права конкретного пользователя, не являющегося владельцем |
| owning group | `group::rwx` | Права группы-владельца файла (соответствует битам `g` в минимальном ACL) |
| named group | `group:имя:rwx` | Права конкретной группы |
| mask | `mask::rwx` | Эффективная маска, ограничивающая права всех записей, кроме owner и other |
| other | `other::rwx` | Права остальных пользователей (соответствует битам `o`) |

ACL подразделяются на два класса: **минимальный** и **расширенный**. Минимальный ACL состоит ровно из трёх записей — `user::`, `group::`, `other::` — и полностью эквивалентен традиционным битам прав. Если добавляется хотя бы одна запись типа named user, named group или явная запись mask, ACL становится расширенным, и его поведение меняется.

Ключевой элемент расширенного ACL — запись `mask`. Она вводит понятие **эффективных прав** для именованных пользователей, групп и группы-владельца. Права, фактически предоставляемые этим субъектам, вычисляются как логическое «И» между разрешениями в их записи и разрешениями в маске. Например (иллюстративная схема, значения зависят от установленной ACL):

```text
user:jane:r-x
mask::rw-
эффективные права для jane: r--
```

Если запись маски отсутствует, она неявно вычисляется как объединение всех прав в записях named user, owning group и named group, но при ручной установке ACL маску рекомендуется задавать явно.

Принципиально различное отображение групповых прав в минимальном и расширенном ACL иллюстрируется следующей схемой (основанной на рисунках B.1 и B.2 документации SUSE):

**Минимальный ACL (без mask)**
```text
user::rwx    →   традиционный «владелец» = rwx
group::r-x   →   традиционная «группа» = r-x
other::---   →   традиционные «остальные» = ---
```

**Расширенный ACL (с mask)**
```text
user::rwx             →   традиционный «владелец» = rwx
user:jane:rwx         }   эффективные права jane = rw- (ограничены маской)
group::r-x            }
group:devs:rwx        }   все эти групповые записи ограничиваются маской
mask::rw-             →   традиционная «группа» = rw- (← поле берётся из маски)
other::---            →   традиционные «остальные» = ---
```

Таким образом, вывод `ls -l` для файла с расширенным ACL показывает права группы не из записи `group::`, а из маски. Это сделано для обратной совместимости: приложения, не знающие об ACL, видят в поле групповых прав максимальное разрешение, которое реально предоставляется любой из групповых записей (включая named users). Сама группа-владелец может обладать более широкими правами в своей записи, но фактически она ограничена маской так же, как и все остальные дополнительные записи.

Изменение традиционных битов через `chmod` воздействует на ACL: модификация групповых битов приводит к изменению записи mask, а изменение битов владельца или остальных — к изменению соответствующих записей `user::` и `other::`. Это гарантирует, что базовые права всегда являются «верхней планкой» для всех уточнений, сделанных через ACL [Red Hat, 10.1. Managing file permissions, описание взаимодействия](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/configuring_basic_system_settings/managing-file-system-permissions_configuring-basic-system-settings).

### 2.3. Взаимодействие umask и ACL при создании объектов

При создании нового файла или каталога ядро действует по следующему алгоритму, учитывающему наличие или отсутствие default ACL у родительского каталога:

1. Если родительский каталог **не имеет** default ACL, итоговые права = `mode & ~umask`. Здесь `mode` — аргумент, переданный программой (например, 0666 для `creat()`, 0777 для `mkdir()`). umask процесса просто отсекает запрещённые биты.
2. Если родительский каталог **имеет** default ACL, umask игнорируется. Вместо этого:
   - Из записей default ACL формируются начальные записи для нового объекта: `default:user::` становится `user::`, `default:group::` → `group::`, `default:other::` → `other::`, а `default:user:имя:` и `default:group:имя:` копируются напрямую как именованные записи.
   - На основе унаследованных прав и аргумента `mode` вычисляется финальная маска (mask). При этом права, заданные в `mode`, но отсутствующие в inherited ACL, сбрасываются: финальные биты = inherited_permissions ∩ (mode и права из ACL). Это означает, что если default ACL предоставляет обширные права, а программа запросила более ограниченный mode, итоговые права будут соответствовать более строгим ограничениям.

Пример из документации к umask иллюстрирует это поведение: default ACL, эквивалентный umask 022 (`u::rwx,g::r-x,o::r-x`), при запросе `mode=0666` даст файл с правами 0644 (`rw-r--r--`), несмотря на то, что umask процесса мог быть иным [umask(2) — Linux manual page](https://man7.org/linux/man-pages/man2/umask.2.html). Именно поэтому default ACL часто используется для создания общих каталогов, где необходимо принудительно устанавливать групповые разрешения независимо от пользовательских umask.

Таким образом, выбор между управлением через umask и default ACL зависит от требований к наследованию. Если нужна простая политика типа «пользователь всегда получает права 0755 на каталоги», достаточно umask. Если же требуется гибкое назначение прав для нескольких групп и пользователей с гарантированным наследованием, правильным выбором является default ACL.

## 3. Применение и работа с umask и ACL: команды, сценарии и подводные камни

Практическая работа с umask и ACL требует знания утилит командной строки, файлов конфигурации и типовых административных процедур. В этом разделе описываются основные операции и инструменты, а также разбираются ошибки, часто встречающиеся при настройке прав в корпоративной среде.

### 3.1. Просмотр и изменение umask

Значение umask текущего сеанса отображается встроенной командой оболочки `umask` (без аргументов). Вывод обычно в восьмеричном виде, однако может быть в символьной форме при вызове с опцией `-S`:

```bash
$ umask
0022
$ umask -S
u=rwx,g=rx,o=rx
```

Для временного изменения маски в сеансе используется та же команда с аргументом — восьмеричным числом либо символьной строкой:

```bash
$ umask 027   # -w для группы, полный запрет для остальных
$ umask u=rwx,g=rx,o=
```

Постоянное значение задаётся в файлах инициализации оболочки (например, `~/.bashrc`), общесистемных профилях (`/etc/profile`, `/etc/bash.bashrc`) или через PAM-модуль `pam_umask`. Типичные значения для многопользовательских систем: 022 или 002 (разрешить запись группе). В серверных окружениях, ориентированных на безопасность, иногда устанавливают 077, полностью запрещая доступ группе и остальным.

Демонстрация влияния umask на создаваемые файлы без вмешательства ACL:

```bash
$ umask 077
$ touch testfile
$ mkdir testdir
$ ls -ld testfile testdir
-rw------- 1 alice alice  0 Mar  5 10:00 testfile
drwx------ 2 alice alice 40 Mar  5 10:00 testdir
```

Здесь базовый `mode` для файла — 0666, после применения `077`: `0666 & ~077 = 0600` (rw-------). Для каталога `0777 & ~077 = 0700` (rwx------).

Важно помнить, что umask никак не влияет на уже существующие объекты; она применяется только при создании новых.

### 3.2. Управление ACL с помощью setfacl и getfacl

Работа с ACL осуществляется парой утилит из пакета `acl`:

- **`getfacl`** — отображение ACL файла или каталога, включая default-записи.
- **`setfacl`** — модификация (добавление, изменение, удаление) записей ACL.

Для работы с ACL файловая система должна быть смонтирована с опцией `acl`. Большинство современных дистрибутивов (RHEL, SUSE, Ubuntu) включают её по умолчанию для ext4, XFS, но проверить не помешает:

```bash
$ mount | grep " / "
/dev/sda1 on / type ext4 (rw,relatime,acl)
```

Если опция отсутствует, её можно добавить в `/etc/fstab`:
```
/dev/sda1  /  ext4  defaults,acl  0 1
```
и перемонтировать: `mount -v -o remount /` [Server Fault, Can I override my umask using ACLs?](https://serverfault.com/questions/349145/can-i-override-my-umask-using-acls-to-make-all-files-created-in-a-given-director).

#### Добавление и изменение ACL

Синтаксис `setfacl` для модификации:
```bash
setfacl -m <запись> <файл>
```
где запись может быть вида `u:username:permissions`, `g:groupname:permissions`, `m::permissions`, `o::permissions`. Права указываются в символьной форме (`r`, `w`, `x`) или восьмеричной маске.

Пример предоставления пользователю `jane` прав на чтение и запись файла `report.txt`:
```bash
$ setfacl -m u:jane:rw- report.txt
$ getfacl report.txt
# file: report.txt
# owner: alice
# group: staff
user::rw-
user:jane:rw-
group::r--
mask::rw-
other::r--
```

Обратите внимание, что при добавлении первой именованной записи утилита автоматически вычисляет и устанавливает маску, равную объединению прав всех групповых записей и именованных пользователей (в данном примере `rw-`). При необходимости маску можно изменить явно:

```bash
$ setfacl -m m::r-- report.txt
$ getfacl report.txt
...
user:jane:rw-          #effective:r--
mask::r--
```

Теперь эффективные права Джейн ограничены маской только чтением.

#### Default ACL для каталогов

Ключевая возможность POSIX ACL — наследование через **default** записи на каталогах. Default ACL определяется опцией `-d` команды `setfacl` и определяет, какие записи будут автоматически скопированы на новые объекты, создаваемые внутри каталога. Типичный пример — создание общего каталога для группы `developers`, где все новые файлы должны быть доступны группе на чтение и запись:

```bash
$ mkdir /shared
$ chgrp developers /shared
$ chmod 2770 /shared          # setgid + базовые права
$ setfacl -d -m g:developers:rwx /shared
$ getfacl /shared
# file: shared
# owner: root
# group: developers
# flags: -s-
user::rwx
group::rwx
other::---
default:user::rwx
default:group::rwx
default:group:developers:rwx
default:mask::rwx
default:other::---
```

Теперь любой файл, созданный в `/shared`, получит ACL, включающий запись `group:developers:rwx`, а благодаря маске `rwx` (при условии, что `mode` включает эти биты) группа получит полные права. Установка setgid бита (`chmod g+s`) гарантирует, что группа-владелец новых файлов будет унаследована от каталога, а не от первичной группы создателя [Права в Linux — Habr](https://habr.com/ru/articles/469667).

### 3.3. Совместное использование umask и ACL: приоритеты и ограничения

При работе в средах, где одновременно настроены пользовательские umask и default ACL на каталогах, следует учитывать несколько важных аспектов:

1. **Приоритет default ACL над umask при создании.** Если на родительском каталоге есть default ACL, umask создающего процесса полностью игнорируется. Это означает, что пользователь с umask 077, создавая файл в таком каталоге, не сможет заблокировать групповые разрешения, предписанные ACL. Данное поведение является штатным и часто используется для принудительной реализации политик безопасности.
2. **Поведение команды `chmod` без указания класса.** Как отмечено в Wikipedia (umask), многие реализации `chmod` при символьной записи без указания `who` (например, `chmod +x`) применяют текущую umask к запрашиваемым изменениям. Это может приводить к неожиданностям: в окружении с umask 077 команда `chmod +rw` не добавит чтение/запись для группы и остальных, потому что эти биты запрещены маской. Рекомендуется всегда явно указывать класс: `chmod a+x`, `chmod u+w` и т.п.
3. **Маска ACL и `chmod`.** При изменении групповых битов через `chmod` модифицируется именно запись mask ACL, а не owning group. Если администратор случайно выполнит `chmod g-w` на файле с расширенным ACL, он может заблокировать запись всем именованным пользователям и группам, так как эффективные права пересчитываются через новую маску.
4. **Ограничения на некоторых файловых системах.** Не все ФС поддерживают POSIX ACL (например, FAT, NTFS при использовании драйверов ядра, NFS в некоторых конфигурациях). Для таких ФС иногда применяются mount-опции `umask`, `fmask`, `dmask`, которые задают маски для отображения прав, но это не имеет отношения к ACL — это отдельный механизм, симулирующий права на ФС без нативной поддержки UNIX-прав [umask — Wikipedia](https://en.wikipedia.org/wiki/Umask).

Ниже приведён практический пример проверки взаимодействия: создание файла в каталоге с default ACL при umask 077.

```bash
$ umask 077
$ mkdir /data
$ setfacl -d -m g:analysts:r-x /data
$ cd /data
$ touch analysis.txt
$ getfacl analysis.txt
# file: analysis.txt
# owner: alice
# group: analysts
user::rw-
group::r-x          # эффективные права: r-x
group:analysts:r-x  # эффективные права: r-x
mask::r-x
other::---
```

Несмотря на umask 077, файл получил права `r-x` для группы `analysts`. Это объясняется наследованием default ACL и игнорированием umask. Без default ACL результат был бы `-rw-------`.

### 3.4. Типичные сценарии использования

В практике администрирования и SOC L1 можно выделить несколько повторяющихся сценариев:

- **Совместная работа над проектом.** Для каталога `/project` создаётся группа `project-team`, назначается setgid и default ACL с правами `g:project-team:rwx`. Любой участник группы автоматически получает доступ к новым файлам, а umask участников не имеет значения.
- **Публикация через веб-сервер.** Директория `/var/www/html` с default ACL `u:www-data:rX` и `g:webadmins:rwX` позволяет веб-серверу читать контент, а администраторам — модифицировать, независимо от umask процессов-генераторов контента.
- **Журналы аудита.** Для каталога с логами может быть установлен ACL, дающий право чтения только группе `auditors`, а umask для пишущего сервиса — 077, что предотвратит случайное раскрытие логов другим пользователям.
- **Выявление инцидентов.** При обнаружении подозрительного файла с расширенным ACL специалист SOC L1 может с помощью `getfacl` проанализировать, какие именно пользователи или группы получили доступ, и определить, является ли это следствием легитимной настройки или атаки (например, злоумышленник мог добавить запись `u:backdoor:rwx`).

Понимание команд и их вывода позволяет быстро интерпретировать списки прав при разборе инцидентов и выполнять корректирующие действия.

## 4. Сквозной практический пример: настройка защищённого общего каталога для группы разработчиков

Лабораторный сценарий, демонстрирующий совместную работу umask и ACL для достижения чётких прав доступа к файлам проекта. Задача: каталог `/opt/devproject` должен быть доступен на чтение, запись и выполнение (для каталогов) всем членам группы `developers`; все новые файлы и подкаталоги должны автоматически получать соответствующие права и принадлежать группе `developers`, независимо от индивидуальной umask пользователей.

**Исходные условия**

- ОС: Red Hat Enterprise Linux 8, файловая система ext4, ACL включены по умолчанию.
- Пользователь `alice` — член группы `developers`, её umask — 0077 (настроена в `~/.bashrc`).
- Целевой каталог: `/opt/devproject`.
- Административные действия выполняются от `root`.

**Шаг 1. Создание группы и каталога, установка начальных прав и setgid**

```bash
# groupadd developers
# mkdir /opt/devproject
# chgrp developers /opt/devproject
# chmod 2770 /opt/devproject
# ls -ld /opt/devproject
drwxrws--- 2 root developers 4096 Mar  5 14:00 /opt/devproject
```

Установлен setgid-бит (`2` в начале), поэтому новые объекты унаследуют группу `developers`, а не основную группу создателя.

**Шаг 2. Проверка текущей umask пользователя alice**

```bash
# su - alice
$ umask
0077
```

Без дополнительных ACL создаваемый файл получит права 0600 (rw-------) и группу `developers` (благодаря setgid), но группа не будет иметь доступа.

**Шаг 3. Создание тестового файла ДО настройки default ACL**

```bash
$ touch /opt/devproject/test_before
$ ls -l /opt/devproject/test_before
-rw------- 1 alice developers 0 Mar  5 14:02 test_before
```

Как видно, членам группы разработчиков файл недоступен — права для группы отсутствуют.

**Шаг 4. Установка default ACL на каталог**

Администратор (`root`) выполняет:

```bash
# setfacl -d -m g:developers:rwx /opt/devproject
# getfacl /opt/devproject
# file: opt/devproject
# owner: root
# group: developers
# flags: -s-
user::rwx
group::rwx
other::---
default:user::rwx
default:group::rwx
default:group:developers:rwx
default:mask::rwx
default:other::---
```

Default-записи теперь гарантируют, что любой новый объект получит named group запись `developers:rwx` и маску `rwx`.

**Шаг 5. Создание нового файла после настройки ACL**

Пользователь `alice` с umask 077 создаёт файл:

```bash
$ touch /opt/devproject/test_after
$ ls -l /opt/devproject/test_after
-rw-rw----+ 1 alice developers 0 Mar  5 14:05 test_after
$ getfacl /opt/devproject/test_after
# file: opt/devproject/test_after
# owner: alice
# group: developers
user::rw-
group::rwx          # effective: rw-
group:developers:rwx    # effective: rw-
mask::rw-
other::---
```

Несмотря на umask 077, файл получил права группы `rw-` (маска вычислена как `rwx` ∩ `0666` → `rw-`). Группа `developers` имеет полный доступ на чтение и запись. Флаг `+` в выводе `ls` подтверждает наличие ACL. Другие пользователи (other) доступа не имеют, что соответствует политике.

**Шаг 6. Проверка создания подкаталога**

```bash
$ mkdir /opt/devproject/subdir
$ getfacl /opt/devproject/subdir
# file: opt/devproject/subdir
# owner: alice
# group: developers
# flags: -s-
user::rwx
group::rwx
group:developers:rwx
mask::rwx
other::---
default:user::rwx
default:group::rwx
default:group:developers:rwx
default:mask::rwx
default:other::---
$ ls -ld /opt/devproject/subdir
drwxrws---+ 2 alice developers 4096 Mar  5 14:10 subdir
```

Подкаталог унаследовал и ACL, и default ACL, и setgid-флаг (`s` в поле группы). Таким образом, вся иерархия внутри `/opt/devproject` будет автоматически поддерживать согласованные права доступа.

**Вывод примера**

Данный сквозной пример наглядно демонстрирует, как комбинация setgid, default ACL и игнорирования umask позволяет построить надёжную и предсказуемую модель коллективной работы, не зависящую от индивидуальных настроек пользователей. Для специалиста SOC L1 подобная конфигурация означает, что при расследовании инцидента можно сразу судить о легитимности групповых прав на основании ACL родительского каталога, а аномалии (например, файл без ожидаемой записи `group:developers`) будут свидетельствовать о нарушении или ошибке.
