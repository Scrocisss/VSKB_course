# Реестр Windows: кусты и ключевые разделы HKLM, HKCU, HKCR, HKU

## 1. Реестр как иерархическая база данных: понятие кустов и их назначение

Реестр Windows — это централизованное иерархическое хранилище низкоуровневых параметров операционной системы, драйверов, служб и приложений. Он заменил разрозненные INI-файлы, обеспечив атомарность обновлений, контроль версий и разграничение доступа для многопользовательской среды. Реестр организован в виде дерева, узлы которого называются ключами; ключи могут содержать подключи и значения. Корневыми узлами этого дерева выступают **предопределённые разделы верхнего уровня**, традиционно именуемые **кустами** (registry hives). Термин «куст» отражает тот факт, что каждая такая ветвь физически хранится на диске в виде отдельного файла (или набора файлов), который ядро загружает в память при старте системы, формируя единое логическое пространство.

С точки зрения SOC-аналитика и специалиста по форензике, кусты — это не просто разделы реестра, а первоочередные места поиска артефактов, поскольку в них накапливаются следы действий пользователей, установка программ, изменения конфигурации и признаки присутствия вредоносного ПО. Знание того, какой куст за что отвечает, позволяет быстро локализовать нужную категорию доказательств.

Непосредственно в редакторе реестра (`regedit.exe`) отображаются несколько корневых ключей, каждый из которых имеет устоявшуюся аббревиатуру (HKLM, HKCU, HKCR, HKU, HKCC и другие). Нижеприведённая таблица сопоставляет эти аббревиатуры с полными именами, поясняет их роль и указывает на соответствующие файлы данных.

| Аббревиатура | Полное имя | Назначение | Файловая основа |
|--------------|------------|------------|-----------------|
| HKLM | HKEY_LOCAL_MACHINE | Системные параметры, общие для всех пользователей: оборудование, ядро, драйверы, установленное ПО, политики безопасности. | %SystemRoot%\System32\config\SOFTWARE, SYSTEM, SAM, SECURITY (и соответствующие логи) |
| HKCU | HKEY_CURRENT_USER | Настройки и профиль текущего интерактивного пользователя (обои, принтеры, переменные среды, пути к недавним файлам). | %UserProfile%\NTUSER.DAT и файлы классов %UserProfile%\AppData\Local\Microsoft\Windows\UsrClass.dat |
| HKU | HKEY_USERS | Содержит подразделы для всех профилей, когда-либо загруженных на машине, включая шаблон .DEFAULT и SID-идентификаторы конкретных пользователей. HKCU — это символическая ссылка на один из таких подразделов. | Каждый профиль — собственный NTUSER.DAT (и UsrClass.dat) в каталоге пользователя; шаблон — %SystemRoot%\System32\config\default |
| HKCR | HKEY_CLASSES_ROOT | Объединённое представление ассоциаций файловых расширений, COM-объектов и обработчиков протоколов, полученное путём слияния ветвей HKLM\Software\Classes и HKCU\Software\Classes (пользовательские настройки имеют приоритет). | Не хранится отдельным файлом; является представлением, динамически собираемым из частей SOFTWARE и пользовательских UsrClass.dat |
| HKCC | HKEY_CURRENT_CONFIG | Текущий профиль оборудования, используемый при загрузке; фактически — ссылка на HKLM\System\CurrentControlSet\Hardware Profiles\Current. | Не хранится постоянно; собирается на этапе загрузки из параметров HKLM\System. |

Помимо перечисленных, существуют служебные кусты, недоступные через `regedit` на современных системах (например, HKEY_PERFORMANCE_DATA для счётчиков производительности), но в контексте анализа безопасности они не являются первоочередными.

Кусты можно просмотреть не только визуально, но и программно — с помощью интерфейса командной строки `reg query`. Следующая команда перечисляет все корневые разделы, доступные в редакторе, и демонстрирует, что каждый куст является начальной точкой обширного поддерева:

```powershell
reg query HKLM
reg query HKCU
reg query HKU
reg query HKCR
reg query HKCC
```

Вывод каждой команды показывает непосредственные подключи (например, для HKLM — `SOFTWARE`, `SYSTEM`, `SAM`, `SECURITY`), подтверждая, что перед нами именно корневые точки подключения.

Важный для аналитика SOC аспект: все кусты подчиняются иерархической модели прав доступа. Ключи в HKLM по большей части доступны обычным пользователям только для чтения, запись разрешена администраторам и системе. Исключение составляет `HKLM\SOFTWARE` — некоторые его ветви (например, `Microsoft\Windows\CurrentVersion` или разделы определённых приложений) могут быть доступны на запись ограниченному кругу, что часто используется вредоносным ПО для закрепления. Пользовательские кусты (HKU\<SID> и HKCU) полностью доступны на запись владельцу профиля, что делает их излюбленным местом для автозагрузки и сохранения конфигурации малвари без повышения привилегий. Таким образом, понимание кустов — это первый шаг к целенаправленному поиску индикаторов компрометации.

## 2. Внутреннее устройство кустов: файлы, иерархия и типы данных

Логическая структура реестра, которую видит пользователь и администратор, базируется на физическом хранении в виде файлов кустов, реализованных в бинарном формате. Каждый файл куста содержит полное дерево ключей и значений, принадлежащих одному корневому узлу. Операционная система в процессе загрузки монтирует эти файлы в глобальное пространство имён `\Registry`, откуда они без изменений транслируются в представление редактора `regedit`. Знание этого механизма критично для форензики, поскольку при извлечении данных с накопителя аналитик работает именно с файлами кустов, а не с их отображением в работающей ОС.

**Физическое расположение ключевых кустов.**  
- Кусты, принадлежащие HKLM, находятся в каталоге `%SystemRoot%\System32\config`. Каждый подкуст представлен отдельным файлом: `SOFTWARE` содержит дерево `HKLM\SOFTWARE`, `SYSTEM` — `HKLM\SYSTEM`, `SAM` — одноимённую защищённую базу учётных записей, а `SECURITY` — политики безопасности. В этой же папке лежат резервные копии и журналы транзакций (файлы с расширениями `.log`, `.sav`).  
- Пользовательский профиль текущего пользователя хранится в `%UserProfile%\NTUSER.DAT`, который монтируется в `HKU\<SID>` и одновременно отображается в HKCU. Поскольку Windows поддерживает разделение классов для каждого пользователя, существует дополнительный файл `UsrClass.dat` (обычно в `AppData\Local\Microsoft\Windows`), который содержит пользовательскую часть `HKCR` (ветвь `HKCU\Software\Classes`).
- Шаблон нового пользователя `.DEFAULT` расположен по адресу `%SystemRoot%\System32\config\default`, он же виден в `HKU\.DEFAULT`.
- Куст HKCR не имеет отдельного физического файла — он является объединением двух источников: машинной части из `HKLM\SOFTWARE\Classes` и пользовательской из `HKCU\Software\Classes`. При конфликте записей преимущество отдаётся пользовательской.

**Иерархическая модель и отображение.**  
В ядре Windows реестр представлен единым корнем `\REGISTRY`, из которого расходятся ветви `\Registry\Machine` (соответствует HKLM), `\Registry\User` (HKU), `\Registry\User\<SID>_Classes` (часть HKCR) и другие. Редактор реестра скрывает эту топологию, предоставляя плоский список корневых ключей, однако понимание реального пространства имён необходимо для работы с Native API, инструментов вроде `reg.exe` и низкоуровневых отладчиков.

Схематично связь видимых разделов и внутреннего пространства имён можно отобразить так:

```text
\REGISTRY
├── MACHINE ────────────────────────────────► HKLM
│   ├── SOFTWARE ──── (монтируется из файла SOFTWARE)
│   ├── SYSTEM ────── (монтируется из файла SYSTEM)
│   ├── SAM ───────── (монтируется из файла SAM)
│   └── SECURITY ──── (монтируется из файла SECURITY)
├── USER ───────────────────────────────────► HKU
│   ├── .DEFAULT ─────── (монтируется из default)
│   ├── S-1-5-21-... ─── (монтируется из NTUSER.DAT каждого пользователя)
│   │   └── Software\Classes ────────────── (монтируется из UsrClass.dat)
│   └── S-1-5-21-..._Classes ─── (отдельный куст классов пользователя)
└── ??? (HKCR — сборка из MACHINE\SOFTWARE\Classes и USER\<SID>_Classes)
```

Каждый куст заголовком содержит сигнатуру `regf` (первые 4 байта файла), что позволяет форензик-инструментам однозначно идентифицировать файлы реестра. Значения внутри кустов хранятся в виде ячеек (cells) бинарного формата, организующих дерево ключей и списков значений.

**Типы данных.**  
Для понимания того, что можно встретить при анализе кустов, важно знать основные типы значений, с которыми работает реестр. Ниже перечислены ключевые, используемые операционной системой и приложениями:

```text
REG_SZ        — строка с завершающим нулём (наиболее частый тип, например, пути к программам).
REG_EXPAND_SZ — строка, содержащая раскрываемые переменные окружения (напр., %SystemRoot%).
REG_MULTI_SZ  — массив строк, оканчивающийся двойным нулём (например, списки DNS-серверов).
REG_DWORD     — 32-битное целое число (часто для флагов, таймаутов, счётчиков).
REG_QWORD     — 64-битное целое число.
REG_BINARY    — произвольные бинарные данные (конфигурации оборудования, ключи продуктов).
```

В контексте форензики аналитик часто конвертирует эти типы: например, временные метки Windows NT хранятся в виде REG_BINARY или REG_QWORD (64-битное количество 100-наносекундных интервалов с 1 января 1601 г.), а пути — в виде REG_EXPAND_SZ. Понимание структуры кустов и их типов — необходимый фундамент для корректной интерпретации артефактов.

## 3. Применение и работа с кустами: детальный обзор HKLM, HKCU, HKCR, HKU

На практике SOC-аналитик или форензик-эксперт взаимодействует с кустами через утилиты командной строки (`reg query`, `reg export`), скрипты (PowerShell, WMI) либо специализированные средства (Registry Explorer, RegRipper). Знание того, в каком кусте и каком подразделе следует искать тот или иной артефакт, позволяет быстро ответить на вопросы, кто, когда и как воздействовал на систему. В этом разделе детально разбираются четыре куста, наиболее актуальных для анализа безопасности.

### 3.1. HKLM — HKEY_LOCAL_MACHINE: системные настройки и глобальные индикаторы

Куст HKLM содержит информацию, единую для всей машины: сведения об оборудовании, установленных службах и драйверах, зарегистрированных приложениях, параметрах загрузки и безопасности. В редакторе реестра видны четыре основных подраздела: `SOFTWARE`, `SYSTEM`, `SAM` и `SECURITY`. Последние два защищены: обычный пользователь не может их прочитать, однако администратор с соответствующими привилегиями может получить доступ.

- **SOFTWARE** — наиболее востребованная при анализе ветка. Здесь хранятся настройки как компонентов Windows, так и сторонних программ. Особое значение имеют:
  * `Microsoft\Windows\CurrentVersion\Uninstall` — перечень установленных приложений с полями `DisplayName`, `InstallDate`, `Publisher`, `UninstallString`. Это отправная точка для обнаружения подозрительного или устаревшего ПО.
  * `Microsoft\Windows\CurrentVersion\Run`, `RunOnce`, `RunServices` — глобальные точки автозагрузки, часто используемые вредоносным ПО для закрепления в системе без информирования пользователя.
  * `Microsoft\Windows NT\CurrentVersion\ProfileList` — список профилей пользователей с привязкой SID к путям; полезен для идентификации учётных записей при разборе HKU.

- **SYSTEM** — содержит информацию о конфигурации оборудования, наборах управления (ControlSet001, ControlSet002 и т.д.) и параметрах загрузки. Для SOC-аналитика важны разделы:
  * `CurrentControlSet\Services` — описание служб; нелегитимная служба часто оставляет здесь свой образ, путь к исполняемому файлу и тип запуска.
  * `CurrentControlSet\Enum\USBSTOR` — история подключённых USB-устройств с идентификаторами (VID, PID, серийными номерами). Позволяет восстановить факты использования сменных носителей.

Пример извлечения всех зарегистрированных приложений с их строками удаления — первый шаг при поиске нежелательного ПО:

```powershell
reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall /s /f "DisplayName" /e
```

Вывод команды может содержать десятки записей, среди которых типичные легитимные пакеты, а также подозрительные имена вроде иллюстративной схемы; в реальной среде аналитик фильтрует результат по дате установки или названию издателя. Значения полей зависят от среды.

Службы, добавленные в обход стандартных механизмов, часто располагаются непосредственно под `HKLM\SYSTEM\CurrentControlSet\Services`. Их проверка выполняется командой:

```cmd
reg query HKLM\SYSTEM\CurrentControlSet\Services\SuspiciousServiceName
```
(где `SuspiciousServiceName` — название, выявленное по другим индикаторам). Вывод демонстрирует тип запуска (`Start`), путь к исполняемому файлу (`ImagePath`) и учётную запись (`ObjectName`), позволяя быстро оценить легитимность службы.

### 3.2. HKCU — HKEY_CURRENT_USER: профиль текущего пользователя и индикаторы активности

Куст HKCU является символической ссылкой на подключ `HKU\<SID>` текущего интерактивного пользователя. Он содержит все настройки, связанные с конкретной учётной записью: оформление рабочего стола, переменные окружения, сетевые принтеры, а главное — подробный журнал действий (через MRU-списки — Most Recently Used) и пользовательские точки автозагрузки.

Файловую основу HKCU составляет `%UserProfile%\NTUSER.DAT`. При входе пользователя ядро загружает этот файл в реестр и привязывает его к соответствующему SID в HKU. Поэтому во время жизни сеанса HKCU всегда отражает актуальное состояние профиля, включая только что произведённые изменения.

Для форензики наибольшую ценность представляют следующие разделы:

- `Software\Microsoft\Windows\CurrentVersion\Run` и `RunOnce` — пользовательские механизмы автозапуска. В отличие от аналогичных веток HKLM, они не требуют прав администратора, что делает их излюбленными для вредоносных программ, запускаемых без эскалации привилегий.
- `Software\Microsoft\Windows\CurrentVersion\Explorer\RecentDocs` — список недавно открывавшихся документов, упорядоченный по расширениям. Наличие файла, открывавшегося до его удаления или копирования на внешний носитель, может служить ключевым свидетельством.
- `Software\Microsoft\Windows\CurrentVersion\Explorer\RunMRU` — команды, выполненные через диалог «Выполнить» (Win+R), с привязкой к порядку вызова и букве.
- `Software\Microsoft\Windows\CurrentVersion\Explorer\ComDlg32\LastVisitedMRU` — пути, используемые в диалогах «Открыть/Сохранить как», часто указывающие на доступ к теневым копиям или внешним хранилищам.

Пример извлечения списка автозагрузки текущего пользователя с последующей проверкой цифровых подписей (в скриптах) — типичная процедура при расследовании закрепления:

```powershell
reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Run
```

Возможный иллюстративный вывод:

```
HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
    OneDrive    REG_SZ    "C:\Users\John\AppData\Local\Microsoft\OneDrive\OneDrive.exe" /background
    MalwareStub REG_SZ    "C:\Users\John\AppData\Roaming\JavaUpdate\javaw.exe"
```

В данном примере вторая запись, `MalwareStub`, указывающая на подозрительный путь без цифровой подписи и с именем процесса, маскирующимся под легитимное обновление, явно требует дальнейшего анализа. SOC-аналитик может перекрёстно проверить `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` на наличие программы с таким же именем, а также сверить хеш исполняемого файла с базами известных угроз.

Ветка `Software\Microsoft\Windows\CurrentVersion\Explorer\RecentDocs` позволяет восстановить, какие файлы открывались пользователем, даже если они были удалены. Команда:

```cmd
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RecentDocs\.docx"
```

выводит бинарные значения (REG_BINARY), содержащие закодированные имена файлов, для интерпретации которых требуется конвертирование с учётом Windows Shell Item формата. Тем не менее, сам факт наличия записей может служить отправной точкой для восстановления хронологии.

### 3.3. HKCR — HKEY_CLASSES_ROOT: ассоциации файлов и скрытые угрозы

Куст HKCR обеспечивает связь между расширениями файлов и программами, которые их обрабатывают, а также регистрацию COM-серверов, обработчиков протоколов и элементов контекстного меню. Для оконечного пользователя это проявляется в виде программ, предлагаемых для открытия файла, или действий в контекстном меню проводника. Внутренне HKCR — это агрегат двух ветвей:

- `HKLM\SOFTWARE\Classes` — системные ассоциации, действующие для всех пользователей;
- `HKCU\Software\Classes` — пользовательские переопределения, имеющие приоритет при конфликте.

Поскольку HKCR не является отдельным файлом, его изменение затрагивает либо системный SOFTWARE-файл (требует прав администратора), либо пользовательский UsrClass.dat (доступен без повышения привилегий). Атаки на HKCR — распространённый приём сохраняющегося вредоносного ПО: подмена обработчика распространённых типов файлов (например, `.txt`, `.lnk`, `http`) так, чтобы при каждом запуске файла выполнялся вредоносный код.

Проверка ассоциации для конкретного расширения выполняется командой:

```cmd
reg query HKCR\.txt\ShellNew
```

Она покажет класс, связанный с расширением, и параметры создания. Для анализа, какая именно программа откроет файл, необходимо обращаться к подключу, соответствующему ProgID:

```cmd
reg query HKCR\txtfile\shell\open\command
```

Примерный вывод (значения иллюстративны):

```
(Default)    REG_SZ    "%SystemRoot%\system32\NOTEPAD.EXE %1"
```

Злоумышленник может изменить это значение на путь к своему трояну, приписав в конце `%1`, чтобы скрытно запускать оригинальное приложение после вредоносного кода. Проверка HKCR в ходе расследования позволяет выявить:

- подменённые ассоциации для распространённых расширений (`txt`, `exe`, `lnk`, `html`);
- левые обработчики URL-протоколов (`http`, `https`, `ftp`, `telnet`);
- подозрительные контекстные меню, добавляемые через `\*\shell\...`;
- нестандартные COM-объекты, способные внедряться в процессы.

Команда для массового поиска изменённых обработчиков (требует скриптовой обработки, но начальная проверка возможна через `reg query`):

```powershell
reg query HKCR /s /f "cmd.exe" /d
```

Эта команда ищет все значения, содержащие подстроку `cmd.exe` (часто используемую в атаках для обратного shell'а) в разделе HKCR. Вывод позволит локализовать конкретные ключи, в которых прописана командная строка.

Отдельного внимания заслуживает раздел `HKCR\Unknown\shell`, используемый для обработки файлов с неизвестными расширениями, — его модификация может привести к выполнению произвольного кода при любом двойном щелчке на «бесхозном» файле.

### 3.4. HKU — HKEY_USERS: профили всех пользователей и шаблон по умолчанию

Куст HKU — это совокупность всех профилей, когда-либо загружавшихся на данном компьютере (и активных в текущий момент). Каждый профиль идентифицируется уникальным идентификатором безопасности (SID) в виде `S-1-5-21-...`. Помимо профилей конкретных пользователей, здесь присутствует подключ `.DEFAULT`, который служит шаблоном для создания профиля нового пользователя (но не применяется к уже существующим).

Важнейшее свойство HKU для аналитика: администратор имеет полный доступ ко всем загруженным пользовательским кустам, что позволяет исследовать профили даже тех пользователей, которые не находятся в системе в данный момент, при условии, что их кусты ранее были загружены (или если аналитик подключает файл `NTUSER.DAT` вручную с помощью `reg load`). Это критично при расследовании инцидентов с компрометацией нескольких учётных записей.

Связь между SID и именем пользователя устанавливается через:

```cmd
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList"
```

Вывод продемонстрирует подразделы с SID, внутри каждого из которых есть значение `ProfileImagePath`, указывающее путь к профилю (например, `C:\Users\John`). Сопоставив эти данные с записями в HKU, аналитик может быстро идентифицировать владельца каждого куста.

Просмотр всех SID, присутствующих в HKU, выполняется просто:

```cmd
reg query HKU
```

Примерный иллюстративный вывод:

```
HKEY_USERS
    .DEFAULT
    S-1-5-21-1234567890-123456789-1234567890-1001
    S-1-5-21-1234567890-123456789-1234567890-1001_Classes
    S-1-5-21-1234567890-123456789-1234567890-1002
    S-1-5-21-1234567890-123456789-1234567890-1002_Classes
```

Ключи с суффиксом `_Classes` содержат пользовательскую часть HKCR. При проведении расследования инцидента с горизонтальным перемещением (lateral movement) злоумышленник мог модифицировать профиль одной учётной записи с сохранением своей нагрузки, а затем переключиться на другую. Сравнительный анализ автозапусков из нескольких профилей в HKU позволит выявить аномалии. Например, следующая команда извлекает точки Run для конкретного SID:

```powershell
reg query "HKU\S-1-5-21-1234567890-123456789-1234567890-1001\Software\Microsoft\Windows\CurrentVersion\Run"
```

Если в профиле обычного пользователя (без административных прав) обнаруживается ключ, запускающий исполняемый файл из временной папки, это явный индикатор компрометации. Кроме того, в HKU под `.DEFAULT` могут быть прописаны старые вредоносные модификации, которые будут активироваться при создании любого нового пользователя, обеспечивая устойчивое закрепление на продолжительное время.

## 4. Сквозной практический пример: поиск следов вредоносной установки через кусты реестра

В этом разделе демонстрируется реалистичный сценарий, с которым может столкнуться аналитик SOC L1: подозрительная программа была установлена на рабочую станцию, причём ни антивирус, ни штатные средства мониторинга не обнаружили угрозу. Задача — используя только стандартные инструменты командной строки и редактор реестра, найти основные артефакты и подтвердить факт присутствия вредоносного ПО.

**Исходные условия:**  
- Версия ОС: Windows 11 22H2, учётная запись пользователя `jdoe` с правами локального администратора.  
- Из журналов событий известно, что в определённый промежуток времени происходило выполнение неизвестного файла с диска `C:\Users\jdoe\Downloads`.  
- Подозревается, что вредонос внедрился через фишинговый документ и закрепился в системе.

**Шаг 1. Поиск следов установки в HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall**  

Вредоносные программы, пытаясь имитировать легитимное ПО, нередко добавляют запись в список установленных приложений, чтобы избежать обнаружения при поверхностном просмотре «Программы и компоненты». Выполним поиск по ключевому слову, характерному для подозрительного приложения (например, «JavaUpdate» или «AdobeHelper»):

```powershell
reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall /s /f "JavaUpdate"
```

Ожидаемый вывод (иллюстративный):

```
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\JavaUpdate
    DisplayName    REG_SZ    Java Update Manager
    UninstallString    REG_SZ    "C:\Users\jdoe\AppData\Roaming\JavaUpdate\uninstall.exe"
    InstallDate    REG_SZ    20250315
    Publisher    REG_SZ    Oracle Corporation
```

Аналитик обращает внимание, что путь к деинсталлятору указывает на пользовательскую папку `AppData\Roaming\JavaUpdate`, а не на стандартный `C:\Program Files\Java`, что нетипично для легитимного обновления Oracle. Это первый индикатор.

**Шаг 2. Проверка автозагрузки текущего пользователя (HKCU\...\Run)**  

Убедившись, что пользователь запускал файл из папки загрузок, проверяем автозагрузку его учётной записи:

```powershell
reg query HKCU\Software\Microsoft\Windows\CurrentVersion\Run
```

Вывод:

```
HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run
    OneDrive    REG_SZ    "C:\Users\jdoe\AppData\Local\Microsoft\OneDrive\OneDrive.exe" /background
    JavaManager REG_SZ    "C:\Users\jdoe\AppData\Roaming\JavaUpdate\javaw.exe"
```

Запись `JavaManager` снова указывает на тот же каталог. Путь к `javaw.exe` в `AppData\Roaming` в сочетании с «менеджером» не является стандартным. Наличие этой записи означает, что программа будет автоматически запускаться при каждом входе пользователя, обеспечивая постоянство.

**Шаг 3. Анализ HKCR на наличие изменённых ассоциаций**  

Для проверки возможной подмены обработчика файлов выполним поиск по всем значениям HKCR, содержащим путь к подозрительной папке:

```powershell
reg query HKCR /s /f "AppData\\Roaming\\JavaUpdate"
```

Предположим, обнаруживается ключ:

```
HKEY_CLASSES_ROOT\jarfile\shell\open\command
    (Default)    REG_SZ    "C:\Users\jdoe\AppData\Roaming\JavaUpdate\javaw.exe" "%1"
```

Это означает, что при попытке открыть любой `.jar` файл будет выполнен вредоносный `javaw.exe` с передачей пути к файлу в качестве параметра. Таким образом, злоумышленник получил выполнение кода при каждом запуске Java-архивов. Аналитик также проверяет стандартные расширения (`.txt`, `.exe`), но в данном сценарии атака нацелена именно на Java-файлы, вероятно, используемые в корпоративной среде.

**Шаг 4. Обследование профилей в HKU на предмет закрепления в других учётных записях**  

Наконец, проверяем, не оставил ли вредонос артефакты в других профилях, чтобы выжить после смены пользователя. Определяем SID пользователя `jdoe` через `ProfileList`, затем ищем аналогичные записи автозапуска в других подключённых кустах:

```cmd
reg query HKU
```

Выявляется, что помимо SID текущего пользователя, в системе присутствует профиль локального администратора `S-1-5-21-...-500` (встроенный администратор). Проверяем его автозагрузку:

```powershell
reg query "HKU\S-1-5-21-1234567890-123456789-1234567890-500\Software\Microsoft\Windows\CurrentVersion\Run"
```

Вывод:

```
HKEY_USERS\S-1-5-21-1234567890-123456789-1234567890-500\Software\Microsoft\Windows\CurrentVersion\Run
    JavaManager    REG_SZ    "C:\Users\jdoe\AppData\Roaming\JavaUpdate\javaw.exe"
```

Запись в профиле администратора означает, что даже при входе под этой учётной записью запускается тот же вредоносный файл. Аналитик делает заключение о факте компрометации и горизонтального закрепления.

**Ожидаемый вывод сквозного примера:** систематический обход кустов HKLM (следы установки), HKCU (пользовательская автозагрузка), HKCR (изменённые ассоциации) и HKU (закрепление в других профилях) позволил не только подтвердить присутствие вредоносной программы, но и выявить механизмы её устойчивости. Такой подход демонстрирует, как знание структуры и назначения кустов реестра напрямую решает задачи SOC-аналитика по поиску индикаторов компрометации.
