# Риски для SOC: ретрансляция и кража учётных данных в контексте NTLM

## 1. Контекст и базовые понятия: ретрансляция и кража как ключевые угрозы NTLM

Протокол NTLM (NT LAN Manager) — это встроенный в операционные системы Windows механизм аутентификации типа «запрос-ответ» (challenge-response). Он широко применяется как основной или резервный протокол в доменных средах Active Directory, при доступе к сетевым ресурсам через SMB, HTTP, LDAP, RDP и другие сервисы. Несмотря на постепенное вытеснение протоколом Kerberos, NTLM остаётся повсеместно активным из соображений обратной совместимости, а в некоторых сценариях (например, при подключении к ресурсам по IP-адресу, аутентификации на рабочих группах или использовании устаревших приложений) он используется по умолчанию. Именно это массовое присутствие делает NTLM одной из основных мишеней для атак, нацеленных на компрометацию учётных данных и несанкционированный доступ.

Для специалиста SOC принципиально важно различать два основных класса угроз, связанных с NTLM: **ретрансляцию (relay)** и **кражу учётных данных (credential theft)**. Обе используют особенности протокола и могут приводить к захвату привилегированного доступа, однако механизмы, индикаторы и методы предотвращения у них различны. В таблице ниже проведено чёткое разграничение этих понятий, необходимое для правильной расстановки приоритетов в мониторинге и реагировании.

| Характеристика               | Ретрансляция NTLM (NTLM Relay Attack)                                           | Кража учётных данных (Credential Theft)                                      |
|------------------------------|---------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| **Суть**                     | Перехват действительного NTLM-обмена и его перенаправление на другой сервер для получения доступа от имени жертвы | Получение учётных данных (хэш пароля, открытый пароль, билет Kerberos) с целью их последующего использования |
| **Знание секрета**           | Атакующему не требуется знать пароль или хэш жертвы — он лишь ретранслирует криптографическое доказательство | Направлена на извлечение самого секрета (NT-хэша, открытого пароля)           |
| **Положение атакующего**     | Человек-посередине (MitM) или инициатор принудительной аутентификации          | Чаще действует уже внутри скомпрометированной системы (локально или через инструменты постэксплуатации) |
| **Сетевой характер**         | Требует сетевого взаимодействия в реальном времени                              | Может выполняться локально без немедленного сетевого взаимодействия; перехват NetNTLMv2 — сетевая операция |
| **Целостность аутентификации** | Эксплуатирует отсутствие привязки канала (channel binding) в NTLM             | Эксплуатирует возможность извлечь хэш из памяти, реестра или сетевого трафика |
| **Типичные инструменты**     | `ntlmrelayx`, `Responder`, `mitm6`, `Coercer`                                  | `mimikatz`, `secretsdump.py`, `procdump` + `pypykatz`, `LaZagne`              |
| **Целевые протоколы/службы** | SMB, LDAP, HTTP, MS-SQL, AD CS Web Enrollment                                  | Память LSASS, реестр SAM, база NTDS.dit, сетевые ответы NetNTLMv2            |
| **Индикаторы в логах**       | Аномалии в Event ID 4624 (NULL SID, несовпадение рабочей станции и IP), частые NTLM-аутентификации на серверах, где должен быть Kerberos | Доступ к LSASS (Sysmon Event ID 10), создание файла дампа, аномальное использование reg.exe для экспорта SAM |
| **Основные контрмеры**       | Включение SMB/LDAP подписывания, Extended Protection for Authentication (EPA), отключение NTLM где возможно | Credential Guard, LSA Protection, минимизация административных привилегий, защита конечных точек |

Таким образом, ретрансляция NTLM — это атака на процесс аутентификации в реальном времени, использующая отсутствие взаимной проверки подлинности сервера в протоколе. Кража учётных данных, в свою очередь, направлена на непосредственную добычу самого секрета для последующего офлайн-использования или повторного входа. SOC должен отслеживать оба вектора: ретрансляция может служить начальным этапом проникновения, а кража хэша — способом закрепления и lateral movement.

Дополнительно следует отметить, что многие реальные атаки комбинируют оба подхода. Например, злоумышленник может сначала применить технику принудительной аутентификации (например, PetitPotam) для получения NetNTLMv2-хэша через `Responder` (кража учётных данных), а затем использовать `ntlmrelayx` для ретрансляции того же NetNTLMv2 на LDAP или AD CS (ретрансляция). Такое сочетание существенно усложняет детектирование и требует от SOC корреляции событий на разных уровнях: сетевом трафике, журналах аутентификации и конечных точках.

## 2. Внутреннее устройство: механизмы атак NTLM Relay и кражи учётных данных

Угрозы ретрансляции и кражи учётных данных имеют различные технические основы, но обе паразитируют на фундаментальных свойствах протокола NTLM. Для грамотного выявления и нейтрализации этих угроз SOC-аналитику необходимо понимать, как они реализуются на уровне протокола, инфраструктуры и инструментария.

### 2.1. Техническая база NTLM и предпосылки для атак

NTLM аутентификация состоит из трёх сообщений, передаваемых между клиентом и сервером:

1. **NEGOTIATE_MESSAGE** — клиент заявляет поддерживаемые возможности (версия NTLM, флаги сессионного подписания/шифрования).
2. **CHALLENGE_MESSAGE** — сервер генерирует 8-байтовый случайный вызов (ServerChallenge) и отправляет его клиенту вместе с флагами.
3. **AUTHENTICATE_MESSAGE** — клиент на основе NT-хэша своего пароля и полученного вызова вычисляет ответ (NtChallengeResponse), упаковывает его с именем пользователя, доменом и опциональным ключом сессии, затем отправляет серверу.

Ключевой момент: секрет (NT-хэш) никогда не покидает клиента. Однако в протоколе NTLM отсутствует взаимная аутентификация — клиент не проверяет, что общается именно с целевым сервером, а не с промежуточным узлом. Кроме того, сообщения аутентификации не привязаны к конкретному каналу (отсутствие channel binding в базовой реализации). Именно эти два недостатка делают возможной ретрансляцию: атакующий, находящийся между клиентом и сервером, может просто переслать сообщения легитимному серверу, который воспримет их как полноценную аутентификацию от имени жертвы. Важно, что даже если целевой сервер требует подписания трафика после аутентификации, атакующий не сможет его обеспечить (не имея сессионного ключа), но сам факт входа уже состоялся — сессия будет установлена, что может быть достаточно для выполнения критических операций.

Кража учётных данных использует иные слабости: NT-хэш хранится в памяти LSASS, в реестре SAM или базе Active Directory (NTDS.dit) и может быть извлечён администратором или привилегированным процессом. Также в сети можно перехватить NetNTLMv2-хэш (результат ответа на вызов) и попытаться восстановить пароль офлайн-брутфорсом.

### 2.2. Классификация атак ретрансляции NTLM

Ретрансляционные атаки можно разделить по трём измерениям: способ получения NTLM-потока, целевой протокол и наличие принудительной аутентификации. В таблице ниже систематизированы основные техники, которые должен знать аналитик SOC.

| Вариант атаки                        | Способ получения NTLM потока                                                | Целевой протокол / сценарий                   | Типичный инструмент         | Основной индикатор                                                                 |
|--------------------------------------|-----------------------------------------------------------------------------|-----------------------------------------------|-----------------------------|------------------------------------------------------------------------------------|
| Классический MitM через спуфинг имён | Отравление LLMNR/NBT-NS/mDNS с помощью `Responder` или `mitm6`             | SMB (подпись отключена)                       | Responder + ntlmrelayx      | Широковещательные запросы LLMNR, ответы от подозрительных IP                       |
| Принудительная аутентификация        | PetitPotam (MS-EFSRPC), PrinterBug (MS-RPRN), Coercer (различные RPC)      | LDAP на контроллере домена, AD CS Web Enrollment | Coercer + ntlmrelayx       | События EFS RPC, вызовы MS-RPRN с последующими NTLM-аутентификациями на DC        |
| Мульти-ретрансляция                  | Один входящий NTLM-поток ретранслируется на множество целей                | SMB, LDAP, HTTP, MS-SQL одновременно           | ntlmrelayx (режим multi)    | Множественные успешные аутентификации с разных IP в короткий промежуток            |
| Релей на облачные/гибридные сервисы  | Перехват NTLM от клиента, перенаправление на Azure AD Connect, ADFS и др.  | HTTP в облачные федеративные службы            | Специализированные скрипты  | NTLM-аутентификация в облачных логах с нестандартным исходным адресом              |
| Релей с повышением привилегий (Shadow Credentials) | Захват LDAP-сессии и добавление альтернативных ключей в атрибут `msDS-KeyCredentialLink` | LDAP/S на контроллере домена (RBCD)           | ntlmrelayx с модулем shadowcred | Изменение объекта компьютера в AD при отсутствии соответствующих прав у жертвы |

Центральный инструмент в арсенале атакующего — `ntlmrelayx.py` из библиотеки Impacket. Он поддерживает модули для ретрансляции на SMB, HTTP, LDAP, MSSQL, IMAP, а также продвинутые техники вроде добавления «теневых учётных данных» (shadow credentials) или атак на службы сертификатов Active Directory (AD CS, техника ESC8). Именно этот инструмент чаще всего встречается в реальных инцидентах.

Отдельного внимания заслуживает атака PetitPotam, которая эксплуатирует интерфейс MS-EFSRPC (Encrypting File System Remote Protocol), заставляя контроллер домена или другой сервер инициировать NTLM-аутентификацию на подконтрольный атакующему хост. Это позволяет обойти необходимость дожидаться естественного сетевого запроса и делает ретрансляцию детерминированной. Техника активно применяется в связке с relay на AD CS для получения сертификата, пригодного для аутентификации в домене.

### 2.3. Техники кражи учётных данных в контексте NTLM

Кража учётных данных может быть сгруппирована по объекту извлечения и способу доступа. Для SOC критически важны следующие техники.

**Дамп памяти LSASS.** Процесс LSASS хранит в оперативной памяти NT-хэши всех пользователей, чьи сессии активны на машине, а также учётные данные запущенных служб. Инструменты вроде `mimikatz` или его производные (`sekurlsa::logonpasswords`) позволяют извлечь хэши, открытые пароли и даже билеты Kerberos. Альтернативный подход — создание дампа памяти LSASS с помощью легитимной утилиты `procdump` или `taskmgr` и последующий офлайн-анализ, что часто обходит некоторые антивирусные блокировки. Индикаторы: Sysmon Event ID 10 (ProcessAccess) с доступом к lsass.exe от неожиданного процесса, Event ID 11 (FileCreate) для файлов дампа, а также Event ID 1 (ProcessCreate) при запуске известных хакерских инструментов.

**Извлечение SAM и NTDS.dit.** Локальная база учётных записей SAM хранит хэши пользователей, не являющихся доменными, и может быть скопирована через реестр (`reg save hklm\sam`) или теневые копии. Для доменных контроллеров аналогичную роль играет база Active Directory — файл NTDS.dit. Инструменты `secretsdump.py` (Impacket) или `ntdsutil` позволяют извлечь хэши всех пользователей домена. Такая операция оставляет следы: создание задач теневого копирования (vssadmin), доступ к файлам `C:\Windows\NTDS\ntds.dit`, запуск `ntdsutil.exe`.

**Перехват сетевых NetNTLMv2-хэшей.** Когда клиент пытается аутентифицироваться на подконтрольном атакующем сервере, он передает ответ на вызов, который можно захватить с помощью `Responder` или `Inveigh`. Полученный NetNTLMv2-хэш может быть подобран офлайн (режим `john` или `hashcat` с модулем 5600). Для SOC такой сценарий проявляется в виде аномального сетевого трафика на портах 445 или 139, а также в логах запуска `Responder` на скомпрометированных хостах (если он работает локально).

**Кража билетов (Pass-the-Ticket).** Хотя формально это относится и к Kerberos, многие атаки начинаются с получения NTLM-хэша, который затем используется для запроса билетов Kerberos (Overpass-the-Hash). Поэтому контроль за методами кражи NT-хэша напрямую влияет на предотвращение эскалации через Kerberos.

### 2.4. Визуализация архитектуры типовой атаки с комбинацией ретрансляции и кражи

Приведённая ниже схема иллюстрирует возможную последовательность действий злоумышленника, при которой сначала применяется принудительная аутентификация, затем добывается NetNTLMv2-хэш (кража), а параллельно выполняется ретрансляция для мгновенного доступа к LDAP.

```text
[Рабочая станция жертвы] 
       │ (отправка запроса на несуществующий ресурс → LLMNR/NBT-NS запрос)
       ▼
[Атакующий хост (Responder)] ◄── (отравление ответа)
       │
       ├──(1) Захват NetNTLMv2-хэша для офлайн-атаки (КРАЖА)
       │
       └──(2) Передача ответа на ntlmrelayx
               │
               ▼
[ntlmrelayx] ──(ретрансляция на LDAP)──► [Контроллер домена]
               │
               ▼
[Успешная LDAP-сессия] → добавление RBCD/Shadow Credentials (ЭСКАЛАЦИЯ)
```

В данном примере SOC может обнаружить: событие LLMNR-запроса (если включён соответствующий аудит), последующую аутентификацию NTLM на контроллере домена от имени пользователя с подозрительного IP, а затем изменение объекта компьютера в AD.

## 3. Обнаружение и реагирование: практика SOC для угроз NTLM

Работа SOC по выявлению ретрансляции и кражи учётных данных опирается на три основных источника: журналы событий Windows, логи средств защиты конечных точек (EDR) и данные сетевого мониторинга. Ниже рассмотрены ключевые артефакты, методы их анализа и типовые процедуры реагирования.

### 3.1. Мониторинг аутентификационных событий

Основным источником для детектирования ретрансляции служат журналы безопасности на контроллерах домена и целевых серверах. Критические события:

- **Event ID 4624** (успешный вход). Необходимо анализировать поля `LogonType`, `AuthenticationPackageName`, `WorkstationName`, `IpAddress`, `SubjectUserSid`. При ретрансляции часто наблюдается `LogonType = 3` (сетевой вход), `AuthenticationPackage = NTLM` на серверах, где обычно используется Kerberos, `SubjectUserSid = NULL SID` (при определённых вариантах атаки) или несовпадение `WorkstationName` с фактическим IP-адресом (как в примере HackTheBox: рабочая станция wkstn002, а IP 172.17.79.135, в то время как настоящий IP wkstn002 — 172.17.79.136). 
- **Event ID 4776** (учётные данные проверены контроллером домена). Фиксирует NTLM-аутентификацию на DC. Поле `Status` показывает успешность; `Workstation` и `SourceAddress` позволяют выявить аномалии. Массовые неудачные попытки могут указывать на брутфорс NetNTLMv2.
- **Event ID 4625** (неудачный вход) — полезен для выявления подбора хэшей.

Для повышения точности детектирования рекомендуется создать корреляционные правила, связывающие события с активностью на конечных точках. Например, запуск `PetitPotam` или `Coercer` может быть замечен через Windows Event ID 5145 (детальный сетевой доступ к общим ресурсам) с указанием интерфейса MS-EFSRPC.

**Пример аналитического запроса (PowerShell).** Поиск в журнале безопасности событий, где тип входа 3, пакет NTLM и отмечены подозрительные IP-адреса (не из доверенной подсети):

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4624} -MaxEvents 5000 |
  Where-Object {
    $logonType = $_.Properties[8].Value
    $authPkg   = $_.Properties[10].Value
    $workstation = $_.Properties[11].Value
    $ipAddress   = $_.Properties[18].Value
    ($logonType -eq 3) -and ($authPkg -eq 'NTLM') -and ($ipAddress -notlike '10.0.*')
  } |
  Select-Object TimeCreated, 
                @{n='User';e={$_.Properties[5].Value}},
                @{n='Workstation';e={$workstation}},
                @{n='SourceIP';e={$ipAddress}},
                @{n='LogonID';e={$_.Properties[7].Value}}
```

Вывод такого скрипта помогает выявить сессии, где аутентификация прошла с неожиданного адреса, что характерно для ретрансляции.

### 3.2. Журналы EDR и Sysmon для обнаружения кражи учётных данных

Современные EDR-решения и Sysmon предоставляют детальную телеметрию процессов, позволяющую выявить техники кражи хэшей.

**Обнаружение доступа к LSASS (Sysmon Event ID 10).** Легитимные процессы, как правило, не обращаются к lsass.exe. Любое чтение памяти LSASS со стороны подозрительного процесса (например, `powershell.exe`, `cmd.exe`, `mimikatz.exe`) является сильным индикатором попытки дампа учётных данных. Правило Sigma:

```yaml
title: Доступ к памяти LSASS подозрительным процессом
id: 3d1a3bb4-232f-4e1a-a67b-5a78d5b9f5b1
status: experimental
description: Обнаруживает доступ процесса к lsass.exe, исключая известные легитимные (антивирусы и т.п.)
logsource:
    product: windows
    service: sysmon
detection:
    selection:
        EventID: 10
        TargetImage|endswith: '\lsass.exe'
    filter:
        SourceImage|contains: 
            - 'MsMpEng.exe'
            - 'svchost.exe'
            - 'csrss.exe'
    condition: selection and not filter
level: high
```

**Создание файла дампа памяти.** Подозрительными являются процессы, создающие файлы с расширением `.dmp` в системных каталогах или временных папках. Sysmon Event ID 11 (FileCreate) в сочетании с SourceImage, указывающим на `procdump.exe` или `rundll32.exe`, — чёткий признак кражи.

**Запуск известных инструментов.** Список хэшей вредоносных исполняемых файлов (Mimikatz, PwDumpX, LaZagne) должен быть добавлен в базы индикаторов компрометации (IoC) и отслеживаться через антивирусные сканирования и правила контроля приложений.

### 3.3. Сетевые индикаторы

- **Аномальные NTLM-аутентификации через SMB.** Если в организации включена подпись SMB, то любая аутентификация без подписи может быть подозрительной. Сетевые сенсоры анализируют флаг `NTLMSSP_NEGOTIATE_SIGN` в сообщениях.
- **Трафик LLMNR/NBT-NS.** Большое количество многоадресных запросов от одного узла может указывать на активность Responder. Блокировка этих протоколов на уровне сети и мониторинг их использования — рекомендуемая практика.
- **SMB-соединения от неожиданных хостов к контроллеру домена.** Анализ NetFlow позволяет выявить потоковую активность, исходящую от рабочих станций, которые обычно не обращаются непосредственно к DC по SMB.

### 3.4. Процедуры реагирования

При подтверждении инцидента ретрансляции или кражи SOC выполняет типовую последовательность действий:

1. **Изоляция скомпрометированных учётных записей**: немедленный сброс паролей и отзыв активных сессий.
2. **Блокировка источника атаки**: внесение IP-адреса атакующего хоста в чёрные списки межсетевого экрана, отключение портов.
3. **Ретрассировка действий**: по логам определяется, был ли атакующим выполнен дамп хэшей, изменены ли объекты в AD, добавлены ли сертификаты. Если зафиксировано изменение атрибута `msDS-KeyCredentialLink` или создание подозрительного ключа — его немедленное удаление.
4. **Усиление конфигурации**: принудительное включение подписи SMB и LDAP, Extended Protection для HTTP-сервисов, активация Credential Guard и LSA Protection на критичных серверах.

Для SOC L1 особенно важно уметь быстро классифицировать событие как потенциальный relay, чтобы эскалировать инцидент L2-аналитикам с готовым набором артефактов: точное время, вовлечённые системы, идентификаторы сеансов.

## 4. Сквозной практический пример: расследование NTLM Relay с последующей кражей хэша

**Исходные условия.** Корпоративная сеть: домен `contoso.com`, контроллер домена `DC01` (10.0.1.10), рабочие станции Windows 10. В организации используется SIEM, собирающий логи с DC, рабочих станций и межсетевого экрана. SOC получает предупреждение о серии аномальных аутентификаций NTLM на `DC01` с рабочей станции `WSUS-LAB` (10.0.1.50). Сетевая политика требует использования Kerberos для доменных аутентификаций, поэтому NTLM между рабочей станцией и DC — редкость.

**Шаг 1: Анализ событий на контроллере домена.**  
Аналитик L1 выполняет поиск по Event ID 4624 для пользователя `jdoe`, фигурирующего в алерте.

```powershell
Get-WinEvent -ComputerName DC01 -FilterHashtable @{LogName='Security'; ID=4624} -MaxEvents 100 |
  Where-Object { $_.Properties[5].Value -eq 'contoso\jdoe' } |
  Format-List TimeCreated, 
              @{n='LogonType';e={$_.Properties[8].Value}},
              @{n='AuthPkg';e={$_.Properties[10].Value}},
              @{n='Workstation';e={$_.Properties[11].Value}},
              @{n='IPAddress';e={$_.Properties[18].Value}},
              @{n='SubjectUserSid';e={$_.Properties[1].Value}}
```

**Ожидаемый вывод (иллюстративная схема):**
```
TimeCreated : 2025-10-15 09:12:34
LogonType   : 3
AuthPkg     : NTLM
Workstation : WSUS-LAB
IPAddress   : 10.0.1.200
SubjectUserSid : S-1-0-0
```
Несовпадение IP-адреса (10.0.1.200 не принадлежит `WSUS-LAB`; реальный IP рабочей станции — 10.0.1.50) и `SubjectUserSid = NULL SID` — сильный индикатор ретрансляции. Подтверждается, что жертва — пользователь `jdoe` — не инициировала аутентификацию с указанного адреса.

**Шаг 2: Проверка событий на источнике атаки — рабочей станции `WSUS-LAB`.**  
Аналитик удалённо проверяет журналы Sysmon на предмет доступа к lsass.exe.

```powershell
Get-WinEvent -ComputerName WSUS-LAB -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; ID=10} -MaxEvents 50 |
  Where-Object { $_.Message -match 'TargetImage:.*lsass.exe' } |
  Select-Object TimeCreated,
                @{n='SourceImage';e={($_| Select-String -Pattern 'SourceImage: ([^\r\n]+)').Matches.Groups[1].Value}},
                @{n='GrantedAccess';e={($_|Select-String -Pattern 'GrantedAccess: ([^\r\n]+)').Matches.Groups[1].Value}}
```

**Ожидаемый вывод (фрагмент):**
```
TimeCreated : 2025-10-15 09:11:50
SourceImage : C:\Users\Public\mimikatz.exe
GrantedAccess: 0x1FFFFF
```
Обнаружен запуск `mimikatz` из публичной папки с полным доступом к памяти LSASS. Это признак кражи учётных данных — атакующий, вероятно, извлёк NT-хэш пользователя `jdoe` или других пользователей.

**Шаг 3: Корреляция с событиями модификации Active Directory.**  
Поскольку ретрансляция могла быть направлена на LDAP для изменения объектов, аналитик ищет Event ID 5136 (изменение объекта каталога) на DC за тот же промежуток.

```powershell
Get-WinEvent -ComputerName DC01 -FilterHashtable @{LogName='Security'; ID=5136; StartTime='2025-10-15T09:10:00'; EndTime='2025-10-15T09:15:00'} |
  Where-Object { $_.Message -match 'msDS-KeyCredentialLink' } |
  Format-List TimeCreated, 
              @{n='ObjectDN';e={($_|Select-String -Pattern 'Object DN: ([^\r\n]+)').Matches.Groups[1].Value}},
              @{n='Attribute';e={($_|Select-String -Pattern 'Attribute LDAP Display Name: ([^\r\n]+)').Matches.Groups[1].Value}}
```

**Ожидаемый вывод:**
```
TimeCreated : 2025-10-15 09:13:02
ObjectDN    : CN=WSUS-LAB,CN=Computers,DC=contoso,DC=com
Attribute   : msDS-KeyCredentialLink
```
Обнаружено добавление shadow credentials к учётной записи компьютера `WSUS-LAB`, что позволяет атакующему аутентифицироваться как эта машина без пароля. Это подтверждает эскалацию привилегий после успешного ретрансляции.

**Шаг 4: Действия по сдерживанию и восстановлению.**  
Аналитик инициирует сброс пароля `jdoe`, удаляет подозрительный ключ из атрибута `msDS-KeyCredentialLink`, изолирует рабочую станцию `WSUS-LAB` и усиливает настройки подписи SMB на всех серверах через GPO. Команда для проверки и включения подписи SMB на проблемной машине:

```powershell
Set-SmbServerConfiguration -RequireSecuritySignature $true -Force
Set-SmbClientConfiguration -RequireSecuritySignature $true -Force
```

**Ожидаемый вывод:** Конфигурация применена, после перезагрузки службы сервера ретрансляция на данный хост станет невозможной без подписи.

Пример демонстрирует, как SOC выявил ретрансляцию NTLM по аномальным признакам в Event ID 4624, затем обнаружил кражу учётных данных через дамп LSASS и, наконец, раскрыл факт модификации AD, проведя полный цикл расследования.
