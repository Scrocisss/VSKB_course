# Пользователи и права в Linux

## 1. Пользователи и группы: контекст, классификация и базовые принципы

Linux — многопользовательская операционная система, ядро и пользовательское пространство которой изначально проектировались так, чтобы одновременно могли работать несколько субъектов доступа. Каждый процесс, независимо от того, запущен он интерактивно или является системной службой, выполняется от имени конкретного пользователя. Именно идентификатор пользователя (UID) и членство в группах (GID) определяют, какие файлы, каталоги и другие ресурсы оказываются доступными процессу.

Учётная запись пользователя в Linux представляет собой логическую сущность, объединяющую числовой идентификатор и текстовое имя, под которым пользователь входит в систему. Группа — это именованный набор учётных записей, позволяющий назначать права не индивидуально, а коллективно. В сочетании с моделью файловых прав «владелец–группа–остальные» такая структура даёт гибкий, предсказуемый и проверяемый механизм разграничения доступа, что критически важно для специалиста SOC первого уровня, ежедневно анализирующего легитимность действий аккаунтов.

### 1.1 Типы учётных записей

Хотя все субъекты представлены единообразно, по своему функциональному назначению учётные записи разделяются на три категории: **root**, **системные пользователи** и **обычные (регулярные) пользователи**.

- **Root** (UID 0) — суперпользователь с неограниченными полномочиями. Ядро проводит проверку прав доступа для всех, кроме процессов с UID 0; root игнорирует биты разрешений и может читать, изменять и исполнять любой файл, если иное не ограничено мандатными или дополнительными системами безопасности (SELinux, AppArmor). В хорошо администрируемой системе прямой вход от root запрещён, а администраторы повышают привилегии через sudo.
- **Системные пользователи** — учётные записи, создаваемые при установке пакетов для изоляции демонов (например, `www-data`, `ntp`, `mysql`). Они, как правило, имеют UID ниже 1000 (в старых дистрибутивах — ниже 500) и не предназначены для интерактивного входа; оболочка часто указывается как `/usr/sbin/nologin` или `/bin/false`.
- **Обычные пользователи** — учётные записи людей, UID которых начинается с 1000 (по соглашению, принятому в большинстве современных дистрибутивов, включая Red Hat, Debian, Arch и Astra Linux). Им выделяется домашний каталог и задаётся командная оболочка (`/bin/bash`, `/bin/zsh` и т.п.).

Ниже представлена сравниттельная таблица, систематизирующая ключевые признаки каждой категории:

| Категория           | UID диапазон (типичный) | Назначение                                           | Домашний каталог          | Оболочка по умолчанию         |
|---------------------|--------------------------|------------------------------------------------------|---------------------------|-------------------------------|
| Root                | 0                        | Высший административный доступ, обслуживание системы | `/root`                   | `/bin/bash` (или `/bin/sh`)   |
| Системный пользователь | обычно < 1000 (или 1–999) | Изоляция демонов и служб, владение файлами процессов | Может отсутствовать или `/var/lib/<имя>`, `/nonexistent` | `/usr/sbin/nologin` или `/bin/false` |
| Обычный пользователь | ≥ 1000                   | Повседневная работа человека-оператора               | `/home/<login>`           | `/bin/bash` (или другая интерактивная) |

### 1.2 Группы: первичная и дополнительные

Каждый пользователь обязательно состоит ровно в одной **первичной группе**, идентификатор которой (GID) записан в четвёртом поле `/etc/passwd`. Имя этой группы обычно совпадает с именем пользователя (такая схема называется User Private Group, UPG), что предотвращает случайное совместное использование файлов. Кроме неё, пользователь может входить в произвольное число **дополнительных (вторичных) групп**, перечисленных в четвёртом поле `/etc/group`. При создании файла владельцем-группой назначается первичная группа процесса, если иное не модифицируется механизмом SGID на родительском каталоге.

Утилита `id` позволяет с одного взгляда увидеть все идентификаторы и членство:

```bash
id analyst
# uid=1001(analyst) gid=1001(analyst) groups=1001(analyst),1002(soc),27(sudo)
```

С точки зрения SOC-специалиста такой вывод моментально отвечает на вопросы: какому пользователю принадлежит процесс, входит ли он в группу `sudo` и, следовательно, может повышать привилегии.

### 1.3 Идентификация, аутентификация и авторизация

При входе в систему пользователь предъявляет учётные данные (логин и пароль, ключ SSH, PAM-токен). Модули PAM (Pluggable Authentication Modules) проверяют их корректность и, в случае успеха, инициализируют сессию, назначая процессу входа UID, GID и список дополнительных групп. Дальнейший контроль доступа к файлам, сетевым портам и устройствам ядро осуществляет исключительно по числовым идентификаторам, сравнивая их с метаданными владельца и групп объекта. Таким образом, корректность информации в пользовательской базе прямым образом влияет на всю систему безопасности.

В средах с ALD Pro (доменная служба каталогов на базе Samba/FreeIPA) помимо локального UID/POSIX-атрибутов появляются Security Identifiers (SID), позволяющие единообразно управлять доступом к объектам на множестве Linux- и Windows-хостов. Однако для начального освоения и ежедневной работы SOC L1 достаточно глубокого понимания локальной модели UID/GID.

## 2. Внутреннее устройство учётных записей и модели прав

В классической локальной конфигурации Linux все сведения о пользователях и группах хранятся в четырёх текстовых файлах, расположенных в `/etc`. Понимание структуры каждого из них позволяет быстро вручную проверять аномалии, например, неожиданное появление UID 0 у незнакомой учётной записи или пустой пароль у привилегированного пользователя.

### 2.1 Файловая база учётных записей

#### `/etc/passwd` — основные сведения о пользователе

Файл читаем всеми (нужен для трансляции UID в имена), но поле пароля уже не содержит хеша. Формат строки — семь полей, разделённых двоеточием:

`username:password:UID:GID:GECOS:home_directory:shell`

- **username** — регистрозависимое имя (обычно строчные буквы, цифры, дефис и подчёркивание).
- **password** — в современных системах содержит `x`, реальный хеш вынесен в `/etc/shadow`.
- **UID** — числовой идентификатор.
- **GID** — идентификатор первичной группы.
- **GECOS** — поле комментария (обычно полное имя, контакт).
- **home_directory** — абсолютный путь к домашнему каталогу.
- **shell** — абсолютный путь к командному интерпретатору.

Иллюстративная запись:

```
analyst:x:1001:1001:SOC Analyst,room 403,ext 5551:/home/analyst:/bin/bash
```

#### `/etc/shadow` — защищённое хранение паролей

Доступен для чтения только root и группе shadow (по умолчанию права 640). Содержит девять полей:

`username:encrypted_password:last_change:min_age:max_age:warn:inactive:expire:reserved`

- **encrypted_password** — хеш пароля в формате `$id$salt$hash` (например, `$6$` — SHA‑512). Пустое поле означает беспарольную учётную запись, `!` или `*` — заблокировано.
- **last_change** — дата последней смены пароля в днях от 01.01.1970.
- **min_age**, **max_age** — минимальный и максимальный срок действия пароля.
- **warn** — за сколько дней до истечения предупреждать.
- **inactive** — через сколько дней после истечения пароля аккаунт блокируется.
- **expire** — абсолютная дата истечения учётной записи.

Схематичный пример:

```
analyst:$6$rounds=5000$YXrT...:19500:0:99999:7:::
```

#### `/etc/group` — информация о группах

Формат: `group_name:password:GID:member_list`

- **password** — обычно `x`; групповой пароль хранится в `/etc/gshadow` и используется редко.
- **member_list** — список имён пользователей, состоящих в группе в качестве дополнительной, разделённый запятыми.

Пример:

```
soc:x:1002:analyst,hunter
```

#### `/etc/gshadow` — защищённые атрибуты групп

Содержит пароли групп и список администраторов, которые могут управлять групповым паролем с помощью `gpasswd`.

Структура: `group_name:encrypted_password:admin_member:member_list`

### 2.2 Модель прав доступа (стандартные биты)

Метаданные каждого объекта файловой системы (файла, каталога, символьной ссылки, устройства) включают 12 бит прав: 9 бит «обычных» разрешений для трёх классов и 3 специальных бита, рассматриваемых ниже. Права ассоциированы с объектом, а не с пользователем, и хранятся в индексном дескрипторе (inode) файловой системы.

**Классы доступа:**
- **owner (u)** — владелец, определяемый UID.
- **group (g)** — группа-владелец, определяемая GID, права действуют для всех пользователей, входящих в эту группу (кроме владельца, если он тоже член группы).
- **others (o)** — все остальные субъекты, не попавшие в первые две категории.

**Типы разрешений:**
- **read (r)** — для файла разрешает чтение содержимого; для каталога — просмотр списка имён файлов.
- **write (w)** — для файла разрешает изменение и усечение; для каталога — создание, удаление и переименование файлов (при условии, что соответствующие права есть на сами объекты).
- **execute (x)** — для файла разрешает выполнение как программы; для каталога — возможность войти в каталог (сделать его текущим) и обращаться к inode его содержимого, даже если имена не видны.

Проверка доступа ядром выполняется в строгой последовательности:

1. Если UID процесса совпадает с UID владельца файла, применяются права **owner**.
2. Если процесс не владелец, но его GID (или один из дополнительных GID) совпадает с GID группы файла, применяются права **group**.
3. Иначе применяются права **others**.

Исключение: для процессов с привилегиями root (или с capability `CAP_DAC_OVERRIDE`) проверка битов чтения и записи игнорируется; для выполнения всё равно требуется хотя бы один из битов `x` для любого класса, если не установлены дополнительные привилегии.

ASCII-схема потока проверки прав:

```text
Процесс (PID, UID, GIDs)
     │
     ├─ UID == file.owner? ── Да ──▶ Применить owner-права rwx---
     │
     └─ Нет
        │
        ├─ GID (любой) == file.group? ── Да ──▶ Применить group-права ---rwx---
        │
        └─ Нет ──▶ Применить others-права ------rwx
```

### 2.3 Специальные биты

Три старших бита прав добавляют важные свойства, часто встречающиеся при аудите безопасности:

- **setuid (SUID, 4000)** — если установлен на исполняемом файле, процесс запускается от имени владельца файла, а не запускающего пользователя. Классический пример: `/usr/bin/passwd`. Обозначается `s` на позиции выполнения для owner.
- **setgid (SGID, 2000)** — для исполняемых файлов: процесс запускается с эффективным GID, равным группе-владельцу файла. Для каталогов: новые файлы, создаваемые внутри, наследуют группу-владельца каталога, а не первичную группу создателя. Это критически важно для общих папок проектов.
- **sticky bit (1000)** — на каталогах позволяет удалять/переименовывать файлы только их владельцам или владельцу каталога, независимо от прав записи для группы и остальных (типичный пример — `/tmp`). Обозначается `t` на позиции выполнения для others.

Со стороны SOC L1 важно уметь замечать неожиданные SUID-файлы или каталоги с широкими правами, что является классическим признаком компрометации или эскалации привилегий.

Таблица-обзор специальных битов и их отображения:

| Бит    | Октальное значение | Влияние на файл                                      | Влияние на каталог                                   | Отображение в `ls -l`     |
|--------|---------------------|------------------------------------------------------|------------------------------------------------------|----------------------------|
| SUID   | 4000                | Запуск с правами владельца файла                     | Не применяется                                       | `rws------` или `rwS------` (если владелец не имеет x) |
| SGID   | 2000                | Запуск с правами группы-владельца                    | Новые объекты наследуют группу каталога              | `rwxrws---` или `rwxrwS---` |
| sticky | 1000                | Не используется                                      | Удалять/переименовывать может только владелец объекта | `rwxrwxrwt` или `rwxrwxrwT` |

## 3. Управление пользователями, группами и правами

Практическая работа SOC‑аналитика редко обходится без модификации пользователей или анализа их прав. Ниже перечислены ключевые утилиты и типовые операции, которые необходимо уверенно выполнять в терминале.

### 3.1 Управление учётными записями пользователей

**Создание пользователя.** Команда низкого уровня `useradd` с опциями задаёт имя, UID, GID, группу, оболочку и домашний каталог. Высокоуровневая `adduser` (в Debian/Ubuntu) интерактивно запрашивает параметры. В дистрибутивах Red Hat `adduser` — это симлинк на `useradd`.

```bash
sudo useradd -m -s /bin/bash -G soc analyst2
```

После создания необходимо задать (или принудить сменить при первом входе) пароль:

```bash
sudo passwd analyst2
```

Команда `passwd` с ключом `-l` блокирует аккаунт (добавляет `!` перед хешем в shadow), а с `-u` — снимает блокировку. Это более безопасный способ временно деактивировать учётную запись, чем удаление.

**Модификация учётной записи** выполняется через `usermod`:

- Изменить основную группу: `usermod -g soc analyst2`
- Добавить в дополнительную группу (ключ `-aG` важен, чтобы не стереть уже имеющиеся вторичные группы): `usermod -aG audit analyst2`
- Задать новую оболочку: `usermod -s /usr/bin/zsh analyst2`
- Перенести домашний каталог: `usermod -d /data/home/analyst2 -m analyst2`

**Удаление** учётной записи вместе с домашним каталогом и почтовым спулом производится командой `userdel -r`. Без ключа `-r` домашний каталог остаётся, что бывает удобно при расследованиях.

### 3.2 Управление группами

Группы создаются командой `groupadd`, а удаляются — `groupdel`. Для добавления пользователя в группу чаще всего используют `usermod -aG` либо `gpasswd -a`. Последняя утилита также позволяет задавать и удалять групповые пароли и назначать администраторов группы.

```bash
sudo groupadd incident_responders
sudo gpasswd -a analyst2 incident_responders
```

Для массового изменения состава можно задать весь список членов через `gpasswd -M "user1,user2" groupname`; отсутствующие в новом списке пользователи будут удалены.

### 3.3 Просмотр и аудит пользователей и групп

Со стороны SOC L1 важно быстро получать сводку об учётной записи:

- `id username` — UID, GID, группы.
- `getent passwd username` — одна строка из базы данных NSS, где актуальная информация даже при использовании LDAP/FreeIPA.
- `groups username` — имена групп.
- `lslogins username` (из пакета util-linux) — детальный вывод, включающий информацию о блокировке, дате последнего входа, процессах пользователя.

Для анализа активности сессий служат:

- `who` / `w` — кто сейчас в системе, с какого терминала, что запущено.
- `last` — история успешных входов; `lastb` — история неудачных попыток из `/var/log/btmp`.
- `lastlog` — последний вход для каждого пользователя.
- `faillog` — счётчик неудачных попыток аутентификации, с возможностью сброса и установки лимитов.

Пример быстрой проверки подозрительной активности:

```bash
lastb -10
# вывод последних 10 неудачных попыток, указывает на возможный перебор пароля
faillog -u jdoe
# покажет число неудачных попыток, максимально разрешённое, флаг блокировки
```

### 3.4 Управление файловыми правами

#### chmod — изменение прав доступа

Поддерживает два режима: символьный и восьмеричный.

**Символьный режим:** `[ugoa][+-=][rwxXst]`. Удобен, когда нужно относительно изменить существующие права, не зная их точное значение.

```bash
chmod g+w shared_report.txt    # добавить группе запись
chmod o-rwx sensitive.key      # убрать все права у остальных
chmod u+x script.sh            # сделать файл исполняемым для владельца
chmod -R g+rX,o-rwx project/   # рекурсивно: дать группе чтение и проход по каталогам, у остальных забрать всё
```

**Восьмеричный (числовой) режим:** задаёт точную битовую маску. Три цифры соответствуют владельцу, группе, остальным; каждая цифра — сумма 4 (read), 2 (write), 1 (execute). Четырёхзначная запись (например, 0755) старшим разрядом указывает специальные биты: 4 (SUID), 2 (SGID), 1 (sticky). Для SOC‑аналитика предпочтительнее использовать числовой режим при автоматизации и аудите, потому что он гарантирует детерминированный результат.

```bash
chmod 600 id_rsa                # только владелец может читать и изменять
chmod 750 /home/analyst         # владелец rwx, группа rx, others ничего
chmod 644 /etc/passwd           # ожидаемые права по умолчанию
chmod 1777 /tmp                 # sticky'ированный каталог с широкими правами
```

**Распространённая ошибка:** `chmod 777` даёт полный бесконтрольный доступ всем, создавая предпосылки для утечек или подмены файлов. В любом контексте, кроме `/tmp` с sticky-битом, она должна рассматриваться как инцидент.

#### chown и chgrp — смена владельца и группы

```bash
chown analyst2:incident_responders evidence.log   # сменить и пользователя, и группу
chown :soc weekly_report.txt                      # сменить только группу
chgrp audit /var/log/audit.log                    # тоже только группу
```

Эти команды требуют привилегий root (или права `CAP_CHOWN`). Рядовой пользователь не может «отдать» файл другому владельцу.

#### umask — маска создания файлов

`umask` задаёт биты, которые будут **вычтены** из максимальных прав (666 для файлов, 777 для каталогов) при создании нового объекта процессом. Проверка текущего значения:

```bash
umask
# 0022 – типичное значение, дающее права 755 для каталогов и 644 для файлов
```

Для SOC‑аналитика важно помнить, что ненормативно жёсткая или слишком мягкая umask в скриптах или cron-заданиях может приводить к появлению world‑readable конфиденциальных файлов или, наоборот, ломать работу сервисов.

### 3.5 Поиск потенциально опасных прав

Одна из рутинных задач SOC L1 — выявление файлов с избыточными разрешениями. Для этого используется `find` с фильтрами по правам доступа.

- **World‑writable файлы** (права `--- -w- -w-`, т.е. бит записи для others):

```bash
find / -type f -perm -o+w ! -path '/proc/*' ! -path '/sys/*' -ls 2>/dev/null
```

- **World‑writable каталоги без sticky‑бита** — риск несанкционированного удаления чужих файлов:

```bash
find / -type d -perm -o+w ! -perm -1000 -ls 2>/dev/null
```

- **Файлы с SUID или SGID** — потенциальный вектор эскалации, если бит установлен на нестандартном бинарнике:

```bash
find / -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
```

Полученные списки должны сопоставляться с базовым состоянием (baseline) системы и любое неожиданное попадание рассматриваться как инцидент.

### 3.6 Расширенные списки доступа (ACL)

Стандартная модель «один владелец, одна группа, остальные» иногда недостаточна, например, когда необходимо дать разные права трём разным группам к одному файлу. POSIX ACL реализуются через `setfacl` и `getfacl`. Они добавляют дополнительные записей к существующей маске прав.

Просмотр ACL:

```bash
getfacl report.txt
# user:analyst:rw-
# group:soc:r--
# group:audit:r--
# mask:rw-
# other::---
```

Назначение дополнительного права:

```bash
setfacl -m g:incident_responders:rw report.txt
```

ACL — мощный инструмент, но важно помнить, что не все утилиты (в том числе резервного копирования) корректно сохраняют ACL; перед применением в критичных окружениях надо тестировать.

## 4. Сквозной практический пример: аудит доступа и реагирование на инцидент

**Исходные условия.** Аналитик SOC L1 получает алерт SIEM‑системы: в ночное время для пользователя `jdoe` зафиксировано несколько десятков неудачных попыток входа с IP-адреса, ранее не встречавшегося в логах легитимной работы, после чего последовал успешный вход. Система — сервер Red Hat Enterprise Linux 8, мониторинг пользователей осуществляется средствами ОС. Задача: оценить масштаб инцидента, проверить состояние учётной записи, выявить возможные изменения прав и при необходимости заблокировать аккаунт.

**Шаг 1. Анализ истории входов.** Необходимо понять, с каких адресов и когда происходили входы, а также зафиксировать неудачные попытки.

```bash
last -i jdoe
```
Ожидаемый вывод (иллюстративная схема):
```
jdoe     pts/0        10.20.30.45      Thu Mar 27 02:15   still logged in
jdoe     pts/0        10.20.30.45      Thu Mar 27 02:14 - 02:15  (00:01)
...
```
Анализ неудачных попыток:
```bash
lastb -i jdoe | head -10
```
Вывод показывает десятки записей с одного подозрительного IP, подтверждая перебор пароля.

**Шаг 2. Проверка активной сессии и статуса учётной записи.** Для исключения текущего присутствия злоумышленника и получения идентификаторов.

```bash
who -u | grep jdoe
# jdoe     pts/0        2025-03-27 02:15   .          12345 (10.20.30.45)
id jdoe
# uid=1003(jdoe) gid=1003(jdoe) groups=1003(jdoe),1000(users),27(sudo)
```
Вхождение в группу `sudo` говорит о высоких привилегиях; это повышает критичность инцидента. Вывод `passwd -S jdoe` показывает, что пароль активен, значит, злоумышленник уже авторизован.

**Шаг 3. Аудит прав доступа к домашнему каталогу и конфиденциальным файлам.** Злоумышленник мог создать или изменить SSH-ключи, скопировать закрытые данные.

```bash
ls -la /home/jdoe/
ls -la /home/jdoe/.ssh/
```
Ожидаемый вывод:
```
-rw-------. 1 jdoe jdoe  411 Mar 27 02:16 authorized_keys
-rw-r--r--. 1 jdoe jdoe  89 Mar 27 02:16 config
```
Появление несанкционированного публичного ключа в `authorized_keys` подтверждает компрометацию. Права `644` на `config` допустимы, но стоит проверить, не добавлены ли в конфиг подозрительные параметры (например, `UserKnownHostsFile /dev/null`).

**Шаг 4. Поиск нестандартных SUID/SGID файлов и world‑writable объектов, принадлежащих jdoe.** Подобные артефакты часто служат бэкдорами.

```bash
find / -user jdoe -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
find / -type f -perm -o+w ! -path '/proc/*' ! -path '/sys/*' \( -user jdoe -o -group jdoe \) -ls 2>/dev/null
```
Если вывод не пуст (например, обнаружен `/home/jdoe/.hidden/suid_shell`), необходимо немедленно изолировать хост.

**Шаг 5. Блокировка учётной записи и фиксация улик.** После согласования со старшей сменой аккаунт блокируется, чтобы предотвратить дальнейшие действия.

```bash
sudo usermod -L jdoe
# или passwd -l jdoe
```
Дополнительно принудительно завершается его сессия:

```bash
sudo pkill -u jdoe
```

**Ожидаемый результат.** SOC‑аналитик подтверждает факт успешной авторизации после перебора, а также модификацию файла `authorized_keys`. Принимаются меры по изоляции учётной записи, собираются копии логов `/var/log/secure`, `/var/log/btmp` и копия изменённого каталога `.ssh`. Материалы передаются для углублённого форензического анализа. Пример демонстрирует связь управления пользователями и аудита прав доступа как базового навыка специалиста первой линии.
