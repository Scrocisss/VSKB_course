# Архитектура Windows

## Контекст и базовые понятия: эволюция и концепции Windows NT

Современные операционные системы семейства Windows (10, 11, Server 2016/2019/2022) ведут родословную от ядра **Windows NT**, разработка которого началась в 1989 году [Архитектура ядра Windows NT](https://www.osp.ru/os/1999/01/179629). Создатели во главе с Дэвидом Соломоном сформулировали ключевые требования: полностью 32-разрядная ОС (впоследствии 64‑разрядная), переносимая на разные аппаратные платформы, с симметричной многопроцессорной обработкой (SMP), совместимая со стандартом POSIX 1003.1, поддерживающая Unicode и выполняющая большинство 16‑разрядных приложений MS‑DOS и Windows 3.х. Эти принципы заложили основы модульности, изолированности процессов и безопасности, ставшие визитной карточкой NT.

Ядро Windows NT является **гибридным**, или **макроядром** [Архитектура Windows NT](https://ru.wikipedia.org/wiki/%D0%90%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0_Windows_NT). Оно сочетает черты микроядерной архитектуры (выделенный планировщик, подсистемы в пользовательском режиме) и монолитных систем (исполнительная подсистема режима ядра с менеджерами объектов, памяти, ввода‑вывода и безопасности). Важнейшим свойством является **вытесняющая многозадачность**: планировщик ОС сам распределяет процессорное время между потоками согласно приоритетам, не требуя от программ явной передачи управления [АРХИТЕКТУРА WINDOWS NT](https://cyberleninka.ru/article/n/arhitektura-windows-nt). Приоритет процесса можно наблюдать в стандартном Диспетчере задач.

Ключевое разграничение архитектуры — деление на **режим пользователя** (User mode) и **режим ядра** (Kernel mode). Компоненты пользовательского режима работают в изолированных виртуальных адресных пространствах и не могут напрямую обращаться к аппаратуре; компоненты ядра обладают полным доступом к системной памяти и оборудованию [Architecture of Windows NT](https://en.wikipedia.org/wiki/Architecture_of_Windows_NT). Переход между режимами осуществляется через интерфейс системных вызовов (system calls). Это деление критически важно для аналитика SOC, поскольку любое вредоносное ПО, пытающееся выполнить привилегированные операции, должно переходить в ядро — такие события могут быть зафиксированы в логах.

Ниже представлена сравнительная таблица двух режимов, акцентирующая различия, которые имеют значение в ходе инцидентного анализа и расследований.

| Характеристика | Режим пользователя | Режим ядра |
|----------------|-------------------|-------------|
| Виртуальное адресное пространство | Изолированное пространство процесса (0–8 ТБ в 64‑бит) | Единое системное пространство, доступное всем потокам в ядре |
| Привилегии ЦП | Ограниченный набор инструкций, запрет на привилегированные (например, `IN`, `OUT`, `HLT`) | Полный набор, включая управляющие регистры и ввод‑вывод |
| Типичные компоненты | Прикладные программы, подсистемы окружения, динамические библиотеки (DLL), часть служб | Исполнительная подсистема Executive, планировщик (ntoskrnl.exe), HAL, драйверы устройств |
| Защита от сбоев | Падение процесса не нарушает работу всей системы | Ошибка в драйвере или ядре может вызвать крах (синий экран) |
| Взаимодействие с аппаратурой | Только через системные вызовы (Native API) | Прямой доступ через HAL и драйверы |
| Примеры процессов | explorer.exe, notepad.exe, csrss.exe (частично) | System Process (PID 4), потоки Idle, прерывания |

Процессы пользовательского режима взаимодействуют с подсистемами окружения (Win32, POSIX, OS/2, WSL), которые транслируют их запросы в вызовы ядра [Утраченный потенциал подсистемы Windows для Linux (WSL) / Хабр](https://habr.com/ru/companies/vdsina/articles/535214). Главная подсистема — **Win32**, чья поддержка реализована в процессе `csrss.exe` и многочисленных DLL (kernel32.dll, user32.dll и пр.). Существует также **Native API** (ntdll.dll), через который все подсистемы передают запросы в ядро. Для SOC‑аналитика важно, что настоящий исполняемый образ процесса всегда загружается через модули режима пользователя, а любые попытки обхода (например, скрытые процессы) оставляют артефакты в памяти и структурах ядра.

Таким образом, архитектура Windows NT, спроектированная более трёх десятилетий назад, осталась фундаментально неизменной. Понимание двухуровневой модели, гибридного ядра и роли подсистем формирует необходимый контекст для дальнейшего погружения во внутреннее устройство системы.

## Внутреннее устройство: компонентная модель Windows

Архитектура Windows представляет собой многослойный набор модулей, чётко разделённых по границе «пользователь — ядро». Ниже представлена упрощённая структурная диаграмма, отражающая ключевые блоки, описанные в [Архитектура ядра Windows NT](https://www.osp.ru/os/1999/01/179629) и позднейших редакциях Windows Internals [Windows Internals, Sixth Edition, Part 1](https://repo.zenk-security.com/Linux%20et%20systemes%20d.exploitations/Windows%20Internals%20Part%201_6th%20Edition.pdf). Компоненты, расположенные ниже пунктирной линии, выполняются в привилегированном режиме ядра. Главный исполняемый файл — **ntoskrnl.exe** — содержит Executive и собственно ядро. **HAL** реализован в `hal.dll` и обеспечивает переносимость ОС между платформами x86, x64, ARM. Драйверы загружаются в пространство ядра и работают на трёх уровнях: высокоуровневые (драйверы файловых систем), промежуточные (фильтры ввода‑вывода) и низкоуровневые (драйверы шин, портов) [Architecture of Windows NT](https://en.wikipedia.org/wiki/Architecture_of_Windows_NT). Модель WDM (Windows Driver Model) и её преемник KMDF (Kernel‑Mode Driver Framework) упрощают написание драйверов, но ошибка в драйвере способна привести к краху системы — это частая причина синих экранов.

**Исполнительная подсистема (Executive)** — центральный компонент режима ядра, включающий несколько менеджеров:

- **Менеджер объектов** управляет всеми системными объектами (процессами, потоками, файлами, семафорами, ключами реестра и т.д.) через единый механизм указателей (handles). Каждый объект имеет атрибуты безопасности, проверяемые монитором безопасности.
- **Менеджер процессов и потоков** создаёт, отслеживает и завершает процессы и потоки, взаимодействует с планировщиком ядра.
- **Менеджер памяти** реализует виртуальную память: адресные пространства процессов, подкачку, разделяемую и страничную память, кэширование.
- **Менеджер ввода‑вывода** обрабатывает запросы через пакеты IRP (I/O Request Packet), организует асинхронный ввод‑вывод и стековую обработку драйверами.
- **Монитор безопасности** обеспечивает разграничение доступа на основе мандатов и привилегий, работает с подсистемой локальной безопасности (lsass.exe) в пользовательском режиме.
- **Кэш‑менеджер** ускоряет доступ к файлам и данным реестра.
- **Менеджер PnP и питания** управляет обнаружением устройств, динамической загрузкой драйверов и энергосбережением.

Все эти менеджеры обмениваются данными через внутренние интерфейсы Executive, не используя прямых переходов между адресными пространствами, что повышает стабильность.

В пользовательском режиме ключевую роль играет **подсистема Win32 (Client/Server Runtime Subsystem – CSRSS)**. На рисунке она отнесена к системным процессам. В ранних версиях NT именно CSRSS содержала оконный менеджер и графический интерфейс (GDI), но начиная с NT 4.0 они были перенесены в режим ядра (win32k.sys) для повышения производительности [Architecture of Windows NT](https://en.wikipedia.org/wiki/Architecture_of_Windows_NT). Тем не менее `csrss.exe` остаётся критическим процессом: его крах вызывает остановку системы. Второй важнейший процесс — `lsass.exe`, реализующий Local Security Authority Subsystem Service. Он обеспечивает аутентификацию, политику безопасности и взаимодействует с монитором безопасности Executive. Отсутствие `lsass.exe` делает вход в систему невозможным.

Системные процессы, автоматически запускаемые на этапе загрузки, образуют жёсткую иерархию: **System (PID 4)** — родитель всех потоков режима ядра, **smss.exe** (диспетчер сеансов) — первый процесс пользовательского режима, который запускает `csrss.exe` и `winlogon.exe`. `winlogon.exe` в свою очередь стартует `services.exe` (менеджер служб) и `lsass.exe`. Многие службы ОС реализованы в разделяемых процессах **svchost.exe**, которые группируются по типам служб. Знание этой иерархии критично для аналитика SOC: любой легитимный процесс имеет определённого родителя; отклонения (например, `svchost.exe` с родителем `explorer.exe`) сразу указывают на аномалию.

Таблица ниже систематизирует основные системные процессы, их нормальное расположение и цифровую подпись — информацию, которую аналитик должен держать в уме.

| Процесс | Типичный путь | Ожидаемый издатель | Назначение |
|---------|---------------|-------------------|------------|
| System (PID 4) | Не имеет исполняемого файла на диске | — | Потоки ядра, рабочие потоки драйверов |
| smss.exe | %SystemRoot%\System32\smss.exe | Microsoft Corporation | Диспетчер сеансов, запуск CSRSS и Winlogon |
| csrss.exe | %SystemRoot%\System32\csrss.exe | Microsoft Corporation | Подсистема API клиент/сервер |
| winlogon.exe | %SystemRoot%\System32\winlogon.exe | Microsoft Corporation | Управление входом в систему |
| services.exe | %SystemRoot%\System32\services.exe | Microsoft Corporation | Контроллер служб |
| lsass.exe | %SystemRoot%\System32\lsass.exe | Microsoft Corporation | Подсистема локальной безопасности |
| svchost.exe | %SystemRoot%\System32\svchost.exe | Microsoft Corporation | Хост-процесс для служб DLL |
| wininit.exe | %SystemRoot%\System32\wininit.exe | Microsoft Corporation | Инициализация сеанса пользователя |

Все перечисленные исполняемые файлы подписаны сертификатом Microsoft Windows Publisher; их неизменное расположение — каталог `System32`. Любое отклонение (путь в `Temp`, отсутствие подписи, подозрительный родитель) должно рассматриваться как потенциально вредоносное событие.

Таким образом, внутреннее устройство Windows — это не просто набор компонентов, а строгая система взаимосвязанных модулей с чётко определёнными интерфейсами и уровнями привилегий. Понимание этой схемы позволяет аналитику читать системные события не как разрозненные записи, а как проявление поведения тех или иных архитектурных элементов.

## Применение архитектурных знаний в работе аналитика SOC

Аналитик центра мониторинга безопасности (SOC L1) сталкивается с необходимостью быстро оценивать легитимность работающих процессов, загруженных драйверов, сетевых подключений и записей журналов событий. Глубокое знание архитектуры Windows напрямую повышает качество триажа и сокращает время реагирования.

### Идентификация легитимных и подозрительных процессов

Основной навык — отличать системные процессы от возможных зловредов по совокупности признаков: путь исполняемого файла, цифровая подпись, родительский процесс, загружаемые DLL, командная строка. Например, стандартный процесс `svchost.exe` всегда находится в `C:\Windows\System32`, подписан Microsoft, а его родительским процессом должен быть `services.exe`. Появление такой же по названию программы в `C:\Users\<User>\AppData\Local\Temp`, запущенной от имени пользователя через скрипт, — верный признак вредоносной активности.

Практический инструмент — **Process Explorer** (Sysinternals), отображающий дерево процессов, путь к образу, издателя и даже загруженные DLL. В командной строке эквивалентную информацию можно получить с помощью PowerShell:

```powershell
Get-Process | Select-Object Name, Id, Path, Company | Format-Table -AutoSize
```

Эта команда выводит все процессы с путём и компанией-издателем. Нормальные системные процессы будут иметь Company = "Microsoft Corporation", а путь — `C:\Windows\System32\...`. Процессы без пути (системные потоки) отображаются с пустым Path, что также является легитимным поведением для PID 4 и некоторых других.

Дополнительно можно проверять цифровую подпись конкретного файла:

```powershell
Get-AuthenticodeSignature "C:\Windows\System32\svchost.exe"
```

Ожидаемый вывод:

```
SignerCertificate       Status        Path
-----------------       ------        ----
CN=Microsoft Windows Publisher  Valid   C:\Windows\System32\svchost.exe
```
Подозрительные образы обычно возвращают `Status = NotSigned` или содержат недействительный сертификат.

### Мониторинг и анализ событий безопасности

Ключевой журнал для отслеживания запуска процессов — Security (события аудита). При включённой политике "Audit Process Creation" в нём регистрируется событие **4688 (A new process has been created)**. Оно содержит поля: NewProcessName, Creator Process ID, Token Elevation Type и многие другие. Аналитик может с помощью встроенной утилиты `wevtutil` выгрузить последние записи:

```cmd
wevtutil qe Security /q:"*[System[EventID=4688]]" /c:10 /rd:true /f:text
```

Вывод покажет полный путь нового процесса, родительский PID, командную строку. Сопоставляя эти данные с эталонной таблицей системных процессов, аналитик быстро отсеивает подозрительные случаи.

Помимо события 4688, полезны логи создания служб (ID 7045 в System), остановки служб (7036), загрузки драйверов (7045/7000), а также события подсистемы WMI (отслеживаются через канал Microsoft-Windows-WMI-Activity/Operational). Понимание архитектуры подсказывает, что легальная служба регистрируется через `services.exe` со стандартным именем и путём к подписанному образу.

### Анализ загруженных драйверов

Драйверы, работающие в режиме ядра, обладают наивысшими привилегиями и нередко используются руткитами. Легитимные драйверы расположены в `C:\Windows\System32\drivers` (или `\DriverStore`), подписаны Microsoft или другим доверенным вендором. Подозрительные — загружены из временных каталогов, имеют аномальные имена, отсутствуют в чистых конфигурациях. Команда PowerShell:

```powershell
Get-WmiObject Win32_SystemDriver | Where-Object {$_.State -eq 'Running'} | Select-Object Name, PathName, Started | Format-List
```

позволяет перечислить работающие драйверы и их файлы. Насторожить должен путь, не соответствующий системному каталогу.

### Понимание механизмов памяти и изолированности

Архитектура виртуальной памяти гарантирует, что один пользовательский процесс не может записать в память другого без специальных привилегий. Следовательно, инжекция кода (например, используемая Meterpreter) требует вызова API `VirtualAllocEx`, `WriteProcessMemory`, что может быть зафиксировано через ETW-трассировку (Event Tracing for Windows) или EDR-решения. Знание того, что память ядра разделяется всеми процессами, объясняет, почему компрометация драйвера позволяет руткиту скрыть процессы и файлы.

Кроме того, сессионная модель Windows (начиная с NT 4.0 Terminal Server) обеспечивает изоляцию пользовательских окружений. Процесс `smss.exe` создаёт отдельные экземпляры `csrss.exe` и `winlogon.exe` для каждой сессии. Вредоносное ПО, пытающееся мигрировать между сессиями, нарушает эту границу.

### Связь с WSL

В версиях Windows 10 и Windows Server 2019 и позже введена подсистема Windows для Linux (WSL), которая исполняет ELF-образы в рамках специализированной подсистемы окружения. Управляющий процесс `init` (PID 1 в контексте WSL) является обычным Windows-процессом, подконтрольным единому ядру. SOC-аналитик может видеть процессы с именем `bash`, `python` в диспетчере задач, но их образы будут расположены в специальном каталоге `C:\Windows\System32\lxss`. Такие процессы также получают PID в общем пространстве Windows и могут взаимодействовать с сетью через тот же стек, что и обычные Win32-приложения [Утраченный потенциал подсистемы Windows для Linux (WSL) / Хабр](https://habr.com/ru/companies/vdsina/articles/535214). Поэтому обнаружение сетевого соединения от незнакомого "Linux‑процесса" не должно автоматически считаться аномалией, если в среде используется WSL.

Таким образом, архитектурные знания не остаются сухой теорией, а превращаются в практический инструментарий для каждодневной работы SOC‑аналитика. Владение схемой системных процессов, умение проверять путь и подпись, читать журналы — базовый триаж, основанный исключительно на понимании устройства ОС.

## Сквозной практический пример: расследование подозрительного процесса

### Исходные условия

Сработало правило SIEM: обнаружен запуск процесса с именем `svchost.exe` из директории `C:\Users\analyst\AppData\Local\Temp`. Система — Windows 10 22H2, аналитик имеет удалённый доступ к хосту через PowerShell Remoting. Задача: подтвердить или опровергнуть вредоносную активность, используя только знания архитектуры и стандартные инструменты.

### Шаги расследования

**Шаг 1. Получение деталей процесса**

Определим все экземпляры `svchost.exe` и сравним пути.

```powershell
Get-Process svchost -ErrorAction SilentlyContinue | Select-Object Name, Id, Path, Company | Format-Table -AutoSize
```

Ожидаемый вывод (сокращённый):

```
Name      Id  Path                                          Company
----      --  ----                                          -------
svchost   928 C:\Windows\System32\svchost.exe               Microsoft Corporation
svchost  1060 C:\Windows\System32\svchost.exe               Microsoft Corporation
svchost  2344 C:\Users\analyst\AppData\Local\Temp\svchost.exe
```

Процесс с PID 2344 выделяется: его путь не в `System32`, поле Company отсутствует. Это сразу классифицируется как аномалия.

**Шаг 2. Определение родительского процесса**

Выясним, кто запустил подозрительный экземпляр.

```powershell
$sus = Get-CimInstance Win32_Process -Filter "Name='svchost.exe' AND ExecutablePath LIKE '%Temp%'"
$parent = Get-CimInstance Win32_Process -Filter "ProcessId=$($sus.ParentProcessId)"
Write-Output "Parent PID: $($parent.ProcessId), Name: $($parent.Name), CommandLine: $($parent.CommandLine)"
```

Примерный вывод:

```
Parent PID: 3112, Name: cmd.exe, CommandLine: "C:\Windows\System32\cmd.exe" /c C:\Users\analyst\AppData\Local\Temp\launch.bat
```

Родителем оказался `cmd.exe`, выполняющий пакетный файл. Это не соответствует архитектуре: легитимные `svchost.exe` всегда порождаются `services.exe` (PID 636 или около того). Отклонение подтверждает подозрения.

**Шаг 3. Проверка журнала событий безопасности**

Найдём событие создания процесса (4688) с подозрительным образом.

```cmd
wevtutil qe Security /q:"*[System[EventID=4688]]" /c:20 /rd:true /f:text | findstr /i "Temp\\svchost.exe"
```

Среди записей видим:

```
Event[0]:
  ...
  NewProcessName: C:\Users\analyst\AppData\Local\Temp\svchost.exe
  Creator Process Name: C:\Windows\System32\cmd.exe
  TokenElevationType: TokenElevationTypeDefault (1)
```

Событие подтверждает, что процесс создан с правами пользователя и без повышения привилегий (TokenElevationType=1). Это типично для вредоносных дропперов.

**Шаг 4. Проверка цифровой подписи**

Проверим подпись подозрительного файла командой:

```powershell
Get-AuthenticodeSignature "C:\Users\analyst\AppData\Local\Temp\svchost.exe" | Format-List
```

Результат:

```
SignerCertificate :
Status            : NotSigned
Path              : C:\Users\analyst\AppData\Local\Temp\svchost.exe
```

Файл не подписан, в то время как легитимный `C:\Windows\System32\svchost.exe` должен иметь статус `Valid` и подписанта `Microsoft Windows Publisher`. Это окончательно указывает на вредоносность.

**Шаг 5. Корреляция с сетевой активностью и эскалация**

Дополнительно аналитик может проверить сетевые соединения процесса, используя:

```powershell
Get-NetTCPConnection -OwningProcess 2344 | Select-Object LocalAddress, RemoteAddress, State
```

Если обнаружены подозрительные внешние соединения, например, к адресу, отсутствующему в белых списках, это становится дополнительным индикатором.

### Ожидаемый вывод

Проведённый анализ демонстрирует, как понимание архитектуры Windows (правильные пути и родители системных процессов, обязательность цифровой подписи Microsoft для компонентов ОС, регистрация событий аудита) позволяет аналитику SOC всего за несколько шагов подтвердить вредоносную активность и инициировать процедуры реагирования. В результате данный инцидент эскалируется для изоляции хоста и удаления зловреда.
