# systemd: юниты, состояния и зависимости сервисов

## systemd: юниты как объекты управления

**systemd** — это системный и сервисный менеджер, принятый по умолчанию в большинстве современных дистрибутивов Linux. Он запускается как первый процесс пространства пользователя (PID 1) и отвечает за инициализацию системы, поддержание пользовательских служб, монтирование файловых систем, управление устройствами и логирование. Центральным понятием всей экосистемы является **юнит (unit)** — абстрактный ресурс, которым systemd умеет управлять. Каждый юнит описывается файлом конфигурации (unit file) и относится к одному из 12 поддерживаемых типов. Именно через юниты администратор взаимодействует с системой: запускает сервисы, создаёт точки монтирования, организует сокет‑активацию и планирует задания.

Файл юнита — это обычный текстовый файл с синтаксисом, напоминающим INI‑файлы Windows, разбитый на секции: `[Unit]`, специфичную для типа секцию (например `[Service]`, `[Socket]`) и `[Install]`. Имена файлов строятся по схеме `<unit_name>.<type_extension>`. Расширение однозначно идентифицирует тип: `sshd.service`, `sshd.socket`, `multi-user.target`. Допускается создание дополнительного каталога `<unit_name>.d/` для переопределения отдельных параметров без правки оригинального файла.

Расположение unit‑файлов жёстко регламентировано, причём каталоги имеют разный приоритет:

| Расположение | Назначение | Приоритет |
|--------------|------------|-----------|
| `/etc/systemd/system/` | Локально созданные или модифицированные администратором юниты, кастомные переопределения | **Наивысший** |
| `/run/systemd/system/` | Юниты времени выполнения, порождённые динамически (например, контейнерами или скриптами) | Средний |
| `/usr/lib/systemd/system/` (или `/lib/systemd/system/`) | Системные юниты, установленные из пакетов | Низший |

```text
[ /etc/systemd/system/ (admin) ]
          |
          v  переопределяет
[ /run/systemd/system/ (runtime) ]
          |
          v  переопределяет
[ /usr/lib/systemd/system/ (vendor) ]
```

Когда systemd загружает юнит с одним и тем же именем, побеждает файл из каталога с наивысшим приоритетом. Это позволяет администратору безопасно кастомизировать поведение стандартных сервисов, не изменяя пакетные файлы. Набор активных юнитов и их зависимостей systemd хранит в оперативной памяти; они не обязаны иметь статический файл — существуют также динамически создаваемые юниты (device, scope) и параметризованные юниты (instanced units), порождаемые по шаблону `имя@.service`.

Ниже перечислены основные типы юнитов. Для специалиста SOC наиболее важны те, что отражают долгоживущие процессы и сетевые точки входа.

| Тип юнита | Расширение | Описание | Пример |
|-----------|------------|----------|--------|
| **Service** | `.service` | Процесс или группа процессов, управляемых systemd. Основной объект контроля в SOC. | `sshd.service` |
| **Socket** | `.socket` | Файловый или сетевой сокет для активации сервиса по подключению. Позволяет отложить запуск демона до реальной необходимости и даёт возможность systemd передать уже поднятый сокет. | `sshd.socket`, `docker.socket` |
| **Target** | `.target` | Группа юнитов, используемая как точка синхронизации при загрузке или смене режима работы (аналог уровня выполнения SysV). | `multi-user.target`, `network-online.target` |
| **Mount** | `.mount` | Точка монтирования, управляемая напрямую systemd. Имя юнита формируется из пути: `/home` → `home.mount`. | `home.mount` |
| **Automount** | `.automount` | Автоматическое монтирование при первом обращении к каталогу. | `home.automount` |
| **Swap** | `.swap` | Раздел или файл подкачки. | `dev-sda3.swap` |
| **Timer** | `.timer` | Планировщик заданий, вытесняющий cron в systemd‑окружении. Активирует связанный `.service` по расписанию. | `logrotate.timer` |
| **Path** | `.path` | Мониторинг файловой системы: при появлении, изменении или удалении файла запускает привязанный сервис. | `cups.path` |
| **Device** | `.device` | Представление устройства ядра. Создаётся динамически на основе событий udev. | `dev-sda2.device` |
| **Slice** | `.slice` | Группа для иерархического управления ресурсами через cgroups. | `system.slice`, `user.slice` |
| **Scope** | `.scope` | Группа процессов, созданная вне systemd (например, сеанс пользователя, запущенный логин‑менеджером). | `session-1.scope` |
| **Snapshot** | `.snapshot` | (Устарел) Снимок состояния юнитов для отката. Не используется в современных версиях. | — |

С точки зрения SOC, наибольшее внимание уделяется Service, Socket и Target: именно они определяют, какие сетевые службы доступны и в каком состоянии.

Структуру unit‑файла удобно рассмотреть на примере штатного `sshd.service` (иллюстративная схема, реальное содержимое варьируется в зависимости от дистрибутива):

```ini
[Unit]
Description=OpenSSH server daemon
Documentation=man:sshd(8) man:sshd_config(5)
After=network.target sshd-keygen.target
Wants=sshd-keygen.target

[Service]
Type=notify
EnvironmentFile=-/etc/crypto-policies/back-ends/opensshserver.config
EnvironmentFile=-/etc/sysconfig/sshd
ExecStart=/usr/sbin/sshd -D $OPTIONS
ExecReload=/bin/kill -HUP $MAINPID
KillMode=process
Restart=on-failure
RestartSec=42s
LimitNOFILE=32768

[Install]
WantedBy=multi-user.target
```

Секция `[Unit]` содержит метаданные и условия запуска: описание, зависимости, порядок. `[Service]` определяет, какой исполняемый файл запускать, как управлять процессом, политику перезапуска и окружение. `[Install]` указывает, в какой target unit встраиваться, чтобы сервис автоматически стартовал при загрузке (через создание символических ссылок в `.wants/`). Эта структура одинакова для всех типов, но конкретное наполнение варьируется: у socket‑юнитов появляется секция `[Socket]` с параметрами прослушиваемого адреса, у mount — `[Mount]` с источником и точкой монтирования, у timer — `[Timer]` с календарным выражением.

В SOC‑контексте понимание структуры unit‑файлов необходимо для быстрого анализа конфигурации критичного сервиса и обнаружения отклонений: подозрительный сервис может иметь легитимное имя, но указать нестандартный `ExecStart`, ведущий на вредоносный бинарник. Поэтому важно уметь быстро просматривать и сравнивать содержимое unit‑файлов с помощью `systemctl cat`, а также вытаскивать отдельные свойства через `systemctl show`.

## Состояния юнитов

Каждый юнит в systemd в любой момент времени характеризуется трёхкомпонентным состоянием, отображаемым в выводе `systemctl` и `systemctl status`: **LOAD** (статус загрузки файла юнита), **ACTIVE** (обобщённое активное состояние) и **SUB** (подсостояние, специфичное для типа юнита). Эта триада позволяет диагностировать как ошибки конфигурации, так и проблемы выполнения.

**LOAD** отражает, насколько успешно systemd загрузил unit‑файл в память:

- `loaded` — файл успешно прочитан, юнит готов к управлению.
- `not-found` — файл не найден ни в одном каталоге.
- `bad-setting` — файл содержит некорректные директивы или логические ошибки.
- `error` — при загрузке произошла ошибка (например, ошибка ввода‑вывода).
- `masked` — юнит символически связан с `/dev/null`, полностью запрещён к запуску.

**ACTIVE** — это обобщённое высокоуровневое состояние, одинаковое для всех типов. Оно отражает жизненный цикл юнита и является основным индикатором при мониторинге и расследовании инцидентов.

| ACTIVE состояние | Описание |
|------------------|----------|
| `active` | Юнит полностью функционирует: для сервиса означает, что основной процесс запущен и (в зависимости от типа) инициализация завершена; для сокета — прослушивание активно; для устройства — оно подключено. |
| `inactive` | Юнит не работает и не пытается запуститься. Процессов, связанных с ним, нет. Это исходное состояние после чистой остановки. |
| `activating` | Переходное состояние: юнит запущен, но ещё не завершил процедуру инициализации. В этот момент он не считается полностью готовым и блокирует старт зависимых юнитов, ожидающих его активации. |
| `deactivating` | Переходное состояние при остановке: systemd ожидает завершения процессов или выполнения стоп‑команд. |
| `failed` | Ошибка во время активации или аварийное завершение процесса. Юнит не выполняет полезной работы. Причина ошибки регистрируется в журнале. |

```text
          ┌─────────────┐
          │   inactive  │◀────────────────────────┐
          └──────┬──────┘                         │
                 │ start (systemctl start)        │
                 ▼                                │
          ┌─────────────┐     ошибка/таймаут      │
          │  activating │─────────────────────┐   │
          └──────┬──────┘                     │   │
                 │ инициализация успешна      │   │
                 ▼                            │   │
          ┌─────────────┐                     │   │
          │   active    │───stop/авария──────▶│   │
          └──────┬──────┘                     ▼   │
                 │                    ┌─────────────┐
                 │                    │   failed    │
                 │                    └──────┬──────┘
                 │                           │ reset-failed / auto-restart
                 │                           │
                 └───────────────────────────┘ (переход в inactive/deactivating)
          (при штатной остановке active → deactivating → inactive)
```

Из схемы видно, что `failed` — это конечное состояние ошибки, из которого юнит сам не выходит. Только администратор может выполнить `systemctl reset-failed` или настроить `Restart=` на `on-failure`, после чего systemd предпримет попытку перезапуска и, в случае успеха, вернёт юнит в цикл `activating → active`.

**SUB** (подсостояние) зависит от типа юнита и уточняет, что именно происходит. Для сервисов (`Type=simple`, `forking`, `oneshot` и др.) список SUB‑состояний особенно богат. Вот основные из них:

| SUB (service) | Описание |
|---------------|----------|
| `dead` | Сервис не активен (процессов нет) — соответствует `inactive` верхнего уровня |
| `condition` | Одно из условий `Condition*=`, заданных в unit‑файле, не выполнено, сервис не запускается |
| `start-pre`, `start`, `start-post` | Выполняются команды `ExecStartPre`, `ExecStart`, `ExecStartPost` |
| `running` | Основной процесс сервиса выполняется (для `Type=simple`, `forking`) |
| `exited` | Процесс сервиса завершился, но юнит считается активным (только для `Type=oneshot` с `RemainAfterExit=yes`) |
| `stop`, `stop-sigterm`, `stop-sigkill`, `stop-post` | Этапы остановки сервиса |
| `failed` | Сервис завершился с ошибкой или превышен тайм‑аут запуска |
| `auto-restart` | Сервис ожидает истечения `RestartSec` перед автоматическим перезапуском |
| `reload` | Выполняется команда `ExecReload` |

Для сокетов (`.socket`) SUB‑состояния включают: `listening` (прослушивание успешно), `running` (есть активные соединения), `dead` (сокет закрыт). Для устройств — `plugged`, `unplugged`. Полный перечень для каждого типа доступен в соответствующей man‑странице (`systemd.service(5)`, `systemd.socket(5)` и т.д.).

Особо отметим `masked` как специальное состояние LOAD: администратор может замаскировать юнит, создав симлинк на `/dev/null`, что полностью предотвращает его запуск (в том числе вручную). Это распространённый приём для отключения небезопасных или конфликтующих сервисов.

Просмотр состояний — рутинная задача SOC‑аналитика. Основные команды:

```bash
# Список всех загруженных юнитов (за исключением устройств)
systemctl list-units

# Состояние конкретного юнита
systemctl status sshd.service

# Краткий ответ: active / inactive / unknown
systemctl is-active sshd.service

# Просмотр только failed-юнитов (ключевой индикатор инцидента)
systemctl --failed

# Детализированный вывод всех свойств в формате key=value
systemctl show sshd.service
```

Для SOC‑специалиста критично понимать, что внезапный переход критичного сервиса в `failed`, `inactive` или даже `activating` (зависание) может быть как результатом аппаратного сбоя, так и признаком атаки (например, эксплуатация уязвимости с остановкой сервиса или DoS). Мониторинг состояния юнитов через `systemctl --failed` или с помощью централизованной системы логирования (журнал `journald`) должен быть частью базовых проверок.

## Зависимости сервисов

Одна из ключевых функций systemd — автоматическое разрешение зависимостей между юнитами. Это позволяет администратору описать, какой сервис должен быть запущен перед другим, какие unit‑ы требуются обязательно, а какие желательны, а также какие комбинации несовместимы. Правильно настроенные зависимости — залог предсказуемой загрузки и стабильной работы, их нарушение может привести к каскадным отказам, что делает эту тему особенно важной для реагирования на инциденты.

Зависимости описываются директивами в секции `[Unit]` и разделяются на два аспекта: **логическую связь** (обязательность, желательность) и **упорядочивание** (последовательность запуска/останова). systemd чётко разделяет эти два аспекта: директива `After` влияет только на порядок, но не заставляет systemd запускать указанный юнит; а `Requires` гарантирует совместный запуск, но без `After` они могут стартовать одновременно.

Основные директивы зависимостей:

| Директива | Тип зависимости | Поведение |
|-----------|----------------|-----------|
| `Requires=` | Жёсткая обязательная | Если требуемый юнит не может быть активирован, текущий юнит также не запустится или будет остановлен при деактивации требуемого. Совместно с `After=` обеспечивает полную гарантию порядка и активации. |
| `Requisite=` | Жёсткая быстрая | Аналогична `Requires=`, но не пытается запустить требуемый юнит, если тот ещё не активен. Применяется для проверки «уже должно быть». |
| `Wants=` | Мягкая рекомендательная | Активирует указанные юниты при старте, но если они не могут запуститься (не найдены, неисправны), это не влияет на запуск текущего юнита. Наиболее часто встречается в сочетании с `After=` для упорядочивания. |
| `BindsTo=` | Жёсткая с отслеживанием | Как `Requires=`, но дополнительно останавливает текущий юнит при неожиданной остановке привязанного (например, крах). Полезно для тесно связанных компонентов, которые должны разделять судьбу. |
| `PartOf=` | Остановка/перезапуск группой | При остановке или перезапуске «родительского» юнита текущий будет так же остановлен или перезапущен. Не влияет на старт. |
| `Conflicts=` | Взаимоисключение | Если текущий юнит запускается, все перечисленные в `Conflicts=` останавливаются, и наоборот. Применяется для предотвращения одновременной работы несовместимых сервисов (например, двух сетевых менеджеров). |
| `After=` | Порядок: после | Текущий юнит будет запущен только после того, как перечисленные юниты полностью перешли в состояние `active` (или их старт завершён). Не тянет за собой активацию. |
| `Before=` | Порядок: перед | Текущий юнит будет запущен до указанных. Аналогично, не влияет на факт их запуска. |

Часто встречающаяся ошибка: в unit-файле задан только `After=postgresql.service`, но не добавлен `Wants` или `Requires`. В этом случае, если PostgreSQL по какой-то причине не стартовал (например, выключен администратором), systemd не попытается его запустить, но текущий юнит всё равно будет ждать, пока его запуск завершится (что никогда не произойдёт). Это приводит к зависанию юнита в состоянии `activating`. Поэтому типичный паттерн для критичной зависимости — комбинация `Requires=` и `After=`.

Кроме явно заданных, systemd автоматически добавляет **неявные зависимости** (implicit dependencies). Например:
- Сервис с `Type=dbus` получает `Requires=dbus.socket` и `After=dbus.socket`.
- Сокет-юниты добавляют `Before=` на сервис, который они активируют.
- Устройства с `BindsTo=` на сервис.  

Эти зависимости прозрачны, но могут усложнять диагностику, если аналитик не ожидает их присутствия.

**Зависимости по умолчанию** (`DefaultDependencies=yes`, что используется всегда) добавляют базовый уровень: для сервисов — `Requires=basic.target` (минимальная инициализация системы) и `Conflicts=shutdown.target`; для таймеров — `Requires=sysinit.target`. Их отключают только в особых случаях (early boot или late shutdown).

Практическая работа с зависимостями для SOC‑аналитика состоит в быстром определении:
- почему сервис не запустился (зависимость не удовлетворена);
- какие юниты остановятся каскадом при падении одного;
- нет ли циклических зависимостей (возникающих, например, при одновременном переопределении юнитов).

Инструменты анализа:

```bash
# Показать рекурсивное дерево зависимостей для юнита
systemctl list-dependencies sshd.service

# Показать обратные зависимости (кто зависит от данного юнита)
systemctl list-dependencies --reverse sshd.service

# Вывести значения конкретных директив
systemctl show -p Wants,Requires,After,Before,Conflicts sshd.service

# Проверить юнит на циклические зависимости и ошибки конфигурации
systemd-analyze verify /etc/systemd/system/myapp.service

# Определить критическую цепочку загрузки (самый долгий путь) до целевого юнита
systemd-analyze critical-chain multi-user.target

# Просмотреть цепочку для конкретного юнита
systemd-analyze critical-chain sshd.service
```

Пример практического unit‑файла с осознанным заданием зависимостей:

```ini
[Unit]
Description=My Python Web Application
After=network-online.target postgresql.service
Requires=postgresql.service
Wants=redis.service
BindsTo=myapp-metrics.service
PartOf=myapp.target

[Service]
Type=simple
User=myapp
Group=myapp
ExecStart=/usr/bin/gunicorn myapp:app
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

- `Requires=postgresql.service` — без СУБД приложение не работает.
- `After=...postgresql.service` — запускаем только после готовности БД.
- `Wants=redis.service` — кеш желателен, но не критичен.
- `BindsTo=myapp-metrics.service` — если сборщик метрик аварийно упал, перезапускаем и веб-приложение (логическая связка).
- `PartOf=myapp.target` — позволяет одной командой `systemctl restart myapp.target` перезапустить всё приложение с зависимостями.

Диагностика зависимостей напрямую связана с состояниями. Если `Requires=` не выполнен (целевой юнит в `inactive` или `failed`), systemd не переведёт наш юнит в `active`. В выводе `systemctl status` появится сообщение `dependency failed`. SOC‑аналитик должен уметь интерпретировать такие сообщения и быстро проверить, не вызвана ли ошибка простой деактивацией службы в результате вредоносных действий.

Дополнительный аспект, важный для безопасности: некоторые вредоносные программы создают свои unit‑файлы с зависимостями от легитимных сервисов, маскируясь под них, или добавляют зависимости к существующим сервисам через механизм override‑каталогов. Обнаружение таких аномалий требует проверки не только самих юнитов, но и их `.d/` каталогов: `ls -la /etc/systemd/system/sshd.service.d/`.

## Сквозной практический пример: расследование отказа SSH из‑за сбоя зависимости

**Исходные условия.** Сервер на RHEL 9 выполняет роль jump‑host. После плановой перезагрузки SOC получает оповещение, что SSH‑сервер не поднимается. Аналитик уровня L1, имея консольный доступ, начинает расследование. Цель — понять, почему `sshd.service` не активен, и восстановить работоспособность, используя знание unit‑состояний и зависимостей.

**Шаг 1. Проверка статуса проблемного сервиса**

```bash
# systemctl status sshd.service
```

Ожидаемый вывод (иллюстративная схема):

```
● sshd.service - OpenSSH server daemon
   Loaded: loaded (/usr/lib/systemd/system/sshd.service; enabled; vendor preset: enabled)
   Active: inactive (dead)
Condition: start condition failed at Wed 2026-01-21 10:17:45 UTC; 2min ago
           └─ ConditionPathExists=!/etc/ssh/sshd_not_to_be_run was not met
     Docs: man:sshd(8)
           man:sshd_config(5)
```

В данном примере показан случай, когда условие `ConditionPathExists=!/etc/ssh/sshd_not_to_be_run` не выполняется (файл существует), поэтому сервис не стартовал. Но в нашем сценарии предположим, что условие — наличие сбойной зависимости. Допустим, `systemctl status` показывает:

```
● sshd.service - OpenSSH server daemon
   Loaded: loaded (/usr/lib/systemd/system/sshd.service; enabled; vendor preset: enabled)
   Active: inactive (dead)
   ...
   Aug 15 10:05:22 jumphost systemd[1]: Dependency failed for OpenSSH server daemon.
   Aug 15 10:05:22 jumphost systemd[1]: sshd.service: Job sshd.service/start failed with result 'dependency'.
```

**Шаг 2. Анализ дерева зависимостей**

```bash
# systemctl list-dependencies sshd.service
```

Вывод:

```text
sshd.service
● ├─sshd-keygen.service
● ├─system.slice
● ├─network.target
● └─sshd-keygen.target
```

Видно, что `sshd-keygen.service` помечен как failed (кружок ●). Это сервис, генерирующий SSH‑ключи хоста, если их нет.

**Шаг 3. Проверка состояния зависимого юнита**

```bash
# systemctl status sshd-keygen.service
```

Ожидаемый артефакт:

```
● sshd-keygen.service - OpenSSH Server Key Generation
   Loaded: loaded (/usr/lib/systemd/system/sshd-keygen.service; static)
   Active: failed (Result: exit-code) since Thu 2025-08-15 10:05:18 UTC; 2min 13s ago
  Process: 1234 ExecStart=/usr/sbin/sshd-keygen (code=exited, status=1/FAILURE)
 Main PID: 1234 (code=exited, status=1/FAILURE)

Aug 15 10:05:18 jumphost systemd[1]: Starting OpenSSH Server Key Generation...
Aug 15 10:05:18 jumphost sshd-keygen[1234]: Could not create directory '/etc/ssh': No space left on device
Aug 15 10:05:18 jumphost systemd[1]: sshd-keygen.service: Main process exited, code=exited, status=1/FAILURE
Aug 15 10:05:18 jumphost systemd[1]: sshd-keygen.service: Failed with result 'exit-code'.
```

Причина локализована: закончилось дисковое пространство, генерация ключей не удалась. Так как `sshd.service` имеет `Requires=sshd-keygen.target` (который в свою очередь требует `sshd-keygen.service`), старт SSH заблокирован.

**Шаг 4. Устранение причины и перезапуск**

SOC аналитик сообщает администратору о необходимости освободить место или сам удаляет устаревшие файлы, после чего выполняет:

```bash
# Сбрасываем состояние failed
systemctl reset-failed sshd-keygen.service

# Пробуем запустить SSH (зависимость разрешится, sshd-keygen запустится автоматически)
systemctl start sshd.service
```

Проверяем итоговое состояние:

```bash
# systemctl is-active sshd.service
active
```

**Шаг 5. Верификация критической цепочки**

```bash
# systemd-analyze critical-chain sshd.service
```

Вывод (схематично):

```text
The time when unit became active or started is printed after the "@" character.
The time the unit took to start is printed after the "+" character.

sshd.service @10.345s
└─sshd-keygen.target @10.343s
  └─sshd-keygen.service @10.342s +1ms
    └─local-fs.target @10.289s
      └─home.mount @10.287s +1ms
```

Цепочка показывает, что `sshd.service` стартовал после успешного завершения `sshd-keygen`, и теперь времена в норме.

**Итог.** Пример демонстрирует типовую последовательность действий L1‑аналитика при расследовании отказа сервиса: от обнаружения неактивного состояния до трассировки зависимостей и выявления корневой причины. Понимание иерархии состояний и директив зависимостей позволяет быстро отличить ошибку конфигурации от аппаратного сбоя и, что принципиально для безопасности, зафиксировать потенциальные следы злонамеренного вмешательства.
