# Связь групповых политик с аудитом и журналированием в Windows

## 1. Групповые политики, аудит и журналирование: разграничение понятий и роль GPO

Групповая политика (Group Policy) в домене Active Directory — основной механизм централизованной настройки параметров безопасности, включая аудит и журналирование. **Аудит безопасности** определяет, какие действия пользователей и системных процессов будут записываться в журнал событий; **журналирование** — процессы создания, хранения, ротации и передачи записей журналов. Эти две составляющие тесно связаны, но управляются разными разделами GPO и преследуют разные эксплуатационные цели. Аудит конфигурирует *что* отслеживается, а журналирование — *как* собираются и обрабатываются полученные данные.

В среде Windows аудит безопасности строится на **политиках аудита** (Audit Policies). Исторически существовали «базовые» политики, задаваемые в разделе `Local Policies\Audit Policy`, и **расширенные политики аудита** (`Advanced Audit Policy Configuration`), появившиеся в Windows Server 2008 R2 / Windows 7. Расширенные политики предоставляют гранулярный контроль на уровне подкатегорий, позволяя включать аудит только для конкретных операций (например, только Kerberos Authentication Service, а не всех событий Account Logon). GPO, применяемые к компьютерам домена, могут настроить обе группы политик, но Microsoft рекомендует не смешивать базовые и расширенные настройки одновременно для одной категории: расширенная политика всегда имеет приоритет, что может привести к неожиданным результатам в отчётах аудита [Guide to Windows Audit Policy Best Practices | Netwrix](https://netwrix.com/en/resources/guides/windows-audit-policy-best-practices).

Журналирование событий, в свою очередь, определяет параметры самой службы Windows Event Log. Через GPO можно задать максимальный размер журнала безопасности, поведение при его заполнении (перезапись, архивирование, остановка), а также права на управление журналом и чтение записей. Например, право `Manage auditing and security log` (управление аудитом и журналом безопасности) выделяется через `User Rights Assignment` в том же дереве `Security Settings`, что и политики аудита, но представляет собой именно механизм контроля доступа к журналированию, а не к регистрируемым событиям [Manage Auditing and Security Log Configuration | CalCom](https://calcomsoftware.com/manage-auditing-and-security-log-configuration).

Таблица ниже фиксирует ключевые различия между аудитом и журналированием в контексте управления через GPO.

| Характеристика               | Аудит (Audit)                                                         | Журналирование (Logging)                                                      |
|------------------------------|-----------------------------------------------------------------------|-------------------------------------------------------------------------------|
| **Что определяет**           | Какие типы событий регистрируются в журнале безопасности              | Как журнал создаётся, хранится, защищается и передается                       |
| **Раздел GPO**               | `Windows Settings\Security Settings\Advanced Audit Policy Configuration` | `Windows Settings\Security Settings\Event Log`; `Administrative Templates\...\Event Log`; `User Rights Assignment` |
| **Ключевые параметры**       | Категории и подкатегории, отслеживание успеха/отказа, SACL объектов  | Размер журнала, метод усечения, права на управление и чтение, настройки пересылки событий |
| **Главный результат**        | Генерация событий с заданными Event ID и полями                      | Доступность, целостность и полнота журнала для расследования и мониторинга   |
| **Типичное применение**      | Обнаружение несанкционированных действий, расследование инцидентов    | Сбор логов в SIEM, соответствие требованиям регулирующих органов, оперативный мониторинг |

Связь между GPO и этими двумя аспектами выражается в том, что **один объект GPO** может одновременно настраивать и аудит (через расширенные политики), и параметры журнала (через административные шаблоны). Именно так администратор добивается согласованности: например, включая аудит событий входа на контроллерах домена и одновременно увеличивая размер журнала безопасности, чтобы уместить весь поток записей. Следует помнить, что автоматические методы аудита, например встроенные в Microsoft Defender for Identity, могут конфликтовать с GPO, так как настройки локальной политики, применённые сенсором, переопределяются GPO при следующем обновлении [Configure Windows event auditing - Microsoft Defender for Identity](https://learn.microsoft.com/en-us/defender-for-identity/deploy/configure-windows-event-collection).

Таким образом, GPO — это универсальный рычаг управления и политикой аудита, и инфраструктурой журналирования в домене Windows, однако каждый из компонентов требует осознанной настройки в своём контексте.

## 2. Механизмы настройки аудита безопасности через GPO

Основная «точка входа» для управления детальным аудитом в домене — узел `Advanced Audit Policy Configuration`. Он расположен по пути:
`Computer Configuration\Policies\Windows Settings\Security Settings\Advanced Audit Policy Configuration\Audit Policies`.
Этот раздел содержит **десять категорий** верхнего уровня (в разных версиях Windows число может незначительно отличаться), каждая из которых разделена на **подкатегории**. Именно включение подкатегорий со значениями `Success` и/или `Failure` порождает записи в журнале безопасности с соответствующими Event ID [Advanced Audit Policy Configuration | Microsoft Learn](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/dn452415(v=ws.11) "Audit Policy Configuration").

Ниже представлена сводка основных категорий с примерами ключевых подкатегорий и индикаторами, важными для специалиста SOC.

| Категория                | Целевой объект мониторинга                                     | Примеры подкатегорий                         | Практическое значение для расследований                                                                        |
|--------------------------|----------------------------------------------------------------|----------------------------------------------|----------------------------------------------------------------------------------------------------------------|
| **Account Logon**        | Проверка учётных данных на контроллере домена или локальном SAM | Kerberos Authentication Service, Credential Validation | Обнаружение атак Kerberoasting, AS-REP Roasting, подбора паролей                                              |
| **Account Management**   | Изменения учётных записей и групп                              | User Account Management, Security Group Management | Выявление создания или эскалации привилегий, несанкционированного членства в административных группах           |
| **Detailed Tracking**    | Активность отдельных процессов и потоков                       | Process Creation, Process Termination        | Сбор информации о запусках подозрительных исполняемых файлов, анализ цепочек заражения (Event ID 4688)          |
| **DS Access**            | Доступ и изменения объектов Active Directory                   | Directory Service Access, Directory Service Changes | Аудит модификаций объектов AD (Event ID 5136, 5137, 5138, 5141); работает только на контроллерах домена        |
| **Logon/Logoff**         | Попытки интерактивного, сетевого или удалённого входа           | Logon, Logoff, Special Logon                 | Фиксация успешных и неудачных входов, RDP-сессий, обнаружение Pass‑the‑Hash                                    |
| **Object Access**        | Попытки доступа к файлам, ключам реестра и другим объектам      | File System, Registry, Kernel Object         | Требует дополнительной настройки SACL; полезна для отслеживания обращений к критичным файлам и ветвям реестра   |
| **Policy Change**        | Изменения политик безопасности, прав назначения и аудита        | Audit Policy Change, Authorization Policy Change | Выявление попыток отключения аудита или модификации политик злоумышленником                                      |
| **Privilege Use**        | Использование назначенных привилегий (SeTakeOwnership и др.)   | Sensitive Privilege Use                      | Обнаружение злоупотребления правами, например захвата файлов или отладки процессов                              |
| **System**               | Изменения системных настроек, влияющие на безопасность          | Security State Change, System Integrity       | Контроль за перезагрузками, очисткой журнала аудита (Event ID 1102), запуском/остановкой защитных служб         |
| **Global Object Access Auditing** | Глобальный аудит доступа к реестру и файловой системе   | Registry, File System (на уровне GPO)        | Упрощает настройку SACL сразу для многих компьютеров без ручного редактирования безопасности каждого объекта    |

Категории `Object Access` и `DS Access`, а также `Global Object Access Auditing`, требуют не только включения политики аудита в GPO, но и настройки **системных списков управления доступом (SACL)** на целевых объектах. SACL определяет, какие именно попытки доступа генерируют события. В GPO имеется специальный узел `Global Object Access Auditing`, позволяющий централизованно задать SACL для реестра и файловой системы — например, аудит всех запросов на чтение или запись к папке `C:\Finance` [Enable Active Directory Auditing – A Step-by-Step Guide](https://www.lepide.com/how-to/enable-active-directory-security-auditing.html).

Иерархию настроек аудита в GPO можно изобразить упрощённой схемой:

```text
[Computer Configuration]
 └── [Policies]
     └── [Windows Settings]
         └── [Security Settings]
             ├── [Local Policies]
             │   └── [Audit Policy]                     ← базовые политики (устаревший метод)
             ├── [Advanced Audit Policy Configuration]  ← расширенные политики
             │   ├── [Audit Policies]
             │   │   ├── Account Logon
             │   │   ├── Account Management
             │   │   ├── Detailed Tracking
             │   │   ├── DS Access
             │   │   ├── Logon/Logoff
             │   │   ├── Object Access
             │   │   ├── Policy Change
             │   │   ├── Privilege Use
             │   │   └── System
             │   └── [Global Object Access Auditing]    ← SACL для реестра и файлов
             └── [Event Log]                             ← параметры журналов событий
```

Важный элемент, обеспечивающий корректную работу расширенных политик, — настройка `Audit: Force audit policy subcategory settings (Windows Vista or later) to override audit policy category settings`. Она находится в `Security Settings\Local Policies\Security Options`. Её включение гарантирует, что детальные подкатегории, заданные через `Advanced Audit Policy Configuration`, не будут сброшены устаревшими базовыми политиками, которые всё ещё могут применяться из других GPO или локально. Без этого флага значения категорий верхнего уровня, определённые в базовой политике аудита, перезаписывают расширенные настройки, что часто приводит к полной потере гранулярности и пропуску нужных событий [Chapter 2 Audit Policies and Event Viewer](https://www.ultimatewindowssecurity.com/securitylog/book/page.aspx?spid=chapter2). Специалисту SOC рекомендуется всегда проверять состояние этого параметра в целевых GPO.

В доменной среде политики аудита традиционно разносят по разным GPO: настройки для контроллеров домена помещают в `Default Domain Controllers Policy` (или отдельную политику, привязанную к OU Domain Controllers), а для рабочих станций и рядовых серверов — в собственную политику, привязанную к соответствующим OU. Такое разделение оправдано: подкатегории `DS Access` имеют смысл только на контроллерах домена, тогда как `Object Access` (файловый аудит) нужен на файловых серверах и рабочих станциях. Попытка включить всё в `Default Domain Policy` приведёт либо к избыточной нагрузке на DC, либо к неполным данным на конечных точках [Audit Policy in Windows Network - Spiceworks Community](https://community.spiceworks.com/t/audit-policy-in-windows-network/680157).

## 3. Применение GPO для управления журналированием и сбором событий

После того как GPO определяет, **какие** события фиксируются, встаёт задача обеспечения сохранности, целостности и доступности журналов. Здесь на передний план выходит управление службой журналирования Windows, которое также поддаётся настройке через групповые политики.

**Параметры размера и поведения журналов.** Через узел `Computer Configuration\Policies\Administrative Templates\Windows Components\Event Log Service` можно контролировать максимальный размер журналов (Application, Security, System и других), задавать метод усечения (перезапись по необходимости, архивирование при заполнении, полная остановка записи) и управлять правами доступа к файлам журналов. Хотя прямые примеры из выдержек не содержат конкретных GUID этих шаблонов, общий подход известен: администратор должен сопоставить предполагаемый объём записей, создаваемых включёнными политиками аудита, с размером журнала и политикой ротации, чтобы избежать потери критичных событий.

**Права на управление журналом и аудитом.** Право `Manage auditing and security log` (SeSecurityPrivilege) определяет, кто может настраивать аудит объектов, очищать журнал безопасности и просматривать его. Согласно лучшим практикам, это право должно быть предоставлено только администраторам и, при наличии Exchange, группе Exchange Servers. В GPO оно настраивается через `Computer Configuration\Windows Settings\Security Settings\Local Policies\User Rights Assignment\Manage auditing and security log`. Если эта настройка «засера», может оказаться, что локальная политика переопределяется GPO и право ограничено неверно [Manage Auditing and Security Log Configuration | CalCom](https://calcomsoftware.com/manage-auditing-and-security-log-configuration).

**Объём данных и практические ограничения.** Включение детального аудита по всем категориям быстро приводит к генерации сотен мегабайт и гигабайт событий в сутки, особенно в больших доменах. Например, только событие создания процесса (Event ID 4688 из категории Detailed Tracking) может дать огромный поток записей. Как отмечает Тони Рейнке в своём практическом руководстве, 4688 — мощное средство для форензики, но без фильтрации известных легитимных процессов оно перегружает SIEM и каналы передачи [A Practical Guide to Starting Your Windows Logging Journey | by Tony Reinke | Medium](https://medium.com/@coachreinke/a-practical-guide-to-starting-your-windows-logging-journey-ce0a2f9720d1). GPO предоставляет только бинарный переключатель «включить/выключить» подкатегорию; более тонкая фильтрация ложится уже на агенты-сборщики (Winlogbeat, Cribl, Graylog) или на правила нормализации в SIEM.

**Недостаточность только GPO для полной картины.** Статья «Windows Logging: A Guide to Enhanced Visibility» подчёркивает, что GPO — это фундамент, но не вся система журналирования. Чтобы детектировать максимум техник MITRE ATT&CK, необходимы также журналы DNS, DHCP, брандмауэра, Sysmon, командных оболочек. Инструмент DeTTECT, упомянутый в той же статье, помогает оценить, какие логи наиболее ценные: журнал выполнения команд (Command Execution) позволяет обнаружить 275 техник MITRE, однако он не включён по умолчанию и активируется только через специальные настройки (например, PowerShell logging через Administrative Templates). GPO может включить часть из них (через `Administrative Templates\System\Audit Process Creation` или `Windows PowerShell`), но не все [Windows Logging: A Guide To Enhanced Visibility](https://www.securityblue.team/blog/posts/windows-logging-enhanced-visibility-guide).

**Проверка и мониторинг применённых настроек.** В операционной деятельности SOC специалисту необходимо уметь быстро верифицировать, какие политики аудита активны на конкретном узле. Для этого используется утилита командной строки **auditpol**. Например, команда `auditpol /get /category:*` выводит текущее состояние всех категорий и подкатегорий аудита — включены ли Success и/или Failure. После применения GPO и выполнения `gpupdate /force` администратор выполняет именно эту проверку.

```bash
:: Просмотр полного списка политик аудита
auditpol /get /category:*
```
Ожидаемый вывод (иллюстративная схема):
```text
System audit policy
Category/Subcategory                      Setting
Account Logon
  Credential Validation                   Success and Failure
  Kerberos Authentication Service         Success and Failure
...
DS Access
  Directory Service Access                Success
  Directory Service Changes               Success and Failure
...
```

Дополнительно для анализа содержимого журнала безопасности может использоваться утилита **wevtutil**, способная не только запрашивать события, но и выгружать конфигурацию журнала в XML.
```bash
wevtutil gp Microsoft-Windows-Security-Auditing /ge:true /gm:true /f:xml > audit_config.xml
```
Этот приём позволяет получить полную схему возможных событий (все возможные идентификаторы) для данного журнала, что помогает при разработке правил корреляции [Chapter 2 Audit Policies and Event Viewer](https://www.ultimatewindowssecurity.com/securitylog/book/page.aspx?spid=chapter2).

**Связывание GPO с централизованным сбором логов.** Настроив аудит через GPO, необходимо обеспечить доставку событий в SIEM-систему. Применяются агенты (Microsoft Monitoring Agent, Winlogbeat и пр.), которые читают журналы Windows и передают их в коллектор. GPO может влиять на права доступа к этим журналам, но сами настройки пересылки — обычно локальные или управляются через Configuration Manager. Тем не менее, грамотная комбинация расширенных политик аудита (GPO) и агентов сбора даёт специалисту SOC всеобъемлющую телеметрию без дублирования и потери критичных данных. Системные аудиторы Microsoft рекомендуют группировать серверы по классам рабочих нагрузок и определять отдельные политики аудита для каждой группы, чтобы избежать избыточного журналирования и упростить фильтрацию [System Audit Policy recommendations | Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/audit-policy-recommendations).

## 4. Сквозной практический пример: настройка аудита изменений AD через GPO и проверка журналов

### Исходные условия
Тестовая среда: домен `lab.local`, контроллер домена на Windows Server 2019, рабочая станция администратора с установленной консолью Group Policy Management. Задача: включить аудит всех изменений объектов Active Directory (`DS Access`) на контроллере домена, убедиться, что события генерируются и корректно записываются в журнал безопасности. Пример выполняется от имени доменного администратора.

### Шаг 1. Создание и привязка объекта GPO
В консоли `Group Policy Management` создаём новый объект GPO с именем `SOC-Audit-DS` и связываем его с организационной единицей `Domain Controllers`. Редактируем политику:
- Переходим в `Computer Configuration\Policies\Windows Settings\Security Settings\Advanced Audit Policy Configuration\Audit Policies\DS Access`.
- Открываем подкатегорию **Directory Service Changes**, включаем аудит успеха и отказа (`Success and Failure`).
Аналогично включаем подкатегорию **Directory Service Access** (Success and Failure).

### Шаг 2. Принудительное применение и верификация
На контроллере домена выполняем обновление политики и проверяем применённые настройки аудита:

```powershell
gpupdate /force
auditpol /get /category:"DS Access"
```
Ожидаемый вывод:
```text
System audit policy
Category/Subcategory                      Setting
DS Access
  Directory Service Access                Success and Failure
  Directory Service Changes               Success and Failure
  Directory Service Replication           No Auditing
  Detailed Directory Service Replication  No Auditing
```

### Шаг 3. Генерация тестового события
Создаём изменение атрибута любого пользователя в AD (например, меняем описание). Здесь используется модуль Active Directory для PowerShell:

```powershell
Set-ADUser -Identity "testuser" -Description "Test modification for audit"
```
Теперь на контроллере домена ищем соответствующее событие. Изменение объекта AD фиксируется событием **5136** (A directory service object was modified). Запросим последнее событие 5136:

```powershell
Get-WinEvent -LogName Security -FilterXPath "*[System[EventID=5136]]" -MaxEvents 1 | Format-List
```
Ожидаемый вывод (сокращённая иллюстративная схема):
```text
TimeCreated  : 04/01/2025 14:22:10
Id           : 5136
Message      : A directory service object was modified.
```

### Шаг 4. Интерпретация и вывод
Факт: после настройки GPO, включающей подкатегорию `Directory Service Changes`, любое изменение атрибутов объектов в AD записывается в журнал безопасности контроллера домена с детализацией субъекта, объекта и изменённого атрибута. Эти данные могут быть немедленно переданы в SIEM-систему, настроенную на сбор журнала Security с DC, для корреляции и алертинга. Таким образом, продемонстрирована сквозная цепочка: **GPO → расширенная политика аудита → генерация события Windows → запись в журнал безопасности → возможность использования в SOC-аналитике**.
