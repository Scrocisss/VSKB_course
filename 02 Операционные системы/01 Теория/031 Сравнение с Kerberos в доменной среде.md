# Сравнение NTLM и Kerberos в доменной среде Windows

## 1. Место NTLM и Kerberos в экосистеме Windows-аутентификации

NTLM (NT LAN Manager) и Kerberos — два фундаментальных протокола аутентификации в сетях Windows. Оба встроены в архитектуру безопасности операционной системы и используются для проверки подлинности пользователей, компьютеров и служб при доступе к ресурсам. Несмотря на то что Microsoft перевела доменную аутентификацию на Kerberos ещё в Windows 2000, NTLM остаётся активным протоколом, применяемым в качестве запасного варианта во многих сценариях, а также поддерживается для обратной совместимости с устаревшими системами и нестандартными конфигурациями.

Для специалиста SOC L1 критически важно чётко разграничивать эти протоколы: различия в механизмах безопасности напрямую определяют модели угроз, индикаторы компрометации и методологию расследования инцидентов. Путаница между ними может привести к неверной классификации события, пропуску атаки или ложному срабатыванию.

NTLM — это протокол проверки подлинности на основе запроса-ответа (challenge-response), работающий без доверенной третьей стороны. Kerberos, напротив, использует модель с центром распределения ключей (Key Distribution Center, KDC) и билетную систему, обеспечивая взаимную аутентификацию, единый вход (Single Sign‑On) и делегирование полномочий.

В доменной среде Active Directory оба протокола обслуживаются инфраструктурой контроллеров домена, но принципиально различаются криптографической стойкостью, устойчивостью к атакам и способностью масштабироваться. При этом они сосуществуют благодаря протоколу согласования SPNEGO (Simple and Protected GSS-API Negotiation Mechanism), который автоматически выбирает наиболее безопасный доступный метод: Kerberos пытается выполниться первым, а при невозможности — происходит откат на NTLM.

Сравнительная таблица ниже фиксирует ключевые разграничения между протоколами на высоком уровне.

| Характеристика                     | NTLM                                                               | Kerberos                                                                                   |
|------------------------------------|--------------------------------------------------------------------|--------------------------------------------------------------------------------------------|
| Тип протокола                      | Запрос-ответ (challenge-response) без участия третьей стороны      | Билетная система с центром распределения ключей (KDC)                                     |
| Основные версии                    | NTLMv1, NTLMv2                                                      | Kerberos v5 (с расширениями Microsoft)                                                     |
| Взаимная аутентификация            | Отсутствует (клиент проверяет сервер, сервер не проверяет клиента)  | Присутствует (сервер также доказывает свою подлинность клиенту)                            |
| Передача учётных данных по сети    | Хэш пароля не передаётся, но ответ можно атаковать офлайн (NTLMv1) | Пароль передаётся только один раз для получения TGT; последующая работа — по билетам       |
| Криптографическая основа           | MD4 (хэш пароля), DES/RC4 (сессионные ключи) – устаревшие          | AES, RC4-HMAC (современные реализации используют AES)                                     |
| Поддержка SSO                      | Нет (каждое обращение к ресурсу требует нового цикла запрос-ответ)  | Да (один раз полученный TGT позволяет запрашивать сервисные билеты без повторного ввода)   |
| Делегирование                      | Только ограниченное делегирование (через CredSSP)                   | Полное и ограниченное делегирование Kerberos (Kerberos delegation)                         |
| Типичные уязвимости и атаки        | Pass-the-Hash, NTLM Relay, brute-force офлайн                       | Kerberoasting, Golden Ticket, Silver Ticket, AS-REP Roasting                              |
| Роль в современной доменной среде  | Запасной протокол при отказе Kerberos, поддержка устаревших систем  | Протокол по умолчанию для всех версий Windows начиная с 2000 года                          |

Такое разграничение помогает на первом этапе анализа события определить, какой протокол был задействован, и уже исходя из этого выбирать дальнейший вектор расследования.

## 2. Внутреннее устройство и протокольные потоки

Оба протокола опираются на криптографические хэши паролей пользователей, хранящиеся в Active Directory, но кардинально различаются способом их использования. Разберём внутреннюю механику каждого.

### 2.1. Поток аутентификации NTLM

Наиболее полная и безопасная версия — NTLMv2. Классический сценарий: клиент обращается к серверу, не имеющему прямого доступа к контроллеру домена (или когда Kerberos недоступен). Поток выглядит так:

1. **Согласование (Negotiate).** Клиент отправляет серверу имя пользователя и список поддерживаемых возможностей.
2. **Запрос (Challenge).** Сервер генерирует 16-байтовое (128 бит) случайное число — вызов (challenge) — и отсылает его клиенту.
3. **Ответ (Response).** Клиент вычисляет NT-хэш пароля (MD4 от Unicode-пароля), затем с помощью HMAC-MD5 на основе этого хэша и временной метки/случайного числа клиента формирует ответ на вызов. Ответ включает также имя пользователя и имя целевого сервера (для предотвращения relay-атак в NTLMv2). Клиент отправляет ответ серверу.
4. **Проверка.** Сервер пересылает три значения: имя пользователя, вызов и ответ — контроллеру домена по протоколу Netlogon. Контроллер домена извлекает из своей базы NT-хэш пароля пользователя, повторяет вычисление ответа и сравнивает с полученным. При совпадении аутентификация успешна, и сервер получает уведомление.
5. После успеха сервер может создать сеансовый ключ для подписания и шифрования трафика (опционально).

Упрощённая ASCII-схема NTLM-потока:

```text
Клиент                                   Сервер                         Контроллер домена
  │                                        │                                     │
  │──── Имя пользователя (Negotiate) ────►│                                     │
  │◄─── 16-байтовый challenge ────────────│                                     │
  │                                        │                                     │
  │── Ответ = HMAC_MD5(NT-hash, challenge, │                                     │
  │    время/клиентский nonce, target) ──►│                                     │
  │                                        │─── username, challenge, response ──►│
  │                                        │◄───── success/fail ────────────────│
  │◄─── разрешение / отказ ──────────────│                                     │
```

Важно: при использовании локальных учётных записей (не доменных) сервер самостоятельно хранит NT-хэш и не обращается к контроллеру домена — проверка происходит локально.

### 2.2. Поток аутентификации Kerberos

Kerberos реализует модель доверенной третьей стороны. Все стороны доверяют центру распределения ключей (KDC), который совмещён с контроллером домена в Windows. В протоколе задействованы два подсервера KDC: служба выдачи билетов на предоставление билетов (Ticket Granting Service, TGS) и служба аутентификации (Authentication Service, AS). Поток включает три основных обмена:

1. **Обмен AS (Authentication Service).** Клиент отправляет на AS запрос аутентификации (KRB_AS_REQ), содержащий имя пользователя и зашифрованные временные метки. AS проверяет субъект, извлекает его долговременный ключ (полученный из пароля) и в случае успеха возвращает зашифрованный билет (TGT, Ticket Granting Ticket) и сеансовый ключ для дальнейшего взаимодействия с TGS. Ключ шифрования TGT известен только KDC.
2. **Обмен TGS (Ticket Granting Service).** Когда клиенту нужен доступ к конкретному сервису, он предъявляет TGT и запрашивает сервисный билет (KRB_TGS_REQ). TGS расшифровывает TGT, подтверждает подлинность клиента и выпускает сервисный билет, зашифрованный секретным ключом целевого сервера. Клиент получает этот билет и сеансовый ключ для связи с сервером.
3. **Обмен AP (Application Request).** Клиент отправляет сервисный билет серверу вместе с аутентификатором, зашифрованным сеансовым ключом. Сервер, обладая своим секретным ключом, расшифровывает билет, извлекает сеансовый ключ, проверяет аутентификатор и тем самым взаимно аутентифицирует клиента.

ASCII-диаграмма высокоуровнево:

```text
Клиент                                        KDC (AS + TGS)                     Сервер приложений
  │                                                  │                                   │
  │──── KRB_AS_REQ (запрос аутентификации) ────────►│                                   │
  │◄─── KRB_AS_REP (TGT + сеансовый ключ) ──────────│                                   │
  │                                                  │                                   │
  │──── KRB_TGS_REQ (TGT + запрос на сервис) ──────►│                                   │
  │◄─── KRB_TGS_REP (сервисный билет + ключ) ───────│                                   │
  │                                                                                     │
  │──── KRB_AP_REQ (сервисный билет + аутентификатор) ─────────────────────────────────►│
  │◄─── (взаимная аутентификация опциональна в ответе) ────────────────────────────────│
```

В Microsoft-реализации Kerberos существенно расширен: добавлена поддержка публичных ключей (PKINIT), передача авторизационных данных (PAC — Privilege Attribute Certificate), протоколы делегирования (S4U2Self, S4U2Proxy) и другие элементы, критичные для работы доменных служб.

Для наглядного сравнения технических деталей протоколов приведём таблицу:

| Элемент                          | NTLM                                                                 | Kerberos (Microsoft)                                                       |
|----------------------------------|----------------------------------------------------------------------|----------------------------------------------------------------------------|
| Доверенная сторона               | Отсутствует; каждая пара клиент-сервер взаимодействует напрямую       | KDC (контроллер домена)                                                    |
| Идентификатор сессии/пользователя| Имя пользователя + имя целевого сервера в хэше ответа                 | Билет (TGT, сервисный билет) с зашифрованным идентификатором и PAC         |
| Срок действия учётных данных     | Одноразовый, на один цикл запрос-ответ                               | TGT обычно 10 часов, сервисные билеты — 10 часов (настраивается)           |
| Алгоритмы шифрования             | NTLMv1: DES + MD4; NTLMv2: HMAC-MD5 + MD4                             | По умолчанию AES256-CTS-HMAC-SHA1-96, поддержка RC4-HMAC для совместимости  |
| Устойчивость к Pass-the-Hash     | Хэш NT позволяет аутентифицироваться без пароля — Pass-the-Hash возможен | TGT требует сеансового ключа, но Pass-the-Ticket возможен при компрометации|
| Влияние на нагрузку DC           | Каждый вход требует обращения к DC для проверки ответа                | Обращение к DC только при получении TGT; сервисные билеты могут кэшироваться |
| Использование в службах          | При доступе по IP-адресу, отсутствии SPN, в рабочих группах           | Требует регистрации SPN, доступа к DC по имени хоста                      |

Такое детальное сопоставление позволяет специалисту SOC определить, какой протокол вероятнее всего был задействован в конкретном событии, исходя из контекста и параметров входа.

## 3. Применение, мониторинг и типичные сценарии использования

В реальной доменной среде Windows определение задействованного протокола аутентификации — рутинная задача при анализе событий безопасности. Понимание того, какой протокол использован, позволяет не только классифицировать легитимность попытки входа, но и выявить аномалии: например, внезапное использование NTLM на ресурсах, где обычно применяется Kerberos, может указывать на атаки типа NTLM Relay или Pass-the-Hash.

### 3.1. Идентификация протокола в журналах событий

Основным источником информации для аналитика SOC L1 служит журнал безопасности Windows. При успешной сетевой аутентификации (не интерактивной) регистрируется событие **4624** (An account was successfully logged on). Внутри этого события заполняется поле `AuthenticationPackageName`, принимающее значения:

- `NTLM` — если использовался протокол NTLM;
- `Kerberos` — если Kerberos;
- `Negotiate` — когда применялся пакет SPNEGO, выбравший конкретный протокол (обычно при неудаче Kerberos произошёл откат на NTLM, и в итоге пакет покажет фактический протокол).

Фрагмент вывода PowerShell для выборки таких событий (иллюстративный):

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4624} -MaxEvents 10 |
  Select-Object TimeCreated,
    @{n='User';e={$_.Properties[5].Value}},
    @{n='Domain';e={$_.Properties[6].Value}},
    @{n='AuthenticationPackage';e={$_.Properties[10].Value}}
```

Пример ожидаемого вывода (иллюстративная схема, значения зависят от среды):

```
TimeCreated           User           Domain       AuthenticationPackage
-----------           ----           ------       ---------------------
12.05.2023 09:15:32   ivanov         CORP         Kerberos
12.05.2023 09:15:45   petrov         CORP         NTLM
12.05.2023 09:16:01   svc-backup     CORP         NTLM
```

Проверка версии NTLM (v1 или v2) обычно осуществляется через расширенный аудит: дополнительно включается аудит события 4625 (failed logon) с кодом подстатуса 0xC000006A, либо используются специализированные политики аудита (Audit Logon -> Success/Failure). Для детального анализа также анализируют пакет аутентификации в событии 4627 (информация о группе глобальной безопасности), но это редко встречается в L1.

При анализе Kerberos информативны события:

- **4768** — выдан TGT (успех/отказ);
- **4769** — запрос сервисного билета (позволяет обнаружить Kerberoasting: шифрование RC4-HMAC — `TicketEncryptionType 0x17` и `0x0` для DES, что является подозрительным);
- **4771** — неудачный предварительный вход Kerberos (полезен для выявления AS-REP Roasting и брутфорса).

### 3.2. Практические команды для быстрой проверки

**Просмотр кэшированных билетов Kerberos** на рабочей станции:

```cmd
klist
```

Вывод показывает TGT и полученные сервисные билеты. Отсутствие TGT при доменной учётной записи — косвенный признак, что последняя аутентификация могла проходить по NTLM.

**Сброс всех билетов и принудительное получение нового TGT** (помогает в тестировании откатов):

```cmd
klist purge
```

После этого любое обращение к ресурсу либо инициирует полный Kerberos-поток, либо, если Kerberos недоступен, прозрачно упадёт на NTLM.

**Проверка необходимого для Kerberos имени субъекта службы (SPN)** на серверном объекте:

```powershell
setspn -L <имя_сервера>
```

Отсутствие зарегистрированного SPN для службы — одна из самых частых причин использования NTLM вместо Kerberos при доступе к ресурсу по протоколам SMB, HTTP и другим.

### 3.3. Типичные сценарии использования и подводные камни

- **Доступ к ресурсу по IP-адресу**, а не по полному доменному имени (FQDN). Kerberos требует, чтобы клиент мог определить SPN, а он привязывается к DNS-имени. Поэтому `\\192.168.1.10\share` всегда вызовет NTLM. SOC-аналитик должен распознавать такие случаи как неопасные, но указывающие на несоответствие архитектурным рекомендациям.
- **Отсутствие связи с контроллером домена.** Если клиент не может достичь DC, Kerberos невозможен. Например, машина в удалённой сети без VPN, либо проблемы с DNS — в таких ситуациях происходит откат на NTLM с использованием кэшированных учётных данных (если включена политика «кэширования входа»).
- **Устаревшие или плохо сконфигурированные приложения**, жёстко задающие NTLM без поддержки Negotiate. Microsoft ведёт работу по переводу встроенных компонентов на Negotiate с последующей поддержкой IAKerb и локального KDC в Windows 11, однако многие сторонние сервисы (например, старые веб-приложения с Windows-аутентификацией) могут по-прежнему требовать NTLM.
- **Рабочие группы и локальные учётные записи** всегда используют NTLM, поскольку Kerberos требует инфраструктуры KDC и Active Directory.

Мониторинг SOC L1 должен включать регулярный анализ доли NTLM-аутентификаций в общем потоке событий 4624. Внезапный рост может свидетельствовать о DoS-атаке на KDC, ошибках конфигурации или компрометации. Контроль за ивентами 4769 с нетипичным типом шифрования позволяет своевременно выявить попытки Kerberoasting.

## 4. Сквозной практический пример: расследование подозрительного входа с использованием NTLM

**Исходные условия**  
Аналитик SOC L1 получает уведомление от SIEM о повторяющихся успешных аутентификациях на файловый сервер `FS01.corp.local` с рабочей станции `DESKTOP-X`, которая обычно использует Kerberos. Сервер является высокопривилегированным, доступ к нему должен осуществляться строго по Kerberos. Необходимо оперативно проверить, не произошло ли отката на NTLM, и оценить легитимность сессии.

**Инструменты**  
- Журналы безопасности на контроллере домена (или на целевом сервере, если настроен сбор).
- PowerShell для выборки событий.
- Утилита `klist` на клиентской машине (при возможности её опроса).

### Шаг 1. Получение событий входа на сервер

На сервере `FS01` или на сборщике логов аналитик выполняет выборку актуальных событий 4624 за последние 15 минут, фильтруя по имени целевого компьютера.

```powershell
$events = Get-WinEvent -ComputerName FS01.corp.local -FilterHashtable @{
    LogName='Security'; Id=4624; StartTime=(Get-Date).AddMinutes(-15)
} -ErrorAction SilentlyContinue
```

### Шаг 2. Анализ пакета аутентификации и пользователя

Извлекаем основные поля интересующих событий:

```powershell
$events | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $props = @{
        Time = $_.TimeCreated
        User = ($xml.Event.EventData.Data | Where-Object {$_.Name -eq 'TargetUserName'}).'#text'
        Domain = ($xml.Event.EventData.Data | Where-Object {$_.Name -eq 'TargetDomainName'}).'#text'
        AuthPkg = ($xml.Event.EventData.Data | Where-Object {$_.Name -eq 'AuthenticationPackageName'}).'#text'
        LogonType = ($xml.Event.EventData.Data | Where-Object {$_.Name -eq 'LogonType'}).'#text'
        Workstation = ($xml.Event.EventData.Data | Where-Object {$_.Name -eq 'WorkstationName'}).'#text'
    }
    [PSCustomObject]$props
}
```

Пример вывода (значения иллюстративны, структура реальна):

```
Time                  User        Domain  AuthPkg  LogonType Workstation
----                  ----        ------  -------  --------- ----------
12.05.2023 16:01:12   svc-backup  CORP    NTLM     3         DESKTOP-X
12.05.2023 16:02:45   svc-backup  CORP    NTLM     3         DESKTOP-X
```

Наблюдаем, что служебная учётная запись `svc-backup` выполняет вход с типом 3 (сетевая аутентификация) по NTLM, причём с машины, от которой обычно ожидается Kerberos.

### Шаг 3. Проверка контекста через Kerberos-события на DC

Чтобы понять, пыталась ли эта учётная запись получить TGT (что указало бы на нормальную работу Kerberos), аналитик проверяет событие 4768 за тот же период на контроллере домена:

```powershell
Get-WinEvent -ComputerName DC01.corp.local -FilterHashtable @{
    LogName='Security'; Id=4768; StartTime=(Get-Date).AddMinutes(-30)
} | Where-Object { $_.Properties[0].Value -eq 'svc-backup' } |
    Select-Object TimeCreated, @{n='Status';e={$_.Properties[4].Value}}
```

Вывод пуст — ни одного TGT за последние полчаса. Это означает, что учётная запись не аутентифицировалась через Kerberos и, скорее всего, используется скомпрометированный хэш (Pass-the-Hash).

### Шаг 4. Дополнительная перекрёстная проверка на рабочей станции (если доступна)

При наличии агента или возможности удалённого подключения аналитик запускает на `DESKTOP-X`:

```cmd
klist sessions
```

В списке активных сессий Kerberos отсутствует сессия `svc-backup`. Это подтверждает, что ни одна легитимная служба не запускала аутентификацию от имени этой учётной записи через Kerberos, а все сетевые входы шли через NTLM.

**Ожидаемый вывод** по совокупности артефактов: выявлена аномальная активность — серия успешных NTLM-аутентификаций сервисной учётной записи с отсутствием TGT, что является классическим индикатором Pass-the-Hash или использования скомпрометированного NT-хэша. Инцидент эскалируется на L2/L3 для дальнейшего анализа исходной рабочей станции и изоляции.
