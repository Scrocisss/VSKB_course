# Mount points и виртуальные файловые системы в Linux (proc, sysfs, tmpfs)

## 1. Точки монтирования: единое дерево и механизмы присоединения файловых систем

В Linux все файловые системы существуют в рамках единого иерархического дерева каталогов. Корнем этого дерева служит каталог `/`. В отличие от Windows, где каждому диску соответствует отдельная буква (`C:`, `D:`), в Linux нет отдельного пространства имён для носителей — разделы жёсткого диска, сетевые хранилища, образы дисков и даже виртуальные файловые системы становятся частью одной иерархии. Процесс включения содержимого файловой системы в это дерево называется **монтированием** (mounting), а каталог, в который подключается файловая система, — **точкой монтирования** (mount point) [hackware.ru](https://hackware.ru?p=14459).

Монтирование реализовано на уровне ядра через подсистему **Virtual File System (VFS)**. VFS предоставляет приложениям единый интерфейс работы с файлами (`open`, `read`, `write`, `close`) независимо от типа нижележащей файловой системы: ext4, XFS, tmpfs или сетевая NFS. При запросе к файлу VFS перенаправляет вызов драйверу конкретной ФС, скрывая от пользователя детали формата хранения [Selectel](https://selectel.ru/blog/directory-structure-linux), [DEV Community](https://dev.to/kanywst/linux-file-system-architecture-a-deep-dive-into-vfs-inodes-and-storage-1n9). Таким образом, точка монтирования — это позиция в едином дереве, в которой VFS подключает корневую директорию новой ФС, заменяя собой содержимое соответствующего каталога на время монтирования.

### 1.1 Контекст и базовые понятия

Для анализатора SOC первого уровня важно понимать, какие файловые системы смонтированы на исследуемом узле, и как отличить легитимное монтирование от потенциально подозрительного. Основные сущности:

- **Блочное устройство** — физический или виртуальный диск (`/dev/sda`, `/dev/nvme0n1`, `/dev/loop0`). Перед монтированием на нём должна быть создана файловая система (форматирование).
- **Точка монтирования** — существующий каталог (часто пустой), на который выполняется монтирование. Если каталог содержал файлы, они становятся недоступны, пока ФС не будет отмонтирована.
- **Тип файловой системы** — идентификатор драйвера (`ext4`, `xfs`, `tmpfs`, `proc`, `sysfs` и т.д.), передаваемый опцией `-t` команды `mount`. При отсутствии явного указания `mount` пытается определить тип по суперблоку.
- **Опции монтирования** — параметры, управляющие поведением ФС: `ro` (только чтение), `noexec` (запрет исполнения файлов), `nosuid` (игнорирование битов SUID/SGID), `nodev` (запрет интерпретации файлов устройств) и другие. Опции критичны для безопасности.
- **Таблица файловых систем `/etc/fstab`** — статический список файловых систем, которые монтируются автоматически при загрузке или по команде `mount -a`. Каждая строка содержит шесть полей: устройство, точка монтирования, тип ФС, опции, флаг дампа и номер для fsck.
- **Журнал монтирования `/proc/mounts`** — виртуальный файл, отражающий текущее состояние смонтированных ФС в представлении ядра. Этот файл не хранится на диске и является наиболее точным источником информации о точках монтирования [Red Hat](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/4/html/introduction_to_system_administration/s4-storage-mounting-proc).

Стандартный синтаксис монтирования:
```bash
mount -t <тип_ФС> -o <опции> <устройство|имя> <точка_монтирования>
```
Например, подключение раздела ext4 на `/mnt/data`:
```bash
mount -t ext4 /dev/sda3 /mnt/data
```
Для размонтирования используется `umount <точка>` или `umount <устройство>`.

Пользователи часто путают `mount` и `fstab`: первая — разовая операция, вторая — постоянная конфигурация. Точка монтирования, созданная через `mount`, не переживёт перезагрузку, если она не прописана в `/etc/fstab` или не управляется systemd (автоматическое монтирование через `.mount`-юниты).

### 1.2 Специальные виды монтирования

Помимо стандартного подключения блочных устройств, Linux поддерживает несколько особых режимов, которые часто встречаются в SOC-расследованиях.

**Bind mount** — подмонтирование одной части дерева в другую точку без указания типа ФС. Файлы становятся доступными по двум путям одновременно. Применяется для переопределения каталогов (например, в контейнерах) или предоставления доступа к части файловой системы. С точки зрения VFS bind mount выглядит как самостоятельная точка монтирования, но на уровне inode данные остаются общими. Команда:
```bash
mount --bind /var/log /mnt/log_copy
```
Создаёт зеркало `/var/log` в `/mnt/log_copy`. В выводе `findmnt` такие монтирования отображаются с полем `SOURCE`, указывающим на исходный каталог. Для SOC-аналитика bind mount может быть использован злоумышленником для сокрытия файлов путём перекрытия каталога другим монтированием.

**Loop mount** — подключение образа диска (файла) как блочного устройства через loop-драйвер. Широко применяется в форензике для монтирования полученных dd-образов:
```bash
mount -o loop,ro disk_image.dd /mnt/forensic
```
Опция `ro` гарантирует отсутствие изменений в образе.

**Overlay mount** — объединение нескольких каталогов в один многослойный вид (нижний слой только для чтения, верхний — для записи). Используется в контейнеризации (Docker overlay2) и chroot-средах. Для SOC это важно, так как анализ файлов внутри контейнера требует понимания структуры оверлеев.

**Виртуальные файловые системы** (proc, sysfs, tmpfs, devpts) не связаны с физическими носителями — их содержимое формируется на лету ядром и хранится в оперативной памяти или swap. Именно эти ФС и рассматриваются далее.

### 1.3 Просмотр точек монтирования в Linux

Классическая команда `mount` без аргументов выводит список смонтированных ФС, однако её вывод может быть неточным: она читает `/etc/mtab`, который иногда рассинхронизируется с реальным состоянием ядра [Unix & Linux Stack Exchange](https://unix.stackexchange.com/questions/24182/how-to-get-the-complete-and-exact-list-of-mounted-filesystems-in-linux). Более надёжный метод — файл `/proc/mounts`. Он представляет собой построчное перечисление всех смонтированных ФС в формате:
```
<устройство> <точка> <тип> <опции> <частота_дампа> <порядок_fsck>
```
Пример фрагмента:
```text
rootfs / rootfs rw 0 0
/dev/sda1 / ext4 rw,relatime 0 0
proc /proc proc rw,nosuid,nodev,noexec,relatime 0 0
tmpfs /run tmpfs rw,nosuid,nodev,size=... 0 0
```
Содержимое `/proc/mounts` генерируется непосредственно ядром и всегда актуально. Аналитик SOC может использовать его для быстрого выявления неизвестных точек монтирования, особенно тех, что могут маскировать вредоносную активность (например, перекрытие `/etc` bind-монтированием).

Утилита `findmnt` (часть util-linux) выводит иерархическое дерево точек монтирования в удобочитаемой форме и поддерживает форматированный вывод, включая JSON для автоматизации:
```bash
findmnt --json
```
Для исключения виртуальных ФС из отчёта `df` полезна опция `-x`:
```bash
df -hx tmpfs -x devtmpfs -x proc -x sysfs --output=source,target
```
Это даёт картину только физических носителей.

Для SOC важно знать, что злоумышленники могут монтировать ФС с опциями, облегчающими скрытие или сохранение персистентности (например, `noexec` на `/tmp` можно обойти через tmpfs или bind). Поэтому инвентаризация монтирований — обязательный шаг при реагировании на инцидент.

### 1.4 Сравнительная таблица типов монтирования

| Тип монтирования | Описание | Типичная точка | SOC-контекст |
|------------------|----------|----------------|--------------|
| Физическая ФС (ext4, xfs, btrfs) | Хранение данных на блочном устройстве | `/`, `/home`, `/var` | Анализ целостности, обнаружение скрытых файлов |
| Виртуальная ФС (proc, sysfs) | Интерфейс к данным ядра и устройствам | `/proc`, `/sys` | Получение информации о процессах, параметрах системы |
| tmpfs | Файловая система в ОЗУ и swap | `/run`, `/tmp`, `/dev/shm` | Временное хранилище, может скрывать артефакты |
| devtmpfs | Динамическое создание файлов устройств до запуска udev | `/dev` | Интерпретация устройств |
| Bind mount | Зеркалирование каталога | Различные, зависит от конфигурации | Потенциальное сокрытие легитимных каталогов |
| Overlay mount | Многослойное объединение (нижний ro, верхний rw) | `/var/lib/docker/overlay2`, `/run/overlay` | Анализ контейнерных сред |
| Loop mount | Монтирование файла-образа как устройства | Путь анализатора во время форензики | Исследование образов дисков |
| FUSE (userspace) | Файловая система, реализованная в пользовательском пространстве | Например, sshfs, encfs | Может использоваться для эксфильтрации или скрытия |

Таблица иллюстрирует разнообразие механизмов, с которыми сталкивается специалист SOC. Далее мы углубимся в наиболее важные для расследований виртуальные ФС: proc, sysfs и tmpfs.

## 2. Виртуальная файловая система proc — интерфейс к процессам и ядру

### 2.1 Назначение и место в системе

Файловая система `/proc` (procfs) является одним из основных механизмов взаимодействия пользовательского пространства с ядром Linux. Она не хранит данные на диске — всё её содержимое формируется динамически при обращении к файлам. procfs предоставляет информацию о запущенных процессах, состоянии памяти, параметрах сети, версии ядра и позволяет изменять некоторые настройки ядра во время работы (через `/proc/sys`) [kernel doc](https://docs.kernel.org/filesystems/proc.html).

Монтирование procfs обычно задаётся строкой в `/etc/fstab`:
```
proc    /proc    proc    defaults    0    0
```
Типичные опции монтирования: `nosuid`, `noexec`, `nodev` — для минимизации рисков. Ядро монтирует `/proc` автоматически на раннем этапе загрузки, но в среде LFS (Linux from Scratch) необходимо выполнить ручное монтирование:
```bash
mount -vt proc proc /proc
```
[LFS](https://www.linuxfromscratch.org/lfs/view/10.1-systemd/chapter07/kernfs.html)

procfs реализована в коде ядра (подкаталог `fs/proc/`) и использует тот же VFS-интерфейс, что и дисковые ФС. Для каждого процесса создаётся подкаталог с именем PID, содержащий множество псевдофайлов, которые при чтении возвращают структурированную информацию из соответствующих внутренних структур ядра (`task_struct`, `mm_struct` и др.).

### 2.2 Структура файловой системы proc

Корневой каталог `/proc` содержит как глобальные системные файлы, так и подкаталоги процессов. Основные элементы:

**Глобальные файлы (примеры):**

- `/proc/cpuinfo` — информация о процессоре (vendor, модель, флаги).
- `/proc/meminfo` — детальная статистика использования памяти.
- `/proc/loadavg` — средняя загрузка системы.
- `/proc/version` — версия ядра.
- `/proc/mounts` — список смонтированных ФС (обсуждался ранее).
- `/proc/filesystems` — поддерживаемые типы ФС.
- `/proc/net/tcp`, `/proc/net/udp` — таблицы сетевых соединений (raw).
- `/proc/sys/` — подкаталог, через который доступны параметры sysctl для настройки ядра.

**Подкаталоги процессов (примеры для PID=1234):**

- `/proc/1234/cmdline` — командная строка запуска (аргументы, разделённые нулевым байтом).
- `/proc/1234/environ` — переменные окружения процесса.
- `/proc/1234/cwd` — символическая ссылка на текущий рабочий каталог.
- `/proc/1234/exe` — символическая ссылка на исполняемый файл.
- `/proc/1234/fd/` — каталог с символическими ссылками на открытые файловые дескрипторы.
- `/proc/1234/maps` — карта виртуальной памяти.
- `/proc/1234/status` — состояние процесса в удобочитаемой форме.
- `/proc/1234/stat`, `/proc/1234/statm` — компактные статусные данные.

Процесс может читать свои файлы в `/proc/self/` без дополнительных прав, но для чтения файлов других процессов требуются capability `CAP_SYS_PTRACE` или `CAP_PERFMON`, за исключением файла `/proc/PID/mem`, который требует `CAP_SYS_PTRACE` с PTRACE_MODE_ATTACH [kernel doc](https://docs.kernel.org/filesystems/proc.html). Это важно для SOC-аналитика: без соответствующих прав невозможно прочитать, например, переменные окружения или карту памяти чужих процессов, что может ограничить анализ.

### 2.3 Использование proc в SOC-анализе

procfs — один из первых источников при расследовании инцидента. Несколько типовых операций:

1. **Получение списка процессов с путями:** 
   ```bash
   for pid in /proc/[0-9]*; do echo "$pid $(cat $pid/cmdline | tr '\0' ' ')"; done
   ```
   Команда выведет список запущенных процессов с командными строками. Вредоносный процесс может иметь подменённый `cmdline` (например, через `argv[0]`), но путь через `exe` даёт точную информацию.

2. **Анализ открытых файловых дескрипторов:** 
   ```bash
   ls -l /proc/1234/fd
   ```
   Позволяет увидеть, какие файлы, сокеты или pipe использует процесс. Это критично для выявления скрытых соединений или файлов.

3. **Проверка сетевых соединений:** 
   Помимо стандартной `netstat`, можно проанализировать `/proc/net/tcp` и `/proc/net/udp` (шестнадцатеричные таблицы). Они содержат локальный и удалённый адрес, состояние соединения. Инструменты вроде `ss` читают именно эти файлы.

4. **Обнаружение скрытых процессов через `/proc`:** 
   Некоторые руткиты пытаются скрыть процессы, перехватывая системные вызовы чтения каталогов. Если стандартная команда `ps` не видит процесс, прямое сканирование `/proc`-каталогов (например, `ls /proc`) может выдать PID скрытого процесса при условии, что ядро не скомпрометировано на уровне VFS. Сравнение вывода `ps` и прямого листинга `/proc` — известный приём выявления скрытых процессов.

5. **Экспорт параметров системы:** 
   `/proc/meminfo` и `/proc/cpuinfo` иногда полезны для понимания загруженности узла, которая могла быть аномальной во время атаки.

Пример чтения `/proc/1234/status` (иллюстративная схема полей):
```
Name:   nginx
Umask:  0022
State:  S (sleeping)
Tgid:   1234
Ngid:   0
Pid:    1234
PPid:   1
Uid:    80  80  80  80
Gid:    80  80  80  80
FDSize: 64
Groups: 80
VmRSS:    10240 kB
```
Эти поля позволяют определить идентификаторы пользователя, родительский процесс и использование памяти.

### 2.4 /proc/sys — настройка ядра во время работы

Подкаталог `/proc/sys` предоставляет интерфейс к sysctl. Запись чисел или строк в определённые файлы изменяет параметры ядра без перезагрузки. Например, для включения IP-форвардинга:
```bash
echo 1 > /proc/sys/net/ipv4/ip_forward
```
А для чтения текущего значения:
```bash
cat /proc/sys/net/ipv4/ip_forward
```
Злоумышленники могут изменять эти параметры для включения маршрутизации, отключения проверок безопасности (например, `rp_filter`) или изменения параметров памяти. В SOC-анализе необходимо проверять аномальные значения в `/proc/sys`, сравнивая их с эталонной конфигурацией.

Стандартная утилита `sysctl` является более удобной обёрткой:
```bash
sysctl net.ipv4.ip_forward
```
В современных системах `sysctl.conf` и юниты systemd управляются через `/etc/sysctl.d/`, но фактическое чтение/запись происходит через `/proc/sys`.

### 2.5 Ограничения и безопасность procfs

Несмотря на мощь, procfs имеет особенности, важные для SOC:

- **Размеры файлов:** большинство файлов имеют нулевой отображаемый размер (`ls -l` показывает 0). Реальное содержимое генерируется при чтении.
- **Изменчивость:** информация может быть неконсистентна из-за гонок чтения (несколько вызовов `read` могут получить разные данные, если процесс завершился). Рекомендуется за один вызов считывать целостный блок.
- **Права доступа:** ядро строго контролирует доступ к чувствительным файлам. Без правильных capabilities попытка чтения `/proc/<pid>/mem` завершится с `EPERM`.
- **Защита от переполнения ссылок:** при завершении процесса его PID может быть переиспользован. Открытые файловые дескрипторы к `/proc/<pid>` почившего процесса больше не будут действовать на новый процесс с тем же PID (ядро возвращает `ESRCH`) [kernel doc](https://docs.kernel.org/filesystems/proc.html).

### 2.6 Структурная визуализация ключевых файлов proc

```text
/proc
├── 1/                    (процесс init или systemd)
│   ├── cmdline
│   ├── environ
│   ├── exe -> /usr/lib/systemd/systemd
│   ├── fd/
│   │   ├── 0 -> /dev/null
│   │   └── 1 -> /dev/null
│   └── ...
├── self -> 1234/         (символическая ссылка на процесс читающего)
├── cpuinfo
├── meminfo
├── mounts
├── net/
│   ├── tcp
│   └── udp
├── sys/
│   └── net/ipv4/ip_forward
└── version
```

## 3. Виртуальная файловая система sysfs — представление устройств и драйверов

### 3.1 Назначение и отличие от proc

sysfs (монтируется обычно на `/sys`) — это виртуальная файловая система, служащая для представления иерархии объектов ядра (kobjects) в пространстве пользователя. Основное назначение — экспорт информации об устройствах, драйверах, шинах и некоторых подсистемах ядра (питание, firmware) [opensource.com](https://opensource.com/article/19/3/virtual-filesystems-linux). В отличие от procfs, которая содержит плоскую или слабо структурированную коллекцию псевдофайлов, sysfs организована строго иерархически и отражает модель драйверов Linux (device model).

Ключевое разграничение: `/proc` — это в первую очередь интерфейс к процессам и глобальным счётчикам, `/sys` — к объектам ядра, представляющим физические и виртуальные устройства.

sysfs была введена в ядро 2.6 для устранения хаоса в `/proc/bus` и `/proc/driver` и обеспечения единообразного API для скриптов и инструментов управления устройствами. Стандартная точка монтирования:
```
sysfs    /sys    sysfs    defaults    0    0
```
На практике монтирование выполняется на этапе загрузки системой инициализации.

### 3.2 Структура каталогов sysfs

Корень `/sys` содержит несколько подкаталогов верхнего уровня, отражающих основные подсистемы:

- **`/sys/block`** — символические ссылки на блочные устройства (реальные и виртуальные). Каждая ссылка ведёт в реальное расположение в `/sys/devices`. Устарело, но оставлено для совместимости.
- **`/sys/class`** — группировка устройств по функциональным классам: `net` (сетевые интерфейсы), `block`, `tty`, `gpio` и др. Каждая запись — символическая ссылка на узел в `/sys/devices`.
- **`/sys/devices`** — реальное дерево всех устройств, обнаруженных ядром. Отражает физическую топологию (PCI, USB, platform).
- **`/sys/bus`** — содержит подкаталоги для каждой шины (pci, usb, serio, platform) и показывает, какие драйверы и устройства привязаны к шине.
- **`/sys/kernel`** — параметры и статистика различных подсистем ядра, не привязанные к конкретным устройствам (mm, kexec, ftrace).
- **`/sys/firmware`** — интерфейс к firmware (ACPI, DMI, efi).
- **`/sys/power`** — управление энергосбережением и ждущим режимом.

Каждый каталог устройства содержит атрибуты в виде файлов, доступных для чтения и иногда для записи. Например, для сетевого интерфейса eth0 в `/sys/class/net/eth0/` присутствуют файлы:

- `address` — MAC-адрес
- `mtu` — максимальный размер пакета
- `speed` — скорость линка в Мбит/с
- `carrier` — 1, если линк активен
- `statistics/rx_bytes`, `statistics/tx_bytes` — счётчики трафика

Чтение этих файлов не требует повышенных привилегий, что делает sysfs удобным инструментом для SOC-аналитика при сборе сетевой информации.

### 3.3 Применение sysfs в SOC-анализе

Анализ sysfs позволяет:

- **Получить аппаратный MAC-адрес** без угрозы подмены со стороны драйвера в пространстве пользователя:
  ```bash
  cat /sys/class/net/eth0/address
  ```
  Вывод: `aa:bb:cc:dd:ee:ff` (иллюстративная схема). Это более надёжно, чем `ifconfig eth0`, если драйвер не скомпрометирован.
- **Определить наличие скрытых сетевых интерфейсов**: сравнение вывода `ls /sys/class/net` с `ip link` может выявить интерфейсы, которые были скрыты руткитом на уровне procfs, но всё ещё видны в sysfs.
- **Проверить статус блочных устройств**: файл `/sys/block/sda/removable` равен 0 для внутреннего диска, 1 для USB. Это важно при поиске несанкционированных носителей.
- **Изучить загруженные модули ядра**: каталог `/sys/module` содержит подкаталог для каждого модуля с файлом `refcnt` (счётчик ссылок) и подкаталогом `parameters`, где отображаются значения параметров модуля. Команда `ls /sys/module | grep -v "^kernel$"` покажет модули, загруженные в настоящее время. Это дополняет `lsmod` и может помочь в обнаружении вредоносного модуля ядра, который пытается скрыть себя из `lsmod`, но может оставить след в sysfs.
- **Сбор информации о PCI-устройствах**: для поиска подозрительного оборудования (например, карт захвата или беспроводных адаптеров, не ожидаемых в составе сервера) полезно просмотреть `/sys/bus/pci/devices/`. Файлы `vendor` и `device` дают коды VEN/DEV, по которым можно определить производителя.

Пример чтения информации о PCI-устройстве (слот 0000:00:19.0):
```bash
cat /sys/bus/pci/devices/0000:00:19.0/vendor
```
Вывод (иллюстративный): `0x8086` (Intel).

### 3.4 Практические команды и артефакты для sysfs

Ниже приведены типовые операции, используемые при сборе артефактов.

**Список сетевых интерфейсов с адресами и статусом:**
```bash
for iface in /sys/class/net/*; do
  echo "$(basename $iface): addr=$(cat $iface/address), carrier=$(cat $iface/carrier)";
done
```
Пример вывода:
```
eth0: addr=aa:bb:cc:dd:ee:ff, carrier=1
lo: addr=00:00:00:00:00:00, carrier=1
```

**Анализ загруженных модулей (сравнение с lsmod):**
```bash
ls /sys/module/ | sort > /tmp/sys_modules.txt
lsmod | awk 'NR>1 {print $1}' | sort > /tmp/lsmod_modules.txt
diff /tmp/sys_modules.txt /tmp/lsmod_modules.txt
```
Наличие различий может указывать на модуль, скрывающий себя от `lsmod`.

**Получение счётчиков трафика:**
```bash
cat /sys/class/net/eth0/statistics/rx_packets
cat /sys/class/net/eth0/statistics/tx_bytes
```
Эти счётчики обновляются ядром и могут использоваться для обнаружения аномального увеличения трафика во время инцидента.

## 4. Виртуальная файловая система tmpfs — данные в оперативной памяти

### 4.1 Концепция и свойства

tmpfs — виртуальная файловая система, размещающая своё содержимое в виртуальной памяти (ОЗУ ± swap). Она не имеет физического образа на диске и отличается исключительно высоким быстродействием при доступе к файлам. Ключевые свойства [man tmpfs(5)](https://man7.org/linux/man-pages/man5/tmpfs.5.html):

- Размер ФС ограничен либо отсутствием лимита, либо явной опцией `size`. По умолчанию при отсутствии явного размера ядро выделяет 50% физической ОЗУ.
- При нехватке физической памяти страницы вытесняются в swap, если он активирован и не был отключён опцией `noswap` (начиная с Linux 6.4).
- После размонтирования tmpfs все данные теряются безвозвратно, что делает её идеальной для временного хранения, не требующего сохранности после перезагрузки.
- Во время remount (`mount -o remount`) можно изменить размер ФС без потери текущего содержимого.

Базовое создание и монтирование:
```bash
mount -t tmpfs -o size=100M,mode=0755 tmpfs /mnt/ramdisk
```
После этого каталог `/mnt/ramdisk` содержит новую пустую ФС размером 100 МБ с правами доступа `755`. Для демонстрации:
```bash
df -h /mnt/ramdisk
```
вывод (иллюстративный):
```
Filesystem      Size  Used Avail Use% Mounted on
tmpfs           100M     0  100M   0% /mnt/ramdisk
```

### 4.2 Опции монтирования tmpfs

Основными опциями являются:

- **`size=<байты>`** — максимальный размер ФС. Поддерживаются суффиксы k, m, g (киби, меби, гиби), а также процент от RAM (например, `size=20%`). Ноль означает отсутствие ограничения (не рекомендуется).
- **`nr_blocks=<блоки>`** — то же, что size, но в единицах PAGE_SIZE (обычно 4 КиБ).
- **`nr_inodes=<число>`** — максимальное количество инодов. По умолчанию примерно половина числа физических страниц ОЗУ.
- **`mode`**, **`uid`**, **`gid`** — начальные права доступа и владельцы корневого каталога.
- **`noswap`** (с 6.4) — запрещает вытеснение страниц в swap, т.е. данные всегда остаются в ОЗУ, что может привести к OOM при переполнении.

Пример с ограничением размера и указанием конкретного пользователя:
```bash
mount -t tmpfs -o size=50M,mode=0700,uid=1000 tmpfs /home/user/ramdisk
```

Проверка использования:
```bash
df -h /home/user/ramdisk
```
и детальное:
```bash
findmnt /home/user/ramdisk
```
вывод в JSON для автоматизации (иллюстративная структура):
```json
{
  "filesystems": [
    {
      "target":"/home/user/ramdisk",
      "source":"tmpfs",
      "fstype":"tmpfs",
      "options":"rw,nosuid,nodev,size=50M,mode=0700,uid=1000"
    }
  ]
}
```

### 4.3 Стандартные точки монтирования tmpfs

В современных Linux-дистрибутивах tmpfs активно используется:

- **`/tmp`** — временные файлы сессии. Часто монтируется с размером 50% RAM, опциями `nosuid,nodev`.
- **`/run`** (ранее `/var/run`) — информация о работающих демонах (PID-файлы, сокеты). Создаётся на раннем этапе загрузки, обычно небольшого размера.
- **`/dev/shm`** — POSIX shared memory, используется для межпроцессного взаимодействия. По умолчанию размер — 50% RAM.
- **`/run/lock`** или `/var/lock` — файлы блокировок.
- **`/sys/fs/cgroup`** — контрольные группы (cgroups v2), монтируется tmpfs для поддержки иерархий.
- **`/run/user/<UID>`** — временные каталоги пользователей (для XDG_RUNTIME_DIR), управляются pam_systemd.

Эти точки обычно создаются systemd и не требуют ручного вмешательства. Однако аналитик SOC должен быть осведомлён о них для интерпретации вывода `df` и `/proc/mounts`. Например, частое наличие неожиданной tmpfs с нестандартным размером или точкой монтирования (вроде `/var/tmp` или пользовательского пути) может быть следствием действий злоумышленника, создавшего скрытое временное хранилище для вредоносных инструментов.

### 4.4 Безопасность и применение в SOC-контексте

tmpfs предоставляет несколько преимуществ с точки зрения безопасности и анализа:

1. **Автоматическая очистка:** при перезагрузке или размонтировании данные исчезают без возможности восстановления (если только не был настроен выделенный swap-файл, но это нестандартно). Это снижает риск оставления следов после очистки, но в то же время затрудняет форензику.
2. **Создание временного рабочего пространства для аналитики:** SOC-специалист может смонтировать tmpfs (например, `/mnt/analysis`) и скопировать туда подозрительные файлы для проверки в изолированной среде. Поскольку tmpfs не оставляет следов на диске, это минимизирует риск заражения хоста аналитика (если работать без сохранения на диск).
3. **Выявление скрытых процессов через использование tmpfs:** некоторые вредоносные программы размещают свои исполняемые файлы в tmpfs (например, в `/dev/shm` или `/tmp`), чтобы избежать записи на диск и обойти антивирусную проверку. Аналитик должен обращать внимание на исполняемые файлы, лежащие в этих каталогах, особенно с битом execute.
4. **Обход ограничений `noexec`:** если на раздел `/tmp` на реальном диске наложена опция монтирования `noexec`, но злоумышленник создаёт свою tmpfs поверх `/tmp` с другими опциями, он может обойти запрет. Проверка через `/proc/mounts` покажет перекрывающее монтирование.

Пример проверки: команда 
```bash
findmnt -t tmpfs --output=TARGET,OPTIONS
```
выведет все точки tmpfs и их опции, позволяя быстро оценить, есть ли аномалии.

### 4.5 Сравнение tmpfs и ramfs

Существует и более старая виртуальная ФС — ramfs, которая также хранит данные в ОЗУ, но не поддерживает ограничение размера и не использует swap. Из-за этого ramfs может привести к исчерпанию памяти и краху системы. tmpfs безопаснее и предпочтительнее. В современных ядрах ramfs отключена по умолчанию, и её использование не рекомендуется. Для SOC важно знать, что если где-то встретится ramfs, это может быть признаком ручного вмешательства (злоумышленник может попытаться использовать её для скрытия, но это маловероятно из-за риска зависания).

### 4.6 Таблица распространённых tmpfs и их настроек

| Точка монтирования | Типичный размер | Назначение | Примечания для SOC |
|--------------------|-----------------|------------|-------------------|
| `/tmp` | 50% RAM (или размер в fstab) | Временные файлы | Проверить аномальные файлы с execute |
| `/run` | 10–20% RAM | Данные демонов | Содержит PID-файлы, сокеты |
| `/dev/shm` | 50% RAM | POSIX shared memory | Может использоваться для хранения вредоносных полезных нагрузок |
| `/run/user/<uid>` | 10% RAM (до 100 MB) | Сессионные данные пользователя | Проверить скрытые скрипты |
| `/sys/fs/cgroup` | Обычно 1–8 MB | cgroup v2 иерархия | Не изменяется пользователем |

## Сквозной практический пример: обнаружение и анализ подозрительной активности через файловую систему

### Исходные условия
На рабочей станции аналитика SOC развёрнута тестовая среда CentOS 8. В ходе мониторинга поступил алерт о подозрительном сетевом подключении с локального адреса к внешнему IP на нестандартном порту. Необходимо провести экспресс-расследование на предмет возможной компрометации узла, используя знания о точках монтирования и виртуальных ФС.

### Шаг 1. Сбор информации о текущих точках монтирования
Первым делом получаем полный перечень смонтированных ФС напрямую от ядра. Это поможет выявить нестандартные монтирования (например, tmpfs с широкими правами или bind mount, скрывающий легитимные каталоги).

```bash
cat /proc/mounts
```
Ожидаемый фрагмент вывода (иллюстративная схема):
```
sysfs /sys sysfs rw,nosuid,nodev,noexec,relatime 0 0
proc /proc proc rw,nosuid,nodev,noexec,relatime 0 0
tmpfs /run tmpfs rw,nosuid,nodev,size=1638400k,mode=755 0 0
/dev/sda1 / ext4 rw,relatime 0 0
tmpfs /dev/shm tmpfs rw,nosuid,nodev 0 0
tmpfs /var/tmp tmpfs rw,relatime,size=512M 0 0
```
Анализ: видим tmpfs на `/var/tmp` с размером 512M. В стандартной конфигурации `/var/tmp` обычно расположен на корневой ФС. Такое монтирование может быть создано атакующим для временного хранения инструментов. Проверяем, прописана ли эта точка в `/etc/fstab`:

```bash
grep '/var/tmp' /etc/fstab
```
Вывод: строка отсутствует. Значит, монтирование не является постоянным, что усиливает подозрения.

### Шаг 2. Анализ процессов через /proc
Исходя из алерта, определяем PID подозрительного процесса (допустим, PID=5789). Изучаем информацию о нём:

```bash
ls -l /proc/5789/exe
```
Вывод:
```
lrwxrwxrwx 1 root root 0 May 10 14:22 /proc/5789/exe -> /var/tmp/.hidden/binary
```
Путь указывает на исполняемый файл внутри подозрительной tmpfs. Далее смотрим командную строку:

```bash
cat /proc/5789/cmdline | tr '\0' ' '
```
Вывод:
```
/var/tmp/.hidden/binary --server 192.0.2.50:4444
```
Процесс с криптосервером во внешней сети — явный признак обратного шелла. Проверяем открытые дескрипторы:

```bash
ls -l /proc/5789/fd
```
Ожидаемый фрагмент:
```
3 -> socket:[12345678]
4 -> /var/tmp/.hidden/config.lck
```
socket указывает на сетевое соединение.

### Шаг 3. Сбор артефактов устройства и модулей через sysfs
Чтобы выяснить, не был ли загружен вредоносный модуль ядра для скрытия, сравниваем модули, видимые в sysfs, с выводом `lsmod`:

```bash
ls /sys/module/ | sort > /tmp/sys_modules.txt
lsmod | awk 'NR>1 {print $1}' | sort > /tmp/lsmod_modules.txt
diff /tmp/sys_modules.txt /tmp/lsmod_modules.txt
```
Если разница пуста, скрытых модулей нет. Дополнительно проверяем сетевые интерфейсы на предмет промisc-режима (вдруг включен сниффинг):

```bash
cat /sys/class/net/eth0/flags
```
Вывод (иллюстративный): `0x1003`. Флаг 0x100 (IFF_PROMISC) указывает на promiscuous mode. Это может говорить о захвате трафика. Для подтверждения сравниваем с эталоном.

### Шаг 4. Создание безопасного хранилища tmpfs для сохранения улик
Чтобы скопировать подозрительные файлы из `/var/tmp/.hidden/` без риска заражения аналитической машины и без записи на диск, создаём собственную tmpfs только для чтения и переносим туда копии:

```bash
mount -t tmpfs -o size=100M,mode=0500 tmpfs /mnt/forensic
cp /var/tmp/.hidden/binary /mnt/forensic/binary
cp /var/tmp/.hidden/config.lck /mnt/forensic/
```
Точка `/mnt/forensic` доступна только для чтения владельцу root, данные в ней не переживут размонтирование. После копирования можно передать образ tmpfs для углублённого анализа (например, через dd в образ, но tmpfs не является блочным устройством, поэтому придётся копировать файлы по сети). Данная изоляция гарантирует, что даже вредоносный код не сможет изменить скопированные артефакты.

### Ожидаемый результат
Проделанные шаги демонстрируют, как систематическое использование информации о точках монтирования, procfs, sysfs и tmpfs позволяет обнаружить несанкционированное монтирование, идентифицировать вредоносный процесс, проверить целостность ядра и безопасно собрать улики. Аналитик SOC L1, владея этими инструментами, способен оперативно подтвердить или опровергнуть факт компрометации и передать эскалацию с качественным контекстом.
