# Права доступа в Linux: базовые биты rwx для владельца, группы и остальных

## 1. Контекст и базовые понятия: модель безопасности файловой системы Linux

В операционных системах семейства Linux реализована концепция «всё есть файл»: любой ресурс — текстовый документ, жёсткий диск, сетевое соединение — представлен в виде байтового потока, занимающего определённый объём в памяти [netangels.pro](https://www.netangels.pro/article/prava-na-fajly-i-papki-v-linux-rukovodstvo-dlya-razrabotchikov-i). Управление доступом к этим ресурсам осуществляется на уровне файловой системы через дискреционную модель прав, в которой для каждого объекта (файла или каталога) задаются три независимых набора разрешений: для владельца, для группы владельца и для всех остальных пользователей. Понимание этой модели критически важно для специалиста SOC L1, поскольку инциденты часто связаны с некорректными разрешениями на лог-файлы, конфигурационные каталоги, скрипты и инструменты мониторинга.

Фундамент модели составляют три субъекта доступа:

- **Владелец (user, owner)** — учётная запись, создавшая файл или явно назначенная администратором. Каждый пользователь имеет уникальный числовой идентификатор UID; владельцем файла становится эффективный UID процесса, его создавшего. Владелец обладает наиболее широкими (но не обязательно полными) правами на объект и может изменять его разрешения [linuxfoundation.org](https://www.linuxfoundation.org/blog/blog/classic-sysadmin-understanding-linux-file-permissions).
- **Группа владельца (group)** — совокупность пользователей, объединённых общим идентификатором GID. Групповое членство позволяет организовать коллективный доступ без раздачи прав каждому пользователю по отдельности. Один пользователь может входить в несколько групп, но для конкретного файла действует только одна назначенная группа-владелец [firstvds.ru](https://firstvds.ru/technology/linux-permissions).
- **Остальные (others)** — все прочие учётные записи системы, не являющиеся владельцем и не входящие в группу-владельца. Эта категория часто обозначается как «мир» (world), и настройки для неё определяют минимальный уровень доступа [hostiq.ua](https://hostiq.ua/wiki/permissions).

Иерархия проверки прав жёсткая: ядро последовательно сравнивает эффективные UID/GID процесса, пытающегося получить доступ, с владельцем и группой объекта. Совпадение с владельцем сразу определяет результирующие права; если владелец не совпал, проверяется членство в группе, и только затем применяются разрешения для «остальных». Никакого «наследования» или суммирования прав между категориями не происходит.

Каждое из трёх множеств разрешений кодирует три базовых операции:

- **Чтение (r)** — для файла позволяет открыть и прочитать его содержимое; для каталога даёт возможность получить список имён файлов (например, через `ls`). Без права `r` на каталог пользователь не может прочитать имена его записей, даже зная их имена [freecodecamp.org](https://www.freecodecamp.org/news/linux-chmod-chown-change-file-permissions).
- **Запись (w)** — для файла разрешает изменение содержимого, включая добавление и усечение. Для каталога — создание, удаление и переименование записей внутри него, независимо от прав на сами записи [adminvps.ru](https://adminvps.ru/blog/kak-smenit-vladelcza-papki-i-izmenit-prava-dostupa-v-linux).
- **Выполнение (x)** — для файла интерпретируется как право запуска исполняемого бинарного кода или скрипта (при наличии корректного shebang’а). Для каталога бит выполнения означает право на переход внутрь каталога (`cd`), то есть на проход через него к нижележащим объектам [help.rc.unc.edu](https://help.rc.unc.edu/how-to-use-unix-and-linux-file-permissions).

Различие в семантике `x` для файлов и каталогов — одна из распространённых точек недопонимания среди начинающих специалистов. Нижеприведённая таблица фиксирует эти различия и позволяет быстро разграничить операции.

| Операция | Действие с файлом | Действие с каталогом |
|----------|-------------------|-----------------------|
| `r` | Чтение содержимого (`cat`, `less`, копирование) | Просмотр списка имён (`ls` без опций) |
| `w` | Изменение содержимого, усечение | Создание, удаление, переименование записей |
| `x` | Запуск как программы | Переход в каталог (`cd`), доступ к путям внутри |

Для специалиста SOC L1 корректное понимание прав на каталоги напрямую влияет на способность интерпретировать ошибки доступа в логах приложений. Например, если демон логирования теряет возможность писать в `/var/log/app/` из-за снятого бита `w` на каталог, а аналитик видит в логах сообщение «permission denied», знание семантики прав позволяет быстро сузить круг причин.

На практике система прав дополняется специальными битами (setuid, setgid, sticky) и расширенными атрибутами POSIX ACL, но базовые биты `rwx` для трёх категорий составляют минимально необходимый и повсеместно используемый уровень управления.

## 2. Внутреннее устройство прав: структура триад `rwx` для владельца, группы и остальных

Права доступа на объект хранятся в его inode как набор битов и представляются в пользовательском пространстве в двух эквивалентных нотациях: символьной (девять символов) и восьмеричной (трёх- или четырёхзначное число). Оба представления отражают одни и те же разрешения, и понимание взаимопреобразования необходимо для работы на уровне командной строки.

Символьная нотация, выводимая при `ls -l`, выглядит следующим образом (пример для гипотетического файла):

```text
-rwxr-xr--
```

Интерпретация этой строки согласно документации [linuxfoundation.org](https://www.linuxfoundation.org/blog/blog/classic-sysadmin-understanding-linux-file-permissions) и [firstvds.ru](https://firstvds.ru/technology/linux-permissions):

- Символ в позиции 0: тип файла (`-` — обычный, `d` — каталог, `l` — символическая ссылка и т. д.).
- Позиции 1–3: права владельца (`rwx`).
- Позиции 4–6: права группы (`r-x`).
- Позиции 7–9: права остальных (`r--`).

Обобщённая схема трёх триад:

```text
--- --- ---
rwx rwx rwx
 ↑   ↑   ↑
 |   |   └─ остальные (others)
 |   └───── группа (group)
 └───────── владелец (owner)
```

Каждая триада строится из трёх флагов: первый — `r` (read), второй — `w` (write), третий — `x` (execute). Если флаг не установлен, на его месте стоит дефис `-`. Например, `rw-` означает «чтение и запись, без выполнения», а `--x` — «только выполнение».

Восьмеричное (числовое) представление основано на присвоении каждому флагу определённого веса, что позволяет компактно записать любую комбинацию разрешений одной цифрой для каждой из трёх категорий. Веса являются степенями двойки и не пересекаются, поэтому сумма однозначно декомпозируется обратно в набор флагов:

- `r` = 4 (2^2)
- `w` = 2 (2^1)
- `x` = 1 (2^0)

Суммирование весов для категории даёт восьмеричную цифру от 0 до 7 [geeksforgeeks.org](https://www.geeksforgeeks.org/linux-unix/set-file-permissions-linux). Ниже представлена полная таблица соответствия, полезная для моментального перевода.

| Восьмеричное число | Символьное представление | Смысл для категории |
|--------------------|--------------------------|---------------------|
| 0 | `---` | Нет прав |
| 1 | `--x` | Только выполнение |
| 2 | `-w-` | Только запись |
| 3 | `-wx` | Запись и выполнение (4+1=5? Нет, 2+1=3) |
| 4 | `r--` | Только чтение |
| 5 | `r-x` | Чтение и выполнение |
| 6 | `rw-` | Чтение и запись |
| 7 | `rwx` | Полный доступ |

Значениями 3 и 5 часто путают: запись+выполнение даёт `3`, а чтение+выполнение `5`.

Общее восьмеричное число составляется конкатенацией цифр владельца, группы и остальных. Так, `rwxr-xr--` преобразуется как `7 5 4` → `754`. Команда `chmod 754 …` установит именно такую комбинацию. Возможны также четырёхзначные формы, где старшая цифра управляет специальными битами (SUID, SGID, sticky), но в рамках темы рассматриваются только базовые младшие три цифры.

Права на объект можно получить программами `ls -l` и `stat`. Вывод `stat`, согласно иллюстративному примеру из [netangels.pro](https://www.netangels.pro/article/prava-na-fajly-i-papki-v-linux-rukovodstvo-dlya-razrabotchikov-i), содержит как восьмеричную, так и символьную запись в строке «Access»:

```text
Access: (0644/-rw-r--r--)  Uid: ( 1000/   user)   Gid: ( 1000/   group)
```

Здесь `0644` соответствует правам `rw-r--r--`, где владелец может читать и писать, группа и остальные — только читать. Видно также отображение числовых UID и GID на символьные имена.

Ключевой аспект для понимания иерархии — приоритет. Ядро выполняет проверку в строгом порядке: если эффективный UID процесса совпадает с UID владельца, применяются права владельца, и проверка завершается. Если не совпадает, но процесс состоит в группе-владельце файла (сравнение по списку дополнительных групп из /etc/group), применяются права группы. В противном случае используются права остальных. Это исключает ситуацию, когда пользователь-владелец получает права группы или остальных, если его собственные права ограничены.

Для иллюстрации внутренней структуры можно представить права в виде JSON-подобной схемы, заимствованной из метаданных inode (концептуально, без реального кода из бинарных форматов):

```json
{
  "mode": "100644",
  "permissions": {
    "owner": { "r": true, "w": true, "x": false },
    "group": { "r": true, "w": false, "x": false },
    "others": { "r": true, "w": false, "x": false }
  },
  "uid": 1000,
  "gid": 1000,
  "type": "regular file"
}
```

Такой формат демонстрирует разделение категорий и флагов; он полезен для восприятия, как инструменты вроде stat раскладывают битовую маску в человекочитаемый вид.

## 3. Применение и работа с правами: команды, интерпретация и типичные операции

Практическое взаимодействие с правами доступа сводится к трём основным командам: `ls` и `stat` для чтения текущих разрешений, `chmod` для их изменения и `chown`/`chgrp` для смены владельца или группы. Ниже рассмотрены типовые сценарии, актуальные для ежедневной работы специалиста SOC: аудит прав на чувствительных файлах, настройка доступа к логам, исправление ошибок, приводящих к инцидентам.

### 3.1 Просмотр текущих прав

Для быстрого просмотра прав на файлы текущего каталога используется `ls -l`. Расширенный вывод `stat` предоставляет подробную информацию, включая временные метки и числовые идентификаторы.

Примеры (реальные команды, ожидаемый вывод дан в иллюстративной форме на основе [hostiq.ua](https://hostiq.ua/wiki/permissions) и [linuxcommand.org](https://linuxcommand.org/lc3_lts0090.php)):

```bash
ls -l /var/log/syslog
```
Ожидаемый вывод:
```
-rw-r----- 1 syslog adm 1552 Mar 25 08:30 /var/log/syslog
```
Здесь владелец `syslog` имеет `rw-` (чтение и запись), группа `adm` — `r--` (только чтение), остальные — `---` (доступ запрещён).

```bash
stat /var/log/syslog
```
Ожидаемый вывод (сокращён):
```
Access: (0640/-rw-r-----)  Uid: (  104/ syslog)   Gid: (    4/    adm)
```

### 3.2 Изменение прав командой chmod

`chmod` поддерживает символьный и восьмеричный режимы. Символьный режим указывает категорию (`u`, `g`, `o`, `a`), оператор (`+`, `-`, `=`) и права (`r`, `w`, `x`). Восьмеричный задаёт итоговую комбинацию тремя цифрами.

Типовые примеры символьного режима из [geeksforgeeks.org](https://www.geeksforgeeks.org/linux-unix/set-file-permissions-linux) и [freecodecamp.org](https://www.freecodecamp.org/news/linux-chmod-chown-change-file-permissions):

- Добавить право выполнения для владельца файла `script.sh`:
  ```bash
  chmod u+x script.sh
  ```
- Убрать все права у категории «остальные» для файла `private.log`:
  ```bash
  chmod o-rwx private.log
  ```
- Установить фиксированный набор прав для группы — только чтение (назначить явно, сбросив остальные флаги группы):
  ```bash
  chmod g=r shared.conf
  ```
- Комбинированная операция: владельцу и группе дать чтение и выполнение, остальным снять запись:
  ```bash
  chmod ug+rx,o-w data_script.py
  ```

Восьмеричный режим удобен для массовой настройки. Наиболее употребительные комбинации (по [linuxcommand.org](https://linuxcommand.org/lc3_lts0090.php) и [linuxfoundation.org](https://www.linuxfoundation.org/blog/blog/classic-sysadmin-understanding-linux-file-permissions)):

| Число | Символьный вид | Типичное применение |
|-------|---------------|---------------------|
| 755 | `rwxr-xr-x` | Каталоги программ, публичные скрипты |
| 644 | `rw-r--r--` | Конфигурационные файлы, данные, доступные всем на чтение |
| 600 | `rw-------` | Приватные ключи, файлы паролей, доступные только владельцу |
| 700 | `rwx------` | Домашние каталоги, личные скрипты |
| 750 | `rwxr-x---` | Каталоги с групповым доступом, когда требуется запуск скриптов |
| 640 | `rw-r-----` | Лог-файлы, где группе (например, аналитикам) нужно только чтение |

Пример установки прав для файла логов SOC:

```bash
chmod 640 /var/log/soc/alerts.log
```

Результат: владелец получает `rw-`, группа — `r--`, остальные — `---`.

### 3.3 Смена владельца и группы: chown, chgrp

Для смены владельца используется `chown`, группы — `chgrp`. Права на это имеют только root или текущий владелец (для передачи владения другому требуются привилегии root). Рекурсивный флаг `-R` распространяет изменения на все вложенные объекты каталога [adminvps.ru](https://adminvps.ru/blog/kak-smenit-vladelcza-papki-i-izmenit-prava-dostupa-v-linux).

```bash
# Смена владельца и группы рекурсивно для каталога
sudo chown -R soc_analyst:soc_group /var/log/soc
# Смена только группы на adm
sudo chgrp -R adm /var/log/soc
# Смена только владельца, группа остаётся без изменений
sudo chown soc_analyst /var/log/soc/alerts.log
```

### 3.4 Типичные ошибки и их детектирование

**Ошибка 1: Избыточные права «others write».** Сервисы, записывающие логи, иногда создают файлы с правами 777 (или 666). Это позволяет любому пользователю системы модифицировать логи — критическая уязвимость. SOC должен регулярно выполнять аудит мировых записываемых файлов:

```bash
find /var/log -type f -perm -o+w -ls
```

**Ошибка 2: Отсутствие бита выполнения на каталоге.** Если для группы или остальных снят `x` с родительского каталога, доступ к его содержимому становится невозможным, даже при наличии прав на файлы внутри.

**Ошибка 3: Путаница между правами на каталог и файл при удалении.** Удаление файла требует прав записи (`w`) на родительский каталог, а не прав на сам файл. Установка флага sticky на общих каталогах (например, `/tmp`) предотвращает удаление чужих файлов.

### 3.5 Интеграция с инструментами SOC

Специалист L1 может использовать скрипты для мониторинга прав на критичные файлы (например, хэши конфигураций, права агентов мониторинга). Команда `stat` может быть обёрнута в простой cron-сканер, сверяющий текущие октальные маски с эталонными. Пример однострочника, выводящего аномалии:

```bash
stat -c '%a %n' /etc/shadow /etc/passwd /var/log/soc/* | awk '$1 != "0600" && $1 != "0644" {print "WARNING:", $0}'
```
Этот сниппет проверяет, что теневой файл имеет права 600, passwd 644, а логи SOC — заданные.

## 4. Сквозной практический пример: настройка доступа к лог-файлу системы мониторинга SOC

Данный кейс демонстрирует полный цикл работы с правами для сценария, типичного для SOC: развёртывание агента мониторинга, создавшего файл с правами по умолчанию, и последующее приведение их к минимально необходимому уровню с разграничением для владельца, группы и остальных.

**Исходные условия:**  
ОС Ubuntu 22.04 LTS. Пользователь `root` инициировал создание тестового лог-файла `/opt/soc/agent/alerts.log`. Требуется, чтобы аналитик `alex` (входит в группу `soc_readers`) был владельцем и имел право читать и записывать файл; группа `soc_readers` — только читать; все остальные пользователи не должны иметь доступа. Текущее состояние файла: владелец `root`, группа `root`, права `644` (мировое чтение).

**Шаг 1: Просмотр текущих прав.**

```bash
ls -l /opt/soc/agent/alerts.log
```
Вывод:
```
-rw-r--r-- 1 root root 12704 Mar 25 10:15 /opt/soc/agent/alerts.log
```
Анализ: владелец – root (rw-), группа – root (r--), остальные – (r--). Группа `soc_readers` не является группой-владельцем, её члены получат права остальных (только чтение), что допустимо, но для соблюдения принципа минимальных привилегий нужно закрепить доступ через группу.

**Шаг 2: Смена владельца и группы через chown.**

```bash
sudo chown alex:soc_readers /opt/soc/agent/alerts.log
```
Проверка:

```bash
stat /opt/soc/agent/alerts.log | grep -E 'Access|Uid|Gid'
```
Вывод:
```
Access: (0644/-rw-r--r--)  Uid: ( 1001/ alex)   Gid: ( 1002/ soc_readers)
```
Теперь владельцем является `alex`, группой-владельцем — `soc_readers`.

**Шаг 3: Установка прав `640` через восьмеричный режим.**

```bash
sudo chmod 640 /opt/soc/agent/alerts.log
```
Число `640` расшифровывается: владелец `rw-` (4+2=6), группа `r--` (4=4), остальные `---` (0). Достигается требуемое разграничение.

Подтверждение:

```bash
ls -l /opt/soc/agent/alerts.log
```
Вывод:
```
-rw-r----- 1 alex soc_readers 12704 Mar 25 10:20 /opt/soc/agent/alerts.log
```

**Шаг 4: Проверка доступа от лица разных пользователей (иллюстративно).**

- От имени `alex` (владелец): разрешено чтение и запись (`echo "test" >> /opt/soc/agent/alerts.log` выполнится успешно).
- От участника группы `soc_readers`, например `bob`: чтение разрешено (`cat /opt/soc/agent/alerts.log` успешно), попытка записи (`echo "data" >> /opt/soc/agent/alerts.log`) приведёт к `Permission denied`.
- От постороннего пользователя `guest`: любые операции запрещены (`Permission denied`).

**Ожидаемый итог:** файл доступен владельцу и группе, закрыт для остальных, что соответствует требованиям безопасности. Данный пример демонстрирует полный путь: анализ текущих прав, смена владельца/группы, применение восьмеричного `chmod` для точной настройки и верификация результата.
