# Планировщик задач в Linux: cron, systemd-таймеры и автоматизация в SOC

## 1. Контекст, эволюция и ключевые разграничения

Планировщик задач в Linux — это подсистема, обеспечивающая запуск команд или сценариев по заранее заданному календарному или интервальному правилу без непосредственного участия администратора. В контексте операционных центров безопасности (SOC) автоматизация становится критически важной: периодическая проверка целостности файловых систем, ротация и архивация журналов, обновление баз индикаторов компрометации, запуск сканеров уязвимостей или сбор аутентификационных событий — все эти задачи ложатся на планировщик.

Исторически основным инструментом планирования в UNIX-подобных системах служит демон `cron`; его корни восходят к AT&T Bell Laboratories (май 1975 г.), а широкое распространение получил Vixie cron (1987 г.), чьи прямые наследники — cronie, dcron, mcron — до сих пор используются в большинстве дистрибутивов [Wikipedia: Cron](https://en.wikipedia.org/wiki/Cron). Однако с появлением `systemd` (2010 г.) возник альтернативный механизм — системные таймеры (`systemd timers`), реализованные в виде юнитов `.timer` и управляемые штатными средствами systemd. Там, где `cron` ориентирован исключительно на периодический запуск заданий по времени, `systemd timers` тесно интегрированы с менеджером служб и предлагают более богатый функционал: зависимости от других юнитов, мониторинг через журнал `journald`, контроль перезапуска, выполнение задач, пропущенных из-за простоя системы, и возможность запуска по событиям (загрузка, подключение оборудования) [CoadyTech: Stop using cron!](https://coady.tech/systemd-timer-vs-cron). Для систем, которые могут не работать круглосуточно, существует `anacron` — подсистема, запускающая задания из каталогов `cron.daily`, `cron.weekly` и `cron.monthly` с гарантией, что пропущенные из-за выключения сценарии будут выполнены при следующем включении [Rocky Linux Documentation: cron](https://docs.rockylinux.org/10/guides/automation/cron_jobs_howto).

Необходимо чётко разграничивать понятия, так как в повседневной речи термины «cron» и «планировщик» часто смешиваются, а студенты могут путать `cron` с анархичным запуском команд через `at` или со встроенной в ядро диспетчеризацией процессов CFS (Completely Fair Scheduler). Ниже приведена сравнительная таблица, фиксирующая функциональные границы основных инструментов планирования в Linux.

| Инструмент | Уровень | Основное назначение | Пример типичной команды / конфигурации |
|------------|---------|----------------------|----------------------------------------|
| `cron` (классический демон) | Пользовательский/системный, временной | Периодический запуск скриптов по фиксированному расписанию (минимальная гранулярность – 1 минута) | `*/15 * * * * /opt/scripts/check_hashes.sh` |
| `systemd timers` | Системный, событийно-временной | Запуск `.service`-юнитов по календарному или монотонному времени, с гарантией выполнения пропущенных заданий, зависимостями и логированием в journald | Файл `.timer`: `OnCalendar=*-*-* 02:00:00` + `Persistent=true` |
| `anacron` | Системный (надстройка над cron) | Выполнение заданий с дневной/недельной/месячной периодичностью с гарантией, что они не будут пропущены при выключении машины | Записи в `/etc/anacrontab` или каталоги вроде `cron.daily/` |
| `at` | Пользовательский | Однократный запуск задачи в заданное время в будущем | `echo "shutdown -h now" | at 23:00` |
| **CFS (Completely Fair Scheduler)** | Ядро ОС | Распределение процессорного времени между потоками; к планированию задач системного администрирования отношения не имеет | Не конфигурируется пользователем напрямую |

Ключевое различие для специалиста SOC первого уровня — область ответственности. Задания `cron` и `systemd timers` непосредственно влияют на наполнение журналов, частоту проверок и оповещений. Например, если SOC-инженер видит в логах подозрительную активность в 3:00 ночи, знание того, какие легитимные планировщики активны в это время, помогает отделить штатную автоматизацию от аномалии.

## 2. Внутреннее устройство cron и systemd-таймеров: от формата записей до механизма активации

Планировщики в Linux реализуются двумя принципиально разными архитектурами — традиционной демон-центричной (cron) и юнит-ориентированной в рамках systemd. Понимание их внутреннего устройства необходимо для аудита конфигураций и диагностики сбоев, которые могут маскировать вредоносную активность или приводить к пропуску критичных проверок.

### 2.1. Классический cron: демон, таблицы и каталоги

Центральный элемент — демон `crond` (в cronie — `/usr/sbin/crond`), который непрерывно работает в фоне и каждую минуту сканирует несколько источников конфигурации [SUSE: Working with systemd Timers](https://documentation.suse.com/smart/systems-management/html/systemd-working-with-timers/index.html). Источники делятся на общесистемные и пользовательские.

- **Общесистемные источники**:
  - Файл `/etc/crontab` — основной системный crontab, в котором помимо стандартных полей времени присутствует шестое поле — имя пользователя, от которого запускается задание. Пример: `15 2 * * * root /usr/bin/run-backup`.
  - Каталог `/etc/cron.d/` — содержит отдельные файлы с заданиями, оформленными в том же расширенном формате, что и `/etc/crontab`. Удобен для пакетной установки заданий (security-обновления, audit-чеки).
  - Каталоги периодических заданий: `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/`, `/etc/cron.monthly/`. Содержимое этих каталогов выполняется не напрямую демоном, а вспомогательным скриптом `run-parts` (или аналогичным), который вызывается из `/etc/crontab` или через `anacron`.

- **Пользовательские crontab-файлы**:
  Каждый пользователь может иметь собственный crontab, хранящийся в `/var/spool/cron/<username>` (точное расположение зависит от реализации). Редактирование выполняется командой `crontab -e`, которая гарантирует блокировку и синтаксическую проверку при сохранении. Пользовательские задания не содержат поля имени пользователя, а выполняются от владельца crontab.

Формат записи в классическом Vixie-cron (и его потомках) содержит пять полей времени, за которыми следует команда:

```
.---------------- minute (0 - 59)
|  .------------- hour (0 - 23)
|  |  .---------- day of month (1 - 31)
|  |  |  .------- month (1 - 12) OR jan,feb,mar,...
|  |  |  |  .---- day of week (0 - 6) (Sunday=0 or 7)
|  |  |  |  |
*  *  *  *  *  command_to_execute
```

Допускаются списки (`1,15`), диапазоны (`1-5`), шаги (`*/10`) и специальные строки: `@reboot`, `@yearly`/`@annually`, `@monthly`, `@weekly`, `@daily`, `@hourly`. Существует также нестандартное расширение: некоторые реализации добавляют шестое поле (год) или используют поле после дня недели для имени пользователя в системных crontab [Wikipedia: Cron](https://en.wikipedia.org/wiki/Cron).

Демон `crond` проверяет crontab-файлы на предмет модификации каждую минуту или по сигналу. При обнаружении изменённой временной метки файл перечитывается. Вывод и ошибки задания могут отправляться владельцу по локальной почте (если настроен MTA и задана переменная `MAILTO`), однако в современных минималистичных серверных окружениях почта часто отсутствует, что усложняет диагностику.

### 2.2. Systemd timers: юниты, зависимости и Persistent-режим

Вместо единого демона, анализирующего множество текстовых файлов, systemd реализует таймеры как разновидность юнитов (unit files). Юнит таймера (`.timer`) всегда связан с соответствующим сервис-юнитом (`.service`), определяющим исполняемую команду, и может активировать его по временному или событийному триггеру [yieldcode.blog: Working with systemd timers](https://yieldcode.blog/post/working-with-systemd-timers). При этом статусы и журналы таймеров управляются так же, как и для любых других служб.

Типовая пара файлов выглядит так:

**Сервис-юнит** (`/etc/systemd/system/mytask.service` — иллюстративная схема):
```ini
[Unit]
Description=My security audit script

[Service]
Type=oneshot
ExecStart=/usr/local/bin/audit-check.sh
```

**Таймер-юнит** (`/etc/systemd/system/mytask.timer`):
```ini
[Unit]
Description=Run audit-check daily at 2AM

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true
Unit=mytask.service

[Install]
WantedBy=timers.target
```

Секция `[Timer]` поддерживает широкий набор директив, разделённых по типу триггера [SUSE: Working with systemd Timers](https://documentation.suse.com/smart/systems-management/html/systemd-working-with-timers/index.html):

- **Календарные триггеры** (основаны на реальном времени):
  - `OnCalendar=` — принимает выражение в формате `DayOfWeek Year-Month-Day Hour:Minute:Second`, где каждый компонент может быть `*` (любое значение), списком (`1,3`), диапазоном (`Mon..Fri`), либо шагом. Примеры:
    - `Mon..Fri *-*-* 10:00:00` — по будням в 10 утра.
    - `*-*-1 00:00:00` — первого числа каждого месяца в полночь.
    - `Sat,Sun 20:00` — по выходным в 20:00.
    - Можно добавлять часовой пояс: `*-*-* 02:00:00 Europe/Amsterdam`.
  - Директива может указываться несколько раз для задания сложных расписаний.

- **Монотонные триггеры** (основаны на времени относительно некоторого события):
  - `OnBootSec=` — запуск через заданное время после загрузки системы.
  - `OnUnitActiveSec=` — запуск через заданное время после последней активации целевого сервиса (обеспечивает фиксированный интервал между запусками без привязки к стене часов, что важно для избежания наложения).
  - `OnUnitInactiveSec=` — запуск через заданное время после остановки целевого юнита.

Ключевой атрибут `Persistent=true` делает таймер устойчивым к пропуску срабатываний из-за выключенного состояния системы: при загрузке systemd проверяет, был ли пропущен хотя бы один запуск, и если да — немедленно запускает сервис. Это поведение заменяет `anacron` для системных таймеров [CoadyTech: Stop using cron!](https://coady.tech/systemd-timer-vs-cron). Точность таймеров systemd составляет 1 секунду, тогда как cron оперирует минутами.

Структурно взаимодействие компонентов можно изобразить так:

```text
[systemd] ──(загружает)──▶ *.timer ◀──(проверяет OnCalendar)──▶ системные часы
                │
       (активирует при совпадении)
                │
                ▼
[systemd] ──(запускает)──▶ *.service ──(выполняет)──▶ скрипт/программа
                │
       (записывает stdout/stderr)
                ▼
           journald
```

В отличие от cron, где логирование зависит от почтовой подсистемы или явного перенаправления вывода в файл, systemd автоматически захватывает stdout и stderr юнита в централизованный журнал `journald`. Администратор SOC может получить логи командой `journalctl -u mytask.service`. Кроме того, таймеры позволяют ограничивать ресурсы через `ControlGroup`, устанавливать зависимости (`After=`, `Requires=`) и управлять параллелизмом — встроенная блокировка предотвращает одновременный запуск одного и того же сервиса, если предыдущий экземпляр ещё не завершился [Unix & Linux StackExchange: cron vs systemd timers](https://unix.stackexchange.com/questions/278564/cron-vs-systemd-timers).

### 2.3. Anacron как прослойка и эволюция cronie

В классическом cron задания пропускаются, если система была выключена в момент запланированного выполнения. Для исправления этого недостатка появился `anacron`, который, в отличие от cron, оперирует не фиксированными моментами времени, а интервалами в днях. В современных дистрибутивах (RHEL/CentOS, Fedora, Ubuntu) cronie интегрирует anacron: общеизвестные каталоги `cron.daily/` и подобные обрабатываются именно anacron-демоном, вызываемым из `/etc/crontab` раз в час или при старте системы. Если машина была выключена, при включении anacron сравнивает метку времени последнего выполнения и текущую дату и запускает все пропущенные задания с задержкой, но гарантированно [Rocky Linux Documentation: cron](https://docs.rockylinux.org/10/guides/automation/cron_jobs_howto). В мире systemd timers эту роль исполняет директива `Persistent=true`, поэтому при полном переходе на systemd необходимость в anacron отпадает.

## 3. Применение и работа с планировщиками в задачах SOC

Специалист SOC L1 ежедневно сталкивается с артефактами планировщика: событиями в журналах, периодическими запусками скриптов сбора логов, временем появления записей определенного типа. Умение создавать, проверять и диагностировать запланированные задачи — базовая компетенция.

### 3.1. Работа с cron: добавление, проверка, логирование

Для быстрой автоматизации обычно используется cron — его синтаксис интуитивен, а демон предустановлен в большинстве минимальных образов. Добавление задания выполняется редактированием пользовательского crontab (`crontab -e`) или системного файла `/etc/crontab`. Пример мониторинга целостности SSH authorized_keys дважды в час:

```bash
# Открыть редактор для текущего пользователя
crontab -e
# Добавить строку:
*/30 * * * * /usr/local/bin/check_authorized_keys.sh
```

При редактировании системного `/etc/crontab` необходимо указать пользователя:
```bash
*/30 * * * * root /usr/local/bin/check_authorized_keys.sh
```

Проверить текущие задания можно командой `crontab -l` (для пользователя) или просмотром `/etc/crontab` и `/etc/cron.d/`. Для SOC критически важно видеть фактические запуски и возможные ошибки. По умолчанию cron отправляет вывод задания на локальный почтовый ящик пользователя, но во многих серверных инсталляциях почтовая служба отключена. Альтернативные способы:
- Перенаправление вывода в файл: `*/30 * * * * /usr/local/bin/check.sh >> /var/log/check.log 2>&1`.
- Использование systemd-cron журналирования в syslog: демон `crond` обычно логирует запуски в `/var/log/cron` (или `/var/log/syslog`), что можно отслеживать с помощью `grep CRON /var/log/syslog`.
- В современных системах, где cronie работает как сервис systemd, журнал доступен через `journalctl -u cron` (или `cronie`).

Пример логов запуска задания:
```text
Apr 19 12:30:01 host CRON[1234]: (root) CMD (/usr/local/bin/check.sh)
```

### 3.2. Создание и управление systemd-таймерами

При необходимости более тонкого контроля, гарантии выполнения и централизованного логирования применяются systemd timers. Последовательность создания таймера и сервиса:

1. **Создать сервис-юнит** в `/etc/systemd/system/`:
```ini
# /etc/systemd/system/check.service
[Unit]
Description=Security integrity check

[Service]
Type=oneshot
ExecStart=/usr/local/bin/integrity-check.sh
```

2. **Создать таймер-юнит**:
```ini
# /etc/systemd/system/check.timer
[Unit]
Description=Hourly integrity check, persistent

[Timer]
OnCalendar=*-*-* *:30:00
Persistent=true

[Install]
WantedBy=timers.target
```

3. **Проверить корректность** юнитов:
```bash
systemd-analyze verify /etc/systemd/system/check.*
```
Если команда не выводит сообщений, синтаксис корректен.

4. **Запустить и активировать** таймер (включить на автозапуск):
```bash
sudo systemctl start check.timer
sudo systemctl enable check.timer
```

Список активных таймеров и ближайших срабатываний:
```bash
systemctl list-timers --all
```
Пример вывода (иллюстративная схема):
```
NEXT                          LEFT     LAST                          PASSED  UNIT          ACTIVATES
Wed 2026-04-20 14:30:00 MSK   28min   Wed 2026-04-20 13:30:00 MSK   31min   check.timer   check.service
```

Просмотр всех логов, связанных с сервисом, включая stdout/stderr скрипта:
```bash
journalctl -u check.service
```

### 3.3. Типичные ошибки и подводные камни

- **Окружение cron vs пользовательское окружение**. Cron запускает задания с минимальным набором переменных (обычно `HOME`, `LOGNAME`, `SHELL=/bin/sh`, `PATH=/usr/bin:/bin`). Многие администраторы забывают указать полные пути к исполняемым файлам или не экспортируют необходимые переменные (`PATH`, `JAVA_HOME`), что приводит к скрытым сбоям. В systemd юнитах окружение задается явно через `Environment=` или изолируется по умолчанию, что делает поведение детерминированным.
- **Наложение заданий**. Cron не контролирует параллелизм: если скрипт выполняется дольше интервала планирования, следующая копия запустится и может возникнуть гонка данных, например, при обновлении файлов блокировки. Systemd timers по умолчанию не запускают новую копию сервиса, пока предыдущая не завершится.
- **Пропуск заданий**. При использовании чистого демона cron задание, которое должно было сработать в момент простоя системы, не выполняется позже. Применение `anacron` (через cronie) или флага `Persistent=true` в systemd timers решает проблему.
- **Отсутствие мониторинга**. SOC может пропустить инцидент, если задание не выполнилось, а оповещения не настроены. Systemd таймеры упрощают интеграцию с системами мониторинга: о сбое юнита можно сигнализировать через стандартные механизмы типа `OnFailure=` или с помощью проверки состояния `systemctl is-failed check.service`.

## 4. Сквозной практический пример: автоматизация ежедневного аудита с логгированием через systemd timer

**Исходные условия:** сервер под управлением RHEL 9 (или совместимого дистрибутива с systemd). Необходимо ежедневно в 3 часа ночи запускать скрипт `audit-nightly.sh`, который собирает информацию о неудачных попытках входа за последние сутки, вычисляет хеши ключевых конфигурационных файлов и записывает сводку в системный журнал. Требуется гарантировать выполнение даже после ночной перезагрузки, исключить параллельный запуск и обеспечить централизованный лог.

**Шаг 1. Создание сервис-юнита.**  
Скрипт расположен по пути `/usr/local/bin/audit-nightly.sh`. Определим сервис как одноразовый (`Type=oneshot`), чтобы systemd ждал его завершения и не запускал повторно, пока он активен.

```bash
sudo tee /etc/systemd/system/audit-nightly.service <<EOF
[Unit]
Description=Nightly security audit

[Service]
Type=oneshot
ExecStart=/usr/local/bin/audit-nightly.sh
StandardOutput=journal
StandardError=journal
EOF
```

Конструкция `StandardOutput=journal` (значение по умолчанию) приведена для наглядности — она гарантирует захват stdout/stderr в journald.

**Шаг 2. Создание таймер-юнита.**  
Задаём ежедневное срабатывание в 3:00 по местному времени и флаг `Persistent=true`, чтобы задание выполнилось при загрузке, если система была выключена в 3:00. Привязываем к созданному сервису.

```bash
sudo tee /etc/systemd/system/audit-nightly.timer <<EOF
[Unit]
Description=Daily night audit timer

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
Unit=audit-nightly.service

[Install]
WantedBy=timers.target
EOF
```

**Шаг 3. Проверка конфигурации.**  
Перед активацией используем встроенный анализатор systemd, который проверяет синтаксис и ссылочную целостность юнитов.

```bash
sudo systemd-analyze verify /etc/systemd/system/audit-nightly.*
```

Отсутствие вывода означает, что ошибок не обнаружено. (При наличии проблем команда выведет описание.)

**Шаг 4. Запуск и активация таймера.**  
Включаем таймер в автозагрузку и немедленно запускаем для тестирования.

```bash
sudo systemctl enable audit-nightly.timer
sudo systemctl start audit-nightly.timer
```

Убеждаемся, что таймер появился в списке и запланирован на следующее срабатывание.

```bash
systemctl list-timers audit-nightly.timer
```

Ожидаемый вывод (иллюстративная схема):
```
NEXT                          LEFT       LAST PASSED UNIT                 ACTIVATES
Thu 2026-04-21 03:00:00 MSK   11h left   n/a  n/a    audit-nightly.timer  audit-nightly.service
```

При необходимости можно инициировать ручной запуск сервиса без ожидания таймера: `sudo systemctl start audit-nightly.service`.

**Шаг 5. Просмотр результатов и логов.**  
После любых срабатываний журнал доступен через `journalctl`. Для просмотра последних записей, относящихся к нашему сервису, с отображением вывода скрипта:

```bash
journalctl -u audit-nightly.service --since "2026-04-20" --no-pager
```

Пример ожидаемого фрагмента лога (иллюстративная схема):
```text
Apr 20 03:00:01 host systemd[1]: Starting Nightly security audit...
Apr 20 03:00:05 host audit-nightly.sh[1123]: [INFO] Checking SSH authentication failures...
Apr 20 03:00:05 host audit-nightly.sh[1123]: [INFO] 3 failed login records found. Stored in /var/log/audit/failed.log
Apr 20 03:00:06 host audit-nightly.sh[1123]: [INFO] Integrity hashes: /etc/shadow: SHA256:abc... /etc/passwd: SHA256:def...
Apr 20 03:00:06 host systemd[1]: audit-nightly.service: Succeeded.
```

Данный пример демонстрирует не только штатную настройку планировщика, но и реализацию требований, важных для SOC: детерминированное выполнение задач, автоматический захват логов в единый журнал, гранулярный контроль статуса и защита от дублирования запусков.
