# A05: Injection (OWASP Top 10 2025)

## Контекст, определение и разграничение понятий

Инъекция (injection) в контексте веб-безопасности — класс уязвимостей, возникающий при передаче недоверенных данных интерпретатору в составе команды или запроса без надлежащей валидации или экранирования. Интерпретатор (СУБД, командная оболочка ОС, браузер, шаблонизатор, LDAP-сервер) не может отличить легитимные команды от вредоносного ввода, поэтому выполняет атакующий код с привилегиями приложения [1]. Ключевая ошибка разработки — смешивание данных и команд, например конкатенация пользовательского ввода в SQL-запрос, системный вызов или HTML-вывод.

В рейтинге OWASP Top 10 2025 категория Injection занимает позицию A05. По сравнению с предыдущими редакциями позиция снизилась: в 2017 году инъекции были на первом месте, в 2021 — на третьем, в 2025 — на пятом [2][4]. Это снижение отражает не уменьшение опасности, а широкое внедрение параметризованных запросов, подготовленных выражений и фреймворков с автоматическим кодированием вывода [2]. Тем не менее инъекции остаются одной из самых тестируемых категорий: OWASP сообщает, что 100% приложений тестировались на какую-либо форму инъекций [6]. По данным ByteHide Radar, 94% приложений были оценены на наличие инъекций, максимальная частота встречаемости составила 19% [2]. Категория объединяет 37 различных Common Weakness Enumerations (CWE) и породила более 51 000 CVE: свыше 14 000 CVE относятся к SQL-инъекциям, более 30 000 — к межсайтовому скриптингу (XSS) [1]. С редакции 2021 года XSS включена в категорию Injection и остаётся в ней в 2025-м [2].

Понимание места инъекций среди других категорий OWASP Top 10 2025 важно для корректной классификации. Следующая таблица сопоставляет Injection со смежными категориями, с которыми часто возникает путаница.

| Категория OWASP Top 10 2025 | Сущность проблемы | Отличие от Injection |
|---|---|---|
| A05: Injection | Недоверенные данные передаются интерпретатору как часть команды или запроса | Злоумышленник изменяет логику выполнения команды, внедряя код в существующий контекст |
| A06: Insecure Design | Архитектурные или проектные просчёты, не связанные с реализацией конкретного ввода | Уязвимость закладывается на этапе проектирования, а не из-за неправильной обработки данных в коде |
| A01: Broken Access Control | Нарушение ограничений доступа к объектам или функциям | Атакующий получает доступ без изменения команд, эксплуатируя отсутствие проверок прав |
| A02: Security Misconfiguration | Некорректная настройка компонентов, избыточные права, отладочные интерфейсы | Уязвимость не требует специального ввода для эксплуатации, достаточно ошибочной конфигурации |

Внутри самой категории Injection выделяют несколько подтипов, различающихся целевым интерпретатором и характером последствий. В таблице ниже приведены ключевые подтипы и их целевые сущности; подробный разбор механизмов дан в следующем разделе.

| Подтип инъекции | Целевой интерпретатор | Типовой результат эксплуатации |
|---|---|---|
| SQL Injection (SQLi) | Реляционная СУБД | Обход аутентификации, извлечение/изменение/удаление данных, выполнение команд ОС через расширенные функции |
| NoSQL Injection | NoSQL-СУБД (MongoDB, CouchDB и др.) | Нарушение логики запросов, извлечение данных, иногда выполнение JavaScript |
| Command Injection | Командная оболочка ОС (bash, cmd, PowerShell) | Выполнение произвольных команд с правами веб-сервера |
| LDAP Injection | LDAP-сервер (каталог) | Обход аутентификации, несанкционированное чтение/изменение записей каталога |
| XPath Injection | XPath-процессор XML-документа | Обход проверок, извлечение содержимого XML, отказ в обслуживании |
| Template Injection (SSTI) | Серверный шаблонизатор (Jinja2, FreeMarker, Thymeleaf, Pug, ERB) | Удалённое выполнение кода (RCE) через вычисление выражений шаблона |
| XSS (Reflected/Stored/DOM) | Браузер жертвы | Выполнение JavaScript в контексте сеанса, кража cookie, подмена содержимого |

Следует отметить, что термин «инъекция» в OWASP Top 10 охватывает не только классические серверные атаки (SQLi, command injection), но и клиентские (XSS), а также инъекции в нереляционные хранилища и сервисы. Такое объединение отражает общий принцип: недоверенные данные попадают в интерпретатор и трактуются как код.

## Внутреннее устройство класса инъекционных уязвимостей

Механизм возникновения любой инъекции одинаков: приложение получает данные от пользователя, формирует из них строку команды (SQL-запрос, команду ОС, выражение шаблона и т.п.) и передаёт её на исполнение интерпретатору. Поскольку данные не отделены от синтаксических элементов, атакующий способен «вырваться» из контекста данных и добавить собственные инструкции. Классический пример — уязвимая конструкция входа в систему на SQL [1]:

```sql
SELECT * FROM users WHERE username = ' + userInput + ' AND password = ' + passwordInput
```

Атакующий передаёт в поле username значение `admin' --`, в результате итоговый запрос приобретает вид:

```sql
SELECT * FROM users WHERE username = 'admin' --' AND password = ''
```

Двойное тире комментирует оставшуюся часть строки, и проверка пароля исчезает. Это простейший случай обхода аутентификации. Более сложные техники используют UNION для извлечения данных из других таблиц, стековые запросы для модификации данных или слепую (blind) инъекцию с задержками времени для эксфильтрации информации, когда вывод не виден напрямую [1].

Необходимые условия существования инъекции:
1. **Точка входа** — параметр, принимающий недоверенные данные: URL-параметры, тело POST-запроса, заголовки, cookie, поля форм, содержимое загружаемых файлов.
2. **Отсутствие надлежащей обработки** — данные не валидируются, не экранируются и не параметризуются перед подстановкой.
3. **Опасный приёмник (sink)** — данные попадают в функцию или конструкцию, которая передаёт их интерпретатору: `executeQuery()`, `system()`, `popen()`, `eval()`, `document.write()` и т.п.
4. **Исполнение с привилегиями приложения** — интерпретатор выполняет скомпонованную команду, не имея возможности отличить легитимную часть от внедрённой.

На схеме ниже показан поток данных в уязвимом приложении:

```text
[Пользовательский ввод] ──(недоверенные данные)──▶ [Приложение: конкатенация строк] ──(строка команды)──▶ [Интерпретатор]
                                                         ▲                                                       │
                                                         │                                                       ▼
                                        (нет валидации/параметризации)                          (выполнение вредоносной команды)
```

Все подтипы инъекций следуют этому шаблону, но различаются целевым интерпретатором и спецификой эксплуатации. В таблице ниже собраны ключевые варианты атак, условия их возникновения, типичные индикаторы в логах и основные контрмеры.

| Тип инъекции | Механизм эксплуатации | Необходимые условия | Типичные индикаторы в логах | Контрмеры |
|---|---|---|---|---|
| SQL Injection (классическая, error-based) | Внедрение символов `'`, `"`, `;`, `--`, `#` для изменения логики SQL; использование ошибок СУБД для раскрытия структуры БД | Динамическая конкатенация SQL, отсутствие параметризации, вывод ошибок БД | Запросы с `UNION SELECT`, `OR 1=1`, сообщения об ошибках SQL | Подготовленные выражения, ORM, экранирование, отключение детальных ошибок |
| SQL Injection (blind, time-based) | Эксплуатация без видимого вывода: условные запросы, вызывающие задержку (`SLEEP()`, `pg_sleep()`) или различие в ответе | Те же, но без вывода ошибок; вывод не отражается в ответе | Аномально долгие ответы, повторяющиеся запросы с `WAITFOR DELAY`, `BENCHMARK()` | Параметризация, ограничение времени выполнения, мониторинг аномалий |
| Command Injection | Внедрение метасимволов оболочки: `;`, `&&`, `\|\|`, `\`\``, `$()` для выполнения произвольных команд ОС | Передача пользовательского ввода в `system()`, `exec()`, `popen()`, `Runtime.exec()` с shell-расширением | Запросы с `; ls`, `&& whoami`, `\|\| curl`, обращения к `/bin/sh` | Использование `subprocess` с массивом аргументов без shell, whitelist допустимых значений |
| LDAP Injection | Манипуляция LDAP-фильтром через `*`, `(`, `)`, `&`, `\|\|` для обхода аутентификации или изменения семантики поиска | Формирование LDAP-фильтра из пользовательского ввода без экранирования специальных символов | Запросы с `)(&`, `*)(uid=*`, попытки обойти фильтр | Экранирование спецсимволов LDAP, использование готовых API для построения фильтров |
| XPath Injection | Внедрение в XPath-выражения для обхода проверок или извлечения данных из XML | Конкатенация пользовательского ввода в `xpath.evaluate()` или аналогичные вызовы | Запросы с `' or '1'='1`, `'\|\|` в XPath-контексте | Параметризация XPath, валидация ввода, запрет спецсимволов |
| Template Injection (SSTI) | Внедрение выражений шаблонизатора (`{{...}}`, `${...}`, `<%= ... %>`) для выполнения кода на сервере | Передача пользовательских строк в шаблонизатор как шаблон, а не как данные | Запросы с `{{7*7}}`, `${T(java.lang.Runtime)}`, `<%= system('id') %>` | Отказ от динамического создания шаблонов из пользовательского ввода, sandboxing, использование безвредных функций |
| NoSQL Injection | Изменение семантики запросов в NoSQL-СУБД через манипуляции с JSON/операторами (`$gt`, `$ne`, `$where`) | Прямая вставка пользовательских объектов в запросы к MongoDB, CouchDB и др. | Запросы с `{"$gt": ""}`, `{"$ne": null}`, JavaScript-выражения в `$where` | Использование типизированных API, валидация структуры входных данных, запрет операторов в пользовательском вводе |
| XSS (Reflected) | Внедрение JavaScript в параметры запроса, отражаемые в HTML-ответе без кодирования | Вывод пользовательского ввода в HTML-страницу без экранирования (`<`, `>`, `"`, `'`) | Запросы с `<script>`, `javascript:`, `onerror=`, подозрительные параметры | Контекстное кодирование вывода, Content Security Policy, HttpOnly cookies |
| XSS (Stored) | Сохранение вредоносного скрипта в БД, файле или кэше и его последующая выдача другим пользователям | Отсутствие кодирования при сохранении и выводе | POST-запросы с `<script>` в полях, хранящихся в БД; повторяющиеся обращения к странице с вредоносным содержимым | То же, плюс фильтрация при вводе, HTML-санитизация |
| XSS (DOM-based) | Обработка пользовательского ввода в JavaScript на стороне клиента с опасными методами (`innerHTML`, `document.write`) | Использование недоверенных данных в DOM-операциях без безопасных альтернатив | Параметры с `#`, фрагменты URL, необычные паттерны в Referer | Использование `textContent` вместо `innerHTML`, CSP, строгая валидация |

Кроме перечисленных, категория включает менее распространённые, но значимые варианты: инъекции в ORM-запросы (например, через `raw()` в Django, `FromSqlRaw()` в Entity Framework, `find_by_sql()` в ActiveRecord), инъекции в динамические имена таблиц или столбцов, которые невозможно параметризовать, а также инъекции в выражения языка выражений (EL) [2]. Все они подчиняются тому же принципу: пользовательские данные попадают в синтаксическую позицию, где интерпретатор ожидает код.

## Выявление, тестирование и защита от инъекций

Работа с инъекциями на практике включает три направления: выявление уязвимостей в коде и работающем приложении, тестирование (в том числе в рамках пентеста) и внедрение защитных мер. В SOC-контексте дополнительно важны мониторинг и реагирование на попытки эксплуатации, что рассмотрено в сквозном примере.

### Выявление уязвимостей

Статический анализ кода (SAST) позволяет находить инъекционные дефекты до запуска приложения. Современные SAST-движки, такие как ByteHide Radar, выполняют taint analysis: отслеживают путь пользовательского ввода от точек входа до опасных приёмников и выявляют нарушение целостности данных [2]. Radar детектирует конкретные паттерны: конкатенацию SQL-строк, обход параметризации через динамические имена таблиц или ORDER BY, небезопасные ORM-вызовы (`raw()`, `FromSqlRaw()`, `find_by_sql()`), передачу ввода в `exec`/`system`/`popen`, незащищённые LDAP-фильтры, XPath-выражения, шаблоны и XSS [2]. SAST эффективен на ранних этапах, но имеет ограничения: не всегда понимает контекст выполнения, может давать ложные срабатывания.

Динамический анализ (DAST) тестирует работающее приложение, отправляя специально сформированные запросы и анализируя ответы. Инструменты (Burp Suite, OWASP ZAP, sqlmap) автоматизируют поиск инъекций, но ручное тестирование остаётся необходимым для сложных случаев (blind, second-order injection). При пентесте широко применяются прокси-инструменты для перехвата и модификации запросов, а также специализированные утилиты типа sqlmap для эксплуатации SQLi.

### Защита

Основной принцип защиты — полное разделение данных и команд. Для SQL это достигается параметризованными запросами (prepared statements), при которых пользовательский ввод передаётся отдельно от структуры запроса и никогда не интерпретируется как часть SQL-синтаксиса [2]. В Java пример уязвимого кода [5]:

```java
String query = "SELECT * FROM employees WHERE employeeNumber='" + request.getParameter("employeeNumber") + "'";
```

Исправленный вариант с использованием `PreparedStatement`:

```java
String query = "SELECT * FROM employees WHERE employeeNumber = ?";
PreparedStatement stmt = connection.prepareStatement(query);
stmt.setString(1, request.getParameter("employeeNumber"));
ResultSet rs = stmt.executeQuery();
```

Для ORM следует использовать стандартные методы, автоматически параметризующие запросы, и избегать raw-методов; если raw-метод необходим, входные данные нужно валидировать и экранировать [2].

Командные инъекции предотвращаются отказом от вызова оболочки: вместо `system("ls " + userInput)` следует использовать `subprocess.run(["ls", userInput])`, где аргументы передаются списком и не интерпретируются оболочкой [2]. Кроме того, применяется whitelist-валидация допустимых значений параметров.

Для XSS ключевая мера — контекстное кодирование вывода: HTML-экранирование (`&lt;`, `&gt;`, `&quot;`, `&#x27;`), JavaScript-экранирование, URL-кодирование в зависимости от места вставки. Дополнительные контрмеры: Content Security Policy, флаг HttpOnly для cookie, использование безопасных DOM-методов (`textContent` вместо `innerHTML`).

Средства защиты уровня сети/приложения, такие как WAF (Web Application Firewall), способны блокировать многие известные сигнатуры инъекций. Пример правила ModSecurity для обнаружения SQLi в URL-параметрах:

```apache
SecRule ARGS "@rx (union\s+select|select.*from|or\s+1\s*=\s*1|--)" \
  "id:100001,phase:2,deny,status:403,msg:'SQL Injection attempt detected'"
```

Это правило срабатывает на типовые паттерны: `UNION SELECT`, `OR 1=1`, комментарии `--`. Однако WAF не является панацеей: обход с помощью кодирования, многострочных комментариев или нестандартных синтаксических конструкций возможен, поэтому основная защита должна быть на уровне кода.

### Мониторинг и обнаружение в SOC

Для аналитика SOC важно уметь распознавать признаки инъекционных атак в логах веб-сервера, WAF и SIEM. Типичные индикаторы:

- Запросы, содержащие `' OR '1'='1`, `UNION SELECT`, `'; DROP TABLE`, `SLEEP(`, `WAITFOR DELAY`, `<script>`, `{{7*7}}`.
- Аномально высокая частота запросов с одного IP к одному параметру с вариациями payload.
- Ответы сервера с ошибками SQL (`You have an error in your SQL syntax`, `ORA-01756`).
- Резкое увеличение времени ответа для определённых запросов (time-based blind).

SIEM-системы коррелируют такие события с правилами, а WAF генерирует алерты при срабатывании сигнатур.

## Сквозной практический пример: расследование попытки SQL-инъекции в SOC

### Исходные условия

Студент SOC L1 работает в смене, мониторит SIEM (например, Splunk) и WAF (ModSecurity) для веб-приложения интернет-магазина. В 14:32 поступает алерт от WAF: заблокирован запрос, содержащий SQL-инъекцию. Необходимо провести расследование, подтвердить атаку, собрать IoC и рекомендовать исправление.

### Шаги

**Шаг 1. Получение и первичный анализ алерта**

Аналитик открывает алерт в SIEM и видит событие от WAF. Артефакт — фрагмент лога ModSecurity (иллюстративная схема, значения заменены):

```text
[Thu Sep 16 14:32:11 2026] [error] [client 203.0.113.45] ModSecurity: Access denied with code 403 (phase 2). Pattern match "(union\\s+select|select.*from|or\\s+1\\s*=\\s*1|--)" at ARGS:search. [hostname "shop.example.com"] [uri "/products"] [unique_id "abc123"]
```

Аналитик определяет: источник `203.0.113.45`, целевой URI `/products`, параметр `search`, правило сработало на паттерн `or 1=1` или `union select`. Результат: запрос заблокирован (код 403).

**Шаг 2. Детальный анализ логов веб-сервера и WAF**

Аналитик выгружает связанные события из SIEM за последние 10 минут для IP `203.0.113.45`. Находит несколько запросов до блокировки. Артефакт — фрагмент access-лога Apache:

```text
203.0.113.45 - - [16/Sep/2026:14:30:02 +0000] "GET /products?search=test HTTP/1.1" 200 5421
203.0.113.45 - - [16/Sep/2026:14:30:15 +0000] "GET /products?search=test' HTTP/1.1" 500 891
203.0.113.45 - - [16/Sep/2026:14:31:47 +0000] "GET /products?search=test' OR '1'='1 HTTP/1.1" 403 203
```

Наблюдается этап разведки: сначала нормальный запрос, затем попытка с одинарной кавычкой (вызвала ошибку 500, что указывает на возможную SQL-ошибку), затем полноценная инъекция, заблокированная WAF. Результат: подтверждена попытка эксплуатации SQLi.

**Шаг 3. Подтверждение уязвимости на тестовом стенде**

Поскольку запрос был заблокирован WAF, необходимо убедиться, что приложение действительно уязвимо (например, если WAF обойдён). Аналитик обращается к разработчикам, которые поднимают копию приложения в изолированной среде без WAF. Затем запускается sqlmap с тем же параметром. Артефакт — вывод sqlmap (сокращён):


Результат: подтверждена уязвимость типа SQLi в параметре `search`; атакующий мог бы извлечь данные.

**Шаг 4. Сбор индикаторов компрометации (IoC) и блокировка источника**

Аналитик фиксирует IoC: IP-адрес `203.0.113.45`, сигнатуры payload, временные метки, целевой параметр. Артефакт — список IoC:

| Тип IoC | Значение | Источник |
|---|---|---|
| IP-адрес источника | 203.0.113.45 | WAF, access-лог |
| Параметр уязвимости | `search` (GET) | Логи, sqlmap |
| Payload | `' OR '1'='1` | WAF |
| Временной диапазон | 16.09.2026 14:30–14:32 UTC | Логи |
| User-Agent | `sqlmap/1.8.2` (из access-лога, если присутствует) | Логи |

Источник блокируется на межсетевом экране. Артефакт — команда блокировки (иллюстративная):

```bash
iptables -A INPUT -s 203.0.113.45 -j DROP
```

Результат: дальнейшие попытки с этого IP невозможны.

**Шаг 5. Рекомендация по устранению уязвимости**

Аналитик передаёт разработчикам рекомендацию: заменить конкатенацию строк на параметризованный запрос. Артефакт — diff исправления кода (упрощённый):

```diff
- String query = "SELECT * FROM products WHERE name LIKE '%" + search + "%'";
- Statement stmt = connection.createStatement();
- ResultSet rs = stmt.executeQuery(query);
+ String query = "SELECT * FROM products WHERE name LIKE ?";
+ PreparedStatement stmt = connection.prepareStatement(query);
+ stmt.setString(1, "%" + search + "%");
+ ResultSet rs = stmt.executeQuery();
```

Результат: внедрение параметризации устраняет возможность SQLi для данного параметра; рекомендуется применить подход ко всем запросам.
