# DDoS и исчерпание ресурсов

## Контекст и разграничение DDoS-атак как формы исчерпания ресурсов

DDoS (Distributed Denial of Service, распределённый отказ в обслуживании) — тип сетевой атаки, при котором легитимные пользователи теряют доступ к целевому сервису из-за перегрузки его ресурсов вредоносным трафиком, поступающим из множества распределённых источников. Ключевой механизм — **исчерпание одного или нескольких ресурсов** системы: пропускной способности канала, вычислительной мощности (CPU, RAM), количества одновременных соединений, таблиц состояний сетевого стека или логики приложения.

Термин «исчерпание ресурсов» шире: он охватывает не только сетевые атаки, но и локальное злоупотребление (запуск fork-бомбы, бесконечное потребление дескрипторов), ошибки конфигурации и естественные перегрузки. В SOC L1 под «исчерпанием ресурсов» в контексте периметра понимают прежде всего DDoS-инциденты, но также и аномалии, вызванные, например, некорректным балансировщиком или пиковой легитимной нагрузкой, которые выглядят как атака на исчерпание.

Для чёткого разграничения:
- **DoS** (Denial of Service) — атака с одного источника или малого числа источников. Современные системы, как правило, легко блокируют единичный источник на межсетевом экране.
- **DDoS** — атака с сотен, тысяч и более узлов (ботнет, рефлекторы, amplification-серверы), что делает фильтрацию по IP-адресам малоэффективной и требует анализа шаблонов трафика.

Сравнительная таблица разновидностей отказов:

| Тип                         | Источник трафика                     | Механизм исчерпания                                | Пример                           | Масштабируемость защиты                       |
|-----------------------------|--------------------------------------|---------------------------------------------------|----------------------------------|----------------------------------------------|
| Классический DoS            | Один хост / небольшая группа         | Отправка большого числа запросов, эксплуатация уязвимости | SYN-флуд с одного IP             | Легко блокируется ACL                       |
| DDoS (volumetric)           | Ботнет из тысяч географически распределённых узлов | Исчерпание полосы пропускания (bps)               | UDP-флуд, ICMP-флуд              | Требует scrubbing-центров, BGP-фильтрации    |
| Amplification-атаки         | Открытые серверы (DNS, NTP, Memcached) | Отражённый трафик с коэффициентом усиления >20x | DNS amplification (ANY-запрос)    | Фильтрация на upstream-провайдерах, блокировка source ports |
| Application-layer DDoS      | Ботнет, эмулирующий легитимных пользователей | Исчерпание ресурсов приложения (HTTP-сессии, БД-соединения) | HTTP GET/POST flood, Slowloris   | WAF, rate limiting, капча                   |
| Локальное исчерпание (не сетевое) | Процесс внутри сервера            | Истощение CPU, PID, памяти                         | Fork bomb, бесконечная рекурсия  | Hard limits (cgroups, ulimit)               |

Основная задача SOC L1 — отличить DDoS от легитимной вспышки активности (флеш-крауд, распродажа) и от единичного DoS. Первичная классификация происходит по скорости трафика, распределённости источников, наличию повторяющихся шаблонов (паттерны флуда) и косвенным признакам (рост входящего трафика при неизменном исходящем, пропорции пакетов TCP SYN/RST и т.д.).

## Внутреннее устройство DDoS-атак по уровням модели OSI и механизмы исчерпания

Атаки распределённого отказа в обслуживании принято классифицировать по уровню модели OSI, на котором происходит исчерпание. Эта классификация определяет стратегию обнаружения и защиты, а также тип истощаемого ресурса.

### Атаки на сетевом и транспортном уровнях (L3/L4)

Цель — исчерпать пропускную способность канала или таблицы состояний межсетевого экрана / сервера.

**Volumetric L3 (сетевой уровень):**
- UDP flood: массовая отправка UDP-дейтаграмм на случайные порты цели, что вынуждает хост отвечать ICMP Destination Unreachable и потреблять CPU на обработку.
- ICMP flood (ping flood): безответная отправка Echo Request с попыткой насытить канал.
- Fragment flood: злоупотребление фрагментацией IP-пакетов, приводящее к перегрузке сборщика фрагментов на хосте.

**L4 (транспортный) SYN flood:** атакующий отправляет лавину TCP SYN-запросов, часто с поддельными исходными IP. Сервер выделяет под каждое соединение запись в очереди SYN (backlog), отвечает SYN-ACK и ожидает ACK. Поскольку ACK не приходит, очередь переполняется, и легитимные клиенты не могут установить соединение. Исчерпаемый ресурс — **полуоткрытые соединения**.

**L4 amplification (отражённые атаки):** злоумышленник посылает запросы уязвимым серверам-рефлекторам, подставляя в качестве source IP адрес жертвы. Ответы, значительно превышающие размер запроса, направляются на жертву. Классические примеры: DNS amplification (коэффициент усиления до 54х), NTP monlist (до 556x), Memcached (до 51000x). Исчерпание — **полоса пропускания**.

Структура amplification-атаки:
```text
[Атакующий] ──(spoofed запрос от имени Жертвы)──▶ [Рефлектор UDP]
                                                    │
                                                    └──(усиленный ответ)──▶ [Жертва]
```

### Атаки на уровне приложений (L7)

Здесь ресурсы исчерпываются не столько полосой, сколько вычислительными возможностями backend-систем, числом одновременных HTTP-соединений, баз данных и т.п.

- **HTTP GET/POST flood**: ботнет посылает легитимные с виду запросы к ресурсоёмким URL (поиск, динамическая генерация PDF). Исчерпывает CPU, RAM, пул потоков веб-сервера.
- **Slowloris / Slow Read**: устанавливаются медленные HTTP-соединения, удерживающие сокет сервера в открытом состоянии бесконечно долго. Исчерпывается лимит одновременных соединений веб-сервера (MaxClients в Apache).
- **RUDY (R-U-Dead-Yet)**: POST-запросы с очень медленной передачей тела, вызывают таймауты и занятость потоков приложения.
- **HTTP/2 Rapid Reset (CVE-2023-44487)**: злоупотребление возможностью быстрого сброса потоков в HTTP/2, вызывающее колоссальную нагрузку на сервер из-за многократного открытия/закрытия соединений без фактической передачи данных. Исчерпывает CPU и память.

### Атаки на исчерпание состояния промежуточных устройств

Помимо конечного хоста, DDoS может метить в **сетевую инфраструктуру**: межсетевые экраны, балансировщики, IDS/IPS. Например, атака на сессионную таблицу файрвола — посылается множество пакетов с разными кортежами (IP, port, protocol), заставляя устройство создавать записи и быстро заполнять таблицу состояний, что приводит к отказу в обслуживании новых легитимных сессий или даже к аварийной перезагрузке.

Сравнительная таблица атак по уровням с характерными признаками:

| Уровень OSI | Тип атаки             | Исчерпаемый ресурс               | Индикатор в трафике (NetFlow/IPFIX)                | Типичная контрмера                     |
|-------------|-----------------------|----------------------------------|----------------------------------------------------|----------------------------------------|
| L3          | UDP flood             | Полоса пропускания               | Высокий bps, одномоментный рост пакетов, множество src IP по одному dst port | Blackhole routing (RTBH), scrubbing     |
| L3          | ICMP flood            | Полоса пропускания, CPU          | Массовый ICMP Echo Request с разных src            | Rate limit ICMP, ACL                    |
| L4          | SYN flood             | Backlog TCP-соединений           | Резкий рост SYN-пакетов без завершающего ACK       | SYN cookies, уменьшение таймаута backlog |
| L4          | DNS amplification     | Полоса входящего канала          | Аномальный объём DNS ответов на порт 53 в сторону жертвы, размер ответов >512 байт | Source port filtering, BGP flowspec    |
| L7          | Slowloris             | Число соединений веб-сервера     | Длительные открытые соединения с медленной передачей, низкая скорость передачи данных (bytes/sec) | WAF, rate limiting по числу коннектов с одного IP, реверс-прокси |
| L7          | HTTP/2 Rapid Reset    | CPU, память                      | Всплеск RST_STREAM фреймов без данных, высокая частота запросов в рамках одного соединения | Обновление ПО, ограничение числа стримов в секунду |

Схема многокомпонентной DDoS-кампании:
```text
[Мастер C2] ──(команды)──▶ [Ботнет-агенты]
                              │    │
                              │    └──(L7 HTTP flood)──▶ [Web-сервер]
                              │
                              └──(spoofed DNS ANY)──▶ [DNS-рефлекторы] ──(amplified response)──▶ [Маршрутизатор жертвы]─── перегрузка канала
```

## Применение и работа с DDoS-инцидентами в практике SOC L1

Специалист первого уровня играет критическую роль в своевременном выявлении DDoS и запуске процедур эскалации. Основные операции на данном этапе:

1. **Обнаружение по данным мониторинга.** SOC L1 опирается на источники:
   - NetFlow/IPFIX/sFlow с сенсоров на маршрутизаторах.
   - Системы DDoS-детектирования (Arbor, Radware, FastNetMon).
   - SIEM-алерты на пороговые значения (превышение baseline трафика на объекте).
   - Мониторинг доступности (Zabbix, Nagios, Prometheus) — резкое падение доступности или рост задержек.

2. **Верификация инцидента.** Получив уведомление о возможном DDoS, аналитик L1 выполняет экспресс-проверку, используя командные инструменты и панели управления, чтобы исключить ложные срабатывания (например, плановую маркетинговую акцию, вызвавшую всплеск легитимных запросов). Ключевые шаги:
   - Проверить график трафика на периметре: если входящий трафик многократно превышает обычный уровень при неизменном исходящем — вероятен volumetric DDoS.
   - Снять статистику по протоколам: `tcpdump -i eth0 -nn -c 1000 | awk '{print $2}' | sort | uniq -c | sort -rn` — если преобладает UDP или ICMP, это характерно для L3/L4-атаки.
   - Проверить таблицу соединений на пограничном межсетевом экране: `conntrack -S` (Linux) или `show conn count` (Cisco ASA) — аномальный рост числа half-open соединений указывает на SYN flood.

3. **Первичный анализ трафика с помощью tcpdump.** Пример захвата для выявления паттернов атаки:

```bash
tcpdump -i eth0 -nn -c 5000 'udp or icmp or tcp[tcpflags] & (tcp-syn) != 0'
```

Ожидаемый вывод при UDP flood (иллюстративная схема, IP-адреса заменены на обобщённые):
```
12:01:23.045678 IP 10.x.x.x.54321 > 192.0.2.80.80: UDP, length 1400
12:01:23.045679 IP 10.x.x.y.12345 > 192.0.2.80.80: UDP, length 1400
12:01:23.045680 IP 10.x.x.z.54321 > 192.0.2.80.80: UDP, length 1400
...
```
Повторяющиеся паттерны (одинаковые целевые порты, близкие размеры пакетов) подтверждают flood. При SYN flood будет видна лавина пакетов с флагом `S`.

4. **Применение инструментов NetFlow-анализа.** Утилиты командной строки, такие как `nfdump`, позволяют быстро определить top-talkers и аномалии:
```bash
nfdump -R /var/netflow/live -s ip/flows -c 50 | head -20
```
Вывод может показать десятки тысяч однотипных потоков с разных src IP на один dst IP/port, что характерно для DDoS.

5. **Фиксация инцидента и эскалация.** Если атака подтверждена, L1:
   - Заводит инцидент в ITSM (Jira, ServiceNow) с указанием времени начала, затронутого сервиса, типа атаки (если удалось определить), графиков.
   - Передаёт кейс на L2/L3 и уведомляет сетевого инженера по заранее согласованному сценарию.
   - При необходимости (по инструкции) запускает первичные блокировки: внесение IP-адресов в чёрные списки на межсетевом экране (только если атака не распределённая), активация BGP blackhole-команды для сброса трафика на «чёрную дыру» (если есть полномочия и инструкции).

Типовое правило детектирования для SIEM (Sigma, иллюстративная структура) для обнаружения SYN flood на основе логов межсетевого экрана:
```yaml
title: SYN Flood Detection
logsource:
  product: firewall
  category: deny
detection:
  selection:
    protocol: tcp
    flags: 'S'
  condition: selection | count(dst_ip) by src_ip > 1000 per 1 minute
```
Реальное правило должно опираться на поля конкретного вендора, здесь показана лишь логика подсчёта аномального числа SYN-пакетов к одному хосту.

### Типичные ошибки анализа L1
- Ошибочное принятие легитимного скачка трафика за DDoS без проверки профиля мероприятия (релиз продукта, флеш-моб).
- Оценка DDoS только по утилизации CPU сервера — при volumetric атаке сервер может быть свободен, а боттлнек находится на уровне провайдера.
- Игнорирование amplification-атак малого размера, которые укладываются в пропускную способность, но создают задержки из-за заполнения буферов.

## Сквозной практический пример: анализ SYN flood-атаки на пограничном маршрутизаторе

**Исходные условия:** аналитик SOC L1 получает алерт от SIEM о превышении базовой скорости входящего трафика на веб-портал компании (адрес 198.51.100.15) в 5 раз. Сервер работает на Linux, используется межсетевой экран iptables. Инструменты: терминальный доступ к граничному роутеру (Cisco IOS), NetFlow-коллектор, tcpdump на хосте. Необходимо за 10 минут подтвердить атаку, классифицировать её и инициировать эскалацию.

### Шаг 1: Проверка статистики трафика на интерфейсе

На маршрутизаторе выполняем команду для просмотра текущей загрузки интерфейса:
```ios
show interfaces GigabitEthernet0/1 | include rate|input rate|output rate
```
Пример вывода (значения иллюстративные):
```
  5 minute input rate 875045000 bits/sec, 143200 packets/sec
  5 minute output rate 12500000 bits/sec, 8200 packets/sec
```
Входящая скорость (875 Мбит/с) при обычной дневной норме 150–200 Мбит/с и низкий исходящий трафик однозначно указывают на входящий флуд.

### Шаг 2: Анализ NetFlow с граничного устройства

Запрашиваем топ-протоколы за последние 5 минут:
```bash
nfdump -R /data/netflow/router1: -s proto -c 20
```
Вывод может выглядеть так:
```
Top 20 protocols ordered by flows:
    Proto      flows           packets             bytes
    TCP        3842015        1.34 M (93.2%)      1.8 G (99.1%)
    UDP        12893          2345 (0.1%)         4.2 M (0.2%)
...
```
Несмотря на доминирование TCP по пакетам, это может быть SYN flood. Более детально анализируем по флагам:
```bash
nfdump -R /data/netflow/router1: -o "fmt:%ts %pr %sap %dap %flg %pkt" 'dst host 198.51.100.15 and tcp'
```
Обнаруживаем огромное количество записей с флагом `....S.` (SYN) и отсутствие завершающих ACK, что характерно для атаки.

### Шаг 3: Захват трафика для подтверждения на уровне хоста

На веб-сервере запускаем кратковременный захват с фильтром на SYN-пакеты:
```bash
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0 and dst host 198.51.100.15' -c 200
```
Фрагмент вывода:
```
14:02:33.112233 IP 203.0.113.45.54321 > 198.51.100.15.443: Flags [S], seq 123456789, win 65535, length 0
14:02:33.112234 IP 203.0.113.46.12345 > 198.51.100.15.443: Flags [S], seq 987654321, win 65535, length 0
14:02:33.112235 IP 203.0.113.47.54321 > 198.51.100.15.443: Flags [S], seq 1122334455, win 65535, length 0
...
```
Все пакеты приходят на стандартный порт HTTPS (443) с различных IP-адресов (первые два октета 203.0.113.x — адреса из документационного диапазона, в реальной атаке были бы случайные), размер окна фиксирован, поля случайны — типичная картина SYN-флуда.

### Шаг 4: Проверка состояния таблицы соединений на сервере

Выполняем на веб-сервере:
```bash
ss -s
```
Вывод:
```
Total: 45123 (kernel 48765)
TCP:   45000 (estab 23, closed 0, orphaned 0, synrecv 44977)
```
Огромное количество сокетов в состоянии `SYN-RECV` (44977) при почти отсутствующих установленных соединениях означает, что очередь backlog переполнена. Это типичный результат SYN flood.

### Шаг 5: Классификация и первичные меры

На основании собранных данных аналитик классифицирует событие как распределённый SYN flood (L4). В соответствии с процедурами SOC L1 заводит инцидент с пометкой «Critical», прикладывает логи и графики трафика, тут же связывается с дежурным сетевым инженером. Инженер активирует SYN cookies на сервере:
```bash
sysctl -w net.ipv4.tcp_syncookies=1
```
И одновременно применяет upstream-фильтрацию на провайдере (BGP RTBH) для сброса паразитного трафика за периметр, чтобы освободить канал.

### Ожидаемый вывод примера

Пример демонстрирует полный цикл работы SOC L1 при возникновении подозрения на DDoS: от первичного мониторинга и утилит командной строки до верификации, типизации атаки и эскалации с предоставлением доказательной базы (логи, метрики).
