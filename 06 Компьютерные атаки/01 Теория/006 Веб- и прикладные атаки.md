# Веб- и прикладные атаки

## Контекст и базовые понятия: место атак прикладного уровня в ландшафте угроз
Атаки на прикладной уровень (Layer 7 модели OSI) входят в число трёх основных векторов компрометации по ежегодным отчётам Verizon Data Breach Investigations Report, а эксплуатация уязвимостей приложений обогнала фишинг и заняла второе место среди причин утечек данных [Contrast Security Application Attacks](https://www.contrastsecurity.com/glossary/application-attacks). Для специалиста SOC начального уровня критически важно различать сетевые и прикладные атаки, а внутри последних — видеть разницу между атаками, специфичными для веб-технологий, и более широким классом воздействий на любые приложения, обрабатывающие данные из недоверенных источников.

**Терминологические границы.** Под *веб-атаками* понимают атаки, использующие протокол HTTP/HTTPS и уязвимости веб-приложений, веб-серверов, браузеров и связанных с ними технологий (JavaScript, HTML, cookies, URL-параметры). *Прикладные атаки* (application layer attacks) — более общее понятие, охватывающее любые злонамеренные воздействия на уровень приложений, не ограничиваясь HTTP: атаки на API (REST, GraphQL, gRPC), клиент-серверные протоколы биржевых терминалов, мобильные приложения, IoT-устройства, системы управления базами данных. Веб-атаки являются подмножеством прикладных атак, однако в силу повсеместного распространения веб-технологий они доминируют в практике SOC L1.

Для наглядности основные различия сведены в таблицу.

| Категория | Уровень OSI | Типичные протоколы | Примеры атак | Основные средства защиты |
|-----------|-------------|-------------------|--------------|--------------------------|
| Сетевые атаки | 3 – Сетевой, 4 – Транспортный | IP, ICMP, TCP, UDP | SYN flood, UDP amplification, IP-спуфинг, DDoS «отражением» | Сетевой межсетевой экран, ограничение скорости на маршрутизаторе, BCP38 |
| Прикладные атаки (широкий класс) | 7 – Прикладной | HTTP, HTTPS, WebSocket, gRPC, GraphQL, LDAP, SQLnet, проприетарные бинарные протоколы | SQL-инъекция, выполнение команд ОС, небезопасная десериализация, XML External Entities (XXE), GraphQL Batching Attack | WAF, RASP, санитизация входных данных, параметризованные запросы |
| Веб-атаки (подкласс прикладных) | 7 – Прикладной, только HTTP(S) | HTTP, HTTPS, WebSocket | XSS, CSRF, Path Traversal, HTTP-флуд, открытое перенаправление, подделка заголовков Host | WAF на основе сигнатур и поведенческого анализа, CSP-заголовки, HttpOnly- и Secure-флаги cookie |

Такая классификация помогает аналитику SOC правильно выбрать источник событий для расследования: если IDS сигнализирует об аномалии на 4-м уровне, искать её следует в сетевых журналах; если же WAF или сервер приложений сообщает о попытке SQL-инъекции, работа ведётся с журналами веб-доступа и алертами WAF.

**Почему прикладные атаки опаснее для современного периметра.** Традиционные файрволы и системы предотвращения вторжений (IPS) эффективно отсекают атаки нижних уровней, но не способны анализировать содержимое HTTP-запроса на уровне отдельных параметров формы или тела API-вызова. Прикладные атаки минуют сетевую защиту, поскольку с точки зрения транспортного уровня они выглядят как легитимный трафик. Более того, среднее веб-приложение в production-окружении получает порядка 500 миллионов обращений к потенциально опасным функциям в год, и злоумышленники непрерывно сканируют публичные веб-ресурсы на предмет уязвимостей [Contrast Security Application Layer Attacks](https://www.contrastsecurity.com/glossary/application-layer-attacks).

**Модель угроз для веб- и прикладных атак.** Цели злоумышленников можно сгруппировать следующим образом:
- *Кража конфиденциальных данных* — дамп базы данных через SQLi, перехват сессионных токенов через XSS, извлечение учётных записей пользователей;
- *Нарушение бизнес-логики* — обход аутентификации, манипуляции с корзиной интернет-магазина, изменение привилегий через CSRF;
- *Компрометация серверной инфраструктуры* — выполнение команд ОС через command injection, загрузка веб-шеллов, lateral movement после захвата веб-сервера;
- *Отказ в обслуживании* — HTTP-флуд, Slowloris, исчерпание пула соединений с базой данных через дорогостоящие запросы;
- *Заражение клиентов* — drive-by downloads через вредоносную рекламу, использование уязвимых компонентов JavaScript-библиотек для распространения майнеров.

Для специалиста SOC L1 практическое значение имеет то, что подавляющее большинство прикладных атак оставляет следы в журналах веб-сервера, в логах WAF и в событиях самого приложения. Грамотная интерпретация этих артефактов — первый шаг к обнаружению инцидента на ранней стадии.

## Типовое устройство атак: векторы, механизмы и ключевые классы
Атаки на веб-приложения и прикладные протоколы удобно анализировать через общность механизма, с помощью которого злоумышленник воздействует на целевую систему. Все основные классы могут быть отнесены к одной из трёх крупных групп: инъекции (внедрение вредоносного кода в интерпретируемый контекст), межсайтовые атаки (эксплуатация доверия между браузером и сайтом) и отказы в обслуживании на уровне логики приложения. Ниже представлен исчерпывающий перечень ключевых классов, составляющих обязательный минимум знаний для аналитика SOC.

| Класс атаки | Суть механизма | Типичный вектор | Признаки в логах |
|------------|----------------|-----------------|------------------|
| SQL-инъекция (SQLi) | Внедрение фрагментов SQL в поля ввода, позволяющее модифицировать структуру запроса к базе данных [Bright Security](https://brightsec.com/blog/web-application-security) | `GET /products?id=1 OR 1=1--` | Наличие ключевых слов SQL в URL или теле запроса, сообщения об ошибках БД в ответе |
| Межсайтовый скриптинг (XSS) | Вставка вредоносного JavaScript-кода в контент, отображаемый другим пользователям, что приводит к краже cookie, токенов или выполнению действий от имени жертвы | Передаваемый через параметр `?search=<script>alert(1)</script>` или сохранённый в профиле пользователя | Появление `<script>` или JavaScript-событий (`onerror`, `onload`) в параметрах запроса или в содержимом страниц |
| Выполнение команд ОС (Command Injection) | Внедрение метасимволов оболочки (`;`, `|`, `&&`) в параметры, передаваемые системным вызовам, что приводит к выполнению произвольных команд на сервере | `POST /ping HTTP/1.1 ... host=127.0.0.1; cat /etc/passwd` | Обнаружение символов перенаправления, конвейера или наличие путей к файлам ОС в неожиданных полях |
| Path Traversal (Directory Traversal) | Использование последовательностей `../` для выхода за пределы корневой директории веб-сервера и чтения произвольных файлов системы | `GET /download?file=../../etc/shadow` | Паттерны `../`, `..\`, попытки чтения системных файлов (`/etc/passwd`, `boot.ini`) |
| Cross-Site Request Forgery (CSRF) | Принуждение аутентифицированного пользователя выполнить нежелательное действие на доверенном сайте путём перехода по специально созданной ссылке или загрузки изображения | `GET /transfer?to=hacker&amount=1000`, встроенный в `<img>` на стороннем сайте | Отсутствие Referer или его несоответствие, запросы с cookie сессии, инициированные с других доменов |
| Небезопасная десериализация | Эксплуатация логики восстановления объектов из сериализованных данных путём подмены полей или внедрения вредоносных объектов | Передача модифицированного сериализованного объекта (JSON, XML, Java Serialization) в теле запроса | Аномальные структуры сериализованных данных, сообщения об ошибках десериализации, попытки инстанцирования неожиданных классов |
| XML External Entities (XXE) | Обработка XML-документов со ссылками на внешние сущности, позволяющая читать локальные файлы, сканировать порты или выполнять DoS-атаки | `POST /api/xml HTTP/1.1 ... <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>` | Декларации DOCTYPE с внешними SYSTEM-ссылками, попытки чтения локальных файлов через `file://` |
| Прикладной отказ в обслуживании (Application DoS) | Истощение ресурсов сервера путём отправки медленных или ресурсоёмких запросов, не требующее большого объёма трафика (Slowloris, R-U-Dead-Yet, HTTP-флуд на дорогой endpoint) | Медленная отправка HTTP-заголовков, не закрывая соединение; циклические обращения к отчётам, вызывающим тяжёлые JOIN-запросы | Высокая частота запросов к одному URI, аномально долгие сессии без передачи тела, корреляция с ростом времени ответа сервера |

Все перечисленные классы атак (кроме CSRF, который полагается на доверие браузера, а не на инъекцию) основаны на недостаточной проверке входных данных, что является сквозной причиной большинства прикладных уязвимостей.

**Механизм инъекций — канонический пример внутреннего устройства атаки.** Рассмотрим SQL-инъекцию как образец того, как атака проходит через компоненты системы. Веб-приложение обычно построено по трёхзвенной архитектуре: фронт-энд (браузер) ↔ веб-сервер / сервер приложений ↔ база данных. Запрос пользователя на языке HTTP преобразуется приложением в SQL-команду, которая передаётся СУБД. Если при конкатенации строк не применяется параметризация, злоумышленник может «выйти» за пределы ожидаемого синтаксиса.

```text
[Браузер] ── GET /item?id=1 OR 1=1-- ──▶ [Веб-сервер (Apache/nginx)] ──▶ [PHP-скрипт]
                                                        │
                                          конструирует запрос:
                                          "SELECT * FROM goods WHERE id = " + $_GET['id']
                                                        │
                                                        ▼
                                          [СУБД MySQL] получает:
                                          SELECT * FROM goods WHERE id = 1 OR 1=1--
```

В результате атаки приложение выдаёт все записи таблицы вместо одной. Вариации SQLi включают UNION SELECT для извлечения данных из других таблиц, time-based blind при отсутствии прямого вывода и stacked queries для выполнения произвольных операторов.

**Особенности атак на не-HTTP прикладные протоколы.** В рамках SOC L1 аналитик может столкнуться с атаками на API, использующие GraphQL. Например, злоумышленник выполняет batching attack, объединяя множество дорогих запросов в одном теле POST; или проводит интроспективное сканирование, перебирая поля через автогенерированные запросы. Аналогично, gRPC-сервисы могут подвергаться инъекциям полезной нагрузки в protobuf-сообщения, если валидация полей отсутствует. Общий паттерн детекции сохраняется: мониторинг аномалий в размере и структуре сообщений, частоты запросов и появления специфических ключевых слов.

## Выявление и анализ в SOC: артефакты, инструменты и процедуры
Работа аналитика SOC L1 с веб- и прикладными атаками строится на корреляции событий из двух–трёх основных источников: журнал доступа веб-сервера, логи WAF/WAAP-решения и, в идеальном случае, телеметрия самого приложения или runtime-агента (RASP). Практическая задача — по первичному алерту быстро отделить ложное срабатывание от реального инцидента.

**Первичный артефакт — журнал веб-сервера.** В стандартном combined-формате Apache или в JSON-логах nginx атака выглядит как обычный HTTP-запрос, содержащий подозрительные паттерны. Например, попытка SQL-инъекции через параметр URL оставляет такую запись:

```bash
192.168.12.34 - - [12/Jan/2026:14:32:10 +0300] "GET /catalog.php?category=1%27%20UNION%20SELECT%20null,username,password%20FROM%20users-- HTTP/1.1" 200 1245 "-" "Mozilla/5.0"
```

Аналитик обращает внимание на наличие URL-кодированной апострофы `%27` и ключевых слов `UNION SELECT`. Само по себе присутствие таких слов в логе не всегда говорит об успешной эксплуатации — код ответа `200` может сопровождать страницу с ошибкой. Поэтому следующий шаг — проверить ответ сервера из WAF-лога или из сетевого трафика, если доступен.

**Работа с Web Application Firewall.** Современные WAF, такие как Positive Technologies Application Firewall [Отчет PT AF](https://pt-corp.storage.yandexcloud.net/upload/corporate/ru-ru/analytics/Web-Applications-Attacks-rus.pdf), ModSecurity с OWASP Core Rule Set или облачные решения, генерируют событие при совпадении запроса с сигнатурой. Событие обычно содержит разобранные поля: временную метку, IP-источник, URI, тело запроса, сработавшее правило и решение (пропущено/заблокировано). Ниже приведён иллюстративный JSON-алерт WAF:

```json
{
  "timestamp": "2026-01-12T14:32:11+0300",
  "sensor_id": "waf-prod-01",
  "src_ip": "192.168.12.34",
  "method": "GET",
  "uri": "/catalog.php",
  "parameters": {
    "category": "1' UNION SELECT null,username,password FROM users--"
  },
  "matched_rule": {
    "id": "942100",
    "description": "SQL Injection Attempt: Classic UNION SELECT",
    "severity": "CRITICAL"
  },
  "action": "blocked",
  "http_status": 403
}
```

Данный артефакт уже не требует рутинного разбора строк — аналитик видит, что запрос был классифицирован как критический и заблокирован. Тем не менее SOC L1 должен верифицировать событие, чтобы исключить ложные срабатывания на легитимный трафик (например, текст «union select» в параметре поиска по документации).

**Поиск и корреляция с помощью SIEM и командной строки.** При первичном расследовании аналитик часто использует быстрый поиск в SIEM (Splunk, Elastic, OpenSearch) или прямое обращение к лог-файлам на сервере. Пример типовой команды для поиска попыток обхода каталога в журнале nginx:

```bash
grep -P '\.\.\/' /var/log/nginx/access.log | awk '{print $1, $7}' | sort | uniq -c
```

Эта команда выводит IP-адреса и пути, где встретились последовательности `../`. Однако в сжатых средах логи могут храниться в JSON-формате, и тогда поиск удобнее выполнять через `jq`:

```bash
jq 'select(.request | test("\\\\\\.\\\\\\.\\\\/"))' /var/log/nginx/access.json
```

**Правила детекции как артефакт автоматизации.** В SOC принято формализовывать логику обнаружения в виде правил Sigma, которые затем транслируются в запросы SIEM. Пример правила для обнаружения простейших попыток command injection:

```yaml
title: Suspected OS Command Injection in HTTP Request
status: experimental
description: Detects common patterns of command injection in URL or POST body
logsource:
  category: webserver
detection:
  selection:
    cs-uri-query|contains:
      - ';cat '
      - '|cat '
      - '|id'
      - '&& whoami'
      - '|/bin/bash'
  condition: selection
level: high
```

Это правило проверяет наличие типичных цепочек, передаваемых при попытке выполнить команду. В реальной среде следует ожидать высокую вариативность обфускаций (двойное URL-кодирование, использование обратных кавычек, подстановки `$IFS`), поэтому подобные сигнатуры являются лишь базовым слоем, требующим подтверждения поведенческим анализом.

**Типичные ошибки на стадии первичного анализа.** Начинающие аналитики часто считают любой запрос с `' OR 1=1` успешной атакой, не глядя на код ответа и не понимая, что приложение могло экранировать апостроф или не отработать запрос. Вторая ошибка — игнорирование POST-тел запросов: атаки могут скрываться в JSON- или XML-полях, невидимых в access-логе без дополнительного логирования. Третья — незнание специфики легитимного трафика конкретного приложения; например, генератор отчётов может регулярно слать запросы с параметрами, похожими на инъекции, что приводит к засорению очереди алертов. Грамотный триаж всегда включает сравнение с базовым профилем приложения.

## Сквозной практический пример: разбор атаки SQL Injection от обнаружения до реагирования
Данный пример иллюстрирует полный цикл обработки веб-атаки аналитиком SOC L1, от генерации алерта до принятия защитных мер.

**Исходные условия.** Интернет-магазин развёрнут на Linux-сервере с Apache 2.4, PHP 8.1 и MariaDB. Приложение включает страницу `/product.php?id=...`, где параметр `id` напрямую подставляется в SQL-запрос без валидации. Защита представлена WAF ModSecurity с базовыми правилами OWASP CRS, логи WAF в формате JSON направляются в SIEM Splunk. Аналитик SOC L1 Иван имеет доступ к Splunk и к серверу по SSH только для чтения логов.

**Шаг 1. Злоумышленник проводит рекогносцировку.** Он отправляет несколько запросов с различными тестовыми строками, чтобы определить наличие уязвимости.

```http
GET /product.php?id=1' HTTP/1.1
Host: shop.example.com
User-Agent: Mozilla/5.0
```

В ответ приложение выводит ошибку MySQL: "You have an error in your SQL syntax; check the manual...". Злоумышленник убеждается, что экранирование отсутствует.

**Шаг 2. Эксплуатация: извлечение учётных данных.** Сформирован запрос UNION SELECT, чтобы получить имена пользователей и пароли из таблицы `users`.

```http
GET /product.php?id=-1%27%20UNION%20SELECT%20null,username,password%20FROM%20users-- HTTP/1.1
Host: shop.example.com
```

Код состояния `200`, и в ответе отображаются строки с данными пользователей. Одновременно WAF ModSecurity фиксирует срабатывание правила `942100` и генерирует JSON-алерт:

```json
{
  "event": {
    "time": "2026-01-12T15:02:33+0300",
    "src_ip": "203.0.113.45",
    "url": "/product.php?id=-1' UNION SELECT null,username,password FROM users--",
    "rule": "942100",
    "action": "passed",
    "severity": "CRITICAL",
    "message": "SQL Injection Attempt"
  }
}
```

**Шаг 3. Обнаружение в SIEM.** В Splunk настроено сохранение всех событий WAF в индекс `waf_logs`. Правило корреляции создаёт инцидент при критическом алерте, не заблокированном WAF (поле `action: passed`). Иван получает уведомление и выполняет поиск в Splunk для уточнения контекста:

```
index=waf_logs src_ip="203.0.113.45" earliest=-15min
| stats values(url) as URLs by src_ip
```

Результаты показывают цепочку запросов от одного IP, начинающуюся с пробной инъекции `id=1'` и заканчивающуюся UNION SELECT.

**Шаг 4. Валидация инцидента.** Чтобы исключить ложное срабатывание, Иван проверяет ответ сервера, сохранённый в расширенных логах. Из журнала Apache видно, что размер ответа на вредоносный запрос аномально велик (десятки килобайт, обычно страница товара — 5 Кбайт). Фрагмент access-лога:

```
203.0.113.45 - - [12/Jan/2026:15:02:33 +0300] "GET /product.php?id=-1%27%20UNION%20SELECT%20null,username,password%20FROM%20users-- HTTP/1.1" 200 14253 "-" "Mozilla/5.0"
```

Код `200` и размер 14253 байта указывают, что выгрузка данных прошла успешно. Иван эскалирует инцидент на L2, а сам блокирует IP-адрес на межсетевом экране и в WAF.

```bash
# Добавление IP в черный список iptables (выполняется администратором)
iptables -A INPUT -s 203.0.113.45 -j DROP
```

**Вывод примера.** На сквозном кейсе продемонстрирована стандартная цепочка действий SOC L1: приём алерта от WAF, поиск дополнительных артефактов в журналах веб-сервера и SIEM, верификация успешности атаки на основе размера ответа и кода статуса, оперативная блокировка источника. Такой подход позволяет за считанные минуты нейтрализовать активную утечку данных.
