# Rule-based корреляция в SIEM: правила и условия срабатывания

## 1. Контекст и базовые понятия rule-based подхода

Корреляционное правило в SIEM — это предопределённый набор условий и логических конструкций, нацеленный на выявление комплексного инцидента безопасности путём сопоставления нескольких событий из разнородных источников. В отличие от простого сопоставления по сигнатурам, rule-based корреляция объединяет *разрозненные* события, связывая их по времени, общим сущностям (IP, пользователь, хост) или последовательности действий, чтобы ответить на вопрос: «Если произошло событие A, а затем B при определённых обстоятельствах, является ли это угрозой?» [[Cymulate]](https://cymulate.com/cybersecurity-glossary/siem-correlation-rules). Именно через такие правила SOC L1 получает не лавину сырых логов, а структурированные алерты, готовые к триажу.

Правило не существует изолированно — оно всегда опирается на три базовых компонента: источники данных (логи ОС, сетевого оборудования, EDR-систем), логические условия (временные окна, порядок событий, пороговые значения) и механизмы реагирования (оповещения, автоматические действия) [[1275.ru]](https://1275.ru/articles/pravila-korrelyatsii-dlya-siem-sistem-ekspertnoe-rukovodstvo-po-detektirovaniyu-ugroz_10843). Например, чтобы обнаружить брутфорс, правило связывает несколько неудачных аутентификаций (EventID 4625) с одного IP, подсчитывает их количество за пять минут и при превышении порога генерирует инцидент.

Важно разграничить rule-based подход от смежных техник детектирования, которые также могут использоваться в SIEM, но имеют принципиально иную логику. Нижеприведённая таблица фиксирует ключевые различия.

| Подход | Механизм обнаружения | Характерный индикатор | Пример в SIEM |
|--------|----------------------|------------------------|---------------|
| Rule-based (детерминированная корреляция) | Явно описанные логические условия, проверка порогов и последовательностей | Цепочка: 4625 → 4625 → 4625 → 4624 с одного IP | Алерт «Brute force успешен» при count(4625)≥5 и наличии 4624 |
| Сигнатурный (pattern matching, IOC-based) | Поиск совпадения с конкретным значением (хэш, IP, строка) | Индикатор компрометации из threat-фида | Сетевое соединение с IP из блок-листа |
| Поведенческий / аномальный (UEBA, ML) | Отклонение от построенной baseline-модели поведения | Резкий рост объёма исходящего трафика у пользователя, обычно отправляющего 10 МБ в день | Risk-score сессии > 80 |
| Watchlist-корреляция | Сопоставление события с заранее подготовленным списком | Принадлежность IP к адресам управления ботнета | Срабатывание при совпадении SourceIP с динамическим списком threat-фида |

Rule-based подход занимает центральное место в SOC именно благодаря своей *детерминированности* — аналитик первого уровня точно знает, почему сработало правило, и может сразу приступить к проверке. В отличие от статистических моделей, где результат может быть неочевиден, правило всегда содержит явные условия, что критически важно для оперативной триажи на L1 [[Exabeam]](https://www.exabeam.com/blog/siem-trends/siem-rules-or-models-for-threat-detection).

Корреляционные правила также принято классифицировать по уровню зрелости и тактической направленности. Тактические правила нацелены на обнаружение конкретных техник MITRE ATT&CK, например, «Выполнение процесса на удалённом компьютере через WMI» или «Изменение DACL критичного объекта AD в нерабочее время» [[1275.ru]](https://1275.ru/articles/pravila-korrelyatsii-dlya-siem-sistem-ekspertnoe-rukovodstvo-po-detektirovaniyu-ugroz_10843). Контекстные правила анализируют поведение конкретного пользователя или хоста относительно его истории. Статистические правила отслеживают аномалии объёмов событий, но в отличие от ML делают это через фиксированные пороги, а не через самообучающиеся модели.

В реальных внедрениях SIEM наивно полагаться только на предустановленные «коробочные» правила. Исследования показывают, что только для покрытия базовых техник злоумышленников в Windows может потребоваться до 194 правил на тактику, а общее число тактик согласно MITRE ATT&CK требует сотен индивидуальных детектов [[elib.utmn.ru]](https://elib.utmn.ru/jspui/bitstream/ru-tsu/34830/1/miim_2024_318_321.pdf). Поэтому инженеры SOC вынуждены постоянно разрабатывать и адаптировать правила под специфику своей инфраструктуры, используя либо встроенные конструкторы (MaxPatrol SIEM, Kaspersky Unified Monitoring and Analysis Platform), либо полноценный язык описания корреляции (Splunk SPL, QRadar AQL, Microsoft Sentinel KQL) [[ptsecurity]](https://ptsecurity.com/research/knowledge-base/kak-pisat-pravila-korrelyacii-v-siem-sisteme-bez-navykov-programmirovaniya).

## 2. Внутреннее устройство корреляционного правила: типы, структура и логика

Правило корреляции — это детерминированная конструкция, которая в своём теле объединяет фильтры событий, функции агрегации, временные окна и логику сопоставления. Чтобы правило было надёжным, SIEM предварительно нормализует поступающие логи: приводит временные метки к единому формату, унифицирует имена полей (например, `src_ip`, `dst_user`) и, при необходимости, обогащает событие геопривязкой или данными из CMDB. Без такой нормализации корреляция по общему ключу между событиями от разных источников была бы невозможна [[Cymulate]](https://cymulate.com/cybersecurity-glossary/siem-correlation-rules).

Структурно любое правило можно представить как набор следующих слоёв (см. схему).

```text
[Источники событий]
       │
       ▼
[Фильтр событий (event type, поля, условие)]
       │
       ▼
[Группировка (корреляционный ключ: IP, User…)]
       │
       ▼
[Агрегация / оконная функция (count, sum, window 5 мин)]
       │
       ▼
[Логическое условие срабатывания (порог, порядок, наличие)]
       │
       ▼
[Действие: алерт, обогащение, тюнинг]
```

### 2.1 Типология правил по логике обнаружения

В зависимости от цели детекта выделяют пять основных типов правил, каждый из которых решает собственный класс задач [[CyberSilo]](https://cybersilo.tech/what-is-correlation-rule-in-siem-and-how-to-create-one). В таблице ниже они сопоставлены с типичными условиями и примерами.

| Тип правила | Назначение | Характерные условия | Пример использования |
|-------------|------------|---------------------|----------------------|
| Пороговая агрегация (Threshold / Aggregation) | Выявление аномальной частоты событий | `count(event) by src_ip >= N` | 5 неудачных входов за 5 минут → возможно, брутфорс |
| Обнаружение последовательности (Sequence) | Фиксация цепочки событий, происходящих в заданном порядке | `Event A → Event B` в пределах временного окна для одного хоста | Эксплойт (4688 с подозрительным родительским процессом) → запуск cmd.exe |
| Статистическая аномалия | Отклонение от фиксированного порога без поведенческого моделирования | `traffic_size > 1 GB` за 1 час | Пиковый объём исходящих данных с рабочей станции |
| Watchlist-корреляция | Сопоставление события с динамическим списком индикаторов | `dst_ip IN threat_feed_ip_list` | Сетевое соединение с IP, добавленным в TIP-систему |
| Профилирование поведения (Rule-based UEBA) | Отклонение от исторического порога, заданного явным правилом | `downloaded_mb > avg_downloaded_mb + 3*stddev` | Пользователь загрузил в 10 раз больше файлов, чем обычно |

Пороговая агрегация — наиболее простой и широко распространённый тип, с которого обычно начинают SOC L1. Он опирается на оператор `count` (или `distinct_count`) и окно времени. Например, правило брутфорса проверяет `count(distinct TargetUserName) >= 5`, чтобы исключить ситуацию, когда пользователь забыл пароль и несколько раз ввёл его на своей учётной записи. Порог и интервал подбираются эмпирически: слишком низкое значение породит лавину ложноположительных срабатываний; слишком высокое — пропустит атаку. Типичные значения для Active Directory: 3–5 попыток за 5–10 минут.

Последовательностная корреляция сложнее, поскольку требует сохранения состояния между событиями. Движок правила должен запоминать факт возникновения первого события (например, успешной аутентификации с подозрительным типом входа LogonType 3), а затем искать второе событие (создание процесса через WMI с тем же IP) в течение заданного интервала. В MaxPatrol SIEM и аналогичных системах такую цепочку можно задать через интерфейс конструктора, выбирая события из выпадающих списков и настраивая межсобытийные задержки [[ptsecurity]](https://ptsecurity.com/research/knowledge-base/kak-pisat-pravila-korrelyacii-v-siem-sisteme-bez-navykov-programmirovaniya).

Watchlist-правила наиболее тесно интегрированы с threat intelligence. Они не требуют анализа предшествующих событий; алерт возникает при совпадении любого поля (обычно IP-адреса, домена или хэша) с записью в активном списке. Такой подход эффективен для быстрого обнаружения коммуникации с известными командными центрами, но полностью зависит от актуальности и качества фида.

Важно понимать, что на практике одно высокоуровневое правило может комбинировать несколько типов. Например, обнаружение фишинговой атаки: watchlist-условие (письмо с вложением `.hta`) → последовательностное условие (запуск mshta.exe) → пороговое условие (число уникальных получателей > 3). Таким образом, rule-based подход — это не просто «условие A + условие B», а иерархическая композиция логических примитивов.

### 2.2 Компоненты правила на уровне реализации

В реальных SIEM-системах правило, написанное на специализированном языке (Splunk SPL, QRadar AQL, Kusto), обычно содержит следующие секции:

- **Фильтр выборки**: определяет, какие нормализованные события будут участвовать в корреляции. Например, `EventID=4625 AND AuthenticationPackageName="NTLM"`.
- **Корреляционный ключ**: поле или набор полей, по которым события группируются. Чаще всего это `TargetUserName` + `IpAddress` или `Computer`.
- **Временной контейнер**: скользящее или фиксированное окно (например, 5 минут).
- **Функция агрегации**: `count()`, `sum()`, `avg()`, `max()`, `distinct_count()` и пр.
- **Триггерное условие**: предикат, проверяющий результат агрегации, например, `count > 5`.
- **Действия**: генерация оповещения, присвоение критичности, автоматическая блокировка IP на межсетевом экране, обогащение алерта данными из AD.

Многие SIEM позволяют анализировать не только срез «здесь и сейчас», но и проводить ретроспективный анализ: применить новое правило к уже сохранённым в хранилище событиям за прошедший период. Это особенно полезно при расследовании инцидентов, когда новое правило создаётся постфактум для поиска следов атаки в исторических данных [[ptsecurity]](https://ptsecurity.com/research/knowledge-base/kak-pisat-pravila-korrelyacii-v-siem-sisteme-bez-navykov-programmirovaniya).

Дополнительно правило может ссылаться на внешние контекстные таблицы (например, «список административных учётных записей») для исключения из алертов легитимной активности, что напрямую влияет на снижение ложноположительных срабатываний.

## 3. Условия срабатывания: от атомарных полей до сложных корреляционных предикатов

Условие срабатывания — это логический предикат, истинность которого заставляет правило перейти в состояние «алерт». Корреляционное правило может комбинировать десятки различных условий, и именно от их точности зависит соотношение сигнал/шум. В SOC L1 хорошо настроенное условие позволяет оператору реагировать на инцидент, а не на шум.

### 3.1 Атомарные условия и операции сравнения

Базовый кирпичик — проверка значения нормализованного поля события. Например:
- `EventID = 4625` (неудачная аутентификация),
- `Status = "0xC000006A"` (неверный пароль),
- `LogonType = 3` (сетевой вход),
- `src_ip NOT IN 10.0.0.0/8` (исключение внутренней сети).

Атомарные условия могут объединяться булевыми операторами (AND, OR, NOT) и образовывать фильтр выборки. В языке конструктора MaxPatrol SIEM это реализовано через выпадающие списки и макросы, избавляя аналитика от ручного написания кода. Макросы — это предопределённые шаблоны условий, например, «любое событие входа с ненулевым статусом ошибки», которые подставляются щелчком мыши [[ptsecurity]](https://ptsecurity.com/research/knowledge-base/kak-pisat-pravila-korrelyacii-v-siem-sisteme-bez-navykov-programmirovaniya).

### 3.2 Агрегационные условия

Самый распространённый тип условия в SOC — счетчик событий за заданный интервал. Он позволяет отсечь единичные аномалии и реагировать только на устойчивые паттерны. Формально агрегационное условие задаётся как:
`count(event) BY <correlation_key> WITHIN <time_window> > <threshold>`.

Пример псевдокода правила для обнаружения распыления паролей (Password Spray):
```python
# Псевдокод: поиск распыления паролей
for each 5-minute window:
    filter EventID=4771 AND FailureCode=0x18
    group by src_ip
    if distinct_count(TargetUserName) >= 10:
        raise_alert("Возможный Password Spray", src_ip, list_of_users)
```
Здесь ключевое отличие от обычного брутфорса — `distinct_count(TargetUserName)`, а не общее количество попыток. Одиночная учётная запись, на которую пять раз подряд пришла ошибка, не вызовет алерт; атака будет зафиксирована только тогда, когда один IP перебирает множество разных имён пользователей.

Другие агрегатные функции также находят применение:
- `sum(BytesSent) > 100 MB` — выявление эксфильтрации данных,
- `avg(ResponseTime) > 5000 ms` — обнаружение DoS-атаки на веб-сервер,
- `max(AuthenticationDuration) > 10 s` — аномально долгий ответ контроллера домена, возможно, перегрузка.

### 3.3 Последовательностные и временны́е условия

Sequence-based условие предполагает проверку цепочки событий с фиксацией их порядка. Оно формулируется как:
`EventType1 WHERE key1=k1 AND ... → EventType2 WHERE key2=k1 ... WITHIN T`.

Внутренне движок SIEM строит конечный автомат для каждого корреляционного ключа. При поступлении первого события запоминается его время и контекст, затем ожидается второе событие. Если второе событие не появляется в течение времени ожидания, состояние сбрасывается. Такой механизм критичен для обнаружения многошаговых атак, где единичный лог не является индикатором угрозы. Например, обнаружение использования Pass-the-Hash требует видеть последовательность: получение TGT-билета (4768) с необычным типом шифрования → запрос доступа к сетевому ресурсу (4769) с того же хоста в течение короткого интервала.

В практических руководствах по созданию правил часто указывается, что последовательность может включать более двух шагов. Для обнаружения распространения через WMI в статье на 1275.ru описан следующий набор условий [[1275.ru]](https://1275.ru/articles/pravila-korrelyatsii-dlya-siem-sistem-ekspertnoe-rukovodstvo-po-detektirovaniyu-ugroz_10843):
1. Успешная аутентификация (4624) с хоста A на хост B.
2. В течение 2 минут с хоста A фиксируется создание процесса через WMI (4688 с родительским процессом WmiPrvSe).
3. Последующее подключение с хоста B к новому хосту C.

Только выполнение всех трёх шагов порождает инцидент. Любой одиночный шаг сам по себе считается легитимной административной активностью и не генерирует алерт.

### 3.4 Контекстные и динамические условия

Условие может ссылаться не только на поля текущего события, но и на внешние данные. Активные списки (Active Lists) или таблицы обогащения позволяют реализовать логику, подобную:
- `src_user NOT IN privileged_users_list` — исключение администраторов,
- `dst_ip IN internal_ip_ranges` — проверка, что трафик направлен внутрь периметра,
- `process_name MATCHES allowed_software_list` — игнорирование установленного ПО.

Такое связывание резко сокращает количество ложноположительных срабатываний. Например, правило на обнаружение PowerShell-скриптов, запущенных из подозрительных директорий, обязательно должно содержать список легитимных путей, используемых системными задачами, иначе SOC утонет в алертах на плановые задания резервного копирования.

Также в условие может быть заложен временной параметр, не только как окно агрегации, но и как «учёт рабочего времени». Изменение членства в группе «Domain Admins» в промежутке 02:00–04:00 может быть более подозрительным, чем в рабочее время, поэтому в условие можно добавить проверку `Hour(timestamp) BETWEEN 22 AND 6`.

### 3.5 Управление ложноположительными срабатываниями через условия

Любое правило корреляции без настройки исключений будет заваливать SOC инцидентами. Процесс внесения исключений — неотъемлемая часть эксплуатации правил. На этапе тестирования аналитик изучает сработавшие алерты и дополняет правило дополнительными условиями-фильтрами [[in4security]](https://in4security.com/news/ug1v68u4m1-razrabotka-unikalnih-pravil-korrelyatsii). Примеры таких корректирующих условий:

- `TargetUserName NOT LIKE "*$"` — исключение компьютерных учётных записей из правил брутфорса,
- `ProcessName NOT IN ("C:\\Windows\\System32\\svchost.exe", "C:\\Program Files\\...")`,
- `CommandLine NOT MATCHES "backup_script"` — игнорирование известных плановых заданий,
- добавление проверки, что IP-адрес источника не принадлежит сегменту управления ИТ-отдела.

Каждое исключение должно документироваться, чтобы при последующей ревизии можно было оценить, не закрывает ли оно реальную угрозу. Ряд вендоров SIEM предоставляют телеметрию срабатывания правил и статистику их эффективности, позволяя отслеживать, как часто правило вызывает алерты и какая доля из них оказалась инцидентами [[habr]](https://habr.com/ru/companies/pt/articles/451680). Если правило даёт более 90 % ложноположительных срабатываний даже после настройки, возможно, стоит пересмотреть сам подход: заменить пороговое правило поведенческим или скорректировать выборку источников.

## 4. Применение и работа с правилами: от разработки до мониторинга в SOC L1

Для SOC первого уровня правило корреляции — это основной инструмент, предоставляющий алерты на вход трехуровневой модели обработки инцидентов. Поэтому правила должны быть не только технически корректными, но и удобными для оперативного анализа: содержать понятное название, описание цели, прикреплённую тактику ATT&CK и инструкцию по первичному реагированию.

### 4.1 Жизненный цикл правила корреляции

Процесс создания и сопровождения правила носит итеративный характер и включает следующие этапы [[in4security]](https://in4security.com/news/ug1v68u4m1-razrabotka-unikalnih-pravil-korrelyatsii):

1. **Определение цели детекта**: на основе модели угроз и матрицы ATT&CK определяется, какую технику необходимо обнаружить (например, T1110 – Brute Force). Идентифицируются источники, генерирующие релевантные события.
2. **Анализ телеметрии**: проверяется, какие поля событий доступны, корректно ли заполняются, достаточна ли нормализация. Возможно, требуется донастройка аудита на конечных точках.
3. **Прототипирование правила**: в тестовой среде создаётся черновой вариант с фильтрами и условиями. Используется либо конструктор (MaxPatrol, Ankey SIEM NG), либо встроенный язык (Splunk SPL, KQL).
4. **Тестирование на исторических данных**: правило применяется к архиву логов за несколько недель для оценки количества ложноположительных и истинно положительных срабатываний.
5. **Внесение исключений**: по результатам тестирования в правило добавляются фильтры на известную легитимную активность.
6. **Внедрение в эксплуатацию**: правило переносится в боевую среду, включается в real-time поток.
7. **Мониторинг эффективности**: собирается телеметрия срабатываний, анализируется доля инцидентов, при необходимости корректируются пороги или исключения.

### 4.2 Инструментарий для создания правил

Вендоры SIEM движутся в сторону упрощения разработки правил. Конструктор с графическим интерфейсом (MaxPatrol SIEM, Kaspersky KUMA) позволяет создать правило в несколько кликов: выбрать события, задать условия через макросы, указать интервал и нажать «Сохранить». Система автоматически сгенерирует код на внутреннем языке корреляции, который можно просмотреть и проверить на наличие незаполненных обязательных полей [[ptsecurity]](https://ptsecurity.com/research/knowledge-base/kak-pisat-pravila-korrelyacii-v-siem-sisteme-bez-navykov-programmirovaniya). Такой подход снижает порог входа для аналитиков, не владеющих программированием. Однако для реализации сложных многошаговых сценариев чаще используется прямое написание кода на языке SIEM.

Пример минимального правила на псевдо-SPL (Splunk-like) для брутфорса:
```splunk
index=windows EventID=4625
| bucket _time span=5m
| stats count by src_ip, user
| where count > 5
| join type=inner user [ search EventID=4624 | fields user ]
| stats values(user) as users, dc(user) as user_count by src_ip
| where user_count = 1 AND count > 5
```
Здесь после подсчёта неудачных попыток (`count > 5`) проверяется наличие успешного входа (`EventID=4624`), что превращает просто аномалию в индикатор компрометации. Подобные запросы могут быть автоматизированы как корреляционные поиски, исполняемые по расписанию.

### 4.3 Типовые сценарии для SOC L1 и их реализация

**Обнаружение брутфорса (Brute Force)** — классический пример порогового правила. Условие: не менее 5 неудачных аутентификаций (EventID 4625) с одного IP к одной учётной записи за 5 минут. Важно добавить фильтр по статусам ошибок (`Status=0xC000006A` — неверный пароль, исключая ошибку блокировки учётной записи 0xC0000234). Пример структуры правила в виде псевдокода:
```python
rule "Windows Brute Force":
    filter event_id == 4625 and SubStatus == "0xC000006A"
    group by src_ip, TargetUserName over 5 minutes
    if count() >= 5:
        if exists (event_id == 4624 for same TargetUserName in same window):
            alert("High", "Successful brute force", src_ip, TargetUserName)
        else:
            alert("Medium", "Brute force attempt", src_ip, TargetUserName)
```

**Обнаружение использования легитимных инструментов для Lateral Movement** (тактика TA0008). Здесь требуется последовательностное правило. Аналитик может создать правило, следящее за запуском PsExec или WMI. Шаги:
1. Событие 4688 с родительским процессом `services.exe` и образом `psexec.exe` или `cmd.exe /c "wmic ..."`.
2. В течение 2 минут событие 4624 (LogonType 3) с того же хоста-источника на другую машину.
3. Группировка по `src_host` и подсчёт уникальных целевых хостов. Если за 10 минут количество уникальных целей > 2, генерируется инцидент «Lateral movement using PSExec/WMI».

**Детект фишинга** — комбинированное правило, связывающее почтовый шлюз и конечную точку:
Фильтр: из почтового лога (уникальное событие от MTA) — вложение с расширением `.hta` и получатель из внутреннего домена. Затем поиск в логах EDR/Sysmon запуска `mshta.exe` с параметром, указывающим на загрузку с удалённого URL, в течение 5 минут для того же пользователя, что был в поле `TargetUser` почтового события. При совпадении генерируется алерт «Фишинговое вложение исполнено».

### 4.4 Настройка и снижение ложных срабатываний

Как упоминалось, исключения — критический элемент. Для этого в SIEM создаются **вспомогательные инструменты**: словари (списки легитимных учётных записей, IP-адресов), активные списки (автоматически заполняемые, например, IP-адреса администраторов за текущий день), правила обогащения и контекстные таблицы [[in4security]](https://in4security.com/news/ug1v68u4m1-razrabotka-unikalnih-pravil-korrelyatsii). Например, список `exclude_scan_ips` содержит адреса Nessus-сканеров, и правило брутфорса игнорирует события от них:
```python
if src_ip not in list("exclude_scan_ips"):
    # продолжение корреляции
```
Также параметры порогов подбираются итерационно. Если правило на DLP-систему (контроль отправки файлов) генерирует слишком много алертов при пороге 5 МБ, его повышают до 20 МБ, и смотрят на статистику инцидентов. Эксперты Positive Technologies рекомендуют собирать телеметрию по срабатываниям и регулярно пересматривать правила вместе с аналитиками SOC L2/L3 [[habr]](https://habr.com/ru/companies/pt/articles/451680).

### 4.5 Интеграция с процессом реагирования

Хорошее правило не останавливается на генерации алерта. В его определение включают **планы реагирования** — автоматические или рекомендательные. Например, при срабатывании правила на брутфорс с критическим приоритетом SIEM может сразу отправить команду на межсетевой экран для временной блокировки IP-адреса источника. В менее критичных случаях план содержит инструкцию для оператора L1: «Проверить географическую привязку IP, сверить с AD на предмет существования учётной записи; если пользователь не существует — эскалировать». Такая комплектация правила снижает время реакции (MTTR) и стандартизирует действия первой линии.

## Сквозной практический пример: обнаружение атаки Kerberoasting с помощью правила корреляции

**Исходные условия.** SIEM-система (например, MaxPatrol SIEM) получает от контроллера домена логи безопасности Windows и Sysmon с сервера RDP. Цель — выявить атаку Kerberoasting, когда злоумышленник, имея доступ к учётной записи пользователя домена, запрашивает TGS-билеты для сервисных учётных записей, чтобы затем офлайн-подобрать пароль. Стенд: Windows Server 2019 DC, рабочая станция-жертва, сетевой сегмент 10.0.1.0/24. Роль — аналитик SOC L1/инженер.

**Шаг 1. Настройка источников и проверка наличия событий.**  
Убеждаемся, что на контроллере домена включён аудит Kerberos Service Ticket Operations (событие 4769). В SIEM поступает JSON-запись с полем `event_id=4769`. Просматриваем сырые логи для проверки заполнения полей `ServiceName`, `ClientAddress`, `Status` и `TicketEncryptionType`. Команда для ручной проверки через поиск в SIEM:
```spl
index=windows EventID=4769
| stats count by ServiceName, ClientAddress, TicketEncryptionType
| sort - count
```
Ожидаемый вывод: список сервисных имён с указанием IP-адресов и типов шифрования. Легальные запросы обычно имеют `TicketEncryptionType=0x12` (AES256), подозрительные могут быть `0x17` (RC4-HMAC), что упрощает офлайн-перебор.

**Шаг 2. Разработка правила в конструкторе (иллюстративный псевдокод).**  
Определяем логику: если с одного IP-адреса за 10 минут поступает более 10 запросов TGS-билетов, причём хотя бы один запрос использует слабый тип шифрования (RC4), и запросы приходятся на учётные записи, не являющиеся администраторами или серверами (исключаем `*$`), то генерируем инцидент.  
Псевдокод наглядно:
```python
rule "Potential Kerberoasting":
    window = 10 minutes
    events = filter EventID=4769 and Status="0x0" and ServiceName not endswith "$"
    group by ClientAddress
    agg1 = count(events)
    agg2 = count(events where TicketEncryptionType not in (0x12, 0x11))  # только слабые типы
    condition agg1 > 10 AND agg2 > 0
    alert {
        severity = "High",
        description = "Kerberoasting activity from IP {ClientAddress} with weak encryption usage",
        response_plan = "Проверить учетные записи служб, сбросить пароли. Эскалировать."
    }
```

**Шаг 3. Тестирование правила на исторических данных.**  
Применяем правило к вчерашним логам с помощью ретроспективного поиска, например, в Kusto:
```kusto
windows
| where EventID == 4769 and Status == "0x0" and not(ServiceName endswith "$")
| summarize
    TotalAttempts = count(),
    WeakTickets = countif(TicketEncryptionType in (0x17, 0x18, 0x23))
    by ClientAddress, bin(TimeGenerated, 10m)
| where TotalAttempts > 10 and WeakTickets > 0
```
Вывод: список IP-адресов и количество слабых тикетов. Выясняем, что IP 10.0.1.56 генерировал по 15 RC4-запросов каждый час — это подозрительно.

**Шаг 4. Внедрение и настройка исключений.**  
После переноса правила в боевой режим фиксируем ложные срабатывания от легитимного скрипта инвентаризации, обращающегося к SPN. Добавляем исключение: `ClientAddress in list('srv_inventory_ips')` или `UserAgent == "LegacyInventoryTool"`. Мониторим телеметрию правила в панели статистики — убеждаемся, что количество алертов снизилось до 2–3 в сутки.

**Шаг 5. Реакция на инцидент.**  
При очередном алерте оператор L1 получает карточку: IP 10.0.1.56, имя пользователя-инициатора (из поля User), список затронутых SPN. Выполняется первичный триаж: пользователь не из ИТ-отдела, запросы происходят в нерабочее время. Инцидент эскалируется на L2 для изоляции хоста и сброса паролей сервисных учётных записей.

Ожидаемый вывод: правило успешно выявляет Kerberoasting с минимальными шумами; продемонстрирован полный цикл — от анализа сырых логов до автоматизированного алерта и первичного реагирования.
