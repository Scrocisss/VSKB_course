# Нормализованные поля vs сырые события: практическое отличие

## Контекст и базовые понятия

В центре работы любой SIEM-системы находятся события — записи о действиях, зафиксированных источниками данных: операционными системами, сетевыми устройствами, приложениями, средствами защиты. Эти события поступают в SIEM в том виде, в котором их сгенерировал источник — без изменений, со всеми особенностями форматирования конкретного продукта или версии. Такие записи называют **сырыми событиями** (raw events, raw logs). Именно сырые события служат единственным первичным источником истины при расследовании инцидентов.

Однако непосредственный анализ сырых событий наталкивается на фундаментальную проблему: форматы радикально различаются. Журнал Windows использует XML-подобную структуру с EventID, брандмауэр Palo Alto — пары ключ-значение, веб-сервер — комбинированный формат access лога, а облачный сервис AWS CloudTrail — JSON с вложенными объектами. Даже однотипные поля в разных источниках именуются по-разному: IP-адрес отправителя может быть `src`, `src_ip`, `sourceAddress`, `clientIp` и т.д. Без дополнительной обработки аналитик вынужден изучать десятки форматов и писать запросы, учитывающие каждый вариант, что многократно замедляет расследование и повышает риск пропустить угрозу.

Для решения этой проблемы SIEM выполняет **нормализацию** — процесс преобразования сырых событий в унифицированное представление. Результатом становятся **нормализованные поля**: события, в которых ключевые атрибуты (временная метка, IP-адреса, имена пользователей, тип действия, результат) приведены к общей схеме именования и единому формату данных. Нормализация является частью более широкого процесса обработки, включающего также **парсинг** (извлечение значений из текста) и **обогащение** (добавление контекста — геолокации, принадлежности актива и т.п.).

Разграничение между сырыми событиями и нормализованными полями принципиально для специалиста SOC L1. Сырое событие — это исходная улика; нормализованное поле — это улика, уже описанная на универсальном языке, готовая к быстрой корреляции и поиску. Как отмечают в ITU Online, «Raw logs tell you that something happened. Parsed logs tell you what happened, where it happened, who was involved, and whether it matters.» [Event Parsing in SIEM](https://www.ituonline.com/comptia-securityx/comptia-securityx-4/event-parsing-in-siem-analyzing-data-for-enhanced-security-monitoring-and-response).

Для чёткого понимания различий сопоставим ключевые характеристики.

| Характеристика | Сырые события | Нормализованные поля |
|----------------|---------------|----------------------|
| **Определение** | Исходная запись в формате источника без изменений | Событие, преобразованное в единую схему SIEM |
| **Формат** | Зависит от источника: текст, JSON, XML, key-value, бинарный | Унифицированная модель данных SIEM, например, CIM (Common Information Model) |
| **Именование полей** | Оригинальные имена из источника (`src`, `sourceAddress`, `clientIp`) | Стандартизированные имена (`src_ip`, `dst_ip`, `user`) |
| **Полнота данных** | Содержит всю информацию, переданную источником, включая неструктурированные сообщения | Включает только извлечённые и сопоставленные поля; может терять редкие или нестандартные детали |
| **Пригодность для поиска** | Поиск по ключевым словам, регулярным выражениям; высокая вариативность | Поиск по полям с фильтрацией, сортировкой, агрегацией; быстрый и точный |
| **Использование в корреляции** | Непригодно напрямую: правила должны учитывать множество форматов | Основа корреляции: правила оперируют едиными полями |
| **Хранение** | Сохраняется как минимум для соответствия нормативным требованиям и ретроспективного анализа; часто — в «холодном» хранилище | Индексируется для оперативного поиска и визуализации |
| **Роль в расследованиях** | Первичный неопровержимый источник, когда нормализация могла исказить данные; детальное изучение отдельных событий | Основной рабочий слой для SOC L1: быстрый обзор, фильтрация, построение гипотез |

Таким образом, сырые события и нормализованные поля — не конкурирующие, а взаимодополняющие представления одних и тех же данных. Аналитик SOC L1 должен уметь работать с обоими слоями, понимая, когда достаточно нормализованного поиска, а когда необходимо обратиться к исходной записи.

## Внутреннее устройство предмета: от источника до нормализованного поля

Тема раскрывает два взаимосвязанных компонента: структуру сырых событий и технологическую цепочку получения нормализованных полей.

### Форматы и особенности сырых событий

Сырое событие — это атомарная запись, сгенерированная источником в момент совершения действия. В зависимости от источника форматы могут быть:

- **Неструктурированный текст**: классический syslog-сообщение. Пример (иллюстративная схема): `<134>Jan 10 14:05:22 hostname sshd[1234]: Failed password for root from 192.168.1.100 port 22 ssh2`.
- **Key-Value пары (KV)**: записи вида `type=USER_LOGIN, msg=audit(…), user=john, src=10.0.0.1`. Характерны для Linux auditd, многих сетевых устройств.
- **CSV/TSV**: табличное представление с разделителями, часто встречается в журналах веб-серверов (Apache combined log).
- **JSON**: структурированные объекты, типичны для облачных сервисов, современных агентов. Например, запись AWS CloudTrail содержит вложенные объекты `userIdentity`, `sourceIPAddress`, `eventName`.
- **XML/Windows Event Log**: события Windows имеют EventID, каналы и XML-представление с системными и пользовательскими данными.
- **Бинарные форматы**: например, NetFlow/IPFIX, которые требуют специального декодирования.

Общая черта всех сырых событий — их гетерогенность. Одна и та же сущность «неудачный вход» в Linux (`sshd: Failed password`) и в Windows (EventID 4625) представлена принципиально разными текстовыми шаблонами, что делает невозможным единый полнотекстовый запрос на обнаружение без нормализации.

### Процесс нормализации в SIEM

Нормализация не одномоментное действие, а конвейер, реализуемый компонентами SIEM (коллекторами, парсерами, процессорами), как описано в архитектурах ведущих платформ [SIEM: Security Information and Event Management Explained](https://radiantsecurity.ai/learn/siem-security-information-and-event-management-explained-2026-guide). Типовой путь события включает следующие стадии:

1. **Сбор (Ingestion)**: получение события от источника по протоколу (syslog, HTTP, WMI, агенты). Событие сохраняется в сыром виде в буфер или хранилище.
2. **Парсинг (Parsing)**: извлечение значимых значений из сырого текста. Для этого применяются регулярные выражения, словари шаблонов, встроенные парсеры для JSON/XML/CEF/LEEF. Результат — набор пар «ключ-значение», где ключи соответствуют оригинальным именам полей источника. Например, из строки `Failed password for root from 192.168.1.100 port 22` парсер может извлечь: `user=root`, `src_ip=192.168.1.100`, `port=22`.
3. **Нормализация (Normalization)**: отображение извлечённых полей на единую схему данных SIEM. Схема определяет стандартные имена и типы: `src_ip`, `dst_ip`, `user`, `event_type`, `object`, `result` и др. [Как интегрировать аудит-логи с SIEM](https://habr.com/ru/companies/selectel/articles/981796). Так, поле `src` источника, `sourceAddress` другого и `clientIp` третьего — все маппятся в `src_ip`. Типы данных приводятся к единому формату: IP-адреса — к строке стандартного вида, временные метки — к UTC ISO 8601.
4. **Обогащение (Enrichment)**: добавление контекстной информации: геопривязка IP, определение принадлежности IP к внутренней сети, сопоставление пользователей с каталогом, классификация события по таксономии (например, MITRE ATT&CK). Обогащённые данные также размещаются в нормализованных полях.
5. **Индексация и хранение**: нормализованное событие индексируется для быстрого поиска. Сырое событие также сохраняется, часто в отдельное «холодное» хранилище, обеспечивая комплаенс и возможность перепарсить данные в будущем [Для чего нужна система SIEM и как её внедрить TADетали](https://www.tadviser.ru/index.php/%D0%A1%D1%82%D0%B0%D1%82%D1%8C%D1%8F:%D0%94%D0%BB%D1%8F_%D1%87%D0%B5%D0%B3%D0%BE_%D0%BD%D1%83%D0%B6%D0%BD%D0%B0_%D1%81%D0%B8%D1%81%D1%82%D0%B5%D0%BC%D0%B0_SIEM_%D0%B8_%D0%BA%D0%B0%D0%BA_%D0%B5%D1%91_%D0%B2%D0%BD%D0%B5%D0%B4%D1%80%D0%B8%D1%82%D1%8C_TAD%D0%B5%D1%82%D0%B0%D0%BB%D0%B8).

Для наглядности внутреннее устройство представим в виде схемы:

```text
[Источники] ──(syslog, agent, API)──▶ [Коллектор / Ingestion]
                                         │
                    ┌────────────────────┴────────────────────┐
                    ▼                                          ▼
          [Сырое хранилище]                         [Парсер / Regex, JSON]
          (оригинальный текст)                             │
                                               ┌───────────▼───────────┐
                                               │   Нормализатор (Mapper)│
                                               │  схема: src_ip, user...│
                                               └───────────┬───────────┘
                                                           ▼
                                                  [Обогащение: GeoIP, AD]
                                                           │
                                                           ▼
                                          [Индекс нормализованных полей]
                                                           │
                                                           ▼
                                             [Поиск, корреляция, алерты]
```

Важно отметить, что конкретные реализации SIEM могут объединять стадии парсинга и нормализации в одном компоненте (например, logstash pipeline, Splunk Heavy Forwarder), но логическое разделение сохраняется.

### Ключевые нормализованные поля

Практическая ценность нормализации раскрывается через стандартный набор полей, который позволяет аналитику писать единые запросы для всех источников. Типовой набор (на основе схемы Elastic Common Schema, Splunk CIM и обобщения источников) включает:

- **Сетевые**: `src_ip`, `dst_ip`, `src_port`, `dst_port`, `transport_protocol`, `network_zone`.
- **Идентификационные**: `user`, `src_user`, `target_user`, `user_id`, `session_id`.
- **Событийные**: `event_type`, `action`, `outcome` (success/failure), `event_category`, `event_id`.
- **Объектные**: `object`, `file_path`, `process_name`, `url`, `host`.
- **Временные**: `timestamp` (всегда в UTC), `duration`.
- **Контекстные**: `severity`, `log_source_type`, `vendor`, `product`.

Благодаря такому единообразию корреляционное правило «после 5 неудачных аутентификаций с одного IP следует успешная» можно записать на псевдоязыке SIEM, оперируя исключительно полями `user`, `src_ip`, `action="login"`, `outcome`, не заботясь о том, что события пришли от Windows и Linux. Это кардинально повышает переиспользуемость контента и скорость реакции, что подтверждается опытом интеграции различных SIEM [What’s going on? the power of normalization in cloud siem](https://www.sumologic.com/blog/whats-going-on-normalization-cloud-siem).

## Применение и работа с предметом

Для аналитика SOC L1 различие между сырыми событиями и нормализованными полями проявляется прежде всего в языке поисковых запросов и скорости расследования.

### Поиск по сырым событиям: возможности и ограничения

Когда новый источник данных только подключен, и парсер ещё не создан (или работает с ошибками), аналитик может выполнять поиск исключительно по сырому тексту. Такой поиск реализуется полнотекстовыми операторами, регулярными выражениями или wildcard-запросами. Например, в Splunk:

```spl
index=* "Failed password"
```

Запрос вернёт все события, содержащие указанную строку, независимо от источника. Это быстро и просто для ad-hoc поиска, но порождает множество проблем:

- **Шум**: в результат попадают события, не связанные с аутентификацией, но содержащие подстроку (например, сообщение приложения «Failed password validation for config file»).
- **Неоднозначность**: невозможно надёжно отфильтровать по IP-адресу, так как адрес может находиться в разных частях строки и иметь разное контекстное значение (источник или цель?).
- **Низкая производительность**: полнотекстовый поиск по огромным объёмам данных без индексации полей медленнее и ресурсоёмок.
- **Несовместимость с корреляцией**: написать правило, проверяющее логин пользователя с определённым IP, практически нереально без извлечения полей.

Таким образом, поиск по сырым данным — это инструмент «последней надежды» или способ первоначальной разведки, когда структура данных неизвестна, но для системной работы непригоден.

### Поиск с использованием нормализованных полей

При корректно настроенной нормализации запросы становятся точными и выразительными. Аналитик оперирует стандартизированными полями, что даёт следующие преимущества:

- **Фильтрация по смыслу, а не по тексту**: условие `src_ip="203.0.113.5"` вернёт события, где этот IP выступает именно как источник, независимо от формата исходного лога.
- **Кроссплатформенная корреляция**: единый запрос `event_type="authentication" AND outcome="failure"` объединяет данные и Windows, и Linux, и облачных провайдеров.
- **Агрегация и статистика**: легко подсчитать число неудачных входов по пользователям и IP: `stats count by user, src_ip`, что невозможно при работе с сырым текстом.
- **Интеграция с дэшбордами и алертами**: панели мониторинга строятся на нормализованных полях, алерты срабатывают при нарушении порогов по этим полям.
- **Скорость**: индексы по полям обеспечивают быстрый поиск даже на миллиардах записей.

Пример контрастного поиска в Splunk (иллюстративная схема запросов, конкретные имена полей зависят от модели данных SIEM):

*Поиск всех неудачных логинов (сырой текст):*
```spl
index=main sourcetype=linux_secure OR sourcetype=WinEventLog:Security "fail" OR "failure"
```
Такой запрос ненадёжен: может захватить события «logon failure» от Windows и «Failed password» от Linux, но также и строки «failure audit» в других контекстах.

*Поиск с использованием нормализованных полей (Splunk CIM):*
```spl
index=main tag=authentication action=failure
| stats count by src_ip, user, dest
```
В этом запросе `tag` и `action` — нормализованные поля, заполненные парсерами для каждого типа источника. Результат — точная выборка попыток аутентификации, завершившихся неудачей, с группировкой по отправителю, пользователю и целевому хосту.

### Типичные ошибки и подводные камни

- **Неполнота нормализации**: если парсер извлёк не все поля, часть информации остаётся только в сыром тексте. Аналитик должен уметь верифицировать, что нужные поля действительно заполнены, и при необходимости обращаться к `_raw`.
- **Различия в моделях данных**: разные SIEM-вендоры используют свои схемы (Splunk CIM, Elastic ECS, QRadar DSM, ArcSight CEF). Переход между системами требует изучения конкретных имён.
- **Задержки парсинга**: в высоконагруженных средах нормализация может отставать, и свежие события временно доступны только в сыром виде.
- **Ложное чувство полноты**: не следует полагать, что нормализованные поля полностью заменяют сырые. При детальном форензике часто требуется изучить оригинальную запись, чтобы увидеть нюансы (например, точный код ошибки, который не был извлечён как отдельное поле).

Поэтому зрелый SOC-аналитик комбинирует оба подхода: начинает с поиска по нормализованным полям для быстрого сужения области, а затем при необходимости переходит к сырым событиям конкретных записей для извлечения максимальной детализации.

### Практический инструментарий

Хотя конкретные синтаксисы зависят от SIEM, общая логика работы с нормализованными полями универсальна. Например, в Elastic Security (KQL) типичный запрос для выявления подозрительного запуска PowerShell с сетевым подключением может выглядеть так:

```kql
event.provider : "Microsoft-Windows-Sysmon" AND event.code : 1 AND process.name : "powershell.exe" AND network.direction : "outbound"
```
Здесь `process.name` — нормализованное поле из ECS, заполняемое агентом Winlogbeat. Аналогичный поиск по `_raw` потребовал бы сложного регулярного выражения с учётом всех вариаций формата Sysmon.

## Сквозной практический пример: расследование аномальной аутентификации

**Исходные условия**: SIEM-платформа Splunk Enterprise, куда поступают логи с контроллера домена Windows (Event Log) и серверов Linux (syslog). Аналитик SOC L1 получает уведомление от пользователя о странной активности: ему пришло оповещение о неудачных попытках входа на корпоративный портал с неизвестного IP. Необходимо быстро определить масштаб инцидента.

**Шаг 1: Поиск по сырому тексту для первичной оценки**
Аналитик начинает с широкого полнотекстового поиска, так как ещё не знает, какие именно системы затронуты.

```spl
index=main "failed" OR "failure" User=ivanov
```

Результат: тысячи событий, подавляющее большинство — не связанные с аутентификацией: сообщения о сбоях служб, ошибки синхронизации времени, логи аудита с текстом «failure audit». Среди них теряются действительно важные записи. Время на ручную фильтрацию неприемлемо.

**Шаг 2: Переход к нормализованным полям для сужения области**
Зная модель данных Splunk (CIM), аналитик уточняет запрос, используя поля, заполненные настроенными парсерами для источников Windows и Linux.

```spl
index=main tag=authentication user=ivanov action=failure
| table _time, src_ip, user, app, dest, vendor_product
```

Результат: всего 23 события за последний час, все от двух источников (Linux SSH и Windows Logon). Сразу видно, что попытки шли с IP-адреса `203.0.113.45`, для Windows целевым хостом выступает `SRV-APP01`. Запрос отработал мгновенно благодаря индексации полей.

**Шаг 3: Агрегация и выявление паттерна атаки**
Аналитик группирует данные, чтобы понять поведение:

```spl
index=main tag=authentication user=ivanov action=failure src_ip=203.0.113.45
| stats count, values(app) as services, values(dest) as targets by user, src_ip
| sort - count
```

Вывод (иллюстративная схема):
```
user     src_ip          count   services                     targets
ivanov   203.0.113.45    22      sshd, WinLogon, OWA          srv-lnx02, SRV-APP01, mail.contoso.com
```
Статистика показывает атаку типа password spraying: один IP перебирает пароль пользователя на нескольких сервисах. Нормализованные поля позволили объединить события от трёх разрозненных источников в единую картину без ручного сопоставления форматов.

**Шаг 4: Детальный анализ сырого события для уточнения деталей**
Для документирования инцидента аналитик извлекает одно сырое событие — например, запись Windows Event 4625 с того же IP.

```spl
index=main source="WinEventLog:Security" EventCode=4625 src_ip=203.0.113.45 user=ivanov
| table _raw
```

Результат содержит исходный XML-фрагмент с полным перечнем пакетов аутентификации, статусом `0xC000006A` (неверное имя пользователя или пароль) и именем рабочей станции `SRV-APP01`. Эта информация может не быть выделена в отдельные нормализованные поля, но важна для понимания, что атака была направлена именно на локальный вход, а не сетевой.

**Ожидаемый вывод**: сквозной пример демонстрирует, как аналитик SOC L1 комбинирует сырой и нормализованный поиск. Нормализованные поля позволяют в сжатые сроки связать события с разных платформ, выявить вектор атаки и оценить масштаб. Сырые события используются для финальной верификации и извлечения низкоуровневых деталей, которые могут отсутствовать в нормализованном представлении. Такой подход сокращает время реакции и повышает качество расследования.
