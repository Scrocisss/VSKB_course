# Дедупликация повторяющихся событий в SIEM

## 1. Контекст и базовые понятия: место дедупликации в жизненном цикле агрегации

Дедупликация событий — это процесс выявления и удаления повторяющихся записей в потоке данных безопасности, при котором оставляется только одна копия для каждой уникальной комбинации признаков. В SOC уровня L1 эта операция критически важна для снижения информационного шума: один реальный инцидент (например, многократная попытка подбора пароля) может породить тысячи идентичных записей, маскируя другие угрозы и увеличивая время реакции аналитика.

Место дедупликации в пайплайне SIEM определено необходимостью подготовить очищенный поток для корреляции. Как подчёркивается в обзоре внедрения SIEM ArcSight, эффективный сбор логов должен учитывать будущую нагрузку на коррелятор [Успешное внедрение SIEM. Часть 1 - Habr](https://habr.com/ru/articles/271745). Обычно последовательность такова: коллекторы собирают необработанные события, парсеры нормализуют их к единой схеме, затем **агрегационный слой** выполняет группировку и дедупликацию, а уже после этого очищенные уникальные события поступают на корреляцию и в хранилище.

В этой цепочке дедупликацию часто путают с тремя смежными операциями, однако их цели и поведение принципиально различаются. Сравнительная таблица фиксирует ключевые различия:

| Операция       | Цель                                                                  | Входной поток                     | Выходной поток                                             | Типичная точка применения                     |
|----------------|-----------------------------------------------------------------------|-----------------------------------|------------------------------------------------------------|-----------------------------------------------|
| Дедупликация   | Исключение дублирующихся записей                                      | Любые события, содержащие повторы | Поток, в котором каждый уникальный ключ представлен однократно     | После нормализации, непосредственно перед корреляцией |
| Агрегация      | Объединение множества однотипных событий в одно сводное (с подсчётом) | Набор событий с общим признаком   | Одно обогащённое событие, содержащее агрегаты (счёт, сумма) | После дедупликации, для построения метрик и дашбордов |
| Корреляция     | Выявление связей между событиями по правилам                          | События от разных источников      | Алерт или обогащённое событие, инициирующее инцидент       | После агрегации                                |
| Фильтрация     | Удаление событий, не соответствующих условиям                        | Весь поток                        | Подмножество событий, прошедших отбор                     | На ранних этапах (до нормализации)             |

Как видно, дедупликация не добавляет новой информации, а лишь устраняет избыточность. Агрегация же создаёт производные метрики. Корреляция, опираясь на уникальные события, строит инциденты, а фильтрация очищает поток от заранее известного «мусора». В реальной SIEM-инфраструктуре эти операции могут быть тесно переплетены: например, правило агрегации в ArcSight одновременно выполняет группировку с подсчётом и отбрасывает дубликаты внутри окна.

Для SOC L1 дедупликация решает три прикладные задачи:
- **Снижение количества алертов на экране аналитика** за счёт того, что каждая уникальная атака представлена одним событием.
- **Предотвращение ложных выводов при статистическом анализе** (например, без дедупликации число попыток входа будет завышено в разы).
- **Экономия лицензионного объёма хранилища и ресурсов коррелятора** — объём индексации сокращается пропорционально коэффициенту дублирования.

Понимание этих отличий необходимо для осознанного проектирования правил обработки на потоке.

## 2. Внутреннее устройство: методы идентификации дубликатов

Выбор способа поиска дубликатов диктуется характером источника логов, доступными полями события и требованиями к оперативности. Современные SIEM и платформы потоковой обработки предлагают несколько фундаментально разных подходов, каждый из которых обладает собственным механизмом, достоинствами и ограничениями.

**1. Дедупликация по уникальному идентификатору события**  
Если источник генерирует глобально уникальный идентификатор записи (например, `event_id` в Windows Event Log, `metadata.product_log_id` в Google Chronicle, хеш Syslog-сообщения), любое повторное появление того же ID означает точный дубликат, возникший при переотправке логов агентом или сборщиком. Метод реализуется простым сравнением ключа: при поступлении события проверяется, не было ли такого ID ранее. Для этого состояние (множество увиденных идентификаторов) должно храниться некоторое время. В потоковой обработке это реализуется через оконные операторы с состоянием, как показано в примере IBM Event Automation, где Flink SQL использует `ROW_NUMBER()` с секционированием по `event_id` [Deduplicating repeated events - IBM Event Automation](https://ibm.github.io/event-automation/tutorials/event-processing-examples/example-05). Преимущества — высокая точность и минимальное число ложных срабатываний. Недостаток — полная зависимость от источника: если ID не гарантирует уникальности (например, переиспользуется при перезагрузке устройства) или вовсе отсутствует, метод не работает.

**2. Дедупликация по комбинации ключевых полей**  
На практике уникальный ID часто недоступен или ненадёжен, поэтому аналитик определяет собственный композитный ключ — набор полей, комбинация которых должна однозначно характеризовать событие. Типичный ключ для IDS-алерта: `signature` + `source_ip` + `destination_ip` + `destination_port`. Совпадение всех полей считается признаком дубликата. Этот подход требует тщательного подбора полей: включение временной метки (с точностью до секунды) сделает ключ практически уникальным и дедупликация не сработает; наоборот, слишком грубый ключ (только IP) может объединить разнородные инциденты. Метод лежит в основе настройки агрегационных правил в ArcSight — администратор задаёт поля сегментации и временное окно, в пределах которого повторные события отбрасываются.

**3. Дедупликация по хешу контента**  
Вычисление криптографического хеша (MD5, SHA1, SHA256) от полной нормализованной записи или её значимых полей позволяет точно идентифицировать бинарно идентичные события. Например, Logstash-фильтр `fingerprint` вычисляет хеш и сохраняет его в поле; затем с помощью внешнего хранилища (Redis) можно отбрасывать события с уже встреченным хешем. Преимущество — абсолютная точность; ограничение — любое, даже незначительное различие (добавочный пробел, миллисекунда в `_time`) даёт другой хеш, поэтому метод требует жёсткой нормализации до вычисления хеша.

**4. Дедупликация с временным окном (stateful)**  
Наиболее распространённый в SIEM подход, сочетающий ключ и интервал. Событие считается дубликатом, если в течение заданного окна (например, 5 минут) уже поступало событие с таким же ключом. Реализация требует хранения состояния: для каждого уникального ключа запоминается время последнего появления. В Splunk типичная конструкция использует `streamstats` с окном, в ArcSight — rule-based aggregation с duration. В платформах потоковой обработки (Flink) применяются оконные функции с водяными знаками: для ключа хранится временная метка последнего события, и все последующие с тем же ключом отбрасываются до истечения окна. Состояние автоматически очищается по мере продвижения времени события, предотвращая неконтролируемый рост памяти. Этот метод гибко настраивается под семантику источника: если атака может длиться часами, окно можно расширить до 30 минут; для быстротекущих событий — сократить до 1 минуты.

**5. Потоковая ROW_NUMBER-дедупликация**  
В SQL-ориентированных потоковых движках (Flink SQL, ksqlDB) стандартный приём — использование аналитической функции `ROW_NUMBER() OVER (PARTITION BY key ORDER BY event_time)`, которая нумерует события в пределах окна для каждого ключа по времени. Затем выбираются только строки с номером 1. Этот подход эквивалентен предыдущему, но выражается декларативно и легко встраивается в конвейер обработки. В IBM Event Automation специальный узел Deduplicate internally генерирует подобный запрос, который под капотом управляет состоянием и водяными знаками, освобождая разработчика от низкоуровневых деталей [Deduplicating repeated events - IBM Event Automation](https://ibm.github.io/event-automation/tutorials/event-processing-examples/example-05).

Сравнительная таблица обобщает ключевые параметры методов:

| Метод                             | Критерий дубликата                       | Преимущества                              | Ограничения                                  | Пример реализации                   |
|-----------------------------------|------------------------------------------|-------------------------------------------|----------------------------------------------|-------------------------------------|
| Уникальный ID                     | Совпадение `event_id`                   | Высокая точность, простота                | Зависимость от источника; ID может быть не уникален | Chronicle pivot table [Chronicle](https://security.googlecloudcommunity.com/google-security-operations-2/how-to-find-duplicate-events-ingestion-into-chronicle-978) |
| Ключевые поля                     | Совпадение набора полей                  | Гибкость, не требует ID                   | Трудоёмкость подбора полей; возможны коллизии | ArcSight rule aggregation            |
| Хеш контента                      | `hash(normalized_event) == previous`     | Точное соответствие                       | Требует полной нормализации; чувствителен к вариациям | Logstash fingerprint + Redis         |
| Временное окно + ключ             | Совпадение ключа в пределах окна         | Баланс идемпотентности и актуальности     | Необходимо хранить состояние; выбор окна критичен | Splunk `streamstats`                 |
| Потоковая ROW_NUMBER              | Оконная нумерация по времени             | Высокая производительность, декларативность | Требует потокового движка, настройки водяных знаков | IBM Event Automation, Flink SQL     |

Выбор подхода должен опираться на природу данных. Например, для Windows Event Log, где каждое событие имеет `EventRecordID`, достаточно дедупликации по ID. Для Syslog-сообщений без надёжного идентификатора логично использовать ключевые поля с временным окном. В любом случае критически важна предварительная нормализация (приведение временных меток, имён хостов и IP к каноническому виду), иначе даже точный ключ будет различаться.

## 3. Практическое применение: настройка и инструменты

Настройка дедупликации в реальном SOC L1 обычно выполняется инженером SIEM и предоставляется аналитикам в виде готовых поисковых макросов, правил корреляции или потоковых конвейеров. Рассмотрим несколько типовых реализаций, охватывающих распространённые платформы.

### 3.1. Splunk: управление на лету

Для оперативного поиска дубликатов аналитик использует команду `dedup`:

```splunk
index=windows source="WinEventLog:Security" EventCode=4625
| dedup Account_Name, IpAddress
| table _time, Account_Name, IpAddress
```

Это оставляет только первую попытку неудачного входа для каждой комбинации учётной записи и IP-адреса за весь период поиска. Однако в сменной работе L1 часто требуется дедупликация с плавающим окном, чтобы не потерять повторение инцидента спустя час. Здесь помогает `streamstats`:

```splunk
index=windows source="WinEventLog:Security" EventCode=4625
| streamstats current=f window=10m count as dup_count by Account_Name, IpAddress
| where dup_count == 0
```

Параметр `current=f` исключает текущее событие из подсчёта, а `window=10m` задаёт скользящее окно в 10 минут. Если за этот период комбинация встречена впервые, она проходит фильтр. Этот запрос часто оформляется в виде макроса `dedup_login_fail(10m)` и встраивается в панели оперативного мониторинга.

Дополнительно Splunk позволяет создавать summary-индексы с автоматической дедупликацией на этапе индексации с помощью `collect` с параметром `run-command="dedup"`, однако это требует осторожности, так как необратимо удаляет дубликаты из быстрого хранилища.

### 3.2. Потоковая обработка: Flink SQL и IBM Event Automation

В платформах, ориентированных на потоковую обработку, дедупликация встраивается в непрерывный конвейер. Пример из туториала IBM Event Automation показывает запрос, генерируемый визуальным узлом Deduplicate [Deduplicating repeated events - IBM Event Automation](https://ibm.github.io/event-automation/tutorials/event-processing-examples/example-05). Аналогичный SQL для Flink выглядит так:

```sql
INSERT INTO stock_movement_unique
SELECT stock_id, movement_time, quantity
FROM (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY stock_id
            ORDER BY movement_time
        ) AS rn
    FROM stock_movement
)
WHERE rn = 1;
```

Здесь секционирование `PARTITION BY stock_id` задаёт ключ дедупликации, а `ORDER BY movement_time` гарантирует, что сохраняется самое раннее событие. Состояние поддерживается внутренним механизмом Flink; по мере поступления новых событий и продвижения водяного знака устаревшие ключи автоматически удаляются. Такая реализация подходит для крупных SOC, обрабатывающих миллионы событий в секунду.

### 3.3. Ретроспективный анализ дубликатов в Google Chronicle

В Chronicle нет встроенной автоматической дедупликации при приёме, но администратор может выявить дубликаты постфактум. В обсуждении на форуме описывается подход с использованием pivot table: задаётся поиск, например, `metadata.log_type = "CS_EDR"`, затем в режиме pivot группируется по полю с уникальным идентификатором (`metadata.product_log_id`) и подсчитывается количество [How to find duplicate events ingestion into chronicle | Community](https://security.googlecloudcommunity.com/google-security-operations-2/how-to-find-duplicate-events-ingestion-into-chronicle-978). Экспорт в CSV и удаление записей с `count = 1` позволяет оценить масштаб дублирования и скорректировать конфигурацию коллекторов. Этот метод важен для аудита качества данных, хотя и не даёт оперативной дедупликации.

### 3.4. Типичные ошибки и подводные камни

- **Слишком агрессивное окно или ключ.** Если окно установлено на 1 час, а легитимная атака повторяется каждые 30 минут, она будет воспринята как дубликат и потеряна. Необходимо анализировать периодичность событий источника.
- **Игнорирование нормализации.** В Splunk поле `src_ip` может содержать разные представления (`10.0.0.1`, `::ffff:10.0.0.1`, `10.0.0.1/32`), и без приведения к единому формату дедупликация не сработает. Всегда применяйте `eval` и `replace` перед `dedup` или `streamstats`.
- **Расход памяти при неограниченном состоянии.** Если дедупликация ведётся без временного окна (например, `dedup` без ограничений), Splunk хранит список всех увиденных ключей в памяти результатов поиска, что при большой выборке может вызвать ошибку. Аналогично в Flink следует задавать `idle state TTL`, чтобы избежать переполнения.
- **Дубликаты с разным временем.** Часто агенты переотправляют логи с исходной временной меткой, которая дублируется, но время приёма отличается. Если ключ не включает исходное время, такие события будут дедуплицированы. Если же время входит в ключ, дубликаты не найдутся. Решение — использовать в ключе только значимые атрибуты инцидента, а при дедупликации учитывать оригинальную метку времени через `ORDER BY`.

Понимание этих нюансов отличает работу квалифицированного SOC L1 от формального выполнения инструкций.

## 4. Сквозной практический пример: очистка дублирующихся алертов IDS на рабочем месте аналитика

**Исходные условия.** SIEM на базе Splunk индексирует логи сенсоров Snort. Аналитик L1 заступает на смену и видит, что на панели мониторинга количество алертов за последний час в 10 раз выше обычного. Быстрый осмотр показывает, что множество записей имеют идентичные сигнатуры и IP-адреса. Требуется оперативно очистить поток, чтобы оценить реальную картину угроз, не дожидаясь инженера.

### Шаг 1. Количественная оценка дублирования

Аналитик выполняет запрос, группирующий алерты по ключевым полям:

```splunk
index=ids sourcetype=snort alert=1
| stats count by signature, src_ip, dest_ip
| sort - count
```

Ожидаемый вывод (иллюстративная схема, значения показывают масштаб):

```
signature                                     src_ip         dest_ip        count
ET TROJAN ABUSE.CH SSL Blacklist...           10.10.5.3      93.184.216.34  127
ET TROJAN ABUSE.CH SSL Blacklist...           10.10.5.3      198.51.100.12  95
ET SCAN Potential SSH Scan                    10.10.8.7      10.10.9.1      84
...
```

Видно, что одни и те же пары IP дублируются более ста раз, что нехарактерно для точечных алертов.

### Шаг 2. Просмотр конкретных дубликатов

Для детального изучения выбирается пара с максимальным количеством:

```splunk
index=ids sourcetype=snort src_ip="10.10.5.3" dest_ip="93.184.216.34" "SSL Blacklist" alert=1
| head 5
| table _time, signature, src_ip, dest_ip
```

Ожидаемый вывод:

```
_time                   signature                                 src_ip       dest_ip
2025-03-20 08:12:01     ET TROJAN ABUSE.CH SSL Blacklist...       10.10.5.3   93.184.216.34
2025-03-20 08:12:01     ET TROJAN ABUSE.CH SSL Blacklist...       10.10.5.3   93.184.216.34
2025-03-20 08:12:01     ET TROJAN ABUSE.CH SSL Blacklist...       10.10.5.3   93.184.216.34
```

Временные метки идентичны до секунды, содержимое полностью совпадает. Подтверждён факт дублирования приёмником логов.

### Шаг 3. Применение дедупликации с плавающим окном

Аналитик применяет запрос, оставляющий только первое событие для каждой комбинации в 5-минутном окне:

```splunk
index=ids sourcetype=snort alert=1
| streamstats current=f window=5m count as dup_count by signature, src_ip, dest_ip
| where dup_count == 0
| table _time, signature, src_ip, dest_ip
```

`streamstats` вычисляет, сколько раз данная комбинация уже встречалась за последние 5 минут, и фильтр пропускает только события без предшественников. Ожидаемый результат:

```
_time                   signature                                 src_ip       dest_ip
2025-03-20 08:12:01     ET TROJAN ABUSE.CH SSL Blacklist...       10.10.5.3   93.184.216.34
2025-03-20 08:12:39     ET TROJAN ABUSE.CH SSL Blacklist...       10.10.5.3   198.51.100.12
2025-03-20 08:15:02     ET SCAN Potential SSH Scan                10.10.8.7   10.10.9.1
```

Теперь каждая угроза по конкретному адресату отображается однократно, хотя реальный инцидент мог продолжаться дольше (следующая попытка через 5 минут будет записана как новая уникальная запись, что обоснованно).

### Шаг 4. Верификация эффекта на панели

Чтобы убедиться в действенности, аналитик строит простой дашборд, сравнивающий сырое количество алертов и количество после дедупликации:

```splunk
index=ids sourcetype=snort alert=1
| eval raw = 1
| streamstats current=f window=5m count as dup by signature, src_ip, dest_ip
| eval dedup = if(dup==0,1,0)
| stats sum(raw) as "Raw alerts", sum(dedup) as "Deduplicated alerts"
```

Ожидаемый вывод:

```
Raw alerts    Deduplicated alerts
347           12
```

Сокращение на 96.5 % подтверждает, что подавляющая часть потока была паразитным дублированием. Аналитик может теперь сосредоточиться на оставшихся 12 уникальных событиях, в каждом из которых действительно требуется разбор.

**Итог примера.** Сквозной кейс демонстрирует, как L1-аналитик с помощью трёх последовательных запросов выявляет, анализирует и оперативно устраняет дубликаты, возвращая информативность рабочей панели без изменения конфигурации источников. Это стандартная практика быстрого реагирования на проблемы качества данных.
