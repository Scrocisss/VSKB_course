# Топ источников алертов (хосты, пользователи, IP)

## 1. Хосты как источник алертов

Хост (рабочая станция, сервер, контроллер домена, виртуальная машина) — минимальная значимая сущность в инфраструктуре, на которой исполняются процессы, хранятся данные и формируются события безопасности. В SIEM-системе хост является первичным контекстом группировки алертов, поскольку подавляющее большинство индикаторов компрометации (IoC) привязывается к конкретной машине — будь то срабатывание антивируса, аномалия процесса или подозрительный сетевой трафик, ассоциированный с локальным IP и MAC-адресом.

**Зачем топ источников по хостам.**  
Аналитик SOC L1 ежедневно сталкивается с сотнями и тысячами алертов; без агрегации по хосту невозможно быстро выделить машины, требующие немедленного внимания. Дашборд, показывающий «Top Hosts by Alert Count» или «Hosts with Most Critical Alerts», позволяет за секунды обнаружить:
- заражённую рабочую станцию, лавинообразно генерирующую запросы к C2-серверам;
- сервер, на котором массово блокируются учётные записи (атака подбора паролей);
- хост-песочницу, которая превратилась в маяк вредоносной активности после горизонтального перемещения злоумышленника.

Таким образом, группировка по хостам реализует первый шаг triage: ранжирование инцидентов по критичности и потенциальному объёму ущерба.

**Источники событий на хосте.**  
Алерты по хостам поступают в SIEM из нескольких типовых источников, каждый из которых предоставляет свой срез телеметрии:

| Источник                                | Пример продукта/технологии      | Ключевые поля события                                                                          | Типичные порождаемые алерты                                            |
|-----------------------------------------|----------------------------------|------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------|
| Журналы безопасности ОС                | Windows Security Log, Linux auditd | Event ID, Logon Type, Process ID, Object Name                                                  | Неудачные входы (4625), создание процесса (4688), очистка журнала (1102) |
| Sysmon / EDR-агент                     | Microsoft Sysmon, CrowdStrike, SentinelOne | Image, CommandLine, ParentProcessId, NetworkConnection, Hashes                                | Подозрительный запуск PowerShell с обфускацией, DNS-запросы к нелегитимным доменам, запись в автозагрузку |
| Антивирус / анти-malware               | Windows Defender, McAfee, Kaspersky | Threat Name, File Path, Action Taken (Blocked/Quarantined), Severity                           | Обнаружение вредоносного ПО на хосте, потенциально нежелательной программы (PUA) |
| Средства контроля приложений (AppLocker/WDAC) | AppLocker, Windows Defender Application Control | PolicyName, FilePath, RuleId                                                                   | Запуск неразрешённого исполняемого файла, обход политик ограниченного доступа |
| Агенты мониторинга целостности файлов  | Tripwire, OSSEC, Wazuh            | File Path, Hash, Change Type (Modified/Created/Deleted)                                        | Изменение системного конфигурационного файла, подмена библиотеки DLL     |
| Журналы DNS-клиента                    | Windows DNS Client Log, systemd-resolved | QueryName, QueryType, ProcessId                                                               | Запросы к DGA-доменам, разрешение имён, характерных для C2-инфраструктуры |
| Брандмауэр хоста                       | Windows Firewall, iptables/nftables | Direction, Remote IP, Port, Application Path                                                  | Исходящее соединение на порт, нехарактерный для данного приложения       |

Каждый из источников способен производить как чистые информационные события, так и алерты — после обработки корреляционными правилами SIEM или при превышении пороговых значений (например, более пяти неудачных входов с одного хоста за минуту). В результате на уровне SIEM алерт, привязанный к хосту, всегда содержит поле `host` (или `ComputerName`, `agent.hostname`) и часто обогащается тегами типа `asset_criticality` или `environment`.

**Внутреннее устройство группировки по хосту на дашбордах.**  
Типовой дашборд «Host Alert Activity» строится на агрегации по полю, идентифицирующему хост, и обычно включает следующие виджеты:
- **Таблица Top N хостов по количеству алертов** за выбранный период (часто топ-10 или топ-20). Визуально дополняется цветовой шкалой по критичности: хосты с преобладанием high-алертов подсвечиваются красным.
- **Временной график числа алертов по топ-хосту** — тренд, позволяющий отличить короткий всплеск (возможно, ложное срабатывание при развёртывании софта) от устойчивого роста (инфекция).
- **Распределение типов алертов на одном хосте** (круговая или столбчатая диаграмма), показывающее, доминируют ли сетевые аномалии, срабатывания HIPS или проблемы с аутентификацией.
- **Список последних алертов по хосту** с деталями (сигнатура, время, источник).

На практике для построения такого дашборда в Splunk используется SPL-запрос, агрегирующий индексы безопасности, например:
```splunk
index=sec_events sourcetype=wineventlog OR sourcetype=sysmon
| bin span=1h _time
| stats count by host, _time
| timechart limit=10 useother=f count by host
```
Полученный временной ряд визуализируется линейным графиком. Чтобы построить простую таблицу топ-10 хостов по числу алертов за последние 24 часа, достаточно:
```splunk
index=sec_events earliest=-24h
| stats count by host
| sort -count
| head 10
```
Подобные конструкции не зависят от конкретной реализации SIEM и адаптируются для Elasticsearch (язык Lucene/DSL) или QRadar (AQL).

**Типичные ложные срабатывания и нюансы.**  
Хост с максимальным количеством алертов не всегда является скомпрометированным. Частые ложноположительные ситуации:
- **Сервер управления обновлениями (WSUS, SCCM)** генерирует множество событий установки ПО, которые корреляционные правила могут принять за несанкционированное изменение файлов.
- **Сканер уязвимостей (Nessus, OpenVAS)** при активном сканировании вызывает срабатывание IDS/IPS-сенсоров, и алерты привязываются к IP сканера, который может быть одной и той же машиной.
- **Служебная учётная запись**, запрограммированная на частые неудачные попытки входа (например, приложение с неверным паролем), создаёт пик алертов на хосте назначения.
Поэтому аналитик L1 обязан не просто смотреть на цифры, а быстро оценивать репутацию хоста (этот IP — сервер или рабочая станция?), исторические тренды и наличие в алертах признаков компрометации.

## 2. Пользователи как источник алертов

Учётная запись пользователя — это контекст, связывающий алерты с конкретным субъектом: сотрудником, администратором или службой. В отличие от хоста, пользователь может перемещаться между машинами, использовать несколько способов аутентификации и оставлять следы одновременно в локальных журналах, в облачных сервисах и в VPN-концентраторах. Поэтому группировка алертов по пользователю даёт принципиально иной «разрез» расследования: она выявляет скомпрометированные учётные записи и действия, которые могли быть скрыты за счёт смены рабочей станции.

**Роль топа пользователей в операционной деятельности SOC.**  
Топ пользователей по алертам отвечает на вопросы:
- Какие учётные записи подвергаются атакам перебором паролей?
- Какие пользователи демонстрируют аномальное поведение (вход в нерабочее время, с необычных хостов, массовый доступ к ресурсам)?
- Не засветилась ли привилегированная учётная запись в подозрительных событиях (запуск нехарактерных утилит, создание новых учётных записей)?
- Нет ли признаков движения злоумышленника внутри сети (Lateral Movement), когда один и тот же пользователь порождает алерты на множестве хостов?

Дашборд «User Risk» или «Top Users by Alert Volume» — обязательный элемент утреннего обзора для L1-аналитика наряду с хостовым топом.

**Источники событий, привязанных к пользователю.**  
Поле `user` (или `UserName`, `SubjectUserName`, `TargetUserName`) извлекается SIEM из обширного набора журналов:

| Источник                                              | Пример событий / Event ID                             | Порождаемые алерты по пользователю                         |
|-------------------------------------------------------|-------------------------------------------------------|------------------------------------------------------------|
| Журналы аутентификации ОС (Windows Security, Linux auth.log) | 4624 (успешный вход), 4625 (неудачный), 4776 (NTLM-аутентификация) | Брутфорс-атака, вход с необычного хоста, Pass-the-Hash (при 4624 с LogonType=9) |
| Журналы контроллера домена (AD)                       | 4720 (создание пользователя), 4738 (изменение учётной записи), 4728 (добавление в группу) | Несанкционированное создание учётной записи, эскалация привилегий |
| VPN-шлюзы и облачные провайдеры аутентификации        | Логи Cisco ASA, Azure AD Sign-in Logs, Okta            | Невозможное путешествие (вход из двух географически удалённых точек за короткое время), вход с анонимных IP |
| Почтовые серверы (Exchange, O365)                     | События доступа к почтовому ящику                       | Массовый доступ к чужой почте, пересылка правил, свидетельствующая о компрометации ящика |
| Системы DLP и контроля USB                             | События копирования на съёмные носители                | Инсайдерская активность: подозрительно большой объём данных, скопированный пользователем |
| EDR-агенты                                            | Запись события с полем User (процесс, запущенный от определённой учётной записи) | Запуск вредоносного ПО от непривилегированной учётной записи, нехарактерной для данного хоста |

Важно понимать, что в AD-среде учётная запись может быть «пользовательской» (User) или «компьютерной» (Computer account, заканчивающейся на `$`). В алертах обычно фигурируют первые; компьютерные учётные записи тоже могут стать объектом атаки (Silver Ticket), но на уровне L1 они чаще фильтруются.

**Типовая структура дашборда «Топ пользователей».**  
Дашборд для L1 содержит агрегации, помогающие быстро найти «кричащие» учётные записи:
- **Таблица «Top Users by Failed Logon Count»** — кандидаты на брутфорс; строки отсортированы по убыванию числа событий 4625 или аналогичных.
- **График «Failed Logon Attempts per User over Time»** — показывает, нарастает ли частота попыток (характерно для автоматизированных атак).
- **Виджет «Users with Multiple Logon Types»** — выявляет учётные записи, которые использовали интерактивный вход (тип 2) и сетевой вход (тип 3) с одного IP, что может быть признаком Pass-the-Ticket.
- **Географическая карта входов пользователя** — если SIEM обогащает IP геоданными, дашборд показывает разлёт локаций для одного пользователя (индикатор компрометации, если только пользователь не действительно перемещается).

Пример SPL-запроса для поиска пользователей с наибольшим числом неудачных входов и построения таблицы:
```splunk
index=windows sourcetype="WinEventLog:Security" EventCode=4625
| stats count by User
| sort -count
| head 20
```
Для визуализации временного ряда можно использовать:
```splunk
index=windows EventCode=4625
| timechart span=1h count by User limit=5 useother=f
```
Аналитик смотрит на результат и выделяет учётные записи, у которых count резко превышает baseline. Далее можно «провалиться»: кликнуть на пользователя и построить список исходных IP-адресов, с которых шли неудачные попытки.

**Учёт контекста привилегий.**  
При оценке топа пользователей необходимо разделять обычных пользователей и привилегированных. Алерты на учётной записи администратора домена критичны даже в малом количестве. В правильно настроенном SIEM каждый алерт может наследовать метку `privileged`, если пользователь входит в группу Domain Admins, и тогда дашборд фильтрует только такие события, строя отдельную таблицу «Top Privileged Users with Alerts».

**Ловушки при интерпретации.**  
- События 4625 с кодом ошибки 0xC0000064 (пользователь не существует) говорят о переборе по словарю, но имя пользователя не существует — это не скомпрометированная учётка, а разведка. Такой алерт привязывается к подставной записи, и не следует бежать отключать реального пользователя.
- Если пользователь `SYSTEM` или `LOCAL SERVICE` попадает в топ алертов, нужно проверить, не идёт ли речь об аномалии на уровне процессов, а не о компрометации самой учётной записи (она высокопривилегированная и не может быть непосредственно атакована таким образом).
- В крупных средах с доверенными доменами имя пользователя должно содержать домен (DOMAIN\Username), иначе топ может некорректно агрегировать одного и того же человека.

## 3. IP-адреса как источник алертов

IP-адрес — это транспортный идентификатор, фигурирующий практически в каждой сетевой сессии. В SIEM-алертах IP играет роль либо источника (`src_ip`), либо назначения (`dest_ip`). Группировка по IP позволяет аналитику быстро выделить внешние узлы, атакующие периметр, скомпрометированные внутренние хосты, пытающиеся распространить заразу, и выявить командные центры ботнетов. В отличие от хостового и пользовательского топа, IP-топ почти всегда коррелирует с Threat Intelligence, географическими данными и списками репутации.

**Двойственная природа IP: внешние против внутренних.**  
Топ источников алертов по IP обычно разбивается на два отдельных дашборда:

1. **Top External Source IPs** — показывает внешние адреса, с которых приходит наибольшее количество алертов (сканирования, попытки эксплуатации, аномальный трафик). Высокая позиция в этом топе — кандидат на немедленное помещение в чёрный список.
2. **Top Internal IPs** — выделяет внутренние узлы, выступающие источниками вредоносного трафика или иных алертов; по сути, это проекция топа хостов, но ключом является IP, что позволяет увидеть активность устройств без агента (IoT, принтеры, IP-камеры), которые не отправляют журналы, но фигурируют в NetFlow или IDS-алертах.

Третья категория — **Destination IP** (куда обращается внутренний хост) — часто выводится отдельным виджетом «Top Destination IPs for Outbound Alerts», что помогает идентифицировать C2-серверы.

**Источники событий, содержащих IP.**  
Практически все сетевые устройства и системы обнаружения вторжений передают IP-адреса:

| Источник                                          | Пример лога / протокол                       | Поля IP                             | Тип алерта с привязкой к IP                       |
|---------------------------------------------------|----------------------------------------------|-------------------------------------|---------------------------------------------------|
| Межсетевые экраны (NGFW)                          | Palo Alto, FortiGate, Check Point            | src_ip, dst_ip, src_port, dst_port  | Трафик на известный вредоносный IP, подозрительный объём данных |
| IDS/IPS (Signature-based)                         | Suricata, Snort                              | src_ip, dst_ip, signature_id        | Exploit-попытка с внешнего IP, обратный HTTP-shell на нестандартный порт |
| Прокси-серверы                                    | Squid, Blue Coat                             | client_ip, url, category            | Обращение к фишинговому URL, загрузка вредоносного файла |
| NetFlow / IPFIX                                   | NetFlow v5/v9, sFlow                         | src_ip, dst_ip, bytes, packets      | DDoS-атака, горизонтальное сканирование портов       |
| Endpoint Detection (EDR)                          | Sysmon Event ID 3 (Network connection)       | SourceIp, DestinationIp, Image      | Подозрительное исходящее соединение от процесса    |
| Threat Intelligence Feeds / TI-платформы          | MISP, Anomali                                 | ip, threat_type, confidence         | Прямое совпадение src_ip с индикатором компрометации (IoC) |

Сложность работы с IP заключается в динамической природе адресов: внешний вредоносный IP сегодня принадлежит домашнему пользователю, завтра — облачному хосту; один IP может быть использован NAT для тысяч внутренних устройств. Поэтому «топ по IP» должен обязательно обогащаться контекстом: геолокация, принадлежность к хостинг-провайдеру, репутация по VirusTotal или AbuseIPDB.

**Построение дашбордов IP-алертов.**  
Для L1-аналитика целесообразно иметь следующие виджеты:

- **Таблица «Top 10 Source IP by Number of Alerts»** с колонками: IP, количество алертов, страна, провайдер, репутация (если доступна). Это прямой аналог хостового топа, но для внешних связей.
- **Географическая карта источников алертов** — визуализирует распределение атакующих IP по миру, позволяет мгновенно заметить аномалию (например, все атаки из одной страны, где нет филиалов).
- **График «Connections to Suspicious IPs over Time»** — тренд обращений к IP с плохой репутацией; рост означает активную C2-активность внутри сети.
- **Таблица «Top Internal IPs by Outbound Alerts»** — помогает найти заражённые хосты, у которых нет агента, но есть аномальный исходящий трафик.

Пример Lucene-запроса для Elasticsearch/Kibana, который строит топ внешних IP-источников алертов:
```json
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        {"term": { "alert.severity": "high" }},
        {"term": { "network.direction": "inbound" }},
        {"range": { "@timestamp": { "gte": "now-24h" } }}
      ]
    }
  },
  "aggs": {
    "top_src_ips": {
      "terms": {
        "field": "source.ip",
        "size": 10,
        "order": { "_count": "desc" }
      }
    }
  }
}
```
Визуализация в Kibana строится на основе этой агрегации и отображается таблицей.

Для Splunk аналогично:
```splunk
index=network sourcetype=fw OR sourcetype=ids severity=high earliest=-24h
| stats count by src_ip
| sort -count
| head 10
```
При интеграции с TI-платформой запрос дополняется подзапросом `lookup threat_intel src_ip AS src_ip OUTPUT threat_category`, что добавляет колонку с категорией угрозы.

**Пороговые значения и аномалии.**  
Аналитик L1 должен учитывать, что один внешний IP может генерировать множество алертов просто потому, что проводит широкомасштабное сканирование (что само по себе менее критично, чем целевая атака). Поэтому полезно иметь виджет «IPs with Diverse Alert Signatures» — IP, для которых число уникальных сигнатур превышает порог. Это отделяет массовые сканеры от целенаправленных действий, где применяется несколько разных техник.

**Проблема NAT и приватных IP.**  
В логах от межсетевого экрана часто фигурирует публичный IP компании (если трафик выходит через централизованный шлюз). В таких случаях `src_ip` будет одинаковым для тысяч внутренних хостов, и группировка по нему бесполезна. Поэтому современные SIEM (например, Splunk, QRadar) требуют предварительной обработки: извлечения из логов поля `original_client_ip` (или X-Forwarded-For), либо же данные о внутреннем источнике должны приходить из EDR или прокси-логов, где IP рабочий станции доступен до NAT. Дашборд должен опираться именно на это поле, иначе топ внутренних IP превратится в единственную запись с IP шлюза.

**Верификация топа по IP.**  
После выделения подозрительного IP аналитик L1 обязан быстро проверить его репутацию через безопасные каналы (внутренний threat intelligence portal, VirusTotal API). Автоматизированные плейбуки SOAR могут выполнять это за него, но при отсутствии автоматизации L1 вручную отправляет запрос:
```bash
curl -X GET "https://www.virustotal.com/api/v3/ip_addresses/203.0.113.45" -H "x-apikey: <API_KEY>"
```
Ответ содержит счётчики обнаружений и категории, что прямо влияет на решение о блокировке.

## Сквозной практический пример: Анализ алертов с нескольких источников

**Исходные условия.**  
Аналитик SOC L1 в понедельник утром открывает сводный дашборд SIEM. Среда: Splunk с индексами `windows`, `network`, `sysmon`. В дашборд встроены три панели: «Top Hosts by Alert Count (24h)», «Top Users by Failed Logons (24h)» и «Top External Source IPs (24h)». Аналитик должен провести triage и, при необходимости, инициировать эскалацию. Имена хостов, пользователей и IP-адреса в примере условны; поля и структуры событий соответствуют реальным форматам.

**Шаг 1: Выявление аномального хоста.**  
На панели «Top Hosts» первое место занимает хост `SRV-DB01` с 287 алертами, тогда как у следующего хоста лишь 23. Большинство алертов относятся к категории «suspicious_outbound». Аналитик детализирует запросом, чтобы увидеть тип алертов только для этого хоста:

```splunk
index=sec_events host="SRV-DB01" earliest=-24h
| stats count by alert_type
| sort -count
```
Результат (иллюстративная схема):
```
alert_type                      count
--------------------------------------
suspicious_outbound_connection      210
exploit_attempt                      42
malware_detected                     25
credential_dumping                    7
unknown_alert                         3
```
Вывод: хост явно вовлечён в инцидент, так как доминирует исходящий трафик к подозрительным IP и есть попытки эксплуатации. Аналитик принимает решение расследовать немедленно.

**Шаг 2: Детализация исходящих соединений.**  
Чтобы понять, с какими внешними адресами взаимодействует хост и какой процесс инициирует соединения, выполняется SPL-запрос, использующий данные сетевых алертов и Sysmon (Event ID 3):

```splunk
index=network OR index=sysmon host="SRV-DB01" alert_type="suspicious_outbound_connection"
| table _time, src_ip, dest_ip, dest_port, process_name, user
| sort -_time
| head 10
```
Фрагмент вывода (иллюстративная схема):
```
_time               src_ip          dest_ip         dest_port   process_name        user
2025-04-05 08:12:04 10.0.5.45       198.51.100.22   443         powershell.exe      CORP\svc_backup
2025-04-05 08:11:52 10.0.5.45       203.0.113.77    8080        powershell.exe      CORP\svc_backup
2025-04-05 08:11:30 10.0.5.45       198.51.100.22   443         powershell.exe      CORP\svc_backup
...
```
Все подозрительные соединения инициированы процессом `powershell.exe` от имени служебной учётной записи `CORP\svc_backup`. Dest IP-адреса не входят в белые списки и, согласно визуальной проверке через внутренний TI-портал, принадлежат подсетям известных VPS-провайдеров.

**Шаг 3: Анализ учётной записи пользователя.**  
Аналитик переключается на панель «Top Users» и не видит `svc_backup` в топе, потому что количество алертов аутентификации у неё невелико. Однако он выполняет целевой запрос по этому пользователю за последние 24 часа:

```splunk
index=windows user="CORP\\svc_backup" earliest=-24h
| stats count by EventCode, host
```
Результат:
```
EventCode   host                count
---------------------------------------
4625        SRV-DB01            5
4624        SRV-DB01            3
4624        DESKTOP-XZ44        1
```
Среди успешных входов (4624) присутствует хост `DESKTOP-XZ44`, который не является сервером БД и ранее никогда не использовался этой службой. Это красный флаг: служба, обычно работающая только на SRV-DB01, вошла с рабочей станции. Аналитик смотрит детали входа:

```splunk
index=windows EventCode=4624 user="CORP\\svc_backup" host="DESKTOP-XZ44"
| table _time, LogonType, WorkstationName, IpAddress
```
Вывод:
```
_time               LogonType   WorkstationName   IpAddress
2025-04-05 02:15:33  10          DESKTOP-XZ44      10.0.10.89
```
LogonType=10 (RemoteInteractive) и несовпадение имени рабочей станции с ожидаемым (на SRV-DB01 вход должен был быть сетевым от службы) подтверждают, что учётные данные, вероятно, были скомпрометированы и использованы злоумышленником.

**Шаг 4: Корреляция с IP-адресами и завершение расследования.**  
Используя IP рабочей станции `10.0.10.89`, аналитик проверяет, нет ли на ней других алертов:

```splunk
index=sec_events host="DESKTOP-XZ44" OR src_ip="10.0.10.89" earliest=-24h
| stats count by alert_type, dest_ip
```
Результат показывает несколько алертов типа «malware_detected» и одно исходящее соединение на тот же IP `198.51.100.22`, который фигурировал на сервере БД. Кроме того, из панели «Top External Source IPs» аналитик видит, что IP `198.51.100.22` занимает третью строчку в списке целей исходящего трафика за 24 часа, что лишь усиливает подозрения. На этом основании аналитик формирует инцидент и эскалирует его на L2 с приложением всех собранных артефактов.

**Ожидаемый вывод.**  
Пример демонстрирует, как группировка алертов по хосту вывела аномалию (`SRV-DB01`), группировка по пользователю помогла выявить компрометацию учётной записи `svc_backup` через необычный хост и тип входа, а группировка по IP позволила подтвердить связь с известным вредоносным адресом и дополнительно подтвердить цепочку заражения. Сочетание трёх «вершин» анализа является стандартной практикой первичного triage в SOC.
