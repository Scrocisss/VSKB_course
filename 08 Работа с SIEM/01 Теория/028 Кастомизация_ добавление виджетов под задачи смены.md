# Кастомизация SIEM-дашбордов: добавление виджетов под задачи смены SOC L1

## 1. Дашборд SIEM как рабочий инструмент смены: контекст и ключевые понятия

SIEM-дашборд — это централизованная визуальная панель, агрегирующая данные безопасности из множества источников (сетевых устройств, серверов, средств защиты) и представляющая их в компактном, пригодном для быстрой оценки виде. В отличие от статического отчёта, дашборд работает в реальном времени и служит операционным интерфейсом для аналитиков, инженеров и руководителей SOC. Его главная функция — превратить миллионы ежедневных событий в срез текущей ситуации, облегчая обнаружение угроз, расследование инцидентов и контроль работоспособности средств мониторинга [Cyber Silo].

Кастомизация дашбордов — это адаптация содержимого и внешнего вида панелей под конкретные задачи, роли и сценарии работы. Для аналитика первой линии (L1) задача смены сводится к оперативному мониторингу: просмотр активных оповещений, первичная сортировка, проверка целостности поступающих данных и эскалация подозрительных событий. Универсальный, «заводской» дашборд редко отвечает этим потребностям полностью: он либо перегружен избыточными виджетами для смежных ролей, либо, наоборот, не содержит наиболее информативных для конкретной смены разрезов. Поэтому ключевой навык специалиста L1 — умение собрать рабочее пространство «под себя», добавляя, удаляя и настраивая виджеты непосредственно под ритм дежурства.

Виджет — атомарный элемент дашборда, визуализирующий результат запроса к данным SIEM в заданном формате: линейный график, столбчатая диаграмма, круговая диаграмма, счётчик, таблица, карта, текстовая сводка и т. д. Каждый виджет опирается на один или несколько источников данных (индексы событий, хранилище алертов, инцидентов, метрик здоровья) и включает в себя фильтры, временной диапазон и параметры обновления [Logsign]. Совокупность виджетов, размещённых на общей сетке, и образует «дашборд смены L1».

Следует чётко разделять типы дашбордов, с которыми сталкивается специалист SOC. Ниже — сравнительная таблица, фиксирующая разницу между предустановленными, административно управляемыми и кастомными дашбордами, создаваемыми самим аналитиком под нужды смены.

| Тип дашборда | Кто создаёт и изменяет | Источники данных и наполнение | Преимущества для L1 | Ограничения |
|--------------|------------------------|-------------------------------|----------------------|-------------|
| Предустановленный (из коробки) | Вендор SIEM | Фиксированный набор универсальных виджетов: общий объём событий, топ правил, геокарта и т. п. | Быстрый старт; минимальная подготовка | Не адаптирован под конкретную смену, может шумом отвлекать от приоритетных задач |
| Административный (ролевой) | Администратор платформы или старший инженер SOC | Стандартизированный набор виджетов, общий для всех аналитиков L1; основан на корпоративных политиках мониторинга | Единообразие, соответствие регламенту | Не учитывает специфику конкретной смены (утро/ночь), не позволяет оперативно подстраиваться |
| Кастомный (под задачу смены) | Сам аналитик L1 (в разрешённых пределах) или выделенный инженер по запросу смены | Виджеты, отобранные под текущую ситуацию: активные алерты за последние 24 часа, объём логов по критичным источникам, необработанные инциденты | Максимальная релевантность, минимум шума; быстрая оценка обстановки | Требует навыков работы с интерфейсом SIEM и понимания доступных полей данных |

Задачи смены L1, под которые формируется кастомный дашборд, типично включают: мониторинг активных оповещений с высоким и критическим приоритетом, контроль наличия новых инцидентов и их статуса, оценку работоспособности источников логов (не упал ли поток данных), выявление шумящих правил корреляции и быструю проверку аномалий. Таким образом, правильно кастомизированный дашборд становится «приборной панелью» смены, сокращающей время реакции (Mean Time to Detect) и снижающей когнитивную нагрузку на аналитика. Ключевое требование кастомизации — не создавать ещё один «мусорный» экран, а фокусироваться на действенных метриках, непосредственно влияющих на оперативное принятие решений [SearchInform].

## 2. Внутреннее устройство кастомизируемого дашборда: компоненты, типы виджетов и потоки данных

Современный SIEM-дашборд строится по модульному принципу. Его основу составляет холст (layout) с настраиваемой сеткой, на который пользователь помещает виджеты. Каждый виджет представляет собой триединую сущность: **источник данных** (log event index, alert store, incident management database), **запрос** на языке платформы (KQL, RQL, SPL и др.) и **визуализацию** (диаграмма, таблица, числовой индикатор). Дополнительно виджет может содержать фильтры, привязанные к глобальным или локальным переменным дашборда (например, `$time_range`, `$severity_filter`), что делает его интерактивным [R-Vision].

Рассмотрим детально основные типы виджетов, доступные в типовых SIEM‑решениях, и их пригодность для задач смены L1. Сводка представлена в таблице, основанной на обобщении функциональности продуктов Logsign, R-Vision SIEM и практических рекомендаций SecureTrust.

| Тип виджета | Визуализация | Отображаемый срез | Применение в дашборде L1 |
|-------------|-------------|-------------------|----------------------------|
| Гистограмма / Bar Chart | Столбцы с группировкой (по severity, типу, источнику) | Распределение оповещений по категориям за выбранный период | Быстрая оценка баланса критичных и низкоприоритетных алертов; выявление всплесков по одной категории |
| Временной ряд / Line Chart | График изменения метрики во времени | Динамика количества событий, EPS, число алертов в час | Обнаружение аномальных скачков или падений; контроль нагрузки на смену |
| Круговая диаграмма / Pie Chart | Доли от целого | Распределение инцидентов по статусам, типам атак | Оценка доли необработанных инцидентов; быстрый ответ на вопрос «сколько ещё в работе» |
| Числовой счётчик / Number Ticker | Крупное число с пороговой окраской | Текущее количество активных критических алертов, число ошибок приёма логов | Привлечение внимания к показателям, требующим немедленной реакции |
| Таблица / Table | Строки с сортируемыми столбцами | Детальный список: топ-10 правил, последние высокоприоритетные алерты, источники с падением EPS | Переход к детализации для первичного анализа; кликабельность до drill-down в событие |
| Сводка / Grouped Data | Группировка с цветовой индикацией | Распределение по объектам, хостам, пользователям | Быстрое выделение сущностей с наибольшим числом алертов |
| Текст / Text Widget | Произвольный статичный или условный текст | Дежурная информация: контакты эскалации, ссылки на runbook, важные заметки смены | Интеграция процедурного контекста непосредственно в дашборд |

Типовой дашборд для L1 комбинирует несколько из этих виджетов так, чтобы закрыть цикл «обнаружение → первичный triage → контроль здоровья». Например, счётчик критических алертов привлекает внимание, временной ряд показывает, нарастает ли активность, а таблица топ-правил помогает быстро выявить ложноположительную лавину.

Ключевой механизм кастомизации — язык запросов виджета. Ниже приведена иллюстративная структура запроса в RQL-подобном синтаксисе (R-Vision SIEM), демонстрирующая возможности фильтрации и агрегирования, типичные при настройке виджета под смену L1. Конкретные поля и функции зависят от реализации, но семантика остаётся общей.

```text
// Пример запроса виджета "Топ-10 правил корреляции за последние 24 часа"
dataset = alerts
| filter status == "active" and time >= now() - 24h
| stats count() by rule_name
| sort count() desc
| head 10
```

Для представления конфигурации виджета часто используется JSON‑формат, описывающий тип, визуализацию, запрос и интервал обновления. Такая структура позволяет сохранять дашборд как схему и переносить между сеансами или даже между аналитиками смены. Типичный JSON‑каркас виджета (иллюстративная схема) выглядит так:

```json
{
  "widget": {
    "id": "widget-001",
    "title": "Активные критические алерты",
    "type": "number_ticker",
    "query": "SELECT count(*) FROM alerts WHERE severity='critical' AND status='active' AND time > now() - 1d",
    "refresh": "30s",
    "thresholds": {
      "warning": 5,
      "critical": 10
    },
    "filter_mapping": {
      "time_range": "$global_time_range"
    }
  }
}
```

Платформы SIEM предоставляют графический мастер создания виджета, который скрывает ручное написание запроса. В мастере аналитик последовательно выбирает источник данных (например, логи событий, оповещения, инциденты), задаёт тип визуализации, поля для группировки и сортировки, временной интервал и дополнительные фильтры [Logsign, R-Vision]. Однако понимание нижележащей структуры позволяет уверенно работать с более продвинутыми сценариями: копированием виджетов через импорт/экспорт, параметризацией через переменные и отладкой запросов при некорректных данных.

Важный элемент, который необходимо учитывать при кастомизации, — динамические переменные дашборда. В R-Vision SIEM, например, можно определить переменную `timeframe` и привязать её ко всем виджетам; тогда изменение переменной на уровне дашборда одновременно обновит временной срез на всех панелях [R-Vision]. Для смены L1 это позволяет быстро переключаться между просмотром «последний час» и «последние сутки» без правки каждого виджета.

## 3. Применение и работа с кастомизацией: как добавить виджеты под задачи смены L1

Практическая работа по кастомизации дашборда включает несколько универсальных шагов, которые с минимальными отличиями воспроизводятся во всех ведущих SIEM-системах. Рассмотрим типовую цепочку действий аналитика L1 на примере веб‑интерфейса, аналогичного R‑Vision SIEM или Logsign.

**Создание нового дашборда.** В разделе «Дашборды» нажимается кнопка «Добавить» (`+`). В открывшейся форме указываются имя (например, «Смена L1: мониторинг»), описание и, при необходимости, признак «Персональный» — часто дашборд делается общим для всей смены, чтобы сменяющийся аналитик не терял контекст. После сохранения создаётся пустой холст.

**Добавление виджета.** Кнопка «Добавить виджет» запускает мастер. Аналитик выбирает тип визуализации из каталога (гистограмма, таблица, счётчик, круговая диаграмма и т. д.). Затем вводится запрос. Для L1 релевантны следующие базовые виджеты:

- *Активные оповещения по уровням критичности*: столбчатая диаграмма с группировкой по полю severity, фильтр `status=="active"`, временной диапазон «последние 24 часа».
- *Топ‑10 правил корреляции*: таблица, считающая количество срабатываний каждого правила за последние сутки, сортировка по убыванию.
- *Статус инцидентов*: круговая диаграмма или счётчик, показывающий распределение инцидентов по статусам (новый, в работе, решён) — это прямо отражает загруженность смены.
- *Объём поступающих событий по источникам*: временной ряд с разбивкой по источнику (firewall, EDR, AD) для контроля целостности потоков.
- *Ошибки приёма логов*: числовой индикатор (number ticker) с порогами, подсвечивающий проблемы коллекторов.

После выбора типа и написания запроса на последнем шаге задаются параметры обновления (обычно 30–60 секунд) и, если система поддерживает, привязка к переменным дашборда. Виджет появляется на холсте; его можно перемещать и менять размер.

**Пример конфигурации виджета через JSON (иллюстративная схема для SIEM с поддержкой API).** Многие системы позволяют экспортировать или импортировать виджеты в виде JSON, что удобно для быстрого развёртывания набора виджетов в начале смены.

```json
{
  "dashboard": {
    "name": "Смена L1",
    "widgets": [
      {
        "title": "Критические алерты",
        "type": "number_ticker",
        "query": "index=alerts status=active severity>=critical | stats count",
        "refresh_interval": "30s"
      },
      {
        "title": "Топ правил",
        "type": "table",
        "query": "index=alerts | stats count by rule_name | sort -count | head 10",
        "time_range": "last_24h"
      }
    ]
  }
}
```

Приведённый JSON является обобщённым шаблоном; реальные поля зависят от API конкретного SIEM, но отражают логику, общую для Elastic Security, Splunk, R-Vision и аналогов.

**Типичные ошибки и пути их предотвращения.** Новички часто включают слишком много виджетов, превращая дашборд в «шумовую стену». Рекомендуется ограничиться 5–7 элементами, каждый из которых отвечает на конкретный вопрос смены. Ещё одна частая проблема — отсутствие временного ограничения в запросах, из-за чего виджет выполняет полное сканирование данных, вызывая задержки обновления. Лучшая практика — всегда задавать временной фильтр, синхронизированный с длительностью смены (например, `time > now() - 24h`). Наконец, виджеты должны быть кликабельными: щелчок по сегменту диаграммы или строке таблицы должен открывать детализацию (drill-down) в список соответствующих событий. Эта возможность должна проверяться сразу после создания виджета.

**Поддержка и актуализация.** Дашборд смены не статичен: по мере изменения ландшафта угроз или появления новых источников данных его нужно рецензировать. Рекомендуется выделять 5–10 минут в начале смены на быструю валидацию: все ли источники отдают данные, не появились ли новые критичные правила, не деградировала ли производительность запросов [SecureTrust]. Хорошей практикой является сохранение успешных конфигураций в виде схем (шаблонов), чтобы любая смена могла загрузить проверенный дашборд без повторной настройки [R-Vision].

## 4. Сквозной практический пример: сборка дашборда для утренней смены аналитика L1

Рассмотрим реалистичный кейс: аналитик L1 заступает на утреннюю смену в SOC. В его задачи входит оценить обстановку за последние 24 часа, проверить наличие критических инцидентов, оставленных ночной сменой, и убедиться в корректности поступления данных с ключевых источников. Для этого он собирает кастомный дашборд в интерфейсе SIEM, аналогичном R-Vision SIEM, Logsign или Elastic Security.

**Исходные условия:** веб-интерфейс SIEM с правами на создание дашбордов и виджетов; доступны источники данных: индексы оповещений (`alerts`), инцидентов (`incidents`) и событий (`events`). Интерфейс позволяет создавать виджеты через мастер или загружать JSON-конфигурацию.

**Шаг 1. Создание дашборда.**  
Аналитик переходит в раздел «Дашборды» → «Добавить». Указывает имя «Смена L1: утро», описание «Обзор за последние 24 часа», снимает галочку «Персональный», чтобы дашборд был доступен при передаче смены.

```json
{
  "action": "create_dashboard",
  "dashboard": {
    "name": "Смена L1: утро",
    "description": "Обзор за последние 24 часа",
    "personal": false
  }
}
```
Ожидаемый результат: появляется пустой холст нового дашборда.

**Шаг 2. Виджет «Активные алерты по severity».**
Через «Добавить виджет» выбирается «Столбчатая диаграмма» (Bar Chart). В запросе задаётся агрегация числа активных алертов за последние сутки с группировкой по severity.

```json
{
  "widget": {
    "title": "Активные алерты по severity",
    "type": "bar_chart",
    "query": "SELECT severity, count(*) FROM alerts WHERE status='active' AND time > now() - 1d GROUP BY severity",
    "visualization": "stacked",
    "refresh": "60s"
  }
}
```
Визуализация показывает столбцы для critical, high, medium, low. Аналитик сразу видит, есть ли перекос в сторону critical.

**Шаг 3. Виджет «Топ-10 правил корреляции».**
Добавляется таблица с сортировкой по убыванию количества срабатываний правил за 24 часа.

```json
{
  "widget": {
    "title": "Топ-10 правил",
    "type": "table",
    "query": "SELECT rule_name, count(*) AS cnt FROM alerts WHERE time > now() - 1d GROUP BY rule_name ORDER BY cnt DESC LIMIT 10",
    "refresh": "120s"
  }
}
```
Таблица даёт понимание, какие правила шумят или, наоборот, сработали на реальные угрозы. Если правило «Brute Force» лидирует, это повод проверить, не идёт ли атака.

**Шаг 4. Виджет «Статус инцидентов».**
Для контроля загрузки смены используется круговая диаграмма по статусам инцидентов.

```json
{
  "widget": {
    "title": "Инциденты",
    "type": "pie_chart",
    "query": "SELECT status, count(*) FROM incidents WHERE created_time > now() - 1d GROUP BY status",
    "refresh": "60s"
  }
}
```
Зелёный сектор «resolved» и красный «new» дают мгновенную картину: сколько инцидентов не обработано.

**Шаг 5. Виджет «Объём событий по источникам».**
Линейный график с временным рядом EPS по каждому источнику.

```json
{
  "widget": {
    "title": "EPS по источникам",
    "type": "line_chart",
    "query": "SELECT source, timestamp_trunc('hour', time) AS hour, count(*) AS eps FROM events WHERE time > now() - 1d GROUP BY source, hour",
    "refresh": "60s"
  }
}
```
Падение до нуля по источнику «Firewall» будет означать, что логи перестали поступать и требуется вмешательство.

**Ожидаемый итог:** собранный дашборд за 30 секунд даёт аналитику ответы на вопросы: есть ли прямо сейчас критический инцидент, требующий немедленной реакции; не нарастает ли волна атак; не перегружена ли смена необработанными инцидентами; все ли источники живы. Это ускоряет развертывание ситуационной осведомлённости и снижает риск пропуска важного сигнала из-за информационной перегрузки.
