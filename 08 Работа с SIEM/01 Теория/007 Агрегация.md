# Агрегация данных безопасности: централизация событий в SIEM

## 1. Назначение и положение агрегации в инфраструктуре SOC

Агрегация — это технологический процесс непрерывного сбора, приёма и централизации необработанных записей о событиях (логов, алертов, телеметрии) от разрозненных источников ИТ-инфраструктуры в единую платформу, обычно SIEM. Агрегация формирует первичный слой данных, без которого невозможны ни корреляция, ни поиск угроз, ни ретроспективный анализ. В современном Security Operations Center (SOC) именно агрегация определяет полноту видимости: любые пропуски на этом этапе напрямую превращаются в слепые зоны для аналитика уровня L1.

Исторически SIEM возник как объединение двух ранее самостоятельных дисциплин: Security Information Management (SIM) — долговременного сбора и хранения журналов для комплаенса, и Security Event Management (SEM) — оперативного мониторинга и реагирования. Агрегация служит фундаментом для обеих: она насыщает и архивное хранилище, и потоковую обработку в реальном времени одними и теми же нормализованными записями.

В конвейере обработки данных SIEM агрегация занимает начальную фазу, но её часто смешивают с соседними стадиями. Чтобы избежать путаницы, полезно разграничить ключевые понятия.

```text
[Источники] → [Агрегация] → [Нормализация] → [Корреляция] → [Алерты / Инциденты]
                  ↑                ↑               ↑
        Сбор и централизация   Приведение     Выявление связей
        сырых событий          к единой       между событиями
                               схеме
```

| Этап | Ключевая задача | Что происходит с данными | Типичный результат |
|---|---|---|---|
| **Агрегация** (Collection & Aggregation) | Принять данные от всех заданных источников в центральную точку, обеспечить надёжную доставку и первичную буферизацию | Сохраняется исходная форма события; может добавляться metadata об источнике (host, timestamp приёма). Допустима простейшая фильтрация и маршрутизация | Событие попало в индекс/хранилище SIEM, доступно для поиска |
| **Нормализация** (Normalization) | Преобразовать разнородные форматы (syslog RFC 3164/5424, CEF, LEEF, JSON, Windows XML) в единую схему полей | Извлечение значимых полей: `src_ip`, `user`, `action`, `result` и т.п.; таксономия событий по категориям | Структурированная запись с одинаковыми именами полей для всех источников |
| **Корреляция** (Correlation) | Выявить комбинации событий, соответствующие известным сценариям атак или аномалиям, и сгенерировать алерт | Сопоставление событий по одинаковым сущностям (IP, пользователь, хост) в рамках временного окна; применение правил или машинного обучения | Алерт с описанием инцидента и контекстом |

Агрегация в SIEM не является просто «сбором логов», как в классических системах управления логами (log management). Отличие в том, что SIEM сразу готовит данные для оперативного реагирования: потоки маршрутизируются не только на холодное хранение, но и в движок корреляции, во временные окна аналитики. Кроме того, агрегация в SIEM обычно включает механизмы гарантии доставки (acknowledgement, повторные попытки), что критично для событий безопасности, потеря которых может скрыть атаку.

Роль агрегации в SOC уровня L1 двойная. Во-первых, она обеспечивает единую точку доступа ко всем событиям, позволяя аналитику не переключаться между консолями десятков систем. Во-вторых, именно настройки агрегации (какие источники включены, с какой детализацией, с какой фильтрацией) определяют начальный контекст, доступный для триажа — процесса первичной сортировки и оценки алертов. Таким образом, агрегация — это не только технический, но и операционный фундамент деятельности первой линии SOC.

## 2. Архитектура и внутренние механизмы агрегации

Архитектура подсистемы агрегации в SIEM обычно включает четыре функциональных слоя, каждый из которых может масштабироваться независимо для обработки десятков тысяч событий в секунду (EPS — events per second).

```text
┌─────────────┐
│ Источники   │ FW, AD, EDR, веб-серверы, облачные API …
│ данных      │
└──────┬──────┘
       │ syslog/TCP, HTTPS, WEF, агенты
       ▼
┌─────────────────────┐
│ Коллекторы / Edge   │ Приём, проверка формата, начальный парсинг source metadata
│ receivers           │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Шина / очередь      │ Буферизация, балансировка нагрузки (Kafka, internal pipelines)
│ сообщений           │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Индексатор /        │ Запись событий в горячее/тёплое хранилище, разбивка по индексам
│ хранилище           │
└─────────────────────┘
```

**Коллекторы** (сборщики) являются точкой входа в SIEM. Они принимают потоки событий по различным протоколам:

| Протокол / механизм | Типичное применение | Особенности для агрегации |
|---|---|---|
| Syslog (UDP/TCP/TLS) | Сетевые устройства, UNIX-серверы, веб-прокси | Вероятна потеря при UDP; TCP с буфером гарантирует доставку. Формат часто неструктурированный, требуется парсинг заголовков PRI, timestamp |
| HTTP/HTTPS REST API | Облачные сервисы, приложения, агенты без syslog | События передаются обычно в JSON или NDJSON. Поддерживается пакетная отправка, аутентификация по токену |
| Windows Event Forwarding (WEF) | События Windows без установки агента | Использует WinRM; подписки определяют, какие каналы пересылаются. Требует настройки коллектора-подписчика |
| SIEM-агенты (Splunk UF, Elastic Beats) | Универсальный сбор с хостов | Локальный мониторинг файлов, Event Log, метрик; агент сам сжимает и буферизует данные при потере связи, снижая нагрузку на сеть |
| Потоковая телеметрия (NetFlow/IPFIX, eBPF) | Сетевая активность, контейнерные среды | Высокое количество событий; требует выделенной инфраструктуры приёма и агрегации до передачи в хранилище |

При приёме события коллектор присваивает ему метаданные источника: `host`, `source_type`, `index`, `_ingest_timestamp`. Эти метаданные не подменяют исходное тело сообщения, а дополняют его, позволяя впоследствии фильтровать и маршрутизировать потоки. Важно, чтобы временная метка события (`timestamp`) извлекалась из исходного сообщения, а не подменялась временем приёма, иначе корреляция нарушится.

**Шина сообщений** (Kafka, внутренние буферы SIEM) выполняет роль эластичного буфера. Она изолирует приёмную часть от индексаторов, позволяя пережить всплески нагрузки без потери событий. Данные в очереди могут быть временно дублированы, чтобы обеспечить доставку «хотя бы один раз» (at-least-once) — стандарт для SIEM. Однако избыточная дупликация без downstream-дедупликации способна исказить счётчики корреляции, поэтому настройка retention очереди и механизмов идемпотентности записи критична.

**Маршрутизация и фильтрация на этапе агрегации** позволяют отбросить наименее полезные события до того, как они попадут в дорогостоящее индексируемое хранилище. Типичные техники:
- фильтрация по `EventID` (например, отбрасывание событий успешного доступа к файлам, если они не нужны);
- подавление повторяющихся событий за интервал (suppression);
- маршрутизация высокообъёмных потоков в отдельные индексы с сокращённым сроком хранения;
- преобразование избыточных событий в агрегированные метрики (event summarization).

Эти приёмы напрямую решают проблему, описанную в отраслевых источниках как «data ingestion – bane of the SOC»: неконтролируемый рост объёмов сырых логов перегружает инфраструктуру и отвлекает персонал шумом, что снижает эффективность всей команды SOC [Gurucul].

После прохождения очереди события попадают к **индексаторам**, которые строят поисковые индексы и записывают данные в хранилище. На этом физическая агрегация завершается: события становятся доступными для поиска и корреляции. В распределённых системах (например, Elasticsearch) индексаторы и хранилище могут быть объединены в кластер, где данные шардируются для параллельной обработки запросов.

Форматы событий на входе агрегации могут быть любыми; SIEM обязан поддерживать хотя бы базовый набор. Ниже приведена иллюстративная схема полей, формируемая после успешной агрегации и минимального парсинга (нормализация выполняется позже), пригодная для дальнейшей обработки:

```json
{
  "event": {
    "original": "<сырое сообщение, как получено>",
    "ingested": "2025-02-20T10:15:00Z",
    "provider": "WinEventLog:Security",
    "channel": "security"
  },
  "host": {
    "name": "dc01.domain.local",
    "ip": ["10.0.0.5"]
  },
  "agent": {
    "type": "universal_forwarder",
    "version": "9.1.0"
  },
  "fields": {
    "EventCode": 4625,
    "Keywords": "Неудачный вход",
    "src_ip": "198.51.100.25"
  }
}
```
*Примечание: поля `fields.*` появляются после начального извлечения, но полная нормализация выполняется уже на следующем этапе.*

Таким образом, архитектура агрегации — это конвейер, в котором сырые данные проходят через коллекторы, буфер и индексаторы, попутно обогащаясь метаданными и фильтруясь для поддержания управляемого соотношения «сигнал/шум».

## 3. Применение агрегированных данных аналитиками SOC первой линии

Для специалиста L1 агрегированные данные — это рабочий материал, с которым он взаимодействует через поисковый интерфейс SIEM. Ключевая задача на этом уровне не в настройке потоков (это прерогатива инженеров), а в умении извлекать из централизованного моря событий значимую оперативную информацию.

Типовые операции, выполняемые аналитиком L1:

- **Поиск по атомарным индикаторам**: IP-адрес, имя хоста, пользователь, хэш файла. Благодаря агрегации результат охватывает все подключённые источники одновременно.
- **Временная группировка и сортировка**: выявление периодов повышенной активности («spike»), определение хронологии инцидента.
- **Подсчёт частот**: наиболее частые источники, типы событий, коды ответов. Это позволяет быстро определить аномалии без сложных правил корреляции.
- **Проверка гипотез**: например, «видел ли этот хост трафик на известный вредоносный порт?» — одиночный поисковый запрос вместо ручного опроса нескольких систем.
- **Эскалационная подготовка контекста**: перед передачей на L2 аналитик собирает все события, связанные с подозрительной сущностью, в единый отчёт (dashboard или saved search).

Практический пример поиска и агрегации в Splunk (аналогичная логика применима в Elastic/Kibana):

```spl
index=windows EventCode=4625 earliest=-2h
| stats count by src_ip, TargetUserName
| sort - count
| head 20
```
*Интерпретация: выбираются все события неудачного входа за последние 2 часа, агрегируются по источнику IP и целевой учётной записи, сортируются по убыванию числа попыток, и выводятся 20 наиболее активных комбинаций. Результат позволяет мгновенно увидеть брутфорс-атаку.*

Ещё один пример — выявление аномального объёма исходящего трафика, агрегируя события межсетевого экрана:

```spl
index=firewall action=allowed dest_port=443 earliest=-1h
| bin _time span=5m
| stats count by _time, src_ip
| where count > 1000
| timechart span=5m sum(count) by src_ip
```
*Команда группирует события каждые 5 минут и находит хосты, отправляющие более 1000 соединений за интервал, что может свидетельствовать о C2-канале или эксфильтрации данных.*

**Распространённые ошибки при работе** на этом уровне:

- **Игнорирование временных зон**: если в логах источника время указано в локальной зоне без смещения, а SIEM интерпретирует его как UTC, события могут смещаться на часы, ломая корреляцию и поиск. Аналитик должен проверять метаданные `_time` и при необходимости запрашивать нормализацию.
- **Дубликаты из-за повторной пересылки**: при сбоях агенты могут отправить одно и то же событие дважды. Без post-обработки дедупликации в SIEM аналитик видит завышенные счётчики. Нужно уметь выявлять дубли по комбинации `host` + `timestamp` + `EventRecordID`.
- **Потери при UDP syslog**: если источник настроен на syslog/UDP, потеря пакетов неизбежна при высокой нагрузке. Аналитику следует знать, какие источники используют UDP, и с осторожностью интерпретировать отсутствие событий.
- **Слишком широкие запросы**: из-за огромного объёма данных поиск без временного диапазона может выполняться медленно или обрушить поисковый узел. Аналитик L1 обязан всегда ограничивать временное окно.

Средства автоматизации агрегации, встроенные в современные SIEM, также помогают L1: например, summary-индексы (Splunk) или rollup-задачи (Elastic) автоматически пред-агрегируют события в минуты/часы, что ускоряет загрузку дашбордов. Однако аналитик должен понимать, что агрегированные представления скрывают детали, поэтому при обнаружении аномалии всегда следует переходить к исходным событиям.

Таким образом, агрегация — не пассивный склад, а активный инструмент оперативного расследования. Умение формулировать поисковые запросы с агрегационными функциями (stats, timechart, histogram) напрямую определяет скорость триажа и качество эскалации.

## 4. Сквозной практический пример: расследование волны неудачных входов

**Исходные условия**

Аналитик SOC L1 получает автоматический алерт от SIEM: «Множественные неудачные входы с внешнего IP-адреса 198.51.100.88 за последние 60 минут». SIEM уже агрегирует данные из контроллера домена (Windows Security Events), межсетевого экрана и веб-портала организации (nginx). Необходимо провести первичный триаж и принять решение об эскалации.

**Шаг 1: Верификация источника активности**

Аналитик запускает поиск событий неудачного входа по всем системам для указанного IP:

```spl
index=windows OR index=web src_ip="198.51.100.88" earliest=-2h
| stats count by index, sourcetype, EventCode
```

Ожидаемый вывод:

```
index    sourcetype         EventCode   count
windows  WinEventLog:Security  4625     347
windows  WinEventLog:Security  4771      12
web      nginx:access          –       203
```

*Интерпретация:* 347 событий EventID 4625 (явный перебор учётных данных), 12 событий 4771 (сбой Kerberos pre-auth), и 203 запроса к веб-серверу с этим же IP. Подтверждена активность с одного источника.

**Шаг 2: Детализация вектора атаки на AD**

Следующий запрос агрегирует неудачные входы по целевым учётным записям:

```spl
index=windows EventCode=4625 src_ip="198.51.100.88" earliest=-2h
| stats count by TargetUserName, WorkstationName
| sort - count
| head 10
```

Результат:

```
TargetUserName   WorkstationName   count
administrator    SRV-DB01          120
admin            SRV-WEB02          98
service_account  SRV-DB01           55
...
```

*Вывод:* атакующий систематически перебирает пароли к привилегированным учётным записям на критичных серверах. Этот паттерн характерен для targeted brute-force.

**Шаг 3: Корреляция с веб-системой**

Аналитик проверяет логи веб-портала, чтобы понять, использовался ли тот же IP для атак на веб-интерфейс:

```spl
index=web src_ip="198.51.100.88" earliest=-2h
| stats count by status, uri_path
| sort - count
```

Вывод:

```
status   uri_path          count
401      /login            187
403      /admin             15
200      /login              1
```

*Интерпретация:* 187 неуспешных попыток аутентификации на веб-форме (HTTP 401), 15 запрещённых обращений к административной панели и одна успешная попытка входа (HTTP 200) с сессионной кукой. Следовательно, атакующий, вероятно, подобрал пароль на веб-портале и теперь пытается использовать ту же учётную запись на внутренних системах через kerberos.

**Ожидаемый вывод по примеру**

Сквозной кейс демонстрирует, как агрегация событий из трёх разнородных источников (Windows, nginx, firewall) позволяет всего за несколько поисковых запросов собрать полную картину инцидента: от идентификации источника до вектора и стадии компрометации. Без централизованной агрегации аналитику L1 пришлось бы вручную опрашивать каждый компонент, что многократно увеличило бы время реакции и снизило бы шансы на обнаружение взаимосвязей.
