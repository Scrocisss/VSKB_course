# Фильтрация по хосту и пользователю в поисковых запросах SIEM

## 1. Контекст и базовые понятия

**SIEM** (Security Information and Event Management) агрегирует события из разнородных источников: операционных систем, сетевого оборудования, средств защиты, облачных сервисов. Аналитик SOC Level 1 ежедневно использует поисковые запросы для триажа инцидентов, поиска индикаторов компрометации (IoC) и проактивного поиска угроз (threat hunting). Основными «якорями» при фильтрации событий выступают **хост** и **пользователь** — два измерения, позволяющие локализовать подозрительную активность в масштабах всей инфраструктуры.

Фильтрация по хосту отвечает на вопрос «на каком устройстве происходило событие?», а фильтрация по пользователю — «кто выполнил действие?». В реальных SIEM-системах этим вопросам соответствуют конкретные поля событий, прошедших нормализацию. Несмотря на кажущуюся простоту, понятия «хост» и «пользователь» могут обозначаться разными атрибутами в зависимости от источника, формата логов и архитектуры SIEM. Путаница между сходными по названию, но функционально разными полями — частая причина ложных срабатываний и пропущенных инцидентов у начинающих аналитиков. Например, `source.ip` и `host.ip` не всегда эквивалентны: первый указывает IP-адрес источника сетевого соединения, второй — IP-адрес самого хоста, на котором произошло событие. Аналогично `user.name` может относиться к учётной записи в домене, локальной учётной записи или даже к субъекту, от имени которого запущен процесс.

Ниже представлена сравнительная таблица, фиксирующая ключевые поля для хоста и пользователя в трёх распространённых платформах, релевантных в контексте SOC:

| Платформа / формат | Поле хоста (ключевые атрибуты) | Поле пользователя (ключевые атрибуты) | Примечание |
|-------------------|-------------------------------|-------------------------------------|------------|
| Elastic Security (Elastic Common Schema, ECS) | `host.name` (keyword), `host.ip` (ip), `host.os.name` (keyword) | `user.name` (keyword), `user.domain` (keyword), `user.email` (keyword) | Строгая типизация; `host.name` обычно FQDN или NetBIOS-имя. `user.name` — нормализованная учётная запись. |
| Datadog Cloud SIEM (log attributes) | `@host.name` (строка), `@network.client.ip` (IP), `@source` (строка) | `@user.name` (строка), `@actor` (строка), `@usr.id` (строка) | Поля с префиксом `@` — атрибуты; поиск по ним чувствителен к регистру. `@source` может содержать имя хоста-источника логов. |
| CrowdStrike Falcon (FQL) | `hostname` (строка), `local_ip` (строка), `external_ip` (строка) | `user` (строка), `user_name` (строка), `user_sid` (строка) | Свойства FQL; `hostname` — имя хоста в инвентаре Falcon. `user` — имя учётной записи (часто в формате DOMAIN\username). |

Таблица не является исчерпывающей, но демонстрирует, что даже базовые сущности могут быть представлены по-разному. Поэтому первый шаг к грамотной фильтрации — изучить схему данных (data model, mapping) используемого SIEM. Большинство платформ предоставляют документацию по «log schema» или «data dictionary».

Важно разграничить **фильтрацию** в поисковых запросах от **агрегации** и **визуализации**. Фильтрация сужает набор событий до релевантных; агрегация (например, count by host) показывает распределение. При расследовании типичен путь: сначала фильтр по хосту или пользователю, затем визуализация временного ряда или топ-процессов. Также не следует смешивать фильтрацию по хосту с фильтрацией по источнику логов (`source`, `agent.name`): первое — это целевой объект, второе — транспортный агент. Например, событие с Windows-сервера может иметь `host.name` = `dc01` и `agent.name` = `winlogbeat`. Поиск по `host.name` вернёт все события с этого сервера независимо от агента.

Фильтрация по пользователю осложняется тем, что одна и та же учётная запись может быть записана в логах в разных форматах: `DOMAIN\jdoe`, `jdoe@domain.com`, `S-1-5-21-...`. Современные SIEM (в частности, Datadog и Elastic) выполняют нормализацию и enrichment, приводя идентификаторы к единому виду. Однако при ручном конструировании запросов следует знать исходный формат, особенно если используется полнотекстовый поиск. Подробнее практические аспекты раскрыты в разделе 3.

## 2. Внутреннее устройство полей `host` и `user` в SIEM

Как устроены поля хоста и пользователя «под капотом» SIEM, и как это влияет на скорость, точность и гибкость поисковых запросов? Ответ важен для аналитика, который хочет понимать, почему запрос `host.name:*websrv*` выполняется медленнее, чем `host.name:websrv01`, и почему поиск `user.name:"JDOE"` может не найти событие с `user.name:"jdoe"`.

В основе любой современной SIEM лежит хранилище на базе Elasticsearch, Splunk, Datadog Log Management или облачного аналога. Эти системы индексируют события как документы с набором полей. Для каждого поля определён **тип данных** (mapping), который диктует способы поиска. Например, в Elasticsearch различают:

- `keyword` — точная строка, индексированная как единое целое; поддерживает точное совпадение, сортировку, агрегации. Поля `host.name`, `user.name` обычно имеют тип `keyword`.
- `text` — полнотекстовое поле, разбитое на термы анализатором; поддерживает поиск по словам, но не агрегации без `.keyword` подполя. Поле `process.command_line` часто `text`.
- `ip` — IP-адрес, допускает поиск по диапазону, CIDR-нотацию.
- `date` — временная метка.

Для полей хоста и пользователя решающую роль играет тип `keyword`: именно он обеспечивает мгновенный поиск точных значений и поддерживает wildcard-запросы (хотя они и ресурсоёмки). Если поле определено как `text` (что иногда случается при автоматическом маппинге неструктурированных логов), поиск `host.name:"webserver01"` может работать иначе — будут искаться отдельные слова, а не полное имя, что приведёт к неожиданным результатам.

Процесс нормализации, который проводят SIEM-платформы, можно представить следующей упрощённой ASCII-схемой:

```text
Сырые логи (syslog, JSON, XML)
        │
        ▼
[Parser / Pipeline] ── извлечение полей по правилам (grok, regex, key-value)
        │
        ▼
[Enrichment] ── добавление контекста (GeoIP, LDAP, CMDB)
        │
        ▼
[Нормализованное событие]
        ├─ host.name   (из hostname, Computer, agent.name)
        ├─ host.ip     (из source.ip, deviceAddress)
        ├─ user.name   (из username, samaccountname, mail)
        ├─ user.domain (из domain, realm)
        └─ ...
```

На этапе парсинга сырые логи преобразуются в структурированный формат. Например, для Windows Event Log событие с кодом 4624 (вход в систему) содержит поле `TargetUserName` и `WorkstationName`; парсер отображает их на `user.name` и `host.name` соответственно. В Elastic Security встроен модуль `winlog`, который автоматически выполняет такое отображение.

Далее enrichment обращается к внешним источникам: для IP-адресов определяется географическое положение, для пользователей — их роли и группы из Active Directory, для хостов — департамент и критичность из CMDB. Благодаря этому аналитик может фильтровать не только по конкретному имени хоста, но и, например, по `host.hostgroup:"DMZ"` (если такое поле добавлено) или `user.roles:"admin"`.

Технически фильтрация по ключевым полям реализуется через инвертированные индексы. Значение `host.name:"webserver01"` — это поиск терма в индексе. Для поиска по подстроке (например, `host.name:"*web*"`) используется сканирование термов, что на порядок медленнее. Поэтому в SIEM-системах часто рекомендуют избегать leading wildcards (звёздочка в начале) и использовать структурированные запросы с точными значениями.

Структурная таблица ниже показывает сопоставление типов данных и особенностей поиска для типичных полей хоста и пользователя в Elasticsearch (на основе ECS) и Datadog (log attributes):

| Поле | Тип в Elasticsearch | Тип в Datadog | Допустимый поиск | Рекомендация |
|------|-------------------|---------------|------------------|--------------|
| `host.name` | keyword | string (keyword) | Точное совпадение, wildcard (`*` и `?`), список через пробел (OR) | Использовать точное значение, где возможно. Wildcard применяется для поиска по шаблону (например, `dc-???`) |
| `host.ip` | ip | IP | CIDR-блоки (`10.0.0.0/8`), сравнение `>`, `<` | Предпочтителен точный IP или CIDR. Избегать текстового поиска. |
| `user.name` | keyword | string (keyword) | Точное, wildcard | Регистр важен! Всегда проверять нормализацию. В логах Windows имена чувствительны к регистру, но в ряде SIEM приводятся к нижнему регистру. |
| `user.domain` | keyword | string (keyword) | Точное | Позволяет различать локальные и доменные учётные записи. |
| `source.ip` (как хост-источник) | ip | IP | CIDR, сравнение | Не всегда эквивалентен `host.ip`; нужен для сетевых событий. |

Эта таблица подчёркивает необходимость знать схему: в Datadog пользовательский запрос `@user.name:jdoe` и `@user.name:JDOE` дадут разный результат, если не настроен case-insensitive анализатор. В Elasticsearch по умолчанию поля `keyword` чувствительны к регистру. В Splunk, напротив, поиск обычно case-insensitive. Понимание таких деталей предотвращает пропуск событий.

Дополнительную сложность вносит иерархия полей. В Elastic ECS, например, `user` — это объект с вложенными свойствами: `user.name`, `user.id`, `user.group.name`. Аналитик может фильтровать по любому из них. Аналогично `host` имеет `host.name`, `host.ip`, `host.mac`, `host.os.family`. В Datadog применяется плоская модель с префиксами, но есть и вложенные атрибуты, доступные через точку: `@user.name`.

Таким образом, внутреннее устройство полей `host` и `user` — это не просто строки, а тщательно спроектированная модель данных, обеспечивающая эффективный поиск. Грамотный аналитик использует точные поля, а не полагается на свободный текст, а также учитывает типы данных при построении запросов.

## 3. Применение и работа с фильтрацией по хосту и пользователю

Практическая работа аналитика SOC L1 заключается в написании поисковых запросов для решения конкретных задач: проверка алерта, поиск следов компрометации, сбор контекста. Фильтрация по хосту и пользователю — базовые, но критически важные инструменты. В этом разделе мы рассмотрим реальные синтаксисы запросов для трёх распространённых SIEM-платформ (Elastic, Datadog, Falcon), а также типичные ошибки и паттерны.

### 3.1. Языки запросов и конкретные примеры

**Elastic Security (Kibana Query Language — KQL и Lucene).** В Kibana для поиска событий безопасности используется KQL (по умолчанию) либо классический синтаксис Lucene. Поля указываются по имени из ECS. Примеры базовых фильтров:

- Все события с хоста `webserver01`:
  ```
  host.name:"webserver01"
  ```
- События входа для пользователя `jdoe`:
  ```
  user.name:"jdoe" AND event.category:"authentication"
  ```
- Исключение служебных учётных записей из поиска:
  ```
  NOT user.name:"svc-backup" AND NOT user.name:"healthcheck"
  ```

KQL поддерживает операторы `and`, `or`, `not`, а также группировку скобками. В Lucene-синтаксисе (доступен при переключении) это выглядит так: `host.name:webserver01 AND user.name:jdoe`. Важно: свободный текст (просто `webserver01` без указания поля) в Kibana ищет по всем полям и может давать ложные совпадения.

**Datadog Log Search Syntax.** Datadog использует собственный синтаксис с атрибутами, начинающимися с `@`. Поиск по журналу безопасности Cloud SIEM:

- События только с определённого хоста:
  ```
  @host.name:webserver01
  ```
- События для пользователя из домена `example`:
  ```
  @user.domain:example @user.name:jdoe
  ```
- Исключение тестовых хостов:
  ```
  -@host.name:staging-*
  ```

Datadog позволяет комбинировать полнотекстовый поиск с атрибутами. Например, `@host.name:webserver01 failed login` ищет упоминание "failed login" в сообщении только на указанном хосте. Обратите внимание: в Datadog оператор исключения — `-` перед атрибутом, а не `NOT`.

**CrowdStrike Falcon (FQL).** Для поиска событий через API или в интерфейсе Falcon используется FQL. Фильтр по хосту и пользователю может выглядеть так (пример через Python SDK, но синтаксис универсален):

```python
# Поиск деталей инцидента с фильтром по хосту и пользователю
filter_query = "hostname:'webserver01' + user_name:'jdoe'"
```

В чистом виде FQL-строка: `hostname:'webserver01' + user_name:'jdoe'`. Оператор `+` означает логическое "И". Доступны также `,` для "ИЛИ", и операторы сравнения: `>`, `<`, `~` (текстовое соответствие). Например, для поиска хостов, чьё имя начинается с `web`:

```
hostname:'web*'
```

### 3.2. Типовые сценарии и паттерны

Рассмотрим несколько стандартных задач SOC L1 и способы их решения с помощью фильтрации.

**Алерт на подозрительный вход с нового хоста.** SIEM сгенерировал правило «Login from unusual host» для пользователя `jdoe`. Аналитик должен быстро проверить, какие ещё хосты использовал этот пользователь за последние 24 часа. В Elastic KQL можно выполнить агрегацию (визуализацию) по полю `host.name`, но для быстрого взгляда используется фильтр:

```
user.name:"jdoe" AND event.action:"successful_login" AND @timestamp >= now-24h
```
Затем добавить визуализацию «Unique counts» по `host.name`. В Datadog аналогично: `@user.name:jdoe @event.action:successful_login`, после чего в Log Explorer применить группировку по `@host.name`.

**Поиск активности вредоносного ПО на хосте.** Получив индикатор компрометации — хост `hr-ws-15` проявляет подозрительную сетевую активность, аналитик ищет все события с этого хоста за последний час:

```
host.name:"hr-ws-15" AND @timestamp >= now-1h
```

Затем сужает поиск на процессы, запущенные от имени необычного пользователя:

```
host.name:"hr-ws-15" AND user.name:* AND NOT user.name:"SYSTEM" AND event.category:"process"
```

**Расследование утечки учётных данных.** Пользователь `svc-backup` был замечен на хосте, на котором никогда ранее не появлялся. Аналитик ищет все успешные и неудачные аутентификации для этого пользователя:

```
user.name:"svc-backup" AND event.category:"authentication"
```

### 3.3. Типичные ошибки и подводные камни

1. **Поиск по свободному тексту вместо поля.** Если аналитик набирает `webserver01`, Kibana выполняет поиск по всем полям, включая сообщения, user agent и т.д. Это вызывает шум и может пропустить события, где имя хоста записано как `webserver01.domain.com` (если нет точного совпадения). **Всегда используйте квалифицированный запрос с именем поля**, например, `host.name:webserver01*` или точный `host.name:"webserver01"`.

2. **Регистр символов.** В Elastic поля `keyword` чувствительны к регистру. Запрос `user.name:Jdoe` не найдёт `jdoe`. Нужно либо использовать точное написание (как в логах), либо применить нормализацию. В Datadog также чувствительно. Некоторые SIEM (Splunk) нечувствительны, что порождает разное поведение при миграции правил.

3. **Leading wildcard.** Запрос `host.name:*server01` требует перебора всех термов в индексе и крайне медленный. По возможности следует избегать звёздочки в начале и использовать структурированный поиск. Если нужно найти хосты, оканчивающиеся на `server01`, лучше искать `host.name:*-server01`, если такое соглашение об именовании соблюдается.

4. **Путаница между `source.ip` и `host.ip`.** В сетевых логах (firewall, DNS) `source.ip` — это IP-адрес источника пакета, который может быть маршрутизатором или прокси, а не конечным хостом. Для получения истинного хоста следует использовать `host.ip` или `host.name`, если они заполнены корректно. Типичная ошибка новичка: все сетевые события фильтровать по `source.ip`, предполагая, что это IP жертвы.

5. **Игнорирование контекста пользователя.** `user.name` может быть пустым для событий, не связанных с аутентификацией (например, сетевой трафик). Не стоит ожидать, что каждое событие имеет пользователя. При фильтрации по пользователю следует учитывать `event.category` или `event.type`.

### 3.4. Расширенные техники

Для ускорения расследований имеет смысл создавать сохранённые запросы (saved queries) или шаблоны панелей. Например, в Kibana можно сохранить Search "Host Activity Overview" с фильтром по хосту и набором визуализаций. В Datadog — создать Dashboard с шаблонной переменной `$host` для быстрого переключения.

В SOC также применяется фильтрация по хосту для исключения известных рабочих станций администраторов при поиске аномалий: `NOT host.name:"admin-ws-*"` — позволяет сфокусироваться на пользовательских машинах. Аналогично для учётных записей: исключить системные (`NT AUTHORITY\SYSTEM`, `LOCAL SERVICE`) из поиска подозрительных процессов.

Ниже приведён fenced code-блок с реальным запросом в синтаксисе Elasticsearch Query DSL (низкоуровневый), демонстрирующий комбинацию фильтров по хосту и пользователю с временным диапазоном и исключениями:

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "host.name": "webserver01" } },
        { "term": { "user.name": "jdoe" } },
        { "range": { "@timestamp": { "gte": "now-1h" } } },
        { "exists": { "field": "user.name" } }
      ],
      "must_not": [
        { "term": { "event.outcome": "success" } }
      ]
    }
  }
}
```

Этот запрос ищет события с хоста `webserver01`, связанные с пользователем `jdoe`, за последний час, но исключает успешные исходы (поле `event.outcome:success`). Такой DSL применяется в автоматизированных правилах или при интеграции с API.

## 4. Сквозной практический пример: расследование подозрительной активности

### Исходные условия

Среда: Elastic Security в составе Elastic Stack, данные из Windows Event Log (события безопасности) и Sysmon. Роль: аналитик SOC L1 получил уведомление о необычной активности на рабочей станции `HR-WS-15` от пользователя `svc-backup`. Необходимо установить, какие действия выполнялись, и не скомпрометирована ли учётная запись. Инструмент: Kibana Discover.

### Шаг 1: Получить все события с хоста за последние 6 часов

Действие: ограничить временной диапазон панелью времени (last 6 hours) и выполнить фильтр по точному имени хоста.

```kql
host.name : "HR-WS-15"
```

Ожидаемый результат: список событий, включающий как системные, так и события безопасности, связанные с этой рабочей станцией.  
Иллюстративная схема фрагмента вывода:

```json
{
  "@timestamp": "2025-03-20T09:15:30.000Z",
  "host.name": "HR-WS-15",
  "event.code": "4624",
  "event.action": "successful_login",
  "user.name": "svc-backup",
  "source.ip": "10.10.2.45",
  "_id": "abc123"
}
```

Видим успешный вход пользователя `svc-backup`. Но этого недостаточно: нужно оценить, насколько это типично.

### Шаг 2: Фильтрация по пользователю `svc-backup` на всех хостах за тот же период

Действие: убрать фильтр по хосту, оставить только пользователя, чтобы выявить другие хосты, где он появлялся.

```kql
user.name : "svc-backup" and event.category : "authentication"
```

Ожидаемый результат: алерты или события с других машин. Предположим, вывод показывает успешные входы ещё на три сервера, включая `DC01`.  
Иллюстративный фрагмент:

```json
{
  "@timestamp": "2025-03-20T09:16:00.000Z",
  "host.name": "DC01",
  "event.code": "4624",
  "user.name": "svc-backup",
  "user.domain": "CORP",
  "source.ip": "10.10.2.45"
}
```

Это настораживает: `svc-backup` обычно используется только на резервных серверах и никогда не должен входить на контроллер домена.

### Шаг 3: Поиск процессов, запущенных от имени `svc-backup` на `HR-WS-15`

Действие: сузить поиск на категории процесса и аутентификации с фильтром по хосту и пользователю.

```kql
host.name : "HR-WS-15" and user.name : "svc-backup" and (event.category : "process" or event.code : "4688")
```

Ожидаемый результат: события создания процессов (Sysmon Event ID 1 или Windows Event ID 4688).  
Иллюстративный вывод:

```json
{
  "@timestamp": "2025-03-20T09:20:01.000Z",
  "host.name": "HR-WS-15",
  "user.name": "svc-backup",
  "process.name": "cmd.exe",
  "process.command_line": "cmd.exe /c whoami",
  "event.code": "1"
}
```

Обнаружен запуск командного интерпретатора с командой `whoami` — вероятно, злоумышленник проверяет контекст безопасности после компрометации учётной записи.

### Шаг 4: Исключение легитимных активностей и уточнение временного окна

Действие: исключить известные легитимные процессы (например, `svchost.exe`) и события, не связанные с аутентификацией, чтобы отсеять шум.

```kql
host.name : "HR-WS-15" and user.name : "svc-backup" and not process.name : ("svchost.exe" or "lsass.exe") and @timestamp >= "2025-03-20T09:00:00" and @timestamp <= "2025-03-20T10:00:00"
```

Ожидаемый вывод: выявление подозрительного запуска PowerShell с попыткой скачивания файла.

```json
{
  "@timestamp": "2025-03-20T09:22:45.000Z",
  "host.name": "HR-WS-15",
  "user.name": "svc-backup",
  "process.name": "powershell.exe",
  "process.command_line": "powershell -enc ... (base64 encoded payload) ...",
  "event.code": "1"
}
```

Это подтверждает факт эксплуатации учётной записи.

### Ожидаемый вывод примера

Последовательное применение фильтров по хосту и пользователю позволило за несколько минут локализовать источник компрометации, выявить горизонтальное перемещение (вход на контроллер домена) и зафиксировать вредоносную активность. Пример демонстрирует, как грамотное комбинирование полей `host.name` и `user.name` с временными рамками и категориями событий превращает груду логов в содержательную картину инцидента.
