# Threshold: порог срабатывания

## 1. Пороговая корреляция в экосистеме SIEM: ключевые понятия и отличие от других методов

Пороговое правило (threshold rule) — детерминированный механизм корреляции событий в SIEM, который инициирует оповещение, когда накопленное значение некоторого агрегирующего показателя пересекает заданную границу за конечный временной интервал. В отличие от правил, реагирующих на единичное событие, threshold-правило ожидает накопления определённого количества однотипных или разнородных сигналов, что позволяет выделять аномалии на фоне легитимной активности и подавлять шум одиночных ложных срабатываний.

В экосистеме SIEM пороговые правила занимают промежуточное положение между простыми атомарными детектами и сложными композитными сценариями. Они не требуют строгой последовательности шагов, однако за счёт агрегации способны выявлять такие техники атакующего, как bruteforce, сканирование портов, DDoS-флуд или эксфильтрацию данных, где интенсивность или объём событий являются ключевым индикатором вредоносной активности.

Проблематика ложных срабатываний напрямую связана с пороговой корреляцией. Исследование RedLegg, процитированное в [Cyber Sierra](https://cybersierra.co/blog/reduce-false-positives-siem), показывает: **43% организаций** сообщают, что более **20%** их алертов являются ложными, а **15%** организаций фиксируют более **50%** ложных срабатываний. Неправильно выбранный порог — одна из главных причин этого явления. Слишком низкий порог плодит шум; слишком высокий пропускает реальные инциденты. Поэтому настройка порога — ключевой этап построения эффективной detection-логики.

Перед тем как углубиться в структуру правила, необходимо чётко разграничить пороговую корреляцию с другими типами корреляционных правил, используемых в современных SIEM. Таблица ниже фиксирует эти различия.

| Тип правила | Ключевые признаки | Типичный сценарий использования | Поведение при тюнинге |
|-------------|-------------------|--------------------------------|------------------------|
| **Single‑event (атомарное)** | Срабатывает на единичное событие, соответствующее сигнатуре или условию. Минимальная сложность. | Обнаружение запуска известного вредоносного процесса, доступ к критическому файлу. | Легко вызывает ложные срабатывания; требует точной настройки исключений. |
| **Threshold (пороговое)** | Анализирует агрегированные значения (количество, сумма, среднее) в скользящем или фиксированном окне. Срабатывает при превышении/понижении порога. | Подбор пароля (N неудачных попыток за 5 минут), сканирование портов (N запросов с одного IP за минуту). | Чувствительно к выбору окна и порога; может пропускать медленные атаки. |
| **Sequence (композитное)** | Обнаруживает последовательность событий в определённом порядке с учётом временных окон и/или полей корреляции. | Многошаговые атаки: фишинг → загрузка файла → выполнение PowerShell. | Высокая точность, но сложно в отладке; требует полного покрытия шагов. |
| **Anomaly / Behavioral** | Использует машинное обучение или статистические модели для отклонения от базовой линии; порог не статический, а адаптивный. | Обнаружение нетипичного доступа пользователя к ресурсу, аномальный объём трафика. | Требует длительного обучения; может генерировать труднообъяснимые алерты. |

Пороговое правило не следует путать с аномалией, основанной на динамическом пороге (baseline). В первом случае порог жёстко фиксирован администратором, во втором — вычисляется системой на основе исторических данных. На практике оба подхода часто комбинируются: например, правило срабатывает, если число событий превышает среднее значение за последнюю неделю более чем на три стандартных отклонения — это уже статистический порог, который формально является разновидностью threshold-детекта.

Таким образом, пороговые правила служат фундаментом борьбы с alert fatigue, поскольку агрегируют множество сырых событий в один инцидент с контекстом. Аналитик SOC L1 получает не сотню алертов о каждой неудачной попытке логина, а один эскалированный алерт о возможной атаке подбора, содержащий IP-адрес источника, временное окно и агрегированное число попыток. Эта способность напрямую влияет на пропускную способность аналитиков и общую эффективность SOC.

## 2. Структура и параметры порогового правила

Современное SIEM-правило порогового типа представляет собой конфигурационный объект, состоящий из нескольких логических компонентов. Независимо от платформы (Splunk, Elastic Security, Wazuh, QRadar) его можно свести к набору параметров, определяющих, *что* агрегируется, *как* и *когда* принимается решение.

Рассмотрим детально каждый компонент и оформим их в виде таблицы, которая может служить опорным «шаблоном» для создания правила.

| Компонент правила | Описание | Типичные значения / иллюстративная схема |
|-------------------|----------|--------------------------------------------|
| **Фильтр событий (Event filter)** | Определяет, какие исходные события попадают в область видимости правила. Фильтр использует поля нормализованной модели данных (source, event type, action и т.д.). | `sourcetype=linux_secure` (Splunk), `event.code:4625` (Windows), `action = "failure"`. |
| **Поле агрегации (Aggregation field)** | Поле, по которому производится подсчёт, суммирование или иная функция. Часто используется для группировки (GROUP BY). Если агрегация без группировки, считается общее значение. | `src_ip`, `user.name`, `destination.ip`. |
| **Функция агрегации (Aggregation function)** | Статистическая операция над полем значений: `count`, `sum`, `avg`, `distinct_count`, `max`, `min`, `rate`. Определяет, какая характеристика потока событий анализируется. | `count`, `distinct_count(dst_port)`, `sum(bytes_out)`. |
| **Временное окно (Window)** | Интервал, за который вычисляется агрегированное значение. Может быть фиксированным (tumbling) или скользящим (sliding). Правило проверяется по истечении окна или при поступлении каждого нового события в скользящем окне. | `5 minutes`, `1 hour`. Скользящее окно часто реализуется через поиск с `span`. |
| **Пороговое значение (Threshold)** | Численное значение или выражение, с которым сравнивается результат агрегации. Может быть константой или определяться относительно baseline. | `> 10`, `< 1`. Для сложных правил — `> avg + 3*stdev`. |
| **Направление сравнения (Comparison operator)** | Условие срабатывания: больше, меньше, равно, вне диапазона. Наиболее частый — `>`. Для индикаторов отказа используется `<`. | `>`, `<`, `>=`, `<=`. |
| **Группировка (Group-by)** | Опционально. Если задана, правило вычисляет агрегат для каждой уникальной комбинации полей группы и сравнивает с порогом независимо. Позволяет, например, считать попытки на каждый `src_ip`. | `GROUP BY src_ip, dest_host`. |
| **Дополнительные условия (Optional conditions)** | Часто дополняют порог: например, минимальное количество уникальных `dest_host` в группе, чтобы отсеять сканирование только одного хоста. Это повышает точность. | `distinct_count(target) > 3 AND count > 20`. |

Временное окно — один из наиболее критичных параметров. **Фиксированное окно (tumbling)** делит время на непересекающиеся отрезки (каждые 5 минут), и правило проверяет агрегат по окончании отрезка. Реализация проста, но возможна задержка детекта длительностью до размера окна. **Скользящее окно (sliding)** пересчитывает агрегат непрерывно, что обеспечивает более оперативное обнаружение, однако требует больших вычислительных ресурсов. Многие SIEM используют гибридный подход: периодический запуск сохранённого поиска (scheduled search) с фиксированным окном, но с перекрытием для имитации скользящего окна.

Современное развитие пороговых детектов — **адаптивные пороги**, где значение порога вычисляется динамически на основе исторических данных. Например, в [Stellar Cyber](https://ru.stellarcyber.ai/learn/siem-correlation-rules) описан подход: «the system assigns points to each session based on the models applied; when the accumulated points for a session surpass a predefined threshold, the system then triggers an alert». Здесь порог задан, но вес события может меняться моделью. Другой пример — правила на основе стандартного отклонения: если число событий за окно превышает скользящее среднее за 7 дней на N сигм, генерируется алерт. Такие правила требуют, чтобы SIEM умел вычислять baseline в реальном времени, что доступно в продвинутых платформах (Splunk Machine Learning Toolkit, Elastic’s anomaly detection jobs).

Важно учитывать проблемы, присущие временным окнам: дрейф часов на источниках событий может привести к тому, что события, случившиеся одновременно, попадут в разные окна и не вызовут срабатывания. Механизмы SIEM обычно корректируют timestamp, но при рассинхронизации более чем на несколько секунд детектирование ухудшается. Также позднее поступление событий (late arrival) может исказить агрегаты в уже пройденных окнах — платформы решают это водяными знаками и политиками опоздания.

Ниже приведена иллюстративная JSON‑подобная структура порогового правила в абстрактном представлении (не привязана к конкретному вендору):

```json
{
  "rule": {
    "name": "Brute Force Detection",
    "type": "threshold",
    "filter": {
      "query": "event.provider:ssh AND event.action:failure"
    },
    "group_by": ["source.ip"],
    "aggregation": {
      "function": "count",
      "field": "*",
      "window": "5m",
      "window_type": "sliding"
    },
    "threshold": {
      "operator": ">",
      "value": 10
    },
    "alert": {
      "severity": "high",
      "title": "Potential SSH brute force from {source.ip}"
    }
  }
}
```

Параметры правила определяют не только детект, но и то, как алерт будет эскалирован и обогащён контекстом. Глубокое понимание каждого компонента позволяет аналитику L1 не только обрабатывать такие алерты, но и при необходимости участвовать в тюнинге правил.

## 3. Практическое применение пороговых правил: сценарии, инструменты и типичные ошибки

В повседневной работе SOC L1 пороговые алерты — одни из самых частых. Их уверенная обработка требует знания, к каким именно сценариям они применяются, как выглядят в конкретных SIEM-платформах и какие подводные камни встречаются.

### Типовые сценарии использования

- **Brute force / Password spraying**: множество неудачных попыток аутентификации с одного IP на один или несколько аккаунтов. Правило считает `count` событий `login failure` с группировкой по `src_ip` за окно 5–10 минут. Порог часто устанавливают от 5 до 20, в зависимости от размера организации.
- **Сканирование портов (Port scan)**: большое количество попыток соединения с разных портов одного целевого хоста или с одного источника на множество портов. Правило использует `distinct_count(dst_port)` с порогом от 20 уникальных портов за минуту.
- **DDoS‑флуд**: аномальное количество входящих соединений на веб-сервер. Агрегация по `count` или `sum(bytes_in)`, окно — 1 минута, порог выбирается относительно базовой нагрузки (например, > 10 000 запросов).
- **Эксфильтрация данных**: объём исходящего трафика (`sum(bytes_out)`) к внешним IP за час превышает заданную величину (например, 100 МБ). Может комбинироваться с правилом на множество уникальных IP-получателей.
- **Злоупотребление привилегиями**: пользователь выполняет более N подозрительных операций (доступ к критичным ресурсам) за смену.

### Инструментарий и примеры настройки

Вне зависимости от платформы аналитик L1 часто сталкивается с необходимостью просмотреть «сырой поиск», лежащий в основе правила, чтобы верифицировать срабатывание. Рассмотрим практический пример на языке Search Processing Language (SPL) в Splunk, который можно использовать как сохранённое правило-алерт:

```spl
index=linux_auth sourcetype=linux_secure "Failed password"
| bucket _time span=5m
| stats count by _time, src_ip
| where count > 10
| table _time, src_ip, count
```

Этот запрос формирует фиксированные 5-минутные интервалы, считает число неудачных попыток с каждого IP и отбирает лишь те, где превышен порог 10. При использовании в качестве saved search с алертингом он будет запускаться периодически. Аналитик может быстро проверить, действительно ли найденные записи свидетельствуют об атаке, или это легитимная опечатка сотрудника, для чего дополнительно запрашиваются сырые логи за то же окно.

В Elastic Security аналогичное правило настраивается через `Threshold rule` в UI, где указывается:

```yaml
# пример конфигурации Elastic threshold rule (иллюстративная схема)
type: threshold
index: ["auth-logs-*"]
field: "source.ip"
threshold: { value: 15, cardinality: [] }
window: "5m"
query: "event.outcome: failure"
```

Wazuh, популярный у небольших команд, использует XML-конфигурацию правил, где пороговая логика реализуется через атрибуты `frequency` и `timeframe`:

```xml
<!-- иллюстративная схема Wazuh rule -->
<rule id="100010" level="10" frequency="8" timeframe="120">
  <if_matched_sid>5710</if_matched_sid>
  <same_source_ip />
  <description>Multiple SSH authentication failures from same source IP</description>
</rule>
```

Здесь правило срабатывает, если за 120 секунд сработает 8 дочерних событий с одинаковым IP‑адресом.

### Типичные ошибки и способы их устранения

**Ошибка 1: фиксированный порог без учёта цикличности.**
Если порог «>100 запросов» адекватен для рабочего дня, но ночью легитимный трафик падает до 5, а атака в 30 запросов остаётся незамеченной. Решение — внедрять baseline: порог как среднее за аналогичный период плюс буфер.

**Ошибка 2: игнорирование медленных атак (Slow‑brute).**
Злоумышленник может растянуть попытки на несколько часов, по одной в минуту, чтобы остаться ниже порога. Противодействие — использование более длинных окон (например, 1 час) либо комбинация с поведенческим анализом.

**Ошибка 3: threshold poisoning.**
Атака может «нагнать» легитимного трафика, чтобы двигать baseline вверх и тем самым маскировать последующую вредоносную активность. Необходимо внедрять робастные методы вычисления порога (медиана вместо среднего) или применять абсолютные защитные лимиты.

**Ошибка 4: неправильный выбор поля агрегации.**
Использование `count` без учёта того, что некоторые источники генерируют по несколько событий на одно действие. Например, одна неудачная SSH-попытка может породить два события от sshd и PAM. Решение — дедупликация по идентификатору сессии или нормализация на этапе сбора.

**Ошибка 5: группировка по IP без учёта NAT и прокси.**
Множество пользователей могут выходить в интернет через один IP, собирая на него десятки легитимных ошибок и вызывая ложное срабатывание. Справиться помогает корреляция на уровне пользовательских идентификаторов (User-ID) или включение в фильтр поля источника аутентификации.

**Тюнинг пороговых правил** — итеративный процесс, требующий взаимодействия аналитиков L1/L2 и инженеров SIEM. Аналитик L1, регулярно обрабатывая алерты, накапливает контекст: какие IP белые, какие пользователи склонны забывать пароль. Эти наблюдения оформляются в запросы на доработку правил: добавить исключения, увеличить порог для определённых подсетей, применить динамический порог. Правильно отлаженный threshold‑детект резко сокращает количество эскалаций вхолостую и позволяет сосредоточиться на реальных угрозах.

## 4. Сквозной практический пример: обнаружение атаки подбора пароля

**Исходные условия:** в SOC развёрнут Splunk в качестве SIEM. С Linux‑серверов собираются логи `/var/log/auth.log` (sourcetype=linux_secure). Задача — настроить пороговое правило для выявления SSH brute‑force и продемонстрировать его работу.

### Шаг 1. Определение базового уровня (baseline)

Перед созданием правила аналитик выполняет поиск, чтобы понять нормальную интенсивность неудачных попыток в организации. Запрос подсчитывает число ошибок с каждого IP за последние 7 дней в часовых интервалах:

```spl
index=linux_auth sourcetype=linux_secure "Failed password"
| timechart span=1h count by src_ip
```

Анализ показывает, что в среднем с одного IP приходит 0–2 ошибки в час; пики до 5 редки. На основе этого базового профиля принимается решение установить порог в **10 неудачных попыток за 5 минут** — этот уровень заведомо выше легитимных колебаний и не должен вызывать ложных срабатываний.

### Шаг 2. Создание порогового правила

В Splunk настраивается saved search с алертом. Конфигурация (представлена в JSON‑формате, используемом в API) содержит SPL-запрос и параметры триггера:

```json
{
  "name": "SSH Brute Force Detection",
  "search": "index=linux_auth sourcetype=linux_secure \"Failed password\"\n| bucket _time span=5m\n| stats count by _time, src_ip\n| where count > 10\n| table _time src_ip count",
  "alert_type": "rolling",
  "cron_schedule": "*/5 * * * *",
  "trigger.condition": "number of results > 0",
  "alert.severity": "warning",
  "alert.suppress": { "fields": ["src_ip"], "period": "10m" }
}
```

Правило запускается каждые 5 минут, обрабатывает события за последний 5‑минутный интервал и при наличии строк в результате генерирует алерт. Подавление дублей по полю `src_ip` на 10 минут предотвращает лавину одинаковых уведомлений при затяжной атаке.

### Шаг 3. Симуляция атаки и генерация логов

Для проверки используется утилита Hydra. С тестовой машины (IP иллюстративно 192.168.10.100) запускается подбор пароля:

```bash
hydra -l admin -P /usr/share/wordlists/rockyou.txt ssh://192.168.10.50
```

В лог‑файле `/var/log/auth.log` целевого сервера появляется поток записей:

```
Feb 10 14:22:01 server sshd[2143]: Failed password for admin from 192.168.10.100 port 44822 ssh2
Feb 10 14:22:02 server sshd[2145]: Failed password for admin from 192.168.10.100 port 44823 ssh2
...
(12 записей в течение 1 минуты)
```

SIEM‑агент пересылает эти события в Splunk с sourcetype `linux_secure`.

### Шаг 4. Полученный алерт

Splunk выполняет сохранённый поиск и обнаруживает, что за 5‑минутное окно количество ошибок с IP 192.168.10.100 равно 12. Генерируется алерт со следующим содержанием (упрощённый JSON‑объект из results):

```json
{
  "alert_name": "SSH Brute Force Detection",
  "timestamp": "2026-02-10T14:22:00.000Z",
  "severity": "warning",
  "event": {
    "src_ip": "192.168.10.100",
    "count": 12,
    "window_start": "2026-02-10T14:20:00.000Z",
    "window_end": "2026-02-10T14:25:00.000Z"
  },
  "dashboard_link": "https://splunk.local/app/search/..." 
}
```

Аналитик L1, обрабатывая этот алерт, видит агрегированную информацию: источник, количество попыток, временной диапазон. Правило не сработало на единичную ошибку легитимного пользователя — тем самым пороговая логика сократила шум. Аналитик может сразу перейти к ссылке на детализацию сырых событий, чтобы подтвердить атаку, и инициировать процедуру реагирования (блокировка IP, проверка хоста‑источника).

**Ожидаемый вывод:** пример демонстрирует полный цикл от анализа базовой линии до валидации правила. Корректно выбранный порог обеспечил детектирование атаки без срабатывания на рутинные инциденты. Сквозной кейс подчёркивает важность предварительного исследования, итеративного тюнинга и понимания структуры правила аналитиком первого уровня.
