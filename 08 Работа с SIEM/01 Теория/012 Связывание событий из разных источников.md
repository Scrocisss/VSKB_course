# Связывание событий из разных источников (корреляция в SIEM)

## 1. Место корреляции в конвейере обработки SIEM и базовые разграничения

Корреляция событий — это процесс выявления скрытых зависимостей между разнородными записями, позволяющий обнаруживать аномалии и атаки, незаметные при изолированном рассмотрении каждого события. В архитектуре SIEM корреляция не работает изолированно: она опирается на предварительные этапы сбора, агрегации, нормализации и может использовать результаты обогащения. Нечёткое понимание этих смежных, но функционально разных этапов — частая причина ошибок при настройке правил и ложных пропусков инцидентов.

*Сбор (ingestion)* отвечает за получение сырых логов от источников — системных журналов Windows Event Log, syslog-потоков от сетевого оборудования, API-событий облачных сервисов. *Агрегация* объединяет множество однотипных записей в сводки и метрики (например, счётчики событий по часам). *Нормализация* — критически важный переходный этап: разнородные форматы (CEF, LEEF, JSON, неструктурированный текст) приводятся к общей схеме с чётко определёнными полями: временной меткой, IP-адресом источника, именем пользователя, типом события и результатом. Без нормализации корреляционный движок не может сопоставлять события, пришедшие от разных вендоров. *Корреляция* использует нормализованные события для выявления логических, временны́х и статистических связей. *Обогащение* (Threat Intelligence, GeoIP, LDAP-атрибуты) добавляет контекст уже после или параллельно корреляции, повышая ценность алерта.

Чтобы разграничить эти понятия, удобно представить их в виде этапов конвейера обработки данных SIEM:

| Процесс | Назначение | Входные артефакты | Выходные артефакты | Пример реализации |
|---------|------------|-------------------|--------------------|-------------------|
| Сбор логов (Log Collection) | Приём сырых журналов от источников без изменения формата | Сетевые пакеты, файлы логов, API-события | Сохранённые сырые записи в индексе/хранилище | Агент Winlogbeat отправляет события 4625 в Logstash |
| Агрегация | Объединение однотипных записей для статистики и компактности | События одного типа за период | Сводные метрики, счётчики | Счётчик неудачных входов с одного IP за 5 минут |
| Нормализация | Приведение к единой схеме с унифицированными именами и форматами полей | Сырые логи в различных форматах | События с общими полями: `event.code`, `source.ip`, `user.name`, `event.outcome` | Преобразование Windows EventID 4625 в `event.outcome: failure` |
| Корреляция | Логический анализ последовательностей и комбинаций событий для выявления инцидентов | Нормализованные события, хранилище состояния правил | Алерты, инциденты | Последовательность «>5 неудач входа → успешный вход» генерирует алерт «Potential Brute Force» |
| Обогащение | Добавление контекстуальных данных из внешних систем | Событие + справочники (GeoIP, TI-фиды, CMDB) | Событие с дополнительными полями (`geo.country`, `threat.indicator`) | Добавление к IP-адресу источника географической метки и репутации из VirusTotal |

Корреляция часто путается с простым поиском или фильтрацией. Поиск по ключевым словам отвечает на вопрос «есть ли такие события?», тогда как корреляция отвечает на «образуют ли эти события известный паттерн атаки?» и способна удерживать внутреннее состояние частичного совпадения во времени.

Исходные данные для корреляционного движка — это поток событий, уже прошедших нормализацию [SIEM Logging: Components, Log Sources & Best Practices - Coralogix](https://coralogix.com/guides/siem/siem-logging). Понятие корреляции в контексте SIEM охватывает не только выявление последовательностей, но и сопоставление событий по общим ключам (IP, пользователь, сессия) — так называемую entity-based correlation [The Importance of Event Correlation Techniques in SIEM - Graylog](https://graylog.org/post/importance-of-event-correlation-techniques-in-siem).

Таким образом, корреляция превращает разрозненные сигналы от брандмауэра, контроллера домена и VPN-шлюза в единую картину атаки. Для аналитика L1 это означает, что он получает не сотни изолированных сообщений о неудачных входах, а один высокоприоритетный алерт с объяснением: «учётная запись ivanov испытала 15 неудачных попыток входа, после чего произошла успешная аутентификация с нетипичного IP».

## 2. Внутреннее устройство корреляционного движка и механика связывания событий

Корреляционный движок — это программный компонент SIEM, работающий в непрерывном режиме над потоком нормализованных событий. Его задача — проверять каждое входящее событие на соответствие набору правил и при выполнении всех условий генерировать алерт. В академической архитектуре SIEM корреляционный модуль считается ядром системы, соединяющим сбор данных с визуализацией и реагированием [Revolutionizing SIEM Security: An Innovative Correlation Engine ... - PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC11314677).

Архитектурно движок можно представить следующей схемой:

```text
[Источники логов] → [Нормализатор] → Поток событий → [Rule Engine: проверка условий, поддержка сессионного контекста] → Генератор алертов → Консоль SOC
                                   ↑
                                   └─── [Хранилище состояния частичных совпадений (in-memory или persistent state)]
```

Нормализатор преобразует сырые логи так, чтобы корреляционный движок мог оперировать единообразными полями: временная метка, IP-адрес источника, целевой IP, пользователь, тип события, результат. Например, событие неудачного входа от Windows (EventID 4625) и от Linux SSH (PAM) после нормализации принимают вид `{ "event.action": "authentication", "event.outcome": "failure" }`. Такой подход гарантирует, что правила не зависят от вендора источника [What Is Security Information and Event Management (SIEM)? - Coralogix](https://coralogix.com/guides/siem).

Наборы правил корреляции принято классифицировать по типу логики, которую они реализуют. Ниже представлены основные категории, наиболее часто встречающиеся в корпоративных SIEM (Splunk ES, Elastic Security, QRadar):

| Тип правила | Характер связывания | Типичная логика | Пример (иллюстративный) | Особенности реализации |
|-------------|---------------------|-----------------|--------------------------|------------------------|
| Последовательностное (sequence) | Временной порядок событий | `A → B → C` в пределах интервала | Неудачный вход → повышение привилегий → скачивание архива | Требует хранения промежуточного состояния до истечения окна |
| На основе счётчика и порога (threshold) | Накопление однотипных событий | `COUNT(A) > N` за `T` минут | >20 запросов к недоступному порту от одного IP за 1 минуту | Эффективно для выявления сканирований и лавин ошибок |
| Логическая комбинация (AND/OR) | Одновременное или независимое выполнение нескольких условий | `(A AND B) OR C` | (Неудачный вход из-за рубежа) И (доступ к конфиденциальной таблице БД) ИЛИ (новый процесс с правами SYSTEM) | Часто используется для сложных инсайдерских сценариев |
| Статистическое отклонение (baseline/UEBA) | Сравнение с исторической нормой | `value > baseline + 3σ` | Исходящий трафик с сервера в 5 раз выше среднего за неделю | Требует предварительного обучения модели и регулярного пересчёта baseline |
| Сущностно-ориентированное связывание (entity-based) | Связывание событий по общим атрибутам (IP, пользователь, хост) | Все события с `user.name = X` за период | Сотрудник заходит из офиса, через 10 минут его учётная запись используется в облаке из другой страны | Логика проста, но требует высокой производительности запросов к хранилищу |

Источники, детализирующие типы правил, подчёркивают, что наиболее распространёнными в SOC L1 являются последовательностные и пороговые правила, поскольку они тривиально формализуются и дают минимальный поток ложных срабатываний при аккуратной настройке [SIEM Correlation Rules: Fine-Tune Detection Logic at Scale - Cymulate](https://cymulate.com/cybersecurity-glossary/siem-correlation-rules) [SIEM Guide For Beginners - Start Here - Netwitness](https://www.netwitness.com/blog/siem-guide-for-beginners).

Механизм работы последовательностного правила можно разобрать на примере кейса «Brute Force + компрометация». Движок поддерживает состояние для каждой уникальной пары (source.ip, user.name) и окна в 5 минут. При поступлении события неудачного входа счётчик увеличивается. Если в течение окна счётчик достигает порога (например, 10), то движок запоминает, что первая часть условия выполнена, и ожидает событие успешного входа в пределах того же окна. После успешного входа правило срабатывает и порождает алерт. Если окна истекает без успеха, накопленное состояние сбрасывается. Такой подход позволяет отличать обычную опечатку пароля (1–2 ошибки и затем успех без превышения порога) от атаки с перебором, где ошибок много. Аналитики называют эту логику «сначала неудачи потоком, потом успех» [What is Security Information and Event Management (SIEM)? - SecurityScorecard](https://securityscorecard.com/blog/what-is-security-information-and-event-management-siem).

Нормализация — принципиальное условие корректного связывания. Если Windows-событие 4625 не приведено к полям `source.ip`, `user.name` и `event.outcome`, а VPN-лог использует поле `user` вместо `user.name`, правило не сможет сопоставить одни и те же сущности. Именно поэтому на этапе внедрения SIEM большое внимание уделяется парсингу и маппингу событий [Implementing a SIEM detailed Guide - Shreyash Salkade](https://www.linkedin.com/posts/shreyash-salkade-396778166_implementing-a-siem-detailed-guide-1business-activity-7283205409488728065-p-LV).

Понимание внутреннего устройства движка помогает аналитику L1 не только быстрее диагностировать причину несрабатывания правила, но и обоснованно предлагать изменения порогов или временных окон без риска выключить детектирование реальных атак.

## 3. Применение корреляции в повседневной работе SOC L1

Аналитик SOC первого уровня непосредственно взаимодействует с результатами корреляции — алертами. Его работа начинается с триажа (triage): получив оповещение, он проверяет контекст, оценивает достоверность угрозы и принимает решение об эскалации или закрытии как ложного срабатывания. При этом аналитик не просто читает готовый текст алерта, а активно использует возможности SIEM для проверки взаимосвязей вручную, если сомневается в сработавшем правиле.

Типовая процедура обработки сработавшего корреляционного правила на L1 выглядит так:

1. Получение оповещения с указанием типа инцидента, вовлечённых сущностей (IP, пользователь, хост), временной метки и поля «события-триггеры».
2. Быстрая валидация базового контекста: проверка IP-адреса по внутренним спискам разрешённых (VPN-пулы, офисные подсети); проверка рабочего статуса пользователя в корпоративном каталоге.
3. Обогащение события с помощью встроенных в SIEM таблиц GeoIP и Threat Intelligence — если на предыдущих этапах это не было сделано автоматически.
4. Поиск дополнительных индикаторов: выполнение ad-hoc запросов в SIEM за последние 1–24 часа на предмет других подозрительных действий, связанных с теми же сущностями.
5. Классификация: False Positive, True Positive с немедленной эскалацией, True Positive, но не критичный (например, тестовые действия легитимного пентеста).
6. Документирование: добавление комментария к алерту с объяснением решения, при эскалации — сбор артефактов (скриншотов, копий логов).

Ключевой инструмент аналитика — умение вручную проверять связи, не дожидаясь формального срабатывания сложных правил. Для этого используется язык запросов SIEM. Ниже показан иллюстративный SPL-запрос (Splunk), который имитирует проверку корреляции «много неудач + успех» для конкретного пользователя:

```spl
index=windows (EventID=4625 OR EventID=4624) user=ivanov
| eval outcome=if(EventID=4625, "failure", "success")
| stats count by outcome, src_ip
| where outcome="failure" AND count > 5
| append [
    search index=windows EventID=4624 user=ivanov
    | stats count by src_ip
    | where count > 0
  ]
| stats values(src_ip) as src_ips by user
```

Этот поиск не является готовым корреляционным правилом, но демонстрирует логику, заложенную в движок: он проверяет порог неудач и факт успешного входа, а затем коррелирует по IP-адресу и пользователю. Аналитик может уточнить временной диапазон, добавив `earliest=-1h`.

На практике правила корреляции описываются в форматах конкретных SIEM. Elastic Security, например, позволяет задавать правило последовательности через интерфейс или API в виде JSON-структуры, напоминающей следующую (иллюстративная схема):

```json
{
  "name": "Potential Brute Force followed by successful login",
  "rule_id": "correlation-001",
  "type": "threshold",
  "description": "Detect multiple failed logins followed by a success for the same user from the same IP within 5 minutes",
  "conditions": [
    {
      "event_category": "authentication",
      "event_outcome": "failure",
      "threshold": { "min_count": 10, "timeframe": "5m" }
    },
    {
      "event_category": "authentication",
      "event_outcome": "success",
      "timeframe": "5m"
    }
  ],
  "by_fields": ["source.ip", "user.name"]
}
```

Такой декларативный подход позволяет модифицировать пороги без изменения кода движка. От аналитика L1 не требуется писать сами правила — их готовят инженеры направления SIEM, — но он должен уметь интерпретировать их логику, чтобы в случае серии ложных срабатываний предложить изменить `min_count` или `timeframe` на основе своего понимания корпоративной аутентификации.

Наиболее частые ошибки настройки корреляции, с которыми сталкивается L1:

- **Слишком узкое окно** — не успевает накопиться порог, правило «молчит», хотя атака уже идёт.
- **Игнорирование отказов на уровне сети** — IP-адрес в событии может быть адресом балансировщика, а не реальным источником; нужно использовать исходный IP из заголовков пакетов или данные proxy.
- **Слепая зона нормализации** — события от новых систем не попадают в правило из-за отсутствия маппинга полей; первый признак — правило работает только с Windows-логами и игнорирует облачные сервисы.
- **Ложноположительный всплеск** — массовый сброс паролей пользователями после корпоративной рассылки создаёт алерты brute force. В таких случаях помогает создание списка исключений для доверенных диапазонов IP или временное занижение порога.

Аналитик, понимающий механику связывания, способен быстро отличить реальный инцидент от артефакта неудачной конфигурации и тем самым снизить нагрузку на второй уровень.

## 4. Сквозной практический пример: от сырых логов к алерту о компрометации учётной записи

**Цель** — показать полный цикл обнаружения атаки brute force на корпоративный VPN с последующей успешной аутентификацией и реакцию аналитика SOC L1.

### Исходные условия
- **Среда**: Windows Server 2019 (контроллер домена), VPN-шлюз на базе OpenVPN (логи в JSON), SIEM Elastic Stack (Elasticsearch + Kibana + файловый агент).
- **Источники логов**: `dc01` отправляет WinEventLog Security (EventID 4625, 4624); `vpn-gw` отправляет события VPN-сессий в формате JSON через Filebeat.
- **Настройка нормализации**: выполнена маппинг-схема, где `source.ip` берётся из поля `client_ip` VPN-логов или из `IpAddress` для Windows-событий (через Ingest Node). Поля `user.name` и `event.outcome` унифицированы.
- **Роль**: аналитик L1, входящий в смену.

### Шаг 1. Конфигурация корреляционного правила в SIEM
Правило задано в Elastic Security Rules (Threshold-последовательность). Конфигурация сохранена в виде API-объекта (фрагмент):

```json
{
  "name": "VPN Brute Force with successful login",
  "type": "threshold",
  "threshold": {
    "field": "source.ip",
    "value": 10,
    "cardinality": [
        { "field": "user.name", "value": 1 }
    ]
  },
  "anomaly_threshold": null,
  "query": "event.category:authentication AND event.outcome:failure",
  "filters": [],
  "from": "now-5m",
  "interval": "5m",
  "note": "After threshold exceeded, check for successful login in next 5 minutes – implemented via composite rule (not shown)"
}
```

Правило срабатывает, когда за 5 минут набирается 10 неудачных попыток с одного IP на одного пользователя; вторая часть (успешный вход) мониторится отдельным правилом sequence той же группы.

### Шаг 2. Симуляция атакующим подбора пароля
С хоста злоумышленника (IP `203.0.113.42` из недоверенной подсети) запускается утилита hydra против VPN-шлюза в течение 3 минут (15 попыток), затем вводится корректный пароль. Система генерирует следующие нормализованные события (выборочно):

Неудачная попытка (одна из многих):
```json
{
  "@timestamp": "2026-04-08T08:03:12.000Z",
  "event": { "action": "vpn-authentication", "outcome": "failure" },
  "source": { "ip": "203.0.113.42" },
  "user": { "name": "ivanov" },
  "message": "Invalid password attempt"
}
```

Через 3 минуты успешный вход:
```json
{
  "@timestamp": "2026-04-08T08:06:45.000Z",
  "event": { "action": "vpn-authentication", "outcome": "success" },
  "source": { "ip": "203.0.113.42" },
  "user": { "name": "ivanov" }
}
```

Параллельно контроллер домена фиксирует успешную сетевую аутентификацию Kerberos при обращении к ресурсам.

### Шаг 3. Срабатывание корреляционного правила
Движок фиксирует превышение порога неудач (10 из 15) в окне 08:03–08:08, затем наблюдает успешный вход в 08:06:45. Правило sequence срабатывает и генерирует алерт следующей структуры:

```json
{
  "alert_id": "alert-20260408-081500-001",
  "rule_name": "VPN Brute Force with successful login",
  "severity": "high",
  "timestamp": "2026-04-08T08:08:00.000Z",
  "source_ip": "203.0.113.42",
  "user_name": "ivanov",
  "failed_attempts": 15,
  "success_login_time": "2026-04-08T08:06:45.000Z",
  "geoip": { "country_name": "Foreign Country X" },
  "threat_intel_match": false,
  "correlation_events": [
    { "event_id": "vpn-001", "outcome": "failure" },
    { "event_id": "vpn-002", "outcome": "failure" },
    "...",
    { "event_id": "vpn-015", "outcome": "success" }
  ]
}
```

Алерт немедленно отображается на панели SOC.

### Шаг 4. Триаж аналитика L1
Аналитик открывает алерт и видит:
- источник из нетипичной страны для данной учётной записи (при обогащении получена геолокация);
- 15 неудачных попыток за 3 минуты;
- успешный вход сразу после перебора.

Для дополнительной проверки аналитик выполняет поиск в Kibana:

```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "user.name": "ivanov" } },
        { "range": { "@timestamp": { "gte": "2026-04-08T06:00:00Z", "lte": "2026-04-08T09:00:00Z" } } }
      ]
    }
  },
  "size": 100
}
```

Результаты подтверждают, что до окна атаки пользователь ivanov последний раз логинился только из офисных подсетей `10.x.x.x`. Никаких легитимных смен местоположения не было. Также аналитик проверяет, нет ли по алерту уже созданного инцидента в SOAR (кейс не открыт).

### Шаг 5. Эскалация и ожидаемый результат
Уровень аналитика L1 принимает решение об эскалации на L2, так как событие классифицируется как True Positive с высокими последствиями. Он:
- ставит статус «Escalated» в SIEM;
- блокирует IP `203.0.113.42` на граничном межсетевом экране через отработанную процедуру (запрос к Change Management);
- инициирует принудительный сброс пароля для учётной записи ivanov через Service Desk;
- добавляет в комментарий: «15 неудачных попыток с IP 203.0.113.42, затем успех. Пользователь ранее проявлял активность только из офиса. Пароль сброшен, IP заблокирован.»

Благодаря корреляции, сопоставившей молчаливые в отдельности события с VPN и контроллера домена, атака обнаружена на стадии компрометации учётной записи до попыток горизонтального перемещения или эксфильтрации данных.
