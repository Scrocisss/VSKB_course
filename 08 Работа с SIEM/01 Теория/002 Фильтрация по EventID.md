# Фильтрация по EventID в SIEM: базовый инструмент SOC‑аналитика

## Контекст и фундаментальные понятия

Фильтрация по EventID — это методика отбора событий в SIEM‑системе на основе числового идентификатора, присвоенного разработчиком операционной системы или приложения конкретному типу регистрируемой активности. В журналах Windows Event Log идентификатор события (EventID) является первичным классификатором, позволяющим аналитику мгновенно отделить рутинные действия от потенциально опасных, не просматривая всё сообщение. В контексте SOC L1 этот приём считается обязательным: 80 % начинающих аналитиков пропускают критичные следы именно потому, что не используют целенаправленный отбор по EventID, утопая в сырых гигабайтах логов [Форензика логов: гайд SOC-аналитика по Event ID и SIEM].

Основные понятия, с которыми работает аналитик, приведены ниже:

- **EventID** — целочисленный или символьный код, однозначно идентифицирующий шаблон события в рамках конкретного журнала (Security, System, Application и т. д.). Например, 4624 это «учётная запись успешно вошла в систему».
- **Event Source / Provider** — источник, генерирующий событие: «Microsoft-Windows-Security-Auditing», «Microsoft-Windows-Sysmon» и др. EventID уникальны только в паре «источник + журнал», поэтому при фильтрации важно указывать и источник.
- **Log Source** — технологический канал сбора, через который SIEM получает поток событий: WinCollect, агент на хосте, syslog‑сервер и т. п.
- **Search Query / Rule** — выражение, применяемое к индексу SIEM для отбора событий, обычно включающее условие на поле EventID.
- **Filtering Rule** — конфигурация, отбрасывающая или, наоборот, пропускающая события на этапе приёма в SIEM, до попадания в коррелятор.

### Фильтрация по EventID среди других методов

Таблица ниже показывает место фильтрации по EventID в сравнении с альтернативными способами отбора событий:

| Подход                                | Ключевые признаки                                           | Типичные примеры / поля                                    |
|---------------------------------------|------------------------------------------------------------|-----------------------------------------------------------|
| Фильтрация по EventID                 | Максимально точный и быстрый отбор по коду; требует знания числовых идентификаторов целевых событий | `EventID=4624`, `EventCode=4625`, `event_id: 1149`        |
| Фильтрация по строковому шаблону      | Поиск подстроки в неструктурированном тексте; медленнее, может давать ложные срабатывания при совпадении с другими полями | `*password*`, `*failed*`, `*cmd.exe*`                     |
| Фильтрация по категории события       | Группировка событий по функциональным блокам (аудит входа, управление учётными записями); не так детальна, как EventID | `EventCategory="Logon/Logoff"`, `Keywords=0x8010000000000000` |
| Фильтрация по важности (severity)     | Используется для быстрого выделения критических и предупредительных сообщений; не раскрывает природу активности | `Level="Error"`, `Severity>=3`                           |
| Фильтрация по временному окну         | Ограничивает набор событий анализируемым диапазоном, но не сужает типы событий; применяется как дополнительное условие | `Timestamp > now - 1h`, `@timestamp: [now-24h TO now]`    |

Из таблицы видно, что фильтрация по EventID обеспечивает наивысшую точность и скорость при условии, что аналитик помнит или имеет под рукой справочник ключевых идентификаторов. В реальной работе SOC L1 она используется как первый шаг каждого поискового запроса, после чего накладываются дополнительные условия: источник IP, имя учётной записи, тип входа и т. д.

### Зачем нужна целенаправленная фильтрация

Нефильтрованный приём всех событий в SIEM без разбора («отправим всё, потом разберёмся») ведёт к трём негативным последствиям [Event Filtering in IBM QRadar | SOC Prime]:
1. **Необоснованное потребление лицензий.** Плата за SIEM часто рассчитывается по объёму индексируемых данных (EPS — Events Per Second, GB в сутки). Если 60‑80 % потока составляют события, не используемые ни в детектировании, ни в расследованиях, они лишь тратят бюджет.
2. **Падение производительности.** Рост очереди на обработку, появление задержек, а иногда и потеря событий. В результате коррелятор может зарегистрировать инцидент с опозданием на десятки минут.
3. **Снижение отношения сигнал/шум.** Аналитику становится сложнее находить аномалии в море рутины, что прямо повышает риск пропуска атаки.

Фильтрация по EventID позволяет решать эти проблемы двумя основными способами:
- **На уровне коллектора (перед индексацией)** — отбрасывание заведомо бесполезных event‑ов ещё до того, как они попадут в хранилище SIEM. Например, можно исключить события информационного характера (EventID 12 — запуск системы, 43 — изменение часового пояса и т. п.).
- **На уровне поискового запроса** — динамическое отсеивание нерелевантных событий во время интерактивного анализа инцидента. Здесь аналитик, напротив, указывает только те EventID, которые характерны для расследуемой атаки (например, 4624, 4625, 4672, 4688).

Таким образом, фильтрация по EventID — это не единственный, но универсальный примитив, одинаково применимый в конфигурациях сбора, правилах корреляции и ad‑hoc запросах.

## Внутреннее устройство и классификация ключевых EventID

Для осмысленного применения фильтрации аналитик должен понимать, какие именно EventID несут полезную нагрузку для типовых сценариев SOC. Несмотря на то что Windows регистрирует тысячи событий, на практике уверенный разбор 50‑60 идентификаторов закрывает более 90 % потребностей мониторинга безопасности [Top 50 Windows SIEM Use Cases & Event IDs | LinkedIn].

### События Sysmon как расширение EventID

Особое место занимает источник «Microsoft-Windows-Sysmon», предоставляющий детальную информацию о процессах, сетевых соединениях и изменениях файловой системы. Его EventID нумеруются от 1 до 25, но наиболее востребованы для фильтрации:

- **EventID 1** — создание процесса (аналог 4688, но с дополнительными полями, включая хеши файла, командную строку, GUID процесса).
- **EventID 3** — сетевое соединение.
- **EventID 6** — загрузка драйвера.
- **EventID 7** — загрузка образа (DLL).
- **EventID 8** — создание удалённого потока (используется для детектирования инъекций).
- **EventID 11** — создание файла в отслеживаемых каталогах.
- **EventID 12, 13, 14** — события реестра.
- **EventID 15** — создание альтернативного потока (ADS).

При построении фильтров коллектора часто указывают диапазоны идентификаторов через тире: например, `Sysmon 1-3; Ossec 55,4667` (пример из документации QRadar [Event Filtering in IBM QRadar | SOC Prime]).

### Linux‑логи и EventID

Хотя термин EventID устойчиво ассоциирован с операционными системами Windows, аналогичный подход применим и к журналам Linux. В syslog‑сообщениях роль EventID выполняют числовые коды после идентификатора отправляющего процесса (PID) или ключевые поля, уникально определяющие тип события. В ssh‑логах, например, успешный вход часто маркируется строкой `Accepted`, а неудачный — `Failed`. В средах, где используется Ossec, задействуются собственные идентификаторы, такие как 55 (подозрительное чтение файла) или 4667 (доступ к файлу в чувствительной директории). Для SOC L1, работающего в смешанных ландшафтах, полезно выработать единый подход к именованию и группировке, используя нормализацию данных — приведение их к общей схеме с полем `event_id`.

### Как SIEM индексирует и использует EventID

Внутреннее устройство SIEM предусматривает парсинг входящих событий в пары «ключ‑значение». Поле `EventID` (иногда называемое `EventCode`, `event_id`, `EID`, `event_id_number`) после парсинга попадает в индекс вместе с остальными полями. Благодаря этому все современные SIEM (MaxPatrol, IBM QRadar, Splunk, FortiSIEM, Panther) позволяют выполнять фильтрацию с использованием операторов точного соответствия, диапазона или регулярного выражения прямо по этому полю.

Типичная схема прохождения события и места, где может быть применена фильтрация по EventID, показана ниже:

```text
Источник (Windows, Linux)
 │
 ├─> 1. Фильтрация на источнике (Event Subscription, Sysmon config)  ←─ EventID
 │     (часть событий не покидает хост)
 │
 ├─> 2. Агент/коллектор (WinCollect, Fluentd, Beats)                ←─ EventID (исключение/включение)
 │     (отбрасывание высокообъёмных и бесполезных идентификаторов)
 │
 ├─> 3. Индекс SIEM (QRadar, MaxPatrol, Splunk indexer)              ←─ поле EventID индексируется
 │
 ├─> 4. Поисковый запрос или корреляционное правило                   ←─ EventID = 4625
 │     (онлайн‑фильтрация для анализа, алертинга)
 │
 ├─> 5. Вывод результатов аналитику
```

Из этой схемы видно, что аналитик большую часть времени взаимодействует только с последним звеном — поисковым запросом, однако понимание возможностей фильтрации на предыдущих стадиях помогает быстрее разобраться в конфигурации SIEM‑платформы и решить проблему «не вижу событие в запросе».

## Применение и практическая работа с фильтрацией по EventID

Практическая эксплуатация фильтрации по EventID в SOC распадается на два основных сценария: настройка правил сбора (пресейл‑фильтрация) и написание поисковых выражений для расследования. В обоих случаях синтаксис и интерфейс зависят от конкретного продукта, однако логика остаётся одинаковой.

### Настройка фильтрации на коллекторе (на примере QRadar WinCollect)

IBM QRadar использует агент WinCollect для сбора Windows‑событий. Чтобы исключить ненужные идентификаторы, администратор добавляет поименованный фильтр в конфигурационный файл агента. Документация рекомендует предварительно проанализировать поток данных и определить, какие EventID генерируют наибольший объём шума [Event Filtering in IBM QRadar | SOC Prime].

Иллюстративная конфигурация (фрагмент XML‑профиля WinCollect):

```XML
<LogSource name="Windows Security Log">
  <EventFilter filter="Include">
    <EventID>4624</EventID>
    <EventID>4625</EventID>
    <EventID>4672</EventID>
    <EventID>4688</EventID>
  </EventFilter>
</LogSource>
```

Если требуется исключить конкретный диапазон, применяют директиву `Exclude` и задают интервалы через дефис. Например, для Sysmon оставляют только события процессов, сетевых соединений и загрузки образа:

```XML
<LogSource name="Sysmon">
  <EventFilter filter="Exclude">
    <EventID>7-10</EventID>
    <EventID>12-15</EventID>
    <EventID>17-255</EventID>
  </EventFilter>
</LogSource>
```

Применение такого фильтра приводит к тому, что в индекс SIEM попадают только EventID 1–6, 11, 16 — те, что наиболее важны для детектирования.

### Построение поисковых запросов с EventID в разных SIEM

После того как данные оказались в индексе, SOC-аналитик выполняет интерактивные запросы для поиска индикаторов компрометации. Ниже приведены синтаксические конструкции основных SIEM‑продуктов, работающих на российском и международном рынках.

**IBM QRadar — AQL (Ariel Query Language)**  
Выборка успешно вошедших пользователей с указанием типа входа и исходного IP:

```AQL
SELECT DATEFORMAT(startTime, 'YYYY-MM-dd HH:mm:ss') AS Time,
       "sourceIP" AS Source_IP,
       "username" AS User,
       "logontype" AS LogonType
FROM events
WHERE "EventID" = '4624'
  AND "category" = 'Logon/Logoff'
  AND startTime > NOW() - 1 HOURS
ORDER BY Time DESC
LAST 1000
```

Фильтрация по EventID здесь выполняется оператором точного равенства `= '4624'`. Допустимы также операторы `IN ()` и `LIKE '%4624%'` для нечёткого поиска.

**MaxPatrol SIEM (PT SIEM) — язык KQL (PT Query Language)**  
Аналогичный запрос для успешных входов за последний час:

```KQL
event EventID = 4624
| filter LogonType in (2,10)
| rename EventTime as Time, SourceNetworkAddress as SourceIP, TargetUserName as User
| fields Time, SourceIP, User, LogonType
| sort Time desc
| take 500
```

Фильтрация на уровне события задаётся в первой строке: `event EventID = 4624`. Можно комбинировать с отрицанием: `event EventID != 4624`.

**Splunk — SPL**  
Типовой search‑запрос для мониторинга аномальных входов:

```spl
index=windows EventCode=4624
| eval LogonType=case(LogonType==2,"Interactive", LogonType==3,"Network", LogonType==10,"RemoteInteractive")
| stats count by Account_Name, Source_Network_Address, LogonType
| where count > 10
| sort - count
```

В Splunk поле EventID из журнала Windows обычно маппится в поле `EventCode`. Условие `EventCode=4624` задаёт фильтрацию ещё на этапе выборки из индекса.

**FortiSIEM — Advanced Search (ClickHouse‑диалект)**  
Пример из официальной документации [FortiSIEM 7.3: Advanced Search]:

```sql
SELECT
  reptDevName AS Device,
  eventType,
  srcIpAddr AS Source_IP,
  destIpAddr AS Destination_IP,
  count() AS EventCount
FROM phEventview
WHERE eventType LIKE '%4624%'
  AND phRecvTime >= now() - INTERVAL 1 DAY
GROUP BY Device, eventType, Source_IP, Destination_IP
ORDER BY EventCount DESC
```

Обратите внимание: в FortiSIEM поле `eventType` является строкой, содержащей имя события, включая числовой идентификатор, поэтому фильтрацию выполняют через оператор `LIKE '%4624%'`. Аналитик может дополнительно уточнить условие, используя регулярные выражения или конкатенацию.

### Включение и исключение в поисковых запросах: распространённые приёмы

Фильтрация по EventID не ограничивается положительным условием. В ряде случаев необходимо исключить легитимные события той же природы, что и аномалия. Например, при поиске подозрительных подключений по удалённому рабочему столу аналитик хочет видеть только неизвестные IP, исключая корпоративный VPN‑диапазон:

```AQL
SELECT * FROM events
WHERE "EventID" = '4624'
  AND "logontype" = '10'
  AND NOT ("sourceIP" LIKE '10.0.0.%' OR "sourceIP" LIKE '192.168.%')
```

Подобный подход позволяет сконцентрироваться на выбросах и не отвлекаться на штатную активность.

### Типичные ошибки и способы их избежать

1. **Абсолютизация исключений.** Удаление всех событий с определённым EventID на уровне коллектора без оглядки на контекст может скрыть вредоносную активность. Например, EventID 5156 (фильтрация сетевого трафика Windows Filtering Platform) генерирует огромный объём записей, но иногда он — единственный источник данных о заблокированных соединениях эксплоита. Решение: не удалять полностью, а настраивать конденсацию или хранение в дешёвом холодном хранилище.
2. **Жёсткий match вместо поиска по диапазону.** Если в запросе указано `EventID=4624`, а реальный идентификатор пришёл от Sysmon как `EventID=4624` — совпадения не будет, потому что в системах с разными источниками идентификаторы могут пересекаться. Всегда добавляйте условие на источник: `EventSource="Microsoft-Windows-Security-Auditing"`.
3. **Забывание о текстовом представлении.** Некоторые Siemens (включая MaxPatrol) позволяют указывать EventID как строку, поэтому запрос `EventID = 4624` может не сработать, если в индексе поле хранится как `"4624"`. Проверяйте тип данных и используйте явное приведение.
4. **Недостаточная проверка после добавления фильтра.** После внедрения фильтра на коллекторе обязательно выполняйте разностный анализ: какое количество и каких именно событий перестало поступать. Хорошей практикой является запуск отфильтрованного и нефильтрованного потоков в тестовую среду с последующим сравнением корреляционных срабатываний.

## Сквозной практический пример: детектирование брутфорса через EventID 4625

Ниже приведён типовой инцидент, который SOC‑аналитик уровня L1 отрабатывает с помощью фильтрации по EventID. Сценарий взят из практики работы с MaxPatrol SIEM, но шаги легко переносятся на другие платформы.

### Исходные условия
- SIEM: MaxPatrol 10.
- Источник событий: контроллер домена Windows Server 2022, журнал Security.
- Симптом: сработало встроенное правило «Множественные неудачные попытки входа» на основе EventID 4625.
- Задача: определить источник, целевую учётную запись и характер атаки.

### Шаг 1. Подтверждение факта атаки: базовый фильтр по EventID и временному окну
Аналитик открывает поисковый интерфейс и извлекает все события 4625 (неудачный вход) за последние 30 минут, когда, согласно алерту, зафиксирована вспышка ошибок.

```KQL
event EventID = 4625
| filter EventTime > now() - 30m
| fields EventTime, SourceNetworkAddress, TargetUserName, Domain, FailureReason, WorkstationName
| sort EventTime desc
| take 1000
```

Ожидаемый вывод — несколько сотен записей с одним и тем же IP‑адресом в поле `SourceNetworkAddress` (`192.0.2.55` — иллюстративный адрес) и несколькими целевыми учётными записями (`svc_backup`, `operator`, `admin`). Код ошибки `FailureReason` = `0xC000006D` (неверное имя пользователя или пароль) и `0xC0000234` (учётная запись заблокирована).

### Шаг 2. Группировка по источнику и учётной записи для оценки масштаба
Чтобы понять, является ли атака перебором по одной учётной записи или по словарю, аналитик строит агрегацию:

```KQL
event EventID = 4625
| filter EventTime > now() - 30m
| fields SourceNetworkAddress, TargetUserName
| stats count() as AttemptCount by SourceNetworkAddress, TargetUserName
| sort AttemptCount desc
```

Вывод:
```text
SourceNetworkAddress  TargetUserName   AttemptCount
192.0.2.55            svc_backup       187
192.0.2.55            operator          73
192.0.2.55            admin             22
```

Картина характерна для атаки Password Spraying или последовательного Brute‑force: множество попыток к ограниченному числу учётных записей с одного узла.

### Шаг 3. Проверка связанных событий — переход к успешным входам (EventID 4624)
Обнаружив, что для учётной записи `svc_backup` наступила блокировка (EventID 4740), аналитик проверяет, не было ли успешного входа с того же IP ранее:

```KQL
event EventID = 4624
| filter SourceNetworkAddress = "192.0.2.55"
| filter EventTime > now() - 1h
| fields EventTime, TargetUserName, LogonType, SourceNetworkAddress
| sort EventTime desc
```

Результат показывает одну запись:
```text
EventTime               TargetUserName  LogonType  SourceNetworkAddress
2025-01-15 14:08:03     svc_backup      3          192.0.2.55
```
Это означает, что незадолго до пика неудачных попыток злоумышленник однажды вошёл успешно по сети (LogonType=3). Аналитик немедленно передаёт инцидент на второй уровень для изоляции учётной записи и хоста‑источника.

### Шаг 4. Поиск индикаторов компрометации системы (Sysmon EventID 1)
На хосте, где зафиксирован успешный вход, аналитик дополнительно проверяет процессы, созданные в интересующий временной интервал, используя фильтр по Sysmon EventID 1:

```KQL
event EventID = 1
| filter Device = "DC01" and EventTime between ("2025-01-15 14:00:00", "2025-01-15 14:15:00")
| fields EventTime, Image, CommandLine, ParentImage, User
| sort EventTime asc
```

Вывод показывает запуск `cmd.exe` из процесса `wsmprovhost.exe` (WinRM), что объясняет сетевой вход. Данные передаются как артефакты для эскалации.

### Ожидаемый итог

Пример демонстрирует, как грамотная комбинация фильтров по EventID (4625, 4624, 4740, 1) позволяет SOC‑аналитику первого уровня за считанные минуты подтвердить факт атаки, выявить источник и скомпрометированную учётную запись, а также собрать минимально необходимый набор данных для передачи на вышестоящий уровень реагирования. Ключевым фактором скорости выступает именно фильтрация по EventID — без неё пришлось бы просматривать тысячи событий регистрации и доступа к объектам, что радикально замедлило бы реакцию.
