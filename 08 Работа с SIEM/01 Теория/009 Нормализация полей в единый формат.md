# Нормализация полей в единый формат для SIEM

## 1. Сущность нормализации в конвейере SIEM: унификация, а не агрегация

Нормализация (data normalization) в контексте SIEM — это процесс приведения разнородных форматов записей журналов (логов), поступающих от множества источников, к единому внутреннему представлению. Единый формат необходим для последующей унифицированной обработки, хранения, визуализации и, главное, корреляции событий. Без нормализации каждое правило корреляции, каждый поисковый запрос и каждая панель аналитики должны были бы учитывать особенности синтаксиса конкретного источника, что сделало бы SIEM-систему неработоспособной при сколь-либо разнородной инфраструктуре.

Важно разграничить нормализацию со смежными процессами в SIEM-конвейере. Их часто путают из-за того, что все они направлены на сокращение избыточности и повышение информативности данных, однако решают разные задачи.

**Сравнительная таблица: нормализация и смежные процессы**

| Процесс           | Назначение                                                                                  | Входные данные                          | Выходные данные                         | Типичный метод                                                               |
|-------------------|----------------------------------------------------------------------------------------------|-----------------------------------------|-----------------------------------------|-------------------------------------------------------------------------------|
| Нормализация      | Приведение к единой схеме полей и форматам значений                                           | Сырые логи в различных форматах (syslog, JSON, XML, plain text) | Структурированные события с унифицированными именами полей (`src_ip`, `event.action`, `timestamp`) | Парсинг, маппинг полей, преобразование типов данных (строка → IP, временная метка) |
| Агрегация         | Объединение близких по признакам событий для снижения объёма и выделения значимых фактов       | Нормализованные (реже — сырые) события  | Сгруппированные записи (например, «5 неудачных входов с IP X за 60 секунд») | Группировка по ключу, счётчики, временные окна, операция сжатия             |
| Корреляция        | Выявление скрытых взаимосвязей между разнородными событиями на основе правил или моделей      | Нормализованные события, обогащённые контекстом | Инциденты, алерты, срабатывания правил (например, «Brute force + успешный вход») | Правила последовательности, join по полям, статистический анализ            |
| Фильтрация        | Удаление избыточных или нерелевантных событий из потока                                        | Сырые или нормализованные события       | Сокращённый поток событий, направляемый на хранение и корреляцию             | Чёрные/белые списки, пороговые фильтры, исключение по EventID               |
| Обогащение (enrichment) | Дополнение события внешним контекстом (геолокация по IP, данные об активе, репутация)         | Нормализованное событие                 | Событие с дополнительными полями (`geo.country`, `asset.criticality`)        | Запрос к threat intelligence, LDAP, CMDB                                    |

Нормализация предшествует агрегации, корреляции и обогащению. Без качественной нормализации агрегация может быть выполнена по ошибочным или несопоставимым ключам, корреляция даст ложные срабатывания, а обогащение не найдёт соответствий в справочниках. В классической модели SIEM, описанной в том числе в русскоязычных источниках, нормализация стоит первой стадией обработки после сбора, наряду с фильтрацией и классификацией.

Таким образом, нормализация — это не просто «перевод логов в JSON», а создание семантически единой модели данных, где поле `source_ip` означает IP-адрес источника пакета, независимо от того, пришло ли исходное событие от межсетевого экрана (запись `SRC=192.168.1.1`), от прокси-сервера (`client_ip`) или от веб-приложения (REMOTE_ADDR в логах Apache). Такая модель — фундамент, на котором строится вся последующая SIEM-аналитика.

## 2. Внутреннее устройство конвейера нормализации

Нормализация — это не одно действие, а многоэтапный конвейер, выполняемый SIEM-платформой или коллектором логов на этапе приёма данных. В современных системах (таких как Datadog Cloud SIEM, Google Chronicle, Elastic Security) этот конвейер чаще всего реализован как набор настраиваемых процессоров, работающих по схеме «приемник → парсер → трансформер → выход в общую схему». Рассмотрим стандартные стадии, опираясь на общепринятые в индустрии описания.

**Таблица этапов нормализации с примерами**

| Этап                          | Задача                                                                 | Входные данные                                         | Выходные данные                                                            | Инструменты/механизмы                         | Пример действия                                                                                                   |
|-------------------------------|------------------------------------------------------------------------|--------------------------------------------------------|----------------------------------------------------------------------------|-----------------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| 1. Приём (ingestion)          | Получение сырого потока логов от источника                             | Поток syslog-сообщений, файл, API-вызов                | Сырое событие с метаданными источника (host, source_type)                 | Listener-ы на портах, агенты                  | Получение сообщения `<134>1 2024-03-15T10:05:23Z firewall.local filterlog: … ACT=block …`                           |
| 2. Предварительный разбор     | Идентификация формата и выделение грубой структуры (syslog header, JSON body) | Сырое событие                                          | Событие с отделёнными метаданными (facility, severity, программа) и телом | Встроенные парсеры syslog, JSON, key-value      | Выделение `pri=134`, `timestamp=2024-03-15T10:05:23Z`, `host=firewall.local`, `program=filterlog`, `message=ACT=block…` |
| 3. Глубокий парсинг тела      | Извлечение индивидуальных пар «ключ-значение» или полей из тела сообщения | Тело сообщения (текст или структурированная строка)      | Набор полей с временными именами, отражающими оригинальный синтаксис       | Grok-шаблоны, регулярные выражения, dissect    | Из `ACT=block SRC=192.168.1.100 DST=10.0.0.1 PROTO=TCP` получаем `ACT=block, SRC=192.168.1.100, DST=10.0.0.1, PROTO=TCP` |
| 4. Маппинг полей (field mapping) | Переименование временных полей в поля целевой унифицированной модели данных | Набор полей с исходными ключами                        | Событие с унифицированными именами (например, `source.ip`, `event.action`) | Таблицы маппинга, lookup, статические правила  | `SRC` → `source.ip`, `DST` → `destination.ip`, `ACT` → `event.action` (приведение значения `block` к `denied`)     |
| 5. Преобразование типов и значений | Приведение значений полей к единому формату (временные метки в ISO 8601, IP-адреса в стандартную нотацию, нормализация действий) | Сопоставленные поля с «сырыми» значениями               | Поля с корректными типами данных (date, ip, keyword)                       | Конвертеры дат, парсеры IP, подстановки (dictionary) | Текстовую строку `2024-03-15T10:05:23Z` — в timestamp-объект; значение `block` — в унифицированный action `denied`   |
| 6. Выходной формат / сериализация | Формирование финального события с полной структурой согласно выбранной модели (ECS, OCSF, UDM) и запись в хранилище | Нормализованный набор полей                            | Индексированное событие в хранилище SIEM, готовое к поиску и корреляции    | Сериализатор в JSON, Avro и т.п.               | Готовый JSON-объект с полями `@timestamp`, `source`, `destination`, `network`, `event` и т.д.                       |

Ключевая особенность этапа 4 — отказ от лексики конкретного вендора в пользу общей модели. Именно на этом этапе SIEM-инженер определяет, что `proto=6` (числовой код из логов IPTABLES) и `PROTO=TCP` (из логов pfSense) должны быть преобразованы в одинаковое значение `network.transport: "tcp"` с опусканием номера протокола.

В качестве целевых моделей данных индустрия предлагает несколько открытых схем. Среди лидеров:

- **Elastic Common Schema (ECS)** — применяется в экосистеме Elastic (Elasticsearch/Kibana), делит поля по категориям: `source.*`, `destination.*`, `event.*`, `network.*`, `user.*` и т.д.
- **Open Cybersecurity Schema Framework (OCSF)** — продвигается Datadog, AWS, Splunk и другими; строго определяет классы событий (Authentication, Detection Finding, Network Activity) и атрибуты, стремясь к единому языку для XDR и SIEM.
- **Google Chronicle Unified Data Model (UDM)** — используется Google SecOps; задаёт фундаментальные сущности, такие как `principal`, `target`, `security_result`, `network`.

Выбор конкретной модели зависит от платформы, но принцип остаётся неизменным: все события после нормализации должны иметь предсказуемый набор полей с однозначной семантикой.

## 3. Практическое применение: конфигурации парсеров и работа со схемами

В реальной SIEM-среде нормализация реализуется через конвейеры обработки, задаваемые инженерами в виде конфигурационных файлов или через графические интерфейсы. Можно выделить два доминирующих подхода:

1. **Grok-подобные правила** (Logstash, Elastic Agent, Graylog, rsyslog) — основаны на библиотеке регулярных выражений, где именованные группы (`%{IP:src_ip}`) одновременно извлекают и типизируют поля.
2. **Маппинг по образцу с встроенными парсерами** (NXLog с модулями xm_xml, xm_json, xm_kv; Datadog OCSF processor) — сначала структурирует вход с помощью специализированного парсера, затем применяет таблицы маппинга.

Ниже приведён пример конфигурации нормализации для NXLog (на основе подхода, описанного в документации NXLog), решающий задачу приведения логов брандмауэра pfSense к общей схеме. Входные данные — сообщения формата key=value после syslog-заголовка.

```nginx
<Extension _json>
    Module   xm_json
</Extension>

<Input tcp_syslog>
    Module   im_tcp
    Host     0.0.0.0
    Port     514
    InputType Syslog_TCP
    Exec     parse_syslog();         # Парсинг syslog-заголовка
</Input>

<Processor normalize_firewall>
    Module   pm_transformer
    # Извлекаем пары key=value из $Message
    Exec     if $Message =~ /ACT=(\S+)\s+SRC=(\S+)\s+DST=(\S+)\s+PROTO=(\S+)\s+SPT=(\S+)\s+DPT=(\S+)\s+/
             {
                 $event.action = $1;
                 $source.ip    = $2;
                 $destination.ip = $3;
                 $network.transport = lc($4);  # tcp, udp
                 $source.port      = integer($5);
                 $destination.port = integer($6);
             }
    # Преобразование значений событий в унифицированные
    Exec     if $event.action == 'block' $event.action = 'denied';
    Exec     if $event.action == 'pass'  $event.action = 'allowed';
    # Временная метка уже в $EventTime после parse_syslog()
</Processor>

<Output elastic_ecs>
    Module   om_elasticsearch
    URL      https://elasticsearch:9200
    Index    ecs-firewall-*
    OutputType  json
    Exec     to_json();
</Output>
```

В этом упрощённом, но показательном фрагменте решены основные задачи нормализации: извлечены поля, произведено отображение (маппинг) с переименованием ключей (`SRC` → `source.ip`), выполнено преобразование типов и значений (строковые порты — в целочисленный тип, `block` — в стандартизированное `denied`). После такого процессора события готовы для записи в индекс Elasticsearch в соответствии с ECS.

Аналогичную цепочку можно построить в виде grok-фильтра для конвейера Logstash:

```ruby
filter {
  grok {
    match => { "message" => "ACT=%{WORD:temp_action}\s+SRC=%{IP:source.ip}\s+DST=%{IP:destination.ip}\s+PROTO=%{WORD:temp_proto}\s+SPT=%{INT:source.port}\s+DPT=%{INT:destination.port}" }
  }
  mutate {
    add_field => { "network.transport" => "%{temp_proto}" }
    replace  => { "temp_action" => "denied" } if [temp_action] == "block"
  }
  mutate {
    convert => { "source.port" => "integer" "destination.port" => "integer" }
    lowercase => [ "network.transport" ]
  }
}
```

Ключевая мысль: нормализация не обязательно должна быть реализована «глобальным парсером, понимающим всё». В больших средах конвейер декомпозируют — один набор правил для сетевых устройств, другой — для серверов аутентификации, третий — для веб-приложений. Однако все они приводят события к единой модели. Это позволяет аналитику SOC первого уровня (L1) писать запрос вроде:

```kibana
source.ip:10.5.5.5 AND event.action:denied
```

и получать результаты одновременно из логов межсетевого экрана, файлового аудита и системы предотвращения вторжений, не задумываясь о том, как именно в каждом из них выглядит «запрет доступа».

Типичная ошибка при настройке нормализации — оставление числовых кодов действий без перевода в человекочитаемые метки (например, код выхода SSH, числовые ID событий Windows). Это вынуждает аналитика обращаться к справочникам в разгар инцидента, что снижает скорость сортировки алертов. Рекомендуется всегда добавлять текстовые категории на этапе преобразования.

## 4. Сквозной практический пример: унификация логов межсетевого экрана и веб-сервера для обнаружения атаки

**Исходные условия**:  
В небольшой инфраструктуре работают межсетевой экран (pfSense) и внутренний веб-сервер (nginx). Администратор настроил отправку логов обоих источников в SIEM-коллектор (по syslog и filebeat соответственно). Задача аналитика L1 — проверить подозрительный IP-адрес `192.168.50.12`, который по данным Threat Intelligence фигурирует в недавних атаках.

**Шаг 1. Получение сырых логов**  
Логи межсетевого экрана приходят в формате syslog с телом в виде набора пар `key=value`:

```log
<134>1 2024-05-22T08:15:32Z fw.local filterlog: 5,16777216,,,0,pppoe0,match,block,in,4,0x0,,1,10967,0,DPT=22,PROTO=TCP,SPT=54321,SRC=192.168.50.12,DST=10.0.0.5,ACT=block
```

Логи nginx отправляются в комбинированном формате (combined log format) через Filebeat:

```log
192.168.50.12 - - [22/May/2024:08:15:34 +0000] "GET /admin/login.php HTTP/1.1" 403 1234 "https://portal.local/" "Mozilla/5.0 (X11; Linux x86_64)"
```

**Шаг 2. Нормализация: конфигурация парсера SIEM**  
Применим конвейер, аналогичный описанному в разделе 3. Для брандмауэра используем grok-правило, извлекающее все значимые поля. Итоговая конфигурация (фрагмент):

```ruby
filter {
  if [source][type] == "firewall" {
    grok {
      match => { "message" => "DPT=%{INT:destination.port},PROTO=%{WORD:temp_proto},SPT=%{INT:source.port},SRC=%{IP:source.ip},DST=%{IP:destination.ip},ACT=%{WORD:temp_action}" }
    }
    mutate {
      add_field => { "network.transport" => "%{temp_proto}" }
      replace   => { "temp_action" => "denied" } if [temp_action] == "block"
    }
    mutate {
      convert   => { "source.port" => "integer", "destination.port" => "integer" }
      lowercase => [ "network.transport" ]
      add_field => { "event.module" => "firewall", "event.kind" => "alert" }
    }
  }
  
  if [source][type] == "nginx" {
    grok {
      match => { "message" => "%{IP:source.ip} %{HTTPDUSER:ident} %{USER:auth} \[%{HTTPDATE:date}\] \"%{WORD:http.method} %{URIPATHPARAM:url.path} HTTP/%{NUMBER:http.version}\" %{INT:http.response.code} %{INT:http.response.bytes} \"%{GREEDYDATA:http.referrer}\" \"%{GREEDYDATA:user_agent}\"" }
    }
    mutate {
      add_field => { "event.module" => "web", "event.kind" => "event" }
      rename    => { "date" => "@timestamp" }
    }
  }
}
```

**Шаг 3. Результат нормализации**  
После прохождения конвейера оба события выглядят как два структурированных JSON-объекта с общей системой координат:

Событие от брандмауэра (иллюстративная схема):

```json
{
  "@timestamp":          "2024-05-22T08:15:32Z",
  "event": {
    "module":            "firewall",
    "kind":              "alert",
    "action":            "denied"
  },
  "source": { "ip": "192.168.50.12", "port": 54321 },
  "destination": { "ip": "10.0.0.5", "port": 22 },
  "network": { "transport": "tcp" },
  "message":             "DPT=22,PROTO=TCP,SPT=54321,SRC=192.168.50.12,DST=10.0.0.5,ACT=block"
}
```

Событие от nginx:

```json
{
  "@timestamp":          "2024-05-22T08:15:34Z",
  "event": {
    "module":            "web",
    "kind":              "event"
  },
  "source": { "ip": "192.168.50.12" },
  "url":    { "path":    "/admin/login.php" },
  "http": {
    "method":            "GET",
    "response": {
      "code":            403,
      "bytes":           1234
    }
  },
  "user_agent":          "Mozilla/5.0 (X11; Linux x86_64)",
  "message":             "192.168.50.12 - - [22/May/2024:08:15:34 +0000] \"GET /admin/login.php HTTP/1.1\" 403 1234"
}
```

Оба события содержат поле `source.ip` с идентичным значением.

**Шаг 4. Корреляционный поиск**  
Аналитик выполняет запрос в интерфейсе SIEM (Kibana, язык запросов KQL) для IP-адреса, который проверяется:

```kql
source.ip:"192.168.50.12"
```

Результат объединяет оба события в единой временной ленте. Последовательность просматривается и интерпретируется:

1. В 08:15:32 межсетевой экран зафиксировал блокировку TCP-соединения на порт 22 (`destination.port:22`) с хоста `192.168.50.12`, протокол — SSH. Действие `denied` указывает, что попытка не была пропущена.
2. Через две секунды тот же IP получает ответ 403 Forbidden от веб-сервера на запрос `/admin/login.php`.

Вывод: с адреса `192.168.50.12` была предпринята попытка сканирования или эксплуатации сервиса SSH, немедленно после которой атакующий переключился на веб-приложение, вероятно пытаясь подобрать учётные данные к административной панели. Без нормализации такие события находились бы в двух разных индексах с различными схемами полей, и аналитику пришлось бы вручную сопоставлять время и адрес в двух разных вкладках. Нормализация превратила разнородные записи в единый поток инцидента, позволив связать два, казалось бы, независимых события и идентифицировать целенаправленную атаку. Это и есть практическая ценность процесса нормализации полей для специалиста SOC L1.
