# Сбор событий из множества источников: агрегация в SIEM

## 1. Агрегация событий в SIEM: контекст и базовые понятия
Агрегация в контексте SIEM — это процесс перемещения и централизованного накопления логов и событий от тысяч разнородных источников в единое хранилище. Она не сводится к простому «включению приёма логов». Агрегация решает задачу консолидации данных, которые изначально распределены по множеству систем, форматов и протоколов, обеспечивая базу для всех последующих аналитических этапов: нормализации, корреляции, визуализации и долгосрочного хранения. Без надёжной агрегации SIEM-система теряет ценность — невозможно выстроить сквозную картину инцидента, если данных от межсетевого экрана, контроллера домена и конечной точки нет на одном аналитическом слое.

В профессиональной литературе агрегацию часто путают с другими этапами жизненного цикла событий. Чтобы сразу снять неоднозначность, зафиксируем базовые понятия.

- **Сбор логов (log collection)** — технический акт получения данных от конкретного источника: демон забирает файл, syslog-сервер принимает сообщение, агент перехватывает события Windows и т. д.
- **Агрегация** — централизация разнородных потоков событий в общем репозитории, будь то плоское файловое хранилище, колоночная база данных или распределённая очередь. Именно агрегация обеспечивает единую точку применения политик хранения, безопасности и резервного копирования, а главное — даёт возможность корреляции событий от различных источников.
- **Нормализация** — преобразование сырых записей к общей схеме. Например, временна́я метка из разных логов может быть приведена к UTC в одном формате, а поле «IP-адрес отправителя» всегда будет называться `src_ip`, независимо от того, как оно именовалось в исходном логе. Нормализацию иногда выполняют на этапе агрегации (на лету), но логически это следующий шаг после приёма данных.
- **Парсинг** — извлечение структурированных элементов (имён пользователей, IP-адресов, кодов HTTP-статуса) из неструктурированного текста лога.

SIEM-система исторически объединила в себе три направления, между которыми важно не потерять грань: __Log Management (LMS)__ — традиционный сбор, хранение и ротация логов; __Security Information Management (SIM)__ — централизованное управление данными о безопасности от многих источников и подготовка отчётов; __Security Event Management (SEM)__ — проактивный мониторинг, корреляция и алертинг в реальном времени (см. [What is SIEM?](https://logz.io/blog/what-is-siem)). Агрегация в SIEM обслуживает все три функции: она поставляет сырой материал в LMS-компонент, создаёт единый набор событий для корреляции в SEM и наполняет аналитическую базу для ретроспективы и отчётности SIM.

Чтобы наглядно отделить агрегацию от смежных процессов, приведём сравнительную таблицу.

| Процесс | Основная цель | Что происходит с данными | Типичное средство реализации |
|---------|---------------|---------------------------|------------------------------|
| Сбор (collection) | Получение логов от источника | Чтение файла, приём UDP/TCP-потока, опрос API | Syslog-сервер, агент ОС, библиотека журналирования |
| Агрегация (aggregation) | Консолидация в едином репозитории | Перемещение, фильтрация и централизованное хранение потоков от сотен/тысяч источников | Logstash, Fluentd, syslog-ng (в роли коллектора), промежуточный концентратор SIEM |
| Нормализация (normalization) | Приведение к общей модели данных | Сопоставление полей: `time→timestamp`, `src→src_ip`, приведение часового пояса | Парсеры SIEM, конфигурации Logstash, CIM-маппинги вендора |
| Обогащение (enrichment) | Добавление контекста | Подстановка геолокации по IP, информации об активе, репутационных данных | Threat Intelligence Feeds, CMDB-коннекторы |

Зачем такое разделение? Практика показывает, что попытка «всё сразу» без чёткого агрегационного слоя ведёт к потере событий при пиковых нагрузках и усложняет расследование. Поэтому во всех современных архитектурах SIEM (Splunk, Elastic Security, Microsoft Sentinel, Wazuh) явно выделяют компоненты сбора и агрегации, даже если поставщик объединяет их в один термин «data ingestion».

Агрегация критически важна ещё и по причине комплаенс-требований. Стандарты PCI DSS, HIPAA, SOX и GDPR требуют не только мониторинга, но и долговременного хранения журналов событий с гарантией целостности. Именно агрегационное хранилище становится тем местом, к которому применяются политики retention и аудита ([Understanding and Selecting SIEM/LM: Aggregation, Normalization, and Enrichment](https://securosis.com/blog/understanding-and-selecting-siem-lm-aggregation-normalization-and-enrichmen)).

С ростом объёмов данных (организации генерируют десятки и сотни гигабайт логов в сутки) классическая централизованная модель агрегации наталкивается на ограничения масштабируемости. Поэтому всё чаще применяются распределённые пайплайны: первичная фильтрация и предварительная агрегация выполняются на границе сети (агентами или легковесными форвардерами), а в центральное хранилище уходит уже очищенный и структурированный поток ([там же](https://securosis.com/blog/understanding-and-selecting-siem-lm-aggregation-normalization-and-enrichmen)). Такой подход снижает нагрузку на ядро SIEM и экономит лицензируемый объём индексации.

## 2. Внутреннее устройство процесса агрегации
Агрегацию событий в SIEM удобно рассматривать как сквозной процесс передачи данных от источника до центрального индекса или таблицы. Он включает выбор источников, способа доставки, протокола, буферизацию, приём и сохранение. Поскольку тема объединяет несколько аспектов — обзор класса источников и методов, а также архитектуру потоков — ниже материал организован в подразделы, охватывающие логические блоки этого процесса.

### 2.1 Источники событий и категории собираемых данных
SIEM собирает логи из трёх основных категорий, каждая из которых несёт разный «разрез» безопасности:

- **Сетевые устройства и защитные средства**: маршрутизаторы, коммутаторы, межсетевые экраны, IDS/IPS. Логи содержат информацию о разрешённых и запрещённых соединениях, сигнатурах атак, изменениях конфигурации. Форматы: syslog (RFC 3164/5424), NetFlow/sFlow, проприетарные бинарные потоки (Cisco ASA).
- **Серверы и операционные системы**: Windows Event Log, Linux syslog/auditd, macOS unified log. Здесь фиксируются входы в систему, повышение привилегий, изменения реестра, запуск служб. Для Windows сбор обычно реализуется через агенты (Winlogbeat, агенты SIEM), для Unix-систем — по syslog или auditd.
- **Приложения и облачные сервисы**: веб-серверы (access log, error log), СУБД (Microsoft SQL Server Error Log, PostgreSQL log), SaaS-платформы (Microsoft 365 Unified Audit Log, Google Workspace audit, Salesforce), облачная инфраструктура (AWS CloudTrail, Azure Activity Log, GCP Cloud Audit Logs). Сбор здесь часто организован через API, Push-уведомления или специализированные коннекторы ([SIEM Log Sources из Coralogix](https://coralogix.com/guides/siem/siem-logging)).

Разнообразие источников — одновременно сила и главный вызов агрегации. Каждый источник может генерировать события в собственном синтаксисе, с различной степенью детализации и в собственном темпе (от десятков событий в секунду от одного коммутатора до сотен тысяч EPS от прокси-сервера). Именно поэтому агрегационный слой должен быть гибким к форматам и устойчивым к перегрузкам.

### 2.2 Методы и протоколы сбора
На практике применяют несколько стратегий доставки данных в агрегационный конвейер.

- **Агентный сбор**. На источнике или выделенной машине устанавливается программа-агент, которая читает локальные файлы логов, перехватывает события Windows, собирает метрики и отправляет их в центральный коллектор. Агент может фильтровать и буферизовать данные локально, решая проблему кратковременных обрывов связи. Примеры: Winlogbeat, Elastic Agent, Splunk Universal Forwarder, Wazuh Agent. Агентная модель обеспечивает надёжную доставку, но требует установки и обновления ПО на каждом хосте, что увеличивает административную нагрузку ([Breaking Down Raw Logs: A Guide to SIEM Analysis](https://www.examcollection.com/blog/breaking-down-raw-logs-a-guide-to-siem-analysis)).

- **Syslog-приём (UDP/TCP/RELP)**. Огромное число сетевых устройств и Unix-систем умеют отправлять логи по стандартному протоколу syslog. SIEM-коллектор слушает UDP-порт 514 или TCP-порт 601 (для надёжной доставки с квитированием). UDP обеспечивает высокую пропускную способность, но пакеты могут теряться; TCP гарантирует доставку, но требует управления очередями. В высоконагруженных средах часто используют промежуточные syslog-серверы (syslog-ng, rsyslog с буферами) для приёма и пересылки с фильтрацией ([там же](https://www.examcollection.com/blog/breaking-down-raw-logs-a-guide-to-siem-analysis)).

- **API-коннекторы и pull-модель**. Для облачных платформ, SaaS-сервисов и современных приложений прямая отправка syslog недоступна. Вместо этого коллектор или коннектор SIEM периодически (или по триггеру) запрашивает данные через REST API, как правило с авторизацией OAuth2. Например, Microsoft Sentinel использует встроенные коннекторы к Microsoft 365 Management API, AWS CloudTrail получают через S3-уведомления или прямой опрос CloudTrail Lake. Такой метод может вносить задержку в несколько минут, но он крайне гибок и не требует доступа к ОС источника.

- **Пересылка логов (log forwarding)**. Некоторые SIEM поддерживают трансляцию потоков от уже существующих коллекторов. Например, один центр сбора отправляет данные в SIEM через syslog, CEF (Common Event Format) или LEEF (Log Event Extended Format). Это удобно при миграции или интеграции двух платформ.

### 2.3 Форматы и структура данных на входе агрегации
Сырые логи приходят в разнообразных форматах, и агрегатор должен уметь их принять без потерь. Наиболее распространённые:

- **Syslog (RFC 3164/5424)** — текстовые строки с приоритетом, временной меткой, хостом и телом сообщения. Простота формата контрастирует с отсутствием строгой схемы: тело не структурировано, парсинг зависит от вендора устройства.
- **JSON** — основной формат современных API-источников (CloudTrail, Okta, Docker). Содержит пары «ключ-значение», легко парсится. Агрегатор может сразу извлекать нужные поля без сложных регулярных выражений.
- **CEF (Common Event Format)** — стандарт ArcSight для межсетевых экранов, IDS/IPS. Строка начинается с префикса `CEF:0|...` и содержит расширенные поля вида `src=... dst=...`.
- **LEEF (Log Event Extended Format)** — формат IBM QRadar, похож на CEF, но с другой структурой заголовка.
- **Неструктурированный текст** — логи приложений без строгой схемы (например, отладочные сообщения Java-приложений). Здесь требуется предварительный парсинг на стороне агента или коллектора с использованием регулярных выражений, чтобы извлечь хотя бы временную метку и уровень серьёзности до помещения в хранилище.

На этапе агрегации важно сохранять исходное сообщение в неизменном виде (поле `_raw` или `message`), а после нормализации добавлять структурированные поля в параллельные объекты. Это позволяет вернуться к «сырой» записи при судебном анализе и в то же время строить быстрые поиски по нормализованным атрибутам (см. [How SIEM Works](https://www.linkedin.com/posts/hatemenaami_how-siem-security-information-and-event-activity-7395262684541231104-IsXv)).

### 2.4 Типовая архитектура агрегационного конвейера
На практике поток событий от источников до SIEM-хранилища проходит несколько стадий. Визуализируем их в виде ASCII-схемы:

```text
[Источники]
│  Сетевые устройства (syslog), серверы (агенты), облачные API
│
▼
[Транспортный слой]
│  UDP/TCP syslog, агентская передача (Elastic Agent/Beat), HTTPS pull
│
▼
[Коллектор / Агрегатор-приёмник]
│  syslog-ng, rsyslog, Logstash, Fluentd, агент SIEM-концентратора
│  Функции: фильтрация шума, сжатие, маршрутизация потоков, буферизация
│
▼
[Очередь / Буфер (опционально)]
│  Kafka, RabbitMQ, дисковые буферы — для сглаживания пиковых нагрузок
│
▼
[SIEM-индексатор / Хранилище]
   Elasticsearch (индексы), Sentinel Log Analytics, Splunk Indexer
   Нормализация, обогащение, корреляция
```

Агрегация на этой схеме охватывает промежуток от источников до входа в индексатор. В распределённых системах (Elastic Stack) первый коллектор и сбор данных могут быть разнесены: Logstash или Elastic Agent принимают потоки, фильтруют и отправляют в централизованный Kafka-кластер или напрямую в Elasticsearch. Это позволяет гибко масштабировать сбор, добавляя новые коллекторы без изменения логики основного SIEM.

Стоит упомянуть и недостатки такого подхода. Централизованная агрегация создаёт «бутылочное горло» на сборщике логов, если через него проходят десятки тысяч событий в секунду. В результате возможны задержки в детектировании и потеря данных. Решение — горизонтальное масштабирование коллекторов и вынос ресурсоёмкой нормализации на узлы-парсеры ([Understanding and Selecting SIEM/LM: Aggregation, Normalization, and Enrichment](https://securosis.com/blog/understanding-and-selecting-siem-lm-aggregation-normalization-and-enrichmen)). Именно поэтому зрелые архитектуры включают промежуточный message broker.

## 3. Применение и работа с агрегацией событий
Работа аналитика SOC L1 с агрегацией чаще всего сводится к проверке, что события от конкретного источника действительно поступают в систему, а также к базовой настройке стандартных источников. Администратор SIEM отвечает за более глубокое конфигурирование, но понимание практических деталей необходимо обоим.

### 3.1 Настройка типовых источников
Рассмотрим три наиболее частых сценария, встречающихся в любой организации.

**Linux-сервер (rsyslog → центральный syslog/SIEM)**. Подавляющее большинство дистрибутивов по умолчанию используют демон rsyslog. Чтобы перенаправить все логи на удалённый коллектор, в файл `/etc/rsyslog.d/50-forward.conf` добавляют:

```bash
# Отправка всех сообщений с уровнем info и выше по TCP на порт 514
*.* @@192.0.2.10:514
```

Одна собака `@` означает UDP, две собаки `@@` — TCP. Для надёжной доставки предпочтителен TCP; в высоконагруженных средах дополнительно включают пересылку с дисковыми очередями для защиты от потерь при перезагрузке сети:

```bash
$ActionQueueType LinkedList
$ActionQueueFileName fwdQueue
$ActionResumeRetryCount -1
$ActionQueueSaveOnShutdown on
*.* @@192.0.2.10:514
```

После внесения изменений необходим перезапуск службы (`systemctl restart rsyslog`) и проверка, что порт слушается удалённым коллектором: `ss -tlnp | grep 514`.

**Сетевое оборудование (Cisco IOS, syslog)**. Настройка отправки логов на коммутаторе Cisco выполняется командами глобальной конфигурации:

```
logging host 192.0.2.10 transport tcp port 514
logging trap informational
logging facility local0
logging source-interface Vlan10
```

Здесь `trap informational` задаёт уровень важности (аналог severity); `facility local0` позволяет группировать потоки на стороне SIEM. Многие администраторы по ошибке оставляют уровень `debugging`, что затапливает коллектор ненужным шумом. После настройки стоит проверить поступление событий через `show logging`.

**Облачные источники (AWS CloudTrail)**. CloudTrail сохраняет журналы API-вызовов в S3-бакет. Интеграция с SIEM (например, Wazuh, Splunk) реализуется через коннектор, который опрашивает S3 по событию SQS-уведомления о создании нового объекта. Фрагмент конфигурации AWS-политики роли для SIEM-коллектора выглядит следующим образом (иллюстративная схема):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": "arn:aws:s3:::cloudtrail-bucket-*/*"
    },
    {
      "Effect": "Allow",
      "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage"],
      "Resource": "arn:aws:sqs:us-east-1:123456789:cloudtrail-queue"
    }
  ]
}
```

Этот метод обеспечивает непрерывный ingest событий без ручного копирования.

### 3.2 Проверка целостности потока и типовые ошибки
После настройки любого источника аналитик должен убедиться, что события действительно поступают. На центральном коллекторе для этого используется простой захват трафика или журналы локального syslog:

```bash
tcpdump -i eth0 port 514 -nn -c 20
```

Если сообщения приходят, следующим шагом проверяют, индексируются ли они в SIEM. В Elastic-стеке запрос к индексу `logstash-*`:

```json
GET /logstash-*/_search
{
  "query": { "match": { "host.name": "linux-server01" } },
  "size": 1
}
```

Отсутствие событий часто указывает на одну из трёх типовых проблем:

- **Расхождение времени**. Источник и SIEM должны быть синхронизированы по NTP. Если часы Linux-сервера ушли вперёд, индексатор может отбрасывать будущие события (временной фильтр). Решение: `timedatectl set-ntp true` и проверка `chronyc sources -v`.
- **Ошибка парсинга или формата**. Сетевой экран отправляет события в проприетарном формате, не совместимом с парсером SIEM по умолчанию. В логах коллектора появляются записи вида «parse error for message …». Требуется включить модуль разбора для конкретного вендора или создать пользовательский парсер.
- **Блокировка сетевым экраном**. Часто забывают открыть порт 514 или 9200 на пути от источника к SIEM. Проверка: `nc -zv 192.0.2.10 514`.

### 3.3 Обеспечение сохранности данных при сбоях
Устойчивость агрегации критически важна — потеря даже нескольких секунд логов может скрыть следы атаки. Для этого все серьёзные коллекторы (rsyslog, syslog-ng, Logstash) поддерживают дисковые очереди:

```yaml
# Пример конфигурации Logstash для отправки в Elasticsearch с dead letter queue
queue.type: persisted
queue.max_bytes: 2gb
```

В rsyslog аналогично задаются ActionQueue-параметры, которые мы видели выше. Администратор должен мониторить размер и отставание очереди; если очередь растёт, необходимо наращивать ресурсы индексатора или увеличивать количество коллекторов.

Также следует настроить мониторинг самого коллектора: количество принимаемых событий в секунду (metrics `logstash_events_in_rate`, `syslog_received_total`) и отправку алертов при падении потока ниже порогового значения.

### 3.4 Команда для быстрой проверки агрегации
В качестве интеграции с SIEM часто используют простую отправку тестового сообщения прямо из командной строки:

```bash
logger -n 192.0.2.10 -P 514 -T "TEST: user login event"
```

На приёмной стороне (SIEM) через поиск по `TEST` можно убедиться, что событие попало в индекс. Это универсальный приём, не зависящий от конкретной платформы.

## 4. Сквозной практический пример: агрегация событий с Linux-хоста, сетевого коммутатора и AWS CloudTrail

**Исходные условия.** В организации развёрнута SIEM-платформа на базе Wazuh (индексирование — Elasticsearch). Центральный сервер-менеджер Wazuh имеет IP-адрес `192.168.100.10`. Необходимо наладить приём событий с трёх разнородных источников: Linux-хоста (`linux-srv01`), управляющего коммутатора Cisco (модель Catalyst 2960X) и облачного журнала AWS CloudTrail из рабочего аккаунта AWS. Роль студента: администратор SIEM, выполняющий настройку и первичную проверку агрегации.

### Шаг 1: отправка журналов аудита с Linux-хоста на Wazuh

Действие: на хосте `linux-srv01` необходимо передать логи демона `auditd` в SIEM. Так как Wazuh использует агент, мы воспользуемся встроенной возможностью агента пересылать дополнительные лог-файлы. В конфигурационный файл агента `/var/ossec/etc/ossec.conf` добавляем секцию `localfile`:

```xml
<localfile>
  <log_format>syslog</log_format>
  <location>/var/log/audit/audit.log</location>
</localfile>
```

После перезапуска агента (`systemctl restart wazuh-agent`) демон начинает следить за файлом и передавать новые строки менеджеру Wazuh. Альтернативный путь — использовать rsyslog для перенаправления, но в рамках SIEM Wazuh агент предпочтительнее с точки зрения целостности и простоты управления.

Проверка поступления: на сервере Wazuh выполняем запрос к API:

```bash
curl -u admin:wazuh "https://localhost:55000/security/user/authenticate" -k -X POST
TOKEN=$(получаем токен)
curl -k -H "Authorization: Bearer $TOKEN" "https://localhost:55000/events?search=linux-srv01&limit=3"
```

Ожидаемый вывод: три последних события с указанием `linux-srv01` в поле `agent.name` и типом `syslog`.

### Шаг 2: конфигурация syslog на коммутаторе Cisco

Подключаемся к коммутатору по SSH и входим в режим глобального конфигурирования. Настраиваем отправку всех информационных сообщений на Wazuh-менеджер (у менеджера должен работать syslog-приёмник, например rsyslog, пересылающий события в Wazuh):

```
configure terminal
logging host 192.168.100.10 transport tcp port 514
logging trap informational
logging facility local0
logging source-interface Vlan50
end
write memory
```

Здесь `Vlan50` — интерфейс управления. Для немедленной проверки можно инициировать тестовое событие, изменив настройку консольного логирования:

```
configure terminal
logging console critical
end
```

Это генерирует сообщение `%SYS-5-CONFIG_I: Configured from console by ...`. На центральном syslog-коллекторе (rsyslog на Wazuh-менеджере) проверяем его появление:

```bash
tail -f /var/log/syslog | grep 192.168.100.10
```

### Шаг 3: интеграция AWS CloudTrail

В AWS создан трейл CloudTrail, доставляющий логи в S3-бакет `cloudtrail-logs-123456789`. Wazuh не имеет нативной интеграции с S3-событиями из коробки, поэтому мы настраиваем прослойку — Logstash с input-плагином `s3`. В файл `/etc/logstash/conf.d/cloudtrail.conf` помещаем конфигурацию:

```ruby
input {
  s3 {
    bucket => "cloudtrail-logs-123456789"
    region => "us-east-1"
    prefix => "AWSLogs/123456789/CloudTrail/"
    interval => 60
    additional_settings => {
      force_path_style => false
      follow_redirects => false
    }
  }
}

filter {
  json { source => "message" }
  # Здесь могут идти преобразования полей, обогащение гео-данными и т.д.
}

output {
  elasticsearch {
    hosts => ["https://192.168.100.10:9200"]
    index => "cloudtrail-%{+YYYY.MM.dd}"
    ssl => true
    cacert => "/etc/logstash/certs/ca.crt"
    user => "elastic"
    password => "secret"
  }
}
```

После перезапуска Logstash (`systemctl restart logstash`) конвейер начинает опрашивать бакет каждые 60 секунд и индексировать новые записи. Типичная запись CloudTrail имеет вид (фрагмент):

```json
{
  "eventVersion": "1.08",
  "userIdentity": { "type": "IAMUser", "arn": "arn:aws:iam::123456789:user/admin" },
  "eventTime": "2025-01-15T10:00:00Z",
  "eventSource": "ec2.amazonaws.com",
  "eventName": "RunInstances",
  "sourceIPAddress": "203.0.113.45",
  "userAgent": "console.ec2.amazonaws.com",
  "requestParameters": { "instancesSet": { "items": [{ "imageId": "ami-12345" }] } },
  "responseElements": { "instancesSet": { "items": [{ "instanceId": "i-0abcd" }] } }
}
```

### Шаг 4: проверка агрегации в SIEM

Через веб-интерфейс Kibana (при использовании Elasticsearch) или через API Wazuh выполняется запрос, показывающий события от всех трёх источников за последние 5 минут:

```bash
curl -k -H "Authorization: Bearer $TOKEN" \
"https://localhost:55000/events?search=cloudtrail&limit=2"
```

Ожидаемый вывод: два события CloudTrail, перемежающиеся с сообщениями от `linux-srv01` и Cisco. На общей панели «Security events» в Wazuh теперь видны записи из разных сред, а время событий выровнено по UTC благодаря предварительной нормализации.

**Ожидаемый вывод примера.** Студент видит, как распределённые, изначально не связанные между собой источники — внутренний хост, сетевое оборудование и облачный сервис — стекаются в единое хранилище, готовое к корреляции. Лог неудачного входа на Linux-сервер (`audit.type=USER_LOGIN` failure) может быть сопоставлен с вызовом API `ConsoleLogin` из CloudTrail, подтверждая факт атаки, что без агрегации было бы невозможно обнаружить. Это замкнёт цикл понимания агрегации как фундамента для всей последующей аналитики SOC.
