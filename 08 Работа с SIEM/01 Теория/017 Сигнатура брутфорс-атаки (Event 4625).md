# Сигнатура брутфорс-атаки (Event 4625)

## 1. Место события 4625 в детектировании атак на учётные данные

Событие с идентификатором 4625 в журнале безопасности Windows фиксирует неудачную попытку входа в систему. Для аналитика SOC уровня L1 это — атомарный индикатор, который, будучи агрегированным и скоррелированным с другими событиями, позволяет выявить попытки подбора учётных данных (brute force), распыления паролей (password spraying) и credental stuffing. В SIEM-системах событие 4625 нормализуется, обогащается и становится фундаментом для корреляционных правил, реализующих сигнатуры атак.

Ключевая особенность брутфорс-атак через RDP, SMB, WinRM или веб-интерфейсы — устойчивая генерация множества событий 4625 с малым интервалом. В реальных инцидентах, описанных в сообществе (например, на Spiceworks [Strange 4625 Failed Login Events](https://community.spiceworks.com/t/strange-4625-failed-login-events/957711)), наблюдаются сотни событий в минуту с несуществующими учётными записями типа `Cisco1`, `bob`, `test`, `admin`. Это классический признак атаки по словарю. Аналитик должен отличать такой паттерн от легитимных неудачных входов (забытый пароль, смена учётной записи, проблемы с сервисами) и от других техник, которые также оставляют записи 4625, но имеют принципиально иные временные и количественные характеристики.

Терминология MITRE ATT&CK чётко разделяет техники злоупотребления учётными данными, каждая из которых требует собственной сигнатуры на основе событий 4625:

- **T1110.001 Password Guessing** — перебор паролей для одного или нескольких заранее известных учётных записей. Характеризуется всплесками 4625 с ограниченным набором `TargetUserName` и высокой частотой попыток с одного источника.
- **T1110.002 Password Cracking** — офлайн-атака, которая напрямую не отражается в журнале 4625 до момента использования взломанного хэша, но может проявляться косвенно через последующие успешные входы без видимых предшествующих неудач.
- **T1110.003 Password Spraying** — попытка входа с одним широко распространённым паролем на множество учётных записей. В логах — множество 4625 с различными `TargetUserName`, одним `Source Network Address` и низкой частотой (один запрос на пользователя, чтобы избежать блокировки) на длительном промежутке.
- **T1110.004 Credential Stuffing** — автоматизированная проверка скомпрометированных пар логин-пароль, часто из утечек. Характерна смесь успешных и неудачных входов с разных IP-адресов, корреляция с внешними данными об утечках.

Разграничение этих вариантов критически важно для настройки порогов, выбора полей агрегации и минимизации ложных срабатываний. Например, для классического брутфорса типично пороговое правило «N событий 4625 за M минут с одного IP на одну учётную запись», тогда как для password spraying применяется подсчёт уникальных `TargetUserName` с одного IP за интервал.

Ниже представлена сравнительная таблица, обобщающая различия в сигнатурах по событиям 4625 для SOC-аналитика. Она позволяет на этапе триажа быстро классифицировать атаку.

| Техника MITRE | Паттерн событий 4625 | Ключевые поля для агрегации | Типовое правило SIEM | Реальный сценарий атаки |
|---------------|----------------------|-----------------------------|-----------------------|--------------------------|
| Password Guessing (T1110.001) | Высокая частота, ограниченный список TargetUserName, один source IP | `TargetUserName`, `IpAddress` | Threshold: count > 10 за 5 мин. | Злоумышленник вводит `administrator`, перебирает 20 паролей за минуту. |
| Password Spraying (T1110.003) | Низкая частота, множество уникальных TargetUserName, один source IP, Status 0xC000006A | `IpAddress`, distinct count `TargetUserName` | Distinct count > 30 за 10 мин. | Используется пароль `Spring2024!` против всех пользователей домена. |
| Credential Stuffing (T1110.004) | Разные IP и UserName, быстрое срабатывание, возможно появление 4624 после серии 4625 | `TargetUserName`, `IpAddress` с обогащением TI | Threshold; обогащение списками утечек | Автоматизированный скрипт проверяет пары из утекшей БД. |
| Kerberos-атаки (Kerbrute) | 4768/4771 (Kerberos) + 4625 (NTLM) при падении, с одного хоста | `TargetUserName`, `IpAddress` (если есть) | Sequence: 4771 → 4625 за 5 мин. | Инструмент kerbrute passwordspray с флагом `--dc-ip`. |

Таким образом, событие 4625 — универсальный строительный блок для обнаружения попыток несанкционированного доступа. Однако, как отмечается на ServerFault [Brute force attack with no IP to trace](https://serverfault.com/questions/861775/brute-force-attack-with-no-ip-to-trace), при использовании NLA и TLS в RDP поле `Source Network Address` может быть пустым, что усложняет прямую блокировку. В таких случаях сигнатура должна опираться на косвенные признаки: `WorkstationName`, временные метки, `Status`/`SubStatus`, а также корреляцию с соседними событиями, например, 4776 (сброс NTLM-хэша) или 4648 (явное указание учётных данных).

## 2. Анатомия события 4625 и его роль в корреляции

Событие 4625 содержит богатый набор полей, которые транслируются в SIEM в нормализованную структуру. Понимание семантики каждого поля — основа для составления точных правил детектирования и эффективной триажи.

### Структура события Windows Security 4625 (XML/EVTX)

Оригинальное событие в формате EVTX представлено в XML и содержит следующие ключевые элементы (описаны на основе официальной документации, реальных примеров из выдержек [Event log failure 4625](https://learn.microsoft.com/en-us/answers/questions/198575/event-log-failure-4625-(brute-force-attack)), [ServerFault](https://serverfault.com/questions/690770/how-to-find-source-of-4625-event-id-in-windows-server-2012)):

- **Subject**: информация об инициаторе попытки входа. При атаке извне обычно содержит NULL SID (`S-1-0-0`), пустые `Account Name` и `Account Domain`, что указывает на то, что учётная запись отправителя не была определена до аутентификации.
- **Logon Type** (числовой код): критическое поле, определяющее вектор атаки. Основные значения:
  - `2` – Interactive (локальный вход)
  - `3` – Network (доступ к сетевой папке, PsExec, SMB)
  - `10` – RemoteInteractive (RDP)
  - `7` – Unlock (разблокировка)
  - `5` – Service (запуск службы)
- **Account For Which Logon Failed**: целевой пользователь — `TargetUserName`, `TargetDomainName`. Именно по этим полям агрегируются попытки, и они же являются ответом на вопрос «кого атакуют?».
- **Failure Information**: коды ошибок — `Status` и `SubStatus`. Например, `0xC000006D` означает «имя пользователя не существует или пароль неверен», `0xC0000064` — «указанное имя пользователя не существует», а `0xC000006A` — неверный пароль при существующем пользователе. Разбор этих кодов позволяет отделить атаки, целящиеся в реальных пользователей, от перебора несуществующих имён (словарные атаки на имена).
- **Process Information**: идентификатор вызывающего процесса (`Caller Process ID`) и его имя (например, `C:\Windows\System32\winlogon.exe` или `svchost.exe`). Может указывать на необычное поведение, если процесс не характерен для интерактивного входа.
- **Network Information**: `WorkstationName`, `Source Network Address`, `Source Port`. При Network Logon (тип 3) или RDP (тип 10) эти поля обычно заполнены, но, как упоминалось выше, при определённых настройках безопасности (NLA/TLS) IP-адрес может отсутствовать. `WorkstationName` может быть подделан, но в некоторых сценариях (внутренняя атака) даёт зацепку.
- **Detailed Authentication Information**: используемый пакет аутентификации (`NTLM`, `Kerberos`, `Negotiate`). Позволяет понять, на каком протоколе работает атака.

### Нормализация в SIEM (на примере Elastic Common Schema)

В SIEM событие 4625 разбирается и преобразуется в поля Elastic Common Schema (ECS) или аналогичную унифицированную модель. Пример нормализованного JSON-документа, создаваемого Winlogbeat (иллюстративная схема на основе типового шаблона):

```json
{
  "@timestamp": "2021-02-03T14:30:45.123Z",
  "event": {
    "action": "logon_failed",
    "id": "4625",
    "outcome": "failure"
  },
  "host": {
    "name": "windows-server-01",
    "ip": "10.0.1.100"
  },
  "source": {
    "ip": "192.168.1.55",
    "port": 57477
  },
  "user": {
    "name": "administrator",
    "domain": "CORP"
  },
  "winlog": {
    "logon_type": 10,
    "status": "0xC000006D",
    "sub_status": "0xC000006A",
    "process_name": "C:\\Windows\\System32\\winlogon.exe"
  },
  "message": "An account failed to log on..."
}
```

В этой структуре ключевыми для корреляции являются:
- `source.ip` — источник атаки;
- `user.name` — целевая учётная запись;
- `winlog.logon_type` — вектор;
- `winlog.status` / `winlog.sub_status` — код ошибки.

Некоторые SIEM-системы дополнительно добавляют теги MITRE ATT&CK на основе этих полей (например, `attack.t1110` при большом количестве 4625) или обогащают геолокацией источника.

### Сигнатурный принцип: агрегация и корреляция

Событие 4625 само по себе не является индикатором атаки. Сигнатура брутфорса формируется путём применения логических и временных условий к потоку событий. Выделяют три основных типа правил, которые закрывают практически все сценарии:

1. **Threshold (пороговое правило)** — срабатывает при превышении числа событий с определёнными одинаковыми полями за интервал времени. Например: «более 10 событий 4625 с одного `source.ip` на один `user.name` за 5 минут». Это простейшее правило лежит в основе детекта классического брутфорса и password spraying (distinct count).
2. **Sequence (последовательность)** — обнаруживает упорядоченную цепочку событий: серия 4625, за которой следует 4624 (успешный вход) на том же хосте с теми же учётными данными. Это даёт высокую достоверность того, что атака была успешной. Пример из обсуждения Elastic [Elastic SIEM - Detection Rules - Combination...](https://discuss.elastic.co/t/elastic-siem-detection-rules-combination-of-time-based-threshold-aggregation-and-sequence-events/263175): `sequence by host.name with maxspan=5m [...] 4625 repeated 10 times, then 4624`.
3. **Aggregation with statistical anomaly** — подсчитывается количество уникальных значений `TargetUserName` с одного IP за интервал; порог срабатывания определяется на основе профиля поведения системы. Используется для обнаружения медленного распыления паролей или аномальной активности.

Каждый из этих шаблонов опирается на конкретные поля события 4625. Ниже таблица, связывающая поля оригинального события 4625 с их ролью в правилах детектирования.

| Поле события (Winlog) | Нормализованный вид в ECS/UDM | Роль в сигнатуре | Пример использования |
|------------------------|-------------------------------|------------------|-----------------------|
| `TargetUserName`       | `user.name`                   | Идентификатор атакуемой учётной записи | Агрегация по `user.name`, проверка на легитимность через LDAP-запрос |
| `IpAddress` / `Source Network Address` | `source.ip`       | Источник атаки | Группировка по `source.ip`, обогащение GeoIP, добавление в watchlist |
| `LogonType`            | `winlog.logon_type`           | Вектор атаки | Фильтр: только `3` или `10`, исключение служебных попыток |
| `Status` / `SubStatus` | `winlog.status`, `winlog.sub_status` | Тип ошибки | Подавление легитимных сбоев (например, `0xC0000234` — учётная запись заблокирована) |
| `WorkstationName`      | `source.hostname`             | Имя машины-источника | Используется при отсутствии IP (RDP с NLA) |
| `ProcessName`          | `winlog.process_name`         | Инициатор попытки | Исключение событий от известных сканеров или сервисных учётных записей |

Таким образом, внутреннее устройство сигнатуры — это композиция условий на основе полей 4625, объединённых операторами агрегации (`count`, `distinct count`, `sequence`) и временными окнами.

## 3. Построение и эксплуатация корреляционных правил на практике

Аналитик SOC L1 редко создаёт правила с нуля, но обязан понимать логику их работы, чтобы интерпретировать срабатывания, настраивать исключения и подавлять ложные срабатывания. Рассмотрим три основные реализации сигнатур брутфорса на основе 4625, встречающиеся в современных SIEM: EQL (Elastic), YARA-L (Google SecOps / Chronicle) и Sigma (универсальный формат обмена).

### EQL sequence rule (Elastic Security)

В Elastic Security для детектирования успешной брутфорс-атаки применяется EQL-запрос, встраиваемый в правило типа «Sequence». На форуме сообщества [Elastic SIEM - Detection Rules](https://discuss.elastic.co/t/elastic-siem-detection-rules-combination-of-time-based-threshold-aggregation-and-sequence-events/263175) предложен подход с повторением искомого события нужное количество раз из-за отсутствия на тот момент встроенного счётчика. Современные версии EQL поддерживают более компактный синтаксис с использованием `until` или `runs`, но в реальных внедрениях часто комбинируют пороговое правило на 4625 с отдельным правилом на 4624, связывая их через общий алерт.

Пример рабочего правила в формате, приближенном к тому, что используется в Kibana Security Rules API:

```eql
sequence by host.name, user.name with maxspan=10m
  [authentication where event.id == "4625" and winlog.logon_type == 10] with runs = 10
  [authentication where event.id == "4624" and winlog.logon_type == 10]
```

Здесь `with runs = 10` указывает, что первое условие должно повториться не менее 10 раз. Правило срабатывает, если за 10 минут с одного хоста и под одну учётную запись совершено 10 неудачных попыток RDP, после чего следует успешный вход.

Артефакт: иллюстративная структура правила в формате Elastic alert (JSON), используемая при создании через REST API:

```json
{
  "rule_id": "brute-force-sequence-rdp",
  "type": "eql",
  "eql": {
    "query": "sequence by host.name, user.name with maxspan=10m\n[authentication where event.id == \"4625\" and winlog.logon_type == 10] with runs = 10\n[authentication where event.id == \"4624\" and winlog.logon_type == 10]"
  },
  "name": "Successful RDP Brute Force Attack",
  "severity": "high",
  "risk_score": 85,
  "tags": ["T1110.001", "RDP"]
}
```

### YARA-L multi-event rule (Google SecOps)

В Google Security Operations (бывший Chronicle SIEM) корреляционные правила пишутся на YARA-L — языке, ориентированном на сопоставление событий с заданными временными окнами и агрегацию. В теме [Multi Event Rule --Bruteforce_with_4624_and_4625--Rule](https://security.googlecloudcommunity.com/google-security-operations-2/multi-event-rule-bruteforce-with-4624-and-4625-rule-5776) обсуждалась типичная ошибка при построении такого правила. Исходный вариант пытался использовать переменную `$fail` без привязки к полю в блоке `outcome`. Исправленный подход, опирающийся на документацию по агрегациям, использует `count($fail.target.user.userid)`:

```yara
meta:
  author = "SOC Team"
  description = "Detects successful brute force: 3+ failed logins then success within 5 mins"
  severity = "High"
  mitre = "T1110.001"

events:
  $fail.metadata.event_type = "LOGIN_FAILED"
  $fail.principal.asset.ip = $ip_address
  $fail.target.user.userid = $user_id

  $success.metadata.event_type = "LOGIN_SUCCESS"
  $success.principal.asset.ip = $ip_address
  $success.target.user.userid = $user_id

match:
  $ip_address, $user_id over 5m

outcome:
  $failed_attempts = count($fail.target.user.userid)
  $alert_type = array_distinct("Brute Force Login")

condition:
  $success and $fail and $failed_attempts >= 3
```

Принцип работы: переменные `$fail` и `$success` привязываются к нормализованным событиям в UDM (Unified Data Model). Блок `match` задаёт ключи и временное окно. Условие `$success and $fail` гарантирует наличие обоих типов событий, а `$failed_attempts >= 3` — минимальное количество неудач. Это правило отрабатывает на любом векторе, если нормализация выполнена корректно.

### Sigma-правило (универсальный формат)

Sigma — открытый формат для описания сигнатур, конвертируемый в запросы конкретных SIEM (Splunk, Elastic, QRadar и др.). Правило на брутфорс с 4625, взятое из реального каталога Sigma и адаптированное под обсуждаемую тему, имеет следующую структуру:

```yaml
title: Failed Logon Brute Force Attack (Event 4625)
id: bf73a1d2-57d2-4f36-8d6f-d7f29ae3b6d1
status: stable
description: Detects multiple failed logons (Event 4625) from the same source towards a single account within a short timeframe, indicating brute force.
logsource:
    product: windows
    service: security
detection:
    selection:
        EventID: 4625
    timeframe: 5m
    condition: selection | count() by IpAddress, TargetUserName > 10
falsepositives:
    - Vulnerability scanners (e.g. Nessus)
    - Misconfigured service accounts
    - User typos in small environments
level: medium
tags:
    - attack.t1110.001
    - attack.credential_access
```

Такой файл с помощью `sigmac` или встроенного конвертера превращается, например, в поисковый запрос Splunk: `EventID=4625 | stats count by IpAddress, TargetUserName | where count > 10`.

### Типичные ошибки и тюнинг

Ложные срабатывания — главная проблема сигнатур на 4625. Как видно из обсуждений на [Spiceworks](https://community.spiceworks.com/t/am-i-being-brute-force-attack/437261/12) и практического опыта, большинство шума порождается внутренними сканерами уязвимостей, забытыми скриптами администрирования и даже редкими, но легитимными опечатками пользователей. Основные приёмы тюнинга:

- **Whitelist IP-адресов**: исключение адресов доверенных сканеров (Nessus, Qualys, Tenable) через условие `not (source.ip == "10.0.0.50")` или список исключений в правиле SIEM.
- **Проверка SubStatus**: игнорирование событий 4625 с кодами, обусловленными не атакой, а состоянием учётной записи, например:
  - `0xC0000234` — учётная запись заблокирована (результат предыдущей атаки или неверной политики). Частые повторения могут быть шумом.
  - `0xC0000071` — пароль устарел (эксплуатационный шум).
  - `0xC0000064` — пользователь не существует, что полезно для детекта, но если IP сканера, то исключается.
- **Минимальное количество событий**: снижение порога до 3–5 в небольших средах, увеличение до 20–50 в крупных доменах с высоким трафиком.
- **Контекстная агрегация**: разделение правил на «горизонтальный» брутфорс (один IP на много пользователей) и «вертикальный» (один пользователь, много паролей), что дифференцирует типы атак и упрощает реакцию.
- **Обогащение TI-фидами**: проверка source IP по спискам известных вредоносных адресов; если адрес в списке — событие получает повышенную критичность.

Артефакт: пример дополнительного Elasticsearch-запроса, используемого аналитиком для быстрой триажи сработавшего правила и отсеивания шума:

```json
GET /winlogbeat-*/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "event.id": "4625" } },
        { "range": { "@timestamp": { "gte": "now-15m" } } }
      ],
      "must_not": [
        { "terms": { "source.ip": ["10.0.0.50", "10.1.2.3"] } }
      ]
    }
  },
  "aggs": {
    "by_user": {
      "terms": { "field": "user.name", "size": 20 }
    },
    "by_ip": {
      "terms": { "field": "source.ip", "size": 20 }
    },
    "by_logon_type": {
      "terms": { "field": "winlog.logon_type" }
    }
  }
}
```

Такой запрос выдаёт агрегацию по пользователям и IP за последние 15 минут, исключая заведомо доверенные адреса. Он помогает быстро подтвердить или опровергнуть атаку.

## 4. Сквозной практический пример: расследование алерта Brute Force RDP в Elastic SIEM

**Исходные условия**: SOC-аналитик L1 дежурит за консолью Kibana Security. Сработало правило «Successful RDP Brute Force Sequence» на хосте `WS-APP02` (Windows Server 2019, аудит включён, агент Winlogbeat отправляет логи). Алерт получил высокий риск. Необходимо проверить его обоснованность и, при подтверждении, выполнить первичные действия.

**Шаг 1: Просмотр деталей алерта.**  
В интерфейсе алертов Kibana Security открыт JSON-представление:

```json
{
  "kibana.alert.rule.name": "Successful RDP Brute Force Sequence",
  "kibana.alert.severity": "high",
  "host": { "name": "WS-APP02" },
  "source": { "ip": "203.0.113.45" },
  "user": { "name": "svc_backup" },
  "event": {
    "action": "alert",
    "start": "2021-02-03T14:30:00.000Z",
    "end": "2021-02-03T14:35:00.000Z"
  }
}
```

Ключевая информация: целевой хост, внешний IP-источник `203.0.113.45`, атакуемая учётная запись `svc_backup`, интервал 5 минут.

**Шаг 2: Анализ сырых событий 4625.**  
Для подтверждения всплеска неудачных попыток в Kibana Discover выполняется поиск за указанный интервал:

```kql
event.code : 4625 and source.ip : 203.0.113.45 and user.name : svc_backup
```

Система возвращает 27 документов. Один из них:

```json
{
  "@timestamp": "2021-02-03T14:33:12.456Z",
  "event": { "action": "logon_failed", "id": "4625", "outcome": "failure" },
  "host": { "name": "WS-APP02" },
  "source": { "ip": "203.0.113.45", "port": 60123 },
  "user": { "name": "svc_backup", "domain": "CORP" },
  "winlog": {
    "logon_type": 10,
    "status": "0xC000006A",
    "sub_status": "0xC000006A",
    "process_name": "C:\\Windows\\System32\\winlogon.exe"
  }
}
```

Анализ полей: `logon_type` 10 (RDP), `status` 0xC000006A (неверный пароль при существующей учётной записи). Это указывает, что атакующий знает имя пользователя и перебирает пароль, что характерно для Password Guessing.

**Шаг 3: Поиск успешного входа (Event 4624).**  
Согласно логике правила, за серией неудач должен следовать успех. Выполняется запрос:

```kql
event.code : 4624 and host.name : "WS-APP02" and user.name : svc_backup
```

Среди нескольких результатов найден наиболее поздний, соответствующий интервалу:

```json
{
  "@timestamp": "2021-02-03T14:34:58.123Z",
  "event": { "action": "logon_success", "id": "4624", "outcome": "success" },
  "host": { "name": "WS-APP02" },
  "source": { "ip": "203.0.113.45", "port": 60124 },
  "user": { "name": "svc_backup", "domain": "CORP" },
  "winlog": { "logon_type": 10 }
}
```

Временная метка успешного входа (14:34:58) практически сразу после последней неудачи (14:33:12) подтверждает факт подбора.

**Шаг 4: Верификация источника и эскалация.**  
Аналитик проверяет, не является ли IP-адрес `203.0.113.45` легитимным корпоративным адресом (VPN-концентратор). Быстрый просмотр списка внутренних сетей (ручное сопоставление) показывает, что это внешний адрес. В Kibana Threat Intelligence (при наличии интеграции) IP имеет репутацию «malicious». Дополнительно проверяется, не было ли других успешных входов с этого IP на другие хосты — это может свидетельствовать о горизонтальном перемещении. Формируется код поиска:

```kql
source.ip : 203.0.113.45 and event.code : 4624
```

Обнаруживается несколько алертов на соседние серверы, что усугубляет ситуацию.

На основе полученных данных аналитик L1 эскалирует инцидент аналитику L2: заводится тикет в системе учёта инцидентов с кратким резюме: «Подтверждён успешный брутфорс RDP на WS-APP02, учётная запись svc_backup скомпрометирована с IP 203.0.113.45, зафиксирован успешный вход. Рекомендация: немедленно отключить учётную запись, заблокировать IP на межсетевом экране, инициировать процедуру IR».

Ожидаемый вывод: сквозной пример демонстрирует, как сигнатура на основе последовательности событий 4625–4624 приводит к быстрому обнаружению и подтверждению атаки, а роль аналитика L1 сводится к проверке фактов, отсеиванию шума и своевременной эскалации.
