# Типы алертов в SIEM и базовый tuning FP

## Границы понятий: алерт, событие, инцидент и роль FP в рабочем процессе SOC

SIEM-алерт — это извещение, автоматически сгенерированное платформой управления информационной безопасностью и событиями (SIEM) при совпадении поступающих данных с заранее определённым детектирующим правилом. Алерт сигнализирует о потенциально вредоносной активности, политике безопасности или аномалии и требует анализа оператором SOC первого уровня (L1). В отличие от «сырого» события (event), которое представляет собой единичную запись в логе, и в отличие от подтверждённого инцидента, алерт — это пороговый, интерпретированный сигнал с присвоенным приоритетом. Ложноположительный алерт (false positive, FP) возникает, когда правило зарегистрировало легитимную, безопасную активность как подозрительную. Противоположное явление — ложноотрицательный (false negative) — пропуск реальной угрозы. Настройка (tuning) правил детектирования направлена на минимизацию FP при сохранении максимальной чувствительности к реальным угрозам.

Современный SOC обрабатывает тысячи алертов в день, и доля FP может превышать 50 % для неподготовленных сред. Поэтому для аналитика L1 критически важно не только знать типы алертов, но и владеть базовыми приёмами их настройки, чтобы снизить шум и не пропустить инцидент. Путаница между типами алертов, методами их генерации и стратегиями подавления ведёт к «усталости от алертов» (alert fatigue), когда оператор начинает игнорировать даже значимые сигналы.

```text
[Источники логов] ──(нормализация)──▶ [SIEM-движок]
                                        │
                          ┌─────────────┼─────────────┐
                          ▼             ▼             ▼
                     [Правила]   [Корреляция]   [Аналитика]
                          │             │             │
                          └─────────────┼─────────────┘
                                        ▼
                                  [Алерт] ──▶ [SOC-аналитик]
                                        │
                          ┌─────────────┼─────────────┐
                          ▼             ▼             ▼
                   [True Positive] [False Positive] [Обратная связь для тюнинга]
```

Ключевые сущности, разграничиваемые в контексте алертов, сведены в таблицу:

| Сущность           | Определение                                                                                     | Пример                                                                                       |
|--------------------|-------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| Событие (event)    | Атомарная запись из лога, не имеющая самостоятельно присвоенной критичности.                        | `EventID 4625: An account failed to log on` в Windows Security Log                           |
| Алерт (alert)      | Результат срабатывания правила; содержит описание, временную метку, уязвимый актив и приоритет. | «Brute-force атака на хост 10.1.2.5: 15 неудачных попыток входа за 2 минуты»               |
| Инцидент (incident)| Подтверждённое нарушение безопасности или политики, требующее реагирования.                     | Скомпрометированная учётная запись, повлёкшая боковое перемещение злоумышленника           |
| False Positive (FP)| Алерт, фиксирующий легитимную, не угрожающую деятельность.                                       | Массовый алерт на неудачные входы, вызванный плановой сменой паролей сервисным скриптом     |
| True Positive (TP) | Алерт, корректно идентифицировавший реальную угрозу или нарушение.                               | Обнаружен вход злоумышленника с украденными учётными данными в нерабочее время              |

Тюнинг алертов — итеративная практика: аналитик L1 или старший инженер, опираясь на обратную связь по FP, изменяет условия правил, пороги, списки исключений, временные окна и источники данных. Цель — оставить алерты значимыми и операционально оправданными. Слепое отключение правил без анализа метрик недопустимо; необходимо понимать внутреннюю классификацию алертов и их «механику».

## Внутреннее устройство: таксономия алертов и природа ложноположительных срабатываний

SIEM-алерты классифицируются по нескольким осям: по источнику данных, по методу детектирования и по типу выявляемой угрозы. Понимание этих измерений позволяет осознанно подходить к тюнингу, так как каждая категория имеет характерные причины FP и соответствующие инструменты коррекции.

### Классификация по источнику телеметрии

1. **Сетевые алерты** — формируются на базе NetFlow, пакетных данных, логов межсетевого экрана, IDS/IPS, DNS, прокси. Пример: «Соединение с известным вредоносным IP». Частые FP связаны с устаревшей threat intelligence или легитимным трафиком к CDN/облачным конечным точкам, разделяющих IP-адреса.

2. **Хостовые алерты** — основаны на Windows Event Log, Sysmon, Linux auditd, журналах EDR. Пример: «Обнаружен подозрительный процесс PowerShell». FP здесь возникают из-за внутренних скриптов обновлений, легитимных утилит администрирования (PsExec, WMI).

3. **Алерты идентификации и доступа (identity)** — события аутентификации, изменения членства в группах, эскалации привилегий (Active Directory, Azure AD, Okta). Характерен FP для сервисных учётных записей или массовой ротации паролей.

4. **Облачные и прикладные алерты** — логи SaaS, IaaS, CASB. Пример: «Массовое скачивание файлов из облачного хранилища». Часто FP генерирует синхронизация резервного копирования.

5. **Композитные (корреляционные) алерты** — агрегируют признаки из нескольких источников, например: «Подозрительная цепочка: фишинг-письмо → переход по URL → запуск PowerShell». Такие правила имеют более высокую точность за счёт контекста, но остро реагируют на ошибки в парсинге и временные несоответствия.

### Классификация по методу детектирования

Ниже приведена сравнительная таблица, отражающая ключевые механизмы срабатывания и характерные подходы к тюнингу:

| Метод детектирования | Принцип | Типичные причины FP | Инструменты тюнинга |
|----------------------|---------|----------------------|---------------------|
| **Сигнатурный / Rule-based** | Точное совпадение с шаблоном (строка, regex, последовательность событий) | Жёсткие сигнатуры цепляют легитимное ПО; неучтённые варианты параметров | Смягчение регулярных выражений, добавление исключений (white-listing) по процессу, пользователю, хосту |
| **Пороговый (Threshold)** | Количество одинаковых событий за временное окно превышает заданный лимит | Легитимные всплески: сканирование уязвимостей, плановые обновления, синхронизации | Подбор порога (n) и окна (T) на основе исторических метрик шумовой линии |
| **Аномалийный (Behavioral/UEBA)** | Отклонение от профиля «нормального» поведения сущности (пользователя, хоста) | Новый сотрудник, смена роли, миграция — модель ещё не обучена; резкие сезонные изменения | Обучение модели на расширенном временном промежутке, добавление контекстных сигналов (время суток, группа риска) |
| **Корреляционный (rule-chaining)** | Логическая связка нескольких разнородных событий (например, IDS + EDR + фаервол) | Расхождение временных меток, пропуск одного звена из-за проблем сбора логов | Настройка допустимого временного окна соединения (join window), проверка целостности конвейера логов |
| **Threat Intelligence (IoC)** | Сравнение индикаторов (IP, хэш, домен) с фидами TI | Устаревшие или слишком широкие индикаторы; cloud-провайдеры, попавшие в чёрные списки | Сокращение срока жизни индикатора (TTL), исключение собственных корпоративных подсетей, фильтрация по типам индикаторов |

Каждое правило в SIEM может комбинировать несколько методов. Например, правило «Подозрительная PowerShell активность» может содержать сигнатурную часть (командлеты Invoke-Expression, закодированные параметры) и пороговую часть (более 3 запусков за 5 минут). Тюнинг такого гибридного правила требует раздельной обработки каждой компоненты.

### Механизмы возникновения ложных срабатываний и стратегии коррекции

FP в SIEM вызывается тремя главными факторами:

- **Недостаточный контекст правила**: правило не учитывает роль пользователя, принадлежность к группе админов, типичное время активности. Исправляется добавлением контекстных условий (например, исключение администраторов из правила на вход в нерабочие часы).

- **Жёсткие или устаревшие условия**: буквальное совпадение с конкретной командной строкой при наличии десятка вариаций обновлений ПО. Решение — использование «разреженных» паттернов (wildcard, более общие индикаторы) и регулярное обновление содержимого от вендора.

- **Избыточность сбора**: логи с систем, не требующих мониторинга данного типа активности, генерируют шум. Тюнинг на уровне источника данных — отключение приёма журналов отладки с рабочих станций в продуктивное правило.

Базовый tuning FP строится на последовательности: собрать метрики по алертам (имя, источник, число срабатываний, время расследования, доля TP), идентифицировать правила с наихудшим соотношением затраченных человекочасов к реальной полезности и применить целенаправленные изменения — от настройки порогов и исключений до полного отключения правила с документированием риска.

## Применение: повседневная работа с типами алертов и практический тюнинг

В SOC первого уровня оператор взаимодействует с очередью алертов, где каждый алерт имеет название, серьёзность (severity), затронутые активы и краткое описание. Приоритет сортировки (triage) определяется серьёзностью и типом алерта: например, корреляционные алерты с high severity требуют немедленной реакции, тогда как одиночные пороговые алерты низкой критичности могут обрабатываться по расписанию. Знание внутренней структуры типов алертов помогает быстрее оценить достоверность: алерт от UEBA с высокой confidence требует проверки профиля пользователя; сигнатурный алерт на известный вредоносный хэш проверяется сверкой с актуальностью TI; пороговый алерт на неудачные входы — анализом источника и временного окна.

### Сбор метрик для выбора кандидатов на тюнинг

Эффективный тюнинг начинается не с правки правил, а с измерения. Рекомендуется собрать по каждому алерту (или хотя бы по топ-20 по частоте) следующие параметры за последние 90 дней:

- **Alert Name** (имя правила).
- **Alert Source** (источник: Windows Event Log, Firewall, EDR).
- **Alert Count** (количество срабатываний).
- **Total Time Investigated** — суммарное время, затраченное аналитиками на разбор алертов этого типа; в идеале — от момента acknowledge до закрытия.
- **Median Investigation Time** (медианное время разбора).
- **Efficacy** — доля истинноположительных срабатываний (TP / Total Count) на основе вердиктов аналитиков.

Эти данные агрегируются из SIEM или платформы управления инцидентами (case management). Набор из шести полей является минимальной иллюстративной схемой; в реальных SOC перечень может дополняться полями «severity drift», «mitre tacttics», но для базового тюнинга достаточно перечисленных.

После построения диаграммы, где по оси Y — efficacy, по оси X — суммарное время расследования, а размер точки соответствует количеству алертов, выделяют четыре сегмента:

   - **Высокий FP, высокое время** → приоритетный кандидат на тюнинг: много ресурсов тратится на ложные срабатывания.
   - **Высокий TP, низкое время** → хорошо настроенные правила, можно оставить без изменений.
   - **Высокий FP, низкое время** → кандидат на удаление или значительное смягчение (быстро разбираемые FP всё равно отвлекают).
   - **Высокий TP, высокое время** → ценные, но трудоёмкие алерты: стоит автоматизировать обогащение или частичную триажность.

Такая визуализация — практический инструмент приоритезации, рекомендованный в методиках [prophetsecurity.ai].

### Техники настройки на уровне правил

После идентификации проблемного правила применяют один или несколько приёмов:

1. **Настройка порога срабатывания (threshold tuning)**. Если правило «Brute-force: 5 неудачных входов за 1 минуту» генерирует много FP из-за пользователей, забывших пароль, можно увеличить порог до 10 и расширить окно до 5 минут, опираясь на статистику обычных ошибок в организации.

   ```yaml
   # Иллюстративная схема правила в Splunk ES (фрагмент)
   search: index=windows EventCode=4625
   | stats count by src_ip, user, dest
   | where count > 10 AND _time_window > 5m
   ```

2. **Добавление исключений (suppression, whitelist)**. Исключаются заведомо безопасные сущности: IP-адреса доверенных сканеров уязвимостей, учётные записи сервисов, конкретные имена процессов. Платформы SIEM обычно позволяют задавать suppression-правила либо на уровне алерта, либо прямо в логике корреляции.

   Пример suppression-окна в веб-интерфейсе (иллюстративный JSON-объект):
   ```json
   {
     "rule_id": "RUL-0042",
     "suppress": {
       "field": "user",
       "values": ["svc_backup", "sqlagent", "sccm_svc"],
       "suppress_period_sec": 86400,
       "description": "Planned service account password rotation window"
     }
   }
   ```

   В некоторых системах suppression добавляется командой или через REST API (ниже — концептуальный вызов):
   ```
   curl -X POST https://siem.local/api/rules/RUL-0042/suppress \
        -H "Authorization: Bearer <token>" \
        -d '{"field":"user","value":"svc_backup","ttl":86400}'
   ```

3. **Изменение временного окна корреляции (join window)**. Для цепочечных правил, где события A и B должны произойти в течение одной минуты, расширение окна до трёх минут может снизить FP, вызванные задержками доставки логов, при этом не теряя реальные инциденты.

4. **Обогащение контекстом и сужение фокуса**. Например, правило на подозрительные PowerShell дополняется условием, что процесс не был развернут через SCCM или не запущен из доверенной директории (`C:\Program Files\*`). Это уменьшает FP без изменения порога.

5. **Отключение правила с документированием исключения**. Если правило даёт более 95% FP и не может быть эффективно исправлено без потери смысла, принимается решение об отключении. В SOC-процессе такой шаг оформляется записью в CMDB/GRC-системе с указанием причины, временного интервала и ответственного.

### Операционная практика L1: от тюнинга к обратной связи

Аналитик L1, сталкиваясь с очевидным FP, не только закрывает алерт с вердиктом «FP», но и, согласно процессу, создаёт заявку на улучшение правила (tuning request). В зрелой SOC такая заявка содержит: идентификатор правила, краткое описание легитимного сценария, доказательства (логи), предложение по исправлению (например, добавить исключение для подсети). Инженер SIEM, рассмотрев запрос, вносит изменения и отслеживает метрики правила в последующие две недели, чтобы убедиться, что TP-срабатывания не исчезли. Таким образом, тюнинг — непрерывный цикл.

Для начинающего специалиста важно усвоить, что тюнинг — не синоним «отключения алерта». Каждое изменение должно опираться на данные и тестироваться. Платформа может предоставлять встроенные средства симуляции: прогнать изменённое правило на исторических логах и сравнить количество срабатываний до и после.

## Сквозной практический пример: снижение FP для правила «Brute-Force атаки на RDP»

**Исходные условия:** SIEM-платформа Splunk Enterprise Security (ES), аналитик L1 замечает, что правило «Excessive Failed Logins — RDP» (стандартное из набора ES) генерирует до 80 алертов в день, из которых примерно 70 являются FP. Основная причина — корпоративный скрипт инвентаризации, который каждые 30 минут опрашивает все рабочие станции по RDP с корректными учётными данными, но иногда использует устаревший пароль, вызывая серию из 6–8 событий EventID 4625 с одного хоста-источника. Порог правила: ≥5 неудачных попыток за 2 минуты. Необходимо снизить FP до уровня <5 алертов в сутки, не пропуская реальные атаки.

### Шаг 1: Анализ текущих метрик и выделение паттерна FP

Собираем статистику за 7 дней по правилу. Используем поиск в Splunk:

```spl
index=wineventlog sourcetype=WinEventLog:Security EventCode=4625
| bin _time span=2m
| stats count by _time, src_ip, dest
| sort - count
```

Вывод (усечённый) показывает, что 95% пиков приходится на одну подсеть источников `10.3.0.0/24` и пользователя `svc_inventory`. Среднее число попыток от этого источника — 7 за 2 минуты.

```text
_time                  src_ip       dest            count
2025-12-12 02:00:00   10.3.0.15   10.2.5.44         7
2025-12-12 02:02:00   10.3.0.15   10.2.5.45         6
2025-12-12 02:00:00   10.3.0.12   10.2.5.33         7
```

### Шаг 2: Добавление исключения для доверенной учётной записи и подсети

Исключаем сервисную учётную запись из правила. В редакторе ES открываем детекцию «Excessive Failed Logins — RDP» и добавляем условие `NOT (user = "svc_inventory")` в поисковый запрос правила. Также можно добавить исключение для подсети сканирования, если все узлы надёжны:

```spl
| search NOT (src_ip IN (10.3.0.0/24))
```

После сохранения мониторим правило в тестовом режиме.

### Шаг 3: Корректировка порога на основе анализа «шумовой линии»

Чтобы дополнительно снизить FP от случайных ошибок легитимных пользователей, изучаем распределение числа неудачных попыток для обычных пользователей (исключая `svc_inventory`). Запросим квантили:

```spl
index=wineventlog EventCode=4625 user!=svc_inventory
| bin _time span=5m
| stats count by user, src_ip, _time
| eventstats p95(count) as p95 by user
| table user, p95
```

Вывод показывает, что для 95% пользователей максимум составляет 4 попытки за 5 мин. Тогда повышаем порог до 8 и расширяем временное окно до 5 минут, согласовав с командой. Вносим изменения:

```spl
| where count > 8 AND _time_window > 5m
```

### Шаг 4: Временное подавление (suppression) на период плановых активностей

Раз в месяц серверный скрипт обновления вызывает аналогичный всплеск легитимных неудачных входов. Аналитик заранее ставит алерт на suppression на 24 часа через ES-команду для правила с ID `ESCU-42`:

```bash
/opt/splunk/bin/splunk add suppression "ESCU-42" \
   -match "user=svc_update" \
   -expire_after 86400
```

Или через GUI ES suppression list.

### Ожидаемый результат и проверка эффективности

Через неделю после изменений количество алертов правила снизилось с 80 до 4 в день. Два из оставшихся алертов подтверждены как TP (реальная атака подбора). Доля FP упала до менее 20 % (1–2 ложных срабатывания в день). Высвободившееся время аналитиков направлено на другие задачи. Данный кейс демонстрирует комбинацию приёмов тюнинга: исключение доверенных сущностей, подбор порога по реальным данным и периодическое подавление плановых активностей.
