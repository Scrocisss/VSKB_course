# Корреляция DNS-запрос + соединение в SIEM: детектирование C2-каналов

## Контекст и базовые понятия: DNS как командный канал и роль корреляции в SOC

DNS (Domain Name System) — фундаментальный протокол преобразования доменных имён в IP-адреса. В легитимном трафике он используется кратковременно и предсказуемо: клиент запрашивает адрес, получает ответ, после чего устанавливает непосредственное соединение с целевым узлом по IP. Злоумышленники давно эксплуатируют DNS как скрытый канал управления (C2 — Command and Control), поскольку трафик UDP/53 и TCP/53 редко фильтруется межсетевыми экранами и воспринимается как базовый инфраструктурный сервис.

Корреляция «DNS-запрос + последующее сетевое соединение» — одна из классических методик обнаружения C2-активности в SOC (Security Operations Center). Аналитик уровня L1 должен понимать, что сама по себе запись о DNS-запросе не является инцидентом, а изолированное сетевое соединение с IP-адресом — тем более. Однако связка этих двух событий во временном и контекстном окне даёт сильный сигнал: хост сначала разрешает домен, а затем устанавливает TCP/UDP‑сессию с IP, полученным в ответе. Такая цепочка типична для вредоносного ПО, которое использует DNS для обнаружения инфраструктуры управления, после чего переходит к полноценному обмену данными.

В современных SOC корреляция реализуется через SIEM-системы (Security Information and Event Management), которые агрегируют логи DNS-серверов и журналы сетевых устройств (межсетевых экранов, прокси, NetFlow/IPFIX), нормализуют поля и применяют правила корреляции. Ниже приведена сравнительная таблица, разграничивающая основные формы эксплуатации DNS в целях C2 и их видимость для корреляционного анализа «запрос + соединение».

| Форма DNS-злоупотребления | Ключевые признаки | Типичная связка «DNS‑запрос → соединение» | Пример индикаторов |
|---------------------------|-------------------|-------------------------------------------|-------------------|
| DNS‑туннелирование (T1071.004) | Данные кодируются в поддоменах; аномально длинные или высокоэнтропийные метки; TXT‑записи с произвольным содержимым | **Не всегда**: туннель может работать только в плоскости DNS без TCP-соединения к IP из ответа. Однако некоторые реализации передают управляющие команды через DNS, а полезную нагрузку забирают отдельным TCP-сеансом на полученный IP. Тогда корреляция применима. | Запрос `a3f7c2d9.bad.org`, ответ `A 198.51.100.12`, затем TCP/443 с `198.51.100.12`. |
| DNS‑маяк (beaconing) | Регулярные запросы к фиксированному домену с постоянным или джиттерным интервалом; домен разрешается на IP C2-сервера | **Применима полностью**: бэкдор периодически разрешает домен и сразу после этого устанавливает исходящее соединение с полученным адресом для получения команд. | Каждые 30 с DNS query `upd.attacker.net`, ответ `A 203.0.113.55`, затем TCP/80 `203.0.113.55`. |
| Domain Generation Algorithm (DGA) | Большое количество неуспешных NXDOMAIN-запросов к псевдослучайным доменам, пока один не разрешится в IP C2 | **Применима частично**: корреляция фиксирует момент, когда сгенерированный домен разрешился и был установлен коннект. Но детект эффективнее по аномалии NXDOMAIN-лавины. | Серия NXDOMAIN, затем A-ответ для `xg47k.example.com`, соединение с `198.51.100.99`. |
| Fast‑flux сети | Домен с коротким TTL (300 с и менее), постоянно меняющий набор IP-адресов; соединения с новыми IP после каждого разрешения | **Применима**: каждый виток разрешения приводит к новым исходящим коннектам. Аномалия — частая смена IP при одном домене + соединения. | DNS ответ для `bad.net` меняется каждые 5 мин; соединения с каждым новым IP. |
| DNS‑over‑HTTPS (DoH) / DNS‑over‑TLS (DoT) для C2 | Скрытый канал управления, зашитый в обычный HTTPS или TLS к стороннему резолверу; без расшифровки видна только TLS-сессия к порту 443/853 | **Условна**: классическая корреляция «запрос → соединение» малопригодна, поскольку сам DNS-запрос скрыт. Однако можно коррелировать TLS-сессию к DoH-провайдеру с последующим подозрительным трафиком (например, beacon‑паттерн объёмов). | TCP/443 к `doh.attacker-resolver.com`, затем через 1 с TCP/8080 к IP из этого же AS. |

**Разъяснение места корреляции в SOC-процессах**. Сотрудник SOC L1 получает автоматически сгенерированные SIEM алерты, основанные на правилах корреляции. Правило «DNS-запрос + соединение» определяет логическую цепочку: в пределах заданного временного окна (обычно от 10 с до 60 с) один и тот же конечный узел выполняет DNS-запрос к домену и затем создаёт сетевое соединение с IP, присутствовавшим в DNS-ответе. События агрегируются из разных источников: DNS-логов (Windows DNS, BIND, Infoblox, Umbrella) и фаервольных/NetFlow- журналов. SIEM нормализует поля вроде source IP, destination IP, domain, timestamp, и на их основе срабатывает правило.

Даже если C2-канал реализован через DNS-туннель без отдельного TCP-соединения, правило срабатывать не будет. Поэтому в SOC обязательно применяются несколько комплементарных детектов — как минимум одно правило на чистый DNS‑туннель (по энтропии, длине меток, периодичности), и как минимум одно правило на связку «запрос → сессия». Таким образом, корреляция «DNS + соединение» не является универсальным детектором, но закрывает значительный класс угроз, где разрешение домена предшествует полноценному взаимодействию.

## Внутреннее устройство корреляционного правила: структура, поля, индикаторы

Корреляционное правило в SIEM представляет собой автоматизированный сценарий, выполняемый в реальном времени над потоком нормализованных событий. Применительно к связке «DNS‑запрос → соединение» правило конструктивно состоит из следующих элементов:

1. **Фильтр первичного события** — выделяет события типа «DNS‑запрос», в которых зафиксирован успешный ответ с A‑записью (Address Record). Ключевые поля: `source.ip` (IP хоста‑инициатора), `dns.question.name` (запрашиваемый домен), `dns.answer.ip` (IP-адрес из ответа, часто — массив), `timestamp`.
2. **Фильтр вторичного события** — выделяет события «начало сетевого соединения» (TCP SYN или UDP-поток) от того же `source.ip` к IP-адресу, совпадающему с одним из `dns.answer.ip`. Используются журналы межсетевых экранов (syslog, NetFlow, sFlow). Поля: `netflow.src_ip`, `netflow.dst_ip`, `netflow.dst_port`, `netflow.bytes`, `timestamp`.
3. **Временное окно корреляции** — интервал, в течение которого ожидается соединение после DNS-запроса. Стандартное значение — 60 с. Значение подбирается эмпирически: слишком узкое окно потеряет легитимные отложенные соединения (например, браузер сначала делает DNS prefetch, а реальный connect позже), слишком широкое — увеличит ложные срабатывания.
4. **Логика обогащения** — добавление контекста: репутация домена (threat intelligence), возраст домена (WHOIS), географическая принадлежность IP, порт назначения, объём трафика. На основе обогащения правило может принимать решение о тревоге или накапливать баллы риска.
5. **Механизм подавления** — исключение известных легитимных сервисов: CDN (Akamai, Cloudflare) с быстрой сменой IP, почтовые серверы, доверенные обновления ОС и т.п. Реализуется через белые списки доменов или IP, а также проверку категорий веб-фильтрации.

Структурно правило часто использует «сеансовую» модель: SIEM запоминает факт DNS-разрешения от конкретного хоста в виде временного состояния и ожидает последующего события соединения с IP из ответа. При совпадении генерируется алерт с объединённой записью, содержащей поля обоих исходных событий.

Ниже показана ASCII-диаграмма, демонстрирующая поток событий и их корреляцию в SIEM:

```text
[Хост 192.168.2.88] ──DNS query: bad.example.com──▶ [DNS-сервер] ──лог──▶ [Агрегатор SIEM]
                                  │
                                  └──DNS response: A 48.217.188.16──▶
[Хост 192.168.2.88] ──TCP SYN dst: 48.217.188.16:443──▶ [МСЭ] ──лог──▶ [Агрегатор SIEM]
                                                                          │
                                                      (окно корреляции 60 с) 
                                                                          ▼
                                                                  [Правило SIEM]
                                                                   │  совпадение: запрос + соединение
                                                                   ▼
                                                                  [Алерт L1]
```

Ключевые индикаторы, на которые опирается правило, систематизированы в таблице ниже.

| Поле/индикатор                  | Признак аномалии                                                                 | Типичные легитимные значения                  |
|--------------------------------|----------------------------------------------------------------------------------|----------------------------------------------|
| `dns.question.length`          | >52 символов (макс. длина метки 63, всего имени 253); длинные поддомены характерны для туннелирования | Обычно <40 символов                         |
| `dns.question.subdomain_count` | 4 и более уровней (например, `data.payload.bad.example.com`)                     | 2–3 уровня                                   |
| `dns.question.entropy`         | Высокая энтропия (близка к 4.0 на символ) указывает на кодированный payload      | Низкая (осмысленные слова)                   |
| `dns.answer.ip` репутация      | IP принадлежит хостинг-провайдеру(Bulletproof), VPS, недавно зарегистрирован     | IP из известных AS (Amazon, Google, Akamai)  |
| `dns.answer.ip` смена          | Для одного домена ответ меняется быстрее, чем TTL; признак fast‑flux             | Стабильный IP                                |
| `dns.timestamp` периодичность  | Фиксированный интервал ± джиттер (beaconing)                                     | Хаотичная периодичность, нет постоянного ритма|
| `netflow.dst_port`             | Нестандартный порт (напр., 4444, 8080 без веб-специфики)                         | 80, 443, 53                                  |
| `netflow.bytes`                | Постоянный небольшой объём передаваемых данных (маяк) или, наоборот, большой аплоад (экфильтрация) | Вариативно, зависит от приложения           |
| `netflow.duration`             | Очень короткие (<1 с) или сверхдлинные соединения без трафика                    | Зависит от приложения, обычно не аномально  |
| `geoip.dst.country`            | Направление на «редкое» для организации государство (например, нецелевое)       | Основные страны присутствия компании         |

Для повышения точности правило должно комбинировать несколько индикаторов. Например, сам по себе запрос к новому домену с последующим соединением на 443-й порт не является подозрительным. Но если домен зарегистрирован 12 часов назад (`whois.creation_date`), его длина 47 символов, ответил IP из дешёвого VPS-провайдера, а соединение происходит каждые 120 с ± 5 с, — доверие к тревоге значительно возрастает.

## Применение и работа с корреляционным правилом: настройка, тестирование, ошибки

На практике внедрение правила «DNS-запрос + соединение» в SIEM требует тесного взаимодействия инженера по детектированию и аналитиков SOC. Рассмотрим основные этапы и инструментарий.

**Выбор источников данных**. Минимальный набор — журналы DNS-серверов (Microsoft DNS debug log, BIND querylog) и журналы межсетевых экранов (аппаратных или программных). В крупных средах добавляют NetFlow/IPFIX от маршрутизаторов или выделенных сборщиков. Для примера, при использовании Splunk ES источники настраиваются как data model «Network_Resolution» (DNS) и «Network_Traffic» (All_Traffic). В Elastic Security поля сопоставляются с `dns` и `network` ECS. Необходимо убедиться, что временные метки синхронизированы по NTP с точностью до секунды, иначе корреляция будет пропускать события.

**Написание правила**. Правило может быть реализовано на языке запросов SIEM (Splunk SPL, Elastic KQL, Azure Sentinel KQL) или через встроенный конструктор корреляций. Важно корректно обрабатывать множественные A-записи в ответе. Грубый пример правила на псевдо-SIEM-языке, иллюстрирующий логику (конкретный синтаксис зависит от платформы):

```pl
// Псевдо-SIEM: поиск связки DNS→соединение в окне 60 секунд
WITH dns_events AS (
    SELECT src_ip, question_name, answer_ip_list, timestamp
    FROM dns_logs
    WHERE query_type = 'A' AND response_code = 'NOERROR'
),
conn_events AS (
    SELECT src_ip, dst_ip, dst_port, timestamp
    FROM firewall_logs
    WHERE action = 'allowed' AND transport = 'tcp' AND tcp_flags HAS 'SYN'
)
SELECT dns.src_ip, dns.question_name, conn.dst_ip, conn.dst_port,
       dns.timestamp as dns_time, conn.timestamp as conn_time
FROM dns_events dns
JOIN conn_events conn
  ON dns.src_ip = conn.src_ip
  AND CONTAINS(dns.answer_ip_list, conn.dst_ip)
  AND conn.timestamp BETWEEN dns.timestamp AND dns.timestamp + 60s
WHERE conn.dst_ip NOT IN (whitelist_ips)
  AND question_name NOT IN (whitelist_domains)
```

Поля `whitelist_ips` и `whitelist_domains` заполняются из регулярно обновляемого списка известных CDN, публичных резолверов, серверов обновлений.

**Тестирование и настройка порогов**. Перед вводом в эксплуатацию правило запускается на исторических данных (1–2 недели) для оценки количества срабатываний. Для платформ, не поддерживающих ретро-тестирование, аналитики эмулируют трафик. В статье [Malware of the Day — Encrypted DNS Comparison](https://www.activecountermeasures.com/malware-of-the-day-encrypted-dns-comparison-detecting-c2-when-you-cant-see-the-queries) авторы использовали специально написанный Go-симулятор DNS-C2, генерирующий запросы к подконтрольному серверу 48.217.188.16 с джиттером. Аналогичный подход применим в лабораторной среде. На реальном трафике правило может давать десятки тысяч ложных срабатываний, если не применены контекстные фильтры. Метод подавления шума — динамический репутационный скоринг: каждый факт «DNS+соединение» увеличивает риск-счёт хоста, и тревога генерируется только при превышении порога после нескольких часов наблюдения.

**Типичные ошибки и подводные камни**.
- **Игнорирование кэширования DNS**. Если хост использует локальный кэш, повторные соединения с тем же IP не будут сопровождаться DNS-запросом. Правило увидит только первое разрешение и соединение, а последующие маяки останутся незамеченными. В таком случае нужно дополнять детект правилами на периодичность сетевых соединений (beaconing).
- **Слепая корреляция по IP без учёта NAT и балансировщиков**. За NAT один source IP могут делить сотни хостов, и корреляция с DNS-запросами разных пользователей будет некорректной. Решение: использовать `source.mac` или `hostname` из DHCP-логов в комбинации с DNS.
- **Ложные срабатывания на CDN и многокомпонентных веб-сайтах**. Современная страница загружает ресурсы с десятков доменов, каждый из которых может отдавать разные IP в зависимости от геолокации. Белый список доменов категории «Content Delivery» и «Web Ads» критически важен. Однако злоумышленники могут прятать C2 за популярным CDN (например, Cloudflare Workers) — тогда только контекстные признаки (периодичность, порт, редкость) помогут выделить зловред.
- **Использование единственного временного окна**. Разное ПО ведёт себя по-разному: браузеры могут делать prefetch DNS задолго до соединения; некоторые трояны разрешают домен и ждут команды, а потом соединяются через часы. Поэтому в SOC держат несколько вариантов правила с окнами 10 с, 60 с и 600 с, агрегируя результаты.
- **Отсутствие нормализации регистра букв**. Домены DNS case-insensitive, но в некоторых логах они могут быть по-разному капитализированы. SIEM должен приводить к нижнему регистру и извлекать эффективный домен второго уровня (eTLD+1) перед корреляцией.

Таким образом, эффективная эксплуатация правила требует от L1-аналитика понимания источников ложных срабатываний и умения эскалировать алерт, если связка DNS+соединение сопровождается характерными признаками из второй таблицы (длинный поддомен, энтропия, быстрая регистрация домена).

## Сквозной практический пример: выявление C2-канала через DNS-маяк с последующим TCP-коннектом

**Исходные условия**. В лабораторной сети размещён SIEM (Splunk), настроены источники: DNS-логи от сервера BIND и журналы межсетевого экрана iptables (логируются все NEW-пакеты). Время на всех узлах синхронизировано. Злоумышленник предварительно сконфигурировал домен `malc2.lab` с A-записью, указывающей на его C2-сервер `10.99.0.10` (внутренний домен для теста). На хосте жертвы `192.168.2.88` запущен троян, который каждые 30 с с джиттером ±2 с выполняет DNS-запрос к `malc2.lab`, а затем устанавливает TCP-соединение на порт 4444 по полученному IP.

**Шаг 1. Проверка поступления DNS-логов в SIEM**. Аналитик выполняет搜索 в Splunk за последние 15 минут, чтобы убедиться, что события разрешения `malc2.lab` видны.

```spl
index=dns sourcetype=bind_querylog query_name="malc2.lab"
| table _time, src_ip, query_name, answer
```

_Ожидаемый вывод_: записи с полем `answer="10.99.0.10"` от IP `192.168.2.88`, повторяющиеся примерно каждые 30 с. Если записей нет — необходимо проверить синхронизацию логов или настройку аудита DNS.

**Шаг 2. Просмотр журналов межсетевого экрана**. Аналитик ищет соединения от того же хоста к адресу `10.99.0.10` на порт 4444.

```spl
index=firewall sourcetype=iptables src_ip="192.168.2.88" dst_ip="10.99.0.10" dst_port=4444
| table _time, src_ip, dst_ip, dst_port, action
```

_Ожидаемый вывод_: события `action="NEW"` с временными метками, следующими через 1–2 с после соответствующих DNS-запросов.

**Шаг 3. Применение правила корреляции вручную**. Чтобы воспроизвести логику правила без создания автоматического алерта, аналитик выполняет streaming search с window-функцией (конкретный синтаксис Splunk):

```spl
index=dns sourcetype=bind_querylog query_name="malc2.lab" answer="10.99.0.10"
| eval dns_time=_time
| table src_ip, dns_time, answer
| join src_ip [
    search index=firewall sourcetype=iptables dst_ip="10.99.0.10" dst_port=4444 action=NEW
    | eval conn_time=_time
    | table src_ip, conn_time
]
| eval delta=conn_time-dns_time
| where delta>0 AND delta<60
| table src_ip, dns_time, conn_time, delta, answer, dst_ip, dst_port
```

_Ожидаемый результат_: строки с `delta` от 0.5 до 3 с, подтверждающие корреляцию. Это демонстрирует, что каждое разрешение домена сопровождается немедленной TCP-сессией — классический паттерн маяка.

**Шаг 4. Анализ дополнительных контекстных индикаторов** (реализуется через обогащение в SIEM). Аналитик вручную проверяет домен `malc2.lab`:

```bash
dig malc2.lab A +short
whois malc2.lab  # возраст домена (если применимо)
```

_Вывод_: `whois` показывает дату регистрации менее 24 часов назад. В SIEM этот признак был бы добавлен полем `whois.creation_date` и вызвал бы дополнительное повышение серьёзности алерта.

**Шаг 5. Реагирование**. На основании полученных данных L1-аналитик эскалирует инцидент на L2 с приложением скриншотов запросов и описанием цепочки доказательств: регулярные DNS-запросы к свежезарегистрированному домену, корреляция с TCP-коннектами на нестандартный порт 4444, джиттер 2 с. Рекомендуется изолировать хост `192.168.2.88` и провести форенсику.

Этот сквозной пример иллюстрирует полный цикл: от поступления сырых логов до подтверждённого алерта с высоким контекстом. Корреляционное правило автоматизирует шаги 3 и частично 4, позволяя L1 быстро принимать решение без ручного построения запросов.
