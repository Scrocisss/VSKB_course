# TCP: трёхстороннее рукопожатие, порты и флаги

## Контекст транспортного уровня и ключевые понятия TCP

Transmission Control Protocol (TCP) — основной протокол транспортного уровня стека TCP/IP, обеспечивающий надёжную, потоковую, ориентированную на соединение доставку данных между приложениями на разных хостах. Он оперирует на четвёртом уровне модели TCP/IP (транспортном) и непосредственно использует сервисы сетевого уровня (IP) для маршрутизации сегментов. В отличие от протоколов нижних уровней, которые отвечают за передачу пакетов между интерфейсами и хостами, TCP добавляет сквозную надежность: контроль последовательности, повторную передачу потерянных сегментов, управление потоком и борьбу с перегрузкой.

Для специалиста SOC L1 фундаментальное понимание TCP необходимо, поскольку подавляющее большинство инцидентов и подозрительной активности отражается в TCP-трафике: сканирования портов, атаки на установление соединений (SYN flood), попытки перехвата сессий, туннелирование и эксфильтрация данных. Без знания механики трёхстороннего рукопожатия, семантики флагов и логики назначения портов невозможно эффективно читать журналы сетевых устройств, анализировать алармы IDS/IPS и расследовать события на транспортном уровне.

В стеке протоколов TCP/IP транспортный уровень представлен двумя базовыми протоколами: TCP и UDP. Принципиальная разница между ними определяет области применения и методы анализа. TCP — это протокол с установлением соединения (connection-oriented), в котором перед передачей полезных данных выполняется процедура handshake, согласующая начальные номера последовательности и параметры сессии. UDP — дейтаграммный протокол без установки соединения (connectionless), не гарантирующий ни доставку, ни порядок, что делает его быстрым, но менее надёжным.

Важнейшими понятиями транспортного уровня являются **порты** и **флаги**. Порт — это 16-битное число, идентифицирующее конкретное приложение или сервис на хосте. Комбинация IP-адреса и порта образует сокет, однозначно определяющий конечную точку коммуникации. В то время как IP-адрес позволяет найти целевой узел в сети, порт доставляет данные нужному процессу внутри узла. Флаги — это управляющие биты в заголовке TCP-сегмента, которые координируют состояние соединения: инициируют установку (SYN), подтверждают получение данных (ACK), завершают передачу (FIN), сбрасывают соединение (RST) и так далее. Без флагов невозможно реализовать конечный автомат TCP, обеспечивающий надёжность и упорядоченность.

Чтобы устранить распространённую путаницу, приведем сравнение ключевых смежных понятий в виде таблицы.

```text
+-----------------------------------+-------------------------------------------+-----------------------------------------------+
| Пара понятий                      | Различие по функции                       | Пример / следствие для SOC                   |
+-----------------------------------+-------------------------------------------+-----------------------------------------------+
| TCP vs UDP                        | TCP — с установлением соединения,         | HTTP/HTTPS, SSH, FTP используют TCP;         |
|                                   | гарантирует доставку и порядок;           | DNS (запросы), VoIP, потоковое видео — UDP.  |
|                                   | UDP — без соединения, нет гарантий        | SYN-пакеты характерны только для TCP.        |
+-----------------------------------+-------------------------------------------+-----------------------------------------------+
| Порт vs IP-адрес                  | IP-адрес идентифицирует хост (L3);        | Пакет приходит на IP сервера, порт 443       |
|                                   | порт идентифицирует процесс/сервис (L4)   | направляет данные процессу веб-сервера.      |
|                                   |                                           | Сканирование портов выявляет открытые сервисы|
|                                   |                                           | на конкретном IP.                            |
+-----------------------------------+-------------------------------------------+-----------------------------------------------+
| Флаг vs Опция TCP                 | Флаг — однобитовый сигнал управления      | SYN, ACK, FIN — обязательные для handshake;  |
|                                   | состоянием (обязателен для автомата);     | опции — факультативные расширения (MSS,      |
|                                   | опция — дополнительные параметры          | масштабирование окна, SACK), согласуются    |
|                                   | соединения, расширяющие возможности       | при установке.                               |
+-----------------------------------+-------------------------------------------+-----------------------------------------------+
| Порт источника vs порт назначения | Источник — обычно эфемерный (>1024)       | SOC-аналитик по порту назначения определяет |
|                                   | на клиенте; назначение — фиксированный    | целевой сервис (80 → HTTP, 22 → SSH).        |
|                                   | номер сервиса на сервере (часто <1024)    | Необычное сочетание или подозрительный       |
|                                   |                                           | порт назначения — индикатор аномалии.        |
+-----------------------------------+-------------------------------------------+-----------------------------------------------+
```

Диапазоны портов стандартизированы IANA: well-known ports (0–1023) закреплены за системными сервисами (HTTP — 80, HTTPS — 443, SSH — 22, FTP — 21 и т.д.), registered ports (1024–49151) используются приложениями по соглашению (например, 3306 для MySQL), dynamic / private ports (49152–65535) обычно выбираются операционной системой клиента для исходящих соединений как временные (эфемерные). Знание этих диапазонов помогает при фильтрации трафика: SYN на неожиданный порт назначения может говорить о сканировании, а обращение с эфемерного порта к нестандартному high-порту — о custom-протоколах или туннелях.

Таким образом, TCP через механизм портов и управление флагами создаёт иллюзию выделенного канала связи между приложениями поверх ненадёжной IP-сети. Следующий раздел детально рассматривает, как устроен TCP-сегмент и как флаги управляют жизненным циклом соединения, начиная со знаменитого трёхстороннего рукопожатия.

## Внутреннее устройство TCP-сегмента и механика трёхстороннего рукопожатия

### Структура заголовка TCP как носитель портов и флагов

Каждая единица данных, передаваемая протоколом TCP, называется сегментом. Сегмент состоит из заголовка и, возможно, полезной нагрузки. Минимальный размер заголовка — 20 байт, максимальный (с опциями) — 60 байт. Именно заголовок содержит поля портов и управляющие флаги, а также номера последовательности и подтверждения, критичные для надёжной доставки.

Основные поля заголовка TCP (RFC 9293, ранее RFC 793) показаны в таблице ниже. Для SOC-аналитика наиболее важны поля, выделяемые жирным, так как они напрямую фигурируют в фильтрации и сигнатурах атак.

```text
+---------------------------+-----------+--------------------------------------------------+
| Поле                      | Размер    | Назначение в контексте SOC                        |
+---------------------------+-----------+--------------------------------------------------+
| Source Port               | 16 бит    | Идентификатор приложения-отправителя. Позволяет   |
|                           |           | определить, с какого процесса пошёл трафик.        |
| Destination Port          | 16 бит    | Идентификатор приложения-получателя. Основной      |
|                           |           | индикатор целевого сервиса.                         |
| Sequence Number           | 32 бит    | Номер первого байта данных в сегменте. Используется|
|                           |           | для упорядочивания и выявления повторов/пропусков. |
| Acknowledgment Number     | 32 бит    | Номер следующего ожидаемого байта. Подтверждает    |
|                           |           | успешный приём данных. Действителен при ACK=1.     |
| Data Offset               | 4 бит     | Длина заголовка в 32-битных словах (минимум 5).    |
| Reserved                  | 3 бит     | Зарезервировано, всегда 0 (в некоторых реализациях  |
|                           |           | использовалось для ECN, но по стандарту нули).    |
| Control Flags             | 9 бит     | Управляющие биты (NS, CWR, ECE, URG, ACK, PSH,   |
|                           |           | RST, SYN, FIN) — определяют состояние сессии.      |
| Window Size               | 16 бит    | Размер окна приёма. Для управления потоком.         |
| Checksum                  | 16 бит    | Контрольная сумма заголовка и данных.               |
| Urgent Pointer            | 16 бит    | Указатель на срочные данные, если URG=1.           |
| Options                   | переменная| Дополнительные параметры (MSS, SACK, Timestamp).   |
+---------------------------+-----------+--------------------------------------------------+
```

В реальном трафике поля портов и флагов извлекаются анализаторами пакетов (Wireshark, tcpdump) и являются ключевыми для построения правил корреляции. Например, IDS-сигнатура может искать пакет с флагом SYN и портом назначения 445 (SMB) для обнаружения попыток эксплуатации уязвимости EternalBlue.

### Семантика управляющих флагов

Девятибитное поле Control Flags (в классическом представлении — 6 бит, но с учётом ECN — больше) содержит следующие флаги, каждый из которых задаёт определённую команду или состояние для конечного автомата TCP:

- **NS (Nonce Sum)** — экспериментальный флаг для защиты от скрытых подтверждений (RFC 3540), редко встречается в обычном трафике.
- **CWR (Congestion Window Reduced)** — сигнал отправителю о снижении окна перегрузки (используется с ECN).
- **ECE (ECN Echo)** — уведомление о перегрузке без потери пакетов.
- **URG (Urgent)** — указывает, что поле Urgent Pointer значимо; данные помечены как срочные. В современных сетях практически не используется, при анализе SOC можно игнорировать, если нет специфических сигнатур legacy-атак.
- **ACK (Acknowledgment)** — флаг подтверждения. Если установлен, поле Acknowledgment Number действительно. Почти все пакеты, кроме начального SYN, несут ACK=1.
- **PSH (Push)** — требует немедленной передачи данных приложению без буферизации. Часто встречается в сегментах с данными, например, HTTP-запрос или ответ.
- **RST (Reset)** — принудительный сброс соединения. Используется как при аварийных ситуациях, так и злоумышленниками для обрыва чужих сессий.
- **SYN (Synchronize)** — используется при установке соединения для синхронизации начальных номеров последовательности. Встречается только в первом и втором шагах рукопожатия.
- **FIN (Finish)** — флаг завершения соединения; указывает, что отправитель закончил передачу данных. Инициирует процедуру graceful shutdown.

Наиболее критичными для работы SOC L1 являются флаги **SYN, ACK, RST, FIN**, так как они формируют базовые состояния соединения и являются индикаторами аномалий. Например, пакет с комбинацией `SYN+FIN` аномален и часто используется при fingerprinting ОС; лавина SYN-пакетов без завершения рукопожатия — признак SYN flood; неожиданный RST может говорить о сбросе соединения межсетевым экраном или атакующим.

### Процесс трёхстороннего рукопожатия (Three-Way Handshake)

Трёхстороннее рукопожатие — это обязательная процедура инициализации надёжного TCP-соединения. Оно решает две задачи: согласование начальных номеров последовательности (ISN) обеих сторон и подтверждение готовности к обмену данными. Процесс происходит строго в три шага и управляется флагами SYN и ACK.

ASCII-диаграмма классического активного открытия (клиент инициирует соединение с сервером, находящимся в состоянии LISTEN):

```text
CLIENT                                            SERVER
(состояние CLOSED)                              (состояние LISTEN)
   |                                                 |
   |   1. SYN, seq=x, Flags [S]                     |
   |----------------------------------------------->|  (SYN-SENT)
   |                                                 |  переходит в SYN-RECEIVED
   |                                                 |
   |   2. SYN+ACK, seq=y, ack=x+1, Flags [S.]       |
   |<-----------------------------------------------|
   | (принимает SYN-ACK)                             |
   |                                                 |
   |   3. ACK, seq=x+1, ack=y+1, Flags [.]          |
   |----------------------------------------------->|
   |                                                 |
   | состояние ESTABLISHED                         состояние ESTABLISHED
```

**Шаг 1 — SYN (Synchronize).** Клиент генерирует случайный начальный номер последовательности (ISN) `x` и отправляет TCP-сегмент с установленным флагом SYN, без флага ACK. Поле Sequence Number = `x`, поле Acknowledgment Number = 0 (не действительно). В опциях часто передаётся Maximum Segment Size (MSS), например, 1460 байт для Ethernet. Клиент переходит в состояние SYN-SENT. В терминах tcpdump такой пакет отображается как `Flags [S]`.

**Шаг 2 — SYN+ACK.** Сервер, получив SYN, генерирует свой ISN `y`, устанавливает флаги SYN и ACK (пакет `[S.]`). Sequence Number = `y`, Acknowledgment Number = `x+1`, подтверждая получение клиентского SYN. Сервер переходит в состояние SYN-RECEIVED. Фактически сервер одновременно синхронизирует свой номер и подтверждает клиентский.

**Шаг 3 — ACK.** Клиент, получив SYN-ACK, отправляет сегмент с флагом ACK (`[.]`), Sequence Number = `x+1`, Acknowledgment Number = `y+1`. С этого момента соединение считается установленным с обеих сторон, и начинается передача данных. Поле Acknowledgment Number действительно, так как флаг ACK установлен.

После успешного рукопожатия клиент и сервер находятся в состоянии ESTABLISHED и могут обмениваться данными. Каждый последующий сегмент данных будет нести флаг ACK, а номера последовательности и подтверждения будут инкрементироваться на количество переданных байт.

### Завершение соединения (контекст)

Хотя основное внимание уделяется трёхстороннему рукопожатию, важно представлять полный жизненный цикл, особенно в SOC, где некорректное закрытие может быть признаком атаки. Корректное завершение (graceful shutdown) использует четыре шага с флагами FIN и ACK:

1.  Активная сторона (например, клиент) отправляет FIN (`Flags [F.]` или `[.F]` с ACK), переходя в FIN-WAIT-1.
2.  Пассивная сторона подтверждает FIN через ACK, переходит в CLOSE-WAIT.
3.  Пассивная сторона, завершив свои данные, отправляет свой FIN, переходя в LAST-ACK.
4.  Активная сторона подтверждает FIN через ACK, переходит в TIME-WAIT (обычно 2MSL), после чего соединение закрывается.

Аварийный сброс происходит с помощью флага RST: отправитель немедленно разрывает соединение без ожидания подтверждений. RST-пакеты генерируются при попытке подключения к закрытому порту, при нарушении последовательности, а также межсетевыми экранами для блокировки нежелательного трафика.

### Конечный автомат TCP и флаги

Детальное поведение TCP описывается конечным автоматом с 11 состояниями (RFC 793). Наиболее часто встречающиеся в трассировке состояния, связанные с флагами:

- `LISTEN` — сервер ожидает входящий SYN.
- `SYN-SENT` — клиент отправил SYN, ждёт SYN-ACK.
- `SYN-RECEIVED` — сервер получил SYN, отправил SYN-ACK, ждёт ACK.
- `ESTABLISHED` — нормальный обмен данными.
- `FIN-WAIT-1` — отправлен FIN, ожидание ACK или FIN.
- `CLOSE-WAIT` — получен FIN, отправлен ACK, ожидание закрытия со стороны приложения.
- `LAST-ACK` — отправлен FIN после CLOSE-WAIT, ожидание ACK.
- `TIME-WAIT` — активное закрытие завершено, ожидание таймаута для очистки сети.

SOC-аналитик редко видит напрямую состояния конечного автомата, но может восстанавливать их по флагам в захваченном трафике. Например, затянувшееся состояние SYN-RECEIVED без завершающего ACK — признак SYN flood.

Таким образом, порты в заголовке определяют приложения, а флаги управляют переходом между состояниями, реализуя надёжное соединение. Следующий раздел посвящён практическим аспектам анализа этих артефактов специалистом уровня L1.

## Применение в SOC: анализ TCP-портов и флагов в трафике

### Инструменты и базовые операции

В работе SOC L1 основной инструментарий для работы с TCP на уровне пакетов — анализаторы трафика (tcpdump, TShark, Wireshark) и системы генерации алармов (IDS/IPS, SIEM). Умение быстро извлечь из PCAP или живого трафика информацию о портах и флагах — обязательный навык. Рассмотрим типовые команды и фильтры под операционной системой Linux (или в среде песочницы SOC).

**Чтение pcap-файла с tcpdump:**
```bash
tcpdump -nr captured.pcap
```
Ключ `-n` отключает DNS-разрешение, `-r` читает файл. Вывод по умолчанию содержит временную метку, IP-адреса, порты и сокращённые флаги в квадратных скобках.

**Фильтрация по портам.** Для выделения трафика конкретного сервиса:
```bash
tcpdump -nr captured.pcap port 443
```
Или для проверки соединений на определённый серверный порт:
```bash
tcpdump -nr captured.pcap dst port 22
```
Для анализа сканирующей активности полезны фильтры на диапазоны портов, например:
```bash
tcpdump -nr captured.pcap 'tcp dst portrange 1-1024'
```

**Фильтрация по флагам.** Беркли-синтаксис tcpdump позволяет выбирать пакеты с конкретным набором флагов. Вот несколько примеров, критичных для SOC:

- Все SYN-пакеты (независимо от ACK): `'tcp[tcpflags] & tcp-syn != 0'`
- Только чистый SYN (без ACK): `'tcp[tcpflags] == tcp-syn'`
- SYN-ACK: `'tcp[tcpflags] & (tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)'`
- RST-пакеты: `'tcp[tcpflags] & tcp-rst != 0'`
- FIN-пакеты: `'tcp[tcpflags] & tcp-fin != 0'`
- Необычные комбинации, например SYN+FIN: `'tcp[tcpflags] & (tcp-syn|tcp-fin) == (tcp-syn|tcp-fin)'`

Эти выражения можно комбинировать с фильтрами по портам и хостам.

### Чтение флагов в выводе tcpdump

В выводе tcpdump флаги показываются в квадратных скобках после `Flags`. Сокращения:
- `S` — SYN
- `.` — ACK (точка)
- `F` — FIN
- `R` — RST
- `P` — PSH
- `U` — URG (редко)
Комбинации записываются слитно: `[S.]` — SYN+ACK, `[F.]` — FIN+ACK, `[R.]` — RST+ACK, `[P.]` — PSH+ACK. Чистый ACK обозначается `[.]`.

Пример разбора фрагмента вывода трёхстороннего рукопожатия:
```text
12:34:56.789012 IP 192.168.1.100.54321 > 10.0.0.1.443: Flags [S], seq 1234567890, win 64240, options [mss 1460], length 0
12:34:56.790123 IP 10.0.0.1.443 > 192.168.1.100.54321: Flags [S.], seq 987654321, ack 1234567891, win 65535, options [mss 1460], length 0
12:34:56.790256 IP 192.168.1.100.54321 > 10.0.0.1.443: Flags [.], ack 1, win 64240, length 0
```
Из этой записи видно:
- Клиентский эфемерный порт 54321, серверный порт 443.
- Первый пакет: чистый SYN, seq=1234567890.
- Второй: SYN-ACK, seq=987654321, ack=1234567891 (подтверждение клиентского SYN).
- Третий: ACK, ack=1 (tcpdump показывает относительные номера после первого SYN по умолчанию, на самом деле ack=987654322). Соединение установлено.

Для SOC важно уметь отличать успешное рукопожатие от неудачного. Если после SYN идёт RST вместо SYN-ACK — порт закрыт или трафик блокируется. Массовые SYN без ответа — признак сканирования. Отсутствие завершающего ACK при установке (half-open) может указывать на асимметричную маршрутизацию или SYN flood.

### Анализ в Wireshark

В Wireshark флаги отображаются в деталях пакета в виде набора битов с галочками, а также в краткой информации колонки Info. Для быстрой фильтрации можно использовать выражения:
`tcp.flags.syn == 1 and tcp.flags.ack == 0` — чистый SYN.
`tcp.flags.syn == 1 and tcp.flags.ack == 1` — SYN-ACK.
`tcp.flags.reset == 1` — RST.
Для поиска аномалий полезна статистика Expert Infos, подсвечивающая, например, дублирующиеся ACK, предыдущий сегмент потерян, повторные передачи и т.д.

### Типичные индикаторы атак на уровне TCP

С точки зрения SOC L1, ряд шаблонов TCP-трафика должен немедленно привлекать внимание:

- **SYN flood (Direct DDoS)**: множество SYN-пакетов с одного или многих IP к одному порту жертвы. При этом пакеты приходят быстрее, чем сервер может отвечать, вызывая переполнение очереди полуоткрытых соединений. Обнаруживается по пороговому правилу на количество SYN в единицу времени.
- **Port scan**: серия SYN-пакетов с одного IP на множество портов одной или нескольких целевых систем. Может быть TCP Connect scan (полное рукопожатие) или SYN scan (half-open, ответ RST после получения SYN-ACK). Сигнатура: за короткий период времени много `Flags [S]` с разных портов назначения.
- **TCP session hijacking**: внедрение пакета с корректными номерами последовательности и флагом RST в чужую сессию для её обрыва. В логах может выглядеть как неожиданный RST от неавторизованного IP.
- **Сканирование с использованием нестандартных флагов**: Xmas scan (FIN, URG, PSH), Null scan (без флагов), FIN scan. Такие пакеты часто используются для определения ОС. При обнаружении в трафике внутренней сети следует расследовать источник.
- **Covert channels (туннелирование)**: использование полей флагов или нестандартных комбинаций для скрытой передачи данных. Например, поток ACK-пакетов без полезной нагрузки может переносить данные в полях Sequence/Acknowledgment number.

Практическое занятие по анализу с использованием tcpdump будет представлено в следующем разделе.

## Сквозной практический пример: идентификация трёхстороннего рукопожатия и анализ портов/флагов

### Исходные условия

Студент уровня SOC L1 получает задание проанализировать небольшой дамп трафика `lab.pcap`, захваченный на межсетевом экране между внутренней сетью 192.168.100.0/24 и внешним веб-сервером. Цель: найти первый успешный TCP-сеанс к HTTPS-серверу и определить используемые клиентский и серверный порты, а также подтвердить корректность рукопожатия. Рабочее окружение — терминал Linux с установленным tcpdump.

### Шаг 1. Загрузка дампа и просмотр общей статистики

```bash
tcpdump -nr lab.pcap | head -n 20
```
*Ожидаемый вывод:* первые 20 пакетов позволяют оценить, какие протоколы присутствуют. Видим смесь ARP, DNS (UDP) и TCP. Для фильтрации только TCP используем:

```bash
tcpdump -nr lab.pcap tcp | head -n 20
```
*Вывод (иллюстративная схема):* Отображаются TCP-пакеты вида `IP 192.168.100.50.54321 > 93.184.216.34.443: Flags [S]`, что сразу указывает на потенциальное начало HTTPS-сессии.

### Шаг 2. Выделение трафика HTTPS (порт 443)

Фильтруем дамп по порту 443, чтобы сузить область поиска:

```bash
tcpdump -nr lab.pcap -tttt port 443
```
*Ожидаемый вывод (фрагмент):*
```text
12:00:01.123456 IP 192.168.100.50.49152 > 93.184.216.34.443: Flags [S], seq 1000, win 64240, length 0
12:00:01.124567 IP 93.184.216.34.443 > 192.168.100.50.49152: Flags [S.], seq 5000, ack 1001, win 65535, length 0
12:00:01.124600 IP 192.168.100.50.49152 > 93.184.216.34.443: Flags [.], ack 1, win 64240, length 0
12:00:01.125000 IP 192.168.100.50.49152 > 93.184.216.34.443: Flags [P.], seq 1:200, ack 1, win 64240, length 199
12:00:01.125100 IP 93.184.216.34.443 > 192.168.100.50.49152: Flags [.], ack 200, win 65535, length 0
...
```
Это классическое трёхстороннее рукопожатие с последующей передачей данных. Флаг `-tttt` выводит временную метку в человекочитаемом формате.

### Шаг 3. Верификация рукопожатия по флагам

Проверяем, что пакеты действительно формируют полную установку соединения. Для этого отфильтруем только пакеты с флагами SYN или FIN/RST, чтобы увидеть границы сессии:

```bash
tcpdump -nr lab.pcap 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0 and port 443'
```
*Ожидаемый вывод (фрагмент):*
```text
12:00:01.123456 IP 192.168.100.50.49152 > 93.184.216.34.443: Flags [S] ...
12:00:01.124567 IP 93.184.216.34.443 > 192.168.100.50.49152: Flags [S.] ...
```
Третий пакет (ACK) не содержит SYN/FIN/RST, поэтому он не выводится, но это нормально. Убеждаемся, что первым идёт `[S]` от клиента, затем `[S.]` от сервера, что соответствует успешному началу.

### Шаг 4. Извлечение информации о портах

Используем утилиту `tshark` (командная версия Wireshark), если доступна, для получения структурированного вывода:

```bash
tshark -r lab.pcap -Y "tcp.flags.syn==1 and tcp.flags.ack==0 and tcp.dstport==443" -T fields -e ip.src -e tcp.srcport -e ip.dst -e tcp.dstport -e tcp.flags
```
*Вывод:*
```text
192.168.100.50   49152   93.184.216.34   443   0x0002
```
Значение флагов 0x0002 соответствует SYN. Ищем ответный SYN-ACK:

```bash
tshark -r lab.pcap -Y "tcp.flags.syn==1 and tcp.flags.ack==1 and tcp.srcport==443" -T fields -e ip.src -e tcp.srcport -e ip.dst -e tcp.dstport -e tcp.flags
```
*Вывод:*
```text
93.184.216.34   443   192.168.100.50   49152   0x0012
```
0x0012 — это SYN+ACK. Таким образом, клиент использовал эфемерный порт 49152, сервер — стандартный порт 443. Соединение корректно.

### Ожидаемый вывод

Пример демонстрирует, как SOC-аналитик может вручную извлечь из дампа трафика признаки трёхстороннего рукопожатия, идентифицировать порты взаимодействия и верифицировать флаги. Полученная информация (внутренний IP, порт назначения, успешность handshake) может быть сопоставлена с политиками безопасности: не является ли IP клиента несанкционированным, не обращается ли он на подозрительный порт, не наблюдаются ли аномальные флаги. В данном случае оконечная точка 192.168.100.50 легитимно соединилась с публичным HTTPS-сервером, что является нормальным поведением.
