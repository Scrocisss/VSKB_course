# SMTP: путь письма и заголовки для анализа

## 1. Электронная почта как распределённая система: протоколы, роли и понятие «конверта»

Электронная почта — это не единый сервис, а распределённая система передачи сообщений, функционирующая поверх протокола SMTP (Simple Mail Transfer Protocol, RFC 5321). В отличие от HTTP, SMTP работает по принципу store-and-forward: сообщение не передаётся напрямую от отправителя получателю, а проходит цепочку серверов (Mail Transfer Agents, MTA), каждый из которых временно хранит письмо и пересылает его следующему. Стек TCP/IP относит SMTP к **прикладному уровню**; порт 25 используется для межсерверной пересылки, порт 587 — для отправки клиентом (submission), порт 465 — для SMTPS (устаревший, но применяемый). Параллельно существуют протоколы доступа к ящику: POP3 (порт 110/995) и IMAP (143/993). Их разграничение — фундамент для понимания того, где заканчивается транспортировка и начинается чтение письма.

Каждое письмо состоит из трёх логических частей:
1. **SMTP-конверт** (envelope) — информация, переданная в командах `MAIL FROM` и `RCPT TO` во время SMTP-сессии. Она не видна в клиенте и используется для маршрутизации и формирования bounce-уведомлений.
2. **Заголовки** (headers) — блок метаданных, следующий за конвертом, оформленных в соответствии с RFC 5322 (Internet Message Format). Включает `From:`, `To:`, `Subject:`, `Date:`, `Message-ID:`, а также технические поля `Received:`, `Return-Path:`, `Authentication-Results:` и др.
3. **Тело** — содержимое письма, часто состоящее из нескольких MIME-частей.

Именно смешение конверта и заголовков порождает множество атак: злоумышленник может указать произвольный адрес в заголовке `From:`, в то время как реальный отправитель (envelope `MAIL FROM`) остаётся скрытым. Анализ служебных заголовков для SOC-специалиста начинается с чёткого разделения этих понятий.

Субъекты доставки:
- **MUA** (Mail User Agent) — клиент отправителя или получателя (Thunderbird, Outlook, веб-интерфейс).
- **MSA** (Mail Submission Agent) — сервер, принимающий письмо от MUA по порту 587 после аутентификации; выполняет первичную проверку и добавляет недостающие заголовки.
- **MTA** (Mail Transfer Agent) — сервер ретрансляции (например, Postfix, Exchange). Каждый MTA добавляет новый заголовок `Received:`.
- **MDA** (Mail Delivery Agent) — финальный сервер, помещающий письмо в ящик получателя (Dovecot, procmail, Exchange Mailbox Server).

Ниже приведено ключевое отличие конвертных данных от представленных в заголовке `From:`:

| Параметр | SMTP-конверт | Заголовок `From:` |
|----------|---------------|-------------------|
| Источник команды | `MAIL FROM:<адрес>` в ходе SMTP-сеанса | Поле в теле сообщения, задаваемое отправителем |
| Использование | Маршрутизация, bounce-доставка | Отображение в клиенте получателя |
| Проверяется SPF | Да (по домену адреса `MAIL FROM` и IP отправителя) | Только с DMARC alignment |
| Подвержен спуфингу | Может быть подделан, но IP-адрес сессии фиксируется | Подвержен полному контролю атакующего |

Протокол SMTP текстовый, диалог состоит из команд (`EHLO`, `MAIL FROM`, `RCPT TO`, `DATA`) и ответов сервера (коды 2xx, 4xx, 5xx). Например, после `DATA` клиент передаёт заголовки и тело, завершая последовательность точкой на отдельной строке. Заголовки не проверяются на соответствие конверту — именно это делает анализ заголовков критичным для выявления подделок.

Эволюция стандартов ужесточила правила аутентификации: с 2024 года крупные провайдеры (Google, Yahoo, Microsoft) требуют SPF, DKIM и DMARC для массовых рассылок. [Email Header Analyzers: The Ultimate Guide](https://emailanalytics.com/email-headers) отмечает, что проверка заголовков остаётся быстрейшим способом подтвердить прохождение всех трёх проверок.

```text
┌─────────┐   SMTP (587)    ┌───────┐   SMTP (25)    ┌───────┐   SMTP (25)   ┌───────┐   POP3/IMAP   ┌─────────┐
│  MUA    │ ───────────────>│  MSA  │ ──────────────>│ MTA 1 │ ─────────────>│  MDA  │ <────────────│  MUA    │
│ (отпр.) │                 │       │                │       │               │       │              │ (получ.) │
└─────────┘                 └───────┘                └───────┘               └───────┘              └─────────┘
   │                           │                        │                       │
   │  задаёт "From:"           │ добавляет 1-й          │ добавляет 2-й          │ финальная доставка,
   │  и тело                   │ Received,              │ Received,              │ сохраняет в mailbox,
   │                           │ Return-Path            │ возможно проверяет SPF │ добавляет Authentication-Results
   │                           │                        │                       │
   └───────────────────────────┴────────────────────────┴───────────────────────┘
```

## 2. Трассировка пути письма: Added‑значения заголовков и структура «Received»

Движение письма сквозь SMTP-инфраструктуру документируется в заголовках `Received:`, которые добавляются каждым MTA/MDA **строго в начало** — новые строки помещаются над существующими. Поэтому просмотр `Received:` **снизу вверх** восстанавливает путь от источника к получателю. Каждая строка содержит:

- `from` — хост (или IP) и reverse-DNS-имя передающего сервера;
- `by` — хост принимающего сервера;
- `with` — протокол (ESMTP, ESMTPS для TLS, ESMTPA для аутентифицированной отправки);
- `id` — идентификатор сессии на принимающем сервере;
- `for` — (опционально) адрес получателя, если он был указан в `RCPT TO`;
- `;` временно́й штамп (date-time) в локальном времени сервера.

Пример фрагмента (иллюстративная схема, детализирует формат полей):

```text
Received: from smtp-attacker.fake (unknown [203.0.113.45])
    by mx1-defender.example.com (Postfix) with ESMTPS id 4RgH7s1vBZzL0N
    for <user@example.com>; Wed, 14 Jun 2026 14:22:10 +0300 (EEST)
Received: from [10.0.0.5] (dhcp-10-0-0-5.local [10.0.0.5])
    (authenticated bits=0)
    by smtp-attacker.fake (Exim 4.96) with ESMTPA id 1sDFkL-0007Qx-Uu;
    Wed, 14 Jun 2026 11:21:45 +0000
```

Первая строка (верхняя) — приём письма MX-сервером получателя `mx1-defender.example.com` от хоста `smtp-attacker.fake` с IP 203.0.113.45 по TLS (ESMTPS). Вторая строка — отправка с локального IP 10.0.0.5 через аутентифицированного пользователя на сервере `smtp-attacker.fake`. Чтение снизу вверх показывает, что письмо прошло два транзитных узла.

Дополнительно в заголовки включаются:

- `Return-Path:` — адрес, извлечённый из `MAIL FROM`, используется для bounce-писем; обычно совпадает с `MAIL FROM`, но может быть перезаписан MDA получателя. Согласно [Проверка и Анализ заголовков e-mail - Сообщество uCoz](https://forum.ucoz.ru/forum/45-59689-1), именно этот адрес является «настоящим отправителем».
- `Message-ID:` — уникальный идентификатор, генерируемый первым MSA или MUA; содержит доменную часть, позволяющую определить, где сообщение было создано.
- `Authentication-Results:` — структурированный блок, добавляемый MDA получателя после проверки SPF, DKIM и DMARC. Пример:

```text
Authentication-Results: mx1-defender.example.com;
    spf=fail (domain of sender@spoofed.com does not designate 203.0.113.45 as permitted sender) smtp.mailfrom=spoofed.com;
    dkim=none (no signature);
    dmarc=fail (SPF fail, DKIM none)
```

Стандарт RFC 8601 определяет формат Authentication-Results. Поле `smtp.mailfrom` показывает домен, использованный в `MAIL FROM` (конвертном), а `header.from` в DMARC-проверке сравнивается с заголовком `From:`. Расхождение — красный флаг для аналитика.

MIME-заголовки (`MIME-Version:`, `Content-Type:`, `Content-Transfer-Encoding:`) не имеют отношения к маршрутизации, но могут нести признаки вредоносности: необычные типы вложений (например, `application/x-shockwave-flash`), многокомпонентная структура с обфускацией.

Схематично формирование `Received:` и ключевых полей выглядит так:

```text
[MUA отправителя]
  │  создаёт From:, To:, Subject:, Message-ID: (клиентом)
  ▼
[MSA] ── добавляет Received: from … by msa.example.com …  
  │           устанавливает Return-Path: = MAIL FROM
  ▼
[MTA-Intermediary] ── добавляет Received: from … by relay.example.net …
  │
  ▼
[MDA получателя] ── добавляет Received: from … by mx.example.com …
  │                 вычисляет Authentication-Results: (SPF/DKIM/DMARC)
  │                 может перезаписать Return-Path
  ▼
[Почтовый ящик] ── доставляется в Maildir/mbox
```

Каждый штамп `Received` — это улика, позволяющая сопоставить IP-адреса и временные метки. Расхождение часовых поясов между серверами может вызвать ложное ощущение задержки, но систематический анализ снизу вверх даёт объективную картину. [What Is an Email Header? A Guide for Security Teams](https://abnormal.ai/blog/what-is-an-email-header) сравнивает заголовки с цифровым паспортом письма, документирующим каждый контрольный пункт.

## 3. Методика анализа заголовков в процессах SOC L1: от извлечения до вердикта

Аналитик первой линии SOC использует заголовки для быстрой классификации инцидента: легитимное письмо, фишинг, spoofing, компрометация деловой переписки (BEC). Процедура начинается с **извлечения полных заголовков** из почтового клиента:
- **Gmail** → три точки (⋮) → «Показать оригинал» → скопировать весь блок заголовков.
- **Outlook** → двойной клик на письме → Файл → Свойства → «Служебные заголовки».
- **Yahoo, Apple Mail, Thunderbird** — аналогично через просмотр исходного кода сообщения.

После получения сырого текста можно использовать ручной анализ или онлайн-анализаторы (MXToolbox Email Header Analyzer, Google Admin Toolbox Messageheader, PowerDMARC Header Analyzer). Принципиально важно: анализаторы работают на стороне клиента, особо конфиденциальные данные не передаются третьим лицам (многие инструменты, например [Email Header Analyzer Tool - Parse and Trace Email Delivery](https://netoz.au/tools/email-header-analyzer), выполняют разбор локально в браузере).

### Этапы ручного анализа (иллюстрируются примерами — поля зависят от среды; здесь демонстрируется логика, а не конкретные значения)

**Шаг 1. Определение реального источника.** Начать следует с `Return-Path:`, который отражает `MAIL FROM`. Проверить соответствие домену в `From:` — несовпадение (например, `Return-Path: <attacker@evil.com>`, а `From: "Bank" <noreply@legitbank.com>`) означает попытку спуфинга. Также поле `Reply-To:`, если задано, может перенаправить ответы на другой адрес.

**Шаг 2. Трассировка `Received:` снизу вверх.** Выявить первый `Received` (ближайший к отправителю) — IP-адрес и hostname. Проверить, не принадлежит ли он подозрительной AS, стране, не соответствует ли типичным IP источника для заявленного отправителя. Например, если письмо якобы от банка из ЕС, а исходный IP — из неавторизованного диапазона в Нигерии,Verdict явно не в пользу легитимности. Также проверяются все промежуточные серверы: нет ли open relay или скомпрометированного сервера.

**Шаг 3. Анализ `Authentication-Results`.** Ключевые протоколы:
- `spf=` — pass, fail, softfail, neutral, none. Fail (`spf=fail`) при проверке IP отправителя по SPF-записи целевого домена — признак подделки.
- `dkim=` — pass, fail, none. Отсутствие подписи (`none`) не обязательно вредоносно, но в комбинации с другими факторами усиливает подозрения.
- `dmarc=` — pass, fail, bestguesspass, none. DMARC fail указывает, что ни SPF, ни DKIM не выровнены с доменом `From:`, и письмо должно быть отвергнуто или помечено согласно политике (p=reject/quarantine). Прохождение DMARC с `p=none` не гарантирует безопасности.

**Шаг 4. Изучение вспомогательных полей.** `Message-ID`: если в идентификаторе отсутствует домен или используется сомнительный домен, не связанный с отправителем, это аномалия. `X-Mailer` или `User-Agent` (например, `X-Mailer: Microsoft Outlook 16.0`) — нестандартные значения или их подделка. Заголовки `X-CSA-Complaints` или `X-Spam-*`, добавленные спам-фильтрами получателя, показывают, почему письмо попало в спам, и могут отражать репутационные оценки.

На практике SOC L1 часто использует скрипты для автоматического разбора. Ниже приведён пример простейшего извлечения ключевых полей с помощью `grep` и `sed` (иллюстративная схема, зависит от ОС и кодировки):

```bash
# Извлечение Return-Path, SPF и DMARC из файла с заголовками (headers.txt)
echo "=== Return-Path ==="
grep -m1 '^Return-Path:' headers.txt
echo "=== SPF Result ==="
grep -oP 'spf=\K\w+' headers.txt
echo "=== DMARC Result ==="
grep -oP 'dmarc=\K\w+' headers.txt
echo "=== Received chain (short) ==="
grep '^Received:' headers.txt | sed 's/^.*by \([^ ]*\).*from \([^ ]*\).*/\1 <-- \2/'
```

Ожидаемый вывод может содержать `spf=fail`, `dmarc=fail`, a в цепочке `Received` — указание на неавторизованный сервер. Сравнение с ручной вычиткой ускоряет эскалацию инцидента.

Типичные ошибки начинающих аналитиков: игнорирование разницы между `Return-Path` и `From`, проверка только SPF (DKIM может пройти, но при несовпадении доменов DMARC всё равно сработает), невнимание к временны́м аномалиям (письмо от 2020 года, доставленное в 2026 году). Многие корпоративные среды добавляют собственные `X-`заголовки (`X-Env-Sender`, `X-MS-Exchange-Organization-AuthSource`), которые дают дополнительную информацию.

Согласно [The Ultimate Guide To Email Headers](https://emaillabs.io/en/the-ultimate-guide-to-email-headers), понимание заголовков критически важно для успешной доставки email-кампаний, но для SOC — для отражения атак. Сочетание ручного анализа с автоматизированным парсингом (в SIEM) составляет основу процесса проверки почтовых инцидентов.

## 4. Сквозной практический пример: анализ фишингового письма от «финансового департамента»

### Исходные условия
Пользователь переслал в SOC письмо с темой «Срочно: обновление платёжных реквизитов», якобы от `finance@company.com`. Письмо содержит HTML-ссылку на поддельный портал. Задача аналитика L1 — на основе заголовков определить легитимность сообщения. Рабочая станция аналитика с установленным почтовым клиентом (Outlook) и доступом к веб-анализатору. Используем ручной разбор с выгрузкой заголовков в текстовый файл.

### Шаг 1. Извлечение заголовков
Аналитик открывает сообщение в Outlook, переходит в «Свойства → Служебные заголовки», копирует их в файл `headers.txt`. Фрагмент (поля иллюстративные, но соответствуют реальному фишингу; конкретные IP и домены заменены на учебную схему):

```text
Return-Path: <attacker@phish-kit.example>
Received: from mx.phish-kit.example (unknown [198.51.100.88])
    by mx.company.com (Exchange 2019) with ESMTPS id 5hGk83zP2rVc0M
    for <user@company.com>; Tue, 20 Jun 2026 09:14:52 +0300
Received: from localhost (localhost [127.0.0.1])
    by mx.phish-kit.example (Postfix) with ESMTP id 3kL92B4q1RT
    for <user@company.com>; Tue, 20 Jun 2026 06:14:50 +0000 (UTC)
Received: from [192.168.1.101] (unknown [192.168.1.101])
    by mx.phish-kit.example (Postfix) with ESMTPA id 3kL92B4q1RT;
    Tue, 20 Jun 2026 06:14:48 +0000 (UTC)
From: "Finance Department" <finance@company.com>
To: user@company.com
Subject: URGENT: Update Payment Details
Date: Tue, 20 Jun 2026 06:14:45 +0000
Message-ID: <20260620061445.abc123@phish-kit.example>
Authentication-Results: mx.company.com;
    spf=fail (domain of company.com does not designate 198.51.100.88 as permitted sender) smtp.mailfrom=phish-kit.example;
    dkim=none (no signature);
    dmarc=fail (alignment failed, SPF fail, DKIM none) header.from=company.com
```

### Шаг 2. Анализ Return-Path и From
Поле `Return-Path: <attacker@phish-kit.example>` указывает конвертного отправителя. Заголовок `From: "Finance Department" <finance@company.com>` — подставной. Возвратный адрес не совпадает с отображаемым, что является признаком spoofing’а. Дополнительно проверяем `Reply-To`, но в данном письме он отсутствует — получатель ответит на `Return-Path`, т.е. атакующему.

### Шаг 3. Трассировка Received цепочки
Чтение снизу вверх:
- Нижний `Received`: отправлено с IP `192.168.1.101` (частный адрес, возможно, машина атакующего за NAT) через аутентифицированную сессию (ESMTPA) на `mx.phish-kit.example`.
- Второй `Received`: локальный relay на том же сервере.
- Верхний `Received`: письмо получено MX-сервером получателя от `mx.phish-kit.example` с IP `198.51.100.88`. Хост и IP не имеют отношения к `company.com`. Флаг: источник не соответствует отправителю.

Аналитик может проверить IP 198.51.100.88 по репутационным базам — он засвечен в фишинговых кампаниях.

### Шаг 4. Authentication-Results
- `spf=fail`: сервер-отправитель `198.51.100.88` не авторизован для домена `company.com` (smtp.mailfrom=phish-kit.example).
- `dkim=none`: отсутствует подпись, нет возможности подтвердить целостность.
- `dmarc=fail`: политика DMARC домена `company.com` требует выравнивания SPF или DKIM с доменом From, оба не выполнены.

Совокупность факторов явно указывает на подделку. Письмо должно было быть отбраковано или помещено в спам согласно DMARC-политике (если `p=reject` или `quarantine`).

### Шаг 5. Вердикт и эскалация
На основе анализа SOC L1 классифицирует инцидент как фишинг с подделкой отправителя. Рекомендации: удалить письмо из ящиков пользователей, внести IP `198.51.100.88` и домен `phish-kit.example` в чёрные списки, проверить, не переходил ли кто-либо по ссылке, проинформировать пользователей. При необходимости эскалировать на L2 для более глубокого расследования инфраструктуры атакующего.
