# HTTP и HTTPS: методы, коды ответов и заголовки

## Протокол HTTP: основы, версии и место в стеке TCP/IP

HTTP (HyperText Transfer Protocol) — протокол прикладного уровня, предназначенный для передачи гипертекстовых документов в распределённых информационных системах. Он лежит в основе Всемирной паутины и определяет формат сообщений, которыми обмениваются клиент (обычно браузер) и сервер. Взаимодействие построено по модели «запрос-ответ»: клиент отправляет HTTP-запрос к определённому ресурсу, идентифицируемому URI, а сервер возвращает HTTP-ответ, содержащий статус обработки, метаданные и, при необходимости, тело ресурса.

С точки зрения стека TCP/IP HTTP находится на прикладном уровне. Нижележащий транспортный уровень для версий HTTP/1.1 и HTTP/2 — почти всегда TCP, порт по умолчанию 80. Протокол не сохраняет состояние (stateless): каждый запрос обрабатывается независимо, а для поддержки сессий используются внешние механизмы — чаще всего cookie или токены аутентификации.

HTTP-сообщение состоит из трёх структурных частей:
- **стартовая строка** (request line или status line) — метод, URI и версия протокола для запроса; версия, код состояния и пояснительная фраза для ответа;
- **заголовки** (headers) — набор пар «имя: значение», передающих метаинформацию;
- **тело** (body) — опциональные данные, отделённые от заголовков пустой строкой.

Заголовки подразделяются на `end-to-end` (проходят весь путь от отправителя до получателя и пересылаются промежуточными узлами) и `hop-by-hop` (действуют только для соединения между двумя соседними узлами, например, `Connection`, `Keep-Alive`). Современные реализации, начиная с HTTP/2 и HTTP/3, дополнительно используют бинарное кадрирование, но семантика методов, кодов и заголовков остаётся общей.

### Место HTTP в многоуровневой архитектуре

Для специалиста SOC L1 важно различать, на каком уровне возникают те или иные события. Ниже приведена упрощённая схема стека применительно к веб-трафику:

```text
Прикладной уровень:       HTTP (RFC 9110), HTTPS (HTTP over TLS)
                           │
Транспортный уровень:      TCP (порт 80 / 443)       QUIC (UDP 443 — для HTTP/3)
                           │
Сетевой уровень:           IP
                           │
Канальный уровень:         Ethernet / Wi-Fi
```

HTTP/1.1 и HTTP/2 используют TCP: устанавливается трёхстороннее рукопожатие, затем следует HTTP-диалог. HTTP/3 работает поверх QUIC — транспорта на базе UDP со встроенным шифрованием, что меняет профиль сетевого трафика и требует поддержки со стороны межсетевых экранов.

### Версии протокола

| Версия      | Год стандарта | Транспорт      | Основные особенности                                                                 |
|-------------|---------------|----------------|--------------------------------------------------------------------------------------|
| HTTP/0.9    | 1991          | TCP            | Только метод GET, нет заголовков, нет кодов состояния — просто «сырой» HTML         |
| HTTP/1.0    | 1996 (RFC1945)| TCP            | Добавлены методы POST, HEAD; заголовки; коды состояния; соединение закрывается после каждого запроса |
| HTTP/1.1    | 1997–2014     | TCP            | Постоянные соединения (Keep-Alive), pipelining, chunked transfer encoding, расширенное кэширование, обязательный заголовок Host |
| HTTP/2      | 2015 (RFC7540)| TCP            | Бинарное кадрирование, мультиплексирование потоков, сжатие заголовков (HPACK), server push |
| HTTP/3      | 2022 (RFC9114)| QUIC (UDP)     | Устранение блокировки на уровне потока, 0-RTT установка соединения, обязательное шифрование (TLS 1.3 встроен в QUIC) |

В SOC‑центре практическую ценность представляет различие между HTTP/1.1 и HTTP/2, так как многие системы обнаружения вторжений и WAF первоначально разрабатывались для текстового протокола, а бинарное кадрирование HTTP/2 потребовало глубокой инспекции на уровне фреймов. При анализе логов следует обращать внимание на версию протокола в стартовой строке или в поле `:version` псевдозаголовка (HTTP/2).

### Ключевые отличия HTTP от HTTPS

Хотя HTTPS полностью базируется на HTTP, его наличие принципиально меняет модель безопасности. Следующая таблица фиксирует основные разграничения.

| Характеристика                 | HTTP                             | HTTPS                                                 |
|--------------------------------|----------------------------------|-------------------------------------------------------|
| Порт по умолчанию              | 80                               | 443                                                   |
| Шифрование                     | Отсутствует; данные в открытом виде | TLS-шифрование (конфиденциальность, целостность)      |
| Аутентификация сервера         | Нет                              | X.509‑сертификат, проверка цепочки доверия             |
| Уязвимость к MITM              | Полная; трафик может быть перехвачен и модифицирован | Устойчив при корректной реализации и отсутствии компрометации CA |
| Поддержка HTTP/2 браузерами   | Только через `h2c` (почти не используется) | Только через `h2` (ALPN согласование)                 |
| Транспортные сессии            | Обычное TCP-соединение           | TCP + TLS-рукопожатие; для HTTP/3 — QUIC с встроенным TLS |
| Кэширование прокси-серверами   | Возможно                         | Затруднено, т.к. трафик шифруется (если прокси не выполняет SSL‑bump) |

Эти различия напрямую влияют на работу SOC-аналитика: при расследовании инцидента необходимо понимать, был ли сеанс зашифрован, какие заголовки могли быть добавлены прокси-устройствами (например, `X-Forwarded-*` при терминировании TLS), и мог ли злоумышленник подменить ответ сервера.

## HTTPS и методы HTTP: защищённый канал и действия над ресурсами

### HTTPS: протокол, рукопожатие и сертификаты

HTTPS расшифровывается как HTTP over TLS (ранее — SSL). Он решает три ключевые задачи безопасности:
1. **Конфиденциальность** — содержимое HTTP‑сообщений шифруется симметричным ключом, вырабатываемым в ходе рукопожатия.
2. **Целостность** — каждая запись защищена кодом аутентификации сообщения (MAC), предотвращающим подделку.
3. **Аутентификация сервера** — клиент проверяет подлинность сервера по цифровому сертификату X.509, подписанному доверенным удостоверяющим центром (CA), или по заранее заданному пину (HPKP, устарел).

Процесс установки защищённого соединения (TLS 1.2) включает следующие фазы:

1. **ClientHello** — клиент отправляет поддерживаемые версии протокола, наборы шифров, случайное число и, опционально, идентификатор сессии.
2. **ServerHello** — сервер выбирает версию и шифр‑сьют, возвращает своё случайное число и сертификат.
3. **Аутентификация и обмен ключами** — клиент проверяет сертификат (срок действия, подпись, соответствие домену, статус отзыва — через CRL/OCSP). Затем, в зависимости от механизма (RSA, (EC)DHE), стороны договариваются о предмастер‑секрете.
4. **Вычисление сессионных ключей** — из случайных чисел клиента и сервера и предмастер‑секрета по псевдослучайной функции вычисляются симметричные ключи для шифрования и контроля целостности каждого направления.
5. **Переход на шифрование** — клиент и сервер обмениваются сообщениями ChangeCipherSpec и Finished, после чего весь последующий HTTP‑трафик идёт внутри TLS‑записей.

TLS 1.3 упрощает рукопожатие, сокращая количество обменов и отказываясь от статического RSA‑обмена ключами в пользу обязательного (EC)DHE, что обеспечивает свойство forward secrecy.

Для SOC-аналитика важны следующие практические индикаторы:
- Отсутствие валидного сертификата или ошибки проверки могут свидетельствовать об атаке «человек посередине» (MITM) или фишинговом ресурсе.
- Использование устаревших версий TLS (менее 1.2) или слабых шифров (RC4, экспортные) зачастую является признаком неправильной конфигурации или атакующей инфраструктуры.
- Заголовок `Strict-Transport-Security` (HSTS) принудительно переключает браузер на HTTPS; его отсутствие допускает downgrade-атаки.

### Классификация методов HTTP

Метод HTTP указывает желаемое действие над ресурсом, заданным URI. Спецификация RFC 9110 и дополнительные документы определяют следующие стандартные методы, каждый из которых обладает свойствами безопасности (safe), идемпотентности (idempotent) и поддержки кэширования.

- **Безопасный метод** не изменяет состояние сервера: это исключительно запросы только для чтения. Примеры — `GET`, `HEAD`, `OPTIONS`.
- **Идемпотентный метод** при повторном выполнении приводит к одному и тому же результату; `PUT` и `DELETE` — идемпотентны, `POST` — нет.
- **Кэшируемость** определяется возможностью сохранения ответа на стороне клиента или прокси и зависит от метода и заголовков управления кэшем.

Ниже представлена сводная таблица основных методов. В SOC знание этих свойств помогает отличать легитимную активность от подозрительной: например, повторяющиеся `POST`-запросы к одному ресурсу с одним и тем же телом могут быть редким легитимным поведением, тогда как для `PUT` это вариант нормы.

### Методы в контексте HTTPS

Набор методов и их семантика не зависят от того, используется HTTP или HTTPS. Однако безопасность трафика принципиально меняет риски:

- При HTTP данные, пересылаемые в теле `POST`, передаются открытым текстом; при HTTPS — зашифрованы. Следовательно, SOC-аналитик не может полагаться только на SSL‑терминирующие прокси, чтобы полностью просматривать содержимое.
- Метод `CONNECT` в HTTPS используется для туннелирования через прокси (обычно к целевому серверу). Анализ целевого хоста и порта в запросе `CONNECT` позволяет выявить нелегитимные соединения, например, к нестандартным портам, характерным для C2‑каналов.
- Протокол HTTP/2 вводит псевдозаголовок `:method` вместо текстовой строки, но методы остаются теми же. Современные системы обнаружения должны нормализовать HTTP/2‑запросы к каноническому виду.

## Коды состояния HTTP: классификация и интерпретация в SOC

Код состояния HTTP — это трёхзначное число, которым сервер в стартовой строке ответа сообщает результат обработки запроса. Первая цифра определяет класс ответа, последующие две уточняют детали. Все зарегистрированные коды и их значения описаны в реестре IANA; наиболее важные — в RFC 9110. Для специалиста SOC коды состояния выступают ключевыми индикаторами при анализе веб‑трафика, так как позволяют быстро оценить характер взаимодействия.

### Класс 1xx – Информационные

Ответы этого класса носят промежуточный характер и не содержат тела. Клиент обязан быть готов принять один или несколько 1xx-ответов перед финальным.

- **100 Continue** — сервер получил начальную часть запроса и ожидает продолжения. Используется совместно с заголовком `Expect: 100-continue`, позволяет избежать отправки большого тела, если запрос будет отклонён (например, по авторизации). В SOC почти не встречается в финальных логах, но может указывать на долгоживущие сессии при сканировании.
- **101 Switching Protocols** — сервер согласен сменить протокол согласно заголовку `Upgrade` (например, переход с HTTP/1.1 на WebSocket). Злоумышленники иногда используют для обхода ограничений прокси.
- **103 Early Hints** — экспериментальный код, позволяющий серверу отправить предварительные заголовки до финального ответа, чтобы браузер начал предзагрузку ресурсов. Сам по себе не опасен.

### Класс 2xx – Успех

Свидетельствует о том, что запрос успешно принят, понят и обработан.

- **200 OK** — стандартный успех. Конкретное значение ответа зависит от метода: для `GET` — сам ресурс, для `HEAD` — только заголовки, для `POST` — результат обработки. В SOC-мониторинге огромное количество 200-х кодов не должно вызывать тревоги, если они не сочетаются с иными аномалиями (например, 200 OK в ответ на запрос к несанкционированному URL через брутфорс).
- **201 Created** — результат успешного создания ресурса (обычно после `POST` или `PUT`). Заголовок `Location` указывает URI созданного объекта. В SOC важно отслеживать несанкционированное создание ресурсов, особенно если 201 сопровождается загрузкой файла.
- **202 Accepted** — запрос принят в обработку, но результат не гарантирован; используется для асинхронной обработки. Легитимно для API очередей задач, но может служить каналом для скрытых атак (медленная обработка).
- **204 No Content** — успешный запрос, но тело отсутствует (например, после `DELETE`). Сам по себе не несёт риска, однако серия 204 внутри защищённого API без аутентификации — потенциальный признак эксплуатации.
- **206 Partial Content** — ответ на запрос с заголовком `Range`, содержит только часть ресурса. Используется для докачки файлов. Аномалией может быть агрессивное использование Range-запросов для обхода детекции или для исчерпания ресурсов (Rapid Reset).

### Класс 3xx – Перенаправление

Требует от клиента дополнительных действий для завершения запроса. Обычно браузеры автоматически выполняют переход.

- **301 Moved Permanently** — ресурс окончательно перемещён на новый URI, указанный в `Location`. Поисковые системы обновляют индекс. Злоумышленники могут эксплуатировать открытые редиректы: передача URL в параметре заставляет сервер отвечать 301 на вредоносный домен, что используется в фишинге.
- **302 Found (Moved Temporarily)** — временное перемещение. Семантически подразумевает, что в следующий раз клиент должен обращаться к исходному URI. Часто используется после успешной аутентификации. Небезопасная практика: редирект на URL, переданный в параметре, без валидации — классический open redirect.
- **307 Temporary Redirect** и **308 Permanent Redirect** — отличаются гарантией сохранения метода запроса при переходе. Их подмена может нарушить логику приложения.
- **304 Not Modified** — ответ на условный GET-запрос (заголовок `If-Modified-Since` или `If-None-Match`), означающий, что ресурс не изменился и можно использовать кэшированную версию. В SOC‑мониторинге 304‑е часто игнорируются, однако их аномально большое число может сигнализировать о чрезмерном кэшировании или разведывательной активности.

### Класс 4xx – Ошибка клиента

Эти коды возникают из-за ошибки на стороне клиента: неверный синтаксис, отсутствие аутентификации, запрет доступа.

- **400 Bad Request** — сервер не может распознать запрос из-за неверного синтаксиса. Часто является результатом fuzzing-атак: инструменты сканирования генерируют некорректные запросы. Высокая интенсивность 400‑х сигнализирует о попытке подбора параметров.
- **401 Unauthorized** — требуется аутентификация. Ответ содержит заголовок `WWW-Authenticate`. Важно понимать: 401 означает «не аутентифицирован», а не «не авторизован». В логах SOC серия 401‑х, за которой следует успешный запрос — возможно, успешный подбор пароля (брутфорс).
- **403 Forbidden** — сервер понял запрос, но отказывается его выполнять из-за недостаточности прав. Отличие от 404 иногда размыто намеренно: чтобы скрыть существование ресурса (например, вместо 403 отдают 404). При мониторинге: нарастание 403 после ряда запросов может указывать на блокировку со стороны WAF или rate‑limiting в ответ на атаку.
- **404 Not Found** — запрашиваемый ресурс не существует. Самый известный код. При анализе веб‑сервера частые 404 к несуществующим путям — признак сканирования директорий (dirbusting) или рекогносцировки.
- **405 Method Not Allowed** — сервер знает ресурс, но не поддерживает указанный метод. Например, `POST` к конечной точке, допускающей только `GET`. В логах может свидетельствовать об исследовании поддерживаемых методов или попытке эксплуатации (загрузка файла методом `PUT` на статический ресурс).
- **429 Too Many Requests** — превышен лимит запросов (rate limiting). Само по себе может указывать на добросовестного робота или DoS/DDoS. SOC должен сопоставлять с источником.

### Класс 5xx – Ошибка сервера

Указывает на неспособность сервера выполнить корректный запрос.

- **500 Internal Server Error** — универсальная ошибка сервера. Может быть результатом некорректных входных данных, приводящих к исключению. В контексте атак — частое следствие SQL‑инъекций или некорректных десериализаций. Мониторинг всплесков 500‑х критичен.
- **502 Bad Gateway** — шлюз/прокси получил недопустимый ответ от вышестоящего сервера. Характерен для проблем обратного прокси (nginx, HAProxy) или атак на бэкенд. Если бэкенд «упал» под нагрузкой DDoS, прокси начинает отдавать 502.
- **503 Service Unavailable** — сервер временно не может обрабатывать запросы (перегрузка, обслуживание). Заголовок `Retry-After` сообщает, через сколько можно повторить. Массовые 503 — индикатор DoS‑атаки или отказа инфраструктуры.
- **504 Gateway Timeout** — шлюз не дождался ответа от вышестоящего сервера за отведённое время. Может быть следствием медленной атаки (Slowloris, Slow Read).

### Практическое применение: анализ кода ответа с помощью curl

Для иллюстрации работы с кодами состояния рассмотрим получение и интерпретацию ответа сервера на запрос к несуществующему ресурсу. Команда `curl` с опцией `-I` запрашивает только заголовки (метод HEAD), а `-v` включает подробный вывод. Ниже пример запроса к гипотетическому серверу с последующим разбором.

```bash
$ curl -v http://example.com/nonexistent
```

Иллюстративный вывод:

```
*   Trying 93.184.216.34:80...
* Connected to example.com (93.184.216.34) port 80 (#0)
> GET /nonexistent HTTP/1.1
> Host: example.com
> User-Agent: curl/7.68.0
> Accept: */*
>
* Mark bundle as not supporting multiuse
< HTTP/1.1 404 Not Found
< Server: nginx/1.18.0
< Content-Type: text/html; charset=UTF-8
< Content-Length: 233
< Connection: keep-alive
< Keep-Alive: timeout=5
...
```

Здесь код 404 Not Found однозначно указывает на отсутствие ресурса. При анализе лога прокси SOC-аналитик увидит запись с `status=404`. Если такие записи идут с высокой частотой от одного IP — это повод для проверки сканирования. Дополнительно можно оценить серверный заголовок `Server`, однако в боевой среде его часто скрывают, чтобы не раскрывать технологию.

## Заголовки HTTP: структура, категории и безопасность

HTTP-заголовки — это механизм обмена метаданными между клиентом, сервером и промежуточными узлами. Они определяют параметры кэширования, аутентификации, сжатия, тип контента, политику безопасности и многие другие аспекты. Современный стандарт предписывает использование структурированных полей (Structured Fields) — типизированных списков, словарей и параметров со строгими правилами парсинга, что исключает неоднозначности старых текстовых форматов.

Заголовки делятся по направлению использования:
- **Запросные (Request headers)** — описывают контекст клиента и его предпочтения: `Accept`, `Accept-Language`, `Authorization`, `Host`, `User-Agent`, `Cookie`, `Referer`.
- **Ответные (Response headers)** — содержат инструкции сервера: `Server`, `Set-Cookie`, `Location`, `WWW-Authenticate`, `Retry-After`.
- **Представительские (Representation headers)** — описывают тело сообщения: `Content-Type`, `Content-Length`, `Content-Encoding`, `Content-Language`, `Content-Disposition`.
- **Общие (General headers)** — могут появляться как в запросе, так и в ответе: `Cache-Control`, `Connection`, `Date`, `Transfer-Encoding`.

Каждый заголовок далее относится к категориям, определённым IANA; ниже рассмотрены наиболее значимые для практики SOC и обеспечения безопасности.

### Заголовки безопасности

Эти ответные заголовки управляют политиками защиты браузера, снижая риск распространённых клиентских атак. Отсутствие или некорректная установка каждого из них — потенциальный вектор уязвимости.

1. **Strict-Transport-Security (HSTS)**  
   Принудительно запрещает браузеру использовать HTTP для данного домена в течение заданного промежутка.  
   Пример: `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`  
   - `max-age` — время действия в секундах. Рекомендуемое значение ≥ 1 год (31536000).  
   - `includeSubDomains` — распространяет политику на все поддомены.  
   - `preload` — указывает готовность к включению в список предзагрузки HSTS браузеров.  
   Отсутствие HSTS делает возможным downgrade-атаку (sslstrip). SOC может выявить незащищённый ресурс, проверив ответ на запрос по HTTPS на наличие этого заголовка.

2. **Content-Security-Policy (CSP)**  
   Определяет разрешённые источники контента (скрипты, стили, изображения, шрифты) и ограничивает выполнение inline-кода.  
   Пример: `Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'; object-src 'none';`  
   CSP — один из самых эффективных защитных механизмов против XSS и инъекций данных. Сложная политика требует тщательного конфигурирования; неверное значение может как ослабить защиту (использование `'unsafe-inline'`), так и сломать легитимный функционал. В режиме report-only (`Content-Security-Policy-Report-Only`) нарушения не блокируются, а только отправляются отчёты на указанный URI, что полезно для SOC в ходе пилотного внедрения.

3. **X-Content-Type-Options**  
   Единственное допустимое значение — `nosniff`. Запрещает браузеру «угадывать» MIME-тип, если сервер указал неправильный. Это предотвращает атаки, связанные с переопределением типа (например, загрузка JavaScript как изображения). Отсутствие этого заголовка позволяет браузеру выполнить контент, посчитав его исполняемым, что особенно опасно в сочетании с загрузкой произвольных файлов.

4. **X-Frame-Options**  
   Управляет возможностью встраивания страницы во `<frame>` или `<iframe>`.  
   - `DENY` — полностью запрещает фрейминг.  
   - `SAMEORIGIN` — разрешает встраивание только страницами с тем же источником.  
   Защита от clickjacking. Современная альтернатива — директива `frame-ancestors` в CSP, которая предпочтительнее.

5. **Referrer-Policy**  
   Определяет, какую часть исходного URL браузер отправляет в заголовке `Referer` при переходе по ссылкам или запросе ресурсов.  
   Директивы: `no-referrer`, `strict-origin-when-cross-origin` (значение по умолчанию в современных браузерах), `same-origin` и др.  
   Неверная политика может привести к утечке чувствительной информации в URL (токены, сессионные идентификаторы) при переходах на внешние сайты.

6. **Permissions-Policy** (бывший Feature-Policy)  
   Ограничивает API браузера (геолокация, камера, микрофон) для текущего источника или фреймов.  
   Пример: `Permissions-Policy: geolocation=(), camera=()` — отключает геолокацию и камеру для всех источников.

### Заголовки управления кэшированием и аутентификацией

- **Cache-Control** — основной заголовок управления кэшем. Может содержать директивы как в запросе, так и в ответе. Пара `no-cache` разрешает кэширование, но требует предварительной проверки актуальности, `no-store` — запрещает любое сохранение данных (важно для конфиденциальных ответов). Для SOC-аналитика некорректное кэширование может привести к утечке данных, если ответы с приватной информацией кэшируются прокси-серверами.
- **Authorization** — запросный заголовок для передачи учётных данных. Наиболее распространённая схема: `Basic <base64-credentials>` (небезопасна без HTTPS), `Bearer <token>` для OAuth2.0. SOC должен обращать внимание на передачу токенов в незашифрованном виде и факты многократного использования одного и того же токена с разных IP.
- **Set-Cookie** — ответный заголовок, передающий браузеру cookie. Критически важные атрибуты безопасности: `Secure` (передача только по HTTPS), `HttpOnly` (запрет доступа из JavaScript, предотвращает захват через XSS), `SameSite` (Strict/Lax/None — управление кросс-сайтовыми запросами, защита от CSRF). Отсутствие этих атрибутов должно вызывать немедленное внимание при аудите веб-приложения.

### Заголовки, добавляемые прокси и балансировщиками

Для SOC значительную ценность представляют заголовки, вносимые промежуточной инфраструктурой:

- **Forwarded** (стандартный) и его нестандартные аналоги **X-Forwarded-For**, **X-Forwarded-Host**, **X-Forwarded-Proto**, **X-Real-IP** — передают информацию об оригинальном клиенте при терминировании TLS на прокси. Аналитик должен понимать, что злоумышленник может подменять эти заголовки, если прокси не настроен на их перезапись; ложный IP-адрес в X-Forwarded-For способен запутать расследование. Правильная настройка предполагает использование директив типа `set_real_ip_from` в nginx.

### Практический запрос: получение и анализ заголовков безопасности

Для аудита защищённости веб-приложения специалист часто использует `curl` с перехватом заголовков. Пример ниже демонстрирует, как быстро оценить наличие HSTS, CSP и X-Content-Type-Options.

```bash
$ curl -I https://example.com
```

Иллюстративный вывод (с сокращениями):

```
HTTP/2 200
strict-transport-security: max-age=31536000; includeSubDomains; preload
content-security-policy: default-src 'self'; script-src 'self' 'unsafe-inline'; object-src 'none'
x-content-type-options: nosniff
x-frame-options: SAMEORIGIN
referrer-policy: strict-origin-when-cross-origin
permissions-policy: geolocation=(), microphone=()
```

Наличие полного набора актуальных заголовков с корректными директивами свидетельствует о высоком уровне защиты. В SOC-центре подобные проверки включаются в регламент регулярного сканирования внешних активов компании.

## Сквозной практический пример: аудит HTTP-ответа веб-приложения

Нижеследующий кейс моделирует действия аналитика SOC L1 при первичной оценке защищённости внешнего веб-ресурса компании. Цель — выявить отсутствие обязательных заголовков безопасности и некорректные коды ответа, что может указывать на риск для пользователей и инфраструктуры.

### Исходные условия

- Аналитик использует рабочую станцию под управлением Linux (Ubuntu 22.04), установлены утилиты `curl` и `openssl`.
- Целевой домен — `target.example.org`. Сетевое взаимодействие разрешено политиками, подключение к интернету активно.
- Предполагается, что веб-сервер принимает соединения на порт 80 (HTTP) и 443 (HTTPS), конфигурация типичная (nginx или Apache).
- Задача: зафиксировать методы, доступные на основном URI, коды состояния для HTTP и HTTPS, а также перечень и значения критических защитных заголовков.

### Шаг 1. Проверка перенаправления HTTP → HTTPS

Первым делом следует убедиться, что сервер принудительно перенаправляет клиентов на HTTPS и не отдаёт контент в открытом виде.

```bash
curl -I http://target.example.org
```

Ожидаемый вывод (иллюстративная схема):

```
HTTP/1.1 301 Moved Permanently
Location: https://target.example.org/
Connection: keep-alive
Server: nginx
...
```

Отсутствие ответа 301 (или 302) при обращении по HTTP означает, что ресурс доступен без шифрования — это критичная проблема безопасности. Попутно аналитик фиксирует заголовок `Server`, раскрывающий технологический стек (должен быть скрыт, но в примере оставлен для иллюстрации).

### Шаг 2. Получение ответа по HTTPS и анализ кода состояния

Далее отправляем HEAD-запрос к HTTPS-версии:

```bash
curl -I https://target.example.org
```

Иллюстративный вывод:

```
HTTP/2 200
date: Thu, 20 Jun 2024 09:15:42 GMT
server: nginx
content-type: text/html; charset=UTF-8
content-length: 1256
strict-transport-security: max-age=31536000
```

Код 200 OK — ожидаемый результат для главной страницы. Аналитик обращает внимание на `strict-transport-security`: значение `max-age=31536000` присутствует, но отсутствует директива `includeSubDomains`. Это означает, что поддомены (например, `app.target.example.org`) могут не иметь политики HSTS, что допустимо только при осознанной конфигурации.

### Шаг 3. Определение поддерживаемых методов

Для выяснения разрешённых методов отправляется запрос `OPTIONS`:

```bash
curl -X OPTIONS -I https://target.example.org
```

Ожидаемый ответ (схематично):

```
HTTP/2 204 No Content
allow: GET, HEAD, POST, OPTIONS
content-length: 0
```

Сервер вернул статус 204 и перечислил допустимые методы. Отсутствие `TRACE` и `CONNECT` — хороший признак. Если бы в списке оказались `PUT`, `DELETE` и особенно `TRACE`, это требовало бы дополнительной проверки на несанкционированный доступ. В SOC-аналитике сигнатура обнаружения `OPTIONS`-запроса с последующим использованием редкого метода (например, `PROPFIND` в WebDAV) может активировать расследование.

### Шаг 4. Проверка защитных HTTP-заголовков

Наконец, комплексная проверка всех ключевых заголовков безопасности. Используем `curl` и утилиту фильтрации:

```bash
curl -Is https://target.example.org | grep -iE 'strict-transport|x-frame|x-content|csp|referrer-policy|permissions-policy'
```

Предположим, вывод следующий:

```
strict-transport-security: max-age=31536000
x-content-type-options: nosniff
referrer-policy: no-referrer-when-downgrade
```

Здесь налицо несколько недостатков:
- Отсутствует `Content-Security-Policy` — полное отсутствие защиты от XSS/инъекций;
- `X-Frame-Options` не задан — уязвимость к clickjacking;
- `Referrer-Policy` установлен в `no-referrer-when-downgrade`, что может приводить к утечке части URL на HTTP-сайты;
- Политика HSTS без `includeSubDomains`, как отмечено ранее.

Данный набор наблюдений должен быть зафиксирован в тикете и передан инженерам по безопасности приложений для донастройки сервера.

### Ожидаемый вывод

Сквозной пример показывает, как аналитик SOC L1, используя базовые клиентские утилиты, может получить сведения о протоколе (HTTP/HTTPS), доступных методах, кодах ответа и критически важных заголовках безопасности. Полученные артефакты — коды 301, 200, 204, состав заголовков — позволяют сделать вывод о текущем уровне зрелости защиты веб-ресурса и сформулировать рекомендации по его усилению.
