# Порты: well-known, registered, ephemeral — что отслеживать аналитику

## Порты well-known: фундамент серверных коммуникаций
В модели TCP/IP порт представляет собой 16-битный идентификатор (0–65 535), позволяющий операционной системе направить входящий сегмент конкретному процессу или службе. Пространство портов разделено на три диапазона, закреплённых стандартом IANA: *well-known ports* (0–1023), *registered ports* (1024–49 151) и *dynamic/ephemeral ports* (49 152–65 535). Разделение отражает сочетание исторических соглашений, требований к полномочиям и динамики клиент-серверных взаимодействий.

Well‑known ports резервируются для наиболее распространённых системных служб и протоколов прикладного уровня. Их главная особенность — жёсткая привязка номера к сервису, благодаря которой клиент, зная только имя хоста, может автоматически определить целевой порт. Например, веб‑браузер, получив URL `https://example.com`, без дополнительных настроек формирует TCP-соединение к порту 443. Такое поведение реализовано через файл `/etc/services` в UNIX-подобных ОС или аналогичный реестр в Windows, где зафиксированы соответствия «имя службы — порт/протокол».

Ключевое свойство well‑known портов — требование привилегий суперпользователя (`root`/`SYSTEM`) для открытия на прослушивание. Это предохраняет от подмены легитимных сервисов непривилегированным процессом. Если злоумышленник попытается запустить HTTP-сервер на порту 80 от имени обычного пользователя, операционная система откажет в привязке. В Windows аналогичное поведение регулируется членством в группе «Администраторы» или политиками, разрешающими определённым учётным записям захватывать привилегированные порты (например, через `http.sys` для IIS).

С позиции SOC-аналитика well‑known порты служат точкой опоры — любое TCP-соединение, направленное на такой порт из внешней или внутренней сети, с высокой вероятностью является попыткой обращения к известному сервису. Это упрощает первичную классификацию трафика: 22/TCP → SSH, 25/TCP → SMTP, 53/UDP → DNS, 80/TCP → HTTP, 443/TCP → HTTPS, 3389/TCP → RDP. Ниже приведена сводная таблица наиболее значимых для SOC well‑known портов, их типичного поведения и возможных признаков злоупотребления.

| Порт (протокол) | Служба | Штатное поведение | Индикаторы аномалий (примеры) |
|----------------|--------|-------------------|--------------------------------|
| 21/TCP | FTP control | Установка командного канала, переход в активный/пассивный режим с открытием динамического порта для данных | Брутфорс учётных записей, попытки анонимного входа, передача данных на нестандартный порт |
| 22/TCP | SSH | Защищённое терминальное соединение, туннелирование | Многочисленные неудачные попытки аутентификации, подключения с нетипичных IP, SSH-туннелирование на внешние ресурсы |
| 23/TCP | Telnet | Незашифрованный удалённый доступ (устаревший) | Само присутствие открытого Telnet считается опасным из‑за передачи паролей в открытом виде |
| 25/TCP | SMTP | Пересылка почты между MTA | Спам-рассылки через открытый релей, большое количество RCPT TO на несуществующие ящики |
| 53/UDP,TCP | DNS | Разрешение имён, зонные трансферы (TCP 53) | DGA-запросы, туннелирование данных через DNS-запросы к подозрительным доменам, высокая частота TXT-записей |
| 80/TCP | HTTP | Веб-трафик, API вызовы | SQL-инъекции, загрузка вредоносных скриптов, аномально большие POST-запросы |
| 443/TCP | HTTPS | Защищённый веб-трафик | C2-каналы, маскирующиеся под HTTP/2 или TLS, сертификаты с неправильным CN, исходящий HTTPS на нестандартные порты |
| 445/TCP | SMB | Файловый и принтерный доступ в Windows | Эксплуатация уязвимостей (EternalBlue), попытки подключения с гостевой учётной записью, латеральное распространение |
| 3389/TCP | RDP | Удалённый рабочий стол Windows | Брутфорс, попытки подбора учётных записей, использование устаревших версий протокола без Network Level Authentication |

Контроль well‑known портов важен также потому, что многие межсетевые экраны и системы предотвращения вторжений (IPS) применяют к ним сигнатуры, завязанные на протокол верхнего уровня. Если злоумышленник запускает HTTPS на порту 8443 (registered), ряд систем детекции, ориентированных на стандартный порт 443, могут не применить нужные проверки. Следовательно, аналитик должен понимать, что «привязка к порту» — лишь одна из эвристик, а достоверная идентификация сервиса возможна только при анализе полезной нагрузки (например, TLS‑рукопожатия).

Архитектурная роль well‑known портов отражает принцип «сервер слушает — клиент инициирует». Серверный процесс пассивно ожидает подключений на фиксированном порту, клиент же использует для исходящего запроса динамически выделенный эфемерный порт. Эта модель закладывает основу для корреляции сессий в логах межсетевого экрана: пара `src_ip:ephemeral_port → dst_ip:well_known_port` однозначно идентифицирует клиентское соединение, а обратное направление — ответ сервера.

Таким образом, well‑known порты — это статичные, защищённые привилегиями точки входа в систему, обеспечивающие предсказуемость сетевого взаимодействия. Для аналитика Level 1 они служат исходным фильтром при триаже алертов: любое соединение на неожиданный well‑known порт или аномальная активность с привычного порта (например, сканирование диапазона 22 по внутренним хостам) обязаны немедленно привлекать внимание. Умение быстро сопоставить номер порта с ожидаемой службой и оценить степень отклонения от базовой линии является фундаментальным навыком начального звена SOC.

```
Иллюстративная выдержка из файла /etc/services (Unix):
ssh    22/tcp
smtp   25/tcp
domain 53/udp
http   80/tcp
https  443/tcp
```

## Registered ports: регламентированная гибкость
Диапазон registered ports (1024–49 151) заполняет промежуток между жёстко закреплёнными системными портами и полностью динамическим пространством. IANA регистрирует эти порты по заявкам производителей ПО и стандартизирующих организаций, однако, в отличие от well‑known, открытие registered порта не требует привилегий суперпользователя. Этот контраст формирует две ключевые особенности: с одной стороны, registered порты обеспечивают официальную идентификацию приложений в масштабах Интернета, с другой — любой непривилегированный процесс может занять такой порт, создавая риск подмены легитимного сервиса.

Процесс регистрации в IANA предусматривает выбор «владельцем» протокола или номера порта, который ещё не занят в реестре. Заявка рассматривается экспертами; после утверждения пара «порт/протокол» публикуется в общедоступном реестре Service Name and Transport Protocol Port Number Registry. Примеры зарегистрированных портов охватывают промышленные СУБД, средства удалённого управления, альтернативные HTTP-порты, корпоративные приложения и мультимедийные протоколы.

С точки зрения внутреннего устройства, registered порты ничем не отличаются от остальных: это те же 16-битные номера, обрабатываемые сетевым стеком по единым правилам. Отличие лежит исключительно в организационной плоскости и в последствиях для мониторинга. Поскольку эти порты официально сопоставлены с конкретными приложениями, аналитик может использовать их для детектирования специализированных сервисов, которые не попадают в базу well‑known, но тем не менее широко распространены.

Ниже представлена таблица наиболее критичных для SOC registered портов, их нормативного использования и типичных аномалий, регистрируемых на уровне L1.

| Порт (протокол) | Зарегистрированное приложение | Характерная активность | Поведенческие аномалии |
|----------------|-------------------------------|------------------------|-------------------------|
| 1433/TCP | Microsoft SQL Server | Запросы TDS (Tabular Data Stream), аутентификация | Попытки брутфорса учётной записи `sa`, высокая частота ошибок аутентификации, репликация на недоверенные адреса |
| 1521/TCP | Oracle Database | Протокол Oracle Net Services | Эксплуатация уязвимостей TNS Listener, попытки PoC по CVE‑2012‑1675 |
| 3306/TCP | MySQL | Подключения клиентов, репликация | Сканирование порта, атаки на `root` без пароля, эксфильтрация через UDF-функции |
| 5432/TCP | PostgreSQL | Соединения по протоколу FE/BE | Инъекции в SQL‑запросах, длительные COPY‑сессии к внешним таблицам |
| 5900/TCP | VNC | Удалённый графический доступ (RFB) | Подбор паролей, использование незашифрованных соединений |

| 8443/TCP | HTTPS Alternate | Защищённые веб-серверы | Те же риски, что и для 443, но с ослабленным вниманием средств мониторинга |
| 27017/TCP | MongoDB | Документо-ориентированные запросы | Доступ без учётных данных, широкая эксфильтрация коллекций, эпидемии вымогателей |
| 5060/UDP,TCP | SIP | Сигнализация VoIP | Сканирования, SPIT, попытки подмены вызова, отказ в обслуживании через фальшивые INVITE |

Для аналитика registered порты представляют двойной интерес. Во‑первых, они маркируют сервисы, часто содержащие критичные данные, и потому являются приоритетной целью атакующих. Во‑вторых, злоумышленники сознательно используют registered порты для обхода политик безопасности, ориентированных исключительно на well‑known диапазон. Например, вредоносное ПО может поднять C2‑сервер на порту 8080 или 8443, имитируя легитимный веб‑трафик, а бэкдор — прослушивать порт 5900, маскируясь под VNC. Следовательно, SOC должен рассматривать любой зарегистрированный порт не как автоматически легитимный, а как повод для проверки соответствия фактического протокола ожидаемому.

Особое значение registered порты приобретают в контексте микро-сегментации и политик Zero Trust, где каждый сетевой поток должен быть явно разрешён и идентифицирован. Инвентаризация используемых registered портов внутри организации (через CMDB или сканирование) позволяет построить базовую линию и выявлять отклонения. Любое новое соединение на registered порт, отсутствующее в этой базе, должно рассматриваться как потенциально подозрительное.

Таким образом, registered порты — это «регламентированная гибкость»: они дают разработчикам официальный идентификатор, но не накладывают технических ограничений на занятие порта. Для SOC L1 это означает, что при анализе алертов необходимо не просто запомнить список, а уметь быстро сверяться с IANA-реестром и внутренней документацией, чтобы отличить штатную работу корпоративной СУБД от установки неавторизованного сервиса.

## Ephemeral ports: клиентская динамика и безопасность
Эфемерные (динамические) порты занимают верхний диапазон 49 152–65 535 (рекомендация IANA). Они играют роль временных идентификаторов клиентской стороны в TCP- и UDP-сессиях. Когда пользователь открывает браузер и переходит на веб-сайт, операционная система автоматически выделяет свободный эфемерный порт (например, 52 113) и связывает его с исходящим сокетом `192.168.1.10:52113 → 93.184.216.34:80`. Сервер отвечает на тот же динамический порт, и сетевая подсистема доставляет ответное сообщение нужному процессу. По завершении соединения порт освобождается и может быть использован повторно.

Принципиальное отличие эфемерного порта от well‑known — его временный характер и отсутствие априорной привязки к какому‑либо приложению. На одном хосте одновременно могут существовать тысячи эфемерных сессий, каждая со своим портом. Управление пулом осуществляет ядро ОС, используя алгоритм, учитывающий текущую занятость, таймауты TIME_WAIT и диапазон, заданный в параметрах системы. В Linux диапазон регулируется через `net.ipv4.ip_local_port_range`, в Windows — через `netsh int ipv4 set dynamicport tcp start=49152 num=16384` или аналогичную команду для UDP. Реальные границы могут отличаться: старые Windows использовали 1025–5000, современные — 49 152–65 535; Linux по умолчанию нередко открывает 32 768–60 999, но администратор может сузить или расширить диапазон.

С позиции SOC эфемерные порты не являются самоцелью анализа, но служат контекстом для ответа на вопрос: «какой именно клиентский процесс инициировал соединение?». Поскольку лог межсетевого экрана содержит пару `src_ip:src_port`, эфемерный порт позволяет различать сессии, исходящие с одного IP. Если внутренний хост внезапно открывает сотни соединений с разными удалёнными адресами, каждое на своём эфемерном порту, это может указывать на сканирование или активность вредоносного загрузчика.

Эфемерные порты также фигурируют в ряде атак. Исчерпание пула динамических портов (ephemeral port exhaustion) может привести к отказу в обслуживании локальных приложений, которые не могут создать новые исходящие соединения. Подобный сценарий возможен при неправильно оптимизированном коде, создающем множество короткоживущих TCP-сессий без повторного использования портов из состояния TIME_WAIT, или намеренной DoS-атаке. Кроме того, пассивные серверные приложения, ожидающие данные от многих клиентов (например, P2P-узлы), могут использовать эфемерные порты для обратных соединений, обходя правила брандмауэра, разрешающие инициацию сессий только изнутри.

Для детектирования злоумышленники могут выбирать эфемерные порты в качестве «скрытых» слушающих портов, поскольку традиционные сканеры часто сосредоточены на well‑known и registered диапазонах. Бэкдор, открывший порт 54 321, с меньшей вероятностью попадёт в стандартный профиль `nmap -F`. Поэтому SOC-аналитику важно периодически проверять, не появились ли на хостах подозрительные прослушивающие порты вне documented server ports, особенно в динамическом диапазоне.

Сводные характеристики диапазонов портов, включая эфемерные, на различных ОС приведены в таблице ниже.

| ОС (версия) | Диапазон well‑known | Диапазон registered | Эфемерный диапазон по умолчанию | Настройка |
|------------|-------------------|--------------------|-------------------------------|-----------|
| Windows Server 2003 / XP | 0–1023 | 1024–49151 | 1025–5000 | `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters` — MaxUserPort |
| Windows Server 2008 и новее, Windows 7+ | 0–1023 | 1024–49151 | 49152–65535 | `netsh int ipv4 set dynamicport tcp start=...` (по умолчанию 49152, число портов 16384) |
| Linux (ядро 2.6+) | 0–1023 | 1024–49151 | Определяется параметром `ip_local_port_range`; часто 32768–60999 | `sysctl net.ipv4.ip_local_port_range="32768 60999"` |
| FreeBSD | 0–1023 | 1024–49151 | 49152–65535 (по умолчанию) | `sysctl net.inet.ip.portrange.first` и `net.inet.ip.portrange.last` |
| macOS | 0–1023 | 1024–49151 | 49152–65535 (по умолчанию) | `sysctl net.inet.ip.portrange.first` и `net.inet.ip.portrange.last` |

Артефактом анализа эфемерных портов в реальном времени служит утилита `ss` (Linux) или `netstat` (Windows). Например, команда `ss -tan state time-wait sport le 65535` покажет все сокеты в состоянии TIME_WAIT, занимающие динамические порты. Чрезмерное количество таких записей (особенно к одному удалённому адресу) может свидетельствовать о проблеме или атаке. Фрагмент типичного вывода `netstat -ano` в Windows во время множественных исходящих сессий:

```bash
C:\> netstat -ano | find "ESTABLISHED"
  TCP    192.168.1.100:50432   52.84.125.42:443      ESTABLISHED     1232
  TCP    192.168.1.100:50433   52.84.125.42:443      ESTABLISHED     1232
  TCP    192.168.1.100:50434   142.250.185.4:80       ESTABLISHED     3544
```

Аналитик видит, что процесс с PID 1232 открыл два параллельных соединения на 443 порт к одному серверу (возможный мультиплексированный HTTP/2), а процесс 3544 — к другому на 80. Такой снимок используется для привязки PID к сетевой активности, хотя для детального расследования нужны логи брандмауэра с временными метками.

Эфемерные порты также важны при анализе NetFlow/sFlow, где запись потока включает `src port`. Группировка по src IP и подсчёт уникальных src портов за интервал времени даёт метрику «количество исходящих соединений». Пороговые значения (например, >1000 уникальных src портов за минуту для одного хоста) могут указывать на сканирование или fast‑flux‑поведение.

## Мониторинг портов для SOC‑аналитика: ключевые индикаторы и методы
Для специалиста Level 1 центр внимания — не просто классификация портов, а способность выявить в потоке событий признаки злонамеренной активности. Анализ портов интегрируется в несколько этапов типового цикла реагирования: триаж алерта, первичный сбор контекста (связка порт–процесс–хост), обогащение данных (репутация удалённого IP, геолокация, принадлежность порта к известным кампаниям) и эскалация либо закрытие инцидента. Ниже рассмотрены практические метрики, источники данных и приёмы, используемые при отслеживании портов.

### Источники данных о портах
- **Логи межсетевого экрана / NGFW**: содержат 5-кортеж (src IP, src port, dst IP, dst port, protocol). Именно здесь аналитик чаще всего видит инициирующие сессии.
- **Endpoint Detection & Response (EDR) / sysmon**: регистрируют события сетевых подключений с привязкой к процессу, идентификатору пользователя и родительскому процессу. Событие с кодом 3 в Sysmon (Network connection detected) даёт полную картину: `Image`, `User`, `SourcePort`, `DestinationPort`.
- **NetFlow / IPFIX**: агрегированная информация о потоках, позволяет строить «тепловые карты» коммуникаций, выявляя резкие всплески по нетипичным парам портов.
- **Журналы веб-прокси / DNS**: полезны для кросс-корреляции — если HTTP-запрос через прокси на порт 8080 сопровождается DNS-запросом к DGA-домену, это усиливает подозрение.
- **Логи аутентификации (Windows Security Event ID 4625, SSH `auth.log`)**: показывают попытки на конкретных портах (часто с указанием порта источника, хотя важнее порт назначения).

### Приоритетные сигнатуры для L1
Аналитик не должен вручную просматривать каждую запись; необходимо опираться на готовые правила корреляции и базовые эвристики. Примеры правил, сформулированных на языке, близком к Sigma или SPL (иллюстративная структура):

```yaml
title: Outbound Connection from Workstation to Unusual Port
description: Детектирует TCP-соединения от рабочих станций на порты,
             не входящие в белый список разрешённых.
status: experimental
logsource:
  category: firewall
detection:
  selection:
    action: "allowed"
    src_ip_category: "workstation"
    dst_port|re: '^(?!80$|443$|22$|53$|123$|993$|995$|8080$)'
  condition: selection
```

Правило может быть реализовано в SIEM (Splunk, QRadar, Elastic). В Splunk запрос выглядел бы так (иллюстративный шаблон):

```splunk
index=firewall sourcetype="pan:traffic" src_zone=workstation
| where NOT (dest_port IN (80, 443, 22, 53, 123, 8080))
| stats count by src_ip, dest_ip, dest_port
```

Аналитик L1, получив алерт, сопоставляет `dest_port` с внутренними политиками: если порт 445 (SMB) в интернет-сегменте — это признак попытки латерального движения или утечки через наружу открытый SMB, что требует немедленной эскалации. Если порт 6666–6669 (часто используются ботнетами) — необходимо проверить репутацию IP.

### Портовые аномалии — быстрые проверки
- **Соединения на порты 0, 1, 137/udp (NetBIOS) вовне**: однозначно аномалия, если только не задокументированная служебная активность.
- **Исходящие соединения на порт 25 (SMTP) от рабочей станции**: может означать массовую рассылку спама вредоносным ПО (например, в рамках TrickBot).
- **Резкий рост сессий на порт 53/udp (DNS) к случайным серверам**: признак DNS‑туннелирования или DGA.
- **Внутренние хосты, открывающие множество эфемерных соединений на IRC‑порты (6667, 6697)**: типичное поведение ботов.
- **Внешние подключения к высоким динамическим портам (49 152+) извне**: обычно это ответный трафик, но если брандмауэр допускает входящую инициацию на эфемерный порт, это может быть индикатором работы reverse shell или сервера C2, прослушивающего замаскированный порт. Необходимо проверить, какой процесс слушает порт на конечной точке.

### Применение netflow для контекста
Аналитик L1 может использовать предварительно построенные панели (dashboards) в SIEM, показывающие топ‑10 портов назначения во времени. Резкое появление порта 1080 (SOCKS) или 4444 (Metasploit Meterpreter) требует немедленного реагирования. Для углублённого анализа применяются инструменты вроде `zeek-cut` на записях conn.log:

```bash
cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p proto service | sort | uniq -c | sort -nr | head
```

Пример вывода (иллюстративно):
```
 1523 192.168.0.105 8.8.8.8 53 udp dns
  412 192.168.0.105 142.251.1.1 443 tcp ssl
   10 192.168.0.105 185.220.101.1 9001 tcp -
```

Последняя строка с портом 9001 без определённого сервиса (`-`) на фоне десятков соединений к DNS и HTTPS должна привлечь внимание — возможно, это нестандартный C2‑канал.

### Связка порта с процессом на хосте
Когда брандмауэр зафиксировал подозрительное соединение от внутреннего IP на порт 31337, аналитик инициирует live‑опрос хоста через EDR или агент. Команда в Windows (PowerShell) с административными привилегиями:

```powershell
Get-NetTCPConnection -RemotePort 31337 | Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, State, OwningProcess | Format-List
```

Аналогично в Linux через `ss`:

```bash
ss -tnp | grep ':31337'
```

Вывод покажет PID и имя процесса. Если процесс — `svchost.exe` с теневой загрузкой DLL или скриптовый движок (`powershell.exe`, `wscript.exe`), инцидент эскалируется на Level 2.

### Профилирование и базовые линии
Задача L1 — не только реагировать на алерты, но и замечать отклонения от утверждённого профиля. Например, если SQL-сервер (Windows, порт 1433) внезапно начинает слать данные на внешний IP через порт 80 или 8080, это может быть признаком эксфильтрации. Здесь применяется белый список разрешённых направлений: «сервер БД имеет право инициировать исходящие соединения только на порты репликации внутри сегмента». Отклонение запускает алерт.

Таким образом, отслеживание портов для SOC‑аналитика сводится к трём шагам:
1. Идентифицировать порт назначения и классифицировать (well‑known, registered, ephemeral).
2. Сопоставить с ожидаемой функцией хоста (сервер или рабочая станция) и с утверждёнными политиками.
3. Использовать контекст (частота, объём трафика, репутация удалённого IP, привязка к процессу) для принятия решения об эскалации.

## Сквозной практический пример: расследование подозрительного исходящего соединения на порт 8080 от бухгалтерского ПК

Исходные условия:  
Организация использует SIEM на базе Elastic Stack, межсетевой экран Palo Alto Networks, EDR SentinelOne. Сотрудник бухгалтерии (рабочая станция `10.1.2.30`, Windows 10) сообщает о медленной работе, хотя явных признаков компрометации нет. SOC L1 получает автоматически сгенерированный алерт:

> **Alert**: Outbound connection from workstation to uncommon port 8080/TCP.  
> Source: 10.1.2.30:52114 → Destination: 203.0.113.47:8080, bytes sent: 1.2 MB, bytes received: 14 KB, duration: 8 min.

**Шаг 1.**  
Действие: анализ контекста соединения в SIEM (запрос к логам фаервола). Аналитик выполняет поиск всех сессий с этим IP за последние 24 часа и визуализирует временную шкалу.

```splunk
index=firewall src_ip=10.1.2.30
| timechart span=5m count by dest_port
```

Вывод (текстовое представление): столбец порта 8080 начинает появляться около 2 часов назад, с периодичностью каждые 15 минут, объём переданных данных в каждом сеансе ~1.2 МБ. Другие порты — только стандартные (443, 53). Это аномально.

**Шаг 2.**  
Действие: обогащение информации об удалённом IP. Аналитик использует встроенную интеграцию с Threat Intelligence (например, через Logstash output to VirusTotal API или GreyNoise). Результат: IP 203.0.113.47 принадлежит хостинг-провайдеру в стране, нехарактерной для бизнес-партнёров, и отмечен тегами «cobalt-strike» в сообществе. Предположительно это C2-сервер.

```json
{ "ip": "203.0.113.47", "tags": ["cobalt-strike", "command-and-control"], "asn": "AS64496", "country": "XX" }
```

**Шаг 3.**  
Действие: поиск на конечной точке процесса, инициировавшего соединение. Через EDR-консоль отправляется запрос на просмотр событий сетевых подключений (Sysmon event ID 3) за указанный период.

```sql
SELECT Image, SourcePort, DestinationPort, DestinationIp
FROM NetworkEvents
WHERE DeviceName = 'ACCT-PC01' AND DestinationPort = 8080
```

Результат:  
```
Image: C:\Users\acct_user\AppData\Local\Temp\svchost.exe
SourcePort: 52114, DestinationPort: 8080, DestinationIp: 203.0.113.47
```
Обращает внимание легитимно выглядящее имя `svchost.exe`, но расположенное в `AppData\Local\Temp`, а не в `C:\Windows\System32`. Это однозначный признак маскировки вредоносного файла.

**Шаг 4.**  
Действие: сбор дополнительных артефактов с хоста. Аналитик инициирует сканирование hosts-файла и запланированных задач, чтобы найти механизм закрепления. Через PowerShell удалённо (Invoke-Command) выполняется:

```powershell
Get-ScheduledTask | Where-Object { $_.TaskPath -like "*Temp*" } | Select TaskName, Actions
```

Вывод: обнаружена задача “GoogleUpdateCheck”, выполняющая `C:\Users\acct_user\AppData\Local\Temp\svchost.exe` каждые 15 минут. Это объясняет периодичность соединений.

**Шаг 5.**  
Действие: эскалация инцидента. Подготовлен отчёт для Level 2 с цепочкой доказательств:
- Временная шкала подозрительной сетевой активности.
- Результаты threat intel — IP связан с Cobalt Strike.
- Путь вредоносного файла и информация о персистентности.
- Рекомендация изолировать хост от сети и произвести детальный форензик.

Ожидаемый вывод примера:  
Данный кейс демонстрирует, как через призму нетипичного registered порта (8080) аналитик L1 выявил действующий канал управления, используя стандартные источники: SIEM, EDR, TI и базовые команды опроса хоста. Порт выступил первой зацепкой, а корреляция с нестандартным расположением процесса и периодичностью трафика позволила подтвердить факт компрометации без глубокого анализа вредоносного кода.
