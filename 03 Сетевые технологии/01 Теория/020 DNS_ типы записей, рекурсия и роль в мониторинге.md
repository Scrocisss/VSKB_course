# DNS: типы записей, рекурсия и роль в мониторинге

## Основы DNS: иерархия, серверы и ключевые понятия

DNS (Domain Name System) — это распределённая иерархическая база данных, которая сопоставляет доменные имена с IP-адресами и другой служебной информацией. Протокол DNS работает на прикладном уровне модели TCP/IP, используя для обмена транспортом UDP (порт 53) для запросов и ответов, размер которых не превышает 512 байт; для больших ответов и операций передачи зон (AXFR) применяется TCP [ru.wikipedia.org](https://ru.wikipedia.org/wiki/DNS). Каждое устройство в сети, выступающее в роли DNS-клиента (stub resolver), отправляет запросы к настроенному DNS-серверу, чтобы преобразовать удобочитаемое имя (например, `example.com`) в IP-адрес, необходимый для установки соединения.

С точки зрения ролей в экосистеме DNS выделяют две принципиально разные сущности — **рекурсивный (кэширующий) DNS-сервер** и **авторитативный DNS-сервер**. Первый обслуживает конечных клиентов: он получает рекурсивный запрос и берёт на себя всю цепочку обращений к другим серверам, пока не получит окончательный ответ, который затем возвращает клиенту. Второй хранит эталонные ресурсные записи для конкретной зоны (домена) и отвечает на запросы только теми данными, за которые он ответственен. Путаница между этими ролями — одна из распространённых ошибок начинающих администраторов; таблица ниже фиксирует ключевые различия.

| Характеристика | Рекурсивный (кэширующий) сервер | Авторитативный сервер |
|----------------|--------------------------------|------------------------|
| Основная задача | Выполнить полный поиск от имени клиента, обращаясь к иерархии серверов | Хранить и отдавать оригинальные записи своей зоны |
| Источник данных | Комбинация кэша и динамических запросов к другим серверам | Локальный файл зоны или база данных |
| Тип ответа на запрос | Может возвращать данные любой зоны, если они найдены или получены | Отвечает только за свои зоны; для чужих — ссылка на другие серверы или отказ |
| Кэширование | Активно кэширует ответы, соблюдая TTL | Обычно не кэширует ответы (отдаёт актуальное состояние зоны) |
| Примеры ПО и сервисов | BIND в роли recursive resolver, Unbound, PowerDNS Recursor, общедоступные 8.8.8.8, 1.1.1.1 | BIND как authoritative, NSD, Knot DNS, облачные провайдеры (AWS Route 53, Cloudflare DNS) |

В зависимости от флагов в запросе поведение сервера может быть **рекурсивным** или **итеративным**. Рекурсивный запрос (RD — Recursion Desired) требует от сервера полного разрешения цепочки; сервер сам проходит путь от корневых серверов до авторитативного источника. Итеративный запрос означает, что сервер отвечает либо известными ему данными, либо ссылкой на следующий сервер, более близкий к искомой зоне. Рекурсивный режим — типичный для взаимодействия клиент–сервер провайдера, тогда как итеративный режим преобладает при общении между серверами в процессе разрешения. Важно помнить: некорректно настроенный нерекурсивный сервер, который вместо отказа возвращает адреса корневых серверов, может быть использован для усиления DDoS-атак.

Ресурсная запись (RR) — элементарная единица хранения в DNS. Каждая запись содержит поля: имя домена, тип, класс (практически всегда IN — Internet), TTL (время жизни в кэше) и данные определённого формата. Именно наборы RR различных типов формируют ответы на запросы и являются основным предметом мониторинга. Краткий перечень критически важных типов записей:

- **A** — сопоставление имени с IPv4-адресом.
- **AAAA** — сопоставление с IPv6-адресом.
- **CNAME** — каноническое имя, алиас для другого имени.
- **MX** — почтовый обменник, указывает сервер для приёма почты домена.
- **NS** — сервер имён, авторитативный для зоны.
- **SOA** — начальная запись зоны, содержит административную информацию и серийный номер.
- **TXT** — текстовые данные, часто используются для SPF, DMARC, верификации.
- **PTR** — обратное преобразование IP-адреса в имя (reverse DNS).
- **CAA** — ограничение центров сертификации, которым разрешено выпускать сертификаты для домена.
- **SRV** — указатель на сервер определённой службы (например, LDAP, SIP).
- **DNSKEY** и **RRSIG** — ключи и подписи для DNSSEC.

Перечисленные типы записей подробно рассматриваются в следующем разделе, а уже здесь стоит отметить, что мониторинг целостности этих записей — одна из ключевых практик SOC L1, поскольку несанкционированное изменение любой из них может свидетельствовать о компрометации учётной записи регистратора или DNS-сервера.

## Внутреннее устройство: полный спектр типов ресурсных записей и механика рекурсивного разрешения

### Исчерпывающий обзор типов DNS-записей

Современная экосистема DNS насчитывает несколько десятков типов записей. Ниже приведены те, с которыми аналитик SOC или сетевой инженер сталкивается регулярно. Таблица структурирована по функциональному назначению и содержит поля: тип, описание, пример данных (значения иллюстративны) и важность для мониторинга.

| Тип записи | Назначение | Пример содержимого (значения иллюстративны) | Значимость для мониторинга |
|------------|------------|----------------------------------------------|----------------------------|
| **A** | Прямое отображение имени хоста на IPv4-адрес | `93.184.216.34` | Изменение A-записи может указывать на угон домена или ошибку конфигурации |
| **AAAA** | Отображение имени на IPv6-адрес | `2001:0db8:85a3:0000:0000:8a2e:0370:7334` | Аналогично A, важно для организаций, использующих IPv6 |
| **CNAME** | Каноническое имя: указывает, что запрашиваемое имя является псевдонимом другого имени | `real-server.example.com.` | Неожиданное изменение или цепочка CNAME могут вести на вредоносный ресурс |
| **MX** | Почтовый обменник: задаёт приоритет и имя почтового сервера для домена | `10 mail.example.com.` | Изменение MX без согласования может перехватить всю почту домена |
| **NS** | Делегирует зону на указанные серверы имён | `ns1.example.com.` | Замена NS-записей передаёт контроль над зоной злоумышленнику |
| **SOA** | Стартовая запись зоны: содержит почту администратора, серийный номер, таймауты | `ns1.example.com. admin.example.com. 2025042101 3600 900 1209600 86400` | Резкое уменьшение TTL или изменение серийного номера может быть признаком подготовки атаки |
| **TXT** | Произвольный текст; используется для SPF, DMARC, DKIM, верификации владения доменом | `"v=spf1 include:_spf.example.com ~all"` | Мониторинг TXT-записей помогает выявить подделку SPF/DMARC, ослабляющую защиту от спуфинга |
| **PTR** | Обратное разрешение IP-адреса в доменное имя (reverse DNS) | `host-93-184-216-34.example.com.` | Несоответствие прямого и обратного отображений часто используется в фишинговых кампаниях |
| **SRV** | Указатель на сервер определённой службы и протокола | `0 5 5060 sipserver.example.com.` | Компрометация SRV может перенаправить внутренние сервисы (SIP, LDAP) на хост атакующего |
| **CAA** | Определяет центры сертификации, которым разрешено выпускать SSL/TLS-сертификаты для домена | `0 issue "letsencrypt.org"` | Появление или удаление CAA записи — признак подготовки к выпуску мошеннического сертификата |
| **DNSKEY** | Публичный ключ, используемый для проверки подписей DNSSEC | `256 3 13 <key-data>` | Замена DNSKEY может сломать валидацию или позволить подписывать поддельные ответы |
| **RRSIG** | Цифровая подпись для набора записей (DNSSEC) | `A 13 3 86400 20250501000000 ...` | Отсутствие или невалидность RRSIG свидетельствует о попытке подмены данных зоны |
| **DS** | Делегирование подписания: хэш ключа дочерней зоны, хранится в родительской | `12345 13 1 <hash>` | Мониторинг DS на уровне родительской зоны — защита от атаки на цепочку доверия DNSSEC |
| **NSEC / NSEC3** | Указывает на существование или отсутствие имени в зоне (DNSSEC) | `next.example.com. A RRSIG NSEC` | Используется для доказательства несуществования имени; злоумышленники могут анализировать для обхода блокировок |

TTL (Time To Live) каждой записи определяет, как долго кэширующий сервер может хранить ответ. Для записей с высоким TTL (например, 86400 секунд) изменение распространяется медленно, что даёт атакующему окно для эксплуатации «застывших» данных. Поэтому мониторинг TTL также важен.

### Рекурсивное разрешение: пошаговый механизм

Рекурсивный запрос запускает следующую стандартную последовательность (иллюстративная схема):

```text
Клиент (stub resolver) ──(рекурсивный запрос)──▶ Рекурсивный сервер (кэширующий)
                                                      │
                                    (1) нет в кэше -> запрос к корневому серверу
                                                      ▼
                               Корневой сервер ──(NS для .com)──▶ Рекурсивный сервер
                                                      │
                                    (2) запрос к TLD-серверу .com
                                                      ▼
                         TLD-сервер .com ──(NS для example.com)──▶ Рекурсивный сервер
                                                      │
                                    (3) запрос к авторитативному серверу example.com
                                                      ▼
               Авторитативный сервер example.com ──(A-запись: 93.184.216.34)──▶ Рекурсивный сервер
                                                      │
                                                     (4) ответ клиенту + кэширование
```

Конкретные шаги:

1. Рекурсивный сервер получает запрос на разрешение `www.example.com`. Если запись отсутствует в кэше, сервер обращается к одному из 13 корневых серверов (например, `a.root-servers.net`), отправляя итеративный запрос.
2. Корневой сервер не знает полного ответа, но возвращает список TLD-серверов для зоны `.com` (NS-записи и их A/AAAA-адреса, называемые glue records).
3. Рекурсивный сервер выбирает один из TLD-серверов и посылает следующий итеративный запрос. TLD-сервер отвечает списком авторитативных серверов для домена `example.com` (NS-записи и glue-адреса).
4. Рекурсивный сервер обращается к одному из авторитативных серверов `example.com`, который и возвращает искомую A-запись. Сервер кэширует все промежуточные ответы (NS для `.com`, NS для `example.com`, саму A-запись) на время их TTL и возвращает финальный IP-адрес клиенту.

Если DNSSEC включён, на каждом шаге дополнительно проверяются подписи: рекурсивный сервер запрашивает RRSIG и DNSKEY, начиная от корня, и строит цепочку доверия до конечной записи. Это значительно повышает устойчивость к атакам типа cache poisoning, но требует корректной конфигурации всех звеньев.

Рекурсивный сервер, обслуживающий корпоративную сеть, является критической точкой мониторинга: его логи содержат полный перечень доменных имён, к которым обращались внутренние узлы. Любое аномальное поведение — частые запросы к случайным поддоменам, попытки разрешения несуществующих имён с высокой энтропией (характерно для DGA-вредоносов) или запросы к известным вредоносным доменам — немедленно привлекает внимание SOC L1.

## Применение в SOC: DNS-мониторинг как инструмент обнаружения угроз и контроля целостности

DNS-трафик предоставляет один из наиболее информативных источников данных для специалиста первой линии мониторинга. В отличие от многих других протоколов, DNS почти всегда проходит через небольшое количество централизованных серверов (корпоративные рекурсивные резолверы), что упрощает сбор и анализ. Рассмотрим основные направления использования DNS-мониторинга в SOC.

### Мониторинг доступности и производительности

Базовая задача — убедиться, что DNS-сервис отвечает вовремя и корректно. Метрики, которые отслеживают системы вроде PRTG, Site24x7 или UptimeRobot, включают:

- Время отклика на запросы рекурсивного и авторитативных серверов.
- Процент успешных ответов (отсутствие SERVFAIL, NXDOMAIN для существующих записей).
- Согласованность ответов между разными авторитативными серверами одной зоны.

Современные сенсоры, например, [DNS v2 sensor в PRTG](https://www.paessler.com/manuals/prtg/dns_v2_sensor), позволяют задавать список записей и опрашивать их на нескольких серверах, сравнивая полученные значения с эталоном. Именно подобные проверки образуют первый рубеж обнаружения несанкционированных модификаций DNS.

### Мониторинг целостности ресурсных записей

Изменение любой критичной RR — A, MX, NS, CNAME, TXT — может быть индикатором атаки. Отслеживание ведётся по трём осям:

- **Сравнение с эталоном**: система мониторинга хранит ожидаемые значения и генерирует алерт при расхождении.
- **Контроль синхронизации между NS**: проверка того, что все авторитативные серверы возвращают идентичный набор записей. Расхождение (например, ns1 отдаёт корректную A-запись, а ns3 — подставную) — классический признак компрометации одного из серверов или некорректной зонной передачи.
- **Анализ истории изменений**: платформы вроде [DNS Spy](https://dnsspy.io/features/dns-record-monitoring) ведут полный журнал: какая запись, когда и с какого значения на какое изменилась. Это критично для расследований и аудита.

Пример алерта о рассинхронизации A-записи на разных NS (иллюстративная схема, структура типична для систем типа DNS Spy):

```json
{
  "alert": "dns_record_out_of_sync",
  "domain": "vpn.example.com",
  "record_type": "A",
  "timestamp": "2025-04-21T14:32:00Z",
  "nameservers": {
    "ns1.example.com": "198.51.100.1",
    "ns2.example.com": "198.51.100.1",
    "ns3.example.com": "203.0.113.99"
  },
  "expected_value": "198.51.100.1",
  "status": "out_of_sync"
}
```

При получении такого алерта аналитик L1 должен немедленно инициировать проверку: является ли изменение авторизованным (плановые работы) или следствием атаки (DNS spoofing, компрометация панели управления хостингом).

### Обнаружение угроз через анализ логов DNS-запросов

Журналы рекурсивного сервера (BIND query log, логи Unbound, записи DNS-прокси) — кладезь сигналов о вредоносной активности. Типовые паттерны, выявляемые на уровне L1:

1. **DNS-туннелирование и эксфильтрация данных**: аномально длинные TXT-записи, большой объём TXT или NULL-запросов к одному домену, частые запросы к поддоменам, закодированным в base64.
2. **Command & Control (C2)**: периодические запросы к динамически генерируемым доменам (DGA) — множество NXDOMAIN ответов на имена с высокой энтропией, чередующиеся с успешными запросами к одному-двум доменам.
3. **DNS-спуфинг/отравление кэша**: внезапное изменение разрешаемого IP для хорошо известного домена, особенно если это зафиксировано после всплеска трафика к этому домену с аномального источника.
4. **Подозрительная смена DNS-серверов на конечных узлах**: если агенты EDR или DHCP-логи сообщают о смене настроек DNS на неподконтрольные адреса.

Современные SIEM (Splunk, Elastic, Microsoft Sentinel) имеют встроенные правила корреляции для DNS-аномалий. Например, правило может подсчитывать количество уникальных поддоменов, запрошенных одним хостом за короткий промежуток, и при превышении порога генерировать алерт «Potential DGA activity».

### Инструментарий и практические команды для SOC L1

Для оперативной проверки гипотез аналитик должен владеть утилитами командной строки. Ниже приведены базовые команды, применяемые при расследовании инцидентов, связанных с DNS.

**1. Проверка A-записи на конкретном авторитативном сервере (dig):**

```bash
dig @ns1.example.com vpn.example.com A +short
```
Ожидаемый вывод (эталонное значение или подозрительный IP):
```
198.51.100.1
```
Сравнение вывода с данными из алерта — первый шаг верификации.

**2. Полный трассировочный вывод для анализа цепочки делегирования (+trace):**

```bash
dig +trace vpn.example.com A
```
Позволяет увидеть, на каком именно этапе появляется подставной адрес, и помогает отличить проблему кэша от подмены на авторитативном сервере.

**3. Запрос TXT-записи для выявления туннелирования (например, длинная base64-строка):**

```bash
dig @resolver txt suspicious.example.com +short
```
Аномальный вывод: очень длинная текстовая строка или подозрительный паттерн. SOC L1 может передать образец на углублённый анализ.

**4. Автоматизированный скрипт сравнения ответов нескольких NS (иллюстративная схема):**

```bash
#!/bin/bash
DOMAIN="vpn.example.com"
NS1="ns1.example.com"
NS2="ns2.example.com"

IP1=$(dig +short @$NS1 $DOMAIN A)
IP2=$(dig +short @$NS2 $DOMAIN A)

if [ "$IP1" != "$IP2" ]; then
  echo "ALERT: Discrepancy for $DOMAIN: $NS1 -> $IP1, $NS2 -> $IP2"
fi
```
В реальной среде подобные проверки запускаются по расписанию с отправкой результатов в систему мониторинга.

### Типичные ошибки и подводные камни

- Полагаться на единственный рекурсивный сервер при проверке записей: ответ может быть взят из кэша, что скроет недавнюю подмену.
- Игнорировать TTL: после изменения записи с большим TTL кэш по всему миру может сохранять старое значение ещё сутки; атакующий использует это окно.
- Не учитывать DNSSEC: если зона подписана, но проверка подписи не выполняется (валидация отключена на резолвере), поддельные ответы не будут отброшены, и мониторинг ответов без валидации бессмысленен.
- Мониторинг только A-записей: изменения MX, NS или TXT могут быть более опасными и не менее частыми.

## Сквозной практический пример: расследование инцидента компрометации A-записи VPN-шлюза

### Исходные условия

Организация использует два авторитативных DNS-сервера (`ns1.example.com` и `ns2.example.com`) для домена `example.com`. Внешний VPN-сервис доступен по имени `vpn.example.com`. SOC L1 аналитик получает алерт от системы мониторинга DNS (типа DNS Spy или PRTG) о рассинхронизации A-записи между серверами имён. Время инцидента: 14:32 UTC, 21 апреля 2025 года. Инструменты аналитика: `dig`, `whois`, доступ к логам рекурсивного сервера, интерфейс системы мониторинга.

### Шаги расследования

**Шаг 1. Анализ входящего алерта.**  
Алерт содержит структурированную информацию об изменении записи (формат JSON — иллюстративная схема, подобная используемой в системах мониторинга). Аналитик сразу видит, что `ns2` возвращает IP `203.0.113.99`, тогда как `ns1` и эталонное значение — `198.51.100.1`.

```json
{
  "alert": "dns_record_out_of_sync",
  "domain": "vpn.example.com",
  "record_type": "A",
  "timestamp": "2025-04-21T14:32:00Z",
  "nameservers": {
    "ns1.example.com": "198.51.100.1",
    "ns2.example.com": "203.0.113.99"
  },
  "expected_value": "198.51.100.1",
  "status": "out_of_sync"
}
```

**Шаг 2. Проверка актуальных ответов напрямую с каждого сервера имён.**  
Аналитик выполняет команды, чтобы убедиться, что ситуация сохраняется и не вызвана ложным срабатыванием (например, временным сбоем сети). Используется `dig` с прямым указанием сервера.

```bash
dig @ns1.example.com vpn.example.com A +short
```
Вывод:
```
198.51.100.1
```
```bash
dig @ns2.example.com vpn.example.com A +short
```
Вывод:
```
203.0.113.99
```
Подтверждено: `ns2` отдаёт чужеродный IP-адрес. Одновременно можно проверить, когда истекает TTL текущей записи:

```bash
dig @ns1.example.com vpn.example.com A
```
В выводе, среди прочего, будет строка `vpn.example.com. 3600 IN A 198.51.100.1`, где 3600 — TTL. Это значит, что кэши по всему миру могут хранить корректный IP ещё час, а часть пользователей уже получают вредоносный адрес от `ns2`.

**Шаг 3. Анализ истории изменений и аудит зоны.**  
Через систему мониторинга аналитик запрашивает историю для `vpn.example.com`. Интерфейс или API возвращает лог изменений (иллюстративная структура):

```text
Date                Nameserver   Change
2025-04-21 14:32    ns2          + 203.0.113.99
2025-04-21 14:32    ns2          - 198.51.100.1
2025-03-15 09:11    ns1,ns2      -> 198.51.100.1
```
Запись добавлена на `ns2` ровно в момент алерта, предыдущая удалена. На `ns1` изменений не зафиксировано. Это подтверждает несанкционированное вмешательство именно на `ns2`. Дополнительно аналитик вручную проверяет NS-записи зоны, чтобы исключить изменение делегирования:

```bash
dig @a.gtld-servers.net example.com NS +short
```
Вывод соответствует ожидаемым `ns1.example.com.` и `ns2.example.com.` — делегирование не тронуто.

**Шаг 4. Поиск корреляции в логах рекурсивного DNS-сервера.**  
Теперь необходимо понять, было ли вредоносное разрешение использовано на практике. Аналитик извлекает из логов запросы к `vpn.example.com` за последние несколько часов (команда фильтрации логов Unbound или BIND — иллюстративная).

```bash
grep "vpn.example.com" /var/log/dns-queries.log | grep -E "A\s+" | awk '{print $1,$2,$5}' | sort | uniq -c
```
Пример вывода:
```
 15 10:15:10 198.51.100.1
  3 14:35:22 203.0.113.99
  8 14:35:40 203.0.113.99
```
Где первая колонка — количество запросов, вторая — время, третья — IP, который вернул резолвер. Видно, что после 14:32 начали появляться ответы с вредоносным IP. Это означает, что рекурсивный сервер уже получил и закэшировал подставную запись от `ns2` (если резолвер по какой-то причине выбрал его) или что часть клиентов напрямую использовали `ns2` в качестве DNS-сервера. Высокая частота запросов после инцидента может свидетельствовать о том, что вредоносный сайт уже принимает соединения.

**Шаг 5. Идентификация источника и выводы.**  
Обнаружив, что вредоносный IP `203.0.113.99` не принадлежит организации и не связан с легитимной инфраструктурой, аналитик эскалирует инцидент. В качестве немедленной меры предлагается:
- Временно исключить `ns2` из списка NS-записей (если возможно) или настроить вышестоящий рекурсивный сервер игнорировать его ответы.
- Очистить кэш корпоративных резолверов (`rndc flush` или перезапуск).
- Инициировать сброс учётных данных панели управления DNS-хостингом.
- Провести анализ хоста `ns2` на предмет компрометации.

---

Данный пример демонстрирует, как мониторинг DNS-записей и базовые навыки работы с утилитами позволяют аналитику L1 в течение нескольких минут выявить, подтвердить и локализовать инцидент, связанный с подменой A-записи. Те же подходы применимы к любым другим типам записей и к другим векторам атак, включая перехват почты (MX), перенаправление служб (SRV) или ослабление SPF/DMARC (TXT).
