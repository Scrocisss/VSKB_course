# Baseline в мониторинге безопасности: построение профилей нормального поведения для обнаружения инцидентов

## 1. Концепция базового уровня (Baseline) в информационной безопасности

**Baseline** (базовый уровень, профиль нормального поведения) — это статистическая или логическая модель типичной активности контролируемой сущности за определённый период. В SOC (Security Operations Center) baseline служит эталоном, с которым сравниваются текущие наблюдаемые события для выявления отклонений — аномалий, потенциально указывающих на инцидент. Ключевая идея: атака, вредоносная активность или ошибка конфигурации часто изменяют характер трафика, загрузки системы или поведение пользователя относительно привычного фона.

В отличие от сигнатурных методов, где детектирование опирается на заранее известные паттерны (например, хеш вредоносного файла или конкретная сигнатура snort), baseline-подход не требует знания точного облика угрозы. Он фиксирует «норму» и реагирует на любое существенное отклонение. Вместе с тем baseline не заменяет сигнатурный анализ, а дополняет его: многие SOC выстраивают гибридную аналитику, где часть правил основана на сигнатурах, а часть — на отклонениях от baseline.

Важно различать **поведенческий baseline** и **конфигурационный baseline** (compliance baseline). Первый используется для мониторинга и детектирования, второй — для оценки соответствия требованиям (например, CIS Benchmarks, DISA STIG). В SOC L1 под baseline обычно понимают именно поведенческий профиль: типовую сетевую активность, загрузку CPU, количество событий входа в систему и т.п. Далее речь идёт именно об этом значении.

**Место baseline в жизненном цикле анализа инцидентов на уровне L1**  

Аналитики первой линии в SOC обрабатывают срабатывания автоматизированных детектирующих систем. Значительная доля этих срабатываний генерируется правилами, сравнивающими текущую телеметрию с построенным baseline. Типовой сценарий:

1. SIEM-платформа (или UEBA-модуль) накапливает исторические данные и периодически пересчитывает профили нормального поведения для различных объектов: хостов, пользователей, сетевых сегментов, приложений.
2. Для каждого объекта вычисляются базовые значения контролируемых метрик (среднее, медиана, межквартильный размах) с учётом временного профиля — рабочие часы, выходные, ночные интервалы.
3. При поступлении нового события его параметры сравниваются с актуальным baseline. Если отклонение превышает настроенный порог, генерируется алерт категории «anomaly» или «deviation from baseline».
4. Аналитик L1, получив такой алерт, должен быстро оценить его контекст: действительно ли отклонение нетипично для данной среды или это легитимное изменение (запланированная миграция, новая версия ПО). Для этого он может обратиться к исходным данным baseline, запросить детализацию или сопоставить с другими событиями.

Таким образом, baseline — не просто статистическая абстракция, а инструмент ежедневной операционной работы, который определяет значительную часть очереди инцидентов.

Ниже представлено сравнение поведенческого baseline c другими подходами к детектированию.

| Подход                     | Суть                                                                 | Преимущества                                                                 | Ограничения                                                                 |
|----------------------------|----------------------------------------------------------------------|------------------------------------------------------------------------------|-----------------------------------------------------------------------------|
| Сигнатурное детектирование | Сопоставление событий с фиксированными шаблонами угроз                | Высокая точность на известных атаках, низкий уровень ложных срабатываний     | Бесполезно против новых угроз; требует постоянного обновления сигнатур     |
| Поведенческий baseline     | Контроль отклонений от статистической нормы                          | Обнаруживает неизвестные аномалии, адаптируется к среде                      | Требует периода обучения и стабильной среды; чувствителен к легитимным изменениям |
| Конфигурационный baseline  | Проверка настроек системы на соответствие жёсткому эталону           | Гарантирует заданный уровень защищённости, подходит для аудита               | Не выявляет динамические аномалии; требует ручной актуализации эталона     |
| Rule-based корреляция      | Логические цепочки: «если событие А и В, то инцидент»                | Гибкость в описании сложных сценариев                                        | Зависит от экспертных знаний; пропускает не описанные в правилах атаки      |
| Машинное обучение (UEBA)   | Модели классификации/кластеризации для поиска нетипичных паттернов   | Может улавливать тонкие отклонения без явных порогов                         | Требует качественную разметку, объяснимость результатов ограничена         |

**Ключевые термины**

- **Метрика** — количественная характеристика, по которой строится baseline (число DNS-запросов в минуту, объём исходящего трафика, частота аутентификаций и т.д.).
- **Период обучения** — исторический интервал, данные за который используются для расчёта начального профиля. Обычно не менее 7 суток, чтобы охватить недельный цикл активности.
- **Отклонение (аномалия)** — значение метрики, выходящее за допустимые границы (например, превышение 99-го перцентиля).
- **Порог срабатывания** — параметр, определяющий чувствительность детектора отклонений. Задаётся в терминах стандартных отклонений, абсолютных/относительных величин или вероятностных оценок.

## 2. Типы базовых профилей и их внутреннее устройство

В SOC применяют несколько видов behavioural baseline, различающихся источником данных, характером контролируемых метрик и способом вычисления. Комбинация нескольких baseline на разных уровнях позволяет создать многослойную систему детектирования аномалий.

### 2.1. Сетевой baseline (Network Baseline)

Характеризует типовую активность сетевого устройства, сегмента или сетевого приложения. Строится на основе NetFlow/IPFIX, данных пакетных фильтров, SNMP-опросов, метаданных прокси-серверов.

**Типичные метрики:**
- Суммарный объём трафика (входящий/исходящий, бит/с, пакетов/с).
- Количество уникальных IP-адресов назначения/источников за интервал.
- Распределение трафика по портам и протоколам (TCP/UDP, порты назначения).
- Число DNS-запросов по типам (A, AAAA, TXT, MX) и средняя длина ответа.
- Объём трафика в нерабочие часы.

**Методы построения:**
- Статистические: вычисление среднего и стандартного отклонения (μ, σ) для временных слотов; аномалия — значение, удалённое более чем на kσ от среднего.
- Процентильные: определение 95-го или 99-го перцентиля; выход за них считается аномалией.
- Сезонные модели (например, на базе алгоритма ETS или SARIMA) для учёта дневных и недельных паттернов.

### 2.2. Хостовый baseline (Host Baseline)

Описывает нормальное поведение сервера или рабочей станции на основе системных метрик: загрузка CPU, памяти, дисковая активность, сетевые соединения, запущенные процессы, события ОС.

**Метрики:**
- Средняя загрузка CPU (load average) и потребление памяти по временным окнам.
- Количество и типы запущенных процессов (родитель-потомок, подпись, хеш).
- Объём операций ввода-вывода на дисковых устройствах.
- Частота событий входа/выхода, ошибок аутентификации, повышения привилегий.
- Список сетевых подключений: число уникальных удалённых адресов, количество установленных соединений по портам.

**Сбор данных:** локальные агенты (например, osquery, Wazuh, Elastic Agent), EDR-сенсоры (CrowdStrike, Microsoft Defender for Endpoint), журналы системы (EventLog, syslog, auditd).

**Особенность:** для статичных серверов baseline достаточно стабилен; для пользовательских рабочих станций нужен более сложный профиль, учитывающий активность конкретного сотрудника.

### 2.3. Профиль пользователя (User Behavior Baseline / UEBA)

Отражает типичные действия учётной записи. В отличие от хостового профиля, акцент на активности, связанной с идентификацией и доступом, вне зависимости от конкретной машины.

**Метрики:**
- Временная сетка входов: среднее время начала и окончания сессий, типичные дни недели.
- Геолокация аутентификации (при использовании облачных сервисов).
- Частота обращений к файловым ресурсам, почтовым ящикам, корпоративным приложениям.
- Объём переданных/загруженных данных через корпоративные облачные хранилища.
- Паттерны использования привилегированных команд (sudo, выполнение скриптов администрирования).

Эти метрики собираются из логов AD/LDAP, VPN, прокси, IDM-систем. Профиль пользователя часто реализуется в UEBA-решениях (Microsoft Sentinel UEBA, Exabeam, Securonix).

### 2.4. Прикладной baseline (Application Baseline)

Фокусируется на поведении конкретного сервиса или приложения: веб-сервер, база данных, ERP-система. Анализируются логи приложения и показатели его производительности.

**Пример для веб-сервера:**
- Количество HTTP-запросов по методам (GET, POST) и URL-путям.
- Распределение кодов ответа (200, 404, 5xx).
- Доля трафика от ботов и краулеров.
- Среднее время отклика на страницу.

Для СУБД — число запросов в секунду, соотношение SELECT/INSERT/UPDATE, объём данных, передаваемых клиенту.

**Методы построения:** как правило, на основе временных рядов с учётом пиковых бизнес-часов.

Ниже представлена сравнительная таблица четырёх основных типов baseline, используемых аналитиками SOC.

| Тип baseline       | Источники данных                                 | Типичные метрики                                                                 | Период обучения (рекомендация) | Характерный порог отклонения          |
|--------------------|--------------------------------------------------|----------------------------------------------------------------------------------|--------------------------------|---------------------------------------|
| Сетевой            | NetFlow, sFlow, DNS-логи, прокси                 | Объём трафика, топ-IP и порты, число DNS-запросов                                | 7–14 дней (недельный цикл)     | 3σ от среднего или 99-й процентиль    |
| Хостовый           | Sysmon, журналы ОС, EDR                          | Загрузка CPU, список процессов, события аутентификации                           | 7–30 дней                      | Выход за Q3 + 1.5 * IQR               |
| Пользовательский   | AD, VPN, облачные логи доступа                   | Время и география входов, доступ к ресурсам, повышение прав                      | 14–30 дней                     | Низкая вероятность по исторической модели |
| Прикладной         | Access-лог веб-сервера, БД, логи приложений      | Кол-во запросов, коды ответа, время отклика                                      | 7 дней                         | Процентное отклонение от скользящего среднего |

## 3. Применение и работа с baseline в SOC L1

Аналитик первой линии взаимодействует с baseline не на этапе его построения, а на этапе реагирования на срабатывания. Тем не менее понимание принципов вычисления профилей и владение базовыми инструментами проверки существенно ускоряют триаж.

### 3.1. Типовые операции аналитика с baseline-driven алертами

1. **Получение алерта** — в SIEM формируется событие с полями: `entity` (хост/пользователь/приложение), `metric`, `actual_value`, `baseline_value`, `deviation_percent`, `severity`.
2. **Первичная валидация:** проверить, не вызвано ли отклонение плановыми работами (тикеты изменений) или известными событиями (релиз ПО, миграция). Для этого используются поля обогащения алерта или проверка в ITSM-системе.
3. **Расширенный контекст:** построить запрос в SIEM для извлечения детализации по отклонению: какие именно IP-адреса, процессы, команды стали причиной всплеска.
4. **Сравнение с историей:** быстро оценить, наблюдались ли похожие отклонения ранее в этой же среде (например, за последний месяц) — это помогает отличить новую угрозу от повторяющегося ложноположительного срабатывания.
5. **Эскалация:** если аномалия не объяснена легитимной причиной, алерт направляется на L2/L3 для углублённого расследования и реагирования.

### 3.2. Инструментарий аналитика

В работе активно используются возможности SIEM-платформы, а также запросные языки для прямого исследования данных.

**Характерные запросы (иллюстративная схема на SPL для Splunk):**

Поиск самых отклоняющихся хостов по объёму исходящего трафика за последний час:
```spl
index=netflow earliest=-1h
| bin _time span=5m
| stats sum(bytes_out) as total_bytes by host, _time
| eventstats avg(total_bytes) as avg_bytes, stdev(total_bytes) as stdev_bytes by host
| eval deviation = (total_bytes - avg_bytes) / stdev_bytes
| where deviation > 3
| table _time, host, total_bytes, avg_bytes, deviation
```
Этот запрос вычисляет среднее и стандартное отклонение для каждого хоста на основе данных текущего часа и выводит моменты, когда отклонение превышало 3 сигмы. Аналитик может быстро идентифицировать проблемный узел.

Поиск аномального количества уникальных доменов, к которым обращался конкретный хост:
```spl
index=dns sourcetype=dns host="web-server-01" earliest=-24h
| bin _time span=1h
| stats dc(query) as unique_queries by _time
| eventstats avg(unique_queries) as avg_q, stdev(unique_queries) as stdev_q
| eval anomaly_score = (unique_queries - avg_q) / stdev_q
| where anomaly_score > 2
```
Здесь аномалия обнаруживается, если количество уникальных DNS-запросов в час более чем на 2σ выше среднего за сутки.

В продуктах, не поддерживающих продвинутую статистику на лету, baseline рассчитывается заранее (например, средствами машинного обучения в UEBA) и хранится в виде сводной таблицы. Тогда запрос аналитика выглядит как сравнение текущих агрегатов с готовыми профилями:
```sql
-- Псевдо-SQL для платформы с предрассчитанными baseline-таблицами
SELECT a.host, a.time_window, a.request_count, b.avg_count, b.p99_count,
       (a.request_count - b.avg_count) / b.stdev_count AS deviation
FROM current_stats a
JOIN baseline_profiles b ON a.host = b.host
WHERE a.time_window = b.applicable_window
AND (a.request_count > b.p99_count OR ABS(deviation) > 2.5);
```
Такие запросы часто автоматизированы в правилах корреляции, но аналитик должен уметь их писать для ad-hoc расследований.

### 3.3. Типичные ошибки и подводные камни

- **Некорректный период обучения:** если baseline построен на данных, содержащих скрытую атаку или аномальную активность, то такая «норма» будет принимать вредоносное поведение за допустимое. Необходимо очищать обучающую выборку от известных инцидентов.
- **Статические пороги для сезонных данных:** использование единого среднесуточного значения для метрик, которые имеют выраженный дневной и недельный цикл, приводит к лавине ложных срабатываний в часы пик или, наоборот, к пропуску атак в ночное время.
- **Игнорирование плановых изменений:** не подключив обогащение данными из системы управления изменениями (Change Management), аналитик будет тратить время на легитимные отклонения.
- **Слишком длинные окна агрегации:** расчёт baseline с окном в 1 час может размыть короткие, но интенсивные аномалии (DDoS-атака длительностью 5 минут). Желательно использовать многоуровневые окна.
- **Зависимость от одного baseline:** отсутствие корреляции между baseline разных уровней (сеть + хост + пользователь) снижает общую надёжность детектирования.

## 4. Сквозной практический пример: обнаружение аномального исходящего DNS-трафика с помощью baseline

Данный кейс демонстрирует, как аналитик SOC L1 может выявить подозрительную активность, сравнивая текущий DNS-трафик с профилем нормального поведения, и провести первичное расследование.

**Исходные условия:**
- Организация использует внутренний DNS-сервер на ОС Linux (BIND), журналы запросов централизованно собираются в SIEM.
- Построен baseline числа запросов для каждого клиентского IP в разрезе часов и типов записей (A, TXT, MX).
- Baseline рассчитан за предшествующие 14 дней (период обучения) и ежедневно пересчитывается посуточно.
- Аналитик использует консоль SIEM и терминал управления DNS-сервера.

### Шаг 1. Построение baseline из исторических логов (вне операционной работы, но понимание процесса необходимо)

Аналитик может проверить корректность профиля, воспроизведя расчёт на Python.

```python
import pandas as pd
logs = pd.read_csv('dns_logs_14days.csv', parse_dates=['timestamp'])
logs['hour'] = logs['timestamp'].dt.floor('H')
logs['record_type'] = logs['query'].apply(lambda q: q.split()[-1])  # извлечение типа записи

# Группировка по клиенту, часу и типу записи, подсчёт числа запросов
hourly = logs.groupby(['client_ip', 'hour', 'record_type']).size().reset_index(name='count')
baseline = hourly.groupby(['client_ip', 'record_type']).agg(avg_count=('count', 'mean'),
                                                             std_count=('count', 'std'),
                                                             p99=('count', lambda x: x.quantile(0.99)))
print(baseline.head())
```
Вывод (сокращённый):
```
client_ip      record_type  avg_count    std_count  p99
192.168.1.10   A            120.3        15.4       210
192.168.1.10   MX           0.2          0.5        2
...
```
Этот профиль загружается в SIEM.

### Шаг 2. Сравнение текущего временного окна с baseline и обнаружение аномалии

В SIEM настроено правило, сравнивающее агрегаты за последний час с хранимым профилем. Аналитик получает алерт о превышении порога для хоста `192.168.1.10` (рабочая станция бухгалтера) по запросам типа `TXT`.

Алерт в формате JSON (иллюстративная схема):
```json
{
  "alert_id": "dns-anom-20250315-001",
  "entity": "192.168.1.10",
  "metric": "dns_queries TXT",
  "window": "2025-03-15T08:00:00/09:00:00",
  "current_count": 175,
  "baseline_avg": 1.2,
  "baseline_p99": 5,
  "deviation": "+14580%",
  "severity": "HIGH"
}
```
Станция внезапно сгенерировала 175 TXT-запросов за час при историческом максимуме в 5. Это серьёзное отклонение.

### Шаг 3. Детализация и сбор артефактов

Аналитик выполняет запрос в SIEM для извлечения конкретных запросов за этот час:

```spl
index=dns sourcetype=bind client_ip="192.168.1.10" earliest="2025-03-15T08:00:00" latest="2025-03-15T09:00:00" query_type="TXT"
| stats count by query
| sort - count
| head 10
```

Результаты показывают множество запросов к домену вида `dga-suffix.xyz` и его поддоменам. Аналитик подозревает DGA-активность или туннелирование данных через DNS. Для проверки он также выгружает сетевые соединения с хоста:

```bash
# На центральном сборщике netflow
sudo nfdump -R /var/netflow/nfcapd.202503150850 -c 100 'host 192.168.1.10 and port 53'
```
В выводе видны многочисленные UDP-дейтаграммы на порт 53 к внешнему резолверу 8.8.8.8 с необычно высокой частотой, подтверждая обход корпоративного DNS.

### Шаг 4. Контекстный анализ и эскалация

Аналитик проверяет процессы на хосте через EDR-консоль (команда удалённого опроса):
```powershell
Get-Process -ComputerName 192.168.1.10 | Where-Object { $_.NetworkUsage -gt 100KB } | Format-Table Name, Id, Path
```
Обнаружен подозрительный процесс `updater.exe` в пользовательской папке. Его хеш не совпадает с корпоративным whitelist.

На основании совокупности артефактов алерт эскалируется на уровень L2 для изоляции хоста и проведения обратного анализа. Baseline-ориентированное детектирование позволило выявить угрозу, не имевшую открытых сигнатур.

**Вывод примера:** baseline превращает аномальное поведение в измеримый инцидент, а предоставленные инструменты дают аналитику L1 возможность быстро подтвердить или опровергнуть подозрение, минимизируя время реакции.
