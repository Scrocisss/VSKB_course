# Приоритизация инцидентов в SOC: Severity и Priority

## Severity и Priority: две стороны приоритизации инцидентов

Ключевая задача специалиста SOC L1 при поступлении оповещения — максимально быстро определить, насколько серьёзен инцидент и в каком порядке его следует обрабатывать. Для этого используются две тесно связанные, но фундаментально различные метрики: **Severity** (серьёзность) и **Priority** (приоритет). Их смешение — одна из наиболее частых причин несогласованности действий дежурных смен и затягивания реагирования. Чёткое разделение понятий закладывает основу любого процесса управления инцидентами.

**Severity** — это мера воздействия инцидента на бизнес, пользователей, системы или данные. Она отвечает на вопрос «Насколько плоха ситуация технически и организационно?» и, как правило, определяется объективными критериями: количество затронутых пользователей, критичность отказавшей системы, потеря данных, нарушение регуляторных требований. Severity не зависит от того, происходит ли инцидент в пик нагрузки или ночью в выходной, и не учитывает доступность инженеров. Эта характеристика описывает *импакт* [Splunk](https://www.splunk.com/en_us/blog/learn/incident-severity-levels.html).

**Priority** — это мера срочности, устанавливающая порядок обработки инцидентов относительно друг друга. Приоритет отвечает на вопрос «Что следует исправлять прямо сейчас?» и комбинирует severity с фактором *Urgency* (срочность). Urgency отражает, насколько быстро проблема должна быть устранена с учётом бизнес-контекста: близость критичных дедлайнов, время пиковой нагрузки, число одновременных инцидентов. Поэтому приоритет может не совпадать с severity [Atlassian](https://www.atlassian.com/incident-management/kpis/severity-levels).

Классический подход ITIL формализует эту связь формулой:

**Priority = Impact + Urgency**

Где Impact — по сути Severity, а Urgency — самостоятельный параметр, оцениваемый по шкале High/Medium/Low. Результирующий Priority получается из матрицы совмещения, обеспечивая тонкую настройку очерёдности реагирования [censhare](https://knowledgebase.censhare.com/tk/incident-management-prioritization-itil-severity-l). Такой подход даёт SOC гибкость: два инцидента с одинаковой severity могут получить разный приоритет, если один из них угрожает финансовому закрытию месяца, а второй возник в период минимальной активности.

Чтобы разграничить понятия наглядно, рассмотрим их ключевые отличия:

| Параметр | Severity (серьёзность) | Priority (приоритет) |
|----------|-------------------------|----------------------|
| Что измеряет | Масштаб и глубина ущерба (Impact) | Срочность устранения (Urgency + Impact) |
| Вопросы | Сколько пользователей затронуто? Какие системы отказали? Есть ли утечка данных? | Как быстро это нужно исправить? Что из списка инцидентов делать первым? |
| Зависимость от контекста | Относительно стабильна, не зависит от загрузки команды | Может меняться при изменении внешних обстоятельств |
| Пример несовпадения | Критический сбой приложения, затрагивающий 0.05% пользователей, — High Severity | Это же приложение может иметь Low Priority, если есть более массовые аварии |
| Пример типичного совпадения | Полный отказ платёжной системы для всех клиентов — Critical Severity и Highest Priority | |

Источники: [Atlassian](https://www.atlassian.com/incident-management/kpis/severity-levels), [Splunk](https://www.splunk.com/en_us/blog/learn/incident-severity-levels.html), [incident.io](https://incident.io/blog/differences-between-severity-and-priority).

Важно не путать **Severity** с **приоритетом багов в тестировании**, где термины иногда меняются местами. В управлении инцидентами SOC действуют приведённые выше определения. Дополнительно некоторые модели выделяют «Major Incident» — это не отдельный уровень severity, а управленческий флаг, означающий, что инцидент (обычно SEV1 или SEV2) требует формальных процедур координации, создания выделенного канала связи и участия Incident Commander [PagerDuty](https://www.pagerduty.com/resources/incident-management-response/learn/incident-severity-classification).

Таким образом, разделение severity и priority в SOC является фундаментальной предпосылкой для построения эффективной очереди обработки и предотвращения ситуаций, когда действительно катастрофический инцидент остаётся незамеченным из-за шума менее значимых, но срочных задач.

## Модели severity и матрицы приоритизации: внутренняя структура

Поскольку тема охватывает целый класс моделей (системы уровней критичности, матрицы приоритетов), исчерпывающее покрытие ключевых элементов здесь является обязательным. Ниже представлены базовые элементы, знание которых ожидается от любого специалиста по реагированию на инциденты.

### Классические шкалы уровней серьёзности (SEV)

Наиболее распространённый подход — деление инцидентов на пять уровней, где SEV‑1 — самый критический, SEV‑5 — косметический. Такая шкала зафиксирована в документации большинства систем мониторинга и ITSM-решений [PagerDuty](https://www.pagerduty.com/resources/incident-management-response/learn/incident-severity-classification), [Splunk](https://www.splunk.com/en_us/blog/learn/incident-severity-levels.html), [UptimeRobot](https://uptimerobot.com/knowledge-hub/monitoring/severity-levels-explained), [Instatus](https://instatus.com/blog/incident-severity-matrix). Некоторые организации вводят дополнительный уровень SEV‑0 для экстремальных катастроф вроде полной потери ЦОДа, но технически это расширение стандартной SEV‑1 [Xurrent](https://www.xurrent.com/blog/incident-severity-levels).

Ниже приведена сводная таблица, обобщающая общепринятые параметры уровней серьёзности с типичными примерами. Точные пороговые значения (например, процент затронутых пользователей) всегда определяются внутренней политикой организации.

| Уровень | Название | Описание воздействия | Типичные примеры (без привязки к конкретной среде) | Стандартная реакция |
|---------|----------|----------------------|--------------------------------------------------|---------------------|
| **SEV‑1** | Critical | Полная остановка критичного бизнес-сервиса, массовая потеря данных, масштабная утечка конфиденциальной информации, нарушение нормативных требований | Полный отказ системы интернет-банкинга, невозможность приёма платежей, выход из строя основной базы данных с потерей данных, действующий шифровальщик на ключевых серверах | Немедленная мобилизация команды реагирования, создание военного штаба (war room), уведомление руководства, публичная коммуникация |
| **SEV‑2** | High | Серьёзное нарушение функциональности, затрагивающее многих пользователей, но не приводящее к полному отказу; возможен обходной путь | Деградация производительности основного приложения для 30% пользователей, отказ важного, но не единственного компонента (например, модуля отчётности) | Формальный процесс Major Incident, немедленная эскалация, выделенный канал связи |
| **SEV‑3** | Medium | Частичное ухудшение работы, недоступность отдельных функций; пользователи в основном могут продолжать работу | Сбой в одной из подсистем (например, выгрузка отчётов задерживается), периодические ошибки при оформлении заказов, временное увеличение времени отклика | Стандартная эскалация на профильную группу, срок реагирования в пределах часов, тикет с пометкой «высокая важность» |
| **SEV‑4** | Low | Некритичный сбой, не влияющий на основной бизнес-процесс; проблема имеет обходной путь и не вызывает срочного неудобства | Ошибка в административной панели, косметический дефект интерфейса, единичный сбой некритичного сервиса | Создаётся задача в бэклоге, выполняется в порядке очереди |
| **SEV‑5** | Cosmetic | Не имеет функционального влияния, чисто оформительский недочёт, опечатка в тексте | Орфографическая ошибка в названии кнопки, неверный отступ в мобильной версии страницы | Регистрируется тикет с низким приоритетом, исправляется при плановых работах |

Источники: [PagerDuty](https://www.pagerduty.com/resources/incident-management-response/learn/incident-severity-classification), [Splunk](https://www.splunk.com/en_us/blog/learn/incident-severity-levels.html), [Instatus](https://instatus.com/blog/incident-severity-matrix).

Важно понимать, что «Major Incident» в большинстве фреймворков не является отдельным уровнем, а обозначает управленческий статус, присваиваемый SEV‑1 и часто SEV‑2 инцидентам. Такой статус запускает специальные протоколы координации: назначение Incident Commander, создание выделенного коммуникационного канала, регулярные отчёты перед руководством и документирование всех действий [PagerDuty](https://www.pagerduty.com/resources/incident-management-response/learn/incident-severity-classification).

### Матрицы приоритетов (Priority Matrix)

Если шкала severity фокусируется на техническом воздействии, то priority требует учёта срочности (urgency). В ITIL-ориентированных процессах SOC используют таблицу совмещения Impact × Urgency, формирующую итоговый Priority. Такая матрица может быть закреплена в ITSM-системе и автоматически рассчитываться при заполнении полей инцидента.

Ниже приведён иллюстративный пример матрицы приоритетов (на основе модели `censhare`), где Impact соответствует severity, а Urgency оценивается аналитиком:

```text
                  | Urgency: High   | Urgency: Medium | Urgency: Low  
------------------|-----------------|-----------------|---------------
 Impact: Critical | P1 (Critical)   | P2 (High)       | P3 (Medium)   
 Impact: High     | P2 (High)       | P3 (Medium)     | P4 (Low)      
 Impact: Medium   | P3 (Medium)     | P4 (Low)        | P5 (Very Low) 
 Impact: Low      | P4 (Low)        | P5 (Very Low)   | P5 (Very Low) 
```

Пояснение: инцидент с критичным воздействием (например, отказ ядра платёжной системы) и высокой срочностью (авария произошла в день массовых выплат) получает Priority 1 — немедленный ответ. Тот же отказ, но в период гарантированного простоя, когда ни один пользователь не работает (Low Urgency), может быть классифицирован как P3 и запланирован к устранению в рабочее время [censhare](https://knowledgebase.censhare.com/tk/incident-management-prioritization-itil-severity-l).

Альтернативные шкалы приоритетов, независимые от severity, встречаются в инструментах наподобие xMatters, где P1 означает критичный инцидент с широким воздействием, а P4 — низкое влияние без потери дохода [xMatters](https://www.xmatters.com/blog/a-guide-to-incident-severity-levels). Такой подход, по сути, подменяет severity, что допустимо в небольших командах, но в SOC зрелых организаций обычно придерживаются строгого разделения.

### Компоненты экосистемы управления приоритетами

Для полноты картины внутреннее устройство любой системы приоритизации в SOC включает следующие элементы помимо самих шкал:

- **Критерии классификации** — чётко описанные пороговые значения: «больше 1000 затронутых пользователей», «невозможность выполнения критичной бизнес-операции», «активная сессия вредоносного ПО на контроллере домена» и т.п.
- **Правила эскалации** — для каждого уровня severity/priority задаётся время реакции (time to acknowledge) и цепочка уведомлений (L1 → L2 → L3 → руководство).
- **Процедуры пересмотра уровня** — возможность повышения/понижения severity или priority в ходе жизненного цикла инцидента при появлении новых фактов.
- **Интеграционные механизмы** — автоматическая синхронизация severity между SIEM, тикет-системой и пейджинг-платформой (например, PagerDuty, Opsgenie). Это гарантирует, что изменение уровня в одном инструменте мгновенно отразится на всех остальных.

Таким образом, внутреннее устройство моделей приоритизации — это не только перечень SEV‑1…SEV‑5, а целостный каркас из критериев воздействия, шкал urgency, матриц сопоставления и процедурных правил.

## Практика применения severity и priority в операционной работе SOC

Знание теории бесполезно без понятных операционных процедур. В реальной работе SOC L1 применяет понятия severity и priority в рамках жёстко регламентированного пайплайна триажа, который можно представить в виде последовательности шагов.

**1. Первичная оценка алерта и присвоение severity.**  
Аналитик получает оповещение, например, из SIEM или системы мониторинга. Первым делом он сверяется с матрицей критериев: скольких пользователей затронуло событие? Задета ли критичная инфраструктура (контроллер домена, платёжный шлюз, база данных)? Если событие подпадает под заранее заданные правила (например, сработало правило корреляции с severity "High"), система автоматически проставляет уровень серьёзности. В противном случае аналитик вручную выбирает уровень в интерфейсе ITSM-системы.

Типичный артефакт автоматического назначения severity — правило детектирования в SIEM, написанное на языке корреляции (Sigma, Splunk SPL, KQL). Для иллюстрации приведём фрагмент правила Sigma, регистрирующего массовую модификацию файлов — признак возможного шифровальщика. Правило задаёт высокий severity ещё до участия человека:

```yaml
title: Mass File Rename Indicative of Ransomware
id: 1234abcd-12ab-34cd-56ef-7890abcdef01
status: stable
description: Обнаруживает переименование более 100 файлов за 5 минут, типичное для ransomware
logsource:
    product: windows
    category: file_event
detection:
    selection:
        TargetFilename|endswith:
            - '.encrypted'
            - '.locked'
            - '.crypt'
    timeframe: 5m
    condition: selection | count() by ComputerName > 100
severity: critical
```

Примечание: пример иллюстративный; идентификатор и точные условия зависят от среды, но структура поля `severity` универсальна для многих правил.

**2. Определение urgency и вычисление priority.**  
После фиксации severity аналитик уточняет urgency, задавая себе вопросы: происходит ли атака прямо сейчас? Насколько близок финансовый/операционный дедлайн для затронутого сервиса? Много ли параллельных инцидентов в очереди? Инструментарий современных SOC (SOAR-платформы, обогащение инцидентов) может подсказывать urgency на основе календаря обслуживания, конфигурации SLA или статуса клиента. Результат — вычисление приоритета по матрице Impact × Urgency и занесение его в карточку инцидента.

Для автоматизации этого шага часто применяют скрипты обогащения. Ниже показан иллюстративный фрагмент на Python, который получает severity и urgency, а затем вычисляет priority по упрощённой таблице. В реальном продукте подобный код может выполняться в среде SOAR (например, Cortex XSOAR, Splunk Phantom) как playbook:

```python
priority_matrix = {
    ('Critical','High'):    'P1',
    ('Critical','Medium'):  'P2',
    ('Critical','Low'):     'P3',
    ('High','High'):        'P2',
    ('High','Medium'):      'P3',
    ('High','Low'):         'P4',
    ('Medium','High'):      'P3',
    ('Medium','Medium'):    'P4',
    ('Medium','Low'):       'P5',
}

def calculate_priority(severity, urgency):
    return priority_matrix.get((severity, urgency), 'P5')
```

После расчёта приоритет автоматически проставляется в поле `priority` инцидента.

**3. Эскалация и уведомление.**  
Итоговый приоритет определяет таймеры SLA и способ вызова ответственных. Для P1 (SEV‑1 с высокой срочностью) срабатывает round‑robin вызов дежурного через пейджинг-систему с немедленным эскалированием при отсутствии подтверждения в течение 5 минут. Для P4‑P5 инциденты просто попадают в бэклог. Современные платформы (PagerDuty, Opsgenie, ServiceNow) позволяют настроить такие правила через API и конфигурационные файлы.

**4. Пересмотр уровня в ходе инцидента.**  
Severity и priority не статичны. Если в ходе расследования выясняется, что инцидент затронул гораздо больше систем, аналитик повышает severity (например, с Medium до Critical). Автоматизация часто отслеживает появление новых индикаторов компрометации и может генерировать уведомление о необходимости пересмотра. Важно, чтобы все изменения фиксировались в аудиторском логе инцидента.

Инструментальные реализации этих процедур разнообразны, но все они сводятся к единому знаменателю: SIEM/EDR фиксирует факт — severity вычисляется на основе правил — urgency определяется аналитиком или контекстом — priority назначается и определяет скорость реагирования.

## Сквозной практический пример: классификация и эскалация инцидента в SOC

Рассмотрим реалистичный кейс, иллюстрирующий полный цикл приоритизации инцидента уровня SEV‑1 в гипотетической среде SOC. Сценарий намеренно упрощён, чтобы продемонстрировать взаимодействие severity и priority без отвлечения на детали конфигурации.

### Исходные условия

- Инфраструктура: корпоративная сеть с контроллером домена Windows Server 2022, веб-приложением на Linux (основной доходный сервис), SIEM Splunk, ITSM Jira Service Management, пейджинг PagerDuty.
- Роль: аналитик SOC L1 первой смены, рабочий день.
- Ситуация: в 10:05 утра поступает оповещение от системы мониторинга о том, что основное веб-приложение не отвечает по HTTPS.

### Шаг 1. Первичная классификация severity

Аналитик открывает алерт в Splunk. Инцидентный объект выглядит следующим образом (формат JSON, упрощён):

```json
{
  "alert_id": "INC-20260113-1005-001",
  "timestamp": "2026-01-13T10:05:00Z",
  "source": "monitoring_check_https",
  "target": {
    "host": "app-prod-01.example.com",
    "service": "web-frontend",
    "port": 443
  },
  "details": "HTTP 503 Service Unavailable, check interval 30s, consecutive failures: 3",
  "automatic_severity": "pending"
}
```

Согласно внутренней матрице критериев, недоступность основного доходного сервиса для всех пользователей классифицируется как **SEV‑2** (High) или **SEV‑1**, если подтверждена полная недоступность. Аналитик выполняет быстрый тест доступности, чтобы исключить ложное срабатывание:

```bash
$ curl -Ik https://app-prod-01.example.com
HTTP/2 503
server: nginx
content-type: text/html
...
```

Вывод подтверждает статус 503. Дополнительно проверяется, что страница не загружается в браузере. С учётом того, что сервис критичен для бизнеса и недоступен для всех пользователей, аналитик вручную устанавливает severity = "Critical" (SEV‑1). В интерфейсе Jira заполняется поле `severity`.

### Шаг 2. Оценка urgency и назначение priority

Аналитик сверяется с календарём бизнес-операций: сегодня обычный рабочий день, веб-приложение генерирует выручку в реальном времени, каждый час простоя оценивается как значительный финансовый ущерб. Urgency определяется как «High». На основе матрицы (Critical + High) высчитывается Priority = **P1**.

Автоматизация через playbook SOAR записывает этот приоритет в инцидент. Ниже приведён пример вызова API PagerDuty для создания инцидента с заданным severity и priority (иллюстративная структура):

```bash
curl -X POST "https://api.pagerduty.com/incidents" \
  -H "Authorization: Token token=YOUR_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "incident": {
      "type": "incident",
      "title": "Critical: Web application outage",
      "service": { "id": "SERVICE_ID" },
      "urgency": "high",
      "incident_key": "INC-20260113-1005-001",
      "body": {
        "type": "incident_body",
        "details": "Веб-приложение возвращает 503, подтверждена недоступность для всех. Severity: Critical, Priority: P1"
      },
      "escalation_policy": { "id": "EP_ID" },
      "priority": { "id": "P1_ID" }
    }
  }'
```

Значения `SERVICE_ID`, `EP_ID` и `P1_ID` определяются конфигурацией организации.

### Шаг 3. Эскалация и уведомление

Priority P1 автоматически запускает процесс Major Incident: создаётся отдельный канал в Slack/Teams, дежурный L2 получает звонок через PagerDuty с требованием подтвердить приём в течение 5 минут. Статус инцидента переходит в состояние «In Progress». Лог-строка из PagerDuty подтверждает эскалацию:

```json
{
  "event": "incident.triggered",
  "incident_id": "Q1A2B3C",
  "priority": "P1",
  "status": "triggered",
  "assigned_to": ["oncall-l2-engineer"],
  "escalation_count": 1,
  "timestamp": "2026-01-13T10:12:00Z"
}
```

Аналитик L1 продолжает мониторинг, пока L2 занимается восстановлением. При появлении признаков устранения (HTTP 200) инцидент переводится в статус «Resolved» с сохранением всей истории изменений severity и priority для постмортема.

### Ожидаемый вывод

На примере продемонстрировано, как SOC связывает техническую серьёзность отказа (Critical/SEV‑1) с бизнес-срочностью (High Urgency) и получает **Priority P1**, запускающий немедленную эскалацию. Если бы тот же отказ произошёл в период планового техобслуживания (Urgency Low), итоговый Priority мог бы составить P2 или P3, и вызов дежурного не производился бы — инцидент устранялся бы в рабочем порядке. Этот кейс иллюстрирует, что правильная приоритизация не только ускоряет восстановление, но и предотвращает выгорание инженеров, исключая необоснованную эскалацию.
