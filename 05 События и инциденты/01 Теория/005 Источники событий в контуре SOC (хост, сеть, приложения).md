# Источники событий в контуре SOC: хостовые, сетевые и прикладные  

## 1. Роль источников событий в SOC и ключевые определения  

Security Operations Center (SOC) — централизованное подразделение, отвечающее за мониторинг, обнаружение и реагирование на киберугрозы. Информационная основа его работы — непрерывный поток данных от компонентов ИТ-инфраструктуры. **Источник событий** — любой элемент (устройство, программа, сервис), который генерирует записи, отражающие его состояние или действия. Без таких источников SOC лишается первичной телеметрии и становится неспособным различить легитимную активность и атаку.  

Событие безопасности — наблюдаемое изменение в системе, которое может указывать на нарушение политик безопасности или угрозу. Оно фиксируется в виде лога (журнальной записи) или алерта. Важно не путать **событие**, **алерт** и **инцидент**:  
- **Событие (event)** — элементарная запись, например, успешный вход пользователя или открытое сетевое соединение.  
- **Алерт (alert)** — уведомление, сформированное SIEM или средством защиты при обнаружении подозрительной комбинации событий.  
- **Инцидент (incident)** — подтверждённое нарушение безопасности, требующее реагирования (например, компрометация учётной записи).  

SOC получает данные преимущественно из трёх традиционных доменов: **хостового**, **сетевого** и **прикладного**. Такая классификация отражает архитектурные уровни организации и позволяет соотнести событие с местом его возникновения. На практике современные SOC также обрабатывают информацию из облачных сред, средств идентификации, промышленных систем (OT) и Threat Intelligence-платформ, однако именно хост, сеть и приложения формируют основу мониторинга.  

```text
[Рабочая станция] ──(Windows Event Logs)──▶ [Winlogbeat] ──(TLS)──▶ [Коллектор Logstash] ──▶ [Elasticsearch] ◀──(Kibana)── [Аналитик SOC]
[Сетевой экран]   ──(Syslog)──────────────▶ [Syslog-сервер] ────▶ [SIEM]
[Веб-сервер]      ──(Access Logs)─────────▶ [Агент Filebeat] ──▶ [Kafka] ──▶ [SIEM]
```

Иллюстративная схема: основные потоки данных от источников до аналитика.

Чёткое представление о том, какие именно источники предоставляют данные, помогает специалисту уровня L1 корректно интерпретировать алерты. Сравнительная таблица ниже систематизирует фундаментальные отличия трёх базовых классов источников.

| Класс источника  | Уровень стека IT | Типичные представители                  | Типовые форматы логов             | Протоколы передачи              | Характерные события безопасности                           |
|------------------|------------------|------------------------------------------|-----------------------------------|--------------------------------|------------------------------------------------------------|
| **Хостовый**     | ОС, конечные устройства | Серверы (Windows/Linux), рабочие станции, ноутбуки, виртуальные машины | Windows Event Log (EVTX), syslog, auditd, macOS Unified Log | Syslog, Windows Event Forwarding, агенты (Beats, nxlog) | Успешный/неудачный вход (EID 4624/4625), повышение привилегий, запуск подозрительного процесса |
| **Сетевой**      | Уровни 3–4 OSI, канальный | Маршрутизаторы, коммутаторы, межсетевые экраны, IDS/IPS, прокси   | Syslog, NetFlow/IPFIX, CEF, LEEF | syslog, SNMP, NetFlow v9, AMQP | Блокировка трафика файрволом, сработка сигнатуры IDS, аномальный объём исходящего трафика |
| **Прикладной**   | Уровень 7 OSI, прикладной | Веб-серверы (Apache, Nginx, IIS), серверы СУБД, почтовые системы, ERP | Access/error-логи, JSON, специализированные форматы (W3C) | HTTP/S (REST API), syslog, Kafka | SQL-инъекция, перебор учётных данных веб-формы, доступ к конфиденциальным данным СУБД |

Примечание: перечисленные протоколы отражают наиболее распространённые способы экспорта, однако каждая реализация может использовать иные механизмы.

Из таблицы видно, что хостовые источники акцентируют внимание на действиях пользователей и процессах в операционной системе, сетевые — на коммуникациях между узлами, а прикладные — на транзакциях, специфичных для конкретного сервиса. SOC L1 должен уметь быстро соотнести конкретный алерт с классом источника, чтобы понять контекст оповещения.

## 2. Классификация и детальный обзор хостовых, сетевых и прикладных источников  

Чтобы проводить квалифицированный первичный анализ, аналитику необходимо знать, какие именно данные доступны от каждого класса источников, в каком виде они поступают и на какие события следует обращать внимание. Современный SOC собирает десятки и сотни типов журналов; ниже рассмотрены ключевые категории, охватывающие хост, сеть и приложения.

### 2.1. Хостовые источники  

Хостовые источники — это операционные системы и агенты, установленные на конечных устройствах и серверах. Они предоставляют детальную информацию о действиях пользователей, работе процессов, изменении конфигурации и системных ошибках. Основные представители:

- **Windows Event Log** — централизованный механизм ведения журналов в ОС Windows. События классифицируются по каналам: *Security* (аудит входа, доступ к объектам), *System* (запуск/остановка служб, ошибки драйверов), *Application* (сообщения приложений), а также специализированные: *Windows PowerShell*, *TaskScheduler*, *Microsoft-Windows-Sysmon/Operational* (при установке Sysinternals Sysmon). Каждое событие характеризуется Event ID, уровнем важности, источником и телом записи в XML-формате. Критичные для SOC идентификаторы: 4624 (успешный вход), 4625 (неудачный вход), 4648 (вход с явными учётными данными), 4688 (создание процесса), 5156 (фильтрация пакетов Windows Filtering Platform).  
- **Sysmon** — драйвер от Microsoft, расширяющий возможности стандартного аудита. Регистрирует создание процессов, сетевые соединения, изменение реестра, создание файлов и т.д. События имеют идентификаторы 1 (создание процесса), 3 (сетевое соединение), 7 (загрузка образа DLL) и др. Широко используется в SOC как надёжный источник для детектирования аномалий.  
- **Linux Audit Daemon (auditd)** — подсистема аудита ядра Linux. Позволяет отслеживать системные вызовы, доступ к файлам, изменение учётных записей. Конфигурируется правилами (`/etc/audit/audit.rules`), события имеют тип `SYSCALL`, `USER_LOGIN`, `CRED_ACQ` и т.д. Логи записываются в `/var/log/audit/audit.log`.  
- **Syslog (rsyslog/syslog-ng)** — стандартный протокол и формат ведения журналов в UNIX-подобных системах (RFC 5424). Большинство демонов и ядро записывают сообщения с определённым facility и severity. Для SOC интересны messages, auth.log, kern.log.  
- **Endpoint Detection and Response (EDR)** — агенты, например Microsoft Defender for Endpoint, CrowdStrike Falcon, SentinelOne. Они поставляют телеметрию высокого уровня: процессы, загрузка DLL, сетевые подключения, попытки эксплуатации уязвимостей. Обычно передают данные по защищённому каналу в облачную платформу, интегрированную с SIEM.  
- **Логи антивирусных решений** — записи о срабатываниях сигнатур, карантине, обновлениях баз. Часто отправляются в SOC как индикатор возможной заражённости.  

Ниже приведена сводная таблица важнейших хостовых источников с примерами критичных событий безопасности:

| Источник                        | Формат                    | Канал / компонент                            | Примеры критичных событий (иллюстративные ID)            |
|---------------------------------|---------------------------|----------------------------------------------|----------------------------------------------------------|
| Windows Event Log               | EVTX (XML)                | Security, System, Sysmon                     | 4625 – неудачный вход; 4688 – создан процесс; 4672 – назначение привилегий |
| Sysmon                          | Windows Event Log (EID)  | Microsoft-Windows-Sysmon/Operational          | 1 – создание процесса; 3 – сетевое соединение; 11 – создание/изменение файла |
| auditd                          | Бинарный/текстовый       | /var/log/audit/audit.log                     | SYSCALL execve, USER_LOGIN, ADD_GROUP, DAEMON_End (смены прав) |
| rsyslog (UNIX auth)             | Текстовый syslog         | /var/log/auth.log                             | Failed password for root from 203.0.113.45 port 22 ssh2 |
| EDR-агент (напр., CrowdStrike) | JSON / LEEF               | API / канал TLS                               | ProcessRollup2, NetworkConnectIP4, SuspiciousActivity   |
| Journactl (systemd)             | Бинарный с экспортом в syslog | journal                                          | Сообщения о запуске службы, ошибки модулей ядра        |

Любой анализ на хостовом уровне требует сопоставления нескольких записей, например цепочки: неудачный вход (4625) → успешный вход (4624) → запуск подозрительного процесса (4688).

### 2.2. Сетевые источники  

Сетевые источники охватывают все компоненты, отвечающие за передачу, фильтрацию и мониторинг трафика. В отличие от хостовых, они дают сквозную картину взаимодействия узлов, независимо от операционной системы. Основные категории:

- **Межсетевые экраны (Firewall)** — генерируют логи разрешённых и заблокированных соединений. Традиционные форматы: syslog с сообщениями о deny/allow, а также специализированные CEF (Common Event Format) или LEEF (Log Event Extended Format). Важные поля: source IP, destination IP, source/destination port, protocol, action. События типа «Traffic Deny» могут указывать на разведку или попытки эксплуатации.  
- **Маршрутизаторы и коммутаторы** — предоставляют информацию о состоянии интерфейсов, ACL, ошибках. Системные события (STP, отказ порта) важны для корреляции с аномалиями трафика. Логи обычно передаются по syslog.  
- **Системы обнаружения и предотвращения вторжений (IDS/IPS)** — анализируют трафик и генерируют алерты по сигнатурам или поведенческому анализу. Примеры: Snort, Suricata, Cisco Firepower. Каждый алерт содержит идентификатор сигнатуры (SID), классификацию атаки, IP-адреса, полезную нагрузку (payload).  
- **Прокси-серверы (Web Proxy)** — записывают все веб-запросы пользователей: URL, метод, код ответа, объём переданных данных. Инструменты: Squid, Broadcom Blue Coat. Логи прокси незаменимы для обнаружения фишинга, обращения к вредоносным доменам, утечки данных.  
- **NetFlow/IPFIX** — протоколы экспорта учётных записей о потоках трафика с сетевых устройств. Позволяют фиксировать кортежи: src IP, dst IP, src port, dst port, protocol, количество пакетов/байт, временные метки. В отличие от логов фаервола, NetFlow не показывает содержимое, но даёт общую статистику, что полезно для выявления аномальных объёмов передачи.  
- **DNS-серверы** — логи разрешения имён содержат запрошенные домены, ответы, информацию о клиенте. Подозрительные запросы к DGA-доменам (Domain Generation Algorithm) или туннелирование DNS — типичные индикаторы компрометации.  
- **VPN-концентраторы и контроллеры беспроводных точек** — логи подключений и отключений пользователей, попытки аутентификации, неудачные попытки могут сигнализировать о несанкционированном доступе.  

Сводная таблица ключевых сетевых источников:

| Источник               | Типовой формат            | Протокол экспорта      | Ключевые события безопасности                              |
|------------------------|---------------------------|------------------------|-------------------------------------------------------------|
| Межсетевой экран       | syslog / CEF / LEEF      | syslog (TCP/UDP)       | Deny inbound TCP 3389 – попытка доступа к RDP извне         |
| IDS/IPS (Suricata)      | eve.json                 | syslog / JSON / Redis  | alert “ET EXPLOIT” – эксплуатация уязвимости                |
| Веб-прокси (Squid)     | native log format        | syslog / TCP           | http_access DENIED; высокий объём POST-запросов на незнакомый хост |
| NetFlow/IPFIX         | NetFlow v9 / IPFIX       | UDP                    | Резкое увеличение трафика с внутреннего хоста на порт 443 нестандартного сервера |
| DNS-сервер (BIND)      | текстовый / JSON         | syslog / file          | Запрос к домену с высокой энтропией (DGA)                  |

Аналитик L1 должен уметь по IP-адресу источника или назначения определить, относится ли алерт к хосту внутри периметра, и быстро найти связанные сетевые логи для оценки масштаба.

### 2.3. Прикладные источники  

Прикладные источники включают логи серверов приложений и баз данных, а также специализированных сервисов и облачных сред. Их особенность — наличие бизнес-контекста (пользователи, транзакции, объекты данных), что позволяет выявлять целевые атаки на конкретные приложения.  

- **Веб-серверы** (Apache, Nginx, IIS) — журналы доступа (`access.log`) и ошибок (`error.log`). Содержат URL, метод, HTTP-код, User-Agent, IP клиента. Из них можно извлечь признаки SQL-инъекций (`UNION SELECT` в параметрах), сканирования (`404` на множество несуществующих страниц), эксплуатации уязвимостей (нестандартные заголовки).  
- **Веб-фаерволы (WAF)** — специализированные устройства/сервисы (Cloudflare, ModSecurity), фильтрующие трафик к веб-приложениям. Логи блокировок чётко указывают на попытки инъекций, межсайтового скриптинга (XSS) и других атак.  
- **Серверы баз данных** — СУБД (Microsoft SQL Server, Oracle, PostgreSQL) предоставляют аудит запросов, успешных и неудачных подключений, изменение схемы. В SQL Server: аудит действий на уровне сервера и БД, события `DATABASE_OBJECT_ACCESS`, `DATABASE_PRINCIPAL_CHANGE`; в Oracle: Unified Audit Trail с записями операций `SELECT`, `ALTER`. Обнаружение несанкционированного доступа к таблицам с конфиденциальными данными — прямая задача SOC.  
- **Почтовые серверы и шлюзы** (Microsoft Exchange, Postfix, IronPort) — фиксируют отправку/получение писем, попытки релея, срабатывания антиспама и антивируса. Инцидент может начаться с вредоносного вложения; логи почтового сервера помогают восстановить цепочку доставки.  
- **ERP и CRM-системы** (SAP, Oracle Siebel, Salesforce) — логи доступа, изменения записей клиентов, массовые выгрузки данных. Критичны для предотвращения инсайдерских угроз и мошенничества.  
- **Облачные сервисы** (AWS, Azure, Google Workspace) — предоставляют Audit Logs через API (CloudTrail, Azure Monitor), содержащие действия пользователей, изменения политик IAM, создание ресурсов.

Структурируем основные прикладные источники:

| Источник                     | Формат                      | Протокол передачи      | Характерные события безопасности                            |
|------------------------------|-----------------------------|------------------------|-------------------------------------------------------------|
| Apache HTTP Server           | Combined Log Format / JSON  | File, syslog, HTTPS    | `GET /admin/config.php?passwd=` – попытка доступа к конфигурации |
| WAF (ModSecurity)            | JSON / CEF                  | syslog / API           | `XSS Attack Prototype Detected`                             |
| Microsoft SQL Server         | XML / собственный аудит     | Windows Event Log, файл | `DATABASE_AUDIT_SPECIFICATION: SELECT ON Employee.Salary` – неавторизованный запрос |
| Microsoft Exchange           | IIS-логи + очередь сообщений| Windows Event Log      | Сработало правило антиспама с высокой достоверностью, массовая рассылка |
| AWS CloudTrail               | JSON                        | HTTPS API              | `ConsoleLogin` с нестандартной геолокацией; `UpdateTrail` отключение аудита |

Важно понимать, что многие прикладные источники генерируют громадные объёмы данных, поэтому в SOC обычно направляют только подмножество — например, логи ошибок и существенные транзакции.

## 3. Сбор, нормализация и практическая работа с источниками событий в SOC  

Настройка и эксплуатация источников событий — задача, которая ложится как на инженеров SOC, так и на администраторов систем. В этом разделе рассматриваются технические аспекты доставки логов, их предварительная обработка и типичные проблемы, с которыми сталкивается команда мониторинга.

### 3.1. Методы сбора и транспортировка  

Выбор способа сбора зависит от возможностей источника, объёмов и требований безопасности. Выделяют агентный и безагентный подходы.

**Агентный сбор** предполагает установку специализированного ПО на каждый хост (или контейнер). Агенты работают локально, читают необходимые журналы, буферизуют и отправляют данные центральному коллектору. Это даёт гарантию доставки, возможность фильтрации до передачи и поддержку шифрования. Популярные решения:  
- *Elastic Beats* — семейство легковесных отправителей: Winlogbeat (для Windows Event Log), Filebeat (для текстовых логов), Auditbeat (для аудита Linux).  
- *Splunk Universal Forwarder* — агент, умеющий собирать практически любые локальные логи и метрики, передавать в Splunk Indexer.  
- *nxlog* — кроссплатформенный агент, поддерживающий множество форматов и протоколов, часто используется для Windows-сред.  
- *Osquery* — агент, предоставляющий SQL-интерфейс к состоянию системы; его результаты могут по расписанию отправляться в SIEM.  

**Безагентный сбор** опирается на встроенные механизмы удалённого получения событий. Наиболее распространённый — **syslog**. Сетевое устройство или UNIX-хост конфигурируется для отправки всех или отфильтрованных сообщений на удалённый syslog-сервер (часто выступающий как коллектор для SIEM). В средах Microsoft применяется **Windows Event Collector** — служба, которая по подписке собирает события с множества систем в одну централизованную базу. Для облачных и SaaS-приложений логи получают через REST API, Amazon S3-бакеты или потоковые сервисы (Amazon Kinesis, Azure Event Hubs).

Протоколы и форматы:  
- *Syslog (RFC 5424)* — преимущественно UDP (514) для локальных сетей, TCP/TLS (6514) для надёжной и защищённой передачи.  
- *HTTP/HTTPS* — REST API многих современных SIEM (Splunk HEC, Elasticsearch).  
- *Kafka* — распределённый потоковый брокер, часто применяется в качестве буфера перед SIEM для развязки пиковых нагрузок.  
- *NetFlow / IPFIX* — экспорт учётных записей о потоках; обычно направляется на специализированный коллектор, затем в SIEM.

### 3.2. Нормализация и обогащение  

Сырые логи поступают в SIEM в разнородных форматах. Для анализа их необходимо привести к общей модели данных — это процесс нормализации. Например, схемы Elastic Common Schema (ECS) или Splunk Common Information Model (CIM) определяют единые имена полей: `source.ip`, `user.name`, `event.action`, `event.code`. Парсинг осуществляется с помощью:  
- Grok (регулярные выражения) в Logstash.  
- Ingest Pipeline в Elasticsearch.  
- Data Models в Splunk.  

Обогащение добавляет контекст: GeoIP по IP-адресу, FQDN хоста по обратному DNS, принадлежность к отделу через сопоставление с LDAP/Active Directory, репутацию URL по Threat Intelligence. Всё это выполняется на этапе приёма логов в коллекторе.

### 3.3. Настройка источников: примеры конфигураций  

Приведём практические фрагменты настройки отправки событий с двух типичных источников.

**Пример 1: пересылка журналов аутентификации Linux через rsyslog в SIEM по TLS**

```bash
# /etc/rsyslog.d/50-siem.conf
# Пересылаем все сообщения с facility auth и authpriv на удалённый syslog-сервер

$DefaultNetstreamDriver gtls
$DefaultNetstreamDriverCAFile /etc/ssl/certs/ca-certificates.crt
$ActionSendStreamDriverPermittedPeer siem.example.com

auth,authpriv.* action(
  type="omfwd"
  Target="siem.example.com"
  Port="6514"
  Protocol="tcp"
  StreamDriver="gtls"
  StreamDriverMode="1"
  Template="RSYSLOG_SyslogProtocol23Format"
)
```

**Пример 2: отправка событий Windows Security через Winlogbeat в Elasticsearch**

```yaml
# winlogbeat.yml (фрагмент)
winlogbeat.event_logs:
  - name: Security
    ignore_older: 72h
    # передаём только ключевые EventID, сокращая объём
    include:
      - event_id: 4624, 4625, 4648, 4688, 5140, 5156

output.elasticsearch:
  hosts: ["https://elasticsearch.siem.local:9200"]
  username: "winlogbeat_writer"
  password: ${ES_PASSWORD}
  ssl.certificate_authorities: ["/etc/ssl/ca.pem"]
```

Эти конфиги иллюстрируют подходы к снижению сетевой нагрузки и обеспечению конфиденциальности.

### 3.4. Типичные ошибки и рекомендации  

- **Расхождение системного времени** — источник и приёмник должны иметь расхождение не более нескольких секунд (NTP обязателен). В противном случае корреляция событий нарушается.  
- **Переполнение очереди syslog** — при высокой нагрузке UDP-пакеты могут теряться без уведомления. Использование TCP/TLS и достаточного объёма приёмного буфера решает проблему.  
- **Недостаточный или избыточный уровень аудита** — слишком детальный аудит создаёт «шум» и дополнительные затраты на хранение, а недостаточный может пропустить критичные события. Необходимо настроить аудит в соответствии с политиками (например, аудит только неудачных попыток для обычных рабочих станций, но полный аудит для критичных серверов).  
- **Отсутствие фильтрации на источнике** — веб-прокси способен генерировать гигабайты логов в день, из которых SOC-аналитику нужны только аномалии. Предварительная фильтрация по категориям URL и кодам ответа помогает сократить входящий поток.  
- **Неправильная настройка прав агентов** — агент должен иметь доступ на чтение только требуемых журналов; работа под избыточной учётной записью повышает риск компрометации.

## 4. Сквозной практический пример: обнаружение атаки перебора учётных записей через хостовой лог и SIEM  

**Исходные условия:**  
Организация развернула домен Active Directory. На рабочей станции Windows 10 включён расширенный аудит, установлен агент Winlogbeat, отправляющий события в SIEM на базе Elastic Stack. Цель — продемонстрировать путь события безопасности от его генерации до алерта аналитика.

**Шаг 1. Настройка аудита на рабочей станции**  
Включаем аудит неудачных и успешных входов в систему.

```powershell
# Запуск от имени администратора
auditpol /set /subcategory:"Logon" /failure:enable /success:enable
```

Результат: команда изменяет политику аудита. Проверить можно командой `auditpol /get /category:"Logon/Logoff"`.

**Шаг 2. Конфигурация Winlogbeat**  
Файл `winlogbeat.yml` настроен на сбор событий Security с ключевыми EventID и отправку в Elasticsearch (см. раздел 3.3). После перезапуска службы агент начинает чтение журнала.

```yaml
winlogbeat.event_logs:
  - name: Security
    include:
      - event_id: 4625
output.elasticsearch:
  hosts: ["https://elasticsearch.siem.local:9200"]
  username: "winlogbeat_writer"
  password: "${ES_PASSWORD}"
```

**Шаг 3. Имитация атаки перебора пароля**  
Локально запускаем цикл, пытающийся выполнить команду от имени несуществующего пользователя с заведомо неверным паролем:

```batch
for /L %i in (1,1,10) do runas /user:DOMAIN\bruteforce_user cmd.exe
```

Система ответит запросом пароля. После нескольких неудачных попыток события фиксируются в журнале Security с кодом 4625.

**Шаг 4. Просмотр сгенерированного события на хосте**  
Для проверки используем PowerShell, извлекая последние записи.

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625} -MaxEvents 5 |
    Select-Object TimeCreated, Id, @{n='User';e={$_.Properties[5].Value}}, @{n='IP';e={$_.Properties[18].Value}} |
    Format-Table -AutoSize
```

*Типовой вывод (иллюстративная схема, значения зависят от среды):*  
```
TimeCreated           Id   User              IP
-----------           --   ----              --
2025-03-20 09:17:12   4625 DOMAIN\bruteforce_user 192.168.5.45
2025-03-20 09:17:11   4625 DOMAIN\bruteforce_user 192.168.5.45
2025-03-20 09:17:10   4625 DOMAIN\bruteforce_user 192.168.5.45
...
```

**Шаг 5. Поиск в SIEM и создание правила обнаружения**  
В Elastic Stack (Kibana) выполняем запрос, агрегирующий количество неудачных попыток по учётной записи за последние 5 минут:

```json
{
  "query": {
    "bool": {
      "must": [
        { "match": { "event.code": "4625" } },
        { "range": { "@timestamp": { "gte": "now-5m" } } }
      ]
    }
  },
  "aggs": {
    "by_user": {
      "terms": { "field": "winlog.event_data.TargetUserName", "size": 10 },
      "aggs": {
        "source_ip": { "terms": { "field": "winlog.event_data.IpAddress" } }
      }
    }
  },
  "size": 0
}
```

Для автоматического оповещения можно создать правило типа `threshold`, которое генерирует алерт, если количество событий 4625 для одной учётной записи превышает 5 за 5 минут. Алерт поступит аналитику L1 с деталями: пользователь `bruteforce_user`, IP 192.168.5.45, временной промежуток.

**Ожидаемый вывод:**  
Сквозной пример демонстрирует полную цепочку: источник (хост Windows, Event ID 4625) → сбор агентом → отправка в SIEM → нормализация → индексация → корреляция → алерт. Аналитик SOC L1 на основе этого алерта может начать расследование: проверить, является ли IP внутренним или внешним, связаться с пользователем, при необходимости заблокировать учётную запись.
