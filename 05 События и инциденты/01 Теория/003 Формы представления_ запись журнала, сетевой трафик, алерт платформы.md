# Формы представления событий безопасности: запись журнала, сетевой трафик, алерт платформы

## 1. Контекст и базовые понятия

Событие безопасности (security event) — это зафиксированное наблюдаемое происшествие в информационной системе, которое потенциально влияет на конфиденциальность, целостность или доступность ресурсов. Согласно руководству Канадского центра кибербезопасности, **запись в журнале (log)** представляет собой данные о конкретной активности, состоянии системы или ошибке, а **событие** — это уже сущность, извлечённая из лога и признанная значимой для безопасности [Network security logging and monitoring - ITSAP.80.085](https://www.cyber.gc.ca/en/guidance/network-security-logging-monitoring-itsap80085). Провайдеры SIEM‑систем (Graylog, Splunk) уточняют, что событие становится **инцидентом** (incident), когда подтверждено злонамеренное действие или нарушение политики [Security Events](https://go2docs.graylog.org/current/what_more_can_graylog_do_for_me/security_events.htm); [Security Event Logs: A Complete Introduction](https://www.splunk.com/en_us/blog/learn/security-event-logs.html). Таким образом выстраивается цепочка: **запись журнала (log) → событие безопасности (event) → инцидент**, а каждая ступень обладает своей формой представления.

На уровне SOC L1 аналитик оперирует тремя фундаментальными формами, в которых событие безопасности попадает в поле зрения:

* **Запись журнала (log entry)** — неструктурированная или слабоструктурированная строка, сгенерированная операционной системой, приложением или сетевым устройством как результат штатного протоколирования. Пример: запись Windows Event Log или сообщение syslog.

* **Сетевой трафик** — поток пакетов или сессионных данных, захваченный сенсорами (снифферами, NDR‑системами) непосредственно с канала передачи. Трафик содержит первичные свидетельства взаимодействия узлов ещё до того, как они могут быть отражены в логах хостов. Иногда трафик **является единственным источником** события, если атакующий воздействует на узел без оставления локальных журнальных следов.

* **Алерт платформы (alert)** — производный цифровой объект, сформированный средством мониторинга (SIEM, IDS/IPS, EDR) в момент срабатывания правила корреляции или сигнатурного обнаружения. Алерт агрегирует, обогащает и приоритизирует исходные записи или пакеты, предоставляя аналитику контекст и указание на необходимость немедленной реакции.

Эти три формы не являются взаимоисключающими; напротив, типичный инцидент виден через все три одновременно: в логе сервера появляется запись о неудачном входе, сенсор NDR фиксирует соответствующую TCP‑сессию, а SIEM генерирует алерт о брутфорсе при превышении порога.

Ключевое различие между формами — **степень вторичности** по отношению к исходной активности и **объём пригодного для автоматической обработки контекста**. Следующая сравнительная таблица фиксирует основные свойства.

| Форма представления | Происхождение | Степень обработки | Типичный объём единицы | Основное назначение на L1 |
|---------------------|---------------|-------------------|-------------------------|----------------------------|
| Запись журнала | Источник‑генератор (ОС, приложение, устройство) | Сырая, может содержать неструктурированный текст | Порядка сотен байт – единицы килобайт | Поиск конкретной активности по идентификатору события, первичная оценка легитимности |
| Сетевой трафик | Сетевой адаптер / зеркало порта / TAP‑устройство | Сырая битовая последовательность либо агрегированные flow‑записи | От десятков байт (один пакет) до гигабайт (полный pcap) | Подтверждение факта взаимодействия, реконструкция таймлайна, выявление вредоносного обмена, не попавшего в логи |
| Алерт платформы | SIEM, IDS/IPS, EDR‑консоль | Обработанная, нормализованная, приоритизированная | Обычно JSON‑документ в несколько килобайт | Быстрое оповещение об угрозе, эскалация по приоритету, начало расследования |

Необходимо понимать, что даже в рамках одного типа логов представление разнится в зависимости от источника. Так, запись журнала Windows Security Event использует XML‑пространство, определяемое расширенной схемой Windows Event Log, в то время как Linux‑системы полагаются на простой текст в соответствии с традицией syslog. Следующий фрагмент демонстрирует типичную запись успешного входа в систему Windows 10/11 (Event ID 4624) — событие, которое аналитик SOC обязательно умеет читать «с листа»:

```xml
<Event xmlns='http://schemas.microsoft.com/win/2004/08/events/event'>
  <System>
    <Provider Name='Microsoft-Windows-Security-Auditing' Guid='{...}'/>
    <EventID>4624</EventID>
    <Version>2</Version>
    <Level>0</Level>
    <Task>12544</Task>
    <Opcode>0</Opcode>
    <Keywords>0x8020000000000000</Keywords>
    <TimeCreated SystemTime='2025-01-15T08:30:15.1234567Z'/>
    <EventRecordID>1837465</EventRecordID>
    <Correlation/>
    <Execution ProcessID='4' ThreadID='88'/>
    <Channel>Security</Channel>
    <Computer>SRV-APP01.contoso.com</Computer>
    <Security/>
  </System>
  <EventData>
    <Data Name='SubjectUserSid'>S-1-5-18</Data>
    <Data Name='SubjectUserName'>SRV-APP01$</Data>
    <Data Name='SubjectDomainName'>CONTOSO</Data>
    <Data Name='SubjectLogonId'>0x3e7</Data>
    <Data Name='TargetUserSid'>S-1-5-21-1234567890-123456789-123456789-1104</Data>
    <Data Name='TargetUserName'>jdoe</Data>
    <Data Name='TargetDomainName'>CONTOSO</Data>
    <Data Name='TargetLogonId'>0x5c3a2b7d</Data>
    <Data Name='LogonType'>10</Data>
    <!-- Значение 10 = RemoteInteractive (RDP) -->
    <Data Name='LogonProcessName'>User32</Data>
    <Data Name='AuthenticationPackageName'>Negotiate</Data>
    <Data Name='WorkstationName'>WS-JDOE</Data>
    <Data Name='IpAddress'>192.168.15.250</Data>
    <Data Name='IpPort'>0</Data>
  </EventData>
</Event>
```

Этот XML — пример структурированной записи журнала. Аналитик обращает внимание на поля `EventID`, `LogonType`, `IpAddress`, по которым строится первичный вывод: легитимный ли это RDP‑сеанс сотрудника или потенциальное вторжение. События с `LogonType=10` (удалённый интерактивный вход) в сочетании с необычным IP могут быть отмечены корреляционным правилом SIEM, что породит алерт. Так одна форма — журнальная запись — служит сырьём для другой — алерта платформы.

Параллельно сетевой сенсор фиксирует ту же самую RDP‑сессию как поток TCP‑пакетов на порт 3389. Сетевой трафик служит независимым источником истины; если атакующий сумел очистить локальные логи, пакеты всё равно останутся в буфере захвата.

Таким образом, понимание трёх форм и их взаимоотношений — фундамент для работы на первой линии SOC. Далее каждая форма рассматривается детально.

## 2. Внутреннее устройство форм представления

Данный раздел даёт обзор класса «формы представления событий безопасности», поэтому здесь обязательно присутствует сравнительная таблица, обобщающая технические характеристики трёх форм, и последующие подразделы детализируют каждую.

### 2.1 Запись журнала

Записи журналов генерируются агентами, встроенными в операционные системы, приложения, серверы баз данных, межсетевые экраны и прочие компоненты. Их цель — зафиксировать факт операции с минимальной задержкой. Базовыми атрибутами любой журнальной записи являются:

* **Временная метка (timestamp)** — момент события с точностью, определяемой источником (обычно от секунд до десятых долей микросекунды). Синхронизация по NTP критична для последующей корреляции.
* **Идентификатор события (event ID/type)** — числовой или текстовый код, позволяющий классифицировать запись (например, 4624 для успешного входа в Windows).
* **Источник (source)** — хост, приложение или процесс, породивший запись.
* **Категория/уровень (severity/level)** — условная важность (Information, Warning, Error, Critical и др.).
* **Описание (message)** — свободный или параметризованный текст, иногда с включением динамических данных (имя пользователя, IP‑адрес).

С точки зрения формата индустрия выработала несколько общепринятых схем, обеспечивающих ту или иную степень структурированности:

* **Syslog (RFC 5424)** — классический текстовый формат для Unix‑подобных сред и сетевого оборудования. Сообщение состоит из заголовка (PRI, версия, timestamp, hostname, app‑name, procid, msgid) и структурированных данных в виде пар ключ-значение, завершающихся свободным сообщением.

* **Common Event Format (CEF)** — разработан ArcSight (ныне Micro Focus), преобладает в продуктах безопасности. Каждая запись начинается с префикса `CEF:Version|Device Vendor|...`, после которого следуют пары `key=value`, разделённые `|` или пробелами.

* **Log Event Extended Format (LEEF)** — предложен IBM для QRadar, похож на CEF, но использует разделитель `;` и свой набор обязательных полей.

* **JSON‑события** — всё чаще используются современными агентами (Filebeat, Winlogbeat, Graylog Sidecar). JSON даёт естественную вложенность, прост в парсинге и позволяет передавать сложные объекты.

Ниже приведён пример записи в формате syslog (RFC 5424), иллюстрирующий неудачный вход через SSH (соответствует событию, которое может лечь в основу алерта о брутфорсе):

```text
<14>1 2025-05-10T14:28:03.151Z app-srv-01 sshd 22873 - - Failed password for root from 192.168.50.12 port 53022 ssh2
```

Поля здесь: `<14>` — приоритет (facility=1 user, severity=6 info), `1` — версия, временная метка, хост, приложение, PID, msgid «-», структурированные данные «-», сообщение. Аналитик SOC может извлечь IP‑адрес источника и факт неудачной аутентификации, чтобы сопоставить с другими данными.

Сравним ключевые аспекты форматов представления в таблице:

| Параметр | Syslog (RFC 5424) | CEF (ArcSight) | LEEF (IBM QRadar) | JSON (Graylog/ELK) |
|----------|-------------------|----------------|--------------------|---------------------|
| Структура | Текстовый заголовок + опциональные SD‑элементы | Фиксированный префикс + key=value‑пары | Фиксированный заголовок + ;key=value‑пары | Вложенный объект ключ‑значение |
| Расширяемость | Через SD‑элементы, ограниченно | Произвольные доп. поля через `key=value` | Аналогично CEF | Полная, за счёт произвольных JSON‑структур |
| Размер накладных расходов | Низкий (десятки байт) | Средний (строка с escaping) | Средний | Высокий (относительно, за счёт синтаксиса) |
| Удобство для машинного разбора | Требует парсера, SD‑иды | Непосредственное извлечение | Непосредственное извлечение | Нативная десериализация |

Для Windows‑сред основным форматом является XML, как показано в разделе 1. Структура жёстко задаётся манифестом провайдера событий, а подписчики получают события через каналы (Security, System, Application и др.).

### 2.2 Сетевой трафик

Сетевой трафик как форма представления событий безопасности выступает в двух основных ипостасях: **полный захват пакетов (Full Packet Capture, FPC)** и **агрегированные записи о потоках (flow records)**.

**Полный захват пакетов** обычно выполняется сенсорами на зеркалируемых портах коммутаторов или TAP‑устройствах. Инструменты — tcpdump, Wireshark, высокопроизводительные системы типа Corelight (на базе Zeek). Захваченный поток хранится в pcap‑файлах и содержит сырые байты канального, сетевого и транспортного уровней, а также частично — прикладного.

Кадр Ethernet, пакет IP и сегмент TCP образуют иерархию заголовков. Минимальный набор полей, важных для SOC‑анализа, включает:
- MAC‑адреса источника и назначения;
- IP‑адреса и номера протоколов транспортного уровня;
- порты TCP/UDP;
- флаги TCP (SYN, ACK, RST, FIN и пр.);
- временную метку пакета.

Типичная команда tcpdump для захвата и одновременного отображения заголовков с ограниченной глубиной полезной нагрузки:

```bash
tcpdump -nn -c 5 -X 'tcp port 3389'
```

Вывод может выглядеть следующим образом (иллюстративная схема):

```text
14:28:03.151234 IP 192.168.50.12.53022 > 192.168.15.10.3389: Flags [S], seq 124567890, win 64240, options [mss 1460,nop,wscale 8,nop,nop,sackOK], length 0
	0x0000:  4500 003c 1c46 4000 4006 b1e6 c0a8 320c
	0x0010:  c0a8 0f0a cf26 0d3d 076d 3ed2 0000 0000
	0x0020:  a002 faf0 2b9f 0000 0204 05b4 0103 0308
	0x0030:  0101 0402 0000 0000
14:28:03.151452 IP 192.168.15.10.3389 > 192.168.50.12.53022: Flags [S.], seq 3910371929, ack 124567891, win 28960, options [mss 1460,nop,nop,sackOK,nop,wscale 7], length 0
```

Такая запись демонстрирует начальный handshake TCP‑сессии к порту 3389 (RDP). Аналитик может мгновенно подтвердить, что с хоста `192.168.50.12` был отправлен SYN к порту RDP сервера, и сервер ответил SYN‑ACK. В совокупности с логами безопасности это даёт уверенность в том, что сетевой контакт имел место, даже если локальные журналы отсутствуют.

**Flow‑записи** (NetFlow v9, IPFIX) — это агрегированные метаданные о сетевых сессиях, собираемые маршрутизаторами или выделенными probes. Они значительно компактнее pcap и содержат: IP‑адреса, порты, протокол, времена начала и окончания, количество переданных байт и пакетов. Flow не включает полезную нагрузку, но позволяет строить общую картину взаимодействия и выявлять объёмные аномалии.

Особое место занимает формат журналов сетевой активности, создаваемый Zeek (ранее Bro) — он находится на стыке FPC и log. Zeek анализирует трафик и генерирует высокоуровневые структурированные записи, например `conn.log`, `dns.log`, `http.log`. Пример строки `conn.log` (одна TCP‑сессия):

```text
#fields	ts	uid	id.orig_h	id.orig_p	id.resp_h	id.resp_p	proto	service	duration	orig_bytes	resp_bytes	conn_state	local_orig	local_resp	missed_bytes	history	orig_pkts	orig_ip_bytes	resp_pkts	resp_ip_bytes	tunnel_parents
1715334483.151234	Co0l1a2b3c4d5e6f	192.168.50.12	53022	192.168.15.10	3389	tcp	rdp	15.204567	1234	5678	SF	-	-	0	ShADadfF	12	1234	8	5678	-
```

Поля `conn_state=SF` (синхронный финиш) и наличие сервиса `rdp` дают аналитику информацию о завершённой RDP‑сессии, продолжительности и объёмах переданных данных. Эта запись — более сжатая и осмысленная форма представления сетевого события, чем сырой pcap.

Сводка характеристик двух разновидностей представлена в таблице:

| Характеристика | Полный захват (pcap) | Flow‑записи (NetFlow/IPFIX) | Zeek‑логи |
|----------------|-----------------------|-----------------------------|-----------|
| Содержит payload | Да (L2‑L7) | Нет | Нет (метаданные) |
| Объём данных на сессию | Большой (МБ – ГБ) | Порядка сотен байт | Порядка одного килобайта |
| Требования к хранению | Существенные, ротация | Минимальные | Средние |
| Основной сценарий SOC | Глубокая разборка инцидентов, восстановление файлов | Профилирование трафика, поиск аномалий объёмов | Быстрый детект известных паттернов, обогащение SIEM |

### 2.3 Алерт платформы

Алерт — это итоговый продукт работы корреляционного движка SIEM, IDS/IPS или EDR. В отличие от пассивной регистрации факта в логе, алерт **явно маркирует ситуацию как потенциально вредоносную** и требует реакции. Любая зрелая платформа предоставляет его в машиночитаемом виде (почти всегда JSON), что позволяет автоматизировать дальнейший workflow.

Стандартная структура алерта включает:

* **Идентификаторы** — уникальный ID алерта, ID правила/сигнатуры, версию правила.
* **Severity (criticality)** — оценки от низкой до критической (например, Low/Medium/High/Critical).
* **Временной диапазон** — время срабатывания правила, временной интервал исходных событий.
* **Контекстные поля** — IP‑адреса, имена хостов, пользователи, геолокация, активы.
* **Ссылки на исходные события** — идентификаторы или прямые URL, позволяющие аналитику «провалиться» от алерта к конкретным записям логов или сессиям.
* **Описание и рекомендации** — текстовое описание угрозы и возможных шагов реагирования.

Примерная структура алерта в нотации, схожей с оповещением SIEM (Graylog Security, Splunk Enterprise Security):

```json
{
  "alert_id": "alert-9a8b7c6d-5e4f-3a2b-1c0d-ef0987654321",
  "rule_id": "brute-force-rdp-high",
  "rule_name": "Excessive RDP login failures",
  "severity": "High",
  "event_time": "2025-05-10T14:33:10.000Z",
  "window_start": "2025-05-10T14:28:00.000Z",
  "window_end": "2025-05-10T14:33:00.000Z",
  "asset": {
    "hostname": "SRV-APP01.contoso.com",
    "ip": "192.168.15.10",
    "owner": "IT Services",
    "criticality": "medium"
  },
  "attacker": {
    "ip": "192.168.50.12",
    "country": "Unknown"
  },
  "anomalies": [
    {"event_type": "windows_security", "event_id": 4625, "count": 47},
    {"event_type": "network_session", "sessions": 1, "direction": "inbound"}
  ],
  "events": [
    {"source": "windows_log", "event_id": 4625, "record_id": "1837521", "time": "2025-05-10T14:28:03.123Z"},
    {"source": "zeek_conn", "uid": "Co0l1a2b3c4d5e6f", "time": "2025-05-10T14:28:03.151Z"}
  ],
  "investigation_link": "https://siem.contoso.com/investigation/alert-9a8b...",
  "recommended_action": "Block source IP, reset account password, forensic analysis of host."
}
```

Такой документ — агрегат, который связывает воедино и журнальные записи (здесь событие 4625 — неудачный вход), и сетевую сессию (Zeek `conn.log`). Аналитик первой линии, получив алерт с severity `High`, в первую очередь проверяет, не является ли он ложноположительным (например, сработал на тестовый стенд), и, убедившись в реальности угрозы, выполняет эскалацию.

Следующая таблица сравнивает представление алертов в трёх типичных продуктах — SIEM, IDS и EDR — по ряду ключевых параметров.

| Параметр | SIEM‑алерт (Splunk ES, Graylog) | IDS‑сигнатура (Suricata) | EDR‑алерт (CrowdStrike) |
|----------|--------------------------------|--------------------------|--------------------------|
| Источник данных | Логи, flow, IDS, EDR, OSquery | Сетевой трафик (пакеты) | События конечных точек (процессы, syscalls) |
| Пример поля идентификации | `rule_name` / `signature_id` | `alert.signature_id` (sid) | `detection_id` / `technique_id` (MITRE) |
| Встроенный контекст | Обогащён данными об активах, таймлайном | Минимален (src/dst, сигнатура) | Богатый (дерево процессов, артефакты) |
| Корреляция | Межсобытийная (порог, цепочки) | Пакетная (потоковая) | На основе поведения (IOA, ML) |
| Типовой путь расследования на L1 | Прямой drill‑down к сырым логам | Прямой переход к pcap | Прямая детализация в консоли EDR |

Таким образом, алерт платформы служит «единым окном», в котором концентрируются свидетельства из разных первичных форм. Грамотный аналитик никогда не ограничивается одним алертом, а использует его как трамплин для изучения исходных логов и трафика.

## 3. Применение и работа с формами представления

На первой линии SOC работа с тремя формами представляет собой циклический процесс: наблюдение → первичный анализ → обогащение → принятие решения. Ниже рассмотрены типовые операции и инструменты для каждой формы, а также частые ошибки.

### 3.1 Работа с записями журналов

Первичная задача — быстро найти и интерпретировать нужную запись в массиве логов. Инструментарий зависит от среды, но общий паттерн — фильтрация по временному окну, идентификатору события и ключевым полям.

**Windows** (PowerShell):

```powershell
# Просмотр последних 10 событий с EventID 4625 (неудачный вход) из журнала Security
Get-WinEvent -LogName Security | Where-Object { $_.Id -eq 4625 } | Select-Object -First 10 | Format-List TimeCreated, Id, Message
```

Эта команда выдаёт список событий, из которого аналитик извлекает IP‑адреса, имена учётных записей и LogonType. Признаком атаки будет большое количество записей с одного IP за короткий промежуток.

**Linux** (grep по системным журналам):

```bash
grep "Failed password" /var/log/auth.log | tail -20
```

Вывод укажет источник, целевую учётную запись и порт.

При работе с логами важно помнить:

* Временная метка должна быть в UTC или явно преобразована, чтобы совпадать с другими источниками.
* Не все приложения пишут логи в едином формате; коннекторы SIEM нормализуют поля, но при прямом просмотре аналитик должен знать структуру конкретного лога.
* Удалённый злоумышленник может фальсифицировать поля вроде `WorkstationName` или `Process Name`; следовательно, ориентироваться только на них нельзя.

### 3.2 Работа с сетевым трафиком

На SOC L1 часто приходится подтверждать факт сетевого взаимодействия по IP‑адресу или порту, указанному в алерте. Для этого используют быструю фильтрацию сохранённого pcap или запрос к Zeek‑логам.

**Фильтрация pcap с помощью tcpdump**:

```bash
tcpdump -nn -r capture_20250510.pcap 'host 192.168.50.12 and tcp port 3389' -c 10
```

После выполнения в консоли появляются первые 10 пакетов соответствующей сессии. Ключевым индикатором является состояние TCP (флаги SYN, ACK, RST). Например, множество повторных SYN‑пакетов с одного источника без завершения handshake может указывать на сканирование.

**Анализ Zeek conn.log напрямую** (с использованием `zeek-cut` или `awk`):

```bash
cat conn.log | awk -F '\t' '$4=="192.168.50.12" && $7=="tcp" {print $1,$4,$6,$9,$10,$11}'
```

Такой запрос выводит временную метку, IP‑порт ответа, сервис, длительность, байты источника и приёмника. Для инцидента брутфорса короткие сессии длительностью несколько секунд с небольшим объёмом переданных данных и статусом `S0` (SYN только отправлен) — характерный рисунок.

**Потенциальные ловушки**:

* Сетевой трафик может быть зашифрован (TLS). Тогда L1 видит только метаданные и длину пакетов; расшифровка обычно не входит в обязанности.
* Наличие NAT искажает IP‑адреса; необходимо сверяться с картой сети.
* Flow‑записи, в отличие от pcap, могут не содержать информации о конкретных пакетах‑откликах, что затрудняет факт‑чекинг.

### 3.3 Работа с алертами платформы

Алерт — точка входа в инцидент. SOC L1 действует по процедуре триажа:

1. Оценить severity и затронутые активы.
2. Проверить, не является ли алерт ложноположительным (путем проверки контекста — например, IP‑адрес принадлежит известному сканеру уязвимостей Nessus).
3. При необходимости перейти к исходным событиям.

Типичный шаг в SIEM — выполнить запрос для получения деталей алерта и связанных событий. Пример на языке Splunk SPL (Search Processing Language):

```spl
index=windows EventCode=4625  | stats count by AccountName, IpAddress, _time
| where count > 5
| sort - count
```

Хотя эта команда больше относится к поиску аномалий, она демонстрирует, как аналитик может воспроизвести логику, породившую алерт. В реальной консоли SIEM алерт уже является результатом подобного запроса, оформленным в виде сохранённого правила.

Если используется платформа типа Graylog Security, аналитик может через веб‑интерфейс открыть детали алерта и одним кликом перейти к полнотекстовому поиску сырых сообщений, из которых он собран. Аналогично в Splunk ES рекомендуется открыть «notable event» и использовать вкладку «Contributing Events».

**Ошибки и подводные камни**:

* Ложная уверенность в том, что алерт «всегда правильный». Механизмы корреляции часто дают сбои при неполной нормализации данных (например, доменное имя вместо имени хоста).
* Слишком большое количество алертов (alert fatigue). Если политика не предполагает тюнинг порогов, L1 может пропустить важный инцидент.
* Игнорирование ссылок на исходные события. Без погружения в сырые логи аналитик рискует сделать неверное заключение.

## 4. Сквозной практический пример: брутфорс‑атака по RDP с эскалацией

**Исходные условия.** Инфраструктура включает контроллер домена Windows Server 2022, на котором поднят сервер терминалов (RDP, порт 3389). Журналы безопасности с сервера пересылаются в SIEM агентом Winlogbeat. На уровне ядра сети зеркалирующий порт подаёт трафик на сенсор Corelight/Zeek, который пишет структурированные `conn.log` и `rdp.log` в ту же SIEM‑платформу. Настроено правило корреляции: если за 5 минут фиксируется более 10 событий Event ID 4625 с одного IP, генерируется алерт severity «High». Аналитик первой линии — оператор SOC, использующий консоль SIEM.

**Шаг 1. Получение алерта.** В консоли SIEM появляется алерт, подобный описанному в разделе 2.3. Его JSON‑представление, доступное через API, содержит ссылки на исходные записи. Аналитик открывает детали алерта и видит агрегированную информацию:

```json
{
  "alert_id": "alert-d4c3b2a1-9876-54fe-ba98-76543210fedc",
  "rule_name": "Excessive RDP login failures",
  "severity": "High",
  "triggered": "2025-05-10T14:33:10.000Z",
  "attacker_ip": "192.168.50.12",
  "target": "SRV-APP01 (192.168.15.10)",
  "failed_attempts": 47,
  "event_ids": ["1837521","1837522",...,"1837567"]
}
```

Поле `failed_attempts=47` явно превышает порог, и алерт не похож на тестовый, так как IP принадлежит внешнему для организации сегменту.

**Шаг 2. Проверка сырых записей журнала.** Для подтверждения аналитик выполняет drill‑down к логам Security. В SIEM это выглядит как запрос по `EventRecordID` либо временному окну. Воспроизведём эквивалентную команду PowerShell на целевом сервере (в реальности аналитик использует SIEM‑интерфейс):

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625; StartTime=(Get-Date).AddMinutes(-10)} | Where-Object { $_.Properties[19].Value -eq '192.168.50.12' } | Format-Table TimeCreated, @{L='Account';E={$_.Properties[6].Value}}, @{L='LogonType';E={$_.Properties[10].Value}}
```

Пример вывода:

```text
TimeCreated           Account  LogonType
-----------           -------  ---------
10.05.2025 14:28:03   Administrator    10
10.05.2025 14:28:05   admin             10
10.05.2025 14:28:06   jdoe              10
... (всего 47 строк)
```

Видно, что перебираются различные учётные записи (`Administrator`, `admin`, `jdoe`), причём `LogonType=10` указывает на удалённый интерактивный вход (RDP). Это классический брутфорс.

**Шаг 3. Подтверждение сетевым трафиком.** Чтобы исключить сценарий подмены логов (хотя в данном случае это маловероятно), аналитик обращается к network evidence — Zeek‑логам. В SIEM он выполняет поиск по IP‑источнику `192.168.50.12`:

```bash
cat conn.log | awk -F '\t' '$4=="192.168.50.12" && $6==3389 {print $1,$4,$6,$9,$14,$15}'
```

Результат:

```text
1715334483.151234 192.168.50.12 3389 tcp S0 0
1715334484.201111 192.168.50.12 3389 tcp S0 0
1715334485.301234 192.168.50.12 3389 tcp S0 0
...
```

Здесь `S0` означает, что Zeek зафиксировал SYN‑пакеты без ответного SYN‑ACK (возможно, таймаут или сброс). Это коррелирует с неудачными попытками входа. Количество записей с `S0` примерно совпадает с числом событий 4625. Дополнительно аналитик может запросить `rdp.log`, где будет видно поле `result` с значением `fail`.

**Шаг 4. Эскалация и выводы.** Убедившись, что атака реальна, аналитик L1 выполняет предписанные процедуры: временная блокировка IP на межсетевом экране, проверка учётных записей на предмет компрометации, фиксация тревоги в тикет‑системе и эскалация на L2 для глубинного анализа хоста. Через 10 минут алерт закрывается с соответствующим комментарием.

**Демонстрация ценности трёх форм.** Благодаря алерту оператор мгновенно сфокусировался на угрозе. Записи журнала позволили увидеть перебираемые учётные записи и удостовериться, что атака идёт по RDP. Сетевой трафик подтвердил, что соединения действительно имели место от указанного IP, исключив вероятность подлога локальных логов. Таким образом, три формы представления — алерт, лог, трафик — замкнули цикл верификации.
