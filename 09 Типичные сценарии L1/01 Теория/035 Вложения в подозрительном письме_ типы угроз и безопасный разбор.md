# Вложения в подозрительном письме: типы угроз и безопасный разбор

## Классификация угроз, реализуемых через вложения электронной почты

Электронная почта остаётся доминирующим вектором начальной компрометации: по данным ежегодных отчётов Verizon DBIR и Proofpoint, более 90 % целевых атак содержат фишинговый компонент, а вложение является ключевым носителем вредоносной нагрузки. В контексте SOC L1 под вложением понимается любая MIME-часть письма, отмеченная заголовком `Content-Disposition: attachment` или `Content-Type`, указывающим на передачу файла. Угрозы, передаваемые через вложения, неоднородны и различаются по механизму активации, требуемым условиям выполнения и наблюдаемым артефактам. Ниже представлена классификация, охватывающая все основные категории, с которыми аналитик уровня L1 сталкивается при сортировке алертов песочницы или антивирусного шлюза.

| Тип угрозы | Описание | Характерные форматы | Основной механизм | Индикаторы на уровне вложения |
|------------|----------|---------------------|-------------------|-------------------------------|
| Вредоносный исполняемый файл (троян, бэкдор, шифровальщик) | Автономный PE/ELF-файл, выполняющий вредоносную логику после запуска пользователем | `.exe`, `.dll`, `.scr`, `.bat`, `.com`, `.elf` в архиве или переименованные в `.jpg`, `.pdf` с двойным расширением | Прямой вызов функции WinMain/main; может быть упакован (UPX, Themida) или полиморфен | PE-заголовок (MZ), аномальная энтропия секций, высокая доля неизвестных детектов на VirusTotal |
| Документ с макросом (VBA, XLM) | Офисный документ, содержащий автозапускаемый макрос, загружающий или исполняющий полезную нагрузку | `.docm`, `.xlsm`, `.pptm`, `.doc` (OLE2 с макросом), `.xls` (Excel 4.0 macro sheet) | Событие AutoOpen/Document_Open/Workbook_Open; старые форматы — автозапуск XLM-макроса | Наличие потоков `Macros/VBA/_VBA_PROJECT`; флаг `M=YES` в oleid; обфусцированный VBA-код с вызовами `Shell`, `WScript.Shell`, `CreateObject` |
| Документ с эксплойтом (без макроса) | Файл, использующий уязвимость в парсере формата для выполнения произвольного кода (CVE-2017-11882 Equation Editor, CVE-2018-0802) | `.docx`, `.rtf`, `.xlsx`, `.pdf` | Специально сформированная структура документа вызывает переполнение буфера или порчу памяти, передавая управление шелл-коду | Нестандартные поля в OLE-структуре, аномальные размеры объектов, наличие подозрительного шелл-кода в теле документа |
| Скрипт (VBS, JS, PowerShell, HTA) | Файл сценария, исполняемый интерпретатором Windows Script Host или PowerShell напрямую либо через ярлык | `.vbs`, `.js`, `.ps1`, `.hta`, `.wsf` | Двойной клик или вызов из другого процесса; часто обфусцирован, загружает полезную нагрузку по URL | Строки eval, base64-декодеры, обфускация строк, обращение к WMI, WinHTTP, MSXML |
| Ярлык (.lnk) с вредоносной командной строкой | Ярлык Windows, в поле цели которого прописана команда, запускающая скрипт или исполняемый файл | `.lnk` | При открытии папки в проводнике или клике по ярлыку выполняется `cmd.exe /c ...` | Поле LinkInfo с командой, включающей `cmd`, `powershell`, `mshta`, пути к временным папкам |
| ISO/IMG/VHDX образ | Образ диска, монтируемый в Windows как виртуальный привод; содержит исполняемый файл или скрипт, часто скрытый от AV-сканирования содержимого | `.iso`, `.img`, `.vhd` | Автозапуск отключён, но пользователь вручную запускает файл из смонтированного образа; обход сканирования «на лету» | Файловая система внутри образа, отсутствие цифровой подписи, имитация установщика |
| Архив с паролем | ZIP/RAR/7z архив, защищённый паролем, который сообщается в теле письма; обходит контентные фильтры | `.zip`, `.rar`, `.7z` | Пользователь вводит пароль и извлекает вредоносный объект; шлюз не может проверить содержимое | Пароль в теле письма, архив содержит PE-файл или документ с макросом |
| Многоуровневый архив (сжатие бомба) | Глубоко вложенная структура архивов или архив с очень большим коэффициентом сжатия, направленная на истощение ресурсов сканера | `.zip` с вложенностью 100+, `.tar.gz` с большим файлом нулей | Распаковка требует аномально много времени/памяти, что приводит к отказу или обходу сканирования | Глубина вложенности > 20, суммарный размер > 100 МБ при сжатии в 1 МБ |
| HTML-вложение с формой фишинга | Локальный HTML-файл, отображающий поддельную страницу аутентификации, собирающую учётные данные | `.html`, `.htm` | Открывается в браузере, отправляет данные через POST на управляемый злоумышленником сервер | Форма с action на внешний домен, скрытые поля, JavaScript для обфускации |

При анализе подозрительного письма L1-специалист должен уметь сопоставить расширение и `Content-Type` MIME-части с одним из перечисленных классов, чтобы выбрать корректный инструментарий и оценить потенциальный ущерб. Отдельно стоит отметить, что вложения могут использоваться не только для доставки вредоносного кода, но и для фишинга учётных данных (HTML-формы), социальной инженерии (фальшивые счета) или обхода многофакторной аутентификации (файл-подделка). Таким образом, классификация является базисом для дальнейшего безопасного разбора.

## Внутренняя структура и жизненный цикл вредоносного вложения

Чтобы понимать, почему одни вложения опаснее других и какие артефакты они оставляют, необходимо рассмотреть, как устроены ключевые форматы и как злоумышленники внедряют в них вредоносную нагрузку. В данном разделе предметом анализа становится само вложение как носитель угрозы: от MIME-кодирования до исполнения payload в памяти целевой системы. Обобщённо обработка вложения в почтовом потоке выглядит следующим образом (иллюстративная схема взаимодействия агентов):

```text
[Отправитель] -> (SMTP) -> [MTA/шлюз] -> [Почтовый сервер] -> [Клиент (Outlook/OWA)]
                                     |
                      [Антивирус/песочница] -> [SOC L1: алерт/ручной анализ]
```

На этапе передачи вложение представляется в виде MIME-части, закодированной base64 или quoted-printable. Пример разметки для документа Microsoft Word:

```
Content-Type: application/msword; name="invoice.doc"
Content-Transfer-Encoding: base64
Content-Disposition: attachment; filename="invoice.doc"
```

После декодирования мы получаем файл, внутренняя структура которого определяет возможные векторы атаки. Рассмотрим основные форматы и их эксплуатационные особенности, обобщённые в таблице ниже. Таблица фиксирует не только тип формата, но и элементы, непосредственно используемые злоумышленником.

| Формат | Используемые структурные элементы | Техника злоумышленника | Типовые артефакты, обнаруживаемые при статическом анализе |
|--------|-----------------------------------|------------------------|-----------------------------------------------------------|
| OLE2 (doc, xls) | Хранилище `Macros/VBA`, поток `_VBA_PROJECT`, свойства документа | VBA-макрос с AutoOpen, обфусцированный код, загрузка шелл-кода через `CreateObject("WScript.Shell")`, `Shell()` | oleid: "VBA Macros" = YES; olevba: строки `AutoOpen`, `Document_Open`, подозрительные вызовы WinAPI, высокая энтропия в строках |
| OOXML (docx, xlsx) | Часть `word/vbaProject.bin` в ZIP-контейнере, файл `xl/worksheets/sheet1.xml` для XLM-макросов | Внедрение VBA-проекта в новый формат, активация через событие; Excel 4.0 макросы — скрытые листы с XLM-кодом | Наличие `vbaProject.bin`; XML-теги `<sheet ... state="hidden">`, формулы типа `EXEC`, `CALL`, `REGISTER` |
| PDF | Объекты `/JavaScript`, `/JS`, `/OpenAction`, `/AA`, `/EmbeddedFile`, `/RichMedia` | Вставка JavaScript, выполняющегося при открытии (CVE-2021-28550 для Adobe Reader), эксплуатация уязвимостей в парсерах шрифтов, встроенные исполняемые файлы | pdfid: `/JS > 0`, `/OpenAction > 0`; наличие `/EmbeddedFile` с PE-сигнатурой; подозрительные URI в `/URI` |
| RTF | Управляющие слова `\objupdate`, `\objdata` для внедрения OLE-объектов | Внедрение Equation Editor (CVE-2017-11882) или упакованных OLE-объектов с шелл-кодом | rtfobj.py показывает OLE-объекты с CLSID Equation.3 или нетипичными CLSID; наличие hex-блоков с подозрительной энтропией |
| PE (exe, dll) | PE-заголовок (MZ), секции `.text`, `.data`, ресурсы, таблица импорта | Упаковка/обфускация, внедрение шелл-кода в ресурсы, подмена точки входа (EP) | Сигнатуры упаковщиков (UPX0, UPX1); нестандартные имена секций; импорт `VirtualAlloc`, `WriteProcessMemory`, `CreateRemoteThread` |
| Скрипты (vbs, js, ps1) | Текстовые строки, кодировка (UTF-16LE для VBS), автозапуск через `WScript.Shell` | Обфускация с помощью `Chr()`, `eval`, base64-декодирование, загрузка с удалённого URL | Строки с `eval`, `Execute`, `ActiveXObject`, высокая доля вызовов кодировочных функций; URL с нетипичным TLD |
| LNK | ShellLinkHeader, LinkTargetIDList, поле `COMMAND_LINE_ARGUMENTS` | Подстановка команды `%comspec% /c start powershell...` в цель ярлыка; иконка подменена для имитации документа | В структуре ярлыка обнаружены строки `cmd.exe`, `powershell`, `-enc`; размер поля аргументов аномально велик |
| ISO/IMG | Файловая система (ISO9660/UDF), загрузочный сектор отсутствует, внутри — исполняемый файл | Создаётся ISO с единственным PE-файлом; пользователь монтирует и запускает, думая, что открывает документ | 7z l показывает .exe внутри; `file` определяет как ISO 9660; внутри нет ожидаемого содержимого документа |

Эта таблица даёт аналитику SOC L1 основу для выбора инструмента статического анализа. Например, увидев файл `.doc` с высоким риском по oleid, специалист запускает olevba для извлечения макроса и проверки на обфусцированные вызовы. Понимание структурных элементов позволяет не только обнаружить известные угрозы, но и идентифицировать аномалии, характерные для новых векторов (скажем, использование DDE-функций в Excel без макросов). 
Механизм активации угрозы зачастую требует взаимодействия пользователя: открытие файла, нажатие «Enable Editing», ввод пароля архива. Однако современные атаки эксплуатируют доверенные отношения (например, подписанные макросы, похищенные сертификаты) или уязвимости, срабатывающие при предварительном просмотре в почтовом клиенте. Поэтому безопасный разбор должен проводиться в изолированной среде, исключающей случайную активацию.

## Методология безопасного разбора вложений на уровне SOC L1

Безопасный разбор вложения — это последовательность операций, выполняемых аналитиком первого уровня для подтверждения или опровержения вредоносной природы файла без риска компрометации рабочей станции или корпоративной сети. Методология опирается на принцип «изоляция-статический анализ-динамический анализ-корреляция» и использует как автоматизированные средства (песочницы), так и ручные утилиты.

**1. Подготовка изолированной среды.**  
Анализ производится на выделенной виртуальной машине, не имеющей сетевого доступа к корпоративному окружению, или на аир-гапнутом хосте. В качестве гостевой ОС используется стандартная конфигурация с антивирусным мониторингом (ClamAV, Windows Defender в режиме аудита) и инструментарием анализа. Все операции с подозрительным файлом выполняются внутри этой среды; передача файла на рабочую станцию запрещена. Рекомендуется использовать снапшоты ВМ для быстрого восстановления.

**2. Извлечение вложения из письма.**  
Письмо сохраняется в формате `.eml` (RFC 5322) или `.msg` (Microsoft Outlook). Извлечение вложений выполняется утилитами, которые разбирают MIME-структуру. Пример для Linux-среды:

```bash
munpack -t /tmp/analysis sample.eml
```

Вывод (иллюстративная схема):
```
invoice.docm (application/vnd.ms-word.document.macroEnabled.12)
```

Если письмо содержит несколько вложений, каждое извлекается в указанную директорию. Для `.msg`-файлов можно применить `libmsg` или `msgconvert` из пакета `Email::Outlook::Message`. После извлечения файл помещается в карантинную директорию.

**3. Идентификация типа файла.**  
Расширение не является надёжным индикатором, поэтому первым шагом статического анализа является определение типа по сигнатуре (magic bytes) с помощью утилиты `file`:

```bash
file invoice.docm
```
Вывод:
```
Composite Document File V2 Document, Little Endian, ... (может показать OLE2 или ZIP для docx)
```

Для Windows-среды аналог — `TrID`. Это позволяет выявить несоответствие между заявленным расширением и реальным форматом (например, `.pdf` оказывается PE-файлом).

**4. Статический анализ на известные индикаторы.**  
На этом этапе применяются сигнатурные сканеры и специализированные анализаторы без выполнения кода.

- **Проверка антивирусом (ClamAV):**
  ```bash
  clamscan --max-filesize=100M --max-scansize=100M invoice.docm
  ```
  Вывод (положительный):
  ```
  invoice.docm: Doc.Dropper.Agent-1234567 FOUND
  ```

- **Проверка хэша на VirusTotal (с осторожностью):**  
  *Примечание: отправка файла целиком может раскрыть конфиденциальные данные. В SOC L1 предпочтительно загружать только хэш-сумму, если политика разрешает.*  
  ```bash
  sha256sum invoice.docm
  ```
  Полученный хэш проверяется через API или веб-интерфейс. Отчёт содержит сведения о детектах и поведении.

- **Анализ OLE-документов с помощью oletools:**  
  Утилита `oleid` даёт быструю оценку риска:
  ```bash
  oleid invoice.docm
  ```
  Вывод (рисковый файл):
  ```
  Indicator: VBA Macros -> YES
  Indicator: Suspicious keywords -> YES
  ```
  Для извлечения и декодирования VBA-макроса используется `olevba`:
  ```bash
  olevba --deobfuscate invoice.docm
  ```
  Вывод покажет обфусцированный код, часто содержащий вызовы `Shell("powershell -enc ...")` или `CreateObject("MSXML2.XMLHTTP")`.

- **Анализ PDF:** `pdfid.py invoice.pdf` показывает количество объектов `/JS`, `/OpenAction`. При наличии JavaScript применяется `peepdf` для извлечения и обезвреживания.

- **Проверка ярлыков:** `lnkinfo` или `exiftool` выявляет аномальные командные строки в LNK-файле.

- **Поиск по YARA-правилам:**  
  SOC часто имеет набор сигнатур для известных вредоносных семейств. Пример запуска:
  ```bash
  yara -s rules/malware.yar invoice.docm
  ```
  Вывод:
  ```
  Malware_Generic_VBA_obfuscation invoice.docm
  0x14a3c:$a: PowerShell
  ```

**5. Динамический анализ (песочница).**  
Если статический анализ не дал однозначного вердикта, файл запускается в контролируемой среде. Для SOC L1 чаще всего используется автоматическая песочница (Cuckoo Sandbox, Any.Run, VMRay) или локальная ВМ со средствами мониторинга (ProcMon, Wireshark, RegShot). Процесс:

- Копирование файла в гостевую ОС, подключённую к изолированной сети.
- Запуск с типичными действиями пользователя (открытие в Office с включёнными макросами).
- Мониторинг: создаваемые процессы, сетевые соединения, изменения файловой системы и реестра.
- Сбор индикаторов компрометации (IoC): IP-адреса C2, URL загрузки, мутации файлов, имена созданных служб.

Автоматизированные отчёты песочницы предоставляют вердикт и поведенческие признаки, которые аналитик L1 сопоставляет с известными паттернами.

**6. Корреляция и эскалация.**  
На основе собранных артефактов (хэши, URL, IP, ключевые строки) аналитик проверяет, наблюдались ли подобные индикаторы в SIEM-системе или логах конечных точек. Если факт вредоносной активности подтверждён, создаётся инцидент с детальным описанием и эскалируется на L2/L3 для реагирования (изоляция хоста, блокировка IoC). В противном случае файл помещается в чёрный список локального антиспам-фильтра.

Ключевыми ошибками, которых следует избегать: запуск подозрительного файла на рабочей станции, использование общей папки для обмена образцами, открытие вложений в продуктивных почтовых клиентах даже в режиме «только чтение», пренебрежение проверкой на несоответствие расширения реальному типу.

## Сквозной практический пример: анализ фишингового письма с документом .docm, содержащим макрос

**Исходные условия.**  
В почтовый ящик пользователя поступило письмо от якобы контрагента с темой «Срочно оплатить счет до 15.03». Во вложении находится файл `Invoice_230315.docm`. Письмо сохранено аналитиком SOC L1 в формате `.eml` и перемещено на изолированную виртуальную машину с Ubuntu 22.04 и установленным пакетом `oletools`, `munpack`, `yara`, `clamav`. Виртуальная машина не имеет сетевого доступа, кроме VPN-туннеля к песочнице.

**Шаг 1. Извлечение вложения из EML-файла.**  
Команда:
```bash
munpack -t /home/analyst/sample.eml
```
Ожидаемый вывод (иллюстративная схема):
```
Invoice_230315.docm (application/vnd.ms-word.document.macroEnabled.12)
```
В текущей директории создан файл `Invoice_230315.docm`.

**Шаг 2. Первичный анализ типа и сигнатурная проверка.**  
Определяем реальный тип:
```bash
file Invoice_230315.docm
```
Вывод:
```
Composite Document File V2 Document, Little Endian, Os: Windows, Version 6.3, Code page: 1252, ...  (OLE2, вероятно, с макросами)
```
Запускаем ClamAV:
```bash
clamscan Invoice_230315.docm
```
Вывод:
```
Invoice_230315.docm: Win.Malware.Generic-9876543 FOUND
```
Сигнатурный детект подтверждает вредоносность, но для полноты анализа продолжим.

**Шаг 3. Детальный анализ OLE-структуры.**  
Используем `oleid`:
```bash
oleid Invoice_230315.docm
```
Вывод:
```
Filename: Invoice_230315.docm
Indicator: VBA Macros -> YES
Suspicious keywords -> YES
Risk: HIGH
```
Далее декомпилируем макрос:
```bash
olevba Invoice_230315.docm
```
Фрагмент вывода (обфусцированный код):
```vb
Sub AutoOpen()
  Dim objShell As Object
  Set objShell = CreateObject("WScript.Shell")
  objShell.Run "pow" & "ersh" & "ell -e " & "JABhAD0AKABHAGUA..."
End Sub
```
Макрос при открытии запускает PowerShell с base64-закодированной командой. Закодированная строка может быть декодирована вручную или автоматически `olevba --deobfuscate`, но уже виден признак вредоносной активности.

**Шаг 4. Проверка по YARA-правилам.**  
Применяем правило для VBA-дропперов:
```bash
yara -s /opt/soc/yara/rules/malware_vba.yar Invoice_230315.docm
```
Вывод:
```
VBA_CreateObject_WshShell Invoice_230315.docm
0x001a4f:$s: WScript.Shell
VBA_Base64_Decode Invoice_230315.docm
0x001b2e:$b: FromBase64String
```
Таким образом, статический анализ однозначно подтверждает присутствие вредоносного макроса-загрузчика.

**Шаг 5. Динамический анализ в песочнице (опционально).**  
Файл загружается в локальную Cuckoo Sandbox или Any.Run (если политика разрешает) для извлечения индикаторов. Отчёт песочницы показывает:
- Создание процесса `powershell.exe` с аргументом `-enc JABhAD0AKABHAGUA...`
- Установка исходящего соединения на `203.0.113.45:443`
- Загрузка исполняемого файла `payload.exe` во временную папку и его запуск.
- Регистрация в автозагрузке.

Собранные IoC: IP-адрес C2 `203.0.113.45`, URL загрузки `https://evil.example.com/update.dll`, хэш SHA256 дроппера `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. Эти индикаторы передаются для блокировки и дальнейшего расследования.

**Ожидаемый вывод.**  
Пример демонстрирует полный цикл работы аналитика SOC L1 с подозрительным вложением: от изолированного извлечения до выявления конкретных IoC. Подобный подход позволяет минимизировать риски и обеспечивает воспроизводимость результатов. Даже если бы ClamAV не обнаружил угрозу, структурный анализ и поиск аномалий в макросе (обфускация, вызов PowerShell) позволили бы идентифицировать атаку без исполнения кода.
