# Аномальный вход в систему в практике SOC L1

## 1. Аномалии входа как приоритетный сигнал для аналитика первой линии

События входа в систему — один из самых информативных источников данных для мониторинга безопасности. В SOC L1 аномальный вход (anomalous logon) трактуется как событие успешной или неуспешной аутентификации, характеристики которого существенно отклоняются от устоявшейся поведенческой модели субъекта (пользователя, сервисной учётной записи) или от стандартных параметров среды. Аномальность не обязательно означает злонамеренность; задача аналитика L1 — провести первичную сортировку, исключить ложные срабатывания и предоставить контекст для эскалации на уровень L2, если инцидент подтверждается.

Понятие аномального входа стоит отделять от смежных категорий, с которыми оно пересекается, но не совпадает по объёму. Ниже приведена сравнительная таблица, фиксирующая разграничение ключевых понятий, используемых при триаже событий входа.

| Понятие | Сущность | Индикаторы, типичные для SOC | Пример контекста |
|----------|----------|-------------------------------|-------------------|
| **Failed logon (неуспешный вход)** | Единичная или множественная неудачная попытка аутентификации. Фиксируется как Event ID 4625 (Windows), сообщение `Failed password` в auth.log (Linux). | Высокая частота за короткий интервал, перебор пользователей, нетипичная рабочая станция. | Несколько попыток с одного IP подряд под одним пользователем. |
| **Brute force (перебор паролей)** | Автоматизированный подбор учётных данных путём множественных попыток входа, обычно с одного или нескольких источников. | Десятки/сотни 4625 за минуту, Event ID 4771 (Kerberos pre-auth failure) на контроллере домена, рост количества блокировок учётных записей. | Атака через открытый RDP или OWA, направленная на конкретного пользователя или список. |
| **Password spray** | Разновидность атаки, при которой один или несколько распространённых паролей испытываются на множестве пользователей с низкой частотой во избежание блокировок. | Одиночные 4625 на множество имён пользователей с одного IP с периодичностью раз в несколько минут, отсутствие тренда на одного пользователя. | Попытка входа с паролем "Winter2023!" для десятков учётных записей за ночь. |
| **Impossible travel** | Два успешных входа, зафиксированных с географически удалённых IP за промежуток времени, физически недостаточный для перемещения между ними. | Два Event ID 4624 с разницей в минуты из стран, разделённых океаном, при отсутствии корпоративного VPN или использования облачных промежуточных узлов. | Первый вход из Москвы, через 5 минут вход из Сиднея под той же учётной записью. |
| **Anomalous logon (аномальный вход)** | Общее понятие, охватывающее любые события входа, параметры которых (время, IP, геолокация, тип входа, процесс, частота) не соответствуют историческому профилю пользователя, группы или хоста. | Срабатывание UEBA-модели, ручное обнаружение при проверке: вход с нового устройства, LogonType 10 вне пределов служебной VPN-подсети, успешный вход после серии отказов. | Субботний вход бухгалтера с домашнего IP на сервер терминалов, хотя по baseline его активность строго в будни с офисного диапазона. |

Аномальный вход — это, по сути, родовое понятие, которое может включать в себя и impossible travel (как одну из форм аномалии), и признаки атаки после password spray, и необычное время активности. В SOC-процессах к категории аномальных относят события, требующие контекстного анализа, потому что ни одна сигнатура не даёт однозначного вывода о вредоносности. Именно поэтому разбор аномального входа относят к типичным сценариям L1.

Источники информации для анализа поступают из журналов операционных систем, средств аудита домена, облачных провайдеров и VPN-концентраторов. В Windows-средах центральное место занимают журналы безопасности (Security Event Log) с событиями:

- **4624**: успешный вход (Logon Type указывает способ);
- **4625**: отказ входа (Status/Sub Status — причина);
- **4648**: попытка входа с явными учётными данными (RunAs);
- **4771**: сбой предварительной аутентификации Kerberos;
- **4768**: выдан TGT, с IP-адресом клиента.

В Linux /var/log/auth.log и /var/log/secure фиксируют сообщения от sshd, sudo, login с указанием имени пользователя, исходного IP, метода аутентификации (password, publickey) и статуса. Облачные журналы (Azure AD Sign-in Logs, AWS CloudTrail) предоставляют обогащённые данные: геолокацию, тип устройства, условный доступ, идентификатор сессии.

Для аналитика L1 аномальный вход — это не только единичный алерт, но и запись, подлежащая выяснению обстоятельств через корреляцию. В современных SOC широко применяются User and Entity Behavior Analytics (UEBA), формирующие baseline по пользователям на основе истории входов за 30–90 дней. Если новый вход выбивается из baseline, система генерирует алерт с risk score, например: «Пользователь jdoe впервые выполнил RemoteInteractive вход с IP, не входящего в корпоративный пул». Система сама подсвечивает аномальные аспекты, ускоряя триаж. Аналитик, в свою очередь, должен понимать логику работы таких детектов и уметь перепроверять их выводы, особенно в случаях, когда baseline искажён (долгий отпуск, смена проекта).

## 2. Структура событий входа: поля, формирующие индикаторы аномалий

Ключ к пониманию аномального входа — знание структуры журналируемого события. Каждая запись о входе содержит фиксированный набор полей, значения которых либо в точности, либо в комбинации создают сигнал аномалии. Рассмотрим детально формат событий на примере Windows Event ID 4624, как наиболее универсального для доменных сред.

Запись 4624 в формате XML включает разделы: **System** (метаданные) и **EventData** (параметры входа). На уровне SIEM поля обычно парсятся в плоскую структуру. Иллюстративная схема полей в JSON-подобном представлении, используемом в Splunk/Sentinel после нормализации:

```json
{
  "EventID": 4624,
  "System": {
    "Computer": "workstation01.contoso.com",
    "TimeCreated_SystemTime": "2024-11-22T03:14:07Z",
    "Channel": "Security",
    "RecordID": 1234567
  },
  "EventData": {
    "SubjectUserSid": "S-1-5-18",
    "SubjectUserName": "WORKSTATION01$",
    "SubjectLogonId": "0x3e7",
    "TargetUserSid": "S-1-5-21-...-1145",
    "TargetUserName": "jdoe",
    "TargetLogonId": "0x123abc",
    "LogonType": 10,
    "LogonProcessName": "User32",
    "AuthenticationPackageName": "Negotiate",
    "IpAddress": "203.0.113.5",
    "IpPort": "49321",
    "WorkstationName": "DESKTOP-XYZ",
    "LogonGuid": "{GUID}",
    "TransmittedServices": "-",
    "LmPackageName": "-",
    "KeyLength": 0,
    "ProcessId": "0x4b8",
    "ProcessName": "C:\\Windows\\System32\\svchost.exe"
  }
}
```

Каждое из выделенных полей может служить основанием для оценки аномальности:

- **SubjectUserSid/SubjectUserName**: инициатор входа (обычно SYSTEM или сетевая служба). Нетипичный Subject, например, локальная учётная запись, инициирующая сетевой вход, может быть признаком атаки типа silver ticket.
- **TargetUserName**: имя пользователя, под которым производится вход. Интерес представляет наличие неиспользуемых учётных записей, административных учёток в нецелевых системах, или вход от имени krbtgt.
- **LogonType** (код типа входа) — одна из важнейших характеристик, отражающая способ взаимодействия с системой. Полный перечень типов с их интерпретацией:

| LogonType | Наименование             | Типичный сценарий                | Аномалии для мониторинга |
|-----------|--------------------------|----------------------------------|---------------------------|
| 2         | Interactive              | Физический вход за консолью       | Появление на серверах, где это запрещено |
| 3         | Network                  | Доступ к общим папкам, WinRM     | Вход с несерверных IP на DC |
| 4         | Batch                    | Планировщик заданий               | Фоновый вход под админом без сопутствующего события 4674 |
| 5         | Service                  | Запуск службы                     | Подозрительная служба, запущенная с пользовательским контекстом |
| 7         | Unlock                   | Разблокировка рабочей станции     | Вход после длительного простоя вне рабочих часов |
| 8         | NetworkCleartext         | Аутентификация с передачей пароля открытым текстом (IIS, некоторые сторонние) | Факт использования незашифрованной передачи |
| 9         | NewCredentials           | RunAs / разные учётные данные      | Запуск процесса под другими данными без переключения сеанса |
| 10        | RemoteInteractive        | RDP, Remote Assistance            | Появление на рядовых рабочих станциях от непривилегированных пользователей, вход из нетипичных стран |
| 11        | CachedInteractive        | Вход с кэшированными учётными данными, когда DC недоступен | Может указывать на попытку локального входа после компрометации, особенно на ноутбуках вне корпоративной сети |
| 12        | CachedRemoteInteractive  | RDP с кэшированными учётными данными | Редко встречается, но аналогично type 11 |
| 13        | CachedUnlock             | Разблокировка с кэшированными данными | Аналогично type 11 |

- **LogonProcessName** и **AuthenticationPackageName**: указывают на механизм (NTLM, Kerberos, Negotiate). Например, вход с NTLM на доменном контроллере может быть подозрительным, если политика требует исключительно Kerberos.
- **IpAddress**: исходный IP клиента. Именно с этим полем работают гео-аномалии, списки Threat Intelligence и проверки на принадлежность внутренним подсетям. Важно учитывать, что для входа через VPN в логах может фигурировать внутренний IP VPN-концентратора, поэтому необходима корреляция с VPN-логами для получения реального публичного IP.
- **WorkstationName**: NetBIOS-имя машины, с которой произведён вход. Появление нового или нестандартного имени (например, случайный набор символов) — весомый признак.
- **ProcessId / ProcessName**: идентификатор процесса, обработавшего запрос входа. Например, если LogonType=3, а процесс — неизвестный исполняемый файл, это повод для проверки.
- **LogonId**: идентификатор сеанса входа, используется для связывания событий в рамках одной сессии (например, 4624 → 4672 → 4634).

В Linux-системах аналогом служит запись в auth.log, которая после обработки в SIEM обычно имеет поля: `timestamp, hostname, service (sshd, login), user, src_ip, port, status, method, session_id`. Ключевые метрики аномалий те же, но добавляется специфика: попытки входа с использованием ключей, тогда как по baseline пользователь работает только по паролю, или наоборот.

Облачные журналы, в частности Azure AD Sign-in Logs, предоставляют обогащённые сведения: `UserPrincipalName, IP address, DeviceDetail (operatingSystem, browser), Location (city, state, country), Status (error code), ConditionalAccessStatus, RiskLevelDuringSignIn`. Здесь можно выявить входы с устройств под управлением устаревших ОС, обход условного доступа (например, успешный вход при `MFA requirement not satisfied`), или рискованные входы из анонимных прокси.

Любая автоматизированная система детекта аномалий строит профиль на основе комбинации этих полей. Например, детектор impossible travel вычисляет разницу во времени между двумя 4624 для одного пользователя, смотрит геолокацию IP и оценивает физическую невозможность перемещения, допуская погрешность на VPN и облачные сервисы. Детектор нетипичного рабочего времени сравнивает `TimeCreated` с часами активности за последние 30 дней. Аналитику L1 не обязательно помнить все нюансы формирования baseline, но он должен уметь «прочитать» поля события, сопоставить их с нормой и задать себе контрольные вопросы: «Этот IP когда-либо использовался этим пользователем? От имени SYSTEM или пользователя? Почему LogonType 10 на рабочую станцию бухгалтера?»

## 3. Процедуры и инструменты первичного анализа аномального входа

Работа аналитика L1 с аномальным входом регламентируется плейбуками или стандартными операционными процедурами (SOP). Основная цель — в сжатые сроки либо закрыть алерт как ложный, либо эскалировать, собрав структурированный набор артефактов. Для этого используется арсенал SIEM-запросов, внешних сервисов и локальных скриптов.

**Платформы и язык запросов.** Наиболее распространённые SIEM — Splunk (SPL) и Microsoft Sentinel (KQL). В них накапливаются логи с рабочих станций, контроллеров домена, VPN, облачных провайдеров. Аналитик выполняет поиск по инциденту через заданные временные рамки. Ниже пример типового SPL-запроса для проверки истории входов пользователя за 30 дней и определения, является ли IP новым:

```spl
index=windows EventCode=4624 TargetUserName="jdoe" earliest=-30d
| stats count BY IpAddress
| sort - count
```

Результат покажет все IP и количество успешных входов. Если `203.0.113.5` отсутствует в списке или встречается единично в далёком прошлом, это усиливает подозрение. В Sentinel аналогичный запрос на KQL:

```kql
SecurityEvent
| where EventID == 4624 and TargetUserName == "jdoe"
| where TimeGenerated >= ago(30d)
| summarize count() by IpAddress
| order by count_ desc
```

**Геопривязка и репутация IP.** SIEM часто автоматически обогащают события геолокацией (MaxMind GeoIP). Если же алерт пришёл без таких данных, аналитик может быстро уточнить через командную строку с помощью API сервисов репутации. Иллюстративная команда проверки через AbuseIPDB (без фактического ключа):

```bash
curl -s -G "https://api.abuseipdb.com/api/v2/check" \
  --data-urlencode "ipAddress=203.0.113.5" \
  -H "Key: $ABUSEIPDB_API_KEY" | jq '.data.abuseConfidenceScore, .data.countryCode'
```

Ожидаемый вывод — уровень вредоносности (0–100) и страна. Если IP принадлежит хостинг-провайдеру, а не домашнему диапазону, вероятность атаки выше.

**Корреляция с VPN-логами.** Многие организации маршрутизируют RDP и другие протоколы только через VPN; тогда вход с публичного IP напрямую невозможен, и событие 4624 с внешним IP без предшествующей VPN-сессии — серьёзный инцидент. L1 проверяет наличие сессии пользователя в логах VPN-концентратора за несколько минут до времени входа. Поиск в Splunk:

```spl
index=vpn user="jdoe" earliest=-24h
| table _time, src_ip, dest_port, action
| sort - _time
```

Если записи о VPN-подключении пользователя в последние часы отсутствуют, а `IpAddress` в 4624 — внешний, сценарий эскалируется как подозрение на прямой доступ к внутренней сети (возможно, скомпрометирован публично доступный сервер).

**Анализ цепочки событий.** Одиночное событие 4624 редко бывает показательным. Аналитик ищет сопутствующие события вокруг временной метки и того же LogonId: 4672 (назначение привилегий), 4625 непосредственно перед успешным входом, 4648 с указанием подставленных учётных данных. Пример SPL для ретроспективы за 5 минут до и после:

```spl
index=windows (EventCode=4624 OR EventCode=4625 OR EventCode=4648 OR EventCode=4672) TargetUserName="jdoe" earliest=-5m latest=+5m
| table _time, EventCode, LogonType, IpAddress, WorkstationName, ProcessName
```

Такая выборка может показать паттерн: сначала несколько 4625 (подбор), потом 4624. Повышается приоритет.

**Типовой чек-лист первичного анализа (плейбук L1).**
1. Открыть алерт, записать время и пользователя.
2. Определить тип входа (LogonType) и источник IP.
3. Если IP внешний:
   - проверить геолокацию и соответствует ли она стране присутствия пользователя;
   - проверить наличие VPN-сессии в логах;
   - проверить репутацию IP через Threat Intelligence.
4. Сравнить IP с историей входов пользователя за прошлые 30 дней.
5. Оценить временной контекст: соответствует ли рабочим часам, не праздничный ли день, не отпуск ли у пользователя.
6. Проверить процесс и рабочую станцию: не являются ли они подозрительными.
7. Поискать другие события с тем же LogonId: повышение прав, доступ к чувствительным папкам.
8. Если есть признаки компрометации или невозможно исключить угрозу — эскалировать на L2 с заполненной формой, включающей все собранные поля и скриншоты запросов.

Важно помнить, что L1 не должен выполнять активное воздействие (сброс пароля, отключение учётной записи) без согласования с L2 или сменным руководителем. Его задача — максимально точно описать картину и предоставить данные для принятия решения.

## 4. Внутреннее устройство механизмов аутентификации как фундамент для понимания аномалий

Для точной интерпретации аномальных событий входа необходимо иметь представление о том, как технически протекает процесс аутентификации в среде, где работает SOC. Знание протоколов и этапов помогает объяснить неочевидные комбинации полей и избежать ложных тревог.

Рассмотрим упрощённую схему Kerberos-аутентификации в домене Windows, которая порождает записи 4768 (TGT-запрос) и 4624 (успешный вход с LogonType 3 или 10). ASCII-диаграмма взаимодействия:

```text
Клиентская рабочая станция                     Контроллер домена (DC)                 Целевой сервер
        |                                           |                                    |
        |--(1) TGT-запрос (KRB_AS_REQ)------------->|                                    |
        |                                           |--(2) Проверка pre-auth             |
        |<-(3) TGT-ответ (KRB_AS_REP)---------------|                                    |
        |                                           |                                    |
        |--(4) TGS-запрос (KRB_TGS_REQ)------------->|                                    |
        |<-(5) TGS-ответ (KRB_TGS_REP)--------------|                                    |
        |                                                                                 |
        |-------------(6) AP-запрос (KRB_AP_REQ)---------------------------------------->|
        |<-------------(7) Аутентификация (успех) - в логах целевого сервера Event 4624--|
```

На этапе (1) клиент отправляет запрос с зашифрованной меткой времени. Если предварительная аутентификация не проходит (неверный пароль), DC регистрирует 4771 с кодом ошибки 0x18. Серия таких ошибок — индикатор брутфорс-атаки. Успешный ответ (3) выдаёт TGT и сессионный ключ. Затем (4) запрашивается билет на конкретную службу, и на целевом сервере при предъявлении билета (6) создаётся сессия входа, о чём свидетельствует событие 4624. Важно, что в событии 4624, сгенерированном на целевом сервере, IpAddress будет содержать IP клиента, а не DC. Однако в сценариях делегирования или при использовании удалённого рабочего стола IP может искажаться.

NTLM-аутентификация представляет собой challenge-response и часто отображается как 4624 с LogonType=3, но без предварительного билета Kerberos. В журнале на целевом сервере поле AuthenticationPackageName будет равно «NTLM». Использование NTLM на системах, где возможно применение Kerberos, считается потенциально аномальным (например, при LLMNR/NBT-NS poisoning), и аналитик должен обращать на это внимание.

Тип входа (LogonType) также тесно связан с техническими деталями. Например, LogonType=10 (RemoteInteractive) генерируется службой терминалов, когда пользователь подключается через RDP. При этом в журнале на целевом хосте поле WorkstationName может содержать имя компьютера пользователя (если передаётся), а ProcessName обычно — `C:\Windows\System32\svchost.exe` (запускающий Termsrv). Если в событии с LogonType=10 ProcessName отличается от стандартного или запущен из нестандартного пути, это подозрительно (например, C2-фреймворки часто имитируют RDP-сессию, но порождают несколько иной контекст).

Знание архитектуры позволяет аналитику не плодить ложные эскалации: например, вход сервисной учётной записи с типом 5 (Service) с IP 127.0.0.1 — норма, а такой же вход с внешнего IP — инцидент. События с LogonType=3 от имени пользователя на DC из нестандартной подсети — возможный признак использования украденного хэша для сетевого входа (Pass-the-Hash), что автоматически повышает criticality.

Некоторые продукты UEBA дополнительно анализируют последовательности Kerberos-билетов (Event ID 4769) на наличие аномалий в зашифрованных частях (Silver Ticket), но это уже выходит за рамки первичного триажа. Однако L1 должен узнавать об этих механизмах настолько, чтобы корректно эскалировать подозрительные комбинации.

## Сквозной практический пример: расследование подозрительного входа пользователя `jdoe`

**Исходные условия.**  
SIEM: Splunk, индексирующий журналы безопасности Windows (EventLog) с рабочих станций и серверов, а также логи VPN (Cisco AnyConnect). Правила корреляции срабатывают при обнаружении входа пользователя с нетипичным IP и в нерабочее время. Сегодня в 03:14 UTC поступил алерт UEBA: «Anomalous logon for jdoe: RemoteInteractive from new IP 203.0.113.5 (country: Russia), outside working hours». Рабочие часы пользователя 08:00–18:00 UTC, стандартные IP — корпоративный пул `10.10.0.0/16` через VPN.

Аналитик L1 приступает к проверке согласно плейбуку.

**Шаг 1. Анализ первичного события.**  
В Splunk открыто детальное событие 4624, послужившее триггером:

```json
{
  "EventID": 4624,
  "SystemTime": "2024-11-22T03:14:07Z",
  "Computer": "RDSH-01.contoso.com",
  "EventData": {
    "TargetUserName": "jdoe",
    "LogonType": 10,
    "IpAddress": "203.0.113.5",
    "WorkstationName": "DESKTOP-UNKNOWN",
    "ProcessName": "C:\\Windows\\System32\\svchost.exe",
    "AuthenticationPackageName": "Negotiate",
    "SubjectUserName": "RDSH-01$"
  }
}
```

**Вывод:** пользователь выполнил RDP-подключение к серверу терминалов RDSH-01 с внешнего IP `203.0.113.5`. Поле `SubjectUserName` показывает, что инициатор входа — сам сервер (его учётная запись компьютера), что типично для RDP. Но WorkstationName указан как `DESKTOP-UNKNOWN`, что уже несколько подозрительно (обычно передаётся имя хоста инициатора, часто совпадающее с доменным именем). Проверим IP.

**Шаг 2. Проверка IP через Threat Intelligence.**  
Выполняется запрос к AbuseIPDB через консоль (предположим, скрипт запущен на jump-хосте аналитика):

```bash
curl -s -G "https://api.abuseipdb.com/api/v2/check" \
  --data-urlencode "ipAddress=203.0.113.5" \
  -H "Key: $ABUSEIPDB_API_KEY" | jq '.'
```

Пример вывода:

```text
{
  "data": {
    "ipAddress": "203.0.113.5",
    "abuseConfidenceScore": 87,
    "countryCode": "RU",
    "isp": "HOSTING provider",
    "usageType": "Data Center/Web Hosting/Transit",
    "lastReportedAt": "2024-11-21T22:03:00+00:00"
  }
}
```

**Интерпретация:** IP принадлежит российскому хостинг-провайдеру, имеет высокую вредоносную репутацию. Для сотрудника, работающего из дома, маловероятно использование IP дата-центра. Подозрительность алерта повышается.

**Шаг 3. Сравнение с историей входов.**  
В Splunk выполняется запрос:

```spl
index=windows EventCode=4624 TargetUserName="jdoe" earliest=-30d
| stats count by IpAddress
| where IpAddress!="10.10."  // исключаем внутренние подсети
| sort - count
```

Результат:

| IpAddress      | count |
|----------------|-------|
| 198.51.100.23  | 142   |
| 198.51.100.45  | 89    |
| 203.0.113.5    | 1     |

Два верхних IP — известные домашние диапазоны пользователя (подтверждены в прошлом). Адрес `203.0.113.5` появляется впервые. Это дополнительное подтверждение аномалии.

**Шаг 4. Проверка VPN-сессии.**  
Пользователь должен подключаться через VPN перед доступом к RDSH. Запрос логов VPN:

```spl
index=vpn user="jdoe" earliest=-3h
| table _time, src_ip, action, reason
```

Вывод:

```text
_time                  src_ip          action    reason
2024-11-21 22:14:00    198.51.100.23   success   -
2024-11-22 03:13:45    -               -         -
```

Последняя сессия была завершена в 22:14 предыдущего дня с домашнего IP. В 03:13 сессии нет. Следовательно, вход на RDSH-01 произошёл минуя корпоративный VPN. Это явное нарушение политик доступа и признак возможной компрометации, если только пользователь не получил случайный проброс через облако (что маловероятно).

**Шаг 5. Анализ сопутствующих событий.**  
Ищем события в окрестности времени входа:

```spl
index=windows host="RDSH-01" (EventCode=4624 OR EventCode=4625 OR EventCode=4672) TargetUserName="jdoe" earliest=-10m latest=+10m
| table _time, EventCode, LogonType, IpAddress, Keywords, ProcessName
```

Получено:

```text
_time                   EventCode   LogonType   IpAddress       ProcessName
2024-11-22T03:14:03     4625        10          203.0.113.5     C:\Windows\System32\svchost.exe
2024-11-22T03:14:07     4624        10          203.0.113.5     C:\Windows\System32\svchost.exe
2024-11-22T03:14:12     4672        -           203.0.113.5     -
```

За четыре секунды до успешного входа зафиксирована одна неудачная попытка (Status: 0xC000006D – неверное имя пользователя или пароль). Затем успех, и сразу же событие 4672 (назначение привилегий) — это значит, что данная учётная запись обладает административными правами на RDSH-01 и после входа ей были назначены привилегии (например, SeSecurityPrivilege). Это крайне опасно и повышает критичность до высокого уровня.

**Ожидаемый вывод примера.**  
Собранные артефакты однозначно указывают на несанкционированный доступ: вход с IP, принадлежащего хостинг-провайдеру в РФ, минуя VPN, с единичным предварительным отказом и последующим назначением привилегий. Аналитик L1 оформляет эскалацию на L2 с приложением логов, результатов проверок IP и VPN. Дальнейшие действия (отключение учётной записи, изоляция хоста, запуск IR) выполняются старшей сменой.
