# Анализ подозрительного письма в SOC L1

## Контекст и место анализа писем в рабочем процессе SOC

Анализ подозрительного электронного письма — это структурированный процесс оценки сообщения, поступившего через систему отчётов пользователей или автоматическое детектирование, с целью определить, представляет ли оно угрозу, и принять меры. В SOC уровня 1 (Tier 1) эта задача относится к категории рутинных операций начальной сортировки (triage) и составляет до 25% рабочего времени аналитиков из-за высокой частоты фишинговых атак [Dropzone, Phishing Investigation Challenges]. Ключевое отличие анализа письма от общего алерт-триажа заключается в артефактах: здесь первичный объект — само письмо в формате `.eml` или его метаданные, а не события SIEM или срабатывания EDR.

Следует разграничить сам «анализ подозрительного письма» и смежные процедуры. Под «анализом» понимается техническая экспертиза на стороне SOC: исследование заголовков, вложений, ссылок и контекста доставки. Это не начальная классификация почтовым шлюзом и не полномасштабное расследование инцидента, проводимое аналитиком L2/L3. Задача L1 — за ограниченное время (обычно 10–30 минут на один отчёт) дать обоснованную оценку «зловредное/подозрительное/ложное» и, при необходимости, инициировать эскалацию. На практике путаница часто возникает между понятиями «спам», «graymail», «фишинг» и «BEC», поскольку они имеют сходные внешние признаки, но требуют разной реакции. Ниже приведена классификация, помогающая разграничить эти категории на этапе первичного осмотра.

| Тип угрозы / письма | Описание | Ключевые индикаторы для L1 | Типичный сценарий |
|----------------------|----------|----------------------------|-------------------|
| Массовый фишинг (Phishing) | Рассылка, нацеленная на кражу учётных данных через поддельные страницы входа. | URL с опечатками в домене (typosquatting), обезличенное обращение, срочность, ссылки на IP-адреса или свежезарегистрированные домены. | Пользователь получает письмо якобы от IT-отдела со ссылкой на «продление пароля». |
| Целевой фишинг / BEC | Атака на конкретного сотрудника или финансовый отдел, часто без вредоносных ссылок, с целью мошенничества (поддельный счёт, перевод средств). | Сходство с легитимным отправителем, подмена поля Reply-To, нехарактерная лексика, домен-двойник (lookalike domain). | Письмо от «CEO» с просьбой срочно оплатить счёт; проверка показывает, что Reply-To ведёт на внешний адрес. |
| Вредоносное ПО (Malware delivery) | Письмо с вложением или ссылкой, содержащим исполняемый код, макросы или эксплойты. | Вложение с двойным расширением (`.pdf.exe`), макросы в документах Office, ссылки на скачивание архивов с паролем. | Вложение `invoice.iso` — файл образа диска, обходящий Mark-of-the-Web. |
| Спам / Graymail | Не запрошенные маркетинговые рассылки, новостные подписки, легитимные, но нежелательные письма. | Массовая отправка с известных маркетинговых платформ, наличие ссылок для отписки, отсутствие вредоносной активности в теле письма. | Пользователь ошибочно отправляет на анализ рекламную акцию крупного ритейлера, срабатывает кнопка «Report Phish». |

Такое разграничение важно, потому что эскалация BEC или целенаправленного фишинга требует реагирования в течение минут, тогда как graymail можно закрыть с пояснением пользователю. Аналитик L1, таким образом, выступает фильтром, который снижает нагрузку на старшие линии и ускоряет обработку настоящих инцидентов. Согласно выдержкам, до 70% рабочего времени L1 может уходить на рутинный просмотр отчётов пользователей, если процесс не автоматизирован [Prophet Security, SOC Tiers Explained].

## Внутренняя структура процесса анализа подозрительного письма

Анализ письма в SOC L1 разворачивается как повторяемый конвейер, объединяющий технические проверки и принятие решений. Рассматриваемый процесс не является единичным объектом вроде протокола или алгоритма, а представляет собой методологию, поэтому его внутреннее устройство удобно описывать в виде фаз с чёткими артефактами и точками перехода. Многочисленные методологии (NIST IR, SANS, подходы вендоров) сходятся в том, что центральными остаются четыре этапа: приём и первичная классификация, технический анализ артефактов, оценка воздействия и документирование/эскалация [Sublime Security, Email Triage; LinkedIn Oxford Fredrick; Prophet Security, Phishing Investigation]. Ниже представлена структурная визуализация этих фаз и их взаимосвязей в контексте L1.

```text
[Источник отчёта: пользователь / автоматический детектор]
                │
                ▼
┌──────────────────────────────┐
│ 1. Приём и первичная оценка  │
│ - Получение .eml / заголовков│
│ - Проверка, не обработано ли │
│ - Исключение дубликатов      │
│ - Быстрая категоризация:     │
│   фишинг / BEC / спам        │
└──────────────┬───────────────┘
                │ (если требует анализа)
                ▼
┌──────────────────────────────┐
│ 2. Технический анализ        │
│ ┌───────────────────────────┐│
│ │ a. Анализ заголовков      ││
│ │   - SPF/DKIM/DMARC        ││
│ │   - IP-адреса источников  ││
│ │   - Путь письма           ││
│ │ b. Анализ тела и контента ││
│ │   - Признаки соц. инженерии││
│ │   - Подозрительные ссылки ││
│ │   - Вложения              ││
│ │ c. Инструментальные       ││
│ │    проверки               ││
│ │   - VirusTotal, URLScan,  ││
│ │     песочницы             ││
│ └───────────────────────────┘│
└──────────────┬───────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 3. Оценка воздействия        │
│ - Поиск других получателей   │
│ - Проверка факта переходов   │
│   (click/open)               │
│ - Определение IOC            │
└──────────────┬───────────────┘
                │
                ▼
┌──────────────────────────────┐
│ 4. Решение и реагирование    │
│ - Закрыть как ложное / спам  │
│ - Эскалировать на L2         │
│ - Удалить/поместить в каран- │
│   тин, заблокировать IOCs    │
│ - Уведомить пользователя     │
└──────────────────────────────┘
```

**Фаза 1: Приём и первичная оценка.** Входной точкой служит отчёт пользователя через встроенную в почтовый клиент кнопку «Report Phish», либо сообщение, пересланное на abuse-ящик. Аналитик L1 фиксирует факт поступления в тикетовой системе, извлекает полный исходный код письма (сырой `.eml`) и заголовки. Важно сразу проверить, не было ли аналогичное письмо уже проанализировано коллегой — дублирование отчётов разных пользователей частое явление. Уже на этом этапе по теме письма, отправителю и внешнему виду можно грубо отнести его к одной из категорий таблицы из раздела 1, что ускорит выбор дальнейших шагов.

**Фаза 2: Технический анализ.** Основной объём работы L1 приходится именно сюда. Анализ разбивается на три параллельные ветки.  
*Анализ заголовков* начинается с извлечения цепочки `Received`, поля `From`, `Reply-To`, `Return-Path` и результатов аутентификации `Authentication-Results`, содержащих статусы SPF, DKIM, DMARC. Расхождение между `From` и `Return-Path`, провал DKIM или мягкий fail SPF при подозрительном IP — типичные индикаторы спуфинга. IP-адреса источников проверяются через репутационные сервисы.  
*Анализ тела* выявляет социально-инженерные приёмы: срочность, необычные запросы, имитацию внутренних легитимных процессов. Все URL извлекаются, проверяется структура доменов. Подозрение вызывают домены, зарегистрированные несколько часов назад, длинные случайные поддомены, использование IP-адресов вместо имён.  
*Ветка инструментальных проверок* включает проверку хешей вложений через VirusTotal, Urlscan.io или MalwareBazaar, а также безопасную детонацию в песочнице (Any.Run, Hybrid Analysis, Cuckoo). Для L1 критично не выполнять код на рабочей станции; все исполняемые файлы изолируются.

**Фаза 3: Оценка воздействия.** Если технический анализ подтверждает злонамеренность, L1 инициирует поиск по почтовым логам (например, журналы M365 или Proofpoint) других получателей того же письма. Далее через EDR-инструменты или защищённые шлюзы определяется, были ли совершены переходы по ссылкам или открытия вложений. Это разделяет инциденты на «доставлено без взаимодействия» и «скомпрометировано». Результатом фазы становится список индикаторов компрометации (IOC): домены, URL, хеши файлов, IP-адреса отправителя.

**Фаза 4: Решение и реагирование.** На основе всех данных L1 либо закрывает дело как ложное срабатывание/спам, либо, если подтверждена угроза, эскалирует на L2 с уже готовым пакетом артефактов. Параллельно выполняются немедленные блокирующие действия: письмо удаляется из ящиков всех получателей через административные инструменты почтовой системы, IOC вносятся в чёрные списки шлюза, пользователи уведомляются. Вся цепочка документируется в SOAR или тикетовой системе для последующего аудита. Автоматизация этих шагов через AI/ML (классификаторы, автообогащение) значительно сокращает ручную работу; современные платформы, такие как Sublime Security или Prophet AI, могут автономно выполнять фазы 1–3 и предлагать решение, оставляя L1 функцию контроля [Sublime, Email Triage; Prophet, Phishing Investigation].

## Практические методы и инструменты анализа для аналитика L1

В реальной работе SOC Tier 1 использует комбинацию ручных технических приёмов и автоматизированных помощников. Приоритетом является скорость и безопасность: ни одна ссылка не открывается на рабочей машине, ни одно вложение не запускается вне песочницы. Для каждого типа артефакта существует проверенный набор команд и утилит, знание которых обязательно для начинающего специалиста.

**Работа с заголовками.** Первым действием является извлечение полного дампа заголовков. В почтовых клиентах это делается через меню «Показать оригинал»; в Unix-среде можно использовать стандартные утилиты над файлом `.eml`. Пример команды для извлечения ключевых полей из сохранённого файла `suspicious.eml`:

```bash
# Извлечь заголовки, представляющие интерес для анализа
cat suspicious.eml | grep -i -E "^(From:|To:|Subject:|Date:|Reply-To:|Return-Path:|Received:|Authentication-Results:|DKIM-Signature:|Message-ID:)"
```

Результат вывода будет содержать строки вроде:
```
From: "IT Support" <it-support@company-secure-portal.com>
Reply-To: attacker@evildomain.xyz
Received: from mail.evildomain.xyz (evildomain.xyz [203.0.113.50])
Authentication-Results: spf=softfail (sender IP is 203.0.113.50) smtp.mailfrom=evildomain.xyz; dkim=none (no signature) header.d=none; dmarc=fail (p=reject sp=reject) ...
```
Такой вывод сразу показывает расхождение: письмо якобы от `company-secure-portal.com`, но фактически отправлено с `evildomain.xyz`, SPF softfail, DKIM отсутствует, DMARC fail — явный признак подделки.

Далее IP-адрес источника (здесь `203.0.113.50`) проверяется на репутацию. Для этого можно использовать API VirusTotal (после регистрации и получения ключа) или командную утилиту `curl` к публичным сервисам, например, AbuseIPDB. Пример запроса к AbuseIPDB (API v2) с фейковым ключом:

```bash
curl -G https://api.abuseipdb.com/api/v2/check \
  --data-urlencode "ipAddress=203.0.113.50" \
  -d maxAgeInDays=90 \
  -H "Key: $ABUSEIPDB_API_KEY"
```
Ответ в JSON содержит `data.abuseConfidenceScore` и список зарегистрированных жалоб. Если рейтинг превышает 80%, IP считается неблагонадёжным. Аналогично можно использовать API VirusTotal для IP или домена (`/api/v3/ip_addresses/{ip}`), что возвращает detections от множества антивирусов.

**Анализ ссылок и вложений.** Ссылки ни в коем случае не кликаются; их извлекают и анализируют через промежуточные сервисы. В сценарии L1 удобно использовать интеграцию с VirusTotal через скрипт:

```python
import requests
url = "https://www.virustotal.com/api/v3/urls"
headers = {"x-apikey": "<ваш_API_ключ>"}
data = {"url": "http://подозрительная-ссылка.example.com/login"}
response = requests.post(url, headers=headers, data=data)
# получаем id анализа, затем polling результата
```

Но на практике чаще применяется веб-интерфейс VirusTotal или urlscan.io. Важно не полагаться на кешированный результат, а инициировать повторное сканирование. Для вложений вычисляется хеш (SHA256) и сверяется с базой:

```bash
sha256sum suspicious_attachment.exe | awk '{print $1}' | xargs -I {} curl --request GET \
  --url "https://www.virustotal.com/api/v3/files/{}" \
  --header "x-apikey: $VT_API_KEY"
```

**Песочницы и поведенческий анализ.** Если файл не детектируется по хешу и есть сомнения, его отправляют в динамическую песочницу. Для быстрой проверки L1 может использовать утилиту `curl` для отправки файла в Any.Run через публичное API (необходим токен). В ответ приходит идентификатор задачи, и через некоторое время можно получить отчёт с индикаторами запуска процессов, сетевых запросов и скриншотами. Аналогично работают и корпоративные песочницы, интегрированные в платформу. В выдержках упоминаются Joe Sandbox, Cuckoo, Hybrid Analysis [LinkedIn Oxford Fredrick, LinkedIn Shahrukh Khan]. Важно документировать использование песочницы, чтобы L2 видел контекст.

**Поиск по почтовым журналам.** После подтверждения вредоносности L1 должен найти всех получателей. В Microsoft 365 это делается через командлет `New-ComplianceSearch` в PowerShell (при наличии прав), или через GUI Security & Compliance Center. Пример запроса через Exchange Online PowerShell для поиска писем с идентичной темой и отправителем:

```powershell
Search-Mailbox -Identity "targetmailbox" -SearchQuery "Subject:'Invoice #45721' AND From:'bad@domain.xyz'" -TargetMailbox "DiscoverySearchMailbox" -TargetFolder "SearchResults" -LogOnly
```
Это позволяет собрать все копии для последующего удаления.

**Типичные ошибки.** Начинающие аналитики часто пренебрегают проверкой SPF/DKIM/DMARC из-за недостатка времени, полагаясь только на VirusTotal, что приводит к пропуску BEC-атак без вредоносных ссылок. Другая распространённая ошибка — открытие вложений на хосте до помещения в песочницу, особенно файлов формата `.iso` или `.html`, которые могут содержать скрипты. Также важно проверять не только сам домен, но и его дату регистрации через WHOIS; многие фишинговые домены живут менее суток, и кеш репутационных сервисов может не успеть их занести в чёрный список. Все эти нюансы требуют постоянной практики и следования стандартным операционным процедурам (SOP) SOC.

## Сквозной практический пример: расследование фишингового письма

**Исходные условия.** Студент в роли аналитика SOC L1 получает уведомление от системы тикетов: пользователь `ivanov@company.ru` переслал на abuse-ящик письмо с темой «Срочно: продление срока действия пароля». Приложен raw-файл письма `phish.eml`. Инфраструктура: рабочая станция с Linux, доступ к интернету, API-ключи для VirusTotal и AbuseIPDB, песочница Any.Run. Цель — провести первичный анализ и принять решение об эскалации.

**Шаг 1: Извлечение артефактов и предварительный осмотр.** Сначала получаем заголовки и вычленяем поля.

```bash
cat phish.eml | grep -i -E "^(From|To|Subject|Reply-To|Return-Path|Received|Authentication-Results|DKIM-Signature)"
```

Вывод (иллюстративная схема):
```
From: "IT Service Desk" <it@company-sso-secure.link>
To: ivanov@company.ru
Subject: Срочно: продление срока действия пароля
Reply-To: it@company-sso-secure.link
Return-Path: bounce@mail102.hosting.xyz
Received: from mail102.hosting.xyz (mail102.hosting.xyz [198.51.100.23]) ...
Authentication-Results: spf=pass (sender IP=198.51.100.23) smtp.mailfrom=mail102.hosting.xyz;
   dkim=pass header.d=company-sso-secure.link; dmarc=none
```
Обращаем внимание: `From:` и `Reply-To:` указывают на домен, похожий на легитимный (`company-sso-secure.link`), но `Return-Path` идёт на общий хостинг (`hosting.xyz`). Аутентификация DKIM прошла для домена `company-sso-secure.link`, значит злоумышленник контролирует этот домен, а само письмо не просто спуфинг — это phishing site hosting.

**Шаг 2: Проверка репутации IP и домена.** Определяем IP источника `198.51.100.23` и домен `company-sso-secure.link`.

```bash
curl -s -G https://api.abuseipdb.com/api/v2/check \
  --data-urlencode "ipAddress=198.51.100.23" \
  -d maxAgeInDays=30 \
  -H "Key: $ABUSEIPDB_KEY" | jq '.data.abuseConfidenceScore'
```
Допустим, ответ `85`. Высокий рейтинг злонамеренности. Затем WHOIS-запрос домена:

```bash
whois company-sso-secure.link | grep -i "Creation Date\|Registrar"
```
Видим, что домен создан сегодня утром. Подозрение усиливается.

**Шаг 3: Анализ URL и вложения.** Извлекаем все ссылки из тела письма:

```bash
cat phish.eml | grep -oP 'https?://[^\s"]+' | sort -u > urls.txt
cat urls.txt
```
Вывод:
```
https://company-sso-secure.link/login.php?email=ivanov@company.ru
```
Проверяем URL через VirusTotal, используя API:

```python
import requests
h = {"x-apikey": "<VT_KEY>"}
r = requests.post("https://www.virustotal.com/api/v3/urls", headers=h, data={"url": "https://company-sso-secure.link/login.php?email=ivanov@company.ru"})
analysis_id = r.json()['data']['id']
# далее polling результата...
```
Ждём результат; предположим, 7/92 детектов, категория "phishing, credential theft". Этого достаточно для подтверждения.

**Шаг 4: Решение и эскалация.** На основе совокупности признаков (свежий домен, высокий AbuseIPDB, положительный вердикт VirusTotal) принимаем решение: письмо является целевым фишингом, попыткой кражи учётных данных. Действия L1: помечаем инцидент как «Confirmed Phishing», добавляем IOC (домен `company-sso-secure.link`, IP `198.51.100.23`, URL `login.php`). Выполняем немедленное блокирование домена на почтовом шлюзе (например, через веб-консоль Proofpoint или командой PowerShell в Exchange Online) и инициируем эскалацию на L2 для проверки, не вводил ли пользователь учётные данные. В тикетовой системе документируем все шаги:

```json
{
  "ticket_id": "INC-2718",
  "analyst": "l1_student",
  "verdict": "malicious",
  "iocs": {
    "domain": "company-sso-secure.link",
    "ip": "198.51.100.23",
    "url": "https://company-sso-secure.link/login.php",
    "emails": ["ivanov@company.ru"]
  },
  "actions_taken": ["url_blocked", "email_quarantined", "escalated_to_L2"]
}
```

Ожидаемый вывод примера: демонстрация полного цикла работы L1 над подозрительным письмом от первичного получения до обоснованного решения и блокировки угрозы, с реальными артефактами на каждом этапе. Студент должен усвоить, что даже без продвинутых средств автоматизации можно провести качественный анализ, строго следуя методике.
