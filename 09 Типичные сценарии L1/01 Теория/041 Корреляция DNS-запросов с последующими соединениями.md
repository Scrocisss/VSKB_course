# Корреляция DNS-запросов с последующими соединениями для выявления подозрительной активности (SOC L1)

## 1. DNS как индикаторный слой и предпосылки корреляции

Система доменных имён (Domain Name System, DNS), стандартизированная в [RFC1034] и [RFC1035], выполняет фундаментальную функцию: преобразование удобных для человека доменных имён в IP-адреса, необходимые для маршрутизации пакетов. С точки зрения сетевой безопасности DNS представляет собой **опережающий индикатор**: практически любое сетевое взаимодействие инициируется DNS-транзакцией. Как отмечено в [Introduction to DNS Privacy](https://www.internetsociety.org/resources/deploy360/dns-privacy/intro), «почти каждое действие в Интернете начинается с DNS-запроса (а часто и с нескольких)». Следовательно, анализ DNS позволяет обнаружить злонамеренные намерения ещё до того, как будет установлено вредоносное соединение.

В корпоративной среде центральным элементом наблюдения выступает **рекурсивный DNS-резолвер**, обслуживающий внутренних клиентов. Именно его логи, а также перехваченный сетевой трафик дают SOC-аналитику исходный материал. Однако единичного DNS-события редко бывает достаточно для однозначного вердикта: запрос к подозрительному домену может быть вызван безобидной причиной (рекламный трекер, опечатка пользователя), а злоумышленники постоянно совершенствуют техники обхода, маскируя трафик под легитимный. Поэтому на уровне SOC L1 стандартной операционной процедурой становится **корреляция DNS-запроса с последующим сетевым соединением** — связывание факта разрешения имени с конкретным потоком данных, источником и поведенческими признаками.

| Параметр | DNS-запрос (и ответ) | Последующее сетевое соединение |
|----------|----------------------|--------------------------------|
| **Наблюдаемые артефакты** | Домен, тип записи (A, AAAA, TXT, MX…), IP‑адрес клиента, IP‑адрес резолвера, разрешённый IP (если логируется ответ), временная метка | IP-адрес источника, IP-адрес назначения, порт назначения, протокол, длительность, число переданных байт/пакетов, временные метки начала/окончания |
| **Момент фиксации** | До установления TCP/UDP‑сессии; часто за миллисекунды до соединения | После успешного DNS‑разрешения (или из кэша), при фактической попытке взаимодействия |
| **Роль в расследовании** | Обнаружение намерений: связь с вредоносной инфраструктурой, DGA‑активность, туннелирование, запросы к недавно зарегистрированным доменам | Подтверждение факта эксплуатации: передача данных, загрузка полезной нагрузки, beaconing, эксфильтрация |
| **Уровень уверенности** | Средний — легитимные сервисы могут эпизодически резолвиться на IP с плохой репутацией; возможны ложные срабатывания из‑за пользовательских ошибок | Высокий — если аномалии DNS сопровождаются аномальными характеристиками трафика (нестандартный порт, периодичность, большой объём) |
| **Источники данных** | Логи DNS‑сервера (syslog, dnstap), пассивный DNS (pDNS), сетевой захват (pcap) | Логи межсетевого экрана, NetFlow/IPFIX, прокси‑логи, EDR‑телеметрия |

Ботнеты и вредоносное ПО активно используют DNS для управления и разведки. Исследование Шу и Калафата [Characterizing DNS Resolvers and their Clients](https://web.cs.wpi.edu/~cshue/research/toit13.pdf) подчёркивает: «ботнеты регулярно задействуют DNS для командных центров (C2) и рекогносцировки целевой организации». В частности, ботнет Feederbot направлял кастомизированные DNS‑запросы в обход локальных ISP‑резолверов, вероятно, чтобы избежать обнаружения, — а значит, одних только централизованных логов может быть недостаточно. Аналогично, DNS‑туннели (например, iodine) и алгоритмы генерации доменов (DGA) создают аномальные паттерны, видимые исключительно при сопоставлении DNS‑активности и последующего трафика.

Конфиденциальность DNS также имеет прямое отношение к SOC. В [RFC 9076 (DNS Privacy Considerations)](https://www.rfc-editor.org/rfc/rfc9076.txt) детально описаны риски: данные в запросах и ответах по умолчанию передаются открытым текстом, что позволяет любому наблюдателю восстановить профиль активности пользователя. С точки зрения защиты это означает, что SOC, напротив, может извлекать ценную информацию из незашифрованного DNS, но сталкивается с проблемой, когда злоумышленник использует DNS‑over‑TLS (DoT) или DNS‑over‑HTTPS (DoH). В таких условиях корреляцию приходится выстраивать косвенно — через анализ трафика к известным DoH‑провайдерам, SNI‑поля в TLS ClientHello или данные с конечных точек. Тем не менее базовый принцип остаётся неизменным: за DNS‑запросом часто следует соединение, и их взаимосвязь — мощный детектирующий инструмент.

Таким образом, SOC L1 работает не с изолированными сигнатурами доменов, а с **гибридными событиями**: подозрительный DNS‑запрос + последующее соединение с нехарактерными параметрами = высокая вероятность инцидента. Эта логика заложена в большинство SIEM‑правил начального уровня.

## 2. Архитектура и методология процесса корреляции

Процесс корреляции DNS с сетевыми соединениями можно представить как конвейер обработки разнородных источников данных с последующей логической стыковкой. На высоком уровне архитектура включает четыре слоя: источники, сбор и нормализация, движок корреляции и генерация алертов.

```text
[DNS-сервер]───(syslog/stream)──▶[Коллектор логов]
                                      │
                                      ▼
                           ┌──────────────────────┐
                           │ Нормализация и парсинг│
                           └──────────────────────┘
                                      │
                                      ▼
[Межсетевой экран/NetFlow]──▶[Коллектор NetFlow/логов]
                                      │
                                      ▼
                           ┌──────────────────────┐
                           │ Нормализация и парсинг│
                           └──────────────────────┘
                                      │
                                      ▼
                        ┌──────────────────────────┐
                        │   ДВИЖОК КОРРЕЛЯЦИИ     │
                        │  (SIEM: Splunk, Elastic)│
                        └──────────────────────────┘
                                      │
                       ┌──────────────┼──────────────┐
                       ▼                             ▼
                 [Правило 1:                [Правило 2:
            домен из TI + соединение]   аномалия в NetFlow + DNS]
                       │                             │
                       └──────────┬──────────────────┘
                                  ▼
                          [Алерт SOC L1]
```

**Источники данных** и их ключевые поля, используемые для корреляции:

- **DNS-логи (рекурсивного резолвера)**. Типовые поля: `timestamp`, `client_ip`, `query_domain`, `query_type` (A, AAAA, TXT…), `response_code` (NOERROR, NXDOMAIN…), `resolved_ips` (если логгируется ответ). Пример записи BIND query log: `client 192.168.1.100#53089 (bad.example.com): query: bad.example.com IN A + (192.168.1.1)`. В современных стеках, таких как dnstap, информация полнее и структурирована.
- **Логи межсетевого экрана (L4)**. Поля: `start_time`, `duration`, `src_ip`, `dst_ip`, `dst_port`, `protocol` (TCP/UDP), `action` (allow/deny), `bytes_sent`, `bytes_received`.
- **NetFlow / IPFIX**. Агрегированные записи потоков: `src_ip`, `dst_ip`, `src_port`, `dst_port`, `protocol`, `packets`, `bytes`, `start_time`, `end_time`. Благодаря высокой производительности NetFlow отлично подходит для ретроспективного анализа больших объёмов трафика.
- **Прокси-логи (HTTP/HTTPS)**. Дополнительный контекст: полный URL, метод, User-Agent. Но для прямого соединения на нестандартный порт они неприменимы.

Корреляция чаще всего реализуется через **join-операции** по общим ключам: `client_ip` DNS‑запроса и `src_ip` соединения; `resolved_ip` (одно или несколько значений) и `dst_ip` соединения. Второй этап — временная фильтрация. Эвристика проста: соединение должно происходить после момента получения ответа DNS, но не слишком поздно, чтобы не выходить за пределы TTL записи и естественного «окна активности». Типичное окно — от 1 секунды до 10–15 минут; для более долгосрочных кэшей (TTL часами) можно расширять, но с увеличением окна растёт и шум.

**Методологически** различают два направления:

1. **DNS‑инициированная корреляция (наиболее частая в SOC L1)**. Триггером выступает подозрительный DNS‑запрос (совпадение с threat intelligence, NXDOMAIN‑шторм, аномальная длина, DGA‑подобное имя). Аналитик или автоматическое правило запрашивает все сетевые соединения с того же хоста-источника на IP, фигурировавшие в ответе DNS, за заданный временной интервал.
2. **Flow‑инициированная корреляция**. Нехарактерный сетевой поток (например, TCP‑сессия на нестандартный порт с большим объёмом данных) запускает проверку: не предшествовал ли ему DNS‑запрос, который можно идентифицировать в пассивном DNS или логах резолвера. Такой подход часто применяется в Threat Hunting, но на L1 может использоваться как дополнительное обогащение алерта.

В реальных SOC-платформах корреляцию ускоряют с помощью **пассивного DNS (pDNS)** — базы исторических DNS‑разрешений. Если логи резолвера не содержат ответов (только запросы), pDNS позволяет ретроспективно найти, какой IP был возвращён доменом `bad.example.com` в нужный момент времени. Архитектура, описанная в [Beyond the Network View: DNS-Driven Application Visibility](https://labs.ripe.net/author/danny-lachos/beyond-the-network-view-dns-driven-application-visibility), иллюстрирует сходную идею: обогащение NetFlow‑записей данными DNS для получения отображения «поток → хост/CDN». В контексте безопасности это обогащение работает в обратную сторону — от подозрительного домена к конкретному потоку.

**Ключевые индикаторы**, повышающие достоверность корреляции:

- Домен недавно зарегистрирован (Newly Registered Domain, NRD) или имеет низкую репутацию по TI.
- Соединение установлено на нестандартный порт (не 80/443/53/8080).
- Периодичность соединений совпадает с DNS‑запросами (beaconing с постоянным интервалом).
- Большой объём данных, переданный в соединении, особенно если DNS‑запрос содержал TXT‑запись большого размера (признак туннелирования).
- NXDOMAIN‑ответ на DNS‑запрос, но тем не менее предпринята попытка TCP‑соединения с одним из IP, полученных ранее (злоумышленник мог изменить A‑запись).

В таблице ниже сопоставлены основные методы стыковки DNS и соединений, используемые в промышленных SIEM.

| Метод | Описание | Сильные стороны | Ограничения |
|-------|----------|-----------------|-------------|
| **Прямое совпадение IP** | `dns.resolved_ip == firewall.dst_ip` и `dns.client == firewall.src` | Простая реализация в любом SIEM; легко автоматизируется | Требует, чтобы DNS‑логи содержали ответный IP; не работает при NAT между клиентом и DNS‑сервером (если IP‑клиента в Firewall заменён) |
| **Корреляция через pDNS + NetFlow** | pDNS выдаёт исторический IP для домена, затем NetFlow‑запрос показывает общавшихся с этим IP | Позволяет провести расследование post‑factum; не зависит от логирования ответов DNS | Требует поддержки pDNS‑инфраструктуры; временная точность ограничена периодичностью импорта данных |
| **Временное окно** | Соединение, начавшееся в интервале `(dns_response_time, dns_response_time + TTL_estimate)`, считается коррелированным | Учитывает кэширование и естественную задержку | При большом TTL окно может дать много ложных связей; при малом окне можно пропустить соединение, если клиент ждал |
| **Эвристика на основе DGA/beacon** | Сначала группируются DNS‑запросы по хосту, выявляются паттерны DGA, затем ищутся соединения на полученные IP с аналогичной периодичностью | Эффективна против сложных угроз; снижает количество ручного труда | Сложна в реализации без ML; требует настройки под ландшафт сети |

Применение того или иного метода диктуется доступностью логов и зрелостью SOC. На начальном уровне (L1) чаще всего используют прямое совпадение IP и временные окна, реализованные в виде готовых корреляционных правил в SIEM.

## 3. Инструментарий аналитика L1 и типичные аналитические процедуры

Аналитик первого уровня SOC, получив алерт о подозрительном DNS‑обращении, должен быстро подтвердить или опровергнуть эскалацию, опираясь на корреляцию. Минимальный набор инструментов включает утилиты командной строки для предварительного анализа дампов трафика и текстовых логов, а также поисковые запросы в SIEM.

**Типичный рабочий процесс (ручной анализ):**

1. **Извлечение DNS‑событий из pcap или логов.** Если трафик захвачен на резолвере или зеркалирован, применяется `tshark`:
```bash
tshark -r capture.pcap \
  -Y "dns.flags.response == 0 && dns.qry.name contains suspicious" \
  -T fields -e frame.time -e ip.src -e dns.qry.name -e dns.a
```
Ожидаемый вывод — временная метка, IP‑адрес клиента, полное доменное имя и разрешённые IP‑адреса (если ответ записан в том же файле). Для выделения только запросов и ответов в паре полезна фильтрация по DNS transaction ID.

2. **Поиск соединений на полученный IP в логах межсетевого экрана.** Логи NGFW часто сохраняются в syslog‑формате. Оператор может выполнить:
```bash
grep -E "src=192.168.1.100.*dst=203.0.113.99" /var/log/syslog | grep "action=allow"
```
Результат покажет разрешённые сессии, включая порт назначения, длительность и объём переданных данных. Если системы используют бинарный NetFlow, применяется `nfdump`:
```bash
nfdump -r /var/netflow/nfcapd.202503221600 \
  -o "fmt:%ts %td %sa %da %sp %dp %pr %byt" \
  'host 192.168.1.100 and host 203.0.113.99'
```
Вывод в табличном формате демонстрирует все потоки между данными IP; внимание привлекают нестандартные порты (4444, 1337) и большой объём байт.

3. **Автоматизация в SIEM (Splunk/Elastic).** Правило корреляции на SPL-подобном языке может выглядеть следующим образом (иллюстративная схема):
```spl
index=dns sourcetype=dns domain="*.example.org" response_code="NOERROR"
| stats latest(resolved_ip) as resolved_ip by client_ip, domain
| join type=inner client_ip
    [search index=firewall sourcetype=firewall earliest=-15m@m latest=now
    | stats values(dst_ip) as dst_ip, values(dst_port) as port by src_ip
    | rename src_ip as client_ip]
| where like(dst_ip, resolved_ip)
| table _time, client_ip, domain, resolved_ip, port
```
Такой поиск находит совпадения между IP, полученными из DNS, и адресами назначения в логах файрвола. В зависимости от платформы синтаксис варьируется, но логика остаётся стандартной.

**Типичные ошибки и способы их компенсации:**

- **DNS‑кеширование.** Клиент мог разрешить домен за несколько часов до соединения, и текущие логи резолвера не содержат первичного запроса. Решение: расширение временного окна до величины максимального TTL, использование пассивного DNS или утилит кэша (например, `dnscmd /displaydns` на Windows‑хосте).
- **Шифрованный DNS (DoH/DoT).** Запросы передаются внутри TLS‑сессий на порт 443; классические DNS‑логи не работают. В этом случае корреляция возможна через парсинг SNI в ClientHello или через интеграцию с EDR, который перехватывает вызовы `getaddrinfo` до шифрования. Как отмечено в [RFC 9076](https://www.rfc-editor.org/rfc/rfc9076.txt), «использование шифрованного транспорта убирает видимость содержимого DNS для промежуточных устройств», следовательно, SOC должен компенсировать это endpoint‑телеметрией.
- **Ложные срабатывания на CDN и облака.** Домены, обслуживающие многочисленные сервисы (например, `*.akamaihd.net`, `*.azureedge.net`), резолвятся в широкий пул IP; соединение с любым из них выглядит как корреляция, но не является злонамеренным. В правила добавляют фильтры по репутации IP, исключающие диапазоны известных CDN и облачных провайдеров (Whitelist Autonomous System Numbers).
- **Несинхронизированные временные метки.** Если системные часы резолвера и файрвола расходятся на несколько секунд, строгое окно может не сработать. Помогает предварительный контроль NTP и применение нечётких интервалов (например, ±60 секунд).
- **Отсутствие DNS-ответа в логах.** Многие резолверы логируют только запросы. В таком случае корреляцию проводят по предположению: после запроса домена любое соединение с IP, известным из pDNS для этого домена, считается связанным. Требуется осторожная интерпретация.

Для повышения эффективности SOC L1 часто использует готовые корреляционные паки (например, Sigma-правила, преобразуемые в SPL). Но понимание базовых команд остаётся критичным: именно они позволяют быстро провести «ручную» проверку, когда автоматика дала сбой или перегружена ложными срабатываниями.

## 4. Сквозной практический пример: детектирование C2‑канала через DNS и последующее аномальное соединение

**Исходные условия:** рабочая станция Windows (IP `192.168.1.100`) предположительно заражена. SIEM сгенерировал алерт на подозрительный DNS‑запрос к домену `x8f3j2k0.bad-domain.org` (шаблон характерен для DGA) в 10:44:03 UTC. Рекурсивный DNS‑резолвер (192.168.1.1) вернул IP `203.0.113.99`. Аналитик L1 должен в течение 5 минут подтвердить или снять эскалацию, используя логи резолвера, лог файрвола и данные NetFlow.

**Шаг 1: Извлечение информации о DNS‑запросе и ответе из логов BIND.**
```bash
grep "x8f3j2k0.bad-domain.org" /var/log/named/queries.log
```
Пример вывода (иллюстративная схема):
```
10:44:03.456 client 192.168.1.100#50432 (x8f3j2k0.bad-domain.org): query: x8f3j2k0.bad-domain.org IN A + (192.168.1.1)
10:44:03.460 client 192.168.1.100#50432 (x8f3j2k0.bad-domain.org): response: x8f3j2k0.bad-domain.org IN A + (192.168.1.1) -> 203.0.113.99
```
Событие фиксирует запрос и успешный ответ с IP‑адресом `203.0.113.99`. Временная метка – 10:44:03.

**Шаг 2: Поиск последующих соединений с этим IP в логах межсетевого экрана.**
Лог файрвола (syslog-формат) анализируется командой:
```bash
grep -E "src=192.168.1.100.*dst=203.0.113.99" /var/log/firewall/2025/03/22.log
```
Ожидаемый результат:
```
Mar 22 10:44:04 fw01 kernel: IN=eth0 OUT=eth1 SRC=192.168.1.100 DST=203.0.113.99 PROTO=TCP SPT=49156 DPT=4444 SYN ACK=0
Mar 22 10:44:05 fw01 kernel: IN=eth0 OUT=eth1 SRC=192.168.1.100 DST=203.0.113.99 PROTO=TCP SPT=49156 DPT=4444 ACK=1 LEN=60
Mar 22 10:44:15 fw01 kernel: IN=eth0 OUT=eth1 SRC=192.168.1.100 DST=203.0.113.99 PROTO=TCP SPT=49156 DPT=4444 ACK=1 LEN=1500
...
```
Соединение инициировано через 1 секунду после DNS‑ответа на TCP‑порт 4444, отсутствующий в списке корпоративных сервисов. Наблюдается рост длины пакетов, что типично для C2‑канала.

**Шаг 3: Анализ NetFlow для оценки объёма переданных данных.**
С помощью `nfdump` аналитик запрашивает сводку потоков между хостом и подозрительным IP:
```bash
nfdump -r /var/netflow/nfcapd.202503221045 -s record -o "fmt:%ts %te %sa %da %pr %sp %dp %byt %pkt" 'host 192.168.1.100 and host 203.0.113.99'
```
Пример вывода:
```
Date first seen        Duration Src IP           Dst IP        Proto Src Port Dst Port   Bytes   Packets
2025-03-22 10:44:04.000  120.000 192.168.1.100   203.0.113.99  TCP   49156    4444      245678   1623
```
Поток длился 120 секунд, передано ~240 Кбайт, что сопоставимо с загрузкой полезной нагрузки или эксфильтрацией данных.

**Шаг 4: Обогащение из threat intelligence.**
Аналитик выполняет запрос к VirusTotal API для проверки IP (пример с curl, допуская, что API‑ключ настроен):
```bash
curl -s -X GET "https://www.virustotal.com/api/v3/ip_addresses/203.0.113.99" \
  -H "x-apikey: $VT_API_KEY" | jq '.data.attributes.last_analysis_stats'
```
Гипотетический ответ:
```json
{
  "malicious": 6,
  "suspicious": 2,
  "harmless": 85,
  "undetected": 7
}
```
Шесть антивирусных движков классифицировали IP как вредоносный, что подтверждает подозрения.

**Шаг 5: Формирование вывода.**
Аналитик L1 делает заключение: домен `x8f3j2k0.bad-domain.org` с высокой вероятностью является DGA‑именем; DNS‑запрос к нему завершился успешным разрешением; в течение секунды с заражённого хоста установлено TCP‑соединение на нестандартный порт 4444 с пересылкой значительного объёма данных; IP‑адрес имеет неблагоприятную репутацию. Данный набор индикаторов удовлетворяет критериям инцидента безопасности. Алерт эскалируется на уровень L2 для углублённого анализа и изоляции хоста.

Приведённый пример демонстрирует полный цикл работы корреляции — от DNS‑триггера до подтверждённого инцидента — с использованием реальных форматов логов и утилит командной строки, что составляет повседневную практику аналитика SOC L1.
