# Разбор полей HTTP-запроса и сетевого пакета в теле алерта WAF/NTA для задач SOC L1

## 1. Контекст: алерты WAF и NTA в цепочке первичного анализа
Системы защиты веб-приложений (Web Application Firewall, WAF) и сетевого анализа трафика (Network Traffic Analysis, NTA) генерируют алерты — структурированные сообщения о событиях, требующих проверки специалистом первой линии (L1). Алерт содержит полный или частичный слепок вредоносного HTTP-запроса либо сетевого пакета, а также метаданные правила, вызвавшего срабатывание. Задача L1-аналитика — за ограниченное время (обычно 5–10 минут) определить, требует ли алерт эскалации на L2/L3 или является ложным срабатыванием. Для этого необходимо быстро извлечь из тела алерта значимые поля и сопоставить их с типовыми индикаторами атак.

WAF и NTA работают на разных уровнях модели OSI, потому и состав полей в их алертах различается. WAF (ModSecurity, AWS WAF, Cloudflare WAF, Imperva) инспектирует HTTP-трафик на уровне приложения: он полностью разбирает запрос и ответ, нормализует кодировки, анализирует содержимое параметров, заголовков, тела. Алерт WAF всегда содержит детали HTTP-транзакции, иногда — уже идентифицированный атакующий вектор. NTA (Zeek/Bro, Suricata, Corelight, Darktrace, Vectra) работает преимущественно с сетевыми сессиями и пакетами, собирая метаданные потоков, статистику протоколов, а при наличии правил — извлекая и разбирая заголовки и payload прикладного уровня. В результате алерт NTA чаще содержит сетевые характеристики (IP-адреса, порты, протокол транспортного уровня, длительность сеанса, объём переданных данных) и, в зависимости от глубины разбора, некоторые поля HTTP и TLS.

Поля HTTP-запроса и сетевого пакета пересекаются, но не дублируют друг друга. Например, IP-адрес отправителя по версии приложения может отличаться от реального источника из-за балансировщиков нагрузки или прокси (заголовки `X-Forwarded-For`, `X-Real-IP`). Именно поэтому алерты NTA, анализирующие сетевые пакеты без искажений, ценны как источник истинного IP, тогда как WAF-алерт может содержать несколько IP-адресов: один на сетевом уровне, другой — в HTTP-заголовках. Аналитик L1 обязан понимать различие и при необходимости сопоставлять обе картины.

Ниже приведена сравнительная таблица типичных полей в алертах WAF и NTA, иллюстрирующая разницу в фокусе и полноте.

| Аспект                | WAF-алерт                                                    | NTA-алерт                                                    |
|-----------------------|--------------------------------------------------------------|--------------------------------------------------------------|
| **Источник данных**   | HTTP-прокси, модуль веб-сервера, облачный фильтр             | Зеркалирование порта, span, tap, сенсор на хосте             |
| **Уровень анализа**   | Прикладной (HTTP/HTTPS)                                      | Сетевой + извлечение прикладного уровня (DPI)                |
| **IP-адрес клиента**  | Может содержать `X-Forwarded-For`; реальный IP не всегда     | Всегда реальный IP (src_ip), если нет туннелирования         |
| **HTTP-метод и URI**  | Полный метод, путь, query-строка, нормализованные            | Присутствуют, если трафик не зашифрован или разобран TLS     |
| **Заголовки запроса** | Полный набор (Host, User-Agent, Cookie, Referer и др.)       | Могут отсутствовать; если есть — извлечённые ключевые поля   |
| **Тело запроса**      | Полное или первые N байт (по конфигурации)                   | Обычно отсутствует, если не настроено сохранение payload     |
| **Транспортный уровень** | Не всегда доступен; порт может быть задан в конфигурации   | TCP/UDP флаги, TTL, размер окна, номера последовательностей, VLAN |
| **Метаданные сессии** | Ограничены (идентификатор сессии, cookies)                   | Длительность, объём байт, пакетов, направление, состояние    |
| **Правило срабатывания** | Идентификатор правила WAF и категория атаки (SQLi, XSS)   | Сигнатура (sid) или поведенческая модель, описание угрозы    |
| **Шифрование трафика**| Алерт генерируется после расшифрования (WAF выступает как terminator) | NTA не может анализировать зашифрованный трафик без расшифровки |

Таким образом, WAF предоставляет детальный портрет атаки на уровне веб-приложения, а NTA — объективный сетевой контекст. В современной SOC-архитектуре алерты обоих классов стекаются в SIEM-систему (Splunk, Elastic Security, Microsoft Sentinel), где L1-аналитик видит объединённую запись. Типовая задача первого звена — разобрать поля в теле алерта, вычленить индикаторы компрометации и принять решение об эскалации.

## 2. Структура тела алерта: ключевые поля и их интерпретация
Тело алерта WAF или NTA, как правило, представлено в формате JSON или syslog-совместимом тексте. Независимо от вендора, можно выделить несколько функциональных групп полей. L1-аналитик должен безошибочно идентифицировать каждую группу и понимать, какую гипотезу атаки подтверждает или опровергает значение поля.

Рассмотрим иерархию полей на примере обобщённой JSON-структуры алерта WAF (иллюстративная схема):

```json
{
  "alert": {
    "timestamp": "2024-03-15T08:21:33Z",
    "rule": {
      "id": "950901",
      "name": "SQL Injection Attack",
      "category": "web_attack",
      "severity": "high"
    },
    "http": {
      "request_line": {
        "method": "GET",
        "uri": "/products.php?item_id=105+UNION+SELECT+null,null--",
        "http_version": "HTTP/1.1"
      },
      "headers": {
        "Host": "shop.example.com",
        "User-Agent": "sqlmap/1.7#stable (http://sqlmap.org)",
        "Accept": "text/html,application/xhtml+xml",
        "Cookie": "PHPSESSID=a1b2c3d4",
        "X-Forwarded-For": "10.10.10.10"
      },
      "body": "",
      "response_status": 403
    },
    "network": {
      "src_ip": "203.0.113.45",
      "src_port": 61234,
      "dst_ip": "192.168.1.5",
      "dst_port": 443
    }
  }
}
```

Для NTA-алерта типичная структура может быть похожа, но с акцентом на сетевые поля и часто с включением части HTTP как извлечённых метаданных:

```json
{
  "event": {
    "timestamp": "2024-03-15T08:21:33.456Z",
    "signature_id": 2018964,
    "signature": "ET WEB_SPECIFIC_APPS SQL Injection attempt",
    "severity": 1,
    "src_ip": "203.0.113.45",
    "src_port": 61234,
    "dst_ip": "192.168.1.5",
    "dst_port": 80,
    "proto": "TCP",
    "http": {
      "method": "GET",
      "host": "shop.example.com",
      "uri": "/products.php?item_id=105 UNION SELECT null,null--",
      "user_agent": "sqlmap/1.7#stable"
    },
    "tx_id": 4294967295
  }
}
```

**Поля HTTP-запроса**

- **Request line (метод, URI, версия HTTP).** `GET` и `POST` — обычные, но `PUT`, `DELETE`, `OPTIONS`, `TRACE` заслуживают внимания, если не ожидаются приложением. Аналитик L1 сверяет метод со списком разрешённых (например, из документации или здравого смысла). URI и query-строка — основной носитель атаки. Полезно визуально выискивать SQL-ключевые слова (`UNION`, `SELECT`, `DROP`, `--`), HTML/JS-теги (`<script>`, `onerror`), обходы путей (`../..`), команды ОС (`; ls`, `| cat /etc/passwd`). В WAF-алерте URI часто нормализован, т.е. подозрительные символы могут быть уже раскодированы (URL decode), что облегчает анализ. NTA-алерт обычно содержит сырой URI, где кодировки сохранены; L1 должен уметь быстро выполнить декодирование в уме или инструментами.

- **Заголовки (Headers).** `Host` указывает целевой виртуальный хост; если он не соответствует известному домену организации, алерт может быть ложным или целью атаки является неизвестный ресурс. `User-Agent` — один из самых информативных полей для L1. Легитимные браузеры имеют характерные строки (Chrome, Firefox, Edge); подозрительные значения включают инструменты пентеста (`sqlmap`, `nikto`, `nmap`), скриптовые языки (`python-requests`, `curl/7.x`, `Go-http-client`), пустую или аномально длинную строку. Поле `Cookie` содержит идентификаторы сессий; наличие фиксированной сессионной куки позволяет предположить, что атакуют авторизованный сеанс, что повышает серьёзность. Заголовок `X-Forwarded-For` (и `X-Real-IP`) раскрывает исходный IP клиента за прокси; аналитик должен перекрёстно проверить его с сетевым источником: если они различаются, реальный атакующий может скрываться за цепочкой прокси. Другие заголовки (`Content-Type`, `Accept`, `Referer`) редко становятся ключевыми, но могут указать на подделку запроса (CSRF) или попытки инъекций в неожиданных полях.

- **Тело запроса (Body).** Для методов POST/PUT тело может содержать параметры, закодированные в формате URL-encoded или multipart/form-data, а также XML/JSON. WAF обычно включает тело в алерт, если обнаружена атака в payload. L1 должен просмотреть тело на наличие явно вредоносных строк (шестнадцатеричный код, длинные бинарные последовательности). NTA редко сохраняет тело из-за его объёма.

- **Код ответа (Response status).** Если WAF передаёт ответ, код 403 (Forbidden) — норма, 200 (OK) в теле алерта говорит о том, что атака могла пройти мимо WAF (false negative), что требует немедленного внимания. NTA-алерты обычно не содержат кода ответа, если не включена запись полного сеанса.

**Поля сетевого пакета**

- **Источник и назначение (src_ip, dst_ip, src_port, dst_port).** В NTA-алерте это самые достоверные значения, полученные из заголовка IP и TCP/UDP. Src_ip — адрес, с которого пришла атака. L1 должен провести репутационную проверку (через whois, threat intelligence платформы, чёрные списки). Dst_ip указывает атакуемый сервер; аналитик проверяет, является ли он частью контролируемой инфраструктуры. Если dst_ip не соответствует ожидаемому сегменту, возможно, это сканирование.

- **Транспортные параметры.** Порт назначения: 80/443 — веб, но если атака пришла на нестандартный порт (8080, 8443, 9000), это может указывать на администрирование или незащищённый сервис. TCP-флаги (SYN, ACK, RST) позволяют отличить начальную фазу соединения от повторных передач; в алертах NTA они иногда присутствуют. TTL (время жизни) может намекнуть на операционную систему отправителя (например, начальное значение 64 характерно для Linux, 128 — для Windows), что помогает в пассивном определении хоста атакующего.

- **Метаданные соединения.** Длительность, объём байт и пакетов важны для поведенческих алертов (C&C, data exfiltration). В простых сигнатурных алертах они могут отсутствовать.

**Поля контекста WAF/NTA**

- **Идентификатор правила / сигнатуры.** Например, ModSecurity rule ID `950901` или Suricata `sid 2018964`. Позволяет быстро найти документацию и понять, на какую именно уязвимость или технику направлено правило. L1 обязан посмотреть описание правила во внутренней базе знаний (KB).

- **Уровень критичности (severity).** Обычно от 1 (info) до 5 (critical). Не является единственным критерием эскалации, но критичные алерты проверяются в первую очередь.

- **Временная метка (timestamp).** Важна для корреляции с другими событиями в тот же временной интервал.

Структурно, в теле алерта все эти поля могут быть вложены в несколько уровней JSON. Чтобы облегчить ориентацию, L1 может представлять их в виде иерархической схемы:

```text
[alert]
 |
 +-- [meta]        (rule_id, severity, timestamp)
 |
 +-- [http]        (request_line)
 |     +-- method
 |     +-- uri
 |     +-- version
 |     +-- [headers]
 |     |     +-- Host
 |     |     +-- User-Agent
 |     |     +-- Cookie
 |     |     +-- X-Forwarded-For
 |     +-- (body)
 |
 +-- [network]     (src_ip, src_port, dst_ip, dst_port, proto)
 |
 +-- [response]    (status_code)
```

Такая ментальная модель помогает быстро перейти к нужному блоку и не тратить время на чтение всего JSON.

## 3. Практические приёмы работы с полями алерта
Аналитик L1 редко вручную разбирает сырой JSON; рабочее место, как правило, оборудовано SIEM-решением, которое отображает поля в удобном виде (таблица, панель деталей). Тем не менее умение работать с консольными утилитами даёт гибкость и скорость, особенно при массовой проверке. Ниже рассмотрены типовые операции, которые должен выполнять аналитик, опираясь на поля алерта.

**Извлечение полей из алерта.** В большинстве дистрибутивов SIEM предусмотрен экспорт алерта в сыром виде. Если аналитик работает в Linux-окружении (или WSL), он может использовать `jq` для быстрого извлечения нужных полей. Например, из входящего файла `alert.json` получить HTTP-метод и URI:

```bash
jq -r '.alert.http.request_line.method + " " + .alert.http.request_line.uri' alert.json
```
Вывод:
```
GET /products.php?item_id=105+UNION+SELECT+null,null--
```

Утилита `jq` также позволяет фильтровать альтернативные структуры (NTA без ключа `http.request_line`):

```bash
jq -r 'if .alert then .alert.http.request_line.uri elif .event then .event.http.uri else "no uri" end' alert.json
```

**Валидация IP-адреса источника.** После извлечения `src_ip` необходимо оценить его репутацию. Стандартный рабочий процесс включает несколько действий. Первое — определение принадлежности адреса через whois:

```bash
whois 203.0.113.45
```
(иллюстративный вывод сокращён)
```
NetRange:       203.0.113.0 - 203.0.113.255
Organization:   Example Hosting Provider
Country:        NL
...
```

Если IP принадлежит крупному хостинг-провайдеру, VPS или VPN-сервису, а не динамическому пулу провайдера последней мили, шанс реальной атаки возрастает. Второе действие — обратное разрешение DNS (PTR-запись):

```bash
dig -x 203.0.113.45 +short
```
Вывод (иллюстративный):
```
scan-45.example-scanner.net.
```

Имя, содержащее `scan` или `crawler`, может указывать на автоматизированный сканер (Shodan, Censys, поисковые роботы). Если же PTR-запись отсутствует или имеет вид динамического IP (`12-34-56-78.broadband.provider.com`), это менее подозрительно. Третье действие — проверка по локальной репутационной базе SIEM (обычно через API или встроенный lookup). Аналитик вводит IP в поле поиска и видит метку: «Malicious», «Suspicious», «Tor exit node» и т.п. В условиях учебной среды аналогом может служить файл с репутациями, опрашиваемый скриптом:

```bash
grep -q "203.0.113.45" /opt/threat_intel/bad_ips.txt && echo "Known bad"
```

**Анализ User-Agent.** Поле `User-Agent` часто даёт быстрый ответ о природе трафика. L1 сверяет его со списком легитимных UA, которые одобрены политикой (например, браузеры организации), и с библиотечным списком известных инструментов. Практический пример проверки через `grep` с регулярным выражением:

```bash
echo "sqlmap/1.7#stable (http://sqlmap.org)" | grep -qiE "(sqlmap|nikto|nessus|nmap|python-requests|curl)" && echo "Malicious UA"
```
Вывод: `Malicious UA`.

При этом важно понимать, что User-Agent легко подделывается, поэтому его отсутствие или нестандартность — лишь один из индикаторов, требующий перекрёстной проверки с другими полями.

**Проверка URI на наличие паттернов атаки.** L1 не должен проводить полноценный пентест, однако базовый поиск сигнатурных строк даёт быстрый результат. Пример для WAF-алерта: используем `grep` или `awk` для выделения query-строки:

```bash
uri="/products.php?item_id=105+UNION+SELECT+null,null--"
echo "$uri" | grep -oP '\?.*' | python3 -c "import sys,urllib.parse; print(urllib.parse.unquote(sys.stdin.read()))"
```
Вывод:
```
?item_id=105 UNION SELECT null,null--
```
Здесь мы видим классическую SQL-инъекцию с `UNION SELECT`. Подобные строки — красный флаг, почти всегда требующий эскалации.

Менее очевидные атаки, например, инъекции команд ОС, можно искать по символам `;`, `|`, `` ` ``, `$()`. Типовой сниппет:

```bash
echo "$uri" | grep -oP '[;|`&]' && echo "Potential command injection chars"
```

**Консолидация полей и принятие решения.** Проанализировав `src_ip`, `User-Agent`, `uri`, аналитик строит общую картину. Приведём шаблон мысленного check-list’а L1:
1. Является ли IP-источник легитимным (офис компании, тестовый полигон)? Если нет, отмечаем.
2. Содержит ли URI явные вредоносные последовательности? Если да, эскалируем.
3. Соответствует ли User-Agent инструменту атаки? Подтверждает ли он картину?
4. Есть ли другие алерты от этого же IP за короткое время (горизонт 5 минут)? Если да, атака скорее всего автоматизирована.
5. Соответствует ли правило срабатывания (rule id) документированной ложной тревоге (например, легитимный параметр с именем `select`)?

Только после ответа на эти вопросы аналитик меняет статус алерта и при необходимости эскалирует.

**Типичные ошибки L1.** Наиболее частые ошибки при разборе полей:

- Принятие поддельного `X-Forwarded-For` за истинный IP без проверки сетевого `src_ip` из NTA.
- Игнорирование нормализованного URI в WAF: если WAF не сообщает о нормализации, а аналитик видит `%27` (одинарная кавычка), он ошибочно не распознаёт SQLi.
- Слишком строгая фильтрация по User-Agent: легитимный клиент мониторинга (Zabbix, Nagios) может использовать `curl`, что не является атакой.
- Переоценка severity: не каждый alert high требует эскалации, если все поля указывают на ложное срабатывание (например, XSS-правило сработало на URL с `?q=<b>test</b>`, который не исполняется).

Таким образом, практическая работа с полями — это не механическое чтение, а именно интерпретация с учётом контекста.

## 4. Сквозной практический пример: анализ алерта WAF на SQL-инъекцию
Рассмотрим рабочий кейс, с которым сталкивается аналитик L1 в SOC, на примере алерта, полученного от WAF ModSecurity, интегрированного с SIEM-системой.

**Исходные условия**

- SIEM: Elastic Security (индекс `waf-alerts-*`), доступ к Kibana и консоли с утилитами `jq`, `whois`, `grep`.
- Алерт: `waf_sqli_attempt` (иллюстративные данные, все IP и домены условны).
- Роль: L1-аналитик, цель — за 8 минут определить, является ли событие реальной попыткой SQL-инъекции.

**Шаг 1. Получение алерта в JSON**

Экспортируем алерт из SIEM в файл `alert.json` (в реальной работе — копируем из интерфейса или выполняем поисковый запрос). Фрагмент файла:

```json
{
  "alert": {
    "timestamp": "2024-03-15T08:21:33Z",
    "rule": {
      "id": "950901",
      "severity": "high"
    },
    "http": {
      "request_line": {
        "method": "GET",
        "uri": "/products.php?item_id=105+UNION+SELECT+1,concat(table_name)+FROM+information_schema.tables--",
        "http_version": "HTTP/1.1"
      },
      "headers": {
        "Host": "shop.example.local",
        "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36",
        "X-Forwarded-For": "10.10.10.10"
      }
    },
    "network": {
      "src_ip": "203.0.113.45",
      "src_port": 52100,
      "dst_ip": "192.168.1.5",
      "dst_port": 443
    }
  }
}
```

Просматриваем структуру в консоли:

```bash
cat alert.json | jq .
```
Ожидаемый вывод — весь документ, убеждаемся, что все ожидаемые поля присутствуют.

**Шаг 2. Извлечение ключевых полей для анализа**

С помощью `jq` выделяем основные поля:

```bash
jq -r '[.alert.timestamp, .alert.rule.id, .alert.http.request_line.uri, .alert.http.headers."User-Agent", .alert.network.src_ip] | @tsv' alert.json
```
Вывод (табулированный):
```
2024-03-15T08:21:33Z  950901  /products.php?item_id=105+UNION+SELECT+1,concat(table_name)+FROM+information_schema.tables--  Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36  203.0.113.45
```

Одной командой получили срез: время, правило, URI, User-Agent, IP-источник. Данных достаточно для первичного анализа.

**Шаг 3. Оценка вредоносного запроса**

URI сразу обращает на себя внимание. Декодируем `+` в пробелы (в терминале bash замена тривиальна):

```bash
uri="/products.php?item_id=105+UNION+SELECT+1,concat(table_name)+FROM+information_schema.tables--"
echo "${uri//+/ }"
```
Вывод:
```
/products.php?item_id=105 UNION SELECT 1,concat(table_name) FROM information_schema.tables--
```
В запросе отчётливо видна попытка извлечения имён таблиц через `information_schema` — это классический этап слепой SQL-инъекции. Дополнительно ищем характерные ключевые слова:

```bash
echo "$uri" | grep -iq 'union.*select' && echo "SQLi pattern detected"
```
Результат: `SQLi pattern detected`. Атака подтверждена содержимым.

**Шаг 4. Проверка IP-адреса источника**

Проверяем репутацию `203.0.113.45`:

```bash
whois 203.0.113.45 | grep -iE 'Organization|Country|NetName'
```
Иллюстративный вывод:
```
Organization:   Bulletproof Hosting Ltd.
Country:        NL
NetName:        VPN-RANGE-1
```
Данные указывают на «пуленепробиваемый» хостинг, часто используемый злоумышленниками. Далее обратное DNS:

```bash
dig -x 203.0.113.45 +short
```
Вывод (иллюстративный):
```
vps-45.anonymizer.net
```
Имя подчёркивает анонимизированный источник. Чтобы убедиться, что IP не принадлежит разрешённому сканеру безопасности компании, сверяемся с локальным списком доверенных адресов:

```bash
grep -q "203.0.113.45" /opt/soc/whitelist.txt || echo "Not whitelisted"
```
Вывод: `Not whitelisted`. IP-источник не легитимен.

**Шаг 5. Проверка User-Agent и заголовков**

Несмотря на то что URI содержит явную атаку, полезно оценить User-Agent: `Mozilla/5.0 ... Chrome/91...`. На первый взгляд, это подделка — современный хром, но, скорее всего, злоумышленник подставил популярную строку. Однако это не противоречит картине атаки. Проверяем, не содержит ли UA подозрительных подстрок:

```bash
ua="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/91.0.4472.124 Safari/537.36"
echo "$ua" | grep -qi 'sqlmap\|nikto\|curl' || echo "Clean UA"
```
Вывод: `Clean UA`. Значит, атакующий намеренно скрыл инструмент.

Обратим внимание на заголовок `X-Forwarded-For: 10.10.10.10` — это внутренний приватный адрес, что выглядит как попытка запутать логирование или использование прокси. Сетевой `src_ip` при этом внешний, следовательно, XFF подделан, но это не меняет факта атаки.

**Ожидаемый вывод и решение**

Совокупность признаков: явная SQL-инъекция в URI, IP из хостинга анонимайзеров, поддельный X-Forwarded-For — указывает на true positive. User-Agent не является определяющим, но не противоречит. Алерт требует немедленной эскалации на L2 для дальнейшего расследования (проверка, была ли уязвимость эксплуатацией, блокировка IP-пула, уведомление владельца приложения). Данный пример демонстрирует, как L1-аналитик, владея навыками разбора полей HTTP-запроса и сетевого пакета, способен за несколько минут принять обоснованное решение, не углубляясь в детальный анализ эксплойта.
