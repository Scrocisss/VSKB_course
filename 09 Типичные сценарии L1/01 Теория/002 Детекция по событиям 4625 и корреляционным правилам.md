# Детекция брутфорс-атак через Event ID 4625 и корреляционные правила

## 1. Контекст и базовые понятия: брутфорс, аутентификация Windows и роль SIEM в SOC L1

Атаки перебором учётных данных (brute-force) остаются одним из наиболее распространённых векторов компрометации корпоративных сред. Их принцип прост — злоумышленник автоматизирует попытки входа, пробуя различные комбинации логин/пароль до тех пор, пока не подберёт валидную пару. Несмотря на кажущуюся примитивность, брутфорс остаётся актуальным: слабые пароли, отсутствие блокировок после определённого числа попыток и недостаточный мониторинг делают эту угрозу реальной даже для зрелых организаций.

В контексте работы специалиста первой линии SOC (Security Operations Center) брутфорс относится к так называемым «громким» атакам — он генерирует хорошо заметные артефакты в журналах событий, что позволяет выявлять его относительно простыми правилами. Ключевым источником данных для детекции на Windows-инфраструктуре выступает событие с кодом **4625** — «An account failed to log on». Это событие фиксирует факт неуспешной попытки аутентификации, включая причину отказа, тип входа и сетевой источник. Набор таких событий легко агрегируется и анализируется средствами SIEM, что превращает Event ID 4625 в основу для корреляционных правил, обнаруживающих брутфорс и схожие техники.

Прежде чем углубляться в технические детали, необходимо чётко разграничить несколько смежных понятий, которые часто путают начинающие специалисты.

* **Online brute-force** (онлайн-брутфорс) — атака, при которой злоумышленник непосредственно взаимодействует с сервисом в реальном времени, отправляя запросы аутентификации по сети. Именно этот тип генерирует события 4625 на атакуемом хосте или контроллере домена и обнаруживается с помощью SIEM.
* **Offline brute-force** (офлайн-брутфорс) — взлом дампов хэшей (например, извлечённых из реестра SAM или базы NTDS.dit) без взаимодействия с живым сервисом. Он не порождает событий 4625 и требует иных методов обнаружения, выходящих за рамки данной темы.
* **Password spraying** (рассеивание паролей) — подвид онлайн-атаки, при котором атакующий перебирает множество учётных записей, используя один или несколько распространённых паролей (например, «Password1», «SeasonYear»). Эта техника позволяет обходить пороговые блокировки, настроенные на конкретную учётную запись, и оставляет характерный паттерн в логах: одна-две попытки на множество разных пользователей с небольшой частотой.
* **Credential stuffing** (набивка учётных данных) — использование ранее скомпрометированных паролей (из утечек) для попыток входа в другие системы. Технически схож с password spraying, но словарь паролей основан на реальных утечках, что повышает шансы успеха.

Различить эти техники на этапе первичного анализа инцидента помогает как раз Event ID 4625, поскольку он содержит поля, позволяющие оценить масштаб атаки и её целенаправленность. Ниже приведена сравнительная таблица, систематизирующая ключевые признаки типовых атак на аутентификацию с точки зрения SOC-аналитика.

| Тип атаки | Паттерн событий 4625 | Количество учётных записей | Количество исходных IP | Временной интервал | Характерный признак |
|-----------|----------------------|----------------------------|------------------------|--------------------|---------------------|
| Online brute-force | Множественные события (до десятков и сотен) для **одной** учётной записи за короткий промежуток | 1 | 1 (редко несколько при смене прокси) | Сконцентрированные в минуты | Одно и то же TargetUserName, высокая частота |
| Password spraying | Небольшое число событий (1-2) для **множества** учётных записей с интервалом в несколько минут-часов | Много (десятки-сотни) | Обычно 1 | Растянутый, с паузами | Разные TargetUserName, одинаковый пароль (не виден напрямую) |
| Легитимный ошибочный ввод | Отдельные 4625 с типовыми кодами ошибок (0xC000006A – неверный пароль, 0xC0000064 – неизвестный пользователь) | 1–2 | Разные | Случайные | Отсутствие корреляции с успешным входом, небольшой объём |

Для SOC L1 это разделение критически важно: истинный брутфорс, как правило, требует немедленной реакции (эскалации или блокировки источника), в то время как изолированный ложный ввод может быть проигнорирован или отправлен на накопление статистики. Корреляционные правила помогают автоматизировать выделение значимых инцидентов из фонового шума.

Говоря о Windows-среде, необходимо сразу отделить событие 4625 от его парного аналога — **Event ID 4624** («An account was successfully logged on»). Если 4625 сообщает о неудаче, то 4624 фиксирует успешный вход, включая такие же поля Logon Type и Network Information. Связка этих двух событий лежит в основе продвинутых корреляций, способных выявить удачную попытку подбора пароля, когда за серией 4625 следует 4624 с совпадающими параметрами. Кроме того, нередко используются события 4672 (привилегированный вход) и 4776 (проверка учётных данных на контроллере домена), однако для детекции брутфорса уровня L1 центральным является именно 4625.

Корреляционное правило в SIEM представляет собой конструкцию, которая агрегирует низкоуровневые события (raw logs) и генерирует инцидент, если за определённый промежуток времени накапливается заданное количество событий, удовлетворяющих условию. Простейшее правило брутфорса выглядит так: «если в течение 60 секунд с одного IP-адреса зафиксировано 5 и более событий 4625 для одной учётной записи, создать алерт с высоким приоритетом». Именно подобные правила являются первым эшелоном защиты, который и эксплуатирует аналитик L1.

Таким образом, Event ID 4625 выступает как атомарный сигнал, а корреляционные правила — как детектор аномально высокой частоты таких сигналов, превращающий их в actionable алерты. Далее мы рассмотрим внутреннее устройство события и правил, чтобы понять, какие поля и параметры определяют качество детекции.

## 2. Анатомия события 4625 и структура корреляционного правила

### 2.1 Детальный разбор полей Event ID 4625

Событие с кодом 4625 регистрируется на том компьютере, на котором была предпринята попытка входа. Для доменной аутентификации это может быть либо рабочая станция (если вход локальный или через RDP), либо контроллер домена (при сетевой проверке учётных данных). Содержимое события варьируется в зависимости от версии Windows и способа логирования, но ключевые поля сохраняются неизменными. Ниже представлена структура в виде набора наиболее информативных секций.

```json
{
  "EventID": 4625,
  "Provider": { "Name": "Microsoft-Windows-Security-Auditing" },
  "EventData": {
    "SubjectUserSid": "S-1-0-0",
    "SubjectUserName": "-",
    "SubjectDomainName": "-",
    "SubjectLogonId": "0x0",
    "TargetUserSid": "S-1-0-0",
    "TargetUserName": "jdoe",
    "TargetDomainName": "CORP",
    "Status": "0xC000006A",
    "FailureReason": "%%2313",
    "SubStatus": "0xC000006A",
    "LogonType": 3,
    "LogonProcessName": "NtLmSsp",
    "AuthenticationPackageName": "NTLM",
    "WorkstationName": "DESKTOP-VICTIM02",
    "TransmittedServices": "-",
    "LmPackageName": "-",
    "KeyLength": 0,
    "ProcessId": "0x0",
    "ProcessName": "-",
    "IpAddress": "192.168.56.101",
    "IpPort": "52456"
  }
}
```

*Иллюстративная структура, значения зависят от конкретной среды.*

Рассмотрим наиболее значимые поля с практической точки зрения.

**TargetUserName** и **TargetDomainName** — целевая учётная запись, для которой фиксируется неудачная попытка. Это основной идентификатор, по которому группируются события при анализе. Если в логах фигурирует множество разных имён, подозрение склоняется к password spraying. Если повторяется одно и то же имя — это классический брутфорс.

**LogonType** — числовой код, указывающий тип входа, то есть способ, которым пользователь (или процесс) пытался аутентифицироваться. Наиболее частые значения в контексте брутфорса:

- **2** (Interactive) — интерактивный вход с консоли (локально или через физическую клавиатуру). Встречается редко при атаках, но может указывать на физический доступ.
- **3** (Network) — сетевой вход без интерактивной оболочки (доступ к общим папкам, удалённому управлению через WinRM, PowerShell Remoting). Именно Logon Type 3 характерен для большинства сетевых атак, включая попытки подбора к общим ресурсам.
- **10** (RemoteInteractive) — вход через службу терминалов (RDP). Типичен для атак на публично доступные RDP-серверы. События с LogonType 10 и частыми неудачами — явный сигнал брутфорса на RDP.
- **7** (Unlock) — разблокировка рабочей станции. Может фигурировать при попытках подбора пароля на заблокированном экране.
- **5** (Service) — запуск службы. Неудачные входы этого типа чаще вызваны проблемами с конфигурацией сервисных учётных записей, а не атаками.

**Failure Reason и коды Status/SubStatus** — детализируют причину отказа. Поле `Status` представляет собой NTSTATUS-код. Наиболее важные коды приведены в таблице ниже (на основе [документации ManageEngine](https://www.manageengine.com/products/active-directory-audit/kb/windows-security-log-event-id-4625.html) и официальной документации Microsoft).

| Status (hex) | SubStatus (hex) | Описание | Значение для триажа |
|--------------|------------------|----------|---------------------|
| 0xC0000064 | совпадает | Указанное имя пользователя не существует | Злоумышленник перебирает по словарю имён. Если событий много с разными именами — вероятен spraying. |
| 0xC000006A | совпадает | Неверный пароль для существующей учётной записи | Наиболее характерный код для активного брутфорса. Большое число событий с этим кодом — высокая уверенность в атаке. |
| 0xC0000234 | совпадает | Учётная запись заблокирована | Серия предыдущих неудач привела к блокировке. Полезен для подтверждения брутфорса. |
| 0xC0000072 | совпадает | Учётная запись в настоящий момент отключена | Может быть признаком того, что злоумышленник пытается войти под давно неиспользуемой учёткой. |
| 0xC000006D | совпадает | Попытка входа не разрешена на данном компьютере (например, пользователь не имеет права локального входа) | Показывает, что атакующий пытается использовать действительную учётную запись, но на неверной системе. |
| 0xC000006F | совпадает | Вход в неразрешённое время | Обычно связан с политикой ограничения рабочих часов. Может быть признаком попытки компрометации во внерабочее время. |
| 0xC0000193 | совпадает | Срок действия учётной записи истёк | Потенциально компрометация старой учётной записи. |

Важное уточнение: в новых версиях Windows некоторые описания `FailureReason` могут отображаться в виде текста (например, «Unknown user name or bad password.»), что упрощает поиск. Это используется в правилах SIEM (как показано в [примере UserGate](https://docs.usergate.com/primery-nastrojki-pravila-analitiki_947.html)), где применяется регулярное выражение к полю `data`.

**Network Information** — cодержит `IpAddress` и `IpPort` источника попытки. Это ключевой идентификатор атакующего хоста, позволяющий блокировать атаку на сетевом уровне. При анализе важно учитывать, что в случае проксирования или NAT-трансляции IP может быть не единственным; источники могут меняться.

### 2.2 Корреляционное правило: логика и компоненты

Корреляционное правило, нацеленное на выявление брутфорса, строится вокруг трёх базовых параметров: частота, временное окно и группировка. В терминологии большинства SIEM-систем (Wazuh, Elastic Security, Splunk) это реализуется с помощью конструкции, включающей:

- **if_matched_sid** (или аналогичный идентификатор) — ссылка на базовое правило, которое срабатывает на каждое отдельное событие 4625. Базовое правило может быть встроенным (в Wazuh это, например, правило с `id="60112"`, соответствующее «Windows logon failure», как указано в [статье по настройке Wazuh](https://medium.com/@sathinsha/detecting-a-brute-force-attack-on-wazuh-lab-49b2e3834141)) или пользовательским.
- **frequency** — целое число, порог срабатывания. Если за заданный timeframe базовое правило сработало не менее `frequency` раз, правило корреляции генерирует алерт.
- **timeframe** — временной интервал в секундах, в пределах которого накапливается счётчик.

Дополнительно могут использоваться поля для группировки, чтобы подсчёт вёлся не глобально, а в разрезе определённых атрибутов, например, одинакового `src_ip` или одинакового `TargetUserName`. Без грамотной группировки правило будет считать все 4625 по всем пользователям и источникам, что приведёт к ложным срабатываниям.

Схематически работу простейшего правила можно представить так:

```text
Сырые события (Event Log)
        │
        ▼
[Базовое правило: Event ID 4625]
        │
        ▼
[Аккумулятор: подсчёт совпадений за timeframe]
        │
        ├─ frequency достигнуто? ──▶ [Генерация алерта корреляции, level=high]
        │
        └─ frequency не достигнуто ──▶ сброс счётчика по истечении timeframe
```

*Иллюстративная схема потока обработки правила.*

В реальных продуктах конфигурация правила выглядит как XML или YAML. Пример из Wazuh (фрагмент):

```xml
<group name="windows,bruteforce">
  <rule id="100100" level="10" frequency="5" timeframe="60">
    <if_matched_sid>60112</if_matched_sid>
    <same_source_ip />
    <description>Multiple Windows logon failures from same source IP (possible brute-force).</description>
  </rule>
</group>
```

В этом примере `same_source_ip` означает группировку по IP-адресу источника: алерт генерируется, когда с одного IP за 60 секунд произошло 5 и более неудачных попыток (по правилу 60112). Параметр `level="10"` задаёт высокий приоритет.

Более тонкие правила включают дополнительные условия, например, проверку успешного входа после серии неудач. Такая корреляция может выглядеть как «если за 120 секунд для одной учётной записи было не менее 5 событий 4625, а затем появилось событие 4624 с теми же полями TargetUserName и LogonType = 10, создать критический алерт». Это позволяет автоматически выявлять удавшийся подбор пароля и эскалировать его с наивысшим приоритетом. Подобная логика описана в [Blue Team Cookbook](https://vasilisa-l.gitbook.io/blue-team-cookbook/detection-engineering/top-siem-rules) как улучшенный вариант правила.

Таким образом, корреляционное правило представляет собой не просто счётчик, а гибкий механизм оконно-пороговой детекции с возможностью учёта контекста. Именно от настройки `frequency`, `timeframe` и полей группировки зависит баланс между полнотой обнаружения и уровнем шума.

## 3. Применение и работа с правилами анализа в SOC L1

### 3.1 Триаж алертов брутфорса и дифференциация ложных срабатываний

Получив оповещение от корреляционного правила, аналитик L1 должен за короткое время определить, является ли оно реальным инцидентом или false positive. Типичная последовательность действий включает:

1. **Проверка параметров алерта** в консоли SIEM — сколько событий сгруппировалось, за какой период, с какого IP, на какую учётную запись, какой LogonType преобладает.
2. **Анализ контекста учётной записи** — критичность пользователя (привилегированный или обычный), принадлежность к доменным администраторам, наличие сервисных признаков.
3. **Сравнение с baseline** — использовался ли ранее этот IP для взаимодействия с инфраструктурой, характерно ли такое количество неудач для данного пользователя.
4. **Поиск сопутствующих событий** — есть ли успешный вход 4624 сразу после? Не заблокирована ли учётная запись (событие 4740)?

Частые причины ложных срабатываний на правила брутфорса, о которых должен помнить аналитик:

- **Сервисная учётная запись с истекшим паролем:** если приложение постоянно пытается запустить службу, у которой сменился пароль, может генерироваться множество событий 4625 с LogonType 5 (Service). Такие алерты безопасны для эскалации по безопасности, но требуют устранения проблемы с паролем.
- **Пользователь, забывший сменить пароль в почтовом клиенте:** после смены пароля домена старые сохранённые пароли в Outlook, мобильных устройствах вызывают повторяющиеся отказы с LogonType 3 или 10. Отличаются низкой частотой и отсутствием успешного входа после.
- **Приложения, циклически проверяющие доступность:** некоторые мониторинговые системы могут выполнять проверку учётных данных, что при неверном пароле даст всплеск 4625. Здесь важен белый список легитимных IP-адресов мониторинга.
- **Легитимные пользователи, ошибающиеся при вводе:** 2-3 попытки в течение минуты не должны вызывать корреляционное правило, если threshold настроен адекватно (например, 5 попыток). Однако при низких порогах (3 попытки) возможен шум.

Поэтому на этапе внедрения правил важно калибровать `frequency` и `timeframe` под специфику организации, а также при необходимости добавлять исключения по полям `LogonType` и статусам ошибок.

### 3.2 Конфигурация правила на практике

Рассмотрим практический пример создания правила детекции брутфорса в SIEM-системе Wazuh, используя Event ID 4625. Предположим, что Wazuh-агенты установлены на Windows-хостах и успешно пересылают логи канала Security. Встроенное правило 60112 уже сопоставляет любое событие с кодом 4625 и присваивает ему уровень 3 (низкий). Нам необходимо поверх него построить корреляционное правило, которое будет генерировать алерт при 5 неудачах в течение 60 секунд с одного источника.

Файл `/var/ossec/etc/rules/local_rules.xml` дополняется следующим блоком:

```xml
<group name="windows,bruteforce_l1">
  <rule id="100150" level="10" frequency="5" timeframe="60">
    <if_matched_sid>60112</if_matched_sid>
    <same_source_ip />
    <description>Possible brute-force: 5 failed logons (Event 4625) from same IP in 60 sec.</description>
    <mitre>
      <id>T1110.001</id>
    </mitre>
  </rule>
</group>
```

После перезагрузки менеджера Wazuh правило становится активным. Любой всплеск неудачных входов с одного IP, достаточный для превышения порога, породит алерт уровня 10.

Для подтверждения работоспособности можно выполнить ручную симуляцию, например, используя Hydra (как в сквозном примере ниже), или даже просто несколько раз ввести неверный пароль при RDP-подключении. Алерт будет отображён в Wazuh Dashboard с деталями: `rule.id:100150`, `rule.description`, список IP и учётных записей, участвовавших в корреляции.

Важно убедиться, что базовое правило действительно срабатывает на конкретной среде. Это можно сделать через `wazuh-logtest` или просмотрев алерты в `/var/ossec/logs/alerts/alerts.json`. Если правило 60112 не активно или замещено другим, корреляция не сработает.

### 3.3 Ручной поиск и анализ логов с помощью встроенных средств Windows

При отсутствии централизованного SIEM или в целях углублённого расследования аналитик может обратиться к журналу событий на отдельном хосте. Наиболее быстрый способ извлечь все события 4625 за период — PowerShell. Например:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625} -MaxEvents 100 |
  Select-Object TimeCreated,
    @{n='TargetUser';e={$_.Properties[5].Value}},
    @{n='Domain';e={$_.Properties[6].Value}},
    @{n='LogonType';e={$_.Properties[10].Value}},
    @{n='IP';e={$_.Properties[19].Value}}
```

Этот однострочник выводит время, целевую учётную запись, тип входа и IP-адрес источника для последних 100 событий. Аналитик может отсортировать вывод и вручную обнаружить аномальную концентрацию записей.

Для более точной проверки можно агрегировать подсчёт по IP и пользователю:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625} -MaxEvents 1000 |
  Group-Object { "{0}_{1}" -f $_.Properties[19].Value, $_.Properties[5].Value } |
  Sort-Object Count -Descending |
  Select-Object -First 5 Count, Name
```

Такой подход помогает быстро выявить подозрительную активность даже без корреляционного движка, что незаменимо при инцидентах, когда SIEM недоступен или не покрывает нужные хосты.

### 3.4 Продвинутые корреляции: связка «4625 → 4624» и поведенческий анализ

Пороговое правило первого уровня ловит грубые попытки подбора, но может пропустить медленный spraying или случайную удачу. Для повышения качества детекции применяют двухэтапные корреляции. Первый этап фиксирует аномальный рост 4625 (например, 10 попыток за 5 минут с одного IP), а второй — ищет последующий успешный вход 4624 с совпадающими полями (TargetUserName, IP). Это принципиально меняет приоритет инцидента: теперь мы говорим не о попытке, а о состоявшейся компрометации.

Пример правила для Wazuh, реализующего эту логику:

```xml
<rule id="100200" level="12" frequency="1" timeframe="120">
  <if_matched_sid>100150</if_matched_sid>
  <if_sid>60106</if_sid>  <!-- 60106 — базовое правило для 4624 -->
  <same_source_ip />
  <same_user />
  <description>Brute-force successful: 4625 burst followed by successful logon 4624.</description>
</rule>
```

*Иллюстративная конфигурация, требует адаптации под конкретные идентификаторы правил.*

В данной конструкции правило 100200 срабатывает, если за 120 секунд после срабатывания корреляции брутфорса (100150) появляется событие успешного входа (правило 60106) с тем же IP и тем же пользователем. Уровень 12 указывает на критичность.

На практике подобные составные правила могут давать больше ложных срабатываний, так как успешный вход может произойти от легитимного пользователя на фоне фонового шума, поэтому их обязательно сопровождать белыми списками доверенных IP и учётных записей.

Таким образом, работа с Event ID 4625 и корреляционными правилами — это многоуровневый процесс: от простого счётчика к контекстно-зависимому анализу, который в совокупности обеспечивает эшелонированную защиту от атак на аутентификацию.

## Сквозной практический пример: выявление брутфорса на RDP с помощью Wazuh

### Исходные условия

Лабораторная среда: Windows Server 2019 (целевая машина RDP-VICTIM) с настроенным аудитом входов, Wazuh агент 4.x, подключённый к Wazuh Manager 4.x. Атакующая машина Kali Linux с установленной Hydra. Задача: продемонстрировать, как корреляционное правило фиксирует онлайн-брутфорс и как аналитик L1 подтверждает инцидент.

### Шаг 1: Включение аудита попыток входа и отправка логов в SIEM

Убедимся, что на целевом Windows-сервере активна политика аудита «Audit Logon Events» для успешных и неудачных попыток. С помощью `auditpol` можно проверить состояние:

```cmd
auditpol /get /category:"Logon/Logoff"
```

Вывод должен содержать строку:
```
Logon                                    Success and Failure
```

Если политика не задана, включить её можно командой:
```cmd
auditpol /set /category:"Logon/Logoff" /success:enable /failure:enable
```

В конфигурационном файле агента Wazuh (`ossec.conf`) убеждаемся, что канал Security отслеживается:
```xml
<localfile>
  <location>Security</location>
  <log_format>eventchannel</log_format>
</localfile>
```

После перезапуска агента все события 4625 начнут поступать на менеджер.

### Шаг 2: Создание корреляционного правила в Wazuh

На Wazuh Manager добавляем в `local_rules.xml` правило из раздела 3.2. Для наглядности повторим его:

```xml
<group name="windows,bruteforce_l1">
  <rule id="100150" level="10" frequency="5" timeframe="60">
    <if_matched_sid>60112</if_matched_sid>
    <same_source_ip />
    <description>Possible brute-force: 5 failed logons (Event 4625) from same IP in 60 sec.</description>
  </rule>
</group>
```

После сохранения файла перезапускаем менеджер. Проверяем загрузку правила:

```bash
sudo tail -f /var/ossec/logs/ossec.log | grep -i "100150"
```

Если ошибок парсинга нет, правило активно.

### Шаг 3: Симуляция атаки с помощью Hydra

С атакующей машины выполняем тестовый подбор пароля по RDP. Предположим, в Active Directory существует пользователь `analyst_user`, и мы пытаемся угадать его пароль, используя словарь из нескольких вариантов:

```bash
hydra -t 1 -w 5 -l analyst_user -P /usr/share/wordlists/rockyou.txt rdp://192.168.56.20
```

Ожидаемый вывод в терминале будет содержать строки вида:
```
[DATA] attacking rdp://192.168.56.20:3389/
[3389][rdp] host: 192.168.56.20   login: analyst_user   password: P@ssw0rd
```

В реальности для демонстрации корреляции достаточно, чтобы Hydra выполнила 5 неверных попыток за минуту. Это гарантирует превышение порога.

### Шаг 4: Просмотр сработавшего алерта в SIEM

Спустя минуту после начала атаки на Wazuh Dashboard появится алерт. Пример фрагмента соответствующей записи из `alerts.json`:

```json
{
  "timestamp": "2025-02-20T10:12:30.456+0000",
  "rule": {
    "id": "100150",
    "level": 10,
    "description": "Possible brute-force: 5 failed logons (Event 4625) from same IP in 60 sec.",
    "mitre": { "id": ["T1110.001"] }
  },
  "agent": { "id": "001", "name": "RDP-VICTIM" },
  "data": {
    "srcip": "192.168.56.101",
    "dstuser": "analyst_user",
    "count": 5
  },
  "full_log": "Event ID 4625, Logon Type 10, ..."
}
```

В интерфейсе Wazuh аналитик L1 видит описание инцидента, IP-адрес источника и учётную запись, что позволяет немедленно принять меры.

### Шаг 5: Проверка успешного входа и эскалация

Аналитик дополнительно ищет события 4624 (успешный вход) с фильтрацией по тому же IP и пользователю. В консоли Wazuh можно выполнить запрос:

```
rule.id:60106 AND data.srcip:192.168.56.101 AND data.dstuser:analyst_user
```

Если Hydra случайно подобрала пароль (как в примере вывода), то будет зафиксировано событие 4624 с LogonType 10. Это немедленно повышает серьёзность инцидента до критической. В противном случае алерт остаётся лишь попыткой брутфорса, что требует блокировки IP на межсетевом экране и уведомления ответственных.

Альтернативно, для локальной проверки на сервере RDP-VICTIM можно воспользоваться PowerShell:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4624} -MaxEvents 50 |
  Where-Object { $_.Properties[18].Value -eq '192.168.56.101' } |
  Select-Object TimeCreated, @{n='User';e={$_.Properties[5].Value}}, @{n='LogonType';e={$_.Properties[8].Value}}
```

Результат либо покажет событие успешного входа для `analyst_user`, либо не покажет — тогда атака безрезультатна.

### Ожидаемый вывод

Сквозной пример демонстрирует полный цикл: от включения аудита и создания простого корреляционного правила до выявления атаки в реальном времени и последующего поиска признаков компрометации. Студент на практике убеждается, что Event ID 4625 — не просто запись в журнале, а фундамент SOC-детекции, а корреляционные правила превращают одиночные неудачи в actionable intelligence.
