# Событие 4624: удалённый интерактивный сеанс (Logon Type 10)

## 1. Контекст и базовые понятия: аудит входа в Windows и тип 10

Событие с кодом 4624 генерируется подсистемой безопасности Windows при каждой успешной аутентификации, создающей новый сеанс входа. Оно записывается в журнал безопасности (Security Event Log) независимо от способа входа: интерактивный, сетевой, пакетный, служебный или удалённый. Внутренний механизм формирования этого события опирается на API Local Security Authority (LSA), которое после успешной проверки учётных данных создаёт маркер доступа и уведомляет подсистему аудита. Для аналитика SOC L1 критически важно не только зафиксировать факт успешного входа, но и верно классифицировать тип сеанса — именно для этого в событии 4624 присутствует поле Logon Type.

Тип 10 (RemoteInteractive) определяется ОС, когда пользователь инициирует интерактивный сеанс через удалённые службы терминалов: протокол RDP на стандартном порту 3389/TCP или его обёртки RemoteFX/RemoteApp. Визуально это выглядит как графический вход в систему по RDP, запуск оболочки explorer.exe и получение доступа к рабочему столу. Технически между клиентом и сервером устанавливается терминальная сессия, после чего служба Winlogon на сервере выполняет те же шаги, что и при локальном входе, за исключением факта передачи ввода-вывода по сети.

Путаница между Logon Type 10 и другими типами входа — одна из типичных ошибок начинающих аналитиков. Приведённая ниже таблица сопоставляет ключевые типы, с которыми может столкнуться специалист Tier 1 при первичном триаже.

| Тип | Название | Как возникает | Ключевые поля события | Практический риск |
| --- | --- | --- | --- | --- |
| 2  | Interactive | Консольный вход с клавиатуры и экрана сервера или VM (физическая консоль, гипервизор) | Session Name начинается с Console, Source Network Address чаще отсутствует или ::1/127.0.0.1 | Доступ только при физическом присутствии или доступе к гипервизору |
| 3  | Network | Сетевой вход без интерактивной оболочки (SMB-подключение к общим папкам, WinRM, PSRemoting, планировщик задач с сетевыми учётными данными) | Authentication Package преобладает Kerberos или NTLM, Session Name – пусто, часто встречается Elevated Token No | Часто легитимен для серверных служб, но подозрителен при массовых аномалиях с пользовательских учёток |
| 4  | Batch | Запуск задания планировщиком задач или пакетным процессом | Обычно от имени SYSTEM или специальной учётной записи, Security ID субъекта может быть SYSTEM | Как правило легитимен, если не используется злоумышленником для доступа через at-команду |
| 5  | Service | Запуск службы от имени заданной учётной записи | Subject часто SYSTEM, Logon Process – Advapi, часто без Elevated Token | Используется при компрометации через вредоносные службы |
| 7  | Unlock | Разблокировка существующей сессии (восстановление после заставки) | Logon ID совпадает с ранее созданным сеансом, Network Address отсутствует | Может маскировать реальный вход, если злоумышленник повторно использует сессию |
| 8  | NetworkCleartext | Сетевой вход с передачей пароля открытым текстом (устаревший, но встречается при Basic-аутентификации IIS) | Протокол аутентификации чаще ClearText | Устаревший, почти не используется, но может быть индикатором legacy-систем |
| 9  | NewCredentials | Функция «Запуск от имени другого пользователя» (RunAs) без выхода из текущего сеанса | Subject остаётся текущий пользователь, NewLogon – альтернативная учётка, Logon ID разный | Легитимно для администраторов, злоумышленники применяют runas с получением привилегированной сессии |
| 10 | RemoteInteractive | Полноценный удалённый рабочий стол RDP | Session Name содержит «RDP-Tcp», Source Network Address содержит реальный IP‑адрес клиента, Source Port – динамический порт клиента, Elevated Token обычно Yes | Основной вектор удалённого управления, частый объект атак перебора и использования украденных учётных данных |
| 11 | CachedInteractive | Вход с использованием кэшированных учётных данных домена (отключенный контроллер домена) | Logon Process – CachedInteractive, разрешён только для доменных учёток | Позволяет вход при отсутствии DC, может срабатывать на ноутбуках вне сети |
| 12 | CachedRemoteInteractive | Аналог 11 для RDP‑сессий в отсутствие DC | Сочетает свойства 10 и 11 | Опасен, если злоумышленник получил физический доступ к изолированной машине |

При проведении расследования аномального входа SOC‑аналитик в первую очередь будет искать события с типом, допускающим интерактивное взаимодействие, — это именно тип 2 и тип 10. В большинстве организаций доступ по RDP ограничен определёнными учётными записями администрирования и белыми IP‑адресами. Любой успешный вход типа 10, не соответствующий этим параметрам, потенциально представляет собой инцидент, требующий дальнейшего расследования. Даже полностью легитимный RDP‑сеанс оставляет после себя ценнейшие артефакты: IP-адрес клиента, имя его компьютера (если включено NLA или передача имени рабочей станции), пакет аутентификации и временные метки, позволяющие простроить временную линию активности злоумышленника.

Выделим ещё один важный аспект: в обиходе иногда смешивают удалённый сеанс с типом 3 (доступ к файловым шарам) или с WinRM-сессиями. РDP‑сессия — интерактивна, у пользователя есть рабочий стол, возможность запуска графических приложений; WinRM или PSRemoting — неинтерактивны, работают через командную строку, и им соответствует тип 3. Эта разница принципиальна, потому что злоумышленник, получивший RDP‑доступ, получает гораздо более удобный и опасный плацдарм.

## 2. Внутреннее устройство: структура события 4624 с Logon Type 10

Событие 4624 формируется стандартным образом как экземпляр событийного журнала провайдера «Microsoft-Windows-Security-Auditing». Схема полей закреплена в документированной структуре события, доступной через GUI просмотровщика или командлеты PowerShell. Ниже приведена иллюстративная JSON‑схема, адаптированная под формат, возвращаемый командой `Get-WinEvent -FilterXml`, но в целях наглядности упрощённая до ключевых подразделов.

```json
{
  "Event": {
    "System": {
      "EventID": 4624,
      "Provider": {"Name": "Microsoft-Windows-Security-Auditing", "Guid": "<GUID провайдера>"},
      "TimeCreated": {"SystemTime": "<временная метка UTC>"},
      "Computer": "<имя машины, записавшей событие>"
    },
    "EventData": {
      "SubjectUserSid": "<SID инициатора входа>",
      "SubjectUserName": "<учётная запись, выполнившая вход>",
      "SubjectDomainName": "<домен этой учётной записи>",
      "SubjectLogonId": "<идентификатор сеанса инициатора>",
      "TargetUserSid": "<SID вошедшего пользователя>",
      "TargetUserName": "<вошедшая учётная запись>",
      "TargetDomainName": "<домен вошедшей учётной записи>",
      "TargetLogonId": "<идентификатор нового сеанса>",
      "LogonType": "10",
      "LogonProcessName": "User32",
      "AuthenticationPackageName": "Negotiate",
      "WorkstationName": "<NetBIOS-имя клиентской рабочей станции>",
      "LogonGuid": "<глобально уникальный идентификатор входа>",
      "TransmittedServices": "-",
      "LmPackageName": "-",
      "KeyLength": 0,
      "ProcessId": "<PID процесса, принявшего вход>",
      "ProcessName": "C:\\Windows\\System32\\svchost.exe",
      "IpAddress": "<IPv4/IPv6-адрес клиента>",
      "IpPort": "<TCP-порт клиента>",
      "ImpersonationLevel": "%%1833",
      "RestrictedAdminMode": "-",
      "TargetOutboundUserName": "-",
      "TargetOutboundDomainName": "-",
      "VirtualAccount": "%%1843",
      "TargetLinkedLogonId": "<0x786...>",
      "ElevatedToken": "%%1842"
    }
  }
}
```

Для логического разбора поля удобно разделить на три смысловых блока.

1. **Субъект (Subject).** Это учётная запись, которая непосредственно инициировала вход. При локальном входе субъект обычно совпадает с целевой учётной записью. Для RDP‑сессии субъектом выступает служба Network Service, а поля `SubjectUserSid`, `SubjectUserName`, `SubjectDomainName` и `SubjectLogonId` заполняются значениями, относящимися к этой служебной учётной записи. Иногда в роли субъекта может быть учётная запись компьютера (Machine Account), если вход выполняется через службы делегирования. Для аналитика L1 интерес обычно представляет только блок целевого пользователя, но при сложных расследованиях субъект помогает восстановить цепочку делегирования.

2. **Целевая учётная запись (Target / New Logon).** `TargetUserName`, `TargetDomainName` и `TargetUserSid` идентифицируют того, кто вошёл в систему. `TargetLogonId` — это уникальный Locally Unique Identifier (LUID), назначаемый каждому новому сеансу и повторно используемый только после перезагрузки. Этот идентификатор критичен для корреляции с другими событиями того же сеанса (например, создание процесса — 4688, выход из системы — 4634).

3. **Сетевые артефакты и особенности RDP.** Именно здесь события с типом 10 демонстрируют поведение, отличное от остальных типов. `IpAddress` содержит реальный IPv4- или IPv6-адрес клиента (не адрес шлюза терминалов, если не используется проксирование), `IpPort` — динамический порт исходного endpoint’а, что редко используется при расследованиях, но может помочь в сопоставлении с сетевыми логами. `WorkstationName` фиксирует NetBIOS-имя рабочей станции, с которой осуществлён вход, если в настройках RDP-клиента включена соответствующая опция. Эта информация часто является лучшим индикатором источника подключения, так как IP может быть динамическим или NAT-адресом, а имя машины — более стабильным признаком.

Поле `AuthenticationPackageName` показывает фактический протокол аутентификации, использованный для создания сеанса. Для доменных учётных записей чаще всего фигурирует «Negotiate», который внутри себя может эскалироваться до Kerberos или NTLM. Прямое указание «NTLM» при доменной учётной записи в инфраструктуре с Kerberos может служить признаком нестандартного поведения: например, злоумышленник использует аутентификацию Pass-the-Hash или настроил принудительный NTLM для обхода защиты.

`LogonGuid` — это глобально-уникальный 128-битный идентификатор, который позволяет связывать события на разных машинах домена при расследовании в SIEM, особенно если включён журнал транзитных событий входа на контроллере домена (событие 4769). Однако его применение требует централизованного сбора и корреляции.

Структурную визуализацию процесса создания удалённого интерактивного сеанса можно представить упрощённой ASCII-схемой:

```text
[Клиент RDP] ──(TCP:3389 / NLA)──▶ [Winlogon на сервере] ──(Credential Validation)──▶ LSASS
                                          │
                                          └──(создание сеанса)──▶ Userinit → explorer.exe
                                          │                                 │
                                          └──(запись события 4624 с Logon Type 10)──▶ Security Event Log
```

Поле `ElevatedToken` принимает значение `%%1842` («Yes») или `%%1843` («No»). Для административных учётных записей, подпадающих под UAC, первый вход всегда даёт `Yes`, но после фильтрации UAC создаётся разделённый маркер. Важно понимать, что ElevateToken=Yes не обязательно означает, что сеанс обладает полными привилегиями — разделённые маркеры и UAC Remote Restrictions (включённые по умолчанию на многих версиях) могут ограничивать административные права, даже если RDP‑пользователь — член группы администраторов. Для L1‑аналитика поле ElevatedToken служит быстрым индикатором потенциальной опасности: если RDP‑сессия не должна иметь повышенных привилегий, а ElevatedToken=Yes, это красный флаг.

Итак, внутренняя структура события при Logon Type 10 концентрирует в себе исчерпывающий сетевой и системный контекст, позволяя быстро провести первичную оценку аномалии без обращения к дополнительным источникам.

## 3. Применение и работа с событием 4624 типа 10 в SOC Level 1

Аналитик первого уровня получает сигнал о подозрительной активности обычно из SIEM‑системы, настроенной на корреляцию событий. Правила корреляции могут быть построены следующим образом: для каждой учётной записи, не входящей в «белый список удалённых пользователей», или для любого IP, не принадлежащего доверенным сегментам, инцидент генерируется при появлении события 4624 с LogonType=10. Более тонкие корреляции могут учитывать территориальное расстояние, время суток, частоту входов.

На этапе первичного триажа L1‑специалист должен ответить, используя поля события, на несколько контрольных вопросов:

- Является ли учётная запись легитимной для удалённого интерактивного доступа? (Сопоставить с перечнем разрешённых учёток.)
- Источник входа (IP, WorkstationName) совпадает с ожидаемой точкой сети? (DNS‑имя, зона внутренней сети vs внешний IP.)
- Время входа укладывается в рамки рабочего времени, принятого для данной учётной записи, включая плановые ночные операции?
- Есть ли сопроводительные аномалии: несколько неудачных попыток (событие 4625) за короткое время непосредственно перед успехом, указывающие на brute-force, или вход сразу после создания учётной записи?
- Отличается ли рабочая станция-источник от обычных рабочих мест данного пользователя?

Практическая работа с событиями в среде Windows начинается с извлечения их из журнала безопасности. Ниже показан пример команды PowerShell, которую аналитик может использовать на целевой машине или удалённо, для получения всех событий 4624 с типом 10 за последние 24 часа.

```powershell
$startTime = (Get-Date).AddHours(-24)
$filterXML = @"
<QueryList>
  <Query Id="0" Path="Security">
    <Select Path="Security">
      *[System[(EventID=4624) and TimeCreated[timediff(@SystemTime) &lt;= 86400000]]]
    </Select>
  </Query>
</QueryList>
"@
Get-WinEvent -FilterXml $filterXML | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = @{} 
    $xml.Event.EventData.Data | ForEach-Object { $data[$_.Name] = $_.'#text' }
    [PSCustomObject]@{
        Time = $_.TimeCreated
        IP = $data['IpAddress']
        User = $data['TargetUserName']
        Domain = $data['TargetDomainName']
        LogonType = $data['LogonType']
        Workstation = $data['WorkstationName']
        AuthPackage = $data['AuthenticationPackageName']
    }
} | Where-Object { $_.LogonType -eq '10' } | Format-Table -AutoSize
```

Результатом такой команды станет таблица, в которой аналитик сразу увидит отличающиеся записи, например, IP-адрес из внешней сети или нетипичное имя рабочей станции. Подчеркнём, что `WorkstationName` заполняется только при включённой сетевой аутентификации уровня NLA, и именно NLA помогает получить это поле ещё до полного создания сеанса.

Типичная ошибка новичка — пытаться искать входы типа 10, ориентируясь только на процесс `LogonProcessName = "User32"`. Хотя для типа 10 это стандартное значение, похожее поле встречается и при типе 2, а также при Unlock. Правильный ключ — именно `LogonType = 10`.

Связка с соседними событиями даёт более полную картину:

- **Событие 4625** (неудачный вход) с тем же TargetUserName и IpAddress за несколько секунд или минут до успеха практически гарантирует brute‑force или перебор по словарю.
- **Событие 4648** (попытка входа с явными учётными данными) может объяснить, почему субъект и целевая учётка отличаются: например, администратор запустил RDP-клиент с параметрами другого пользователя.
- **Событие 4778 / 4779** (переподключение сеанса) позволяет понять, что сессия была не создана заново, а восстановлена после отключения — это важно, потому что 4624 будет только при первом входе, а затем злоумышленник может подключаться к существующему сеансу без нового события входа.

Для анализа источника IP‑адреса аналитик может использовать стандартные средства ресолвинга DNS и геолокации, но прямой вызов сторонних сервисов обычно автоматизирован в SIEM. На уровне Windows-машины можно выполнить `Resolve-DnsName`, однако результат зависит от PTR-записи, которую контролирует провайдер IP, поэтому внешний адрес часто возвращает лишь generic-имя, предоставляемое хостингом. Тем не менее совпадение PTR с ожидаемым хостом в собственной сети может снять подозрения.

Одним из мощных методов выявления аномалий является сравнение с поведенческим базовым профилем (baseline). Если за прошедший месяц конкретная учётная запись ни разу не заходила через RDP, а сегодня произошло 3 входа с разных стран, это явный инцидент. В небольших SOC без UEBA-систем аналитик может вручную построить такой профиль, используя команду наподобие:

```powershell
Get-WinEvent -LogName Security -MaxEvents 500000 | 
    Where-Object { $_.Id -eq 4624 } | 
    ForEach-Object { $xml = [xml]$_.ToXml(); $d = @{}; $xml.Event.EventData.Data | % { $d[$_.Name] = $_.'#text' }; [PSCustomObject]@{User=$d['TargetUserName']; Date=$_.TimeCreated.ToString('yyyy-MM-dd'); IP=$d['IpAddress']; Type=$d['LogonType']} } |
    Where-Object { $_.Type -eq '10' } |
    Group-Object User | ForEach-Object { 
        $user = $_.Name
        $IPs = ($_.Group.IP | Sort-Object -Unique) -join ', '
        [PSCustomObject]@{User=$user; UniqueIPs=$IPs; Count=$_.Count}
    }
```

Эта команда даст сводку по каждому пользователю, сколько раз и с каких IP он заходил удалённо; аномалия выделится сразу.

В организационном плане L1‑аналитик после выявления аномального события 4624/10 должен передать кейс на уровень L2 с уже собранными полями события и предварительным вердиктом. Чёткое документирование всех полей и связей сокращает время реагирования и является частью цикла постоянного улучшения правил корреляции.

## 4. Сквозной практический пример: расследование RDP-входа с нехарактерного IP

**Исходные условия**

- Контролируемая среда: Active Directory, сервер Windows Server 2022 с ролью RDS, SIEM собирает журналы со всех хостов.
- Аналитик SOC L1 получил правило срабатывания на событие 4624 с Logon Type 10 для пользователя `svc_backup`, IP‑адрес источника 203.0.113.45 (внешний диапазон, не принадлежащий организации).
- Учётная запись `svc_backup` является сервисной, по политике никогда не должна использоваться для интерактивного RDP-входа.
- Необходимо подтвердить инцидент и эскалировать на L2.

**Шаг 1. Извлечение всех событий 4624 с типом 10 для подозрительной учётной записи за последние сутки**

Аналитик выполняет PowerShell-команду на самом сервере, к которому было обращение, либо на сборщике событий SIEM, используя доступ к журналу.

```powershell
$query = @"
<QueryList>
  <Query Id="0" Path="Security">
    <Select Path="Security">
      *[System[(EventID=4624)]] and
      *[EventData[Data[@Name='TargetUserName']='svc_backup']]
    </Select>
  </Query>
</QueryList>
"@
Get-WinEvent -FilterXml $query | ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = @{}
    $xml.Event.EventData.Data | ForEach-Object { $data[$_.Name] = $_.'#text' }
    if ($data['LogonType'] -eq '10') {
        [PSCustomObject]@{
            Time      = $_.TimeCreated
            User      = $data['TargetUserName']
            SrcIP     = $data['IpAddress']
            Workstation = $data['WorkstationName']
            Auth      = $data['AuthenticationPackageName']
        }
    }
} | Format-Table -AutoSize
```

**Результат (иллюстративная схема вывода):**

```
Time                     User        SrcIP        Workstation    Auth
----                     ----        -----        -----------    ----
20.03.2025 03:14:55      svc_backup  203.0.113.45 WIN-K0W31D3Q   NTLM
```

Видно, что вход произошёл в 03:14 ночи (нетипично для административной работы) с IP 203.0.113.45, имя рабочей станции отсутствует (поле пустое), аутентификация по протоколу NTLM. Отсутствие имени рабочей станции может указывать на отключённую функцию передачи NetBIOS-имени или нестандартный клиент.

**Шаг 2. Проверка сопутствующих событий неудачного входа (4625) для той же учётной записи и того же IP**

Поиск в журнале за тот же период.

```powershell
$startTime = (Get-Date).AddHours(-24)
Get-WinEvent -LogName Security -MaxEvents 50000 |
Where-Object {
    $_.Id -eq 4625 -and
    $_.TimeCreated -ge $startTime
} |
ForEach-Object {
    $xml = [xml]$_.ToXml()
    $data = @{}
    $xml.Event.EventData.Data | ForEach-Object { $data[$_.Name] = $_.'#text' }
    if ($data['TargetUserName'] -eq 'svc_backup' -and $data['IpAddress'] -eq '203.0.113.45') {
        [PSCustomObject]@{
            Time         = $_.TimeCreated
            FailureReason = $data['FailureReason']
            Status        = $data['Status']
        }
    }
} | Format-Table -AutoSize
```

**Прогнозируемый вывод:**

```
Time                     FailureReason                  Status
----                     -------------                  ------
20.03.2025 03:14:45      %%2313 - Unknown user name     0xc0000064
20.03.2025 03:14:50      %%2313 - Unknown user name     0xc0000064
20.03.2025 03:14:53      %%2304 - Bad password          0xc000006a
20.03.2025 03:14:55      %%2313 - Unknown user name     0xc0000064
```

Наблюдаем каскад неудачных попыток, где статус `0xc000006a` указывает на неверный пароль, а `0xc0000064` — на отсутствие учётной записи. Вероятно, злоумышленник перебирал возможные имена и лишь затем угадал верное сочетание. Это классическая картина атаки методом brute-force через RDP.

**Шаг 3. Геолокация исходного IP и проверка на соответствие политикам**

Используя корпоративный инструмент анализа IP (результат работы которого аналитик может вручную внести в тикет), получаем, что адрес 203.0.113.45 принадлежит хостинг-провайдеру в стране, с которой у организации нет никаких деловых связей. Внутреннее правило SIEM может автоматически подставлять эту информацию в событие, но для полноты примера допустим, что данный поиск выполнялся отдельным скриптом. Вывод: IP внешний, подозрительный, ранее не зафиксирован в легитимных логах. Аналитик документирует: «Источник не соответствует ожидаемой сетевой зоне».

**Шаг 4. Эскалация и начальные контрмеры**

Аналитик формирует инцидент: «Несанкционированный удалённый интерактивный вход сервисной учётной записи svc_backup в нерабочее время с внешнего IP, предварённый brute‑force. Рекомендуется немедленная изоляция учётной записи, принудительное завершение сеанса и передача на L2 для глубокого анализа действий злоумышленника внутри сеанса». Параллельно L1 может выполнить:

```powershell
# Принудительный логаут сеанса через query session и logoff (на сервере)
query session
# Находим ID сеанса, соответствующий svc_backup, затем:
logoff 3
# Блокировка учётной записи на уровне домена (выполняется доступными правами)
Disable-ADAccount -Identity svc_backup
```

**Ожидаемый демонстрируемый вывод.** Сквозной пример показывает полный цикл реагирования на аномальный вход типа 10: от обнаружения единичного события до подтверждения аномалии и первоначальной изоляции. Студент видит практическое применение полей `IpAddress`, `TargetUserName`, `AuthenticationPackageName`, видит связь между событиями 4624 и 4625, а также осваивает PowerShell‑приёмы фильтрации и обработки журнала безопасности.
