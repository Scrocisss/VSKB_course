# Подозрительное DNS-обращение: обзор для SOC L1

## 1. DNS как вектор угроз: контекст и базовые понятия

DNS (Domain Name System) — фундаментальный сетевой протокол, преобразующий доменные имена в IP-адреса и обслуживающий другие типы записей. Из‑за критической роли в функционировании любой IP‑сети DNS-трафик редко блокируется на периметре (порты 53/UDP и 53/TCP, а также DNS поверх HTTPS/TLS), что делает его идеальным каналом для управления вредоносным ПО (C2), эксфильтрации данных и обхода корпоративных политик безопасности. Аналитик SOC L1 ежедневно сталкивается с DNS-алертами, и его задача — быстро отделить нормальное поведение от подозрительного, требующего углублённого расследования или эскалации.

Под подозрительным DNS-обращением понимается любое DNS-событие, параметры которого выходят за пределы обычного для конкретной среды или демонстрируют известные шаблоны, ассоциированные с вредоносной активностью. Важно разграничить три категории:

*   **Нормальный DNS** — запросы, соответствующие профилю пользователей и ИТ‑систем организации, обслуживающих легитимные сервисы. Характеризуются предсказуемыми доменами (корпоративные ресурсы, известные CDN, облачные провайдеры) и низкой частотой ошибок.
*   **Аномальный, но не вредоносный DNS** — отклонения, вызванные ошибками конфигурации, некорректно работающим ПО или исследовательскими инструментами. Например, шквал запросов к несуществующему внутреннему узлу из‑за опечатки в скрипте или высокая доля NXDOMAIN при опросе списка удалённых хостов. Такие события требуют верификации, но не всегда указывают на инцидент.
*   **Вредоносный DNS** — запросы, явно связанные с деятельностью злоумышленников: обращения к известным C2-доменам, использование DGA-алгоритмов, DNS-туннелирование, запросы к фишинговым ресурсам и т.д.

Разграничение этих категорий является основной сложностью для оператора L1, поскольку даже легитимные приложения (CDN, обновления, телеметрия) могут генерировать «шумные» DNS-паттерны. Для структурирования анализа ниже приведена сравнительная таблица характеристик различных классов DNS-трафика.

| Характеристика               | Нормальный DNS                                                                 | Аномальный (не вредоносный) DNS                                              | Подозрительный/вредоносный DNS                                                        |
|------------------------------|--------------------------------------------------------------------------------|-------------------------------------------------------------------------------|---------------------------------------------------------------------------------------|
| **Повторяемость**            | Регулярная, соответствует бизнес-циклам                                        | Может быть внезапной, но не цикличной                                        | Часто циклическая (beaconing) или стохастическая по заданному алгоритму (DGA)        |
| **Домены**                   | Известные, с высокой репутацией, длинная история WHOIS                         | Ошибочные, внутренние несуществующие, разовые опечатки                       | DGA-сгенерированные (высокая энтропия), домены с низкой репутацией, недавно зарегистрированные (менее 30 дней) |
| **Типы записей**             | A, AAAA, CNAME, PTR, SRV; редко TXT для проверок (SPF, DKIM)                  | Преимущественно A/AAAA, могут быть запросы к _tcp, _udp и пр.                | Нестандартные: TXT, NULL, KEY; аномально высокая доля TXT-запросов; запросы к NS/MX для чужих доменов |
| **NXDOMAIN/отказы**          | Единичные, обычно из-за опечаток пользователей                                 | Серии однотипных отказов (сбойное ПО)                                       | Массовые NXDOMAIN с высокой энтропией (DGA), постоянные отказы к одному домену-распылителю |
| **Объём трафика**            | Стабильный, зависит от количества устройств                                    | Всплески в определённые интервалы                                             | Может быть минимальным (low‑and‑slow), либо аномально большим (туннелирование)         |
| **Направленность**           | Преимущественно к известным резолверам (локальный DNS, публичный)             | Только внутренние или только к одному внешнему резолверу                     | Может использовать нестандартные DNS-серверы, direct IP‑запросы, DoH/DoT               |
| **Связь с процессами**       | Соответствует запущенным приложениям (браузер, почтовый клиент)                | Ошибка конкретного ПО, легко выявляется                                      | Процесс-злоумышленник, часто маскирующийся под легитимный (rundll32, svchost, PowerShell)|

Аналитик L1 должен воспринимать DNS не как изолированный источник событий, а как один из сигналов в общей картине атаки. Поток DNS-запроса в контексте компрометации выглядит следующим образом:

```text
[Заражённый хост] ──(DNS-запрос к C2-домену)──▶ [Корпоративный DNS-сервер]
                                                     │
        (Если нет в кэше) ──(рекурсивный запрос)──▶ [Внешний DNS-резолвер]
                                                     │
                                                     └──(ответ с IP)──▶ [Хост]
                                                                          │
                    (Далее прямое TCP/HTTP-соединение)──▶ [C2-сервер]
```

Таким образом, DNS-событие часто предшествует установлению вредоносного сеанса, поэтому его оперативное обнаружение позволяет предотвратить кражу данных или развитие атаки. Далее мы детально рассмотрим типовые сценарии подозрительных DNS-обращений и их характерные признаки.

## 2. Классификация подозрительных DNS-событий: от DGA до туннелирования

Для успешного триажа аналитик L1 должен опознавать конкретный подтип угрозы по набору признаков. Ниже представлена расширенная классификация подозрительных DNS-обращений, охватывающая наиболее распространённые техники, используемые злоумышленниками.

**Сравнительная таблица типов подозрительных DNS-событий**

| Тип подозрительного поведения | Ключевые признаки | Типичные индикаторы (иллюстративные примеры, значения зависят от среды) | Связанные угрозы |
| :--- | :--- | :--- | :--- |
| **1. Домены, генерируемые по алгоритму (DGA)** | Большое количество уникальных доменов с высокой энтропией, массовые NXDOMAIN-ответы. Домены выглядят как случайный набор символов. | `xvzqpbmgj.net`, `a3f8d2c.net`, `wlkqjrpnx.info`. Доля цифр и согласных выше, чем в естественном языке. Запросы идут с постоянной периодичностью или по триггеру (загрузка системы). | Ботнеты (Conficker, Necurs, Emotet), программы-вымогатели, tRoаны удалённого доступа. |
| **2. DNS-туннелирование** | Аномально большой объём TXT‑запросов, длинные имена поддоменов в кодировке base64/hex, пакеты размером более 512 байт, использование типов записей NULL, TXT, CNAME с подозрительным содержимым. | `aGVsbG8gd29ybGQ= .malicious.com` (полезная нагрузка в поддомене), ответ TXT размером 2 КБ, содержащий не‑ASCII‑символы. Поток пакетов DNS, не соответствующий обычным моделям. | Эксфильтрация данных, скрытый канал C2, обход межсетевых экранов. |
| **3. Запросы к недавно зарегистрированным доменам (NRD)** | Обращение к домену, возраст которого менее 30 дней. Высокий процент NRD от одного хоста. | `new-c2server.xyz` (WHOIS creation date: последние 24 часа). Часто комбинируется с DGA или фишингом. | Целевой фишинг, эксплойт-киты, C2 с коротким временем жизни. |
| **4. Алгоритмически выглядящие поддомены** | Длинная случайная строка в качестве поддомена легитимного сервиса (dynamic DNS, облачный хостинг). | `23ab45ef7890cd1234.bounce.example.com`, `a1b2c3d4.userstorage.googleapis.com`. | Маскировка вредоносной активности под трафик известных платформ, обход чёрных списков. |
| **5. Обращения к динамическим DNS-провайдерам** | Домены из семейств free‑dynamic‑dns (например, `*.ddns.net`, `*.hopto.org`, `*.duckdns.org`) при отсутствии обоснованной бизнес-потребности. | `malware-update.ddns.net`, `c2-panel.duckdns.org`. Часто используются для недорогого, легко сменяемого C2. | C2 для вредоносного ПО, фишинг-панели. |
| **6. Серийные NXDOMAIN (Domain Generation Algorithm – общий случай)** | Хост генерирует цепочку уникальных несуществующих доменов. Количество NXDOMAIN от одного источника превышает порог (например, более 50 уникальных NXDOMAIN за час). | `favorite-cdn123.com`, `service-backup45.org`, `cloud-update9.net` — все возвращают NXDOMAIN. | Признак работы DGA, но может быть вызвано сбоем в приложении; требует дополнительного анализа. |
| **7. Запросы к доменам с нестандартными типами записей** | Массовые или одиночные запросы TXT, NULL, KEY, LOC, CNAME для нехарактерных доменов (не связанных с SPF/DKIM). | `dig @8.8.8.8 attacker.example.com TXT` → ответ содержит скрытые команды. | DNS-туннелирование, скрытая передача данных, C2 на основе DNS. |
| **8. DNS-запросы с подозрительной длиной** | Имя запроса длиннее 253 символов (нарушение RFC) или метка поддомена длиннее 63 символов. Может указывать на попытку переполнения буфера или тунеллирование. | `AAAAAAA…(300 символов)…AAAAAAA.example.com` | Эксплуатация уязвимостей DNS-парсеров, туннелирование. |
| **9. Beaconing через DNS** | Регулярные (например, каждые 60, 300, 1800 секунд) запросы к одному и тому же домену или набору доменов. Временные интервалы стабильны или подчиняются джиттеру. | Каждые 5 минут выполняются запросы A‑записей на `heartbeat.c2-server.top`. При отсутствии легитимных агентов обновлений. | Командно-контрольное управление, этап закрепления. |
| **10. Fast-flux DNS** | Домен, для которого в ответах DNS-сервера быстро меняются IP‑адреса (TTL очень низкий, от 0 до 300 секунд). За одним доменом стоят сотни и тысячи меняющихся адресов. | `flux.example.biz` → TTL 30 сек, каждые 5 минут новый набор IP. Множественные A‑записи принадлежат разрозненным сетям ботов. | Сокрытие реальных C2-серверов за постоянно меняющейся сетью прокси. |
| **11. Обращение к доменам-двойникам (typosquatting)** | Домен отличается от легитимного на одну или две буквы (очепятка), зарегистрирован злоумышленником и используется для фишинга. | `goolge.com`, `micrsoft.com`, `facebok.com`. Запрос может исходить от пользователя, либо вредоносная программа подменяет DNS. | Фишинг, кража учётных данных, распространение ВПО. |

Перечисленные типы редко встречаются изолированно: реальные атаки часто комбинируют, например, DGA-домены, зарегистрированные за несколько часов до обращения (NRD), или DNS-туннелирование, замаскированное под запросы к `*.ddns.net`. Аналитик должен научиться выделять главный паттерн и сопоставлять его с конкретным этапом цепочки атаки (Cyber Kill Chain). Например, регулярные NXDOMAIN от рабочей станции с последующим обращением к внезапно зарегистрированному домену соответствуют стадиям «C2-коммуникация» и «доставка полезной нагрузки». Для углублённого разбора каждого сценария существуют детальные руководства по каждому семейству вредоносного ПО (DGA-классификация по семействам, анализ протоколов туннелирования и т.д.), однако на уровне L1 достаточно умения идентифицировать тип угрозы по представленным признакам и понимать, кому и как эскалировать инцидент.

## 3. Инструментарий и процедуры анализа для L1

Аналитик L1 работает не в вакууме: в его распоряжении находятся SIEM-системы, логи DNS-серверов, данные пассивного DNS, threat intelligence платформы и простые сетевые утилиты. Рассмотрим типовой инструментарий и процедуры обработки алертов о подозрительных DNS-обращениях.

**Источники данных и первичные запросы**

Основным источником служат логи корпоративных DNS-серверов (Microsoft DNS, BIND, Infoblox и т.д.), собираемые в SIEM. Типичная запись лога содержит: временную метку, IP‑адрес источника (клиента), запрошенное доменное имя, тип записи, статус ответа (NOERROR, NXDOMAIN, SERVFAIL), IP‑адрес назначения (если ответ успешен). Аналитик часто использует язык запросов SIEM для быстрого выявления аномалий. Ниже приведён пример простого запроса на языке Kusto (Azure Sentinel / Microsoft Defender) для поиска хостов с подозрительно высоким числом NXDOMAIN за короткий промежуток времени:

```kusto
DnsEvents
| where TimeGenerated > ago(1h)
| where ResponseCode == "NXDOMAIN"
| summarize NXCount = count() by ClientIP, QueryType, bin(TimeGenerated, 10m)
| where NXCount > 50
| project ClientIP, NXCount, TimeGenerated, QueryType
```

Аналогичный поиск в Splunk может выглядеть так (индекс и sourcetype зависят от среды, иллюстративная схема):

```spl
index=dns sourcetype=bind:query
| fields src_ip, dest_domain, response_code, _time
| where response_code="NXDOMAIN"
| bin _time span=10m
| stats count by src_ip, _time
| where count > 50
```

После выделения подозрительного узла аналитик переходит к детализации, получая все DNS-запросы с этого IP за тот же период. Это позволяет увидеть полную картину активности и выявить DGA-паттерн или beaconing.

**Проверка по данным Threat Intelligence и пассивному DNS**

Ключевой шаг — проверка доменов по репутационным базам. Коммерческие платформы (VirusTotal, Cisco Umbrella, DomainTools, IBM X-Force) предоставляют API, но при ручном триаже L1 может использовать веб-интерфейс VT. Иллюстративный запрос через консоль:

```bash
curl -s "https://www.virustotal.com/api/v3/domains/dga-example.com" \
  -H "x-apikey: YOUR_API_KEY" | jq '.data.attributes.last_analysis_stats'
```

Вывод (схематичный) покажет соотношение детектов разных вендоров. Также полезна информация о возрасте домена, whois:

```bash
whois dga-example.com | grep -E "Creation Date|Registrar|Updated Date"
```

Пассивный DNS (например, через панель Umbrella Investigate или выгрузки из системы пассивного DNS-мониторинга) позволяет ответить на вопрос: «видела ли наша инфраструктура этот домен раньше, и если да, то насколько часто?» Аналитик проверяет, существовал ли домен ранее, менялись ли его IP-адреса, и какие ещё хосты к нему обращались. Запрос к API пассивного DNS может выглядеть так (формат зависит от вендора, иллюстративно):

```bash
curl "https://pdns.example.sec/api/v1/query?domain=suspicious.net&type=A"
```

Возвращаемый JSON содержит историю разрешений с временными метками.

**Корреляция с событиями на хосте**

Если источником запросов является корпоративная рабочая станция, аналитик должен запросить у смежной команды (или через EDR-консоль, если есть доступ) информацию о процессах, сетевых соединениях и временных рамках. В идеале необходимо установить, какой именно процесс инициировал DNS-запросы. Современные EDR-решения (Microsoft Defender for Endpoint, CrowdStrike, Carbon Black) позволяют выполнять запросы вроде:

```kusto
DeviceNetworkEvents
| where RemoteUrl contains "dga-example.com"
| join kind=inner (DeviceProcessEvents) on DeviceId, Timestamp
| project Timestamp, DeviceName, Process = InitiatingProcessFileName, CommandLine, RemoteUrl
```

Даже без глубокого доступа L1 может сопоставить временные метки DNS-запросов с временем запуска подозрительных процессов, взятых из журналов Windows Event Log (event ID 4688) или Sysmon.

**Типовой рабочий процесс (triage)**

1.  Получить алерт SIEM (правило на основе аномалии: «Host with high DNS NXDOMAIN count»).
2.  Определить IP-адрес источника и временной диапазон.
3.  Выполнить запрос на выборку всех DNS-событий от этого IP.
4.  Вычислить уникальные домены, долю NXDOMAIN, выявить паттерн (например, энтропия > 3.5 для DGA).
5.  Проверить 3–5 доменов с наивысшей энтропией по Threat Intelligence (VT, whois).
6.  Если домены злонамеренные — проставить приоритет инцидента (High/Critical). Если сомнительные — открыть кейс и передать на L2 с собранными артефактами.
7.  При наличии доступа к EDR проверить процессы на хосте, инициировавшие запросы.
8.  Задокументировать результаты и эскалировать.

Вся процедура должна занимать не более 5–10 минут для опытного аналитика. Основные ошибки на этом этапе: игноривание контекста (например, пик NXDOMAIN может быть вызван тестовым запуском сканера уязвимостей) и преждевременное закрытие алерта без проверки по TI.

## Сквозной практический пример: расследование DGA-активности на хосте

### Исходные условия
Организация использует SIEM, куда поступают логи DNS-серверов (BIND) и EDR-телеметрия. Сработал алерт правила «DNS_NX_Spike»: хост с IP 10.20.30.101 (рабочая станция Win10, имя DESKTOP-XP01) за последние 15 минут сгенерировал свыше 120 уникальных доменов, все с ответом NXDOMAIN. Аналитик L1 приступает к анализу.

### Шаг 1. Извлечение всех DNS-запросов хоста за период активности
Сначала получаем полный список доменов, запрошенных хостом, из индекса `dns`. Используем Splunk (среда условная, запрос адаптирован под популярный формат):

```spl
index=dns host="DESKTOP-XP01" earliest=-20m latest=now
| table _time, src_ip, query, response_code
| sort _time
```

Результат (фрагмент):

```
_time                src_ip          query                         response_code
...
2025-03-17 10:12:05  10.20.30.101    abcdefgh12340.example.net      NXDOMAIN
2025-03-17 10:12:07  10.20.30.101    xyz9876543210.malware.com      NXDOMAIN
2025-03-17 10:12:09  10.20.30.101    qrstuvw24680.c2server.top      NXDOMAIN
2025-03-17 10:12:12  10.20.30.101    rfgjwqpz.biz                   NXDOMAIN
...
```

Видим плотный поток случайно выглядящих доменов с интервалом 2–5 секунд — характерный признак DGA.

### Шаг 2. Вычисление энтропии для выявления DGA
Для быстрого автоматического определения DGA аналитик может направить выгрузку доменов в простой Python-скрипт, вычисляющий энтропию Шеннона (чем выше, тем более случайная строка). Типичный DGA даёт энтропию >3.5 для доменов второго уровня.

```python
import math
def shannon_entropy(s):
    prob = [float(s.count(c)) / len(s) for c in set(s)]
    return -sum([p * math.log(p) / math.log(2.0) for p in prob])

domains = ["abcdefgh12340", "xyz9876543210", "qrstuvw24680", "rfgjwqpz", "www", "google"]
for d in domains:
    print(f"{d:<20} entropy: {shannon_entropy(d):.2f}")
```

Вывод:

```

xyz9876543210        entropy: 3.36
qrstuvw24680         entropy: 3.28
rfgjwqpz             entropy: 2.75
www                  entropy: 1.52
google               entropy: 2.53
```

Большинство подозрительных доменов имеют энтропию >3.2, что подтверждает DGA-природу. Домен `www` и `google` (нормальные, взятые для сравнения) — значительно ниже.
