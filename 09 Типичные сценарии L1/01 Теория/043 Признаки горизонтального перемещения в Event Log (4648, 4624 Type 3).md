# Признаки горизонтального перемещения в журналах Windows: события 4648 и 4624 (тип входа 3)

## 1. Контекст горизонтального перемещения и роль событий 4648 и 4624

Горизонтальное перемещение (lateral movement) — совокупность техник, применяемых злоумышленником после получения первоначального доступа для расширения присутствия в сети, перехода на смежные узлы и достижения критичных ресурсов (контроллеров домена, файловых серверов, баз данных) [EventPeeker]. В отличие от вертикального повышения привилегий, цель здесь — не столько получить права `Administrator`, сколько охватить больше систем, чтобы собрать учётные данные, развернуть полезную нагрузку или закрепиться перед финальной стадией атаки. Наиболее распространённые инструменты горизонтального перемещения — PsExec, WMI, PowerShell Remoting, RDP, Impacket, CrackMapExec — эксплуатируют штатные протоколы и механизмы Windows, поэтому их активность внешне напоминает легитимное администрирование [CyberDefenders Blog, Lateral Movement Detection Guide].

Для обнаружения горизонтального перемещения специалисты SOC L1 опираются на журналы безопасности Windows, где фиксируются события входа в систему и использования учётных данных. Два события имеют первостепенное значение:

- **Событие 4648** (`A logon was attempted using explicit credentials`) — регистрируется, когда процесс пытается выполнить вход в систему, явно указывая учётные данные, отличные от контекста безопасности вызывающего процесса. Другими словами, субъект (`Subject`) запускает программу или службу от имени другого пользователя. Типичные ситуации: запуск `runas`, подключение к удалённому рабочему столу с альтернативными данными, выполнение заданий планировщика, вызов API `LogonUser` с переданными логином и паролем [Microsoft Learn].
- **Событие 4624 с типом входа 3** (`An account was successfully logged on`, Logon Type 3 — Network) — фиксирует успешный сетевой вход, когда учётная запись получает доступ к данному компьютеру по сети (без интерактивного рабочего стола). Примерами служат подключения к общим папкам, аутентификация на веб-сервере IIS, вход через WinRM, PsExec, WMI [UltimateWindowsSecurity, 4624].

Оба события дополняют друг друга: 4648 часто появляется на инициирующей стороне (компьютере, с которого выполняется попытка перемещения), тогда как 4624 Type 3 регистрируется на целевой системе, куда производится вход. Корреляция между ними позволяет отследить полную цепочку: кто и откуда инициировал подключение, под чьими учётными данными, к какому ресурсу и с помощью какого процесса.

Ключевое различие между двумя событиями сведено в таблицу.

| Характеристика | Событие 4648 | Событие 4624 (тип входа 3) |
|----------------|--------------|-----------------------------|
| **Сущность, о которой сообщает** | Попытка входа с явными учётными данными, инициированная процессом | Успешный сетевой вход на локальной системе |
| **Где регистрируется** | Компьютер, на котором выполняется процесс, инициирующий вход (часто *исходная* машина атакующего) | Целевая система, куда осуществляется сетевой доступ |
| **Ключевые поля** | `Subject` (кто инициировал), `Account Whose Credentials Were Used` (чей аккаунт использован), `Target Server`, `Process Name`, `Network Address` | `New Logon` (кто вошёл), `Logon Type` = 3, `Process Name`, `Source Network Address`, `Authentication Package` |
| **Назначение в SOC** | Выявляет подозрительное применение чужих учётных данных, особенно из нетипичных процессов (`cmd.exe`, `powershell.exe`) | Фиксирует факт успешного доступа к целевому узлу; массовые Type 3 входы с одного источника — индикатор автоматизированного перемещения |
| **Пример легитимного использования** | Запуск запланированной задачи от имени `SYSTEM` | Обращение рабочей станции к общей папке на файловом сервере |
| **Пример злонамеренного использования** | `cmd.exe` выполняет `runas /user:domain\admin` для доступа к удалённому хосту | Использование PsExec: на целевом хосте появляется `4624 Type 3` от учётной записи администратора с процессом `PSEXESVC` |

Помимо этих двух событий, в контексте горизонтального перемещения всегда анализируют вспомогательные индикаторы: доступ к скрытым административным общим ресурсам (событие 5140), создание служб (7045), удалённое создание процессов (4688), а также события проверки подлинности на контроллере домена (4776 — NTLM, 4768 — Kerberos TGT, 4769 — TGS) [CERT-EU Whitepaper]. Однако именно связка 4648 и 4624 Type 3 представляет собой минимальный, но надёжный сигнал, доступный аналитику первого уровня без погружения в сложную корреляцию множества событий.

Таким образом, задача SOC L1 — не просто регистрировать появление этих событий, а выделять в их потоке аномалии: цепочки, в которых `4648` от необычного процесса предшествует `4624 Type 3` на контроллере домена или нескольких рабочих станциях, особенно если используется NTLM-аутентификация вместо Kerberos, что характерно для атак Pass-the-Hash [CERT-EU Whitepaper].

## 2. Внутреннее устройство событий 4648 и 4624 (тип входа 3)

Понимание полей событий необходимо для написания точных правил корреляции и быстрого отсеивания ложных срабатываний. Ниже детально разобраны структуры обоих событий с акцентом на поля, критичные для выявления горизонтального перемещения.

### 2.1. Событие 4648: состав полей и интерпретация

Событие 4648 фиксирует факт использования явных учётных данных. Оно содержит следующие значимые блоки (на основе документации Microsoft и [UltimateWindowsSecurity]):

- **Subject** (`SubjectUserSid`, `SubjectUserName`, `SubjectDomainName`, `SubjectLogonId`). Описывает учётную запись, от имени которой работает процесс, инициировавший попытку входа. Например, если пользователь `j.smith` запускает `runas`, то Subject — `j.smith`.
- **Account Whose Credentials Were Used** (`TargetUserName`, `TargetDomainName`). Учётные данные, которые были переданы для входа. В контексте злонамеренного перемещения часто фигурирует привилегированная учётная запись (`Administrator`, `Domain Admin`), в то время как Subject остаётся контекстом скомпрометированной машины или непривилегированного пользователя.
- **Target Server** (`TargetServerName`). Имя сервера, к которому выполняется попытка подключения. Может содержать `localhost`, если процесс выполняет локальный вход, или удалённое имя, если запрос направлен на другой хост. В случае горизонтального перемещения Target Server обычно указывает на удалённую систему.
- **Process Information** (`ProcessName`, `ProcessId`). Полный путь к исполняемому файлу процесса, инициирующего запрос. Это ключевое поле: легитимные процессы — `svchost.exe`, `winlogon.exe`, `services.exe`, `mstsc.exe` (RDP клиент), `schtasks.exe`. Подозрительные — `cmd.exe`, `powershell.exe`, `wmic.exe`, `psexec.exe`. Появление 4648 от `cmd.exe` почти всегда требует немедленной проверки [LinkedIn Sanket Singh].
- **Network Information** (`NetworkAddress`, `Port`). IP-адрес и порт, с которых пришёл запрос (если применимо). Для событий, инициированных локально, это поле может быть пустым. При удалённом использовании (RDP с альтернативными учётными данными) здесь окажется IP-адрес клиента.

Важный нюанс: событие 4648 регистрируется *даже если попытка входа завершилась неудачей*. Оно лишь документирует факт предъявления явных учётных данных. Успешность входа нужно проверять по сопутствующему событию 4624 (с тем же `Logon GUID`) или по коду ошибки в журнале [Microsoft Learn].

Иллюстративная структура JSON, отражающая основные поля 4648, может выглядеть следующим образом (поля, наиболее информативные для анализа, выделены):

```json
{
  "EventID": 4648,
  "Subject": {
    "UserName": "j.smith",
    "Domain": "CORP",
    "LogonId": "0x3F2A1"
  },
  "AccountWhoseCredentialsUsed": {
    "UserName": "Administrator",
    "Domain": "CORP"
  },
  "TargetServer": "DC01.corp.local",
  "Process": {
    "Name": "C:\\Windows\\System32\\cmd.exe",
    "PID": 4880
  },
  "Network": {
    "Address": "10.1.2.30",
    "Port": 0
  },
  "LogonGuid": "{0887F1E4-39EA-D53C-804F-31D568A06274}"
}
```

`LogonGuid` — уникальный идентификатор сеанса входа, который совпадает в событиях 4648, 4624 и 4964 на одной системе, что позволяет связывать их без дополнительных эвристик.

### 2.2. Событие 4624 (тип входа 3): значимые поля

Событие 4624 регистрирует каждый успешный вход в систему. Нас интересует только `Logon Type = 3` — сетевой вход. Поля:

- **Subject** (`Security ID`, `Account Name`, `Account Domain`, `Logon ID`). Содержит сведения об учётной записи, которая запросила вход. Для сетевого входа это обычно `NULL SID` и `Account Name: -`, так как запрос инициирован сетевым сервисом (например, `Server`). Однако в некоторых реализациях может быть указан конкретный процесс.
- **New Logon** (`Security ID`, `Account Name`, `Account Domain`, `Logon ID`, `Logon GUID`). Собственно учётная запись, вошедшая в систему. `Logon GUID` позволяет выполнить корреляцию с исходным событием 4648 (если оно зарегистрировано на той же машине). Для горизонтального перемещения `Account Name` часто представляет привилегированного пользователя.
- **Process Information** (`Process ID`, `Process Name`). Процесс, обслуживающий вход на целевой системе. Для `Type 3` типичны `C:\Windows\System32\svchost.exe`, `C:\Windows\System32\inetsrv\w3wp.exe` (IIS), `C:\Windows\System32\WinRM\wsmprovhost.exe` (PowerShell Remoting), `C:\Windows\System32\PSEXESVC.exe` (PsExec). Само имя процесса служит индикатором используемого инструмента.
- **Network Information** (`Workstation Name`, `Source Network Address`, `Source Port`). IP-адрес и порт исходной системы, с которой пришёл запрос. Поле критично: если с одного IP идёт множество входов на разные целевые хосты в короткий промежуток — это признак автоматизированного перемещения.
- **Detailed Authentication Information** (`Logon Process`, `Authentication Package`). Показывает протокол аутентификации (`Kerberos`, `NTLM`, `Negotiate`). Для атак Pass-the-Hash характерно использование `NTLM`, так как передаётся хеш пароля, а не тикет Kerberos [CERT-EU Whitepaper]. Наличие `Kerberos` само по себе не исключает атаку (Pass-the-Ticket), но для начального перемещения PtH чаще регистрируется именно NTLM.

Пример представления события:

```json
{
  "EventID": 4624,
  "LogonType": 3,
  "NewLogon": {
    "SecurityID": "S-1-5-21-xxxx-Administrator",
    "AccountName": "Administrator",
    "AccountDomain": "CORP",
    "LogonGuid": "{0887F1E4-39EA-D53C-804F-31D568A06274}"
  },
  "Process": {
    "Name": "C:\\Windows\\System32\\svchost.exe",
    "PID": 900
  },
  "Network": {
    "SourceAddress": "10.1.2.30",
    "SourcePort": 59752
  },
  "Authentication": {
    "Package": "NTLM"
  }
}
```

### 2.3. Связь 4648 и 4624 в единой цепочке

События не существуют изолированно. Типичная картина атаки горизонтального перемещения:

1. На исходной машине (`WS01`, адрес 10.1.2.30) злоумышленник запускает шелл и выполняет `cmd.exe`, из которого вызывает инструмент удалённого доступа, передавая учётные данные `Administrator`.
2. Локально на `WS01` генерируется событие 4648: Subject = скомпрометированный пользователь (или `SYSTEM`), Account Whose Credentials Used = `Administrator`, Process = `cmd.exe`, Target Server = `FILE01` (целевой сервер). Одновременно создаётся `Logon GUID`.
3. Инструмент (например, PsExec) устанавливает сетевое соединение с `FILE01`. На `FILE01` регистрируется событие 4624 Type 3: New Logon = `Administrator`, Source Network Address = `10.1.2.30`, Process = `PSEXESVC.exe`, Authentication Package = `NTLM`.

Если аналитик наблюдает 4648 с полем Target Server ≠ localhost, он может сразу искать соответствующий 4624 на указанном сервере. Если Target Server равен localhost, но через Process видно `cmd.exe` или `powershell.exe`, это может означать подготовку локального повышения привилегий для дальнейшего перемещения; в таком случае стоит искать последующие исходящие 4648 с удалёнными серверами.

Структурная схема потоков регистрации событий (ASCII):

```text
[Исходный хост WS01]
    ▲
    │  процесс cmd.exe
    │  запуск PsExec/WMI/RDP с /user:Administrator
    │
    ├── Event 4648 (локально)
    │   Subject: wsuser
    │   Account Used: Administrator
    │   Target Server: FILE01
    │   Process: cmd.exe
    │   Logon GUID: {A...}
    │
    └── Сетевое подключение ──────────► [Целевой хост FILE01]
                                          ├── Event 4624 Logon Type 3
                                          │   New Logon: Administrator
                                          │   Source IP: 10.1.2.30
                                          │   Process: PSEXESVC.exe
                                          │   Auth Package: NTLM
                                          └── Event 5140 (доступ к ADMIN$)
```

Таким образом, поля `Logon GUID`, `Target Server`, `Source Network Address` и имена процессов создают основу для построения точных корреляций.

## 3. Анализ и применение в работе SOC: выявление аномалий и практические методики

### 3.1. Паттерны, характерные для злонамеренного горизонтального перемещения

Для аналитика первого уровня важно не просто видеть отдельные события, а распознавать типичные аномалии в их комбинации. Ниже перечислены поведенческие индикаторы, основанные на официальных документах CERT-EU и отраслевой практике.

- **4648 от нетипичных процессов**. Легитимный явный ввод учётных данных почти всегда происходит из процессов `svchost.exe`, `winlogon.exe`, `services.exe`, `mstsc.exe`, `schtasks.exe`, `explorer.exe`. Появление `powershell.exe`, `cmd.exe`, `wmic.exe`, `psexec.exe`, `python.exe` — тревожный сигнал.
- **Массовая генерация 4648 с одним `Account Used` на разные Target Servers**. Если в течение нескольких минут с одного хоста и от имени одного субъекта зафиксированы десятки попыток входа на различные серверы — это признак использования автоматизированного инструмента вроде CrackMapExec или Impacket.
- **Один и тот же `Account Used` в 4648 на многих системах**. При пассивной атаке (Pass-the-Hash) хеш извлекается на одной машине, а затем применяется для входа на другие. Это приводит к тому, что на разных исходных системах регистрируется одно и то же `Account Whose Credentials Used`, но разный `Subject`.
- **4624 Type 3 с `Authentication Package = NTLM` там, где ожидается Kerberos**. В правильно настроенной доменной среде сетевые входы обычно выполняются по протоколу Kerberos. Если на рабочей станции или сервере появляется Type 3 с NTLM, особенно от привилегированной учётной записи, это может указывать на Pass-the-Hash [CERT-EU Whitepaper].
- **4624 Type 3 на контроллере домена от рабочей станции**. Рабочие станции не должны напрямую аутентифицироваться на контроллере домена, кроме как для получения Kerberos-тикетов (которые обрабатываются иначе). Сетевой вход Type 3 на DC обычно возникает при доступе к общим ресурсам SYSVOL/NETLOGON (что нормально), но если он идёт от непривилегированной машины под учётной записью администратора, это подозрительно [Server Fault].
- **Короткий временной интервал между 4648 и 4624 на одном целевом хосте**. Если событие 4648 на источнике с Target Server=X и через 1–2 секунды на X регистрируется 4624 Type 3 с тем же Logon GUID, связь практически доказана.

### 3.2. Типовые запросы и правила детекции

На практике аналитики используют SIEM-системы с языком запросов (Splunk SPL, Azure KQL, Elastic EQL) для выявления описанных паттернов. Ниже приведён иллюстративный пример запроса в Kusto Query Language (Azure Sentinel / Microsoft Defender for Identity), который ищет подозрительные 4648 с последующим сетевым входом:

```kusto
SecurityEvent
| where EventID == 4648
| where Process has_any ("cmd.exe", "powershell.exe", "wmic.exe")
| where TargetServerName != "localhost"
| project TimeGenerated, Computer, SubjectAccount = strcat(SubjectDomainName,"\\",SubjectUserName), 
          TargetAccount = strcat(TargetDomainName,"\\",TargetUserName), 
          TargetServerName, ProcessName
| join kind=inner (
    SecurityEvent
    | where EventID == 4624 and LogonType == 3
    | project TimeGenerated, TargetComputer = Computer, TargetAccount = strcat(TargetDomainName,"\\",TargetUserName),
              SourceIp = IpAddress, AuthPackage = AuthenticationPackageName
) on TargetAccount
| where TargetComputer == TargetServerName
| project TimeGenerated, SubjectAccount, TargetAccount, SourceIp, ProcessName, AuthPackage
```

Этот запрос соединяет 4648 и 4624 по совпадению имени целевой учётной записи и имени целевого компьютера, отфильтровывая только подозрительные процессы. В реальных системах для соединения используют `Logon GUID`, но для иллюстрации приведён упрощённый вариант.

Для быстрой ручной проверки на отдельной машине аналитик может выполнить PowerShell-команду:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4648,4624} -MaxEvents 100 |
  Where-Object { $_.Id -eq 4648 -and $_.Properties[5].Value -match 'cmd.exe|powershell.exe' } |
  Format-Table TimeCreated, @{n='Subject';e={$_.Properties[1].Value}}, @{n='TargetUser';e={$_.Properties[5].Value}}, @{n='Process';e={$_.Properties[9].Value}}
```

Здесь свойство `Properties[5]` — `Account Whose Credentials Were Used`, `Properties[9]` — `Process Name`. Команда выводит таблицу подозрительных явных попыток входа, которые затем можно сопоставить с событиями 4624.

### 3.3. Ложные срабатывания и методы их фильтрации

События 4648 и 4624 Type 3 генерируются в огромных объёмах из‑за легитимной активности: работа планировщика, обновление групповых политик, запросы к сетевым папкам, функционирование антивирусов и агентов мониторинга. Основные категории ложных срабатываний:

- **Службы и запланированные задачи**. Процессы `svchost.exe` и `taskhostw.exe` постоянно используют явные учётные данные для запуска задач от имени `SYSTEM`. Они должны быть занесены в белый список.
- **RDP-подключения администраторов**. `mstsc.exe` с альтернативными учётными данными — штатная практика; аналитик должен знать IP-адреса административных jump-серверов и исключать их из правил.
- **Агенты резервного копирования и развёртывания ПО**. Такие продукты, как SCCM или Veeam, используют сетевые входы типа 3 для доступа к клиентам; они идентифицируются по фиксированному имени процесса или учётной записи.

Фильтрация реализуется через контекст: проверка принадлежности исходного IP к подсети управления, анализ репутации процесса, учёт времени суток и рабочего расписания администраторов.

### 3.4. Вспомогательные события и расширенный контекст

При подтверждении подозрительной активности аналитик обязан расширить поиск на другие индикаторы, перечисленные в [EventPeeker Detection Guide] и [CERT-EU Whitepaper]:

- **Событие 5140** (`A network share object was accessed`). Тип общего ресурса `C$` или `ADMIN$` — явный признак использования PsExec или подобного инструмента.
- **Событие 7045** (`A service was installed in the system`). Имя службы `PSEXESVC` однозначно указывает на PsExec.
- **Событие 4688** (`A new process has been created`). На целевом хосте можно обнаружить запуск `cmd.exe` или `powershell.exe` с родительским процессом `PSEXESVC.exe` или `WmiPrvSE.exe`.
- **Sysmon Event ID 1** (Process Creation). Предоставляет командную строку, хеши выполняемых файлов и поля `ParentCommandLine`, что бесценно при расследовании.

Таким образом, работа с 4648 и 4624 не заканчивается на констатации факта: эти события служат триггерами для более глубокого анализа цепочки атаки.

## 4. Сквозной практический пример расследования подозрительного горизонтального перемещения

**Исходные условия:** SOC L1 получает алерт от SIEM-платформы (Splunk) о правиле «Multiple 4648 from non-standard process». В алерте указано, что с рабочей станции `WS-ENG-05` (IP 192.168.10.45) за 10 минут зарегистрировано 15 событий 4648, где Target Server меняется, процесс — `cmd.exe`, Account Used — `CORP\svc_backup`. Сервисная учётная запись `svc_backup` никогда ранее не использовалась для интерактивных или удалённых входов на этих хостах.

**Задача аналитика:** подтвердить или опровергнуть факт горизонтального перемещения, определить источник, затронутые системы и передать эскалацию на L2.

### Шаг 1. Детальный анализ 4648 на исходном хосте

На `WS-ENG-05` выполняем запрос для извлечения всех 4648 за последний час, связанных с процессом `cmd.exe`:

```powershell
Get-WinEvent -ComputerName WS-ENG-05 -FilterHashtable @{LogName='Security'; Id=4648; StartTime=(Get-Date).AddHours(-1)} |
  Where-Object { $_.Properties[9].Value -like '*cmd.exe' } |
  Select-Object TimeCreated, @{n='Subject';e={$_.Properties[1].Value}},
                @{n='TargetUser';e={$_.Properties[5].Value}},
                @{n='TargetServer';e={$_.Properties[7].Value}},
                @{n='Process';e={$_.Properties[9].Value}},
                @{n='SourceIP';e={$_.Properties[11].Value}}
```

Вывод (сокращённый, иллюстративная схема):

```
TimeCreated          Subject       TargetUser       TargetServer        Process                             SourceIP
10:15:01             WS-USER       svc_backup       FILE01              C:\Windows\System32\cmd.exe         192.168.10.45
10:15:02             WS-USER       svc_backup       SQL02               C:\Windows\System32\cmd.exe         192.168.10.45
10:15:03             WS-USER       svc_backup       DC01                C:\Windows\System32\cmd.exe         192.168.10.45
...
```

Видно, что за короткое время один пользовательский контекст (`WS-USER`) пытается войти на различные серверы под `svc_backup`. Процесс `cmd.exe` означает, что, скорее всего, запущен батч-файл или скрипт.

### Шаг 2. Поиск коррелирующих 4624 Type 3 на целевых системах

На каждом из целевых серверов (`FILE01`, `SQL02`, `DC01`) ищем события 4624 Type 3 с той же учётной записью `svc_backup` и временем, близким к 10:15:

```powershell
$targets = @("FILE01","SQL02","DC01")
foreach ($target in $targets) {
    Get-WinEvent -ComputerName $target -FilterHashtable @{LogName='Security'; Id=4624; StartTime=(Get-Date).AddHours(-1)} |
      Where-Object { $_.Properties[8].Value -eq 3 -and $_.Properties[5].Value -eq 'svc_backup' } |
      Select-Object MachineName, TimeCreated, @{n='Account';e={$_.Properties[5].Value}},
                    @{n='SourceIP';e={$_.Properties[18].Value}},
                    @{n='AuthPackage';e={$_.Properties[11].Value}},
                    @{n='ProcessName';e={$_.Properties[17].Value}}
}
```

Пример вывода по `FILE01`:

```
MachineName TimeCreated         Account      SourceIP          AuthPackage ProcessName
FILE01      10:15:02            svc_backup   192.168.10.45     NTLM        C:\Windows\System32\svchost.exe
```

На `DC01`:

```
MachineName TimeCreated         Account      SourceIP          AuthPackage ProcessName
DC01        10:15:03            svc_backup   192.168.10.45     NTLM        C:\Windows\System32\svchost.exe
```

Аутентификация прошла по NTLM, что подозрительно для доменной учётной записи. Процесс `svchost.exe` на целевых машинах говорит о стандартном сетевом входе (через SMB), но факт использования NTLM и совпадение IP с исходной машиной подтверждает перемещение.

### Шаг 3. Поиск дополнительных индикаторов на целевых системах

Проверяем наличие доступа к административным общим ресурсам (событие 5140) на тех же хостах:

```powershell
Get-WinEvent -ComputerName DC01 -FilterHashtable @{LogName='Security'; Id=5140; StartTime=(Get-Date).AddHours(-1)} |
  Where-Object { $_.Properties[6].Value -like '*ADMIN$*' } |
  Format-Table TimeCreated, @{n='Share';e={$_.Properties[6].Value}}, @{n='Account';e={$_.Properties[1].Value}}
```

Результат на `DC01`:

```
TimeCreated         Share       Account
10:15:03            \\*\ADMIN$  CORP\svc_backup
```

Доступ к `ADMIN$` — основный метод работы PsExec. Действительно, находим событие 7045 на `FILE01`:

```powershell
Get-WinEvent -ComputerName FILE01 -FilterHashtable @{LogName='System'; Id=7045; StartTime=(Get-Date).AddHours(-1)} |
  Where-Object { $_.Properties[1].Value -like '*PSEXESVC*' }
```

Вывод:

```
TimeCreated         ServiceName  ServiceFileName
10:15:02            PSEXESVC     %SystemRoot%\PSEXESVC.exe
```

Это доказывает использование Sysinternals PsExec.

### Шаг 4. Проверка родительских процессов на источнике

С помощью Sysmon Event ID 1 на `WS-ENG-05` уточняем, что именно запустило `cmd.exe`:

```powershell
Get-WinEvent -ComputerName WS-ENG-05 -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; Id=1; StartTime=(Get-Date).AddHours(-1)} |
  Where-Object { $_.Properties[5].Value -like '*cmd.exe' } |
  Format-Table TimeCreated, @{n='CommandLine';e={$_.Properties[10].Value}},
                @{n='ParentCommandLine';e={$_.Properties[21].Value}}
```

Пример:

```
TimeCreated   CommandLine                          ParentCommandLine
10:14:55      cmd.exe /c for /L %i ...             C:\Windows\System32\wbem\WmiPrvSE.exe
```

Родительский процесс `WmiPrvSE.exe` указывает на использование WMI для удалённого запуска команды. Злоумышленник, вероятно, использовал WMI-шелл или Impacket wmiexec.py.

### Шаг 5. Формирование временной шкалы и эскалация

На основе собранных артефактов восстанавливается последовательность:

- 10:14:55 — С удалённой (пока неизвестной) системы через WMI на `WS-ENG-05` запускается `cmd.exe`, который в цикле использует `runas` или напрямую `net use` с явными учётными данными `svc_backup` для подключения к `FILE01`, `SQL02`, `DC01`.
- 10:15:01–10:15:03 — На `WS-ENG-05` фиксируются 4648; на целевых хостах появляются 4624 Type 3 с NTLM, а на `DC01` ещё и доступ к `ADMIN$` (5140). На `FILE01` регистрируется установка службы `PSEXESVC` (7045).

**Ожидаемый вывод:** злоумышленник использовал комбинацию WMI и явных учётных данных для распространения по сети, добравшись до контроллера домена. Обнаружение на этапе аномальных 4648 позволило зафиксировать активность до того, как была достигнута более глубокая компрометация. Аналитик L1 должен немедленно изолировать `WS-ENG-05`, заблокировать учётную запись `svc_backup` и передать инцидент на L2 для полного расследования, включая проверку на наличие Pass-the-Hash и дампа учётных данных.

Таким образом, связка событий 4648 и 4624 Type 3 обеспечивает ранние и надёжные признаки горизонтального перемещения, а чёткая методика их анализа позволяет даже начинающему специалисту SOC быстро идентифицировать и остановить атаку.
