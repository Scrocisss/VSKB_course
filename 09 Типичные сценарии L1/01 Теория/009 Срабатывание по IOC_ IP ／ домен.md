# Срабатывание по IOC: IP и домен в SOC L1

## 1. Контекст и базовые понятия: что такое IOC и почему IP/домен — особый случай

**Indicator of Compromise (IOC)** — конкретный цифровой артефакт, свидетельствующий о компрометации системы или сети. В отличие от общих событий безопасности, описывающих аномальное поведение, IOC представляет собой точно идентифицируемый объект: IP-адрес, доменное имя, хэш файла, ключ реестра или сигнатуру сетевого трафика. В SOC первого эшелона (L1) работа именно с такими артефактами составляет основу первичной сортировки — быстрого отделения шума от потенциальных инцидентов.

IP-адреса и домены занимают центральное место среди всех типов IOC. Через них реализуется сетевое взаимодействие вредоносного ПО с управляющими серверами, распространяются фишинговые страницы, выполняются атаки типа «drive-by download». Эти индикаторы постоянно меняются: один и тот же сервер за сутки может получить новый IP, домен перерегистрируется или скрывается за Fast Flux. Поэтому их срок жизни — от нескольких часов до нескольких дней — делает работу с ними особенно чувствительной ко времени. Для аналитика L1 это означает, что алерт, полученный по такому индикатору, требует немедленной проверки, а запоздалая реакция может оставить угрозу незамеченной.

Важно чётко разграничивать IOC как «цифровой отпечаток» и сам факт компрометации. IOC говорит не о текущей активности атакующего, а о том, что в прошлом (или в данный момент) были обнаружены следы этой активности. По своей природе такие индикаторы реактивны — они фиксируют уже известные плохие артефакты, а не предсказывают будущие атаки. Современные SOC всё чаще дополняют IOC поведенческими индикаторами (IOA), однако для L1 именно проверка «попал ли хост в чёрный список» остаётся наиболее частым сценарием.

**Сравнение IOC-типов по ключевым характеристикам** помогает понять специфику IP и доменов среди всего разнообразия индикаторов.

| Элемент | Характерные черты | Волатильность | Типичные примеры / контекст |
|---------|-------------------|---------------|-----------------------------|
| IP-адрес | Быстро меняется; множество легитимных сервисов могут делить один адрес; требует контекста порта и протокола. | Высокая | `198.51.100.42` — C2-сервер APT; `185.220.101.45` — выходной узел Tor, часто блокируемый. |
| Доменное имя | Может быть зарегистрировано мгновенно; легко маскируется под легитимные (typosquatting); живёт дольше IP, но всё равно недолговечно. | Средняя | `update-security-ms[.]com` — фальшивый домен, имитирующий Microsoft; `update-cdn-secure[.]com` — распространитель вредоносного ПО. |
| URL | Содержит путь и параметры, более специфичен; требует разбора структуры. | Средняя | `https://evil.com/login.php?user=...`; часто применяется в фишинге. |
| Хэш файла (MD5/SHA256) | Не меняется при копировании; привязан к конкретному образцу вредоносного ПО. | Низкая | `d41d8cd98f00b204e9800998ecf8427e` (иллюстративная схема). |
| Ключ реестра / Mutex | Характерен для конкретных семейств вредоносного ПО; редко даёт ложные срабатывания. | Низкая | `HKCU\Software\Microsoft\Windows\Run\svchost32`; `Global\MicrosoftWindowsUpdateMutex`. |
| SSL-сертификат (SHA1) | Может быть самоподписанным или украденным; связывает несколько доменов одним сертификатом. | Низкая | `SHA1: AA:BB:CC:...` (иллюстративная схема). |
| User-Agent строка | Легко подделать; подозрительные паттерны (нестандартные, старые браузеры). | Средняя | `Mozilla/5.0 (compatible; MSIE 6.0)` — аномалия для современных систем. |

Для SOC L1 работа с IP/доменом всегда начинается с проверки: действительно ли это индикатор атаки или случайный шум. Инструменты, описанные далее, дают аналитику опору для принятия такого решения.

## 2. Внутреннее устройство: источники срабатываний, структура алерта и уровни достоверности

Алерт по IOC на базе IP или домена попадает в очередь L1 из множества источников. Ниже приведена упрощённая схема движения данных от сенсоров до инженера SOC.

```text
[Внешние TI-фиды (коммерческие, OSINT)] ──(IOC-списки)──▶ [SIEM / TIP] ──(алерт с обогащением)──▶ [Очередь L1]
[Внутренняя DNS-инфраструктура (логи)] ──(аномалия)──▶ [SIEM]
[Прокси / веб-шлюзы] ──(блокировка URL)──▶ [SIEM]
[EDR на конечных точках] ──(сетевое соединение)──▶ [SIEM / SOAR]
[IDS/IPS] ──(сигнатура)──▶ [SIEM]
```

Каждый из этих источников накладывает свой отпечаток на содержимое алерта. Общим для всех срабатываний является базовый набор полей, который аналитик L1 видит в интерфейсе SIEM или системы управления инцидентами.

**Типовая структура алерта**, приходящего на IOC-срабатывание:

- **Alert Title / Name**: краткое описание, например «Malicious domain detected — update-security-ms[.]com».
- **Severity / Priority**: классификация угрозы (Critical, High, Medium, Low). Выставляется источником или правилом корреляции, но не всегда отражает реальный риск.
- **Timestamp**: время регистрации события (UTC).
- **Source System / Asset**: узел сети, хост или учётная запись, вовлечённая в событие (IP-адрес, hostname, user ID).
- **Destination / Indicator**: IOC (IP, домен, URL) и, возможно, порт назначения.
- **IOC Details**: тип индикатора, репутация (например, категория ThreatSTOP или теги VirusTotal).
- **Context**: дополнительная информация — процесс, инициировавший соединение, родительский процесс, командная строка, объём переданных данных, HTTP-метод или DNS-тип запроса.

Пример из практики (иллюстративная JSON-схема):

```json
{
  "alert": {
    "id": "ALERT-20250328-001",
    "severity": "critical",
    "timestamp": "2025-03-28T10:15:00Z",
    "source": {
      "host": "10.2.3.15",
      "user": "jdoe",
      "process": "powershell.exe"
    },
    "ioc": {
      "type": "domain",
      "value": "update-security-ms.com",
      "category": "phishing",
      "confidence": "high"
    },
    "action": "blocked",
    "logged_by": "webproxy01"
  }
}
```

Такой алерт сообщает аналитику, что внутренний хост `10.2.3.15` пытался обратиться к домену `update-security-ms.com`, классифицированному threat intelligence как фишинговый (`high confidence`), и соединение было заблокировано прокси-сервером.

**Достоверность (confidence) IOC** — ключевой параметр, определяющий срочность и жёсткость реагирования. Обычно выделяют три уровня:

- **Высокая (High)**: индикаторы, полученные из нескольких независимых достоверных источников, прошедшие проверку в песочнице, привязанные к известной кампании (APT, финансовые атаки). Например, хэш вредоносного файла, подтверждённый VirusTotal, или C2-домен, в течение нескольких дней активный и уникально связанный с вредоносной активностью. Такие IOC можно блокировать автоматически, а обнаружение связи с ними внутри сети — немедленно эскалировать.
- **Средняя (Medium)**: индикаторы, имеющие признаки злонамеренности, но недостаточно проверенные, либо присутствующие в одном источнике и не имеющие актуальной активности. Часто к этой категории относятся adware-домены, IP-адреса, ранее замеченные в рассылке, или URL, принадлежащие скомпрометированным легитимным сайтам. Требуют обязательной проверки контекста: кто обращался, что именно делал.
- **Низкая (Low)**: разовые индикаторы, устаревшие данные, индикаторы с очень широкой областью (например, облачные IP-адреса CDN), либо те, что внесены на основе слабых сигнатур. Как правило, просто записываются в базу для исторического анализа, но не требуют немедленной реакции без дополнительного триггера.

**Источники IOC для L1** можно сгруппировать по их ценности и ограничениям (таблица ниже адаптирует выводы из реальных SOC-практик).

| Источник | Что даёт | Где подводит |
|----------|----------|--------------|
| Коммерческие/бесплатные Threat Intelligence фиды | IP/домен с репутацией, категорией, временем последней активности | Неполнота покрытия, задержка обновления; низкокачественные фиды дают много ложноположительных срабатываний |
| SIEM-корреляция с правилами (на основе правил, а не фидов) | Выявление подозрительной активности по комбинации событий (например, DNS-запрос к новому домену + запуск Powershell) | Высокая зависимость от качества инжеста логов; может не выявить скрытого обращения по IP без DNS |
| EDR-алерты | Контекст процесса и пользователя, инициировавшего обращение | Покрывает только конечные точки с агентом; не видит трафик серверов без агента |
| DNS-логи (серверы, умные маршрутизаторы) | Факт попытки разрешения имени, источник, тип записи | Не показывает, состоялось ли соединение; легко пропадает при использовании альтернативных DNS-серверов |
| Прокси / веб-шлюзы | URL, ответ сервера, объём данных, HTTP-метод | Видит только HTTP(S)-трафик; если злоумышленник использует нестандартный порт, останется слепым пятном |

Понимание ограничений каждой из этих «линз» помогает L1-аналитику не делать поспешных выводов. Например, если алерт пришёл на основе DNS-лог только как факт запроса, нельзя утверждать, что зловредный файл был загружен. Нужно искать дополнительные доказательства в прокси или на хосте.

## 3. Применение: методология триажа алерта по IP/домену

Работа с таким алертом в SOC L1 подчиняется чёткой последовательности — именно по ней строится обучение новичков и ежедневная практика. Последовательность укладывается в несколько шагов, каждый из которых опирается на конкретные инструменты и артефакты.

### Шаг 1. Получение алерта и первичный осмотр

Аналитик видит алерт в очереди. Важнейшая задача за первые 90–120 секунд — определить, не является ли он очевидным ложным срабатыванием (например, известный легитимный CDN-домен попал в список из-за кросс-контаминации) и приоритезировать относительно других алертов. Оцениваются поля: severity, источник, IOC, время. Если алерт помечен как «Critical» и содержит IOC High Confidence, он получает наивысший приоритет.

### Шаг 2. Проверка репутации IOC

Далее выполняется запрос к платформам анализа индикаторов. Самые распространённые — VirusTotal / Google Threat Intelligence, ThreatSTOP, AlienVault OTX. Аналитик L1 не обязан глубоко интерпретировать детали поведения вредоносного ПО, но должен получить ответ на вопрос: «Считает ли сообщество и вендоры этот индикатор вредоносным сейчас?».

Пример запроса к API платформы Threat Intelligence (иллюстративная схема, структура полей зависит от конкретного API):

```bash
curl -s -H "x-apikey: $API_KEY" \
  "https://www.virustotal.com/api/v3/domains/update-security-ms.com" | jq '.data.attributes'
```

Ответ содержит секцию `last_analysis_results`, показывающую вердикты десятков антивирусных движков, а также категории (phishing, malware, suspicious). Ключевое — счётчик обнаружений: если 15+ вендоров классифицируют домен как вредоносный, это высоко достоверный сигнал. Однако даже 0 срабатываний не гарантирует чистоту — возможно, домен слишком новый и ещё не попал в базы.

Платформы вроде ThreatSTOP дополнительно показывают, в каких таргет-листах (targets) состоит IP/домен и как давно он туда добавлен. Из выдержки [Check IOC](https://docs.threatstop.com/portal_cioc.html): активные цели — те, в которых IOC состоит прямо сейчас, исторические — был ранее; также выполняется A-запись для проверки текущих IP, на которые резолвится домен. Это помогает понять, активна ли угроза в данный момент.

### Шаг 3. Контекстный поиск в собственных логах

Репутация из внешних источников — лишь полдела. Необходимо выяснить, что именно происходило в инфраструктуре. На этом этапе аналитик выполняет запросы к логам DNS, прокси, сетевым потокам.

**Поиск DNS-запросов к домену** (пример для AWS CloudWatch Logs Insights, адаптировано из документации MoJ):

```sql
filter query_name = "update-security-ms.com" 
 and query_type in ("A", "AAAA")
| stats min(@timestamp) as first_seen, max(@timestamp) as last_seen,
         count(*) as query_count by srcAddr, query_name, rcode
| sort by first_seen asc
```

Такой запрос вернёт перечень IP-источников, временное окно активности и коды ответа DNS. Если `rcode=NOERROR` и запрос повторился несколько раз, высока вероятность реального обращения. Если `NXDOMAIN`, вероятнее всего, ботнет пытался резолвить домен, но инфраструктура не отвечает.

**Поиск HTTP-обращений в прокси-логах** (Splunk, из блога Mlab):

```spl
index=proxy url="*update-security-ms.com*"
| table _time, client_ip, method, url, status, bytes_sent, user_agent
| sort by _time
```

Этот запрос покажет, передавались ли файлы, какого объёма, был ли успешен HTTP-статус (200, 301 и т.п.). Дополнительно можно применить фильтр легитимных доменов, чтобы исключить шум.

**Проверка сетевых соединений (flow logs)**, если DNS не даёт картины, но IP-адрес известен:

```bash
# Пример для VPC Flow Logs в CloudWatch
filter dstAddr = '198.51.100.42' and action = 'ACCEPT'
| stats count() by srcAddr, dstPort, protocol
```

### Шаг 4. Оценка контекста и принятие решения

Теперь аналитик сопоставляет три слоя информации:
1. Внешнюю репутацию (вредоносный / подозрительный / чистый).
2. Внутренние логи: факт обращения, объём переданных данных, процесс-инициатор (если есть EDR).
3. Бизнес-контекст: критичность актива, роль пользователя, является ли обращение типичным (например, разработчик тестирует API нового партнёра).

На основе этого применяется трёхвопросная модель триажа, полезная для L1:

- **Находится ли IOC в зоне нашей ответственности?** (In scope?) Если источник — гостевая Wi-Fi-сеть, не связанная с корпоративными системами, алерт может быть понижен.
- **Является ли активность заведомо ложной?** (Known benign?) Например, домен `zoom.us` в алерте о передаче данных — ложное срабатывание (как в кейсе TryHackMe).
- **Соответствует ли поведение известным паттернам угроз?** (Relevant?) Соединение с фишинговым доменом после получения подозрительного письма — это истинный инцидент.

Если все три вопроса указывают на вредоносную активность, алерт эскалируется на L2. При этом L1 выполняет первичные действия по сдерживанию: может инициировать блокировку IOC на межсетевом экране или прокси (через заявку, если нет прямой возможности), изолировать хост в EDR или уведомить владельца актива.

**Типичные ошибки и ложные срабатывания:**
- Агрегированные облачные IP (AWS, Azure) с плохой репутацией из-за соседей по подсети, но используемые легитимным приложением.
- Обращения к CDN (Cloudflare) — сами по себе не доказывают вредоносность; нужно смотреть на HTTP Host-заголовок.
- Алерты только на основе DNS-запроса без подтверждения фактического TCP-соединения — нельзя утверждать, что данные утекли.
- Прокси-блокировка не всегда означает попытку загрузки вредоносного ПО: возможно, это рекламный трекер, встроенный в сайт.

Аналитик L1 всегда документирует свой разбор в системе: какие запросы выполнены, какие источники проверены, почему принято решение. Это необходимо для последующего анализа и улучшения правил детекции.

## 4. Сквозной практический пример: фишинговый домен "update-security-ms[.]com"

**Исходные условия:** корпоративная сеть использует SIEM (Splunk), прокси-шлюз и централизованные DNS-серверы, логи которых поступают в CloudWatch Logs. Рабочее место аналитика L1 имеет доступ к API VirusTotal и к поисковым дашбордам Splunk. В очередь приходит алерт.

### Шаг 1. Получение и осмотр алерта

Алерт от системы обнаружения на базе прокси:

```json
{
  "alert_id": "ALT-20250328-0421",
  "severity": "High",
  "timestamp": "2025-03-28T11:47:00Z",
  "source": { "host": "10.2.3.42", "user": "mkoval" },
  "ioc": {
    "type": "domain",
    "value": "update-security-ms.com",
    "category": "malware-distribution, phishing",
    "confidence": "high"
  },
  "proxy_action": "blocked",
  "url_requested": "http://update-security-ms.com/install.exe",
  "rule": "BLOCK_TI_MALICIOUS_DOMAIN"
}
```

Описание: попытка скачать исполняемый файл с домена, известного как распространитель вредоносного ПО. Действие прокси — заблокирован запрос. Начальный приоритет высокий, требуется немедленный триаж.

### Шаг 2. Проверка репутации домена через VirusTotal

Выполняем curl-запрос к API (авторизация по ключу, скрыт для иллюстрации). Ответ содержит сводку:

```bash
curl -s -H "x-apikey: $VT_API" \
  "https://www.virustotal.com/api/v3/domains/update-security-ms.com" \
  | jq '.data.attributes.last_analysis_results | to_entries[] | select(.value.category == "malicious") | {engine: .key}'
```

Пример вывода (иллюстративная схема):

```
{
  "engine": "Fortinet",
  "category": "malware"
}
{
  "engine": "Kaspersky",
  "category": "phishing"
}
...  // всего 18 детектов
```

Вывод: 18 из 89 антивирусных движков классифицируют домен как вредоносный. Также отметка о регистрации домена 2 дня назад. Это высоко достоверный индикатор фишинга.

### Шаг 3. Поиск в DNS-логах за последние 48 часов

Запрос в CloudWatch Logs Insights:

```sql
filter query_name = "update-security-ms.com" 
 and query_type in ("A", "AAAA")
| stats count(*) by srcAddr, query_name, rcode, bin(1h) as hour
| sort by hour asc
```

Результат:

```
srcAddr: 10.2.3.42
query_name: update-security-ms.com
rcode: NOERROR
hour: 2025-03-28T11:00
count: 1
```

Дополнительно выполняется поиск по тому же хосту других подозрительных DNS-запросов, но ничего аномального не обнаружено. Значит, обращение единичное.

### Шаг 4. Проверка сетевого соединения (VPC Flow Logs)

Поскольку DNS резолвил домен, нужно выяснить, было ли фактическое соединение с IP, который вернул DNS. Из DNS-лога извлекается обратный адрес `198.51.100.87`. В CloudWatch запрос:

```sql
filter srcAddr = '10.2.3.42' and dstAddr = '198.51.100.87' and action = 'ACCEPT' 
| stats count() by dstPort, protocol, bytes_sent, packets
```

Ответ пустой — соединение было блокировано сетевым экраном или оконечной системой (возможно, EDR или локальный брандмауэр). Следовательно, фактической загрузки файла не произошло.

### Шаг 5. Итоговое решение и действия

Аналитик делает вывод: злоумышленник использовал фишинговый домен для распространения вредоносного ПО. Внутренний хост попытался получить доступ, но был заблокирован на уровне прокси и, скорее всего, не смог установить TCP-сессию. Угроза не реализована, но сам факт обращения требует реагирования — индикатор сработал достоверно.

Действия L1:
- Изолировать хост `10.2.3.42` в EDR для последующего анализа L2 (команда или кнопка в консоли).
- Внести домен `update-security-ms[.]com` и связанные IP в чёрные списки межсетевого экрана на 30 дней с комментарием «Active phishing campaign».
- Эскалировать инцидент на L2 с приложением всех собранных артефактов: дамп алерта, ответ VirusTotal, результаты поиска в логах.
- Уведомить владельца актива (пользователя `mkoval`) о возможном фишинговом воздействии.

Данный пример демонстрирует стандартный workflow SOC L1: от первичного приёма алерта до документированного решения с использованием внешнего обогащения и внутренних логов.
