# Брутфорс и перебор паролей

## 1. Контекст и базовые понятия

Под **брутфорсом** (brute force) в информационной безопасности понимают атаку перебора полного пространства возможных значений с целью подобрать корректный ключ, пароль, учётные данные или иной секрет. Атака гарантированно успешна при достаточном времени и вычислительных ресурсах, поскольку не эксплуатирует слабости алгоритма, а опирается на конечность пространства перебора. В контексте SOC L1 термин чаще всего сужается до **перебора паролей** — попыток многократной аутентификации с последовательным или псевдослучайным подбором пароля пользователя. Хотя «брутфорс» и «перебор паролей» часто используются как синонимы, между ними существует принципиальное различие: брутфорс как метод применим к любой криптографической или аутентификационной задаче (перебор хеш-суммы, PIN-кода, ключа шифрования), тогда как перебор паролей — это специализированный случай брутфорса, нацеленный на учётные записи и проходящий через реальные сервисы аутентификации.

Аналитик SOC L1 сталкивается преимущественно со вторым — попытками подбора паролей к доменным учётным записям, веб-приложениям, сетевым службам (RDP, SSH, FTP, SMB). Эти попытки фиксируются в журналах аудита целевых систем и при должной настройке корреляции превращаются в инциденты, требующие немедленной эскалации. В терминах фреймворка MITRE ATT&CK брутфорс паролей относится к технике **Brute Force** (ID T1110) и включает подтехники Password Guessing, Password Spraying, Credential Stuffing. Именно путаница между этими подвидами является одной из главных проблем для начинающего специалиста.

Для чёткого разграничения типов брутфорса паролей в SOC-контексте приведена сравнительная таблица (типовой ориентир атакующих действий).

| Тип атаки                               | Принцип                                                                                     | Индикатор в логах аутентификации                             | Типичная цель                                  |
|-----------------------------------------|---------------------------------------------------------------------------------------------|--------------------------------------------------------------|------------------------------------------------|
| **Password Guessing (полный перебор)**  | Последовательный перебор всех комбинаций из заданного алфавита или словаря для одной учётной записи | Множество отказов Event ID 4625 за короткий интервал с одинаковым именем пользователя, разными паролями | Конкретный пользователь с высокой ценностью    |
| **Password Spraying (распыление)**      | Попытка подобрать один простой пароль ко множеству учётных записей, не триггеря порог блокировки | Отказы 4625 от разных пользователей с интервалами, низкая интенсивность на одну запись | Организация, большая выборка доменных учёток |
| **Credential Stuffing (подстановка учётных данных)** | Использование утекших пар логин-пароль с других ресурсов в предположении повторного использования | Логины с успехом (Event ID 4624) от учётной записи, которая ранее не входила с текущего хоста, либо массовые 4625 с разными пользователями и одинаковым IP | Веб-сервисы, облачные порталы, VPN         |
| **Offline Brute Force (офлайн-перебор)**| Добыча хеша пароля (SAM, NTDS.dit) и его перебор вне контролируемой системы, нет сетевых попыток входа | Событий аутентификации нет, индикатор — компрометация файлов хешей, подозрительный доступ к базе SAM или LSASS | После повышения привилегий на хосте        |

Понимание разницы критично: SOC L1 должен классифицировать тип атаки, чтобы выбрать приоритет реагирования и маршрут эскалации. Например, одиночный Password Guessing против одного администратора с высокой интенсивностью может означать целенаправленную атаку, в то время как Password Spraying с низкой частотой — массовую автоматизированную попытку компрометации.

**Где сосредоточен SOC L1**. Уровень L1 работает с событиями систем мониторинга (SIEM), логами конечных точек и сетевых устройств. Основной источник — журналы неудачных попыток аутентификации. В среде Windows наиболее значимы события:
- **4625** — отказ входа на локальную систему (Logon Type 3 — сетевой вход, 10 — RDP, 2 — интерактивный);
- **4771** — ошибка предварительной аутентификации Kerberos (типична для Password Spraying);
- **4776** — отказ при проверке NTLM-учётных данных на контроллере домена (аудит NTLM).

В Linux/Unix-средах анализируются записи `/var/log/auth.log` с сообщениями `Failed password for user` от sshd, сущности pam_unix, а также журналы приложений (Apache, nginx с кодами 401). Важно, что единичный отказ не представляет ценности — лишь совокупность событий, превышающая порог за временное окно, формирует инцидент брутфорса.

## 2. Внутреннее устройство предмета

Внутреннее устройство брутфорса и перебора паролей можно рассматривать на двух уровнях: структурном (компоненты атаки) и процессном (фазы реализации с точки зрения злоумышленника и, зеркально, детектирующие артефакты). Поскольку тема относится к классу «Класс атак», используем таблицу вариантов атак с условиями, индикаторами и контрмерами, а также схему фаз для онлайнового брутфорса.

### 2.1 Архитектура онлайнового перебора паролей

Атака через сеть с попытками аутентификации по протоколу (SMB, Kerberos, LDAP, HTTP, RDP, SSH) требует от атакующего наличия списка учётных записей (или генератора) и словаря/правил генерации паролей. Ключевые компоненты:

- **Генератор логинов**: основан на известных шаблонах (и.ф. фамилии, LFI веб-сервера, перебор из открытых источников) или на результатах рекогносцировки.
- **Модуль протокольного взаимодействия**: библиотека, инициирующая соединение и передающая учётные данные. Например, для SMB это вызов NetrLogonSamLogonEx в протоколе MS-NRPC, для Kerberos — отправка AS-REQ.
- **Рабочий словарь**: статический список паролей (rockyou.txt) или генератор мутаций (John the Ripper, Hashcat в режиме правил).
- **Прокси/ботнет**: множество IP-адресов для распределения запросов и уклонения от блокировки по IP.
- **Тайминг-настройки**: задержки между попытками для обхода механизмов защиты от распыления (например, задание интервала 30–60 минут между проверкой одного пароля на разных учётных записях).

Атака обычно протекает поэтапно:

1. **Разведка** — сбор имён пользователей (через утечки, OSINT, null-сессионный RPC, перебор SID).
2. **Инициализация** — выбор протокола и настройка инструмента (Crowbar, Hydra, Medusa, CrackMapExec, Kerbrute).
3. **Проверка учётных данных** — отправка попыток. Для каждого варианта фиксируется результат: успех (4624, 528), отказ (4625, 4771), блокировка (4740). Злоумышленник анализирует коды ошибок, чтобы не вызвать блокировку.
4. **Постэксплуатация** — при успешном входе выполняется горизонтальное перемещение, закрепление и сбор данных.

Ниже — иллюстративная ASCII-схема потока данных в ходе онлайн-брутфорса Active Directory (SMB/NTLM):

```text
[Злоумышленник (CrackMapExec/IP: 10.0.0.50)]
   │
   ├── SMB-запрос: NetrLogonSamLogon (user=admin, pass=P@ssw0rd)
   │      └─> [DC 10.0.0.10] 
   │             │ Проверка политиками блокировки
   │             │ Проверка пароля в базе SAM/NTDS
   │             └─ Ответ: STATUS_WRONG_PASSWORD
   │
   ├── Следующая попытка через 3 сек: pass=Summer2024
   │      └─> STATUS_ACCOUNT_LOCKED (сработала политика 3 попытки)
   │
   └── SOC видит цепочку событий:
      4625 (Logon Type 3) → 4740 (блокировка) → SIEM-алерт
```

### 2.2 Классификация методов перебора паролей

С точки зрения SOC L1 важно различать не только тип атаки, но и используемые злоумышленником методы подбора. Они определяют характерный рисунок событий и длительность атаки. Следующая таблица обобщает ключевые методы и их проявления в журналах.

| Метод подбора          | Типичный инструмент              | Признак в логах                                                                             | Вероятность обхода базовых защит |
|------------------------|----------------------------------|---------------------------------------------------------------------------------------------|----------------------------------|
| **Словарная атака**    | Hydra, Medusa, CrackMapExec      | События 4625 с паролями, имеющими смысловое значение (можно только по контексту SIEM-парсинга паролей, если включён аудит в открытом виде; обычно пароли не логируются, но некоторые системы пишут хеши) | Высокая, если политика сложности слабая |
| **Гибридная атака**    | John the Ripper (--rules)        | Как и словарная, но увеличивается разнообразие попыток                                      | Средняя, обходит правила минимальной сложности |
| **Полный перебор (брутфорс)** | Hashcat brute-force mode | Экспоненциальный рост попыток, быстрое исчерпание лимитов блокировки                        | Практически невозможна при современных требованиях к длине пароля; детектится мгновенно |
| **Password Spraying с таймингом** | Kerbrute (passwordspray) | Низкая частота 4771 событий от множества пользователей, равномерные интервалы, отсутствие блокировок | Высокая; требует корреляции по длительному периоду |

С точки зрения защиты и мониторинга наиболее сложен Password Spraying, так как одиночные события 4771 или 4625 от разных учётных записей не превышают пороги правил реального времени. Его детекция строится на статистических аномалиях: число уникальных пользователей с отказами за окно (например, 50 пользователей за 10 минут с одного IP) или число отказов с кодом 0x18 в Kerberos AS-REP. Поэтому архитектура SIEM должна агрегировать события по источнику IP или по времени.

## 3. Применение и работа с предметом

SOC L1-аналитик в своей повседневной деятельности сталкивается с брутфорсом преимущественно через автоматически сгенерированные инциденты от SIEM/EDR. Задача L1 — первичная триаж, верификация ложного срабатывания, быстрый сбор контекста и эскалация на L2 в случае подтверждения. Работа строится вокруг типовых операций: анализ сырых логов, обогащение инцидента данными об источнике и учётной записи, документирование временной шкалы.

### 3.1 Инструментарий и практические команды

Ключевой артефакт расследования — журналы событий. Поскольку L1 не выполняет активных защитных действий (блокировка IP, сброс пароля) без санкции, его основная роль — доказать факт атаки. Ниже приведены практические команды для быстрого извлечения индикаторов брутфорса из логов Windows и Linux. Команды используют только штатные утилиты (PowerShell, wevtutil, grep, awk) и могут выполняться на конечных точках или через централизованную систему сбора логов.

**Поиск событий 4625 за последние 2 часа с группировкой по пользователю-жертве (PowerShell):**
```powershell
$events = Get-WinEvent -FilterHashtable @{
    LogName='Security'
    ID=4625
    StartTime=(Get-Date).AddHours(-2)
} -MaxEvents 5000

$events | ForEach-Object {
    $xml = [xml]$_.ToXml()
    [PSCustomObject]@{
        Time     = $_.TimeCreated
        TargetUser = $xml.Event.EventData.Data | Where-Object Name -eq 'TargetUserName' | Select -ExpandProperty '#text'
        IpAddress  = $xml.Event.EventData.Data | Where-Object Name -eq 'IpAddress' | Select -ExpandProperty '#text'
        Status     = $xml.Event.EventData.Data | Where-Object Name -eq 'Status' | Select -ExpandProperty '#text'
    }
} | Group-Object TargetUser | Sort-Object Count -Descending
```
Ожидаемый вывод: таблица с именами учётных записей и количеством неудачных попыток. Если для какого-то пользователя счёт превышает порог (например, 15 попыток за 120 минут), это повод для эскалации.

**Фильтрация неудачных SSH-попыток из auth.log (Linux) с подсчётом уникальных IP:**
```bash
grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -nr | head -20
```
Ключ `$(NF-3)` извлекает IP-адрес в типовом формате сообщения sshd. Дополнительно можно отфильтровать по времени с помощью `grep -E "Failed password.*$(date '+%Y-%m-%dT%H' -d '2 hours ago')"`. Результат показывает частоту попыток по IP. Аналогично для Windows можно использовать wevtutil:
```cmd
wevtutil qe Security /q:"*[System[(EventID=4625) and TimeCreated[timediff(@SystemTime) <= 7200000]]]" /c:1000 /rd:true /f:text | findstr /i "TargetUserName IpAddress"
```

**Обнаружение Kerberos Password Spraying по событиям 4771 (PowerShell):**
```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4771; StartTime=(Get-Date).AddHours(-4)} -MaxEvents 5000 |
    ForEach-Object {
        $x = [xml]$_.ToXml()
        [PSCustomObject]@{
            Time = $_.TimeCreated
            User = $x.Event.EventData.Data | Where-Object Name -eq 'TargetUserName' | Select -ExpandProperty '#text'
            IP   = $x.Event.EventData.Data | Where-Object Name -eq 'IpAddress' | Select -ExpandProperty '#text'
        }
    } | Group-Object -Property IP | Where-Object Count -gt 20 | Select-Object Name, Count
```
Здесь порог 20 уникальных пользователей с отказами от одного IP за 4 часа сигнализирует о распылении. L1-аналитик должен проверить, не является ли это легитимной активностью (например, корпоративный VPN-концентратор с множеством сессий), прежде чем эскалировать.

### 3.2 Типовые ошибки при триаже

Новички в SOC часто допускают характерные ошибки при обработке алертов брутфорса:

- **Игнорирование источника IP** – внутренний IP-адрес может означать компрометацию другой машины в сети, что следует проверять в первую очередь, а не блокировать IP без разбирательства.
- **Фокус только на количестве** – высокая интенсивность не всегда злонамеренна: срабатывание устаревшего скрипта обслуживания с неправильным паролем даст те же 4625. Важно проверять User-Agent, время суток, имя процесса.
- **Смешивание типов атак** – путаница между распылением и полным перебором ведёт к неверному приоритету. Password Spraying против всего домена опаснее, чем безуспешный перебор на одну заблокированную учётку.

### 3.3 Использование SIEM и типовые правила корреляции

Большинство L1-команд работают с дашбордами SIEM (Splunk, QRadar, Microsoft Sentinel). Типовые корреляционные правила для детекции брутфорса:

- **Правило дефолтного порога**: count событий EventID=4625 с одинаковым TargetUserName и Status=0xC000006A за 5 минут >= 10.
- **Правило Password Spraying**: count уникальных TargetUserName для одного IpAddress за 15 минут >= 30 при EventID=4771 и FailureCode=0x18.
- **Правило Credential Stuffing**: EventID=4624 с LogonType=3 для пользователя, у которого в предыдущие 30 дней не было входа с этого WorkstationName или IpAddress, и одновременно срабатывает тревога на аномалию локации.

Следует учитывать, что работа сейм-правил может давать ложные срабатывания при легитимных скриптах аутентификации, поэтому L1 обязан выполнить ручную верификацию, запросив у пользователя подтверждение или проверив характер активности.

## 4. Сквозной практический пример: Password Spraying на Active Directory

Рассмотрим реалистичный сценарий обнаружения атаки Password Spraying в корпоративной среде Windows AD с использованием SIEM и штатных утилит расследования. Данный пример объединяет понимание контекста, устройства атаки и практические навыки, формируя целостный кейс работы L1.

**Исходные условия**: Организация использует контроллер домена Windows Server 2022, SIEM Splunk агрегирует события Windows Event Log. Аналитик L1 получает email-нотификацию о срабатывании правила корреляции «Kerberos Preauth Failure Spraying» (54 уникальных пользователя с событиями 4771 от IP 192.168.58.105 за 10 минут). Время — 03:15 ночи, обычная рабочая активность отсутствует. Система не входит в VPN-диапазон, адрес принадлежит внутренней подсети серверов. Аналитик приступает к расследованию.

### Шаг 1 — Детализация событий 4771 из Splunk для подтверждения

Аналитик выполняет поиск в Splunk для указанного временного окна и IP:

```
index=wineventlog EventCode=4771 IpAddress="192.168.58.105" earliest=-30m
| stats count by TargetUserName
| sort - count
```

Вывод (фрагмент):
```
TargetUserName     count
svc_sqlagent       5
svc_webapp         5
jsmith             4
...
(всего 54 записи)
```

Наблюдается равномерное распределение: примерно 5 попыток на учётную запись, что характерно для распыления с 5-ю паролями. Отмечено, что имена в основном — сервисные учётные записи и несколько пользователей.

### Шаг 2 — Проверка события 4625 для жертв и статуса блокировки

Для исключения блокировки и подтверждения, что пароли не угаданы, ищем связанные 4625 и 4740:

```powershell
$dc = "DC01"
Get-WinEvent -ComputerName $dc -FilterHashtable @{
    LogName='Security'; ID=4625,4740; StartTime=(Get-Date).AddHours(-1)
} -MaxEvents 1000 | Where-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    ($data | Where-Object Name -eq 'IpAddress').'#text' -eq '192.168.58.105'
}
```

Вывод показывает серию 4625 с кодом Status 0xC000006A (неверное имя пользователя или пароль) для каждого из имён, событий блокировки 4740 нет (политика 5 попыток, но атакующий останавливался, не превышая лимит). Это подтверждает Password Spraying.

### Шаг 3 — Идентификация источника: обратное разрешение имени хоста и анализ процесса

На источнике IP (192.168.58.105) могла быть запущена утилита Kerbrute. L1 подключается к этому серверу (с разрешения) и выполняет поиск подозрительных процессов и сетевых соединений:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -FilterXPath "*[System[EventID=1]]" -MaxEvents 500 |
    Where-Object { $_.Properties[4].Value -match 'kerbrute|ruby|python' }
```

В логах Sysmon обнаруживается запись:

```
ParentImage: C:\Windows\System32\cmd.exe
Image: C:\Users\admin\Downloads\kerbrute_windows_amd64.exe
CommandLine: kerbrute_windows_amd64.exe passwordspray -d corp.local --dc dc01.corp.local users.txt Password123
```
Это однозначно подтверждает использование Kerbrute с паролем по умолчанию.

### Шаг 4 — Оценка масштаба и эскалация

Аналитик проверяет, были ли успешные входы в период атаки для пострадавших учётных записей:

```powershell
Get-WinEvent -ComputerName $dc -FilterHashtable @{
    LogName='Security'; ID=4624; StartTime=(Get-Date).AddHours(-1)
} -MaxEvents 5000 | Where-Object {
    $xml = [xml]$_.ToXml()
    $data = $xml.Event.EventData.Data
    $data | Where-Object Name -eq 'TargetUserName' | Select -ExpandProperty '#text' -in @('svc_sqlagent','jsmith')
}
```

Никаких событий 4624 не обнаружено — пароль не подобран. Однако факт запуска инструмента и компрометации рабочей станции администратора требует немедленной эскалации.

**Ожидаемый вывод примера**: SOC L1 успешно классифицировал атаку как Password Spraying, верифицировал её, определил исходный хост и инструмент, подтвердил отсутствие компрометации учётных записей, но инициировал процедуру реагирования на угрозу (изоляция хоста, смена паролей для перечисленных учёток). Весь процесс документирован в системе управления инцидентами.
