# Поиск хэша в VirusTotal, AnyRun и корпоративной базе

## Индикаторы компрометации и роль хэша в рабочем процессе SOC L1
Индикатор компрометации (IoC) — это артефакт, наблюдаемый в сети или на хосте, который с высокой достоверностью указывает на несанкционированную или вредоносную активность. Хэш файла (криптографическая свёртка содержимого, обычно вычисляемая алгоритмами MD5, SHA‑1 или SHA‑256) является одним из наиболее оперативных и однозначных типов IoC. В отличие от сетевых адресов или имён доменов, хэш жёстко привязан к конкретному файлу, что позволяет идентифицировать даже безымянные образцы вредоносного ПО.

В рабочем процессе SOC первого уровня (L1) оповещение, сгенерированное SIEM, EDR или антивирусным средством, часто содержит хэш‑сумму файла, расценённого как вредоносный. Задача аналитика L1 — проверить достоверность срабатывания, исключить ложные срабатывания и, при необходимости, эскалировать инцидент на второй уровень. Первичная триада источников, используемых для такой проверки, включает публичную агрегирующую платформу VirusTotal, интерактивную песочницу AnyRun и внутреннюю корпоративную базу индикаторов (Threat Intelligence Platform, SIEM-репозиторий или специализированную базу вроде MISP).

Каждый из трёх источников решает отдельную задачу и обладает уникальными характеристиками, которые необходимо учитывать аналитику L1. Ниже представлена сравнительная таблица, фиксирующая ключевые разграничения между ними.

| Элемент                   | Ключевые признаки                                                                                     | Типичные параметры / индикатор для L1                                      |
|---------------------------|-------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| **VirusTotal**            | Публичный облачный сервис, агрегирующий сигнатуры и вердикты более 70 антивирусных движков и песочниц | Массовый опрос репутации; число положительных детекций, имена вредоносных семейств, метаданные файла |
| **AnyRun**                | Интерактивная облачная песочница, позволяющая выполнять анализ файлов в реальном времени с захватом сетевой и системной активности | Детальный отчёт о поведении: вердикт, сетевые соединения, процессы, MITRE ATT&CK, скриншоты |
| **Корпоративная база (MISP / SIEM)** | Внутренняя система управления индикаторами, наполняемая данными собственных инцидентов и внешних фидов | Контекст актива: теги (например, “Emotet”), время первого обнаружения, связанные инциденты, источник поступления |

Разграничение трёх типов источников критически важно для аналитика L1: VirusTotal даёт быстрый срез известности образца в индустрии («видели ли этот файл раньше и как его классифицируют?»). AnyRun предоставляет поведенческий профиль в изолированной среде, что особенно ценно, если файл новый или недостаточно освещён антивирусными вендорами. Корпоративная база отражает внутреннюю историю наблюдений организации — именно она указывает, встречался ли этот индикатор ранее в контексте атак на компанию и какая аналитика уже была проведена.

Таким образом, валидация хэша через три независимых источника образует эшелонированный подход к проверке IOC: от глобальной репутации до внутреннего контекста, снижая вероятность как ложноположительных, так и ложноотрицательных решений.

## Внутреннее устройство поисковых платформ и структура отчётов
Раздел рассматривает архитектурные особенности VirusTotal, AnyRun и типовой корпоративной базы IOC с точки зрения аналитика L1, которому необходимо понимать, как формируются и хранятся результаты проверки хэша.

### VirusTotal: модель многодвижковой агрегации и API‑ответ
VirusTotal получает файл или его хэш, после чего опрашивает множество подключённых сканеров (антивирусные движки, статические анализаторы, песочницы). Результат возвращается в виде JSON‑объекта с корневым ключом `data`. Внутри него содержатся:
- `attributes.last_analysis_stats` — словарь агрегированной статистики: `malicious`, `suspicious`, `undetected`, `harmless`, `timeout`.
- `attributes.last_analysis_results` — детализированный список вердиктов каждого движка (имя движка, категория, результат).
- `attributes.sha256`, `md5`, `sha1` — проверяемые хэши.
- `attributes.tags`, `attributes.type_description`, `attributes.size` — метаданные файла.
- `attributes.popular_threat_classification` — обобщённое имя семейства (например, “trojan.emotet”).

**Иллюстративная JSON‑схема** (поля скорректированы в соответствии с актуальным API v3):
```json
{
  "data": {
    "id": "<base64-url-safe идентификатор ресурса>",
    "type": "file",
    "attributes": {
      "sha256": "<SHA-256>",
      "md5": "<MD5>",
      "sha1": "<SHA-1>",
      "last_analysis_stats": {
        "malicious": 35,
        "suspicious": 2,
        "undetected": 28,
        "harmless": 15,
        "timeout": 0
      },
      "last_analysis_results": {
        "<engine_name>": {
          "category": "malicious",
          "result": "Trojan.Emotet"
        }
      },
      "tags": ["emotet", "trojan"],
      "times_submitted": 42,
      "first_submission_date": 1678901234,
      "meaningful_name": "invoice_342.doc"
    }
  }
}
```
Структура показывает, что аналитик L1 может немедленно оценить известность образца: высокий счётчик `malicious` в комбинации с повторяющимся семейством в `last_analysis_results` служит сильным индикатором вредоносности.

### AnyRun: поведенческий анализ и поиск по хэшу
AnyRun предоставляет два режима: интерактивную песочницу для загрузки файлов и публичный API для поиска существующих отчётов. При поиске по хэшу система ищет завершённые (публичные) анализы, в которых фигурировал данный образец. Ответ API включает `data` с массивом объектов, каждый из которых содержит:
- `taskId`, `status`, `verdict` — идентификатор анализа, его состояние (“done”, “running”, “pending”) и вердикт (“malicious”, “no threats”, “suspicious”).
- `hash` — SHA‑256 файла.
- `hashes` — набор доступных хэшей (MD5, SHA‑1, SHA‑256).
- `processes` — дерево процессов с аргументами командной строки.
- `network` — извлечённые HTTP‑запросы, DNS‑запросы, соединения.
- `scores` и `scores.mitre` — сопоставление с техниками MITRE ATT&CK.
- `screenshots` — ссылки на скриншоты рабочего стола ВМ.

**Иллюстративная JSON‑схема результата поиска**:
```json
{
  "data": {
    "tasks": [
      {
        "taskId": "uuid-string",
        "status": "done",
        "verdict": "malicious",
        "file": {
          "hash": "a94a8fe5ccb19ba61c4c0873d391e987982fbbd3...",
          "md5": "d41d8cd98f00b204e9800998ecf8427e",
          "sha1": "da39a3ee5e6b4b0d3255bfef95601890afd80709",
          "name": "invoice.exe"
        },
        "processes": [
          {
            "pid": 2856,
            "commandLine": "invoice.exe",
            "children": [
              {"pid": 3012, "commandLine": "cmd.exe /c powershell -enc ..."}
            ]
          }
        ],
        "network": {
          "httpRequests": [
            {"url": "http://malicious-c2.example/panel/gate.php", "method": "POST"}
          ],
          "connections": [
            {"ip": "192.0.2.100", "port": 443, "protocol": "tcp"}
          ]
        },
        "scores": {
          "verdict": {"score": 100, "threatLevel": 2},
          "mitre": [
            {"id": "T1055", "name": "Process Injection"}
          ]
        }
      }
    ]
  }
}
```
Аналитик L1, получив подобный результат, видит не только факт вредоносности, но и конкретные индикаторы следующего этапа: C2‑адреса, командные строки, техники, что облегчает корреляцию.

### Корпоративная база индикаторов (на примере MISP)
В корпоративной среде распространённой платформой управления IoC является MISP (Malware Information Sharing Platform). Хэш хранится как атрибут типа `sha256`, `md5` или `sha1` внутри события. Каждый атрибут может быть снабжён тегами (например, “tlp:amber”, “emotet”, “campaign:TA444”), контекстом первого и последнего появления, комментариями аналитиков. Атрибуты связаны с объектами “File”, что позволяет хранить дополнительные свойства (имя файла, размер, тип MIME).

Внутреннее устройство типовой корпоративной базы включает:
- REST API для поиска атрибутов по значению.
- Интеграцию с SIEM: хэши регулярно экспортируются в индексы Elasticsearch для использования в корреляционных правилах.
- Источники пополнения: импорт фидов от коммерческих провайдеров (AlienVault OTX, Proofpoint ET), результаты ручных расследований, автоматизированные загрузки из EDR.

**Иллюстративная структура записи атрибута MISP**:
```json
{
  "Attribute": {
    "id": "12345",
    "event_id": "678",
    "object_id": "0",
    "type": "sha256",
    "category": "Payload delivery",
    "value": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "to_ids": true,
    "uuid": "51c1e4a0-8d8e-48ca-a098-...",
    "timestamp": "1693500000",
    "comment": "Observed in phishing campaign targeting finance",
    "Tag": [
      {"name": "tlp:amber", "colour": "#FFC000"},
      {"name": "emotet", "colour": "#ff0000"}
    ]
  }
}
```
У аналитика L1, выполняющего поиск в корпоративной базе, появляется контекст: индикатор уже встречался в инциденте со схожей тематикой, имеет ограничительную метку TLP и, следовательно, эскалация должна учитывать уже существующий опыт.

**Сравнительная таблица** архитектурных особенностей трёх источников:

| Источник            | Механизм поиска                  | Содержимое отчёта                                            | Обогащение                               | Ограничения                                   |
|---------------------|----------------------------------|--------------------------------------------------------------|------------------------------------------|-----------------------------------------------|
| VirusTotal          | Хэш-индекс многодвижкового опроса | Статистика детектов, имена вредоносных программ, метаданные   | Связи с другими сэмплами, граф файлов     | Только статическая репутация, возможна зашумлённость |
| AnyRun              | Поиск по завершённым публичным анализам | Поведенческий профиль: процессы, сеть, скриншоты, MITRE ATT&CK | Извлечённые IoC, техники атаки            | Требует, чтобы анализ был проведён и опубликован |
| Корпоративная база  | Поиск по точному значению атрибута | Внутренние теги, связанные инциденты, источники               | Внутренний контекст (отделы, пользователи) | Данные ограничены историей организации, может быть пусто |

Понимание внутреннего устройства каждого источника позволяет аналитику L1 задавать правильные вопросы: не “вредоносен ли файл?”, а “с какой вероятностью это вредоносный файл, уже известный в сообществе?” (VT), “как именно он атакует систему?” (AnyRun), “как он уже атаковал нашу организацию?” (корпоративная база).

## Применение и работа с поисковыми источниками в потоке L1
Аналитик L1, получивший на рассмотрение инцидент с подозрительным хэшем, выполняет последовательность проверок в VirusTotal, корпоративной базе и AnyRun. Порядок, как правило, определяется скоростью получения результата и необходимостью сохранения конфиденциальности: сначала быстрый запрос в VT, затем уточнение в локальной базе, потом поведенческая проверка в AnyRun.

### Поиск хэша в VirusTotal через API
Наиболее используемый метод для автоматизации — обращение к REST API с передачей API‑ключа уровня доступа, соответствующего роли аналитика. Следующая команда выполняет запрос к конечной точке файлового отчёта:
```bash
curl -s -X GET "https://www.virustotal.com/api/v3/files/44d88612fea8a8f36de82e1278abb02f" \
  -H "x-apikey: ${VT_API_KEY}" | jq '.data.attributes | {stats: .last_analysis_stats, threat: .popular_threat_classification}'
```
При успешном ответе (HTTP 200) вывод будет содержать структуру, подобную приведённой в разделе 2. Аналитик обращает внимание на поле `last_analysis_stats.malicious`; если значение >0 и движки сходятся на одном семействе (например, “Trojan.Emotet”), индикатор считается подтверждённым. Дополнительно можно извлечь детальные вердикты:
```bash
curl -s "https://www.virustotal.com/api/v3/files/44d88612fea8a8f36de82e1278abb02f" \
  -H "x-apikey: ${VT_API_KEY}" | jq '.data.attributes.last_analysis_results | to_entries[] | select(.value.category == "malicious") | {engine: .key, result: .value.result}'
```
Иллюстративный вывод:
```
{"engine":"Fortinet","result":"W32/Emotet.A!tr"}
{"engine":"Kaspersky","result":"Trojan.Win32.Emotet.gen"}
```
Результат, при котором ни один движок не определил угрозу, либо обнаружены только generic-сигнатуры при низком общем счёте, требует дальнейшего анализа в песочнице или корпоративных источниках.

### Работа с корпоративной базой индикаторов
В зависимости от используемой платформы (MISP, Elasticsearch, ThreathQ) поиск осуществляется либо через GUI, либо через API/командную утилиту. Типовой запрос к MISP API для поиска атрибута по значению:
```bash
curl -k -X POST "https://misp.local/attributes/restSearch" \
  -H "Authorization: ${MISP_API_KEY}" \
  -H "Accept: application/json" \
  -d '{"value":"e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855","type":"sha256"}'
```
Ответ включает событие и его теги. Аналитик проверяет наличие тега, указывающего на вредоносное семейство, а также поле `to_ids` (true означает, что атрибут используется в корреляционных правилах IDS). Если атрибут не найден, API возвращает пустой массив `Attribute: []`. В средах с SIEM-интеграцией удобно использовать язык запросов Elasticsearch:
```bash
curl -X GET "localhost:9200/ioc-*/_search" -H 'Content-Type: application/json' -d'
{
  "query": {
    "term": {
      "file.sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
    }
  }
}'
```
Вывод содержит исходные данные инцидента и может быть сопоставлен с временной меткой текущего оповещения.

### Поиск в AnyRun
AnyRun предоставляет REST API с аутентификацией по токену. Эндпоинт `/v1/analysis` с параметром `hash` позволяет найти публичные анализы:
```bash
curl -s -X GET "https://api.any.run/v1/analysis?hash=a94a8fe5ccb19ba61c4c0873d391e987982fbbd3" \
  -H "Authorization: Bearer ${ANYRUN_TOKEN}" | jq '.data.tasks[] | {verdict: .verdict, mitre: .scores.mitre, connectivity: .network.connections[].ip}'
```
Пример вывода (иллюстративный):
```
{
  "verdict": "malicious",
  "mitre": [
    { "id": "T1055", "name": "Process Injection" },
    { "id": "T1105", "name": "Ingress Tool Transfer" }
  ],
  "connectivity": [
    "192.0.2.100",
    "203.0.113.45"
  ]
}
```
Если публичный анализ не найден (код 404 или пустой список), аналитик может инициировать загрузку файла через веб-интерфейс или API, но это обычно выходит за рамки L1 и передаётся на L2.

**Типовые ошибки и подводные камни:**
- VirusTotal требует права доступа на поиск по хэшу в публичном API; коммерческий API имеет дополнительные возможности.
- При большом количестве запросов может сработать ограничение скорости (rate-limit); в ответах API возвращается статус 429.
- Корпоративная база может содержать устаревшие или ложные индикаторы, добавленные без надлежащей проверки. Всегда следует обращать внимание на тег TLP и источник.
- AnyRun возвращает только публичные отчёты. Файлы, проанализированные в закрытом режиме, не видны. Пользователь должен иметь лицензию для доступа к полной истории.
- Хэш может быть вычислен разными алгоритмами; необходимо искать по точному значению (MD5, SHA‑1, SHA‑256), а не преобразовывать между ними.

В идеальном процессе аналитик формирует сводку: хэш присутствует в VT с высокой степенью уверенности, внутренняя база связывает его с предыдущим инцидентом, AnyRun подтверждает вредоносное поведение и извлекает дополнительные индикаторы для охоты (hunting). На основании этой триады принимается решение об эскалации.

## Сквозной практический пример: верификация подозрительного файла аналитиком SOC L1

### Исходные условия
- SIEM сгенерировал оповещение: правило “Suspicious Hash Detected” активировалось на рабочей станции сотрудника отдела финансов. В алерте передан SHA‑256: `a94a8fe5ccb19ba61c4c0873d391e987982fbbd3`.
- Среда: рабочая станция аналитика под управлением Linux, установлены утилиты `curl`, `jq`. Имеются API‑ключи: `VT_API_KEY` для VirusTotal, `MISP_API_KEY` для внутреннего MISP, `ANYRUN_TOKEN` для AnyRun.
- Задача L1: за 15 минут подтвердить или опровергнуть вредоносный характер инцидента.

### Шаг 1: Проверка хэша через VirusTotal
```bash
curl -s -X GET "https://www.virustotal.com/api/v3/files/a94a8fe5ccb19ba61c4c0873d391e987982fbbd3" \
  -H "x-apikey: ${VT_API_KEY}" \
  | jq '.data.attributes | {
    malicious: .last_analysis_stats.malicious,
    total: (.last_analysis_stats.malicious + .last_analysis_stats.suspicious + .last_analysis_stats.undetected + .last_analysis_stats.harmless),
    family: .popular_threat_classification.suggested_threat_label
  }'
```
Вывод:
```json
{
  "malicious": 43,
  "total": 72,
  "family": "trojan.emotet"
}
```
43 из 72 движков классифицировали файл как вредоносный, предложенная угроза — Emotet. Это даёт высокую уверенность в злонамеренности.

### Шаг 2: Поиск в корпоративной базе MISP
```bash
curl -k -X POST "https://misp.local/attributes/restSearch" \
  -H "Authorization: ${MISP_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"value":"a94a8fe5ccb19ba61c4c0873d391e987982fbbd3","type":"sha256"}' \
  | jq '.response.Attribute[] | {value: .value, event_id: .event_id, tags: [.Tag[].name], comment: .comment}'
```
Вывод:
```json
{
  "value": "a94a8fe5ccb19ba61c4c0873d391e987982fbbd3",
  "event_id": "1427",
  "tags": ["emotet", "tlp:amber", "campaign:TA444"],
```
