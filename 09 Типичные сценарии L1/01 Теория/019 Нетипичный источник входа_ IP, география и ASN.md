# Нетипичный источник входа: IP, география и ASN

## Раздел 1. Контекст и базовые понятия нетипичного источника входа

Анализ источника входа по IP-адресу, географической принадлежности и номеру автономной системы (ASN) — один из фундаментальных элементов работы аналитика SOC уровня L1. Под нетипичным источником входа понимается любая ситуация, когда атрибуты события аутентификации (IP, геолокация, ASN) существенно отклоняются от исторически сложившейся модели поведения пользователя или корпоративных политик безопасности. Эти метрики позволяют на ранней стадии выделить инциденты компрометации учётных записей, использования VPN/прокси-серверов злоумышленниками и нарушений геозонирования.

IP-адрес — базовый сетевой идентификатор устройства, с которого выполняется попытка входа. Однако сам по себе IP редко несёт достаточный контекст для оценки аномальности: публичные адреса могут динамически меняться, принадлежать легитимным VPN-сервисам, NAT-пулам провайдеров или облачным провайдерам. Дополнение IP производными атрибутами даёт более полную картину.

Геолокация — определение страны, региона, города, а иногда и координат на основе IP-адреса с помощью специализированных баз данных (MaxMind GeoLite2, IP2Location, DB-IP). Важно понимать, что геолокация по IP не является абсолютно точной — на уровне страны точность коммерческих баз достигает 99%, на уровне города — около 80%, координаты могут отклоняться на десятки километров. Тем не менее, страна входа — один из наиболее надёжных индикаторов: резкое изменение страны или вход из «редкой» для пользователя локации — триггер для проверки.

Номер автономной системы (Autonomous System Number, ASN) — уникальный идентификатор автономной системы (группы IP-сетей под единым административным управлением, придерживающихся общей политики маршрутизации). ASN позволяет классифицировать провайдера: корпоративный провайдер (ISP), хостинг-провайдер (например, Amazon AWS, DigitalOcean), облачный сервис (Office 365), мобильный оператор, образовательная сеть, анонимные сети (Tor) или VPN-провайдеры. Использование ASN как фактора анализа позволяет отличать типичные корпоративные подключения от подозрительных: вход с IP, принадлежащего дата-центру (ASN хостинга), в то время как пользователь обычно работает из офиса или через корпоративный VPN, — серьёзный сигнал.

В SOC L1 эти три атрибута обычно анализируются комплексно через правила корреляции в SIEM-системах. Типовой сценарий: система собирает события входа (Windows Event ID 4624, Linux auth.log, облачные аудит-логи), обогащает их гео- и ASN-данными из локальной копии баз или через API, затем сравнивает с историческим профилем пользователя. Аномалия может быть сформулирована как:
- вход с IP из новой страны (отсутствующей в профиле за последние 30/90 дней);
- невозможность перемещения (impossible travel) — два последовательных входа из географически удалённых точек за время, меньшее, чем требуется для физического перелёта;
- смена категории ASN (например, с корпоративного ISP на хостинг);
- использование IP из TOR-сети (ASN, связанных с узлами Tor).

Ниже приведена сравнительная таблица, разграничивающая роли IP, географии и ASN в контексте анализа аномального входа.

| Атрибут          | Функция в анализе                                                                 | Типичная норма для легитимного пользователя                          | Пример нетипичного значения (индикатор угрозы)                     |
|------------------|-----------------------------------------------------------------------------------|----------------------------------------------------------------------|---------------------------------------------------------------------|
| IP-адрес         | Идентификация исходного узла, проверка по чёрным/белым спискам, репутационные базы  | Динамический IP ISP или статический корпоративный IP из известного пула | IP из диапазона хостинг-провайдера, Tor-выходного узла, прокси     |
| Геолокация (страна/город) | Определение географического происхождения запроса, выявление несоответствия профилю пользователя | Страна офиса/региона проживания, возможно несколько стран при командировках | Вход из страны, где у компании нет бизнеса и пользователь никогда не был |
| ASN (организация) | Классификация типа сети, идентификация провайдера, обнаружение анонимизирующих сервисов | ISP домашнего региона, корпоративный ASN VPN-концентратора          | ASN публичного облака (AWS, GCP), VPS-хостинга, Tor, коммерческого VPN-сервиса |

Эта таблица иллюстрирует, что каждый атрибут вносит свой вклад, но максимальная информативность достигается при их корреляции — например, IP из диапазона хостинга наряду с геолокацией, не соответствующей ожидаемой, и ASN дата-центра существенно повышает приоритет алерта.

Следует также различать смежные понятия: геолокация на уровне страны (country-level) и на уровне города (city-level). Первая используется для правил «новой страны» и геозонирования, вторая — для детектирования невозможных перемещений и атак с подбором координат. ASN, в свою очередь, не следует путать с именем провайдера (ISP name), которое является лишь строкой, тогда как ASN — числовой идентификатор с чёткой иерархией в глобальной таблице маршрутизации. ASN неизменяем для диапазона IP, в отличие от PTR-записи, которую владелец IP может легко подделать.

Таким образом, три параметра образуют контекстную триаду, на основе которой строятся сигнатуры и правила корреляции в SOC L1, а их мониторинг позволяет быстро выявлять попытки несанкционированного доступа.

## Раздел 2. Внутреннее устройство: связка IP, геолокации и ASN в системах обнаружения

Чтобы эффективно использовать нетипичный источник входа в операциях SOC, необходимо понимать, как технически формируются и связываются эти атрибуты. Анализ начинается с поступления сырого события аутентификации, содержащего минимум поле `src_ip`. Это поле извлекается парсером SIEM, после чего производится обогащение внешними данными.

**Базы геолокации** — ключевой элемент. Наиболее распространены:
- MaxMind GeoLite2 (бесплатная, точность на уровне страны >99%, города ~80%);
- IP2Location LITE;
- DB-IP Lite.
Все они основаны на регистрационных данных RIR (Regional Internet Registries), информации whois, данных от интернет-провайдеров и измерений задержек. База представляет собой бинарный файл или CSV с диапазонами IP в виде CIDR-префиксов, каждому из которых сопоставлены записи: `country_iso_code`, `city_name`, `latitude`, `longitude`, `accuracy_radius`. Поле `accuracy_radius` указывает радиус (в км), в котором находится реальный узел с заданной вероятностью. В продуктивных SOC обычно используется коммерческая версия MaxMind GeoIP2 с более высокой точностью.

**Привязка ASN** осуществляется через другие базы:
- MaxMind GeoLite2 ASN (база привязки IP к ASN и имени организации);
- данные BGP-маршрутизации (Route Views, RIPE RIS).
ASN-база возвращает номер автономной системы и строку организации-владельца (например, `AS15169 Google LLC`). Альтернативный способ — запрос whois к региональному интернет-регистратору (RIPE, ARIN, APNIC) командой `whois`, но это неприемлемо в потоковой обработке из-за задержек.

В архитектуре SIEM обогащение обычно выглядит как последовательный pipeline:
1. **Нормализация** — приведение события к общей схеме (например, ECS, Common Event Format).
2. **Обогащение геоданными** — локальный демон (GeoIP lookup service) или встроенный плагин (Splunk GeoIP, ELK Elasticsearch ingest pipeline с GeoIP-процессором) по IP находит диапазон и добавляет поля `geo.country_name`, `geo.city_name`, `geo.location` и другие.
3. **Обогащение ASN** — аналогично, из ASN-базы добавляется `as.number`, `as.organization.name`.
4. **Контекстуализация** — IP проверяется по спискам репутации (Threat Intelligence Feeds) на принадлежность к известным вредоносным IP, TOR-выходным узлам, публичным VPN-сервисам. Признак выставляется в поле `threat.indicator_type`.
5. **Профилирование** — для учётной записи по историческим данным за 30/90 дней формируется baseline: множество стран, городов, ASN, временные интервалы активности. Этот профиль может храниться в Redis/Elasticsearch или вычисляться на лету.

Для иллюстрации структуры обогащённого события входа приведём JSON-схему (иллюстративная, основана на Elastic Common Schema с расширениями):

```json
{
  "@timestamp": "2025-01-20T14:32:10Z",
  "user": { "name": "ivanov", "domain": "corp.local" },
  "source": {
    "ip": "203.0.113.45",
    "geo": {
      "country_name": "Argentina",
      "city_name": "Buenos Aires",
      "location": { "lat": -34.61, "lon": -58.38 },
      "accuracy_radius_km": 50
    },
    "as": {
      "number": 12345,
      "organization": { "name": "Example Hosting Ltd." }
    }
  },
  "event": {
    "action": "logon",
    "outcome": "success",
    "code": "4624"
  },
  "threat": {
    "indicator_type": ["hosting", "anonymous_proxy"]
  },
  "observer": { "product": "AD FS", "vendor": "Microsoft" }
}
```

В этой структуре поля `source.geo.*` и `source.as.*` добавлены на шаге обогащения и становятся доступными для правил корреляции.

**Процесс детектирования аномалии** в SIEM может использовать следующие подходы:
- **Правила на основе сигнатур**: условие `geo.country_name IS NOT IN [Russia, Kazakhstan, ...]` и `user` не в группе командированных.
- **Машинное обучение**: вычисление baseline для пользователя (среднеквадратическое отклонение по странам, ASN) и оценка вероятности текущего события.
- **Поиск аномалий по времени и месту**: разница во времени между двумя последовательными входами сравнивается с минимальным временем перемещения по дуге большого круга между координатами (impossible travel).

Структурная визуализация взаимодействия компонентов при анализе нетипичного источника представлена ниже:

```text
[Событие входа] 
       │
       ▼
[SIEM Collector] ──нормализация──▶ [Нормализованное событие (src_ip, user)]
       │
       ▼
[GeoIP-сервис] ────────────────▶ добавляет geo.country, geo.city, geo.location
[ASN-сервис] ─────────────────▶ добавляет as.number, as.organization
[TI-фиды] ────────────────────▶ threat.indicator_type (TOR, hosting, malware)
       │
       ▼
[Обогащённое событие] ──▶ [Правило корреляции] ──сравнивает с baseline──▶ [Алерт]
                                                                          │
                                                                          ▼
                                                                 [SOC L1 Analyst]
```

В данном потоке ключевыми являются сервисы обогащения, которые должны обеспечивать высокую скорость (менее 5 мс на запрос) и локальное кэширование, чтобы не замедлять конвейер и не зависеть от внешних сетевых API в реальном времени. Обычно GeoIP- и ASN-базы обновляются раз в неделю или по расписанию.

Базы геолокации хранят данные в виде бинарного дерева или префиксного дерева, что позволяет быстро находить соответствие IP диапазону. В MaxMind, например, используется формат MMDB, оптимизированный для поиска за O(log N). В открытом доступе также есть базы IP2Location в формате CSV для периодической загрузки.

Таким образом, внутреннее устройство связки IP–гео–ASN представляет собой pipeline обогащения событий данными из специализированных баз с последующей оценкой отклонения от индивидуального профиля пользователя. Разработка корректных baseline-профилей требует накопления исторических данных и аккуратного учёта «шумов» (например, пользователи, регулярно работающие через VPN, должны иметь ASN этого VPN в своём нормальном профиле).

## Раздел 3. Применение и работа аналитика SOC L1 с атрибутами источника

В повседневной практике SOC L1 анализ нетипичного источника входа сводится к выполнению оперативных процедур при срабатывании алертов или при плановом threat hunting. Основная задача аналитика первого уровня — быстро отличить реальный инцидент от ложного срабатывания и, при подтверждении угрозы, инициировать первичные меры сдерживания и эскалацию на L2/L3. Ниже рассмотрены типовые сценарии и инструменты.

### Типовые операции при поступлении алерта

1. **Верификация алерта**. Аналитик открывает карточку инцидента в SIEM (Splunk ES, Microsoft Sentinel, IBM QRadar) или SOAR (Cortex XSOAR, TheHive) и проверяет ключевые поля: `src_ip`, `geo.country_name`, `as.organization`, `user`, `event.outcome`, `timestamp`. На этом этапе часто достаточно беглого взгляда, чтобы определить очевидное ложное срабатывание (например, IP принадлежит мобильному оператору «Beeline» и геолокация может ошибочно указывать другую страну из-за особенностей маршрутизации — такие кейсы должны быть задокументированы в базе знаний смены).

2. **Проверка истории пользователя**. Выполняется запрос в SIEM для получения всех успешных входов пользователя за последние 30–90 дней, сгруппированных по странам, городам и ASN. Это позволяет быстро оценить, действительно ли текущий источник является аномалией или ранее наблюдался. Пример такого запроса на Kusto Query Language (KQL) для Microsoft Sentinel:

```kql
SigninLogs
| where TimeGenerated > ago(90d)
| where UserPrincipalName == "ivanov@corp.com"
| where ResultType == 0
| summarize LoginCount = count(), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
         by Country = Location, ASN = tostring(ASNumber), IP=IPAddress
| sort by LastSeen desc
```

Результат такого запроса содержит перечень стран, ASN и IP-адресов, из которых пользователь когда-либо успешно входил. Если текущая страна и ASN отсутствуют в выводе, аномалия подтверждается. Дополнительно можно визуализировать на карте через встроенные средства SIEM.

3. **Обогащение IP внешними данными**. Хотя SIEM уже добавил гео- и ASN-данные, аналитик может вручную перепроверить IP с помощью командной строки (whois, curl к API Shodan или GreyNoise) для получения свежей информации. Например:

```bash
whois 203.0.113.45
```

Вывод, иллюстрирующий принадлежность к хостингу:

```
inetnum:        203.0.113.0 - 203.0.113.255
netname:        EXAMPLE-HOSTING
descr:          Example Hosting Ltd.
country:        US
org:            ORG-EHL1-RIPE
...
```

Также можно выполнить обратный DNS-запрос (`dig -x 203.0.113.45`), который может указать на поддомен хостинга (например, `vps12345.examplehosting.com`). Если IP относится к TOR-выходному узлу, команда `curl https://check.torproject.org/torbulkexitlist?ip=203.0.113.45` вернёт статус.

4. **Контекстный анализ соседних событий**. Аналитик ищет другие события от того же IP за короткий период (например, последние 24 часа) на предмет сканирования других учётных записей, подбора паролей или перемещения по ресурсам. Запрос на Splunk SPL (Search Processing Language):

```spl
index=windows sourcetype=WinEventLog:Security EventCode=4625 OR EventCode=4624 src_ip="203.0.113.45" earliest=-24h
| stats count by User, EventCode, src_ip, Computer
| sort - count
```

Если один IP использовался для атак на несколько учётных записей (spray attack), это подтверждает злонамеренность и требует немедленной блокировки.

5. **Принятие решения и реагирование**. При подтверждённой аномалии аналитик выполняет:
   - временную блокировку IP на межсетевом экране или в NAD (Network Access Device) через панель управления или SOAR playbook;
   - сброс пароля пользователя и принудительное завершение сессий;
   - классификацию инцидента и эскалацию на L2 с детальным описанием атрибутов входа;
   - добавление IP в локальный blacklist TI-платформы для предотвращения повторных попыток.

### Детектирование на основе правил и машинного обучения

В SOAR/SIEM применяются готовые правила детектирования. Рассмотрим пример Sigma-правила для обнаружения входа из новой страны для пользователя:

```yaml
title: User Login from New Country
id: 3d5e2a1c-4b6f-4a2d-8f1e-9d4b6c3a1e2f
status: experimental
description: Detects a successful login from a country not seen in the previous 30 days for the user.
logsource:
    product: windows
    service: security
detection:
    selection:
        EventID: 4624
        LogonType: 3
    timeframe: 30d
    compute_baseline:
        by: TargetUserName
        attributes: [Country]
    condition: selection and not baseline
falsepositives:
    - Users on business trips
    - VPN connections causing geoip inaccuracies
level: medium
tags:
    - attack.initial_access
    - attack.t1078
```

Данное правило (иллюстративная структура, основанная на Sigma) использует вычисление baseline стран для каждого пользователя за 30 дней и алертит, если текущая страна отсутствует в списке.

Ещё один распространённый сценарий — обнаружение входа с IP, принадлежащего ASN хостинг-провайдера, при условии, что пользователь обычно использует корпоративные или домашние ISP. Реализуется простым фильтром: `as.organization` содержит известные хостинги (Amazon, DigitalOcean, Hetzner и т.п.) и `user` не относится к привилегированным администраторам облачной инфраструктуры.

### Типичные ошибки и подводные камни

- **Ложные срабатывания из-за мобильных сетей**. Мобильные операторы часто назначают IP, геолоцируемые в другом регионе или стране, что приводит к алертам «новой страны», хотя пользователь не перемещался. Решение: включать ASN мобильных операторов в белый список или понижать серьёзность таких алертов.
- **VPN и частные облака**. Легитимное использование корпоративного VPN может менять страну входа на страну расположения VPN-концентратора. Необходимо, чтобы baseline включал ASN и страны VPN-серверов. Аналитик обязан знать перечень корпоративных VPN-выходов.
- **Агрегация прокси-серверов**. Zscaler, Cisco Umbrella и подобные сервисы могут направлять трафик через множество IP с разной геолокацией. Для таких пользователей профиль стран и ASN будет чрезвычайно широким, и нужно создавать отдельные политики, исключающие их из общих правил.
- **Неточность геолокации для Anycast**. IP-адреса CDN и Anycast-сервисов (Cloudflare, Akamai) могут показывать географию сервера, а не клиента, поэтому их следует исключать из анализа.
- **Статистическая незначимость baseline**. Если пользователь новый (менее 30 дней), baseline может быть недостаточным, и частые false-позитивы неизбежны. Аналитик должен использовать порог минимального количества событий для вычисления baseline (например, не менее 20 входов).

Таким образом, работа аналитика SOC L1 с атрибутами источника — это комплекс быстрых проверок, требующий навыков работы с SIEM, понимания ограничений геолокации и здравого смысла. Эффективность работы напрямую зависит от качества профилирования пользователей и настроенных правил корреляции, позволяющих минимизировать шум и выделять действительно подозрительную активность.

## Сквозной практический пример: расследование входа пользователя «ivanov» из Аргентины

**Исходные условия**: в SIEM Microsoft Sentinel настроено обогащение событий Azure AD / Active Directory (EventID 4624) данными MaxMind GeoLite2 City и ASN. Правила аналитики: «Logon from new country» и «Login from hosting provider ASN». Учётная запись `ivanov@corp.com` обычно работает из головного офиса в Москве (страна Россия, ASN 8359 — МТС) и иногда через корпоративный VPN (страна Германия, ASN 3320 — DTAG). За последние 90 дней других стран не зафиксировано.

В 09:15 UTC поступил инцидент: успешный вход с IP `203.0.113.45`, страна — Аргентина, город Буэнос-Айрес, ASN 12345 «Example Hosting Ltd.». Алерт имеет приоритет Medium.

Расследование проводит аналитик L1, используя KQL в Azure Sentinel.

**Шаг 1. Проверка сырого события входа и обогащённых полей.** Аналитик открывает таблицу `SigninLogs` и получает полную информацию о событии-триггере.

```kql
SigninLogs
| where TimeGenerated between (datetime(2025-01-20 09:10:00) .. 5m)
| where UserPrincipalName == "ivanov@corp.com"
| project TimeGenerated, IPAddress, Location, ASN=ASNumber,
          ISP=ASDescription, DeviceDetail, RiskLevel, ConditionalAccessStatus
```

Вывод (иллюстративный):

| TimeGenerated       | IPAddress      | Location    | ASN   | ISP                   | DeviceDetail          | RiskLevel |
|---------------------|----------------|-------------|-------|-----------------------|-----------------------|-----------|
| 2025-01-20T09:15:22Z| 203.0.113.45  | Argentina   | 12345 | Example Hosting Ltd.  | UnknownDevice         | medium    |

Видно, что устройство незнакомо (отсутствует в истории) и ConditionalAccess не применялся — риск уже средний.

**Шаг 2. Построение исторического профиля входов.** Запрос для получения всех успешных входов за 90 дней с группировкой по странам и ASN, чтобы подтвердить аномалию:

```kql
let user = "ivanov@corp.com";
SigninLogs
| where TimeGenerated > ago(90d)
| where UserPrincipalName == user and ResultType == 0
| summarize LoginCount = count(), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated)
         by Country = Location, ASN = ASNumber, ISP = ASDescription
| sort by LastSeen desc
```

Вывод:

| Country      | ASN   | ISP                   | LoginCount | FirstSeen           | LastSeen            |
|--------------|-------|-----------------------|------------|---------------------|---------------------|
| Russia       | 8359  | MTS PJSC              | 345        | 2024-10-22T08:00:00 | 2025-01-20T08:58:00 |
| Germany      | 3320  | Deutsche Telekom AG   | 78         | 2024-11-05T12:00:00 | 2025-01-20T08:45:00 |

Аргентина и ASN 12345 отсутствуют — аномалия подтверждена. Пользователь никогда не входил из этой страны и не использовал данного провайдера.

**Шаг 3. Внешняя проверка IP-адреса.** В терминале SOC-аналитика выполняется команда whois для получения первичной информации:

```bash
whois 203.0.113.45
```

Частичный вывод:

```
inetnum:        203.0.113.0 - 203.0.113.255
netname:        EXAMPLE-HOSTING-NET
descr:          Example Hosting Ltd.
country:        BZ
org:            ORG-EHL1-RIPE
admin-c:        EHL1-RIPE
tech-c:         EHL1-RIPE
status:         ASSIGNED PA
mnt-by:         EHL1-MNT
...
```

Страна в whois-записи (BZ, Белиз) не совпадает с геолокацией (Аргентина), что типично для хостингов, регистрирующих IP на одну страну, но размещающих серверы в другой. Это дополнительный индикатор нетипичности.

Дополнительно выполняется проверка через сервис GreyNoise (внутренний API шлюз SOC) для оценки репутации:

```bash
curl -s "https://api.greynoise.io/v3/community/203.0.113.45"
```

Ответ (иллюстративный):

```json
{
  "ip": "203.0.113.45",
  "noise": true,
  "riot": false,
  "classification": "malicious",
  "name": "Example Scanner",
  "last_seen": "2025-01-20",
  "tags": ["scanner", "ssh bruteforce"]
}
```

IP помечен как источник вредоносного сканирования, что дополнительно подтверждает злонамеренность. (В реальной среде GreyNoise может быть не доступен, но аналитик может использовать другие TI-источники, например, AbuseIPDB.)

**Шаг 4. Проверка горизонтальной активности с этого IP.** Запрос на поиск всех событий аутентификации с тем же IP за последние 24 часа на всех контроллерах домена и облачных сервисах:

```kql
let malicious_ip = "203.0.113.45";
union SigninLogs, (CommonSecurityLog | where DeviceVendor == "Microsoft" and DeviceProduct == "Windows")
| where TimeGenerated > ago(24h)
| where IPAddress == malicious_ip
| project TimeGenerated, Type, User=TargetUserName, IPAddress, Action=Activity, Result=LogonResult
| sort by TimeGenerated desc
```

Результат:

| TimeGenerated        | Type        | User               | Action     | Result  |
|----------------------|-------------|--------------------|------------|---------|
| 2025-01-20T09:20:00Z | SigninLogs  | petrov@corp.com    | Sign-in    | Failed  |
| 2025-01-20T09:18:00Z | SigninLogs  | sidorov@corp.com   | Sign-in    | Failed  |
| 2025-01-20T09:15:22Z | SigninLogs  | ivanov@corp.com    | Sign-in    | Success |
| 2025-01-20T09:10:00Z | CommonSec.. | adm_ivanov         | NetLogon   | Failed  |

Обнаружены дополнительные попытки (неудачные) входа от этого же IP на других пользователей за короткий промежуток — классический спрей паролей или использование скомпрометированных учётных данных. Это усиливает подозрения.

**Шаг 5. Реакция и эскалация.** Исходя из собранных доказательств, аналитик классифицирует инцидент как подтверждённый (True Positive) и выполняет следующие действия в SOAR-платформе (автоматизированный playbook или ручные команды):
- Блокировка IP `203.0.113.45` на пограничном брандмауэре (команда playbook вызывает API фаерволла).
- Принудительный сброс пароля пользователя `ivanov@corp.com` через Azure AD (команда `Revoke-AzureADUserAllRefreshToken` и `Set-AzureADUserPassword`).
- Добавление IP в индикатор TI в Microsoft Sentinel:

```kql
let TIData = datatable (ThreatIndicator: string, Description: string, ExpirationDateTime: datetime)
[
    "203.0.113.45", "Brute-force and unauthorized access from hosting ASN", datetime(2025-01-27T09:15:22Z)
];
// Загрузка через API Sentinel TI, здесь иллюстративно
```

- Формирование отчёта для эскалации на L2 с приложением всех логов, результатов whois, GreyNoise, списка атакованных учётных записей.

**Ожидаемый вывод:** на сквозном примере продемонстрировано, как последовательный анализ IP, географии и ASN позволяет аналитику L1 быстро и уверенно выявить компрометацию учётной записи. Комплекс трёх атрибутов (незнакомая страна, хостинговый ASN, вредоносная репутация IP) в сочетании с аномалией профиля пользователя и горизонтальной активностью даёт неопровержимые доказательства атаки. Практические навыки работы с KQL, командной строкой и SOAR ускоряют реагирование, а систематическое использование baseline-профилей снижает количество ложных срабатываний.
