# URL в письме: редиректы, обфускация и проверка репутации

## Основные понятия и классификация угроз, связанных с URL в почтовых сообщениях

Анализ URL-вложений — одна из ключевых задач аналитика SOC L1 при разборе подозрительных писем. Вредоносные кампании используют URL как основной вектор доставки полезной нагрузки или кражи учётных данных через фишинговые страницы. При этом злоумышленники применяют два фундаментальных приёма: **редиректы** и **обфускацию**, чтобы скрыть конечный целевой ресурс и обойти автоматические фильтры. Проверка репутации URL, в свою очередь, служит основным инструментом оперативного принятия решения о вредоносности такой ссылки.

С точки зрения SOC L1 необходимо чётко различать эти три составляющие:

- **Редирект** — механизм перенаправления пользователя с одного URL на другой. Сам по себе редирект не является вредоносным, но часто используется злоумышленниками для маскировки конечного фишингового или вредоносного хоста.
- **Обфускация** — техника искажения URL с целью скрыть истинный домен или путь, затруднить автоматический парсинг и обмануть визуальный анализ. Включает кодирование символов, применение Punycode, вставку легитимных доменов в параметры и прочее.
- **Проверка репутации** — процесс сверки URL, домена или IP-адреса с внешними базами данных, репутационными сервисами и собственными индикаторами компрометации для классификации ссылки как безопасной, вредоносной или подозрительной.

Следующая таблица разграничивает эти понятия по основным признакам, целям злоумышленника и типовым индикаторам, которые должен искать аналитик первого уровня.

| Сущность                  | Ключевые признаки                                                                                     | Цели злоумышленника                                          | Типичные индикаторы для SOC L1                                   |
|---------------------------|--------------------------------------------------------------------------------------------------------|--------------------------------------------------------------|------------------------------------------------------------------|
| Редирект                  | Цепочка HTTP-ответов 3xx, JavaScript `window.location`, HTML `<meta refresh>`, заглушки ссылок-шорткатов | Скрыть конечный фишинговый сайт, обходить блокировки по статическому URL | Множественные перенаправления, смена доменной зоны, открытые редиректы легитимных сервисов |
| Обфускация                | Модификация написания URL, кодирование отдельных сегментов, злоупотребление похожими символами (homograph) | Затруднить визуальную и автоматическую идентификацию поддельного домена | Знаки `%` в нестандартных кодировках, base64-подобные строки в параметрах, Punycode-префикс `xn--` |
| Проверка репутации        | Получение оценок от VirusTotal, URLscan.io, Google Safe Browsing; сверка с черными и белыми списками    | — (защитный механизм)                                      | Низкий детект (0/90), свежая регистрация домена, наличие в фид-листах |

Все три составляющие тесно переплетены: обфусцированный URL может содержать закодированный адрес промежуточного редиректа, который в итоге приведёт на фишинговую страницу. Задача аналитика — развернуть всю цепочку и убедиться в отсутствии угрозы либо зафиксировать инцидент.

## Технические механизмы редиректов и обфускации URL

### Классификация и устройство редиректов

Редиректы классифицируются по механизму, используемому для перенаправления. Наиболее часто в фишинговых письмах встречаются:

1. **HTTP-редиректы на уровне протокола:** сервер возвращает код состояния 3xx (301, 302, 303, 307, 308) с заголовком `Location`, указывающим новый URL. Браузер автоматически следует по нему.
2. **JavaScript-редиректы:** выполняются на стороне клиента при загрузке HTML-страницы. Примеры: `window.location.href = "http://evil.com";`, `document.location.replace(...)`, или динамическая установка `window.location` после таймаута.
3. **HTML-редирект через мета-тег `<meta>`:** `<meta http-equiv="refresh" content="0; url=http://evil.com" />` — альтернатива, не требующая JavaScript.
4. **Редиректы через сторонние сервисы:** злоумышленники маскируют целевой URL с помощью легитимных укорачивателей ссылок (bit.ly, tinyurl), сервисов отслеживания или открытых редиректов известных доменов (Google, LinkedIn), добавляя параметры, которые перенаправляют на подконтрольный ресурс.

Ниже представлен упрощённый обзор этих типов в табличной форме с примерами сигнатур для детектирования.

| Тип редиректа | Пример вредоносного использования | Признаки для анализа |
| --- | --- | --- |
| HTTP 302 / 301 JavaScript window.location Meta refresh Открытый редирект легитимного Шорткат (bit.ly) | Заголовок Location указывает на фишинговый домен <script>window.location="hXXp://badsite[.]com";</script> <meta http-equiv="refresh" content="0;url=bad"> https://legit-site.com/redirect?url=http://evil.com https://bit.ly/3xyzabc  →  http://phish.site | Множественные Location в ответ Фрагмент *.js с window.location Тег <meta> с refresh Параметр url/referer в запросе Короткий домен, не соответствую |

Каждый из этих механизмов важен для аналитика, поскольку злоумышленники могут комбинировать их в цепочки: например, письмо содержит ссылку на легитимный укорачиватель, тот перенаправляет через 302 на промежуточный сервер с JavaScript-редиректом, который после нескольких этапов приводит к фишинговой форме. При автоматизированном анализе необходимо «развернуть» все перенаправления до конечной точки.

### Обфускация URL: методы и примеры

Обфускация URL направлена на сокрытие настоящего домена или пути от беглого визуального осмотра пользователем и от регулярных выражений спам-фильтров. Основные техники:

- **Percent-encoding (URL encoding):** замена символов их шестнадцатеричным представлением с префиксом `%`. Например, `http://%65%76%69%6c%2e%63%6f%6d` декодируется в `http://evil.com`. Часто применяется двойное или тройное кодирование: `%252e` превращается в `%2e` после первого раунда декодирования, а затем в точку `.`.
- **Punycode и homograph-атаки:** использование международных доменных имён (IDN), которые визуально похожи на легитимные, но содержат символы других алфавитов. Например, домен `аррӏе.com` (с кириллической ‘р’) отображается в браузере как `xn--apple-6k1a.com`. В письме такой URL может быть представлен прямо в кодировке Punycode или в Unicode, обманывая пользователя.
- **Вставка легитимного домена в путь или параметры:** `http://evil.com/legit.com/login` — пользователь видит знакомый домен в URL, но на самом деле он находится в пути, а не в имени хоста. Ещё один вариант — использование `@` в URL: `http://legit.com@evil.com` приведёт к переходу на `evil.com`, так как `legit.com` интерпретируется как учётные данные (username:password) перед `@`.
- **Кодирование в base64 / base32 / hex:** параметр в URL может содержать закодированный адрес целевого редиректа, например `?url=aHR0cDovL2V2aWwuY29t` (base64 от `http://evil.com`). После перенаправления сервер раскодирует его и отправляет Location.
- **Использование IP-адресов в различных нотациях:** вместо доменного имени указывается IP в десятичном, восьмеричном или шестнадцатеричном формате, например `http://2130706433` (что соответствует `127.0.0.1`). Многие фильтры не распознают такие адреса без проверки.

Для наглядности рассмотрим несколько примеров обфускации и их декодирование с помощью инструментов командной строки.

```bash
# Пример: URL-кодирование, декодирование в консоли
$ echo -n '%68%74%74%70%3a%2f%2f%65%76%69%6c%2e%63%6f%6d' | python3 -c "import sys,urllib.parse; print(urllib.parse.unquote(sys.stdin.read()))"
http://evil.com
```

```bash
# Punycode-домен: визуально "apple.com" с кириллической 'а'
$ idn2 xn--pple-43d.com
аррӏе.com
# Для проверки, куда реально указывает домен, можно использовать dig
$ dig +short xn--pple-43d.com
192.0.2.5  # иллюстративный адрес
```

Вредоносные URL в письмах часто содержат несколько слоёв обфускации, что требует последовательного раскручивания при анализе.

## Применение инструментов проверки репутации и анализа URL в SOC L1

На практике аналитик SOC первого уровня выполняет следующие шаги при обработке подозрительного письма, содержащего URL:

1. **Извлечение всех URL из тела и заголовков письма.** Используются как встроенные возможности почтового шлюза, так и ручные методы — вывод письма в формате `.eml` и парсинг с помощью `grep` или специализированных скриптов.
2. **Первичная проверка репутации:** отправка извлечённых ссылок, доменов и IP-адресов в публичные и корпоративные сервисы репутации.
3. **Анализ цепочки редиректов:** имитация перехода по URL с сохранением всех промежуточных ответов и конечного контента для последующей классификации.
4. **Деобфускация и разбор составных частей URL** — выявление истинного целевого домена, скрытого за кодировками или шорткатами.
5. **Сравнение с базами IOC и принятие решения:** эскалация на второй уровень при подозрительных результатах или журналирование ложного срабатывания.

Ниже рассмотрены конкретные инструменты и команды, которыми оперирует L1-аналитик.

### Инструменты проверки репутации

**VirusTotal (VT):** наиболее распространённый агрегатор антивирусных движков и репутационных баз. Для оперативной проверки URL можно использовать как веб-интерфейс, так и API. Аналитик обращает внимание не только на финальный детект (`malicious` / `clean`), но и на детали: дату последнего сканирования, категорию (фишинг, вредоносный сайт), наличие в популярных фид-листах.

Пример запроса через API для автоматизированного triage (токен `REDACTED` для иллюстрации):

```python
import requests
import sys

url_to_scan = sys.argv[1]
apikey = 'your_vt_api_key'

# Отправка URL на сканирование
scan_resp = requests.post('https://www.virustotal.com/api/v3/urls',
                          headers={'x-apikey': apikey},
                          data={'url': url_to_scan})
scan_id = scan_resp.json()['data']['id']

# Получение отчёта (подождать несколько секунд)
report = requests.get(f'https://www.virustotal.com/api/v3/analyses/{scan_id}',
                      headers={'x-apikey': apikey})
stats = report.json()['data']['attributes']['stats']
print(f"Malicious: {stats['malicious']}, Suspicious: {stats['suspicious']}")
```

**URLscan.io:** сервис, который загружает страницу в изолированной среде, делает скриншот, фиксирует все редиректы, HTTP-транзакции и даже выполняет JavaScript. Для автоматизации подходит отправка URL через API с последующим получением отчёта в JSON.

```bash
# Отправка URL в urlscan.io (требуется API-ключ)
curl -X POST "https://urlscan.io/api/v1/scan/" \
     -H "Content-Type: application/json" \
     -H "API-Key: $URLSCAN_APIKEY" \
     -d '{"url": "http://suspicious-link.com", "visibility": "public"}'
# Ответ содержит UUID сканирования; результат доступен через веб или API
```

**Командная строка и curl с опциями для разворачивания редиректов:** простое и быстрое средство при ручной проверке.

```bash
# Следование по HTTP-редиректам с выводом заголовков и кодов состояния
curl -s -I -L --max-redirs 5 "http://short.link/abc" 
# Вывод покажет цепочку Location и финальный код 200 или 403
```

Для более детального анализа можно использовать `wget --max-redirect` и `-d` для отладки.

### Деобфускация и извлечение скрытого URL

Обфусцированный URL нередко содержит в параметрах закодированный целевой адрес. Аналитику необходимо уметь раскодировать наиболее распространённые форматы. Пример обратной конвертации base64:

```bash
# Извлечение base64 из параметра 'goto' и декодирование
echo "aHR0cDovL2V2aWwuY29t" | base64 -d
```
Вывод: `http://evil.com`

Иногда злоумышленники применяют экзотические схемы вроде комбинаций XOR или самописного шифрования, но на уровне L1 обычно достаточно распознать популярные паттерны и отправить образец на песочницу.

### Детектирование в SIEM

В SOC для массового обнаружения писем с редиректными и обфусцированными URL используются правила корреляции. Ниже представлена иллюстративная сигнатура для SIEM (в формате, напоминающем Sigma-правило), нацеленная на обнаружение писем с использованием открытых редиректов известных сервисов:

```yaml
title: Possible Phishing via Open Redirect
status: experimental
description: Detect emails containing URLs that leverage open redirect of popular services
logsource:
    category: email_filter
detection:
    selection:
        url|contains:
            - '//google.com/url?'
            - '//linkedin.com/redirect'
            - '//youtube.com/redirect'
            - '//amazon.com/gp/r.html'
    condition: selection
falsepositives:
    - Legitimate marketing campaigns
level: medium
```

Аналитик L1, получив такой алерт, должен проверить конечную точку редиректа и репутацию домена-получателя.

## Сквозной практический пример: анализ фишингового письма с многоэтапным редиректом и обфускацией

### Исходные условия

На почтовый шлюз поступило подозрительное письмо, помеченное спам-сканером как `SUSPICIOUS` из-за наличия URL с нетипичной структурой. Письмо сохранено в файл `phish.eml`. Роль аналитика L1 — провести первичный анализ ссылки, определить конечный домен и оценить вредоносность. Используемая среда: Linux с установленными `curl`, `idn2`, `base64`, Python 3, доступ к API VirusTotal и urlscan.io (токены доступны). Файл `.eml` содержит HTML-тело с кнопкой «Подтвердить учётную запись», за которой стоит URL:

```
https://bit.ly/3xyzAbC?utm_source=legit
```

### Шаг 1: Извлечение и декодирование очевидной обфускации

Первичный осмотр: bit.ly — легитимен, но в параметрах подозрительная строка `3xyzAbC`. Развернём короткую ссылку командой, которая не переходит по редиректам, а лишь показывает заголовок Location.

```bash
curl -s -I -L -o /dev/null -w '%{url_effective}\n' "https://bit.ly/3xyzAbC"
```

Вывод: `http://xn--mgbbx8g1d.com/login?next=aHR0cDovL2ZpbmFsLWV2aWwuY29t`. Мы видим Punycode-домен и base64-параметр.

### Шаг 2: Деобфускация домена и параметра

Сначала преобразуем Punycode в человекочитаемый вид:

```bash
echo "xn--mgbbx8g1d.com" | idn2
```

Вывод: `банк-онлайн.com` (иллюстративное значение, визуально похожее на `bank-online.com`). Это домен с кириллическими символами.

Теперь декодируем параметр `next`:

```bash
echo "aHR0cDovL2ZpbmFsLWV2aWwuY29t" | base64 -d
```

Результат: `http://final-evil.com`. Таким образом, после первого редиректа мы попадём на фишинговую страницу с дальнейшим JavaScript-редиректом на `final-evil.com`.

### Шаг 3: Имитация полного цикла перехода и захват промежуточных страниц

Используем `curl` с опцией `-L` и сохранением заголовков каждого шага:

```bash
curl -s -L -D headers.txt -o intermediate.html "https://bit.ly/3xyzAbC"
cat headers.txt
```

Вывод заголовочного файла показывает цепочку:

```text
HTTP/2 301
location: http://xn--mgbbx8g1d.com/login?next=...
...
HTTP/1.1 302
location: http://final-evil.com
...
HTTP/1.1 200
...
```

Это подтверждает двойной редирект. Загруженная страница `final-evil.com` содержит фишинговую форму.

### Шаг 4: Проверка репутации всех доменов в цепочке

Извлекаем домены: `bit.ly`, `xn--mgbbx8g1d.com`, `final-evil.com`. Для каждого выполняем проверку через VT API (для краткости приведём вывод по `final-evil.com`).

```python
import requests

apikey = 'your_vt_key'
domain = 'final-evil.com'
resp = requests.get(f'https://www.virustotal.com/api/v3/domains/{domain}',
                    headers={'x-apikey': apikey})
data = resp.json()
malicious = data['data']['attributes']['last_analysis_stats']['malicious']
print(f"Malicious detections: {malicious}")
```

Вывод: `Malicious detections: 12` — подтверждает зловредность.

Дополнительно отправляем конечный URL в urlscan.io:

```bash
curl -X POST "https://urlscan.io/api/v1/scan/" \
     -H "API-Key: $URLSCAN_KEY" -d '{"url":"http://final-evil.com","visibility":"unlisted"}'
```

Скриншот в отчёте показывает поддельную страницу входа в банк.

### Ожидаемый вывод примера

Данный кейс демонстрирует типичную фишинговую цепочку: ссылка-шорткат → промежуточный домен с обфусцированным именем и кодированным адресом → финальный вредоносный сайт. Аналитик L1 успешно развернул все этапы, деобфусцировал URL и с помощью репутационных сервисов подтвердил вредоносность. Инцидент эскалирован на L2 для блокировки доменов и оповещения пользователей.
