# Lateral Movement: обнаружение на уровне SOC L1

## 1. Контекст и базовые понятия

**Lateral Movement (горизонтальное перемещение)** — тактика злоумышленника, заключающаяся в перемещении по скомпрометированной сети от одной системы к другой с целью расширения контроля, сбора данных или приближения к критическим активам. В классической модели Kill Chain эта техника располагается после этапов первоначального проникновения и закрепления (Execution, Persistence) и предшествует действиям по сбору информации и финальному воздействию. Атакующий уже находится во внутренней сети, имеет как минимум один опорный хост, и теперь методично обходит сегменты сети, используя легитимные механизмы удалённого управления или похищенные учётные данные.

Принципиальное значение для SOC L1 имеет разграничение горизонтального перемещения со смежными активностями, поскольку не каждое соединение между хостами является злонамеренным, а неопытный аналитик может спутать симптомы с другими стадиями атаки.

Сравнительная таблица ниже проясняет отличия.

| Активность                     | Ключевые признаки и цели                                                                                  | Уровень сети (OSI)       | Типичный вектор                                               | Роль в цепочке атаки                         |
|--------------------------------|-----------------------------------------------------------------------------------------------------------|--------------------------|---------------------------------------------------------------|----------------------------------------------|
| **Lateral Movement**           | Расширение присутствия, использование валидных учётных данных для доступа к новым хостам.                 | Прикладной / транспортный | SMB, RDP, WinRM, SSH, PSRemoting, WMI, DCOM, Pass-the-Hash    | Между начальным доступом и воздействием       |
| **Pivoting (пивотинг)**        | Переброска атакующего трафика через скомпрометированный хост или туннель для доступа к изолированному сегменту. | Сетевой / транспортный    | SSH tunnelling, Meterpreter portfwd, VPN, reverse proxies      | Обеспечение связности, часто сопутствует lateral movement |
| **Vertical Movement**          | Повышение привилегий на том же хосте (Privilege Escalation).                                              | Локально (приложение)    | Эксплойты ядра, уязвимости сервисов, UAC bypass, sudo misconfig | Переход от низких прав к SYSTEM или root      |

Горизонтальное перемещение практически всегда опирается на применение имеющихся у атакующего учётных данных или хэшей, либо на эксплуатацию доверенных административных протоколов, поэтому первичная задача аналитика L1 — выделить аномалии в потоках аутентификации и связанных событиях. Базовые термины, необходимые для понимания:

- **Pass-the-Hash (PtH)** — аутентификация с использованием NTLM-хэша без знания пароля.
- **Pass-the-Ticket (PtT)** — использование билетов Kerberos, украденных из памяти.
- **Overpass-the-Hash** — получение TGT билета по хэшу и последующее использование для запросов к службам.
- **Token theft** — захват токена сеанса для выполнения действий от имени другого пользователя.
- **PSRemoting / WinRM** — легитимные протоколы Windows для удалённого выполнения команд.
- **SMB** — протокол общего доступа к файлам и принтерам, один из главных векторов перемещения в Windows-средах.

## 2. Внутреннее устройство: техники и механизмы горизонтального перемещения

Горизонтальное перемещение не является монолитным приёмом; MITRE ATT&CK® классифицирует десятки техник и подтехник. Для аналитика SOC L1 важно понимать общий ландшафт, чтобы правильно классифицировать инцидент. В SOC L1 наибольшая доля обнаружений приходится на техники класса **Remote Services** (особенно SMB/Admin Shares) и **Pass-the-Hash/Pass-the-Ticket** как способ аутентификации.

## 3. Применение и работа с тематикой в SOC L1

На уровне Tier 1 аналитик работает с алертами систем мониторинга (SIEM, EDR) и выполняет три базовые функции: **верификацию** (действительно ли событие является подозрительным), **триаж** (определение срочности и критичности) и **начальное обогащение** (сбор контекста для L2/L3). В случае lateral movement задача сводится к отделению злонамеренных перемещений от повседневной административной работы.

**Источники данных и базовые запросы.** Основным источником в Windows-инфраструктурах выступают события подсистемы безопасности:

- `4624` An account was successfully logged on — ключевой идентификатор типа входа: **Type 3** (сетевой) для SMB, **Type 10** для RDP, **Type 5** для служб, **Type 2** для интерактивных.
- `4625` An account failed to log on — важно при поиске атак подбора или использования невалидных хэшей.
- `4776` The domain controller attempted to validate the credentials for an account — содержит пакет NTLM и код ошибки; критически важен при Pass-the-Hash.
- `4768` и `4769` — запросы TGT и ST в Kerberos; аномалии во флагах времени или подписи могут указывать на Pass-the-Ticket.
- Sysmon Event ID 1 (process creation) и Event ID 3 (network connection) — дают контекст о запущенных процессах и исходящих соединениях.
- EDR-логи (CrowdStrike Falcon, Microsoft Defender for Endpoint) предоставляют нормализованные события `NetworkEvent, ProcessRollup2, UserLogon` и т.п.

Для ручного расследования в малой среде аналитик может обратиться к PowerShell-командам, подобным приведённой ниже. Она извлекает все события входа с типом 3 на хосте за последний час, агрегируя по учётной записи и источнику:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4624; StartTime=(Get-Date).AddHours(-1)} |
  Where-Object { $_.Properties[8].Value -eq 3 } |
  Select-Object TimeCreated,
    @{n='User';e={$_.Properties[5].Value}},
    @{n='SourceIP';e={$_.Properties[18].Value}},
    @{n='AuthPackage';e={$_.Properties[11].Value}} |
  Group-Object User,SourceIP |
  Sort-Object Count -Descending
```

Вывод такой команды позволяет быстро выявить всплески аутентификаций. Аналитик обращает внимание на:

- учётные записи, не типичные для удалённого администрирования (например, HR-менеджер не должен инициировать SMB-сессию на файловый сервер с рабочей станции бухгалтерии);
- хосты-источники, которые раньше никогда не обращались к целевому серверу (аномалия «first seen»);
- время суток (массовые сетевые логины в 3:00);
- пакет аутентификации — NTLM при наличии Kerberos в домене может быть нормой для legacy-систем, но внезапное появление NTLM на новых хостах подозрительно.

**Типовые ошибки первого уровня.** Самая частая — ложное срабатывание на легитимную работу администраторов. Инструменты управления конфигурациями (SCCM, Ansible) и сценарии резервного копирования генерируют множество сетевых входов под учётными записями служб. Необходимо сверять источник с заранее составленным белым списком админских IP, а также проверять длительность сеанса: инструмент администрирования часто создаёт множество быстрых сессий, а атакующий — одну продолжительную. Другая распространённая ошибка — немедленная эскалация без проверки контекста, например, при обнаружении алерта на Pass-the-Hash из-за некорректной настройки аудита NTLM.

**Паттерны анализа.** Для ускорения принятия решений в SOC вырабатываются повторяемые алгоритмы. Базовый сценарий анализа lateral movement включает:

1. **Селекция алерта** — определение первоначального события (обычно успешный сетевой вход).
2. **Проверка исходного хоста** — поиск Evidence of Compromise на источнике (запуск подозрительных процессов, нестандартные сетевые подключения, наличие известных артефактов Mimikatz в памяти).
3. **Анализ учётной записи** — просмотр предшествующих событий 4625, 4776 для выявления подбора или аномальной активности. Проверка привилегий: если учётка обладает Domain Admin, риск максимален.
4. **Построение временной линии** — последовательность событий на целевом хосте после входа. Если сразу после 4624 появляется процесс `cmd.exe` с родителем `wmiprvse.exe` или `wsmprovhost.exe`, это явное указание на удалённое выполнение кода.
5. **Обогащение** — Threat Intelligence (внутренний репозиторий IOC), геолокация IP, сопоставление с другими алертами за тот же период.

Именно такая методология встроена в современные платформы автоматизированного реагирования, но понимание её аналитиком позволяет быстрее и точнее отсеивать ложные срабатывания и не пропускать критичные инциденты.

**Связь с детальными подтемами.** Аналитику следует углублённо изучить разновидности атак на Kerberos (Golden Ticket, Silver Ticket, AS-REP roasting), особенности логирования в конкретной SIEM (Splunk, Elastic, Microsoft Sentinel) и нюансы протоколов удалённого управления. Но уже на уровне базового обучения важно запомнить: Lateral Movement редко появляется изолированно — ему почти всегда предшествуют разведка и сбор учётных данных, а за ним следуют действия на цели.

## 4. Сквозной практический пример: обнаружение Pass-the-Hash атаки с помощью журналов Windows

Рассмотрим реалистичный инцидент, с которым может столкнуться аналитик Tier 1.

**Исходные условия.** Инфраструктура на базе Windows Server 2019/2022, контроллер домена `DC01`, файловый сервер `FS01`, десять рабочих станций. В качестве SIEM используется Elastic Stack с настроенной пересылкой журналов. Аналитик получает алерт от правила корреляции, которое срабатывает при обнаружении успешного сетевого входа с учётной записью администратора на `FS01` с нетипичного хоста. Подозрительная система — `DESKTOP-AD03` — обычная рабочая станция маркетинга, не участвующая в администрировании.

**Шаг 1. Изучение события входа.** Аналитик выполняет поиск события `4624` в индексе журналов за последние 15 минут.

```json
{
  "@timestamp": "2025-03-14T02:12:33.145286Z",
  "event_id": 4624,
  "LogonType": 3,
  "TargetUserName": "DOMAIN\\svc_admin",
  "TargetDomainName": "DOMAIN",
  "WorkstationName": "DESKTOP-AD03",
  "IpAddress": "10.10.15.42",
  "IpPort": "49188",
  "ProcessName": "-",
  "AuthenticationPackageName": "NTLM",
  "host": { "name": "FS01.domain.local" }
}
```

Ключевые поля: `LogonType=3` (сетевой доступ к SMB-папке), пакет `NTLM` вместо ожидаемого `Kerberos`, источник — рабочая станция, не принадлежащая административной подсети. Эти три признака переводят событие в разряд подозрительных.

**Шаг 2. Верификация источника.** Аналитик запрашивает историю входов с хоста `DESKTOP-AD03` (10.10.15.42) за последний час, чтобы понять, как учётная запись `svc_admin` могла там использоваться.

```powershell
# Запрос в SIEM: поиск событий 4624 и 4625 для указанного IP и пользователя
index=windows event_id IN (4624,4625) source.ip=10.10.15.42 user.name=svc_admin
| stats count by event_id, logon_type, result
```

Вывод (иллюстративный):

```
event_id | logon_type | result   | count
4625     | 2          | 0xC000006A | 12
4624     | 2          | 0x0        | 1
4625     | 3          | 0xC000006A | 5
4624     | 3          | 0x0        | 2
```

Наблюдается всплеск неудачных интерактивных (Type 2) и сетевых входов с кодом ошибки `0xC000006A` (неправильное имя пользователя или пароль). Это типичный след атаки Pass-the-Hash, когда злоумышленник пытается применить хэш, но предварительно мог выполнять попытки входа с реальным (но, возможно, неверным) паролем. Успешный сетевой вход без предшествующего успешного интерактивного означает, что аутентификация произошла не по паролю.

**Шаг 3. Анализ целевого хоста.** На `FS01` сразу после входа аналитик находит процесс, запущенный через удалённый вызов. Sysmon Event ID 1:

```json
{
  "@timestamp": "2025-03-14T02:12:35.523431Z",
  "event_id": 1,
  "Image": "C:\\Windows\\System32\\cmd.exe",
  "CommandLine": "cmd.exe /c net user attacker Password123! /add && net localgroup administrators attacker /add",
  "ParentImage": "C:\\Windows\\System32\\wsmprovhost.exe",
  "ParentCommandLine": "wsmprovhost.exe -Embedding",
  "User": "DOMAIN\\svc_admin",
  "host": "FS01"
}
```

Родительский процесс `wsmprovhost.exe` указывает на использование WinRM (Windows Remote Management) для выполнения команд. Командная строка однозначно говорит о создании нового пользователя и добавлении его в локальную группу администраторов — классический признак компрометации. Таким образом, первоначальный вход по SMB, скорее всего, использовался для бокового перемещения или загрузки инструментов, а WinRM был задействован для выполнения кода.

**Шаг 4. Валидация артефактов Pass-the-Hash.** Для окончательного подтверждения аналитик проверяет журнал `4776` на контроллере домена `DC01`:

```plaintext
Event ID 4776
Credential Validation
  Authentication Package: MICROSOFT_AUTHENTICATION_PACKAGE_V1_0
  Logon Account: svc_admin
  Source Workstation: DESKTOP-AD03
  Error Code: 0x0
```

При успешной аутентификации пакет указан как `MICROSOFT_AUTHENTICATION_PACKAGE_V1_0`, что соответствует NTLM. Журнал не содержит события Kerberos. Поскольку для аутентификации был использован только хэш, события предварительной аутентификации (Kerberos AS-REQ) отсутствуют. Эта констелляция событий подтверждает Pass-the-Hash, так как современные домены по умолчанию используют Kerberos, а NTLM-аутентификация от хоста, работающего с доменной учётной записью, обычно сигнализирует о вмешательстве.

**Ожидаемый вывод.** Пример демонстрирует, как, начиная с одного события успешного входа, аналитик L1 может быстро подтвердить факт горизонтального перемещения через Pass-the-Hash, проанализировав связанные журналы аутентификации и создания процессов. Этап эскалации следует незамедлительно — изолировать `DESKTOP-AD03` и `FS01`, инициировать процедуру реагирования.
