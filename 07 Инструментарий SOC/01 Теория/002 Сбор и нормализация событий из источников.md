# Сбор и нормализация событий из источников в SIEM

## 1. Базовые определения и место сбора/нормализации в SOC

Сбор событий и их нормализация — два последовательных, но концептуально различных этапа обработки данных в SIEM‑системе. Сбор отвечает за непрерывную доставку записей от разнородных источников (серверов, сетевых устройств, приложений, облачных сервисов) в централизованное хранилище или шину событий. Нормализация преобразует полученные разноформатные записи в единую структурированную модель, пригодную для корреляции, поиска и визуализации. Без корректно работающего сбора аналитик SOC L1 не увидит инцидент вовсе; без качественной нормализации он утонет в несопоставимых полях и не сможет построить элементарную поисковую гипотезу.

В операционной модели SOC уровня 1 именно сбор и нормализация определяют «видимость» инфраструктуры. Аналитик L1, принимая алерт из очереди, должен понимать, как событие попало в SIEM, какие трансформации с ним произошли и насколько можно доверять значениям полей. Это знание критично при первичном триаже: опираясь на время, источник, тип события и ключевые артефакты, специалист принимает решение о дальнейшей эскалации.

Для полноценного охвата введём необходимые термины.

**Событие (event)** — атомарная запись о некотором действии или состоянии в информационной системе. Примеры: вход пользователя, срабатывание правила межсетевого экрана, запись веб‑сервера о запросе. Событие имеет источник, временную метку, тип и тело сообщения, которое часто представлено в произвольном текстовом или бинарном формате.

**Инцидент (incident)** — одно или несколько событий, которые с определённой вероятностью свидетельствуют о нарушении политик безопасности, компрометации или аномалии. SIEM генерирует инцидент по результатам корреляции нормализованных событий.

**Сбор (collection)** — технический процесс получения событий от источников, включающий их приём, буферизацию и первичную валидацию (проверку целостности, формата). Реализуется агентами, коллекторами, протокольными слушателями или через безагентное подключение к API.

**Нормализация (normalization)** — многоэтапная обработка входящего события: разбор исходного формата (парсинг), извлечение значащих полей, приведение значений к общей таксономии, обогащение контекстными данными (GeoIP, принадлежность хоста, репутация IP) и запись в унифицированную схему индекса SIEM.

**Парсинг (parsing)** — технический подэтап нормализации, отвечающий за синтаксический анализ исходной записи и выделение пар «ключ–значение».

**Таксономия событий** — согласованный перечень типов событий и их атрибутов (например, `event.category: authentication`, `event.type: start`), используемый в SIEM для единообразной классификации.

Для чёткого разграничения всех понятий полезна следующая таблица.

| Понятие | Определение | За что отвечает | Типичная реализация |
|---------|------------|-----------------|----------------------|
| Источник события (log source) | Система, генерирующая первичную запись | Формирует содержимое события | ОС Windows, Linux syslog, сетевой экран, веб‑сервер |
| Транспортный протокол | Механизм доставки события от источника до коллектора | Гарантирует передачу (с потерями/без) и формат инкапсуляции | Syslog (UDP/TCP/TLS), HTTP/S, Kafka, AMQP |
| Агент сбора | Программный компонент на стороне источника, осуществляющий чтение и отправку событий | Мониторит файлы, журналы, API; буферизует, сжимает, шифрует | Splunk Universal Forwarder, Elastic Agent, Fluent Bit, Winlogbeat |
| Коллектор/коннектор | Серверная служба SIEM, принимающая потоки от множества источников | Приём, распаковка, валидация; может выполнять первичный парсинг | syslog‑ng, Logstash, ArcSight SmartConnector |
| Парсер (нормализатор) | Логика обработки конкретного формата событий | Разбирает сообщение на поля согласно грамматике формата | Grok‑шаблоны, регулярные выражения, специализированные плагины (CEF, LEEF) |
| Схема SIEM (Common Information Model) | Унифицированная модель данных, в которую отображаются все события | Обеспечивает единую точку доступа и корреляции | Elastic Common Schema (ECS), Splunk CIM, QRadar DSM |
| Тэги и категории | Классификационные метки, присваиваемые после нормализации | Позволяют быстро фильтровать события одного класса | `event.category: authentication`, `event.outcome: failure` |
| Обогащение (enrichment) | Добавление внешних данных к событию после нормализации | Повышает контекстную ценность записи (GeoIP, владелец подсети, репутация) | Справочники, Threat Intelligence Feeds |

Главное разграничение, которое обязан удерживать аналитик L1: сбор касается доступности событий, а нормализация — их смысловой интерпретации. Отказ агента означает пропажу событий; ошибка парсинга — появление событий с неразобранным телом, которые проходят мимо корреляции. Понятийная чистота на этом этапе позволяет точечно диагностировать проблемы: «нет событий от контроллера домена» — проблема сбора; «поле `src_ip` пустое для событий входа» — проблема нормализации.

## 2. Компоненты и потоки данных подсистемы сбора событий

Подсистема сбора в SIEM выстраивается вокруг трёх логических ярусов: генерации событий на оконечных устройствах, транспорта через сеть и приёма на стороне платформы. Конфигурация каждого яруса варьируется в зависимости от типа источника, требований к надёжности и объёма данных.

### Ярус источника

Источники событий классифицируются по способу предоставления данных. Выделяют:

1. **Локальные файлы журналов** — классический вариант для Windows (Event Log), Linux (`/var/log/messages`, `auth.log`, журналы systemd), сетевых устройств (локальное хранилище syslog). Для чтения необходим агент, имеющий доступ к файловой системе или API журнала.

2. **Сетевые потоковые протоколы** — устройство само отправляет события по UDP/TCP на указанный коллектор. Наиболее распространён syslog (RFC 5424). Windows‑системы без агента не поддерживают такой режим; требуется дополнительный инструмент (например, Windows Event Forwarding с подписками, который, по сути, формирует агентскую схему).

3. **API‑источники** (REST, gRPC, GraphQL) — современный метод получения событий из облачных сервисов (Microsoft 365, AWS CloudTrail, Google Workspace). SIEM или промежуточный коллектор опрашивает API с заданной периодичностью или подписывается на поток событий через webhook. Характерны rate‑limit’ы и необходимость аутентификации по ключам.

4. **Шина сообщений (Kafka, RabbitMQ, Azure Event Hub)** — внутренний транспорт данных в крупных enterprise‑архитектурах. Приложения публикуют события в топики, а SIEM‑коллектор выступает потребителем. Обеспечивает развязку производителей и потребителей, высокую пропускную способность.

5. **Базы данных и специализированные хранилища** — редкий, но встречающийся случай: сбор событий напрямую из таблиц БД (аудитные записи MS SQL, PostgreSQL) через JDBC/ODBC‑коннекторы. Требует осторожности, чтобы не перегрузить промышленную БД.

Разные SIEM‑платформы предоставляют собственные классификации источников. Например, в Splunk принято разделение на «forwarder inputs» (файлы, сетевые порты, скрипты) и «modular inputs» (REST API). В Elastic Stack — интеграции через агенты или модули Filebeat.

### Агенты и безагентные методы

Выбор архитектуры сбора определяется компромиссом между простотой развёртывания и функциональностью.

**Агентский сбор** предполагает установку легковесного сервиса непосредственно на узле‑источнике. Агент получает доступ к локальным журналам, может выполнять предварительный парсинг, фильтрацию, буферизацию на диске и сжатие. При обрыве связи с коллектором агент сохраняет данные в локальной очереди и возобновляет отправку. Типичные представители: Universal Forwarder (Splunk), Elastic Agent, Fluent Bit, Winlogbeat. Агенты потребляют минимум ресурсов (обычно < 100 МБ ОЗУ, < 5 % CPU в штатном режиме) и поддерживают управление конфигурацией через централизованный сервер.

**Безагентный сбор** реализуется через прямое подключение коллектора к источнику. Это возможно, когда источник сам инициирует отправку (сетевые устройства с syslog) или когда коллектор может удалённо монтировать журналы (WMI, SMB). Безагентный подход снижает административную нагрузку на конечные системы, но несёт риски: отсутствие буферизации в случае сетевого сбоя, невозможность локальной фильтрации, потенциально более высокая загрузка центрального коллектора при разборе тысяч потоков.

На практике SOC‑инженеры комбинируют оба подхода: критически важные серверы (контроллеры домена, базы данных, файловые серверы) обязательно оснащаются агентами, а сетевое оборудование и необслуживаемые IoT‑устройства передают syslog на центральный коллектор.

### Транспортный ярус

Данные от источника до коллектора проходят через IP‑сеть. Базовые требования — надёжность и безопасность.

Протокол syslog исторически использует UDP (порт 514), что не даёт гарантий доставки. Современные развёртывания переходят на TCP (порт 601) и TLS‑обёртку (RFC 5425). Агенты Splunk и Elastic могут передавать данные по проприетарным протоколам, которые внутри используют TCP с опциональным сжатием и шифрованием.

Для высоконагруженных сред между источником и SIEM встраивают промежуточную шину Kafka. Агенты пишут в топики Kafka, а несколько экземпляров Logstash или пользовательских consumer’ов читают и направляют в SIEM. Такая архитектура защищает индексаторы от пиковых нагрузок и позволяет масштабировать обработку.

Граничные устройства (балансировщики, NGFW) иногда используют NetFlow/sFlow для передачи не событий, а статистики потоков — это не относится к сбору событий в классическом понимании SIEM, но может дополнять картину.

### Ярус приёма

На стороне SIEM за приём отвечают сервисы, называемые коллекторами, индексерами-приёмниками или шлюзами событий. Их задачи:

- Принимать соединения от тысяч агентов и syslog‑источников;
- Выполнять TLS‑терминацию;
- Проводить первичную проверку формата (например, является ли сообщение корректным JSON или CEF);
- Буферизовать и направлять во внутреннюю очередь платформы.

Примером служит компонент Splunk Heavy Forwarder, который может агрегировать события от множества Universal Forwarder’ов, фильтровать и маршрутизировать их в нужные индексы. В Elastic Stack аналогичную роль выполняет Logstash (с input‑плагинами beats, syslog, tcp) или напрямую Elastic Agent, отправляющий данные в Elasticsearch через HTTP.

Важным аспектом является асинхронная обработка. Коллектор не должен блокироваться на записи каждого события; он накапливает пакеты и сбрасывает их с групповыми операциями. Поэтому событие проходит путь от возникновения на источнике до появления в индексе с задержкой (lag), которая при штатной работе не превышает нескольких секунд, но может возрастать при пиковых нагрузках или переполнении очередей.

### Потоки данных — иллюстративная схема

Типичный путь события в распределённой инфраструктуре выглядит так:

```text
[Источник (Windows Server)]──(чтение Event Log)──▶ [Агент (Winlogbeat)] 
       │
       └──(TCP/TLS)──▶ [Коллектор (Logstash)]──(фильтрация, обогащение)──▶ [Шина (Kafka)]──▶ [Индексатор (Elasticsearch)]
                                                                                 │
                                                                                 └──▶ [Агент (Fluent Bit)]────▶ [Syslog сервер (syslog-ng)]──▶ [SIEM Collector]
```

Каждый переход может добавлять метаданные: агент проставляет hostname и путь к файлу; коллектор добавляет часовой пояс и метку входящего потока. Контроль целостности на каждом этапе — задача мониторинга: SOC‑инженер отслеживает объёмы поступающих событий по каждому источнику и сравнивает с ожидаемым профилем.

### Ключевые метрики и индикаторы исправности сбора

Аналитик L1 должен уметь интерпретировать простейшие метрики, доступные в панелях мониторинга SIEM:

- **EPS (Events Per Second)** по источнику — резкое падение может означать отказ агента или сетевую проблему.
- **Задержка доставки** (`_ingest_lag`) — разница между временем генерации события (timestamp источника) и временем попадания в индекс. Рост задержки сигнализирует о перегрузке коллектора или шины.
- **Количество ошибок парсинга** — сообщения, которые коллектор не смог разобрать, попадают в «мёртвый» индекс или логи ошибок. Их рост — индикатор смены формата логов на источнике без обновления конфигурации коллектора.

Таким образом, подсистема сбора — это распределённый конвейер, управляемый как централизованными конфигурациями, так и локальными политиками агентов. Без понимания его устройства диагностика даже простейших проблем (например, «не приходят логи с удалённого офиса») превращается в гадание.

## 3. Механизмы нормализации: от сырых записей к структурированной модели

Нормализация преобразует гетерогенный поток событий в унифицированный формат, делая возможной автоматическую корреляцию и ручной поиск. Процесс состоит из нескольких обязательных этапов, реализуемых в коллекторе или непосредственно на индексаторе SIEM.

### Этап 1: Приём и первичная обработка

Событие поступает в коллектор в виде набора байтов. Первый шаг — определение исходного формата. Современные SIEM поддерживают несколько способов идентификации:

- **По источнику (source type)** — администратор заранее привязывает конкретный порт, путь к файлу или тэг агента к определённому формату. Например, события, приходящие на TCP‑порт 514 с IP‑адреса межсетевого экрана, интерпретируются как syslog определённого вендора.
- **Автоопределение** — коллектор анализирует первые байты сообщения на соответствие известным сигнатурам (JSON‑открывающая скобка, `<\\d+>` для syslog‑приоритета, ключевые слова CEF). Надёжность автоопределения неабсолютна и требует тестирования.

После идентификации формата коллектор разбивает входной поток на отдельные события. В TCP‑потоке это последовательные сообщения, разделённые символом перевода строки. В syslog по UDP каждое сообщение — это одна датаграмма.

### Этап 2: Парсинг

Парсинг извлекает из сырого текста или JSON структурированные поля. Используются три основных подхода:

1. **Регулярные выражения с именованными группами** — классический метод, реализованный в Grok (Logstash), регулярных выражениях Splunk, шаблонах ArcSight. Например, для строки `Failed password for root from 192.168.1.100 port 22 ssh2` будет применён Grok‑шаблон:

```text
Failed password for %{USER:user} from %{IP:src_ip} port %{INT:src_port} %{WORD:protocol}
```

Результат: извлечены поля `user`, `src_ip`, `src_port`, `protocol`. Сложность регулярных выражений требует тщательного тестирования на репрезентативной выборке, так как незначительное изменение формата сообщения (лишний пробел, перевод регистра) приводит к провалу парсинга.

2. **Специализированные парсеры известных форматов** — CEF (Common Event Format), LEEF (Log Event Extended Format), Syslog RFC 5424 (структурированные данные). Эти форматы самодокументированы: поля имеют предопределённые имена, и коллектор может использовать готовые библиотеки для разбора без написания regex. Например, сообщение CEF:

```text
CEF:0|vendor|product|version|signature_id|name|severity|extension
```

Парсер CEF автоматически выделит все поля из секции `extension`.

3. **Структурированные форматы (JSON, XML, AVRO)** — если источник отправляет события в JSON, парсинг фактически сводится к десериализации. Коллектор лишь проверяет корректность и извлекает поля верхнего уровня. Опасность кроется во вложенных объектах и массивах, которые могут не поддерживаться плоской схемой SIEM; требуется «разворачивание» (flatten) с помощью dotted‑нотации (например, `user.name`, `user.domain`).

### Этап 3: Нормализация полей

После извлечения сырые поля необходимо отобразить в целевую схему данных. Здесь выполняется несколько операций:

- **Переименование** — сопоставление названий полей источника с именами в CIM (Common Information Model). Например, исходное `src` преобразуется в `source.ip`, а `dst` в `destination.ip`.
- **Приведение типов** — конвертация строкового представления IP‑адреса в тип `ip`, строки с временной меткой в тип `date`, строкового номера порта в `integer`. Ошибки приведения (например, `src_port` = "http") должны обрабатываться: в этом случае можно попытаться преобразовать символьное имя порта в число через справочник, а при неудаче либо записать null, либо поместить событие в очередь ошибок.
- **Разбор составных значений** — некоторые поля источника содержат несколько сущностей: `src_user@src_domain`. С помощью регулярных выражений или функций разделения коллектор может создать отдельные поля `user.name` и `user.domain`.
- **Унификация значений** — приведение к единому справочнику. Например, статус входа в Windows записывается как `0x0` (успех) или `0xC000006A` (неверный пароль); нормализатор сопоставляет коды с человекочитаемыми строками и проставляет `event.outcome: success` или `failure`.

В Splunk процесс нормализации описывается в конфигурациях `props.conf` и `transforms.conf`. В Logstash — через фильтры `mutate`, `grok`, `date`, `translate`. Пример фрагмента конфигурации Logstash для нормализации события SSH:

```ruby
filter {
  grok {
    match => { "message" => "Failed password for %{USER:user} from %{IP:source.ip} port %{INT:source.port} %{WORD:protocol}" }
  }
  date {
    match => [ "timestamp", "ISO8601" ]
    target => "@timestamp"
  }
  mutate {
    convert => { "source.port" => "integer" }
    add_field => { "event.category" => "authentication" }
    add_field => { "event.type" => "start" }
    add_field => { "event.outcome" => "failure" }
  }
}
```

### Этап 4: Обогащение

После приведения к единой модели событие может обогащаться внешними данными, не содержащимися в исходном сообщении:

- **Геолокация** — по IP‑адресу источника определяется страна, город, координаты (GeoIP lookup). Реализуется через загружаемую базу MaxMind. Высокая нагрузка требует кэширования.
- **Контекст хоста** — на основе `source.ip` или `host.name` подтягиваются данные из CMDB: владелец сервера, критичность, среда (продуктив/разработка). Это позволяет правилам корреляции учитывать бизнес‑контекст.
- **Threat Intelligence** — сравнение IP‑адресов, доменов, хэшей с индикаторами компрометации (IoC). Если `source.ip` присутствует в списке известных C2‑серверов, событие помечается тегом `threat.indicator:true`.

Обогащение обычно выполняется на коллекторе до записи в индекс, чтобы все последующие операции использовали уже расширенные данные. В Logstash есть фильтры `geoip`, `elasticsearch` (lookup), `memcached`. Splunk реализует обогащение через workflow `lookup` на этапе поиска, но возможна и предварительная загрузка через трансформации.

### Этап 5: Запись в хранилище и построение индекса

Финальное нормализованное событие попадает в SIEM‑хранилище — обычно документо‑ориентированную базу (Elasticsearch, Splunk Indexer). Поля индексируются в соответствии с заданной схемой: ключевые поля (временная метка, IP‑адреса, hostname, категория события) индексируются как ключевые слова и числовые значения, позволяя выполнять быстрый поиск и агрегации. Неиндексированные поля (`raw_message`) сохраняются для полноты, но поиск по ним медленный.

Таким образом, нормализация — это конвейер, где каждый этап добавляет ценность. Ошибка на любом шаге делает событие бесполезным для анализа. Типичная ошибка — пропуск временной метки из‑за неопознанного формата: событие будет записано с временем приёма, а не генерации, что нарушит хронологию в расследовании. Другая распространённая проблема — перегрузка regex‑парсеров при появлении нового варианта сообщения: поле остаётся неразобранным, и корреляционное правило, завязанное на `event.outcome`, не срабатывает.

## 4. Операционные аспекты: конфигурирование, отладка и мониторинг пайплайна

Работа с подсистемой сбора и нормализации в SOC не заканчивается на этапе проектирования. Аналитики и инженеры постоянно решают задачи по добавлению новых источников, модификации парсеров и расследованию сбоев. Понимание типовых операций и диагностических приёмов позволяет быстро восстанавливать поток событий.

### Добавление нового источника с нормализацией (типовой workflow)

Рассмотрим пошаговый алгоритм действий, обобщённый для популярных SIEM, без привязки к конкретному продукту:

1. **Инвентаризация формата.** Получить образцы событий от источника (обычно 50–100 уникальных сообщений). Определить структуру: syslog‑сообщение с plain‑текстом, JSON, CEF, многорядный стек. Задокументировать вариативность: в каких случаях меняется порядок полей, какие поля опциональны.

2. **Выбор метода сбора.** Исходя из типа ОС, сетевой доступности и объёма, определить, будет ли использоваться агент или сетевой приём. Настроить транспорт: на источнике — отправку на коллектор; на коллекторе — открыть порт и прописать input.

3. **Создание конфигурации парсера.** Написать правило нормализации в соответствии с форматом. Для Grok‑подобных систем это набор шаблонов; для CEF — указание типа источника с готовым коннектором. Ниже приведён иллюстративный фрагмент правила для Splunk `props.conf` и `transforms.conf`:

```ini
# props.conf
[source::udp:514]
sourcetype = my_firewall
TRANSFORMS-normalize = firewall_normalizer

# transforms.conf
[firewall_normalizer]
REGEX = (?i)allow\s+src=(?<src_ip>\S+)\s+dst=(?<dst_ip>\S+)\s+sport=(?<src_port>\d+)\s+dport=(?<dst_port>\d+)
FORMAT = src_ip::$1 dst_ip::$2 src_port::$3 dst_port::$4
```

4. **Тестирование на стенде.** Пропустить образцы через коллектор в тестовой среде, проверив, что все ключевые поля (`src_ip`, `dst_ip`, `action`) извлечены корректно. Обратить внимание на события с нестандартными значениями (пустые IP, нулевые порты).

5. **Валидация таймстемпов.** Убедиться, что временная метка события берётся из исходного сообщения, а не подменяется временем приёма. Для syslog‑сообщений анализируется заголовок приоритета и timestamp; для JSON — поле, указанное явно.

6. **Ввод в эксплуатацию.** Перенаправить поток на продуктивный коллектор, активировать мониторинг EPS и ошибок парсинга. Первые сутки пристально наблюдать за метриками.

### Отладка проблем сбора и нормализации

Аналитик L1, столкнувшись с отсутствием ожидаемых событий или их некорректным отображением, действует по чёткой методике.

**Проверка сбора:**
- Убедиться, что агент запущен и отправляет heartbeat (многие агенты шлют внутренние сообщения о своём состоянии).
- Проверить сетевую связность: `telnet <коллектор> <порт>`, `nc -vz`; удостовериться, что межсетевые экраны не блокируют трафик.
- Просмотреть локальные логи агента на наличие ошибок аутентификации, переполнения очереди, ошибок чтения журнала.

**Проверка нормализации:**
- В SIEM найти любое событие от проблемного источника за последний час. Если события есть, но ключевые поля пусты, проблема в парсере.
- Воспользоваться поисковым запросом для идентификации событий с неразобранным телом (например, `sourcetype=my_app NOT "field_expected=*"` или `_raw` содержит характерную подстроку).
- Извлечь `_raw` сообщение и вручную прогнать через Grok‑дебаггер (встроенный в Kibana Dev Tools или standalone‑утилиты). Пример тестирования Grok в Kibana:

```json
POST _ingest/pipeline/_simulate
{
  "pipeline": {
    "processors": [
      {
        "grok": {
          "field": "message",
          "patterns": ["Failed password for %{USER:user} from %{IP:src_ip}"]
        }
      }
    ]
  },
  "docs": [
    {
      "_source": {
        "message": "Failed password for admin from 10.0.0.5"
      }
    }
  ]
}
```

Ответ покажет извлечённые поля или ошибку.

**Мониторинг ошибок нормализации:**
В SIEM-платформах предусмотрены специальные индексы или дашборды для «мёртвых писем» (dead letter queue). В Splunk это может быть индекс `_internal` с логами `splunkd.log` о неудачных трансформациях. В Elastic — мониторинг Logstash, где есть метрика `logstash_stats_events_filtered_dlq`. Превышение порога ошибок должно инициировать алерт для инженерной команды.

### Управление жизненным циклом парсеров

Форматы логов изменяются при обновлении ПО на источниках. Без контроля версий парсеров возникает drift, когда новая версия приложения добавляет поле, и старый regex‑парсер перестаёт его захватывать, а в худшем случае — не может разобрать сообщение целиком. Для предотвращения:

- Применяют систему контроля версий к конфигурациям парсеров (хранят в Git).
- Внедряют непрерывное тестирование pipeline: каждый коммит в репозиторий парсера запускает симуляцию на наборе образцов и проверяет, что целевые поля корректно извлекаются. Это возможно с помощью фреймворков автоматизации (Ansible + Testinfra, или специализированные решения типа `vector test`).
- Обеспечивают обратную связь: если аналитик L1 замечает аномалию в поле, он создаёт тикет на доработку парсера.

### Взаимодействие аналитика L1 с пайплайном

Для SOC уровня 1 важно уметь не только пользоваться уже нормализованными полями, но и понимать, насколько поле надёжно. Например, если в событии аутентификации значение `user.name` взято из неструктурированного сообщения путём довольно свободного regex, а не из CEF‑раздела, существует риск, что в определённых сценариях туда попадёт IP‑адрес или пустая строка. Аналитик должен уметь проверять исходное событие (`_raw`), чтобы валидировать подозрительные значения, прежде чем эскалировать.

Кроме того, L1 может участвовать в составлении требований к новому источнику: указать, какие поля обязательно должны быть нормализованы для корреляции с существующими правилами (например, `source.ip` и `user.name` обязательно; `process.command_line` желательно). Тем самым он связывает практическую работу с алертами и инженерную настройку пайплайна.

## Сквозной практический пример: настройка приёма логов Windows и их нормализация в SIEM

Рассмотрим реалистичный кейс добавления журнала безопасности контроллера домена Windows Server 2019 в SIEM на базе Elastic Stack (Elasticsearch + Kibana + Logstash). Пример демонстрирует полный цикл: от конфигурирования агента до проверки нормализованного события в Kibana.

**Исходные условия.** Контроллер домена `dc01.lab.local` пишет события аудита в журнал Security. Требуется собирать события с EventID 4624 (успешный вход) и 4625 (неудачный вход) и нормализовать их в Elastic Common Schema (ECS), чтобы в дальнейшем они участвовали в корреляции подозрительных аутентификаций. Сетевой доступ между контроллером домена и сервером Logstash разрешён по TCP 5044 (протокол beats). Установлен Elastic Agent с интеграцией Winlogbeat.

### Шаг 1: Установка и базовая конфигурация агента

На контроллере домена загружен и установлен Elastic Agent. Настройка первичной политики выполняется через Fleet в Kibana. Создаётся агентская политика, в неё добавляется интеграция «Windows Event Log». В YAML‑конфигурации, генерируемой Fleet (доступной для просмотра локально), указываются интересующие каналы и EventID:

```yaml
# фрагмент конфигурации Winlogbeat (иллюстративная схема)
winlogbeat.event_logs:
  - name: Security
    event_id: 4624,4625
    ignore_older: 72h
    processors:
      - add_fields:
          target: ''
          fields:
            event.provider: "Microsoft-Windows-Security-Auditing"
```

После применения политики агент регистрируется в Fleet и начинает пересылку данных на адрес логистического сервера `logstash.lab.local:5044`.

### Шаг 2: Конфигурирование Logstash pipeline для приёма и нормализации

На сервере Logstash создаётся pipeline, включающий input beats, фильтр для разбора JSON‑событий от Winlogbeat и дополнительный фильтр нормализации под конкретные EventID. Фрагмент конфигурации:

```ruby
input {
  beats {
    port => 5044
  }
}
filter {
  if [@metadata][beat] == "winlogbeat" {
    # Winlogbeat уже отправляет JSON с распарсенными полями Windows
    json {
      source => "message"
      target => "winlog"
    }
    # Извлекаем ключевые поля согласно ECS
    mutate {
      copy => {
        "[winlog][event_id]" => "event.code"
        "[winlog][computer_name]" => "host.name"
        "[winlog][record_id]" => "event.id"
        "[winlog][process_id]" => "process.pid"
        "[winlog][thread_id]" => "process.thread.id"
      }
    }

    # Парсим поле event_data, которое содержит специфичные для EventID данные
    if [winlog][event_id] == "4624" or [winlog][event_id] == "4625" {
      grok {
        match => { 
          "[winlog][event_data][TargetUserName]" => "%{NOTSPACE:user.name}" 
        }
        match => {
          "[winlog][event_data][IpAddress]" => "%{IP:source.ip}"
        }
      }
      # Приводим типы
      mutate {
        convert => { "[winlog][event_id]" => "integer" }
      }
      # Классификация события
      if [winlog][event_id] == 4624 {
        mutate {
          add_field => { "event.category" => "authentication" }
          add_field => { "event.type" => "start" }
          add_field => { "event.outcome" => "success" }
        }
      } else if [winlog][event_id] == 4625 {
        mutate {
          add_field => { "event.category" => "authentication" }
          add_field => { "event.type" => "start" }
          add_field => { "event.outcome" => "failure" }
        }
      }
    }
  }
}
output {
  elasticsearch {
    hosts => ["https://es01:9200"]
    index => "logs-windows-%{+YYYY.MM.dd}"
    user => "logstash_writer"
    password => "secret"
    ssl => true
  }
}
```

Комментарии: Winlogbeat отправляет событие в виде JSON, где уже есть выделенные поля `winlog.event_id`, `winlog.event_data.IpAddress` и т.д. Logstash извлекает их, приводит к ECS‑совместимым именам и добавляет категорию. Grok извлекает имя пользователя и IP из подполей `event_data`, так как они могут быть вложенным объектом.

### Шаг 3: Тестирование pipeline на образце события

До включения в продуктовый поток разработчик тестирует конфигурацию с помощью симуляции. В Kibana Dev Tools выполняется запрос к `_ingest/pipeline/_simulate` с примером документа, эмулирующего то, что приходит от Winlogbeat:

```json
POST _ingest/pipeline/_simulate
{
  "pipeline": {
    "description": "test windows auth pipeline",
    "processors": [
      {
        "json": {
          "field": "message",
          "target_field": "winlog"
        }
      },
      {
        "grok": {
          "field": "winlog.event_data.TargetUserName",
          "patterns": ["%{NOTSPACE:user.name}"]
        }
      },
      {
        "grok": {
          "field": "winlog.event_data.IpAddress",
          "patterns": ["%{IP:source.ip}"]
        }
      }
    ]
  },
  "docs": [
    {
      "_source": {
        "message": "{\"event_id\":4625,\"computer_name\":\"dc01.lab.local\",\"record_id\":123456,\"event_data\":{\"TargetUserName\":\"Administrator\",\"IpAddress\":\"10.0.0.100\"}}"
      }
    }
  ]
}
```

Ожидаемый ответ содержит извлечённые поля `user.name`, `source.ip`, `host.name`. Если всё корректно, pipeline утверждается и загружается в продуктовый Logstash.

### Шаг 4: Проверка индексации и поиск в Kibana

После того как агент начал отправку и Logstash обработал несколько событий, индексатор Elasticsearch получает документы. В Kibana создаётся Data View на индекс `logs-windows-*`. Аналитик L1 открывает Discover и выполняет поиск:

```kql
event.code: 4625 and source.ip: *
```

Система возвращает отфильтрованный список неудачных входов. Для каждого события видны нормализованные поля: `user.name`, `source.ip`, `event.outcome: failure`, временная метка `@timestamp`, соответствующая времени генерации события на контроллере домена. Если поле `source.ip` окажется пустым для некоторых записей, аналитик может раскрыть исходный документ и увидеть `winlog.event_data.IpAddress`, что подскажет о проблеме в Grok‑выражении (например, ipv6‑адрес не попал под шаблон `%{IP}`), и инициирует доработку.

### Шаг 5: Мониторинг потока

Для уверенности в стабильности сбора настраивается дашборд с метриками Winlogbeat (количество отправленных событий, ошибки) и Logstash (output events, errors). Команда L1 ежесменно проверяет, нет ли аномалий в EPS от контроллера домена. Пример запроса к метрикам Elastic Agent:

```text
GET metrics-beat-*/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "agent.id": "dc01-agent-id" } }
      ]
    }
  }
}
```

Полученные данные сравниваются с базовым профилем.

Этот пример иллюстрирует полную цепочку: от настройки сбора на источнике до верификации нормализованных полей. Он подчёркивает, что без тщательной проработки конфигурации Logstash SOC‑аналитик рискует получить неполные данные и упустить инцидент.
