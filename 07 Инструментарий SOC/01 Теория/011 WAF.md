# Web Application Firewall (WAF)

## 1. Контекст и базовые понятия

Web Application Firewall (WAF) — это специализированная система защиты, работающая на прикладном уровне (уровень 7 модели OSI) и выполняющая функции обратного прокси-сервера между пользователями и веб-приложением. WAF анализирует входящие HTTP/HTTPS-запросы и ответы приложения, выявляет вредоносные действия и блокирует их до достижения целевого сервера. В отличие от традиционных сетевых файрволов, оперирующих IP-адресами и портами, WAF инспектирует содержимое трафика — заголовки, параметры, тело запроса и файлы cookie — на предмет признаков атак на само приложение.

Основное назначение WAF — защита от угроз, перечисленных в рейтинге OWASP Top 10, наиболее критичных рисков безопасности веб-приложений: SQL-инъекции, межсайтовый скриптинг (XSS), подделка межсайтовых запросов (CSRF), небезопасная десериализация, утечка конфиденциальных данных и другие. По данным [SentinelOne](https://www.sentinelone.com/cybersecurity-101/cybersecurity/web-application-firewall-waf), внедрение WAF способно сократить количество релевантных предупреждений безопасности до 88%, автоматически отсеивая типовые атаки. WAF также часто выступает необходимым элементом в соответствии стандартам, например, требованию 6.6 PCI DSS о защите данных держателей карт.

Следует чётко разграничивать WAF и сходные по названию, но иные по функциональности средства защиты. Таблица ниже фиксирует ключевые различия.

| Средство защиты | Уровень OSI | Основной метод защиты | Типичные защищаемые угрозы |
|------------------|--------------|------------------------|-----------------------------|
| Сетевой файрвол | 3–4 | Фильтрация по правилам IP/порт, контроль сессий | Сканирование портов, подбор паролей по сети, DoS на сетевом уровне |
| Система обнаружения/предотвращения вторжений (IPS/IDS) | 3–7 | Сигнатурный и поведенческий анализ пакетов, часто на уровне протоколов | Эксплойты к ОС и сетевым службам, аномалии протоколов, некоторые атаки на приложения (если есть сигнатуры) |
| **Web Application Firewall (WAF)** | **7** | **Глубокая инспекция HTTP/HTTPS: семантика запросов, сигнатуры веб-атак, поведенческий анализ приложения** | **SQL-инъекция, XSS, CSRF, включение файлов, OWASP Top 10, атаки на бизнес-логику** |
| Защита во время выполнения (RASP) | 7 (внутри приложения) | Встраивание агента в среду выполнения, перехват вызовов изнутри | Те же веб-атаки, но с контекстом выполнения кода, обнаружение аномалий на уровне вызовов |

Таким образом, WAF не заменяет сетевые средства защиты, а дополняет их, закрывая разрыв на уровне логики приложений, где классические межсетевые экраны бессильны. Согласно терминологии [Cloudflare](https://www.cloudflare.com/learning/ddos/glossary/web-application-firewall-waf), WAF часто является частью комплексной эшелонированной обороны, работая в связке с сетевыми файрволами, системами предотвращения DDoS-атак и другими инструментами.

WAF реализует фильтрацию, анализируя входящие HTTP-запросы на предмет соответствия заранее заданным политикам безопасности. Он работает как «стеклянная стена»: легитимные запросы пропускаются незаметно, подозрительные — блокируются либо журналируются для дальнейшего анализа. Современные WAF могут работать в двух основных режимах: **мониторинг** (только запись событий без прерывания трафика) и **активная блокировка**. Такой подход позволяет минимизировать влияние на легитимный бизнес-трафик во время внедрения и тонкой настройки.

## 2. Внутреннее устройство: архитектура, модели фильтрации и виды развёртывания

Внутреннее устройство WAF целесообразно рассматривать сразу с нескольких точек зрения: модель фильтрации, определяющая логику принятия решений, архитектурный тип развёртывания и компонентная структура. Эти аспекты тесно взаимосвязаны, поэтому в данном разделе они объединены в единую систему.

### 2.1. Модели фильтрации

WAF использует комбинацию нескольких моделей для выявления аномалий и атак [Kemp Technologies](https://kemptechnologies.com/blog/web-application-firewall-implementing-and-managing-your-website-security):

- **Сигнатурный анализ (Signature-Based Detection)** — ядро большинства WAF. База сигнатур содержит шаблоны известных вредоносных запросов (например, `' OR 1=1 --` для SQL-инъекции). При совпадении с шаблоном запрос блокируется. Подход эффективен против известных угроз, но бессилен против новых, незнакомых векторов атак и обфускаций.
- **Анализ аномалий (Anomaly-Based Detection)** — строится на отклонении от предварительно обученной «нормальной» модели трафика приложения. Может выявлять атаки нулевого дня и нестандартные варианты эксплуатации, однако требует этапа обучения и более склонен к ложным срабатываниям.
- **Модель безопасности на основе списков (Allow/Block Lists)**:
  - **Отрицательная модель (Negative Security Model)** — определяет, что **запрещено** (сигнатуры атак), а всё остальное разрешено. Проста в начальной настройке, но пропускает атаки, сигнатур которых ещё нет в базе.
  - **Положительная модель (Positive Security Model)** — определяет, что **разрешено** (строго соответствующие ожидаемой структуре запросы), а всё остальное запрещено. Обеспечивает более высокий уровень защиты, но требует детального понимания легитимного трафика приложения и сложнее в поддержке.

На практике применяется гибридный подход: используются как готовые сигнатурные наборы (например, OWASP Core Rule Set), так и поведенческий анализ с контекстными правилами, учитывающими сессии, роли пользователей и последовательности API-вызовов [Oligo Security](https://www.oligo.security/academy/web-application-firewalls-waf-in-2025-in-depth-guide).

### 2.2. Типы развёртывания WAF

По способу размещения и модели обслуживания выделяют три основных типа, описанные в индустрии [UZCERT](https://uzcert.uz/ru/10-web-application-firewall-waf-2025), [Cloudflare](https://www.cloudflare.com/learning/ddos/glossary/web-application-firewall-waf) и других источниках.

| Тип WAF | Размещение | Преимущества | Недостатки | Примеры (иллюстративно) |
|---------|------------|--------------|------------|--------------------------|
| **Сетевой (аппаратный) WAF** | Выделенное устройство в ЦОД, устанавливается в разрыв сети перед серверами приложений | Минимальная задержка, высокая производительность, полный контроль над оборудованием и данными | Высокие капитальные затраты, сложность масштабирования, необходимость физического обслуживания | F5 Advanced WAF, Fortinet FortiWeb (аппаратные серии) |
| **Хостовый (программный) WAF** | Программный модуль/плагин, устанавливаемый непосредственно на веб-сервер или виртуальную машину | Гибкая настройка под конкретное приложение, умеренная стоимость, можно встроить в существующую среду | Потребляет локальные ресурсы сервера, увеличение задержки, сложность централизованного управления множеством инстансов | ModSecurity (Open Source), NAXSI |
| **Облачный WAF** | Сервис, предоставляемый провайдером; трафик перенаправляется через глобальную сеть точек присутствия (PoP) провайдера | Простота внедрения (обычно смена DNS-записи), автоматическое масштабирование, регулярные обновления без участия клиента, модель оплаты по подписке | Передача трафика третьей стороне, возможная дополнительная задержка, ограниченный контроль над специфическими настройками | Cloudflare WAF, AWS WAF, Akamai App & API Protector |

На практике выбор типа WAF диктуется архитектурой приложения и требованиями к производительности. Для распределённых, быстрорастущих систем (интернет-магазины) облачный WAF даёт наибольшую гибкость, тогда как для жёстко регулируемых сред с требованиями суверенитета данных может предпочитаться сетевой вариант.

### 2.3. Архитектурная схема обработки трафика (inline-развёртывание)

Типичное включение WAF в качестве обратного прокси-сервера показано на схеме.

```text
Клиент (браузер)
        │
        ▼
   [Интернет]
        │
        ▼
 ┌─────────────────┐
 │   WAF (reverse   │
 │   proxy, L7)     │
 └────────┬────────┘
          │
          ▼
   [Балансировщик нагрузки / ADC]
          │
          ▼
┌───────────────────┐
│  Веб-серверы, API │
└───────────────────┘
```

WAF терминирует TLS-соединение, дешифрует запрос, применяет политики фильтрации, и, в случае положительного решения, пересылает очищенный запрос далее. При использовании облачного WAF запрос сначала приходит на ближайший PoP провайдера, где происходит фильтрация, и лишь затем отправляется в origin-инфраструктуру клиента. Некоторые архитектуры допускают работу WAF в режиме «out-of-band» (копия трафика), когда устройство получает копию пакетов для анализа и пассивного журналирования, но не имеет возможности блокировать запросы в реальном времени — такой подход безопасен на этапе первоначального обучения.

### 2.4. Внутренние компоненты и управление правилами

Ядро любого WAF состоит из движка обработки правил, где каждая политика безопасности представлена набором условий (инспектируемые части запроса, операторы сравнения, действия). События безопасности агрегируются и могут передаваться в SIEM-системы через syslog или API, обеспечивая централизованную видимость. Помимо встроенных сигнатурных наборов, современные WAF позволяют создавать контекстно-зависимые правила, привязанные к сессионному состоянию, ролями или известным последовательностям API-вызовов, что сокращает количество ложных срабатываний [Oligo Security](https://www.oligo.security/academy/web-application-firewalls-waf-in-2025-in-depth-guide). Обновление сигнатур обычно происходит автоматически через вендорские подписки, но для уникальной логики приложений требуются ручная доработка и регулярный аудит правил.

## 3. Применение и работа с WAF

Практическая работа с WAF — это непрерывный цикл: планирование → внедрение → настройка правил → мониторинг → оптимизация. В SOC L1 специалисты часто сталкиваются с эскалацией алертов от WAF, первичным анализом инцидентов и рутинными операциями по поддержанию политик.

### 3.1. Жизненный цикл внедрения

Обобщая рекомендации [Fortinet](https://www.fortinet.com/resources/cyberglossary/business-web-application-firewall) и [Check Point](https://www.checkpoint.com/cyber-hub/cloud-security/what-is-web-application-firewall/web-application-firewall-waf-best-practices), успешное внедрение WAF строится по фазам:

1. **Оценка и инвентаризация** — составление полного перечня веб-приложений, API и сторонних интеграций, определение критичных активов, сбор базовых метрик трафика.
2. **Архитектурное проектирование** — выбор типа WAF и схемы его встраивания (inline/out-of-band), решение вопросов терминирования TLS, интеграции с балансировщиками и CDN.
3. **Тестовое развёртывание (staging)** — WAF запускается в режиме мониторинга на среде, зеркалирующей продакшен. Импортируются рекомендованные вендором наборы правил (OWASP Top 10, боты, репутационные списки). Проводится нагрузочное тестирование и тестирование на проникновение для валидации как защитных свойств, так и отсутствия деградации производительности.
4. **Продуктивный ввод** — постепенный перевод правил из режима журналирования в режим блокировки с пристальным наблюдением за логами. Корректировка правил для устранения ложных срабатываний.
5. **Эксплуатация и совершенствование** — регулярный анализ событий, настройка контекстных правил, интеграция алертов в SIEM/SOAR, периодический пересмотр политик.

### 3.2. Типовые операции аналитика SOC L1

При работе с WAF в рамках SOC аналитик первого уровня выполняет следующие типовые задачи:

- **Мониторинг дашбордов WAF** (графики блокировок, топ-атак, аномалии трафика) для выявления всплесков.
- **Разбор алертов**: определение, является ли срабатывание истинной атакой или ложным срабатыванием (например, легитимный запрос с длинной строкой, ошибочно классифицированный как инъекция).
- **Реагирование на подозрительную активность**: блокировка IP-адреса/сессии вручную, если атака прошла через фильтры, или временное ослабление правила, мешающего бизнесу.
- **Эскалация** на L2/L3, если обнаружена целенаправленная атака, требующая корректировки правил или расследования инцидента.
- **Выборочный анализ логов** WAF для поиска скрытых угроз (например, медленные сканирования, растянутые во времени).

Типичный фрагмент лога WAF, который может попасть на анализ (структура записи на примере ModSecurity):

```json
{
  "timestamp": "2025-06-10 14:32:15",
  "client_ip": "192.0.2.55",
  "method": "GET",
  "uri": "/products.php?id=1 OR 1=1--",
  "status": 403,
  "rule_id": "942100",
  "message": "SQL Injection Attack: Common Injection Testing Detected",
  "action": "denied"
}
```

Аналитик идентифицирует атаку SQL-инъекции, проверяет IP-адрес по репутационным базам, сопоставляет с другими событиями и, если атака успешно заблокирована, фиксирует инцидент как «предотвращённый».

### 3.3. Настройка пользовательских правил

Кроме готовых наборов, часто требуется тонкая настройка под логику конкретного веб-приложения. Аналитик или инженер формирует правила на языке, специфичном для выбранного WAF. Далее приведён иллюстративный пример правила для open-source WAF ModSecurity, блокирующего запросы, содержащие ключевые слова SQL-манипуляций в любом параметре.

```modsecurity
# Правило для обнаружения SQL-инъекций в аргументах запроса (фаза обработки запроса)
SecRule ARGS "@rx (?i)\b(select|union|insert|delete|update|drop)\b" \
    "id:100001,\
    phase:2,\
    deny,\
    status:403,\
    msg:'Potential SQLi detected in request arguments',\
    logdata:'Matched Data: %{TX.0} found within ARGS',\
    severity:CRITICAL"
```

В данном случае `phase:2` — фаза обработки запроса после декодирования, `deny` — действие блокировки с ответом 403, `@rx` — оператор регулярного выражения. Для промышленной эксплуатации подобные правила комбинируются с проверкой типов данных и длин параметров (положительная модель), чтобы минимизировать ложные срабатывания.

### 3.4. Интеграция с SIEM и операционные метрики

Для централизованного мониторинга события WAF направляются в SIEM-систему (Splunk, Elastic, Sentinel) по протоколу syslog или через HTTPS API. При интеграции настраиваются следующие ключевые поля:

- `src_ip`, `dest_ip`, `http_method`, `uri`, `http_status`
- `waf_rule_id`, `action` (block/detect/log)
- `matched_data` — фрагмент запроса, инициировавший срабатывание.

В SOC по этим данным строятся корреляционные правила: например, «множественные срабатывания WAF с одного IP за короткое время» или «статус 200 после блокировки WAF», что может указывать на обход защиты. Согласно [SecurityScorecard](https://securityscorecard.com/blog/what-is-a-web-application-firewall-and-do-you-need-one), интеграция с процессами TPRM (Third-Party Risk Management) позволяет выявлять внешние уязвимости до того, как ими воспользуются злоумышленники.

## 4. Сквозной практический пример: защита веб-приложения с помощью AWS WAF

### Исходные условия

Организация развернула интернет-магазин в среде AWS. Приложение работает на нескольких EC2-инстансах за Application Load Balancer (ALB). Необходимо внедрить WAF для защиты от SQL-инъекций и XSS, а также ограничить доступ к административной панели только для IP-адресов офиса. Используется AWS WAF — облачный WAF, интегрированный с ALB, CloudFront и API Gateway. Внедрение будет проводиться специалистом SOC / Cloud Security.

### Шаг 1. Создание Web ACL и привязка к ресурсу

Создаётся Web ACL — контейнер для правил. В консоли AWS или через интерфейс командной строки:

```bash
aws wafv2 create-web-acl \
    --name "Ecommerce-ACL" \
    --scope REGIONAL \
    --default-action Block={} \
    --description "WAF for e-commerce application" \
    --rules file://rules.json \
    --visibility-config SampledRequestsEnabled=true,CloudWatchMetricsEnabled=true,MetricName=EcommerceACL \
    --region us-east-1
```

Затем Web ACL ассоциируется с ALB:

```bash
aws wafv2 associate-web-acl \
    --web-acl-arn arn:aws:wafv2:us-east-1:123456789012:regional/webacl/Ecommerce-ACL/abc123 \
    --resource-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/my-alb/abc123
```

**Ожидаемый результат**: команды возвращают идентификаторы созданных объектов; трафик через ALB начинает проверяться пустым (пока без детальных правил) Web ACL, по умолчанию блокирующим всё (`default-action Block`). Это временная конфигурация.

### Шаг 2. Добавление управляемых правил AWS Managed Rules

Добавляется группа правил от AWS для защиты от общих угроз (Core Rule Set, SQLi, XSS). Манифест правил в файле `rules.json`:

```json
[
  {
    "Name": "AWSManagedRulesCommonRuleSet",
    "Priority": 1,
    "Statement": {
      "ManagedRuleGroupStatement": {
        "VendorName": "AWS",
        "Name": "AWSManagedRulesCommonRuleSet"
      }
    },
    "OverrideAction": {
      "None": {}
    },
    "VisibilityConfig": {
      "SampledRequestsEnabled": true,
      "CloudWatchMetricsEnabled": true,
      "MetricName": "CommonRuleSet"
    }
  },
  {
    "Name": "AWSManagedRulesSQLiRuleSet",
    "Priority": 2,
    "Statement": {
      "ManagedRuleGroupStatement": {
        "VendorName": "AWS",
        "Name": "AWSManagedRulesSQLiRuleSet"
      }
    },
    "OverrideAction": {
      "None": {}
    },
    "VisibilityConfig": {
      "SampledRequestsEnabled": true,
      "CloudWatchMetricsEnabled": true,
      "MetricName": "SQLi"
    }
  }
]
```

После обновления Web ACL:

```bash
aws wafv2 update-web-acl \
    --name "Ecommerce-ACL" \
    --scope REGIONAL \
    --id <web-acl-id> \
    --default-action Block={} \
    --rules file://updated-rules.json \
    --visibility-config SampledRequestsEnabled=true,CloudWatchMetricsEnabled=true,MetricName=EcommerceACL \
    --region us-east-1
```

**Ожидаемый результат**: типовые атаки, распознаваемые сигнатурами AWS, будут блокироваться; легитимные запросы пропускаются. В панели мониторинга появятся метрики по каждому набору правил.

### Шаг 3. Создание кастомного правила геоблокировки

Для административной панели `/admin` разрешается доступ только с IP офиса (`203.0.113.0/24`). Правило добавляется в Web ACL (приоритет 0 — применяется первым):

```json
{
  "Name": "AdminGeoRestriction",
  "Priority": 0,
  "Action": { "Allow": {} },
  "Statement": {
    "AndStatement": {
      "Statements": [
        {
          "ByteMatchStatement": {
            "SearchString": "/admin",
            "FieldToMatch": { "UriPath": {} },
            "TextTransformations": [ { "Priority": 0, "Type": "NONE" } ],
            "PositionalConstraint": "STARTS_WITH"
          }
        },
        {
          "NotStatement": {
            "Statement": {
              "IPSetReferenceStatement": {
                "ARN": "arn:aws:wafv2:us-east-1:123456789012:regional/ipset/office-ips/abc123"
              }
            }
          }
        }
      ]
    }
  },
  "VisibilityConfig": {
    "SampledRequestsEnabled": true,
    "CloudWatchMetricsEnabled": true,
    "MetricName": "AdminGeoRestriction"
  }
}
```

IP-сет создаётся отдельно:

```bash
aws wafv2 create-ip-set \
    --name "office-ips" \
    --scope REGIONAL \
    --ip-address-version IPV4 \
    --addresses 203.0.113.0/24 \
    --region us-east-1
```

**Ожидаемый результат**: запросы к `/admin` с любых адресов, кроме офисного диапазона, будут блокированы с ответом 403.

### Шаг 4. Проверка срабатывания и анализ логов

Эмулируется атака SQL-инъекцией (тест из разрешённой сети, чтобы обойти геоблокировку):

```bash
curl -v "http://my-app.example.com/products?id=1' OR '1'='1"
```

В логах AWS WAF (доступны через CloudWatch Logs) появляется запись:

```json
{
    "httpRequest": {
        "clientIp": "198.51.100.10",
        "requestUri": "/products?id=1' OR '1'='1"
    },
    "action": "BLOCK",
    "terminatingRule": "AWSManagedRulesSQLiRuleSet",
    "alignedRule": "SQLi_QueryArguments",
    "timestamp": 1717978123456
}
```

Аналитик SOC видит в SIEM, куда поступают логи, алерт: «AWS WAF: SQL Injection blocked from IP 198.51.100.10». Срабатывание классифицируется как предотвращённая атака, IP вносится в чёрный список для дополнительной изоляции.

### Ожидаемый вывод

Пример демонстрирует, как облачный WAF (AWS WAF) внедряется для защиты реального веб-приложения. С помощью комбинации управляемых сигнатурных наборов и кастомных правил удаётся автоматически блокировать веб-атаки и контролировать доступ к чувствительным ресурсам. Логирование и интеграция с системами мониторинга обеспечивают прозрачность инцидентов для SOC L1, позволяя быстро реагировать на угрозы и совершенствовать политики безопасности.
