# Хранение, поиск и отчётность в SIEM

## 1. Фундамент SIEM: агрегация, хранение и аналитика

Security Information and Event Management (SIEM) — это класс программных решений, объединяющих функции **сбора**, **нормализации**, **корреляции**, **поиска** и **долгосрочного хранения** событий информационной безопасности, а также **генерации отчётности** по ним [SIEM vs Система управления логами, iIT Distribution](https://iitd.ua/ru/siem-vs-sistema-upravleniya-logami-chto-nuzhno-znat-chtoby-vybrat-luchshee-reshenie). Понятие SIEM сложилось из двух исторически самостоятельных направлений: Security Information Management (SIM), отвечающего за долговременное хранение, анализ трендов и подготовку отчётов для комплаенса, и Security Event Management (SEM), концентрирующегося на мониторинге в реальном времени, корреляции событий и оповещениях. Современная SIEM-платформа неразрывно связывает хранение, поиск и отчётность, превращая сырой поток логов в действенный инструмент обнаружения и расследования инцидентов.

Специалисту SOC уровня L1 необходимо чётко разграничивать SIEM и смежную, но функционально более узкую категорию — системы управления логами (Log Management System, LMS). Внешне обе платформы собирают и хранят журналы событий, однако их целевые функции, глубина аналитики и роль в реагировании принципиально различны. Нижеприведённая таблица фиксирует ключевые различия, значимые при выборе инструмента и интерпретации его возможностей.

| Характеристика | SIEM | LMS |
|----------------|------|-----|
| Основная задача | Обнаружение угроз, корреляция, управление инцидентами | Централизованный сбор и удобный поиск по логам |
| Корреляция событий | Встроенные движки правил (корреляция в реальном времени) | Отсутствует или реализуется внешними скриптами |
| Реагирование | Автоматические алерты, интеграция с SOAR | Только базовые уведомления по порогам |
| Аналитика | Поведенческий анализ (UEBA), threat intelligence | Преимущественно поиск по ключевым словам |
| Хранение | Горячее/холодное, индексы для быстрого поиска событий ИБ | Длительное архивирование, оптимизация под объём |
| Комплаенс-отчётность | Встроенные шаблоны (HIPAA, PCI DSS, GDPR, SOX) | Базовая, часто требует ручной настройки |
| Примеры продуктов | Splunk ES, Microsoft Sentinel, Rapid7 InsightIDR, RuSIEM | Graylog, ELK Stack (базовый), rsyslog+хранилище |

Таблица 1.1 — Сравнение SIEM и системы управления логами (на основе [SIEM vs Система управления логами, iIT Distribution](https://iitd.ua/ru/siem-vs-sistema-upravleniya-logami-chto-nuzhno-znat-chtoby-vybrat-luchshee-reshenie)).

Три столпа, на которых строится практическая ценность SIEM для SOC, — это **хранение**, **поиск** и **отчётность**. Хранение определяет, как долго и в каком виде доступны свидетельства компрометации; поиск — способность аналитика быстро локализовать нужную иголку в стоге сена; отчётность — средство демонстрации результатов работы, соблюдения нормативных требований и накопления доказательной базы. Далее каждый из этих аспектов рассматривается детально на уровне, достаточном для осмысленной работы аналитика L1.

## 2. Хранение логов в SIEM: архитектура, форматы и политики удержания

Подсистема хранения SIEM выполняет гораздо более сложную задачу, чем просто запись файлов на диск. Её цель — обеспечить **неизменяемость**, **доступность для быстрого поиска** и **экономическую эффективность** при соблюдении жёстких регуляторных сроков удержания. Архитектура хранения типовой SIEM-платформы включает несколько функциональных слоёв, каждый из которых влияет на производительность поиска и глубину ретроспективного анализа (рис. 2.1).

```text
                   ┌─────────────┐      ┌──────────────────┐
Источники (DC,     │ Коллекторы  │────▶ │   Нормализация   │
сетевые экраны,    │ (агенты,    │      │  (парсеры, CEF,  │
облачные API…)     │ syslog)     │      │   LEEF, JSON)    │
                   └─────────────┘      └──────┬───────────┘
                                               │
                   ┌─────────────┐      ┌──────▼───────────┐
                   │  «Холодное»  │◀──── │  Индексация и    │
                   │  хранилище   │      │  «горячее» хра-  │
                   │ (S3, HDFS,   │      │  нилище (Elastic,│
                   │  Data Lake)  │      │  колоночные БД)  │
                   └─────────────┘      └──────────────────┘
```

### 2.1. От коллекторов к нормализованным событиям

SIEM получает данные от сотен и тысяч источников: контроллеров домена, межсетевых экранов, IDS/IPS, облачных провайдеров (AWS CloudTrail, Azure Activity Log) и пр. Разнородные форматы — syslog, Windows Event Log, JSON API, бинарные протоколы — сначала попадают на **коллекторы** (агенты на хостах либо централизованные приёмники syslog). На этом этапе важно гарантировать доставку без потерь (буферизация на агенте, TCP с подтверждением). Далее события проходят **нормализацию**: парсеры извлекают значащие поля (временную метку, идентификатор события, пользователя, IP-адрес) и приводят их к единой схеме. Типичными форматами нормализованного события выступают CEF (Common Event Format), LEEF (Log Event Extended Format) или внутренняя JSON-модель конкретной SIEM.

```json
{
  "event": {
    "id": "4625",
    "provider": "Microsoft-Windows-Security-Auditing",
    "outcome": "failure"
  },
  "user": { "name": "jdoe", "domain": "CORP" },
  "source": { "ip": "<иллюстративный IP>", "hostname": "desktop-01" },
  "timestamp": "<метка времени UTC>",
  "raw": "<исходная строка события для отладки>"
}
```

Пример 2.1 — Схема нормализованного события неудачного входа (значения полей иллюстративны, структура отражает реальные модели SIEM-систем, таких как RuSIEM или Elastic Event Model).

### 2.2. Горячее и холодное хранение: компромисс стоимости и скорости

События, к которым аналитикам SOC нужен регулярный и быстрый доступ (обычно за последние 30–90 дней), размещаются в **«горячем» хранилище** на базе технологий, оптимизированных для полнотекстового поиска: Elasticsearch, Apache Solr или колоночные аналитические базы данных. Горячее хранение дорого в пересчёте на гигабайт, но обеспечивает отклик в сотни миллисекунд, что критически важно при оперативном расследовании.

По мере старения данные перемещаются в **«холодное»** или архивное хранилище (Amazon S3, Hadoop HDFS, локальные объектные хранилища). Стоимость хранения здесь на порядок ниже, однако поиск может требовать восстановления индексов или последовательного сканирования. Организации описывают эту модель как «hot/warm/cold» иерархию, а австралийский центр кибербезопасности (ACSC) рекомендует тщательно продумать разделение на «hot» (легкодоступные) и «cold» данные, чтобы не раздувать бюджет при сохранении способности к форензике [ACSC, Best practices for event logging and threat detection](https://www.cyber.gov.au/sites/default/files/2024-08/best-practices-for-event-logging-and-threat-detection.pdf).

### 2.3. Политики удержания (retention) и нормативная база

Длительность удержания событий диктуется тремя факторами: законодательными требованиями, потребностями расследований и финансовыми ограничениями. В таблице 2.1 приведены минимальные сроки для нескольких ключевых стандартов; реальная политика часто ориентируется на самый строгий из применимых, а затем накладывается на корпоративный риск-профиль.

| Регулятор / стандарт | Минимальный срок хранения | Тип логов, на которые распространяется |
|----------------------|---------------------------|----------------------------------------|
| HIPAA (США) | 6 лет | Логи доступа к электронной защищённой медицинской информации (ePHI) [Cyber Silo, How Long Should a SIEM Retain Log Data?](https://cybersilo.tech/how-long-should-a-siem-retain-log-data) |
| PCI DSS | 1 год | Все логи, имеющие отношение к обработке данных банковских карт |
| SOX (США) | 7 лет | Аудиторские логи финансовых систем |
| GDPR (ЕС) | Явно не фиксирован, общепринятая практика 6–12 мес. | Любые логи, содержащие персональные данные (IP, имена пользователей), если они необходимы для accountability [Cyber Silo](https://cybersilo.tech/how-long-should-a-siem-retain-log-data) |

Таблица 2.1 — Примеры нормативных требований к срокам хранения событий.

Практические рекомендации, подкреплённые опытом реагирования и требованиями киберстраховщиков, таковы: **минимум 90 дней горячего хранения, предпочтительно 6–12 месяцев общим сроком**. Страховые компании всё чаще требуют 12-месячного удержания логов как условия выплаты покрытия [Blumira, 5 Best Practices For Security Log Retention](https://www.blumira.com/blog/5-best-practices-for-security-log-retention). Вендоры SIEM задают ориентиры: например, Rapid7 InsightIDR по умолчанию хранит логи 13 месяцев, а для долгосрочного архивирования предлагает интеграцию с S3-бакетом клиента [Rapid7, Data Storage and Retention FAQs](https://docs.rapid7.com/insightidr/data-storage-faq). На этапе проектирования SOC важно зафиксировать retention policy в документации и настроить автоматическую ротацию, чтобы избежать потери значимых артефактов.

### 2.4. Неизменяемость и целостность хранимых логов

Атакующий, получивший привилегированный доступ, зачастую пытается уничтожить следы своего присутствия — очистить Event Log на хосте или модифицировать записи в централизованном хранилище. Поэтому SIEM-архитектура обязана реализовывать **иммутабельность (неизменяемость)** логов. Это достигается разграничением прав (запись разрешена только коллекторам, удаление — никому, кроме узкого круга администраторов хранилища), размещением хранилища в отдельном сетевом сегменте и применением WORM-политик (Write Once Read Many) на уровне файловой системы или объектного хранилища. Австралийские рекомендации (ACSC) прямо указывают, что логи должны храниться в отдельной или сегментированной сети с дополнительными мерами защиты, чтобы снизить риск подделки при компрометации основной инфраструктуры [ACSC, Best practices for event logging and threat detection](https://www.cyber.gov.au/sites/default/files/2024-08/best-practices-for-event-logging-and-threat-detection.pdf).

Cloud SIEM-решения обеспечивают неизменяемость на уровне платформы: например, Rapid7 шифрует данные на коллекторе, передаёт их по защищённому каналу в AWS, где они токенизируются, изолируются на уровне тенантов и защищены строгими ACL [Rapid7 Data Storage FAQ](https://docs.rapid7.com/insightidr/data-storage-faq). Для on-premise решений рекомендуется выносить дисковые массивы SIEM в выделенный VLAN, применять снапшоты и регулярное резервное копирование.

## 3. Поиск в SIEM: язык запросов, индексы и оперативная аналитика

Поисковая подсистема — основной рабочий инструмент аналитика L1 при разборе алертов и проактивном поиске угроз (threat hunting). От того, насколько быстро и точно SIEM позволяет извлечь нужные события из миллиардов записей, зависит время обнаружения (Mean Time to Detect, MTTD) и производительность смены.

### 3.1. Индексация временных рядов событий

В основе быстрого поиска лежит **инвертированный индекс**, хранящий соответствие между значениями полей и идентификаторами документов. Большинство SIEM-систем строят индексы, разбитые по времени (time-partitioned indices): ежедневные или еженедельные сегменты. Это позволяет ограничивать сканирование только релевантным временным диапазоном, существенно ускоряя запросы. Например, в Elasticsearch каждый индекс вида `logstash-2025.03.15` содержит события за конкретные сутки; запрос, явно указывающий временные границы, обращается только к нескольким таким индексам, а не ко всему хранилищу.

### 3.2. Языки запросов: от простого к сложному

Каждая SIEM-платформа предлагает собственный язык запросов, но все они строятся вокруг нескольких общих парадигм:

- **Поиск по полю-значению** — базовые фильтры, эквивалентные SQL-условию `field = value`.
- **Полнотекстовый поиск** — нечёткий поиск по всем или заданным полям.
- **Агрегации и вычисляемые метрики** — `group by`, `count()`, `stats` для построения сводок.
- **Временные окна** — группировка по временным интервалам для выявления аномалий.

Рассмотрим несколько характерных примеров. Они иллюстративны и демонстрируют синтаксис популярных SIEM-систем, однако конкретные имена полей и значения зависят от среды.

**Splunk (SPL)** — наиболее развитый и часто цитируемый язык поиска в SIEM.
```
index=windows event_id=4625 status=failure
| stats count by user, src_ip
| sort -count
```
Пример 3.1 — SPL-запрос, подсчитывающий количество неудачных попыток входа (Event ID 4625) в разрезе пользователя и IP-адреса, с сортировкой по убыванию.

**Microsoft Sentinel / Azure Data Explorer (KQL)** — язык Kusto, широко применяемый облачными SIEM.
```
SecurityEvent
| where EventID == 4625
| summarize Count = count() by Account, IpAddress, bin(TimeGenerated, 1h)
| where Count > 5
```
Пример 3.2 — KQL-запрос, выявляющий хосты и учётные записи, для которых за час произошло более 5 неудачных входов. Оператор `bin` группирует события по часовым интервалам.

**Rapid7 InsightIDR (LEQL)** — простой язык, ориентированный на быстрое составление запросов без глубоких знаний синтаксиса [Rapid7 Data Storage FAQ](https://docs.rapid7.com/insightidr/data-storage-faq).
```
where(service = 'windows_security' AND event_id = 4625)
groupby(user)
calculate(count)
```
Пример 3.3 — LEQL-запрос, агрегирующий количество событий 4625 по пользователям.

Общая рекомендация для аналитика L1: начинайте с узкого временного окна (15–30 минут вокруг события), затем расширяйте, используйте фильтры по идентификаторам событий и ключевым полям, и только потом применяйте полнотекстовый поиск — он наиболее дорогой и может возвращать много шума.

### 3.3. Поиск по нераспарсенным событиям

На начальном этапе подключения нового источника или при отсутствии готового парсера события попадают в SIEM в «сыром» виде, без выделенных полей. Аналитик должен уметь искать и по такому тексту. Например, в RuSIEM для этого необходимо включить чекбокс **«Поиск по нераспарсенным событиям»** в разделе «События → Все события → Параметры» [Habr, Интеграция аудит-логов с SIEM](https://habr.com/ru/companies/selectel/articles/981796). После этого система просматривает не индексированные поля, а исходное тело сообщения. Недостаток — значительно более низкая скорость, поэтому такой поиск следует использовать точечно, для первичной проверки наличия логов от источника.

Пример настройки приёма syslog из облачного источника (иллюстративная схема на основе реального кейса Selectel):
```ini
AUDIT_LOGS_URL=<URL эндпоинта>
USERNAME=<учётная запись>
PASSWORD=<пароль>
ACCOUNT_ID=<идентификатор аккаунта>
SYSLOG_ENABLED=true
SYSLOG_HOST=<IP вашего SIEM>
SYSLOG_PORT=<порт приёма>
```
Пример 3.4 — Фрагмент конфигурации для отправки логов аудита в SIEM по протоколу syslog [Habr, Интеграция аудит-логов с SIEM](https://habr.com/ru/companies/selectel/articles/981796).

После запуска потока аналитик выполняет поиск по сырому тексту (например, «`account_id`=XXXXX»), убеждается в поступлении событий, а затем инициирует создание парсера силами L2-инженеров.

### 3.4. Типичные ошибки начинающего аналитика при поиске

- **Слишком широкий временной диапазон** — запрос за месяц на горячем индексе может выполняться минуты и затронуть лимиты ресурса. Всегда сужайте окно до разумного, используйте фильтры.
- **Поиск по строке без учёта регистра и спецсимволов** — поле «User» может храниться как «JDOE», «jdoe», «CORP\jdoe»; применяйте регулярные выражения или ключи `*` аккуратно.
- **Игнорирование лимитов вывода** — SIEM по умолчанию возвращает первые 100–1000 результатов. Если вы не увеличили этот лимит, можно пропустить редкие, но значимые события.
- **Использование полнотекстового поиска как основного инструмента** — это медленно и энергоёмко. Где возможно, опирайтесь на индексированные поля.

## 4. Отчётность в SIEM: автоматизация, шаблоны и compliance-документация

Отчётность — мост между операционной работой SOC и бизнес-потребностями организации: демонстрация эффективности средств защиты, доказательство соблюдения нормативных требований, накопление доказательств для разбора инцидентов. SIEM-платформа способна не только генерировать статические «бумажные» отчёты, но и поддерживать интерактивные дашборды, отражающие текущую картину безопасности.

### 4.1. Виды отчётов в SOC

Отчёты условно делятся на три категории, различающиеся по периодичности и целевой аудитории:

- **Оперативные (дашборды)** — обновляются в реальном времени, отображают ключевые метрики: количество алертов по серьёзности, топ источников атак, статус здоровья коллекторов. Аналитик L1 мониторит их на протяжении смены.
- **Тактические (ежедневные/еженедельные)** — агрегированные данные за период: количество обработанных инцидентов, среднее время реакции, статистика по типам событий. Используются руководителем смены для оценки нагрузки и трендов.
- **Стратегические (ежемесячные/квартальные) и комплаенс-отчёты** — подготавливаются для CISO, аудиторов, регуляторов. Включают долгосрочные тренды, отчёты по доступу к критичным системам, подтверждение выполнения retention policy и покрытия источников.

### 4.2. Инструменты генерации и автоматизации

Большинство SIEM предоставляют **планировщик отчётов** (Report Scheduler) и библиотеку шаблонов. Аналитик выбирает источник данных (набор проиндексированных логов или сохранённый поиск), задаёт расписание (cron-выражение), формат (PDF, CSV, HTML) и список получателей. Такой подход минимизирует ручной труд и гарантирует своевременную доставку. Пример конфигурации задания отчёта, выраженный в виде иллюстративной YAML-схемы, типичной для ряда SIEM-решений:

```yaml
report_job:
  name: "Еженедельный отчёт о неудачных входах"
  schedule: "0 8 * * 1"       # каждый понедельник в 08:00
  source:
    type: saved_search
    id: "failed_logins_7d"
  format: pdf
  template: "compliance_summary"
  recipients:
    - "soc-lead@company.com"
    - "compliance@company.com"
  parameters:
    time_range: "last_7_days"
    group_by: ["department", "user"]
```
Пример 4.1 — Иллюстративная схема конфигурации автоматического отчёта.

Современные SIEM также поддерживают отправку сырых данных во внешние BI-системы (Power BI, Tableau) для построения кастомных визуализаций, однако для оперативных задач SOC обычно достаточно встроенных возможностей.

### 4.3. Комплаенс-отчётность на практике

Пожалуй, наиболее жёсткие требования к отчётности предъявляются регуляторами. SIEM должен уметь продемонстрировать цепочку событий, подтверждающую соблюдение политик доступа, и сохранить такие отчёты на срок, определённый стандартом. Так, для HIPAA типовой отчёт может включать:

- Перечень всех случаев доступа к системам, обрабатывающим ePHI, за последние 6 лет.
- Информацию о неудачных попытках аутентификации на этих системах.
- Данные об изменениях прав доступа.

Эти отчёты формируются на основе корреляции логов контроллера домена (события 4624, 4625, 4672, 4720 и др.) и файловых серверов (события 4663). Шаблон в SIEM предварительно настраивается инженером L2, задача L1 — убедиться, что отчёт сгенерирован без ошибок, покрывает требуемый период и что в нём отсутствуют аномалии (например, нулевое количество событий за дни, когда активность заведомо была). Расхождения немедленно эскалируются, так как могут свидетельствовать о потере части логов или о проблемах с Retention Policy.

### 4.4. Типичные проблемы и их индикаторы для L1

- **Пустой отчёт за период, когда ожидалась активность** — возможный разрыв в цепочке доставки логов; требует проверки статуса коллекторов и сетевой связности.
- **Слишком большой размер отчёта, невозможность открыть** — избыточно широкий фильтр. Необходимо уточнить условия поиска у старшего аналитика.
- **Отчёт содержит события из будущего** — рассинхронизация времени на источнике или коллекторе. Может ломать корреляцию; подлежит эскалации.
- **Отсутствие событий от критичного источника** (например, Domain Controller) — требует немедленного реагирования, поскольку нарушает видимость инфраструктуры.

## Сквозной практический пример: от подозрительного входа до еженедельного отчёта

### Исходные условия

- Среда: тестовый стенд с контроллером домена Windows Server 2022 (hostname `DC01`), развёрнут SIEM на базе Wazuh + Elasticsearch (on-premise), коллектор установлен на DC01.
- Роль: аналитик SOC L1, ежедневно мониторящий дашборд и разбирающий автоматические алерты.
- Сценарий: в 09:32 сработал алерт о множественных неудачных попытках входа (Event ID 4625) для учётной записи `svc_scan`. Требуется выполнить поиск для уточнения деталей и подготовить недельный отчёт об активности этой учётной записи.

### Шаг 1. Убедиться в корректной отправке логов с DC01

На DC01 настроен агент Wazuh, отправляющий в SIEM канал Security. Конфигурационный фрагмент `ossec.conf` на DC01:

```xml
<localfile>
  <location>Security</location>
  <log_format>eventchannel</log_format>
</localfile>
```
Пример 5.1 — Фрагмент конфигурации Wazuh-агента для сбора событий Windows Security Event Log.

Аналитик проверяет, что события поступают в индексы Elasticsearch без задержек, выполнив быструю проверку наличия свежих записей:

```bash
curl -s -X GET "http://siem.internal:9200/wazuh-alerts-*/_count" \
  -H 'Content-Type: application/json' \
  -d '{"query": {"bool": {"filter": [
    {"term": {"agent.name": "DC01"}},
    {"range": {"@timestamp": {"gte": "now-15m"}}}
  ]}}}'
```
Пример 5.2 — Команда curl, возвращающая количество алертов от агента DC01 за последние 15 минут. Ожидаемый вывод: `{"count":1250,"_shards":{...}}`. Ненулевое значение подтверждает, что сбор работает.

### Шаг 2. Поиск деталей неудачных входов

Используя панель Kibana / Dev Tools, аналитик формирует запрос на поиск событий 4625 для `svc_scan` за последний час:

```json
GET wazuh-alerts-*/_search
{
  "query": {
    "bool": {
      "must": [
        {"match": {"data.win.system.eventID": 4625}},
        {"match": {"data.win.eventdata.targetUserName": "svc_scan"}}
      ],
      "filter": [
        {"range": {"@timestamp": {"gte": "now-1h"}}}
      ]
    }
  },
  "size": 10,
  "sort": [{"@timestamp": "desc"}]
}
```
Пример 5.3 — Elasticsearch-запрос для поиска неудачных входов конкретной учётной записи.

Ожидаемый результат: набор документов, в каждом из которых поле `data.win.eventdata.ipAddress` содержит один и тот же IP `192.168.100.45`, что свидетельствует о злонамеренной брутфорс-активности с одного хоста. Аналитик фиксирует находку в заметках к инциденту.

### Шаг 3. Создание недельного отчёта

Для документирования инцидента и демонстрации тренда аналитик генерирует CSV-отчёт, используя встроенный планировщик (альтернативно — Python-скрипт, извлекающий данные через Elasticsearch API):

```python
import requests, csv, datetime
from elasticsearch import Elasticsearch
es = Elasticsearch("http://siem.internal:9200")
query = {
    "query": {
        "bool": {
            "must": [{"match": {"data.win.system.eventID": 4625}}],
            "filter": [{"range": {"@timestamp": {"gte": "now-7d/d"}}}]
        }
    },
    "size": 1000
}
res = es.search(index="wazuh-alerts-*", body=query)
with open('failed_logins_week.csv', 'w', newline='') as f:
    writer = csv.writer(f)
    writer.writerow(["Timestamp", "User", "Source IP", "Workstation"])
    for hit in res['hits']['hits']:
        s = hit['_source']['data']['win']['eventdata']
        writer.writerow([hit['_source']['@timestamp'],
                         s.get('targetUserName'),
                         s.get('ipAddress'),
                         s.get('workstationName')])
print(f"Exported {len(res['hits']['hits'])} events.")
```
Пример 5.4 — Python-скрипт, выгружающий все события 4625 за последнюю неделю в CSV-файл (иллюстративная схема; в реальном SOC формат и поля определяются политикой отчётности).

### Ожидаемый вывод

Пример подтверждает сквозную связку: настройка коллектора гарантирует попадание событий в горячее хранилище Elasticsearch; поисковый запрос позволяет в течение секунд извлечь релевантные артефакты; отчёт агрегирует недельные данные и может быть автоматически направлен руководителю SOC или прикреплён к тикету инцидента. Аналитик L1, владеющий этими базовыми операциями, способен самостоятельно провести начальное расследование и предоставить структурированные результаты, не привлекая смежные команды.
