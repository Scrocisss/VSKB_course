# Примеры систем управления инцидентами: TheHive, R-Vision SOAR и Naumen Service Desk

## 1. TheHive: платформа управления инцидентами с аналитическим ядром Cortex

TheHive — свободно распространяемая платформа реагирования на инциденты безопасности (Security Incident Response Platform, SIRP), созданная в 2014 году группой экспертов CERT‑Banque de France. Проект распространяется под лицензией AGPLv3; на начало 2025 года актуальна версия 4.0.5, выпущенная в феврале 2021 г., а также ветка 5.x с переработанной архитектурой. В отличие от классических SOAR‑систем, TheHive сам по себе не оркеструет действия на сетевом оборудовании — он фокусируется на управлении расследованием, кооперации аналитиков и автоматическом обогащении индикаторов компрометации (IoC) через тесно интегрированный аналитический движок Cortex. Именно эта связка «SIRP + аналитический двигатель» даёт возможность автоматизировать типовые этапы первичного анализа без написания сложных плейбуков.

В сообществе нередко путают функциональные границы TheHive и полновесных SOAR. Следующая таблица разграничивает предметные области:

| Система / подход | Основная функция | Типовые возможности | Примеры реализации (иллюстративно) |
|-------------------|-------------------|---------------------|-----------------------------------|
| SIRP (TheHive) | Управление кейсами и задачами расследования | Создание кейсов из алертов, обогащение наблюдаемых через анализаторы, ведение журнала действий, REST API для интеграций | TheHive, DFIR‑IRT, FIR |
| SOAR (оркестровка) | Автоматизация цепочек реагирования на инциденты | Запуск плейбуков, выполнение команд на межсетевых экранах/EDR, маршрутизация по SLA, управление инцидентами на всех стадиях | R‑Vision SOAR, Cortex XSOAR, Splunk Phantom |
| ITSM / Service Desk (Naumen SD) | Учёт, маршрутизация и контроль исполнения заявок | Регистрация обращений, автоматическое назначение исполнителей, контроль SLA, отчётность, согласование | Naumen Service Desk, OTRS, ServiceNow |

Таким образом, TheHive занимает нишу «умного» кейс‑менеджмента, централизуя работу аналитиков и освобождая их от ручного поиска информации по каждому IoC.

### 1.1 Внутреннее устройство и интеграционная экосистема

TheHive написан на Scala, фронтенд использует AngularJS с Bootstrap. В качестве хранилища выступает ElasticSearch, обеспечивающий полнотекстовый поиск по кейсам и наблюдаемым. Все сценарии взаимодействия с внешними системами реализованы через REST API, что позволяет подключать SIEM, NDR, почтовые шлюзы и чат‑каналы.

Архитектурно продукт не монолитен, а существует в составе экосистемы, ключевые компоненты которой показаны на схеме:

```text
                  ┌─────────────┐
                  │   SIEM/NDR  │ (Stamus SSP, Wazuh, Splunk)
                  └──────┬──────┘
                         │ alert/webhook
                         ▼
┌────────────────────────────────────────────────────────────┐
│                      TheHive                               │
│  ┌───────────┐  ┌────────────┐  ┌──────────────┐           │
│  │  Кейсы    │  │ Наблюдаемые│  │  Задачи (tasks)│          │
│  └─────┬─────┘  └─────┬──────┘  └──────┬───────┘           │
│        │              │               │                    │
│        │ REST API     ▼               │                    │
│        │        ┌──────────┐          │                    │
│        │        │  Cortex  │          │                    │
│        │        └────┬─────┘          │                    │
│        │             │                │                    │
└────────┼─────────────┼────────────────┼────────────────────┘
         │             │                │
         ▼             ▼                ▼
 ┌────────────┐  ┌──────────────┐  ┌───────────────┐
 │   MISP     │  │ Hippocampe   │  │ TheHive4Py    │
 │ (фиды IoC) │  │ (агрегатор)  │  │ (Python API)  │
 └────────────┘  └──────────────┘  └───────────────┘
```

**Cortex** — аналитический движок, исполняющий «анализаторы» (Python-скрипты) для обогащения наблюдаемых. Анализаторы обращаются к VirusTotal, Shodan, PassiveTotal, Whois и десяткам других сервисов. Результаты возвращаются в TheHive и прикрепляются к кейсу. Помимо анализаторов, Cortex содержит «респондеры» — скрипты, выполняющие активные действия, например отправку уведомления в мессенджер или блокировку IP на межсетевом экране (при интеграции с SOAR или прямым доступом к оборудованию). Однако штатно респондеры в TheHive не выполняют тяжёлых оркестровок, поскольку для этого требуется управление контекстом и безопасное выполнение команд на целевых системах — задача полноценной SOAR‑платформы.

**MISP** (Malware Information Sharing Platform) выступает источником и хранилищем IoC. Интеграция двусторонняя: аналитик может импортировать индикаторы из MISP в кейс TheHive и, наоборот, экспортировать подтверждённые индикаторы в MISP для обмена с партнёрами.

**Hippocampe** — агрегатор TI‑фидов с собственным REST API; Cortex содержит анализатор для поиска по его базе. Таким образом, экосистема позволяет реализовать замкнутый цикл: получение алерта → создание кейса → автоматическое обогащение → принятие решения → запись IoC в MISP.

### 1.2 Практическое применение: приём алертов и обогащение

В реальной работе SOC первого эшелона TheHive обычно интегрируется с SIEM-источником. Сценарий выглядит так:

1. SIEM генерирует алерт высокого приоритета (например, сработка правила на подозрительное DNS-туннелирование).
2. Через вебхук или скрипт интеграции алерт автоматически создаёт кейс в TheHive. Используется REST API: `POST /api/case` с передачей заголовка, описания и извлечённых наблюдаемых (исходный и целевой IP, домен, хэш файла).
3. Аналитик L1 открывает кейс в веб‑интерфейсе. TheHive уже запустил для каждого наблюдаемого соответствующие анализаторы Cortex — результаты отображаются в карточке наблюдаемого.
4. Аналитик просматривает отчёты: GeoIP-локация IP, Whois-данные домена, репутация на VirusTotal. На основе совокупности оценок он принимает решение: ложное срабатывание, требование эскалации на L2 или начало немедленной блокировки.
5. Действия аналитика (добавление комментариев, создание задач, изменение статуса) протоколируются в журнале кейса, что формирует полный аудиторский след.

Ниже приведён практический пример отправки алерта через API (иллюстративный запрос для среды с авторизацией по API-ключу):

```bash
curl -X POST "https://thehive.local/api/alert" \
  -H 'Authorization: Bearer <api_key>' \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Подозрительный DNS-запрос на хост bad.xyz",
    "description": "Обнаружена активность с рабочей станции client23 на домен bad.xyz, характерная для туннелирования",
    "type": "external",
    "source": "SIEM_KUMA",
    "sourceRef": "alert-12345",
    "artifacts": [
      { "dataType": "ip", "data": "10.20.30.40" },
      { "dataType": "domain", "data": "bad.xyz" }
    ]
  }'
```

В ответ система возвращает JSON с идентификатором созданного алерта, который затем может быть преобразован в кейс (руками аналитика или автоматическим правилом). Для автоматической конвертации алертов используется встроенный механизм правил, задаваемый в административном интерфейсе.

Данный подход типичен для SOC уровня зрелости выше начального. На ранних этапах аналитики могут создавать кейсы вручную, вводя наблюдаемые через веб‑форму. TheHive сохраняет универсальность: минимальные требования к внедрению делают его популярным на этапе становления SOC‑процессов, а позже через API наращиваются интеграции.

## 2. R-Vision SOAR: российский комплекс оркестровки и автоматизации реагирования

R-Vision SOAR — отечественная платформа класса Security Orchestration, Automation and Response, разработанная компанией R-Vision и включённая в обзор российских средств автоматизации SOC‑центров. Решение появилось в ответ на потребность рынка в импортозамещении западных SOAR‑систем и создавалось с учётом специфики отечественной регуляторики: поддержка ГОСТ‑сертификации, интеграция с российскими средствами защиты (ViPNet, Kaspersky, Positive Technologies) и совместимость с продуктами из реестра Минцифры.

### 2.1 Контекст и разграничение с SIRP

Если TheHive фокусируется на управлении расследованием и обогащении, то SOAR решает более широкую задачу — автоматизацию полного цикла реагирования на инцидент, от момента регистрации до выполнения ответных действий на сетевой инфраструктуре. Сравнение ключевых характеристик классов систем приведено ниже:

| Характеристика | SIRP (TheHive) | SOAR (R-Vision SOAR) | ITSM (Naumen SD) |
|----------------|----------------|----------------------|------------------|
| Управление кейсами и задачами | Полноценный функционал | Частично (фокус на инцидентах из очереди) | Полноценный, универсальный |
| Автоматическое обогащение | Через анализаторы Cortex | Собственные коннекторы к внешним сервисам | Отсутствует или минимальное |
| Оркестровка ответных действий | Только при ручном запуске респондеров | Плейбуки с условной логикой, параллельным/последовательным выполнением | Не предусмотрена |
| Интеграция с российскими СЗИ | Ограничена (нет готовых адаптеров) | Широкий набор готовых коннекторов | Интеграция через API по проекту |
| Работа в контуре государственных ИС | Требуется доработка | Соответствует требованиям (сертификация ФСТЭК, работа с российской криптографией) | Возможна, зависит от версии |

Таким образом, R-Vision SOAR — это инструмент автоматизации действий SOC, в то время как TheHive — инструмент аналитической поддержки. На практике они часто используются совместно: TheHive ведёт базу знаний расследования, а R-Vision выполняет команды на межсетевых экранах, конечных точках и серверах.

### 2.2 Архитектура и внутреннее устройство

Архитектура R-Vision SOAR построена по модульному принципу. Основные компоненты, определяющие типовую инсталляцию:

```text
┌─────────────────────────────────────────────────────────┐
│                    R-Vision SOAR                        │
│                                                         │
│  ┌──────────────┐  ┌───────────────┐  ┌──────────────┐ │
│  │ Оркестратор  │  │ Дизайнер      │  │ Хранилище    │ │
│  │ (ядро)       │  │ плейбуков     │  │ инцидентов   │ │
│  └──────┬───────┘  └───────┬───────┘  └──────┬───────┘ │
│         │                  │                  │         │
│         └──────────┬───────┘                  │         │
│                    ▼                          ▼         │
│           ┌──────────────────┐        ┌────────────┐    │
│           │ Менеджер         │        │ База        │    │
│           │ коннекторов      │        │ PostgreSQL  │    │
│           └─────┬────────────┘        └────────────┘    │
│                 │                                       │
└─────────────────┼───────────────────────────────────────┘
                  │
   ┌──────────────┼──────────────┐
   ▼              ▼              ▼
┌───────┐  ┌──────────┐  ┌───────────┐
│ SIEM  │  │ Антивирус│  │ Межсетевой│
│ KUMA  │  │  Kasp.   │  │  экран    │
└───────┘  └──────────┘  └───────────┘
```

- **Оркестратор** — ядро, отвечающее за интерпретацию плейбуков, маршрутизацию инцидентов по очередям и контроль SLA. Он принимает решения о запуске ответных действий на основе контекста инцидента и доступных разрешений.
- **Дизайнер плейбуков** — графический редактор, позволяющий описывать сценарии реагирования в виде блок‑схем с ветвлениями, циклами и параллельным исполнением. Плейбуки хранятся в формате, допускающем версионирование и экспорт/импорт.
- **Менеджер коннекторов** — обеспечивает взаимодействие с внешними системами через унифицированный набор драйверов. Каждый коннектор содержит описание команд, которые можно отправить на устройство (например, «заблокировать IP на межсетевом экране UserGate», «запустить полное сканирование в Kaspersky Endpoint Security», «запросить репутацию IP в Threat Intelligence Platform»). Производитель утверждает наличие десятков готовых коннекторов к популярным российским продуктам.
- **Хранилище инцидентов** обычно базируется на PostgreSQL и содержит полную историю по каждому инциденту: исходный алерт, запущенные плейбуки, результат каждого шага, действия оператора.

Для обеспечения отказоустойчивости компоненты могут разворачиваться в кластерной конфигурации; оркестратор поддерживает горизонтальное масштабирование.

### 2.3 Сценарий использования: автоматическое реагирование на фишинг

Типичный сценарий для L1‑аналитика с помощью R‑Vision SOAR:

1. SIEM (например, KUMA) обнаруживает подозрительное письмо, классифицирует алерт как «Фишинг» и отправляет его в SOAR через API.
2. R‑Vision SOAR создаёт карточку инцидента, автоматически присваивает приоритет на основе severity и запускает предварительный плейбук «Анализ фишинга».
3. Плейбук выполняет обогащение: извлекает URL‑адреса из тела письма, проверяет их репутацию через встроенный коннектор к TIP, проверяет, открывались ли аналогичные вложения на других машинах через запрос к EDR.
4. Если подтверждено вредоносное содержимое, плейбук автоматически выполняет ответные действия: помещает скомпрометированные URL в чёрный список прокси‑сервера, инициирует задание в EDR на сканирование хоста получателя, и, при необходимости, деактивирует учётную запись пользователя в AD.
5. Весь ход исполнения плейбука фиксируется в журнале инцидента. Аналитик L1 может наблюдать за процессом с панели мониторинга и вмешаться, только если требуется ручная проверка.

Такой уровень автоматизации резко сокращает время реакции (Mean Time to Response, MTTR) на массовые атаки. По данным публичных кейсов, описанных в отраслевых обзорах, внедрение SOAR‑платформ способно сократить ручную нагрузку на аналитиков на 70–80 % для типовых инцидентов.

Иллюстрация фрагмента описания плейбука (приведена адаптированная схема, реальный синтаксис зависит от версии продукта):

```yaml
playbook: "Анализ фишингового письма"
on_alert:
  severity: high
  type: phishing
steps:
  - name: "Обогащение URL"
    action: connector:threat_intelligence
    params:
      query: "{{.alert.url}}"
    output: reputation
  - name: "Проверка открытия вложений"
    action: connector:edr
    params:
      host: "{{.alert.destination_host}}"
  - decision:
      if: "reputation == 'malicious'"
      then:
        - name: "Блокировка на прокси"
          action: connector:proxy
          params:
            url: "{{.alert.url}}"
            action: block
        - name: "Сканирование хоста"
          action: connector:edr
          params:
            host: "{{.alert.destination_host}}"
            scan_type: full
      else: "Закрыть инцидент"
```

Фактические имена коннекторов и формат плейбуков зависят от конкретной конфигурации организации и обновлений платформы.

## 3. Naumen Service Desk как универсальная ITSM-прослойка в SOC-процессах

Naumen Service Desk (далее — Naumen SD) — российская система класса ITSM, предназначенная для автоматизации процессов управления услугами, инцидентами и запросами в ИТ‑подразделениях. В контексте SOC она не является специализированным средством обработки киберинцидентов, но часто применяется в качестве «единого окна» для регистрации всех обращений, включая события безопасности, особенно в организациях, где ИБ‑процессы выстроены на базе единой платформы ИТ‑менеджмента.

### 3.1 Роль Service Desk в SOC и отличие от SIRP/SOAR

В зрелом SOC-процессе инциденты проходят через несколько информационных систем. SIEM/SOAR генерируют и обрабатывают чисто технические события, а для взаимодействия с внешними службами (связь, HR, ИТ-подразделение) и для подготовки отчётности часто используется корпоративная ITSM-система. Naumen SD выполняет следующие функции:

- Регистрация инцидентов, поступивших из TheHive/R-Vision по API или по электронной почте.
- Маршрутизация заявок на группы аналитиков в соответствии с категорией и приоритетом.
- Контроль SLA (время реакции, время разрешения) с эскалацией при нарушении.
- Автоматическое формирование отчётов для руководства и регуляторов.
- Ведение базы знаний с историей всех инцидентов, что обеспечивает сквозную прослеживаемость.

Принципиальное различие: Naumen SD не понимает специфику киберинцидентов. В нём нет понятий «наблюдаемая», «плейбук», «обогащение» — он оперирует категориями тикетов, исполнителей и временных метрик. Данная система выступает транспортным и учётным слоем, а аналитическая глубина обеспечивается инструментами классов SIRP и SOAR.

Типовая схема сопряжения инструментов в SOC может выглядеть так:

```text
                    ┌──────────┐
                    │  SIEM    │
                    └────┬─────┘
                         │ алерты
                         ▼
          ┌──────────────────────────────┐
          │   SIRP / SOAR                │
          │ (TheHive / R-Vision SOAR)    │
          └──────┬───────────────────────┘
                 │ подтверждённый инцидент,
                 │ готовый тикет
                 ▼
          ┌──────────────────────────────┐
          │   Naumen Service Desk        │
          │  Заявка → назначение → SLA   │
          └──────┬───────────────────────┘
                 │
                 ▼
          ┌──────────────────────────────┐
          │ Исполнители (L2, ИТ‑отдел)   │
          └──────────────────────────────┘
```

При такой архитектуре аналитик L1 работает преимущественно в инструменте SIRP/SOAR, а в Naumen SD лишь фиксирует факт создания заявки и отслеживает сроки. Глубинная интеграция позволяет автоматически создавать заявку в Naumen SD после того, как R‑Vision SOAR завершил плейбук и подтвердил инцидент.

### 3.2 Интеграция и типовые операции

Naumen SD обладает REST API, что позволяет внешним системам создавать, обновлять и закрывать заявки. Типичный вызов API для создания заявки по инциденту безопасности (иллюстративная схема, реальные параметры зависят от кастомизации конкретного экземпляра Naumen):

```json
POST /restapi/tickets
Content-Type: application/json
Authorization: Bearer <token>

{
  "subject": "Обнаружен фишинг на пользователя Ivanov",
  "description": "Инцидент зафиксирован SIEM KUMA, подтверждён R-Vision SOAR. Подробности: case id 1234 в TheHive.",
  "category": "Информационная безопасность",
  "priority": "Высокий",
  "service": "SOC",
  "assignee_group": "SOC_L1",
  "custom_fields": {
    "source_system": "TheHive",
    "external_id": "case-5678"
  }
}
```

При успешной обработке запроса Naumen SD возвращает идентификатор созданной заявки, который затем может быть зарегистрирован в TheHive в поле `externalLink` для двусторонней связи.

Таким образом, Naumen SD замыкает контур: он обеспечивает соблюдение корпоративных регламентов, а SIRP/SOAR — скорость и эффективность расследования. При выборе конфигурации важно избегать дублирования информации и ручного переноса данных между системами, для чего и реализуют автоматическое взаимодействие.

## Сквозной практический пример: от алерта SIEM до заявки в Naumen через TheHive и R-Vision

**Исходные условия.** В компании действует SOC первого уровня. Инфраструктура мониторинга: SIEM Kaspersky Unified Monitoring and Analysis Platform (KUMA), SIRP TheHive (с подключенным Cortex), SOAR R-Vision SOAR, ITSM Naumen Service Desk. Аналитик L1 работает за консолью TheHive. SIEM KUMA сконфигурирован на отправку алертов в TheHive через вебхук. При подтверждении серьёзного инцидента предусмотрена эскалация в R‑Vision SOAR, где запускается стандартный плейбук, и финальная регистрация заявки в Naumen SD.

**Рассматриваемый инцидент:** обнаружение подозрительной сетевой активности на рабочей станции `host78` (IP 10.1.1.78). KUMA сработал по правилу «Подозрительный DNS‑трафик»: зафиксированы множественные запросы к домену `evil‑dns.xyz`, характерные для туннелирования данных.

### Шаг 1. Поступление алерта и создание кейса в TheHive

KUMA формирует JSON‑алерт и отправляет его на `/api/alert` TheHive. Пример полезной нагрузки:

```json
{
  "title": "DNS туннелирование с хоста host78",
  "description": "Обнаружена аномальная активность DNS: интенсивные запросы к домену evil-dns.xyz со стороны 10.1.1.78. Возможна эксфильтрация данных.",
  "source": "KUMA",
  "sourceRef": "kuma-event-998877",
  "artifacts": [
    { "dataType": "ip", "data": "10.1.1.78" },
    { "dataType": "domain", "data": "evil-dns.xyz" }
  ]
}
```

TheHive принимает алерт; согласно настроенному правилу авто‑конвертации, создаёт кейс `#CASE-2025-0042` и автоматически запускает анализаторы Cortex для каждого наблюдаемого. Аналитик L1 открывает кейс и видит результат обогащения: для домена получена низкая репутация (подтверждено через анализатор `VirusTotal_GetReport`), для IP — геолокация совпадает с локальным адресным пространством компании, анализ `AbuseIPDB` не выявил зловредной активности. На основании совокупности данных аналитик подтверждает инцидент и переводит кейс в статус **Resolved** с флагом «Требуется эскалация».

### Шаг 2. Эскалация в R-Vision SOAR и выполнение плейбука

TheHive через интеграционный скрипт отправляет информацию о подтверждённом инциденте в R-Vision SOAR (используется REST API). Скрипт, запускаемый по изменению статуса кейса, отправляет такой запрос:

```bash
curl -X POST "https://soar.r-vision.local/api/incidents" \
  -H "Authorization: Bearer <soar_api_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "DNS туннелирование host78",
    "description": "Подробности в TheHive case #CASE-2025-0042",
    "external_id": "CASE-2025-0042",
    "artifacts": [
      {"type": "ip", "value": "10.1.1.78"},
      {"type": "domain", "value": "evil-dns.xyz"}
    ],
    "severity": "high"
  }'
```

R‑Vision SOAR создаёт инцидент, присваивает приоритет и автоматически запускает плейбук «Реагирование на DNS-туннелирование». Плейбук выполняет следующие действия (вывод этапов доступен в журнале SOAR):

```text
[Playbook] Шаг 1: Запрос в EDR на изоляцию хоста 10.1.1.78
  -> Отправлена команда "network-isolate" через коннектор Kaspersky EDR; успех: true
[Playbook] Шаг 2: Добавление домена evil-dns.xyz в чёрный список DNS-сервера
  -> Исполнен скрипт на DNS-сервере (PowerShell Remote); успех: true
[Playbook] Шаг 3: Отправка уведомления в Telegram-канал SOC
  -> Сообщение доставлено
```

Журнал инцидента в R‑Vision сохраняет все детали, включая временные метки и результаты.

### Шаг 3. Автоматическое создание заявки в Naumen Service Desk

По завершении плейбука R-Vision SOAR финализирует инцидент и через собственный коннектор к Naumen SD отправляет запрос на создание заявки. Соответствующий вызов API (иллюстративный формат):

```json
POST https://naumen.local/restapi/tickets
Content-Type: application/json
Authorization: Basic <encoded_creds>

{
  "subject": "[SOC] Инцидент: DNS-туннелирование на host78",
  "description": "Детали: SIEM KUMA обнаружил подозрительный DNS-трафик на хост 10.1.1.78. Инцидент расследован в TheHive (case #CASE-2025-0042), подтверждён. R-Vision SOAR выполнил плейбук: изоляция хоста, блокировка домена. Требуется проверка логов EDR на предмет возможной эксфильтрации.",
  "category": "Информационная безопасность",
  "priority": "Высокий",
  "service": "SOC",
  "assignee_group": "SOC_L1",
  "custom_fields": {
    "external_case_id": "CASE-2025-0042",
    "soar_id": "INC-1003"
  }
}
```

Naumen SD создаёт заявку `SD#567890`, которая попадает в рабочую очередь группы SOC_L1. Аналитик L1 (или дежурный по смене) видит её в интерфейсе Naumen, может дополнить комментариями и принять в работу. Параллельно в TheHive в поле «Связанная заявка» автоматически проставляется ссылка на `SD#567890`.

### Ожидаемый результат

Сквозной пример демонстрирует, как три системы — TheHive (SIRP), R-Vision SOAR и Naumen SD — составляют целостный конвейер обработки инцидента на первом уровне SOC. Время от появления алерта до регистрации заявки в ITSM‑системе составляет единицы минут, все шаги протоколируются, и аналитик L1 выполняет контролирующую роль, а не рутинную. Подобная архитектура масштабируется на типовые инциденты и снижает нагрузку на персонал, одновременно повышая качество реагирования.
