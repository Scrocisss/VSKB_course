# Web Application Firewall: ModSecurity, PT AF и BI.ZONE WAF в работе SOC

## 1. Роль WAF в многоуровневой защите и сравнительный обзор решений

Web Application Firewall (WAF) — это специализированное средство фильтрации и мониторинга трафика на прикладном уровне (уровень 7 модели OSI), предназначенное для обнаружения и блокирования атак на веб-приложения. В отличие от классических межсетевых экранов (L3/L4), оперирующих IP-адресами и портами, WAF анализирует содержимое HTTP‑запросов и ответов: URL, параметры, заголовки, тело запроса, cookies. Основная задача WAF — компенсировать уязвимости прикладного кода, не требуя его изменения, а также предоставлять видимость и контроль над HTTP‑трафиком для команд SOC уровня L1 и выше. WAF является не заменой безопасной разработки, а дополнительным рубежом, реализующим принцип эшелонированной обороны (defence in depth).

В контексте SOC WAF выступает источником событий безопасности, интегрируемым в SIEM-системы. Аналитик L1 получает алерты о срабатывании правил, просматривает детализированные логи и принимает решение об эскалации. Современные WAF также предоставляют возможности виртуального патчинга — оперативной блокировки эксплуатации свежих уязвимостей (например, CVE в CMS или серверном ПО) до установки обновлений.

Три решения, рассматриваемые в этом конспекте, представляют собой три разных подхода к реализации WAF:
- **ModSecurity** — открытый, кроссплатформенный движок WAF, наиболее часто разворачиваемый непосредственно на веб-сервере (host-based). Имеет статус де-факто эталонного open-source WAF и рекомендован OWASP [ModSecurity WAF - OWASP Developer Guide].
- **PT AF (Positive Technologies Application Firewall)** — коммерческий продукт, ориентированный на корпоративный сектор, сочетающий сигнатурный и поведенческий анализ с интеграцией в экосистему продуктов Positive Technologies (MaxPatrol, PT SIEM).
- **BI.ZONE WAF** — облачный сервис с возможностью гибридного развертывания, построенный по модели «managed WAF»: настройку, сопровождение и мониторинг осуществляет команда провайдера. Ориентирован на полный спектр угроз веб-приложениям, включая L7 DDoS, ботов и специфические атаки на бизнес-логику [BI.ZONE WAF | Inquire].

Начинающему специалисту SOC легко спутать одноимённые, но разные по функции сущности. Поэтому прежде всего необходимо разграничить базовые понятия и способы развёртывания.

### 1.1 Классификация WAF по модели развёртывания

```text
[Модели развёртывания WAF]

1. Host-based (на стороне сервера): WAF как модуль или процесс, выполняющийся на том же хосте, что и веб-сервер.
   ┌────────────┐      ┌──────────────────────┐
   │ Интернет   │─────▶│ Веб-сервер + WAF (Mod)│
   └────────────┘      └──────────────────────┘
   Пример: ModSecurity (модуль Apache/Nginx/IIS).

2. Reverse proxy / appliance (периметр): выделенный узел (физический или виртуальный), через который проходит трафик к веб-серверам.
   ┌──────────┐      ┌───────────┐      ┌──────────┐
   │ Интернет │─────▶│ WAF-узел  │─────▶│ Веб-серв │
   └──────────┘      └───────────┘      └──────────┘
   Может поддерживать балансировку, TLS-терминацию. Примеры: PT AF, Nginx + ModSecurity, коммерческие appliance.

3. Cloud / Edge WAF: сервис, развёрнутый в облаке провайдера, трафик направляется через его точки присутствия (DNS-делегирование или reverse proxy).
   ┌──────────┐      ┌───────────────┐      ┌──────────┐
   │ Интернет │─────▶│ Облачный WAF  │─────▶│ Origin   │
   └──────────┘      └───────────────┘      └──────────┘
   Пример: BI.ZONE WAF (Cloud), Cloudflare WAF, AWS WAF.

4. Hybrid: комбинация периметра и облака. Фильтрующие узлы размещаются в инфраструктуре заказчика, управление и аналитика остаются в облаке.
   Пример: BI.ZONE WAF в гибридном режиме.
```

Приведённая схема иллюстрирует размещение компонентов фильтрации относительно защищаемого ресурса. ModSecurity в классическом варианте относится к host-based модели, PT AF и BI.ZONE WAF могут работать в режиме обратного прокси или облачного сервиса соответственно (PT AF также поддерживает распределённые схемы с централизованным управлением).

### 1.2 Ключевые различия трёх решений

| Критерий                     | ModSecurity                              | PT AF (`Positive Technologies`)          | BI.ZONE WAF (`BI.ZONE`)                 |
|------------------------------|------------------------------------------|-------------------------------------------|------------------------------------------|
| **Лицензия / модель поставки** | Open source (Apache 2.0)                 | Коммерческая лицензия                     | Услуга (SaaS / hybrid), подписка          |
| **Основной сценарий**        | Host-based; модуль к веб-серверу         | Enterprise WAF на периметре; кластерное развёртывание | Облачная фильтрация; модель managed WAF |
| **Источник правил**          | OWASP CRS (свободно распространяемый) + пользовательские | Вендорские наборы сигнатур, поведенческий анализ, машинное обучение | Вендорские правила, обновляемые экспертами BI.ZONE; виртуальный патчинг |
| **Видимость для SOC**        | Лог-файлы (audit log) → SIEM через агент; возможна интеграция с Elastic Stack | Интеграция с PT SIEM (MaxPatrol); syslog, JSON-события | Личный кабинет с аналитикой; экспорт событий и дашборды |
| **Управление**               | Ручное редактирование конфигураций и правил | Централизованная консоль управления (GUI) | Обслуживается провайдером; клиент получает настроенный профиль |
| **Типичные возможности**     | Полный анализ HTTP-запросов/ответов, аномальная оценка, псевдографический язык правил (SecRule) | Сигнатурный + аномальный детект, защита от ботов, кластеризация, машинное обучение | Защита OWASP Top 10, L7 DDoS, бот-менеджмент, защита от CSRF, session hijacking, поведенческие проверки (JS Challenge, CAPTCHA) |
| **Характерная сложность**    | Высокая потребность в тонкой настройке (тюнинг паранойя-уровней CRS) | Требует квалифицированного внедрения, но менее ресурсоёмка в эксплуатации | Минимальная нагрузка на администратора; все задачи конфигурации решает провайдер |

Таблица показывает, что каждое решение занимает свою нишу: ModSecurity — бюджетный и гибкий инструмент, дающий полный контроль ценой усилий на сопровождение; PT AF — мощный корпоративный продукт с расширенным детектом; BI.ZONE WAF — сервис, минимизирующий операционные издержки и подходящий для компаний, желающих переложить экспертизу на внешнюю команду.

## 2. Архитектура WAF: от ядра ModSecurity до облачной платформы BI.ZONE

Рассматриваемые продукты имеют принципиально разную внутреннюю организацию, что напрямую влияет на методику их использования в SOC и характер генерируемых артефактов. Ниже анализируются архитектурные особенности каждого решения в порядке, соответствующем типовым этапам развития WAF: от монолитного движка до сервисной облачной платформы.

### 2.1 ModSecurity: движок с правилами и фазами обработки

ModSecurity представляет собой программную библиотеку (libmodsecurity в версии 3.x) или подключаемый модуль для веб-сервера (Apache 2.x). Его ключевой особенностью является разделение на движок, реализующий жизненный цикл обработки запроса, и набор правил, описывающих логику обнаружения. Наиболее распространённым набором правил является OWASP Core Rule Set (CRS), покрывающий OWASP Top 10. Согласно документации OWASP, «ModSecurity — это движок, обрабатывающий правила и выполняющий действия на их основе, тогда как фактические правила, определяющие вредоносное поведение, предоставляются OWASP CRS» [DevGuide].

Жизненный цикл запроса разбит на пять фаз, в каждой из которых могут срабатывать правила:

```text
   ┌───── Запрос от клиента ──────────────────────────────────────────────┐
   │                                                                       │
   │  Фаза 1: Заголовки запроса (Request Headers)                         │
   │  ─ анализ метода, URI, заголовков (Host, User-Agent, Accept, etc.)   │
   │                                                                       │
   │  Фаза 2: Тело запроса (Request Body)                                 │
   │  ─ разбор POST-параметров, multipart-форм (файлы)                     │
   │                                                                       │
   │  ──── передача запроса приложению ────                                │
   │                                                                       │
   │  Фаза 3: Заголовки ответа (Response Headers)                         │
   │  ─ Content-Type, статус                                               │
   │                                                                       │
   │  Фаза 4: Тело ответа (Response Body)                                 │
   │  ─ анализ выходящего контента (утечки информации, XSS в ответе)       │
   │                                                                       │
   │  Фаза 5: Логирование (Logging)                                        │
   │  ─ окончательное решение по запросу, запись в audit log               │
   └───────────────────────────────────────────────────────────────────────┘
```

Правило ModSecurity описывается директивой `SecRule`. Её структура в иллюстративной форме:
```
SecRule <переменные> "<оператор>" "<действия>"
```
Переменные — это коллекции (`ARGS`, `REQUEST_HEADERS`, `TX` и пр.), оператор определяет сопоставление (регулярное выражение, `@rx`, `@eq`, `@detectSQLi` и т.д.), а действия задают реакцию: `deny`, `pass`, `log`, `setvar` для аномальной оценки.

Важнейшей концепцией является **аномальная оценка** (anomaly scoring). Каждое правило добавляет балл к счётчику для транзакции (`TX:anomaly_score`) при срабатывании. Пороговые значения определяют итоговое действие. Паранойя-уровни CRS (от 1 до 4) регулируют строгость правил: уровень 1 — минимальное количество ложных срабатываний, уровень 4 — максимальная чувствительность. Это позволяет адаптировать защиту под конкретное приложение и снижать false positives.

**Структура audit log** (типовой формат ModSecurity):
```json
{
  "transaction": {
    "id": "уникальный-идентификатор",
    "timestamp": "время",
    "request": {
      "method": "GET",
      "uri": "/path",
      "headers": { ... },
      "body": "..."
    },
    "response": {
      "status": 403,
      "headers": { ... }
    },
    "producer": ["ModSecurity v3", "CRS v4.x"],
    "rules": [
      {
        "id": "941100",
        "msg": "XSS Attack Detected via libinjection",
        "data": "матчинговая строка",
        "severity": "2"
      }
    ]
  }
}
```
Приведённая JSON-иллюстрация даёт представление о полях, которые аналитик SOC может использовать в SIEM для фильтрации (по id правила, severity, URI).

Особенностью ModSecurity является возможность интеграции внешних источников threat intelligence. Например, в исследовании IJERT продемонстрирована интеграция с AbuseIPDB: правило проверяет IP-адрес клиента через API и при высоком abuse-рейтинге блокирует запрос [IJERT]. Подробнее этот вариант будет рассмотрен в сквозном примере.

### 2.2 PT AF: высокопроизводительное корпоративное решение

PT AF (Positive Technologies Application Firewall) строится по модели обратного прокси-сервера, способного работать в кластере для обеспечения отказоустойчивости и пропускной способности. Архитектурно включает следующие компоненты (иллюстративная схема):

```text
   ┌──────────────┐    ┌────────────────────┐    ┌──────────────┐
   │ Внешние сети │───▶│ Балансировщик      │───▶│ Узел PT AF 1 │
   └──────────────┘    │ (L4/L7)           │    └──────┬───────┘
                       └─────────┬──────────┘         │
                                 │                     │
                       ┌─────────▼──────────┐    ┌──────▼───────┐
                       │ Узел управления    │◀───│ Узел PT AF 2 │
                       │ (GUI, политики, ЛК)│    └──────────────┘
                       └────────────────────┘
                              │
                       ┌──────▼───────┐
                       │ PT SIEM /    │
                       │ MaxPatrol    │
                       └──────────────┘
```

Узлы фильтрации выполняют глубокий анализ запросов с использованием сигнатур, шаблонов поведения и моделей машинного обучения. В отличие от ModSecurity, PT AF не требует написания низкоуровневых правил: базовые политики составляются в графическом интерфейсе. Детектирующие возможности включают:
- Полный разбор структурированных форматов (JSON, XML, GraphQL).
- Защита от автоматизированных атак: определение ботов по поведенческим характеристикам без привязки к IP-репутации.
- Виртуальный патчинг: оперативная блокировка эксплойтов для свежих CVE по мере публикации сигнатур вендором.
- Корреляция событий с сессией пользователя (отслеживание цепочек запросов).

Данные о событиях экспортируются в форматах syslog, CEF, JSON и легко интегрируются с SIEM‑системами, в первую очередь с продуктами Positive Technologies. Типовой алерт PT AF содержит идентификатор сигнатуры, рейтинг угрозы, контекст атаки, хиты поведенческого анализа и рекомендации.

Важно: описание PT AF дано на основе общей отраслевой практики и общеизвестных сведений о продукте. Конкретные версии, схемы и конфигурации могут различаться в зависимости от внедрения и должны уточняться в документации вендора.

### 2.3 BI.ZONE WAF: сервисная облачная платформа

BI.ZONE WAF представляет собой полностью управляемый сервис, архитектура которого разделена на два слоя: фильтрующие компоненты и централизованную систему управления. Официальный сайт продукта указывает два варианта развёртывания [BI.ZONE WAF | Inquire]:

- **Cloud**: все компоненты, включая фильтрующие узлы, размещены в облаке BI.ZONE. Трафик клиента направляется на эти узлы через DNS или через обратный прокси. Заказчик не управляет инфраструктурой.
- **Hybrid**: фильтрующие узлы устанавливаются в инфраструктуре заказчика (в виде виртуальных машин или контейнеров) перед защищаемым веб-приложением, а система управления и личный кабинет остаются в облаке BI.ZONE.

Централизованная система обеспечивает:
- Контроль конфигурации политик безопасности.
- Обновление сигнатур и правил экспертами BI.ZONE в режиме, близком к реальному времени (примеры публичных кейсов: нейтрализация уязвимостей в Confluence, GitLab, WordPress [там же]).
- Дашборды и отчёты для клиента, отражающие количество атак, типы угроз, эффективность фильтрации.

Возможности сервиса, согласно описанию, охватывают:
- Многослойную защиту OWASP Top 10 с учётом вложенных данных.
- Защиту данных пользователей: предотвращение перехвата сессий, DOM‑XSS, брутфорс-атак и CSRF.
- Защиту от L7 DDoS: поведенческий и корреляционный анализ, мониторинг метрик здоровья приложения.
- Бот-митигацию: JavaScript Challenge, CAPTCHA, поведенческие проверки.

Для SOC-аналитика BI.ZONE WAF ценен минимальным числом ложных срабатываний (настройку осуществляют эксперты провайдера) и готовой аналитикой в личном кабинете. В случае инцидента L1 может опираться на заранее настроенные политики и, при необходимости, эскалировать подозрительную активность через обращение к поддержке.

Структура события безопасности, поступающего от BI.ZONE WAF, обычно включает: временную метку, идентификатор правила/сигнатуры, источник запроса, детали атакуемого URL, тип атаки и предпринятое действие (блокировка/капча/пропуск). Конкретная схема JSON-события зависит от формата интеграции.

## 3. Применение и работа с WAF: типовые операции аналитика SOC L1

Вне зависимости от выбранного WAF аналитик первого уровня выполняет схожие операции: классификацию алертов, первичный анализ, поиск ложных срабатываний и передачу подтверждённых инцидентов на следующий уровень. Этот раздел фокусируется на практических аспектах эксплуатации каждого из решений, необходимых для эффективной работы.

### 3.1 Работа с ModSecurity: от чтения логов до тюнинга правил

Типичный рабочий день аналитика, обслуживающего ModSecurity, включает следующие процедуры.

**Просмотр и фильтрация audit log.** Журнал ModSecurity может быть настроен на запись в файл в формате Concurrent (ключ-значение) или JSON. Для быстрого анализа применяются утилиты `grep`, `jq` и специализированные инструменты. Пример получения последних десяти срабатываний правила с ID 941100 (XSS) из JSON-лога:
```bash
jq 'select(.rules[]?.id == "941100")' /var/log/modsec_audit.log | tail -10
```
Вывод покажет последние транзакции с деталями матчинга, которые необходимо проанализировать: действительно ли запрос был вредоносным или это ложное срабатывание (например, передача HTML-кода в поле комментария, допустимого бизнес-логикой).

**Настройка исключений (tuning).** При обнаружении повторяющихся ложных срабатываний аналитик SOC L1 (часто совместно с L2/администратором) может предложить правило исключения. В ModSecurity исключения реализуются через директиву `SecRuleUpdateTargetById` или `SecRuleRemoveById`. Например, чтобы исключить конкретный параметр из-под проверки правила ID 942100 (SQL injection) для отдельного приложения, можно поместить в конфигурацию:
```apache
SecRuleUpdateTargetById 942100 "!ARGS:comment"
```
В реальной среде такие изменения проходят регламент согласования, так как могут открыть брешь в защите.

**Интеграция threat intelligence.** Разобранный в литературе [IJERT] пример с AbuseIPDB демонстрирует расширение возможностей ModSecurity за счёт стороннего API. Правило на иллюстративном уровне выглядит так:
```
SecRule REMOTE_ADDR "@streq 0" \
  "id:100001,\
   phase:1,\
   t:none,\
   exec:/usr/local/bin/abuseipdb-check.sh,\
   setvar:tx.abuse_score=%{MATCHED_VAR},\
   ..."
```
Где скрипт `abuseipdb-check.sh` получает IP клиента и опрашивает API, возвращая оценку. В зависимости от значения переменной `tx.abuse_score` другое правило выполняет блокировку. Аналитик должен отслеживать, не блокируются ли легитимные IP из-за неточной репутации.

**Анализ производительности.** Поскольку ModSecurity разбирает тело HTTP-запроса, это влияет на время ответа сервера. Аналитик при расследовании медленных ответов должен уметь отличать проблемы с сервером от задержек, вызванных WAF, проверяя логи на фазы обработки и параметр `duration`.

### 3.2 PT AF: централизованное управление и реакция на инциденты

В среде с PT AF SOC L1 получает алерты через SIEM или консоль управления. Основной артефакт — обогащённое событие безопасности, содержащее информацию об атакуемом ресурсе, типе атаки, номере сигнатуры; часто добавляется информация о геолокации, репутации IP из встроенных баз.

**Типовые процедуры:**
- **Первичный триаж:** проверка поля `severity` и категории атаки. Например, срабатывание сигнатуры «SQL Injection» на критичном ресурсе — инцидент, требующий немедленной эскалации.
- **Корреляция с уязвимостями:** PT AF поддерживает виртуальный патчинг. Аналитик может сопоставить ID сигнатуры с CVE эксплуатации и, при наличии, инициировать проверку системы на предмет обновлений.
- **Анализ трафика:** В консоли доступна запись сессии (pcap), что позволяет восстановить полную картину атаки без привлечения сетевой команды.
- **Формирование отчётности:** PT AF предоставляет готовые отчёты по типам атак и защищаемым ресурсам; L1 может периодически использовать их для оценки трендов.

Пример фрагмента экспортируемого события в условном формате:
```
CEF:0|PositiveTechnologies|PTAF|2.0|100|SQL Injection Attempt|8|src=10.20.30.40 dst=192.168.1.5 request=/login.php method=POST cs1=SQL injection cs2=UNION SELECT cs3=942100 cs4=Blocked out=deny
```
Это позволяет легко парсить события в SIEM.

### 3.3 BI.ZONE WAF: управляемый сервис и действия аналитика

Модель managed WAF подразумевает, что настройка и адаптация правил выполняется провайдером. Поэтому спектр операций, выполняемых SOC заказчика, смещается в сторону мониторинга и коммуникации.

**Действия L1:**
- **Мониторинг дашборда** в личном кабинете: отслеживание общего количества атак, топ атакуемых URL, источников и типов угроз.
- **Обработка уведомлений:** сервис может присылать алерты о критических событиях (например, о продолжительной L7 атаке или срабатывании на новую уязвимость). Аналитик должен оперативно подтвердить легитимность трафика и, при необходимости, связаться с поддержкой BI.ZONE для изменения политики (временное усиление бот-защиты, включение CAPTCHA).
- **Анализ ложноположительных блокировок:** пользователи могут жаловаться на недоступность легитимного функционала. L1, имея доступ к статистике, ищет соответствующие заблокированные запросы и направляет запрос на корректировку профиля провайдеру.
- **Координация действий при инцидентах:** при масштабной атаке аналитик может инициировать коммуникацию с BI.ZONE, которая, в свою очередь, может активировать дополнительные механизмы (AntiDDoS, фильтрацию по стране, усиление бот-менеджмента).

Для самостоятельного анализа доступны логи в личном кабинете с возможностью фильтрации. Типовой JSON-алерт BI.ZONE WAF может содержать поля:
```json
{
  "timestamp": "2025-03-15T10:05:23Z",
  "action": "denied",
  "rule_id": "by_pass_csrf",
  "attack_type": "Cross-Site Request Forgery",
  "source_ip": "203.0.113.45",
  "request": {
    "method": "POST",
    "uri": "/transfer",
    "headers": { "Referer": "null", "Origin": "..." }
  },
  "client_reputation": "suspicious"
}
```
Наличие детализированного контекста помогает аналитику быстро оценить серьёзность.

### 3.4 Общие подходы к интеграции в рабочий процесс SOC

Независимо от типа WAF, работа L1 строится по модели «анализ‑решение». Полезные практики:
- Разработка playbook’ов по типам атак (SQLi, XSS, RCE, брутфорс) для каждого конкретного WAF.
- Создание в SIEM дашбордов: число алертов по времени, топ-источников, процент блокированных атак.
- Ведение реестра ложных срабатываний и согласованных исключений.
- Периодическая оценка эффективности: сопоставление заблокированных WAF атак с результатами пентестов или внешних сканирований.

## 4. Сквозной практический пример: настройка ModSecurity с OWASP CRS и интеграция threat intelligence

### 4.1 Исходные условия

**Среда:** Ubuntu Server 22.04, Apache 2.4, ModSecurity 3.0.14 (libmodsecurity) с модулем ModSecurity-nginx или Apache connector, OWASP CRS версии 4.0.0. В качестве дополнения настроена интеграция с AbuseIPDB API v2 (ключ API получен после регистрации). Аналитик SOC L1 тестирует защиту от SQL-инъекции и работу с репутационными данными.

### 4.2 Шаг 1: Установка и базовая активация ModSecurity с CRS

Устанавливаем пакеты и подключаем правила. В реальной среде последовательность может отличаться, но концептуально она такова:

```bash
# Установка libmodsecurity и коннектора для nginx/apache
apt install libmodsecurity3 modsecurity-crs
# Копируем example CRS настройку
cp /usr/share/modsecurity-crs/crs-setup.conf.example /etc/modsecurity/crs/crs-setup.conf
# Включаем движок и правила
echo 'include modsecurity-crs/crs-setup.conf' >> /etc/modsecurity/modsecurity.conf
echo 'include modsecurity-crs/rules/*.conf' >> /etc/modsecurity/modsecurity.conf
```

После перезапуска веб-сервера ModSecurity начинает обрабатывать трафик. Проверяем, что движок работает, просмотрев заголовки ответа или логи:

```bash
curl -I http://localhost | head -5
```

Вывод может содержать `Server: Apache/2.4.x (Ubuntu)`, но явного указания на ModSecurity нет. Смотрим audit log:

```bash
tail -f /var/log/modsec_audit.log | jq .
```

В логах должны появляться записи даже при `SecRuleEngine DetectionOnly` (рекомендуемый начальный режим для сбора baseline’а без блокировки).

### 4.3 Шаг 2: Тестовая SQL-инъекция и анализ срабатывания правил

Отправляем запрос с классической инъекцией:

```bash
curl -i "http://localhost/vulnerable?id=1'+OR+1=1--"
```

В ответе получаем статус `403 Forbidden` (если движок в режиме `On`). В audit log формируется транзакция:

```json
{
  "transaction": {
    "client_ip": "127.0.0.1",
    "time_stamp": "Tue Apr  8 10:15:22 2025",
    "request": { "method": "GET", "uri": "/vulnerable?id=1%27+OR+1%3D1--", ... },
    "response": { "http_code": 403 },
    "producer": [ "ModSecurity for Apache/2.9.7", "OWASP_CRS/4.0.0" ],
    "messages": [
      {
        "message": "Pattern match \"(?i:...)\" at ARGS:id. [file \"/etc/modsecurity/crs/rules/REQUEST-942-APPLICATION-ATTACK-SQLI.conf\"] [line \"...\"] [id \"942100\"]",
        "details": {
          "match": "1'+OR+1=1--",
          "reference": "o0o0o0o0"
        }
      }
    ]
  }
}
```

Аналитик должен отметить: правило 942100 «SQL Injection Attempt» корректно заблокировало атаку. Важно проверить, что легитимные запросы с апострофами (например, ввод фамилии O’Brien) не блокируются. Для этого используют тестовые наборы.

### 4.4 Шаг 3: Тюнинг ложного срабатывания

Пути тестирования выявили, что запрос `/search?q=John's` не должен блокироваться. Вносим исключение в файл `RESPONSE-999-EXCLUSION-RULES-AFTER-CRS.conf`:

```apache
SecRuleUpdateTargetById 942100 "!ARGS:q"
```

Перезагружаем Apache и повторяем тест:

```bash
curl -i "http://localhost/search?q=John's"
```

Ожидаемый вывод: статус `200 OK`, в логах срабатывание отсутствует. Аналитик документально фиксирует причину исключения: легитимное использование апострофа в поисковом запросе.

### 4.5 Шаг 4: Интеграция с AbuseIPDB и автоматическая блокировка

Создаём правило, которое при получении запроса проверяет репутацию IP. Используем скрипт `abuseipdb-check.sh`, который принимает IP и ключ API, и возвращает оценку по шкале 0‑100.

Сам скрипт (иллюстративный, без жёстко закодированных ключей):
```bash
#!/bin/bash
SCORE=$(curl -s -G https://api.abuseipdb.com/api/v2/check \
  --data-urlencode "ipAddress=$1" \
  -H "Key: $ABUSEIPDB_API_KEY" \
  -H "Accept: application/json" | jq '.data.abuseConfidenceScore')
echo $SCORE
```

Помещаем скрипт в `/usr/local/bin/`, делаем исполняемым. В конфигурацию ModSecurity добавляем правило:

```apache
SecRule REMOTE_ADDR "@rx .*" \
  "id:200001,\
   phase:1,\
   t:none,\
   exec:/usr/local/bin/abuseipdb-check.sh %{REMOTE_ADDR},\
   setvar:tx.abuse_score=%{MATCHED_VAR},\
   chain"
SecRule TX:abuse_score "@gt 75" \
  "deny,status:403,log,msg:'High abuse score - blocked by threat intel'"
```

Проверяем с тестовым IP, имеющим высокий abuse score (используем заранее идентифицированный из AbuseIPDB). Выполняем запрос:

```bash
curl -v "http://localhost/" --header "X-Forwarded-For: 198.51.100.23"
```

Если IP имеет репутацию >75, получаем `403 Forbidden`, а в логах:

```
ModSecurity: Access denied with code 403 (phase 1). High abuse score - blocked by threat intel [id "200001"] [hostname "localhost"] [uri "/"] [unique_id "..."]
```

Такой подход позволяет автоматически блокировать запросы с плохой репутацией, снижая нагрузку на SOC.

### 4.6 Ожидаемый вывод

Пример демонстрирует полный жизненный цикл работы с WAF в рамках SOC: развёртывание, валидация детекта (SQLi), тюнинг ложного срабатывания и расширение защиты с помощью threat intelligence. Аналитик L1 на практике видит структуру алертов, учится интерпретировать правила и выполнять базовую настройку исключений, что является критически важным навыком при обслуживании любого WAF.
