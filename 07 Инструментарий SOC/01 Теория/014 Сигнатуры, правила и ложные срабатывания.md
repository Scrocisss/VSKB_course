# Сигнатуры, правила и ложные срабатывания в Web Application Firewall (WAF) для SOC L1

## 1. Сигнатуры WAF: основа детектирования известных угроз

Сигнатура (в контексте WAF) — это формализованный шаблон, описывающий характерные признаки известной атаки или вредоносного поведения в HTTP-трафике. Подобно антивирусным базам, сигнатурный механизм сравнивает поля запроса (URL, заголовки, тело) с библиотекой заранее определённых паттернов. При совпадении WAF применяет заданное действие — блокировку, логирование или вызов дополнительной проверки.

Современные WAF опираются на управляемые наборы сигнатур, наиболее распространённым из которых является OWASP ModSecurity Core Rule Set (CRS). Такие наборы, как правило, разбиты на группы по классам угроз: SQL-инъекции, межсайтовый скриптинг (XSS), включение локальных файлов (LFI), удалённое выполнение команд (RCE) и т.д. Производители WAF, в том числе облачные провайдеры, адаптируют CRS или поставляют собственные сигнатурные базы, регулярно пополняемые группами threat intelligence. Например, Cloudflare Managed Rules наряду с CRS обновляются при появлении новых уязвимостей, а система оценки атак Cloudflare WAF, обученная на реальных истинно-положительных срабатываниях, способна блокировать обходы ещё до того, как они станут общеизвестными [1].

Сигнатурный подход обладает рядом сильных сторон. Во-первых, он даёт высокую детерминированность: если правило составлено грамотно, ложные срабатывания редки, а детектирование известных атак практически гарантировано. Во-вторых, каждая сигнатура обычно сопровождается идентификатором (rule ID), описанием и уровнем критичности, что упрощает анализ журналов специалистами SOC. В-третьих, сигнатуры легко поддаются тюнингу: администратор может отключить отдельное правило, настроить исключения или переопределить действие (например, перевести из режима блокировки в режим только логирования).

Однако у сигнатурного WAF есть принципиальные ограничения. Главное — он не защищает от атак zero-day, для которых ещё не создано сигнатур. Кроме того, злоумышленники применяют обфускацию, разбиение payload на несколько запросов или используют шифрование, чтобы обойти сигнатуры, ориентированные на конкретные синтаксические конструкции. Наконец, излишне агрессивные правила вызывают ложные срабатывания, блокируя легитимные бизнес-операции. Эти недостатки стимулируют развитие дополнительных методов детектирования: поведенческого анализа отклонений от нормального профиля приложения и моделей машинного обучения, автоматически выявляющих аномалии.

Для SOC L1 критично понимать, что срабатывание сигнатурного правила — это не приговор, а индикатор, требующий проверки. Аналитик должен знать основные идентификаторы и категории OWASP CRS, уметь сопоставлять содержимое алерта с легитимной функциональностью приложения и быстро определять, является ли событие ложным срабатыванием.

### Сравнение подходов к детектированию в WAF

| Подход | Принцип | Сильные стороны | Слабые стороны | Типичные ложные срабатывания / пропуски |
|--------|---------|-----------------|---------------|----------------------------------------|
| Сигнатурный | Сравнение трафика с базой известных шаблонов атак | Высокая точность для известных угроз; простота интерпретации; возможность тонкого тюнинга | Бессилен против zero‑day; обходится обфускацией; требует постоянного обновления сигнатур | Ложные срабатывания из‑за жёстких регулярных выражений на спецсимволах; пропуск новых атак |
| Поведенческий (аномалии) | Построение数学模型 нормального поведения приложения и выявление отклонений | Способен детектировать неизвестные атаки; меньше зависит от сигнатур | Высокая ресурсоёмкость обучения; сложность настройки; требует времени для построения профиля | Много ложных срабатываний в период обучения; пропуск медленных атак, не нарушающих профиль |
| Машинное обучение (AI/ML) | Модели, обученные на размеченных данных (легитимный/вредоносный трафик), предсказывают вероятность атаки | Автоматическое выявление сложных паттернов; адаптация к изменению приложения; подавление ложных срабатываний [2] | «Чёрный ящик» для аналитика; необходимость качественных обучающих данных; возможны пропуски новых классов атак при недостаточной обучающей выборке | Ложные срабатывания на редких легитимных сценариях; ложные отрицания при смещённых данных |

Студент SOC L1 должен чётко разграничивать: сигнатурный алерт — это следствие проверки на соответствие конкретному шаблону, а не вывод искусственного интеллекта. Это различие принципиально для выбора дальнейших действий — тюнинга правила, добавления исключения или эскалации инцидента.

## 2. Правила WAF: логика, структура и управление

Правило WAF — атомарная единица политики безопасности, определяющая условие проверки трафика и действие при его выполнении. Все правила объединяются в политику (WAF policy), которая, в свою очередь, привязывается к защищаемому приложению. Исторически прообразом многих реализаций служит ModSecurity, где правила записываются в унаследованном синтаксисе SecRule, но в облачных и современных продуктах распространён JSON-формат, позволяющий описывать сложные композиции условий.

Различают два ключевых типа правил:

- **Управляемые (managed rules)** — предварительно скомпонованные наборы, разрабатываемые вендором или сообществом (OWASP CRS). Они нацелены на широкие классы угроз и поставляются с готовыми идентификаторами, уровнями серьёзности и описаниями. Администратор может только корректировать действие (например, с `Block` на `Log`) или временно отключать правило.
- **Пользовательские (custom rules)** — создаются под нужды конкретного приложения. Их пишут, когда управляемые правила не покрывают специфическую логику (например, защиту кастомного API-ключа) или, напротив, вызывают неоправданные блокировки, требующие точечного разрешения легитимного трафика.

### Структура правила на примере Azure Application Gateway WAF

Для иллюстрации рассмотрим структуру пользовательского правила в политике Azure WAF. Основные элементы приведены в таблице, типичный JSON-документ выглядит следующим образом (поля и допустимые значения основаны на документации Microsoft):

```json
{
  "name": "AllowSpecificAPICall",
  "priority": 100,
  "ruleType": "MatchRule",
  "action": "Allow",
  "matchConditions": [
    {
      "matchVariables": [
        { "variableName": "RequestUri" }
      ],
      "operator": "Contains",
      "negationConditon": false,
      "matchValues": ["/api/health"]
    }
  ]
}
```

| Элемент | Описание | Пример значения |
|---------|----------|-----------------|
| `name` | Уникальное имя правила в рамках политики | `BlockSQLiComments` |
| `priority` | Целое число; чем меньше, тем выше приоритет обработки | `10` (обрабатывается раньше, чем `20`) |
| `ruleType` | `MatchRule` для проверки на совпадение либо `RateLimitRule` для ограничения частоты запросов | `MatchRule` |
| `action` | Действие при совпадении: `Allow`, `Block`, `Log`, `AnomalyScoring` | `Block` |
| `matchConditions` | Массив условий; для срабатывания правила достаточно выполнения одного (логическое ИЛИ между условиями) | |
| `matchVariables` | Список анализируемых переменных: `RequestUri`, `RequestArgs`, `RequestHeaders`, `RemoteAddr` и др. | `{ "variableName": "RequestArgs" }` |
| `operator` | `Contains`, `Equals`, `StartsWith`, `IPMatch`, `GeoMatch` и т.д. | `Contains` |
| `negationConditon` | Инверсия условия | `false` |
| `matchValues` | Список значений, с которыми сравнивается переменная | `["' OR 1=1--"]` |

Управляемые наборы в Azure WAF представлены как OWASP CRS (версии 3.2, 3.1 и т.д.), где каждое правило обладает идентификатором вида `942100` (SQL Injection: Comment Sequence Detected). Включение или отключение таких правил осуществляется ссылкой на их ID в конфигурации политики.

Для SOC L1 важно, что запись в журнале WAF при срабатывании правила содержит все значимые поля: `ruleId`, `action`, `message`, `details` (совпавшая переменная и её значение). Именно эта информация ложится в основу анализа ложных срабатываний.

### Приоритеты и порядок обработки

WAF обрабатывает правила в порядке возрастания `priority`. Первое совпавшее правило с терминальным действием (`Block` или `Allow`) останавливает дальнейший проход по списку, за исключением случаев, когда используются оценочные режимы (например, Anomaly Scoring в CRS, где отдельные совпадения суммируются для вынесения вердикта). Поэтому неверная расстановка приоритетов может привести к тому, что разрешающее правило окажется «перебито» более ранним блокирующим.

### Управление правилами в жизненном цикле SOC

- **Идентификация избыточного правила**: аналитик видит в SIEM всплеск блокировок по `ruleId`, совпадающий с легитимной активностью.
- **Принятие решения**: на основании анализа (см. раздел 3) выбирается стратегия — отключение правила, сужение его действия через исключения, либо написание custom rule `Allow` с более высоким приоритетом.
- **Реализация**: вносится изменение в политику WAF через API, портал или CI/CD-пайплайн.
- **Валидация**: проверяется, что легитимный трафик больше не блокируется, а защитные свойства не ухудшились.

## 3. Ложные срабатывания: анализ и стратегии минимизации

**Ложное срабатывание (false positive)** — это ошибочная блокировка (или пометка как вредоносного) запроса, который на самом деле является частью нормального функционирования приложения. Противоположная ситуация — ложное отрицание (false negative), когда атака проходит незамеченной. В SOC L1 большая часть рутинной работы по WAF связана именно с обработкой ложных срабатываний: по данным опросов, в среднем только 53% организаций эксплуатируют WAF в режиме блокировки, опасаясь сбоев из‑за ложных срабатываний [3].

### Причины возникновения

Причины разделяют на три группы:

- **Избыточная обобщённость сигнатур**. Например, правило OWASP, ищущее символ апострофа `'` в аргументах запроса для выявления SQL-инъекций, будет срабатывать на фамилиях типа O'Reilly, географических названиях и любых легитимных данных, содержащих одинарную кавычку.
- **Специфика приложения**. Веб-приложения могут легально передавать в GET/POST-параметрах URL-адреса, HTML-разметку, JSON-фрагменты или спецсимволы, которые совпадают с сигнатурными паттернами. Устаревшие ASP.NET WebForms способны генерировать обширные POST-запросы с viewstate, вызывая массовые ложные срабатывания [4].
- **Конфигурационные ошибки**. Неправильно выбранный режим блокировки без предварительного тестирования, отсутствие исключений для внутренних API, устаревший CRS — всё это провоцирует поток ложных алертов.

### Последствия

Ложные срабатывания наносят ущерб сразу по нескольким направлениям:

- **Бизнес‑ущерб**: блокировка критичных API нарушает бизнес‑процессы, приводит к отказу в обслуживании клиентов и финансовым потерям.
- **Усталость от алертов (alert fatigue)**: SOC‑аналитики тонут в фальшивых инцидентах и могут пропустить реальную атаку.
- **Снижение доверия к WAF**: команды разработки нередко настаивают на переводе WAF в режим только логирования, что сводит на нет его защитную функцию.

### Выявление ложных срабатываний

Стандартный сценарий обнаружения в SOC L1:

1. Мониторинг аномалий срабатываний: резкий рост блокировок определённого rule ID после деплоя новой версии приложения.
2. Анализ логов WAF, интегрированных с SIEM‑системой. Ниже приведён пример KQL-запроса для Azure Log Analytics, выявляющего наиболее часто срабатывающие правила:

```kusto
AzureDiagnostics
| where Category == "ApplicationGatewayFirewallLog"
| summarize Count = count() by ruleId_s, action_s
| order by Count desc
```

3. Детальная выгрузка по конкретному `ruleId` и сопоставление полей `details` с бизнес‑логикой: если заблокированный параметр содержит легитимную строку, а не инъекцию, — это ложное срабатывание.

### Стратегии уменьшения количества ложных срабатываний

#### Тюнинг порогов и чувствительности

Многие правила допускают регулировку. Например, правило rate limiting с низким лимитом запросов будет блокировать активных, но легальных пользователей — достаточно поднять порог. В Azure WAF для rate‑limit правил можно задать `threshold` и `matchConditions` только на специфичные URL.

#### Исключения (Exclusion Lists)

Исключения позволяют вывести из‑под действия определённого правила конкретные поля, URL-адреса или аргументы. В Azure Application Gateway WAF настройка исключения для аргумента `comment`, вызывавшего ложное срабатывание на символе `'`, может выглядеть так:

```json
{
  "exclusions": [
    {
      "matchVariable": "RequestArgNames",
      "selector": "comment",
      "selectorMatchOperator": "Equals",
      "exclusionManagedRuleSets": [
        {
          "ruleSetType": "OWASP",
          "ruleSetVersion": "3.2",
          "ruleGroups": [
            {
              "ruleGroupName": "SQL Injection",
              "rules": [
                { "ruleId": "942100" }
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

Этот фрагмент может быть добавлен в конфигурацию WAF-политики.

#### Отключение правила

Если сигнатура полностью нерелевантна приложению (например, правило для ASP-специфичных атак в окружении, где ASP не используется), допустимо временно отключить её по `ruleId`. В Azure WAF это делается через свойство `disabledRuleGroups` в конфигурации managedRules.

#### Пользовательские разрешающие правила

Иногда проще написать custom rule `Allow` с высоким приоритетом, которое разрешает конкретный легитимный запрос, чем исключать множество параметров из‑под десятка правил. Однако злоупотребление этим подходом чревато образованием «дыр» в защите, если разрешающее правило окажется слишком широким.

#### AI/ML‑подавление

Новейшие WAF‑решения, такие как F5 Distributed Cloud, применяют модели машинного обучения, обученные на реальном трафике, чтобы оценивать вероятность того, что сработавшая сигнатура действительно свидетельствует об атаке. Модель действует как дополнительный слой интеллекта, автоматически подавляя ложные срабатывания без вмешательства человека [2]. Аналогично, Cloudflare WAF рассчитывает «оценку атаки» (attack score), позволяя блокировать только запросы с высокой достоверностью [1].

### Лучшие практики для SOC L1

- **Документировать все исключения** с указанием причины и даты.
- **Внедрить A/B‑тестирование правил** в среде стейджинга перед переводом в блокирующий режим.
- **Интегрировать WAF‑логи с SIEM** и настроить пороговые алерты на аномальный рост срабатываний.
- **Рассматривать каждое ложное срабатывание как сигнал к пересмотру политики**, а не как разовую правку.

## 4. Сквозной практический пример: расследование и устранение ложного срабатывания WAF в Azure Application Gateway

### Исходные условия

Организация использует Azure Application Gateway с WAF (OWASP 3.2) перед веб‑приложением для приёма заявок клиентов. Внедрена отправка диагностических логов в Azure Log Analytics. SOC L1 получает жалобу от пользователя, который не может отправить форму «Заявка на возврат»: после заполнения поля «Комментарий» со значением `O'Reilly` страница зависает. Предполагается ложное срабатывание WAF.

### Шаг 1. Поиск релевантного события в логах

Аналитик выполняет KQL‑запрос, чтобы найти блокированные запросы к конечной точке `/return` за последний час, содержащие в деталях подстроку `O'Reilly`:

```kusto
AzureDiagnostics
| where TimeGenerated > ago(1h)
| where Category == "ApplicationGatewayFirewallLog"
| where requestUri_s contains "/return"
| where details_s contains "O'Reilly"
| project TimeGenerated, clientIp_s, requestUri_s, ruleId_s, action_s, message_s, details_s
```

Вывод (иллюстративная схема):

```text
TimeGenerated         : 2026-01-15T10:05:00Z
clientIp_s            : 203.0.113.45
requestUri_s          : /return/submit
ruleId_s              : 942100
action_s              : Blocked
message_s             : SQL Injection: Comment Sequence Detected
details_s             : "matchVariableName": "postArgs:comment", "matchVariableValue": "O'Reilly"
```

Правило 942100 посчитало значение `O'Reilly` похожим на SQL-инъекцию из‑за апострофа.

### Шаг 2. Анализ легитимности запроса

Аналитик проверяет контекст. Через отдельный запрос к логам приложения он убеждается, что это авторизованный пользователь с корректной сессией, а форма всегда принимает текстовые комментарии. Очевидно, что апостроф в фамилии — обычная ситуация. Ложное срабатывание подтверждено.

### Шаг 3. Выбор стратегии устранения

Решено добавить исключение для аргумента `comment`, чтобы правило 942100 (и другие правила SQL Injection) не проверяли это поле. Такой подход точечный и не снижает общий уровень защиты. Аналитик документирует инцидент и эскалирует запрос на изменение политики.

### Шаг 4. Добавление исключения через Azure CLI

Инженер применяет исключение через Azure CLI (или через политику в шаблоне ARM). Команда обновляет существующую WAF‑политику:

```bash
az network application-gateway waf-policy managed-rule exclusion add \
  --policy-name MyWafPolicy \
  --resource-group MyResourceGroup \
  --match-variable RequestArgNames \
  --selector comment \
  --selector-match-operator Equals \
  --rule-set-type OWASP \
  --rule-set-version 3.2 \
  --rule-group-name "SQL Injection" \
  --rule-id 942100
```

После выполнения команды политика перезагружается, и изменения вступают в силу в течение пары минут.

### Шаг 5. Верификация

Тестовый запрос с тем же значением `O'Reilly` повторяется. Аналитик мониторит логи и видит, что запрос успешно передан на бэкенд (действие `Allowed` или отсутствие записи в логах WAF). Алертов от пользователя больше не поступает. Таким образом, SOC L1 отработал инцидент от обнаружения до валидации, используя штатные инструменты и практики.
