# Примеры EDR-систем для SOC L1: Wazuh, Kaspersky EDR, PT XDR

## EDR и XDR в рабочем процессе SOC первой линии: ключевые понятия и сравнительный анализ

Endpoint Detection and Response (EDR) — класс средств кибербезопасности, ориентированных на непрерывный мониторинг конечных точек (рабочих станций, серверов, ноутбуков) и автоматизированное реагирование на инциденты. В отличие от классического антивируса, который преимущественно опирается на сигнатуры известных угроз, EDR собирает и анализирует телеметрию поведения процессов, сетевых соединений, изменений файловой системы и реестра, применяя методы машинного обучения и поведенческого анализа. Это позволяет выявлять сложные угрозы: бесфайловые атаки, lateral movement, компрометацию учётных записей, аномальную активность легитимных утилит.

Extended Detection and Response (XDR) расширяет идею EDR, объединяя данные не только с конечных точек, но и с сетевых сенсоров, облачных рабочих нагрузок, систем электронной почты, средств идентификации и доступа. Главная ценность XDR — корреляция событий из разнородных источников в единой панели, что уменьшает нагрузку на аналитика и ускоряет расследование. XDR-решения способны автоматически формировать инциденты, связывая разрозненные алерты в хронологию атаки, и выполнять кросс-доменные сценарии реагирования (например, изолировать узел и одновременно заблокировать IP на межсетевом экране).

Для специалиста SOC первой линии (L1) EDR/XDR — основной рабочий инструмент. Именно в консоли EDR/XDR аналитик просматривает алерты, проводит первичную сортировку (триаж), проверяет индикаторы компрометации (IoC) и эскалирует подозрительные случаи на L2. Глубина видимости, качество корреляции и удобство интерфейса напрямую определяют скорость и точность отработки инцидентов.

Часто возникает путаница между понятиями EDR, XDR, SIEM и антивирусом. Таблица ниже фиксирует принципиальные различия, важные для понимания места каждого класса в SOC.

| Класс решения | Основной источник данных | Метод обнаружения | Типовые действия SOC L1 | Ограничения |
|---------------|---------------------------|-------------------|-------------------------|-------------|
| **Антивирус (EPP)** | Сигнатуры, эвристики на конечной точке | Сравнение с базой сигнатур, простые эвристики | Просмотр логов карантина, выяснение пути заражения | Не видит бесфайловые атаки, легитимные инструменты злоумышленников, lateral movement |
| **EDR** | Телеметрия процессов, сети, файлов на конечных точках | Поведенческий анализ, ML, threat intelligence, IoC | Разбор алертов, проверка графа атаки, изоляция хоста, сбор артефактов | Ограничен областью конечных точек; требует ручной корреляции с сетью и облаком |
| **XDR** | Конечные точки + сеть + почта + облачные рабочие нагрузки + учётные записи | Кросс-доменная корреляция, ML над объединённым потоком, автоматическое построение инцидентов | Работа с инцидентами, а не отдельными алертами; запуск кросс-доменных плейбуков | Высокая стоимость и сложность внедрения, зависимость от экосистемы вендора |
| **SIEM** | Логи всевозможных систем (ОС, приложения, сетевые устройства) | Правила корреляции, статистические аномалии, поиск по историческим данным | Анализ нормализованных событий, ручная корреляция, поиск угроз (threat hunting) | Не имеет нативного агента на конечной точке, ограниченная автоматизация реагирования; высокий объём ручной работы по настройке правил |

Современные SOC-функции часто стирают границы: Wazuh, например, объединяет в одной платформе возможности SIEM и XDR; Kaspersky Next XDR Expert предлагает нативное XDR с элементами SIEM; PT XDR глубоко интегрирован с SIEM-системой MaxPatrol. Таким образом, аналитик L1 должен понимать не только терминологию, но и компромиссы между открытостью, стоимостью и эффективностью, характерные для решений, рассматриваемых ниже.

## Wazuh: архитектура и функциональные блоки открытой XDR/SIEM-платформы

Wazuh — свободная платформа (лицензия GPLv2), объединяющая агентский мониторинг, анализ логов, файловый контроль целостности, обнаружение уязвимостей и автоматическое реагирование. С точки зрения SOC L1, Wazuh интересна тем, что обеспечивает базовые XDR-возможности без лицензионных затрат, при этом по количеству пользователей и оценкам сообщества (рейтинг 7,8 на PeerSpot, 5,0% доля голосов в категории XDR) платформа занимает заметное место среди открытых альтернатив.

### Архитектура взаимодействия компонентов

Платформа построена по клиент-серверной модели с четырьмя основными элементами:

1. **Wazuh-агент** — лёгкая программа, устанавливаемая на контролируемую систему (Windows, Linux, macOS, контейнеры). Агент собирает системные журналы (Event Log, syslog, аудит Linux), телеметрию процессов, данные о сетевых соединениях, контролирует целостность файлов (FIM) и выполняет активные ответные действия (блокировка IP, изоляция хоста, выполнение скриптов).

2. **Wazuh-сервер** — центральный компонент, разбирающий полученные от агентов данные. Он состоит из трёх подсистем: `ossec-remoted` (приём трафика от агентов по защищённому каналу), `ossec-analysisd` (анализ событий с помощью набора правил, сопоставление с Threat Intelligence, вычисление оценок риска) и `ossec-monitord` (отслеживание состояния агентов). Сервер также управляет политиками активного ответа.

3. **Elastic Stack** — используется как хранилище и поисковый движок: Elasticsearch индексирует алерты, Filebeat пересылает их от Wazuh-сервера, Logstash может применяться для дополнительной нормализации. Это обеспечивает высокую скорость поиска и масштабируемость.

4. **Wazuh Dashboard** — веб-интерфейс на базе Kibana с плагинами Wazuh. Предоставляет обзорную панель для SOC L1: список алертов, детали каждого события (PID, хэш файла, командная строка, граф процессов), отчеты о соответствии (PCI DSS, CIS), управление агентами и конфигурациями.

ASCII-схема потоков данных в платформе:

```text
[Агенты (сотни/тысячи)] ──(TCP/UDP 1514, зашифрованный канал)──▶ [Wazuh Server: ossec-remoted]
                                                              │
                                                              ▼
                                                    [ossec-analysisd: правила, FIM, сканер уязвимостей]
                                                              │
                                     (JSON-алерты через Filebeat) ▼
                               [Elasticsearch] ◀── [Logstash/Filebeat] ──▶ [Kibana + Wazuh Dashboard]
```

### Функциональные возможности как EDR/XDR

Wazuh покрывает ключевые сценарии, востребованные аналитиком L1. Ниже представлена сравнительная таблица основных функций и соответствующих им типовых алертов.

| Функция | Что отслеживает | Пример алерта для SOC L1 | Связанные действия агента |
|---------|-----------------|--------------------------|---------------------------|
| **File Integrity Monitoring (FIM)** | Изменения критических файлов и каталогов, атрибутов, хэшей | Модификация `/etc/shadow` или `C:\Windows\System32\drivers\etc\hosts` | Запись детализированного события (кто, что изменил), принудительное восстановление из резервной копии |
| **Анализ системных логов** | Аудит входа/выхода, создание процессов, события безопасности Windows (EventID 4624, 4688, 5156 и др.) | Обнаружение интерактивного входа с локальной учётной записи на сервере в нерабочее время | Отправка алерта с контекстом (учётная запись, IP-адрес источника, PID) |
| **Сканер уязвимостей** | Сопоставление установленных пакетов с базой CVE (National Vulnerability Database) | Уведомление об уязвимости CVE-2023-38408 в OpenSSH на 5+ узлах | Неделя на исправление, автоматическая приоритизация по CVSS |
| **Обнаружение руткитов и аномалий** | Поиск скрытых процессов, аномальных сетевых соединений, изменения в реестре | Алерт "Process with hidden inode detected" | Активный ответ: блокировка порта-источника на межсетевом экране, изоляция хоста |
| **Контроль соответствия конфигурациям (SCA)** | Проверка конфигураций ОС и приложений на соответствие CIS-бенчмаркам | Нарушение правила "Ensure password length is 14 or more characters" | Генерация отчёта для аудита, подсветка несоответствующих узлов |

Мониторинг целостности файлов (FIM) реализован через хэширование (SHA256) и оповещение в реальном времени. Агент фиксирует не только факт изменения, но и атрибуты (владелец, права доступа), а детальный diff-журнал может сохраняться на стороне агента до отправки. Это позволяет аналитику L1 быстро идентифицировать несанкционированные модификации, например, подмена исполняемого файла службы вредоносной версией.

Активный ответ в Wazuh выполняется автоматически по сработавшему правилу. Поддерживаются готовые скрипты: `firewall-drop` (блокировка IP на заданное время), `host-deny` (добавление в `/etc/hosts.deny`), а также пользовательские сценарии. В инфраструктуре SOC L1 это означает, что простые изолирующие действия могут быть автоматизированы без эскалации, например блокировка хоста, обращающегося к известному C2-серверу.

## Kaspersky EDR в составе XDR-платформы: работа с инцидентами и интеграция с внешними системами

Kaspersky Endpoint Detection and Response (EDR Expert) — компонент экосистемы Kaspersky Next XDR Expert. В контексте SOC L1 данное решение предоставляет рабочее место аналитика в Kaspersky Security Center или в облачной консоли, где формируются инциденты на основе расширенной телеметрии конечных точек и, опционально, сетевых сенсоров (Kaspersky Anti Targeted Attack Platform — KATA).

### Компонентный состав и потоки данных

Согласно официальной документации, архитектура Kaspersky XDR включает:

- **Kaspersky Endpoint Security for Business** — агент на конечной точке с функциями предотвращения угроз (EPP), behavioural detection, контроля приложений и веб-фильтрации.
- **Kaspersky Endpoint Detection and Response Expert** — надстройка, активирующая глубокую телеметрию: запись событий процессов, сетевых соединений, операций с файлами и реестром, а также реагирование (изоляция узла, сбор артефактов, удалённый запуск команд).
- **Kaspersky Unified Monitoring and Analysis Platform** — центральный компонент XDR, принимающий данные от агентов EDR, KATA (сетевой анализ) и сторонних источников через коннекторы. Он выполняет корреляцию, хранит данные в «озере данных» (data lake) и предоставляет граф расследования.
- **Kaspersky Threat Intelligence** — обогащает события данными об угрозах (репутация IP/URL, индикаторы атак).
- **Kaspersky Security Center** — консоль управления, где аналитик видит сводку инцидентов, может запускать плейбуки и формировать отчёты.

Ключевое отличие от Wazuh — нативная экосистема: все компоненты разработаны одним вендором и глубоко интегрированы. В то же время Kaspersky предлагает Open XDR, позволяя подключать сторонние продукты, что даёт гибкость при построении SOC.

### Применение в SOC L1: типовые операции

Аналитик первой линии ежедневно взаимодействует с интерфейсом «Case Management». Типовой сценарий отработки инцидента выглядит так:

1. **Мониторинг очереди инцидентов** — в консоли отображается список инцидентов, сгенерированных корреляционным движком, с оценкой серьёзности (Severity), затронутыми активами и фазой MITRE ATT&CK.
2. **Первичный триаж** — аналитик открывает инцидент, видит сводную карточку: график атаки (attack graph), перечень артефактов (хэши файлов, командные строки, IP), результаты автоматического реагирования.
3. **Сбор дополнительных данных** — при необходимости аналитик запускает задачу «Collect forensics» для изъятия образа памяти, журналов или сетевого трафика с конечной точки. Действие выполняется через EDR Expert.
4. **Эскалация или закрытие** — если угроза подтверждена, инцидент эскалируется на L2 с прикреплённым графом атаки; иначе закрывается с обоснованием.

### Интеграция с Wazuh: конфигурация приёма событий Kaspersky Security Center

На практике нередко возникает потребность передавать события Kaspersky в центральный SIEM/XDR (например, в Wazuh) для единой корреляции. Процесс реализуется путём настройки syslog-экспорта из Kaspersky Security Center и приёма логов Wazuh-агентом или сервером. Ниже приведён иллюстративный фрагмент конфигурации `ossec.conf` на сервере Wazuh, позволяющий принимать syslog-сообщения и декодировать типовые записи Kaspersky.

```xml
<ossec_config>
  <remote>
    <connection>syslog</connection>
    <port>514</port>
    <protocol>tcp</protocol>
    <allowed-ips>192.168.10.15</allowed-ips>  <!-- IP Kaspersky Security Center -->
  </remote>
</ossec_config>
```

После получения данных необходимо определить пользовательское правило декодирования для извлечения полей события (дата, имя задачи, статус обнаружения, путь к файлу). Пример правила (`/var/ossec/etc/rules/kaspersky_rules.xml`):

```xml
<group name="kaspersky,">
  <rule id="100001" level="5">
    <decoded_as>kaspersky</decoded_as>
    <match>ON_DEMAND_SCAN_START</match>
    <description>Kaspersky on-demand scan started</description>
  </rule>
  <rule id="100002" level="10">
    <decoded_as>kaspersky</decoded_as>
    <match>DETECTED_MALWARE</match>
    <description>Kaspersky detected malware</description>
    <group>malware_detected,</group>
  </rule>
</group>
```

Конфигурация передаётся на сервер и Wazuh начинает отображать алерты Kaspersky в общем дашборде. Для аналитика L1 это означает единую точку контроля: на панели Wazuh видны и собственные FIM-алерты, и антивирусные события Kaspersky, и результаты сетевого анализа (если добавлены). Такой подход реализован в руководстве по интеграции Kaspersky Security Center с Wazuh (Yury Xisto, Medium) и активно используется в гибридных SOC.

## PT XDR: практика применения в среде Positive Technologies для обнаружения и реагирования

Positive Technologies Extended Detection and Response (PT XDR) — компонент экосистемы продуктов PT, предназначенный для сбора, корреляции и анализа телеметрии с конечных точек, сетевых устройств и облачных сред в связке с SIEM-системой MaxPatrol. В контексте SOC L1 это решение закрывает потребность в централизованном мониторинге инцидентов, предоставляя автоматизированные цепочки реагирования и глубокую интеграцию с другими сенсорами PT.

### Архитектурные особенности и место в стеке SOC

PT XDR состоит из следующих ключевых элементов:

1. **Агенты PT EDR** — устанавливаются на целевые узлы (Windows, Linux). Они осуществляют запись событий процессов, сетевых соединений, изменений файловой системы и реестра. Агент также может выполнять действия активного реагирования: изоляцию хоста, завершение процессов, сбор цифровых артефактов.

2. **Сервер PT XDR** — осуществляет приём и агрегацию телеметрии, выполняет корреляцию событий с использованием правил PT, алгоритмов машинного обучения и индикаторов угроз.

3. **MaxPatrol SIEM** — выступает центральным хранилищем и аналитическим модулем. PT XDR тесно интегрирован с MaxPatrol: данные EDR загружаются в MaxPatrol как нормализованные события, а интерфейс MaxPatrol используется для расследования инцидентов и построения отчётов.

4. **PT Network Attack Discovery (PT NAD)** — опциональный сетевой сенсор, передающий информацию о сетевых аномалиях и атаках.

5. **PT Sandbox** — автоматический анализ подозрительных файлов в изолированной среде.

ASCII-схема взаимодействия компонентов PT XDR:

```text
[Агенты PT EDR] ──(защищённый канал)──▶ [Сервер PT XDR] ──(нормализованные события)──▶ [MaxPatrol SIEM]
        │                                          │                                     │
        ▼                                          ▼                                     ▼
    [PT NAD]                           [PT Sandbox]                          [Веб-консоль MaxPatrol для аналитиков]
```

Все компоненты функционируют в режиме on-premise, что обеспечивает суверенитет данных и возможность развёртывания в закрытых сегментах. Отсутствие облачной зависимости является сильным аргументом для организаций с высокими требованиями конфиденциальности.

### Работа аналитика L1 с консолью PT XDR

Основным рабочим интерфейсом выступает веб-консоль MaxPatrol с вкладкой «XDR». Аналитик выполняет следующие типовые операции:

- **Просмотр сводной панели** — отображает топ-10 атакуемых хостов, распределение инцидентов по техникам MITRE ATT&CK, количество новых IoC.
- **Фильтрация и поиск** — позволяет отфильтровать события по типу (Process creation, Network connection, File modification) и периоду.
- **Реагирование** — одним кликом запускается сценарий «Изоляция узла» или «Сбор дампа памяти». Статусы заданий отображаются в реальном времени.

### Использование API для автоматизации задач L1

PT XDR предоставляет REST API для интеграции с SOAR-системами или автоматизации рутинных операций. Ниже приведён пример запроса на получение списка инцидентов, сформированных за последние 24 часа (иллюстративная схема, параметры зависят от версии продукта).

```bash
curl -k -X GET "https://ptxdr.example.com/api/v1/incidents?time_from=2026-03-20T00:00:00Z&time_to=2026-03-21T00:00:00Z" \
  -H "Authorization: Bearer <токен_доступа>" \
  -H "Content-Type: application/json"
```

Ответ API содержит массив объектов, каждый из которых включает идентификатор инцидента, серьёзность, затронутые активы и текущий статус. В среде SOC L1 такой вызов может быть встроен в скрипт автоматического назначения инцидентов дежурной смене.

### Типовые сценарии и преимущества для SOC L1

PT XDR позволяет реализовать несколько сценариев, критичных для первой линии:

- **Обнаружение аномалий в поведении пользователей** — при попытке запуска подозрительных утилит (например, `mimikatz`) агент генерирует событие, которое через корреляцию с событиями входа MaxPatrol формирует инцидент с высоким приоритетом.
- **Контроль целостности на основе сравнения с эталонным образом** — встроенный механизм проверки хэшей исполняемых файлов на предмет отклонений от утверждённого baseline.
- **Автоматическая блокировка IP-адресов на межсетевых экранах** — при обнаружении взаимодействия с IoC PT XDR отправляет команду на изменение политики МСЭ через API PT NAD или сторонние коннекторы, не дожидаясь ручного вмешательства.

Эти возможности снижают нагрузку на оператора, позволяя ему сосредоточиться на сложных инцидентах, требующих экспертного анализа.

## Сквозной практический пример: развёртывание Wazuh, настройка FIM и реагирование на несанкционированное изменение

**Исходные условия:** лабораторная среда SOC L1. Сервер Ubuntu 22.04 LTS (4 vCPU, 8 ГБ ОЗУ) используется для развёртывания Wazuh all-in-one с Elastic Stack. Контролируемая система — Windows 10 Pro, на которой необходимо отслеживать изменения в каталоге `C:\Program Files\MyApp`. Аналитик должен убедиться, что при модификации критического конфигурационного файла генерируется алерт, и автоматически выполняется изоляция рабочей станции.

### Шаг 1: Установка серверной части Wazuh (All-in-one)

Выполняется загрузка и запуск скрипта быстрой установки, который разворачивает Wazuh-сервер, Elasticsearch, Filebeat и Kibana с плагином Wazuh.

```bash
curl -sO https://packages.wazuh.com/4.7/wazuh-install.sh
sudo bash wazuh-install.sh --wazuh-server wazuh-server --elasticsearch --kibana
```

После завершения установки в консоли выводятся пароли для административных учётных записей. Доступ к Dashboard осуществляется по `https://<server_ip>`.

### Шаг 2: Установка и регистрация Wazuh-агента на Windows

На целевую Windows 10 устанавливается Wazuh-агент с параметрами, указывающими адрес сервера. Для автоматической регистрации агента используется парольный метод.

```powershell
$env:WAZUH_MANAGER = "192.168.10.100"
$env:WAZUH_AGENT_NAME = "win10-myapp"
New-Item -Path "C:\Program Files (x86)\ossec-agent\ossec.conf" -ItemType File -Force
```

В конфигурационном файле агента добавляется секция для мониторинга целевого каталога (FIM):

```xml
<syscheck>
  <directories check_all="yes" report_changes="yes" realtime="yes">C:\Program Files\MyApp</directories>
</syscheck>
```

Агент перезапускается службой `OssecSvc`. На сервере выполняется запрос на авторизацию агента:

```bash
sudo /var/ossec/bin/manage_agents -a <agent_id>
```

После успешного подключения в Dashboard появляется новый агент в статусе `Active`.

### Шаг 3: Симуляция несанкционированного изменения файла

Для воспроизведения инцидента на агенте редактируется конфигурационный файл `app.conf` из отслеживаемой папки, эмулируя действия злоумышленника.

```powershell
Add-Content -Path "C:\Program Files\MyApp\app.conf" -Value "malicious_backdoor_param=1"
```

Агент мгновенно фиксирует изменение. В файле `/var/ossec/logs/alerts/alerts.json` на сервере появляется запись события, содержащая детали модификации.

### Шаг 4: Просмотр алерта в Wazuh Dashboard

В веб-интерфейсе аналитик открывает раздел "Integrity monitoring" и видит алерт с деталями: полный путь, хэш SHA256 до и после изменения, атрибуты файла, имя учётной записи, выполнившей операцию. JSON-представление алерта (иллюстративная схема полей) выглядит так:

```json
{
  "timestamp": "2026-03-21T10:15:30.123Z",
  "rule": { "id": "550", "level": 7, "description": "File integrity monitoring event." },
  "agent": { "id": "003", "name": "win10-myapp" },
  "syscheck": {
    "path": "C:\\Program Files\\MyApp\\app.conf",
    "size_before": "1024",
    "size_after": "1072",
    "md5_before": "...",
    "md5_after": "...",
    "sha256_before": "...",
    "sha256_after": "...",
    "changed_attributes": ["size", "md5", "sha256", "mtime"]
  }
}
```

Аналитик видит, что изменение произведено вне регламентного окна, поэтому расценивает событие как потенциально опасное.

### Шаг 5: Настройка активного ответа и автоматическая изоляция

Для демонстрации автоматического реагирования на угрозу на сервере Wazuh создаётся пользовательское правило и настраивается активный ответ на блокировку агента. В файл `/var/ossec/etc/ossec.conf` добавляется:

```xml
<active-response>
  <command>host-isolate</command>
  <location>local</location>
  <rules_id>550</rules_id>
  <timeout>3600</timeout>
</active-response>
```

Сценарий `host-isolate` вызывает изоляцию узла (в Windows — блокировка всех сетевых подключений, кроме канала к серверу). После срабатывания правила агент становится недоступным для других сетевых взаимодействий. В Dashboard статус агента меняется на `Isolated`.

В результате SOC L1 получает автоматически сдержанное инцидент: подозрительное изменение файла мгновенно блокирует узел до выяснения обстоятельств. Аналитик, проверив контекст, может либо снять изоляцию (после подтверждения легитимности), либо эскалировать инцидент, имея полный набор артефактов и временную шкалу.
