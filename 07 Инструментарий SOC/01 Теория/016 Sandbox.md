# Sandbox в инструментарии SOC L1

## 1. Песочница в защите SOC: место и базовые понятия

Malware sandbox (песочница) — изолированная среда, в которой подозрительный файл или URL выполняются без риска для продуктивной инфраструктуры с целью выявления вредоносного поведения. В работе SOC L1 песочница служит автоматическим «детонатором», позволяющим быстро получить вердикт по объектам, не обнаруженным классическими сигнатурными и репутационными проверками. Без песочницы аналитик вынужден либо блокировать файл на основании только статических признаков, либо тратить время на ручной динамический анализ.

Принципиальное отличие malware sandbox от обычной виртуальной машины — фокус на автоматическом мониторинге, извлечении индикаторов компрометации (IoC) и вынесении машиночитаемого вердикта. Если ВМ используется для изоляции и ручного исследования, то песочница автоматически запускает образец, записывает системные вызовы, сетевую активность, изменения в реестре и файловой системе, анализирует поведение с помощью машинного обучения и предоставляет готовый отчёт. SOC L1 получает не сырые артефакты, а разметку: «вердикт: вредоносный», «угроза: Emotet», «извлечены такие-то IP, хеши, URL».

Понятие «песочница» в SOC часто путают с другими изолирующими механизмами, поэтому важно разграничить контексты.

| Термин | Контекст использования | Функции и ограничения |
|--------|------------------------|------------------------|
| Malware sandbox | Изолированная среда для автоматического поведенческого анализа вредоносных объектов | Автоматический мониторинг, генерация IoC, интеграция с SIEM/SOAR. Не предназначена для интерактивной работы пользователя с легитимными приложениями. |
| Песочница приложений (App Sandbox) | Ограничение прав конкретного приложения в ОС (например, AppContainer в Windows, песочница браузера) | Защита самой ОС от скомпрометированного приложения; не анализирует поведение вредоносного ПО, а изолирует его. |
| Виртуальная машина для анализа | Ручное исследование вредоносного ПО аналитиком уровня L2/L3 | Гибкость и интерактивность, но требует высокой квалификации и не автоматизирует выдачу вердикта. |
| Cloud sandbox (SaaS) | Удалённый сервис поведенческого анализа, доступный через API или веб-интерфейс | Масштабирование, обновление антиэвазионных техник вендором; зависимость от интернет-подключения. |
| On-premises sandbox appliance | Аппаратное или виртуальное решение внутри периметра организации | Полный контроль над данными, низкая задержка; требует обслуживания инфраструктуры. |

В SOC L1 песочница почти всегда интегрирована в конвейер обработки угроз по принципу «фильтр-воронка». Статистика из практики Symantec CAS: из 2,4 млрд файлов, поступивших за 30 дней, после отсечения известных зловредов репутационными базами только 539 000 попали в песочницу. Из неё лишь 389 оказались реально вредоносными и были эскалированы команде реагирования [Security.com](https://www.security.com/expert-perspectives/how-achieve-highly-effective-sandboxing). Такое многоуровневое просеивание избавляет SOC L1 от тысяч ложных срабатываний и позволяет сосредоточиться на подтверждённых инцидентах.

Ключевые определения для аналитика L1:

- **Детонация** — запуск подозрительного файла в песочнице с предоставлением ему всех необходимых ресурсов для исполнения вредоносной логики.
- **Вердикт** — итоговое решение на основе анализа: clean (чистый), malicious (вредоносный), suspicious (подозрительный, требует дополнительного расследования).
- **IoC** — индикаторы компрометации: IP-адреса, домены, хеши, мутации реестра, сигнатуры, по которым можно обнаружить аналогичную угрозу в инфраструктуре.
- **Поведенческий профиль** — последовательность действий (process tree, DNS-запросы, HTTP-сессии), которая описывает тактику вредоносного ПО.

## 2. Архитектура и типизация современных песочниц

Внутреннее устройство malware sandbox можно представить как многослойную среду, объединяющую изолированную ОС, агентов мониторинга и аналитическое ядро.

```text
[Загрузчик образцов] ──▶ [Диспетчер задач]
                          │
                          ▼
[Хранилище эталонных образов ОС] ──▶ [Изолированная среда]
       (Windows 10/11, Linux, Android)        │
                                              │ (автоматический запуск)
                                              ▼
                                     [Агент мониторинга]
                                     (Process Monitor, сетевой сниффер,
                                      трекер изменений ФС/реестра)
                                              │
                                              ▼
                                     [Сбор артефактов] ──▶ [Аналитическое ядро]
                                                              │
                                                              ▼
                                                     [Вердикт + отчёт]
```

Загрузчик принимает файл через API или веб-интерфейс. Диспетчер задач выбирает подходящий шаблон гостевой ОС (версия Windows с определённым набором приложений), восстанавливает чистый снимок и запускает образец. Агент мониторинга работает на уровне ядра или через инжект библиотек, перехватывая системные вызовы, операции с файлами, реестром, процессы и сетевые пакеты. Современные песочницы дополнительно имитируют активность пользователя — движения мыши, клики, ввод с клавиатуры, чтобы спровоцировать эвазивное вредоносное ПО, ожидающее взаимодействия с человеком. После завершения анализа (обычно 2–5 минут) собирается полный набор артефактов; аналитическое ядро сопоставляет их с сигнатурами поведенческих моделей, срабатывает машинное обучение, и выносится вердикт в унифицированном формате.

По способу создания изолированной среды различают три основных архитектурных типа.

| Тип песочницы | Принцип работы | Преимущества | Ограничения | Примеры реализации |
|---------------|----------------|--------------|-------------|-------------------|
| **VM-based** | Полноценная виртуальная машина на гипервизоре (VirtualBox, VMware, KVM) с установленной гостевой ОС | Высокая совместимость с реальным ПО; возможность анализа сложных многокомпонентных угроз | Легко детектируется вредоносным ПО (VM-артефакты); относительно высокое потребление ресурсов | Cuckoo Sandbox, VMRay Analyzer (Legacy), многие облачные сервисы |
| **Эмуляция ОС (user-mode)** | Воспроизведение API операционной системы без полноценной виртуализации оборудования | Очень быстрое развёртывание; сложнее обнаружить, чем VM | Ограниченная поддержка системных вызовов уровня ядра; не все вредоносные программы выполняются корректно | ANY.RUN (частично использует гибридный подход), специализированные эмуляторы (например, для Office-макросов) |
| **Full system emulation (Bare-metal)** | Эмуляция аппаратного обеспечения (CPU, память, устройства) с высокой точностью; иногда — запуск на выделенном физическом хосте с восстановлением из образа | Практически неотличима от реального оборудования; обходит практически все техники детекта виртуализации | Наибольшее потребление ресурсов; сложность масштабирования; более длительное время подготовки | Bare-metal analysis в продвинутых песочницах (например, специализированные IR-платформы) |

Большинство SOC используют облачные SaaS-песочницы именно VM-based или гибридного типа, так как они обеспечивают баланс между скоростью, глубиной анализа и антиэвазионными возможностями. On-premises appliance чаще выбирают организации с жёсткими требованиями к суверенитету данных.

Аналитическое ядро включает компоненты:

- **Статический предиктор** — быстрая проверка структуры файла (PE-заголовки, энтропия, цифровая подпись) до запуска.
- **Поведенческий движок** — анализ графа процессов, сетевых соединений, паттернов внедрения кода (process hollowing, reflective DLL injection).
- **Ретроспективный анализ** — сравнение с предыдущими сессиями для выявления новых вариаций известных вредоносных семейств.
- **Генератор IoC** — выделение уникальных артефактов: хешей запущенных файлов, адресов C2, мутированных ключей реестра, мутаций файлов-дропперов.

Эвазионные техники вредоносного ПО (VM detection, проверка имени системы, поиск процессов анализа, ожидание перезагрузки) вынудили вендоров внедрять контрмеры: рандомизацию аппаратных серийных номеров, имитацию работы аккумулятора на ноутбуке, симуляцию движения мыши по реалистичному паттерну, поддержку множества версий ОС и установленного ПО. Современные песочницы могут динамически варьировать параметры среды для каждой детонации, что резко снижает вероятность успешного уклонения. Интерактивные песочницы (ANY.RUN) позволяют аналитику вручную кликать и вводить данные в реальном времени, полностью уничтожая задержки, на которые рассчитывает вредонос.

## 3. Эксплуатация песочницы аналитиком SOC L1

Типовой workflow аналитика SOC L1 с песочницей выглядит следующим образом:

1. **Поступление алерта или подозрительного объекта.** Почтовый шлюз или EDR помечает вложение как неизвестное (например, файл `invoice.exe` без цифровой подписи, не найденный в репутационных базах). Система автоматизации передаёт хеш объекта в песочницу для анализа. В случае отсутствия автоматической передачи аналитик вручную извлекает файл из карантина и загружает его.
2. **Поиск предыдущих вердиктов.** Перед отправкой аналитик проверяет, не анализировался ли этот же файл ранее (поиск по хешу в истории песочницы). Если вердикт уже есть, он немедленно используется.
3. **Отправка на анализ.** Через веб-интерфейс или REST API образец помещается в песочницу. Аналитик может выбрать профиль гостевой ОС, соответствующей рабочей станции организации (обычно Windows 10 64-bit, Office 2016).
4. **Получение отчёта.** Через 2–5 минут аналитик получает структурированный JSON‑отчёт. Ключевые поля: `verdict` и `score` (степень уверенности), `threat` (название семейства), `iocs` (список индикаторов), `process_tree` (дерево запущенных процессов), `network` (сетевые соединения и DNS-запросы).
5. **Интерпретация и реагирование.** Если вердикт `malicious`, аналитик L1 немедленно заносит индикаторы в блок-листы, инициирует сканирование хостов на предмет аналогичной активности и эскалирует инцидент аналитикам L2 для более глубокого расследования. Вердикт `suspicious` требует дополнительной проверки — часто с привлечением интерактивного анализа. Вердикт `clean` позволяет снять алерт как ложный.

Ниже приведены иллюстративные вызовы REST API песочницы с подстановочными параметрами.

*Отправка образца на анализ (bash)*
```bash
curl -X POST "https://sandbox.example.com/api/v2/submit" \
  -H "Authorization: Bearer $SANDBOX_API_KEY" \
  -F "file=@/path/to/suspicious.exe" \
  -F "environment=win10_64" \
  -F "comment=Submitted by SOC L1 analyst from case #4502"
```
Ответ:
```json
{
  "task_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "status": "running",
  "message": "Sample accepted, analysis in progress"
}
```

*Получение отчёта о завершённом анализе (bash)*
```bash
curl -X GET "https://sandbox.example.com/api/v2/report/a1b2c3d4-e5f6-7890-abcd-ef1234567890" \
  -H "Authorization: Bearer $SANDBOX_API_KEY"
```
Фрагмент ответа:
```json
{
  "task_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "verdict": "malicious",
  "score": 95,
  "threat": "Emotet Downloader",
  "iocs": {
    "ip": ["203.0.113.42", "198.51.100.7"],
    "domain": ["bad.example.net"],
    "mutex": ["Global\\I98gh7s"],
    "sha256": ["d2f6b4e..."]
  },
  "process_tree": [
    {
      "pid": 2048,
      "name": "suspicious.exe",
      "children": [
        {"pid": 2056, "name": "cmd.exe", "command_line": "cmd /c powershell -enc ..."},
        {"pid": 2060, "name": "svchost.exe", "injected": true}
      ]
    }
  ],
  "network": {
    "dns": [
      {"query": "bad.example.net", "type": "A", "response": "203.0.113.42"}
    ],
    "http": [
      {"uri": "/gate.php", "method": "POST", "user_agent": "Mozilla/4.0"}
    ]
  }
}
```

Аналитик видит вердикт `malicious` с высоким score, название угрозы, и набор IоC, которые сразу же пригодны для блокировки. Для передачи в SIEM/SOAR песочница высылает аналогичную структуру через syslog или webhook, что позволяет автоматически создавать инциденты.

Типичные ошибки аналитика L1 при работе с песочницей:
- полагаться исключительно на вердикт `clean` без проверки окружения: вредонос может не активироваться, если не смог определить подходящую среду;
- игнорировать вердикт `suspicious` — такой файл часто является новым или эвазивным, и его следует отправить на ручной анализ;
- загружать файлы, извлечённые из защищённого архива без пароля, не зная пароль — песочница не сможет их открыть и выдаст ошибочный вердикт.

Современные SOC-платформы интегрируют песочницу в автоматизированные плейбуки: SOAR забирает подозрительный файл, отправляет в sandbox, получает IоC, обогащает инцидент и при высоком score автоматически помещает индикаторы в блок-листы сети и конечных точек.

## 4. Сквозной практический пример: от фишингового письма до изоляции угрозы

**Исходные условия:** корпоративная среда с облачным email-шлюзом и облачной песочницей, доступной по API. Аналитик SOC L1 получает уведомление о том, что письмо с темой «Необходимо срочно оплатить» было доставлено пользователю, вложение `INVOICE_2025.xlsm` не классифицировано. Email-шлюз пометил вложение как потенциально небезопасное и поместил его в карантин.

**Шаг 1. Просмотр алерта и извлечение файла.**  
Аналитик открывает консоль шлюза и видит событие:

```json
{
  "event_type": "malicious_email_attachment",
  "sender": "accounting@external-supplier.com",
  "recipient": "cfo@company.com",
  "subject": "Необходимо срочно оплатить",
  "attachment": {
    "filename": "INVOICE_2025.xlsm",
    "md5": "c4ca4238a0b923820dcc509a6f75849b",
    "size": 345210,
    "type": "Microsoft Excel Macro-Enabled Worksheet"
  },
  "action": "quarantined",
  "severity": "medium"
}
```

**Шаг 2. Отправка в песочницу.**  
Аналитик загружает файл из карантина на собственную защищённую рабочую станцию, проверяет хеш по истории песочницы — предыдущего анализа нет. Затем отправляет образец через REST API:

```bash
curl -X POST "https://sandbox.company.com/api/v2/submit" \
  -H "Authorization: Bearer $SANDBOX_API_KEY" \
  -F "file=@INVOICE_2025.xlsm" \
  -F "environment=win10_64_office2016" \
  -F "comment=Phishing attachment from SOC case #20259"
```

Ответ:
```json
{"task_id": "task-0912345678", "status": "submitted"}
```

Ждёт 120 секунд, пока анализ выполнится (интервал опроса через `GET /api/v2/report/task-0912345678`).

**Шаг 3. Получение и интерпретация отчёта.**  
Готовый отчёт содержит вердикт `malicious` со score 88 и именем угрозы «Macro-based downloader, likely Dridex». Фрагмент:

```json
{
  "task_id": "task-0912345678",
  "verdict": "malicious",
  "score": 88,
  "threat": "Dridex macro downloader",
  "iocs": {
    "ip": ["198.51.100.77"],
    "domain": ["cdn.contoso-support.com"],
    "sha256": ["a1b2c3d4...","e5f6g7h8..."],
    "registry": ["HKCU\\Software\\Microsoft\\Windows\\CurrentVersion\\Run\\drvmon"]
  },
  "behavior": {
    "macro_execution": "AutoOpen() launches cmd.exe",
    "download_payload": "powershell -enc ..."
  }
}
```

Аналитик понимает, что вложение пыталось загрузить полезную нагрузку с подставного домена, и прописало в автозагрузку ключ реестра.

**Шаг 4. Эскалация и блокировка.**  
Он создаёт инцидент в SIEM, прикрепляет отчёт и инициирует блокировку IоC через API межсетевого экрана:

```bash
curl -X POST "https://firewall.company.com/api/policy/block/ip" \
  -H "Authorization: Bearer $FW_API_KEY" \
  -d '{"ip": "198.51.100.77", "comment": "SOC case #20259 - Dridex C2"}'
```

Зеркально добавляет домен в DNS-фильтрацию и хеши в EDR-черный список. Инцидент эскалируется на L2 для проверки хоста пользователя и очистки почтового ящика от аналогичных писем.

**Ожидаемый вывод:** песочница позволила за считанные минуты превратить неизвестный файл в формальный инцидент с полным набором действенных индикаторов, сократив MTTR с часов (если бы аналитик анализировал вручную) до пары минут и предотвратив возможное заражение.
