# Корреляция и генерация алертов в SIEM

## Корреляция и алерты в контексте SIEM: ключевые понятия и место в работе SOC

SIEM (Security Information and Event Management) объединяет сбор, нормализацию, хранение и анализ событий безопасности из всей IT-инфраструктуры. Центральная функция платформы — выявление скрытых угроз путём сопоставления разрозненных записей журналов. Для этого используются два тесно связанных механизма: **корреляция событий** и **генерация алертов**. Без них SIEM остаётся лишь дорогим хранилищем логов.

Корреляция — это процесс анализа отношений между двумя или более событиями с целью обнаружения поведения, характерного для злоумышленника. Одиночная неудачная попытка входа не вызывает тревогу, но несколько десятков таких попыток с одного IP-адреса за короткий промежуток, за которыми следует успешный вход, формируют явный индикатор атаки перебора учётных данных. Именно корреляция «связывает точки» во времени, пространстве и логике.

Генерация алерта — это результат срабатывания корреляционного правила или иной аналитической логики. Алерт представляет собой автоматически создаваемое уведомление, содержащее ключевую информацию о подозрительной активности: источник, цель, временную метку, описание паттерна, уровень критичности и ссылки на исходные события. В SOC Level 1 аналитик первым встречает эти алерты и выполняет их сортировку (триаж).

Исторически SIEM разделялся на Security Information Management (SIM) — долговременное хранение, отчётность и анализ трендов — и Security Event Management (SEM) — мониторинг в реальном времени, корреляция и оповещение. Современные платформы интегрируют обе составляющие, предоставляя централизованное рабочее место для реагирования.

Ниже приведена сравнительная таблица базовых терминов, которая разграничивает сущности, часто смешиваемые начинающими специалистами.

| Термин | Определение | Пример |
|---|---|---|
| **Событие (Event)** | Отдельная запись, сгенерированная источником (ОС, приложением, сетевым устройством). | Одно событие Windows Security с Event ID 4625 (неудачный вход). |
| **Сырое событие** | Исходный формат записи до обработки SIEM. | Неструктурированный syslog-сообщение. |
| **Нормализованное событие** | Событие, преобразованное SIEM в общую схему (общие поля: timestamp, source IP, event type, user и т.д.). | Все события, классифицированные как «Authentication Failure», с единообразным именованием полей. |
| **Корреляционное правило (Correlation Rule)** | Логика, определяющая комбинацию событий, временные рамки и условия, при которых формируется алерт. | «5 и более неудачных попыток входа за 5 минут с одного IP + успешный вход» — правило брутфорса. |
| **Алерт (Alert)** | Уведомление, создаваемое SIEM при совпадении корреляционного правила или иного триггера. | Запись с идентификатором, severity=Medium, сообщением «Превышен порог неудачных попыток входа». |
| **Инцидент (Incident)** | Группа связанных алертов или подтверждённый аналитиком факт нарушения безопасности, требующий действий. | Подтверждённая атака перебора паролей, переросшая в компрометацию учётной записи. |
| **Триггер (Trigger)** | Условие запуска генерации алерта: пороговое значение, сигнатура, аномалия. | Превышение порога в 10 неудачных аутентификаций с одного адреса. |
| **Enrichment (обогащение)** | Добавление к алерту контекстных данных (геолокация IP, репутация, информация о пользователе). | К IP-адресу источника добавлены страна, провайдер и теги Threat Intelligence. |

ASCII-схема ниже иллюстрирует поток данных от источников до рабочего места аналитика.

```text
[Источники: серверы, AD, брандмауэры, облачные сервисы, EDR]
        │ события (syslog, Windows Event, JSON, …)
        ▼
[Сбор и нормализация] ──► [Хранилище событий (Data Lake)]
        │
        ▼
[Корреляционный движок (Rule Engine, ML/Statistics)]
        │ при совпадении правила
        ▼
[Генератор алертов] → [Консоль SOC: Очередь алертов, Dashboards]
```

Корреляция оперирует нормализованными событиями: единый формат временных меток, IP-адресов, идентификаторов пользователей и хостов позволяет правилам объединять данные из разнородных источников. Без нормализации корреляция практически невозможна, поскольку одни и те же сущности (IP, пользователь) могут именоваться по-разному.

Таким образом, корреляция отвечает на вопрос «какие отдельные события образуют подозрительную цепочку?», а генерация алерта превращает этот вывод в действенный сигнал для команды SOC. Оба механизма являются сердцем любой SIEM-платформы и определяют эффективность мониторинга.

## Механизмы корреляции: типы, архитектура и реализация внутри SIEM

В этом разделе мы детально рассмотрим внутреннее устройство корреляции — класса методов, с помощью которых SIEM связывает отдельные события в осмысленные индикаторы угроз. В современных платформах применяется несколько взаимодополняющих подходов, выбор которых зависит от зрелости SOC, объёмов данных и характера угроз.

Корреляционный движок может быть реализован как потоковый обработчик (CEP — complex event processing) или как движок поиска, работающий поверх сохранённых данных. Вне зависимости от архитектуры, правила корреляции оперируют тремя основными измерениями:

- **Время**: окно анализа, в которое должны вместиться связываемые события.
- **Последовательность**: строгий (событие A, затем B, затем C) или неупорядоченный (A и B в любом порядке) порядок.
- **Логические условия**: атрибуты (одинаковый пользователь, IP, хост, процесс), агрегации (count, sum), сравнения с порогами.

Ниже представлена сравнительная таблица основных методов корреляции, охватывающая их суть, типичные примеры, преимущества и ограничения.

| Метод корреляции | Суть | Пример обнаружения | Преимущества | Ограничения |
|---|---|---|---|---|
| **Rule-based (сигнатурный)** | Точное совпадение по заданному шаблону событий с учётом временных и атрибутивных условий. | 5 неудачных входов (Event ID 4625) + успешный вход (4624) с одного IP в пределах 10 минут. | Прост, прозрачен, легко настраивается, высокая точность для известных атак. | Не выявляет новые или модифицированные техники. |
| **Пороговая (threshold)** | Срабатывание при превышении количественного показателя за временной интервал. | >50 событий блокировки соединения брандмауэром от одного IP за минуту. | Хорошо ловит аномалии объёма, простота реализации. | Сложность выбора адекватного порога; чувствительность к легитимным всплескам. |
| **Статистическая (baseline-based)** | Отклонение от статистически вычисленной «нормы» поведения (скользящее среднее, стандартное отклонение). | Пользователь отправляет в 10 раз больше данных вовне, чем среднее за прошлые 30 дней. | Выявляет неизвестные аномалии, адаптируется к окружению. | Требует длительного периода обучения, может пропускать медленные атаки. |
| **Временная последовательность (sequence)** | Цепочка событий в заданной очерёдности, часто с жёсткими временными рамками. | Process A запущен → реестр изменён → установлено соединение с внешним IP → запуск cmd.exe. Характерно для некоторых вредоносных программ. | Детектирует многостадийные атаки, сложные для срабатывания по одиночному событию. | Зависит от строгого порядка поступления логов; может пропустить при задержках. |
| **На основе активов и контекста** | Учёт критичности хоста, роли пользователя, уязвимостей, информации CMDB при оценке комбинации событий. | Событие выполнения подозрительной команды на контроллере домена пользователем с правами администратора. | Резко снижает ложные срабатывания, повышает приоритет реальных угроз. | Требует поддержания в актуальном состоянии базы активов и их свойств. |
| **Машинное обучение (ML) / Искусственный интеллект** | Модели (кластеризация, автоэнкодеры, изолирующий лес) выявляют неочевидные зависимости и аномалии без явных правил. | Обнаружение редкой последовательности процессов у пользователя, которая не похожа ни на один из ранее виденных профилей. | Способен обнаруживать неизвестные атаки, устойчив к изменениям тактик. | Требует больших ресурсов, сложен в интерпретации для аналитика, возможны ложные срабатывания. |
| **Графовая корреляция** | Построение графа «пользователь – хост – процесс – сетевой поток» и анализ путей, циклов, центральности. | Выявление пути перемещения злоумышленника от первоначально скомпрометированной рабочей станции к файловому серверу (latent movement). | Наглядно показывает распространение атаки, подходит для расследования. | Вычислительно ёмкая, не всегда работает в реальном времени. |

Все эти методы могут комбинироваться. Например, пороговая корреляция неудачных входов дополняется контекстом — проверкой, не принадлежит ли IP известным легитимным сканерам уязвимостей, — и обогащается геолокацией для повышения точности.

В основе любой корреляции лежит этап нормализации. SIEM приводит события к единой схеме, выделяя такие поля, как `src_ip`, `dest_ip`, `user`, `host`, `process_name`, `event_type`. Благодаря этому правило может сопоставлять событие неудачного входа из Windows Event Log с событием блокировки от брандмауэра, если IP-адрес источника совпадает.

Пример корреляционного правила в SQL-подобном синтаксисе (на основе подхода, применяемого в Panther и облачных SIEM, работающих с data lake-хранилищами):

```sql
-- Поиск брутфорса: более 5 неудачных входов за час по одному пользователю и одной сессии
SELECT
    actor.alternateId AS user,
    client.geographicalContext.country AS country,
    COUNT(*) AS failures
FROM
    okta_system_log
WHERE
    eventType = 'user.session.start'
    AND outcome.result = 'FAILURE'
    AND published >= dateadd(hour, -1, current_timestamp())
GROUP BY
    user, client.device, authenticationContext.externalSessionId
HAVING
    COUNT(*) > 5
LIMIT 100;
```

Этот запрос, адаптированный из документации Panther, иллюстрирует простую, но эффективную корреляцию: группировка событий по пользователю и сеансу, агрегация числа неудач с условием превышения порога за скользящее окно. Результат выполнения такого запроса может использоваться для автоматической генерации алерта через планировщик SIEM.

Ещё один широко распространённый подход — корреляция с привязкой к тактикам и техникам MITRE ATT&CK. Система правил стремится покрыть несколько техник в рамках одной тактики или целой цепочки атаки. Например, правило «Обнаружение подозрительных процессов + сетевое соединение + модификация реестра» может соответствовать технике T1059 (Command and Scripting Interpreter), T1071 (Application Layer Protocol) и T1112 (Modify Registry). Карты охвата ATT&CK позволяют SOC оценить видимость угроз и пробелы в мониторинге.

Современные SIEM (Splunk, Microsoft Sentinel, Elastic Security) предоставляют языки поиска (SPL, KQL, EQL), позволяющие создавать гибкие корреляционные правила в виде поисковых запросов с окнами агрегации и триггерами. В разделе применения мы увидим, как такие запросы воплощаются в практическую работу аналитика.

Таким образом, арсенал корреляционных методов достаточно широк, чтобы покрыть как известные сигнатуры, так и аномальное поведение. Однако каждый метод сам по себе не гарантирует качественных алертов — их ценность определяется следующим компонентом: генерацией и управлением алертами.

## Генерация алертов: от срабатывания правила до уведомления SOC L1

Генерация алерта — финальная стадия аналитического конвейера, на которой результат работы корреляционного правила или модели машинного обучения превращается в действенный сигнал для специалиста. Этот процесс охватывает не только создание записи об алерте, но и его обогащение, приоритизацию, группировку и доставку на консоль.

**Типы триггеров для генерации алертов**

В зависимости от внутренней логики SIEM-платформы, алерты инициируются несколькими видами триггеров. Основные категории сведены в таблицу:

| Тип триггера | Описание | Пример условия | Частота использования |
|---|---|---|---|
| **Rule-based (сигнатурный)** | Проверка точного совпадения с набором условий или шаблоном событий. | Обнаружение конкретной сигнатуры вредоносного PowerShell-скрипта в журналах Sysmon. | наиболее распространён |
| **Пороговый (threshold)** | Срабатывание при пересечении количественного порога заданного события. | Более 20 отказов в доступе к объекту файловой системы за 10 минут от одного пользователя. | очень часто |
| **Аномалий (anomaly)** | Отклонение от профиля нормального поведения сущности (пользователя, хоста, процесса). | Внезапный вход пользователя в систему из двух географически удалённых стран в течение часа (признак компрометации учётной записи). | применяется совместно с UEBA |
| **IOC-based (индикаторы компрометации)** | Срабатывание при обнаружении в событиях известных вредоносных артефактов (хешей, IP, доменов) из фидов Threat Intelligence. | DNS-запрос к домену из списка известных C2-серверов. | широко применяется |
| **Составной (composite)** | Комбинация нескольких условий: например, сигнатурное совпадение плюс высокая критичность целевого хоста. | Срабатывание вредоносного поведения на критическом сервере БД. | высокая ценность, но сложнее настройка |

Важно понимать, что один и тот же тип триггера может использоваться для разных категорий алертов. Практика показывает, что начинающие SOC-аналитики чаще всего сталкиваются с правилами, построенными на пороговых и сигнатурных триггерах.

**Основные категории SIEM-алертов**

Алерты принято группировать по тактикам злоумышленника или объектам атаки. Ниже перечислены ключевые категории, большинство из которых покрывают техники MITRE ATT&CK:

- **Аутентификационные аномалии (Authentication Anomalies)**: массовые неудачные входы, входы с необычных локаций, атаки типа password spray. Индикатор T1110 (Brute Force) и T1078 (Valid Accounts).
- **Вредоносное ПО и IOC-триггеры**: обнаружение хешей или поведения вредоносного ПО, соединения с C2, загрузка подозрительных файлов. Связано с T1204 (User Execution), T1547 (Boot or Logon Autostart Execution) и др.
- **Подозрительное использование привилегий (Privilege Escalation / Abuse)**: запуск процесса от имени SYSTEM нестандартным способом, использование утилит вроде PsExec, добавление пользователя в группу администраторов.
- **Нарушения политик (Policy Violations)**: использование запрещённых протоколов, передача конфиденциальных данных по нешифрованным каналам, попытки доступа к отключённым системам.
- **Эксфильтрация данных и подозрительный сетевой трафик**: необычный объём исходящих данных, соединения с портами, не характерными для принятых политик, туннелирование DNS.
- **Deactivation/Modification of Security Controls**: остановка антивируса, очистка журналов, отключение брандмауэра. Критичные алерты, указывающие на активное противодействие.

Каждая категория может быть реализована через несколько корреляционных правил, а один алерт — относиться сразу к нескольким тактикам.

**Процесс генерации алерта и его структура**

Когда корреляционный движок фиксирует совпадение, инициируется следующий процесс:

1. **Формирование записи алерта**: присваивается уникальный идентификатор, фиксируются временная метка, название правила, список идентификаторов исходных событий.
2. **Назначение severity** (обычно по шкале Critical, High, Medium, Low) на основе заданных в правиле значений или влияния на критичный актив.
3. **Обогащение (enrichment)**: запросы к внутренним базам (CMDB, Active Directory) и внешним источникам (GeoIP, репутационные сервисы) добавляют к алерту сведения о стране, подразделении пользователя, уровне доверия к IP.
4. **Группировка в инциденты**: несколько алертов, относящихся к одному пользователю или хосту и сработавших в близкое время, объединяются в единый инцидент, снижая хаос в консоли.
5. **Доставка**: алерт / инцидент отображается в рабочей очереди SOC-консоли, может отправляться уведомление по email, в мессенджер или передаваться через API в SOAR для автоматической реакции.

Ниже показана иллюстративная JSON-схема алерта, с которой может иметь дело аналитик L1 (конкретные значения полей зависят от вендора).

```json
{
  "alert_id": "uuid-string",
  "rule_name": "Brute Force: Multiple 4625 followed by 4624",
  "severity": "Medium",
  "timestamp": "2025-04-07T08:45:30Z",
  "status": "Open",
  "description": "User 'jdoe' experienced 12 failed logons from IP 198.51.100.27 within 5 minutes, followed by a successful logon.",
  "mitre_technique": "T1110.001",
  "source": {
    "ip": "198.51.100.27",
    "country": "RU",
    "user": "jdoe",
    "host": "WS-DOE-01"
  },
  "target": {
    "ip": "192.168.10.5",
    "host": "DC01",
    "application": "Windows Logon"
  },
  "events_count": 13,
  "contributing_events": [
    { "event_id": "evt-12345", "type": "4625", "timestamp": "2025-04-07T08:42:12Z" },
    ...
  ],
  "enrichments": {
    "src_ip_rep": "Suspicious",
    "threat_intel_tags": ["brute_force_source"]
  }
}
```

**Проблема alert fatigue и лучшие практики управления**

Избыточное количество низкокачественных алертов ведёт к «усталости от алертов» (alert fatigue) — одной из острейших проблем в работе SOC. Аналитик перестаёт доверять системе, пропускает реальные угрозы, растёт текучесть кадров. Поэтому применяются следующие подходы, выработанные индустрией:

- **Непрерывный тюнинг правил**: регулярный пересмотр порогов, условий и списков исключений (white listing) на основе обратной связи от разбора инцидентов.
- **Согласование severity с бизнес-контекстом**: алерт на тестовой системе не должен иметь такой же вес, как алерт на продуктивном контроллере домена; severity динамически корректируется в зависимости от контекста актива.
- **Группировка алертов в инциденты**: снижает нагрузку, позволяя аналитику фокусироваться на целостной картине.
- **Интеграция с Threat Intelligence**: обогащение позволяет автоматически снижать приоритет алертов с IP, которые уже классифицированы как ложные срабатывания, или, наоборот, поднимать уровень угрозы при совпадении с актуальными индикаторами.
- **Использование suppression-правил**: временное подавление алертов для ожидаемой активности, например, во время планового сканирования уязвимостей.

Таким образом, генерация алерта — не просто уведомление, а сложный процесс, требующий осмысленного дизайна правил и постоянной эксплуатационной поддержки, чтобы SOC мог работать с высококачественными сигналами.

## Применение корреляции и работа с алертами в повседневной практике SOC L1

Для специалиста начального уровня (L1) работа с SIEM сводится к взаимодействию с готовыми алертами и выполнению начального расследования. Однако понимание того, как создаются и настраиваются корреляционные правила, помогает быстрее интерпретировать алерты и давать качественную обратную связь инженерам по обнаружению. В этом разделе мы рассмотрим типовые операции, конфигурационные инструменты и практические нюансы.

**Поток задач аналитика L1 при обработке алерта**

Обобщённый алгоритм действий после появления нового алерта:

1. **Просмотр очереди**: аналитик видит список алертов/инцидентов, сортирует по severity и времени.
2. **Первичная проверка (triage)**: открытый алерт изучается на предмет очевидных ложных срабатываний (известная тестовая учётная запись, плановые работы). Читается описание правила, сверяются IP, пользователи и время.
3. **Анализ контекста**: используются drill-down к исходным событиям (contributing events), просматриваются связанные логи на временной шкале до и после инцидента. Проверяются данные обогащения (геолокация, репутация, принадлежность хоста к критическим системам).
4. **Принятие решения**: если алерт явно ложный или соответствует ожидаемому поведению — закрывается с пометкой «False Positive» и, при необходимости, создаётся тикет на доработку правила тюнинга. Если подозрительный, но недостаточно очевидный — эскалируется аналитику L2 с приложением собранных артефактов.

**Настройка корреляционных правил: от идеи до алерта**

Хотя аналитики L1 редко пишут правила с нуля, полезно представлять жизненный цикл правила, чтобы понимать, откуда берутся обрабатываемые ими алерты.

1. **Формулировка use case**: «обнаружение брутфорса на RDP-серверы». Используя MITRE (T1110), инженер определяет необходимые источники: Windows Security Event Log (события 4625 и 4624 с LogonType=10).
2. **Выбор полей и нормализация**: идентификатор пользователя, IP-адрес источника, время.
3. **Создание запроса в языке SIEM**: например, на SPL для Splunk или KQL для Sentinel. Пример поиска, фиксирующего 10+ неудачных попыток за 5-минутное окно с последующим успехом.

```spl
index=windows (EventCode=4625 OR (EventCode=4624 AND LogonType=10))
| bin _time span=5m
| eval failure = if(EventCode==4625, 1, 0)
| eval success = if(EventCode==4624 AND LogonType==10, 1, 0)
| stats sum(failure) as failures, sum(success) as successes by src_ip, TargetUserName, _time
| where failures > 10 AND successes > 0
| table _time, src_ip, TargetUserName, failures, successes
```

Этот запрос возвращает строки с превышением порога. Далее на его основе в Splunk создаётся **alert action**: сохранённый поиск, который выполняется каждые 5 минут и при наличии результатов отправляет запись в индекс алертов или инициирует веб-хук.

Альтернативный пример — правило обнаружения в формате Elastic Security, основанное на пороговом запросе:

```yaml
name: "RDP Brute Force Attempt"
description: "Detects multiple failed RDP logins followed by a success"
index: ["winlogbeat-*"]
type: threshold
language: eql
query: |
  sequence by host.name, source.ip with maxspan=5m
    [ authentication where event.code : "4625" and winlog.event_data.LogonType : "10" ] with runs >= 10
    [ authentication where event.code : "4624" and winlog.event_data.LogonType : "10" ]
severity: high
```

Эта конфигурация демонстрирует использование событийного языка (EQL) для задания последовательности: 10 и более провалов, затем успех. Такие правила загружаются в SIEM и сразу генерируют алерты.

**Тюнинг и адаптация под изменяющуюся среду**

Правила со временем устаревают: появляются новые легитимные сервисы, меняются IP-диапазоны, внедряются обновления безопасности. Периодическая оптимизация включает:

- Добавление исключений (suppression) для известных сервисных учётных записей или IP сканеров уязвимостей.
- Корректировка порогов по анализам ложных срабатываний: например, увеличение порога с 10 до 15 при большом потоке легитимных повторных вводов.
- Обновление критериев привязки к реальным тактикам злоумышленников.

Во многих SIEM предусмотрен режим «тихого срабатывания» (alert only if threshold exceeded and then send notification) или создание корреляционного правила с отложенным уведомлением, чтобы не забивать канал.

**Типичные ловушки для новичков**

- **Игнорирование дубликатов**: один и тот же инцидент может порождать множество алертов — нужно уметь группировать.
- **Избыточное доверие severity**: не все помеченные как Critical действительно критические; обязательно проверять контекст.
- **Неучёт временных зон и задержек поступления логов**: событие может прийти с задержкой, и последовательность, задуманная правилом, нарушится; важно понимать, что правила работают с временем события, а не с временем приёма.
- **Отсутствие обратной связи**: если алерт регулярно закрывается как ложный, аналитик должен сообщить об этом инженеру по детектированию для улучшения правила.

Практическое владение этими аспектами позволяет специалисту L1 не только эффективно обрабатывать инциденты, но и постепенно расти в инженера по обнаружению, проектируя новые корреляционные правила и совершенствуя алертный ландшафт.

## Сквозной практический пример: обнаружение и обработка атаки перебора RDP-учётных данных

**Исходные условия**

SIEM-платформа Splunk Enterprise собирает логи с Windows Server 2019, выступающего в роли RDP-сервера, а также журналы Sysmon. В консоли настроен сохранённый поиск для обнаружения брутфорса, который при срабатывании создаёт алерт. Аналитик L1 разбирает события в утреннюю смену. Цель — пройти весь путь от сырых событий до эскалации подтверждённой атаки.

**Шаг 1. Настройка корреляционного правила (сохранённый поиск)**

Инженер создаёт следующий поиск с опцией Alert, выполняемой каждые 5 минут.

```spl
index=windows (EventCode=4625 OR (EventCode=4624 AND LogonType=10))
| bin _time span=5m
| eval failure = if(EventCode==4625, 1, 0)
| eval success = if(EventCode==4624 AND LogonType==10, 1, 0)
| stats sum(failure) as failures, sum(success) as successes by src_ip, TargetUserName, _time
| where failures > 10 AND successes > 0
| table _time, src_ip, TargetUserName, failures, successes
```

Назначено действие: сохранить значимые события в индекс `alerts_index` с полем `alert_type="brute_force_rdp"`.

**Шаг 2. Поступление сырых событий (фрагмент лога в виде событий 4625 и 4624)**

В течение 5 минут в журнале зафиксирована серия неудачных попыток входа под учётной записью `svc-backup` с IP-адреса `203.0.113.42`, после чего успешный вход.

```text
Event ID: 4625, Time: 2025-04-07T08:42:12, TargetUserName: svc-backup, IpAddress: 203.0.113.42, LogonType: 10, Status: 0xC000006A, SubStatus: 0xC0000064
Event ID: 4625, Time: 2025-04-07T08:42:27, TargetUserName: svc-backup, IpAddress: 203.0.113.42, ...
... (всего 13 событий 4625) ...
Event ID: 4624, Time: 2025-04-07T08:45:30, TargetUserName: svc-backup, IpAddress: 203.0.113.42, LogonType: 10, Status: 0x0
```

Все события нормализованы и имеют общий Src IP, имя пользователя и тип логона.

**Шаг 3. Выполнение корреляционного запроса и получение результата**

Запуск приведённого выше SPL-запроса даёт такие строки:

```text
_time                     src_ip         TargetUserName failures successes
2025-04-07 08:45          203.0.113.42   svc-backup      13        1
```

Результат удовлетворяет условиям `where`, поэтому поиск возвращает данные, и создаётся алерт.

**Шаг 4. Генерация алерта**

Создаётся JSON-запись алерта (иллюстративная структура):

```json
{
  "alert_id": "a7f3b2d4-181a-4c5e-b903-4e7a2f9c0b3f",
  "rule_name": "RDP Brute Force Detection",
  "severity": "High",
  "timestamp": "2025-04-07T08:50:00Z",
  "status": "Open",
  "description": "User svc-backup had 13 failed RDP logins from 203.0.113.42 within 5 minutes, followed by a successful login.",
  "mitre_technique": "T1110.001",
  "source": { "ip": "203.0.113.42", "user": "svc-backup" },
  "target": { "host": "RDP-SRV-01", "LogonType": 10 },
  "events_count": 14,
  "enrichments": { "src_ip_rep": "High risk", "src_ip_geo": "Unknown" }
}
```

Алерт появляется в консоли Splunk ES в очереди с severity High.

**Шаг 5. Действия аналитика L1**

Аналитик открывает алерт, видит сводку. Проверяет связанные события; IP `203.0.113.42` не принадлежит внутреннему диапазону и отсутствует в списке разрешённых. Учётная запись `svc-backup` является сервисной и согласно политикам не должна использоваться для интерактивного входа. Успешный вход произошёл сразу после серии отказов, что характерно для успешного подбора пароля. Наличие успешного входа указывает на высокую вероятность компрометации.

Аналитик повышает уровень инцидента до Critical, связывается с владельцем системы и эскалирует инцидент на L2 для немедленной изоляции хоста и сброса пароля. В журнале отмечает действия и оставляет обратную связь для правила: оно сработало верно.

**Ожидаемый вывод**

Сквозной пример демонстрирует, как сырые события после обработки нормализацией и временной агрегации преобразуются в осмысленный алерт благодаря корреляционному правилу, а специалист L1 на основе единого консолидированного представления способен быстро распознать реальную атаку и принять меры. Понимание всей цепочки «логи → корреляция → алерт → действия» критически важно для начинающего аналитика SOC.
